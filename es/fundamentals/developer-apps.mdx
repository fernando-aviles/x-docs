Las apps son contenedores para tus credenciales de API. Cada app tiene sus propias claves, tokens y configuración.

---

<div id="app-credentials">
  ## Credenciales de la app
</div>

Cuando creas una app, puedes generar estas credenciales:

| Credencial | Caso de uso |
|:-----------|:------------|
| **API Key & Secret** | Autenticarse mediante OAuth 1.0a. Se utiliza para firmar solicitudes o generar tokens de usuario. |
| **Access Token & Secret** | Realizar solicitudes en nombre de tu propia cuenta (OAuth 1.0a). |
| **Client ID & Secret** | Autenticarse mediante OAuth 2.0. Se utiliza para el flujo de código de autorización. |
| **Bearer Token** | Autenticación solo de la aplicación para endpoints de datos públicos. |

<Tip>
Elige **OAuth 2.0** para proyectos nuevos. Ofrece permisos de acceso granulares y es obligatorio para endpoints de X API v2 con contexto de usuario.
</Tip>

<div id="creating-an-app">
  ## Crear una app
</div>

<Steps>
  <Step title="Abre la Consola de Desarrollador">
    Ve a [console.x.com](https://console.x.com) e inicia sesión.
  </Step>
  <Step title="Haz clic en «Create App»">
    Introduce un nombre, una descripción y el caso de uso de tu app.
  </Step>
  <Step title="Genera credenciales">
    Después de crearla, genera las claves y tokens que necesites.
  </Step>
  <Step title="Almacena de forma segura">
    Guarda las credenciales de inmediato; solo se mostrarán una vez.
  </Step>
</Steps>

<div id="app-permissions-oauth-10a">
  ## Permisos de la app (OAuth 1.0a)
</div>

Las apps de OAuth 1.0a tienen tres niveles de permisos:

<Tabs>
  <Tab title="Solo lectura">
    - Ver publicaciones, usuarios y datos públicos
    - No puede publicar, dar "me gusta" ni modificar nada
    - No puede acceder a los Mensajes Directos
  </Tab>
  <Tab title="Lectura y escritura">
    - Todos los permisos de lectura
    - Publicar y eliminar publicaciones
    - Seguir y dejar de seguir usuarios
    - Dar "me gusta" y republicar
    - No puede acceder a los Mensajes Directos
  </Tab>
  <Tab title="Lectura, escritura y MD">
    - Todos los permisos de lectura y escritura
    - Enviar y leer Mensajes Directos
  </Tab>
</Tabs>

<Note>
Cambiar los permisos requiere que los usuarios reautoricen tu app para obtener nuevos tokens con el alcance actualizado.
</Note>

<div id="oauth-20-app-types">
  ## Tipos de aplicaciones OAuth 2.0
</div>

Al configurar OAuth 2.0, selecciona el tipo de aplicación:

| Tipo | Cliente | Caso de uso |
|:-----|:-------|:------------|
| **Aplicación web** | Confidencial | Aplicaciones del lado del servidor que pueden almacenar secretos de forma segura |
| **Aplicación automatizada / Bot** | Confidencial | Bots y servicios automatizados que se ejecutan en servidores |
| **Aplicación nativa** | Público | Aplicaciones móviles o de escritorio que no pueden almacenar secretos de forma segura |
| **Aplicación de una sola página** | Público | Aplicaciones JavaScript basadas en el navegador |

**Los clientes confidenciales** reciben un Client Secret. **Los clientes públicos** utilizan PKCE exclusivamente.

<div id="callback-urls">
  ## URLs de callback
</div>

Las URLs de callback (URIs de redireccionamiento) son obligatorias en los flujos de OAuth. Después de que un usuario autoriza tu aplicación, se le redirige a tu URL de callback con un código de autorización.

<div id="requirements">
  ### Requisitos
</div>

- Añade las URL de callback a la lista de permitidos de tu aplicación en la Consola de Desarrollador
- Las URL deben coincidir exactamente (incluida la barra diagonal final)
- Máximo de **10 URL de callback** por aplicación
- Usa `https://` en producción
- Para desarrollo local, usa `http://127.0.0.1` (no `localhost`)

<div id="disallowed-protocols">
  ### Protocolos no permitidos
</div>

Estos protocolos no se pueden utilizar: `javascript`, `data`, `file`, `ftp`, `mailto`, `telnet` y otros esquemas no estándar.

<Accordion title="Lista completa de protocolos no permitidos">
`vbscript`, `javascript`, `vbs`, `data`, `mocha`, `keyword`, `livescript`, `ftp`, `file`, `gopher`, `acrobat`, `callto`, `daap`, `itpc`, `itms`, `firefoxurl`, `hcp`, `ldap`, `mailto`, `mmst`, `mmsu`, `msbd`, `rtsp`, `mso-offdap`, `snews`, `news`, `nntp`, `outlook`, `stssync`, `rlogin`, `telnet`, `tn3270`, `shell`, `sip`
</Accordion>

<div id="automated-account-labels">
  ## Etiquetas de cuentas automatizadas
</div>

Si tu aplicación usa una cuenta de bot, puedes etiquetarla como automatizada:

1. Ve a la **Configuración** de tu cuenta de bot
2. Selecciona **Tu cuenta** → **Automatización**
3. Vincula tu cuenta de gestión

Esto genera confianza entre los usuarios y distingue tu bot del spam.

<div id="troubleshooting">
  ## Solución de problemas
</div>

<Accordion title="Error: URL de callback no aprobada">
Asegúrate de que la URL de callback coincida exactamente con la registrada en la Consola de Desarrollador, incluido el protocolo y cualquier barra inclinada final. Codifica la URL (URL encoding) cuando la pases como parámetro de consulta.
```json
{
  "errors": [{
    "code": 415,
    "message": "Callback URL not approved for this client application."
  }]
}
```
</Accordion>

<Accordion title="Aplicación suspendida">
Si tu aplicación aparece como suspendida, revisa tu correo electrónico para ver si recibiste una notificación del equipo de la plataforma de X. Usa el [Formulario de ayuda de la plataforma](https://help.x.com/forms/platform) para apelar.
</Accordion>

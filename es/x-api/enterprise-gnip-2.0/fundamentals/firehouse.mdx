> **Ten en cuenta**
>
> Hemos lanzado una nueva herramienta de cumplimiento para X API v2 llamada [batch compliance](/es/x-api/compliance/batch-compliance). Esta nueva herramienta permite cargar grandes conjuntos de datos de IDs de Publicación o de usuario para recuperar su estado de cumplimiento y determinar qué datos requieren acciones a fin de que tus conjuntos de datos se ajusten a las normas de cumplimiento.

> Además, tanto batch compliance como el firehose de cumplimiento se han actualizado para admitir ediciones de Publicaciones. Para el firehose de cumplimiento, se añadió un nuevo evento `tweet_edit`. Consulta la documentación de [Objetos de datos de cumplimiento](/es/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects) para más detalles. Obtén más información sobre cómo funcionan los metadatos de las Publicaciones editadas en la página [Fundamentos de Publicaciones editadas](/es/x-api/fundamentals/edit-posts).

<div id="overview">
  ## Descripción general
</div>

`Enterprise`

Uno de los valores fundamentales de X es defender y respetar la voz de los usuarios. Esto incluye respetar sus expectativas e intención cuando eliminan, modifican o editan el contenido que deciden compartir en X. Creemos que esto es de importancia crítica para la salud a largo plazo de una de las mayores plataformas públicas de información en tiempo real del mundo. X pone el control en manos de sus usuarios, brindando a las personas la capacidad de gestionar su propia experiencia en X. Creemos que las empresas que reciben datos de X tienen la responsabilidad de respetar las expectativas y la intención de los usuarios finales.

Para obtener más información sobre los tipos de eventos de cumplimiento posibles en la plataforma X, consulta nuestro artículo, [Honoring User Intent on X](/es/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter).

Cualquier desarrollador o empresa que consuma datos de X a través de una API tiene la obligación de hacer todos los esfuerzos razonables para respetar los cambios en el contenido de los usuarios. Esta obligación se extiende a eventos de usuario como eliminaciones, modificaciones y cambios en las opciones para compartir (por ejemplo, contenido que pasa a estar protegido o retenido). Esto también incluye cuando los usuarios editan sus Publicaciones. Consulta la redacción específica en la [Developer Policy](https://developer.x.com/en/developer-terms/policy) y/o en tu Acuerdo de datos de X para comprender cómo esta obligación afecta tu uso de datos de X.

X ofrece las siguientes soluciones que proporcionan información sobre estos eventos de cumplimiento de usuario y sobre si una Publicación o un Usuario específico está disponible públicamente o no. A continuación se presenta una breve descripción general de las soluciones y de sus patrones de integración generales:

<div id="get-statuseslookup-and-get-userslookup">
  #### GET statuses/lookup y GET users/lookup
</div>

* Formato: API REST. Consulta: [GET statuses/lookup](https://developer.x.com/en/docs/x-api/v1/tweets/post-and-engage/api-reference/get-statuses-lookup) y [GET users/lookup](https://developer.x.com/en/docs/x-api/v1/accounts-and-users/follow-search-get-users/api-reference/get-users-lookup).

* Estos endpoints siempre devuelven la versión más reciente de cualquier Publicación editada. Todos los objetos de Publicación correspondientes a publicaciones creadas después de que se introdujo la función de edición incluirán metadatos de edición de Publicación. Esto se aplica incluso a las publicaciones que no se hayan editado.

* Para todas las Publicaciones, las solicitudes efectuadas más de 30 minutos después de su creación representarán el estado final de todas las publicaciones.

* Proporcionan información sobre la disponibilidad de Publicaciones o Usuarios específicos definidos por el cliente en la solicitud de API.

* Se pueden usar para comprobaciones puntuales ad hoc sobre el estado de disponibilidad actual de un grupo concreto de publicaciones o usuarios.

* Son ideales para clientes que necesitan una forma de comprobar el estado actual de una publicación o usuario específico en un momento dado.

* Estas API proporcionan un mecanismo útil que pueden utilizar los clientes que necesiten comprobar la disponibilidad de una pieza de contenido, por ejemplo cuando:
  1. Muestran publicaciones
  2. Interactúan con una(s) publicación(es) o usuario(s) de forma 1:1
  3. Distribuyen contenido de X a un tercero mediante una descarga de archivos autorizada
  4. Almacenan publicaciones durante períodos prolongados de tiempo

<div id="compliance-firehose-enterprise-only">
  #### Compliance Firehose (solo para empresas)
</div>

* Formato: Streaming API. Consulta: [Compliance Firehose](/es/x-api/enterprise-gnip-2.0/fundamentals/firehouse#api-reference).
* Proporciona un flujo en tiempo real de [actividades de cumplimiento](/es/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects) en X. Estas actividades incluyen la edición de Publicaciones. 
* Puede utilizarse para mantener el estado de cumplimiento en un conjunto de datos almacenados a medida que se producen nuevos eventos de cumplimiento en la plataforma.
* Ideal para clientes que consumen y almacenan grandes volúmenes de datos de X durante períodos prolongados.

<div id="recommendations-best-practices">
  #### **Recomendaciones y mejores prácticas**
</div>

* **Cree esquemas de almacenamiento de datos que almacenen el ID numérico de la Publicación y el ID de usuario**: Los mensajes de usuario requieren que se tomen medidas sobre todas las Publicaciones de ese usuario. Por lo tanto, dado que todos los mensajes de cumplimiento se entregan solo por ID numérico, es importante diseñar esquemas de almacenamiento que mantengan la relación entre la Publicación y el usuario basándose en IDs numéricos. Los consumidores de datos deberán supervisar los eventos de cumplimiento tanto por ID de la Publicación como por ID de usuario y poder actualizar el almacén de datos local de forma adecuada.

* **Cree esquemas que contemplen todos los estados de cumplimiento**: Según cómo se gestionen las actividades de cumplimiento en las distintas aplicaciones, puede ser necesario agregar otros metadatos al almacén de datos. Por ejemplo, los consumidores de datos pueden decidir agregar metadatos a una base de datos existente para facilitar la restricción de la visualización del contenido en países afectados por un mensaje status&#95;withheld.

* **Gestión de eliminaciones de Retweet**: Los Retweets son un tipo especial de Publicación en la que el mensaje original está anidado en un objeto dentro del Retweet. En este caso, hay dos IDs de Publicación referenciados en un Retweet: el ID del Retweet y el ID del mensaje original (incluido en el objeto anidado). Cuando se elimina un mensaje original, se emite un mensaje de eliminación de Publicación para el ID original. Los eventos de eliminación de Publicaciones normalmente desencadenan eventos de eliminación para todos los Retweets. Sin embargo, en algunos casos no se envían todos y los sistemas cliente deben tolerar eliminaciones de Retweets incompletas. La eliminación del ID original debería ser suficiente para eliminar todos los Retweets posteriores. Es una práctica recomendada hacer referencia al ID de la Publicación original al almacenar Retweets y eliminar todos los Retweets referenciados cuando se reciban eventos de eliminación de Publicaciones.

<div id="compliance-firehose-api">
  #### **Compliance Firehose API**
</div>

Los posibles tipos de eventos de cumplimiento incluyen eventos de publicaciones (o «status») y eventos de usuarios, para los cuales se describen varios tipos a continuación.  

Ten en cuenta lo siguiente:

* Consulta más información sobre los estados de usuario [aquí](https://support.x.com/articles/14016) y nuestra política para desarrolladores sobre publicaciones eliminadas [aquí](https://dev.x.com/overview/terms/policy#3.Update_Respect_Users_Control_and_Privacy).
* El Compliance Firehose se ha actualizado para proporcionar eventos &#39;tweet&#95;edit&#39;. 
* Varios eventos de eliminación, protección y suspensión de usuario no son necesariamente permanentes y pueden alternar entre estados indefinidamente. Estos incluyen: user&#95;delete, user&#95;undelete, user&#95;protect, user&#95;unprotect y user&#95;suspend, user&#95;unsuspend.
* Los user&#95;deletes son seguidos por status&#95;deletes 30 días después solo si el usuario no ha elegido realizar un user&#95;undelete de su cuenta. Es posible que un user&#95;delete sea revertido por el usuario y que, por tanto, las eliminaciones de todas sus publicaciones 30 días después no se produzcan.
* user&#95;suspend es una acción que permanece vigente a menos que el usuario esté sujeto a un evento user&#95;unsuspend. Estos no están sujetos a ningún cambio en un período de 30 días.

Consulta la columna ‘Recommended Action’ para entender cómo procesar cada tipo de evento a fin de respetar la privacidad y la intención del usuario final.

| Original Message Type | Object | Permanent (Yes/No) | Recommended Action |
| :--- | :--- | :--- | :--- |
| delete | Status | Yes | Elimina la publicación asociada. |
| status&#95;withheld | Status | Yes | Suprime la publicación asociada en los países específicos enumerados en el mensaje status&#95;withheld. |
| drop | Status | No  | Quita la publicación de la vista pública. |
| undrop | Status | No  | El Status puede mostrarse de nuevo y tratarse como público. |
| tweet&#95;edit | Status | Yes | Respeta y, cuando corresponda, muestra la nueva edición. |
| user&#95;delete | User | No  | Suprime o elimina todas las publicaciones del usuario asociado. |
| user&#95;undelete | User | No  | Todas las publicaciones del usuario asociado pueden mostrarse de nuevo y tratarse como públicas. |
| user&#95;protect | User | No  | Suprime o elimina todas las publicaciones del usuario asociado. |
| user&#95;unprotect | User | No  | Todas las publicaciones del usuario asociado pueden mostrarse de nuevo y tratarse como públicas. |
| user&#95;suspend | User | No  | Suprime o elimina todas las publicaciones del usuario asociado. |
| user&#95;unsuspend | User | No  | Todas las publicaciones del usuario asociado pueden mostrarse de nuevo y tratarse como públicas. |
| scrub&#95;geo | User | Yes | Elimina todos los geodatos proporcionados por X para todas las publicaciones del usuario anteriores a la publicación especificada en el mensaje scrub&#95;geo. Ten en cuenta que las publicaciones posteriores de un usuario pueden contener geodatos que pueden usarse. |
| user&#95;withheld | User | Yes | Suprime las publicaciones del usuario asociado en los países específicos enumerados en el mensaje user&#95;withheld. |
| delete | Favorite | Yes | Elimina el like/favorito asociado. |

<div id="integrating-compliance-firehose">
  ### integrating Compliance Firehose
</div>

Compliance Firehose es una API de transmisión en tiempo real que entrega eventos de cumplimiento que ocurren en la plataforma X. Para comprender los eventos de cumplimiento y cómo se generan en X, consulta nuestro artículo [Honoring User Intent on X](/es/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter).

Es importante tener en cuenta que los eventos de Publicación y de Usuario se entregan de forma independiente y que cada uno debe procesarse de forma independiente (es decir, la eliminación de una Publicación no implica un evento de Usuario y viceversa). Algunos eventos de Usuario no son necesariamente permanentes y pueden alternar entre estados de forma indefinida. Estos incluyen: user&#95;delete, user&#95;undelete, user&#95;protect, user&#95;unprotect y user&#95;suspend, user&#95;unsuspend.

Los user&#95;deletes son seguidos por status&#95;deletes 30 días después solo si el usuario no ha optado por user&#95;undelete su cuenta. Es posible que un user&#95;delete sea revertido por el usuario y que las eliminaciones de todas sus Publicaciones 30 días después no se produzcan.

User&#95;suspend es una acción que permanece vigente a menos que el usuario sea objeto de un evento user&#95;unsuspend. Estos no están sujetos a ningún cambio asociado a un periodo de 30 días.

Nunca es adecuado mostrar directamente eventos de cumplimiento a los usuarios de tu software ni incorporarlos de otro modo en tus productos o experiencias para clientes. Están destinados únicamente a mantener el cumplimiento y respetar las acciones de los usuarios de X.

<div id="integrating-with-the-compliance-firehose">
  #### **Integrating with the Compliance Firehose**
</div>

Para integrar el Compliance Firehose en tu sistema, deberás crear una integración que pueda hacer lo siguiente:

1. Establecer una conexión de streaming con cada partición de la API de streaming del Compliance Firehose
2. Manejar altos volúmenes de datos: desacoplar la ingesta del stream del procesamiento adicional utilizando procesos asíncronos
3. Volver a conectarte automáticamente a las particiones del stream cuando se desconecten por cualquier motivo
4. Procesar los eventos de cumplimiento que sean relevantes para los datos de Publicación y Usuario que hayas almacenado, según las indicaciones anteriores

<div id="honoring-user-intent-on-twitter">
  ### Respetar la intención del usuario en Twitter
</div>

Creemos que respetar la privacidad y la intención de los usuarios de X es fundamental para la salud a largo plazo de una de las plataformas públicas de información en tiempo real más grandes del mundo. X pone los controles de privacidad en manos de sus usuarios, dándoles la capacidad de controlar su propia experiencia en X. Como clientes empresariales de los datos de X, tenemos una responsabilidad colectiva de respetar la privacidad y las acciones de los usuarios finales para mantener este entorno de confianza y respeto.

Existen diversas acciones que pueden aplicarse a las Publicaciones y a las cuentas de usuario que afectan la forma en que se muestran en la plataforma. Las acciones que afectan a la privacidad y la intención se definen tanto a nivel de Status (Publicación) como de usuario. Estas acciones incluyen:

<div id="user">
  #### Usuario
</div>

| Acción | Descripción |
| :--- | :--- |
| Proteger cuenta | Un usuario de X puede proteger o desproteger su cuenta en cualquier momento. Las cuentas protegidas requieren la aprobación manual por parte del usuario de cada persona a la que se le permite ver las Publicaciones de su cuenta.   <br />Para obtener más información, consulta [Publicaciones públicas y protegidas](https://support.x.com/articles/14016-about-public-and-protected-tweets). |
| Eliminar cuenta | Un usuario de X puede decidir eliminar su cuenta y todos los mensajes de estado asociados en cualquier momento. X conserva la información de la cuenta durante 30 días después de la eliminación en caso de que el usuario decida recuperarla y, de forma efectiva, reactivar su cuenta. |
| Borrar datos de ubicación | Un usuario de X puede eliminar todos los datos de ubicación de Publicaciones anteriores en cualquier momento. Esto se conoce como “scrub geo”. |
| Suspender cuenta | X se reserva el derecho de suspender cuentas que infrinjan las Reglas de X o si se sospecha que una cuenta ha sido hackeada o comprometida. Solo X puede revertir una suspensión de cuenta (levantar la suspensión). |
| Retener cuenta | X se reserva el derecho de retener de forma reactiva el acceso a cierto contenido en un país específico de vez en cuando. Solo X puede levantar la retención de una cuenta.   <br />Para obtener más información, consulta [Contenido retenido por país](https://support.x.com/articles/20169222-country-withheld-content). |

<div id="status">
  #### Estado
</div>

| Acción | Descripción |
| :--- | :--- |
| Eliminar estado | Un usuario de X puede eliminar un estado en cualquier momento. Los estados eliminados no se pueden revertir y se eliminan de forma permanente. |
| Retener estado | X se reserva el derecho de retirar de forma reactiva el acceso a cierto contenido en un país específico en determinados momentos. Solo X puede levantar la retención de un estado.   <br />Para obtener más información, consulta [Contenido retenido por país](https://support.x.com/articles/20169222-country-withheld-content). |

<div id="keeping-track-of-user-and-status-changes">
  #### Seguimiento de cambios en usuarios y estados
</div>

El estado de un User o un Status puede cambiar en cualquier momento debido a una de las acciones anteriores, y esto afecta la forma en que se espera que los consumidores de datos de X gestionen la disponibilidad y la privacidad de todo el contenido asociado. Cuando se producen estas acciones, se envía un mensaje de cumplimiento asociado que indica que el estado de un Status o un User ha cambiado.

Las siguientes respuestas pueden ser retornadas por la API para estas solicitudes. La mayoría de los códigos de error se devuelven con una cadena de texto con información adicional en el cuerpo. Para respuestas distintas de 200, los clientes deben intentar volver a conectarse.

| Status | Text | Definition |
| :--- | :--- | :--- |
| 200 | Success | La conexión se abrió correctamente y se enviarán nuevas actividades a medida que vayan llegando. |
| 401 | Unauthorized | La autenticación HTTP falló debido a credenciales no válidas. Inicia sesión en console.gnip.com con tus credenciales para asegurarte de que las estás usando correctamente en tu solicitud. |
| 406 | Not Acceptable | Generalmente, esto ocurre cuando tu cliente no incluye correctamente los encabezados para aceptar la codificación gzip del flujo, pero también puede ocurrir en otras circunstancias. Contendrá un mensaje JSON similar a &quot;Esta conexión requiere compresión. Para habilitar la compresión, envía un encabezado &#39;Accept-Encoding: gzip&#39; en tu solicitud y prepárate para descomprimir el flujo a medida que se lea en el lado del cliente.&quot; |
| 429 | Rate Limited | Tu aplicación ha excedido el límite de solicitudes de conexión. |
| 503 | Service Unavailable | Problema del servidor de Twitter. Vuelve a conectarte utilizando un patrón de backoff exponencial. Si no se ha publicado ningún aviso sobre este problema en la [X API Status Page](https://api.twitterstat.us/), ponte en contacto con el soporte. |

<div id="other-recommendations-best-practices">
  #### Otras recomendaciones y mejores prácticas
</div>

* **Cree esquemas de almacenamiento de datos que almacenen el ID numérico del Tuit y el ID de usuario**: Los mensajes de usuario requieren que se actúe sobre todos los Tuits de ese usuario. Por lo tanto, dado que todos los mensajes de cumplimiento se entregan únicamente por ID numérico, es importante diseñar esquemas de almacenamiento que mantengan la relación entre Tuit y usuario a partir de IDs numéricos. Los consumidores de datos deberán supervisar los eventos de cumplimiento tanto por ID de Tuit como por ID de usuario y poder actualizar el almacén de datos local de forma adecuada.

* **Cree esquemas que aborden todos los estados de cumplimiento**: Dependiendo de cómo se gestionen las actividades de cumplimiento en varias aplicaciones, puede ser necesario añadir otros metadatos al almacén de datos. Por ejemplo, los consumidores de datos pueden decidir añadir metadatos a una base de datos existente para facilitar la restricción de la visualización de contenido en países afectados por un mensaje status&#95;withheld.

* **Gestión de eliminaciones de Retuits**: Los Retuits son un tipo especial de Tuit en el que el mensaje original está anidado en un objeto dentro del Retuit. En este caso, hay dos IDs de Tuit referenciados en un Retuit: el ID del Retuit y el ID del mensaje original (incluido en el objeto anidado). Cuando se elimina un mensaje original, se emite un mensaje de eliminación de Tuit para el ID original. NO se emiten mensajes de eliminación posteriores para todos los Retuits. La eliminación del ID original debería ser suficiente para eliminar todos los Retuits posteriores.

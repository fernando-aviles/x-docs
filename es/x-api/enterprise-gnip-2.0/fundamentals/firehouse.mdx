> **Ten en cuenta**
>
> Hemos lanzado una nueva herramienta de compliance para X API v2 llamada [batch compliance](/es/x-api/compliance/batch-compliance). Esta nueva herramienta te permite cargar grandes conjuntos de datos con IDs de Publicación o de usuario para recuperar su estado de cumplimiento normativo y así determinar qué datos requieren alguna acción para que tus conjuntos de datos cumplan con las normativas.

> Además, tanto batch compliance como compliance firehose se han actualizado para admitir ediciones de Publicaciones. Para compliance firehose, se añadió un nuevo evento `tweet_edit`. Consulta la documentación de [Compliance Data Objects](/es/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects) para obtener más detalles. Obtén más información sobre cómo funcionan los metadatos de Edit Post en la página [Edit Posts fundamentals](/es/x-api/fundamentals/edit-posts).

<div id="overview">
  ## Descripción general
</div>

`Enterprise`

Uno de los valores fundamentales de X es defender y respetar la voz de los usuarios. Esto incluye respetar sus expectativas e intenciones cuando eliminan, modifican o editan el contenido que deciden compartir en X. Creemos que esto es de importancia crítica para la salud a largo plazo de una de las plataformas de información pública en tiempo real más grandes del mundo. X pone controles en manos de sus usuarios, brindando a las personas la posibilidad de controlar su propia experiencia en X. Creemos que las empresas que consumen datos de X tienen la responsabilidad de respetar las expectativas e intenciones de los usuarios finales.

Para obtener más información sobre los tipos de eventos de cumplimiento que son posibles en la plataforma X, consulta nuestro artículo, [Honoring User Intent on X](/es/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter).

Cualquier desarrollador o empresa que consuma datos de X a través de una API tiene la obligación de hacer todos los esfuerzos razonables para respetar los cambios en el contenido de los usuarios. Esta obligación se extiende a eventos de usuario tales como eliminaciones, modificaciones y cambios en las opciones para compartir (por ejemplo, cuando el contenido pasa a estar protegido o retenido). Esto también incluye los casos en que los usuarios editan sus Publicaciones. Consulta el texto específico de la [Developer Policy](https://developer.x.com/en/developer-terms/policy) y/o de tu X Data Agreement para entender cómo esta obligación afecta tu uso de los datos de X.

X ofrece las siguientes soluciones que proporcionan información sobre estos eventos de cumplimiento de los usuarios y sobre si una Publicación o Usuario específico está disponible públicamente o no. A continuación se presenta una breve descripción general de las soluciones y sus patrones generales de integración:

<div id="get-statuseslookup-and-get-userslookup">
  #### GET statuses/lookup y GET users/lookup
</div>

* Formato: API REST. Ver: [GET statuses/lookup](https://developer.x.com/en/docs/x-api/v1/tweets/post-and-engage/api-reference/get-statuses-lookup) y [GET users/lookup](https://developer.x.com/en/docs/x-api/v1/accounts-and-users/follow-search-get-users/api-reference/get-users-lookup).

* Estos endpoints siempre devuelven la versión más reciente de cualquier edición de la Publicación. Todos los objetos de tipo Publicación que describen Publicaciones creadas después de que se introdujo la función de edición incluirán metadatos de edición de Publicación. Esto es cierto incluso para las Publicaciones que no fueron editadas.

* Para todas las Publicaciones, las solicitudes de Publicaciones realizadas más de 30 minutos después de su creación representarán el estado final de todas las Publicaciones.

* Proporcionan información de disponibilidad para Publicaciones o Usuarios específicos definidos por el solicitante como parte de la solicitud a la API.

* Pueden utilizarse para comprobaciones puntuales ad hoc del estado actual de disponibilidad de un grupo específico de Publicaciones o Usuarios.

* Ideales para clientes que necesitan una forma de comprobar el estado actual de una Publicación o Usuario específico en un momento determinado.

* Estas APIs proporcionan un mecanismo útil que puede utilizarse por clientes que necesitan comprobar la disponibilidad de una pieza de Contenido, por ejemplo cuando:
  1. Se muestran Publicaciones
  2. Se interactúa con una o varias Publicaciones o Usuarios de forma 1:1
  3. Se distribuye Contenido de X a un tercero mediante una descarga de archivo permitida
  4. Se almacenan Publicaciones durante períodos prolongados

<div id="compliance-firehose-enterprise-only">
  #### Compliance Firehose (solo para Enterprise)
</div>

* Formato: API de streaming. Consulte: [Compliance Firehose](/es/x-api/enterprise-gnip-2.0/fundamentals/firehouse#api-reference).
* Proporciona un flujo en tiempo real de [actividades de cumplimiento](/es/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects) en X. Estas actividades incluyen cuando se editan Publicaciones. 
* Puede utilizarse para mantener el estado de cumplimiento en un conjunto de datos almacenados a medida que se producen nuevos eventos de cumplimiento en la plataforma.
* Ideal para clientes que consumen y almacenan grandes cantidades de datos de X durante períodos prolongados.

<div id="recommendations-best-practices">
  #### **Recomendaciones y mejores prácticas**
</div>

* **Cree esquemas de almacenamiento de datos que guarden el ID numérico de la Publicación y el ID numérico de usuario**: Los mensajes de usuario requieren que se actúe sobre todas las Publicaciones de ese usuario. Por lo tanto, dado que todos los mensajes de cumplimiento se entregan solo por ID numérico, es importante diseñar esquemas de almacenamiento que mantengan la relación entre la Publicación y el usuario basándose en IDs numéricos. Los consumidores de datos deberán supervisar los eventos de cumplimiento tanto por ID de la Publicación como por ID de usuario y poder actualizar el almacén de datos local de forma adecuada.

* **Cree esquemas que aborden todos los estados de cumplimiento**: Según cómo se vayan a gestionar las actividades de cumplimiento en las distintas aplicaciones, puede ser necesario añadir otros metadatos al almacén de datos. Por ejemplo, los consumidores de datos pueden decidir añadir metadatos a una base de datos existente para facilitar la restricción de la visualización de contenido en países afectados por un mensaje status&#95;withheld.

* **Gestión de eliminaciones de Retuits**: Los Retuits son un tipo especial de Publicación en la que el mensaje original está anidado en un objeto dentro del Retuit. En este caso, hay dos IDs de Publicación referenciados en un Retuit: el ID del Retuit y el ID del mensaje original (incluido en el objeto anidado). Cuando se elimina un mensaje original, se emite un mensaje de eliminación de Publicación para el ID original. Los eventos de eliminación de Publicación normalmente desencadenan eventos de eliminación para todos los Retuits. Sin embargo, en algunos casos no se envían todos y los sistemas cliente deben tolerar eliminaciones de Retuits incompletas. La eliminación del ID original debería ser suficiente para eliminar todos los Retuits posteriores. Es una buena práctica hacer referencia al ID de la Publicación original al almacenar Retuits y eliminar todos los Retuits referenciados al recibir eventos de eliminación de Publicación.

<div id="compliance-firehose-api">
  #### **Compliance Firehose API**
</div>

Los posibles tipos de eventos de cumplimiento incluyen eventos de Publicación (o «status») y eventos de Usuario, para los cuales hay varios tipos descritos a continuación.  

Ten en cuenta lo siguiente:

* Obtén más información sobre los estados de usuario [aquí](https://support.x.com/articles/14016) y nuestra política para desarrolladores sobre Publicaciones eliminadas [aquí](https://dev.x.com/overview/terms/policy#3.Update_Respect_Users_Control_and_Privacy).
* La Compliance Firehose API se ha actualizado para proporcionar eventos `tweet_edit`. 
* Varios eventos de eliminación, protección y suspensión de Usuario no son necesariamente permanentes y pueden alternar entre estados indefinidamente. Estos incluyen: user&#95;delete, user&#95;undelete, user&#95;protect, user&#95;unprotect y user&#95;suspend, user&#95;unsuspend.
* Los eventos user&#95;delete van seguidos de status&#95;deletes 30 días después solo si el usuario no ha optado por user&#95;undelete su cuenta. Es posible que un user&#95;delete sea revertido por el usuario y que las eliminaciones de todas sus Publicaciones 30 días después no se produzcan.
* user&#95;suspend es una acción que permanece vigente a menos que el usuario sea objeto de un evento user&#95;unsuspend. Estos no están sujetos a ningún cambio en un período de 30 días.

Consulta la columna «Recommended Action» para saber cómo procesar cada tipo de evento con el fin de respetar la privacidad y la intención del usuario final.

| Original Message Type | Object | Permanent (Sí/No) | Recommended Action |
| :--- | :--- | :--- | :--- |
| delete | Status | Yes | Elimina la Publicación asociada. |
| status&#95;withheld | Status | Yes | Suprime la Publicación asociada en los países específicos indicados en el mensaje status&#95;withheld. |
| drop | Status | No  | Quita la Publicación de la vista pública. |
| undrop | Status | No  | La Publicación puede mostrarse de nuevo y tratarse como pública. |
| tweet&#95;edit | Status | Yes | Respeta y, cuando corresponda, muestra la nueva edición. |
| user&#95;delete | User | No  | Suprime o elimina todas las Publicaciones del usuario asociado. |
| user&#95;undelete | User | No  | Todas las Publicaciones del usuario asociado pueden mostrarse de nuevo y tratarse como públicas. |
| user&#95;protect | User | No  | Suprime o elimina todas las Publicaciones del usuario asociado. |
| user&#95;unprotect | User | No  | Todas las Publicaciones del usuario asociado pueden mostrarse de nuevo y tratarse como públicas. |
| user&#95;suspend | User | No  | Suprime o elimina todas las Publicaciones del usuario asociado. |
| user&#95;unsuspend | User | No  | Todas las Publicaciones del usuario asociado pueden mostrarse de nuevo y tratarse como públicas. |
| scrub&#95;geo | User | Yes | Elimina todos los datos de geolocalización proporcionados por X para todas las Publicaciones del usuario anteriores a la Publicación especificada en el mensaje scrub&#95;geomessage. Ten en cuenta que las Publicaciones posteriores de un usuario pueden contener datos de geolocalización que pueden utilizarse. |
| user&#95;withheld | User | Yes | Suprime las Publicaciones del usuario asociado en los países específicos indicados en el mensaje user&#95;withheld. |
| delete | Favorite | Yes | Elimina el «like»/favorito asociado. |

<div id="integrating-compliance-firehose">
  ### Integración con Compliance Firehose
</div>

Compliance Firehose es una API de transmisión en tiempo real que entrega eventos de cumplimiento que ocurren en la plataforma X. Para comprender los eventos de cumplimiento y cómo se generan en X, consulta nuestro artículo [Honrando la intención del usuario en X](/es/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter).

Es importante tener en cuenta que los eventos de Publicación y de Usuario se entregan de forma independiente y que cada uno debe procesarse de manera independiente (es decir, la eliminación de una Publicación no implica un evento de Usuario y viceversa). Varios eventos de Usuario no son necesariamente permanentes y pueden alternar entre estados indefinidamente. Estos incluyen: user&#95;delete, user&#95;undelete, user&#95;protect, user&#95;unprotect y user&#95;suspend, user&#95;unsuspend.

Los user&#95;delete van seguidos de status&#95;delete 30 días después solo si el usuario no ha elegido aplicar user&#95;undelete a su cuenta. Es posible que un user&#95;delete sea revertido por el usuario y que las eliminaciones de todas sus Publicaciones 30 días después no se produzcan.

user&#95;suspend es una acción que permanece vigente a menos que el usuario esté sujeto a un evento user&#95;unsuspend. Estos no están sujetos a ningún cambio en un período de 30 días.

Nunca es adecuado mostrar los eventos de cumplimiento directamente a los usuarios de tu software ni incorporarlos de ningún otro modo en tus productos o experiencias de cliente. Están destinados únicamente a mantener el cumplimiento y respetar las acciones de los usuarios de X.

<div id="integrating-with-the-compliance-firehose">
  #### **Integrating with the Compliance Firehose**
</div>

Para integrar Compliance Firehose en tu sistema, deberás crear una integración que pueda hacer lo siguiente:

1. Establecer una conexión de streaming con cada partición de la API de streaming de Compliance Firehose
2. Gestionar grandes volúmenes de data: desacoplar la ingesta del stream del procesamiento adicional utilizando procesos asíncronos
3. Restablecer automáticamente la conexión con las particiones del stream cuando se interrumpa por cualquier motivo
4. Procesar los eventos de cumplimiento que sean relevantes para la data de Publicaciones y de usuarios que hayas almacenado, de acuerdo con la guía presentada arriba

<div id="honoring-user-intent-on-twitter">
  ### Respetar la intención del usuario en Twitter
</div>

Creemos que respetar la privacidad y la intención de los usuarios de X es fundamental para la salud a largo plazo de una de las plataformas de información pública y en tiempo real más grandes del mundo. X pone los controles de privacidad en manos de sus usuarios, dando a las personas la capacidad de controlar su propia experiencia en X. Como empresas que utilizan los datos de X, tenemos la responsabilidad colectiva de respetar la privacidad y las acciones de los usuarios finales para mantener este entorno de confianza y respeto.

Hay una variedad de situaciones que pueden afectar a las publicaciones y a las cuentas de usuario, influyendo en cómo se muestran en la plataforma. Las acciones que afectan la privacidad y la intención se definen tanto a nivel de Status (Publicación) como de Usuario. Estas acciones incluyen:

<div id="user">
  #### Usuario
</div>

| Acción | Descripción |
| :--- | :--- |
| Proteger cuenta | Un usuario de X puede proteger o desproteger su cuenta en cualquier momento. Las cuentas protegidas requieren la aprobación manual del usuario para cada persona a la que se le permite ver las Publicaciones de su cuenta.   <br />Para obtener más información, consulta [Acerca de las Publicaciones públicas y protegidas](https://support.x.com/articles/14016-about-public-and-protected-tweets). |
| Eliminar cuenta | Un usuario de X puede decidir eliminar su cuenta y todos los mensajes de estado asociados en cualquier momento. X conserva la información de la cuenta durante 30 días después de la eliminación en caso de que el usuario decida restaurarla y así reactivar su cuenta. |
| Eliminar datos de ubicación | Un usuario de X puede eliminar todos los datos de ubicación de Publicaciones anteriores en cualquier momento. Esto se conoce como “scrub geo”. |
| Suspender cuenta | X se reserva el derecho de suspender cuentas que infrinjan las Reglas de X o si se sospecha que una cuenta ha sido hackeada o comprometida. Las suspensiones de cuentas solo pueden revertirse (anular la suspensión) por X. |
| Retener cuenta | X se reserva el derecho de retener de forma reactiva el acceso a cierto contenido en un país específico de vez en cuando. Una cuenta retenida solo puede ser restablecida por X.   <br />Para obtener más información, consulta [Contenido retenido por país](https://support.x.com/articles/20169222-country-withheld-content). |

<div id="status">
  #### Estado
</div>

| Acción | Descripción |
| :--- | :--- |
| Eliminar estado | Un usuario de X puede eliminar un estado en cualquier momento. Los estados eliminados no se pueden restaurar y se eliminan de forma permanente. |
| Retener estado | X se reserva el derecho de retener de manera reactiva el acceso a cierto contenido en un país específico de vez en cuando. Solo X puede dejar de retener un estado.  <br />Para obtener más información, consulta [Country Withheld Content](https://support.x.com/articles/20169222-country-withheld-content). |

<div id="keeping-track-of-user-and-status-changes">
  #### Seguimiento de los cambios de User y Status
</div>

El estado de un User o Status puede cambiar en cualquier momento debido a una de las acciones anteriores, y esto afecta la forma en que se espera que los consumidores de datos de X gestionen la disponibilidad y la privacidad de todo el contenido asociado. Cuando se producen estas acciones, se envía un mensaje de cumplimiento correspondiente que indica que el estado de un Status o User ha cambiado.

<div id="other-recommendations-best-practices">
  #### Otras recomendaciones y buenas prácticas
</div>

* **Cree esquemas de almacenamiento de datos que guarden el ID numérico del Tuit y el ID de usuario**: Los mensajes de usuario requieren que se tomen medidas sobre todos los Tuits de ese usuario. Por lo tanto, dado que todos los mensajes de cumplimiento se entregan únicamente mediante ID numéricos, es importante diseñar esquemas de almacenamiento que mantengan la relación entre el Tuit y el usuario basándose en IDs numéricos. Los consumidores de datos deberán supervisar los eventos de cumplimiento tanto por ID de Tuit como por ID de usuario y poder actualizar el almacén de datos local de forma adecuada.

* **Cree esquemas que aborden todos los estados de cumplimiento**: Dependiendo de cómo se gestionen las actividades de cumplimiento en diversas aplicaciones, puede ser obligatorio añadir otros metadatos al almacén de datos. Por ejemplo, los consumidores de datos pueden decidir añadir metadatos a una base de datos existente para facilitar la restricción de la visualización de contenido en países afectados por un mensaje `status_withheld`.

* **Gestión de eliminaciones de Retuits**: Los Retuits son un tipo especial de Tuit en el que el mensaje original está anidado en un objeto dentro del Retuit. En este caso, hay dos IDs de Tuit referenciados en un Retuit: el ID del Retuit y el ID del mensaje original (incluido en el objeto anidado). Cuando se elimina un mensaje original, se emite un mensaje de eliminación de Tuit para el ID original. No se emiten mensajes de eliminación posteriores para todos los Retuits. La eliminación del ID original debería ser suficiente para eliminar todos los Retuits posteriores.

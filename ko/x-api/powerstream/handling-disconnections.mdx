<div id="what-is-a-disconnection">
  ## 연결 해제란 무엇인가요?
</div>

스트리밍 API에 연결한다는 것은 매우 오래 지속되는 HTTPS 요청을 보내고, 응답을 순차적으로 파싱하는 것을 의미합니다. powerstream 엔드포인트에 연결할 때는 HTTPS 요청을 생성한 뒤, 가능한 한 오래 결과 스트림을 계속 읽어들여야 합니다. 서버 측 오류, 과도한 클라이언트 측 지연, 네트워크 문제, 정기적인 서버 유지보수, 중복 로그인과 같은 경우를 제외하고는, 당사 서버는 연결을 무기한 유지합니다. 스트리밍 엔드포인트에 대한 연결에서는 연결이 끊어지는 일이 발생할 가능성이 높으며 이는 예상해야 하며, 이를 대비해 재연결 로직을 구현해야 합니다.

<div id="why-a-streaming-connection-might-be-disconnected">
  ## 스트리밍 연결이 끊어질 수 있는 이유
</div>

스트림은 여러 이유로 끊어질 수 있습니다. 스트림에서 반환된 오류 메시지를 확인해 실패 원인을 파악하세요. 연결이 끊어질 수 있는 이유는 다음과 같습니다:

* 잘못된 토큰 사용 또는 잘못된 인증 방식 사용과 같은 인증 오류가 발생한 경우
* X 측의 스트리밍 서버가 재시작된 경우. 이는 보통 코드 배포와 관련이 있으며, 일반적으로 이를 예상하고 그에 맞게 설계해야 합니다.
* 클라이언트가 스트림이 전달하는 포스트 양을 따라가지 못하거나 데이터를 너무 느리게 읽는 경우. 모든 스트리밍 연결 뒤에는 클라이언트로 전송할 메시지 큐가 있습니다. 이 큐가 시간이 지나면서 너무 커지면 연결이 종료됩니다.
* 계정이 일간/월간 포스트 할당량을 초과한 경우
* 활성화된 중복 연결이 너무 많은 경우
* 클라이언트가 갑자기 데이터 읽기를 중단한 경우. 스트림에서 읽어들이는 포스트 속도가 갑자기 떨어지면 연결이 종료됩니다.
* 서버와 클라이언트 간에 네트워크 문제가 발생한 경우
* 일시적인 서버 측 문제나 예정된 유지 관리 및 업데이트가 있는 경우 ([status 페이지](/ko/status)를 확인하세요)

<div id="anticipating-disconnects-and-reconnecting">
  ## 연결 끊김을 예상하고 다시 연결하기
</div>

포스트를 스트리밍할 때의 목표는 연결이 끊길 수 있다는 점을 인지하면서 가능한 한 오래 연결을 유지하는 것입니다. 이 엔드포인트는 20초마다 keep-alive 하트비트를 제공하며(새 줄 문자처럼 보입니다), 이 신호를 사용해 연결이 끊겼는지 감지할 수 있습니다.

1. 코드에서 새 콘텐츠와 하트비트가 더 이상 도착하지 않을 때를 감지해야 합니다.
2. 그런 경우, 코드에서 재연결 로직을 실행해야 합니다. 일부 클라이언트와 언어에서는 읽기 타임아웃을 지정할 수 있으며, 이를 20초로 설정할 수 있습니다.
3. 서비스는 이러한 연결 끊김을 감지하고 가능한 한 빨리 다시 연결해야 합니다.

한 번 설정된 연결이 끊어지면 즉시 재연결을 시도합니다. 재연결이 실패하면, 발생한 오류 유형에 따라 재연결 시도를 점진적으로 늦춰야 합니다:

* TCP/IP 수준 네트워크 오류에 대해서는 선형적으로 재시도 간격을 늘리십시오. 이러한 문제는 일반적으로 일시적이며 빠르게 해소되는 경향이 있습니다. 재연결 시도마다 대기 시간을 250ms씩 증가시키되, 최대 16초까지 늘립니다.
* 재연결이 적절한 HTTP 오류에 대해서는 지수적으로 재시도 간격을 늘리십시오. 처음에는 5초를 기다린 후 시도할 때마다 대기 시간을 두 배로 늘리되, 최대 320초까지 늘립니다.
* HTTP 429 오류(요청 한도 초과)에 대해서는 지수적으로 재시도 간격을 늘리십시오. 1분 대기부터 시작해 시도할 때마다 대기 시간을 두 배로 늘리십시오. HTTP 429 응답을 받을 때마다, 계정에 적용된 rate limit이 더 이상 유효하지 않게 될 때까지 기다려야 하는 시간이 증가한다는 점에 유의하십시오.
   

<div id="recovering-lost-data">
  ## 손실된 데이터 복구
</div>

연결이 끊어진 경우 놓쳤을 수 있는 모든 데이터를 다시 수신할 수 있도록 활용할 수 있는 여러 가지 전략이 있습니다. [데이터 복구](/ko/x-api/powerstream/recovery-and-redundancy) 통합 가이드에서 누락된 데이터를 복구하기 위해 수행할 수 있는 핵심 단계들을 안내합니다. 
 

<div id="rate-limits-and-usage">
  ## Rate limits and usage
</div>

연결 한도를 확인하기 위해 응답에는 세 개의 헤더가 포함되어 반환됩니다. 이를 통해 rule endpoint를 15분 동안 얼마만큼 사용할 수 있는지, 그리고 스트리밍 endpoint에 대해 몇 번의 재연결 시도가 허용되는지 파악할 수 있습니다.

* x-rate-limit-limit은 15분 단위 기간 동안 클라이언트가 수행할 수 있도록 할당된 요청 수를 나타냅니다.

* x-rate-limit-remaining은 해당 15분 단위 기간 동안 지금까지 수행된 요청 수를 나타냅니다.

* x-rate-limit-reset은 15분 단위 기간이 다시 시작되어 x-rate-limit-remaining이 0으로 초기화되는 시점을 나타내는 UNIX 타임스탬프입니다.

filter stream endpoint는 현재 사용량 data를 보고하지 않습니다. 얼마나 많은 포스트가 전달되었는지 확인하기 위해, 코드에서 계량(metering) 로직을 구현하여 소비량을 측정하고 필요 시 중단할 수 있습니다. 

스트림의 클라이언트 측을 호스팅하는 코드는 단순히 들어오는 포스트를 선입선출(FIFO) 큐 또는 이와 유사한 메모리 구조에 삽입합니다. 별도의 프로세스/스레드는 해당 큐에서 포스트를 꺼내 파싱하고, 저장을 위한 콘텐츠를 준비해야 합니다. 이러한 설계를 사용하면, 들어오는 포스트량이 급격하게 변하더라도 효율적으로 확장 가능한 서비스를 구현할 수 있습니다. 개념적으로는 HTTP를 통해 무한히 긴 파일을 다운로드하는 것처럼 생각할 수 있습니다.

<div id="reconnection-best-practices">
  ## 재연결을 위한 모범 사례
</div>

<div id="test-backoff-strategies">
  ### 백오프 전략 테스트
</div>

백오프 구현을 테스트하는 좋은 방법은 잘못된 인증 자격 증명을 사용하고 재연결 시도를 살펴보는 것입니다. 올바르게 구현되었다면 429 응답을 전혀 받지 않아야 합니다.

<div id="issue-alerts-for-multiple-reconnects">
  ### 여러 번 재연결 발생 시 알림 설정
</div>

클라이언트가 재연결 간 시간에 대한 상한 임계값에 도달하면, 연결에 영향을 미치는 문제를 신속히 파악하고 조치할 수 있도록 알림을 보내도록 해야 합니다.

<div id="handle-dns-changes">
  ### DNS 변경 처리
</div>

클라이언트 프로세스가 DNS TTL(Time To Live)을 준수하는지 테스트하세요. 일부 스택은 프로세스가 실행되는 동안 해석된 주소를 계속 캐시하여, 지정된 TTL 내의 DNS 변경 사항을 반영하지 않을 수 있습니다. 이러한 과도한 캐싱은 X가 IP 주소 간에 부하를 이동할 때 클라이언트 측 서비스 중단으로 이어질 수 있습니다.

<div id="user-agent">
  ### User Agent
</div>

`user-agent` HTTP 헤더에는 반드시 클라이언트 버전을 포함해야 합니다. 이는 X 측에서 문제를 진단하는 데 매우 중요합니다. 사용 중인 환경에서 `user-agent` 헤더를 설정할 수 없다면, 대신 `x-user-agent` 헤더를 설정하십시오.

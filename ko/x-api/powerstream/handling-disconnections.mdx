<div id="what-is-a-disconnection">
  ## 연결 끊김이란 무엇인가요?
</div>

스트리밍 API에 대한 연결을 설정한다는 것은 수명이 매우 긴 HTTPS 요청을 만들고 그 응답을 점진적으로 파싱해 처리하는 것을 의미합니다. powerstream 엔드포인트에 연결할 때는 HTTPS 요청을 생성하고, 가능한 한 오래 결과 스트림을 읽어들여 소비해야 합니다. 서버 측 오류, 과도한 클라이언트 측 지연, 네트워크 문제, 정기적인 서버 유지 관리, 또는 중복 로그인과 같은 상황이 발생하지 않는 한, 당사 서버는 연결을 무기한 유지합니다. 스트리밍 엔드포인트에 대한 연결은 끊어질 가능성이 높으며, 이러한 끊김은 당연히 발생할 수 있는 것으로 보고 재연결 로직을 구현해야 합니다.

<div id="why-a-streaming-connection-might-be-disconnected">
  ## 스트리밍 연결이 끊어질 수 있는 이유
</div>

스트림은 여러 가지 이유로 끊어질 수 있습니다. 스트림에서 반환된 오류 메시지를 확인하여 실패 원인을 파악하세요. 연결이 끊어질 수 있는 가능한 이유는 다음과 같습니다:

* 인증 오류(잘못된 토큰 사용 또는 잘못된 인증 방식 사용 등).
* X 측에서 스트리밍 서버가 재시작되는 경우. 이는 일반적으로 코드 배포와 관련이 있으며, 미리 예상하고 이에 맞게 설계해야 합니다.
* 클라이언트가 스트림에서 전달되는 포스트의 양을 따라가지 못하거나 데이터를 너무 느리게 읽는 경우. 모든 스트리밍 연결 뒤에는 클라이언트로 전송될 메시지 큐가 있습니다. 이 큐가 시간이 지나면서 너무 커지면 연결이 종료됩니다.
* 계정이 일일/월간 포스트 할당량을 초과한 경우.
* 활성화된 중복 연결이 너무 많은 경우.
* 클라이언트가 갑자기 데이터 읽기를 중단한 경우. 스트림에서 읽어 들이는 포스트의 속도가 갑자기 떨어지면 연결이 종료됩니다.
* 서버와 클라이언트 간의 네트워크 문제
* 일시적인 서버 측 문제, 정기 점검 및 업데이트. ([상태 페이지](/ko/status)를 확인하세요)

<div id="anticipating-disconnects-and-reconnecting">
  ## 연결 끊김을 예상하고 재연결하기
</div>

포스트를 스트리밍할 때의 목표는 연결이 끊길 수 있다는 점을 인지하면서 가능한 한 오래 연결 상태를 유지하는 것입니다. 이 엔드포인트는 20초 간격으로 keep-alive 하트비트 신호를 제공합니다(새 줄 문자처럼 보입니다). 이 신호를 사용해 연결이 끊겼는지 감지하십시오.

1. 새 콘텐츠와 하트비트가 더 이상 도착하지 않을 때를 코드에서 감지해야 합니다.
2. 그런 상황이 발생하면 코드에서 재연결 로직을 트리거해야 합니다. 일부 클라이언트와 언어에서는 읽기 타임아웃을 지정할 수 있으며, 이를 20초로 설정할 수 있습니다.
3. 서비스는 이러한 연결 끊김을 감지하고 가능한 한 빨리 다시 연결해야 합니다.

이미 설정된 연결이 끊어지면 즉시 재연결을 시도하십시오. 재연결에 실패한 경우, 발생한 오류 유형에 따라 재연결 시도 간격을 늦추십시오.

* TCP/IP 수준 네트워크 오류에 대해서는 선형적으로 백오프(back off)하십시오. 이러한 문제는 일반적으로 일시적이며 빠르게 해결되는 경향이 있습니다. 재연결 간 지연 시간을 시도할 때마다 250ms씩 늘려 최대 16초까지 증가시키십시오.
* 재연결이 적절한 HTTP 오류에 대해서는 지수적으로 백오프하십시오. 5초 대기부터 시작해 시도할 때마다 두 배로 늘려 최대 320초까지 증가시키십시오.
* HTTP 429 오류(요청 한도 초과)에 대해서는 지수적으로 백오프하십시오. 1분 대기부터 시작해 시도할 때마다 두 배로 늘리십시오. HTTP 429를 받을 때마다 계정에 대한 요청 한도(rate limit) 제한이 더 이상 적용되지 않을 때까지 기다려야 하는 시간이 증가한다는 점에 유의하십시오.
   

<div id="recovering-lost-data">
  ## 손실된 데이터 복구
</div>

연결이 끊기는 상황이 발생하더라도, 놓쳤을 수 있는 모든 데이터를 다시 수신할 수 있도록 사용할 수 있는 여러 가지 전략이 있습니다. 손실된 데이터를 복구하기 위해 취할 수 있는 핵심 단계는 [데이터 복구](/ko/x-api/powerstream/recovery-and-redundancy) 통합 가이드에 정리되어 있습니다. 
 

<div id="rate-limits-and-usage">
  ## Rate limits and usage
</div>

연결 한도를 확인할 때 응답에는 세 개의 헤더가 포함됩니다. 이는 rule endpoint를 얼마나 자주 사용할 수 있는지와 streaming endpoint에서 허용되는 재연결 시도 횟수를 파악하는 데 유용합니다.

* x-rate-limit-limit은 15분 구간 동안 클라이언트가 보낼 수 있도록 할당된 요청 수를 나타냅니다.

* x-rate-limit-remaining은 15분 구간 동안 지금까지 수행된 요청 수를 나타냅니다.

* x-rate-limit-reset은 15분 구간이 언제 다시 시작되는지를 나타내는 UNIX 타임스탬프로, 재시작 시 x-rate-limit-remaining이 0으로 재설정됩니다.

filter stream endpoint는 현재 사용량 데이터를 보고하지 않습니다. 몇 개의 포스트가 전송되었는지 확인하려면, 코드에 계량(metering) 로직을 구현하여 소비량을 측정하고 필요 시 일시 중지할 수 있도록 해야 합니다. 

스트림의 클라이언트 측 코드는 들어오는 포스트를 선입선출(FIFO) 큐 또는 유사한 메모리 구조에 삽입하고, 별도의 프로세스/스레드가 해당 큐에서 포스트를 가져와 콘텐츠를 파싱하고 저장을 위해 준비해야 합니다. 이러한 설계를 통해, 들어오는 포스트 트래픽 양이 급격하게 변하더라도 효율적으로 확장 가능한 서비스를 구현할 수 있습니다. 개념적으로는 HTTP를 통해 끝없이 긴 파일을 다운로드하는 것으로 생각할 수 있습니다.

<div id="reconnection-best-practices">
  ## 재연결을 위한 모범 사례
</div>

<div id="test-backoff-strategies">
  ### 백오프 전략 테스트
</div>

백오프 구현을 테스트하는 좋은 방법은 잘못된 인증 자격 증명을 사용한 뒤 재연결 시도를 관찰하는 것입니다. 올바르게 구현되었다면 429 응답을 전혀 받지 않아야 합니다.

<div id="issue-alerts-for-multiple-reconnects">
  ### 여러 차례 재연결 시 문제 알림
</div>

클라이언트가 재연결 간 시간의 상한값에 도달하면, 연결에 영향을 주는 문제를 판단하고 우선순위를 정할 수 있도록 알림을 보내도록 해야 합니다.

<div id="handle-dns-changes">
  ### DNS 변경 처리
</div>

클라이언트 프로세스가 DNS TTL(Time To Live)을 준수하는지 테스트하세요. 일부 스택은 프로세스가 실행되는 동안 조회된 주소를 캐시하고, 지정된 TTL 내에 발생하는 DNS 변경 사항을 반영하지 못할 수 있습니다. 이처럼 과도한 캐싱은 X가 IP 주소 간에 부하를 이동할 때 클라이언트에서 서비스 중단을 초래할 수 있습니다.

<div id="user-agent">
  ### User Agent
</div>

`user-agent` HTTP 헤더에 클라이언트 버전을 포함하세요. 이는 X 측에서 문제를 진단하는 데 매우 중요합니다. 사용 중인 환경에서 `user-agent` 헤더를 설정할 수 없는 경우, 대신 `x-user-agent` 헤더를 설정하세요.

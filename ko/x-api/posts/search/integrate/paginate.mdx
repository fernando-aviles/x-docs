<div id="recent-search-pagination">
  ### 최근 검색 페이지네이션
</div>

<div id="introduction">
  #### 소개
</div>

검색 쿼리는 일반적으로 단일 API 응답에 포함될 수 있는 것보다 더 많은 포스트와 일치합니다. 그런 경우 data는 여러 &#39;페이지&#39;로 나누어 반환됩니다. 페이지네이션(pagination)은 전체 데이터 세트를 가져오기 위해 이 모든 페이지를 순서대로 요청하는 방법을 의미합니다.

다음은 최근 검색 페이지네이션의 기본 사항입니다.

* recent search 엔드포인트는 쿼리에 대해 최소 한 페이지의 응답을 반환하며, 추가 페이지가 있을 경우 JSON 응답에 next&#95;token 을 제공합니다. 일치하는 포스트를 모두 받기 위해, 응답에 토큰이 더 이상 포함되지 않을 때까지 이 과정을 반복할 수 있습니다.

* next&#95;token 은 만료되지 않습니다. 동일한 next&#95;token 값을 사용한 여러 요청은, 요청 시점과 관계없이 동일한 결과를 받게 됩니다.

* 포스트는 UTC 타임존 기준으로 최신순(역연대순)으로 제공됩니다. 이는 개별 페이지 내에서도, 여러 페이지 전체에 대해서도 마찬가지입니다.
  * 첫 번째 응답의 첫 번째 포스트는 쿼리와 일치하는 가장 최근 포스트입니다.
  * 마지막 응답의 마지막 포스트는 쿼리와 일치하는 가장 오래된 포스트입니다.

* max&#95;results 요청 매개변수를 사용하면 응답 하나당 반환되는 포스트 수를 설정할 수 있습니다. 기본값은 포스트 10개이며, 최대값은 100개입니다. 

* 모든 페이지네이션 구현에서는 응답 페이로드에서 next&#95;token 값을 파싱하고, 이를 &#39;다음 페이지&#39; 검색 요청에 포함하는 과정이 필요합니다. 이러한 &#39;다음 페이지&#39; 요청을 구성하는 방법에 대한 자세한 내용은 아래를 참고하세요.
   

recent search 엔드포인트는 두 가지 기본 사용 패턴을 지원하도록 설계되었습니다.

* **Get historical** - 관심 있는 기간에 해당하는 일치하는 포스트를 요청하는 것. 이는 일반적으로 과거 연구를 위한 일회성 요청입니다. 검색 요청은 start&#95;time 및 end&#95;time 요청 매개변수를 기준으로 구성할 수 있습니다. recent search 엔드포인트는 가장 최근에 일치한 포스트부터 시작하여 포스트를 최신순(역연대순)으로 반환합니다. 

* **Polling** - 마지막으로 받은 포스트 이후에 새로 게시된 일치하는 포스트를 요청하는 것. 이러한 사용 사례는 종종 거의 실시간에 가까운 요구를 가지며, 관심 있는 새 포스트를 &quot;수신&quot;하기 위한 잦은 요청이 특징입니다. recent search 엔드포인트는 &#39;polling&#39; 패턴을 지원하기 위해 since&#95;id 요청 매개변수를 제공합니다. 포스트 ID 를 기준으로 탐색하는 데 도움이 되도록 until&#95;id 요청 매개변수도 사용할 수 있습니다.
   

다음으로 historical 모드에 대해 설명합니다. 이는 recent search 엔드포인트의 기본 모드이며 페이지네이션의 기본 개념을 보여 줍니다. 그다음에는 polling 사용 사례의 예를 살펴보겠습니다. polling 으로 인해 페이지네이션이 발생하는 경우, 검색 요청을 관리하기 위한 추가 단계가 필요합니다.
 

<div id="retrieving-historical-data">
  #### 과거 데이터 가져오기
</div>

이 섹션에서는 start&#95;time 및 end&#95;time 요청 매개변수를 사용하여 관심 있는 기간(현재는 최근 7일로 제한) 동안의 포스트를 가져오는 방법을 설명합니다. 과거 데이터 요청은 일반적으로 연구 및 분석을 지원하기 위한 일회성 요청입니다. 

기간을 지정해 데이터를 요청하는 방식은 최근 검색 엔드포인트의 기본 모드입니다. 검색 요청에 start&#95;time, end&#95;time 또는 since&#95;id 요청 매개변수가 지정되지 않은 경우 end&#95;time은 기본적으로 &quot;지금&quot;(실제로는 쿼리 시점 30초 전)으로 설정되고, start&#95;time은 7일 전으로 설정됩니다.

엔드포인트는 가장 최근 포스트부터 시작하여 시간 역순(최신순)으로 정렬된 첫 번째 &#39;페이지&#39;의 포스트를 반환합니다. 응답 JSON payload에는 추가 데이터 페이지가 있는 경우 next&#95;token도 포함됩니다. 일치하는 포스트의 전체 집합을, 페이지 수와 상관없이 모두 수집하려면 next&#95;token이 더 이상 제공되지 않을 때까지 요청을 계속 보냅니다. 

예를 들어, 지난주 동안 snow라는 키워드가 포함된 포스트에 대한 초기 요청은 다음과 같습니다:

https://api.x.com/2/tweets/search/recent?query=snow

응답에는 가장 최근 10개의 포스트와 함께 JSON 응답의 다음과 같은 &quot;meta&quot; 속성도 포함됩니다:

```
"meta": {
        "newest_id": "1204860593741553664",
        "oldest_id": "1204860580630278147",
        "next_token": "b26v89c19zqg8o3fobd8v73egzbdt3qao235oql",
        "result_count": 10
    }
```

다음 10개의 포스트를 가져오려면 이 next&#95;token을 원래 요청에 추가합니다. 요청은 다음과 같습니다:

https://api.x.com/2/tweets/search/recent?query=snow&amp;next&#95;token=b26v89c19zqg8o3fobd8v73egzbdt3qao235oql

next&#95;token을 찾고 이를 이후 요청에 포함하는 과정을, 모든(또는 일정 개수의) 포스트를 수집할 때까지, 혹은 지정된 횟수만큼 요청을 보낼 때까지 반복할 수 있습니다. 데이터 충실도(쿼리와 일치하는 모든 결과를 수집하는 것)가 사용 사례에서 중요하다면, 단순한 &quot;request.next&#95;token이 null이 될 때까지 반복&quot; 방식으로 충분합니다.

<div id="polling-and-listening-use-cases">
  #### 폴링 및 리스닝 사용 사례
</div>

이 섹션에서는 `since_id` 요청 매개변수를 사용해 recent search 엔드포인트를 폴링하여 최신 포스트를 조회하는 방법을 설명합니다. 

폴링 사용 사례에서는 “관심 있는 새로운 포스트가 있는가?”라는 쿼리를 지속적이고 빈번하게 수행합니다. 시간 기준으로 요청을 구성하는 과거 데이터 사용 사례와 달리, 폴링 사용 사례는 일반적으로 포스트 ID를 기준으로 요청을 구성합니다.

폴링 사용 패턴의 핵심은 모든 새로운 포스트가 X 플랫폼에서 일반적으로 오름차순으로 ‘발행(emitted)’되는 [고유 ID](/ko/resources/fundamentals/x-ids)를 가진다는 점입니다. 어떤 포스트의 ID가 다른 포스트의 ID보다 더 작다면, 더 먼저 게시되었다는 의미입니다.

recent search 엔드포인트는 포스트 ID를 사용해 포스트 아카이브를 탐색하는 기능을 지원합니다. 이 엔드포인트의 응답에는 `oldest_id` 및 `newest_id` 포스트 ID가 포함됩니다. 폴링 모드에서는 지금까지 받은 ID 중 가장 크고 최신인 값을 `since_id`로 설정해 요청을 보냅니다. 

예를 들어, 눈(snow)에 대한 새로운 포스트를 5분마다 조회하고 있고, 마지막으로 받은 포스트의 포스트 ID가 10000이라고 가정해 봅니다. 폴링 시점이 되면 요청은 다음과 같습니다:

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=10000

그다음, 마지막 요청 이후 포스트 7개가 게시되었다고 가정해 봅시다. 이 포스트들이 모두 하나의 data ‘페이지’에 들어가기 때문에 `next_token`은 없습니다. 응답은 가장 최근(최신) 포스트의 포스트 ID를 제공합니다:

```
"meta": {
        "newest_id": "12000",
        "oldest_id": "10005",
        "result_count": 7
    }
```

다음 폴링 쿼리를 수행하기 위해 이 newest&#95;id 값을 사용하여 다음 since&#95;id 매개변수를 설정합니다:

`https://api.x.com/2/tweets/search/recent?query=snow&since_id=12000`

추가 데이터가 있고 next 토큰이 제공되는 경우, 결과 첫 페이지에 있는 newest&#95;id 값만 필요합니다. 각 데이터 페이지에는 newest&#95;id 및 oldest&#95;id 값이 포함되지만, 다음에 정기적으로 수행할 폴링 요청에는 첫 페이지에 제공된 값만 사용하면 됩니다. 따라서 폴링 방식을 구현하거나 ID 범위로 포스트를 검색하는 경우, 페이지네이션 로직이 약간 더 복잡해집니다. 

이제 일치하는 포스트가 18개 더 있다고 가정해 보겠습니다. 이 엔드포인트는 이 5분 구간에서 다음 데이터 페이지를 요청할 수 있도록 전체 데이터 페이지와 next&#95;token 이 포함된 초기 응답을 반환합니다. 또한 5분 후 다음 폴링 주기에 필요한 최신 포스트 ID도 함께 포함합니다.

```
"meta": {
        "newest_id": "13800",
        "oldest_id": "12500",
        "next_token": "fnsih9chihsnkjbvkjbsc",
        "result_count": 10
    }
```

이 5분 동안의 모든 일치하는 데이터를 수집하려면, 다음 요청에서도 이전 요청과 동일한 since&#95;id 값을 사용하면서 next&#95;token을 함께 전달하세요.

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=12000&amp;next&#95;token=fnsih9chihsnkjbvkjbsc

```
"meta": {
        "newest_id": "12300",
        "oldest_id": "12010",
        "result_count": 8
    }
```

두 번째 응답은 나머지 8개의 포스트를 포함하며, next&#95;token은 제공되지 않습니다. newest&#95;id 값(12300)은 업데이트하지 않고, 대신 첫 번째 응답의 newest&#95;id 값을 기준으로 다음 since&#95;id 요청을 보냅니다:

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=13800

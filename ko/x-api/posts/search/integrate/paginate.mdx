<div id="recent-search-pagination">
  ### 최근 검색 페이지네이션
</div>

<div id="introduction">
  #### 소개
</div>

검색 쿼리는 일반적으로 단일 API 응답으로 반환할 수 있는 것보다 더 많은 포스트와 매치됩니다. 이때 data는 여러 &#39;페이지&#39;로 나누어 반환됩니다. 페이지네이션은 전체 data 세트를 가져오기 위해 이러한 모든 페이지를 순차적으로 요청하는 방법을 의미합니다.

다음은 최근 검색 페이지네이션의 기본 사항입니다:

* 최근 검색 엔드포인트는 쿼리에 대해 최소 한 페이지로 응답하며, 추가 페이지가 있으면 JSON 응답에 next&#95;token을 제공합니다. 일치하는 포스트를 모두 받기 위해, 응답에 더 이상 토큰이 포함되지 않을 때까지 이 과정을 반복할 수 있습니다.

* next&#95;token은 만료되지 않습니다. 동일한 next&#95;token 값을 사용한 여러 요청은, 요청 시점과 관계없이 항상 동일한 결과를 받게 됩니다.

* 포스트는 UTC 타임존을 기준으로 최신순(내림차순)으로 전달됩니다. 이는 각 개별 페이지 내뿐 아니라 여러 페이지 전체에 걸쳐서도 마찬가지입니다:
  * 첫 번째 응답의 첫 번째 포스트는 쿼리와 일치하는 가장 최근 포스트입니다.
  * 마지막 응답의 마지막 포스트는 쿼리와 일치하는 가장 오래된 포스트입니다.

* max&#95;results 요청 파라미터를 사용하여 응답당 반환되는 포스트 수를 설정할 수 있습니다. 기본값은 포스트 10개이며, 최대값은 100입니다. 

* 모든 페이지네이션 구현에는 응답 페이로드에서 next&#95;token을 파싱하고, 이를 &#39;다음 페이지&#39; 검색 요청에 포함하는 과정이 필요합니다. 이러한 &#39;다음 페이지&#39; 요청을 구성하는 방법에 대한 자세한 내용은 아래를 참고하세요.
   

최근 검색 엔드포인트는 두 가지 기본 사용 패턴을 지원하도록 설계되었습니다:

* **Get historical** - 관심 있는 기간에 대해 일치하는 포스트를 요청하는 방식입니다. 일반적으로 과거 데이터 연구를 위한 일회성 요청입니다. 검색 요청은 start&#95;time 및 end&#95;time 요청 파라미터를 기반으로 할 수 있습니다. 최근 검색 엔드포인트는 가장 최근에 일치하는 포스트부터 시작하여 최신순으로 포스트를 반환합니다. 

* **Polling** - 마지막으로 수신한 포스트 이후에 게시된 일치하는 포스트를 요청하는 방식입니다. 이러한 사용 사례는 종종 거의 실시간에 가까운 특성을 가지며, 관심 있는 새 포스트를 “수신 대기(listening)”하기 위해 잦은 요청을 보내는 것이 특징입니다. 최근 검색 엔드포인트는 &#39;폴링&#39; 패턴을 지원하기 위해 since&#95;id 요청 파라미터를 제공합니다. 또한 포스트 id를 기준으로 탐색하는 데 도움을 주기 위해 until&#95;id 요청 파라미터도 제공합니다.
   

다음으로, 히스토리컬 모드에 대해 설명하겠습니다. 이는 최근 검색 엔드포인트의 기본 모드이며, 페이지네이션의 기본 개념을 보여줍니다. 이후에 폴링 사용 사례의 예를 살펴보겠습니다. 폴링 과정에서 페이지네이션이 발생하는 경우, 검색 요청을 관리하기 위한 추가 단계가 필요합니다.
 

<div id="retrieving-historical-data">
  #### 과거 데이터 가져오기
</div>

이 섹션에서는 start&#95;time 및 end&#95;time 요청 매개변수를 사용해 관심 있는 기간(현재는 최근 7일로 제한) 동안의 포스트를 가져오는 방법을 설명합니다. 과거 데이터 요청은 일반적으로 연구 및 분석을 위한 일회성 요청입니다. 

기간 단위로 데이터를 요청하는 방식은 recent search 엔드포인트의 기본 동작입니다. 검색 요청에서 start&#95;time, end&#95;time 또는 since&#95;id 요청 매개변수를 지정하지 않으면 end&#95;time은 기본적으로 &quot;지금&quot;(실제 값은 쿼리 시각 30초 전)으로 설정되고, start&#95;time은 기본적으로 7일 전으로 설정됩니다.

엔드포인트는 가장 최근 포스트부터 시작하여 포스트의 첫 &#39;페이지&#39;를 최신순(역순)으로 반환합니다. 응답 JSON 페이로드에는 추가 데이터 페이지가 있는 경우 next&#95;token도 포함됩니다. 페이지 수와 상관없이 일치하는 포스트 전체 집합을 모두 수집하려면, 더 이상 next&#95;token이 제공되지 않을 때까지 요청을 반복해야 합니다. 

예를 들어, 지난 한 주 동안 snow라는 키워드가 포함된 포스트에 대한 최초 요청은 다음과 같습니다:

https://api.x.com/2/tweets/search/recent?query=snow

응답에는 가장 최근의 포스트 10개와 함께 JSON 응답의 &quot;메타&quot; 속성이 다음과 같이 포함됩니다:

```
"meta": {
        "newest_id": "1204860593741553664",
        "oldest_id": "1204860580630278147",
        "next_token": "b26v89c19zqg8o3fobd8v73egzbdt3qao235oql",
        "result_count": 10
    }
```

다음 10개의 포스트를 가져오려면 이 next&#95;token 값을 원래 요청에 추가합니다. 요청은 다음과 같습니다:

https://api.x.com/2/tweets/search/recent?query=snow&amp;next&#95;token=b26v89c19zqg8o3fobd8v73egzbdt3qao235oql

next&#95;token을 확인하고 이를 이후 요청에 포함하는 작업을, 모든(또는 원하는 개수의) 포스트를 수집할 때까지 또는 정해진 횟수만큼 요청을 보낼 때까지 반복할 수 있습니다. 데이터 완전성(쿼리와 일치하는 결과를 빠짐없이 수집하는 것)이 사용 사례에서 중요하다면, 간단히 &quot;request.next&#95;token 이 null 이 될 때까지 반복&quot;하는 방식으로 설계하면 충분합니다.

<div id="polling-and-listening-use-cases">
  #### 폴링 및 리스닝 사용 사례
</div>

이 섹션에서는 `since_id` 요청 매개변수를 사용해 최근 검색 엔드포인트를 폴링(polling)하여 최신 포스트를 가져오는 방법을 설명합니다. 

폴링 사용 사례에서는 “관심 있는 새 포스트가 있나요?”와 같은 질의를 지속적이고 빈번하게 수행합니다. 시간 기준으로 요청을 구성하는 과거 데이터 사용 사례와 달리, 폴링 사용 사례는 일반적으로 포스트 ID를 기준으로 요청을 구성합니다.

폴링 사용 패턴의 핵심은 모든 새로운 포스트에는 X 플랫폼에서 일반적으로 오름차순으로 &#39;부여&#39;되는 [고유 ID](/ko/resources/fundamentals/x-ids)가 있다는 점입니다. 한 포스트의 ID가 다른 포스트의 ID보다 작다면, 그 포스트가 더 먼저 게시되었다는 의미입니다.

최근 검색 엔드포인트는 포스트 ID를 사용해 포스트 아카이브를 탐색하는 기능을 지원합니다. 이 엔드포인트의 응답에는 `oldest_id` 및 `newest_id` 포스트 ID가 포함됩니다. 폴링 모드에서는 지금까지 받은 가장 크고/가장 최신의 ID를 `since_id`로 설정하여 요청을 보냅니다. 

예를 들어, 눈(snow)에 대한 새 포스트를 5분마다 조회하고 있고, 마지막으로 받은 포스트의 포스트 ID가 10000이라고 가정해 보겠습니다. 폴링을 수행할 시점의 요청은 다음과 같습니다:

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=10000

다음으로, 마지막 요청 이후에 포스트 7개가 게시되었다고 가정해 보겠습니다. 이 포스트들은 모두 하나의 data &#39;페이지&#39;에 들어가기 때문에 `next_token`은 없습니다. 응답에는 가장 최근(최신) 포스트의 포스트 ID가 제공됩니다:

```
"meta": {
        "newest_id": "12000",
        "oldest_id": "10005",
        "result_count": 7
    }
```

다음 폴링 쿼리를 만들기 위해 이 newest&#95;id 값을 사용해 다음 since&#95;id 파라미터를 설정합니다:

`https://api.x.com/2/tweets/search/recent?query=snow&since_id=12000`

추가 data가 있고 next 토큰이 제공되는 경우, 결과의 첫 페이지에 있는 newest&#95;id 값만 필요합니다. 각 data 페이지에는 newest&#95;id와 oldest&#95;id 값이 모두 포함되지만, 첫 페이지에서 제공되는 값만 이후에 정기적으로 수행되는 폴링 요청에 사용하면 됩니다. 따라서 폴링 방식을 구현하거나 ID 범위로 포스트를 검색하는 경우 페이지네이션 로직이 약간 더 복잡해집니다. 

이제 일치하는 포스트가 18개 더 있다고 가정해 봅시다. 이 엔드포인트는 이 5분 구간에 대해 전체 data 페이지와, 다음 data 페이지를 요청하기 위한 next&#95;token이 포함된 초기 응답을 반환합니다. 또한 5분 후 다음 폴링 간격에 필요로 하는 최신 포스트 ID도 함께 포함합니다.

```
"meta": {
        "newest_id": "13800",
        "oldest_id": "12500",
        "next_token": "fnsih9chihsnkjbvkjbsc",
        "result_count": 10
    }
```

이 5분 동안의 모든 일치하는 데이터를 수집하려면, 이전 요청과 동일한 since&#95;id 값을 사용하면서, 다음 요청에 next&#95;token을 함께 포함해 보내면 됩니다.

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=12000&amp;next&#95;token=fnsih9chihsnkjbvkjbsc

```
"meta": {
        "newest_id": "12300",
        "oldest_id": "12010",
        "result_count": 8
    }
```

두 번째 응답에서는 나머지 8개의 포스트를 반환하며, `next_token`은 포함되지 않습니다. `newest_id` 값(12300)은 업데이트하지 않고, 대신 첫 번째 응답의 `newest_id` 값을 기준으로 다음에 보낼 `since_id` 요청을 구성합니다:

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=13800

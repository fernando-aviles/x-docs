<div id="introduction">
  #### 소개
</div>

스트리밍 데이터를 수신할 때, 연결 시간을 최대화하고 일치하는 모든 데이터를 받는 것은 기본적인 목표입니다. 이를 위해서는 중복 연결을 활용하고, 연결 끊김을 자동으로 감지해 빠르게 재연결하며, 손실된 데이터를 복구할 수 있는 계획을 마련하는 것이 중요합니다.

이 통합 가이드에서는 중복 연결, 백필(backfill), 복구 등 다양한 복구 및 중복성 기능에 대해 설명합니다.
 

**중복 연결**

중복 연결은 간단히 말해 Filtered stream에 두 개 이상의 동시 연결을 설정할 수 있게 해 줍니다. 이렇게 하면 두 개의 별도 컨슈머가 동일한 스트림에 연결하여 두 연결 모두를 통해 동일한 데이터를 수신하므로, 중복성이 확보됩니다. 따라서 한 스트림이 끊기거나 애플리케이션의 기본 서버에 장애가 발생하는 등의 다양한 상황에서 앱에 핫 페일오버(hot failover)를 제공할 수 있습니다.

Filtered stream은 현재 Enterprise 액세스 권한이 있는 Project만 최대 두 개의 중복 연결을 설정할 수 있습니다. 중복 스트림을 사용하려면 기본 연결에 사용한 것과 동일한 URL에 다시 연결하기만 하면 됩니다. 스트림의 데이터는 두 연결 모두를 통해 전송됩니다.

<div id="recovering-missed-data-after-a-disconnection-backfill">
  #### 연결 끊김 이후 누락된 데이터 복구하기: 백필(Backfill)
</div>

연결 끊김을 탐지한 후에는 시스템이 스트림에 자동으로 다시 연결할 수 있어야 합니다. 가능하다면, 적절한 복구 기능을 사용해 데이터를 백필할 수 있도록 연결이 얼마나 오래 끊어져 있었는지 기록해 두어야 합니다. 

엔터프라이즈 액세스가 있는 Project를 사용하고 있고, 연결 끊김이 5분 이하였다고 판단한 경우, 백필 파라미터인 `backfill_minutes`를 사용할 수 있습니다. 이 파라미터를 [GET /tweets/search/stream](/ko/x-api/posts/filtered-stream#get-2-tweets-search-stream) 요청에 함께 전송하면, 지난 1분에서 5분 사이에 규칙과 일치한 포스트를 받을 수 있습니다. 일반적으로 이러한 오래된 포스트를 새로 매칭된 포스트보다 먼저 전달하며, 포스트에 대한 중복 제거도 수행하지 않습니다. 즉, 90초 동안 연결이 끊겼는데 2분 분량의 백필 데이터를 요청하면, 30초 분량의 중복 포스트를 받게 되며, 이에 대해 시스템이 문제없이 처리할 수 있어야 합니다. 다음은 백필 파라미터를 포함한 요청 예시입니다:

`curl 'https://api.x.com/2/tweets/search/stream?backfill_minutes=5' -H "Authorization: Bearer $ACCESS_TOKEN"`

엔터프라이즈 액세스가 없거나, 연결 끊김 시간이 5분보다 길었다고 판단한 경우, [최근 검색 엔드포인트](/ko/x-api/posts/search/introduction) 또는 복구 기능을 사용하여 누락된 데이터를 요청할 수 있습니다. 다만, 검색 포스트 엔드포인트에는 `sample:`, `bio:`, `bio_name:`, `bio_location:` 연산자가 포함되지 않으며, 키워드 및 `#hashtag` 연산자에 악센트와 발음 구별 기호를 사용할 때 매칭 동작에 일부 차이가 있습니다. 이러한 차이로 인해 필터링된 스트림 엔드포인트를 통해 수신되었을 수 있는 모든 포스트를 완전히 복구하지 못할 수도 있습니다. 

**연결 끊김 이후 누락된 데이터 복구하기: Recovery**

엔터프라이즈 액세스가 있는 Project를 사용하는 경우, 5분 백필 윈도우 내에서 재연결할 수 없는 경우에도 Recovery 기능을 사용해 지난 24시간 동안의 누락된 데이터를 복구할 수 있습니다.

스트리밍 복구 기능을 사용하면 백필 윈도우를 24시간으로 확장할 수 있습니다. Recovery를 사용하면 누락된 데이터의 시간 구간을 ‘재생(replay)’할 수 있습니다. `start_time`과 `end_time` 요청 파라미터를 사용하여 연결 요청을 보내면 복구 스트림이 시작됩니다. 연결이 완료되면, Recovery는 지정된 시간 구간을 다시 스트리밍한 뒤 연결을 끊습니다.  

동시에 두 개의 복구 요청, 즉 “두 개의 복구 작업”을 수행할 수 있습니다. Recovery는 시작 및 종료 시간이 정의된다는 점을 제외하면 기술적으로 백필과 동일한 방식으로 동작합니다. 하나의 복구 기간은 하나의 시간 범위에 대해서만 적용됩니다.

|     |     |     |
| :--- | :--- | :--- |
| **이름** | **유형** | **설명** |
| start&#95;time | date (ISO 8601) | YYYY-MM-DDTHH:mm:ssZ (ISO 8601/RFC 3339).<br /><br />복구를 시작할 시간을 나타내는 UTC 기준 날짜입니다. |
| end&#95;time | date (ISO 8601) | YYYY-MM-DDTHH:mm:ssZ (ISO 8601/RFC 3339).<br /><br />복구를 종료할 시간을 나타내는 UTC 기준 날짜입니다. |

요청 URL 예시: [https://api.x.com/2/tweets/search/stream?start&#95;time=2022-07-12T15:10:00Z&amp;end&#95;time=2022-07-12T15:20:00Z](https://api.x.com/2/tweets/search/stream?start_time=1985-04-12T23:20:50.52Z\&end_time=1985-04-13T00:20:50.52Z)

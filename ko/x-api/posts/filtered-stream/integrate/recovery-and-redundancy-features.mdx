<div id="introduction">
  #### 소개
</div>

스트리밍 데이터를 수신할 때, 연결 시간을 최대화하고 일치하는 모든 데이터를 받는 것은 가장 기본적인 목표입니다. 이를 위해서는 중복 연결을 활용하고, 연결 해제를 자동으로 감지해 빠르게 재연결하며, 손실된 데이터를 복구하기 위한 계획을 마련하는 것이 중요합니다.

이 통합 가이드에서는 중복 연결, 백필(backfill), 복구(recovery)와 같은 다양한 복구 및 중복 기능에 대해 설명합니다.
 

**중복 연결(Redundant connections)**

중복 연결은 필터링된 스트림에 동시에 두 개 이상의 연결을 설정할 수 있게 해 주는 기능입니다. 두 개의 개별 컨슈머가 동일한 스트림에 연결되어 두 연결 모두를 통해 동일한 데이터를 수신할 수 있으므로, 이를 통해 중복성이 확보됩니다. 따라서 하나의 스트림 연결이 끊기거나 애플리케이션의 기본 서버에 장애가 발생하는 등의 다양한 상황에서 애플리케이션에 즉시 전환 가능한 핫 페일오버(hot failover)가 제공됩니다.

현재 Filtered stream 은 Enterprise 액세스 권한이 있는 Project 에 대해서만 최대 두 개의 중복 연결을 허용합니다. 중복 스트림을 사용하려면 기본(primary) 연결에 사용한 것과 동일한 URL 에 단순히 다시 연결하면 됩니다. 스트림의 데이터는 두 연결을 통해 모두 전송됩니다.

<div id="recovering-missed-data-after-a-disconnection-backfill">
  #### 연결 끊김 이후 누락된 데이터 복구하기: 백필(Backfill)
</div>

연결 끊김을 감지한 이후에는, 시스템이 스트림에 자동으로 다시 연결할 수 있어야 합니다. 가능하다면, 적절한 복구 기능을 사용해 데이터를 백필(Backfill)할 수 있도록 연결이 끊겨 있던 시간이 얼마나 되었는지 시스템에서 기록해야 합니다. 

Enterprise 액세스가 있는 Project를 사용 중이고 연결 끊김이 5분 이하였음을 확인했다면, 백필 파라미터인 `backfill_minutes`를 사용할 수 있습니다. 이 파라미터를 [GET /tweets/search/stream](/ko/x-api/posts/filtered-stream#get-2-tweets-search-stream) 요청에 함께 전달하면, 지난 1~5분 동안 설정한 규칙에 일치하는 포스트를 받게 됩니다. 일반적으로 이러한 과거 포스트를 새로 매칭된 포스트보다 먼저 전달하며, 포스트에 대해 중복 제거도 수행하지 않습니다. 즉, 90초 동안 연결이 끊겨 있었는데 2분 분량의 백필 데이터를 요청한 경우, 30초 분량의 중복 포스트를 받게 되며, 시스템은 이에 대해 문제없이 동작할 수 있어야 합니다. 다음은 백필 파라미터를 사용한 요청 예시입니다:

`curl 'https://api.x.com/2/tweets/search/stream?backfill_minutes=5' -H "Authorization: Bearer $ACCESS_TOKEN"`

Enterprise 액세스가 없거나, 연결이 5분 이상 끊겨 있었음을 확인한 경우에는 [최근 검색 엔드포인트](/ko/x-api/posts/search/introduction) 또는 Recovery 기능을 사용하여 누락된 데이터를 요청할 수 있습니다. 다만, 검색 포스트 엔드포인트에는 `sample:`, `bio:`, `bio_name:`, `bio_location:` 연산자가 포함되지 않으며, 키워드 및 `#hashtag` 연산자 사용 시 악센트와 발음 구별 부호(다이액리틱)를 처리하는 방식에 일부 차이가 있습니다. 이러한 차이로 인해, 필터링된 스트림 엔드포인트를 통해 수신했을 수 있는 모든 포스트를 완전히 복구하지 못할 수도 있습니다. 

**연결 끊김 이후 누락된 데이터 복구하기: Recovery**

Enterprise 액세스가 있는 Project를 사용 중이라면, 5분 백필 윈도우 내에서 다시 연결할 수 없을 때 Recovery 기능을 사용하여 최대 지난 24시간 이내의 누락된 데이터를 복구할 수 있습니다.

스트리밍 Recovery 기능은 최대 24시간까지 확장된 백필 윈도우를 제공합니다. Recovery를 사용하면 누락된 데이터가 발생한 기간을 ‘재생(replay)’할 수 있습니다. Recovery 스트림은 `start_time` 및 `end_time` 요청 파라미터를 사용해 연결 요청을 보낼 때 시작됩니다. 한 번 연결되면, Recovery는 지정된 시간 구간을 다시 스트리밍한 다음 연결을 종료합니다.  

동시에 최대 2개의 Recovery 요청, 즉 “두 개의 Recovery 작업”을 수행할 수 있습니다. Recovery는 시작 시간과 종료 시간을 지정한다는 점을 제외하면 기술적으로 백필과 동일한 방식으로 동작합니다. Recovery는 한 번에 하나의 시간 구간에 대해서만 수행됩니다.

|     |     |     |
| :--- | :--- | :--- |
| **Name** | **Type** | **Description** |
| start&#95;time | date (ISO 8601) | YYYY-MM-DDTHH:mm:ssZ (ISO 8601/RFC 3339).<br /><br />복구를 시작할 UTC 기준 시작 시간을 나타내는 날짜입니다. |
| end&#95;time | date (ISO 8601) | YYYY-MM-DDTHH:mm:ssZ (ISO 8601/RFC 3339).<br /><br />복구를 종료할 UTC 기준 종료 시간을 나타내는 날짜입니다. |

<div id="what-is-a-disconnection">
  ### 연결 해제란 무엇인가요?
</div>

스트리밍 API에 연결을 설정한다는 것은 장시간 지속되는 HTTPS 요청을 보내고, 응답을 점진적으로 파싱한다는 의미입니다. 필터링된 스트림 엔드포인트에 연결할 때는 HTTPS 요청을 작성한 뒤, 가능한 한 오래 결과 스트림을 수신하고 처리해야 합니다. 서버 측 오류, 과도한 클라이언트 측 지연, 네트워크 문제, 정기적인 서버 유지 관리, 중복 로그인과 같은 상황을 제외하면, 우리 서버는 연결을 무기한 유지합니다. 스트리밍 엔드포인트에 대한 연결에서는 연결이 끊어지는 일이 발생할 가능성이 높으며, 이는 예상해야 하는 동작입니다. 따라서 재연결 로직을 구현해 두어야 합니다.
 

<div id="why-a-streaming-connection-might-be-disconnected">
  #### 스트리밍 연결이 끊어질 수 있는 이유
</div>

스트림은 여러 가지 이유로 끊어질 수 있습니다. 오류가 발생한 원인을 이해하려면 스트림에서 반환된 오류 메시지를 확인하십시오. 연결이 끊어질 수 있는 이유는 다음과 같습니다.

* 인증 오류(잘못된 토큰을 사용했거나 잘못된 인증 방식을 사용한 경우 등).
* X 측에서 스트리밍 서버를 재시작하는 경우. 이는 보통 코드 배포와 관련이 있으며, 일반적으로 발생할 수 있는 상황으로 보고 이에 맞춰 설계해야 합니다.
* 클라이언트가 스트림이 전달하는 포스트 수를 따라가지 못하거나 데이터를 너무 느리게 읽는 경우. 모든 스트리밍 연결은 클라이언트로 전송할 메시지를 저장하는 큐를 기반으로 합니다. 이 큐가 시간이 지나면서 너무 커지면 연결이 종료됩니다.
* 계정이 일일/월간 포스트 할당량을 초과한 경우.
* 활성 중복 연결이 너무 많은 경우.
* 클라이언트가 갑자기 데이터 읽기를 중단한 경우. 스트림에서 읽어들이는 포스트의 속도가 갑자기 떨어지면 연결이 종료됩니다.
* 서버와 클라이언트 간의 네트워크 문제 가능성.
* 서버 측의 일시적인 문제, 예정된 유지 관리 또는 업데이트가 있는 경우. ([status 페이지](https://api.twitterstat.us/)를 확인하십시오.)

<div id="anticipating-disconnects-and-reconnecting">
  #### 연결 끊김을 예상하고 재연결하기
</div>

포스트를 스트리밍할 때의 목표는 연결이 끊길 수 있음을 인지하면서 가능한 한 오래 연결 상태를 유지하는 것입니다. 이 엔드포인트는 20초마다 keep-alive 하트비트(새 줄 문자처럼 보입니다)를 제공합니다. 이 신호를 사용해 연결이 끊겼는지 감지하세요.

1. 코드는 새로운 콘텐츠와 하트비트가 더 이상 도착하지 않을 때를 감지해야 합니다.
2. 그런 상황이 발생하면, 코드는 재연결 로직을 실행해야 합니다. 일부 클라이언트와 언어에서는 읽기 타임아웃을 지정할 수 있으며, 이를 20초로 설정할 수 있습니다.
3. 서비스는 이러한 연결 끊김을 감지하고 가능한 한 빨리 다시 연결해야 합니다.

한번 설정된 연결이 끊어지면 즉시 재연결을 시도하세요. 재연결에 실패한 경우, 경험한 오류 유형에 따라 재연결 시도 간격을 늘리세요.

* TCP/IP 수준의 네트워크 오류가 발생한 경우 선형적으로 대기 시간을 늘리세요. 이러한 문제는 일반적으로 일시적이며 빠르게 해소되는 경향이 있습니다. 재연결 시도마다 대기 시간을 250ms씩 늘려 최대 16초까지 증가시키세요.
* 재연결이 적절한 HTTP 오류의 경우 지수적으로 대기 시간을 늘리세요. 5초 대기부터 시작해 시도할 때마다 두 배로 늘려 최대 320초까지 증가시키세요.
* HTTP 429 오류(요청 한도 초과)의 경우 지수적으로 대기 시간을 늘리세요. 1분 대기부터 시작해 시도할 때마다 두 배로 늘리세요. HTTP 429를 받을 때마다, 계정에 대한 요청 한도(rate limit)가 더 이상 적용되지 않을 때까지 기다려야 하는 시간이 늘어난다는 점에 유의하세요.
   

<div id="recovering-lost-data">
  #### 손실된 데이터 복구
</div>

실제로 연결이 끊어지는 상황이 발생한 경우, 놓쳤을 수 있는 모든 데이터를 다시 수신할 수 있도록 사용할 수 있는 몇 가지 전략이 있습니다. 놓친 데이터를 복구하기 위해 취할 수 있는 핵심 단계는 [데이터 복구](/ko/x-api/posts/filtered-stream/integrate/recovery-and-redundancy-features)에 관한 통합 가이드에 정리되어 있습니다. 
 

<div id="rate-limits-and-usage">
  #### 요청 한도 및 사용량
</div>

연결 한도를 확인하려면 응답에 포함된 세 개의 헤더를 확인하면 됩니다. 이는 규칙 엔드포인트를 몇 번까지 사용할 수 있는지와 스트리밍 엔드포인트에 대해 몇 번의 재연결 시도가 허용되는지 이해하는 데 유용합니다.

* `x-rate-limit-limit`은 15분 시간 창 동안 클라이언트에 허용된 전체 요청 수를 나타냅니다.

* `x-rate-limit-remaining`은 15분 시간 창 동안 지금까지 수행된 요청 수를 나타냅니다.

* `x-rate-limit-reset`은 15분 시간 창이 다시 시작되어 `x-rate-limit-remaining`이 0으로 재설정되는 시점을 나타내는 UNIX 타임스탬프입니다.

filter stream 엔드포인트는 현재 사용량 데이터를 보고하지 않습니다. 얼마나 많은 포스트가 전달되었는지 확인하려면, 코드에서 계량(metering) 로직을 구현하여 소비량을 측정하고 필요 시 중지 또는 일시 중지할 수 있도록 해야 합니다. 

스트림의 클라이언트 측을 담당하는 코드는 단순히 들어오는 포스트를 선입선출(FIFO) 큐 또는 유사한 메모리 구조에 삽입하고, 별도의 프로세스/스레드가 그 큐에서 포스트를 소비하여 내용을 파싱하고 저장을 위해 준비해야 합니다. 이러한 설계를 통해, 유입되는 포스트 양이 급격히 변하는 경우에도 효율적으로 확장 가능한 서비스를 구현할 수 있습니다. 개념적으로는 HTTP를 통해 끝이 없는 매우 긴 파일을 다운로드하는 것으로 생각할 수 있습니다.

<div id="reconnection-best-practices">
  #### 재연결 모범 사례
</div>

**백오프 전략 테스트**

백오프 구현을 테스트하는 좋은 방법은 잘못된 인증 자격 증명을 사용해 재연결 시도를 관찰하는 것입니다. 올바르게 구현된 경우 429 응답이 전혀 발생하지 않아야 합니다.

**여러 차례 재연결 시 알림 발송**

클라이언트가 재연결 간 시간 간격의 상한에 도달하면, 연결에 영향을 주는 문제를 분류할 수 있도록 알림을 보내도록 구성해야 합니다.

**DNS 변경 처리**

클라이언트 프로세스가 DNS Time To live (TTL)를 준수하는지 테스트하세요. 일부 스택은 프로세스 전체 기간 동안 해석된 주소를 캐시하고, 설정된 TTL 내의 DNS 변경 사항을 반영하지 않을 수 있습니다. 이러한 과도한 캐싱은 X가 IP 주소 간에 부하를 이동할 때 클라이언트 측 서비스 중단을 초래할 수 있습니다.

**User Agent**

`user-agent` HTTP 헤더에 클라이언트 버전을 포함하도록 하세요. 이는 X 측에서 문제를 진단하는 데 매우 중요합니다. 환경상 `user-agent` 필드를 설정할 수 없다면, `x-user-agent` 헤더를 설정하세요.

<div id="building-a-client-to-consume-streaming-data">
  ### 스트리밍 데이터를 수신하는 클라이언트 구축
</div>

스트리밍 엔드포인트를 사용할 때는 효율적인 활용을 위해 고려해야 할 일반적인 모범 사례들이 있습니다.  
 

<div id="client-design">
  #### 클라이언트 설계
</div>

filter stream endpoint로 솔루션을 구축할 때, 다음 작업을 수행할 수 있는 클라이언트가 필요합니다:

1. filter stream endpoint에 대한 HTTPS 스트리밍 연결을 설정합니다.
2. 스트림에서 규칙을 추가·삭제하기 위해 filter stream rules endpoint로 POST 요청을 비동기적으로 전송합니다.
3. 낮은 데이터 볼륨 처리 – 스트리밍 연결을 유지하면서 포스트 객체와 keep-alive 신호를 감지합니다.
4. 높은 데이터 볼륨 처리 – 비동기 프로세스를 사용해 스트림 수집과 후속 처리를 분리하고, 클라이언트 측 버퍼가 정기적으로 플러시되도록 합니다.
5. 클라이언트 측에서 데이터 사용량 추적을 관리합니다.
6. 스트림 연결 해제를 감지하고 상태를 평가한 뒤 스트림에 자동으로 재연결합니다.
    

<div id="connecting-to-a-streaming-endpoint">
  #### 스트리밍 엔드포인트에 연결하기
</div>

X API v2 스트리밍 엔드포인트에 연결한다는 것은 매우 장시간 지속되는 HTTP 요청을 보내고, 응답을 점진적으로 파싱하는 것을 의미합니다. 개념적으로는 HTTP를 통해 무한히 긴 파일을 다운로드하는 것과 같다고 볼 수 있습니다. 한 번 연결이 수립되면, 연결이 유지되는 동안 X 서버는 해당 연결을 통해 포스트 이벤트를 전달합니다.
 

<div id="consuming-data">
  #### 데이터 소비
</div>

JSON 객체의 개별 필드는 순서가 보장되지 않으며, 모든 상황에서 모든 필드가 항상 존재하는 것은 아닙니다. 또한 개별 활동 메시지는 정렬된 순서로 전달되지 않고, 중복된 메시지를 수신할 수도 있습니다. 시간이 지나면서 새로운 메시지 유형이 추가되어 스트림을 통해 전송될 수 있다는 점을 염두에 두십시오.

따라서 클라이언트는 다음을 허용해야 합니다.

* 어떤 순서로든 나타나는 필드
* 예기치 않거나 누락된 필드
* 정렬되지 않은 포스트
* 중복 메시지
* 언제든지 스트림으로 전송될 수 있는 새로운 임의의 메시지 유형

관련 포스트 data 및 요청한 필드 파라미터 외에도, 다음과 같은 유형의 메시지가 스트림 연결을 통해 전달될 수 있습니다. 이 목록이 완전하지 않을 수 있으며, 추가 객체가 스트림에 도입될 수 있다는 점에 유의하십시오. 파서가 예기치 않은 메시지 형식도 처리할 수 있도록 구현하십시오.
 

<div id="buffering">
  #### 버퍼링
</div>

스트리밍 엔드포인트는 사용 가능한 즉시 데이터를 전송하므로, 많은 경우 매우 높은 데이터 양이 발생할 수 있습니다. X 서버가 스트림에 새 데이터를 바로 기록할 수 없는 경우(예: 클라이언트가 충분히 빠르게 읽지 못하는 경우, 자세한 내용은 [연결 끊김 처리](/ko/x-api/posts/filtered-stream#what-is-a-disconnection)를 참조) 클라이언트가 따라잡을 수 있도록 서버 쪽에서 콘텐츠를 버퍼링합니다. 그러나 이 버퍼가 가득 차면 연결을 끊기 위한 강제 연결 종료가 발생하며, 버퍼에 있던 포스트는 삭제되고 다시 전송되지 않습니다. 자세한 내용은 아래를 참조하세요.

앱이 뒤처지고 있는 시점을 파악하는 한 가지 방법은 수신 중인 포스트의 타임스탬프를 현재 시간과 비교하고, 이를 시간 경과에 따라 추적하는 것입니다.

공용 인터넷 환경에서는 잠재적인 지연 및 일시적인 장애로 인해 스트림 적체를 완전히 제거할 수는 없지만, 앱을 적절히 구성하면 대부분의 적체를 없앨 수 있습니다. 적체 발생을 최소화하려면 다음을 수행하세요.

* 클라이언트가 스트림을 충분히 빠르게 읽고 있는지 확인합니다. 일반적으로 스트림을 읽는 동안 실제 처리 작업을 수행해서는 안 됩니다. 스트림을 읽고, 처리 작업은 다른 스레드/프로세스/데이터 저장소에 넘겨 비동기적으로 처리하세요.
* 데이터 센터에 대용량의 지속적인 데이터 트래픽과 이보다 훨씬 큰 스파이크(예: 평상시의 5~10배)를 처리할 수 있을 만큼 충분한 인바운드 대역폭이 있는지 확인합니다. Filtered stream의 경우, 발생하는 데이터 양과 이에 따라 필요한 대역폭은 전적으로 규칙이 어떤 포스트와 일치하는지에 따라 달라집니다.
   

<div id="usage-tracking-and-rule-management">
  #### 사용량 추적 및 규칙 관리
</div>

스트림에서 어느 정도의 데이터량을 “정상적인” 수준으로 볼지에 대한 기대치는 개발자마다 다르기 때문에, 특정 퍼센트의 감소/증가나 기간에 대해 일반적인 권장은 제공하지 않습니다. 

스트림 데이터량을 모니터링하여 예기치 않은 변동이 있는지 확인하는 것이 좋습니다. 데이터량 감소는 스트림 연결 해제와는 다른 문제의 징후일 수 있습니다. 이러한 상황에서는 스트림이 여전히 keep-alive 신호와 일부 새로운 활동 데이터를 수신하고 있을 수 있습니다. 그러나 포스트 수가 현저히 줄어든 경우, 애플리케이션이나 네트워크로 유입되는 데이터량 감소를 유발하는 요인이 있는지 조사하고, 관련 공지가 있는지 [status page](https://api.twitterstat.us/)를 확인해야 합니다.

이러한 모니터링을 구현하기 위해, 일정 시간 동안 수신될 것으로 예상하는 새로운 포스트 수를 추적할 수 있습니다. 스트림의 데이터량이 지정된 임계값보다 충분히 낮아지고, 설정된 시간 내에 회복되지 않으면 경보 및 알림이 발생하도록 해야 합니다. 또한 필터링된 스트림의 규칙을 수정하는 중이거나, 포스트 활동이 급증하는 이벤트가 발생하는 경우 특히 데이터량이 크게 증가하는지도 모니터링하는 것이 좋습니다.

필터링된 스트림을 통해 전달되는 포스트는 총 월간 포스트량에 포함된다는 점이 중요하며, 최적화를 위해 소비량을 추적하고 조정해야 합니다. 데이터량이 높은 경우, 각 규칙에 `sample:` 연산자를 추가하여 100% 매칭에서 필요 시 `sample:50` 또는 `sample:25`로 줄이는 것을 고려하십시오. 

또한 사전에 설정한 임계값을 초과할 경우 팀에 알림을 보내는 기능을 앱 내에 구현하고, 너무 많은 데이터를 가져오는 규칙을 자동으로 삭제하거나, 극단적인 상황에서는 스트림에서 완전히 연결을 끊는 등의 조치를 도입하는 것을 권장합니다.
 

<div id="responding-to-system-messages">
  #### 시스템 메시지에 응답하기
</div>

Keep-alive 신호
최소 20초마다 스트림은 열린 연결을 통해 \r\n 캐리지 리턴 형태의 keep-alive 신호(또는 heartbeat)를 보내 클라이언트 연결이 타임아웃되는 것을 방지합니다. 클라이언트 애플리케이션은 스트림에 포함된 \r\n 문자를 적절히 처리하거나 무시할 수 있어야 합니다.

클라이언트가 사용하는 HTTP 라이브러리에 읽기(read) 타임아웃을 올바르게 구현해 두었다면, 이 기간 동안 어떠한 data도 읽히지 않을 때 HTTP 프로토콜과 HTTP 라이브러리가 이벤트를 발생시키도록 할 수 있으며, 이 경우 \r\n 문자를 명시적으로 모니터링할 필요가 없습니다.

이 이벤트는 일반적으로 예외가 발생하는 형태이거나, 사용 중인 HTTP 라이브러리에 따라 다른 형태의 이벤트일 수 있습니다. 이러한 타임아웃을 감지하기 위해 HTTP 메서드를 에러/이벤트 핸들러로 감싸는 것이 강력히 권장됩니다. 타임아웃이 발생하면 애플리케이션은 재연결을 시도해야 합니다.

에러 메시지
v2 스트리밍 엔드포인트는 스트림 내에서 에러 메시지를 전달할 수도 있습니다. 아래에는 이러한 메시지의 기본 형식과 몇 가지 예시를 제공합니다. 전달되는 메시지는 변경될 수 있으며, 새로운 메시지가 도입될 수도 있다는 점에 유의하세요. 클라이언트 애플리케이션은 변경되는 시스템 메시지 페이로드에 대해 유연하게 동작할 수 있어야 합니다.

또한 에러 메시지에는 문제를 해결하는 방법을 설명하는 문서로 연결되는 링크가 포함된다는 점에 유의하세요.

메시지 형식:

```{
	"errors": [{
		"title": "operational-disconnect",
		"disconnect_type": "UpstreamOperationalDisconnect",
		"detail": "운영상의 이유로 업스트림에서 이 스트림의 연결이 해제되었습니다.",
		"type": "https://api.x.com/2/problems/operational-disconnect"
	}]
}
```

버퍼가 가득 차서 강제 연결 종료가 발생했다는 오류 메시지는, 해당 강제 종료를 유발한 정체(backup) 때문에 메시지 자체가 전달되지 못할 수 있으므로 클라이언트에 도달하지 않을 수도 있습니다. 따라서 앱은 재연결을 시작하기 위해 이러한 메시지에 의존해서는 안 됩니다.

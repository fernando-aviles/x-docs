<div id="building-a-client-to-consume-streaming-data">
  ### 스트리밍 데이터를 처리하는 클라이언트 구축
</div>

스트리밍 엔드포인트를 사용할 때는 효율적인 활용을 위해 고려해야 할 일반적인 모범 사례들이 있습니다.  
 

<div id="client-design">
  #### 클라이언트 설계
</div>

Filter stream endpoint를 사용하는 솔루션을 구축할 때는 다음과 같은 작업을 수행할 수 있는 클라이언트가 필요합니다:

1. Filter stream endpoint에 대한 HTTPS 스트리밍 연결을 설정합니다.
2. 스트림에서 규칙을 추가·삭제하기 위해 filter stream rules endpoint로 비동기 POST 요청을 전송합니다.
3. 낮은 데이터량을 처리합니다 – 스트리밍 연결을 유지하고, 포스트 객체와 keep-alive 신호를 감지합니다.
4. 높은 데이터량을 처리합니다 – 비동기 처리를 사용해 스트림 수집을 추가 처리와 분리(de-couple)하고, 클라이언트 측 버퍼가 정기적으로 플러시되도록 합니다.
5. 클라이언트 측에서 처리량(볼륨) 사용 추적을 관리합니다.
6. 스트림 연결 해제를 감지하고, 원인을 평가한 뒤 자동으로 스트림에 다시 연결합니다.
    

<div id="connecting-to-a-streaming-endpoint">
  #### 스트리밍 엔드포인트에 연결하기
</div>

X API v2 스트리밍 엔드포인트에 연결한다는 것은 오랜 시간 동안 유지되는 HTTP 요청을 만들어 응답을 순차적으로 파싱하는 것을 의미합니다. 개념적으로는 HTTP를 통해 끝없이 긴 파일을 다운로드하는 것으로 이해할 수 있습니다. 연결이 수립되면, 연결이 열려 있는 동안 X 서버는 해당 연결을 통해 포스트 이벤트를 전송합니다.
 

<div id="consuming-data">
  #### 데이터 소비
</div>

JSON 객체의 개별 필드는 순서가 없으며, 모든 상황에서 모든 필드가 존재하는 것은 아닙니다. 마찬가지로, 개별 activity는 정렬된 순서로 전달되지 않으며, 중복된 메시지가 발생할 수 있습니다. 시간이 지남에 따라 새로운 메시지 유형이 추가되어 스트림을 통해 전송될 수 있다는 점을 염두에 두십시오.

따라서 클라이언트는 다음과 같은 상황을 처리할 수 있어야 합니다:

* 어떤 순서로든 나타나는 필드
* 예기치 못한 필드 또는 누락된 필드
* 정렬되지 않은 포스트
* 중복 메시지
* 언제든 스트림을 통해 흘러들어올 수 있는 임의의 새로운 메시지 유형

관련 포스트 data 및 요청한 필드 매개변수 외에도, 다음과 같은 유형의 메시지가 스트림 연결을 통해 전달될 수 있습니다. 이 목록이 포괄적이지 않을 수 있으며, 추가 객체가 스트림에 도입될 수 있다는 점에 유의하십시오. 파서가 예기치 못한 메시지 형식도 무리 없이 처리할 수 있도록 구현해야 합니다.
 

<div id="buffering">
  #### Buffering
</div>

스트리밍 엔드포인트는 사용 가능해지는 대로 최대한 빠르게 데이터를 전송하므로, 많은 경우 매우 큰 데이터량이 발생할 수 있습니다. X 서버가 스트림에 새 데이터를 바로 쓸 수 없는 경우(예: 클라이언트가 충분히 빠르게 읽지 못하는 경우, 자세한 내용은 [연결 끊김 처리](/ko/x-api/posts/filtered-stream#what-is-a-disconnection) 참고) 클라이언트가 따라잡을 수 있도록 서버 측에서 콘텐츠를 버퍼링합니다. 그러나 이 버퍼가 가득 차면 연결을 끊기 위한 강제 연결 종료가 발생하고, 버퍼에 저장된 포스트는 폐기되며 다시 전송되지 않습니다. 자세한 내용은 아래를 참고하십시오.

앱이 스트림 처리에서 뒤처지고 있는 시점을 파악하는 한 가지 방법은 수신되는 포스트의 타임스탬프를 현재 시간과 비교하고, 이를 시간 경과에 따라 추적하는 것입니다.

공용 인터넷 환경에서는 잠재적인 지연과 일시적인 장애로 인해 스트림 지연(백업)을 완전히 없앨 수는 없지만, 앱을 적절히 구성하면 대부분의 지연을 해소할 수 있습니다. 지연 발생을 최소화하려면 다음을 수행하십시오.

* 클라이언트가 스트림을 충분히 빠르게 읽고 있는지 확인하십시오. 일반적으로 스트림을 읽는 동안에는 실제 처리 작업을 수행하지 않는 것이 좋습니다. 스트림은 빠르게 읽고, 해당 작업을 다른 스레드/프로세스/데이터 저장소에 넘겨 비동기적으로 처리하십시오.
* 데이터 센터가 대용량의 지속적인 데이터량뿐만 아니라 훨씬 더 큰 스파이크(예: 일반 데이터량의 5~10배)를 수용할 수 있을 만큼 충분한 인바운드 대역폭을 갖추고 있는지 확인하십시오. Filtered stream의 경우, 발생하는 데이터량과 그에 따른 필요한 대역폭은 전적으로 규칙이 어떤 포스트와 매칭되는지에 따라 달라집니다.
   

<div id="usage-tracking-and-rule-management">
  #### 사용량 추적 및 규칙 관리
</div>

개발자마다 자신의 스트림에서 “정상적인” 데이터 볼륨이 어느 정도인지에 대한 기준이 다르기 때문에, 특정 퍼센트 증가/감소나 기간에 대해 일반적인 권장값을 제시하지는 않습니다. 

스트림 데이터 볼륨을 모니터링하여 예상치 못한 변동이 있는지 확인하는 것이 좋습니다. 데이터 볼륨 감소는 스트림이 끊어진 것과는 다른 유형의 문제를 나타낼 수 있습니다. 이런 상황에서는 스트림이 여전히 keep-alive 신호와 일부 새로운 활동 데이터를 수신하고 있을 수 있습니다. 그러나 포스트 수가 눈에 띄게 줄어든다면, 애플리케이션 또는 네트워크로 유입되는 데이터 볼륨 감소를 초래하는 요인이 있는지 조사하고, 관련 공지가 있는지 [status page](https://api.twitterstat.us/)를 확인해야 합니다.

이러한 모니터링을 구현하기 위해, 일정 시간 동안 수신될 것으로 예상하는 새로운 포스트 수를 추적할 수 있습니다. 스트림의 데이터 볼륨이 지정된 임계값보다 크게 떨어지고, 설정한 기간 내에 회복되지 않는다면, 경보와 알림이 발생하도록 설정해야 합니다. 특히 필터된 스트림에서 규칙을 수정하는 중이거나, 포스트 활동에 급격한 스파이크를 일으키는 이벤트가 발생한 경우에는 데이터 볼륨의 큰 증가도 함께 모니터링하는 것이 좋습니다.

필터된 스트림을 통해 전달되는 포스트는 전체 월간 포스트 볼륨에 포함되므로, 최적화를 위해 소비량을 추적하고 조정해야 합니다. 볼륨이 높다면 각 규칙에 `sample:` 연산자를 추가하여, 필요 시 100% 매칭에서 `sample:50` 또는 `sample:25`로 줄이는 것을 고려해 보세요. 

또한, 볼륨이 사전에 설정한 임계값을 초과할 경우 팀에 알림을 보내는 메커니즘을 앱에 구현하고, 너무 많은 데이터를 가져오는 규칙을 자동으로 삭제하거나, 극단적인 상황에서는 스트림에서 완전히 연결을 끊는 등의 추가 조치를 도입할 것을 권장합니다.
 

<div id="responding-to-system-messages">
  #### 시스템 메시지에 응답하기
</div>

Keep-alive 신호
최소 20초마다 스트림은 열린 연결을 통해 \r\n 캐리지 리턴 형태의 keep-alive 신호(또는 하트비트)를 보내서 클라이언트가 타임아웃되지 않도록 합니다. 클라이언트 애플리케이션은 스트림 내의 \r\n 문자를 적절히 처리하거나 무시할 수 있도록 구현되어야 합니다.

클라이언트가 사용하는 HTTP 라이브러리에서 읽기(read) 타임아웃을 올바르게 구현했다면, 이 기간 안에 아무 데이터도 읽히지 않을 경우 HTTP 프로토콜과 HTTP 라이브러리가 이벤트를 발생시키도록 신뢰할 수 있으며, 별도로 \r\n 문자를 모니터링할 필요는 없습니다.

이 이벤트는 일반적으로 예외가 발생하는 형태이거나, 사용 중인 HTTP 라이브러리에 따라 다른 형태의 이벤트일 수 있습니다. 이러한 타임아웃을 탐지하기 위해 HTTP 메서드를 오류/이벤트 처리기로 래핑하는 것을 강력히 권장합니다. 타임아웃이 발생하면 애플리케이션은 재연결을 시도해야 합니다.

오류 메시지
v2 스트리밍 엔드포인트는 스트림 내에서 오류 메시지를 전달할 수도 있습니다. 아래에는 이러한 메시지의 기본 형식과 몇 가지 예시가 제공됩니다. 전달되는 메시지는 변경될 수 있으며, 새로운 메시지가 추가될 수 있다는 점에 유의하세요. 클라이언트 애플리케이션은 변경될 수 있는 시스템 메시지 페이로드에 대해 유연하게 동작해야 합니다.

오류 메시지에는 문제를 해결하는 방법을 설명하는 문서로 연결되는 링크가 포함된다는 점에 유의하세요.

메시지 형식:

```{
	"errors": [{
		"title": "operational-disconnect",
		"disconnect_type": "UpstreamOperationalDisconnect",
		"detail": "운영상의 이유로 업스트림에서 이 스트림의 연결이 해제되었습니다.",
		"type": "https://api.x.com/2/problems/operational-disconnect"
	}]
}
```

버퍼가 가득 찼을 때 발생하는 강제 연결 해제를 나타내는 오류 메시지는, 이러한 강제 연결 해제를 유발한 전송 정체 때문에 클라이언트까지 도달하지 못할 수 있습니다. 따라서 앱은 재연결을 시작하기 위해 이러한 메시지에 의존해서는 안 됩니다.

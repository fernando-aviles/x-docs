> **유의 사항**
>
> X API v2에 [batch compliance](/ko/x-api/compliance/batch-compliance)라는 새로운 컴플라이언스 도구가 출시되었습니다. 이 새로운 도구를 사용하면 포스트 ID 또는 사용자 ID로 이루어진 대규모 데이터 세트를 업로드하여 컴플라이언스 상태를 조회하고, 데이터 세트를 규정에 맞게 조정하기 위해 어떤 데이터에 조치가 필요한지 파악할 수 있습니다.

> 또한 batch compliance와 컴플라이언스 파이어호스 모두 포스트 편집을 지원하도록 업데이트되었습니다. 컴플라이언스 파이어호스에는 새로운 `tweet_edit` 이벤트가 추가되었습니다. 자세한 내용은 [Compliance Data Objects](/ko/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects) 문서를 참조하세요. 포스트 편집 메타데이터가 어떻게 동작하는지는 [Edit Posts fundamentals](/ko/x-api/fundamentals/edit-posts) 페이지에서 자세히 알아보세요.

<div id="overview">
  ## 개요
</div>

`Enterprise`

X의 핵심 가치 중 하나는 사용자의 목소리를 보호하고 존중하는 것입니다. 여기에는 사용자가 X에서 공유하기로 선택한 콘텐츠를 삭제, 수정 또는 편집할 때 그들의 기대와 의도를 존중하는 것이 포함됩니다. 이는 세계에서 가장 큰 공개 실시간 정보 플랫폼 중 하나의 장기적인 건전성을 위해 매우 중요하다고 믿습니다. X는 사용자에게 통제권을 부여해 각 개인이 자신의 X 사용 경험을 스스로 관리할 수 있도록 합니다. 우리는 X data를 수신하는 비즈니스 고객이 최종 사용자의 기대와 의도를 존중할 책임이 있다고 믿습니다.

X 플랫폼에서 가능한 다양한 유형의 컴플라이언스 이벤트에 대한 자세한 내용은 [X에서 사용자 의도 존중하기](/ko/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter) 문서를 참고하세요.

API를 통해 X data를 사용하는 모든 개발자나 회사는 사용자 콘텐츠 변경 사항을 존중하기 위해 합리적으로 가능한 모든 노력을 기울여야 할 의무를 가집니다. 이 의무는 삭제, 수정, 공유 옵션 변경(예: 콘텐츠가 보호되거나 보류됨)과 같은 사용자 이벤트에까지 확장됩니다. 여기에는 사용자가 자신의 포스트를 편집하는 경우도 포함됩니다. 이 의무가 X data 사용에 어떤 영향을 미치는지 이해하려면 [Developer Policy](https://developer.x.com/en/developer-terms/policy) 및/또는 귀하의 X Data Agreement에 명시된 구체적인 내용을 참고하세요.

X는 이러한 사용자 컴플라이언스 이벤트와 특정 포스트 또는 사용자가 공개 상태인지 여부에 대한 정보를 제공하는 다음과 같은 솔루션을 제공합니다. 아래에서는 각 솔루션과 일반적인 통합 패턴에 대한 간략한 개요를 설명합니다:

<div id="get-statuseslookup-and-get-userslookup">
  #### GET statuses/lookup 및 GET users/lookup
</div>

* 형식: REST API. 자세한 내용은 [GET statuses/lookup](https://developer.x.com/en/docs/x-api/v1/tweets/post-and-engage/api-reference/get-statuses-lookup) 및 [GET users/lookup](https://developer.x.com/en/docs/x-api/v1/accounts-and-users/follow-search-get-users/api-reference/get-users-lookup)를 참조하세요.

* 이 엔드포인트들은 항상 포스트 편집의 최신 버전을 반환합니다. 편집 기능 도입 이후에 생성된 포스트를 설명하는 모든 포스트 객체에는 포스트 편집 메타데이터가 포함됩니다. 이는 편집되지 않은 포스트에도 동일하게 적용됩니다. 

* 모든 포스트에 대해, 생성 시점으로부터 30분이 지난 후에 이루어진 요청은 해당 포스트의 최종 상태를 나타냅니다. 

* 호출자가 API 요청의 일부로 지정한 특정 포스트 또는 사용자에 대한 가용성 정보를 제공합니다.

* 특정 포스트/사용자 그룹의 현재 가용 상태를 임시로 점검하는 데 사용할 수 있습니다.

* 특정 시점에 특정 포스트 또는 사용자의 현재 상태를 확인해야 하는 고객에게 적합합니다.

* 이러한 API는 다음과 같은 경우 콘텐츠의 가용성을 확인해야 하는 고객이 활용할 수 있는 유용한 메커니즘을 제공합니다.
  1. 포스트를 표시할 때
  2. 포스트 또는 사용자와 1:1 방식으로 상호작용할 때
  3. 허용된 파일 다운로드를 통해 제3자에게 X 콘텐츠를 배포할 때
  4. 포스트를 장기간 저장할 때

<div id="compliance-firehose-enterprise-only">
  #### 컴플라이언스 파이어호스(엔터프라이즈 전용)
</div>

* 형식: 스트리밍 API. 자세한 내용은 [Compliance Firehose](/ko/x-api/enterprise-gnip-2.0/fundamentals/firehouse#api-reference)를 참조하세요.
* X에서 발생하는 [컴플라이언스 활동](/ko/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects)의 실시간 스트림을 제공합니다. 이 활동에는 포스트가 수정되는 경우 등이 포함됩니다. 
* 플랫폼에서 새로운 컴플라이언스 이벤트가 발생할 때마다, 저장해 둔 데이터 집합 전반에 걸친 컴플라이언스 상태를 유지하는 데 사용할 수 있습니다.
* 장기간에 걸쳐 대량의 X 데이터를 수집·저장하는 고객에게 적합합니다.

<div id="recommendations-best-practices">
  #### **권장 사항 및 모범 사례**
</div>

* **숫자형 포스트 ID와 사용자 ID를 저장하는 데이터 저장 스키마 구축**: 사용자 관련 메시지는 해당 사용자의 모든 포스트에 대해 조치가 필요합니다. 따라서 모든 컴플라이언스 메시지는 숫자형 ID로만 전송되므로, 숫자형 ID를 기반으로 포스트와 사용자 간의 관계를 유지할 수 있도록 저장 스키마를 설계하는 것이 중요합니다. 데이터 소비자는 포스트 ID와 사용자 ID 모두에 대한 컴플라이언스 이벤트를 모니터링하고, 로컬 데이터 저장소를 적절히 업데이트할 수 있어야 합니다.

* **모든 컴플라이언스 상태를 처리할 수 있는 스키마 구축**: 다양한 애플리케이션에서 컴플라이언스 작업을 어떻게 처리하는지에 따라, 데이터 저장소에 다른 메타데이터를 추가해야 할 수도 있습니다. 예를 들어, 데이터 소비자는 `status\_withheld` 메시지로 인해 영향을 받는 국가에서 콘텐츠 표시를 제한하기 위해 기존 데이터베이스에 메타데이터를 추가하기로 결정할 수 있습니다.

* **리트윗 삭제 처리**: 리트윗은 원본 메시지가 리트윗 객체 내에 중첩 객체로 포함된 특수한 유형의 포스트입니다. 이 경우 하나의 리트윗에는 두 개의 포스트 ID가 참조됩니다. 하나는 리트윗 자체의 ID이고, 다른 하나는 (중첩 객체에 포함된) 원본 메시지의 ID입니다. 원본 메시지가 삭제되면, 원본 ID에 대해 포스트 삭제 메시지가 전송됩니다. 포스트 삭제 이벤트는 일반적으로 모든 리트윗에 대한 삭제 이벤트를 트리거합니다. 그러나 일부 경우에는 모든 이벤트가 전송되지 않을 수 있으며, 클라이언트 시스템은 불완전한 리트윗 삭제를 허용하고 이를 처리할 수 있어야 합니다. 원본 ID의 삭제만으로 이후에 발생한 모든 리트윗을 삭제하는 데에는 충분해야 합니다. 리트윗을 저장할 때 원본 포스트 ID를 참조하고, 포스트 삭제 이벤트를 수신하면 해당 원본 포스트 ID를 참조하는 모든 리트윗을 삭제하는 것이 모범 사례입니다.

<div id="compliance-firehose-api">
  #### **Compliance Firehose API**
</div>

가능한 컴플라이언스 이벤트 유형에는 포스트(또는 &quot;status&quot;) 이벤트와 사용자 이벤트가 포함되며, 이에 대해서는 아래에 여러 유형이 설명되어 있습니다.  

다음을 참고하세요.

* 사용자 상태에 대한 자세한 내용은 [여기](https://support.x.com/articles/14016)에서, 삭제된 포스트와 관련된 개발자 정책은 [여기](https://dev.x.com/overview/terms/policy#3.Update_Respect_Users_Control_and_Privacy)에서 확인할 수 있습니다.
* Compliance Firehose는 &#39;tweet&#95;edit&#39; 이벤트를 제공하도록 업데이트되었습니다. 
* 여러 사용자 삭제, 보호 및 정지 이벤트는 반드시 영구적인 것은 아니며, 상태 간을 무제한으로 전환할 수 있습니다. 여기에 포함되는 것은 user&#95;delete, user&#95;undelete, user&#95;protect, user&#95;unprotect, user&#95;suspend, user&#95;unsuspend입니다.
* user&#95;deletes는 사용자가 자신의 계정에 대해 user&#95;undelete를 선택하지 않은 경우에만 30일 후 status&#95;deletes가 뒤따릅니다. 사용자가 user&#95;delete를 되돌려, 30일 후 그 사용자의 모든 포스트에 대한 삭제가 발생하지 않을 수도 있습니다.
* user&#95;suspend는 사용자가 user&#95;unsuspend 이벤트의 대상이 되지 않는 한 참(true)으로 유지되는 동작입니다. 이는 30일 유예 기간과는 무관하게 유지됩니다.

최종 사용자의 프라이버시와 의도를 존중하면서 각 이벤트 유형을 처리하는 방법을 이해하려면 ‘Recommended Action’ 열을 참고하세요.

| Original Message Type | Object | Permanent (Yes/No) | Recommended Action |
| :--- | :--- | :--- | :--- |
| delete | Status | Yes | 연결된 포스트를 삭제합니다. |
| status&#95;withheld | Status | Yes | status&#95;withheld 메시지에 나열된 특정 국가에서 연결된 포스트를 표시하지 않습니다. |
| drop | Status | No  | 포스트를 공개 보기에서 제거합니다. |
| undrop | Status | No  | 포스트를 다시 표시할 수 있으며 공개된 것으로 처리합니다. |
| tweet&#95;edit | Status | Yes | 새 편집 내용을 반영하고, 필요한 경우 이를 표시합니다. |
| user&#95;delete | User | No  | 관련 사용자의 모든 포스트를 표시하지 않거나 삭제합니다. |
| user&#95;undelete | User | No  | 관련 사용자의 모든 포스트를 다시 표시할 수 있으며 공개된 것으로 처리합니다. |
| user&#95;protect | User | No  | 관련 사용자의 모든 포스트를 표시하지 않거나 삭제합니다. |
| user&#95;unprotect | User | No  | 관련 사용자의 모든 포스트를 다시 표시할 수 있으며 공개된 것으로 처리합니다. |
| user&#95;suspend | User | No  | 관련 사용자의 모든 포스트를 표시하지 않거나 삭제합니다. |
| user&#95;unsuspend | User | No  | 관련 사용자의 모든 포스트를 다시 표시할 수 있으며 공개된 것으로 처리합니다. |
| scrub&#95;geo | User | Yes | scrub&#95;geo 메시지에서 지정된 포스트 이전에 해당 사용자가 작성한 모든 포스트에 대해, X가 제공한 모든 지리 데이터를 삭제합니다. 이후 포스트에는 사용 가능한 지리 데이터가 포함될 수 있습니다. |
| user&#95;withheld | User | Yes | user&#95;withheld 메시지에 나열된 특정 국가에서 관련 사용자의 포스트를 표시하지 않습니다. |
| delete | Favorite | Yes | 연결된 좋아요/즐겨찾기를 삭제합니다. |

<div id="integrating-compliance-firehose">
  ### Compliance Firehose 통합
</div>

Compliance Firehose는 X 플랫폼에서 발생하는 컴플라이언스 이벤트를 실시간으로 전달하는 스트리밍 API입니다. X에서 컴플라이언스 이벤트가 무엇이며 어떻게 생성되는지 이해하려면, [X에서 사용자 의도 존중하기](/ko/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter) 문서를 참고하세요.

포스트와 사용자 이벤트는 서로 독립적으로 전달되며, 각각을 독립적으로 처리해야 합니다(즉, 포스트 삭제가 사용자 이벤트의 발생을 의미하지 않으며, 그 반대도 마찬가지입니다). 일부 사용자 이벤트는 반드시 영구적인 것은 아니며, 상태 간을 무한히 전환할 수 있습니다. 여기에는 user&#95;delete, user&#95;undelete, user&#95;protect, user&#95;unprotect, user&#95;suspend, user&#95;unsuspend 가 포함됩니다.

user&#95;delete 가 발생한 뒤, 사용자가 계정을 user&#95;undelete 로 복구하지 않은 경우에만 30일 후 status&#95;delete 가 뒤따릅니다. 사용자가 user&#95;delete 를 되돌려 계정을 복구하면, 30일 후 해당 사용자의 모든 포스트에 대한 삭제가 발생하지 않을 수 있습니다.

user&#95;suspend 는 사용자가 user&#95;unsuspend 이벤트의 대상이 되지 않는 한 계속 유지되는 상태입니다. 이는 30일 기간과 관련된 어떤 변경 사항에도 영향을 받지 않습니다.

컴플라이언스 이벤트를 소프트웨어의 최종 사용자에게 직접 표시하거나, 제품 또는 고객 경험에 다른 방식으로 통합하는 것은 적절하지 않습니다. 이 이벤트는 오직 컴플라이언스를 유지하고 X 사용자의 행동을 존중하기 위한 용도로만 사용되어야 합니다.

<div id="integrating-with-the-compliance-firehose">
  #### **Compliance Firehose 통합하기**
</div>

Compliance Firehose를 시스템에 통합하려면, 다음 작업을 수행할 수 있는 통합을 구축해야 합니다:

1. Compliance Firehose의 각 스트리밍 API 파티션에 대한 스트리밍 연결을 설정합니다.
2. 대량의 데이터를 처리합니다 – 비동기 프로세스를 사용하여 스트림 수집과 후속 처리를 분리합니다.
3. 어떤 이유로든 연결이 끊어진 경우 스트림 파티션에 자동으로 재연결합니다.
4. 위에서 제시한 지침에 따라, 저장해 둔 포스트 및 사용자 데이터와 관련된 컴플라이언스 이벤트를 처리합니다.

<div id="honoring-user-intent-on-twitter">
  ### Twitter에서 사용자 의도를 존중하기
</div>

우리는 X 사용자의 프라이버시와 의도를 존중하는 것이, 세계에서 가장 큰 공개 실시간 정보 플랫폼 중 하나인 X의 장기적인 건전성에 결정적으로 중요하다고 믿습니다. X는 프라이버시 제어 권한을 사용자에게 부여하여 각 개인이 자신의 X 사용 경험을 스스로 관리할 수 있도록 합니다. X data를 활용하는 비즈니스 사용자로서 우리는 이와 같은 신뢰와 존중의 환경을 유지하기 위해 최종 사용자의 프라이버시와 행동을 존중할 공동의 책임이 있습니다.

플랫폼에서 포스트와 사용자 계정이 어떻게 표시되는지에 영향을 미치는 다양한 변화가 발생할 수 있습니다. 프라이버시와 의도에 영향을 주는 조치는 Status(포스트) 수준과 사용자 수준 모두에서 정의됩니다. 이러한 조치에는 다음이 포함됩니다:

<div id="user">

| :--- | :--- |

<div id="response-codes">
  #### 응답 코드
</div>

다음 응답 코드가 이러한 요청에 대해 API에서 반환될 수 있습니다. 대부분의 오류 코드는 본문에 추가 세부 정보가 포함된 문자열과 함께 반환됩니다. 200이 아닌 응답의 경우 클라이언트는 다시 연결을 시도해야 합니다.

| Status | Text | Definition |
| :--- | :--- | :--- |
| 200 | Success | 연결이 성공적으로 열렸으며, 새 활동이 도착하는 즉시 전송됩니다. |
| 401 | Unauthorized | 잘못된 자격 증명으로 인해 HTTP 인증에 실패했습니다. console.gnip.com에 해당 자격 증명으로 로그인하여 요청에서 올바르게 사용하고 있는지 확인하십시오. |
| 406 | Not Acceptable | 일반적으로 스트림에서 gzip 인코딩을 허용하는 헤더를 클라이언트가 올바르게 포함하지 않았을 때 발생하지만, 다른 상황에서도 발생할 수 있습니다. 본문에는 다음과 유사한 JSON 메시지가 포함됩니다. &quot;이 연결에는 압축이 필요합니다. 압축을 활성화하려면 요청에 &#39;Accept-Encoding: gzip&#39; 헤더를 보내고, 클라이언트 쪽에서 스트림을 읽을 때 압축을 해제할 준비를 하십시오.&quot; |
| 429 | Rate Limited | 애플리케이션이 연결 요청 한도를 초과했습니다. |
| 503 | Service Unavailable | Twitter 서버 문제입니다. 지수 백오프(exponential backoff) 패턴을 사용하여 다시 연결하십시오. 이 문제에 대한 공지가 [X API Status 페이지](https://api.twitterstat.us/)에 게시되지 않았다면, 지원팀에 문의하십시오. |

<div id="other-recommendations-best-practices">
  #### 기타 권장 사항 및 모범 사례
</div>

* **숫자 트윗 ID 및 사용자 ID를 저장하는 데이터 저장 스키마를 구축하십시오**: 사용자 메시지의 경우, 해당 사용자가 작성한 모든 트윗에 대해 조치가 필요합니다. 따라서 모든 컴플라이언스 메시지는 숫자 ID로만 전달되므로, 숫자 ID를 기반으로 트윗과 사용자 간의 관계를 유지할 수 있도록 저장 스키마를 설계하는 것이 중요합니다. 데이터 소비자는 트윗 ID와 사용자 ID 모두에 대한 컴플라이언스 이벤트를 모니터링하고, 로컬 데이터 저장소를 적절히 업데이트할 수 있어야 합니다.

* **모든 컴플라이언스 상태를 처리할 수 있는 스키마를 구축하십시오**: 다양한 애플리케이션에서 컴플라이언스 작업을 어떻게 처리하는지에 따라, 데이터 저장소에 다른 메타데이터를 추가해야 할 수 있습니다. 예를 들어, 데이터 소비자는 `status_withheld` 메시지의 영향을 받는 국가에서 콘텐츠 표시를 제한하기 위해, 기존 데이터베이스에 메타데이터를 추가하기로 결정할 수 있습니다.

* **리트윗 삭제 처리**: 리트윗은 원본 메시지가 리트윗 객체 내부에 중첩된 객체로 포함되는 특수한 종류의 트윗입니다. 이 경우, 리트윗에는 두 개의 트윗 ID가 참조됩니다. 하나는 리트윗 자체의 ID이고, 다른 하나는 원본 메시지의 ID(중첩 객체에 포함됨)입니다. 원본 메시지가 삭제되면 원본 ID에 대해 트윗 삭제 메시지가 발행됩니다. 이후에는 모든 리트윗에 대해 별도의 삭제 메시지가 발행되지 않습니다. 원본 ID의 삭제만으로 이후의 모든 리트윗을 삭제하는 데 충분합니다.

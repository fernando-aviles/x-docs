> **유의 사항**
>
> X API v2에 [batch compliance](/ko/x-api/compliance/batch-compliance)라는 새로운 컴플라이언스 도구를 출시했습니다. 이 새로운 도구를 사용하면 대규모 포스트 ID 또는 사용자 ID 데이터셋을 업로드하여 컴플라이언스 상태를 조회하고, 데이터셋을 컴플라이언스 요구사항에 맞추기 위해 어떤 데이터에 조치가 필요한지 판단할 수 있습니다.

> 또한 batch compliance와 컴플라이언스 Firehose 모두 포스트 편집을 지원하도록 업데이트되었습니다. 컴플라이언스 Firehose에는 새로운 &#39;tweet&#95;edit&#39; 이벤트가 추가되었습니다. 더 자세한 내용은 [Compliance Data Objects](/ko/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects) 문서를 참조하세요. 포스트 편집 메타데이터가 어떻게 동작하는지는 [Edit Posts fundamentals](/ko/x-api/fundamentals/edit-posts) 페이지에서 자세히 알아보세요.

<div id="overview">
  ## 개요
</div>

`Enterprise`

X의 핵심 가치 중 하나는 사용자의 목소리를 보호하고 존중하는 것입니다. 여기에는 사용자가 X에서 공유하기로 선택한 콘텐츠를 삭제, 수정 또는 편집할 때 그들의 기대와 의도를 존중하는 것이 포함됩니다. 우리는 이것이 세계에서 가장 규모가 큰 공공 실시간 정보 플랫폼 중 하나의 장기적인 건전성을 위해 매우 중요하다고 믿습니다. X는 사용자에게 자신의 X 경험을 직접 통제할 수 있는 권한을 부여합니다. 우리는 X data를 수신하는 비즈니스 고객 역시 최종 사용자의 기대와 의도를 존중할 책임이 있다고 믿습니다.

X 플랫폼에서 발생할 수 있는 다양한 유형의 컴플라이언스 이벤트에 대한 자세한 내용은 [Honoring User Intent on X](/ko/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter) 문서를 참조하세요.

API를 통해 X data를 소비하는 모든 개발자 또는 회사는 사용자 콘텐츠 변경 사항을 존중하기 위해 합리적으로 가능한 모든 노력을 기울일 의무를 가집니다. 이 의무는 삭제, 수정, 공유 옵션 변경(예: 콘텐츠가 보호되거나 차단됨)과 같은 사용자 이벤트에까지 확장됩니다. 여기에는 사용자가 자신의 포스트를 편집하는 경우도 포함됩니다. 이 의무가 X data 사용에 어떤 영향을 미치는지 이해하려면 [Developer Policy](https://developer.x.com/en/developer-terms/policy) 및/또는 귀하의 X Data Agreement에 명시된 구체적인 내용을 참고하세요.

X는 이러한 사용자 컴플라이언스 이벤트와 특정 포스트 또는 사용자가 공개 상태인지 여부에 대한 정보를 제공하는 다음과 같은 솔루션을 제공합니다. 아래에서는 각 솔루션과 일반적인 통합 패턴에 대한 간단한 개요를 제공합니다:

<div id="get-statuseslookup-and-get-userslookup">
  #### GET statuses/lookup 및 GET users/lookup
</div>

* 형식: REST API. 참고: [GET statuses/lookup](https://developer.x.com/en/docs/x-api/v1/tweets/post-and-engage/api-reference/get-statuses-lookup) 및 [GET users/lookup](https://developer.x.com/en/docs/x-api/v1/accounts-and-users/follow-search-get-users/api-reference/get-users-lookup)을 참조하세요.

* 이 엔드포인트는 항상 포스트 수정의 최신 버전을 반환합니다. 수정 기능이 도입된 이후에 생성된 포스트를 설명하는 모든 Post 객체에는 포스트 수정 메타데이터가 포함됩니다. 이는 실제로 수정되지 않은 포스트에도 해당됩니다.

* 모든 포스트에 대해, 생성 시점으로부터 30분이 지난 후에 요청된 포스트는 해당 포스트의 최종 상태를 나타냅니다.

* API 요청의 일부로 호출자가 정의한 특정 포스트 또는 사용자에 대한 가용성 정보를 제공합니다.

* 특정 그룹의 포스트/사용자에 대한 현재 가용성 상태를 애드혹으로 점검하는 용도로 사용할 수 있습니다.

* 특정 시점에 특정 포스트 또는 사용자의 현재 상태를 확인해야 하는 고객에게 적합합니다.

* 이 API는 콘텐츠의 가용성을 확인해야 하는 고객에게 유용한 메커니즘을 제공합니다. 예를 들어 다음과 같은 경우입니다:
  1. 포스트를 표시할 때
  2. 포스트 또는 사용자와 1:1 방식으로 상호작용할 때
  3. 허용된 파일 다운로드를 통해 X 콘텐츠를 제3자에게 배포할 때
  4. 포스트를 장기간 저장할 때

<div id="compliance-firehose-enterprise-only">
  #### 컴플라이언스 파이어호스(엔터프라이즈 전용)
</div>

* 형식: 스트리밍 API. 자세한 내용은 [Compliance Firehose](/ko/x-api/enterprise-gnip-2.0/fundamentals/firehouse#api-reference)를 참조하세요.
* X에서 발생하는 [컴플라이언스 활동](/ko/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects)의 실시간 스트림을 제공합니다. 이러한 활동에는 포스트가 편집될 때 등이 포함됩니다. 
* 플랫폼에서 새로운 컴플라이언스 이벤트가 발생할 때, 저장된 data 집합 전반의 컴플라이언스 상태를 유지하는 데 사용할 수 있습니다.
* 장기간에 걸쳐 대량의 X data를 수집·저장하는 고객에게 적합합니다.

<div id="recommendations-best-practices">
  #### **권장 사항 및 모범 사례**
</div>

* **숫자형 포스트 ID 및 사용자 ID를 저장하는 데이터 저장 스키마 설계**: 사용자 메시지에 대해서는 해당 사용자의 모든 포스트에 대해 조치를 취해야 합니다. 따라서 모든 준수(compliance) 메시지가 숫자형 ID로만 전송되므로, 숫자형 ID를 기반으로 포스트와 사용자 간의 관계를 유지하도록 저장 스키마를 설계하는 것이 중요합니다. 데이터 소비자는 포스트 ID와 사용자 ID 둘 다에 대한 준수 이벤트를 모니터링하고, 로컬 데이터 저장소를 적절히 업데이트할 수 있어야 합니다.

* **모든 준수 상태를 처리할 수 있는 스키마 구성**: 다양한 애플리케이션에서 준수 작업을 어떻게 처리하느냐에 따라, 데이터 저장소에 다른 메타데이터를 추가해야 할 수도 있습니다. 예를 들어, 데이터 소비자는 status&#95;withheld 메시지의 영향을 받는 국가에서 콘텐츠 표시를 제한할 수 있도록 기존 데이터베이스에 메타데이터를 추가하기로 결정할 수 있습니다.

* **리트윗 삭제 처리**: 리트윗은 원본 메시지가 리트윗 객체 내부의 중첩 객체로 포함된 특수한 형태의 포스트입니다. 이 경우 리트윗에는 두 개의 포스트 ID가 참조됩니다. 리트윗의 ID와 원본 메시지의 ID(중첩 객체에 포함된 ID)입니다. 원본 메시지가 삭제되면 원본 ID에 대해 포스트 삭제 메시지가 발행됩니다. 포스트 삭제 이벤트는 일반적으로 모든 리트윗에 대한 삭제 이벤트를 트리거합니다. 그러나 일부 경우에는 모든 삭제 이벤트가 전송되지 않을 수 있으며, 클라이언트 시스템은 불완전한 리트윗 삭제를 허용할 수 있도록 설계되어야 합니다. 원본 ID가 삭제되는 것만으로도 이후의 모든 리트윗을 삭제하기에 충분해야 합니다. 리트윗을 저장할 때 원본 포스트 ID를 함께 저장해 두고, 포스트 삭제 이벤트를 수신했을 때 참조된 모든 리트윗을 삭제하는 것이 모범 사례입니다.

<div id="compliance-firehose-api">
  #### **Compliance Firehose API**
</div>

발생 가능한 컴플라이언스 이벤트 유형에는 포스트(또는 &quot;status&quot;) 이벤트와 사용자 이벤트가 포함되며, 각 유형은 아래에서 설명합니다.  

다음 사항을 참고하십시오:

* 사용자 상태에 대해 더 알아보려면 [여기](https://support.x.com/articles/14016)를, 삭제된 포스트와 관련된 개발자 정책은 [여기](https://dev.x.com/overview/terms/policy#3.Update_Respect_Users_Control_and_Privacy)를 참조하십시오.
* Compliance Firehose가 업데이트되어 &#39;tweet&#95;edit&#39; 이벤트를 제공합니다. 
* 여러 사용자 삭제, 보호, 정지 관련 이벤트는 반드시 영구적인 것은 아니며 상태 간을 무한히 전환할 수 있습니다. 여기에는 user&#95;delete, user&#95;undelete, user&#95;protect, user&#95;unprotect, user&#95;suspend, user&#95;unsuspend가 포함됩니다.
* user&#95;delete 후 30일 동안 사용자가 계정을 user&#95;undelete로 복구하지 않은 경우에만 user&#95;delete 뒤에 status&#95;delete가 발생합니다. 사용자가 user&#95;delete를 취소할 수 있으며, 그 경우 30일 후에도 해당 사용자의 모든 포스트에 대한 삭제가 발생하지 않을 수 있습니다.
* user&#95;suspend는 사용자가 user&#95;unsuspend 이벤트의 대상이 되지 않는 한 계속 유지되는 조치입니다. 이 조치는 30일 기간과 관련된 어떤 변경 사항의 대상도 아닙니다.

엔드 사용자의 프라이버시와 의도를 존중하면서 각 이벤트 유형을 처리하는 방법을 이해하려면 ‘Recommended Action’ 열을 참고하십시오.

| Original Message Type | Object | Permanent (Yes/No) | Recommended Action |
| :--- | :--- | :--- | :--- |
| delete | Status | Yes | 해당 포스트를 삭제합니다. |
| status&#95;withheld | Status | Yes | status&#95;withheld 메시지에 나열된 특정 국가에서 해당 포스트 노출을 중단합니다. |
| drop | Status | No  | 포스트를 공개 보기에서 제거합니다. |
| undrop | Status | No  | 해당 Status는 다시 표시될 수 있으며 공개 포스트로 취급됩니다. |
| tweet&#95;edit | Status | Yes | 새 편집 내용을 반영하고, 필요한 경우 이를 표시합니다. |
| user&#95;delete | User | No  | 해당 사용자가 작성한 모든 포스트의 노출을 중단하거나 삭제합니다. |
| user&#95;undelete | User | No  | 해당 사용자가 작성한 모든 포스트는 다시 표시될 수 있으며 공개 포스트로 취급될 수 있습니다. |
| user&#95;protect | User | No  | 해당 사용자가 작성한 모든 포스트의 노출을 중단하거나 삭제합니다. |
| user&#95;unprotect | User | No  | 해당 사용자가 작성한 모든 포스트는 다시 표시될 수 있으며 공개 포스트로 취급될 수 있습니다. |
| user&#95;suspend | User | No  | 해당 사용자가 작성한 모든 포스트의 노출을 중단하거나 삭제합니다. |
| user&#95;unsuspend | User | No  | 해당 사용자가 작성한 모든 포스트는 다시 표시될 수 있으며 공개 포스트로 취급될 수 있습니다. |
| scrub&#95;geo | User | Yes | scrub&#95;geo 메시지에 지정된 포스트 이전에 해당 사용자가 작성한 모든 포스트에 대해, X에서 제공한 모든 지리 데이터를 삭제합니다. 이후에 사용자가 작성한 포스트에는 사용할 수 있는 지리 데이터가 포함될 수 있습니다. |
| user&#95;withheld | User | Yes | user&#95;withheld 메시지에 나열된 특정 국가에서 해당 사용자의 포스트 노출을 중단합니다. |
| delete | Favorite | Yes | 해당 좋아요/즐겨찾기를 삭제합니다. |

<div id="integrating-compliance-firehose">
  ### Compliance Firehose 통합
</div>

Compliance Firehose는 X 플랫폼에서 발생하는 컴플라이언스 이벤트를 실시간으로 전달하는 스트리밍 API입니다. X에서 컴플라이언스 이벤트가 무엇이며 어떻게 생성되는지 이해하려면, [X에서 사용자 의도를 존중하기](/ko/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter) 문서를 참고하세요.

포스트 이벤트와 사용자 이벤트는 서로 독립적으로 전달되며, 각각 독립적으로 처리해야 합니다(예: 포스트 삭제가 사용자 이벤트를 의미하지 않으며, 그 반대도 마찬가지입니다). 여러 사용자 이벤트는 반드시 영구적인 것이 아니며 상태 간에 무한히 전환될 수 있습니다. 여기에는 user&#95;delete, user&#95;undelete, user&#95;protect, user&#95;unprotect, user&#95;suspend, user&#95;unsuspend가 포함됩니다.

user&#95;delete는 사용자가 계정을 user&#95;undelete로 복구하지 않은 경우에만 30일 후 status&#95;deletes로 이어집니다. 사용자가 user&#95;delete를 되돌려, 30일 후에 해당 사용자의 모든 포스트가 삭제되지 않는 경우도 있을 수 있습니다.

user&#95;suspend는 사용자가 user&#95;unsuspend 이벤트의 대상이 되지 않는 한 계속 유효한 조치로 유지됩니다. 이 이벤트에는 30일 기간과 관련된 어떠한 변경 사항도 적용되지 않습니다.

컴플라이언스 이벤트를 귀하의 소프트웨어 최종 사용자에게 직접 표시하거나, 제품이나 고객 경험에 이를 그대로 포함시키는 것은 결코 적절하지 않습니다. 이 이벤트는 오로지 컴플라이언스를 유지하고 X 사용자의 행동을 존중하기 위한 목적에만 사용되어야 합니다.

<div id="integrating-with-the-compliance-firehose">
  #### **Compliance Firehose와의 통합**
</div>

Compliance Firehose를 시스템에 통합하려면, 다음 작업을 수행할 수 있는 통합을 구현해야 합니다:

1. Compliance Firehose의 각 스트리밍 API 파티션에 대한 스트리밍 연결을 설정합니다.
2. 비동기 프로세스를 사용하여 스트림 수집을 후속 처리와 분리함으로써, 대용량 데이터를 처리합니다.
3. 어떤 이유로든 연결이 끊어졌을 때 스트림 파티션에 자동으로 재연결합니다.
4. 위에서 제시된 지침에 따라, 저장된 포스트 및 사용자 데이터와 관련된 컴플라이언스 이벤트를 처리합니다.

<div id="honoring-user-intent-on-twitter">
  ### Twitter에서 사용자의 의도를 존중하기
</div>

우리는 X 사용자의 프라이버시와 의도를 존중하는 것이, 세계에서 가장 큰 공개 실시간 정보 플랫폼 중 하나의 장기적인 건전성을 위해 결정적으로 중요하다고 믿습니다. X는 프라이버시 제어 권한을 사용자에게 부여하여 각 개인이 자신의 X 사용 경험을 스스로 관리할 수 있도록 합니다. X data를 비즈니스 목적으로 이용하는 우리 모두에게는, 이와 같은 신뢰와 존중의 환경을 유지하기 위해 최종 사용자의 프라이버시와 행동을 존중해야 할 공동의 책임이 있습니다.

플랫폼에서 포스트와 사용자 계정이 표시되는 방식에 영향을 미치는 다양한 일이 발생할 수 있습니다. 프라이버시와 의도에 영향을 미치는 조치는 Status(포스트) 수준과 User 수준 모두에서 정의됩니다. 이러한 조치에는 다음이 포함됩니다.

<div id="other-recommendations-best-practices">
  #### 기타 권장 사항 및 모범 사례
</div>

* **숫자형 트윗 ID와 User ID를 저장하는 데이터 저장 스키마 구축**: 특정 User의 모든 트윗에 대해 조치가 필요합니다. 또한 모든 컴플라이언스 메시지는 숫자형 ID로만 전달되므로, 트윗과 User 간의 관계를 숫자형 ID를 기반으로 유지할 수 있도록 저장 스키마를 설계하는 것이 중요합니다. 데이터 소비자는 트윗 ID와 User ID 모두에 대한 컴플라이언스 이벤트를 모니터링하고, 로컬 데이터 저장소를 적절하게 업데이트할 수 있어야 합니다.

* **모든 컴플라이언스 상태를 처리하는 스키마 구축**: 다양한 애플리케이션에서 컴플라이언스 작업을 어떻게 처리할지에 따라, 데이터 저장소에 다른 메타데이터를 추가해야 할 수도 있습니다. 예를 들어, 데이터 소비자는 status&#95;withheld 메시지의 영향을 받는 국가에서 콘텐츠 표시를 제한하기 위해 기존 데이터베이스에 메타데이터를 추가하기로 결정할 수 있습니다.

* **리트윗 삭제 처리**: 리트윗은 원본 메시지가 리트윗 객체 내부에 중첩된 객체로 포함된 특수한 형태의 트윗입니다. 이 경우, 리트윗에는 두 개의 트윗 ID가 참조됩니다. 하나는 리트윗 자체의 ID이고, 다른 하나는 원본 메시지의 ID(중첩 객체에 포함됨)입니다. 원본 메시지가 삭제되면 원본 ID에 대한 트윗 삭제 메시지가 전송됩니다. 이후에 모든 리트윗 각각에 대해 삭제 메시지가 추가로 전송되지는 않습니다. 원본 ID 삭제만으로 이후의 모든 리트윗도 삭제할 수 있어야 합니다.

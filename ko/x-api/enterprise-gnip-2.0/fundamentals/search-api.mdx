<div id="overview">
  ## Overview
</div>

`Enterprise`

*엔터프라이즈 API는 관리형 액세스 레벨에서만 사용할 수 있습니다. 이러한 API를 사용하려면 먼저 엔터프라이즈 세일즈 팀과 계정을 설정해야 합니다. 자세한 내용은 [여기](https://developer.x.com/en/products/x-api/enterprise)를 참고하세요.*

*X API 검색 포스트 제공 전체 목록은 [여기](/ko/x-api/enterprise-gnip-2.0/fundamentals/search-api)에서 확인할 수 있습니다.*

엔터프라이즈 검색 API에는 두 가지가 있습니다:

1. 30-Day Search API는 지난 30일의 데이터를 제공합니다.
2. Full-Archive Search API는 2006년 3월의 첫 번째 포스트까지 거슬러 올라가는 X 데이터 전체 말뭉치에 대해 완전하고 즉시 액세스할 수 있도록 해 줍니다.

이 RESTful API는 요청당 최대 2,048자까지의 단일 쿼리를 지원합니다. 쿼리는 PowerTrack 규칙 구문으로 작성되며, 자세한 내용은 [규칙 및 필터링](/ko/x-api/enterprise-gnip-2.0/fundamentals/rules-filtering#getting-started-with-enterprise-rules-and-queries)을 참고하세요. 사용자는 분 단위까지의 정밀도로 임의의 기간을 지정할 수 있습니다. 다만 응답은 사용자가 지정한 maxResults 값 또는 31일 중 더 작은 값으로 제한되며, 다음 결과 세트를 페이지네이션하기 위한 next 토큰이 포함됩니다. 시간 매개변수를 지정하지 않으면, API는 최근 30일 동안의 일치하는 데이터를 반환합니다.

엔터프라이즈 검색 API는 분 단위 정밀도로 포스트 아카이브에 대한 저지연, 완전 충실도의 쿼리 기반 액세스를 제공합니다. 포스트 데이터는 쿼리와 일치하는 가장 최근 포스트부터 시작하여 시간 역순으로 제공됩니다. 포스트는 게시 후 약 30초가 지나면 검색 API를 통해 조회할 수 있습니다.

이 검색 엔드포인트는 편집된 포스트 메타데이터를 제공합니다. 2022년 9월 29일 이후에 생성된 포스트에 대한 모든 객체에는, 포스트가 한 번도 편집되지 않았더라도 포스트 편집 메타데이터가 포함됩니다. 포스트가 편집될 때마다 새로운 Post ID가 생성됩니다. 포스트의 편집 이력은 원래 ID로 시작하는 Post ID 배열로 기록됩니다.

이 엔드포인트는 항상 가장 최근 편집본과 모든 편집 이력을 함께 반환합니다. 포스트의 30분 편집 가능 시간이 지난 후에 수집된 포스트는 최종 버전을 나타냅니다. 포스트 편집 메타데이터에 대해 더 알아보려면 [포스트 편집 기본 사항](/ko/x-api/fundamentals/edit-posts) 페이지를 확인하세요.

요청에는 API 응답당 반환할 최대 포스트 수를 지정하는 maxResults 매개변수가 포함됩니다. 쿼리와 연관된 포스트 수가 응답당 결과 최대 개수를 초과하는 경우, 응답에 next 토큰이 포함됩니다. 이 next 토큰은 후속 요청에서 사용되어 쿼리와 연관된 전체 포스트 집합을 페이지 단위로 조회할 수 있게 합니다.

이 엔터프라이즈 검색 API는 사용자가 자신의 쿼리와 연관된 데이터 볼륨을 요청할 수 있도록 하는 *counts* 엔드포인트를 제공합니다. 

<div id="request-types">
  ### 요청 유형
</div>

엔터프라이즈 검색 API는 두 가지 유형의 요청을 지원합니다.

<div id="search-requests-data">
  #### Search requests (data)
</div>

엔터프라이즈 검색 API에 대한 검색 요청을 사용하면 지정된 기간에 대해 단일 응답에서 최대 500개의 결과를 조회할 수 있으며, 추가 데이터에 대해서는 페이지네이션을 사용할 수 있습니다. `maxResults` 매개변수를 사용하면 화면 표시용 사용 사례에 맞춰 더 작은 페이지 크기를 지정하여(사용자가 필요에 따라 더 많은 결과를 요청할 수 있도록) 설정하거나, 대량 데이터 수집을 위해 더 큰 페이지 크기(최대 500)로 설정할 수 있습니다. 데이터는 최신순(내림차순)으로 전달되며, 전달 시점 기준으로 규정 준수 상태를 유지합니다.

<div id="counts-requests-post-count">
  #### 카운트 요청(포스트 수)
</div>

카운트 요청을 사용하면 지정한 쿼리와 일치하는 활동이 요청한 기간 동안 얼마만큼 발생했는지를 보여 주는 과거 활동 건수를 조회할 수 있습니다. 응답은 기본적으로 일(day), 시간(hour), 또는 분(minute) 단위로 구분된 카운트의 히스토그램을 제공합니다(기본 버킷은 &#95;hour&#95;입니다). 카운트 결과는 포스트가 게시된 후 상당한 시간이 지난 뒤(7일 이상) 발생하는 컴플라이언스 이벤트(예: 포스트 삭제)를 항상 반영하지는 않는다는 점에 유의해야 합니다. 따라서 동일한 쿼리에 대한 data 요청 결과와 카운트 지표가 항상 일치하지 않을 수도 있습니다.

**과금 참고:** data 및 counts 엔드포인트에 대해 수행되는 각 요청(페이지네이션 요청 *포함*)은 과금 대상 요청으로 집계됩니다. 따라서 단일 쿼리에 대해 결과 페이지가 여러 개 있는 경우, 결과의 X개 페이지를 순차적으로 요청하면 과금 기준으로 X개의 요청에 해당합니다.

<div id="data-updates-and-mutability">
  ### 데이터 업데이트 및 가변성
</div>

엔터프라이즈 검색 API에서는 포스트 내 일부 데이터가 가변적이며, 즉 최초 아카이브 이후에도 업데이트되거나 변경될 수 있습니다.

이러한 가변 데이터는 두 가지 범주로 나눌 수 있습니다:

* 사용자 객체 메타데이터:
  * 사용자의 @handle (숫자 id는 절대 변경되지 않음)
  * 자기소개(bio) 설명
  * 수치: 상태(statuses), 팔로워, 친구, 즐겨찾기, 리스트
  * 프로필 위치
  * 시간대 및 언어와 같은 기타 세부 정보
* 포스트 통계 - 즉, 사용자 활동으로 인해 플랫폼에서 변경될 수 있는 항목(아래 예시):
  * 즐겨찾기 수
  * 리트윗 수

대부분의 경우 검색 API는 포스트 생성 시점이 아니라 *query-time* 당시 플랫폼에 존재하는 형태로 데이터를 반환합니다. 그러나 선택 연산자(예: from, to, @, is:verified)를 사용하는 쿼리의 경우에는 그렇지 않을 수 있습니다. 데이터는 당사 인덱스에서 정기적으로 업데이트되며, 최신 시점에 가까울수록 더 자주 업데이트됩니다. 그 결과 일부 경우에는 반환된 데이터가 X.com에 표시되는 현재 데이터와 정확히 일치하지 않을 수 있지만, 마지막으로 인덱싱되었을 때의 데이터와는 일치합니다.

이러한 비일관성 문제는 연산자가 가변 데이터에 적용되는 쿼리에만 해당됩니다. 한 가지 예로 사용자 이름으로 필터링하는 경우가 있으며, 가장 좋은 우회 방법은 이러한 쿼리에서 @handle 대신 사용자 숫자 id를 사용하는 것입니다.

<div id="single-vs-multi-threaded-requests">
  ### 단일 스레드 vs. 다중 스레드 요청
</div>

각 고객은 자신에게 정의된 검색 endpoint의 rate limit이 있습니다. Full-Archive 검색의 기본 분당 rate limit은 분당 120개의 요청이며, 이는 초당 평균 2개의 쿼리(QPS)에 해당합니다. 이 평균 QPS는 이론상 매초 API에 2개의 요청을 보낼 수 있음을 의미합니다. 제품의 페이지네이션 기능을 고려하면, 1년 기간의 쿼리에 연관된 포스트가 100만 개 있고 이것이 1년 동안 고르게 분포되어 있다고 가정할 때, 모든 data를 받기 위해서는 2,000개가 넘는 요청이 필요합니다(‘maxResults’를 500으로 가정). 응답당 2초가 걸린다고 가정하면, 단일 스레드(이전 응답의 “next” 토큰을 사용하여 초당 1개의 요청)로 모든 데이터를 직렬/순차적으로 가져오는 데 4,000초(또는 1시간을 약간 넘는 시간)가 필요합니다. 나쁘지 않습니다!

이제 12개의 병렬 스레드를 사용해 데이터를 수신하는 상황을 고려해 보겠습니다. 100만 개의 포스트가 1년 기간에 고르게 분포되어 있다고 가정하면, 요청을 12개의 병렬 스레드(다중 스레드)로 분할하여 단일 “job”에 대해 초당 rate limit을 더 많이 활용할 수 있습니다. 다시 말해, 관심 있는 각 월별로 하나의 스레드를 실행함으로써 데이터를 12배 더 빠르게(약 6분) 가져올 수 있습니다.

이 다중 스레드 예시는 counts endpoint에도 동일하게 적용됩니다. 예를 들어, 2년 기간에 대한 포스트 수를 조회하고자 한다면, 단일 스레드 요청을 보내 31일 단위로 counts를 거슬러 올라가며 페이지네이션을 할 수 있습니다. 응답당 2초가 걸린다고 가정하면, 전체 counts 집합을 가져오기 위해 24개의 API 요청을 수행하는 데 약 48초가 소요됩니다. 그러나 동시에 여러 개의 한 달 단위 요청을 보낼 수도 있습니다. 초당 12개의 요청을 수행할 경우, 전체 counts 집합을 약 2초 안에 가져올 수 있습니다.

<div id="retry-logic">
  ### 재시도 로직
</div>

Enterprise search API에서 503 오류가 발생하는 경우, 일시적인 오류일 가능성이 높으며, 짧은 시간 후 요청을 다시 시도하면 해결될 수 있습니다.

요청이 연속으로 4회 실패했고 각 실패 사이에 최소 10분을 기다렸다면, 다음 단계를 따라 문제를 해결하세요:

* 요청이 조회하는 시간 범위를 줄인 후 다시 시도하세요. 실패가 계속되면 시간 범위를 최대 6시간 길이의 구간이 될 때까지 점진적으로 줄이면서 반복하세요.
* 많은 수의 검색어를 OR 연산으로 함께 사용하고 있다면, 이를 여러 개의 개별 규칙으로 분리한 뒤 각 규칙을 개별적으로 다시 시도하세요.
* 규칙에서 많은 수의 제외 조건을 사용하고 있다면, 규칙에 포함된 부정 검색어의 개수를 줄이고 다시 시도하세요.

  ### enterprise Search Posts: 30-Day API 시작하기
</div>

enterprise Search Posts: 30-Day API는 최근 30일 이내에 게시된 포스트를 제공합니다. 포스트는 요청에서 지정한 쿼리를 기반으로 매칭되어 반환됩니다. 쿼리는 반환받을 포스트에 어떤 내용이 포함되어야 하는지를 정의하는 규칙입니다. 이 튜토리얼에서는 X 계정 @XDevelopers에서 영어로 게시된 포스트를 검색해 보겠습니다.

응답으로 받는 포스트는 전체 포스트 페이로드를 제공하는 data 형식이거나, 매칭된 포스트의 개수에 대한 숫자 기반 집계 data 를 제공하는 counts 형식일 수 있습니다. 이 튜토리얼에서는 cURL을 사용하여 data 및 counts 엔드포인트에 요청을 보냅니다.

다음이 필요합니다:

* [엔터프라이즈 계정]https://developer.x.com/en/products/x-api/enterprise
* 사용자 이름, 비밀번호, 계정 이름
* console.gnip.com에 표시된 검색 엔드포인트와 연결된 레이블

아래는 X 엔터프라이즈 검색 API에서 지원되는 모든 연산자 목록입니다.

* **Enterprise** 전체 아카이브 검색 API

제품별로 사용 가능한 연산자를 나란히 비교하려면 [여기](/ko/x-api/enterprise-gnip-2.0/fundamentals/rules-filtering#operators-by-product)를 참고하세요.

| 연산자                             | 설명                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| :------------------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 키워드                             | 포스트 본문이나 URL 내에서 토큰화된 키워드와 일치합니다. 이는 토큰화 기반 매칭으로, 키워드 문자열이 포스트 본문의 토큰화된 텍스트와 비교된다는 의미입니다. 토큰화는 구두점, 기호, 구분자에 해당하는 유니코드 기본 평면 문자를 기준으로 수행됩니다. 예를 들어, 텍스트가 “I like coca-cola”인 포스트는 다음과 같은 토큰으로 분리됩니다: I, like, coca, cola. 그런 다음 이 토큰들을 규칙에 사용한 키워드 문자열과 비교합니다. 구두점(예: coca-cola), 기호, 또는 구분자를 포함하는 문자열을 매칭하려면, 아래에 설명된 것처럼 큰따옴표로 감싼 정확히 일치하는 문자열(quoted exact match)을 사용해야 합니다.<br /><br />**참고:** Search API에서는 악센트 및 특수 문자가 표준 라틴 문자로 정규화되므로, 외국어에서 의미가 달라지거나 예기치 않은 결과를 반환할 수 있습니다.<br />예를 들어, &quot;músic&quot;은 “music”과 일치하고 그 반대도 마찬가지입니다.<br />예를 들어, 스페인어의 흔한 문구인 &quot;Feliz Año Nuevo!&quot;는 &quot;Feliz Ano Nuevo&quot;로 색인화되며, 이로 인해 문구의 의미가 달라집니다.<br /><br />**참고:** 이 연산자는 포스트 내의 URL과 언와인드(unwound)된 URL 모두에 대해 매칭됩니다. |
| 이모지                             | 포스트 본문에 포함된 이모지와 일치하는지를 확인합니다. 이모지는 토큰화된 매치이며, 이는 사용한 이모지가 포스트 본문의 토큰화된 텍스트와 비교된다는 의미입니다. 토큰화는 문장 부호, 기호/이모지, 그리고 구분 기호에 해당하는 유니코드 기본 평면 문자들을 기준으로 수행됩니다. 예를 들어, 텍스트가 “I like <Icon icon="pizza-slice" iconType="solid" />”인 포스트는 다음 토큰들로 분리됩니다: I, like, <Icon icon="pizza-slice" iconType="solid" />. 그런 다음 이 토큰들을 규칙에 사용한 이모지와 비교합니다. 이모지에 변형(variant)이 있는 경우, 해당 이모지를 규칙에 추가하려면 반드시 따옴표로 감싸서 사용해야 합니다.                                                                                                                                                                                                                                                                                                                                |
| &quot;정확한 문구 일치&quot;           | 포스트 본문 또는 URL 내에서 토큰화되고 순서가 유지된 구문과 일치합니다. 이는 토큰 단위 매칭으로, 사용자의 키워드 문자열을 포스트 본문의 토큰화된 텍스트와 비교한다는 의미입니다. 토큰화는 구두점, 기호, 구분자 Unicode 기본 평면 문자를 기준으로 수행됩니다. <br /><br />**참고:** 구두점은 토큰화되지 않으며 공백처럼 처리됩니다.<br />예를 들어, 따옴표로 둘러싼 “#hashtag”는 “hashtag”와는 일치하지만 #hashtag와는 일치하지 않습니다(실제 해시태그와 일치시키려면 따옴표 없이 hashtag # 연산자를 사용하세요).<br />예를 들어, 따옴표로 둘러싼 “$cashtag”는 “cashtag”와는 일치하지만 $cashtag와는 일치하지 않습니다(실제 캐시태그와 일치시키려면 따옴표 없이 cashtag $ 연산자를 사용하세요).<br />예를 들어, &quot;Love Snow&quot;는 &quot;#love #snow&quot;와 일치합니다.<br />예를 들어, &quot;#Love #Snow&quot;는 &quot;love snow&quot;와 일치합니다.<br /><br />**참고:** 이 연산자는 포스트 내의 URL과 풀린(unwound) URL 모두에 대해 매칭을 수행합니다.                                                                           |
| &quot;keyword1 keyword2&quot;~N | 일반적으로 근접 연산자로 불리며, 키워드 사이의 거리가 N 토큰을 넘지 않는 포스트를 매칭합니다. <br /><br />키워드의 순서가 반대인 경우, 서로 N-2 토큰을 초과해 떨어져 있을 수 없습니다. 따옴표 안에는 원하는 만큼 키워드를 넣을 수 있습니다. | from:                           | 특정 사용자가 작성한 모든 포스트와 일치합니다.<br />값은 해당 사용자의 X 계정 숫자 ID 또는 사용자 이름(@ 문자는 제외)이어야 합니다. <div id="product-overview">
  ### 제품 개요
</div>

엔터프라이즈 티어 Full-archive Search는 2015년 8월에, 프리미엄 티어 버전은 2018년 2월에 출시되었습니다. 이 검색 제품은 고객이 공개되어 있는 모든 포스트에 즉시 액세스할 수 있도록 해 줍니다. Full-archive Search를 사용하면 단일 쿼리를 제출해 전통적인 RESTful 방식으로 응답을 받습니다. Full-archive Search는 응답당 최대 500개의 포스트를 반환하는 페이지네이션을 구현하며, 프리미엄의 경우 분당 최대 60회(rpm), 엔터프라이즈의 경우 분당 최대 120회(rpm)의 레이트 리밋을 지원합니다. 이러한 특성 덕분에 Full-archive Search는 포스트를 빠르게, 그리고 동시 요청을 활용해 대규모로 수집하는 데 사용할 수 있습니다.

디스크 상의 포스트 플랫 파일 집합을 기반으로 하는 Historical PowerTrack과 달리, Full-archive Search 포스트 아카이브는 온라인 데이터베이스와 매우 유사합니다. 모든 데이터베이스와 마찬가지로, 그 내용에 대해 쿼리를 수행할 수 있습니다. 또한 고성능 데이터 조회를 가능하게 하는 *인덱스* 를 사용합니다. Full-archive Search 엔드포인트에서 사용하는 쿼리 언어는 PowerTrack Operators로 구성되며, 각 Operator는 인덱싱되는 포스트 JSON 속성에 대응합니다.

또한 Historical PowerTrack과 마찬가지로, 쿼리를 수행하는 시점의 현재 상태를 반영하는 포스트 속성들이 있습니다. 예를 들어 오늘 Search API를 사용해 2010년에 게시된 포스트에 액세스하는 경우, 해당 사용자의 프로필 설명, 계정 &#39;home&#39; 위치, 표시 이름, 그리고 즐겨찾기(Favorites) 수와 리트윗(Retweet) 수에 대한 포스트 메트릭은 2010년 당시 값이 아니라 오늘 기준 값으로 업데이트되어 제공됩니다. 

<div id="metadata-timelines">
  ### 메타데이터 타임라인
</div>

아래는 Full-archive search 엔드포인트 연산자들이 매칭을 시작한 시점에 대한 타임라인입니다. 일부 경우에는, 연산자 매칭이 X에서 해당 ‘커뮤니케이션 관행’이 일반화된 이후에야 시작되었습니다. 예를 들어, @Replies는 2006년에 사용자 관행으로 등장했지만, 2007년 초까지는 ‘지원하는’ JSON과 함께 *일급 객체* 또는 *이벤트* 로 취급되지 않았습니다. 따라서 2006년의 @Replies를 매칭하려면 `to:` 및 `in_reply_to_status_id:` PowerTrack 연산자에 의존하는 대신 포스트 본문을 직접 살펴봐야 합니다.

여기 제공된 세부 정보는 Full-Archive Search(수백 건의 검색을 통해 만들어진 결과물)를 사용해 생성되었습니다. 이 타임라인이 100% 완전하거나 정확한 것은 아닙니다. 사용 사례에 근본적으로 중요한 다른 필터링/메타데이터의 “생성일(born-on date)”을 확인하시면 알려주시기 바랍니다.

기반이 되는 검색 인덱스는 재구축될 수 있다는 점에 유의하십시오. 따라서 이 타임라인의 세부 정보는 변경될 수 있습니다.

<div id="filtering-tips">
  ### 필터링 팁
</div>

위에서 설명한 타임라인 정보를 종합해 보면, Search API 필터를 작성할 때 고려해야 할 세부 사항이 매우 많다는 것을 알 수 있습니다. 특히 고려해야 할 두 가지 핵심 사항이 있습니다.

* 일부 메타데이터에는 ‘생성(born-on)’ 날짜가 있어 필터 결과에 &#95;거짓 음성(false negatives)&#95;이 발생할 수 있습니다. 이런 검색에는, 검색 기간 전체 또는 일부에 대해 존재하지 않았던 메타데이터에 의존하는 Operator가 포함됩니다. 예를 들어 `has:images` Operator를 사용하여 포스트를 검색하는 경우, 2011년 7월 이전 기간에 대해서는 일치하는 결과가 없습니다. 이는 해당 Operator가 *네이티브* 사진(사용자가 X 인터페이스를 사용해 포스트에 첨부한 사진)에 대해 매칭하기 때문입니다. 사진 공유 포스트에 대한 보다 완전한 데이터 세트를 얻으려면, 2011년 7월 이전에 대해서는 일반적인 사진 호스팅 URL에 매칭되는 규칙 절을 필터에 포함해야 합니다.
* 일부 메타데이터는 포스트가 X에 게시된 *이후* 시점의 메타데이터로 사후 보강(백필)되었습니다.

PowerTrack 쿼리를 생성할 때 일반적으로 중점적으로 보게 되는 속성 유형은 다음과 같습니다.

* X 프로필
* 원본 또는 공유 포스트
* 포스트 언어 분류
* 지리 정보가 포함된 포스트
* 공유된 링크의 미디어

이 중 일부는 제품별로 동작이 다르며, 일부는 동일한 동작을 합니다. 자세한 내용은 아래를 참고하세요.

<div id="x-profiles">
  #### X 프로필
</div>

Search API는 &#95;검색 시점&#95;의 상태 그대로인 사용자 프로필 데이터 세트를 사용하여 과거 포스트를 제공합니다. 2014년의 포스트를 요청하면, 사용자의 프로필 메타데이터는 해당 포스트가 작성되었을 때가 아니라 쿼리 시점의 상태를 반영합니다.

<div id="original-posts-and-retweets">
  #### 원본 포스트와 리트윗
</div>

PowerTrack `_is:retweet_` 연산자를 사용하면 리트윗을 포함하거나 제외할 수 있습니다. 이 연산자를 사용하는 경우 2009년 8월 이전 data에 대해 리트윗과 일치하도록(또는 일치하지 않도록) 처리하는 두 가지 전략이 필요합니다. 2009년 8월 이전에는 “@RT ” 패턴과 일치하는지 확인하기 위해 정확한 구문(문자열) 일치를 사용하여 포스트 메시지 자체를 검사해야 합니다(실제로 2009년 5월부터 8월 사이의 리트윗을 필터링하는 경우에는 “Via @” 패턴도 포함해야 합니다). 2009년 8월 이후 기간에는 *is:retweet* 연산자를 사용할 수 있습니다.

<div id="post-language-classifications">
  #### 포스트 언어 분류
</div>

포스트의 언어 분류를 기준으로 필터링할 때, X의 히스토리컬 제품들은 동작이 서로 상당히 다릅니다. Search 아카이브가 구축될 당시, 모든 포스트에는 X 언어 분류가 소급 적용되었습니다. 따라서 `lang:` 연산자는 전체 포스트 아카이브에서 사용할 수 있습니다.

<div id="geo-referencing-posts">
  #### 포스트의 지리 정보 참조(Geo-referencing)
</div>

포스트의 지리 정보를 참조하는 주요 방법은 세 가지입니다:

* **포스트 메시지에 포함된 지리적 참조.** 포스트 메시지에 포함된 지리적 참조를 기반으로 매칭하는 방법은 지역에 대한 현지 지식에 크게 의존하기 때문에 가장 까다로운 방법인 경우가 많지만, 전체 포스트 아카이브에 적용할 수 있는 방법입니다. [여기](https://x.com/biz/statuses/28311)는 ‘golden gate’ 필터를 기반으로 2006년에 샌프란시스코 지역을 지리 정보로 참조한 매칭 예시입니다.

* **사용자가 지오태그(geo-tag)를 추가한 포스트.** Search API에서는 2010년 3월부터 일부 Geo Operator를 사용하여 포스트를 매칭할 수 있게 되었고, 2015년 2월부터는 다른 Operator들도 사용할 수 있게 되었습니다:

  * 2010년 3월 6일: `has:geo`, `bounding_box:` 및 `point_radius:`
  * 2015년 2월 17일: `place_country:` 및 `place:`

* **사용자가 계정 프로필에 설정한 ‘home’ 위치.** Profile Geo Operator는 Historical PowerTrack과 Search API 모두에서 사용할 수 있습니다. Search API에서는 이 Profile Geo 메타데이터를 2015년 2월부터 사용할 수 있습니다. Profile Geo 메타데이터가 제공되기 전에 게시된 포스트의 경우, 정규화되지 않은 사용자 입력과 매칭하는 데 사용할 수 있는 `bio_location:` Operator를 사용할 수 있습니다.

<div id="shared-links-and-media">
  #### 공유 링크와 미디어
</div>

2012년 3월에 확장 URL enrichment가 도입되었습니다. 그 이전까지는 포스트 페이로드에 사용자가 제공한 URL만 포함되었습니다. 따라서 사용자가 단축 URL을 포함했다면, 관심 있는 (확장된) URL과 매칭하기가 어려울 수 있습니다. Search API에서는 이 메타데이터를 2012년 3월부터 제공합니다.

2016년 7월에 향상된 URL enrichment가 도입되었습니다. 이 향상된 버전은 웹사이트의 HTML title과 설명을 포스트 페이로드에 제공하며, 이에 대해 매칭할 수 있는 연산자(Operator)도 함께 제공합니다. 이 메타데이터는 2014년 12월부터 나타나기 시작합니다.

2016년 9월에 X는 ‘네이티브 첨부(native attachments)’를 도입하여, 뒤에 오는 공유 링크가 140자 포스트 글자 수 제한에 포함되지 않도록 했습니다. 두 종류의 URL enrichment는 이러한 공유 링크에도 계속 적용됩니다.

관련 검색 연산자(Search Operator)가 매칭을 시작한 시점은 다음과 같습니다:

* 2006년 10월 26일 - `has:links`
* 2011년 7월 20일 - `has:images` 및 `has:media`
* 2011년 8월 - [Expanded URLs enrichment](/ko/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments)와 함께 제공되는 `url:`. 2006년 9월만 해도 `(url:"spotify.com" OR url:gnip OR url:microsoft OR url:google OR url:youtube)`는 twitter&#95;entities와 gnip 객체에 urls[] 메타데이터가 없음에도 불구하고 http://x.com/Adam/statuses/16602와 매칭됩니다. “youtube.com”은 urls[] 메타데이터 없이도 url:youtube와 매칭되는 메시지 콘텐츠의 예입니다.
* 2015년 2월 10일 - 네이티브 동영상에 대한 `has:videos`. 2010/08/28부터 2015/02/10 사이에는 이 연산자는 youtube.com, vimeo.com, vivo.com과 같은 일부 동영상 호스팅 사이트에 대한 링크가 포함된 포스트와 매칭됩니다.
* 2016년 5월 1일 - [Enhanced URLs enrichment](/ko/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments)를 기반으로 하는 `url_title:` 및 `url_description:`이 일반에 제공되기 시작했습니다. 첫 번째 Enhanced URL 메타데이터는 2014년 12월에 등장하기 시작했습니다.

<div id="enterprise-search-apis">
  ### Enterprise search APIs
</div>

엔터프라이즈 검색 API는 두 가지가 있습니다:

* 30-Day Search API - 지난 30일 이내에 게시된 트윗을 제공합니다.
* Full-Archive Search API - 2006년 3월에 게시된 첫 트윗부터의 전체 아카이브 트윗을 제공합니다.

이들 검색 API는 공통된 설계로 구현되어 있으며, 아래 문서는 두 API 모두에 적용됩니다. 2022년 9월 29일부터 생성된 트윗의 경우 Tweet 객체에는 수정 이력을 설명하는 트윗 편집 메타데이터가 포함됩니다. 자세한 내용은 [&quot;Edit Tweets&quot;](/ko/x-api/enterprise-gnip-2.0/fundamentals/edit-tweets) 기본 설명 페이지를 참고하세요.

아래에서는 엔터프라이즈 검색 API를 통합할 때 필요한 중요한 세부 정보를 확인할 수 있습니다:

* 트윗 data 및 개수 요청 메서드
* 인증
* 페이지네이션
* API 요청 매개변수 및 요청 예시
* API 응답 JSON 페이로드 및 응답 예시
* HTTP 응답 코드

엔터프라이즈 API는 트윗 아카이브에 대한 저지연, 손실 없는(full-fidelity), 쿼리 기반 액세스를 제공합니다. 두 API 간의 유일한 차이는 검색할 수 있는 기간으로, 직전 30일 또는 2006년까지 포함하는 전체 아카이브 중에서 선택하는 점뿐입니다. 기간은 분 단위까지 지정할 수 있습니다. 트윗 data는 쿼리와 일치하는 가장 최신 트윗부터 시작하여 역순 시간 순서로 제공됩니다. 트윗은 게시 후 약 30초가 지나면 검색 API를 통해 조회할 수 있습니다.

<div id="methods">
  #### Methods
</div>

엔터프라이즈 검색의 기본 URI는 `https://gnip-api.x.com/search/`입니다.

| Method | Description |
| :--- | :--- |
| [POST /search/:product/accounts/:account&#95;name/:label](#SearchRequests) | 지정된 PowerTrack 규칙과 일치하는 지난 30일 동안의 포스트를 조회합니다. |
| [POST /search/:product/accounts/:account&#95;name/:label/counts](#CountRequests) | 지정된 PowerTrack 규칙과 일치하는 지난 30일 동안의 포스트 개수를 조회합니다. |

여기서:

* `:product`는 요청을 보내는 검색 엔드포인트를 나타내며, `30day` 또는 `fullarchive` 중 하나입니다.
* `:account_name`은 console.gnip.com에 표시되는, 계정과 연결된 (대소문자를 구분하는) 이름입니다.
* `:label`은 console.gnip.com에 표시되는, 검색 엔드포인트와 연결된 (대소문자를 구분하는) 레이블입니다.

예를 들어 TwitterDev 계정이 레이블이 &#39;prod&#39;(production의 약어)인 30일 검색 제품을 가지고 있다면, 검색 엔드포인트는 다음과 같습니다.

* 데이터 엔드포인트: [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json)
* 카운트 엔드포인트: [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json)

완전한 엔터프라이즈 검색 API 엔드포인트는 [https://console.gnip.com](https://console.gnip.com)에서 확인할 수 있습니다.

아래에는 curl이라는 간단한 HTTP 유틸리티를 사용한 여러 예제 요청이 있습니다. 이 예제들은 URL에 `:product`, `:account_name`, `:label`을 사용합니다. 이 예제들을 사용할 때는 URL을 본인의 정보로 업데이트해야 합니다.

<div id="authentication">
  #### 인증
</div>

Enterprise search API에 대한 모든 요청은 [https://console.gnip.com](https://console.gnip.com) 계정에 로그인할 때 사용하는 유효한 이메일 주소와 비밀번호 조합을 사용한 HTTP &#95;Basic Authentication&#95;을 사용해야 합니다. 각 요청마다 이 자격 증명을 *Authorization* 헤더에 포함해야 합니다.

<div id="requestresponse-behavior">
  #### 요청/응답 동작
</div>

`fromDate` 및 `toDate` 매개변수를 사용하면 API가 지원하는 어떤 기간이든 요청할 수 있습니다. 30-Day search API는 가장 최근 31일간의 트윗을 제공합니다(‘30-Day’ API라고 부르지만, 사용자가 한 달 전체에 대한 요청을 할 수 있도록 31일을 제공합니다). Full-Archive search API는 최초의 트윗(2006년 3월 21일)까지 거슬러 올라가는 트윗을 제공합니다. 다만, 단일 응답에는 지정한 `maxResults` 값 또는 31일 중 더 작은 쪽까지만 포함됩니다. 일치하는 데이터의 양이나 시간 범위가 지정한 `maxResults` 또는 31일을 초과하는 경우, 지정한 전체 시간 범위를 페이지네이션하기 위해 사용해야 하는 `next` 토큰을 받게 됩니다.

예를 들어, Full-Archive search를 사용하여 2017년 1월 1일부터 2017년 6월 30일까지 쿼리와 일치하는 모든 트윗을 조회하려 한다고 가정해 보겠습니다. 이 6개월 전체 기간을 `fromDate` 및 `toDate` 매개변수를 사용하여 요청에 지정합니다. 검색 API는 처음 ‘페이지’의 트윗을, `maxResults` 매개변수(기본값은 100)에 해당하는 트윗 개수만큼 반환합니다. 더 많은 트윗이 존재한다고 가정하면(실제로 대부분 더 많습니다), API는 또한 다음 ‘페이지’의 데이터를 요청할 수 있도록 하는 `next` 토큰을 제공합니다. 이 과정은 API가 더 이상 `next` 토큰을 반환하지 않을 때까지 반복됩니다. 자세한 내용은 다음 섹션을 참조하세요.

<div id="pagination">
  #### 페이지네이션
</div>

데이터 요청과 카운트 요청을 모두 수행할 때, 하나의 응답으로 반환할 수 있는 양보다 더 많은 데이터가 있는 경우가 많습니다. 이 경우 응답에 `next` 토큰이 포함됩니다. `next` 토큰은 최상위 수준의 JSON 속성으로 제공됩니다. `next` 토큰이 제공되면, 추가로 가져와야 할 데이터가 더 있다는 의미이므로 계속해서 API 요청을 보내야 합니다.

**참고:** `next` 토큰의 동작은 데이터 요청과 카운트 요청에서 약간 다르며, 두 경우 모두 아래에서 설명하고 예시 응답은 API 레퍼런스 섹션에 제공되어 있습니다.

<div id="data-pagination">
  ##### 데이터 페이지네이션
</div>

데이터에 대한 요청은 단일 응답으로 반환할 수 있는 양보다 더 많은 데이터를 반환해야 하는 경우가 많습니다. 각 데이터 요청에는 요청당 반환할 트윗의 최대 개수를 설정하는 매개변수가 포함됩니다. 이 `maxResults` 매개변수의 기본값은 100이며, 10~500 범위로 설정할 수 있습니다. 요청에 사용한 `maxResults` 매개변수보다 더 많은 트윗이 쿼리와 일치하는 경우, 응답에는 &#39;next&#39; 토큰(루트 수준 JSON 속성으로)이 포함됩니다. 이 &#39;next&#39; 토큰은 이후 요청에서 해당 쿼리에 대해 일치하는 트윗의 다음 부분(즉, 다음 &quot;페이지&quot;)을 가져오는 데 사용됩니다. 쿼리 결과의 마지막 &quot;페이지&quot;에 도달해 더 이상 &#39;next&#39; 토큰이 제공되지 않을 때까지 &#39;next&#39; 토큰은 계속 제공됩니다.

다음 &quot;페이지&quot;의 데이터를 요청하려면, 원래와 완전히 동일한 쿼리를 사용해야 하며, 사용했다면 `query`, `toDate`, `fromDate` 매개변수를 모두 포함해야 하고, 이전 응답에서 받은 값을 설정한 &#39;next&#39; 요청 매개변수도 함께 포함해야 합니다. 이는 GET 또는 POST 요청 모두에서 사용할 수 있습니다. 단, GET 요청의 경우 &#39;next&#39; 매개변수는 URL 인코딩되어야 합니다.

쿼리에서 지정한 기간에 포함된 모든 트윗을 받을 때까지, 이전 쿼리에서 받은 &#39;next&#39; 요소를 계속 전달할 수 있습니다. &#39;next&#39; 요소가 포함되어 있지 않은 응답을 받으면, 이는 마지막 페이지에 도달했으며 지정된 쿼리와 기간에 대해 더 이상 사용 가능한 데이터가 없음을 의미합니다.

<div id="counts-pagination">
  ##### Counts 페이지네이션
</div>

`counts` 엔드포인트는 쿼리와 연관된 트윗량을 일 단위, 시간 단위, 또는 분 단위 기준으로 제공합니다. `counts` API 엔드포인트는 최대 31일치 `counts` 페이로드에 대해 타임스탬프가 포함된 카운트 배열을 반환합니다. 31일보다 많은 기간의 `counts`를 요청하는 경우 `next` 토큰이 제공됩니다. `data`용 `next` 토큰과 마찬가지로, 원래 요청과 완전히 동일한 쿼리를 수행해야 하며, 이전 응답에서 받은 값을 `next` 요청 매개변수에 포함해야 합니다.

31일보다 많은 기간의 `counts`를 요청하는 경우 외에도 `next` 토큰이 제공되는 또 다른 상황이 있습니다. 볼륨이 큰 쿼리에서는 `counts`를 생성하는 데 걸리는 시간이 길어져 응답 타임아웃이 발생할 수 있습니다. 이 경우 31일보다 적은 기간의 `counts`만 받게 되지만, 전체 `counts` 페이로드를 계속 요청할 수 있도록 `next` 토큰이 제공됩니다. ***중요:*** 타임아웃이 발생하면 항상 전체 &quot;버킷&quot; 단위로만 반환됩니다. 예를 들어 2.5일 분량의 결과는 하루 단위의 전체 &quot;버킷&quot; 2개로 반환됩니다.

<div id="additional-notes">
  ##### 추가 참고 사항
</div>

* 검색 요청에서 fromDate 또는 toDate를 사용하는 경우, 지정한 시간 범위 내의 결과만 받게 됩니다. 시간 범위 내의 마지막 결과 그룹에 도달하면 &#39;next&#39; 토큰을 받지 못합니다.
* &#39;next&#39; 요소는 기본값 100을 포함해 10-500 사이의 어떤 maxResults 값과도 함께 사용할 수 있습니다. maxResults는 각 응답에서 반환되는 트윗 개수를 결정하지만, 결국 모든 결과를 가져오는 것을 막지는 않습니다.
* &#39;next&#39; 요소는 만료되지 않습니다. 동일한 &#39;next&#39; 쿼리를 사용한 여러 요청은, 요청이 언제 이루어졌는지에 관계없이 동일한 결과를 받게 됩니다.
* &#39;next&#39; 매개변수를 사용해 결과를 페이지 단위로 조회할 때, 쿼리 범위의 경계에서 중복이 발생할 수 있습니다. 애플리케이션은 이러한 중복을 허용할 수 있어야 합니다.

<div id="example-post-request">
  ###### POST 요청 예시
</div>

* POST 요청의 매개변수는 아래 예시와 같이 JSON 형식의 본문으로 전송됩니다.
* 조회하려는 PowerTrack 규칙의 모든 요소(예: 키워드, bounding&#95;box:와 같은 기타 연산자)는 &#39;query&#39; 매개변수에 넣어야 합니다.
* 규칙의 일부를 쿼리 URL의 개별 매개변수로 분리하지 마십시오.

다음은 초기 data 요청을 수행하기 위한 POST 요청(cURL 사용) 명령 예시입니다:

```bash
    curl -X POST -u<username> "https://gnip-api.x.com/search/:product/accounts/:account_name/:label.json" -d '{"query":"from:twitterDev","maxResults":500,"fromDate":"yyyymmddhhmm","toDate":"yyyymmddhhmm"}'
```

| 422 | Unprocessable Entity | 쿼리에 잘못된 매개변수(예: 잘못된 PowerTrack 규칙)가 포함된 경우 반환됩니다. |
| 429 | Unknown Code | 앱이 연결 요청 한도를 초과했습니다. 이에 해당하는 JSON 메시지는 다음과 유사한 형태입니다. |
| 500 | Internal Server Error | 서버 측에서 오류가 발생했습니다. 지수 백오프 패턴을 사용하여 요청을 다시 시도하세요. |
| 502 | Proxy Error | 서버 측에서 오류가 발생했습니다. 지수 백오프 패턴을 사용하여 요청을 다시 시도하세요. |
| 503 | Service Unavailable | 서버 측에서 오류가 발생했습니다. 지수 백오프 패턴을 사용하여 요청을 다시 시도하세요. |

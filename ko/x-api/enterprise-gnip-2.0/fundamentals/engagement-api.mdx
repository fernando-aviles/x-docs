<div id="overview">
  ## 개요
</div>

[`Enterprise`](https://developer.x.com/en/products/x-api/enterprise)

*이는 관리형 액세스 레벨에서만 제공되는 엔터프라이즈 API입니다. 이 API를 사용하려면 먼저 엔터프라이즈 영업 팀을 통해 계정을 설정해야 합니다. [자세히 알아보기](/ko/x-api/enterprise-gnip-2.0/enterprise-gnip)*

Engagement API는 포스트 노출(impression) 및 참여(engagement) 지표에 접근할 수 있도록 해줍니다. 대부분의 지표와 엔드포인트는 [OAuth 1.0a User Context](/ko/resources/fundamentals/authentication)를 사용해 인증해야 하지만, /totals 엔드포인트와 함께 [OAuth 2.0 Bearer Token](/ko/resources/fundamentals/authentication#oauth-2-0)을 사용하면 공개 Favorite, Retweet, Reply, Video Views 지표에 접근할 수 있습니다.  

**참고:** 일부 X 웹 대시보드에 보고된 데이터와 Engagement API에서 보고되는 데이터 간에 차이가 있을 수 있습니다. 이러한 차이는 웹 대시보드가 일반적으로 선택된 기간 내에 발생한 참여 및/또는 노출만 표시하기 때문에 발생합니다. 예를 들어, 웹 대시보드는 달력 상 한 달 동안의 포스트에 대한 참여만 표시할 수 있지만, Engagement API는 해당 달 범위를 벗어나더라도 요청한 시간 범위 안에 포함되는 참여까지 표시할 수 있습니다. 이러한 경우에는 Engagement API를 신뢰할 수 있는(유효한) 데이터 소스로 간주해야 합니다.
 

<div id="request-endpoints">
  ### 요청 엔드포인트
</div>

Engagement API에는 다음 세 가지 엔드포인트가 있습니다.

<div id="current-totals-totals">
  #### 현재 총합: [/totals]
</div>

* 요청은 원하는 포스트에 대해 노출 수(impressions) 총합과 참여 수(engagements) 총합 지표를 반환합니다
* 다음 지표만 제공합니다: Impressions, Engagements, Favorites, Replies, Retweets, Quote Tweets, Video Views
* OAuth 1.0a User Context를 사용하여 **최근 90일 이내**에 생성된 포스트에 대한 **Impressions** 및 **Engagements** 지표 조회를 지원합니다
* OAuth 2.0 Bearer Token을 사용하여 **모든 포스트**에 대한 **Favorites, Retweets, Quote Tweets, Replies,** 및 **Video Views** 지표 조회를 지원합니다
* 결과는 요청이 수행되는 시점의 현재 노출 수와 참여 수 총합을 기준으로 합니다
* 대시보드 보고서를 구성하고 다양한 @handle 전반에 걸친 참여율을 계산하는 데 적합합니다
* 요청당 최대 250개의 포스트에 대한 지표 요청을 지원합니다
   

<div id="last-28-hours-28hr">
  #### 지난 28시간: [/28hr]
</div>

* 요청은 노출 수에 대한 총합 지표, 참여 수에 대한 총합 지표, 그리고 지난 28시간 동안 발생한 개별 참여 지표의 세부 항목별 값을 함께 반환할 수 있습니다.
* 데이터는 포스트 ID별로, 그리고 전체 집계, 일 단위, 시간 단위의 시계열 기준으로 그룹화할 수 있습니다.
* 최근에 생성된 콘텐츠의 성과를 추적하는 데 적합합니다.
* 사용 가능한 모든 지표를 지원합니다.
* 요청당 최대 25개의 포스트에 대한 지표 요청을 지원합니다.
   

<div id="historical-historical">
  #### Historical: [/historical]
</div>

* 요청은 최근 1년 동안의 노출 수, 참여 수, 그리고 개별 참여 지표의 세부 내역을, 포스트 생성 시간이 아닌 참여 시점을 기준으로 반환할 수 있습니다.
* 요청은 시작 날짜와 종료 날짜 파라미터를 지원하여, 최대 4주 길이의 특정 기간으로 범위를 좁힐 수 있는 유연성을 제공합니다.
* 포스트 참여 data는 최대 과거 365일까지로 제한됩니다.
* data는 포스트 ID별로 그룹화하거나, 일 단위 또는 시간 단위로 집계된 시계열 형태로 그룹화할 수 있습니다.
* 최근 성과를 과거 벤치마크와 비교 평가하거나, @handle의 과거 성과 추이를 파악하는 데 적합합니다.
* 사용 가능한 모든 지표를 지원합니다.
* 요청당 최대 25개의 포스트에 대해 지표를 요청할 수 있습니다.

<div id="engagement-groupings">
  ### 참여 그룹화
</div>

그룹화를 사용하면 반환된 참여 지표를 사용자 지정 방식으로 구성할 수 있습니다. 요청에는 최대 3개의 그룹화를 포함할 수 있습니다. 다음 값 중 하나 이상을 기준으로 지표를 그룹화하도록 선택할 수 있습니다:

*세 엔드포인트 모두에서 지원합니다:*

* tweet.id
* engagement.type
   

*`/28hr` 및 `/historical` 엔드포인트는 시계열 지표를 제공할 수 있으므로 다음을 지원합니다:*

* engagement.day
* engagement.hour

그룹화에 대해 더 자세히 알아보려면 가이드 섹션의 [Engagement API Grouping](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings) 페이지를 방문하세요.

<div id="introduction">
  #### 소개
</div>

이 문서의 목적은 개발자에게 Engagement API 연동에 대한 개요를 제공하는 것입니다. 먼저 왜 연동해야 하는지(연동의 이유)를 살펴본 뒤, 기술적으로 어떻게 연동하는지(구현 방법)에 대한 세부 내용을 살펴보겠습니다.

<div id="what-does-the-engagement-api-provide">
  ##### **Engagement API는 무엇을 제공하나요?**
</div>

* Engagement API는, 해당 계정이 [3-legged OAuth](/ko/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow)를 사용해 앱이 자신을 대신해 지표를 요청하도록 승인한 경우, 지난 90일 동안 해당 X 계정이 소유한 포스트에 대한 노출 수(impression)와 참여(engagement) 데이터를 제공합니다. 구현이 쉽지만 강력한 이 솔루션은 노출 수와 URL 클릭, #해시태그 클릭 등 다양한 심층 참여 데이터를 즉시 제공합니다.
* Engagement API는 어떤 포스트에 대해서든 좋아요, 리트윗, 인용 트윗, 답글, 동영상 조회수의 총합 지표를 제공합니다. 이는 개별 포스트 또는 포스트 모음에 대한 기본적인 참여 데이터를 수집하는 강력한 방법으로 활용할 수 있습니다.
* Engagement API는 15개 이상의 성과 지표를 사용해 콘텐츠 성과를 효과적으로 측정할 수 있게 함으로써, 소셜 리스닝, 마케팅, 퍼블리싱 플랫폼에 X에서의 ROI를 측정할 수 있는 새로운 가치를 제공합니다.
* Engagement API는 요청/응답 API로, 앱 개발자가 포스트 ID, 원하는 지표, 그리고 기간을 포함한 요청을 보내면, 해당 요청에 대해 API가 즉시 데이터를 반환합니다.
   

<div id="why-integrate-example-use-cases">
  ##### **통합해야 하는 이유와 예시 활용 사례**
</div>

* 내 콘텐츠의 전체 도달 범위를 파악해 얼마나 많은 사람이 보는지 이해합니다. 동영상을 시청한 사람 수, 링크를 클릭한 사람 수, 해시태그를 클릭한 사람 수, 내 앱을 설치한 사람 수를 확인합니다.
* 전체 및 시계열 참여 지표를 모두 생성합니다.
* 모든 공개 포스트에 대해 기본적인 참여 지표(즐겨찾기, 리트윗, 인용 트윗, 답글)를 이해합니다.
* 이러한 지표를 활용해 어떤 유형의 포스트가 효과적인지 파악하여, 그런 포스트를 더 자주 게시하고 더 많은 노출과 더 많은 참여를 이끌어냅니다.
* 내 포스트 중 하나가 좋아요 100개 또는 다른 임계값에 도달할 때마다, 다른 보유 계정의 콘텐츠를 리트윗하는 등의 마케팅 행동을 자동화합니다.
* A/B 테스트 도구로 활용하기 위해 캠페인 간 성과를 벤치마킹하고 비교합니다.
* 고객 지원 부서에 어떤 유형의 콘텐츠가 좋은 반응을 얻는지 분석하여, 어떻게 그리고 언제 응답할지 결정합니다.
* 내 플랫폼에서 게시된 콘텐츠에 대한 분석 정보를 보여줍니다.
   

[Engagement API는 2016년에 출시되었으며](https://blog.x.com/official/en_us/a/2016/gnip-s-engagement-api-is-now-generally-available.html), 이러한 심층 참여 지표를 대규모로 제공한 최초의 X API였습니다. Engagement API는 사용이 간편하며 고객이 이 과정을 자동화할 수 있게 해줍니다. 다음은 예시 통합 사례를 설명하는 사례 연구입니다.

* [적십자와 함께 캠페인 성공 측정하기](https://blog.x.com/developer/en_us/topics/spotlight/2016/measuring-campaign-success-with-the-red-cross.html)[](https://simplymeasured.com/blog/true-twitter-impressions-and-url-clicks-new-from-simply-measured/#sm.0007werel134td8zqf02m2mduumr6)

이제 Engagement API를 사용하는 ‘이유’를 살펴보았으므로, 이제부터 기술적 세부 사항을 알아보겠습니다.

<div id="integrating-the-engagement-api">
  #### Engagement API 통합하기
</div>

<div id="introduction-to-api">
  ##### **API 소개**
</div>

Engagement API는 JSON으로 인코딩된 요청을 받아 JSON으로 인코딩된 참여 지표를 반환하는 간단한 RESTful API입니다. 요청은 세 가지 주요 부분으로 구성됩니다(자세한 내용은 링크를 참고하세요).

* ***포스트 ID*** 배열.
* 관심 있는 [지표 유형](https://developer.x.com/en/docs/x-api/v1/metrics/get-tweet-engagement/overview#EngagementTypes)을 지정하는 배열입니다. 유형에는 ‘impressions’, ‘retweets’, ‘hashtag&#95;clicks’, ‘user&#95;follows’ 등이 포함됩니다.
* [Engagement groupings](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings)으로, API 응답에서 참여 데이터가 어떻게 구성되기를 원하는지 나타내는 JSON 구조입니다.

많은 경우에 Engagement Types 및 Groupings은 요청마다 비교적 일정하게 유지되며, 포스트 ID만 변경됩니다.

Engagement API는 [세 가지 엔드포인트](https://developer.x.com/en/docs/x-api/v1/metrics/get-tweet-engagement/overview#RequestEndpoints)를 제공합니다.

* **Totals** - 포스트에 대한 전체 참여 합계를 제공합니다. 일부 지표는 모든 포스트에 대해 제공되지만, 다른 지표는 최근 90일에 대해서만 제공됩니다.
* **28 hour** - 지난 28시간 동안의 시계열 참여 지표를 제공합니다.
* **Historical** - 2014년 9월 1일 이후에 게시된 포스트에 대해, 최대 4주 연속 기간의 시계열 참여 지표를 제공합니다.

**/totals** 엔드포인트는 **요청당 최대 250개의 포스트**에 대한 지표 요청을 지원합니다. **/28hour** 및 **/historical** 엔드포인트는 **요청당 최대 25개**를 지원합니다.

이후에는 Engagement API에 대한 액세스 권한을 얻는 방법을 다룬 다음, API 요청을 수행하는 과정을 단계별로 살펴보고, OAuth 개요를 제공하며, 기타 기술 리소스에 대한 링크를 제공합니다.

  ##### **API 액세스 시작하기**
</div>

이 문서를 읽고 있다면, 대개 이미 Engagement API 액세스 권한을 가지고 있을 것입니다. 그렇지 않은 경우 Enterprise 계정 매니저에게 문의하시거나, [여기](/ko/x-api/enterprise-gnip-2.0/enterprise-gnip)에서 Enterprise 액세스를 신청하세요.

첫 번째 단계는 승인된 개발자 계정을 사용해 [Developer Console](/ko/resources/fundamentals/developer-portal)에서 [X 앱](/ko/resources/fundamentals/developer-apps)을 생성하는 것입니다. 계정 매니저가 액세스 권한을 제공하려면, 이 애플리케이션과 연결된 숫자형 App ID가 필요합니다. 개발자 계정을 새로 신청해야 하는 경우 [여기](/ko/resources/fundamentals/developer-apps)에서 신청할 수 있습니다.

첫 번째 단계는 JSON 형식의 API 요청을 구성하는 것입니다. 여기에는 배열에 담긴 두 개의 포스트 ID, 관심 있는 참여 유형(engagement type)의 배열, 그리고 응답에서 지표를 어떻게 구성해 받고 싶은지 나타내는, 사용자 정의 이름의 &quot;groupings&quot; JSON 객체가 포함됩니다. 우리의 요청은 다음과 같은 형태가 됩니다:

```json
{
  "tweet_ids": [
    1260294888811347969, 850006245121695744
  ],
  "engagement_types": [
    "retweets", "quote_tweets", "favorites", "replies"
  ],
  "groupings": {
    "engagement-types-by-id": {
      "group_by": [
        "Tweet.id", "engagement.type"
      ]
    }
  }
}
```

이러한 전체 메트릭을 조회하기 위해 https://data-api.x.com/insights/engagement/totals 엔드포인트로 JSON 요청을 POST합니다.

요청이 JSON으로 인코딩되어 있고 Gzip으로 압축되었음을 나타내기 위해 다음 헤더를 포함합니다(요청 본문이 커질 수 있음).

* Content-Type: application/json
* Accept-Encoding: gzip
   

요청을 보낼 때는 OAuth를 사용해 인증하며, 이에 대해서는 다음 섹션에서 더 자세히 설명합니다.

API는 다음과 같은 페이로드를 반환합니다.

```json
{
  "grouping name": {
    "1260294888811347969": {
      "favorites": "17111",
      "quote_tweets": "3254",
      "replies": "1828",
      "retweets": "5218"
    },
    "850006245121695744": {
      "favorites": "492",
      "quote_tweets": "66",
      "replies": "42",
      "retweets": "324"
    }
  }
}
```

응답에는 요청한 메트릭이 “groupings” 정의에서 설명한 구조로 포함되어 있으며, 첫 번째 계층에는 포스트 id별 메트릭이, 그다음 계층에는 참여 유형별 메트릭이 나열되어 있습니다.

비교적 간단합니다. OAuth로 인증하는 것이 처음이라면, 다음 섹션을 확인해 보세요.

<div id="authenticating-with-oauth">
  #### OAuth로 인증하기
</div>

OAuth는 기술 업계에서 널리 사용되는 인증 표준입니다. 이미 OAuth를 사용 중이라면(예를 들어 다른 X API와 함께) 아마도 언어별 OAuth 패키지를 사용해 복잡한 세부 사항을 모두 추상화하고 있을 것입니다. OAuth가 처음이라면 [X API와 함께 사용하는 OAuth](/ko/resources/fundamentals/authentication) 페이지를 방문하시거나, 더 자세한 내용을 보려면 [https://oauth.net](https://oauth.net/)으로 바로 이동해 주세요. 그런 다음, 통합에 사용하는 프로그래밍 언어에 맞는 OAuth 패키지를 찾아 그 패키지부터 시작하는 것을 권장합니다. 이러한 패키지를 사용할 때의 일반적인 인증 절차는 키와 토큰을 설정하고, HTTP 클라이언트 객체를 생성한 뒤, 그 객체를 사용해 요청을 보내는 방식입니다.

예를 들어, Ruby 생태계에서는 아래의 의사 코드가 Ruby gem ‘oauth’를 사용해 OAuth를 지원하는 앱을 만들고 POST 요청을 보내는 방법을 보여줍니다.

```js
require 'oauth'

#Assemble JSON request (as above).
request = make_json_request()

#Build an app consumer object with my app consumer key and secret.
consumer = OAuth::Consumer.new(keys['consumer_key'], keys['consumer_secret'], {:site => ‘https://data-api.x.com’})
#권한을 제공하는 계정에서 제공한 토큰으로 사용자 토큰 빌드. 앱 전용 #요청을 만드는 경우 (권한이 필요하지 않은 트윗을 /totals 엔드포인트로 확인), 이 단계는 #건너뛸 수 있습니다.
token = {:oauth_token => keys['access_token'], :oauth_token_secret => keys['access_token_secret']}

#Create oauth-enabled app object.
app = OAuth::AccessToken.from_hash(consumer, token)
#Make POST request.
result = app.post(“/insights/engagement/totals", request, {"content-type" => "application/json", "Accept-Encoding" => "gzip"})
```

Engagement API는 애플리케이션 전용 인증과 사용자 컨텍스트 인증을 모두 지원합니다. /totals 엔드포인트로 소유하지 않은 공개 포스트에 대한 참여 지표를 수집하는 경우, 별도의 사용자 권한이 필요하지 않으므로 애플리케이션 전용 인증을 사용할 수 있습니다. 이 경우 앱 키와 시크릿만으로 인증을 수행합니다.

OAuth는 또한 앱이 사용자와 연관된 토큰을 사용하여 “다른 사용자를 대신해” API 요청을 수행할 수 있도록 합니다. 사용자 토큰을 보유한 사용자가 게시한, 즉 소유한 포스트에 대한 참여 지표를 생성하는 경우에는 사용자 컨텍스트로 요청을 수행하게 되며, 이는 앱 키와 사용자별 액세스 토큰을 모두 사용해 인증한다는 의미입니다. 이러한 사용자 액세스 토큰은 일반적으로 &#39;[Sign-in with X](/ko/resources/fundamentals/authentication#log-in-with-x)&#39; 프로세스를 통해 제공되거나 사용자로부터 직접 획득됩니다(토큰을 사용자로부터 직접 획득하는 경우 반드시 [twurl](https://github.com/xdevplatform/xurl)을 사용해야 합니다). 사용자가 토큰을 제공하면 해당 토큰은 만료되지 않으며, 사용자가 토큰을 재설정하거나 비밀번호를 변경하지 않는 한 Engagement API에서 해당 사용자를 대신해 요청을 수행하는 데 계속 사용할 수 있습니다. 이러한 변경이 발생한 경우 사용자가 새 토큰을 다시 제공해야 합니다.

어떤 지표에 어떤 인증이 필요한지는 [이 표](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings)에서 확인할 수 있습니다.

<div id="selecting-an-engagement-api-endpoint">
  ### Engagement API 엔드포인트 선택하기
</div>

Engagement API는 다음과 같은 세 가지 개별 엔드포인트를 제공합니다:

* **[Totals](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement)** - &#39;owned&#39; 또는 &#39;unowned&#39; 포스트에서 선택된 지표의 총계를 제공합니다. 일부 지표는 모든 포스트에 대해 제공되지만, 일부 지표는 최근 90일 이내에 게시된 포스트에 대해서만 제공됩니다. 요청당 최대 250개의 포스트를 지원합니다.
* **[28 hour](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement)** - 최근 28시간 동안의 &#39;owned&#39; 포스트에 대한 시계열 Engagement 지표를 제공합니다. 요청당 최대 25개의 포스트를 지원합니다.
* **[Historical](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-historical)** - 2014년 9월 1일 이후에 게시된 &#39;owned&#39; 포스트에 대해, 최대 4주간의 연속 기간에 대한 시계열 Engagement 지표를 제공합니다. 요청당 최대 25개의 포스트를 지원합니다.
   

각 엔드포인트는 고유한 특성을 가지고 있습니다. 세 가지 모두를 사용할 계획이든, 또는 어떤 엔드포인트가 사용 사례에 가장 잘 맞는지 결정하려고 하든, 이들 간의 차이를 이해하는 것이 중요합니다.

아래에서는 몇 가지 핵심 개념을 소개한 뒤, 세 가지 엔드포인트를 더 자세히 살펴보고, 일반적으로 특정 엔드포인트에 매핑되는 예시 사용 사례를 제시합니다. 이 정보가 세 가지 엔드포인트를 더 효율적으로 통합하는 데 도움을 주거나, 단일 엔드포인트 중 어떤 것이 여러분의 목적에 가장 적합한지 결정하는 데 도움이 되기를 바랍니다.
 

<div id="key-concepts">
  #### 핵심 개념
</div>

세 가지 Engagement API 엔드포인트에서 제공하는 다양한 기능과 데이터를 설명하는 데 도움이 되는 핵심 개념 몇 가지가 있습니다.
 

<div id="impressions-and-engagement-metrics">
  ##### 노출 수 및 참여 지표
</div>

노출 수는 X 플랫폼에서 특정 포스트가 자연(organic) 환경에서 조회된 횟수를 의미합니다. 프로모션(광고) 또는 유료(Paid) 환경에서 노출된 포스트에서 발생한 노출 수는 포함되지 않습니다. Engagement API 도입 이전에는 포스트 노출 수가 잠재적인 조회 수만을 나타내는 지표였습니다. 이는 작성자의 계정과 해당 콘텐츠를 리트윗한 계정의 팔로워 수를 기반으로 계산되었으며, 특정 사용자가 실제로 그 포스트를 보았는지는 고려하지 않았습니다.

Engagement API가 생성하는 노출 지표는 포스트가 실제로 사용자 화면에 렌더링되어 표시된 횟수를 측정한 값입니다. 사용자가 귀하의 계정을 팔로우하고 있더라도, 그 사용자가 해당 포스트를 보지 못했다면 노출로 계산되지 않습니다.

Engagement API는 사용자가 포스트를 접했을 때 취할 수 있는 개별 행동을 나타내는 14개의 고유한 참여 [지표 유형](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#available-metrics)을 제공합니다. 여기에는 리트윗, 좋아요, 답글, #해시태그·링크·미디어 등의 엔티티 클릭, 작성자 팔로우, 작성자 프로필 보기 등이 포함됩니다. 이러한 개별 행동은 모두 하나의 Engagements(참여) 지표로 집계됩니다.

<div id="owned-and-unowned-x-content">
  ##### 소유 및 비소유 X 콘텐츠
</div>

Engagement API는 소유 포스트와 비소유 포스트를 명확히 구분합니다. 소유 포스트는 귀하의 계정에서 게시된 포스트이거나, Engagement data를 요청할 수 있는 권한을 획득한 포스트를 의미합니다. 다른 X API와 마찬가지로, 다른 X 사용자/계정이 귀하를 대신해 API 요청을 보낼 수 있도록 허용하는 액세스 토큰을 공유하면 해당 권한을 얻게 됩니다. 이러한 토큰을 얻는 일반적인 방법은 [‘Sign in with X’ 절차](/ko/resources/fundamentals/authentication#log-in-with-x)를 사용하는 것입니다.

`/totals` 엔드포인트는 소유 및 비소유 포스트 모두에 대한 Engagement data를 제공합니다. 비소유 포스트의 경우, 포스트 화면에 공개적으로 표시되는 Favorite, Retweet, Reply 지표를 요청할 수 있습니다. 이 지표와 관련해 Engagement API가 제공하는 가치는 이러한 지표를 자동화된 방식으로 대규모로 수집할 수 있는 능력입니다. 소유 포스트의 경우, `/totals` 엔드포인트는 Impression 및 (총) Engagement 지표도 제공합니다.

`/28hr` 및 `/historical` 엔드포인트는 소유 포스트에 대한 지표만 제공하므로, 이 엔드포인트들로 요청을 보낼 때는 사용자 컨텍스트를 함께 전달해야 합니다.

<div id="total-and-time-series-engagement-data">
  ##### 전체 및 시계열 참여 데이터
</div>

`/totals` 엔드포인트는 이름에서 알 수 있듯이 각 참여 유형에 대한 총합만 제공합니다. 이 수치는 포스트가 게시된 이후 현재까지의 최신 누적 합계를 나타냅니다. 포스트가 막 게시된 뒤 해당 포스트의 메트릭을 반복해서 요청하면, 일반적으로 각 요청마다 이 합계 값이 변경됩니다.

`/28hr` 및 `/historical` 엔드포인트는 총합과 시계열 데이터를 모두 제공할 수 있습니다. 시계열 데이터를 요청할 때는 참여 메트릭을 일 단위 또는 시간 단위 데이터로 집계할 수 있습니다.   

`/28hr` 및 `/historical` 엔드포인트로 시계열 데이터를 요청하는 방법은 [engagement groupings](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings) 문서를 참고하세요.

<div id="endpoints-and-example-use-cases">
  #### 엔드포인트와 사용 예시
</div>

위에서 살펴본 특성과 차이점을 바탕으로, 각 엔드포인트는 일반적으로 서로 다른 유형의 사용 사례에 대응합니다. 특정 사용 사례에 가장 적합한 엔드포인트를 선택할 수 있도록, 아래에 몇 가지 예시적인 사용자 요구 문장과 이를 가장 잘 충족하는 엔드포인트를 제시합니다.

<div id="totals">
  ##### **/totals**
</div>

* 일부 지표 유형(노출수, 참여수, 즐겨찾기, 리트윗, 인용 트윗, 답글, 동영상 조회수)만 필요합니다.
* 내가 소유한 포스트뿐만 아니라 모든 포스트에 대한 기본 참여 데이터에 접근해야 합니다.
* 경쟁사와 성과를 비교하고 싶습니다.
* 내가 소유하지 않은 포스트가 포함된 해시태그나 캠페인에 대한 기본 참여 통계를 추적하고 싶습니다.
* 일별이나 시간별로 세분화된 데이터는 필요 없고, 요청 시점의 현재 총합만 알면 됩니다.
* 보고서나 대시보드에 표시할 단일 지표만 필요하고, 데이터를 별도로 저장하고 싶지 않습니다.
* 페이지 로드 시점에 데이터를 표시하고 싶으며, 요청만 보내서 응답을 받으면 됩니다.
* 하루에 수십만 개 또는 수백만 개의 포스트에 대한 데이터에 접근해야 합니다.
   

<div id="28hr">
  ##### **/28hr**
</div>

* 17가지 모든 지표 유형에 대한 접근 권한이 필요합니다.
* 지난 28시간 동안 게시된 최신 포스트의 데이터를 보고 싶습니다.
* 하루에 한 번 실행되는 작업이 있어서, 필요한 데이터는 직전 하루치뿐입니다.
* 지표를 일별 또는 시간별로 나누어 확인할 수 있어야 합니다.
* 대시보드에서 시간 단위 활동을 시계열로 분할해 보여주고 싶습니다.
* 하루에 수십만 개의 포스트에 대해 높은 수준의 접근 권한이 필요합니다.
* 저장소 용량이 있어서 하루에 한 번 데이터를 새로고침하고 누적 합계를 유지할 수 있습니다.
   

<div id="historical">
  ##### **/historical**
</div>

* 모든 17가지 지표 유형에 대한 접근 권한이 필요합니다.
* 2014년 9월까지 거슬러 올라가는 포스트 생성 내역에 대한 과거 데이터가 필요합니다.
* 캠페인 간 비교가 가능한 상세한 과거 분석을 보여주고 싶습니다.
* 지표가 일별 또는 시간별로 구분되어야 합니다.
* Engagement API에 대한 높은 수준의 접근 권한은 필요 없고, 하루에 수백~수천 개의 포스트에 대한 데이터만 조회하면 됩니다.

<div id="engagement-api-key-characteristics">
  ### Engagement API 주요 특성
</div>

* JSON 데이터를 제공하는 **RESTful API**로, JSON 데이터 본문을 사용하는 POST 요청을 지원합니다.
* **요청 유형:** 클라이언트 앱은 다음과 같은 유형의 요청을 수행할 수 있습니다.
  * **총 참여 수** -- /totals 엔드포인트로의 HTTP POST 요청
  * **최근 28시간 참여 수** -- /28hr 엔드포인트로의 HTTP POST 요청
  * **과거 참여 수** -- /historical 엔드포인트로의 HTTP POST 요청
* **OAuth 인증:**
  * [OAuth 1.0 User Context](/ko/resources/fundamentals/authentication): 사용자가 [3-legged OAuth](https://developer.x.com/resources/fundamentals/authentication/obtaining-user-access-tokens)를 사용해 귀하의 앱을 승인한 경우, 해당 사용자가 소유한 포스트에 대해 제공되는 모든 지표를 조회할 수 있습니다. 요청을 보낼 때는 반드시 그 사용자의 Access Token을 사용해야 합니다.[](/ko/resources/fundamentals/authentication)
  * [OAuth 2.0 Bearer Token](/ko/resources/fundamentals/authentication#oauth-2-0): 선택된 지표(Retweets, Quote Tweets, Replies, Favorites, Video Views)는 모든 공개 포스트에 대해 사용할 수 있습니다. 
* **요청 메타데이터 및 구조**: 요청 데이터는 포스트 ID 배열, 참여 유형 배열, 참여 그룹화 구조로 구성된 JSON 객체입니다.
* **요청당 포스트 수:**
  * /totals 엔드포인트: 포스트 ID 250개
  * /28hr 엔드포인트: 포스트 ID 25개
  * /historical 엔드포인트: 포스트 ID 25개
* **참여 지표 제공 범위:**
  * **/totals** -- 포스트가 게시된 시점부터의 지표 총합입니다. Impressions와 Engagements는 최근 90일 내에 게시된 포스트에 대해 제공되며, Retweets, Quote Tweets, Replies, Favorites, Video Views는 모든 포스트에 대해 제공됩니다.
  * **/28hr** -- 요청 시점으로부터 최근 28시간입니다.
  * **/historical** -- 2014년 9월 1일부터 시작되는 임의의 28일 기간입니다.
* **지표 유형:** 각 요청에는 [Metric Types](http://support.gnip.com/apis/engagement_api/overview.html#EngagementTypes) 배열이 포함됩니다. 사용 가능 여부는 엔드포인트에 따라 달라지며, /totals 엔드포인트를 사용하는 경우에는 포스트가 사용자 권한을 부여받은 포스트인지 여부에 따라 달라집니다.
  * /totals 엔드포인트:
    * 모든 포스트: Favorites, Retweets, Quote Tweets, Replies, Video Views
    * OAuth 1.0a User Context 필요: Impressions, Engagements, Favorites, Replies, Retweets
  * /28hr 및 /historical 엔드포인트(OAuth 1.0a User Context와 포스트 소유자의 Access Token 필요): Impressions, Engagements, Favorites, Replies, Retweets, URL Clicks, Hashtag Clicks, Detail Click, Permalink Clicks, Media Clicks, App Install Attempts, App Opens, Post Emails, Video Views, Media Views
* **참여 그룹화(Engagement groupings):** 각 요청에는 [Engagement Groupings](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings) 배열이 포함됩니다. 이러한 그룹화를 사용하면 반환된 지표가 어떻게 구성될지 사용자 정의할 수 있습니다. 요청당 최대 세 개의 그룹화를 포함할 수 있습니다. 지표는 다음 값별로 구성할 수 있습니다.
  * 모든 엔드포인트: 포스트 ID, 참여 유형(Engagement Type)
  * /28hr 및 /historical 엔드포인트: 다음 추가 그룹을 지정하면 시계열(time-series) 데이터를 제공합니다: 참여 일자(Engagement Day), 참여 시간(Engagement Hour)
* **통합 관련 기대 사항:** 귀하의 팀은 다음 사항에 대한 책임을 집니다.
  * 요청에 포함된 포스트 ID에 대한 참여 지표를 반환하는 Engagement API에 HTTP 요청을 보낼 수 있는 클라이언트 앱을 생성하고 유지 관리합니다.
* **제한 사항**
* Video Views는 게시 후 최대 1800일 이내의 포스트에 대해서만 제공됩니다.

<div id="authenticating-with-the-engagement-api">
  ### Engagement API로 인증하기
</div>

> **주의**: 
>
> Engagement API를 사용하기 전에 X가 귀하의 개발자 App에 대해 Engagement API 접근 권한을 활성화해야 합니다. 이를 위해 인증에 사용할 App ID를 계정 매니저 또는 기술 지원 팀과 반드시 공유해 주시기 바랍니다.

Engagement API에서는 두 가지 인증 방식을 사용할 수 있습니다: [OAuth 1.0a](/ko/resources/fundamentals/authentication#oauth-1-0a-2)와 [OAuth 2.0 Bearer Token](/ko/resources/fundamentals/authentication#bearer-token-also-known-as-app-only). 

**OAuth 2.0 Bearer Token**(“application-only”라고도 함)을 사용하면 공개되어 있는 참여(engagement) 지표에 접근할 수 있습니다. 이 인증 방식은 [/totals 엔드포인트](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-totals)에 요청을 보낼 때, 공개된 모든 포스트에 대해 Favorites(일명 Likes), 리트윗, 인용 트윗, 답글, 동영상 조회수의 전체 합계를 가져오는 데 사용할 수 있습니다. 

**OAuth 1.0a**(“user context”라고도 함)를 사용하면 사용자를 대신해 요청을 보내고, 해당 사용자에게 속한 비공개 참여 지표에 접근할 수 있습니다. 

이 인증 방식은 다음의 경우에 필수입니다.

* [/28hr 엔드포인트](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-28hr)와 [/historical 엔드포인트](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-historical)에 전송되는 모든 요청
* 다음 비공개 지표에 접근하는 경우: 노출수(Impressions), 참여수(Engagements), 미디어 조회수(Media Views), 미디어 참여수(Media Engagements), URL 클릭수(URL Clicks), 해시태그 클릭수(Hashtag Clicks), 세부 정보 펼치기(Detail Expands), 퍼머링크 클릭수(Permalink Clicks), 앱 설치 시도(App Install Attempts), 앱 실행(App Opens), 이메일 포스트(Email Post), 사용자 팔로우(User Follows), 사용자 프로필 클릭수(User Profile Clicks)

OAuth 1.0a로 요청을 보낼 때는, 관심 있는 포스트 또는 보호된 리소스의 소유자인 사용자의 Access Token(Access Token과 Secret)을 포함해야 합니다. 보호된 사용자 data를 요청할 때 올바른 사용자 Access Token을 제공하지 않으면 Engagement API는 `403 Forbidden` 오류를 반환합니다.

Engagement API는, 해당 포스트의 소유자를 대신해 인증하더라도 [보호된 포스트](https://help.x.com/en/safety-and-security/public-and-protected-tweets)에 대한 참여 data를 가져오도록 허용하지 않습니다. 이렇게 시도할 경우 `"Tweet ID(s) are unavailable"`라는 메시지와 함께 `400 Bad Request` 오류가 반환됩니다.

자신의 X 계정(즉, 개발자 App을 소유한 계정)을 대신해 요청을 보내는 경우, [Developer Console](https://developer.x.com/en/portal/projects-and-apps)의 해당 개발자 App “Keys and tokens” 탭에서 필요한 Access Token을 직접 생성할 수 있습니다.

다른 사용자를 대신해 요청을 보내는 경우에는, 필요한 Access Token을 얻기 위해 3-legged OAuth 플로우를 사용해야 합니다. 이에 대한 자세한 내용은 다음 문서를 참고하십시오: [OAuth 1.0a: how to obtain a user’s access tokens](/ko/resources/fundamentals/authentication#oauth-1-0a-2).

추가 예제(특히 OAuth 1.0a를 사용한 인증 방법)는 [Engagement API용 XDevelopers Python 샘플 코드](https://github.com/xdevplatform/enterprise-scripts-python/tree/master/Engagement-API)를 참고하십시오.

<div id="recent-changes-to-the-engagement-api">
  ### Engagement API의 최근 변경 사항
</div>

Engagement API는 X에서의 활동 성과를 모니터링할 수 있도록, 매우 중요한 노출 및 참여 지표를 제공합니다. 우리는 data 기반 마케팅 의사결정을 지원하기 위해 지속적으로 노력하고 있으며, 그 일환으로 X 전반의 지표와 더 높은 일관성을 제공하는 Engagement API의 최근 변경 사항을 공유합니다.  

최근 우리는 Engagement API를 최신화하여 X 분석 대시보드(analytics.x.com)에서 사용하는 것과 동일한 지표 집계 방법론을 사용하도록 변경했습니다. 새로운 지표를 도입하면서 호환성이 깨지는 API 변경을 최소화하기 위해 신중하게 접근했으며, 첫 번째 변경 사항 세트는 2017년 10월 9일에 배포했습니다. 이러한 변경 사항은 여러분 또는 여러분의 고객이 X에서 성과를 모니터링하는 모든 위치 간의 일관성을 개선합니다. 아래에서 변경 사항에 대한 자세한 개요를 확인할 수 있습니다:

|     |     |
| :--- | :--- |
| **Metric** | **Change** |
| engagements | 전체 engagements에 포함되는 세부 지표를 업데이트하여 포스트 분석 대시보드와의 일관성을 맞추었습니다. Engagements는 “사람들이 이 포스트와 상호작용한 횟수”를 측정합니다.<br /><br />동영상 또는 GIF와 같은 미디어를 포함하는 포스트의 경우, engagements 지표에는 더 이상 미디어 조회 수가 포함되지 않습니다. 미디어 조회 수는 이제 새로운 지표인 &#95;media&#95;views&#95;에서 확인할 수 있습니다. |

<div id="interpreting-the-metrics">
  ### 메트릭 해석하기
</div>

**참고:** 일부 X 웹 대시보드에 보고되는 데이터와 Engagement API에서 보고되는 데이터 사이에는 차이가 있을 수 있습니다. 이는 웹 대시보드가 일반적으로 선택한 기간 내에 발생한 참여 및/또는 노출 수만 표시하기 때문에 발생합니다. 예를 들어, 웹 대시보드는 달력 기준 한 달 동안의 포스트에 대한 참여만 표시할 수 있지만, Engagement API는 해당 달을 넘어가더라도 요청한 시간 범위 내에 포함되는 모든 참여를 표시할 수 있습니다. 이러한 경우에는 Engagement API를 신뢰할 수 있는 기준 소스로 간주해야 합니다.
 

<div id="impressions-and-engagement-data">
  #### 노출수 및 참여 데이터
</div>

Engagement API는 **자연** 노출 및 참여 데이터를 제공합니다.

노출수(Impressions)는 특정 포스트가 X 플랫폼에서 자연 노출 환경에서 조회된 횟수를 의미합니다. 프로모션 또는 유료 환경에서 노출된 포스트로부터 발생한 노출수는 **포함되지 않습니다**.

참여(Engagement)는 특정 포스트에 대해 시청자가 **자연** 및 **프로모션** 환경 모두에서 상호작용한 횟수를 의미합니다. 참여에는 리트윗, 좋아요, 답글, URL 클릭, 해시태그 클릭, 멘션 클릭, 미디어 조회 등(이에 국한되지 않음)이 포함됩니다. 포함되는 전체 참여 액션 목록은 Engagement Data 섹션을 참조하십시오. 

기본적인 참여율을 계산하려면, 분석 중인 기간에 대해 특정 포스트의 총 참여 횟수를 해당 포스트의 총 노출수로 나누어 사용하십시오.

노출수 및 참여 데이터는 소유 중인 @handle의 포스트 또는 귀하의 애플리케이션이 해당 포스트의 세부 정보 조회를 허용하도록 권한을 부여한 @handle의 포스트에 대해서만 조회할 수 있습니다.  내부적으로 Engagement API는 계약된 @handle 한도에 대해 요청된 고유 @handle 수를 추적합니다.  또한 월 전체에 걸쳐 클라이언트 측에서도 @handle 요청 사용량을 추적할 것을 권장합니다.  

<div id="video-metrics">
  #### 비디오 지표
</div>

X 내에서 미디어 노출을 나타내는 지표에는 몇 가지 서로 다른 종류가 있습니다. 첫 번째는 비디오 조회수 지표로, 비디오 화면의 50% 이상이 최소 2초 동안 노출되어야 한다는 MRC 표준에 기반합니다. 두 번째는 Media Views로, 비디오, Vine, GIF, 이미지 전반에서 자동 재생 및 클릭 재생을 모두 포함한 모든 미디어 조회수를 집계합니다.

비디오 조회수 지표는 /28hour 및 /historical 엔드포인트를 통해 소유한 포스트에 대해 제공되며, 소유하지 않은 모든 포스트에 대해서는 /totals 엔드포인트를 통해 제공됩니다. 

X 사용자 인터페이스 내의 비디오 조회수 지표 역시 동일한 MRC 표준을 사용하지만, X에서 직접 운영하는 플랫폼(모바일 앱 및 웹사이트)에 표시되는 비디오 조회수 지표와 다양한 Engagement API 엔드포인트를 통해 수신하는 수치 사이에 차이가 발생할 수 있다는 점에 유의하십시오.

* /totals 엔드포인트와 X 사용자 인터페이스에서 제공하는 비디오 조회수는 해당 비디오가 게시된 모든 포스트에 걸쳐 집계된 비디오 조회수를 표시합니다. 이는 /totals를 통해 전달되고 X UI에 표시되는 지표에, 해당 비디오가 별도의 포스트에서 리트윗되었거나 다시 포스팅된 모든 경우의 조회수가 합산되어 포함된다는 의미입니다.
* /28hour 및 /historical Engagement API 엔드포인트에서 제공하는 비디오 조회수는, 지표를 조회하는 특정 포스트에서 발생한 조회수만 포함합니다. 
   

또한, 1800일보다 오래된 포스트에 대해서는 비디오 조회수를 제공하지 않는다는 점에 유의하십시오. 대신, 1800일보다 오래된 포스트를 나열한 객체를 제공합니다. 요청한 포스트에 대해서는 다른 모든 지표를 별도의 객체로 계속 수신하게 됩니다. 다음은 예시 응답입니다:

```json

    "477139122520219648"

      "video_views": "0"
    },
    "477139122520219648": {
```

<div id="engagement-api-groupings">
  ### Engagement API 그룹화
</div>

그룹화를 사용하면 반환된 참여(engagement) 메트릭을 사용자 정의 방식으로 구성할 수 있습니다. 요청당 최대 3개의 그룹화를 지정할 수 있습니다. 메트릭을 다음 값 중 하나 이상으로 그룹화할 수 있습니다:

*세 엔드포인트 모두에서 지원:*

* tweet.id
* engagement.type
   

*`/28hr` 및 `/historical`은 시계열 메트릭을 제공할 수 있으므로 다음을 지원합니다:*

* engagement.day
* engagement.hour

그룹화는 순차적으로 적용되므로, `group_by` 값의 순서를 변경해 원하는 결과 형식을 변경할 수 있습니다. 네 개의 `group_by` 값을 포함하는 그룹화는 다음 두 가지 형식 중 하나에서만 지원됩니다:

```bash
"group_by": [
    "tweet.id",
    "engagement.type",
    "engagement.day",
    "engagement.hour"
  ]
```

또는

```bash
"group_by": [
    "engagement.type",
    "tweet.id",
    "engagement.day",
    "engagement.hour"
]
```

예를 들어, 메트릭 유형의 총합을 생성하려면 요청에 다음과 같은 “groupings” 사양을 포함하세요 (요청을 구성하는 방법에 대한 자세한 내용은 [API 레퍼런스](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement) 페이지를 참고하세요):

```json
{
  "engagement_types": [
    "favorites",
    "replies",
    "retweets"
  ],
  "groupings": {
    "Grand Totals": {
      "group_by": [
        "engagement.type"
      ]
    }
  }
}
```

이러한 방식으로 그룹화하면 Engagement API의 JSON 응답에 최상위 수준의 `"Grand Totals"` 속성이 포함되며, 여기에는 메트릭 유형별 전체 합계가 들어 있습니다:

```json
{
  "Grand Totals": {
    "favorites": "12",
    "replies": "2",
    "retweets": "2"
  }
}
```

단일 포스트에 대한 4시간 동안의 시계열 메트릭을 포스트 ID별로 그룹화해 생성하려면, 다음 Grouping 사양을 요청에 포함해야 합니다:

```json
{
  "start": "2016-02-10T17:00:00Z",
  "end": "2016-02-10T21:00:00Z",
  "tweet_ids": [
    "697506383516729344"
  ],
  "engagement_types": [
    "impressions",
    "engagements"
  ],
  "groupings": {
    "Tweets_MetricType_TimeSeries": {
      "group_by": [
        "tweet.id",
        "engagement.type",
        "engagement.hour"
      ]
    }
  }
}
```

이 그룹화를 사용하면 Engagement API의 JSON 응답에 루트 수준의 `"Tweets_MetricType_TimeSeries"` 속성이 추가되며, 여기에는 포스트 ID별, 메트릭 유형별로 세분된 메트릭과 각 시간대별 시계열 데이터가 포함됩니다.

```json
{
  "Tweets_MetricType_TimeSeries": {
    "697506383516729344": {
      "impressions": {
        "2016-02-10": {
          "17": "551",
          "18": "412",
          "19": "371",
          "20": "280"
        }
      },
      "engagements": {
        "2016-02-10": {
          "17": "8",
          "18": "6",
          "19": "3",
          "20": "0"
        }
      }
    }
  }
}
```

    계약에 Engagement API와 함께 사용할 수 있는 고유 핸들의 개수에 대한 한도가 포함되어 있는 경우, X 내부 시스템은 Engagement API로 쿼리되는 포스트를 소유한 인증된 사용자 수를 추적합니다. 고객은 클라이언트 측에서도 이 고유한 수를 직접 추적해야 합니다. 현재 Engagement API의 @handle 사용량을 확인할 수 있는 사용량 API 또는 UI는 제공되지 않습니다. 시스템은 요청된 @handle 수가 계약된 수를 초과하더라도 이를 차단하지 않습니다. 청구 월 말에 쿼리된 고유 @handle 수가 계약된 수와 비교되며, 계약 조건에 따라 초과 사용분이 청구됩니다.
  </Accordion>

  <Accordion title="Engagement API에 대한 @handle 사용량을 확인할 수 있나요?">
    현재 Engagement API의 @handle 사용량을 확인할 수 있는 사용량 API 또는 UI는 제공되지 않습니다. 시스템은 요청된 @handle 수가 계약된 수를 초과하더라도 이를 차단하지 않습니다. 청구 월 말에 쿼리된 고유 @handle 수가 계약된 수와 비교되며, 계약 조건에 따라 초과 사용분이 청구됩니다.

    **페이로드에 반환되는 `engagements` 메타데이터 필드가 다양한 참여 지표 합계의 총합과 같지 않습니다. 왜 이런가요?**

    이는 정상적인 동작입니다. `engagements` 메타데이터 필드는 API에서 반환되는 개별 참여 지표의 합계와 항상 일치하지 않을 수 있습니다. 이는 `engagements` 메타데이터 필드에 페이로드에서 개별 지표로 분리되어 제공되지 않는 추가 참여가 포함될 수 있기 때문입니다. 다시 말해, 다양한 참여 지표의 합계를 모두 더하더라도, 페이로드에 반환되는 `engagements` 메트릭 필드에서 보게 되는 값과 일치하지 않을 수 있습니다.

    `engagements` 메타데이터 필드는 포스트에서 발생한 모든 클릭 또는 상호작용으로 이해하시면 됩니다.
     

    **페이로드 응답의 `url_clicks` 필드가 숫자를 반환하지만, 실제로 해당 포스트에는 URL이 없습니다. 어떻게 가능한가요?**

    이는 해시태그처럼 다른 페이지로 연결되는 링크를 생성하는 요소를 포함한 포스트의 경우, 사용자가 이를 클릭하면 URL 클릭으로 계산되기 때문일 수 있습니다.
     
  </Accordion>

  <Accordion title="특정 포스트에 대한 참여 데이터를 받을 수 없는 이유는 무엇인가요?">
    특정 포스트에 대한 참여 데이터를 검색할 수 없는 이유는 다음과 같이 여러 가지가 있을 수 있습니다.

    * 요청한 포스트 ID가, 서드파티를 대신해 데이터를 가져오기 위해 사용 중인 인증 토큰 기준으로는 사용할 수 없는 경우
    * /totals 엔드포인트에 대해 요청한 포스트 ID가 90일 이내가 아니어서, 노출수나 참여 지표를 반환할 수 없는 경우
    * 요청한 포스트 ID가 더 이상 사용 가능하지 않은 경우로, 보통 해당 포스트가 삭제되었거나 다른 이유로 더 이상 공개적으로 제공되지 않음을 의미합니다.

    위와 같은 상황에서 받게 될 수 있는 다양한 [오류 메시지](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#error-messages)를 검토해 주세요.
  </Accordion>

  <Accordion title="Engagement API에서 발생하는 레이트 리미트를 어떻게 처리할 수 있나요?">
    Engagement API에 요청을 보낼 때 응답 헤더에 반환되는 `x-per-minute-limit` 및 `x-per-minute-remaining` 정보를 사용해 사용량을 모니터링할 수 있습니다.

    `x-per-minute-limit`은 허용량을 알려주고, `x-per-minute-remaining`은 남은 호출 가능 횟수를 알려줍니다.
  </Accordion>
</AccordionGroup>

<div id="authentication">
  #### **Authentication**
</div>

Engagement API를 사용하려면 HTTPS를 사용해야 하며, User Context와 Application-Only OAuth 두 방식을 모두 지원합니다. Engagement API에 대한 대부분의 요청에는 3-Legged OAuth(특정 버전의 User Context)가 필요합니다. 이는 Twitter account manager가 Engagement API 액세스 권한을 부여하도록 승인한 앱의 consumer key와 secret, 그리고 트윗 소유자의 access token 및 access token secret을 사용해 엔드포인트를 호출해야 함을 의미합니다. 다음 요청에는 이 유형의 OAuth가 필요합니다:

* 소유한 트윗에만 제한되는 Impressions 및 Engagements 지표 유형을 얻기 위한 /totals에 대한 모든 요청
* /28hr에 대한 모든 요청
* /historical에 대한 모든 요청

일부 Engagement API 요청은 Application-Only OAuth를 사용하여 수행할 수 있습니다. 이 경우 consumer key와 secret 또는 Bearer Token만 제공하면 됩니다. 다음 요청은 이 유형의 OAuth로 수행할 수 있습니다:

* 임의의 트윗에 대해 Favorites, Replies, Retweets 또는 Video Views 지표 유형을 얻기 위한 /totals에 대한 모든 요청

어떤 요청이든, [developer.x.com](https://developer.x.com/en/portal/dashboard)에서 제공되는 앱 관리 콘솔을 사용해 Twitter 앱과 해당 API key를 설정해야 합니다.

참고: developer.x.com에서 Twitter 계정으로 로그인한 상태라면 [Twitter apps](/ko/resources/fundamentals/developer-apps)를 [Twitter app dashboard](https://developer.x.com/en/apps)를 통해 조회하고 수정할 수 있습니다.

앱 설정을 완료한 후에는, Engagement API에 대한 요청을 앱이 보낼 수 있도록 앱 ID가 담당 account representative의 승인을 받아야 합니다. Access token은 “현재 사용자”를 나타내는 데 사용해야 하며, 다른 사용자를 대신하여 수행되는 요청은 유효한 토큰으로 서명되어야 합니다. OAuth signature base string을 준비하기 전에 URL과 POST 본문에서 [예약 문자를 인코딩](https://tools.ietf.org/html/rfc3986)하고 있는지 확인하십시오.

OAuth 시작 방법에 대한 자세한 내용은 다음 링크를 참고하십시오:

* [OAuth 개요](/ko/resources/fundamentals/authentication)
* [User Context라고도 하는 3 Legged OAuth 사용](/ko/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow)
* [Application-Only OAuth 사용](/ko/resources/fundamentals/authentication#bearer-token-also-known-as-app-only)

<div id="error-messages">
  #### **오류 메시지**
</div>

여러 상황에서 Engagement API는 상황별 오류 메시지를 반환하며, 애플리케이션은 이에 대응할 수 있어야 합니다. 아래 표에는 이러한 오류 메시지의 일반적인 예와, 이를 어떻게 해석해야 하는지가 포함되어 있습니다. 많은 경우 Engagement API는 200 OK 응답의 일부로, 사용 가능한 데이터에 대한 부분적인 결과와 함께 추가 정보로 특정 오류 메시지를 반환한다는 점에 유의하세요.

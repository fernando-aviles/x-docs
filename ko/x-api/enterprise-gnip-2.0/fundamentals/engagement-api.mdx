<div id="overview">
  ## 개요
</div>

[`Enterprise`](https://developer.x.com/en/products/x-api/enterprise)

*이 API는 관리형 액세스 레벨에서만 제공되는 엔터프라이즈 API입니다. 이 API를 사용하려면 먼저 엔터프라이즈 영업 팀을 통해 계정을 개설해야 합니다. [자세히 알아보기](/ko/x-api/enterprise-gnip-2.0/enterprise-gnip)*

Engagement API는 포스트 노출 및 참여 메트릭에 대한 접근을 제공합니다. 대부분의 메트릭과 엔드포인트에는 [OAuth 1.0a User Context](/ko/resources/fundamentals/authentication)를 사용해 인증해야 하지만, 공개 Favorite, Retweet, Reply, Video Views 메트릭은 [OAuth 2.0 Bearer Token](/ko/resources/fundamentals/authentication#oauth-2-0)과 /totals 엔드포인트를 사용해 조회할 수 있습니다.  

**참고:** 일부 X 웹 대시보드에 보고되는 데이터와 Engagement API에서 보고되는 데이터 사이에 차이가 있을 수 있습니다. 이러한 차이는 웹 대시보드가 일반적으로 선택한 기간 내에 발생한 참여 및/또는 노출만 표시하기 때문에 발생합니다. 예를 들어, 웹 대시보드는 달력 기준 한 달 동안의 포스트 참여만 표시할 수 있지만, Engagement API는 해당 달의 범위를 넘어가더라도 요청한 시간 범위 내에 속하는 참여를 표시할 수 있습니다. 이러한 경우에는 Engagement API를 신뢰할 수 있는 기준 데이터 소스로 간주해야 합니다.
 

<div id="request-endpoints">
  ### 요청 엔드포인트
</div>

Engagement API에는 다음의 세 가지 엔드포인트가 있습니다.

<div id="current-totals-totals">
  #### Current Totals: [/totals]
</div>

* 요청은 원하는 포스트에 대해 노출수(impressions)에 대한 총합 지표와 참여수(engagements)에 대한 총합 지표를 반환합니다.
* 다음 지표만 제공됩니다: 노출수(Impressions), 참여수(Engagements), 좋아요(Favorites), 답글(Replies), 리트윗(Retweets), 인용 트윗(Quote Tweets), 동영상 조회수(Video Views)
* OAuth 1.0a User Context를 사용하여 **지난 90일 이내**에 작성된 포스트의 **Impressions** 및 **Engagements** 지표를 조회할 수 있습니다.
* OAuth 2.0 Bearer Token을 사용하여 **모든 포스트**에 대해 **Favorites, Retweets, Quote Tweets, Replies** 및 **Video Views** 지표를 조회할 수 있습니다.
* 결과는 요청 시점을 기준으로 한 현재 노출수와 참여수의 총합에 기반합니다.
* 대시보드 리포트를 구성하고 다양한 @핸들 전반의 참여율을 계산하는 데 적합합니다.
* 한 번의 요청으로 최대 250개의 포스트에 대한 지표 요청을 지원합니다.
   

<div id="last-28-hours-28hr">
  #### 지난 28시간: [/28hr]
</div>

* 요청 결과에는 노출 수 총합 메트릭, 참여 총합 메트릭, 그리고 지난 28시간 동안 발생한 개별 참여 메트릭의 세분화된 값이 포함될 수 있습니다.
* data는 포스트 ID별, 시계열 집계(일 단위 또는 시간 단위)별로 그룹화할 수 있습니다.
* 최근에 생성된 콘텐츠의 성과를 추적하는 데 적합합니다.
* 사용 가능한 모든 메트릭을 지원합니다.
* 요청 한 번에 최대 25개 포스트에 대한 메트릭을 조회할 수 있습니다.
   

<div id="historical-historical">
  #### Historical: [/historical]
</div>

* 요청은 최근 1년 동안의 노출 수(impressions), 참여 수(engagements), 그리고 개별 참여 지표에 대한 세부 내역을 반환할 수 있으며, 이는 포스트 작성 시간이 아니라 참여가 발생한 시간을 기준으로 합니다.
* 요청은 시작 날짜와 종료 날짜 파라미터를 지원하므로, 최대 4주 길이의 특정 기간으로 범위를 좁혀 조회할 수 있습니다.
* 포스트 참여 data는 최대 과거 365일까지만 제공됩니다.
* data는 포스트 ID별로, 그리고 집계 시계열 형태로, 일(day) 또는 시간(hour) 단위로 그룹화할 수 있습니다.
* 최근 성과를 과거 벤치마크와 비교 평가하거나, 특정 @handle의 과거 성과 추이를 파악하는 데 적합합니다.
* 사용 가능한 모든 지표를 지원합니다.
* 요청당 최대 25개의 포스트에 대한 지표 조회를 지원합니다.

<div id="engagement-groupings">
  ### 참여 그룹화
</div>

그룹화는 반환된 참여 지표를 사용자 정의 방식으로 구성할 수 있게 합니다. 요청당 최대 3개의 그룹화를 포함할 수 있습니다. 지표를 다음 값 중 하나 이상을 기준으로 그룹화할 수 있습니다:

*세 엔드포인트 모두에서 지원:*

* tweet.id
* engagement.type
   

*`/28hr` 및 `/historical` 엔드포인트는 시계열 지표를 제공할 수 있으므로 다음을 지원합니다:*

* engagement.day
* engagement.hour

그룹화에 대해 더 자세히 알아보려면, 가이드 섹션에 있는 [Engagement API Grouping](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings) 페이지를 참조하세요.

<div id="introduction">
  #### 소개
</div>

이 문서의 목적은 개발자를 위해 Engagement API 연동에 대한 입문 안내를 제공하는 것입니다. 먼저 연동의 ‘이유’를 살펴본 뒤, 이어서 기술적인 ‘방법’에 대한 세부 내용을 다루겠습니다.

<div id="what-does-the-engagement-api-provide">
  ##### **Engagement API는 무엇을 제공하나요?**
</div>

* Engagement API는 지난 90일 동안 임의의 X 계정이 소유한 포스트에 대해 노출 수(impression)와 참여(engagement) 데이터를 제공합니다. 단, 해당 계정이 [3-legged OAuth](/ko/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow)를 사용해 사용자의 앱이 자신의 메트릭을 대신 요청할 수 있도록 권한을 부여했어야 합니다. 이 강력하면서도 구현이 쉬운 솔루션을 통해 노출 수와 URL 클릭, #해시태그 클릭 등 다양한 심층 참여 데이터를 즉시 확인할 수 있습니다.
* Engagement API는 어떤 포스트에 대해서든 좋아요, 리트윗, 인용 트윗, 답글, 동영상 조회수에 대한 총 집계 메트릭을 제공합니다. 이를 단일 포스트 또는 포스트 모음에 대한 기본적인 참여 데이터를 얻기 위한 강력한 수단으로 활용할 수 있습니다.
* Engagement API는 15개 이상의 성과 메트릭을 사용하여 콘텐츠 성과를 효과적으로 측정할 수 있게 함으로써, 소셜 리스닝, 마케팅, 퍼블리싱 플랫폼이 X 상에서의 ROI(투자 대비 수익)를 측정할 수 있도록 새로운 가치를 제공합니다.
* Engagement API는 요청/응답 방식 API로, 앱 개발자가 포스트 ID, 필요한 메트릭, 기간을 포함한 요청을 보내면 API가 해당 요청에 대한 데이터를 즉시 반환합니다.
   

<div id="why-integrate-example-use-cases">
  ##### **왜 연동해야 할까요? 활용 예시**
</div>

* 내 콘텐츠의 전체 도달 범위를 파악해 얼마나 많은 사람이 보는지 이해합니다. 얼마나 많은 사람이 동영상을 시청하고, 링크를 클릭하고, 해시태그를 클릭하고, 내 앱을 설치하는지 확인합니다.
* 총합 및 시계열 형태의 참여(engagement) 지표를 생성합니다.
* 모든 공개 포스트에 대한 기본 참여 지표(좋아요, 리트윗, 인용 트윗, 댓글)를 파악합니다.
* 이러한 지표를 활용해 어떤 유형의 포스트가 효과적인지 파악하고, 그런 포스트를 더 자주 게시해 콘텐츠의 노출수와 참여를 늘립니다.
* 내 포스트 중 하나가 좋아요 100개 또는 다른 임계값을 달성할 때마다, 내가 소유한 다른 계정의 콘텐츠를 리트윗하는 등의 마케팅 활동을 자동화합니다.
* A/B 테스트 도구로서 캠페인 간 성과를 벤치마크하고 비교합니다.
* 고객 지원 부서에서 어떤 유형의 콘텐츠에 반응이 좋은지 분석하여, 어떻게 언제 대응할지 결정합니다.
* 내 플랫폼에서 게시되는 콘텐츠에 대한 분석 정보를 제공합니다.
   

2016년에 출시된 [Engagement API was launched in 2016](https://blog.x.com/official/en_us/a/2016/gnip-s-engagement-api-is-now-generally-available.html)는 이러한 심층적인 참여 지표를 대규모로 제공한 최초의 X API입니다. Engagement API는 사용하기 쉽고 고객이 이 과정을 자동화할 수 있도록 해 줍니다. 다음은 예시 연동을 보여 주는 사례 연구입니다:

* [Measuring campaign success with the Red Cross](https://blog.x.com/developer/en_us/topics/spotlight/2016/measuring-campaign-success-with-the-red-cross.html)[](https://simplymeasured.com/blog/true-twitter-impressions-and-url-clicks-new-from-simply-measured/#sm.0007werel134td8zqf02m2mduumr6)

이제 Engagement API의 ‘이유’를 살펴보았으니, 기술적인 세부 사항을 자세히 알아보겠습니다.

<div id="integrating-the-engagement-api">
  #### Engagement API 연동
</div>

<div id="introduction-to-api">
  ##### **API 소개**
</div>

Engagement API는 JSON으로 인코딩된 요청을 받고, JSON으로 인코딩된 참여(engagement) 지표로 응답하는 간단한 RESTful API입니다. 요청은 세 가지 주요 요소로 구성됩니다(자세한 내용은 링크를 참고하세요).

* ***포스트 ID*** 배열.
* 관심 있는 [지표 유형](https://developer.x.com/en/docs/x-api/v1/metrics/get-tweet-engagement/overview#EngagementTypes)을 지정하는 배열. 유형에는 ‘impressions’, ‘retweets’, ‘hashtag&#95;clicks’, ‘user&#95;follows’와 같은 항목이 포함됩니다.
* [Engagement groupings](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings). 이는 API 응답에서 참여 데이터가 어떻게 배열되기를 원하는지 나타내는 JSON 구조입니다.

대부분의 경우 Engagement Types와 Groupings은 요청 간에 비교적 일정하게 유지되며, 포스트 ID만 변경됩니다.

Engagement API는 [세 가지 엔드포인트](https://developer.x.com/en/docs/x-api/v1/metrics/get-tweet-engagement/overview#RequestEndpoints)를 제공합니다.

* **Totals** - 포스트에 대한 전체 참여 합계를 제공합니다. 일부 지표는 모든 포스트에 대해 사용할 수 있지만, 다른 지표는 최근 90일 동안만 사용할 수 있습니다.
* **28 hour** - 최근 28시간 동안의 시계열 참여 지표를 제공합니다.
* **Historical** - 2014년 9월 1일 이후에 게시된 포스트를 대상으로, 최대 네 주 연속 기간에 대한 시계열 참여 지표를 제공합니다.

**/totals** 엔드포인트는 한 번의 요청에서 최대 **포스트 250개에 대한 지표 요청**을 지원합니다. **/28hour** 및 **/historical** 엔드포인트는 **요청당 25개**를 지원합니다.

Engagement API에 대한 액세스 권한을 얻는 방법을 다룬 뒤, API 요청을 보내는 절차를 단계별로 살펴보고, OAuth 개요를 제공하며, 기타 기술 리소스에 대한 링크를 안내합니다.

<div id="getting-api-access">
  ##### **API 액세스 권한 얻기**
</div>

이 문서를 읽고 있다면, 대개는 이미 Engagement API에 대한 액세스 권한을 보유하고 있을 것입니다. 아직 액세스 권한이 없다면 Enterprise 계정 담당자에게 문의하거나, [여기](/ko/x-api/enterprise-gnip-2.0/enterprise-gnip)에서 Enterprise 액세스를 신청하세요.

첫 번째 단계는 승인된 개발자 계정으로 [Developer Console](/ko/resources/fundamentals/developer-portal)에 접속해 [X app](/ko/resources/fundamentals/developer-apps)을 생성하는 것입니다. 계정 담당자가 액세스를 제공하려면 이 애플리케이션과 연결된 숫자형 App ID가 필요합니다. 개발자 계정을 새로 신청해야 하는 경우 [여기](/ko/resources/fundamentals/developer-apps)에서 신청할 수 있습니다.

첫 번째 단계는 JSON 형식으로 API 요청을 구성하는 것입니다. 여기에는 배열에 넣은 두 개의 포스트 id, 관심 있는 참여(engagement) 유형 배열, 그리고 응답에서 지표를 어떻게 구성해서 받고 싶은지를 나타내는 사용자 지정 이름의 &quot;groupings&quot; JSON 객체가 포함됩니다. 우리의 요청은 다음과 같습니다:

```json
{
  "tweet_ids": [
    1260294888811347969, 850006245121695744
  ],
  "engagement_types": [
    "retweets", "quote_tweets", "favorites", "replies"
  ],
  "groupings": {
    "engagement-types-by-id": {
      "group_by": [
        "Tweet.id", "engagement.type"
      ]
    }
  }
}
```

이러한 전체 메트릭을 가져오기 위해 JSON 요청을 https://data-api.x.com/insights/engagement/totals 엔드포인트로 POST 요청으로 전송합니다.

요청이 JSON으로 인코딩되어 있으며 Gzip으로 압축되어 있음을 나타내기 위해 다음 헤더를 포함합니다(요청 본문은 매우 커질 수 있습니다):

* Content-Type: application/json
* Accept-Encoding: gzip
   

요청을 보낼 때는 OAuth를 사용해 인증하며, 이에 대해서는 다음 섹션에서 더 자세히 다룹니다.

API는 다음과 같은 페이로드를 반환합니다:

```json
{
  "grouping name": {
    "1260294888811347969": {
      "favorites": "17111",
      "quote_tweets": "3254",
      "replies": "1828",
      "retweets": "5218"
    },
    "850006245121695744": {
      "favorites": "492",
      "quote_tweets": "66",
      "replies": "42",
      "retweets": "324"
    }
  }
}
```

응답에는 “groupings” 정의에서 설명된 구조에 따라 우리가 요청한 지표가 포함되어 있으며, 먼저 포스트 ID별로, 그다음 단계에서 참여 유형별로 지표가 나열됩니다.

꽤 간단했죠. OAuth 인증이 처음이라면 다음 섹션을 확인해 보세요.

<div id="authenticating-with-oauth">
  #### OAuth로 인증하기
</div>

OAuth는 기술 업계에서 매우 널리 사용되는 인증 표준입니다. 이미 OAuth(예를 들어 다른 X API와 함께)를 사용하고 있다면, 아마도 복잡한 세부 구현을 모두 추상화해 주는 언어별 OAuth 패키지를 사용하고 있을 것입니다. OAuth가 처음이라면 [OAuth with the X API](/ko/resources/fundamentals/authentication) 페이지를 방문하거나 바로 [https://oauth.net](https://oauth.net/)으로 이동해 더 알아보시기 바랍니다. 그런 다음, 통합에 사용할 프로그래밍 언어에 맞는 OAuth 패키지를 찾아 사용하는 것을 권장합니다. 이러한 패키지를 사용할 때 일반적인 인증 흐름은 키와 토큰을 설정하고, 어떤 형태로든 HTTP 객체를 생성한 다음, 그 객체를 사용해 요청을 보내는 방식입니다.

예를 들어 Ruby 환경에서는, 아래의 의사 코드가 Ruby gem ‘oauth’를 사용해 OAuth를 사용하는 앱을 만들고 POST 요청을 수행하는 방법을 보여주는 레시피 역할을 합니다.

```js
require 'oauth'

#Assemble JSON request (as above).
request = make_json_request()

#Build an app consumer object with my app consumer key and secret.
consumer = OAuth::Consumer.new(keys['consumer_key'], keys['consumer_secret'], {:site => ‘https://data-api.x.com’})
#권한을 제공하는 계정에서 제공한 토큰으로 사용자 토큰 빌드. 앱 전용 #요청을 만드는 경우 (권한이 필요하지 않은 트윗을 /totals 엔드포인트로 확인), 이 단계는 #건너뛸 수 있습니다.
token = {:oauth_token => keys['access_token'], :oauth_token_secret => keys['access_token_secret']}

#Create oauth-enabled app object.
app = OAuth::AccessToken.from_hash(consumer, token)
#Make POST request.
result = app.post(“/insights/engagement/totals", request, {"content-type" => "application/json", "Accept-Encoding" => "gzip"})
```

Engagement API는 애플리케이션 전용 인증과 사용자 컨텍스트 인증을 모두 지원합니다. /totals 엔드포인트를 사용해 본인이 소유하지 않은 공개 포스트의 인게이지먼트 지표를 수집하는 경우에는 사용자 권한이 필요하지 않으므로 애플리케이션 전용 인증을 사용할 수 있습니다. 이 경우 앱 키와 시크릿만 사용해 인증을 수행하면 됩니다.

OAuth는 또한 사용자와 연관된 토큰을 사용하여 앱이 “다른 사용자를 대신해” API 요청을 수행할 수 있도록 해 줍니다. 소유한 포스트(owned Posts), 즉 사용자 토큰을 보유하고 있는 사용자가 게시한 포스트에 대한 인게이지먼트 지표를 생성하는 경우에는 사용자 컨텍스트에서 요청을 수행하게 되며, 이는 앱 키와 사용자별 액세스 토큰을 모두 사용해 인증한다는 의미입니다. 이러한 사용자 액세스 토큰은 일반적으로 &#39;[X로 로그인](/ko/resources/fundamentals/authentication#log-in-with-x)&#39; 프로세스를 통해 제공되거나 사용자로부터 직접 획득됩니다(토큰을 사용자로부터 직접 획득하는 경우 반드시 [twurl](https://github.com/xdevplatform/xurl)을 사용해야 합니다). 사용자가 토큰을 제공하면 토큰은 만료되지 않으며, 사용자가 토큰을 재설정하거나 비밀번호를 변경하지 않는 한 Engagement API에서 그 사용자를 대신해 요청을 수행하는 데 계속 사용할 수 있습니다. 이러한 경우에는 사용자가 새 토큰을 다시 제공해야 합니다.

어떤 지표에 어떤 인증이 필요한지는 [이 표](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings)에서 확인할 수 있습니다.

<div id="selecting-an-engagement-api-endpoint">
  ### Engagement API 엔드포인트 선택
</div>

Engagement API는 다음과 같은 세 가지 개별 엔드포인트를 제공합니다:

* **[Totals](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement)** - 소유(‘owned’) 또는 비소유(‘unowned’) 포스트에서 선택된 지표의 총합을 제공합니다. 일부 지표는 모든 포스트에 대해 제공되지만, 다른 지표는 최근 90일 이내에 게시된 포스트에만 제공됩니다. 요청당 최대 250개의 포스트를 지원합니다.
* **[28 hour](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement)** - 지난 28시간 동안의 ‘owned’ 포스트에 대한 시계열 Engagement 지표를 제공합니다. 요청당 최대 25개의 포스트를 지원합니다.
* **[Historical](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-historical)** - 2014년 9월 1일 이후에 게시된 ‘owned’ 포스트에 대해 최대 네 주 연속 기간에 대한 시계열 Engagement 지표를 제공합니다. 요청당 최대 25개의 포스트를 지원합니다.
   

각 엔드포인트는 고유한 특성을 갖고 있습니다. 세 가지 모두를 사용할 계획이든, 특정 사용 사례에 가장 잘 맞는 엔드포인트를 선택하려고 하든, 이들 사이의 차이를 이해하는 것이 중요합니다.

아래에서는 몇 가지 핵심 개념을 소개하고, 세 가지 엔드포인트를 더 자세히 살펴본 뒤, 일반적으로 특정 엔드포인트에 매핑되는 예시 사용 사례를 제공합니다. 이 정보가 세 가지 엔드포인트를 보다 효율적으로 통합하거나, 단일 엔드포인트 중 어떤 것이 귀하의 목적에 가장 잘 부합하는지 결정하는 데 도움이 되기를 바랍니다.
 

<div id="key-concepts">
  #### 핵심 개념
</div>

세 가지 Engagement API 엔드포인트 각각이 제공하는 다양한 기능과 데이터의 차이를 이해하는 데 도움이 되는 몇 가지 핵심 개념이 있습니다.
 

<div id="impressions-and-engagement-metrics">
  ##### 노출수 및 참여 지표
</div>

노출수(impressions)는 X 플랫폼에서 특정 포스트가 자연(organic) 환경에서 조회된 횟수를 나타냅니다. 프로모션(광고) 또는 유료(Paid) 환경에서 노출된 포스트로부터 발생한 노출수는 포함되지 않습니다. Engagement API 도입 이전에는 포스트 노출수가 잠재적인 조회 가능 횟수만을 나타냈습니다. 이는 작성자의 계정과 해당 콘텐츠를 리트윗한 계정들의 팔로워 수를 합산하는 방식에 기반했으며, 실제로 사용자가 해당 포스트를 보지 못하는 흔한 상황은 반영하지 못했습니다.

Engagement API가 생성하는 노출 지표는 포스트가 실제로 화면에 려더링되어 표시된 횟수를 측정한 값입니다. 예를 들어, 어떤 사용자가 귀하의 계정을 팔로우하고 있더라도, 해당 사용자가 귀하의 포스트를 실제로 보지 못했다면 그건 노출로 집계되지 않습니다.

Engagement API는 포스트가 사용자에게 노출되었을 때 사용자가 취할 수 있는 각각의 고유한 행동을 나타내는 14가지 고유 참여 [지표 유형](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#available-metrics)을 제공합니다. 여기에는 리트윗, 좋아요, 답글, #해시태그·링크·미디어 등의 엔티티 클릭, 작성자 팔로우, 작성자 프로필 조회 등이 포함됩니다. 이러한 개별 행동은 모두 하나의 통합된 Engagements 지표로 집계됩니다.

<div id="owned-and-unowned-x-content">
  ##### 소유한 X 콘텐츠와 소유하지 않은 X 콘텐츠
</div>

Engagement API는 소유한 포스트와 소유하지 않은 포스트를 명확히 구분합니다. 소유한 포스트란 내 계정에서 게시한 포스트이거나, 해당 포스트의 Engagement data를 요청할 수 있는 권한을 획득한 포스트를 의미합니다. 다른 X API와 마찬가지로, 이러한 권한은 다른 X 사용자/계정이 여러분을 대신해 API 요청을 보낼 수 있도록 해 주는 액세스 토큰을 공유해 줄 때 얻을 수 있습니다. 이러한 토큰을 얻는 일반적인 방법은 [‘Sign in with X’ 프로세스](/ko/resources/fundamentals/authentication#log-in-with-x)를 사용하는 것입니다.

`/totals` 엔드포인트는 소유한 포스트와 소유하지 않은 포스트 모두에 대한 참여 데이터를 제공합니다. 소유하지 않은 포스트의 경우, 포스트 화면에 공개적으로 표시되는 Favorite, Retweet, Reply와 같은 참여 지표를 요청할 수 있습니다. 이러한 지표와 관련해 Engagement API가 제공하는 가치는, 이 지표들을 대규모로 자동으로 조회할 수 있게 해 준다는 점입니다. 소유한 포스트의 경우 `/totals` 엔드포인트는 Impression 및 (총) Engagement 지표도 제공합니다.

`/28hr` 및 `/historical` 엔드포인트는 소유한 포스트에 대한 지표만 제공하므로, 이 엔드포인트들로 요청을 보낼 때는 user context를 함께 전달해야 합니다.

<div id="total-and-time-series-engagement-data">
  ##### 총합 및 시계열 참여 데이터
</div>

`/totals` 엔드포인트는 이름에서 알 수 있듯이 각 참여 유형에 대한 총합만 제공합니다. 이 수치는 포스트가 게시된 이후 현재까지의 최신 누적치를 나타냅니다. 어떤 포스트가 막 게시된 직후에 그 지표를 반복해서 요청하면, 이 총합은 일반적으로 요청할 때마다 변경됩니다.

`/28hr` 및 `/historical` 엔드포인트는 총합과 시계열 데이터 둘 다를 제공할 수 있습니다. 시계열 데이터를 요청하면, 참여 지표를 일별 또는 시간별 data로 집계할 수 있습니다.   

`/28hr` 및 `/historical` 엔드포인트로 시계열 데이터를 요청하는 방법은 [engagement groupings](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings) 관련 문서를 참고하세요.

<div id="endpoints-and-example-use-cases">
  #### 엔드포인트와 예시 사용 사례
</div>

위에서 설명한 특성과 차이점을 바탕으로, 각 개별 엔드포인트는 일반적으로 서로 다른 유형의 사용 사례에 매핑됩니다. 특정 사용 사례에 가장 적합한 엔드포인트를 선택할 수 있도록, 아래에 사용자 발화 예시와 이를 가장 잘 충족하는 엔드포인트를 제시합니다.

<div id="totals">
  ##### **/totals**
</div>

* 일부 지표 유형(노출 수, 참여 수, 즐겨찾기, 리트윗, 인용 트윗, 답글, 동영상 조회 수)에만 접근하면 된다.
* 내가 소유한 포스트뿐 아니라, 어떤 포스트에 대해서도 기본 참여 데이터에 접근할 수 있어야 한다.
* 경쟁사와 성과를 비교하고 싶다.
* 내가 소유하지 않은 포스트가 포함된 해시태그 또는 캠페인의 기본 참여 통계를 추적하고 싶다.
* 일별이나 시간별로 세분화된 데이터는 필요 없고, 요청 시점의 현재 합계만 알면 된다.
* 보고서나 대시보드에 표시할 단일 지표만 필요하고, 데이터를 저장하고 싶지 않다.
* 페이지 로드 시점에 데이터를 표시하고 싶으며, 요청을 한 번 보내서 응답만 받으면 된다.
* 하루에 수십만~수백만 개의 포스트에 대한 데이터에 접근해야 한다.
   

<div id="28hr">
  ##### **/28hr**
</div>

* 모든 17개 지표 유형에 대한 액세스가 필요합니다.
* 지난 28시간 동안 게시된 최신 포스트들의 데이터를 보고 싶습니다.
* 하루에 한 번 실행되는 작업이 있어서, 필요한 데이터는 직전 하루치만 가져오면 됩니다.
* 지표를 일(day) 또는 시간(hour) 단위로 구분해서 보고 싶습니다.
* 대시보드에서 시간(hour)별 활동을 시계열로 구분해 보여주고 싶습니다.
* 하루에 수십만 개의 포스트에 대해 높은 수준의 액세스가 필요합니다.
* 저장소 용량이 있어서 하루에 한 번 데이터를 새로고침하고 누적 합계를 유지할 수 있습니다.
   

<div id="historical">
  ##### **/historical**
</div>

* 17개 모든 지표 유형에 대한 액세스가 필요합니다.
* 2014년 9월까지 소급해 생성된 포스트에 대한 과거 데이터를 가져와야 합니다.
* 캠페인을 비교하는 상세한 과거 분석을 표시하고 싶습니다.
* 지표가 일별 또는 시간별로 세분화되어 있어야 합니다.
* Engagement API에 대한 대량 액세스는 필요하지 않고, 하루에 수백 개 또는 수천 개의 포스트에 대한 data만 가져오면 됩니다.

<div id="engagement-api-key-characteristics">
  ### Engagement API 핵심 특성
</div>

* JSON 데이터를 제공하는 **RESTful API**로, JSON 형식의 body를 포함한 POST 요청을 지원합니다.
* **요청 유형:** 클라이언트 앱은 다음과 같은 유형의 요청을 보낼 수 있습니다.
  * **총 Engagement** -- /totals 엔드포인트로의 HTTP POST 요청
  * **최근 28시간 Engagement** -- /28hr 엔드포인트로의 HTTP POST 요청
  * **히스토리컬 Engagement** -- /historical 엔드포인트로의 HTTP POST 요청
* **OAuth 인증:**
  * [OAuth 1.0 User Context](/ko/resources/fundamentals/authentication): [3-legged OAuth](https://developer.x.com/resources/fundamentals/authentication/obtaining-user-access-tokens)를 사용해 귀하의 앱을 승인한 사용자가 소유한 포스트에 대해서는 사용 가능한 모든 메트릭을 조회할 수 있습니다. 요청을 보낼 때는 해당 사용자의 Access Token을 사용해야 합니다.[](/ko/resources/fundamentals/authentication)
  * [OAuth 2.0 Bearer Token](/ko/resources/fundamentals/authentication#oauth-2-0): 선택된 메트릭(리트윗, 인용 트윗, 답글, 좋아요, 동영상 조회수)은 모든 공개 포스트에 대해 사용 가능합니다. 
* **요청 메타데이터 및 구조**: 요청 데이터는 포스트 ID 배열, Engagement 유형 배열, Engagement 그룹화 구조로 구성된 JSON 객체입니다.
* **요청당 포스트 수:**
  * /totals 엔드포인트: 포스트 ID 250개
  * /28hr 엔드포인트: 포스트 ID 25개
  * /historical 엔드포인트: 포스트 ID 25개
* **Engagement 메트릭 제공 범위:**
  * **/totals** -- 포스트가 게시된 이후의 메트릭 합계입니다. 노출(Impressions)과 Engagement는 최근 90일 이내에 게시된 포스트에 대해 사용할 수 있으며, 리트윗, 인용 트윗, 답글, 좋아요, 동영상 조회수는 모든 포스트에 대해 사용할 수 있습니다.
  * **/28hr** -- 요청 시점 기준 최근 28시간입니다.
  * **/historical** -- 2014년 9월 1일부터 시작하는 임의의 28일 기간입니다.
* **메트릭 유형**: 각 요청에는 [Metric Types](http://support.gnip.com/apis/engagement_api/overview.html#EngagementTypes) 배열이 포함됩니다. 사용 가능 여부는 엔드포인트에 따라 다르며, /totals 엔드포인트를 요청하는 경우 포스트가 사용자 권한이 필요한지 여부에 따라 달라집니다.
  * /totals 엔드포인트:
    * 모든 포스트: 좋아요(Favorites), 리트윗, 인용 트윗, 답글, 동영상 조회수
    * OAuth 1.0a User Context 필요: 노출(Impressions), Engagement, 좋아요(Favorites), 답글, 리트윗
  * /28hr 및 /historical 엔드포인트(OAuth 1.0a User Context와 포스트 소유자의 Access Token 필요): 노출(Impressions), Engagement, 좋아요(Favorites), 답글, 리트윗, URL 클릭, 해시태그 클릭, 상세 보기 클릭, 퍼머링크 클릭, 미디어 클릭, 앱 설치 시도, 앱 열기, 포스트 이메일, 동영상 조회수, 미디어 조회수
* **Engagement 그룹화:** 각 요청에는 [Engagement Groupings](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings) 배열이 포함됩니다. 이러한 그룹화를 사용해 반환되는 메트릭의 구성 방식을 사용자 지정할 수 있습니다. 요청당 최대 세 개의 그룹화를 포함할 수 있습니다. 메트릭은 다음 값에 따라 구성할 수 있습니다.
  * 모든 엔드포인트: 포스트 ID, Engagement 유형
  * /28hr 및 /historical 엔드포인트: 다음 추가 그룹화를 지정하면 시계열 데이터를 제공합니다. Engagement 일자, Engagement 시간
* **통합 관련 요구사항:** 귀하의 팀은 다음 사항을 책임집니다.
  * 요청에 포함된 포스트 ID에 대한 Engagement 메트릭을 반환하는 Engagement API로 HTTP 요청을 보낼 수 있는 클라이언트 앱을 생성하고 유지 관리하는 것
* **제한 사항**
* 동영상 조회수는 게시 후 1800일 이내인 포스트에만 사용 가능합니다.

<div id="authenticating-with-the-engagement-api">
  ### Engagement API 인증
</div>

> **주의:** 
>
> Engagement API를 사용하기 전에 X에서 먼저 귀하의 개발자 App에 대해 Engagement API 액세스를 활성화해 주어야 합니다. 이를 위해, 인증에 사용할 App ID를 담당 계정 매니저 또는 기술 지원 팀과 반드시 공유해야 합니다.

Engagement API에서는 두 가지 인증 방식을 사용할 수 있습니다: [OAuth 1.0a](/ko/resources/fundamentals/authentication#oauth-1-0a-2)와 [OAuth 2.0 Bearer Token](/ko/resources/fundamentals/authentication#bearer-token-also-known-as-app-only). 

**OAuth 2.0 Bearer Token**(“application-only”라고도 함)을 사용하면 공개적으로 이용 가능한 참여(engagement) 메트릭에 접근할 수 있습니다. 이 인증 방식은 [/totals 엔드포인트](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-totals)에 요청을 보낼 때, 공개된 모든 포스트에 대해 Favorites(즉 Likes), Retweets, Quote Tweets, Replies, 동영상 조회수의 총 횟수를 가져오는 데 사용할 수 있습니다. 

**OAuth 1.0a**(“user context”라고도 함)를 사용하면 사용자를 대신해 요청을 보내고, 해당 사용자에게 속한 비공개 참여 메트릭에 접근할 수 있습니다. 

이 인증 방식이 필요한 경우는 다음과 같습니다:

* [/28hr 엔드포인트](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-28hr) 및 [/historical 엔드포인트](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-historical)에 보내는 모든 요청
* 다음 비공개 메트릭에 접근하는 경우: Impressions, Engagements, Media Views, Media Engagements, URL Clicks, Hashtag Clicks, Detail Expands, Permalink Clicks, App Install Attempts, App Opens, Email Post, User Follows, User Profile Clicks

OAuth 1.0a로 요청을 보낼 때는, 관심 있는 포스트나 보호된 리소스의 소유자인 사용자의 Access Tokens(Access Token 및 Secret)를 포함해야 합니다. 보호된 사용자 데이터에 대한 요청 시 올바른 사용자 Access Tokens를 제공하지 않으면 Engagement API는 `403 Forbidden` 오류를 반환합니다.

Engagement API는, 해당 포스트의 소유 사용자를 대신해 인증하더라도 [보호된 포스트](https://help.x.com/en/safety-and-security/public-and-protected-tweets)의 참여 데이터를 가져오는 것을 허용하지 않습니다. 이렇게 시도하면 `"Tweet ID(s) are unavailable"`라는 메시지와 함께 `400 Bad Request` 오류가 반환됩니다.

자신의 X 계정(다시 말해, 개발자 App을 소유한 계정)을 대신해 요청을 보내는 경우에는, [Developer Console](https://developer.x.com/en/portal/projects-and-apps)의 해당 개발자 App에 있는 “Keys and tokens” 탭에서 필요한 Access Tokens를 바로 생성할 수 있습니다.

다른 사용자를 대신해 요청을 보내는 경우에는, 필요한 Access Tokens를 얻기 위해 3-legged OAuth 플로우를 사용해야 합니다. 이에 대한 자세한 내용은 다음 문서를 참고하세요: [OAuth 1.0a: how to obtain a user’s access tokens](/ko/resources/fundamentals/authentication#oauth-1-0a-2).

추가 예시(여기에는 OAuth 1.0a를 사용한 인증 방법도 포함됩니다)는 [XDevelopers의 Engagement API용 샘플 Python 코드](https://github.com/xdevplatform/enterprise-scripts-python/tree/master/Engagement-API)를 참고하세요.

<div id="recent-changes-to-the-engagement-api">
  ### Engagement API의 최근 변경사항
</div>

Engagement API는 X에서의 활동 성과를 모니터링할 수 있도록 노출 및 참여 지표를 제공하는 API입니다. X 전반의 지표 간 일관성을 높여 X의 데이터를 기반으로 마케팅 의사결정을 내릴 수 있도록 지속적으로 개선하고 있으며, 이러한 노력의 일환으로 최근 Engagement API에 적용된 변경사항을 공유합니다.  

최근 Engagement API를 최신화하여 X 애널리틱스 대시보드(analytics.x.com)에서 사용 중인 것과 동일한 지표 집계 방법론을 사용하도록 변경했습니다. 새로운 지표를 도입하면서 API에 큰 호환성 문제가 발생하지 않도록 신중하게 접근했으며, 첫 번째 변경 사항 세트는 2017년 10월 9일에 배포되었습니다. 이 변경으로, 여러분 또는 여러분의 고객이 X에서 성과를 모니터링하는 여러 채널 간의 지표 일관성이 향상되었습니다. 아래에서 변경사항을 상세히 확인하실 수 있습니다:

|     |     |
| :--- | :--- |
| **Metric** | **Change** |
| engagements | 전체 engagements에 포함되는 세부 지표를 업데이트하여 포스트 애널리틱스 대시보드와 일관되도록 맞췄습니다. Engagements는 “사람들이 이 포스트와 상호작용한 횟수(times people interacted with this Post)”를 측정합니다.<br /><br />동영상이나 GIF와 같은 미디어를 포함하는 포스트의 경우, engagements metric에는 더 이상 media views가 포함되지 않습니다. 이제 media views는 새 metric인 &#95;media&#95;views&#95;에서 확인할 수 있습니다. |
| media&#95;clicks* | 이 metric은 “*media&#95;engagements*”라는 새로운 metric으로 대체되었습니다. |
| video&#95;views | 2018년 7월 6일부터, 이 metric은 [/totals](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement) 엔드포인트를 통해 &#39;unowned&#39; 포스트에 대해서도 사용할 수 있게 되었습니다. 이는 앱 전용 인증(app-only authentication)을 사용하여 **모든** 포스트의 동영상 조회수를 확인할 수 있음을 의미합니다. <br /><br />video views는 1800일 이내의 포스트에 대해서만 요청할 수 있습니다. 1800일이 지난 포스트에 대한 video views를 요청하면 다음과 같은 응답을 받게 됩니다:<br /><br />&quot;unsupported&#95;for&#95;video&#95;views&#95;tweet&#95;ids&quot;: [&quot;TWEET&#95;ID&quot;]<br /><br />**참고:** video&#95;views는 동영상의 50% 이상이 최소 2초 동안 화면에 노출되어야 조회수로 집계된다는 MRC 기준에 의존한다는 점에서 media&#95;views와 차이가 있습니다.  <br /><br />**또한** X의 자체 서비스(모바일 앱 및 웹사이트)에 표시되는 video views metric과 /28hr 및 /historical 엔드포인트를 통해 수신하는 값 사이에 차이가 있을 수 있습니다.<br /><br />* X 사용자 인터페이스에 표시되고 /totals 엔드포인트를 통해 제공되는 video views는 해당 동영상이 게시된 **모든** 포스트에서 집계된 조회수를 나타냅니다. 즉, UI에 표시되는 metric에는 해당 동영상이 리트윗되었거나 별도의 포스트로 재게시된 모든 인스턴스에서의 조회수가 합산되어 포함됩니다.<br />* /28hr 및 /historical 엔드포인트에서 제공되는 video views는, 여러분이 metric을 조회 중인 특정 포스트에서 발생한 조회수만 포함합니다. |
| media&#95;views | 이는 동영상, vines, GIF, 이미지 전반에 걸쳐 자동 재생 및 클릭으로 발생한 **모든** 미디어 조회수를 포함합니다.<br /><br />**참고:** 이미지가 포함된 포스트의 경우 애널리틱스 대시보드에는 media&#95;views metric이 표시되지 않지만, Engagement API에서는 반환됩니다. |
| media&#95;engagements* | 이는 동영상, vines, GIF, 이미지 전반에 걸쳐 미디어에 대한 클릭 수를 포함합니다. 이 metric은 &#95;media&#95;clicks&#95;를 대체합니다. |
| quote&#95;tweets | 2020년 7월 7일부터, 이 metric은 /totals 엔드포인트를 통해 &#39;unowned&#39; 포스트에 대해서도 사용할 수 있게 되었습니다. 이는 앱 전용 인증(app-only authentication)을 사용하여 모든 포스트의 인용 포스트(Quote Post) 수에 접근할 수 있음을 의미합니다. |

<div id="interpreting-the-metrics">
  ### 지표 해석하기
</div>

**참고:** 일부 X 웹 대시보드에 보고되는 데이터와 Engagement API에서 보고되는 데이터 사이에 차이가 발생할 수 있습니다. 이러한 차이는 웹 대시보드가 일반적으로 선택한 기간 내에 발생한 참여 및/또는 노출만 표시하기 때문에 발생합니다. 예를 들어, 웹 대시보드는 한 달(달력 기준) 동안의 포스트 참여만 표시할 수 있지만, Engagement API는 요청한 기간 내에서 해당 월 범위를 넘어서는 참여까지 표시할 수 있습니다. 이러한 경우에는 Engagement API를 정확한 기준 데이터 소스로 간주해야 합니다.
 

<div id="impressions-and-engagement-data">
  #### 노출수 및 참여 데이터
</div>

Engagement API는 **오가닉** 노출수와 참여 데이터를 제공합니다.

노출수(Impressions)는 특정 포스트가 X 플랫폼에서 오가닉(자연 발생) 환경에서 조회된 횟수를 의미합니다. 프로모션 또는 유료 환경에서 노출된 포스트로부터 발생한 노출수는 **포함되지 않습니다**.

참여(Engagements)는 특정 포스트에 대해 사용자와의 상호작용이 **오가닉** 및 **프로모션** 환경 모두에서 발생한 총 횟수를 의미합니다. 참여에는 리트윗, 좋아요(Favorites), 답글, URL 클릭, 해시태그 클릭, 멘션 클릭, 미디어 조회 등이 포함되지만 이에 한정되지 않습니다. 포함되는 참여 액션의 전체 목록은 Engagement Data 섹션을 참조하세요. 

기본적인 참여율을 계산하려면, 분석하려는 기간 동안 특정 포스트에 대해 총 참여 수를 총 노출수로 나눈 값을 사용하세요.

노출수 및 참여 데이터는 소유한 @핸들에서 게시된 포스트이거나, 귀하의 앱이 해당 포스트의 세부 정보를 조회할 수 있도록 승인한 @핸들의 포스트에 대해서만 조회할 수 있습니다. 내부적으로 Engagement API는 계약된 @핸들 한도 대비 요청된 고유 @핸들의 수를 추적합니다. 월간 기간 동안 클라이언트 측에서도 @핸들 요청 사용량을 함께 추적할 것을 권장합니다.  

<div id="video-metrics">
  #### 비디오 지표
</div>

X 내에서 미디어 노출을 나타내는 지표는 두 가지가 있습니다. 첫 번째는 비디오 조회수 지표로, 비디오의 50% 이상이 최소 2초 동안 화면에 노출되어야 한다는 MRC 표준에 기반합니다. 두 번째는 Media Views로, 동영상, Vine, GIF, 이미지 전반에 걸쳐 집계되는 모든 미디어 조회(자동 재생 및 클릭 재생)를 포함합니다.

비디오 조회수 지표는 /28hour 및 /historical 엔드포인트를 통해 소유한 포스트에 대해 이용할 수 있으며, /totals 엔드포인트를 통해서는 소유하지 않은 모든 포스트에 대해 이용할 수 있습니다. 

X 사용자 인터페이스의 비디오 조회수 지표도 동일한 MRC 표준을 사용하지만, X가 소유·운영하는 플랫폼(모바일 앱과 웹사이트)에 표시되는 비디오 조회수 지표와 Engagement API의 다양한 엔드포인트를 통해 수신하는 수치 사이에 차이가 있을 수 있다는 점에 유의하십시오.

* /totals 엔드포인트와 X 사용자 인터페이스에서 제공되는 비디오 조회수는 해당 비디오가 게시된 모든 포스트 전반에 걸쳐 집계된 비디오 조회수를 표시합니다. 즉, /totals를 통해 제공되거나 X UI에 표시되는 지표에는 해당 비디오가 리트윗되었거나 별도의 포스트로 재게시된 모든 경우의 조회수가 합산되어 포함됩니다.
* /28hour 및 /historical Engagement API 엔드포인트에서 제공되는 비디오 조회수는, 여러분이 지표를 조회하는 특정 포스트가 생성한 조회수만 포함합니다. 
   

또한, 1800일이 지난 포스트에 대해서는 비디오 조회수를 제공하지 않는다는 점에 유의하십시오. 대신, 1800일보다 오래된 포스트를 나열한 객체를 제공합니다. 요청한 포스트에 대한 다른 모든 지표는 별도의 객체로 계속 수신하게 됩니다. 다음은 예시 응답입니다:

```json
{
  "unsupported_for_video_views_tweet_ids": [
    "479311209565413376",
    "477139122520219648"
  ],
  "grouping name": {
    "479311209565413376": {
      "favorites": "69",
      "impressions": "1692",
      "retweets": "142",
      "video_views": "0"
    },
    "477139122520219648": {
      "favorites": "10",
      "impressions": "1023",
      "retweets": "6",
      "video_views": "0"
    },
    "1397568983931392004": {
      "favorites": "268",
      "impressions": "26803",

```

Media Views 지표는 /28hour 및 /historical 엔드포인트에서 본인 소유 포스트에 대해서만 제공됩니다.

<div id="engagement-api-groupings">
  ### Engagement API 그룹화
</div>

그룹화를 사용하면 반환되는 참여(engagement) 지표를 원하는 방식으로 구성할 수 있습니다. 요청당 그룹화를 최대 3개까지 지정할 수 있습니다. 다음 값 중 하나 이상을 기준으로 지표를 그룹화할 수 있습니다:

*세 개의 엔드포인트에서 모두 지원:*

* tweet.id
* engagement.type
   

*`/28hr` 와 `/historical` 엔드포인트는 시계열 지표를 제공할 수 있으므로, 다음도 지원합니다:*

* engagement.day
* engagement.hour

그룹화는 지정된 순서대로 적용되므로, `group_by` 값의 순서를 변경하여 원하는 결과 형식을 바꿀 수 있습니다. 네 개의 `group_by` 값을 포함하는 그룹화는 다음 두 가지 형식 중 하나에서만 지원됩니다:

```bash
"group_by": [
    "tweet.id",
    "engagement.type",
    "engagement.day",
    "engagement.hour"
  ]
```

또는

```bash
"group_by": [
    "engagement.type",
    "tweet.id",
    "engagement.day",
    "engagement.hour"
]
```

예를 들어, 메트릭 유형별 총계를 생성하려면 요청의 일부로 다음과 같은 “groupings” 사양을 포함하세요(요청을 구성하는 방법에 대한 자세한 내용은 [API 레퍼런스](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement) 페이지를 참조하세요).

```json
{
  "engagement_types": [
    "favorites",
    "replies",
    "retweets"
  ],
  "groupings": {
    "Grand Totals": {
      "group_by": [
        "engagement.type"
      ]
    }
  }
}
```

이렇게 그룹화하면 Engagement API의 JSON 응답 최상위 수준에 지표 유형별 총합을 담은 `"Grand Totals"` 속성이 포함됩니다.

```json
{
  "Grand Totals": {
    "favorites": "12",
    "replies": "2",
    "retweets": "2"
  }
}
```

단일 포스트에 대해 Post ID별로 그룹화된 4시간 시계열 메트릭을 생성하려면, 요청에는 다음 Grouping 사양이 포함되어야 합니다:

```json
{
  "start": "2016-02-10T17:00:00Z",
  "end": "2016-02-10T21:00:00Z",
  "tweet_ids": [
    "697506383516729344"
  ],
  "engagement_types": [
    "impressions",
    "engagements"
  ],
  "groupings": {
    "Tweets_MetricType_TimeSeries": {
      "group_by": [
        "tweet.id",
        "engagement.type",
        "engagement.hour"
      ]
    }
  }
}
```

이 그룹화를 사용하면 Engagement API의 JSON 응답에는 루트 수준 `"Tweets_MetricType_TimeSeries"` 속성이 포함되며, 이 속성에는 포스트 id별, 그다음 지표 유형별로 구분된 메트릭과 이에 해당하는 시간별 시계열이 포함됩니다.

```json
{
  "Tweets_MetricType_TimeSeries": {
    "697506383516729344": {
      "impressions": {
        "2016-02-10": {
          "17": "551",
          "18": "412",
          "19": "371",
          "20": "280"
        }
      },
      "engagements": {
        "2016-02-10": {
          "17": "8",
          "18": "6",
          "19": "3",
          "20": "0"
        }
      }
    }
  }
}
```

    계약에 Engagement API와 함께 사용할 수 있는 고유 핸들의 개수 제한이 포함되어 있는 경우, 내부 X 시스템은 Engagement API로 쿼리되는 포스트를 소유한 인증된 사용자 수를 추적합니다. 고객도 클라이언트 측에서 이 고유 개수를 추적해야 합니다. 현재 Engagement API의 @handle 사용량을 확인할 수 있는 사용량 API나 UI는 없습니다. 시스템은 계약된 것보다 더 많은 @handle이 요청되더라도 초과 사용을 차단하지 않습니다. 청구 월 말에 쿼리된 고유 @handle 수를 계약된 수량과 비교하고, 계약 조건에 따라 초과 사용 요금이 부과됩니다.
  </Accordion>

  <Accordion title="Engagement API의 @handle 사용량을 확인할 수 있나요?">
    현재 Engagement API의 @handle 사용량을 확인할 수 있는 사용량 API나 UI는 없습니다. 시스템은 계약된 것보다 더 많은 @handle이 요청되더라도 초과 사용을 차단하지 않습니다. 청구 월 말에 쿼리된 고유 @handle 수를 계약된 수량과 비교하고, 계약 조건에 따라 초과 사용 요금이 부과됩니다.

    **페이로드에 포함되어 반환되는 `engagements` 메타데이터 필드가 다양한 참여 지표의 합계와 같지 않습니다. 왜 이런가요?**

    이는 예상된 동작입니다. `engagements` 메타데이터 필드는 API에서 반환되는 개별 참여 지표의 합계와 항상 일치하지 않을 수 있습니다. 이는 `engagements` 메타데이터 필드에 페이로드에서 개별 지표로 분리되지 않은 추가 참여가 포함될 수 있기 때문입니다. 다시 말해, 다양한 참여 지표의 합계를 모두 더해도 페이로드에 포함되어 반환되는 `engagements` 지표 필드에서 확인되는 값과 같지 않을 수 있습니다.

    `engagements` 메타데이터 필드는 포스트에서 발생한 모든 클릭 또는 상호작용으로 이해할 수 있습니다.
     

    **응답 페이로드의 `url_clicks` 필드가 숫자를 반환하지만, 실제로 해당 포스트에는 URL이 없습니다. 어떻게 가능한가요?**

    포스트에 해시태그처럼 다른 페이지로 가는 링크를 생성하는 요소가 포함되어 있고, 사용자가 이를 클릭한 경우 URL 클릭으로 집계될 수 있기 때문입니다.
     
  </Accordion>

  <Accordion title="특정 포스트의 참여 데이터를 받을 수 없는 이유는 무엇인가요?">
    특정 포스트의 참여 데이터를 가져올 수 없는 이유는 여러 가지가 있을 수 있으며, 예를 들면 다음과 같습니다.

    * 요청한 포스트 ID가(또는 여러 ID가) 서드파티를 대신해 데이터를 가져오기 위해 사용 중인 인증 토큰으로는 사용 가능하지 않은 경우
    * /totals 엔드포인트에 대해 요청한 포스트 ID가(또는 여러 ID가) 90일 이내가 아니어서 노출수(impressions) 또는 참여 지표를 반환할 수 없는 경우
    * 요청한 포스트 ID가(또는 여러 ID가) 더 이상 사용 가능하지 않은 경우(일반적으로 삭제되었거나 다른 이유로 더 이상 공개적으로 제공되지 않음을 의미)

    위와 같은 상황에서 수신하게 될 수 있는 다양한 [오류 메시지](/ko/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#error-messages)를 검토해 주세요.
  </Accordion>

  <Accordion title="Engagement API의 레이트 리밋은 어떻게 처리할 수 있나요?">
    Engagement API에 요청을 보낼 때 응답 헤더에 반환되는 `x-per-minute-limit` 및 `x-per-minute-remaining` 정보를 사용하여 사용량을 모니터링할 수 있습니다.

    `x-per-minute-limit`은 허용 한도를 알려주며, `x-per-minute-remaining`은 남은 호출 수를 알려줍니다.
  </Accordion>
</AccordionGroup>

<div id="authentication">
  #### **Authentication**
</div>

Engagement API는 HTTPS 사용이 필수이며, User Context와 Application-Only OAuth 두 가지 방식을 모두 지원합니다. Engagement API에 대한 대부분의 요청에는 3-Legged OAuth(특정 버전의 User Context) 사용이 필요합니다. 이는 Engagement API 접근 권한을 부여받은 앱의 consumer key와 secret, 그리고 포스트 소유자의 access token 및 access token secret을 함께 사용해 엔드포인트를 호출한다는 의미입니다. 아래 요청에서는 이 유형의 OAuth가 필요합니다.

* 소유한 포스트에 한정되는 Impressions 및 Engagements 메트릭 유형을 얻기 위한 /totals 요청
* /28hr에 대한 모든 요청
* /historical에 대한 모든 요청

일부 Engagement API 요청은 Application-Only OAuth를 사용하여 수행할 수 있으며, 이 경우 consumer key와 secret 또는 Bearer Token만 제공하면 됩니다. 다음 요청은 이 유형의 OAuth로 수행할 수 있습니다.

* 어떤 포스트에 대해서든 Favorites, Replies, Retweets 또는 Video Views 메트릭 유형을 얻기 위한 /totals 요청

모든 요청을 위해, [developer.x.com](https://developer.x.com/en/portal/dashboard)에 있는 앱 관리 콘솔을 통해 Twitter 앱과 해당 API 키를 설정해야 합니다.

주의: developer.x.com에서 Twitter 계정으로 로그인한 상태라면, [Twitter 앱](/ko/resources/fundamentals/developer-apps)을 확인하고 수정하기 위해 [Twitter app dashboard](https://developer.x.com/en/apps)에 접속할 수 있습니다.

앱을 설정한 후에는 Engagement API에 대한 요청을 보내기 위해 앱 ID가 계정 담당자의 승인을 받아야 합니다. Access token은 “현재 사용자”를 나타내는 데 사용되어야 하며, 다른 사용자를 대신해 수행되는 요청은 유효한 토큰으로 서명되어야 합니다. OAuth signature base string을 준비하기 전에 URL과 POST 본문에 포함된 [예약 문자](https://tools.ietf.org/html/rfc3986)가 적절히 인코딩되었는지 확인하십시오.

OAuth 시작 방법에 대한 자세한 내용은 다음 링크를 참조하십시오.

* [OAuth 개요](/ko/resources/fundamentals/authentication)
* [User Context라고도 불리는 3-Legged OAuth 사용](/ko/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow)
* [Application-Only OAuth 사용](/ko/resources/fundamentals/authentication#bearer-token-also-known-as-app-only)

| **시작일 및 종료일**     | 요청의 일부로 `start` 및 `end` 값을 사용하여 사용자 지정 시작일과 종료일을 지정할 수 있습니다. 시작일과 종료일의 기간은 4주를 초과할 수 없습니다. 현재 기준으로 지정 가능한 가장 이른 시작일은 2014년 9월 1일입니다. 미래 시점의 종료일은 지원되지 않습니다. 시작일과 종료일이 제공되지 않으면, API는 기본적으로 바로 직전 4주 기간으로 설정됩니다.  <br />  <br />Engagement API에서 data가 반환될 수 있는 최소 시간 단위는 1시간입니다. 시작 또는 종료 값이 정확히 정시(1시간 단위 경계)에 맞지 않는 요청의 경우, 요청은 가장 가까운 포함되는 정시로 맞춰집니다. 예를 들어, &quot;start&quot;:&quot;2015-07-01T12:24:00Z&quot; 및 &quot;end&quot;:&quot;2015-07-10T08:37:00Z&quot;로 요청하는 경우, &quot;start&quot;:&quot;2015-07-01T12:00:00Z&quot;,&quot;end&quot;:&quot;2015-07-10T09:00:00Z&quot;로 처리됩니다.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

<div id="error-messages">
  #### **오류 메시지**
</div>

여러 가지 상황에서 Engagement API는 상황별 오류 메시지를 반환하며, 애플리케이션은 이를 처리할 수 있어야 합니다. 아래 표에는 이러한 오류 메시지의 일반적인 예와 각 메시지를 어떻게 해석해야 하는지가 포함되어 있습니다. 많은 경우 Engagement API는 추가 정보가 포함된 200 OK 응답의 일부로, 특정 오류 메시지와 함께 사용 가능한 data에 대한 부분적인 결과를 반환한다는 점에 유의하세요.

| 오류 메시지 | 설명 |
| :--- | :--- |
| `"errors":["Your account could not be authenticated. Reason: Access token not found"]` | 요청의 인증 구성 요소에서 오류가 발생한 경우입니다. “Reason”에는 오류를 해결하는 데 도움이 되는 정보가 제공됩니다. 직접 해결할 수 없는 경우 “Reason”을 포함한 전체 오류를 지원팀으로 보내 주시기 바랍니다. |
| `"errors":["1 Tweet ID(s) are unavailable"],"unavailable_tweet_ids": ["TWEET_IDS"]` | 요청한 트윗 ID 하나 이상을 더 이상 사용할 수 없는 경우로, 일반적으로 삭제되었거나 다른 이유로 더 이상 공개적으로 제공되지 않는 상황을 의미합니다. |
| `"errors":["Impressions & engagements for tweets older than 90 days (*TIME_PERIOD*) are not supported"],"unsupported_for_impressions_engagements_tweet_ids":[*TWEET_IDS*]` | /totals 엔드포인트에 대해 요청한 트윗 ID들이 90일 이내가 아니기 때문에, 해당 트윗들에 대한 노출수(impressions) 또는 참여수(engagements) 지표를 반환할 수 없는 경우입니다. |

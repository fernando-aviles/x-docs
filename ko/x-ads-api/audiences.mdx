## 맞춤 잠재고객

### 개요

파트너가 [Custom Audiences](https://business.x.com/en/targeting/tailored-audiences.html)를 생성하는 방법은 여러 가지가 있습니다.

* [Audience API (CRM)](#crm)
* [Web](#web)
* [Mobile](#mobile)
* [Flexible](#flexible)

유사 맞춤 잠재고객(lookalike custom audiences)은 타기팅 대상에서 제외할 수 없습니다. 또한 동일한 광고 라인 아이템(광고 그룹)에서 하나의 맞춤 잠재고객과 해당 맞춤 잠재고객의 유사 맞춤 잠재고객을 동시에 타기팅할 수 없습니다.

**Audience 관리**

잠재고객은 audience 파트너 및 Ads API 파트너를 통해 관리할 수 있습니다. 우리는 API에서 맞춤 잠재고객(Custom Audiences)에 액세스하고 이를 유지 관리하기 위한 일련의 엔드포인트를 제공합니다.

맞춤 잠재고객 정보용으로 2개의 엔드포인트를 제공합니다.

* [GET accounts/:account&#95;id/custom&#95;audiences](/ko/x-ads-api/audiences)
* [GET accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id](/ko/x-ads-api/audiences)

Audience 업로드 및 관리 방법에 대한 자세한 내용은 [Audience API 가이드](/ko/x-ads-api/audiences)를 참조하세요.

**처리 시간**

일반적으로 잠재고객 변경 사항은 6~8시간 간격으로 실행되는 배치 단위로 처리됩니다. 잠재고객 변경이 처리되는 동안 업데이트 대상이 되는 기존 잠재고객은 영향을 받지 않습니다. 이 시간 범위 내에서 잠재고객 하나당 추가 작업은 한 번, 제거 작업은 한 번을 초과하여 업데이트하지 않을 것을 권장합니다.

**타기팅**

잠재고객은 X가 소유 및 운영하는 클라이언트에서 지난 90일 이내에 활동한 사용자 최소 100명과 일치하는 경우에만 타기팅할 수 있습니다. [GET accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id](/ko/x-ads-api/audiences)는 일치하는 사용자가 너무 적어 해당 잠재고객을 타기팅할 수 없는지 여부를 표시합니다.

  ### 오디언스 FAQ[](#real-time-tailored-audiences "Permalink to this headline")
</div>

**Q: 매우 많은 데이터를 전송했는데, 왜 오디언스 규모가 TOO&#95;SMALL로 표시되나요?**

A: 현재 데이터는 실시간으로 오디언스에 추가되고 있지만, 오디언스 규모를 계산하는 처리는 일정 시간이 지난 후에만 실행됩니다. 몇 시간 정도 지나면 UI에 올바른 오디언스 규모가 표시됩니다.

**Q: 오디언스 데이터 전송을 완료하고 24시간 이상 기다렸는데도 여전히 해당 오디언스를 타게팅할 수 없습니다. 다음 단계로 무엇을 해야 하나요?**

A: 다음 사항을 확인해 주십시오.

* 전달되는 user ID가 올바르고 형식 오류가 없는지 확인합니다.
* 전달되는 오디언스 이름이 올바르며, 이전 멤버십 업데이트와 일치하는지 확인합니다.
* POST 명령에 대한 응답을 확인합니다.
* ID Sync 픽셀이 올바르게 구현되었는지 확인하고, ID Sync 프로세스에서 설명한 대로 해당 사이트를 방문한 사용자가 충분하여 사용자를 매핑할 수 있는지 확인합니다. 멤버십 업데이트에 포함된 매핑되지 않은 사용자는 타게팅 가능한 사용자로 전환되지 않습니다.

위 모든 사항이 올바르고 정상 동작하는 것으로 확인되면, 가능한 한 자세한 정보를 포함하여 X 제품 담당자에게 문의해 주십시오(선호하는 정보 예시는 [Guide to Partner Inbounds](/ko/x-ads-api/introduction)를 참고하십시오).

**Q: 이 endpoint는 몇 번까지 호출할 수 있고, 어떤 방식으로 호출해야 하나요?**

A: 전체 오디언스 멤버십을 다시 보내지 말고, 증분 델타 방식으로 데이터를 전송할 것을 강력히 권장합니다. 이 시스템은 전 세계에서 가장 큰 웹사이트 일부의 증분 데이터 업데이트를 처리할 수 있을 만큼 충분한 처리량을 갖도록 테스트되었습니다. 최초 오디언스 업로드는 신중하게 전송 속도를 제한해야 하며, 첫 업로드 완료까지 상당한 시간이 소요될 수 있습니다.

**Q: 타게팅에 사용할 수 있는 오디언스의 최소 규모는 얼마인가요?**

* 오디언스의 최소 규모는 100명의 사용자(매칭 이후 기준)입니다. 500명 미만의 사용자가 매칭된 오디언스는 X Ads UI에서 타게팅에 사용할 수 없습니다.

**Q: 오디언스 파일을 처리하는 데 얼마나 걸리며, X User Interface에서 오디언스 파일이 준비되는 데는 얼마나 걸리나요?**

* 일반적으로 오디언스 파일 처리에는 4~6시간이 소요되지만, 파일 크기에 따라 달라질 수 있습니다. 파일이 처리되면 해당 오디언스는 X Ads UI에서 사용할 수 있게 됩니다.

**Q: 매치율은 어떻게 계산되나요?**

* 매치율 = 최근 90일 이내 활성 X 사용자 수 / 제공된 사용자 수

**Q: 오디언스 파일이 제대로 작동하는지 어떻게 테스트하나요?**

* 테스트 오디언스 파일을 제공하고 광고주 핸들로 “keltonlynn”을 사용할 수 있습니다. 그러면 해당 파일이 X UI에 올바르게 수집되고 로딩되는지 확인할 수 있습니다.

**Q: 파트너 사용자 식별자(`p_user_id`)란 무엇인가요?**

* 귀사가 각 고객을 고유하게 식별하기 위해 사용하는 식별자입니다.

**Q: 표준 ID란 무엇인가요?**

* 이메일 주소, device ID, X @handle 또는 ID가 이에 해당할 수 있습니다.

**Q: HMAC Key는 어떻게 받나요?**

* 암호화된 이메일로 제공됩니다. [mpp-inquiry@x.com](mailto:mpp-inquiry%x.com)으로 귀하의 공개 PGP 키를 보내주시면, 모든 것이 정상 작동하는지 확인하기 위해 테스트 이메일을 발송합니다. 검증이 완료되면 HMAC Key를 보내드립니다.

**Q: 제공된 HMAC Key를 사용해 해싱 프로세스가 올바르게 작동했는지 어떻게 검증하나요?**

* X에서 테스트 파일(샘플 이메일 주소, device ID 등 포함)과 그에 대한 결과 해시 파일을 제공하므로, 해당 해시 파일과 비교하여 결과를 검증할 수 있습니다.

**Q: 전체 데이터 매치 파일에 파일 크기 제한이 있나요?**

* 아니요, 전체 데이터 매치 파일에는 크기 제한이 없습니다.

**Q: 전체 데이터 매치 파일이 처리되는 데 얼마나 걸리나요?**

* X가 파일을 수신한 후, 파일을 처리하는 데 약 1일이 소요됩니다.

  ### CRM
</div>

<Frame>
  <img src="https://cdn.cms-twdigitalassets.com/content/dam/developer-twitter/images/crm_0.png" alt="image0" />
</Frame>

이 문서는 Custom Audiences CRM 파트너를 위한 연동 세부 정보(파일 형식 및 data 교환 프로세스 포함)를 설명합니다.

**요약**

회사는 고객을 대신하여 해시된 공통 사용자 식별자(예: 이메일 주소) 또는 파트너 사용자 ID 목록을 X에 제공하여 블라인드 매칭을 수행하고, 타게팅에 사용할 X 사용자 ID 목록을 생성합니다. 타게팅용 세그먼트는 ads.x.com 캠페인 설정에서 파일 이름으로 지정된 광고주의 특정 @handle에 사용할 수 있도록 제공됩니다.

회사가 제공하는 모든 파일은 X가 회사에 부여한 특정 계정을 통해 IronBox (www.golockbox.com)의 보안 패키지를 사용하여 X에 전달됩니다. X는 IronBox에 대한 액세스를 제공합니다. IronBox API에 대한 문서는 [https://secure.goironcloud.com/Docs/Help/](https://secure.goironcloud.com/Docs/Help/)에서 확인할 수 있습니다.

<div id="partner-id-matching-requirements">
  #### 파트너 ID 매칭 요건
</div>

회사가 사용자 추적을 위해 자체 표준 ID 시스템을 사용한다면(예: 이메일 주소, 디바이스 id, X user ID 등의 일반적인 사용자 식별자를 사용하지 않는 경우) 다음 프로세스를 권장합니다.

**1. 전체 데이터 매칭**

초기에 회사는 X와 공통으로 사용하는 고유한 사용자 식별자가 포함된 모든 사용자 레코드의 전체 목록을 단일 파일로 제공하여, 파트너 ID(`p_user_id`)와 X ID(`tw_id`) 간의 매핑을 생성하고 이를 X가 보관할 수 있도록 전체 데이터 매칭을 수행합니다. 이는 적절한 유지 관리를 위해 2~3개월 주기로 정기적으로 수행됩니다. 매칭이 완료되면 X는 이 파일을 기반으로 한 기준 매칭률을 이메일을 통해 회사에 공유합니다.

이 파일의 형식은 다음과 같아야 합니다.

Name Convention: FullDataMatch.[CompanyName].txt

Hashing Algorithm: HMAC&#95;SHA-256

Format:

Column 1: 공통 사용자 식별자의 HMAC 해시 값

Column 2: Partner User ID(사용자당 고유, 파일 내에서는 중복 가능)

Column Delimiter (CSV): 해시된 공통 사용자 식별자와 Partner ID를 구분하기 위해 쉼표 사용

줄바꿈으로 구분된 값

* 예: 사용자 레코드 A의 Partner User ID가 1이고 공통 식별자가 1, 2, 3인 경우:

|     |     |
| :--- | :--- |
| 공통 사용자 식별자 1 | p&#95;user&#95;1 |
| 공통 사용자 식별자 2 | p&#95;user&#95;1 |
| 공통 사용자 식별자 3 | p&#95;user&#95;1 |

*아래의 공통 사용자 식별자에 대한 Hashing Directions 섹션을 참조하세요

**2. Custom Segment Lists**

회사는 `p_user_id` 형식의 사용자 목록을 제공하여, X에서 타겟팅을 위한 고객용 맞춤 오디언스를 생성합니다.

* 줄바꿈으로 구분된 값
* `p_user_id`
* * (위의 1. 전체 데이터 매칭 섹션에서 제공된 값과 동일합니다. 전체 데이터 매칭에서 제공된 값이 해시된 값이라면 회사는 오디언스 파일에서도 동일한 해시 값을 제공합니다. 해시되지 않은 값이 제공되었다면, 회사는 해시되지 않은 값을 제공합니다.)

<div id="standard-matching-requirements">
  #### 표준 매칭 요구 사항
</div>

회사가 모든 고객 사용자 식별자를 매핑하는 데 표준 ID를 사용하지 않는 경우, 다음 프로세스를 권장합니다.

**Custom Segment Lists**

회사는 고객을 대신하여 해시된 공통 사용자 식별자 목록을 X에 직접 제공하여 커스텀 오디언스를 생성합니다.

이 파일의 형식은 다음과 같아야 합니다.

* 줄바꿈으로 구분된 값
* 해시된 공통 사용자 식별자(예: 이메일 주소)
* 아래에 설명된 파일 이름 지정 규칙을 따를 것
* 아래의 이메일 주소 해싱 지침(Hashing Directions)을 따를 것

<div id="custom-segment-list-file-naming-operations">
  #### 커스텀 세그먼트 리스트 파일 이름 지정 및 작업
</div>

파일에 대해 수행할 작업은 파일 이름에 따라 결정되며, 사용 가능한 작업과 일반적인 파일 이름 지정 규칙은 다음과 같습니다: audiencename&#95;partnername.handle.operation.filetype

* audiencename: 커스텀 오디언스의 이름입니다. 이 필드는 ads.x.com 캠페인 설정 UI에서 오디언스를 선택할 때 표시되는 이름입니다. 예: brand&#95;loyalty&#95;card&#95;holders.
* partnername: 광고주를 대신하여 data를 제공하는 회사의 이름입니다. 예: company&#95;name.
* handle: 커스텀 오디언스에 액세스 권한을 갖는 X 계정(@handle)입니다. 예: @pepsi, @dietpepsi
* operation: new, add, remove, removeall, replace (아래에 상세 설명)
* : 업로드되는 각 오디언스 파일이 고유하도록 보장하기 위해 사용하는, 초 단위의 표준 Unix epoch 시간
* filetype: 파일은 *.txt 형식이어야 합니다.

<div id="creating-and-updating-audiences">
  #### 오디언스 생성 및 업데이트
</div>

단일 파일을 사용해 새 오디언스를 생성합니다. 예: loyalty&#95;card&#95;holders&#95;partnername.pepsi.new.txt

추가(Add) - 목록에 있는 매칭된 사용자를 기존 오디언스에 추가합니다. 예: loyalty&#95;card&#95;holders&#95;partnername.pepsi.add..txt

제거(Remove) - 목록에 있는 매칭된 사용자를 기존 오디언스에서 제거합니다. 예: loyalty&#95;card&#95;holders&#95;partnername.pepsi.remove..txt

모두 제거(Remove All) - 정기적으로 업데이트되는 누적 목록에서 생성된 매칭된 사용자를 해당 클라이언트의 모든 오디언스에서 제거합니다(즉, 클라이언트의 옵트아웃 목록). 예: partnername.pepsi.removeall.txt

* 이는 광고주로부터 옵트아웃한 사용자들의 포괄적인 목록에 사용할 수 있습니다.
* X는 이 파일에 제공된 최신 목록만을 반영하며, 매칭된 모든 기존 및 향후 오디언스에 대해 이를 적용합니다.

이 파일이 제공되고 처리된 시점에 매칭된 X 사용자에 대해 적용됩니다.

교체(Replace) - 기존 오디언스를 제거하고 새로운 오디언스 목록으로 교체합니다. 예: loyalty&#95;card&#95;holders&#95;partnername.pepsi.replace..txt

회사 전체 옵트아웃(Overall Company Opt-Out) - 회사는 자사 옵트아웃 정책에 따라 옵트아웃한 사용자를 제거하기 위해 누적 옵트아웃 파일을 제공합니다.

X는 이 회사 옵트아웃 파일에 제공된 최신 목록만을 반영하며, 이 파일이 제공되고 처리된 시점에 매칭된 X 사용자에 대해 모든 기존 및 향후 오디언스에 이를 적용합니다. 회사 옵트아웃 파일의 형식은 다음과 같습니다. 예: partnername.removeall.txt

삭제(Delete) - 기존 오디언스를 현재 오디언스 목록에서 제거합니다. 예: loyalty&#95;card&#95;holders&#95;partnername.pepsi.delete.txt

<div id="hashing-directions">
  #### 해싱 지침
</div>

X는 일반적인 사용자 식별자(예: 이메일 주소)를 해싱하기 위해 PGP를 통해 Base64로 인코딩된 운영 키를 안전하게 공유합니다. 회사는 키를 Base64로 디코딩하여 해싱에 사용할 32바이트 키를 생성합니다.

Base64 인코딩된 키 예시:

BrQvOg+dACBUmKjRiNxZgJLh6zydjS0ZOv80FelTNzM=

Base64 디코딩된 키 예시:

/:� TшY

정규화: 회사는 해싱 전에 일반적인 사용자 식별자에 대해 기본적인 정규화 작업을 수행합니다(단, 디바이스 ID는 제외하며, Device ID Normalization 섹션을 참조하십시오).

<div id="e-mail-normalization">
  #### E-mail 정규화
</div>

즉, 앞뒤 공백을 제거하고 이메일 주소를 모두 소문자로 변환합니다.

예: 원본 e-mail 주소: testemail&#95;Organisational&#95;baseball+884`@`It92I6Ev2B`.`Com

정규화 후: testemail&#95;organisational&#95;baseball+884`@`it92i6ev2b`.`com

해시 값: 74d9584eded0ad1e5572a1c1849f3716751d371d6117a6155dad5363f4b4fbec

참고: 인코딩된 hmac과 key의 길이는 입력값과 인코딩 방식에 따라 달라질 수 있으므로, 문자 수가 고정되어 있지는 않습니다.

<div id="device-id-normalization">
  #### 디바이스 ID 정규화
</div>

우리는 디바이스 ID에 대해서도 SHA-256 해싱 알고리즘과 우리가 데이터 파트너에게 제공하는 공통 솔트를 사용한 해싱에 동일한 요구 사항을 적용합니다. 이메일 주소와 마찬가지로 공백은 모두 제거하지만, IDFA/Android ID에 대해서는 소문자 정규화를 수행하지 않으며, IDFA/Android ID의 정확한 형식을 그대로 사용해야 합니다.

다음은 해싱 이전 iOS 및 Android용 디바이스 ID의 원본 형식 예시입니다:

iOS IDFA: DD99CFF7-6186-4602-9DF2-ED3FD0B2D431

Android ID: b5bf2122961b3595

해시된 iOS IDFA: 134fb8cd95c7fd42e2793f469a447198ca5f990968db2dbadad70e723ed9750b

해시된 Android ID: 130dddff1939f229476f50bc8adab8fcb7e3525b0e9604fe8effc15e68cee4a4

<div id="x-user-id-normalization">
  #### X 사용자 ID 정규화
</div>

X ID는 PII는 아니지만 광고주에게만 비공개인 데이터 그룹(예: @handle로 구성된 고객 목록)이기 때문에 계속 해시 처리됩니다. 데이터 파트너에게 제공하는 공통 salt와 SHA-256 해싱 알고리즘을 사용해 X ID를 해시해야 한다는 동일한 요구 사항이 적용됩니다. X ID 및 `@`username에서는 공백을 모두 제거해야 하지만, User ID는 정규화가 필요하지 않습니다. 정규화를 위해 @username은 소문자로 변환해야 하며, username에 @ 기호를 포함하면 안 됩니다.

원시 ID 형식은 다음과 같습니다.

* User ID: 27674040
* @username: testusername

해시된 User ID: bf6b57d4e861e83bea8bbed2b800b251a64c95468ee6e8cb07c3368c9ed45e85

해시된 @username: 12201ae78ad1afa907c7112d17f498154ffb0bf9ea523f5390e072a06d7d9812

<div id="id-sync-integration">
  ### ID Sync Integration
</div>

`p_id`로 데이터를 전송하는 파트너는 광고주 또는 파트너의 사용자 id와 X 사용자 id 간의 매핑을 생성하기 위해 ID 동기화(ID Sync) 프로세스를 거쳐야 합니다. 이를 통해 광고주는 X에서 자사 사용자 세그먼트를 직접 타기팅할 수 있습니다. 파트너는 멤버십 업데이트를 전송할 때 `user_identifier_type` 파라미터 값을 `TALIST_PARTNER_USER_ID` 또는 `TAWEB_PARTNER_USER_ID`로 설정해야 합니다.

* **웹 전용**: 아래에 설명된 대로 광고주의 사이트에 픽셀을 설치하여 구성할 수 있습니다.
* **리스트**: [CRM](/ko/x-ads-api/audiences#crm) 페이지에 설명된 방법 중 어느 것이든 사용하여 구성할 수 있습니다.

<div id="custom-audiences-user-data">
  ### 커스텀 오디언스 사용자 데이터
</div>

이 문서는 [Custom Audience]/x-ads-api/audiences 사용자 데이터의 형식을 설명합니다.

**데이터 정규화**

**디바이스 ID**:

* IDFA - 소문자, 대시 포함; 예: `4b61639e-47cc-4056-a16a-c8217e029462`
* AdID - 디바이스의 원래 형식 그대로여야 하며, 소문자와 대시를 유지하고 대문자로 변환하지 않습니다; 예: `2f5f5391-3e45-4d02-b645-4575a08f86e`
* Android id - 디바이스의 원래 형식 그대로여야 하며, 대문자 없이, 대시나 공백 없이 사용합니다; 예: `af3802a465767e36`

**이메일 주소**:

* 소문자로 변환하고, 앞뒤 공백 제거; 예: `support@x.com`

**X 사용자 이름**:

* `@` 없이, 소문자로 변환하고, 앞뒤 공백 제거; 예: `jack`

**X 사용자 ID**:

* 표준 정수; 예: `143567`

**데이터 해싱**

각 줄의 데이터는 `SHA256`을 사용하여 salt 없이 해시해야 합니다. 또한 최종 출력 해시는 소문자여야 합니다. 예: 49e0be2aeccfb51a8dee4c945c8a70a9ac500cf6f5cb08112575f74db9b1470d이어야 하며, **49E0BE2AECCFB51A8DEE4C945C8A70A9AC500CF6F5CB08112575F74DB9B1470D**가 아니어야 합니다.

```
# python을 사용하여 사용자 @AdsAPI 해싱
import hashlib
hashlib.sha256("adsapi".encode()).hexdigest()

#output
49e0be2aeccfb51a8dee4c945c8a70a9ac500cf6f5cb08112575f74db9b1470d
```

해싱을 위한 추가 코드 샘플은 [github.com/xdevplatform/ads-platform-tools](https://github.com/xdevplatform/ads-platform-tools)에서 확인할 수 있습니다.

  ### 맞춤 잠재고객: 웹

**정보**

파트너는 광고주를 대신해 타게팅할 ID 목록(`p_user_ids`)을 전송합니다. 이는 `p_user_ids`와 X 사용자 ID 간에 매핑을 생성하는 ID 동기화(ID Sync) 프로세스를 통해 이루어집니다. 이 매핑은 이후 타게팅에 사용할 수 있는 X 사용자 ID 목록을 생성하는 데 사용됩니다. 이러한 맞춤 잠재고객은 ads.x.com의 Custom Audiences Web 캠페인 설정에서 라벨로 지정된 광고주의 특정 @handle에서 사용할 수 있게 됩니다.

X는 파트너 태그와 사이트에 삽입하여 ID(`p_user_ids`)를 X 사용자 ID와 매칭할 수 있는 보안 픽셀을 제공합니다. ID 동기화 프로세스가 완료되면 파트너가 타게팅 파일을 생성하고, HTTPS 엔드포인트를 통해 X가 사용할 수 있도록 제공합니다. 이 타게팅 파일은 X에 의해 정기적으로 수집되며, 이후 X UI에서 사용할 수 있게 됩니다.

**X 보안 픽셀**

X 보안 픽셀은 다음과 같은 형태입니다:

https://analytics.x.com/i/adsct?p&#95;user&#95;id=xyz&amp;p&#95;id=123

**`p_user_id`** - xyz는 파트너가 제공한 파트너 사용자 ID를 나타냅니다.

**`p_id`** - 123은 파트너에 대한 고유 ID(X에서 제공)를 나타냅니다.

**파트너 HTTPS 엔드포인트 &amp; 타게팅 사용자 파일**

파트너는 타게팅 파일을 정기적으로 수집할 수 있도록, X에 HTTPS 엔드포인트와 자격 증명(사용자명/비밀번호)을 제공해야 합니다. 샘플 HTTPS 엔드포인트는 다음과 같은 형태입니다:

```
https://<partnerdomain>/twitter/partner_targeting_%Y-%M-%D.tsv.gz
```

%Y - 연도 형식 코드 (YYYY)

%M - 월 형식 코드 (MM)

%D - 일 형식 코드 (DD)

전송되는 데이터는 다음 파일들로 구성됩니다:

1. Partner Targeting User File
2. Targeting Conversion File

모든 파일은 TSV 형식이며, 각 행의 개별 필드는 탭 문자로 구분됩니다. 유효한 필드 값 자체에는 탭 문자가 포함되지 않습니다.

**허용되는 X IP 범위:**

다음은 Partner Endpoint에 대한 액세스를 허용해야 하는 IP 대역입니다.

* 199.16.156.0/22
* 199.59.148.0/22

**Partner Targeting User File:**

| **Column Number** | **Column Name**   | **Column Type** | **Description**                                                                                                                                                                     |
| :---------------- | :---------------- | :-------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1                 | partner id        | 문자열             | “partner id”는 각 Partner를 고유하게 식별하기 위해 X가 Partner에게 제공하는 ID입니다.                                                                                                                      |
| 2                 | advertiser id     | 문자열             | “advertiser id”는 광고주의 @handle입니다.                                                                                                                                                   |
| 3                 | p&#95;user&#95;id | 문자열             | “p&#95;user&#95;id”는 Partner가 사용자를 식별하는 데 사용하는 고유 ID입니다.                                                                                                                            |
| 3                 | confidence score  | 정수              | “confidence score”는 선택 사항입니다. confidence score에 대해서는 0~~100을 사용할 것을 권장합니다. 사용 사례가 리타게팅인 경우, confidence score가 “100”인 사용자는 직접 리타게팅된 사용자입니다. 0~~99 범위의 모든 점수는 유사 타겟에 대한 신뢰 수준에 해당합니다. |
| 4                 | segment label     | 문자열             | “segment label”은 선택 사항입니다. Partner는 예를 들어 상품 카테고리를 지정하기 위해 “segment label”을 사용할 수 있습니다. ads.x.com UI에서 Custom Audiences에 표시되는 사람이 읽을 수 있는 이름이므로 이 “segment label”을 사용할 것을 권장합니다.    |

**참고 사항:**

새로운 Partner Targeting File을 수신할 때마다, 별도 합의가 없는 한 Partner가 타게팅 대상으로 추천하는 사용자 전체 목록으로 간주합니다(증분 파일이 아님). 이 Partner Targeting File의 전송 주기는 각 Partner와 사전에 합의합니다. 예상된 시점에 Partner Targeting File을 수신하지 못한 경우, 사전에 정의된 만료 시간까지 이전 버전을 계속 사용합니다.

  ### Overview
</div>

Audience API는 Ads API의 [v4](/ko/x-ads-api/introduction) 의 일부로 출시되었으며, 이를 통해 기존 Audiences 엔드포인트가 여러 가지 측면에서 개선되었습니다. 이 새로운 엔드포인트는 새로운 Audience 처리 백엔드를 기반으로 하며, 안정성, 견고성 및 신뢰성이 크게 향상되었습니다. 이 가이드의 목적은 Audience API와 기존 Audience 업로드 및 관리 프로세스 간의 차이점을 설명하는 것입니다. 

자세한 내용은 [Audience API](/ko/x-ads-api/audiences) 참조 문서 페이지에서 확인할 수 있습니다. 

**참고**: 모든 Audience 사용자 데이터는 업로드 전에 SHA-256으로 해시 처리해야 합니다. 허용되는 사용자 식별자 유형 및 데이터 정규화에 대한 자세한 내용은 [user data](/ko/x-ads-api/audiences) 페이지에서 확인할 수 있습니다.

**Audience 기능 변경 사항**

다음 Custom Audience 변경 사항은 v4부터 도입되었으며, 사용 중단된 엔드포인트는 Ads API v3가 종료되는 즉시 더 이상 사용할 수 없습니다:

* **사용 중단됨(Deprecated)** TON 업로드:
  * GET accounts/:account&#95;id/custom&#95;audience&#95;changes
  * GET accounts/:account&#95;id/custom&#95;audience&#95;changes/:custom&#95;audience&#95;change&#95;id
  * POST accounts/:account&#95;id/custom&#95;audience&#95;changes
  * PUT accounts/:account&#95;id/custom&#95;audiences/global&#95;opt&#95;out
* **사용 중단됨(Deprecated)** Real Time Audiences:
  * POST custom&#95;audience&#95;memberships
* Custom Audience:
  * 모든 [Custom Audience](/ko/x-ads-api/audiences) 엔드포인트의 요청 및 응답에서 `list_type` 매개변수가 제거됩니다. 이 매개변수는 이전에 Audience의 사용자 식별자 유형(예: 이메일, X User ID 등)을 식별하는 데 사용되었으나, 이제는 동일한 Audience에 대해 여러 사용자 식별자를 허용하므로 이 값은 더 이상 의미가 없습니다.
* 일반:
  * Audience 조회 기간(lookback window)은 과거 30일에서 과거 90일 이내에 활성 상태였던 사용자를 대상으로 일치하도록 업데이트되었습니다.
  * 타깃팅 가능한 오디언스로 간주되기 위해 필요한 일치 사용자 수의 최소값이 500명에서 100명으로 감소했습니다.

<Note>
  **사전 준비 사항(Prerequisites)**

  * Ads API 액세스
  * Audience 엔드포인트에 액세스하려면 허용 목록(allowlist)에 추가되어야 합니다. 이 양식을 작성하고, 2018-08-01 이전에 최초 승인되었다면 새로운 [X Ads Products and Services Agreement](/ko/x-ads-api/introduction)에 동의해야 합니다.
</Note>

**Audience 업로드 프로세스**

다음 표는 기존과 새로운 Audience 생성 흐름 간의 주요 차이점을 요약한 것이며, 아래에서 보다 자세한 설명을 제공합니다:

| Step in Process | Audience API | (Deprecated) TON Upload |
| :--- | :--- | :--- |
| Create a shell Audience | [POST custom&#95;audience endpoint]/x-ads-api/audiences 를 통해 생성할 수 있습니다 | [POST custom&#95;audience endpoint]/x-ads-api/audiences 를 통해 생성할 수 있습니다 |
| Add a new user | [Audience endpoint](/ko/x-ads-api/audiences)에서 `operation_type` `Update` 사용 | [POST custom&#95;audience&#95;changes](/ko/x-ads-api/audiences) 엔드포인트에서 `operation` `ADD` 사용 |
| Remove a user | [Audience endpoint](/ko/x-ads-api/audiences)에서 `operation_type` `Delete` 사용 | [POST custom&#95;audience&#95;changes](/ko/x-ads-api/audiences) 엔드포인트에서 `operation` `REMOVE` 사용 |
| Opting-Out Users | 사용자가 속해 있는 해당 `custom_audience_id`들과 함께 [Audience endpoint](/ko/x-ads-api/audiences)에서 `operation_type` `Delete` 사용 | [Global opt-out endpoint](/ko/x-ads-api/audiences) 사용 |

**참고** TON Upload 경로를 통해 업데이트되거나 옵트아웃되는 모든 Audience에는 [TON Upload](/ko/x-ads-api/audiences) 엔드포인트를 통해 업로드된 해당 목록이 있어야 하며, [custom&#95;audience&#95;changes](/ko/x-ads-api/audiences) 엔드포인트를 사용해 Audience와 연결되어야 합니다.

**Rate Limiting**

Audience API 엔드포인트의 요청 한도(rate limit)는 계정당 1분에 1500회입니다. 단일 페이로드에 보낼 수 있는 사용자 수에는 제한이 없습니다. 페이로드에 대한 제약 조건은 다음과 같습니다:

1. 전체 작업 수: 최대 2,500 operations

2. 최대 페이로드 크기: 5,000,000 bytes

**Audience 사용자 관리**

새로운 Audience를 생성하려면 다음 단계를 수행해야 합니다.

<div id="create-a-new-custom-audience">
  ### 새 Custom Audience 생성
</div>

[POST custom&#95;audience]/x-ads-api/audiences 엔드포인트를 사용해 새로운 Custom Audience &quot;셸&quot;을 생성하고, 해당 Custom Audience `id`를 조회합니다. 이 단계는 오디언스를 처음부터 생성하는 경우 필수입니다. 기존 오디언스를 업데이트하는 경우에는 다음 섹션으로 건너뛰세요.

<div id="add-users-to-an-audience">
  ### 오디언스에 사용자 추가
</div>

Custom Audience의 `id`와 다음과 같은 샘플 페이로드를 사용하여 [POST accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id/users](/ko/x-ads-api/audiences) 엔드포인트를 호출합니다:

POST https://ads-api.x.com/11/accounts/18ce54d4x5t/custom&#95;audiences/1nmth/users

```
    # 모든 값은 해시 처리되어야 하며, 해시되지 않은 값은 설명 목적으로만 이 예제에서 사용됩니다
    [
      {
        "operation_type": "Update",
        "params": {
          "effective_at": "2018-05-15T00:00:00Z",
          "expires_at": "2019-01-01T07:00:00Z",
          "users": [
            {
              "email": [
                "abc@x.com"
              ],
              "handle": [
                "x",
                "adsapi"
              ]
            },
            {
              "email": [
                "edf@x.com"
              ],
              "twitter_id": [
                "121291606",
                "17874544"
              ]
            }
          ]
        }
      }
    ]
```

사용자를 Audience에 추가하려면 `operation_type`으로 `Update`를 사용해야 합니다. 새 Audience 인터페이스를 사용하면 단일 사용자에 대해 여러 사용자 키를 전달할 수 있습니다. JSON 객체 배열의 각 객체는 한 명의 사용자에 해당합니다. 위의 예시 페이로드를 사용할 경우, 이 요청은 두 명의 사용자를 Audience에 추가하며, 한 사용자는 `email`과 `handle`을, 다른 사용자는 `email`과 `twitter_id`를 가집니다.

<div id="remove-users-from-an-audience">
  #### 오디언스에서 사용자 제거
</div>

사용자를 추가하는 과정과 마찬가지로, 다음과 같이 요청을 보내 오디언스에서 사용자를 제거할 수 있습니다:

POST https://ads-api.x.com/11/accounts/18ce54d4x5t/custom&#95;audiences/1nmth/users

```
    # 모든 값은 해시 처리되어야 하며, 이 예제에서는 설명 목적으로 해시되지 않은 값을 사용합니다
    [
      {
        "operation_type": "Delete",
        "params": {
          "effective_at": "2018-05-15T00:00:00Z",
          "expires_at": "2019-01-01T07:00:00Z",
          "users": [
            {
              "email": [
                "abc@x.com"
              ],
              "twitter_id": [
                "783214",
                "1225933934"
              ]
            },
            {
              "email": [
                "edf@x.com"
              ],
              "twitter_id": [
                "121291606",
                "17874544"
              ]
            }
          ]
        }
      }
    ]
```

`operation_type`는 반드시 `Delete`로 설정해야 하며, 사용자는 오디언스에 사용자를 추가할 때 사용된 키 중 어느 것이든 일치하면 됩니다. 예를 들어, 한 사용자가 `email`과 `twitter_id`로 오디언스에 추가된 경우, 동일한 사용자는 이 키들 중 어느 하나만으로도 제거할 수 있습니다. 즉, `email`이나 `twitter_id` 또는 둘 다를 사용할 수 있습니다.

또한, 하나의 요청 내에서 오디언스에 사용자를 추가하고 제거하는 것도 가능합니다. 이 엔드포인트는 요청당 여러 `operation_type` 값을 지원합니다.

<div id="opt-out-users">
  #### 옵트아웃 사용자
</div>

글로벌 옵트아웃 엔드포인트가 사용 중단됨에 따라, 파트너는 어떤 Audience에서든 옵트아웃한 사용자를 `Delete` 해야 합니다. 이를 수행하는 방법은 다음과 같습니다.

1. 어떤 사용자가 어떤 Audience에 속해 있는지 추적하고, 각 Audience에서 해당 사용자를 개별적으로 제거합니다.
2. 해당 사용자와 연결된 Ads 계정의 **모든** Audience에서 사용자를 제거합니다.

**일반 모범 사례**

* 큐에 부하가 몰려 처리 시간이 길어지고 전반적으로 시스템에 불필요한 부하를 주는 것을 피하기 위해, 이 엔드포인트는 준 실시간 배치 방식으로 호출할 것을 강력히 권장합니다. 이렇게 하면 사용자를 캠페인 타기팅에 더 빨리 활용할 수 있습니다.
* 성공적인 API 호출은 요청에서 수신된 `user` 객체 수에 해당하는 `success_count`와 `total_count`를 반환합니다.
* 이 엔드포인트는 원자적(atomic) 특성을 가지므로, 전체 요청이 성공하거나, 오류가 발생할 경우 전체 요청이 실패합니다. 오류 응답이 발생한 경우, API 이용자는 오류를 수정한 뒤 전체 페이로드로 요청을 다시 시도하는 것이 권장됩니다. 
* 실패 시, 파트너에게는 재시도와 함께 [지수 백오프](https://en.wikipedia.org/wiki/Exponential_backoff) 방식을 사용할 것을 권장합니다. 예를 들어, 첫 번째 실패 시에는 즉시 재시도하고, 두 번째 실패 후에는 1분 뒤에 재시도하며, 세 번째 연속 실패 후에는 5분 뒤에 재시도하는 식으로 진행합니다.

이 엔드포인트를 사용하면 파트너가 지정된 `custom_audience_id`에서 사용자를 추가, 업데이트 및 제거할 수 있습니다. 또한 이 엔드포인트는 하나의 사용자에 대해 여러 사용자 식별자 유형도 허용합니다.

요청의 `users` 필드에 제공되는 모든 데이터는 `partner_user_id`를 **제외하고** `SHA256`으로 해시되어야 하며, [정규화](/ko/x-ads-api/audiences#twitter-user-id-normalization)되어야 합니다.

**배치 요청**

* 현재 **이 엔드포인트의** 최대 배치 크기는 `2500`입니다. 배치 크기는 요청당 작업(`Update`/`Delete`) 수에 따라 결정됩니다. 예를 들어, 하나의 배열에 2500개가 넘는 작업 객체(`{"operation_type": "Update/Delete", [..] }`)가 포함되면 오류가 발생합니다.
* 이 엔드포인트가 수락할 수 있는 요청 POST 본문의 최대 크기는 `5,000,000`바이트입니다.
* 이 엔드포인트에 대한 rate limit은 1분당 1500회입니다.
* 모든 매개변수는 요청 본문으로 전송되며, `Content-Type`은 `application/json`이어야 합니다.
* 배치 요청은 그룹 단위로 함께 실패하거나 성공하며, 오류 및 성공에 대한 모든 API 응답은 초기 요청의 항목 순서를 그대로 유지합니다.

**배치 응답**

Ads API가 반환하는 응답에는 `success_count`와 `total_count` 두 개의 필드가 포함됩니다. 이 값들은 항상 동일해야 하며, 백엔드에서 처리한 요청 내 레코드 수를 나타냅니다. 요청 본문에 전송된 레코드 수가 `success_count` 및 `total_count`와 **동일하지 않은** 상황은 오류 상태로 간주해야 하며, 재시도가 필요합니다.

**배치 오류**

* 요청 수준 오류(예: 최대 배치 크기 초과)는 응답의 `errors` 객체에 표시됩니다.
* 항목 수준 오류(예: 필수 매개변수 누락)는 응답의 `operation_errors` 객체에 표시됩니다.
* `operation_errors`의 오류 인덱스는 입력 항목의 인덱스를 가리키며, 해당 인덱스의 항목에 대한 오류 메시지가 함께 제공됩니다.

**배치 요청**

* 현재 최대 배치 크기는 10입니다.
* 모든 파라미터는 요청 본문에 포함되며, `Content-Type`은 `application/json`이어야 합니다.

**배치 응답**

배치 API 응답은 요청 순서가 보존된 항목 컬렉션을 반환합니다. 이외에는 해당 단일 항목 엔드포인트와 구조가 동일합니다.

**배치 오류**

* 요청 수준 오류(예: 최대 배치 크기 초과)는 응답의 `errors` 객체 아래에 표시됩니다.

  #### POST batch/accounts/:account_id/do_not_reach_lists/:do_not_reach_list_id/users[](#post-batch-accounts-account-id-do-not-reach-lists-do-not-reach-list-id-users "Permalink to this headline")

이 엔드포인트를 사용하면 지정된 `do_not_reach_list_id` 에 사용자를 추가, 업데이트 및 제거할 수 있습니다. 이 엔드포인트는 유효한 사용자 식별자 유형으로 이메일만 허용합니다.

요청의 `emails` 필드에 제공되는 모든 데이터는 `SHA256` 을 사용해 해시 처리해야 하며, [정규화](/ko/x-ads-api/audiences#e-mail-normalization)되어야 합니다.

**참고**

* 하나의 `account_id` 는 최대 하나의 Do Not Reach List만 가질 수 있습니다.
* 이 목록에 추가되는 사용자는 현재 타임스탬프 기준으로 13개월 미만이 되도록 `expires_at` 타임스탬프가 **반드시** 설정되어 있어야 합니다.
* Do Not Reach List API는 `effective_at` 타임스탬프를 허용하지 않으며 기본값으로 현재 타임스탬프를 사용합니다.
* Do Not Reach List는 계정의 임의 또는 모든 커스텀 오디언스에서 사용자를 제거하지 않으며, 계정에서 집행되는 모든 캠페인에 대한 제외 타게팅으로 동작합니다.

**배치 요청**

* 이 엔드포인트에 대한 현재 최대 배치 크기는 `2500` 입니다. 배치 크기는 요청당 작업(`Update`/`Delete`) 수에 의해 결정됩니다. 예를 들어, 하나의 배열에 2500개를 초과하는 작업 객체(`{"operation_type": "Update/Delete", [..] }`)가 포함되면 오류가 발생합니다.
* 이 엔드포인트가 허용하는 최대 요청 POST 본문 크기는 `5,000,000` 바이트입니다.
* 이 엔드포인트에 대한 레이트 리밋(요청 제한)은 1분 단위 윈도우당 1500회입니다.
* 모든 파라미터는 요청 본문에 전송되며, `Content-Type` 으로 `application/json` 이 필요합니다.
* 배치 요청은 하나의 그룹으로 함께 실패하거나 성공하며, 오류 및 성공에 대한 모든 API 응답에서 초기 요청의 항목 순서는 그대로 유지됩니다.

**배치 응답**

Ads API가 반환하는 응답에는 `success_count` 와 `total_count` 두 필드가 포함됩니다. 이 값들은 항상 동일해야 하며, 백엔드에서 처리된 요청 내 레코드 수를 나타냅니다. 요청 본문에 전송된 레코드 수가 `success_count` 및 `total_count` 와 **같지 않은** 상황은 오류 상태로 간주해야 하며, 재시도가 필요합니다.

**배치 오류**

* 요청 수준 오류(예: 최대 배치 크기 초과)는 응답의 `errors` 객체 아래에 표시됩니다.

* `operation_errors` 내 오류의 인덱스는 입력 항목 내 인덱스를 가리키며, 해당 오류 메시지와 연결됩니다.

## 맞춤 잠재고객

<div id="overview">
  ### Overview
</div>

파트너가 [Custom Audiences](https://business.x.com/en/targeting/tailored-audiences.html)를 생성하는 방법에는 여러 가지가 있습니다.

* [Audience API (CRM)](#crm)
* [Web](#web)
* [Mobile](#mobile)
* [Flexible](#flexible)

유사 맞춤 잠재고객(Custom Lookalike Custom Audience)은 타기팅에서 제외 대상으로 사용할 수 없습니다. 또한 하나의 광고 라인 아이템(광고 그룹)에서 맞춤 잠재고객과 맞춤 잠재고객 유사 대상을 동시에 타기팅할 수 없습니다.

**Audience management**

잠재고객은 잠재고객(audience) 파트너와 Ads API 파트너를 통해 관리할 수 있습니다. API에서는 맞춤 잠재고객에 액세스하고 이를 유지 관리할 수 있는 일련의 엔드포인트를 제공합니다.

맞춤 잠재고객 정보의 경우 다음 2개의 엔드포인트를 제공합니다.

* [GET accounts/:account&#95;id/custom&#95;audiences](/ko/x-ads-api/audiences)
* [GET accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id](/ko/x-ads-api/audiences)

잠재고객을 업로드하고 관리하는 방법에 대한 자세한 내용은 [Audience API 가이드](/ko/x-ads-api/audiences)를 참고하세요.

**Processing Times**

일반적으로 잠재고객 변경 사항은 6~8시간마다 실행되는 배치 작업으로 처리됩니다. 잠재고객 변경이 처리되는 동안, 업데이트 대상이 되는 기존 잠재고객은 영향을 받지 않습니다. 이 시간 내에 잠재고객 하나당 추가는 한 번, 제거는 한 번을 초과하여 업데이트하지 않는 것을 권장합니다.

**Targeting**

잠재고객은 X가 소유·운영하는 클라이언트에서 지난 90일 동안 활성 상태였던 사용자 최소 100명과 일치하는 경우에만 타기팅할 수 있습니다. [GET accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id](/ko/x-ads-api/audiences)는 잠재고객과 일치하는 사용자가 너무 적어 타기팅할 수 없는 경우 이를 표시합니다.

**Q: 아주 많은 data를 전송했는데, 왜 audience size가 TOO&#95;SMALL로 표시되나요?**

A: 현재 data는 실시간으로 audience에 추가되고 있지만, audience size를 계산하기 위해 data를 처리하는 작업은 일정 주기마다만 실행됩니다. 몇 시간 정도가 지나면 UI에 올바른 audience size가 표시됩니다.

**Q: audience data 전송을 모두 마치고 24시간 이상 기다렸는데도 여전히 해당 audience를 타깃팅할 수 없습니다. 다음 단계로 무엇을 해야 하나요?**

A: 다음 사항들을 확인해 주세요:

* 전달되는 user ID가 올바르고 형식이 깨지지 않았는지 확인합니다.
* 전달되는 audience 이름이 올바르며, 이전 membership 업데이트와 일치하는지 확인합니다.
* POST 명령의 응답을 확인해 주세요.
* ID Sync 픽셀이 올바르게 구현되었는지, 그리고 ID Sync 프로세스에 설명된 대로 충분한 수의 사용자가 해당 사이트를 방문하여 사용자를 매핑할 수 있었는지 확인해 주세요. membership 업데이트에 포함된 매핑되지 않은 사용자는 타깃팅 대상 사용자로 전환되지 않습니다.

위의 모든 항목이 올바르고 정상적으로 작동하는 것이 확인되면, 가능한 한 상세한 정보와 함께 X 제품 담당자에게 문의해 주세요(선호하는 정보 예시는 [Guide to Partner Inbounds](/ko/x-ads-api/introduction)를 참조하세요).

**Q: 이 endpoint는 몇 번까지 호출할 수 있고, 어떤 알고리즘을 사용해야 하나요?**

A: 전체 audience membership을 다시 보내지 말고, 증분 delta 방식으로만 시스템을 호출하실 것을 강력히 권장합니다. 이 시스템은 전 세계에서 가장 큰 웹사이트들에 대해서도 증분 data 업데이트를 처리할 수 있을 만큼 충분한 처리량을 갖추도록 테스트되었습니다. 초기 audience 업로드는 신중하게 속도를 제어해야 하며, 첫 업로드는 완료까지 상당한 시간이 걸릴 것으로 예상됩니다.

**Q: 타깃팅에 사용할 수 있는 audience의 최소 크기는 얼마인가요?**

* audience의 최소 크기는 100명(매칭 이후 기준)입니다. 500명 미만의 사용자가 매칭된 audience는 X Ads UI에서 타깃팅에 사용할 수 없습니다.

**Q: audience 파일을 처리하는 데 얼마나 걸리며, X 사용자 인터페이스에서 audience 파일을 사용할 수 있게 되기까지 얼마나 걸리나요?**

* 일반적으로 audience 파일을 처리하는 데는 4~6시간이 걸리지만, 파일 크기에 따라 달라질 수 있습니다. 파일 처리가 완료되면 해당 audiences는 X Ads UI에서 사용할 수 있게 됩니다.

**Q: 매칭률은 어떻게 계산되나요?**

* 매칭률 = 최근 90일간 활성 X 사용자 수 / 제공한 사용자 수

**Q: audience 파일이 제대로 작동하는지 어떻게 테스트하나요?**

* 테스트 audience 파일을 제공하고 광고주 handle로 “keltonlynn”을 사용하실 수 있습니다. 그러면 해당 파일이 X UI로 적절히 수집되고 로드되는지 확인할 수 있습니다.

**Q: partner user identifier(`p_user_id`)란 무엇인가요?**

* 이는 귀사가 각 고객을 고유하게 식별하기 위해 사용하는 식별자입니다.

**Q: standard ID란 무엇인가요?**

* 이메일 주소, device ID, X @handle 또는 ID가 될 수 있습니다.

**Q: HMAC Key는 어떻게 받나요?**

* 암호화된 이메일을 통해 제공됩니다. [mpp-inquiry@x.com](mailto:mpp-inquiry%x.com)으로 귀사의 공개 PGP 키를 보내 주시면, 모든 것이 정상 작동하는지 확인하기 위한 테스트 이메일을 발송하겠습니다. 확인이 완료되면 HMAC Key를 보내 드립니다.

**Q: 제공된 HMAC Key를 사용하여 해싱 프로세스가 제대로 작동했는지 어떻게 확인하나요?**

* X에서 테스트 파일(샘플 이메일 주소, device ID 등 포함)과 결과 hash 파일을 제공하며, 이를 사용해 귀하의 결과를 검증할 수 있습니다.

**Q: full data match 파일에 파일 크기 제한이 있나요?**

* 아닙니다. full data match 파일에는 크기 제한이 없습니다.

**Q: full data match 파일이 처리되는 데는 얼마나 걸리나요?**

* X에서 파일을 수신한 시점부터 대략 1일 정도가 소요됩니다.

**요약**

Company는 고객을 대신해 해시된 공통 사용자 식별자(예: 이메일 주소) 목록 또는 파트너 사용자 ID 목록을 X에 제공하여 블라인드 매치를 수행하고, 타겟팅에 사용할 X 사용자 ID 목록을 생성합니다. 타겟팅용 세그먼트는 ads.x.com 캠페인 설정 시 파일 이름에 지정된 광고주의 특정 @handle에서 사용할 수 있게 됩니다.

Company에서 X로 전송되는 모든 파일은 X가 Company에 부여한 전용 계정을 통해 IronBox(www.golockbox.com)의 보안 패키지를 사용하여 전송됩니다. X는 IronBox에 대한 액세스를 제공합니다. IronBox API에 대한 문서는 [https://secure.goironcloud.com/Docs/Help/](https://secure.goironcloud.com/Docs/Help/)에서 확인할 수 있습니다.

<div id="partner-id-matching-requirements">
  #### 파트너 ID 매칭 요건
</div>

회사가 사용자 추적을 위해 자체 표준 ID 시스템(즉, 이메일 주소, 디바이스 id, X user ID 등과 같은 일반적인 사용자 식별자가 아님)을 사용하는 경우, 다음 프로세스를 따르는 것을 권장합니다.

**1. 전체 데이터 매칭(Full Data Match)**

초기에는 회사가 X와 공통 사용자 식별자(고유한 값)를 포함하는 모든 사용자 레코드의 전체 목록을 단일 파일로 제공하여 전체 데이터 매칭을 수행하고, 파트너 ID(`p_user_id`)와 X ID(`tw_id`) 간의 매핑을 X가 보관합니다. 이는 적절한 유지 관리를 위해 정기적으로 2~3개월 단위로 수행됩니다. 매칭이 완료되면 X는 이 파일로부터 산출된 기준 매칭률을 이메일로 회사에 공유합니다.

이 파일의 형식은 다음과 같아야 합니다:

Name Convention: FullDataMatch.[CompanyName].txt

Hashing Algorithm: HMAC&#95;SHA-256

Format:

Column 1: 공통 식별자의 HMAC 해시 값

Column 2: 파트너 사용자 ID(사용자별로는 고유하지만, 파일 내에서는 중복 가능)

Column Delimiter (CSV): 해시된 공통 사용자 식별자와 파트너 ID를 구분하기 위해 쉼표 사용

줄 단위로 구분된 값

* 예: 사용자 레코드 A에 파트너 사용자 ID 1과 공통 식별자 1, 2, 3이 있는 경우:

|     |     |
| :--- | :--- |
| common user identifier 1 | p&#95;user&#95;1 |
| common user identifier 2 | p&#95;user&#95;1 |
| common user identifier 3 | p&#95;user&#95;1 |

*공통 사용자 식별자에 대한 자세한 내용은 아래의 Hashing Directions 섹션을 참조하세요.

**2. 커스텀 세그먼트 리스트(Custom Segment Lists)**

회사는 X에서 타게팅할 수 있는 Custom Audiences를 생성하기 위해 `p_user_id` 형식의 사용자 목록을 제공합니다.

* 줄 단위로 구분된 값
* `p_user_id`
* * (위 1. Full Data Match 섹션에서 제공된 값과 동일합니다. Full Data Match에서 제공된 값이 해시된 값인 경우, 회사는 오디언스 파일에서도 동일한 해시 값을 제공합니다. 제공된 값이 해시되지 않은 값인 경우, 회사는 해시되지 않은 값을 제공합니다.)

  #### 표준 매칭 요구 사항
</div>

회사가 모든 고객 사용자 식별자의 매핑에 표준 ID를 사용하지 않는 경우, 다음 프로세스를 권장합니다.

**커스텀 세그먼트 목록**

회사는 고객을 대신하여 맞춤형 오디언스(Custom Audiences)를 생성할 수 있도록, 해시 처리된 공통 사용자 식별자 목록을 X에 직접 제공합니다.

이 파일의 형식은 다음과 같아야 합니다.

* 줄바꿈으로 구분된 값
* 해시 처리된 공통 사용자 식별자(예: 이메일 주소)
* 아래에 설명된 파일 명명 규칙 준수
* 아래의 이메일 주소 해싱 지침(“해싱 지침” 절) 준수

<div id="custom-segment-list-file-naming-operations">
  #### 커스텀 세그먼트 리스트 파일 이름 지정 및 작업
</div>

파일에 적용되는 작업은 파일 이름으로 결정되며, 사용 가능한 작업과 일반적인 파일 이름 지정 규칙은 다음과 같습니다: audiencename&#95;partnername.handle.operation.filetype

* audiencename: Custom Audience의 이름입니다. 이 값은 ads.x.com 캠페인 설정 UI에서 오디언스를 선택할 때 표시되는 이름입니다. 예: brand&#95;loyalty&#95;card&#95;holders.
* partnername: 광고주를 대신해 data를 제공하는 회사의 이름입니다. 예: company&#95;name.
* handle: Custom Audiences에 액세스할 수 있는 X 계정(@handle)입니다. 예: @pepsi, @dietpepsi
* operation: new, add, remove, removeall, replace (자세한 내용은 아래 참조)
* : 각 업로드된 오디언스 파일이 고유해지도록 하기 위해 사용하는, 초 단위의 표준 Unix epoch 시간입니다.
* filetype: 파일은 *.txt 형식이어야 합니다.

<div id="creating-and-updating-audiences">
  #### 잠재고객 생성 및 업데이트
</div>

단일 파일로 새 잠재고객을 생성합니다. 예: loyalty&#95;card&#95;holders&#95;partnername.pepsi.new.txt

Add - 목록의 일치 항목을 기존 잠재고객에 추가합니다. 예: loyalty&#95;card&#95;holders&#95;partnername.pepsi.add..txt

Remove - 목록의 일치 항목을 기존 잠재고객에서 제거합니다. 예: loyalty&#95;card&#95;holders&#95;partnername.pepsi.remove..txt

Remove All - 정기적으로 업데이트되는 누적 목록에서 생성된 일치 항목을 해당 클라이언트의 모든 잠재고객에서 제거합니다(즉, 클라이언트의 옵트아웃 목록). 예: partnername.pepsi.removeall.txt

* 이는 광고주로부터 옵트아웃한 사용자들의 포괄적인 목록에 사용할 수 있습니다.
* X는 이 파일에 제공된 최신 목록만을 기준으로 하며, 이 목록과 매칭되는 기존 및 향후 모든 잠재고객에 대해 이를 적용합니다.

이 파일이 제공되고 처리된 시점에 존재하던 X 사용자를 기준으로 합니다.

Replace - 기존 잠재고객을 제거하고 새 잠재고객 목록으로 교체합니다. 예: loyalty&#95;card&#95;holders&#95;partnername.pepsi.replace..txt

전체 회사 옵트아웃 - 회사는 자사의 옵트아웃 정책에 따라 옵트아웃한 사용자를 제거하기 위해 누적 옵트아웃 파일을 제공합니다.

X는 이 회사 옵트아웃 파일에 제공된 최신 목록만을 기준으로 하며, 이 목록과 매칭되는 기존 및 향후 모든 잠재고객에 대해, 이 파일이 제공되고 처리된 시점에 존재하던 X 사용자에 대해 이를 적용합니다. 회사 옵트아웃 파일의 형식은 다음과 같습니다. 예: partnername.removeall.txt

Delete - 기존 잠재고객을 현재 잠재고객 목록에서 제거합니다. 예: loyalty&#95;card&#95;holders&#95;partnername.pepsi.delete.txt

<div id="hashing-directions">
  #### 해시 지침
</div>

X는 공통 사용자 식별자(예: 이메일 주소)를 해싱하는 데 사용할 Base64 인코딩된 프로덕션 키를 PGP를 통해 안전하게 공유합니다. 회사는 키를 Base64로 디코딩하여 해싱에 사용할 32바이트 키를 생성합니다.

Base64 인코딩된 키 예시:

BrQvOg+dACBUmKjRiNxZgJLh6zydjS0ZOv80FelTNzM=

Base64 디코딩된 키 예시:

/:� TшY

정규화: 회사는 해싱 전에 공통 사용자 식별자에 대해 기본적인 정규화를 수행합니다(단, Device ID는 제외하며 Device ID Normalization 섹션을 참조하십시오).

<div id="e-mail-normalization">
  #### 이메일 정규화
</div>

즉, 앞뒤 공백을 제거하고 이메일 주소의 모든 문자를 소문자로 변환합니다.

예: 원본 이메일 주소: testemail&#95;Organisational&#95;baseball+884`@`It92I6Ev2B`.`Com

정규화 후: testemail&#95;organisational&#95;baseball+884`@`it92i6ev2b`.`com

해시된 값: 74d9584eded0ad1e5572a1c1849f3716751d371d6117a6155dad5363f4b4fbec

참고: 인코딩된 HMAC과 키 모두에서 문자 수는 입력값과 인코딩 방식에 따라 달라질 수 있으므로, 특정한 문자 수로 고정되지 않습니다.

<div id="device-id-normalization">
  #### Device ID 정규화
</div>

디바이스 ID 해싱에는 데이터 파트너에게 제공하는 공통 salt와 SHA-256 해싱 알고리즘을 사용하는 동일한 요건이 적용됩니다. 이메일 주소와 마찬가지로 공백은 제거하지만, IDFA/Android ID에 대해서는 소문자 변환 정규화를 수행하지 않으며, IDFA/Android ID의 정확한 원본 형식을 그대로 사용해야 합니다.

다음은 해싱 이전 iOS 및 Android 디바이스 ID의 원본 형식 예시입니다:

iOS IDFA: DD99CFF7-6186-4602-9DF2-ED3FD0B2D431

Android ID: b5bf2122961b3595

해싱된 iOS IDFA: 134fb8cd95c7fd42e2793f469a447198ca5f990968db2dbadad70e723ed9750b

해싱된 Android ID: 130dddff1939f229476f50bc8adab8fcb7e3525b0e9604fe8effc15e68cee4a4

<div id="x-user-id-normalization">
  #### X 사용자 ID 정규화
</div>

X ID는 계속 해시 처리됩니다. 이는 @handles로 구성된 Customer List와 같은 data의 그룹이 PII는 아니더라도 광고주에게만 속하는 비공개 정보이기 때문입니다. 우리는 데이터 파트너에게 제공하는 공통 salt와 SHA-256 해싱 알고리즘을 사용하여 X ID를 해시하는 데 동일한 요구 사항을 적용합니다. X ID 및 `@`username 둘 다에서 공백은 제거해야 하지만, User ID는 정규화가 필요하지 않습니다. 정규화를 위해 @username은 소문자로 변환해야 합니다. 또한 @ 기호는 username의 일부로 포함하면 안 됩니다.

원시 ID 형식은 다음과 같습니다.

* User ID: 27674040
* @username: testusername

해시된 User ID: bf6b57d4e861e83bea8bbed2b800b251a64c95468ee6e8cb07c3368c9ed45e85

해시된 @username: 12201ae78ad1afa907c7112d17f498154ffb0bf9ea523f5390e072a06d7d9812

<div id="id-sync-integration">
  ### ID Sync 통합
</div>

`p_id`와 함께 데이터를 전송하는 파트너는 광고주 또는 파트너의 사용자 id와 X 사용자 id 간 매핑을 생성하기 위한 ID 동기화(ID Sync) 프로세스를 거쳐야 합니다. 이를 통해 광고주는 X에서 자체 사용자 세그먼트를 직접 타겟팅할 수 있습니다. 파트너는 멤버십 업데이트를 보낼 때 `user_identifier_type` 매개변수의 값을 `TALIST_PARTNER_USER_ID` 또는 `TAWEB_PARTNER_USER_ID`로 설정해야 합니다.

* **리스트**: [CRM](/ko/x-ads-api/audiences#crm) 페이지에 설명된 방법 중 어느 것이든 사용하여 구현할 수 있습니다.

| :---------------- | :---------------------------------- | :-------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| 1                 | Partner ID                          | 문자열             | “partner id”는 각 파트너를 고유하게 식별하기 위해 X가 파트너에게 제공하는 ID입니다.                                                                                                                                                                                                                       |

그 외 모든 단계는 [Real-Time Audience API Integration Guide](/ko/x-ads-api/audiences)에 나열된 내용과 동일하게 유지됩니다.

<div id="custom-audiences-user-data">
  ### 맞춤 잠재고객 사용자 데이터
</div>

이 문서는 [Custom Audience]/x-ads-api/audiences 사용자 데이터의 형식을 설명합니다.

**데이터 정규화**

**디바이스 ID**:

* IDFA - 대시(`-`)를 포함해 모두 소문자; 예: `4b61639e-47cc-4056-a16a-c8217e029462`
* AdID - 기기에서 사용하는 원래 형식이어야 하며, 대문자 없이 대시를 포함; 예: `2f5f5391-3e45-4d02-b645-4575a08f86e`
* Android id - 기기에서 사용하는 원래 형식이어야 하며, 대문자 없이 대시나 공백 없이 표기; 예: `af3802a465767e36`

**이메일 주소**:

* 모두 소문자로 변환하고 앞뒤 공백 제거; 예: `support@x.com`

**X 사용자 이름**:

* `@` 없이, 모두 소문자로 하고 앞뒤 공백 제거; 예: `jack`

**X 사용자 ID**:

* 표준 정수; 예: `143567`

**데이터 해싱**

각 줄의 데이터는 salt 없이 `SHA256`으로 해시해야 합니다. 또한 최종 출력 해시는 모두 소문자여야 합니다. 예: 49e0be2aeccfb51a8dee4c945c8a70a9ac500cf6f5cb08112575f74db9b1470d 이고 **49E0BE2AECCFB51A8DEE4C945C8A70A9AC500CF6F5CB08112575F74DB9B1470D가 아니어야 합니다.**

```
# python을 사용하여 사용자 @AdsAPI 해싱
import hashlib
hashlib.sha256("adsapi".encode()).hexdigest()

#output
49e0be2aeccfb51a8dee4c945c8a70a9ac500cf6f5cb08112575f74db9b1470d
```

추가 해싱 코드 샘플은 [github.com/xdevplatform/ads-platform-tools](https://github.com/xdevplatform/ads-platform-tools)에서 확인할 수 있습니다.

**정보**

파트너는 광고주를 대신해 타겟팅에 사용할 ID(`p_user_ids`) 목록을 전송합니다. 이는 `p_user_ids`와 X 사용자 ID 간의 매핑을 구축하는 ID 동기화(ID Sync) 프로세스를 통해 이루어집니다. 이렇게 생성된 매핑을 사용해 타겟팅에 사용할 수 있는 X 사용자 ID 목록을 생성합니다. 이러한 커스텀 오디언스는 ads.x.com Custom Audiences Web 캠페인 설정에서 레이블로 지정된, 광고주의 특정 @handle에 사용 가능하게 됩니다.

X는 파트너 태그 및 사이트에 삽입할 수 있는 보안 픽셀을 제공하며, 이를 통해 ID(`p_user_ids`)를 X 사용자 ID와 매칭합니다. ID 동기화 프로세스가 완료되면 파트너가 타겟팅 파일을 생성하고, 이 파일을 HTTPS 엔드포인트를 통해 X에서 이용할 수 있도록 제공합니다. 이러한 타겟팅 파일은 X에서 정기적으로 수집되며 이후 X UI에서 사용할 수 있습니다.

**X 보안 픽셀**

X 보안 픽셀은 다음과 같은 형태입니다:

https://analytics.x.com/i/adsct?p&#95;user&#95;id=xyz&amp;p&#95;id=123

**`p_user_id`** - xyz는 파트너가 제공하는 파트너 사용자 ID를 나타냅니다.

**`p_id`** - 123은 파트너에 대한 고유 ID를 나타냅니다(X에서 제공).

**파트너 HTTPS 엔드포인트 &amp; 타겟팅 사용자 파일**

파트너는 타겟팅 파일을 정기적으로 수집할 수 있도록 X에 HTTPS 엔드포인트와 자격 증명(사용자 이름/비밀번호)을 제공해야 합니다. 샘플 HTTPS 엔드포인트는 다음과 같은 형태입니다:

```
https://<partnerdomain>/twitter/partner_targeting_%Y-%M-%D.tsv.gz
```

%Y - 연도(YYYY)를 나타내는 형식 코드

%M - 월(MM)을 나타내는 형식 코드

%D - 일(DD)을 나타내는 형식 코드

전송되는 데이터는 다음 파일들로 구성됩니다:

1. 파트너 타기팅 사용자 파일 (Partner Targeting User File)
2. 타기팅 전환 파일 (Targeting Conversion File)

모든 파일은 TSV 형식이며, 각 행의 개별 필드는 탭(tab) 문자로 서로 구분됩니다. 유효한 필드 값 자체에는 탭 문자가 포함되지 않습니다.

**허용되는 X IP 범위:**

파트너 엔드포인트(Partner Endpoint)에 대한 액세스를 허용할 수 있는 IP 범위는 다음과 같습니다.

* 199.16.156.0/22
* 199.59.148.0/22

**Partner Targeting User File:**

| **Column Number** | **Column Name**   | **Column Type** | **Description**                                                                                                                                                                        |
| :---------------- | :---------------- | :-------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1                 | partner id        | 문자열             | “partner id”는 각 파트너를 고유하게 식별하기 위해 X가 파트너에게 제공하는 ID입니다.                                                                                                                                 |
| 2                 | advertiser id     | 문자열             | “advertiser id”는 광고주의 @handle입니다.                                                                                                                                                      |
| 3                 | p&#95;user&#95;id | 문자열             | “p&#95;user&#95;id”는 파트너가 사용자를 식별하는 데 사용하는 고유 ID입니다.                                                                                                                                   |
| 3                 | confidence score  | 정수              | “confidence score”는 선택 사항입니다. confidence score에 대한 권장 값 범위는 0–100입니다. 리타게팅이 사용 사례인 경우, confidence score가 “100”인 사용자는 직접 리타게팅된 사용자입니다. 0–99 범위의 값은 유사 사용자(look-alike)에 대한 신뢰 수준을 나타냅니다. |
| 4                 | segment label     | 문자열             | “segment label”은 선택 사항입니다. 파트너는 예를 들어 제품 카테고리를 지정하기 위해 “segment label”을 사용할 수 있습니다. 이 “segment label”은 ads.x.com UI에서 Custom Audiences에 표시되는 사람이 읽을 수 있는 이름이므로 사용하는 것을 권장합니다.          |

**참고 사항:**

새로운 Partner Targeting File을 수신할 때마다, 별도로 합의한 경우가 아니라면, 이 파일이 파트너가 타기팅 대상으로 추천하는 사용자의 전체 목록이라고 예상합니다(증분 파일이 아님). 이 Partner Targeting File의 전송 빈도는 각 파트너와 별도로 합의합니다. 예상한 시점에 Partner Targeting File을 수신하지 못한 경우, 미리 정의된 만료 시간까지 이전 버전을 계속 사용합니다.

<div id="audience-api-integration">
  ## Audience API 연동
</div>

### 개요

Audience API는 Ads API의 [v4](/ko/x-ads-api/introduction)에서 도입되었으며, 이를 통해 기존 Audiences 엔드포인트가 여러 측면에서 개선되었습니다. 이 새로운 엔드포인트는 새로운 Audience 처리 백엔드를 기반으로 하며, 안정성, 견고성 및 신뢰성 측면에서 다양한 향상을 제공합니다. 이 가이드의 목적은 Audience API와 기존 Audience 업로드 및 관리 프로세스 간의 차이점을 설명하는 것입니다. 

참조 문서는 [Audience API](/ko/x-ads-api/audiences) 참조 문서 페이지에서 확인할 수 있습니다. 

**참고**: 모든 Audience 사용자 데이터는 업로드 전에 SHA-256으로 해시 처리되어야 합니다. 허용되는 사용자 식별자 유형 및 데이터 정규화에 대한 자세한 내용은 [user data](/ko/x-ads-api/audiences) 페이지에서 확인할 수 있습니다.

**Audience 기능 변경 사항**

다음 Custom Audience 관련 변경 사항은 v4부터 도입되었으며, 지원이 중단된 엔드포인트는 Ads API v3가 종료된 이후 더 이상 사용하실 수 없습니다.

* **사용 중단됨(Deprecated)** TON 업로드:
  * GET accounts/:account&#95;id/custom&#95;audience&#95;changes
  * GET accounts/:account&#95;id/custom&#95;audience&#95;changes/:custom&#95;audience&#95;change&#95;id
  * POST accounts/:account&#95;id/custom&#95;audience&#95;changes
  * PUT accounts/:account&#95;id/custom&#95;audiences/global&#95;opt&#95;out
* **사용 중단됨(Deprecated)** Real Time Audiences:
  * POST custom&#95;audience&#95;memberships
* Custom Audience:
  * 모든 [Custom Audience](/ko/x-ads-api/audiences) 엔드포인트의 요청 및 응답에서 `list_type` 매개변수가 제거됩니다. 이 매개변수는 이전에 Audience의 사용자 식별자 유형(예: 이메일, X User ID 등)을 식별하는 데 사용되었으나, 이제 Audience는 동일한 Audience에 대해 여러 사용자 식별자를 수용할 수 있게 되어 이 값은 더 이상 의미를 갖지 않습니다.
* 일반:
  * Audience 조회(lookback) 기간이 최근 30일에서 90일 이내에 활성 상태였던 사용자와 일치하도록 변경되었습니다.
  * 타겟팅 가능한 Audience에 필요한 최소 매칭 사용자 수가 500명에서 100명으로 감소했습니다.

<Note>
  **사전 준비 사항**

  * Ads API 액세스 권한
  * Audience 엔드포인트에 액세스하려면 allowlist(허용 목록)에 추가되어야 합니다. 이 양식을 작성하고, 2018-08-01 이전에 최초로 동의한 경우에는 새로운 [X Ads Products and Services Agreement](/ko/x-ads-api/introduction)에 다시 동의해 주셔야 합니다.
</Note>

**Audience 업로드 프로세스**

다음 표는 기존 및 새로운 Audience 생성 플로 간의 주요 차이점을 나열한 것이며, 보다 자세한 내용은 아래에서 추가로 설명합니다.

| 프로세스 단계 | Audience API | (사용 중단됨) TON 업로드 |
| :--- | :--- | :--- |
| 셸 Audience 생성 | [POST custom&#95;audience endpoint]/x-ads-api/audiences 를 통해 생성 가능 | [POST custom&#95;audience endpoint]/x-ads-api/audiences 를 통해 생성 가능 |
| 새 사용자 추가 | [Audience endpoint](/ko/x-ads-api/audiences)에서 `operation_type` `Update` 사용 | [POST custom&#95;audience&#95;changes](/ko/x-ads-api/audiences) 엔드포인트에서 `operation` `ADD` 사용 |
| 사용자 제거 | [Audience endpoint](/ko/x-ads-api/audiences)에서 `operation_type` `Delete` 사용 | [POST custom&#95;audience&#95;changes](/ko/x-ads-api/audiences) 엔드포인트에서 `operation` `REMOVE` 사용 |
| 사용자 옵트아웃 처리 | [Audience endpoint](/ko/x-ads-api/audiences)에서 `operation_type` `Delete`와 사용자가 속한 해당 `custom_audience_id`들을 사용 | [Global opt-out endpoint](/ko/x-ads-api/audiences) 사용 |

**참고** TON 업로드 경로를 통해 업데이트되거나 옵트아웃되는 모든 Audience에는 [TON Upload](/ko/x-ads-api/audiences) 엔드포인트를 통해 업로드된 대응 목록이 있어야 하며, [custom&#95;audience&#95;changes](/ko/x-ads-api/audiences) 엔드포인트를 사용해 Audience와 연계되어야 합니다.

**Rate Limiting**

Audience API 엔드포인트의 레이트 리밋은 계정당 1분에 1,500회입니다. 단일 페이로드에 보낼 수 있는 사용자 수에는 제한이 없습니다. 페이로드에 대한 제약은 다음과 같습니다.

1. 전체 작업 수: 최대 2,500개

2. 최대 페이로드 크기: 5,000,000바이트

**Audience 사용자 관리**

새로운 Audience를 생성하려면 다음 단계를 수행해야 합니다.

<div id="create-a-new-custom-audience">
  ### 새 Custom Audience 만들기
</div>

[POST custom&#95;audience]/x-ads-api/audiences 엔드포인트를 사용하여 새로운 Custom Audience의 &quot;쉘&quot;(빈 리소스)을 생성하고, 해당 Custom Audience의 `id`를 조회합니다. 이 단계는 Audience를 처음부터 생성하는 경우에만 필수입니다. 기존 Audience를 업데이트하는 경우에는 다음 섹션으로 넘어갑니다.

<div id="add-users-to-an-audience">
  ### 잠재고객에 사용자 추가
</div>

Custom Audience의 `id` 값과 아래와 같은 예시 페이로드를 사용하여 [POST accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id/users](/ko/x-ads-api/audiences)를 호출합니다:

POST https://ads-api.x.com/11/accounts/18ce54d4x5t/custom&#95;audiences/1nmth/users

```
    # 모든 값은 해시 처리되어야 하며, 해시되지 않은 값은 설명 목적으로만 이 예제에서 사용됩니다
    [
      {
        "operation_type": "Update",
        "params": {
          "effective_at": "2018-05-15T00:00:00Z",
          "expires_at": "2019-01-01T07:00:00Z",
          "users": [
            {
              "email": [
                "abc@x.com"
              ],
              "handle": [
                "x",
                "adsapi"
              ]
            },
            {
              "email": [
                "edf@x.com"
              ],
              "twitter_id": [
                "121291606",
                "17874544"
              ]
            }
          ]
        }
      }
    ]
```

사용자를 Audience에 추가하려면 `operation_type`으로 `Update`를 사용하십시오. 새로운 Audience 인터페이스를 사용하면 단일 사용자에 대해 여러 사용자 키를 전달할 수 있습니다. JSON 객체 배열의 각 객체는 한 명의 사용자에 대응합니다. 위의 예시 페이로드를 사용하면, 요청은 두 명의 사용자를 Audience에 추가하는데, 한 사용자는 `email`과 `handle`을, 다른 한 사용자는 `email`과 `twitter_id`를 포함합니다.

<div id="remove-users-from-an-audience">
  #### 오디언스에서 사용자 제거
</div>

사용자를 추가하는 과정과 유사하게, 다음과 같이 오디언스에서 사용자를 제거할 수 있습니다:

POST https://ads-api.x.com/11/accounts/18ce54d4x5t/custom&#95;audiences/1nmth/users

```
    # 모든 값은 해시 처리되어야 하며, 이 예제에서는 설명 목적으로 해시되지 않은 값을 사용합니다
    [
      {
        "operation_type": "Delete",
        "params": {
          "effective_at": "2018-05-15T00:00:00Z",
          "expires_at": "2019-01-01T07:00:00Z",
          "users": [
            {
              "email": [
                "abc@x.com"
              ],
              "twitter_id": [
                "783214",
                "1225933934"
              ]
            },
            {
              "email": [
                "edf@x.com"
              ],
              "twitter_id": [
                "121291606",
                "17874544"
              ]
            }
          ]
        }
      }
    ]
```

`operation_type`는 반드시 `Delete`로 설정해야 하며, 사용자는 Audience에 추가할 때 사용되었던 키들 중 어느 하나와 일치하면 매칭됩니다. 예를 들어, 사용자가 `email`과 `twitter_id`를 사용해 Audience에 추가되었다면, 동일한 사용자는 이 키들 중 하나만으로도 제거할 수 있습니다. 즉, `email` 또는 `twitter_id` 중 하나만 사용하거나, 둘 다 사용할 수도 있습니다.

또한 하나의 요청 내에서 동일한 Audience에 사용자를 추가하고 제거하는 것도 가능합니다. 이 엔드포인트는 하나의 요청에서 여러 개의 `operation_type` 값을 지원합니다.

<div id="opt-out-users">
  #### 옵트아웃 사용자
</div>

글로벌 옵트아웃 엔드포인트가 사용 중단(deprecation)됨에 따라, 파트너는 어떤 Audience에서든 옵트아웃한 사용자를 `Delete` 해야 합니다. 이를 수행하는 방법은 몇 가지가 있습니다:

1. 어떤 사용자들이 어떤 Audience에 속해 있는지 추적하고, 해당 Audience 각각에서 이 사용자들을 개별적으로 제거합니다.
2. Ads 계정과 연결된 **모든** Audience에서 해당 사용자를 제거합니다.

**일반 모범 사례**

* 이 엔드포인트는 가능한 한 실시간에 가까운 배치 단위로 호출할 것을 강력히 권장합니다. 이렇게 하면 처리 시간이 오래 걸리는 큐가 급격히 늘어나는 것을 방지하고, 전반적으로 당사 시스템에 불필요한 부하가 발생하는 것을 줄일 수 있습니다. 또한 사용자가 캠페인 타기팅에 더 빨리 활용될 수 있도록 보장합니다.
* 성공적인 API 호출은 요청에서 전달된 `user` 객체 수에 해당하는 `success_count` 및 `total_count`를 반환합니다.
* 이 엔드포인트는 본질적으로 원자적(atomic)이므로, 전체 요청이 성공하거나 오류가 발생한 경우 전체 요청이 실패합니다. 오류 응답이 발생한 경우, API 소비자에게는 오류를 수정한 뒤 전체 페이로드로 요청을 다시 시도할 것을 권장합니다. 
* 실패 시, 파트너에게는 재시도와 함께 [지수 백오프](https://en.wikipedia.org/wiki/Exponential_backoff) 방식을 사용할 것을 권장합니다. 예를 들어, 첫 번째 실패 시에는 즉시 재시도하고, 두 번째 실패 후에는 1분 뒤에 재시도하며, 세 번째 연속 실패 후에는 5분 뒤에 재시도하는 식으로 진행합니다.

이 엔드포인트를 사용하면 파트너가 지정된 `custom_audience_id`에서 사용자를 추가, 업데이트 및 제거할 수 있습니다. 또한 이 엔드포인트는 각 사용자에 대해 여러 종류의 사용자 식별자를 함께 전달받을 수 있습니다.

요청의 `users` 필드에 제공되는 **모든** 데이터 중 `partner_user_id`를 **제외한** 값은 `SHA256`으로 해시하고 [정규화](/ko/x-ads-api/audiences#twitter-user-id-normalization)해야 합니다.

**배치 요청**

* 현재 최대 배치 크기는 **이 엔드포인트의 경우** `2500`입니다. 배치 크기는 요청당 작업 수(`Update`/`Delete`)로 결정됩니다. 예를 들어, 하나의 배열에 2500개를 초과하는 작업 객체(`{"operation_type": "Update/Delete", [..] }`)가 포함되면 오류가 발생합니다.
* 이 엔드포인트가 허용하는 요청 POST 본문의 최대 크기는 `5,000,000`바이트입니다.
* 이 엔드포인트에 대한 요청 한도(rate limit)는 1분 윈도우당 1500회입니다.
* 모든 파라미터는 요청 본문에 전송되며, `Content-Type`은 `application/json`이어야 합니다.
* 배치 요청은 하나의 그룹으로 함께 실패하거나 성공하며, 오류 및 성공에 대한 모든 API 응답은 초기 요청의 항목 순서를 그대로 유지합니다.

**배치 응답**

Ads API가 반환하는 응답에는 `success_count`와 `total_count`라는 두 개의 필드가 포함됩니다. 이 값은 항상 같아야 하며, 백엔드에서 처리된 요청 내 레코드 수를 나타냅니다. 요청 본문에 전송된 레코드 수가 `success_count` 및 `total_count`와 **같지 않은** 상황은 오류 상태로 간주해야 하며, 재시도가 필요합니다.

**배치 오류**

* 요청 수준 오류(예: 최대 배치 크기 초과)는 응답의 `errors` 객체에 표시됩니다.
* 항목 수준 오류(예: 필수 파라미터 누락)는 응답의 `operation_errors` 객체에 표시됩니다.
* `operation_errors` 내 오류의 인덱스는 입력 항목의 인덱스를 가리키며, 해당 오류 메시지가 함께 제공됩니다.

이 엔드포인트를 사용하면 지정된 `do_not_reach_list_id`에 사용자를 추가, 업데이트 및 제거할 수 있습니다. 이 엔드포인트는 이메일만을 유효한 사용자 식별자 유형으로 허용합니다.

요청의 `emails` 필드에 제공되는 모든 데이터는 `SHA256`으로 해시되고 [정규화](/ko/x-ads-api/audiences#e-mail-normalization)되어야 합니다.

**Notes**

* 하나의 `account_id`는 최대 하나의 Do Not Reach List만 가질 수 있습니다.
* 이 목록에 추가된 사용자는 현재 타임스탬프로부터 13개월 미만이 되도록 `expires_at` 타임스탬프가 **반드시** 설정되어야 합니다.
* Do Not Reach List API는 `effective_at` 타임스탬프를 허용하지 않으며, 기본값으로 현재 타임스탬프를 사용합니다.
* Do Not Reach List는 계정의 어떤/모든 커스텀 오디언스에서 사용자를 제거하지 않으며, 해당 계정에서 집행되는 모든 캠페인에 대한 제외 타기팅으로 동작합니다.

**Batch Requests**

* 이 엔드포인트에 대한 현재 최대 배치 크기는 `2500`입니다. 배치 크기는 요청당 작업(`Update`/`Delete`) 수로 결정됩니다. 예를 들어, 하나의 배열에 2500개가 넘는 작업 객체(`{"operation_type": "Update/Delete", [..] }`)가 포함되면 오류가 발생합니다.
* 이 엔드포인트가 수락할 수 있는 최대 요청 POST 본문 크기는 `5,000,000` 바이트입니다.
* 이 엔드포인트에 대한 요청 한도(rate limit)는 1분 윈도우당 1500입니다.
* 모든 매개변수는 요청 본문으로 전송되며, `Content-Type`은 `application/json`이어야 합니다.
* 배치 요청은 그룹 단위로 함께 실패하거나 성공하며, 오류와 성공에 대한 모든 API 응답은 초기 요청의 항목 순서를 그대로 유지합니다.

**Batch Responses**

Ads API가 반환하는 응답에는 두 개의 필드, `success_count`와 `total_count`가 포함됩니다. 이 값들은 항상 동일해야 하며, 백엔드에서 처리된 요청 내 레코드 수를 나타냅니다. 요청 본문에 전송된 레코드 수가 `success_count` 및 `total_count`와 **같지 않은** 상황은 재시도가 필요한 오류 상태로 간주해야 합니다.

**Batch Errors**

* 요청 수준 오류(예: 최대 배치 크기 초과)는 응답의 `errors` 객체 아래에 표시됩니다.
* 항목 수준 오류(예: 필수 매개변수 누락)는 응답의 `operation_errors` 객체 아래에 표시됩니다.
* `operation_errors` 내 오류의 인덱스는 입력 항목 내 인덱스를 가리키며, 해당 오류 메시지가 함께 제공됩니다.

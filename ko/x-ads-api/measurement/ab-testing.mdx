  ## 개요

<div id="introduction">
  ### 소개
</div>

A/B 테스트를 사용하면 광고주가 X에서 도달하고 있는 사용자를 세분화하여, 캠페인 성과를 어떻게 최적으로 최적화할 수 있는지 파악하고 마케팅 전략 수립에 참고할 인사이트를 수집할 수 있습니다.

이러한 세분 집단은 사용자 그룹 분할(user group split)이라고 하며, 무작위로 나뉘고 서로 배타적입니다. 무작위화를 통해 결과에 영향을 미치는 요인이 각 그룹에 고르게 분포됩니다. 즉, 그룹 간이나 각 그룹의 예상 행동 간에는 본질적인 차이가 없습니다. 그렇기 때문에 하나의 변형(variation)을 특정 사용자 그룹에만 적용하고 다른 그룹에는 적용하지 않았을 때, 캠페인 성과 차이를 그 변형에 기인한 것으로 볼 수 있습니다.

한 번에 여러 가지 변형을 테스트하는 것도 가능하지만, 단일 변형만을 테스트할 것을 강력히 권장합니다. 이렇게 하면 관찰된 캠페인 성과 차이에 대한 인과 요인을 명확히 분리할 수 있습니다.

변형은 캠페인 수준에서 설정됩니다. 예를 들어, 광고주가 새로운 크리에이티브의 효력을 테스트하고자 하는 경우, 크리에이티브만 다르게 한 동일한 캠페인 두 개를 생성해야 합니다. 향후에는 라인 아이템(line item) 수준에서도 변형을 지원할 예정입니다.

A/B 테스트는 주로 (1) X에서 무엇이 가장 효과적인지 파악해 투자를 최적화하려는 성과 광고주의 최적화 사용 사례와 (2) 얻은 인사이트를 마케팅 전략 수립에 활용하려는 브랜드 광고주의 학습 사용 사례를 지원하는 데 사용됩니다. 

이 API는 다음을 포함한 모든 캠페인 변수에 대해 A/B 테스트를 지원합니다.

* 크리에이티브 

* 타게팅 

* 입찰 유형

* 입찰 단위

<div id="ab-testing">
  ## A/B Testing
</div>

A/B Testing을 사용하면 광고주가 X에서 도달하고 있는 사용자를 세분화하여, 캠페인 성과를 어떻게 최적으로 개선할 수 있는지 이해하고 마케팅 전략 수립에 참고할 인사이트를 수집할 수 있습니다.

이러한 세그먼트는 사용자 그룹 분할(user group split)이라고 하며, 무작위로 설정되고 상호 배타적입니다. 무작위 배정을 통해 결과에 영향을 미치는 요인들이 각 그룹에 고르게 분배됩니다. 즉, 각 그룹 간에 본질적인 차이나 예상 행동의 차이가 없습니다. 그렇기 때문에 하나의 변형안(variation)을 특정 사용자 그룹에만 적용하고 다른 그룹에는 적용하지 않았을 때, 캠페인 성과 차이는 해당 변형안에 기인한다고 볼 수 있습니다.

한 번에 여러 변형안을 테스트하는 것도 가능하지만, 한 번에 하나의 변형안만 테스트할 것을 강력히 권장합니다. 이렇게 하면 관측된 캠페인 성과 차이를 유발한 원인 요소를 명확히 분리할 수 있습니다.

변형안은 캠페인 레벨 또는 광고 그룹(ad group) 레벨에서 설정됩니다. 광고 그룹은 Ads API의 [line item](https://developer.x.com/en/docs/twitter-ads-api/campaign-management/api-reference/line-items)을 통해 설정됩니다. 광고 그룹 레벨 변형안의 예로, 광고주가 새로운 크리에이티브의 효과를 테스트하려는 경우, 크리에이티브만 다른 동일한 광고 그룹 2개가 포함된 단일 캠페인을 생성해야 합니다.

<div id="use-cases">
  ### 사용 사례
</div>

A/B 테스트는 주로 (1) X에서 어떤 방식이 가장 효과적인지 파악해 투자를 최적화하려는 퍼포먼스 광고주를 위한 최적화 사용 사례와 (2) 얻은 인사이트를 바탕으로 마케팅 전략을 수립하려는 브랜드 광고주를 위한 학습 사용 사례를 지원하는 데 사용됩니다. 

이 API는 다음을 포함한 모든 캠페인 변수에 대해 A/B 테스트를 지원합니다.

* 크리에이티브

* 타게팅

* 입찰 유형

* 입찰 단위

<div id="attributes">
  ### 속성
</div>

A/B 테스트는 중첩 구조로 표현됩니다. A/B 테스트 자체에 대한 최상위 필드와, 각 그룹을 설명하는 필드 집합을 가진 사용자 그룹 객체 배열로 구성됩니다.

개괄적으로, 모든 A/B 테스트에는 다음 정보가 포함되어야 합니다.

* 테스트 기간으로, start&#95;time 및 end&#95;time 필드로 표현됩니다.

* 분할이 발생하는 수준으로, entity&#95;type 필드로 표현됩니다.

* 최소 두 개(최대 30개)의 사용자 그룹으로, 각각은 user&#95;groups 배열의 객체로 표현됩니다.

각 사용자 그룹에는 다음 정보가 *반드시* 포함되어야 합니다.

* 해당 사용자 그룹에 할당해야 하는 사용자 비율로, size 필드로 표현됩니다.

* 해당 사용자 그룹의 사용자 풀을 구성해야 하는 캠페인 ID/라인 아이템 ID로, entity&#95;ids 배열로 표현됩니다.

선택적으로, A/B 테스트 및 사용자 그룹에 대해 name과 description 값을 설정할 수 있습니다. 검증 규칙 및 기타 제약 조건에 대한 정보는 아래에서 확인할 수 있습니다.

ID나 생성 시각과 같은 기타 메타데이터도 포함되지만, 이는 X에 의해 자동으로 설정됩니다.

<div id="creating">
  #### 생성
</div>

[POST accounts/:account&#95;id/ab&#95;tests](https://developer.x.com/en/docs/x-ads-api/measurement/api-reference/ab-tests) 엔드포인트를 사용해 A/B 테스트를 생성합니다. 이 엔드포인트는 JSON POST 본문만 허용합니다. `Content-Type`은 `application/json`으로 설정해야 합니다.

광고주가 두 개 이상의 캠페인을 설정한 후에 A/B 테스트를 생성할 수 있습니다. 위에서 설명했듯이 A/B 테스트에는 반드시 다음 항목이 포함되어야 합니다. 테스트 기간, 분할 수준, 그리고 최소 두 개의 사용자 그룹. 각 사용자 그룹은 자신에게 할당해야 하는 사용자 비율과, 해당 사용자 풀을 구성할 캠페인 ID들을 지정해야 합니다. 각 항목은 아래에서 더 자세히 설명합니다.

테스트 기간:

* `start_time`과 `end_time` 값은 다음 조건을 만족해야 합니다.

  * (A/B 테스트가 생성되는 시점 기준으로) 미래 시점이어야 합니다.

  * 캠페인/라인 아이템의 플라이트 기간과 겹쳐야 합니다.

* 앱 기반이 아닌 캠페인의 경우 테스트는 최소 하루 이상이어야 하며, 앱 기반 캠페인의 경우 최소 5일 이상 지속되어야 합니다.

분할 수준:

* `entity_type`은 `CAMPAIGN` 또는 `LINE_ITEM`으로 설정할 수 있습니다.

사용자 그룹:

* 각 사용자 그룹은 `user_groups` 배열의 객체로 표현됩니다.

  * 최소 두 개의 사용자 그룹이 필요합니다.

  * 최대 30개의 사용자 그룹까지 허용됩니다.

* 각 사용자 그룹의 크기는 1.00 이상 99.00 이하의 숫자 값을 문자열로 표현해 설정합니다.

  * **참고**: 각 객체의 size 값은 합계가 반드시 100.00이 되어야 합니다.

* 캠페인 ID는 각 사용자 그룹의 `entity_ids` 배열에 지정해야 합니다.

선택적으로, A/B 테스트 전체 또는 하나 이상의 사용자 그룹에 대해 `name`(이름)과 `description`(설명)을 설정할 수 있습니다.

**라인 아이템 수준 A/B 테스트용**

캠페인 수준과 라인 아이템 수준에서의 A/B 테스트 간 주요 차이점은 entity&#95;type입니다. 라인 아이템 수준의 A/B 테스트의 경우 ‘entity&#95;type’ = ‘LINE&#95;ITEM’으로 설정해야 합니다. 아래에 나와 있는, 이미 생성된 A/B 테스트에 대한 모든 작업에 이 설정이 적용됩니다. 

요구 사항:

1. A/B 테스트 캠페인의 모든 라인 아이템이 분할 테스트에 포함되어야 합니다.
2. 라인 아이템 수준에서는 동일한 비율로만 분할이 허용됩니다.
3. 하나의 분할 테스트에서 허용되는 사용자 그룹 라인 아이템 수는 5개 이하여야 합니다. 
4. 사용자 그룹당 라인 아이템은 1개만 허용됩니다.

<div id="updating">
  ### 업데이트
</div>

[PUT accounts/:account&#95;id/ab&#95;tests/:ab&#95;test&#95;id](https://developer.x.com/en/docs/x-ads-api/measurement/api-reference/ab-tests) 엔드포인트를 사용하여 A/B Test를 업데이트합니다. 이 엔드포인트에서는 요청 본문에 JSON blob을 포함해야 합니다. `Content-Type` 헤더는 `application/json`으로 설정해야 합니다.

다른 업데이트 엔드포인트와 마찬가지로 [PUT accounts/:account&#95;id/ab&#95;tests/:ab&#95;test&#95;id](/ko/x-ads-api/measurement/ab-testing#get-accounts-account-id-ab-tests) 엔드포인트는 URL에서 A/B Test ID를 참조해야 합니다. 일반적으로 A/B Test는 상태가 `SCHEDULED`일 때만 업데이트할 수 있습니다. 예외가 하나 있는데, 상태가 `LIVE`일 때는 `end_time`을 업데이트할 수 있습니다.

이 엔드포인트는 객체 ID를 포함하는 부분(partial) JSON을 지원합니다. 다음 원칙이 적용됩니다.

* 객체나 요소를 추가하거나 제거하려면 전체 배열(및 그 하위 구조)을 전달해야 합니다. 이는 **대체(replacement)** 작업입니다.

* 그 외의 경우에는 키 이름 또는 ID를 참조하여 기존 *필드*를 수정(변경, 추가, 제거)합니다.

  * 필드를 제거하려면 해당 값을 `null`로 설정합니다.
  * 전달되지 않은 필드는 수정되지 않습니다.

예를 들어, 이전에 생성한 A/B Test에 세 번째 사용자 그룹을 추가하려면, 기존 두 개의 사용자 그룹 객체에 더해 새로 추가하려는 객체까지 포함하여 `user_groups` 배열 전체를 전송해야 합니다. 이를 `user_groups` 배열을 *다시 생성하는 것*으로 생각하면 됩니다. 처음부터 이렇게 생성하는 것처럼 데이터를 전달해야 하며(사용자 그룹 객체 ID는 전달하지 마십시오), 업데이트 요청의 `user_groups` 배열은 다음과 같이 표현될 수 있습니다.

```json
[
  {
    "entity_ids": [
      "f2qcw",
      "f2tht"
    ],
    "size": "30.0",
    "name": "first group"
  },
  {
    "entity_ids": [
      "f2rqi",
      "f2tws"
    ],
    "size": "30.0",
    "name": "second group",
    "description": "second AB test group"
  },
  {
    "entity_ids": [
      "i1vwr",
      "i1xre"
    ],
    "size": "40.0"
  }
]
```

객체 전체의 size 값들의 합이 여전히 100.00이 된다는 점에 유의하세요. 만약 처음 두 개의 객체(이전에 각각 50.00으로 설정됨)에 대한 값을 업데이트하지 않았다면, 요청은 실패했을 것입니다.

대신 첫 번째 사용자 그룹에 설명만 추가하고 싶다면, 업데이트 요청의 user&#95;groups 배열은 다음과 같이 표현됩니다.

```json
[
  {
    "id": "p1bcx",
    "description": "updated using a PUT request"
  }
]
```

요청에서는 사용자 그룹 객체를 id로 참조하고, 수정하려는 필드만 포함합니다.

  #### PUT accounts/:account_id/ab_tests/:ab_test_id
</div>

지정된 A/B 테스트를 업데이트합니다.

모든 매개변수는 요청 본문에 포함되며, `Content-Type`은 `application/json`이어야 합니다.

이 엔드포인트는 객체 ID를 사용하는 부분 JSON 업데이트를 지원합니다. 다음 원칙이 적용됩니다:

* 객체나 요소를 추가하거나 제거하려면 전체 배열(및 해당 하위 구조)을 전달해야 합니다. 이는 **대체** 작업입니다.
  * 배열을 다시 생성하는 것으로 생각하면 됩니다.
* 그 외의 경우, 키 이름이나 ID를 참조하여 기존 필드를 수정(변경, 추가, 제거)합니다.
  * 필드를 제거하려면 해당 값을 `null`로 설정합니다.
  * 전달되지 않은 필드는 수정되지 않습니다.

일반적으로 A/B 테스트는 `status`가 `SCHEDULED`일 때만 업데이트할 수 있습니다. 단, 한 가지 예외로, `LIVE` 상태일 때도 A/B 테스트의 `end_time`은 업데이트할 수 있습니다.

## 소개

애널리틱스 지표는 파트너와 광고주가 X에서 프로모션하는 콘텐츠의 성과를 이해하는 데 도움이 됩니다. 여기에는 노출 수, 클릭 수, 동영상 조회 수, 집행 비용(spend)과 같은 정보가 포함됩니다. 또한 파트너와 광고주는 도달한 잠재고객을 다양한 세그먼트로 나누어 각 세그먼트에 대한 상세 지표를 확인할 수 있습니다.

Ads API는 캠페인 성과에 대한 상세 지표를 동기(synchronous) 및 비동기(asynchronous) 두 가지 방식으로 조회하는 기능을 제공합니다. 동기 애널리틱스 호출의 경우, 요청한 지표가 응답에 바로 포함되어 반환됩니다. 비동기 애널리틱스 엔드포인트의 경우, 요청한 지표는 관련 &quot;job&quot; 처리가 완료된 후 다운로드 가능한 결과 파일에서 확인할 수 있습니다. 동기 엔드포인트는 짧은 기간의 조회를 지원하며 실시간 캠페인 최적화에 적합합니다. 비동기 엔드포인트는 훨씬 더 긴 기간을 지원하므로, 더 많은 데이터를 가져오는 데 적합하며, 리포트 생성이나 과거 데이터 백필(backfill)에 이상적입니다.

<div id="details">
  ## 세부 정보
</div>

<div id="synchronous-vs-asynchronous">
  ### 동기식 vs. 비동기식
</div>

동기식 및 비동기식 애널리틱스 endpoint 간의 차이점은 아래 표에 요약되어 있습니다. 이 정보는 개발자가 어떤 endpoint를 사용할지 선택하는 데 도움을 주기 위한 것입니다.

| Feature | Synchronous | Asynchronous |
|:---------|:------------|:--------------|
| Rate limiting | 사용자 수준: 15분당 요청 250개 | 계정 수준: 동시 처리 작업 100개* |
| Time range | 7일 | 90일 (세그먼트 미사용)<br />45일 (세그먼트 사용) |
| Segmentation | 지원 안 함 | 지원 |
| Response returns | 지표 데이터(metrics data) | 작업의 처리 상태** |
| Recommended use case | 실시간 최적화<br />사용자 인터페이스 요청 | 정기적인 동기화<br />과거 데이터 백필링 |

<Note>
  * 이는 어떤 시점이든 처리 중 상태가 될 수 있는 작업의 최대 개수를 의미합니다.

  ** 작업 처리가 성공적으로 완료되면 URL이 반환됩니다. 이 URL에서 압축된(gzip) 결과 파일을 다운로드할 수 있습니다.

  그 외에는 이 endpoint들은 동일한 기능을 제공합니다.
</Note>

<div id="use-cases">
  ### 사용 사례
</div>

주요 분석 사용 사례는 세 가지입니다.

1. 실시간 최적화: 성과 지표를 사용해 진행 중인 캠페인을 업데이트
2. 동기화: 정기적으로 실행되는 백그라운드 동기화
3. 신규 계정 온보딩: 과거 데이터를 백필(backfill)

동기식 분석 endpoint는 최근 5~15분 이내의 지표 변화를 기반으로 캠페인을 업데이트하는 실시간 최적화에 사용할 수 있습니다. 동기식과 비동기식 endpoint 모두 분석 동기화에 사용할 수 있습니다. 원하는 시간 범위와 세분화가 필수인지 여부에 따라 사용할 endpoint가 결정됩니다. 신규 계정 온보딩은 비동기식 분석 endpoint만 사용해 수행해야 합니다. (동기식 분석 endpoint는 대량의 데이터를 조회하는 용도로 절대 사용해서는 안 됩니다.)

비동기식 분석 endpoint는 지표를 백엔드 프로세스에서 동기화하는 경우 대시보드 및 기타 UI 요소를 구동하는 데 사용할 수 있습니다. 구현 시 사용자 인터페이스 요청을 처리하기 위해 비동기식 분석 endpoint를 직접 호출하는 일은 피해야 합니다.

<div id="request-options">
  ### 요청 옵션
</div>

애널리틱스 요청은 광고 계정 단위로 범위가 지정되며, 따라서 리소스 경로에 계정 ID가 필요합니다. 아래에 나열된 요청 옵션은 쿼리 매개변수로 지정합니다. 다음 유형의 값이 필수입니다.

* Entities: 엔티티 유형과 애널리틱스를 조회하려는 엔티티 id 최대 20개
* Time range: ISO 8601 형식으로 표현된 시작 및 종료 시간
  * **참고:** 반드시 정시 단위로 표현해야 합니다
* Metric groups: 하나 이상의 관련 메트릭 그룹(각 메트릭 그룹에 포함된 메트릭 목록은 Metrics and Segmentation을 참조)
* Granularity: 메트릭이 반환되는 집계 수준을 지정
* Placement: X 내에서 노출된 광고인지, X 외부에서 노출된 광고인지에 따라 어떤 광고에 대한 메트릭을 가져올지 결정
  * **참고:** 요청당 하나의 placement 값만 지정할 수 있습니다

`start_time` 및 `end_time` 요청 매개변수를 사용하여 시간 범위를 지정합니다. 이 값들은 아래와 같이 지정된 granularity와 맞아야 합니다.

1. `TOTAL`: 임의의 시간 범위를 지정(엔드포인트의 제한 내)
2. `DAY`: 시작 시간과 종료 시간 모두 계정의 시간대 기준 자정에 맞아야 함
3. `HOUR`: 임의의 시간 범위를 지정(엔드포인트의 제한 내)

종료 시간은 배타적입니다. 예를 들어, `start_time=2019-01-01T00:00:00Z` 및 `end_time=2019-01-02T00:00:00Z`로 요청하면, 이 시간 범위는 24시간만을 포함하므로 애널리틱스 메트릭이 하루치(이틀치가 아님)만 반환됩니다.

**Segmentation**

Segmentation은 비동기 애널리틱스 엔드포인트에서만 제공되며, 파트너와 광고주가 특정 타기팅 값별로 분리된 메트릭을 조회할 수 있도록 해줍니다. 세그먼트된 메트릭을 요청하려면 `segmentation_type` 요청 매개변수를 사용하세요. 세분화 옵션에 대한 자세한 내용은 [Metrics and Segmentation](/ko/x-ads-api/analytics#metrics-and-segmentation)을 참조하세요.

<div id="faqs">
  ## 자주 묻는 질문(FAQs)
</div>

왜 Ads API 수치가 X Ads UI에 표시되는 값과 일치하지 않나요?

* `ALL_ON_TWITTER`, `PUBLISHER_NETWORK`, `SPOTLIGHT`, `TREND` 모든 노출 위치(placement)에 대한 데이터를 모두 요청했는지 확인하세요.
* Ads API의 종료 시간은 배타적(exclusive)이지만, Ads UI에서는 포함적(inclusive)임을 기억하세요.

왜 데이터를 요청하는 시점에 따라 수치가 달라지나요?

* 보고용 지표가 사용 가능해지는 즉시 조회할 수 있으며, 거의 실시간에 가깝게 제공됩니다. 하지만 이 초기 결과는 추정치이므로 변경될 수 있습니다. 지표는 지출(spend) 데이터를 제외하고 24시간 후에 확정됩니다.
* 지출(spend) 지표는 일반적으로 발생 후 3일 이내에 확정됩니다. 다만, 결제(billing) 데이터는 스팸 필터링 등의 이유로 이벤트 발생일로부터 최대 14일 동안 처리됩니다.

특정 기간에 대해 어떤 엔티티 ID를 요청해야 하는지 어떻게 알 수 있나요?

* [Active Entities endpoint](/ko/x-ads-api/analytics#active-entities-2)를 사용하세요.

왜 애널리틱스 응답의 모든 값이 `null`인가요?

* 요청한 기간 동안 캠페인이 집행되지 않았을 가능성이 큽니다.
* [Active Entities endpoint](/ko/x-ads-api/analytics#active-entities-2)를 사용해 어떤 엔티티에 대해 어떤 기간의 애널리틱스를 조회해야 하는지 확인하세요.

왜 API는 `null` 값을 보여 주는데 UI는 0을 보여 주나요?

* UI에서는 이러한 값을 0으로 표시하기로 선택했을 뿐이며, 두 값은 동등한 의미입니다.

X 타임라인처럼 세분화된 placement에 연관된 지표를 어떻게 요청할 수 있나요?

* 애널리틱스에서는 다음 placement 값들을 지원합니다: `ALL_ON_TWITTER`, `PUBLISHER_NETWORK`, `SPOTLIGHT`, `TREND` (즉, [X Audience Platform](/ko/x-ads-api/audiences))

삭제되었거나 일시 중지된 엔티티에 대한 지표도 조회할 수 있나요?

* 가능합니다. 엔티티 상태는 애널리틱스 지표의 가용성에 영향을 주지 않습니다.

왜 세분화된 값이 비세분화 값과 일치하지 않나요?

* 이 정보가 산출되는 방식 때문에, 세분화된 데이터가 비세분화 데이터와 100% 일치하도록 집계되는 것은 *기대할 수 없습니다*.

여러 차원으로 세분화된 데이터를 요청할 수 있나요?

* 다중 세분화는 지원하지 않습니다.

<div id="best-practices">
  ## 모범 사례
</div>

다음은 Ads API에서 [analytics](/ko/x-ads-api/analytics) data를 수집할 때의 모범 사례입니다.

<div id="rate-limiting-and-retries">
  ### 요청 한도 및 재시도
</div>

* `HTTP 429` 상태 코드를 반환하는, 요청 한도 때문에 제한된 쿼리에 대해서는 `x-rate-limit-reset` 헤더를 확인하고, 해당 헤더에 표시된 시각에 도달했을 때나 그 이후에만 재시도해야 합니다.
* HTTP 503 Service Unavailable 상태 코드를 반환하는 쿼리에 대해서는 `retry-after` 헤더를 확인하고, 해당 헤더에 표시된 시각이 지난 후에만 재시도해야 합니다.
* 재시도에 대해 지정된 시각을 준수하지 않는 애플리케이션은 사전 고지 없이 Ads API에 대한 액세스가 철회되거나 제한될 수 있습니다.

<div id="analytics-metrics-in-a-nutshell">
  ### 애널리틱스 지표 한눈에 보기
</div>

* `billed_charge_local_micro`를 제외한 모든 애널리틱스 지표는 24시간이 지나면 고정되며 변경되지 않습니다.
* `billed_charge_local_micro` 지표는 `data`가 반환된 이후 최대 3일 동안 추정치입니다.
* 24시간 이후에는 과다 집행(지정된 `end_time` 이후에 집행된 광고)과 부적격한 것으로 판정된 과금 이벤트에 대한 크레딧 때문에 이 지표가 감소할 수 있습니다. 이 지표는 24시간 이후에는 거의 변경되지 않습니다.
* 자세한 내용은 [Analytics](/ko/x-ads-api/analytics)를 참조하세요.

<div id="fetching-real-time-non-segmented-data">
  ### 실시간 비분할 데이터 가져오기
</div>

* 항상 `start_time`과 `end_time`을 모두 지정해야 합니다.
* 7일보다 오래된 엔터티에 대해서는 데이터를 가져오지 마십시오.
* 되도록 `HOUR` 단위로 데이터를 요청하십시오. 이렇게 하면 언제든지 집계하여 `DAY` 및 `TOTAL` 단위로 지표를 상위 집계할 수 있습니다.
* 되도록 `line_items` 및 `promoted_tweets` 수준에서 데이터를 요청하십시오. 이렇게 하면 언제든지 이 지표들을 집계하여 캠페인, 자금 수단(funding instrument), 계정 수준 등 전체 광고 엔터티 계층에 대한 합계를 계산할 수 있습니다.
* 분석 지표 값은 반드시 로컬(자체 시스템)에 저장하십시오.
* 30일보다 오래된 데이터에 대해서는 반복적으로 쿼리하지 마십시오. 이 데이터는 변경되지 않으므로 로컬에 저장해야 합니다.
* 모든 비분할 데이터는 실시간으로 제공되며, 이벤트 발생 후 몇 초 이내에 데이터를 사용할 수 있어야 합니다.
* 전환 지표와 비전환 지표는 별도의 요청으로 나누어 조회하십시오.

<div id="fetching-segmented-data">
  ### 세분화된 데이터 가져오기
</div>

* 위의 “실시간 비세분화 데이터 가져오기”에 제공된 지침을 참조하세요. 아래에 추가 권장 사항을 제공합니다.
* 대부분의 세분화된 데이터 유형의 경우, 상황에 따라 최대 1시간 동안 데이터가 완전하지 않을 수 있습니다. `INTERESTS`로 세분화된 데이터는 최대 12시간까지 지연될 수 있습니다.
* 이 정보가 생성되는 방식 때문에, 세분화된 데이터가 비세분화 데이터와 100%까지 완전히 합산되어 일치할 것으로 기대해서는 안 됩니다.

<div id="fetching-historical-data">
  ### 과거 데이터 가져오기
</div>

* 데이터 백필(예: 새 광고주 계정을 추가하는 경우)을 수행할 때는 `start_time`과 `end_time`을 더 작은 구간으로 나누어 여러 번 요청해야 할 수 있습니다.
* 조회 기간을 최대 30일 단위의 날짜 구간으로 제한하세요.
* 이러한 요청은 속도를 조절하고 시간에 분산하여, 이 조회를 위한 요청 한도(rate limit)를 소진하지 않도록 하세요.

<div id="metrics-by-objective">
  ## 목표별 지표
</div>

어떤 지표가 엔티티에 적용되는지는 [캠페인 목표](/ko/x-ads-api/campaign-management)에 따라 달라집니다. 이 가이드를 활용해 각 목표 유형마다 조회해야 할 관련 지표 그룹을 파악하고, 추가 파생 지표를 계산하는 방법을 확인하세요.

<div id="engagements">
  ### `ENGAGEMENTS`
</div>

**관련 메트릭 그룹:** `ENGAGEMENT` 및 `BILLING`. 크리에이티브에 미디어가 사용된 경우 `MEDIA`도 해당됩니다.

|     |     |
| :--- | :--- |
| 파생 메트릭 | 노출 메트릭 산출식 |
| 참여율 (Engagement Rate) | `engagements/impressions` |
| CPE | `billed_charge_local_micro/engagements` |
| 미디어 조회율 (Media View Rate) | `media_views/impressions` |

<div id="website_clicks-and-website_conversions">
  ### `WEBSITE_CLICKS` 및 `WEBSITE_CONVERSIONS`
</div>

<div id="active-entities">
  ### 활성 엔티티
</div>

<div id="introduction">
  #### 소개
</div>

[Active Entities endpoint](/ko/x-ads-api/analytics#get-stats-accounts-account-id-active-entities)는 어떤 캠페인에 대해 애널리틱스를 요청할지에 대한 정보를 제공하므로, [동기식](/ko/x-ads-api/analytics#get-stats-accounts-account-id) 및 [비동기식](/ko/x-ads-api/analytics#asynchronous-analytics) 애널리틱스 엔드포인트와 함께 사용되도록 설계되었습니다. 이 엔드포인트는 광고 엔티티에 대한 세부 정보와 해당 메트릭이 언제 변경되었는지를 반환하는 방식으로 이를 제공합니다. 이 엔드포인트를 사용하면 코드와 애널리틱스 조회 로직을 크게 단순화할 수 있습니다.

이 가이드는 엔드포인트와 그 데이터 소스에 대한 정보와 맥락을 포함합니다. 또한 [사용 지침](#usage)과 일련의 [예제 요청](#example)을 제공하여 Active Entities를 애널리틱스 엔드포인트와 함께 사용하는 방법을 보여줍니다. [요약 섹션](#summary)에서는 권장 접근 방식에 대한 개략적인 설명을 제공합니다.

<div id="data">
  #### 데이터
</div>

광고 엔티티의 지표가 변경될 때마다 해당 변경에 대한 정보를 기록합니다. 이러한 변경 이벤트는 시간 단위 버킷에 저장되며, 엔티티에 대한 세부 정보뿐 아니라 변경이 적용되는 시점에 대한 정보도 포함합니다. 후자가 필요한 이유는 변경 이벤트가 항상 기록된 시점과 일치하지 않기 때문입니다. 청구 조정이 그 대표적인 예이지만, 그 외의 이유도 있을 수 있습니다.

<div id="endpoint">
  #### 엔드포인트
</div>

<div id="request">
  ### Request
</div>

Active Entities 요청은 광고 계정 범위 내에서 수행되며, `entity`, `start_time`, `end_time` 세 개의 필수 쿼리 매개변수가 필요합니다.

`twurl -H ads-api.x.com "/11/stats/accounts/18ce54d4x5t/active_entities?entity=PROMOTED_TWEET&start_time=2019-03-05T00:00:00Z&end_time=2019-03-06T00:00:00Z"`

지원되는 `entity` 값은 다음과 같습니다: `CAMPAIGN`, `FUNDING_INSTRUMENT`, `LINE_ITEM`, `MEDIA_CREATIVE`, `PROMOTED_ACCOUNT`, `PROMOTED_TWEET`. 이는 분석 엔드포인트에서 지원하는 엔터티 유형을 반영합니다.

`start_time` 및 `end_time` 값은 [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) 형식으로 지정해야 하며, 조회할 시간별 버킷을 정의합니다. 이 값들은 반드시 정각 단위(whole hours)로만 표현해야 합니다.

이 엔드포인트는 결과를 필터링하는 데 사용할 수 있는 세 가지 선택적 매개변수도 지원합니다: `funding_instrument_ids`, `campaign_ids`, `line_item_ids`. 이 매개변수들은 광고 계층 구조의 모든 레벨에서, 그리고 지정된 모든 `entity` 유형과 함께 사용할 수 있습니다.

<div id="response">
  ### 응답
</div>

위 요청에 대한 Active Entities 응답은 다음과 같습니다.

```json
    {
      "request": {
        "params": {
          "account_id": "18ce54d4x5t",
          "entity": "PROMOTED_TWEET",
          "start_time": "2019-03-05T00:00:00Z",
          "end_time": "2019-03-06T00:00:00Z"
        }
      },
      "data": [
        {
          "entity_id": "2r0wxw",
          "activity_start_time": "2019-03-04T20:55:20Z",
          "activity_end_time": "2019-03-05T03:43:56Z",
          "placements": [
            "ALL_ON_TWITTER"
          ]
        },
        {
          "entity_id": "2r30fn",
          "activity_start_time": "2019-03-05T08:11:08Z",
          "activity_end_time": "2019-03-05T14:40:59Z",
          "placements": [
            "ALL_ON_TWITTER",
            "PUBLISHER_NETWORK"
          ]
        }
      ]
    }
```

`data` 배열에는 이후 애널리틱스 요청에 포함해야 하는 각 엔터티마다 하나의 객체가 포함됩니다. 이 집합에 포함되지 않은 ID에 대해서는 애널리틱스를 요청하면 안 됩니다.

각 객체에는 네 개의 필드가 포함됩니다: `entity_id`, `activity_start_time`, `activity_end_time`, `placements`. 활동 시작 및 종료 시간은 관련 엔터티의 변경 이벤트가 적용되는 기간을 나타내며, 따라서 이후 애널리틱스 요청에서 지정해야 하는 날짜 범위를 결정합니다. `placements` 배열에는 다음 값들이 포함될 수 있습니다: `ALL_ON_TWITTER`, `PUBLISHER_NETWORK`, `SPOTLIGHT`, `TREND`. 이는 주어진 엔터티 ID에 대해 어떤 게재 위치를 요청해야 하는지를 나타냅니다.

<div id="usage">
  #### 사용 방법
</div>

Active Entities 엔드포인트는 분석(analytics) 요청 방식을 결정하는 기준이 되어야 합니다. 아래 사용 지침은 분석 동기화를 지원하기 위해 작성되었으며, 파트너가 Twitter와 data 저장소를 동기화된 상태로 유지할 수 있도록 해 줍니다. 즉, 정기적으로 실행되는 백그라운드 동기화를 수행하는 방법을 설명합니다.

개발자는 두 가지 결정을 내려야 합니다.

1. 활성 엔터티 정보를 얼마나 자주 요청할지, 그리고 그에 따라 분석을 얼마나 자주 수집할지.
2. 활동 시작 및 종료 시간을 사용하여 분석 요청의 `start_time` 및 `end_time` 값을 어떻게 결정할지.

이 두 가지는 아래 요약 이후의 두 개 하위 섹션에서 더 자세히 설명합니다.

<div id="summary">
  ### 요약
</div>

다음과 같은 방식으로 Active Entities 엔드포인트를 사용해 애널리틱스 요청을 수행하는 방식을 정합니다. 활성 엔터티 정보를 얼마나 자주 요청할지, 그리고 그에 따라 애널리틱스를 얼마나 자주 가져올지 결정한 이후에 이 절차를 따르십시오.

1. Active Entities 요청을 수행합니다.
2. 응답을 placement별로 분리합니다. `ALL_ON_TWITTER`용 그룹 하나, `PUBLISHER_NETWORK`용 하나, `SPOTLIGHT`용 하나, `TREND`용 하나로 나눕니다.
3. 각 placement 그룹에 대해 다음을 수행합니다.
   1. 엔터티 ID를 추출합니다.
   2. 애널리틱스 `start_time` 및 `end_time` 값을 결정합니다.
      * 최소 `activity_start_time`을 찾습니다. 이 값을 내림 처리합니다.
      * 최대 `activity_end_time`을 찾습니다. 이 값을 올림 처리합니다.
   3. 애널리틱스 요청을 수행합니다.
      * 엔터티 ID를 20개씩 배치로 묶습니다.
      * 3-b 단계에서 결정한 `start_time` 및 `end_time` 값을 사용합니다.
      * 적절한 `placement` 값을 지정합니다.
   4. 데이터 저장소에 기록합니다.

Python SDK를 사용하는 예시는 [active&#95;entities.py](https://github.com/xdevplatform/twitter-python-ads-sdk/blob/master/examples/active_entities.py)를 참고하십시오.

<div id="frequency">
  ### 빈도
</div>

첫 번째 질문에 대한 답변은 Active Entities 요청에 사용해야 하는 시간 범위를 결정합니다. 예를 들어, 활성 엔티티 정보를 매시간 요청하는 경우 시간 범위는 1시간이 되어야 합니다. 활성 엔티티 정보를 하루에 한 번 요청하는 경우 시간 범위는 하루가 되어야 합니다. 다시 말해, 현재 요청의 `start_time`이 이전 요청의 `end_time`과 같아지도록 시간 범위를 선택해야 합니다.

<Note>
  **Note**: 하나의 시간 구간은 한 번만 요청해야 합니다. 동일한 시간 구간을 여러 번 요청하면 불필요한 analytics 요청이 발생합니다. (예외는 아래 참조.)
</Note>

*현재* 시(hour)에 대해 한 시간에 여러 번 analytics를 요청하려는 파트너의 경우에도 동일한 패턴이 적용됩니다. 즉, 요청 빈도가 시간 범위를 결정합니다. 아래 표는 이 시나리오에서의 Active Entities 시작 및 종료 타임스탬프 예시를 보여줍니다.

|     |     |     |
| :--- | :--- | :--- |
| **Request time** | **`start_time` timestamp** | **`end_time` timestamp** |
| 00:15:00 | 00:00:00 | 00:15:00 |
| 00:30:00 | 00:15:00 | 00:30:00 |
| 00:45:00 | 00:30:00 | 00:45:00 |
| 01:00:00 | 00:45:00 | 01:00:00 |

변경 이벤트가 저장되는 방식으로 인해, 위의 네 개 Active Entities 요청은 모두 동일한 1시간 버킷을 조회하며, 이는 이 사용 사례에 필요합니다. 다만 해당 시간이 지나면 이 1시간 버킷은 더 이상 조회하지 않아야 합니다.

<div id="activity-times">
  ### 활동 시간
</div>

활동 시작 및 종료 시간을 다룰 때는 다음과 같은 방식을 권장합니다. Active Entities 응답에 포함된 모든 객체에서 최소 `activity_start_time`과 최대 `activity_end_time`을 찾습니다. 그런 다음 최소 활동 시작 시간은 내림(이전 시각으로 반올림)하고, 최대 활동 종료 시간은 올림(다음 시각으로 반올림)하여 값을 조정합니다. 구체적으로는 두 타임스탬프 모두 시, 분, 초를 0으로 설정하고, 종료 시간에는 하루를 더합니다. 이는 아래 표와 같습니다. 이렇게 계산한 시작 및 종료 시간을 이후 애널리틱스 요청에 사용해야 합니다.

|     |     |
| :--- | :--- |
| **최소, 최대 활동 시간** | **파생된 시간** |
| 2019-03-04T20:55:20Z  <br />  <br />2019-03-05T14:40:59Z | 2019-03-04T00:00:00Z  <br />  <br />2019-03-06T00:00:00Z |

**참고**: 시, 분, 초가 0으로 설정된 타임스탬프를 포함하는 것이 중요합니다. 그렇지 않고 날짜만 전달하면, 광고 계정의 표준 시간대 기준으로 자정에 시작해서 자정에 끝나는 애널리틱스를 요청한 것으로 간주하며, 이는 원치 않는 결과일 수 있습니다. 예를 들어, 최소 활동 시작 시간이 2019-02-28T01:30:07Z인데 오프셋이 -08:00:00인 광고 계정에서 타임스탬프를 생략하면, 애널리틱스 요청에서는 01:30부터 08:00 사이에 발생한 변경 사항이 누락됩니다.

또는, 하루 단위로 확장하지 않고 반환된 활동 시간 범위에 대해서만 애널리틱스를 요청하고 싶다면 그렇게 할 수도 있습니다. 이 방식을 사용할 경우 파생된 시작 및 종료 시간은 각각 2019-03-04T20:00:00Z와 2019-03-05T15:00:00Z가 됩니다. (이와 같은 범위는 애널리틱스 요청에서 `DAY` 세분성을 지정한 경우에는 허용되지 않습니다.)

<div id="introduction">
  #### 소개
</div>

비동기 분석 엔드포인트를 사용하면 파트너와 광고주는 생성 요청을 제출하여 서버가 메트릭을 비동기적으로 처리하도록 할 수 있습니다. (이를 비동기 분석 &quot;작업(job)&quot;이라고 부릅니다.) 이 방식에서는 요청이 완료될 때까지 클라이언트의 연결을 계속 유지할 필요가 없습니다.

이 엔드포인트는 동기식 엔드포인트와 마찬가지로, 파트너와 광고주가 캠페인 성과에 대한 상세한 통계를 요청할 수 있도록 합니다. 계정, 자금 조달 수단, 캠페인, 라인 아이템, 프로모션된 트윗, 미디어 크리에이티브에 대한 데이터 요청을 지원합니다. 동기식 엔드포인트와의 차이점은 비동기 분석 엔드포인트가 최대 90일에 이르는 더 긴 날짜 범위뿐 아니라 세분화도 지원한다는 점입니다. 두 방식 간 차이에 대한 추가 세부 정보는 [Analytics Overview](/ko/x-ads-api/analytics) 페이지에서 확인할 수 있습니다.

동기식 엔드포인트와 달리, 요청 제한은 특정 계정에 대해 동시에 실행 중인 작업 수를 기준으로 합니다. 즉, 특정 시점에 처리 상태에 있을 수 있는 작업 수를 기준으로 합니다. 이는 광고 계정 단위로 계산됩니다.

<div id="usage">
  #### 사용 방법
</div>

비동기 분석 엔드포인트를 사용하여 캠페인 지표를 가져오는 과정은 여러 단계로 이루어집니다. 이 과정에는 작업을 생성하고, 작업 처리 완료 여부를 확인한 다음, 최종적으로 데이터를 다운로드하는 절차가 포함됩니다. 데이터 파일은 압축을 해제해야 합니다. 아래에 네 가지 구체적인 단계를 정리했습니다.

1. [POST stats/jobs/accounts/:account&#95;id](/ko/x-ads-api/analytics#asynchronous-analytics) 엔드포인트를 사용하여 작업을 생성합니다.
2. [GET stats/jobs/accounts/:account&#95;id](/ko/x-ads-api/analytics#asynchronous-analytics) 엔드포인트에 정기적으로 요청을 보내 작업 처리 완료 여부를 확인합니다.
3. 작업 처리가 완료되면 데이터 파일을 다운로드합니다.
4. 데이터 파일의 압축을 해제합니다.

데이터 파일에 포함되어 반환되는 응답 객체는 동기식 분석 엔드포인트의 응답과 동일한 JSON 스키마를 가집니다.

세분화된 캠페인 지표는 비동기 분석 엔드포인트를 통해서만 사용할 수 있습니다. 캠페인 지표는 위치, 성별, 관심사, 키워드 등으로 분류할 수 있습니다. 사용 가능한 전체 옵션 목록은 [Metrics and Segmentation](/ko/x-ads-api/analytics#metrics-and-segmentation) 페이지를 참고하세요. 세분화된 지표를 요청하려면 작업을 생성할 때 `segmentation_type` 요청 매개변수를 사용하십시오.

<div id="get-statsaccountsaccount_idactive_entities">
  #### GET stats/accounts/:account_id/active_entities[](#get-stats-accounts-account-id-active-entities "Permalink to this headline")
</div>

지정된 기간 동안 어떤 엔티티의 분석 지표가 변경되었는지에 대한 세부 정보를 조회합니다.

이 엔드포인트는 분석 엔드포인트와 함께 사용해야 합니다. 이 엔드포인트의 결과는 어떤 광고 엔티티에 대해 분석을 요청해야 하는지를 나타냅니다. 사용 방법에 대한 지침은 [Active Entities Guide](/ko/x-ads-api/analytics#active-entities)를 참조하세요.

변경 이벤트는 시간 단위 버킷으로 제공됩니다.

* `start_time` 및 `end_time` 값은 조회할 시간 단위 버킷을 지정합니다.
* 반환되는 `data` 배열에는 이후 분석 요청에 포함해야 하는 각 엔티티에 대한 객체가 포함됩니다.
* **중요**: 이후 분석 요청에서 지정해야 하는 날짜는 `activity_start_time` 및 `activity_end_time` 값을 기준으로 결정해야 합니다.
  * 이 값들은 저장된 변경 이벤트가 *적용되는* 시간 범위를 나타냅니다. 이는 엔티티별로 반환됩니다.

**참고**: 허용되는 최대 시간 범위(`end_time` - `start_time`)는 90일입니다.

<div id="resource-url">
  ### 리소스 URL[](#resource-url "Permalink to this headline")
</div>

`https://ads-api.x.com/12/stats/accounts/:account_id/active_entities`

</div>

| Name | Description |
| :--- | :--- |
| account&#95;id  <br />*필수* | 레버리지드 계정의 식별자입니다. 리소스 경로 내에 표시되며, [GET accounts](/ko/x-ads-api/campaign-management#accounts)를 제외한 모든 Advertiser API 요청에서 일반적으로 필수 매개변수입니다. 지정한 계정은 인증된 사용자와 연결되어 있어야 합니다.<br /><br />유형: 문자열<br /><br />예: `18ce54d4x5t` |
| end&#95;time  <br />*필수* | 가져온 데이터의 범위를 [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) 형식으로 표현된 지정 종료 시간으로 제한합니다.<br /><br />**참고**: 반드시 정시(0분 0초) 단위로만 지정해야 합니다.<br /><br />유형: 문자열<br /><br />예: `2017-05-26T07:00:00Z` |
| entity  <br />*필수* | 데이터를 조회할 엔터티 유형입니다.<br /><br />유형: enum<br /><br />가능한 값: `CAMPAIGN`, `FUNDING_INSTRUMENT`, `LINE_ITEM`, `MEDIA_CREATIVE`, `PROMOTED_ACCOUNT`, `PROMOTED_TWEET` |
| start&#95;time  <br />*필수* | 가져온 데이터의 범위를 [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) 형식으로 표현된 지정 시작 시간으로 제한합니다.<br /><br />**참고**: 반드시 정시(0분 0초) 단위로만 지정해야 합니다.<br /><br />유형: 문자열<br /><br />예: `2017-05-19T07:00:00Z` |
| campaign&#95;ids  <br />*optional* | 쉼표로 구분된 id 목록을 지정하여, 원하는 캠페인과 연결된 엔터티만으로 응답 범위를 제한합니다. 최대 200개의 id를 지정할 수 있습니다.<br /><br />**참고**: `funding_instrument_ids` 및 `line_item_ids`와 동시에 사용할 수 없습니다.<br /><br />유형: 문자열<br /><br />예: `8wku2` |
| funding&#95;instrument&#95;ids  <br />*optional* | 쉼표로 구분된 id 목록을 지정하여, 원하는 자금 조달 수단과 연결된 엔터티만으로 응답 범위를 제한합니다. 최대 200개의 id를 지정할 수 있습니다.<br /><br />**참고**: `campaign_ids` 및 `line_item_ids`와 동시에 사용할 수 없습니다.<br /><br />유형: 문자열<br /><br />예: `lygyi` |
| line&#95;item&#95;ids  <br />*optional* | 쉼표로 구분된 id 목록을 지정하여, 원하는 라인 아이템과 연결된 엔터티만으로 응답 범위를 제한합니다. 최대 200개의 id를 지정할 수 있습니다.<br /><br />**참고**: `campaign_ids` 및 `line_item_ids`와 동시에 사용할 수 없습니다.<br /><br />유형: 문자열<br /><br />예: `8v7jo` |

## 소개

애널리틱스 지표는 파트너와 광고주가 X에서 프로모션하는 콘텐츠의 성과를 파악하는 데 도움을 줍니다. 여기에는 노출 수(impressions), 클릭 수, 동영상 조회 수, 지출액(spend)과 같은 정보가 포함됩니다. 또한 파트너와 광고주는 도달한 오디언스를 다양한 세그먼트로 나누어 세부적인 지표를 확인할 수 있습니다.

Ads API는 캠페인 성과 지표를 상세하게 조회하는 동기 방식과 비동기 방식, 두 가지를 지원합니다. 동기 애널리틱스 호출에서는 요청한 지표가 응답에 즉시 포함되어 반환됩니다. 비동기 애널리틱스 엔드포인트에서는 관련 &quot;job&quot; 처리가 완료된 후, 요청한 지표가 다운로드 가능한 결과 파일 형태로 제공됩니다. 동기 엔드포인트는 짧은 기간 범위를 지원하며 실시간 캠페인 최적화에 적합합니다. 비동기 엔드포인트는 훨씬 더 긴 기간 범위를 지원하므로, 훨씬 더 많은 데이터를 가져와 보고용 또는 과거 데이터 보강(backfill)을 생성하는 데 적합합니다.

  ## 자세한 내용

<div id="synchronous-vs-asynchronous">
  ### 동기식 vs. 비동기식
</div>

동기식 및 비동기식 애널리틱스 endpoint 간의 차이점은 다음 표에 요약되어 있습니다. 이 정보는 개발자가 어떤 endpoint를 사용할지 선택하는 데 도움을 주기 위한 것입니다.

| 기능 | 동기식 | 비동기식 |
|:---------|:------------|:--------------|
| Rate limiting | 사용자 수준: 15분당 요청 250개 | 계정 수준: 동시에 처리 중인* 작업 100개 |
| Time range | 7일 | 90일(비분할)<br />45일(분할) |
| Segmentation | 없음 | 있음 |
| Response returns | 메트릭 데이터 | 작업의 처리 상태** |
| Recommended use case | 실시간 최적화<br />사용자 인터페이스 요청 | 정기적 동기화<br />과거 데이터 백필(backfill) |

<Note>
  * 이는 어느 시점에서든 처리 상태에 있을 수 있는 작업 수의 최대값을 의미합니다.

  ** 작업 처리가 성공적으로 완료되면 URL이 반환됩니다. 이 URL에서 압축(gzip)된 결과 파일을 다운로드할 수 있습니다.

  이 외에는 endpoint들이 동일한 기능을 제공합니다.
</Note>

<div id="use-cases">
  ### 사용 사례
</div>

주요 애널리틱스 사용 사례는 세 가지입니다.

1. 실시간 최적화: 성과 지표를 사용해 진행 중인 캠페인을 업데이트
2. 동기화: 정기적으로 실행되는 백그라운드 동기화
3. 신규 계정 온보딩: 과거 데이터 백필(backfilling)

동기식 애널리틱스 엔드포인트는 최근 5~15분 내 지표 변화를 기반으로 캠페인을 업데이트하는 실시간 최적화에 사용할 수 있습니다. 동기식 및 비동기식 엔드포인트 모두 애널리틱스 동기화에 사용할 수 있습니다. 원하는 시간 범위와 세그멘테이션 필요 여부에 따라 어떤 엔드포인트를 사용할지가 결정됩니다. 신규 계정 온보딩은 비동기식 애널리틱스 엔드포인트만 사용해야 합니다. (동기식 애널리틱스 엔드포인트는 대량의 데이터를 조회하는 데 절대 사용해서는 안 됩니다.)

비동기식 애널리틱스 엔드포인트는 지표를 백엔드 프로세스와 동기화하는 경우 대시보드 및 기타 UI 요소를 구동하는 데 사용할 수 있습니다. 구현 시 사용자 인터페이스 요청을 처리하기 위해 비동기식 애널리틱스 엔드포인트를 직접 호출하는 것은 피해야 합니다.

<div id="request-options">
  ### 요청 옵션
</div>

Analytics 요청은 광고 계정 단위로 범위가 지정되며, 따라서 리소스 경로에 계정 ID가 필요합니다. 아래에 나열된 요청 옵션은 쿼리 매개변수로 지정됩니다. 다음 유형의 값이 필요합니다.

* 엔티티: 엔티티 유형과 Analytics를 요청하려는 최대 20개의 엔티티 id
* 시간 범위: ISO 8601 형식으로 표현되는 시작 시간과 종료 시간
  * **참고:** 반드시 정시(정각) 단위로 표현되어야 합니다.
* 메트릭 그룹: 하나 이상의 관련 메트릭 집합 (각 메트릭 그룹에 포함된 메트릭 목록은 Metrics 및 Segmentation을 참조)
* Granularity: 메트릭이 반환되는 집계 수준을 지정합니다.
* Placement: 광고가 X 내에서 게재되었는지, X 외부에서 게재되었는지에 따라 어떤 광고에 대한 메트릭을 가져올지 결정합니다.
  * **참고:** 요청당 하나의 placement 값만 지정할 수 있습니다.

`start_time` 및 `end_time` 요청 매개변수를 사용해 시간 범위를 지정합니다. 이 값들은 다음과 같이 지정된 granularity와 맞춰져야 합니다.

1. `TOTAL`: 엔드포인트의 제한 내에서 임의의 시간 범위를 지정할 수 있습니다.
2. `DAY`: 시작 시간과 종료 시간 값 모두 계정의 시간대 기준 자정에 맞춰져야 합니다.
3. `HOUR`: 엔드포인트의 제한 내에서 임의의 시간 범위를 지정할 수 있습니다.

종료 시간은 포함되지 않습니다. 예를 들어, `start_time=2019-01-01T00:00:00Z` 및 `end_time=2019-01-02T00:00:00Z`로 요청할 경우, 이 시간 범위는 24시간만을 포함하므로 하루치 Analytics 메트릭만 반환됩니다(이틀치가 아님).

**Segmentation**

비동기 Analytics 엔드포인트에서만 제공되는 Segmentation은 파트너와 광고주가 특정 타기팅 값별로 분리된 메트릭을 조회할 수 있도록 합니다. 세그먼트화된 메트릭을 요청하려면 `segmentation_type` 요청 매개변수를 사용하십시오. Segmentation 옵션에 대한 자세한 내용은 [Metrics and Segmentation](/ko/x-ads-api/analytics#metrics-and-segmentation)을 참조하십시오.

<div id="faqs">
  ## 자주 묻는 질문(FAQ)
</div>

왜 Ads API 수치가 X Ads UI에 표시되는 값과 일치하지 않나요?

* `ALL_ON_TWITTER`, `PUBLISHER_NETWORK`, `SPOTLIGHT`, `TREND` 네 가지 게재 위치(placement)에 대한 데이터를 모두 요청했는지 확인하세요.
* Ads API의 종료 시각은 **제외**(exclusive)이지만, Ads UI에서는 **포함**(inclusive)된다는 점을 기억하세요.

왜 데이터를 요청하는 시점에 따라 수치가 달라지나요?

* 리포팅 지표가 사용 가능해지는 즉시 조회할 수 있으며, 거의 실시간에 가깝게 제공됩니다. 그러나 이 초기 결과는 추정치이므로 이후 변경될 수 있습니다. 지표는 지출(spend) 데이터를 제외하고 24시간 후 확정됩니다.
* 지출(spend) 지표는 일반적으로 이벤트 발생 후 3일 이내에 확정됩니다. 다만, 청구(billing) 데이터는 스팸 필터링 등의 처리를 위해 이벤트 발생일로부터 최대 14일 동안 처리됩니다.

특정 기간에 대해 어떤 엔티티 ID를 요청해야 할지 어떻게 알 수 있나요?

* [Active Entities 엔드포인트](/ko/x-ads-api/analytics#active-entities-2)를 사용하세요.

애널리틱스 응답의 모든 값이 왜 `null`인가요?

* 요청한 기간 동안 캠페인이 집행되지 않았을 가능성이 높습니다.
* 어떤 엔티티에 대해, 어떤 기간의 애널리틱스를 가져와야 하는지 파악하기 위해 [Active Entities 엔드포인트](/ko/x-ads-api/analytics#active-entities-2)를 사용하세요.

왜 API에는 `null` 값이 보이는데 UI에는 0으로 표시되나요?

* UI에서는 이러한 값을 0으로 표시하도록 선택했을 뿐이며, 값의 의미는 동일합니다.

X 타임라인처럼 세분화된 게재 위치(placement)와 연관된 지표는 어떻게 요청할 수 있나요?

* 애널리틱스에서 다음과 같은 placement 값을 지원합니다: `ALL_ON_TWITTER`, `PUBLISHER_NETWORK`, `SPOTLIGHT`, `TREND` (즉, [X Audience Platform](/ko/x-ads-api/audiences)).

삭제되었거나 일시 중지된 엔티티의 지표도 조회할 수 있나요?

* 가능합니다. 엔티티의 상태는 애널리틱스 지표의 가용성에 영향을 주지 않습니다.

세그먼트된 값이 세그먼트되지 않은 값과 일치하지 않는 이유는 무엇인가요?

* 이 정보가 산출되는 방식 때문에, 세그먼트된 데이터가 세그먼트되지 않은 데이터와 100% 일치하도록 합산(roll-up)될 것으로 기대해서는 **안 됩니다**.

여러 차원으로 세그먼트된 데이터를 요청할 수 있나요?

* 다중 세분화(multi-segmentation)는 지원하지 않습니다.

<div id="best-practices">
  ## 모범 사례
</div>

Ads API에서 [analytics](/ko/x-ads-api/analytics) data를 수집할 때 따라야 할 모범 사례입니다.

<div id="rate-limiting-and-retries">
  ### 속도 제한 및 재시도
</div>

* 속도 제한이 적용된 쿼리(`HTTP 429` 상태 코드를 반환하는 경우)에 대해서는 `x-rate-limit-reset` 헤더를 확인하고, 표시된 시간이 되었을 때나 그 이후에만 다시 시도해야 합니다.
* `HTTP 503 Service Unavailable` 상태 코드를 반환하는 쿼리의 경우 `retry-after` 헤더를 확인하고, 표시된 시간이 지난 뒤에만 다시 시도해야 합니다.
* 재시도 시간으로 표시된 값을 준수하지 않는 애플리케이션은 사전 통지 없이 Ads API에 대한 액세스가 철회되거나 제한될 수 있습니다.

<div id="analytics-metrics-in-a-nutshell">
  ### Analytics Metrics 한눈에 보기
</div>

* `billed_charge_local_micro`를 제외한 모든 Analytics 지표는 24시간이 지나면 확정되며 더 이상 변경되지 않습니다.
* `billed_charge_local_micro` 메트릭은 데이터가 반환된 시점부터 최대 3일 동안은 추정값입니다.
* 24시간이 지난 후에는, 과다 지출(지정된 `end_time` 이후에 송출된 광고) 및 허위로 판단된 과금 대상 이벤트에 대한 크레딧으로 인해 이 메트릭이 감소할 수 있습니다. 이 메트릭은 24시간 이후에는 거의 변경되지 않습니다.
* 자세한 내용은 [Analytics](/ko/x-ads-api/analytics)를 참조하세요.

<div id="fetching-real-time-non-segmented-data">
  ### 실시간 비세분화 데이터 가져오기
</div>

* 항상 `start_time`과 `end_time`을 모두 지정하십시오.
* 7일보다 오래된 엔티티에 대해서는 데이터를 가져오지 마십시오.
* 가능하면 `HOUR` 단위 세분화 수준으로 데이터를 요청하십시오. 이렇게 하면 언제든지 메트릭을 집계하여 `DAY` 및 `TOTAL` 수준으로 올릴 수 있습니다.
* 가능하면 `line_items` 및 `promoted_tweets` 수준에서 데이터를 요청하십시오. 이렇게 하면 언제든지 이러한 메트릭을 집계하여 전체 광고 엔티티 계층(예: 캠페인, 결제 수단 또는 계정 수준)에 대한 합계를 구할 수 있습니다.
* 분석 메트릭 값을 로컬 환경에 저장해 두십시오.
* 30일보다 오래된 데이터에 대해서는 반복적으로 쿼리하지 마십시오. 이 데이터는 변경되지 않으므로 로컬에 저장해 두어야 합니다.
* 모든 비세분화 데이터는 실시간으로 제공되며, 이벤트 발생 후 수초 내에 데이터를 사용할 수 있습니다.
* 전환 메트릭과 비전환 메트릭은 별도의 요청으로 나누어 전송하십시오.

<div id="fetching-segmented-data">
  ### 세분화된 데이터 가져오기
</div>

* 위의 “실시간, 비세분화 데이터 가져오기”에 제공된 지침을 참조하세요. 추가 권장 사항은 아래를 참고하세요.
* 대부분의 세분화된 데이터 유형의 경우, 상황에 따라 최대 1시간 동안 데이터가 완전하지 않을 수 있습니다. `INTERESTS`로 세분화된 데이터는 최대 12시간까지 지연될 수 있습니다.
* 이 정보가 산출되는 방식으로 인해, 세분화된 데이터가 비세분화 데이터와 100% 일치하거나 합산될 것으로 기대해서는 안 됩니다.

<div id="fetching-historical-data">
  ### 과거 데이터 가져오기
</div>

* 데이터를 백필링할 때(예: 새 광고주 계정을 추가할 때), `start_time`과 `end_time`을 더 작은 구간으로 나누어 여러 번 요청해야 할 수 있습니다.
* 조회 기간은 최대 30일 단위로 제한하세요.
* 이러한 요청의 속도를 조절(throttle)하고 시간에 걸쳐 분산시켜, 이 가져오기 작업에 대한 요청 한도(rate limit)를 소진하지 않도록 하세요.

<div id="metrics-by-objective">
  ## 목표별 측정지표
</div>

엔티티에 어떤 측정지표가 사용되는지는 [캠페인 목표](/ko/x-ads-api/campaign-management)에 따라 달라집니다. 이 가이드를 참고하여 각 목표 유형별로 조회해야 할 관련 측정지표 그룹을 결정하고, 추가 파생 측정지표의 산출 방법을 확인하십시오.

<div id="engagements">

<div id="active-entities">
  ### 활성 엔티티
</div>

<div id="introduction">
  #### 소개
</div>

[Active Entities 엔드포인트](/ko/x-ads-api/analytics#get-stats-accounts-account-id-active-entities)는 어떤 캠페인에 대해 애널리틱스를 요청해야 할지를 알려 주므로, [동기식](/ko/x-ads-api/analytics#get-stats-accounts-account-id) 및 [비동기식](/ko/x-ads-api/analytics#asynchronous-analytics) 애널리틱스 엔드포인트와 함께 사용하도록 설계되었습니다. 이는 광고 엔티티에 대한 세부 정보와 메트릭이 변경된 시점을 반환하는 방식으로 이루어집니다. 이 엔드포인트를 사용하면 코드와 애널리틱스 조회 로직을 크게 단순화할 수 있습니다.

이 가이드는 엔드포인트 및 해당 데이터 소스에 대한 정보와 맥락을 제공합니다. 또한 [사용 가이드라인](#usage)과 일련의 [예제 요청](#example)을 통해 Active Entities를 애널리틱스 엔드포인트와 함께 사용하는 방법을 보여 줍니다. [요약 섹션](#summary)에서는 권장 접근 방식에 대한 상위 수준 설명을 제공합니다.

<div id="data">
  #### 데이터
</div>

광고 엔티티의 메트릭이 변경될 때마다 해당 변경에 대한 정보가 기록됩니다. 이러한 변경 이벤트는 시간 단위 버킷에 저장되며, 엔티티에 대한 세부 정보와 함께 변경이 적용되는 시점에 대한 정보도 포함합니다. 변경 이벤트가 항상 기록된 시점과 일치하는 것은 아니기 때문에 후자가 필요합니다. 청구 조정이 그 대표적인 이유이지만, 이 외에도 여러 가지 이유가 있습니다.

<div id="endpoint">
  #### 엔드포인트
</div>

<div id="request">
  ### Request
</div>

Active Entities 요청은 광고 계정 단위로 수행되며 `entity`, `start_time`, `end_time` 세 개의 필수 쿼리 매개변수를 포함합니다.

`twurl -H ads-api.x.com "/11/stats/accounts/18ce54d4x5t/active_entities?entity=PROMOTED_TWEET&start_time=2019-03-05T00:00:00Z&end_time=2019-03-06T00:00:00Z"`

지원되는 `entity` 값은 `CAMPAIGN`, `FUNDING_INSTRUMENT`, `LINE_ITEM`, `MEDIA_CREATIVE`, `PROMOTED_ACCOUNT`, `PROMOTED_TWEET`입니다. 이는 분석 엔드포인트에서 지원하는 엔티티 유형을 반영합니다.

`start_time`과 `end_time` 값은 [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) 형식이어야 하며, 조회할 시간 단위 버킷(시간별 구간)을 지정합니다. 이 값들은 정시(정각) 단위로만 지정해야 합니다.

이 엔드포인트는 결과를 필터링하는 데 사용할 수 있는 세 가지 선택 매개변수도 지원합니다. `funding_instrument_ids`, `campaign_ids`, `line_item_ids`이며, 광고 계층 구조의 모든 수준과 지정된 모든 `entity` 유형에서 사용할 수 있습니다.

<div id="response">
  ### 응답
</div>

위의 요청에 대한 Active Entities 응답은 다음과 같습니다.

```json
    {
      "request": {
        "params": {
          "account_id": "18ce54d4x5t",
          "entity": "PROMOTED_TWEET",
          "start_time": "2019-03-05T00:00:00Z",
          "end_time": "2019-03-06T00:00:00Z"
        }
      },
      "data": [
        {
          "entity_id": "2r0wxw",
          "activity_start_time": "2019-03-04T20:55:20Z",
          "activity_end_time": "2019-03-05T03:43:56Z",
          "placements": [
            "ALL_ON_TWITTER"
          ]
        },
        {
          "entity_id": "2r30fn",
          "activity_start_time": "2019-03-05T08:11:08Z",
          "activity_end_time": "2019-03-05T14:40:59Z",
          "placements": [
            "ALL_ON_TWITTER",
            "PUBLISHER_NETWORK"
          ]
        }
      ]
    }
```

`data` 배열에는 이후 애널리틱스 요청에 포함되어야 하는 각 엔티티에 대해 하나의 객체가 포함됩니다. 이 집합에 포함되지 않은 ID에 대해서는 애널리틱스를 요청하면 안 됩니다.

각 객체에는 네 개의 필드가 포함됩니다: `entity_id`, `activity_start_time`, `activity_end_time`, `placements`. 활동 시작 및 종료 시각은 해당 엔티티의 변경 이벤트가 적용되는 시간 범위를 나타내며, 따라서 이후 애널리틱스 요청에서 지정해야 하는 날짜를 결정합니다. `placements` 배열에는 다음 값이 포함될 수 있습니다: `ALL_ON_TWITTER`, `PUBLISHER_NETWORK`, `SPOTLIGHT`, `TREND`. 이는 주어진 엔티티 ID에 대해 어떤 게재 위치(placement)를 요청해야 하는지를 나타냅니다.

<div id="usage">
  #### 사용 방법
</div>

Active Entities 엔드포인트는 애널리틱스 요청 방식을 결정하는 기준이 되어야 합니다. 아래 사용 지침은 애널리틱스 동기화를 지원하기 위해 작성되었으며, 파트너가 자체 데이터 저장소를 Twitter와 동기화된 상태로 유지할 수 있도록 합니다. 다시 말해, 정기적으로 실행되는 백그라운드 동기화를 어떻게 수행할지 설명합니다.

개발자가 내려야 하는 결정은 두 가지입니다.

1. 활성 엔터티 정보를 얼마나 자주 요청할지, 그리고 그에 따라 애널리틱스를 얼마나 자주 수집할지.
2. 활동 시작 및 종료 시간을 어떻게 활용하여 애널리틱스 요청의 `start_time` 및 `end_time` 값을 결정할지.

이 내용은 요약 이후 이어지는 두 개의 하위 섹션에서 각각 더 자세히 설명합니다.

<div id="summary">
  ### 요약
</div>

Active Entities 엔드포인트를 다음과 같이 사용하여 애널리틱스 요청 방식과 빈도를 결정합니다. 활성 엔터티 정보를 얼마나 자주 요청할지, 따라서 애널리틱스를 얼마나 자주 수집할지 결정한 이후에 아래 절차를 따르세요.

1. Active Entities 요청을 보냅니다.
2. 응답을 placement별로 분리합니다. `ALL_ON_TWITTER`용 그룹 하나, `PUBLISHER_NETWORK`용 그룹 하나, `SPOTLIGHT`용 그룹 하나, `TREND`용 그룹 하나로 나눕니다.
3. 각 placement 그룹에 대해 다음을 수행합니다.
   1. 엔터티 ID를 추출합니다.
   2. 애널리틱스 `start_time` 및 `end_time` 값을 결정합니다.
      * 최소 `activity_start_time`을 찾습니다. 이 값을 내림 처리합니다.
      * 최대 `activity_end_time`을 찾습니다. 이 값을 올림 처리합니다.
   3. 애널리틱스 요청을 보냅니다.
      * 엔터티 ID를 20개씩 배치로 그룹화합니다.
      * 3b 단계에서 구한 `start_time` 및 `end_time` 값을 사용합니다.
      * 적절한 `placement` 값을 지정합니다.
   4. 데이터 저장소에 기록합니다.

Python SDK 사용 예시는 [active&#95;entities.py](https://github.com/xdevplatform/twitter-python-ads-sdk/blob/master/examples/active_entities.py)를 참고하세요.

<div id="frequency">
  ### 빈도
</div>

첫 번째 질문에 대한 답변은 Active Entities 요청에 사용해야 하는 시간 범위를 결정합니다. 예를 들어, 매시간 Active Entities 정보를 요청하는 경우 시간 범위는 1시간이 되어야 합니다. 하루에 한 번 Active Entities 정보를 요청하는 경우 시간 범위는 하루가 되어야 합니다. 다시 말해, 시간 범위는 현재 요청의 `start_time`이 이전 요청의 `end_time`과 같도록 선택해야 합니다.

<Note>
  **Note**: 하나의 시간 구간(time window)은 한 번만 요청해야 합니다. 동일한 시간 구간을 여러 번 요청하면 불필요한 analytics 요청이 발생합니다. (아래 예외 참조.)
</Note>

파트너가 *현재* 시각이 포함된 1시간 구간에 대해 한 시간에 여러 번 analytics 정보를 요청하려는 경우에도 동일한 패턴이 적용됩니다. 즉, 요청 빈도가 시간 범위를 결정합니다. 아래 표는 이 시나리오에서 Active Entities의 예시 `start_time` 및 `end_time` 타임스탬프를 보여줍니다.

|     |     |     |
| :--- | :--- | :--- |
| **요청 시각** | **`start_time` 타임스탬프** | **`end_time` 타임스탬프** |
| 00:15:00 | 00:00:00 | 00:15:00 |
| 00:30:00 | 00:15:00 | 00:30:00 |
| 00:45:00 | 00:30:00 | 00:45:00 |
| 01:00:00 | 00:45:00 | 01:00:00 |

변경 이벤트가 저장되는 방식 때문에, 위의 네 개 Active Entities 요청은 모두 동일한 1시간 단위 버킷을 조회하며, 이 사용 사례에서는 이것이 필요합니다. 그러나 해당 시간이 지난 이후에는 이 1시간 버킷을 더 이상 조회해서는 안 됩니다.

<div id="activity-times">
  ### 활동 시간
</div>

활동 시작 및 종료 시간을 처리할 때는 다음과 같은 접근 방식을 권장합니다. Active Entities 응답의 모든 객체에서 최소 `activity_start_time`과 최대 `activity_end_time`을 찾습니다. 그런 다음 최소 활동 시작 시간은 내림하고 최대 활동 종료 시간은 올림하여 값을 수정합니다. 구체적으로는 두 시간 모두 타임스탬프의 시·분·초를 0으로 설정하고, 종료 시간에 하루를 더합니다. 이는 아래 표에 나와 있습니다. 이렇게 도출된 시작 및 종료 시간을 이후 분석 요청에 지정해야 합니다.

|     |     |
| :--- | :--- |
| **최소/최대 활동 시간** | **도출된 시간** |
| 2019-03-04T20:55:20Z  <br />  <br />2019-03-05T14:40:59Z | 2019-03-04T00:00:00Z  <br />  <br />2019-03-06T00:00:00Z |

**참고**: 시, 분, 초가 0으로 설정된 타임스탬프를 포함하는 것이 중요합니다. 그렇지 않고 날짜만 전달되면, 광고 계정의 표준 시간대에서 자정부터 자정까지의 분석을 요청한 것으로 간주하며, 이는 원하지 않는 결과일 수 있습니다. 예를 들어 최소 활동 시작 시간이 2019-02-28T01:30:07Z이고, 오프셋이 -08:00:00인 광고 계정에 대해 타임스탬프를 생략하면, 분석 요청은 01:30과 08:00 사이에 발생한 변경 사항을 놓치게 됩니다.

또는, 하루 전체로 확장하지 않고 반환된 활동 시간 구간에 대해서만 분석을 요청하고 싶다면 그렇게 할 수도 있습니다. 이 접근 방식을 사용할 경우 도출된 시작 및 종료 시간은 각각 2019-03-04T20:00:00Z와 2019-03-05T15:00:00Z가 됩니다. (이와 같은 범위는 분석 요청에서 `DAY` 세분성을 지정한 경우에는 허용되지 않는다는 점에 유의하십시오.)

<div id="asynchronous-analytics">
  ### 비동기 분석

<div id="introduction">
  #### 소개
</div>

비동기 분석 엔드포인트를 사용하면 파트너와 광고주는 생성 요청을 제출해 지표 생성을 요청할 수 있고, 서버는 이를 비동기적으로 처리합니다. (이러한 요청을 비동기 분석 &quot;작업&quot;이라고 부릅니다.) 이 방식에서는 요청이 완료될 때까지 클라이언트의 연결을 계속 유지할 필요가 없습니다.

이 엔드포인트는 동기식 엔드포인트와 마찬가지로 파트너와 광고주가 캠페인 성과에 대한 상세한 통계를 요청할 수 있도록 해 줍니다. 계정, 펀딩 수단, 캠페인, 라인 아이템, 프로모션 트윗, 미디어 크리에이티브에 대한 데이터 요청을 지원합니다. 동기식 엔드포인트와의 차이점은 비동기 분석 엔드포인트가 최대 90일까지 더 긴 기간을 지원하며, 세분화(segmentation)도 지원한다는 점입니다. 두 방식 간 차이에 대한 추가 정보는 [Analytics Overview](/ko/x-ads-api/analytics) 페이지에서 확인할 수 있습니다.

동기식 엔드포인트와 달리, 요율 제한(rate limiting)은 특정 계정에 대해 동시에 실행 중인 작업 수를 기준으로 적용됩니다. 다시 말해, 특정 시점에 처리 상태에 있을 수 있는 작업 수를 기준으로 합니다. 이 수치는 광고 계정 단위로 계산됩니다.

<div id="usage">
  #### 사용 방법
</div>

비동기 분석 엔드포인트를 사용해 캠페인 메트릭을 조회하는 과정은 여러 단계로 이루어집니다. 작업을 생성하고, 작업 처리 완료 여부를 확인한 다음, 마지막으로 data를 다운로드하는 순서입니다. data 파일은 압축을 해제해야 합니다. 구체적인 네 가지 단계는 다음과 같습니다.

1. [POST stats/jobs/accounts/:account&#95;id](/ko/x-ads-api/analytics#asynchronous-analytics) 엔드포인트를 사용해 작업을 생성합니다.
2. [GET stats/jobs/accounts/:account&#95;id](/ko/x-ads-api/analytics#asynchronous-analytics) 엔드포인트에 일정 간격으로 요청을 보내 작업 처리가 완료되었는지 확인합니다.
3. 작업 처리가 완료되면 data 파일을 다운로드합니다.
4. data 파일의 압축을 해제합니다.

data 파일에서 반환되는 응답 객체는 동기식 분석 엔드포인트 응답과 동일한 JSON 스키마를 가집니다.

세분화된 캠페인 메트릭은 비동기 분석 엔드포인트를 통해서만 조회할 수 있습니다. 캠페인 메트릭은 위치, 성별, 관심사, 키워드 등으로 세분화할 수 있습니다. 사용 가능한 옵션 전체 목록은 [Metrics and Segmentation](/ko/x-ads-api/analytics#metrics-and-segmentation) 페이지를 참고하세요. 세분화된 메트릭을 요청하려면 작업을 생성할 때 `segmentation_type` 요청 매개변수를 사용합니다.

<div id="example">

</div>

이 섹션에서는 비동기 분석 엔드포인트를 사용하는 방법을 설명합니다.

  #### GET stats/accounts/:account_id/active_entities[](#get-stats-accounts-account-id-active-entities "Permalink to this headline")
</div>

지정된 기간 동안 어떤 엔티티의 애널리틱스 지표가 변경되었는지에 대한 세부 정보를 가져옵니다.

이 엔드포인트는 애널리틱스 엔드포인트와 함께 사용해야 합니다. 이 엔드포인트의 결과는 어떤 광고 엔티티에 대해 애널리틱스를 요청해야 하는지를 나타냅니다. 사용 방법은 [Active Entities Guide](/ko/x-ads-api/analytics#active-entities)를 참고하세요.

변경 이벤트는 1시간 단위의 시간 버킷으로 제공됩니다.

* `start_time` 및 `end_time` 값은 조회할 1시간 단위 버킷을 지정합니다.
* 반환되는 `data` 배열에는 이후 애널리틱스 요청에 포함해야 하는 각 엔티티에 대한 객체가 포함됩니다.
* **중요**: 이후 애널리틱스 요청에서 지정해야 하는 날짜는 `activity_start_time` 및 `activity_end_time` 값을 기준으로 결정해야 합니다.
  * 이 값들은 저장된 변경 이벤트가 *적용되는* 시간 범위를 나타냅니다. 이는 엔티티별로 반환됩니다.

**참고**: 허용되는 최대 시간 범위(`end_time` - `start_time`)는 90일입니다.

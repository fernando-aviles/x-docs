<div id="oauth-20-authorization-code-flow-with-pkce">
  ### PKCE를 사용한 OAuth 2.0 인가 코드 플로우
</div>

<div id="introduction">
  #### 소개
</div>

OAuth 2.0은 애플리케이션의 스코프(scope)와 여러 기기에 걸친 인가 플로우를 보다 세밀하게 제어할 수 있게 해주는 업계 표준 인가 프로토콜입니다. OAuth 2.0을 사용하면 사용자 대신 특정 권한을 부여하는 세분화된 스코프를 선택할 수 있습니다. 

앱에서 OAuth 2.0을 사용하려면 개발자 콘솔의 앱 설정 섹션에 있는 앱 인증 설정에서 OAuth 2.0을 활성화해야 합니다.

<div id="how-long-will-my-credentials-stay-valid">
  #### 내 자격 증명은 얼마 동안 유효한가요?
</div>

기본적으로 PKCE를 사용하는 Authorization Code Flow를 통해 생성한 access token은 `offline.access` scope를 사용하지 않은 경우 2시간 동안만 유효합니다.

<div id="refresh-tokens">
  #### 리프레시 토큰
</div>

리프레시 토큰을 사용하면 애플리케이션이 리프레시 토큰 플로우를 통해 사용자에게 다시 동의를 요청하지 않고 새로운 액세스 토큰을 발급받을 수 있습니다.

`offline.access` 스코프가 적용된 경우 OAuth 2.0 리프레시 토큰이 발급됩니다. 이 리프레시 토큰을 사용해 액세스 토큰을 발급받을 수 있습니다. 이 스코프가 포함되지 않으면 리프레시 토큰은 생성되지 않습니다.

리프레시 토큰을 사용해 새 액세스 토큰을 얻기 위해 전송하는 요청의 예시는 다음과 같습니다:

```bash
POST 'https://api.x.com/2/oauth2/token' \
--header 'Content-Type: application/x-www-form-urlencoded' \
--data-urlencode 'refresh_token=bWRWa3gzdnk3WHRGU1o0bmRRcTJ5VUxWX1lZTDdJSUtmaWcxbTVxdEFXcW5tOjE2MjIxNDc3NDM5MTQ6MToxOnJ0OjE' \
--data-urlencode 'grant_type=refresh_token' \
--data-urlencode 'client_id=rG9n6402A3dbUJKzXTNX4oWHJ
```

<div id="app-settings">
  #### 앱 설정
</div>

앱의 인증 설정을 OAuth 1.0a 또는 OAuth 2.0으로 선택할 수 있습니다. 앱이 OAuth 1.0a와 OAuth 2.0을 모두 사용하도록 설정할 수도 있습니다.

OAuth 2.0은 X API v2에서만 사용할 수 있습니다. OAuth 2.0을 선택한 경우, 앱 설정의 Keys and Tokens 섹션에서 Client ID를 확인할 수 있습니다. 

<div id="confidential-clients">
  #### 기밀 클라이언트
</div>

[기밀 클라이언트](https://datatracker.ietf.org/doc/html/rfc6749#section-2.1)는 자격 증명을 안전하게 보관해 무단 당사자에게 노출하지 않으며, 인증 서버에 안전하게 인증할 수 있어 클라이언트 시크릿을 보호합니다. 반면 공개 클라이언트는 일반적으로 브라우저나 모바일 기기에서 실행되므로 클라이언트 시크릿을 사용할 수 없습니다. 앱 유형으로 기밀 클라이언트를 선택하면 client secret이 제공됩니다. 

개발자 콘솔에서 기밀 클라이언트 유형을 선택했다면 Client Secret도 확인할 수 있습니다. 선택 가능한 옵션은 Native App, Single page App, Web App, Automated App, bot입니다. Native App과 Single page App은 공개 클라이언트이며, Web App과 Automated App 또는 bot은 기밀 클라이언트입니다.

유효한 Authorization Header를 사용하는 기밀 클라이언트의 경우 client id가 필요하지 않습니다. 공개 클라이언트로 요청을 보낼 때는 요청 본문에 client id를 반드시 포함해야 합니다. 

<div id="scopes">
  #### 스코프(Scopes)
</div>

스코프를 사용하면 앱에 대한 액세스 권한을 세분화하여, 앱이 필요로 하는 권한만 부여할 수 있습니다. 어떤 스코프가 어떤 엔드포인트에 매핑되는지 자세히 알아보려면 [인증 매핑 가이드](/ko/resources/fundamentals/authentication/guides/v2-authentication-mapping)를 참고하세요.

|     |     |
| :--- | :--- |
| **Scope** | **설명** |
| tweet.read | 보호된 계정을 포함해 사용자가 볼 수 있는 모든 트윗. |
| tweet.write | 사용자를 대신해 트윗을 게시하고 리트윗합니다. |
| tweet.moderate.write | 사용자의 트윗에 대한 답글을 숨기거나 다시 표시합니다. |
| users.email | 인증된 사용자의 이메일. |
| users.read | 보호된 계정을 포함해 사용자가 볼 수 있는 모든 계정. |
| follows.read | 사용자를 팔로우하는 계정과 사용자가 팔로우하는 계정. |
| follows.write | 사용자를 대신해 계정을 팔로우하거나 언팔로우합니다. |
| offline.access | 사용자가 액세스를 취소할 때까지 계정에 계속 연결된 상태를 유지합니다. |
| space.read | 사용자가 볼 수 있는 모든 스페이스. |
| mute.read | 사용자가 뮤트한 계정. |
| mute.write | 사용자를 대신해 계정을 뮤트하거나 뮤트 해제합니다. |
| like.read | 사용자가 좋아요를 누른 트윗과 사용자가 볼 수 있는 좋아요. |
| like.write | 사용자를 대신해 트윗에 좋아요를 누르거나 취소합니다. |
| list.read | 사용자가 생성했거나 멤버로 속한 리스트(비공개 리스트 포함), 해당 리스트의 멤버 및 팔로워. |
| list.write | 사용자를 대신해 리스트를 생성하고 관리합니다. |
| block.read | 사용자가 차단한 계정. |
| block.write | 사용자를 대신해 계정을 차단하거나 차단 해제합니다. |
| bookmark.read | 인증된 사용자의 북마크된 트윗을 가져옵니다. |
| bookmark.write | 트윗을 북마크하거나 북마크를 제거합니다. |
| media.write | 미디어를 업로드합니다. |

<div id="rate-limits">
  #### 요청 한도
</div>

대부분의 경우 요청 한도는 OAuth 1.0a로 인증할 때와 동일하지만, 트윗 조회와 사용자 조회는 예외입니다. OAuth 2.0을 사용해 트윗 조회 및 사용자 조회를 수행하는 경우, 앱당 15분 기준 요청 한도가 300건에서 900건으로 증가합니다. 자세한 내용은 [요청 한도에 대한 문서](/ko/resources/fundamentals/rate-limits)를 참고하세요.

<div id="grant-types">
  #### 인가 유형
</div>

이 초기 출시에서는 지원되는 [grant types](https://oauth.net/2/grant-types/)로 [PKCE](https://oauth.net/2/pkce/)를 사용하는 [authorization code](https://oauth.net/2/grant-types/authorization-code/)와 [refresh token](https://oauth.net/2/grant-types/refresh-token/)만 지원합니다. 향후 더 많은 인가 유형을 제공할 수 있습니다.

<div id="oauth-20-flow">
  #### OAuth 2.0 플로우
</div>

OAuth 2.0는 현재 OAuth 1.0a에 사용 중인 것과 유사한 플로우를 따릅니다. 이 주제를 다루는 [문서](/ko/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens)에서 다이어그램과 자세한 설명을 확인할 수 있습니다. 

<div id="glossary">
  #### 용어 사전
</div>

|     |     |
| :--- | :--- |
| **용어** | **설명** |
| Grant types | OAuth 프레임워크는 다양한 사용 사례를 위한 여러 가지 Grant 유형과, 새로운 Grant 유형을 정의하기 위한 프레임워크를 제공합니다. 예시로 authorization code, client credentials, device code, refresh token 등이 있습니다. |
| Confidential client | Confidential client는 등록된 client secret을 안전하게 보관하는 등 인가 서버와 안전하게 인증할 수 있는 클라이언트 애플리케이션을 의미합니다. |
| Public client | Public client는 브라우저나 모바일 기기에서 동작하는 애플리케이션처럼 등록된 client secret을 사용할 수 없는 클라이언트를 의미합니다. |
| Authorization code flow | Confidential client와 Public client 모두가 authorization code를 access token으로 교환하는 데 사용하는 플로우입니다. |
| PKCE | Authorization code flow를 확장하여 여러 공격을 방지하고, Public client에서도 안전하게 OAuth 교환을 수행할 수 있도록 하는 확장 기능입니다. |
| Client ID | 개발자 콘솔의 Keys and tokens 섹션에서 &quot;Client ID&quot; 헤더 아래에서 확인할 수 있습니다. 이 항목이 보이지 않는 경우에는 X 팀에 직접 문의해 주시기 바랍니다. Client ID는 authorize URL을 생성하는 데 필요합니다. |
| Redirect URI | 애플리케이션의 콜백 URL입니다. [정확히 일치하는 검증](https://datatracker.ietf.org/doc/html/rfc6749#section-10.6)이 필요합니다. |
| Authorization code | 애플리케이션이 사용자를 대신해 API를 호출할 수 있도록 해주는 코드입니다. auth&#95;code라고도 합니다. 사용자가 승인한 auth&#95;code를 App 소유자가 수신한 시점부터 auth&#95;code의 유효 시간은 30초입니다. 30초 이내에 access token으로 교환해야 하며, 그렇지 않으면 auth&#95;code는 만료됩니다. |
| Access token | Access token은 애플리케이션이 사용자를 대신해 API 요청을 보낼 때 사용하는 토큰입니다. |
| Refresh token | Refresh token 플로우를 통해 사용자를 다시 프롬프트하지 않고도 애플리케이션이 새 access token을 얻을 수 있도록 합니다. |
| Client Secret | Confidential client 유형의 App을 선택한 경우, App의 Keys and tokens 섹션에서 “Client ID” 아래에 “Client Secret”이 제공됩니다. |

<div id="parameters">
  #### 매개변수
</div>

OAuth 2.0 authorize URL을 구성하려면 인가 URL에 다음 매개변수들이 포함되어 있는지 확인해야 합니다. 

|     |     |
| :--- | :--- |
| **매개변수** | **설명** |
| response&#95;type | 이 값이 인가 코드임을 나타내기 위해 “code”로 지정해야 합니다. |
| client&#95;id | 개발자 콘솔의 &quot;Client ID&quot; 헤더 아래에서 확인할 수 있습니다. |
| redirect&#95;uri | 콜백 URL입니다. 이 값은 App 설정에 정의된 Callback URL 중 하나와 정확히 일치해야 합니다. OAuth 2.0의 경우 콜백 URL에 대해 [exact match validation](https://datatracker.ietf.org/doc/html/rfc6749#section-10.6)을 사용해야 합니다. |
| state | [CSRF 공격](https://auth0.com/docs/protocols/state-parameters)을 방지하기 위해 제공하는 임의의 문자열입니다. 이 문자열의 길이는 최대 500자까지 가능합니다. |
| code&#95;challenge | 각 요청마다 사용하는 임의의 비밀값인 [PKCE](https://www.oauth.com/oauth2-servers/pkce/authorization-request/) 매개변수입니다. |
| code&#95;challenge&#95;method | 요청을 보낼 때 사용하는 방식을 지정합니다 (S256 또는 plain). |

<div id="authorize-url">
  #### Authorize URL
</div>

OAuth 2.0를 사용할 때는 사용자가 X로 &quot;Sign In&quot;과 유사한 인증 플로우를 통해 인증할 수 있도록 authorize URL을 생성합니다. 

다음은 생성하게 될 URL의 예시입니다.

```
https://x.com/i/oauth2/authorize?response_type=code&client_id=M1M5R3BMVy13QmpScXkzTUt5OE46MTpjaQ&redirect_uri=https://www.example.com&scope=tweet.read%20users.read%20account.follows.read%20account.follows.write&state=state&code_challenge=challenge&code_challenge_method=plain
```

이 URL이 제대로 작동하려면 올바른 인코딩이 필요합니다. 자세한 내용은 [percent encoding](/ko/resources/fundamentals/authentication/oauth-1-0a/percent-encoding-parameters)에 대한 문서를 참고하세요.

API 키와 토큰은 매우 신중하게 보호해야 합니다. 

이러한 자격 증명은 [developer App](/ko/resources/fundamentals/developer-apps)과, 해당 developer App이 그 계정들을 대신해 요청을 보낼 수 있도록 승인한 X 계정에 직접 연결됩니다. 키가 유출되면, 악의적인 사용자가 이를 사용해 developer App 또는 해당 승인 사용자들을 대신하여 X 엔드포인트로 요청을 보낼 수 있습니다. 이 경우 예기치 못한 rate limit에 도달하거나, 유료 액세스 할당량을 소진하거나, 심지어 developer App이 정지될 수도 있습니다.

다음 섹션에서는 API 키와 토큰을 관리할 때 고려해야 할 모범 사례를 설명합니다.

<div id="regenerate-api-keys-and-tokens">
  ## API 키와 토큰 재발급
</div>

API 키가 노출되었다고 판단되는 경우, 다음 단계를 따라 API 키를 재발급해야 합니다.

1. [Developer Console의 &quot;Apps&quot; 페이지](https://developer.x.com/en/portal/projects-and-apps.html)로 이동합니다.
2. 해당 App 옆에 있는 &quot;Keys and tokens&quot; 아이콘(🗝 )을 클릭합니다.
3. 재발급하려는 키와 토큰 세트 옆의 &quot;Regenerate&quot; 버튼을 클릭합니다. 

Access Token 또는 Bearer Token을 프로그래밍 방식으로 재발급하려는 경우, 인증 엔드포인트를 사용해 처리할 수 있습니다.

* Access Token을 재발급하려면, 먼저 [POST oauth/invalidate&#95;token](/ko/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token) 엔드포인트를 사용해 토큰을 무효화한 뒤, [3-legged OAuth flow](/ko/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens)를 사용해 토큰을 다시 발급받아야 합니다.
* Bearer Token을 재발급하려면, 먼저 [POST oauth2/invalidate&#95;token](/ko/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token) 엔드포인트를 사용해 토큰을 무효화한 뒤, [POST oauth2/token](/ko/resources/fundamentals/authentication/api-reference#post-oauth2-token) 엔드포인트를 사용해 토큰을 다시 발급받아야 합니다.

<div id="having-a-central-file-for-your-secrets">
  ## 시크릿을 위한 중앙 파일 사용
</div>

시크릿을 저장하기 위해 .ENV 파일이나 기타 유형의 .yaml 파일을 사용하는 것은 도움이 될 수 있는 하나의 방법이지만, 이러한 파일이 git 저장소에 실수로 커밋되지 않도록 방지해 줄 수 있는 강력한 .gitignore 파일을 반드시 설정해야 합니다. 

<div id="environment-variables">
  ## 환경 변수
</div>

환경 변수를 사용하는 코드를 작성하면 유용할 수 있습니다. 

Python으로 작성된 예시는 다음과 같습니다:

```python
import os

consumer_key = os.environ.get("CONSUMER_KEY")

consumer_secret = os.environ.get("CONSUMER_SECRET")
```

터미널에서 다음과 같이 입력하세요:

```bash
export CONSUMER_KEY='xxxxxxxxxxxxxxxxxxx'
export CONSUMER_SECRET='xxxxxxxxxxxxxxxxxxxxxxx'
```

<div id="source-code-and-version-control">
  ## 소스 코드와 버전 관리
</div>

개발자가 가장 자주 범하는 보안 실수는 GitHub, BitBucket과 같은 버전 관리 시스템의 소스 코드에 API 키와 토큰을 커밋해 두는 것입니다. 이러한 코드 리포지토리 중 상당수는 공개되어 있습니다. 이 실수는 공개 코드 리포지토리에서 너무 자주 발생하기 때문에, API 키를 스크레이핑(scraping)해 가는 수익성 있는 봇들까지 존재합니다.

* 서버 환경 변수를 사용하세요. API 키를 환경 변수에 저장하면 코드와 버전 관리에서 분리할 수 있습니다. 이렇게 하면 환경별로 서로 다른 키를 쉽게 사용할 수도 있습니다.
* 버전 관리에서 제외된 설정 파일을 사용하세요. 파일 이름을 [.gitignore](https://git-scm.com/docs/gitignore) 파일에 추가하여, 해당 파일이 버전 관리에서 추적되지 않도록 제외하세요.
* 한 번이라도 버전 관리를 사용한 후에 코드에서 API 키를 제거하더라도, 코드베이스의 이전 버전에 접근하면 여전히 해당 API 키를 확인할 수 있을 가능성이 높습니다. 다음 섹션에 설명된 대로 API 키를 재발급(재생성)하세요.

<div id="databases">
  ## 데이터베이스
</div>

액세스 토큰을 데이터베이스에 저장해야 하는 경우, 다음 사항을 유념하세요.

* 액세스 토큰은 토큰 소유자만 읽을 수 있도록 데이터베이스에 대한 접근을 제한해야 합니다.
* 액세스 토큰이 저장된 데이터베이스 테이블에 대한 수정/쓰기 권한을 제한해야 합니다. 이 작업은 키 관리 시스템으로 자동화해야 합니다.
* 어떤 data 저장소에 저장하더라도, 저장하기 전에 액세스 토큰을 암호화해야 합니다.

<div id="password-management-tools">
  ## 비밀번호 관리 도구
</div>

1Password나 LastPass와 같은 비밀번호 관리 도구는 키와 토큰을 안전하게 보관하는 데 유용할 수 있습니다. 다만 이러한 정보를 팀이 공동으로 사용하는 비밀번호 관리 도구 안에서 공유하는 것은 피하는 것이 좋습니다.

<div id="web-storage-cookies">
  ## Web storage &amp; cookies
</div>

웹 스토리지는 LocalStorage와 SessionStorage의 두 가지 유형이 있습니다. 이들은 쿠키(Cookie)를 사용하는 방식의 개선 형태로 만들어졌으며, 웹 스토리지는 쿠키보다 훨씬 더 많은 용량을 저장할 수 있다는 이점이 있습니다. 다만, 각 스토리지 옵션마다 서로 다른 장단점이 있습니다.
 

**Web Storage: LocalStorage**

로컬 웹 스토리지에 저장되는 모든 데이터는 지속적으로 유지됩니다. 즉, 데이터를 명시적으로 삭제하지 않는 한 계속 남아 있게 됩니다. 프로젝트의 요구 사항에 따라, 이를 긍정적으로 볼 수도 있습니다. 그러나 LocalStorage를 사용할 때에는 주의가 필요합니다. 저장된 데이터에 대한 모든 변경 및 추가 내용이 해당 웹페이지에 대한 향후 모든 방문에서 그대로 사용 가능하기 때문입니다. 일반적으로는 LocalStorage 사용을 권장하지 않지만, 몇 가지 예외적인 경우는 있을 수 있습니다. LocalStorage를 사용하기로 했다면, 이것이 동일 출처 정책(same-origin policy)을 지원한다는 점을 알고 있는 것이 좋습니다. 따라서 여기에 저장된 모든 데이터는 동일한 origin에서만 접근할 수 있습니다. LocalStorage 사용 시 추가적인 성능상의 장점으로는, 모든 HTTP 요청마다 데이터를 서버로 다시 전송할 필요가 없으므로 클라이언트-서버 간 트래픽이 줄어든다는 점이 있습니다.
 

**Web Storage: SessionStorage**

SessionStorage는 LocalStorage와 유사하지만, 핵심적인 차이는 SessionStorage가 지속적이지 않다는 점입니다. SessionStorage에 쓰기 작업을 수행한 창(또는 사용 중인 브라우저에 따라 탭)이 닫히면 해당 데이터는 사라집니다. 이는 사용자 세션 내에서 토큰에 대한 읽기 접근을 제한하는 데 유용합니다. 보안 측면에서 보면 일반적으로 LocalStorage보다 SessionStorage를 사용하는 것이 더 바람직한 경우가 많습니다. LocalStorage와 마찬가지로, SessionStorage에도 동일 출처 정책 지원과 클라이언트-서버 트래픽 감소라는 장점이 적용됩니다.
 

**Cookies**

쿠키는 세션 데이터를 저장하는 보다 전통적인 방식입니다. 각 쿠키에 만료 시간을 설정할 수 있어 손쉬운 폐기 및 접근 제한을 구현할 수 있습니다. 그러나 쿠키를 사용하면, 데이터가 모든 HTTP 요청마다 서버로 전송되기 때문에 클라이언트-서버 트래픽이 확실히 증가하게 됩니다. 쿠키를 사용하기로 결정했다면, 세션 하이재킹(session hijacking)에 대비해야 합니다. 기본적으로 쿠키는 HTTP 상에서 평문으로 전송되며, 이로 인해 그 내용이 패킷 스니핑 및/또는 공격자가 트래픽을 수정할 수 있는 중간자 공격(man-in-the-middle attack)에 취약해집니다. 데이터 전송 중 보호를 위해서는 항상 HTTPS 사용을 강제해야 합니다. 이는 기밀성, 무결성(데이터 무결성), 그리고 인증을 제공합니다. 하지만 웹 애플리케이션 또는 사이트가 HTTP와 HTTPS 둘 다로 접근 가능한 경우, 쿠키에 &#39;Secure&#39; 플래그를 설정하는 것이 좋습니다. 이렇게 하면 공격자가 사용자에게 사이트의 HTTP 버전 링크를 보내고, 그로 인해 생성되는 HTTP 요청을 도청하는 것을 방지할 수 있습니다.

쿠키 사용 시 세션 하이재킹에 대한 보조적인 방어 수단으로는, 영향도가 큰 작업을 수행하기 전에 사용자 신원을 다시 검증하는 방법이 있습니다. 쿠키 보안을 강화하기 위해 고려해야 할 또 다른 플래그로는 &#39;HttpOnly&#39; 플래그가 있습니다. 이 플래그는 해당 쿠키가 지정된 서버에서만 접근 가능하도록 브라우저에 지시합니다. 클라이언트 측 스크립트에서의 접근 시도는 이 플래그에 의해 차단되며, 이를 통해 대부분의 크로스 사이트 스크립팅(XSS) 공격으로부터 보호하는 데 도움이 됩니다.

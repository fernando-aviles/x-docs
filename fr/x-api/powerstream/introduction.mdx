Powerstream est notre API de diffusion en temps réel la plus rapide pour accéder aux données publiques X. À l’image de l’ancienne API GNIP Powetrack, elle utilise des règles pour filtrer les Publications en fonction de mots-clés, d’opérateurs et de métadonnées. Une fois qu’une connexion HTTP persistante est établie avec l’endpoint Powerstream, vous pouvez commencer à recevoir des Publications correspondantes en quasi temps réel.

Actuellement, Powerstream prend en charge jusqu’à 1 000 règles et chaque règle peut comporter 2 048 caractères.

<div id="key-features">
  ## Fonctionnalités clés :
</div>

* **Diffusion de données en temps quasi réel** : recevez des données correspondant à vos règles quasiment en temps réel.
* **Filtrage précis** : filtrez exactement les données que vous recherchez grâce à des requêtes booléennes et des opérateurs.
* **Diffusion** : réponse JSON via le mécanisme de transfert par blocs HTTP/1.1.
* **Prise en charge des centres de données locaux** : récupérez uniquement les publications depuis le centre de données local afin de réduire la latence en évitant les délais de réplication.

<div id="quick-start">
  ## Démarrage rapide
</div>

Cette section explique comment démarrer rapidement avec les endpoints PowerStream en Python à l’aide de la bibliothèque `requests`. Installez-la via `pip install requests`. Tous les exemples utilisent l’authentification OAuth 2.0 Bearer Token. Remplacez `YOUR_BEARER_TOKEN` par votre propre jeton (conservez-le de manière sécurisée, par exemple via `os.getenv('BEARER_TOKEN')`).

Nous passerons en revue chaque endpoint avec des extraits de code. Supposons ces imports en haut du fichier :

```python
import requests
import json
import time
import sys
import os  # Pour les variables d'environnement
```

<div id="setup">
  ### Configuration
</div>

```python
bearer_token = os.getenv('BEARER_TOKEN') or "YOUR_BEARER_TOKEN"  # Utiliser une variable d'environnement pour des raisons de sécurité
base_url = "https://api.x.com/2/powerstream"
rules_url = f"{base_url}/rules"  # Pour la gestion des règles
headers = {
   "Authorization": f"Bearer {bearer_token}",
   "Content-Type": "application/json"
}
```

<div id="1-create-rules-post-rules">
  ### 1. Créer des règles (POST /rules)
</div>

Ajoutez des règles pour filtrer votre flux.

```python
data = {
   "rules": [
       {
           "value": "(cat OR dog) lang:en -is:retweet",
           "tag": "pet-monitor"
       },
       # Ajoutez d'autres règles si nécessaire (jusqu'à 100)
   ]
}

response = requests.post(rules_url, headers=headers, json=data)
if response.status_code == 201:
   rules_added = response.json().get("data", {}).get("rules", [])
   print("Règles ajoutées :")
   for rule in rules_added:
       print(f"ID: {rule['id']}, Value: {rule['value']}, Tag: {rule.get('tag', 'N/A')}")
else:
   print(f"Erreur {response.status_code} : {response.text}")
```

<div id="2-delete-rules-post-rules">
  ### 2. Supprimer des règles (POST /rules)
</div>

Supprimez des règles en utilisant leur id (recommandé) ou leur valeur.

```python
data = {
   "rules": [
       {
           "value": "(cat OR dog) lang:en -is:retweet",
           "tag": "pet-monitor"
       },
       # Ajoutez d'autres règles au besoin (jusqu'à 100)
   ]
}

response = requests.delete(rules_url, headers=headers, json=data)
if response.status_code == 200:
   deleted = response.json().get("data", {})
   print(f"Deleted count: {deleted.get('deleted', 'N/A')}")
   if 'not_deleted' in deleted:
       print("Not deleted:", deleted['not_deleted'])
else:
   print(f"Error {response.status_code}: {response.text}")
```

**Conseil** : Pour supprimer toutes les règles, commencez par les récupérer avec une requête GET, extrayez leurs identifiants, puis supprimez-les en une seule opération.

<div id="3-get-rules-get-rules">
  ### 3. Récupérer les règles (GET /rules)
</div>

Récupère toutes les règles actives.

```python
response = requests.get(rules_url, headers=headers)
if response.status_code == 200:
   rules = response.json().get("data", {}).get("rules", [])
   if rules:
       print("Active rules:")
       for rule in rules:
           print(f"ID: {rule['id']}, Value: {rule['value']}, Tag: {rule.get('tag', 'N/A')}")
   else:
       print("No active rules.")
else:
   print(f"Error {response.status_code}: {response.text}")
```

<div id="4-powerstream-get-stream">
  ### 4. PowerStream (GET /stream)
</div>

Connectez-vous au flux pour recevoir des Publications en temps réel. Utilisez `stream=True` pour une lecture ligne par ligne. Implémentez une logique de reconnexion pour améliorer la robustesse.

```python
stream_url = base_url

def main():
   while True:
       response = requests.request("GET", stream_url, headers=headers, stream=True)
       print(response.status_code)
       for response_line in response.iter_lines():
           if response_line:
               json_response = json.loads(response_line)
               print(json.dumps(json_response, indent=4, sort_keys=True))
               if response.status_code != 200:
                   print(response.headers)
                   raise Exception(
                       "Request returned an error: {} {}".format(
                           response.status_code, response.text
                       )
                   )
```

<div id="local-datacenter-support">
  #### Prise en charge du datacenter local
</div>

Pour optimiser la latence, Powerstream offre une option permettant de récupérer uniquement les publications qui ont été émises ou créées dans le datacenter local où la connexion est établie. Cela évite le décalage dû à la réplication, ce qui permet une diffusion plus rapide par rapport aux publications provenant d&#39;autres datacenters. Pour activer cette option, ajoutez le paramètre de requête `?localDcOnly=true` à l&#39;endpoint de flux (par exemple, `/2/powerstream?localDcOnly=true`). Le datacenter auquel vous êtes connecté sera indiqué à la fois dans la charge utile de data initiale du flux et en tant qu&#39;en-tête HTTP dans la réponse.

Pour l&#39;utiliser dans le code :

```python
# Pour le centre de données local uniquement :
stream_url = "https://api.x.com/2/powerstream?localDcOnly=true"
```

Si le paramètre `localDcOnly` est activé, lors de la première connexion du flux, les en-têtes de réponse suivants indiqueront quel centre de données local est utilisé :

```bash
'x-powerstream-datacenter': 'atla',
'x-powerstream-localdconly': 'true'
```

En outre, il enverra également un payload initial spécifiant le centre de données :

```bash
{
    "type": "connection_metadata",
    "datacenter": "atla",
    "timestamp": 1762557264155
}
```

<Note>
  **Astuce :** pour optimiser la latence, configurez des connexions depuis différentes zones géographiques (par exemple, une près d’Atlanta, sur la côte Est des États-Unis, et une autre près de Portland, sur la côte Ouest), en activant `localDcOnly=true` pour chacune d’elles. Cela permet un accès plus rapide aux publications de chaque centre de données. Agrégez les flux de votre côté pour combiner les données entre centres de données.
</Note>

<div id="operators">
  ## Opérateurs
</div>

Pour définir des règles de filtrage, vous pouvez utiliser des mots clés et des opérateurs. Consultez la liste des opérateurs disponibles ci-dessous.

<div id="field-based-operators">
  ### Opérateurs par champ
</div>

<div id="user-operators">
  #### Opérateurs d’utilisateur
</div>

| Opérateur | Résumé | Exemple |
|----------|--------|---------|
| `from:` | Correspond aux publications d’un utilisateur spécifique | `from:xdevelopers` ou `from:123456` |
| `to:` | Correspond aux publications adressées à un utilisateur spécifique | `to:jvaleski` |
| `retweets_of:` | Correspond aux reposts d’un utilisateur spécifique | `retweets_of:xdevelopers` |

<div id="content-operators">
  #### Opérateurs de contenu
</div>

| Operator | Summary | Example |
|----------|---------|---------|
| `contains:` | Correspond aux publications contenant un texte ou des mots-clés spécifiques | `contains:hello` ou `contains:-2345.432` |
| `url_contains:` | Correspond aux publications avec des URL contenant un texte spécifique | `url_contains:"com/willplayforfood"` |
| `lang:` | Correspond aux publications dans des langues spécifiques | `lang:en` |

<div id="entity-operators">
  #### Opérateurs d&#39;entité
</div>

| Operator | Résumé | Exemple |
|----------|---------|---------|
| `has:` | Filtre les publications contenant des entités spécifiques (Options : mentions, geo, links, media, lang, symbols, images, videos) | `has:images`, `has:geo`, `has:mentions` |
| `is:` | Filtre les publications d’un type spécifique ou avec des propriétés spécifiques (Options : retweet, reply) | `is:retweet`, `is:reply` |

<div id="location-operators">
  #### Opérateurs de localisation
</div>

| Opérateur | Résumé | Exemple |
|----------|--------|---------|
| `place:` | Renvoie les publications provenant de lieux/emplacements spécifiques | `place:"Belmont Central"`, `place:02763fa2a7611cf3` |
| `bounding_box:` | Renvoie les publications situées à l’intérieur d’un rectangle géographique | `bounding_box:[-112.424083 42.355283 -112.409111 42.792311]` |
| `point_radius:` | Renvoie les publications situées dans un rayon autour d’un point | `point_radius:[-111.464973 46.371179 25mi]`, `point_radius:[-111.464973 46.371179 15km]` |

<div id="advancedcontent-operators">
  #### Opérateurs avancés/de contenu
</div>

| Opérateur | Résumé | Exemple |
|----------|---------|---------|
| `bio:` | Renvoie les publications d’utilisateurs dont la bio contient un contenu spécifique (utilise une correspondance par expression exacte) | N/A |
| `bio_name:` | Renvoie les publications d’utilisateurs dont la bio contient un nom spécifique (utilise une correspondance par expression exacte) | N/A |

<div id="additional-operators">
  #### Opérateurs supplémentaires
</div>

| Opérateur | Description | Exemple |
|----------|-------------|---------|
| `retweets_of_status_id:` | Correspond aux reposts de publications spécifiques | `retweets_of_status_id:1234567890123456789` |
| `in_reply_to_status_id:` | Correspond aux réponses à des publications spécifiques | `in_reply_to_status_id:1234567890123456789` |

<div id="non-field-operators">
  ### Opérateurs non liés à un champ
</div>

<div id="special-syntax-operators">
  #### Opérateurs de syntaxe spéciale
</div>

| Opérateur | Description | Exemple |
|----------|-------------|---------|
| `@` | Opérateur de mention | `@username` |
| Correspondance d’expressions | Fait correspondre des expressions exactes | `"exact phrase"` |

<div id="logical-operators">
  #### Opérateurs logiques
</div>

| Opérateur | Description | Exemple |
|----------|-------------|---------|
| `OR` | OU logique entre des expressions | `x OR facebook` |
| Espace/AND | ET logique entre des expressions | `x facebook` (les deux termes doivent être présents) |
| `()` | Regroupement d’expressions complexes | `(x OR facebook) iphone` |
| `-` | Négation/exclusion | `x -facebook` (x mais pas facebook) |

<div id="limits-best-practices">
  ## Limites et bonnes pratiques
</div>

* Limites de débit : 50 requêtes/24h pour la gestion des règles ; aucune limite sur les flux (mais des limites de connexion s’appliquent).
* Reconnexion : backoff exponentiel en cas de déconnexion.
* Surveillance : utilisez les en-têtes `Connection: keep-alive`.

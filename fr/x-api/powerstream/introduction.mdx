Powerstream est notre API de diffusion en temps réel la plus rapide pour accéder aux données publiques de X. Comme l’ancienne API GNIP PowerTrack, elle utilise des règles pour filtrer les Publications en fonction de mots-clés, d’opérateurs et de métadonnées. Une fois qu’une connexion HTTP persistante est établie avec l’endpoint Powerstream, vous pouvez commencer à recevoir les Publications correspondantes en quasi temps réel.

Actuellement, Powerstream prend en charge jusqu’à 1 000 règles et chaque règle peut contenir 2 048 caractères.

<div id="key-features">
  ## Principales fonctionnalités :
</div>

* **Diffusion de données en temps réel** : recevez des données correspondant à vos règles en temps quasi réel.
* **Filtrage précis** : filtrez exactement les données que vous recherchez à l’aide de requêtes booléennes avec opérateurs.
* **Diffusion** : réponse JSON via HTTP/1.1 avec encodage de transfert par blocs (chunked transfer encoding).
* **Prise en charge du centre de données local** : récupérez uniquement les publications depuis le centre de données local afin de réduire la latence en évitant les retards de réplication.

<div id="quick-start">
  ## Démarrage rapide
</div>

Cette section illustre comment démarrer rapidement avec les endpoints PowerStream en utilisant Python avec la bibliothèque `requests`. Installez-la via `pip install requests`. Tous les exemples utilisent l’authentification OAuth 2.0 Bearer Token. Remplacez `YOUR_BEARER_TOKEN` par votre jeton d’accès réel (conservez-le de manière sécurisée, par exemple via `os.getenv('BEARER_TOKEN')`).

Nous passerons en revue chaque endpoint avec des extraits de code. Supposons ces imports en début de fichier :

```python
import requests
import json
import time
import sys
import os  # Pour les variables d'environnement
```

<div id="setup">
  ### Configuration
</div>

```python
bearer_token = os.getenv('BEARER_TOKEN') or "YOUR_BEARER_TOKEN"  # Utiliser une variable d'environnement pour des raisons de sécurité
base_url = "https://api.x.com/2/powerstream"
rules_url = f"{base_url}/rules"  # Pour la gestion des règles
headers = {
   "Authorization": f"Bearer {bearer_token}",
   "Content-Type": "application/json"
}
```

<div id="1-create-rules-post-rules">
  ### 1. Créer des règles (POST /rules)
</div>

Ajoutez des règles pour filtrer votre flux.

```python
data = {
   "rules": [
       {
           "value": "(cat OR dog) lang:en -is:retweet",
           "tag": "pet-monitor"
       },
       # Ajoutez d'autres règles si nécessaire (jusqu'à 100)
   ]
}

response = requests.post(rules_url, headers=headers, json=data)
if response.status_code == 201:
   rules_added = response.json().get("data", {}).get("rules", [])
   print("Règles ajoutées :")
   for rule in rules_added:
       print(f"ID: {rule['id']}, Value: {rule['value']}, Tag: {rule.get('tag', 'N/A')}")
else:
   print(f"Erreur {response.status_code} : {response.text}")
```

<div id="2-delete-rules-post-rules">
  ### 2. Supprimer des règles (POST /rules)
</div>

Supprimez des règles via leur id (recommandé) ou leur valeur.

```python
data = {
   "rules": [
       {
           "value": "(cat OR dog) lang:en -is:retweet",
           "tag": "pet-monitor"
       },
       # Ajoutez d'autres règles au besoin (jusqu'à 100)
   ]
}

response = requests.delete(rules_url, headers=headers, json=data)
if response.status_code == 200:
   deleted = response.json().get("data", {})
   print(f"Deleted count: {deleted.get('deleted', 'N/A')}")
   if 'not_deleted' in deleted:
       print("Not deleted:", deleted['not_deleted'])
else:
   print(f"Error {response.status_code}: {response.text}")
```

**Astuce** : pour supprimer toutes les règles, commencez par les récupérer avec GET, extrayez leurs id, puis supprimez-les en une seule opération.

<div id="3-get-rules-get-rules">
  ### 3. Récupérer les règles (GET /rules)
</div>

Récupérer toutes les règles actives.

```python
response = requests.get(rules_url, headers=headers)
if response.status_code == 200:
   rules = response.json().get("data", {}).get("rules", [])
   if rules:
       print("Active rules:")
       for rule in rules:
           print(f"ID: {rule['id']}, Value: {rule['value']}, Tag: {rule.get('tag', 'N/A')}")
   else:
       print("No active rules.")
else:
   print(f"Error {response.status_code}: {response.text}")
```

<div id="4-powerstream-get-stream">
  ### 4. PowerStream (GET /stream)
</div>

Connectez-vous au flux pour des Publications en temps réel. Utilisez `stream=True` pour lire le flux ligne par ligne. Mettez en œuvre une logique de reconnexion pour plus de robustesse.

```python
stream_url = base_url

def main():
   while True:
       response = requests.request("GET", stream_url, headers=headers, stream=True)
       print(response.status_code)
       for response_line in response.iter_lines():
           if response_line:
               json_response = json.loads(response_line)
               print(json.dumps(json_response, indent=4, sort_keys=True))
               if response.status_code != 200:
                   print(response.headers)
                   raise Exception(
                       "Request returned an error: {} {}".format(
                           response.status_code, response.text
                       )
                   )
```

<div id="local-datacenter-support">
  #### Prise en charge des centres de données locaux
</div>

Pour optimiser la latence, Powerstream propose une option permettant de récupérer uniquement les publications créées dans le centre de données local où la connexion est établie. Cela évite le décalage de réplication, ce qui permet une livraison plus rapide que pour les publications provenant d&#39;autres centres de données. Pour activer cette option, ajoutez le paramètre de requête `?localDcOnly=true` à l&#39;endpoint de flux (par exemple, `/2/powerstream?localDcOnly=true`). Le centre de données auquel vous êtes connecté sera indiqué à la fois dans la charge utile data initiale du flux et dans un en-tête HTTP de la réponse.

Pour l&#39;utiliser dans le code :

```python
# Pour le centre de données local uniquement :
stream_url = "https://api.x.com/2/powerstream?localDcOnly=true"
```

Si le paramètre `localDcOnly` est activé, lors de la première connexion du flux, il inclura les en-têtes de réponse suivants indiquant quel centre de données local est utilisé :

```bash
'x-powerstream-datacenter': 'atla',
'x-powerstream-localdconly': 'true'
```

En outre, il enverra une charge utile initiale indiquant le centre de données :

```bash
{
    "type": "connection_metadata",
    "datacenter": "atla",
    "timestamp": 1762557264155
}
```

<Note>
  **Astuce :** Pour optimiser la latence, configurez des connexions depuis différentes zones géographiques (par exemple, une près d’Atlanta sur la côte Est des États-Unis et une autre près de Portland sur la côte Ouest), en activant `localDcOnly=true` pour chacune. Cela permet un accès plus rapide aux publications de chaque datacenter concerné. Agrégez les flux de votre côté pour combiner les données entre datacenters.
</Note>

<div id="operators">
  ## Opérateurs
</div>

Pour définir des règles de filtrage, utilisez des mots-clés et des opérateurs. Vous trouverez ci-dessous la liste des opérateurs disponibles.

<div id="field-based-operators">
  ### Opérateurs par champ
</div>

<div id="user-operators">
  #### Opérateurs d’utilisateurs
</div>

| Opérateur | Description | Exemple |
|----------|-------------|---------|
| `from:` | Correspond aux publications provenant d’un utilisateur spécifique | `from:xdevelopers` ou `from:123456` |
| `to:` | Correspond aux publications adressées à un utilisateur spécifique | `to:jvaleski` |
| `retweets_of:` | Correspond aux republis d’un utilisateur spécifique | `retweets_of:xdevelopers` |

<div id="content-operators">
  #### Opérateurs de contenu
</div>

| Operator | Summary | Example |
|----------|---------|---------|
| `contains:` | Renvoie les publications qui contiennent un texte ou des mots-clés spécifiques | `contains:hello` ou `contains:-2345.432` |
| `url_contains:` | Renvoie les publications dont les URL contiennent un texte spécifique | `url_contains:"com/willplayforfood"` |
| `lang:` | Renvoie les publications rédigées dans des langues spécifiques | `lang:en` |

<div id="entity-operators">
  #### Opérateurs d&#39;entité
</div>

| Operator | Summary | Example |
|----------|---------|---------|
| `has:` | Correspond aux publications contenant des entités spécifiques (Options : mentions, geo, links, media, lang, symbols, images, videos) | `has:images`, `has:geo`, `has:mentions` |
| `is:` | Correspond aux publications d&#39;un type spécifique ou possédant des propriétés spécifiques (Options : retweet, reply) | `is:retweet`, `is:reply` |

<div id="location-operators">
  #### Opérateurs de localisation
</div>

| Opérateur | Résumé | Exemple |
|----------|--------|---------|
| `place:` | Correspond aux publications provenant de lieux/localisations spécifiques | `place:"Belmont Central"`, `place:02763fa2a7611cf3` |
| `bounding_box:` | Correspond aux publications situées dans une boîte englobante géographique | `bounding_box:[-112.424083 42.355283 -112.409111 42.792311]` |
| `point_radius:` | Correspond aux publications situées dans un rayon autour d’un point | `point_radius:[-111.464973 46.371179 25mi]`, `point_radius:[-111.464973 46.371179 15km]` |

<div id="advancedcontent-operators">
  #### Opérateurs avancés/de contenu
</div>

| Opérateur | Résumé | Exemple |
|----------|--------|---------|
| `bio:` | Correspond aux publications d’utilisateurs avec un contenu spécifique dans leur biographie (utilise la correspondance de phrases) | N/A |
| `bio_name:` | Correspond aux publications d’utilisateurs avec un nom spécifique dans leur biographie (utilise la correspondance de phrases) | N/A |

<div id="additional-operators">
  #### Opérateurs supplémentaires
</div>

| Opérateur | Résumé | Exemple |
|----------|--------|---------|
| `retweets_of_status_id:` | Renvoie les republications de publications spécifiques | `retweets_of_status_id:1234567890123456789` |
| `in_reply_to_status_id:` | Renvoie les réponses à des publications spécifiques | `in_reply_to_status_id:1234567890123456789` |

<div id="non-field-operators">
  ### Opérateurs non liés à un champ
</div>

<div id="special-syntax-operators">
  #### Opérateurs de syntaxe spéciale
</div>

| Opérateur | Résumé | Exemple |
|----------|--------|---------|
| `@` | Opérateur de mention | `@username` |
| Correspondance d&#39;expressions | Fait correspondre des expressions exactes | `"exact phrase"` |

<div id="logical-operators">
  #### Opérateurs logiques
</div>

| Opérateur | Description | Exemple |
|----------|-------------|---------|
| `OR` | OU logique entre expressions | `x OR facebook` |
| Space/AND | ET logique entre expressions | `x facebook` (les deux termes doivent être présents) |
| `()` | Regroupement pour des expressions complexes | `(x OR facebook) iphone` |
| `-` | Négation/exclusion | `x -facebook` (x mais pas facebook) |

<div id="limits-best-practices">
  ## Limites &amp; bonnes pratiques
</div>

* Limites de débit : 50 requêtes/24 h pour la gestion des règles ; aucune limite sur les flux (mais des limites de connexion s&#39;appliquent).
* Reconnexion : backoff exponentiel en cas de déconnexion.
* Monitoring : utilisez les en-têtes `Connection: keep-alive`.

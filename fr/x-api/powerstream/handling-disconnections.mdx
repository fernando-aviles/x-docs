<div id="what-is-a-disconnection">
  ## Qu’est-ce qu’une déconnexion ?
</div>

Établir une connexion aux API de streaming signifie effectuer une requête HTTPS de très longue durée et analyser la réponse de manière incrémentielle. Lors de la connexion au endpoint `powerstream`, vous devez envoyer une requête HTTPS et consommer le flux résultant aussi longtemps que possible. Nos serveurs maintiendront la connexion ouverte indéfiniment, sauf en cas d’erreur côté serveur, de latence excessive côté client, de problèmes réseau, de maintenance serveur courante ou de connexions en double. Avec les connexions aux endpoints de streaming, il est probable, et il faut s’y attendre, que des déconnexions se produisent et qu’une logique de reconnexion soit mise en place.

<div id="why-a-streaming-connection-might-be-disconnected">
  ## Pourquoi une connexion de streaming peut être interrompue
</div>

Votre flux peut être interrompu pour plusieurs raisons. Examinez le message d’erreur renvoyé par le flux pour comprendre la cause de l’échec. Les raisons possibles de déconnexion sont les suivantes :

* Une erreur d’authentification (par exemple, un jeton incorrect ou une mauvaise méthode d’authentification utilisée).
* Un serveur de streaming est redémarré du côté de X. Cela est généralement lié à un déploiement de code et doit être considéré comme un événement attendu et pris en compte dans la conception de votre intégration.
* Votre client ne parvient pas à suivre le volume de Publications que le flux délivre ou lit les données trop lentement. Chaque connexion de streaming est soutenue par une file d’attente de messages à envoyer au client. Si cette file d’attente devient trop grande au fil du temps, la connexion sera fermée.
* Votre compte a dépassé votre quota quotidien/mensuel de Publications.
* Vous avez trop de connexions redondantes actives.
* Un client cesse soudainement de lire les données. Si le taux de Publications lues à partir du flux chute soudainement, la connexion sera fermée.
* D’éventuels problèmes réseau entre le serveur et le client.
* Un problème temporaire côté serveur, une opération de maintenance ou des mises à jour planifiées. (Consultez la [page de statut](/fr/status))

<div id="anticipating-disconnects-and-reconnecting">
  ## Anticiper les déconnexions et se reconnecter
</div>

Lorsque vous diffusez un flux de Publications, l’objectif est de rester connecté le plus longtemps possible, en gardant à l’esprit que des déconnexions peuvent survenir. Le point de terminaison fournit un signal de maintien en vie (keep-alive/heartbeat) toutes les 20 secondes (il se présente sous la forme d’un caractère de saut de ligne). Utilisez ce signal pour détecter si vous êtes sur le point d’être déconnecté.

1. Votre code doit détecter quand le contenu récent et le signal de maintien de connexion cessent d’arriver.
2. Si cela se produit, votre code doit déclencher une logique de reconnexion. Certains clients et certains langages vous permettent de spécifier un délai d’expiration de lecture (read timeout), que vous pouvez définir à 20 secondes.
3. Votre service doit détecter ces déconnexions et se reconnecter dès que possible.

Une fois qu’une connexion établie est interrompue, tentez de vous reconnecter immédiatement. Si la reconnexion échoue, ralentissez vos tentatives de reconnexion en fonction du type d’erreur rencontré :

* Appliquez un backoff linéaire pour les erreurs réseau au niveau TCP/IP. Ces problèmes sont généralement temporaires et ont tendance à se résoudre rapidement. Augmentez le délai entre les reconnexions de 250 ms à chaque tentative, jusqu’à 16 secondes.
* Appliquez un backoff exponentiel pour les erreurs HTTP pour lesquelles une reconnexion serait appropriée. Commencez avec une attente de 5 secondes, en la doublant à chaque tentative, jusqu’à 320 secondes.
* Appliquez un backoff exponentiel pour les erreurs HTTP 429 (dépassement de la limite de débit). Commencez avec une attente de 1 minute et doublez-la à chaque tentative. Notez que chaque HTTP 429 reçu augmente la durée pendant laquelle vous devez attendre avant que la limitation de débit ne soit plus appliquée à votre compte.
   

<div id="recovering-lost-data">
  ## Récupération des données perdues
</div>

En cas de déconnexion, vous pouvez utiliser différentes stratégies pour vous assurer de recevoir toutes les données dont vous avez pu être privé. Nous avons documenté quelques étapes clés que vous pouvez suivre pour récupérer les données manquées dans notre guide d’intégration consacré à la [récupération des données](/fr/x-api/powerstream/recovery-and-redundancy). 
 

<div id="rate-limits-and-usage">
  ## Limites de débit et utilisation
</div>

Pour vérifier les limites de connexion, la réponse renverra trois en-têtes. Cela est utile pour comprendre combien de fois vous pouvez utiliser l’endpoint des règles, et combien de tentatives de reconnexion sont autorisées pour l’endpoint de streaming.

* x-rate-limit-limit indique le nombre de requêtes autorisées que votre client peut effectuer pendant la fenêtre de 15 minutes.

* x-rate-limit-remaining indique le nombre de requêtes effectuées jusqu’à présent dans la fenêtre de 15 minutes.

* x-rate-limit-reset est un horodatage UNIX indiquant le moment où la fenêtre de 15 minutes redémarrera, réinitialisant x-rate-limit-remaining à 0.

L’endpoint de flux filtré ne signale actuellement pas les données d’utilisation. Pour vérifier combien de Publications ont été délivrées, votre code peut implémenter une logique de mesure, afin que la consommation puisse être mesurée et mise en pause si nécessaire. 

Le code qui héberge le côté client du flux insère simplement les Publications entrantes dans une file d’attente de type « first in, first out » (FIFO), ou une structure mémoire similaire ; un processus ou thread distinct doit consommer les Publications depuis cette file d’attente pour analyser et préparer le contenu pour le stockage. Avec cette architecture, vous pouvez implémenter un service qui peut s’adapter efficacement si les volumes de Publications entrantes changent de manière significative. Conceptuellement, vous pouvez considérer cela comme le téléchargement d’un fichier infiniment long via HTTP.

<div id="reconnection-best-practices">
  ## Bonnes pratiques de reconnexion
</div>

<div id="test-backoff-strategies">
  ### Tester les stratégies de backoff
</div>

Une bonne façon de tester une implémentation de backoff consiste à utiliser des identifiants d’authentification non valides et à examiner les tentatives de reconnexion. Une bonne implémentation ne doit recevoir aucune réponse 429.

<div id="issue-alerts-for-multiple-reconnects">
  ### Alertes en cas de reconnexions répétées
</div>

Si un client atteint la limite supérieure de l’intervalle entre ses reconnexions, il doit vous envoyer des notifications afin que vous puissiez identifier et traiter les problèmes affectant votre connexion.

<div id="handle-dns-changes">
  ### Gérer les changements DNS
</div>

Vérifiez que le processus client respecte la durée de vie (TTL) du DNS. Certains environnements mettront en cache une adresse résolue pendant toute la durée de vie du processus et ne prendront pas en compte les changements DNS pendant le TTL prescrit. Un mécanisme de mise en cache aussi agressif entraînera des interruptions de service pour votre client lorsque X répartira la charge entre différentes adresses IP.

<div id="user-agent">
  ### Agent utilisateur
</div>

Assurez-vous que votre en-tête HTTP `user-agent` inclut la version de votre client. Cela est essentiel pour diagnostiquer les problèmes du côté de X. Si votre environnement ne permet pas de définir le champ `user-agent`, définissez alors un en-tête `x-user-agent`.

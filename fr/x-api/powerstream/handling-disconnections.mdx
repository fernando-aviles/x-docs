<div id="what-is-a-disconnection">
  ## Qu&#39;est-ce qu&#39;une déconnexion ?
</div>

Établir une connexion aux API de streaming consiste à effectuer une requête HTTPS de très longue durée et à analyser la réponse de manière incrémentale. Lors de la connexion à l&#39;endpoint powerstream, vous devez effectuer une requête HTTPS et consommer le flux résultant aussi longtemps que cela reste praticable. Nos serveurs maintiendront la connexion ouverte indéfiniment, sauf en cas d&#39;erreur côté serveur, de latence excessive côté client, de problèmes réseau, de maintenance serveur planifiée ou de connexions en double. Avec les connexions aux endpoints de streaming, il est probable — et il faut s&#39;y attendre — que des déconnexions se produisent et qu&#39;un mécanisme de reconnexion soit mis en place.

<div id="why-a-streaming-connection-might-be-disconnected">
  ## Pourquoi une connexion de streaming peut être interrompue
</div>

Votre flux peut se déconnecter pour plusieurs raisons. Inspectez le message d’erreur renvoyé par le flux pour en comprendre la cause. Les causes possibles de déconnexion sont les suivantes :

* Une erreur d’authentification (par exemple, un mauvais jeton ou une mauvaise méthode d’authentification utilisée).
* Un serveur de streaming est redémarré côté X. Cela est généralement lié à un déploiement de code et doit être anticipé et pris en compte dans la conception.
* Votre client ne suit pas le volume de Publications que le flux délivre ou lit les données trop lentement. Chaque connexion de streaming est adossée à une file d’attente de messages à envoyer au client. Si cette file devient trop volumineuse au fil du temps, la connexion sera fermée.
* Votre compte a dépassé son quota quotidien/mensuel de Publications.
* Vous avez trop de connexions redondantes actives simultanément.
* Un client cesse soudainement de lire les données. Si le taux de Publications lues à partir du flux chute brutalement, la connexion sera fermée.
* D’éventuels problèmes réseau entre le serveur et le client.
* Un problème temporaire côté serveur, une maintenance ou des mises à jour planifiées. (Consultez la [page de statut](/fr/status))

<div id="anticipating-disconnects-and-reconnecting">
  ## Anticiper les déconnexions et se reconnecter
</div>

Lors du streaming de Publications, l’objectif est de rester connecté aussi longtemps que possible, en gardant à l’esprit que des déconnexions peuvent se produire. Le point de terminaison fournit un signal de maintien de connexion (« keep alive ») toutes les 20 secondes (il se présente sous la forme d’un caractère de saut de ligne). Utilisez ce signal pour détecter si vous êtes en cours de déconnexion.

1. Votre code doit détecter lorsque l’arrivée de nouveau contenu et du signal de maintien de connexion s’arrête.
2. Si cela se produit, votre code doit déclencher une logique de reconnexion. Certains clients et certains langages vous permettent de spécifier un délai d’expiration de lecture (« read timeout »), que vous pouvez définir à 20 secondes.
3. Votre service doit détecter ces déconnexions et se reconnecter dès que possible.

Une fois qu’une connexion établie est interrompue, tentez de vous reconnecter immédiatement. Si la reconnexion échoue, ralentissez vos tentatives de reconnexion en fonction du type d’erreur rencontré :

* Augmentez l’intervalle entre les tentatives de reconnexion de manière linéaire pour les erreurs réseau au niveau TCP/IP. Ces problèmes sont généralement temporaires et ont tendance à se résoudre rapidement. Augmentez le délai entre les reconnexions de 250 ms à chaque tentative, jusqu’à 16 secondes.
* Augmentez l’intervalle entre les tentatives de reconnexion de manière exponentielle pour les erreurs HTTP pour lesquelles une reconnexion serait appropriée. Commencez par une attente de 5 secondes, en la doublant à chaque tentative, jusqu’à 320 secondes.
* Augmentez l’intervalle entre les tentatives de reconnexion de manière exponentielle pour les erreurs HTTP 429 (dépassement de la limite de fréquence). Commencez par une attente de 1 minute et doublez-la à chaque tentative. Notez que chaque HTTP 429 reçu augmente la durée pendant laquelle vous devez attendre avant que la limitation de fréquence ne soit plus appliquée à votre compte.
   

<div id="recovering-lost-data">
  ## Récupération des données perdues
</div>

En cas de déconnexion, vous pouvez appliquer différentes stratégies pour vous assurer de recevoir l’intégralité des données que vous auriez pu manquer. Nous avons décrit les principales étapes à suivre pour récupérer les données manquées dans notre guide d’intégration consacré à la [récupération des données](/fr/x-api/powerstream/recovery-and-redundancy). 
 

<div id="rate-limits-and-usage">
  ## Limites de débit et utilisation
</div>

Pour vérifier les limites de connexion, la réponse renverra trois en-têtes. Cela est utile pour comprendre combien de fois vous pouvez utiliser l&#39;endpoint des règles et combien de tentatives de reconnexion sont autorisées pour l&#39;endpoint de streaming.

* x-rate-limit-limit indique le nombre de requêtes autorisées que votre client peut effectuer pendant la fenêtre de 15 minutes.

* x-rate-limit-remaining indique le nombre de requêtes déjà effectuées pendant la fenêtre de 15 minutes.

* x-rate-limit-reset est un horodatage UNIX indiquant le moment où la fenêtre de 15 minutes redémarrera, réinitialisant x-rate-limit-remaining à 0.

L&#39;endpoint de flux filtré ne signale actuellement pas les données d&#39;utilisation. Pour vérifier combien de Publications ont été livrées, votre code peut implémenter une logique de mesure, afin que la consommation puisse être mesurée et mise en pause si nécessaire. 

Le code qui héberge la partie cliente du flux insère simplement les Publications entrantes dans une file d&#39;attente de type premier entré, premier sorti (FIFO), ou une structure mémoire similaire ; un processus/thread séparé doit consommer les Publications depuis cette file pour analyser et préparer le contenu en vue de son stockage. Avec cette conception, vous pouvez implémenter un service qui peut monter en charge efficacement si les volumes de Publications entrantes changent de manière significative. Conceptuellement, vous pouvez considérer cela comme le téléchargement d&#39;un fichier infiniment long via HTTP.

<div id="reconnection-best-practices">
  ## Bonnes pratiques de reconnexion
</div>

<div id="test-backoff-strategies">
  ### Tester les stratégies de backoff
</div>

Une bonne façon de tester une implémentation de backoff consiste à utiliser des identifiants d’autorisation invalides et à examiner les tentatives de reconnexion. Une bonne implémentation ne doit recevoir aucune réponse 429.

<div id="issue-alerts-for-multiple-reconnects">
  ### Émettre des alertes en cas de reconnexions répétées
</div>

Si un client atteint la limite supérieure de l’intervalle entre les reconnexions, il doit vous envoyer des notifications pour vous permettre de prioriser les problèmes qui affectent votre connexion.

<div id="handle-dns-changes">
  ### Gérer les changements de DNS
</div>

Vérifiez que votre processus client respecte la durée de vie (TTL) du DNS. Certaines piles réseau mettront en cache une adresse résolue pendant toute la durée du processus et ne prendront pas en compte les changements de DNS dans le délai de TTL prescrit. Une telle mise en cache agressive entraînera des interruptions de service pour votre client lorsque X répartit la charge entre différentes adresses IP.

<div id="user-agent">
  ### Agent utilisateur
</div>

Assurez-vous que votre en-tête HTTP `User-Agent` inclut la version de votre client. Cela sera essentiel pour diagnostiquer les problèmes du côté de X. Si votre environnement ne permet pas de définir le champ `User-Agent`, définissez alors un en-tête `X-User-Agent`.

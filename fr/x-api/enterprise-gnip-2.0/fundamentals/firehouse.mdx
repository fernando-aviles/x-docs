> **Veuillez noter**
>
> Nous avons lancé un nouvel outil de conformité pour X API v2 appelé [batch compliance](/fr/x-api/compliance/batch-compliance). Ce nouvel outil vous permet d’importer de grands ensembles de données d’identifiants de Publication ou d’utilisateur afin d’obtenir leur statut de conformité, pour déterminer quelles données nécessitent une action afin de rendre vos ensembles de données conformes.

> De plus, batch compliance et le firehose de conformité ont été mis à jour pour prendre en charge les modifications de Publication. Pour le firehose de conformité, un nouvel événement &#39;tweet&#95;edit&#39; a été ajouté. Consultez la documentation [Compliance Data Objects](/fr/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects) pour plus de détails. Pour en savoir plus sur le fonctionnement des métadonnées de modification de Publication, consultez la page [Edit Posts fundamentals](/fr/x-api/fundamentals/edit-posts).

<div id="overview">
  ## Vue d’ensemble
</div>

`Enterprise`

L’une des valeurs fondamentales de X est de défendre et de respecter la voix de l’utilisateur. Cela inclut le respect de ses attentes et de son intention lorsqu’il supprime, modifie ou édite le contenu qu’il choisit de partager sur X. Nous estimons que cela est d’une importance cruciale pour la santé à long terme de l’une des plus grandes plateformes publiques d’information en temps réel au monde. X met des contrôles entre les mains de ses utilisateurs, en donnant à chacun la possibilité de gérer sa propre expérience sur X. Nous considérons que les entreprises qui reçoivent des données X ont la responsabilité de respecter les attentes et l’intention des utilisateurs finaux.

Pour plus d’informations sur les types d’événements de conformité possibles sur la plateforme X, consultez notre article [Respecter l’intention de l’utilisateur sur X](/fr/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter).

Tout développeur ou entreprise consommant des données X via une API a l’obligation de déployer tous les efforts raisonnables pour respecter les modifications apportées au contenu des utilisateurs. Cette obligation couvre les événements utilisateur tels que les suppressions, les modifications et les changements d’options de partage (par exemple, lorsque le contenu devient protégé ou retenu). Cela inclut également les cas où les utilisateurs éditent leurs Publications. Veuillez vous reporter aux formulations spécifiques de la [Developer Policy](https://developer.x.com/en/developer-terms/policy) et/ou de votre contrat X Data Agreement pour comprendre comment cette obligation affecte votre utilisation des données X.

X propose les solutions suivantes, qui fournissent des informations sur ces événements de conformité utilisateur et indiquent si une Publication ou un Utilisateur spécifique est publiquement disponible ou non. Un bref aperçu de ces solutions et de leurs modèles d’intégration généraux est présenté ci-dessous :

<div id="get-statuseslookup-and-get-userslookup">
  #### GET statuses/lookup et GET users/lookup
</div>

* Format : API REST. Voir : [GET statuses/lookup](https://developer.x.com/en/docs/x-api/v1/tweets/post-and-engage/api-reference/get-statuses-lookup) et [GET users/lookup](https://developer.x.com/en/docs/x-api/v1/accounts-and-users/follow-search-get-users/api-reference/get-users-lookup).

* Ces endpoints renvoient toujours la dernière version de toute modification de Publication. Tous les objets Publication décrivant des Publications créées après l’introduction de la fonctionnalité de modification incluront des métadonnées de modification de Publication. Cela est vrai même pour les Publications qui n’ont pas été modifiées.

* Pour toutes les Publications, les requêtes portant sur des Publications effectuées plus de 30 minutes après leur création représenteront l’état final de toutes les Publications.

* Ces endpoints fournissent des informations de disponibilité pour des Publications ou des utilisateurs spécifiques, tels que définis par l’appelant dans la requête API.

* Ils peuvent être utilisés pour des contrôles ponctuels ad hoc de l’état de disponibilité actuel d’un groupe spécifique de Publications / utilisateurs.

* Ils sont idéaux pour les clients qui ont besoin d’un moyen de vérifier l’état actuel d’une Publication ou d’un utilisateur donné à un moment précis.

* Ces API fournissent un mécanisme utile que les clients peuvent utiliser pour vérifier la disponibilité d’un élément de contenu, par exemple lorsque :
  1. Afficher des Publications
  2. Interagir avec une ou plusieurs Publication(s) ou un ou plusieurs utilisateur(s) de manière 1:1
  3. Distribuer du contenu X à un tiers via un téléchargement de fichier autorisé
  4. Stocker des Publications pendant de longues périodes

<div id="compliance-firehose-enterprise-only">
  #### Compliance Firehose (entreprise uniquement)
</div>

* Format : API de streaming. Voir : [Compliance Firehose](/fr/x-api/enterprise-gnip-2.0/fundamentals/firehouse#api-reference).
* Fournit un flux en temps réel d&#39;[activités de conformité](/fr/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects) sur X, y compris lorsque des Publications sont modifiées. 
* Peut être utilisé pour maintenir l’état de conformité d’un ensemble de données stockées au fur et à mesure que de nouveaux événements de conformité se produisent sur la plateforme.
* Idéal pour les clients qui consomment et stockent de grandes quantités de données X sur de longues périodes.

  ### **Bonnes pratiques en matière de conformité**

<div id="recommendations-best-practices">
  #### **Recommandations et bonnes pratiques**
</div>

* **Créer des schémas de stockage de données qui enregistrent l’ID numérique de Publication et l’ID d’utilisateur** : les messages d’un utilisateur nécessitent d’agir sur toutes les Publications de cet utilisateur. Par conséquent, étant donné que tous les messages de conformité sont délivrés uniquement par ID numérique, il est important de concevoir des schémas de stockage qui maintiennent la relation entre la Publication et l’utilisateur sur la base des IDs numériques. Les consommateurs de données devront surveiller les événements de conformité à la fois par ID de Publication et par ID d’utilisateur et être en mesure de mettre à jour le magasin de données local de manière appropriée.

* **Créer des schémas qui prennent en compte tous les statuts de conformité** : selon la manière dont les activités de conformité seront traitées dans les différentes applications, il peut être nécessaire d’ajouter d’autres métadonnées au magasin de données. Par exemple, les consommateurs de données peuvent décider d’ajouter des métadonnées à une base de données existante pour faciliter la restriction de l’affichage de contenu dans les pays concernés par un message `status_withheld`.

* **Gestion des suppressions de Retweets** : les Retweets sont un type particulier de Publication dans lequel le message original est imbriqué dans un objet au sein du Retweet. Dans ce cas, deux IDs de Publication sont présents dans un Retweet : l’ID du Retweet et l’ID du message original (inclus dans l’objet imbriqué). Lorsqu’un message original est supprimé, un message de suppression de Publication est émis pour l’ID original. Les événements de suppression de Publication déclenchent généralement des événements de suppression pour tous les Retweets. Cependant, dans certains cas, ils ne sont pas tous envoyés et les systèmes clients doivent tolérer des suppressions de Retweets incomplètes. La suppression de l’ID original devrait suffire à supprimer tous les Retweets qui en découlent. Il est recommandé, comme bonne pratique, de référencer l’ID de Publication original lors du stockage des Retweets et de supprimer tous les Retweets ainsi référencés lors de la réception d’événements de suppression de Publication.

<div id="integrating-compliance-firehose">
  ### Intégration de Compliance Firehose
</div>

Compliance Firehose est une API de streaming en temps réel qui fournit les événements de conformité se produisant sur la plateforme X. Pour comprendre les événements de conformité et la manière dont ils sont générés sur X, veuillez consulter notre article : [Honoring User Intent on X](/fr/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter).

Il est important de noter que les événements de Publication et d’utilisateur sont envoyés indépendamment et que chacun doit être traité indépendamment (c’est‑à‑dire qu’une suppression de Publication n’implique pas un événement d’utilisateur, et inversement). Plusieurs événements d’utilisateur ne sont pas nécessairement permanents et peuvent basculer entre des états indéfiniment. Ceux‑ci incluent : user&#95;delete, user&#95;undelete, user&#95;protect, user&#95;unprotect et user&#95;suspend, user&#95;unsuspend.

Les user&#95;deletes sont suivis de status&#95;deletes 30 jours plus tard uniquement si l’utilisateur n’a pas choisi d’effectuer un user&#95;undelete de son compte. Il est possible qu’un user&#95;delete soit annulé par l’utilisateur et que les suppressions de toutes ses Publications 30 jours plus tard n’aient alors pas lieu.

user&#95;suspend est une action qui reste vraie sauf si l’utilisateur est soumis à un événement user&#95;unsuspend. Ceux‑ci ne sont soumis à aucun changement sur une période de 30 jours.

Il n’est jamais approprié d’afficher les événements de conformité directement aux utilisateurs de votre logiciel ni de les intégrer d’une quelconque autre manière dans vos produits ou expériences client. Ils sont exclusivement destinés à assurer la conformité et à respecter les actions des utilisateurs de X.

<div id="integrating-with-the-compliance-firehose">
  #### **Intégration avec le Compliance Firehose**
</div>

Pour intégrer le Compliance Firehose à votre système, vous devrez créer une intégration capable de réaliser les opérations suivantes :

1. Établir une connexion de streaming vers chaque partition d’API de streaming du Compliance Firehose
2. Gérer des volumes de données élevés – découpler l’ingestion du flux du traitement supplémentaire au moyen de processus asynchrones
3. Se reconnecter automatiquement aux partitions de flux lorsqu’une déconnexion survient pour quelque raison que ce soit
4. Traiter les événements de conformité pertinents pour les données de Publication et d’Utilisateur que vous avez stockées, conformément aux recommandations présentées ci-dessus

<div id="honoring-user-intent-on-twitter">
  ### Respecter l’intention des utilisateurs sur Twitter
</div>

Nous pensons que le respect de la vie privée et de l’intention des utilisateurs de X est d’une importance cruciale pour la santé à long terme de l’une des plus grandes plateformes publiques d’information en temps réel au monde. X met les contrôles de confidentialité entre les mains de ses utilisateurs, en donnant à chacun la possibilité de contrôler sa propre expérience sur X. En tant qu’entreprises qui consomment les données de X, nous avons la responsabilité collective de respecter la vie privée et les actions des utilisateurs finaux afin de préserver cet environnement de confiance et de respect.

Différentes choses peuvent arriver aux Publications et aux comptes utilisateur qui influent sur la façon dont ils sont affichés sur la plateforme. Les actions qui affectent la confidentialité et l’intention sont définies à la fois au niveau du Status (Publication) et au niveau User. Ces actions comprennent notamment :

<div id="user">
  #### Utilisateur
</div>

| Action | Description |
| :--- | :--- |
| Protéger le compte | Un utilisateur X peut protéger ou retirer la protection de son compte à tout moment. Les comptes protégés nécessitent l’approbation manuelle par l’utilisateur de chaque personne autorisée à voir les Publications de son compte.   <br />Pour plus d’informations, voir [À propos des Publications publiques et protégées](https://support.x.com/articles/14016-about-public-and-protected-tweets). |
| Supprimer le compte | Un utilisateur X peut décider de supprimer son compte et tous les messages de statut associés à tout moment. X conserve les informations du compte pendant 30 jours après la suppression, au cas où l’utilisateur déciderait d’annuler la suppression et de réactiver son compte. |
| Supprimer les données de géolocalisation | Un utilisateur X peut supprimer toutes les données de localisation de ses Publications passées à tout moment. Ce mécanisme est appelé « scrub geo ». |
| Suspendre le compte | X se réserve le droit de suspendre les comptes qui enfreignent les Règles de X ou si un compte est suspecté d’avoir été piraté ou compromis. Les suspensions de compte ne peuvent être levées (réactivation) que par X. |
| Restreindre le compte dans un pays | X se réserve le droit de restreindre de façon réactive l’accès à certains contenus dans un pays spécifique, de temps à autre. Seul X peut lever la restriction d’un compte.   <br />Pour plus d’informations, voir [Contenu restreint dans un pays](https://support.x.com/articles/20169222-country-withheld-content). |

<div id="status">
  #### Statut
</div>

| Action | Description |
| :--- | :--- |
| Supprimer un statut | Un utilisateur X peut supprimer un statut à tout moment. Les statuts supprimés ne peuvent pas être restaurés et sont définitivement supprimés. |
| Retenir un statut | X se réserve le droit de restreindre de manière réactive l’accès à certains contenus dans un pays donné, ponctuellement. Un statut retenu ne peut être de nouveau rendu accessible que par X.   <br />Pour plus d’informations, consultez [Contenu bloqué par pays](https://support.x.com/articles/20169222-country-withheld-content). |

<div id="keeping-track-of-user-and-status-changes">
  #### Suivi des modifications d’utilisateur et de statut
</div>

L’état d’un User ou d’un Status peut changer à tout moment à la suite de l’une des actions ci‑dessus, ce qui influe sur la manière dont les consommateurs de données X doivent traiter la disponibilité et la confidentialité de l’ensemble du contenu associé. Lorsque ces actions se produisent, un message de conformité correspondant est envoyé pour indiquer que l’état d’un Status ou d’un User a changé.

**Example Curl Request**

L&#39;exemple de requête suivant est réalisé à l&#39;aide de cURL en ligne de commande :

```bash
curl --compressed -v -uexample@customer.com "https://gnip-stream.x.com/stream/compliance/accounts/:account_name/publishers/twitter/:stream_label.json?partition=1"
```

*Remarque :* la requête ci-dessus ne se connecte qu’à la firehose Compliance avec `partition=1` ; vous devrez vous connecter à l’ensemble des 8 partitions pour recevoir l’intégralité de ce flux.

<div id="response-codes">
  #### Codes de réponse
</div>

Les réponses suivantes peuvent être renvoyées par l&#39;API pour ces requêtes. La plupart des codes d&#39;erreur sont renvoyés avec une chaîne de caractères contenant des détails supplémentaires dans le corps de la réponse. Pour les réponses non 200, les clients doivent tenter de se reconnecter.

| Statut | Texte | Définition |
| :--- | :--- | :--- |
| 200 | Succès | La connexion a été ouverte avec succès et les nouvelles activités seront envoyées au fur et à mesure de leur arrivée. |
| 401 | Non autorisé | L&#39;authentification HTTP a échoué en raison d&#39;identifiants non valides. Connectez-vous à console.gnip.com avec vos identifiants pour vérifier que vous les utilisez correctement avec votre requête. |
| 406 | Non acceptable | En général, cela se produit lorsque votre client n&#39;inclut pas correctement les en-têtes nécessaires pour accepter l&#39;encodage gzip sur le flux, mais cela peut également se produire dans d&#39;autres circonstances. Contiendra un message JSON similaire à &quot;This connection requires compression. To enable compression, send an &#39;Accept-Encoding: gzip&#39; header in your request and be ready to uncompress the stream as it is read on the client end.&quot; |
| 429 | Limite de débit atteinte | Votre application a dépassé la limite de requêtes de connexion. |
| 503 | Service indisponible | Problème de serveur X. Reconnectez-vous en utilisant une stratégie de reconnexion avec backoff exponentiel. Si aucune notification concernant ce problème n&#39;a été publiée sur la [X API Status Page](https://api.twitterstat.us/), contactez l&#39;assistance. |

<div id="other-recommendations-best-practices">
  #### Autres recommandations et bonnes pratiques
</div>

* **Créer des schémas de stockage de données qui conservent l’ID numérique du Tweet et l’ID numérique de l’utilisateur** : les messages utilisateur nécessitent une action sur tous les Tweets de cet utilisateur. Par conséquent, puisque tous les messages de conformité ne sont transmis que par ID numérique, il est important de concevoir des schémas de stockage qui maintiennent la relation entre le Tweet et l’utilisateur sur la base de ces IDs numériques. Les consommateurs de données devront surveiller les événements de conformité à la fois par ID de Tweet et par ID d’utilisateur, et être en mesure de mettre à jour correctement le stockage de données local.

* **Créer des schémas qui couvrent tous les statuts de conformité** : selon la manière dont les activités de conformité seront gérées dans différentes applications, il peut être nécessaire d’ajouter d’autres métadonnées au stockage de données. Par exemple, les consommateurs de données peuvent décider d’ajouter des métadonnées à une base de données existante afin de faciliter la restriction de l’affichage du contenu dans les pays concernés par un message `status_withheld`.

* **Gérer les suppressions de Retweets** : les Retweets sont un type particulier de Tweet dans lequel le message d’origine est imbriqué dans un objet à l’intérieur du Retweet. Dans ce cas, deux IDs de Tweet sont référencés dans un Retweet : l’ID du Retweet et l’ID du message d’origine (inclus dans l’objet imbriqué). Lorsqu’un message d’origine est supprimé, un message de suppression de Tweet est émis pour l’ID d’origine. Des messages de suppression supplémentaires NE sont PAS émis pour tous les Retweets. La suppression de l’ID d’origine devrait suffire à supprimer tous les Retweets ultérieurs.

> **Veuillez noter**
>
> Nous avons lancé un nouvel outil de conformité pour X API v2 appelé [batch compliance](/fr/x-api/compliance/batch-compliance). Ce nouvel outil vous permet d’importer de grands ensembles de données d’ID de Publication ou d’utilisateur afin de récupérer leur statut de conformité et de déterminer quelles données nécessitent une action pour rendre vos jeux de données conformes.

> De plus, batch compliance et le firehose de conformité ont été mis à jour pour prendre en charge les modifications de Publications. Pour le firehose de conformité, un nouvel événement `tweet_edit` a été ajouté. Consultez la documentation [Compliance Data Objects](/fr/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects) pour plus de détails. Pour en savoir plus sur le fonctionnement des métadonnées liées à la modification de Publications, reportez-vous à la page [Principes de base des Publications modifiées](/fr/x-api/fundamentals/edit-posts).

<div id="overview">
  ## Vue d’ensemble
</div>

`Enterprise`

L’une des valeurs fondamentales de X est de défendre et de respecter la voix des utilisateurs. Cela inclut le respect de leurs attentes et de leur intention lorsqu’ils suppriment, modifient ou éditent le contenu qu’ils choisissent de partager sur X. Nous pensons que cela est d’une importance cruciale pour la santé à long terme de l’une des plus grandes plateformes publiques d’information en temps réel au monde. X place les contrôles entre les mains de ses utilisateurs, en donnant aux individus la possibilité de contrôler leur propre expérience sur X. Nous pensons que les clients professionnels qui reçoivent des données X ont la responsabilité de respecter les attentes et l’intention des utilisateurs finaux.

Pour plus d’informations sur les types d’événements de conformité possibles sur la plateforme X, consultez notre article : [Respecter l’intention des utilisateurs sur X](/fr/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter).

Tout développeur ou toute entreprise consommant des données X via une API a l’obligation de déployer tous les efforts raisonnables pour respecter les modifications apportées au contenu des utilisateurs. Cette obligation s’étend aux événements utilisateurs tels que les suppressions, les modifications et les changements d’options de partage (par exemple, lorsque le contenu devient protégé ou retenu). Cela inclut également les cas où les utilisateurs modifient leurs publications. Veuillez vous référer au libellé spécifique de la [Politique développeur](https://developer.x.com/en/developer-terms/policy) et/ou à votre contrat « X Data Agreement » pour comprendre comment cette obligation affecte votre utilisation des données X.

X propose les solutions suivantes, qui fournissent des informations sur ces événements de conformité des utilisateurs et indiquent si une publication ou un utilisateur spécifique est publiquement disponible ou non. Un bref aperçu des solutions et de leurs modèles d’intégration généraux est présenté ci-dessous :

<div id="get-statuseslookup-and-get-userslookup">
  #### GET statuses/lookup et GET users/lookup
</div>

* Format : API REST. Voir : [GET statuses/lookup](https://developer.x.com/en/docs/x-api/v1/tweets/post-and-engage/api-reference/get-statuses-lookup) et [GET users/lookup](https://developer.x.com/en/docs/x-api/v1/accounts-and-users/follow-search-get-users/api-reference/get-users-lookup).

* Ces endpoints retournent toujours la dernière version de toute modification de publication. Tous les objets Post décrivant des publications créées après l’introduction de la fonctionnalité de modification incluront les métadonnées de modification de publication. Cela est vrai même pour les publications qui n’ont pas été modifiées.

* Pour toutes les publications, toute requête portant sur des publications plus de 30 minutes après leur création représentera l’état final de ces publications. 

* Fournir des informations de disponibilité pour des publications ou des utilisateurs spécifiques, tels que définis par l’appelant dans le cadre de la requête API.

* Peut être utilisé pour des vérifications ponctuelles ad hoc de l’état de disponibilité actuel d’un groupe spécifique de publications/utilisateurs.

* Idéal pour les clients qui ont besoin d’un moyen de vérifier l’état actuel d’une publication ou d’un utilisateur spécifique à un moment donné.

* Ces API fournissent un mécanisme utile qui peut être utilisé par les clients qui doivent vérifier la disponibilité d’un élément de contenu, par exemple lorsqu’ils :
  1. Affichent des publications
  2. Interagissent avec une ou plusieurs publication(s) ou utilisateur(s) de manière 1:1
  3. Distribuent du contenu X à un tiers via un téléchargement de fichier autorisé
  4. Stockent des publications pendant de longues périodes

<div id="compliance-firehose-enterprise-only">
  #### Compliance Firehose (offre Enterprise uniquement)
</div>

* Format : API de streaming. Voir : [Compliance Firehose](/fr/x-api/enterprise-gnip-2.0/fundamentals/firehouse#api-reference).
* Diffuse en temps réel un flux d’[activités de conformité](/fr/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects) sur X, notamment les modifications de Publications. 
* Peut être utilisé pour maintenir l’état de conformité pour un ensemble de données stockées à mesure que de nouveaux événements de conformité surviennent sur la plateforme.
* Idéal pour les clients qui consomment et stockent de grandes quantités de données de X sur de longues périodes.

  ### **Bonnes pratiques en matière de conformité**

<div id="recommendations-best-practices">
  #### **Recommandations et bonnes pratiques**
</div>

* **Concevoir des schémas de stockage des données qui conservent l’ID numérique de Publication et l’ID d’utilisateur** : les messages d’un utilisateur nécessitent de prendre des mesures sur toutes les Publications de cet utilisateur. Par conséquent, comme tous les messages de conformité sont fournis uniquement par ID numérique, il est important de concevoir des schémas de stockage qui maintiennent la relation entre la Publication et l’utilisateur sur la base des ID numériques. Les consommateurs de données devront surveiller les événements de conformité à la fois par ID de Publication et par ID d’utilisateur et être en mesure de mettre à jour de façon appropriée le stockage local des données.

* **Concevoir des schémas qui prennent en compte tous les statuts de conformité** : en fonction de la manière dont les activités de conformité seront traitées dans les différentes applications, il peut être nécessaire d’ajouter d’autres métadonnées au stockage des données. Par exemple, les consommateurs de données peuvent décider d’ajouter des métadonnées à une base de données existante pour faciliter la restriction de l’affichage de contenu dans les pays affectés par un message status&#95;withheld.

* **Gestion des suppressions de Retweet** : les Retweets sont un type particulier de Publication où le message original est imbriqué dans un objet au sein du Retweet. Dans ce cas, deux ID de Publication sont référencés dans un Retweet : l’ID du Retweet et l’ID du message original (inclus dans l’objet imbriqué). Lorsqu’un message original est supprimé, un message de suppression de Publication est émis pour l’ID original. Les événements de suppression de Publication déclenchent généralement des événements de suppression pour tous les Retweets. Cependant, dans certains cas, tous ne sont pas nécessairement envoyés et les systèmes clients doivent tolérer des suppressions de Retweet incomplètes. La suppression de l’ID original doit suffire à supprimer tous les Retweets ultérieurs. Il est recommandé, comme bonne pratique, de référencer l’ID de Publication original lors du stockage des Retweets et de supprimer tous les Retweets qui y font référence lors de la réception d’événements de suppression de Publication.

<div id="compliance-firehose-api">
  #### **Compliance Firehose API**
</div>

Les types possibles d’événements de conformité comprennent des événements de Publication (ou « status ») et des événements d’utilisateur, pour lesquels plusieurs types sont décrits ci‑dessous.  

Veuillez noter :

* Pour en savoir plus sur les statuts d’utilisateur, consultez cet article [ici](https://support.x.com/articles/14016) ainsi que notre politique développeur concernant les Publications supprimées [ici](https://dev.x.com/overview/terms/policy#3.Update_Respect_Users_Control_and_Privacy).
* Le Compliance Firehose a été mis à jour pour fournir des événements `tweet_edit`. 
* Plusieurs événements de suppression, de protection et de suspension d’utilisateur ne sont pas nécessairement permanents et peuvent alterner entre différents états indéfiniment. Ces événements incluent : user&#95;delete, user&#95;undelete, user&#95;protect, user&#95;unprotect, user&#95;suspend et user&#95;unsuspend.
* Les événements user&#95;delete sont suivis de status&#95;deletes 30 jours plus tard uniquement si l’utilisateur n’a pas choisi d’effectuer un user&#95;undelete de son compte. Il est possible qu’un user&#95;delete soit annulé par l’utilisateur et que les suppressions de toutes ses Publications 30 jours plus tard ne se produisent pas.
* Un user&#95;suspend est une action qui reste vraie tant que l’utilisateur n’est pas soumis à un événement user&#95;unsuspend. Ces événements ne font l’objet d’aucune modification sur une période de 30 jours.

Reportez‑vous à la colonne « Action recommandée » pour comprendre comment traiter chaque type d’événement afin de respecter la confidentialité et l’intention de l’utilisateur final.

| Original Message Type | Object | Permanent (Yes/No) | Recommended Action |
| :--- | :--- | :--- | :--- |
| delete | Status | Yes | Supprimer la Publication associée. |

| user&#95;undelete | User | No  | Toutes les Publications de l’utilisateur associé peuvent de nouveau être affichées et considérées comme publiques. |
| user&#95;protect | User | No  | Masquer ou supprimer toutes les Publications de l’utilisateur associé. |

<div id="integrating-compliance-firehose">
  ### Intégration de Compliance Firehose
</div>

Le Compliance Firehose est une API de streaming en temps réel qui diffuse les événements de conformité se produisant sur la plateforme X. Pour comprendre les événements de conformité et la façon dont ils sont générés sur X, veuillez consulter notre article : [Respecter l’intention des utilisateurs sur X](/fr/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter).

Il est important de noter que les événements de Publication et d’utilisateur sont transmis indépendamment et que chacun doit être traité séparément (c’est‑à‑dire qu’une suppression de Publication n’implique pas un événement d’utilisateur, et inversement). Plusieurs événements utilisateur ne sont pas nécessairement permanents et peuvent basculer entre différents états indéfiniment. Ceux‑ci incluent : user&#95;delete, user&#95;undelete, user&#95;protect, user&#95;unprotect et user&#95;suspend, user&#95;unsuspend.

Les user&#95;deletes sont suivis de status&#95;deletes 30 jours plus tard uniquement si l’utilisateur n’a pas choisi d’effectuer un user&#95;undelete de son compte. Il est possible qu’un user&#95;delete soit annulé par l’utilisateur et que, par conséquent, les suppressions de toutes ses Publications 30 jours plus tard ne se produisent pas.

User&#95;suspend est une action qui reste valable, sauf si l’utilisateur fait l’objet d’un événement user&#95;unsuspend. Ces événements ne sont soumis à aucun changement sur une période de 30 jours.

Il n’est jamais approprié d’afficher directement des événements de conformité aux utilisateurs de votre logiciel ou de les intégrer d’une quelconque manière dans vos produits ou expériences client. Ils sont exclusivement destinés au maintien de la conformité et au respect des actions des utilisateurs de X.

<div id="integrating-with-the-compliance-firehose">
  #### **Intégrer Compliance Firehose**
</div>

Pour intégrer Compliance Firehose à votre système, vous devez créer une intégration capable de :

1. Établir une connexion en streaming à chaque partition de l’API de streaming Compliance Firehose
2. Gérer des volumes de données élevés – découpler l’ingestion du flux du traitement ultérieur en utilisant des processus asynchrones
3. Se reconnecter automatiquement aux partitions de flux en cas de déconnexion, quelle qu’en soit la raison
4. Traiter les événements de conformité relatifs aux données de Publication et d’utilisateur que vous avez stockées, conformément aux recommandations présentées ci-dessus

<div id="honoring-user-intent-on-twitter">
  ### Respecter l’intention des utilisateurs sur X
</div>

Nous pensons que le respect de la vie privée et de l’intention des utilisateurs de X est d’une importance capitale pour la santé à long terme de l’une des plus grandes plateformes publiques d’information en temps réel au monde. X met les contrôles de confidentialité entre les mains de ses utilisateurs, en donnant à chacun la possibilité de contrôler sa propre expérience sur X. En tant que clients professionnels qui consomment les données de X, nous avons la responsabilité collective de respecter la vie privée et les actions des utilisateurs finaux afin de préserver cet environnement de confiance et de respect.

Il peut arriver différentes choses aux Publications et aux comptes utilisateur, ce qui influe sur la façon dont ils sont affichés sur la plateforme. Les actions qui affectent la vie privée et l’intention sont définies à la fois au niveau du Statut (Publication) et au niveau de l’utilisateur. Ces actions incluent :

<div id="user">
  #### Utilisateur
</div>

| Action | Description |
| :--- | :--- |
| Protect Account | Un utilisateur X peut protéger ou retirer la protection de son compte à tout moment. Les comptes protégés nécessitent l’approbation manuelle, par l’utilisateur, de chaque personne autorisée à voir les Publications de son compte.   <br />Pour plus d’informations, voir [À propos des Publications publiques et protégées](https://support.x.com/articles/14016-about-public-and-protected-tweets). |
| Delete Account | Un utilisateur X peut décider de supprimer son compte et tous les messages de statut associés à tout moment. X conserve les informations du compte pendant 30 jours après la suppression au cas où l’utilisateur déciderait d’annuler la suppression et de réactiver son compte. |
| Scrub Geo | Un utilisateur X peut supprimer à tout moment toutes les données de localisation de ses Publications passées. Ce processus est appelé « scrub geo ». |
| Suspend Account | X se réserve le droit de suspendre les comptes qui enfreignent les Règles de X ou si un compte est soupçonné d’avoir été piraté ou compromis. Les suspensions de compte ne peuvent être levées (unsuspend) que par X. |
| Withhold Account | X se réserve le droit de restreindre de façon réactive l’accès à certains contenus dans un pays donné. Un compte restreint ne peut être à nouveau rendu accessible que par X.   <br />Pour plus d’informations, voir [Contenu restreint par pays](https://support.x.com/articles/20169222-country-withheld-content). |

<div id="status">
  #### Statut
</div>

| Action | Description |
| :--- | :--- |
| Supprimer un statut | Un utilisateur X peut supprimer un statut à tout moment. Les statuts supprimés ne peuvent pas être restaurés et sont définitivement supprimés. |
| Restreindre un statut | X se réserve le droit de restreindre de manière réactive l’accès à certains contenus dans un pays spécifique, de temps à autre. Un statut restreint ne peut être de nouveau rendu accessible que par X.   <br />Pour plus d’informations, consultez [Country Withheld Content](https://support.x.com/articles/20169222-country-withheld-content). |

<div id="keeping-track-of-user-and-status-changes">
  #### Suivi des changements d’utilisateurs et de statuts
</div>

L’état d’un utilisateur ou d’un statut peut changer à tout moment en raison de l’une des actions ci-dessus, ce qui affecte la manière dont les consommateurs des données de X doivent gérer la disponibilité et la confidentialité de tout le contenu associé. Lorsque ces actions se produisent, un message de conformité correspondant est envoyé pour indiquer que l’état d’un statut ou d’un utilisateur a changé.

Consultez la documentation [Compliance Data Objects](/fr/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects) pour plus de détails.                                                                                                                                                                                                                                                                                                                                                            |

**Exemple de requête cURL**

La requête d&#39;exemple suivante est effectuée à l&#39;aide de cURL en ligne de commande :

```bash
curl --compressed -v -uexample@customer.com "https://gnip-stream.x.com/stream/compliance/accounts/:account_name/publishers/twitter/:stream_label.json?partition=1"
```

*Remarque :* la requête ci-dessus ne se connecte qu’à la `partition=1` du firehose Compliance ; vous devrez vous connecter aux 8 partitions pour consommer l’intégralité de ce flux.

<div id="response-codes">
  #### Codes de réponse
</div>

Les réponses suivantes peuvent être renvoyées par l’API pour ces requêtes. La plupart des codes d’erreur sont renvoyés avec une chaîne de caractères contenant des détails supplémentaires dans le corps. Pour les réponses non 200, les clients doivent essayer de se reconnecter.

| Statut | Texte | Définition |
| :--- | :--- | :--- |
| 200 | Succès | La connexion a été ouverte avec succès et les nouvelles activités seront envoyées au fur et à mesure de leur arrivée. |
| 401 | Non autorisé | L’authentification HTTP a échoué en raison d’identifiants non valides. Connectez-vous à console.gnip.com avec vos identifiants pour vérifier que vous les utilisez correctement dans votre requête. |
| 406 | Non acceptable | En général, cela se produit lorsque votre client n’inclut pas correctement les en-têtes pour accepter l’encodage gzip pour le flux, mais cela peut également se produire dans d’autres circonstances. Contiendra un message JSON similaire à « Cette connexion nécessite une compression. Pour activer la compression, envoyez un en-tête &#39;Accept-Encoding: gzip&#39; dans votre requête et soyez prêt à décompresser le flux au fur et à mesure qu’il est lu côté client. » |
| 429 | Limitation de débit | Votre application a dépassé la limite de requêtes de connexion. |
| 503 | Service indisponible | Problème de serveur Twitter. Reconnectez-vous en utilisant une stratégie d’attente exponentielle. Si aucun avis concernant ce problème n’a été publié sur la [Page de statut X API](https://api.twitterstat.us/), contactez le support. |

<div id="other-recommendations-best-practices">
  #### Autres recommandations et bonnes pratiques
</div>

* **Concevoir des schémas de stockage de données qui stockent l’ID numérique du Tweet et l’ID numérique de l’utilisateur** : les messages relatifs aux utilisateurs nécessitent une action sur tous les Tweets de cet utilisateur. Par conséquent, puisque tous les messages de conformité sont délivrés uniquement par ID numérique, il est important de concevoir des schémas de stockage qui maintiennent la relation entre le Tweet et l’utilisateur sur la base de leurs ID numériques. Les consommateurs de données devront surveiller les événements de conformité à la fois par ID de Tweet et par ID d’utilisateur et être en mesure de mettre à jour correctement le data store local.

* **Concevoir des schémas qui prennent en compte tous les statuts de conformité** : selon la manière dont les activités de conformité seront gérées dans les différentes applications, il peut être nécessaire d’ajouter d’autres métadonnées au data store. Par exemple, les consommateurs de données peuvent décider d’ajouter des métadonnées à une base de données existante pour faciliter la restriction de l’affichage de contenu dans les pays affectés par un message status&#95;withheld.

* **Gérer les suppressions de Retweets** : les Retweets sont un type particulier de Tweet dans lequel le message d’origine est imbriqué dans un objet au sein du Retweet. Dans ce cas, deux ID de Tweet sont référencés dans un Retweet : l’ID du Retweet et l’ID du message d’origine (inclus dans l’objet imbriqué). Lorsqu’un message d’origine est supprimé, un message de suppression de Tweet est émis pour l’ID d’origine. Des messages de suppression supplémentaires NE SONT PAS émis pour tous les Retweets. La suppression de l’ID d’origine doit suffire à supprimer tous les Retweets associés.

<div id="overview">
  ## Vue d’ensemble
</div>

[`Enterprise`](https://developer.x.com/en/products/x-api/enterprise)

*Ceci est une API Enterprise, disponible uniquement dans le cadre de nos niveaux d’accès gérés. Pour utiliser cette API, vous devez d’abord créer un compte auprès de notre équipe commerciale Enterprise. [En savoir plus](/fr/x-api/enterprise-gnip-2.0/enterprise-gnip)*

L’Engagement API donne accès aux métriques d’impressions et d’engagement des Publications. Alors que la plupart des métriques et des points de terminaison nécessitent une authentification via [OAuth 1.0a User Context](/fr/resources/fundamentals/authentication), vous pouvez accéder aux métriques publiques Favorite, Retweet, Reply et Video Views en utilisant [OAuth 2.0 Bearer Token](/fr/resources/fundamentals/authentication#oauth-2-0) et le point de terminaison /totals.  

**Remarque :** vous pouvez constater des différences entre les données affichées sur certains tableaux de bord web de X et les données fournies par l’Engagement API. Ces différences surviennent parce que les tableaux de bord web affichent généralement uniquement les engagements et/ou impressions qui se sont produits dans l’intervalle de temps sélectionné. Par exemple, un tableau de bord web peut afficher l’engagement sur des Publications sur la durée d’un mois calendaire, tandis que l’Engagement API peut indiquer des engagements qui dépassent la durée de ce mois mais restent dans l’intervalle de temps demandé. Dans ces cas, l’Engagement API doit être considérée comme la source faisant autorité.
 

<div id="request-endpoints">
  ### Points de terminaison des requêtes
</div>

L’API Engagement comprend trois points de terminaison :

<div id="current-totals-totals">
  #### Totaux actuels : [/totals]
</div>

* Les requêtes renvoient une mesure totale pour les impressions et une mesure totale pour les engagements pour les Publications concernées
* Limité aux métriques suivantes : Impressions, Engagements, Favoris, Réponses, Retweets, Tweets cités et Vues de vidéo
* Prend en charge la récupération des métriques **Impressions** et **Engagements** pour les Publications créées **au cours des 90 derniers jours** à l’aide d’OAuth 1.0a User Context
* Prend en charge la récupération des métriques **Favoris, Retweets, Tweets cités, Réponses** et **Vues de vidéo** pour **toute Publication** à l’aide d’un Bearer Token OAuth 2.0
* Les résultats sont basés sur le total actuel des impressions et des engagements au moment où la requête est effectuée
* Idéal pour alimenter un tableau de bord et pour calculer les taux d’engagement sur une variété de @handles
* Permet de demander des métriques pour jusqu’à 250 Publications par requête
   

<div id="last-28-hours-28hr">
  #### 28 dernières heures : [/28hr]
</div>

* Les requêtes peuvent renvoyer une métrique totale pour les impressions, une métrique totale pour les engagements, ainsi qu’une ventilation des différentes métriques d’engagement individuelles survenues au cours des 28 dernières heures
* Les data peuvent être regroupées par ID de Publication, et sous forme de séries chronologiques agrégées, par jour ou par heure
* Idéal pour suivre les performances du contenu récemment créé
* Prend en charge toutes les métriques disponibles
* Permet de demander des métriques pour jusqu’à 25 Publications par requête
   

<div id="historical-historical">
  #### Historique : [/historical]
</div>

* Les requêtes peuvent renvoyer les impressions, les interactions et une répartition des différents indicateurs d’interaction pour l’année écoulée, sur la base de l’heure de l’interaction (et non de l’heure de création de la Publication).
* Les requêtes acceptent des paramètres de date de début et de date de fin, offrant la flexibilité de se concentrer sur une période spécifique d’une durée maximale de 4 semaines.
* Les données d’interaction avec les Publications sont limitées aux 365 derniers jours.
* Les données peuvent être regroupées par ID de Publication et, en séries temporelles agrégées, par jour ou par heure.
* Idéal pour évaluer les performances récentes par rapport à une référence historique ou pour construire une vue historique des performances d’un @handle.
* Prend en charge tous les indicateurs disponibles.
* Prend en charge les demandes d’indicateurs pour jusqu’à 25 Publications par requête.

<div id="engagement-groupings">
  ### Regroupements d&#39;engagement
</div>

Les regroupements permettent d&#39;organiser de manière personnalisée les métriques d&#39;engagement renvoyées. Vous pouvez inclure au maximum 3 regroupements par requête. Vous pouvez choisir de regrouper les métriques selon une ou plusieurs des valeurs suivantes :

*Les trois endpoints prennent en charge :*

* tweet.id
* engagement.type
   

*Les endpoints `/28hr` et `/historical` peuvent fournir des métriques sous forme de séries temporelles et prennent donc en charge :*

* engagement.day
* engagement.hour

Pour en savoir plus sur les regroupements, consultez la page [Engagement API Grouping](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings) dans la rubrique Guides.

<div id="introduction">
  #### Introduction
</div>

L’objectif de cette documentation est de fournir aux développeurs une introduction sur l’intégration à l’Engagement API. Nous commencerons par expliquer les raisons d’intégrer cette API, puis nous approfondirons les aspects techniques de sa mise en œuvre.

<div id="what-does-the-engagement-api-provide">
  ##### **Que fournit l’Engagement API ?**
</div>

* L’Engagement API fournit des données d’impressions et d’engagement pour toutes les Publications appartenant à un compte X au cours des 90 derniers jours, à condition que ce compte ait autorisé votre application à demander des métriques en son nom à l’aide de [3-legged OAuth](/fr/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow). Cette solution puissante, mais facile à mettre en œuvre, donne un accès immédiat aux impressions et aux engagements détaillés, tels que les clics sur les URL, les clics sur les hashtags (#) et bien d’autres.
* L’Engagement API fournit des métriques agrégées totales pour les favoris, les Retweets, les Tweets cités, les réponses et les vues vidéo pour toute Publication. Cela peut être utilisé comme un moyen efficace d’obtenir des données d’engagement de base sur n’importe quelle Publication ou collection de Publications.
* L’Engagement API apporte une nouvelle valeur aux plateformes d’écoute sociale, de marketing et de publication en permettant aux clients de mesurer le retour sur investissement (ROI) sur X en évaluant efficacement les performances du contenu à l’aide de plus de 15 indicateurs de performance.
* L’Engagement API est une API de requête/réponse qui permet aux développeurs d’applications d’envoyer des requêtes avec des identifiants de Publication (Post IDs), les métriques souhaitées et une plage temporelle, pour lesquelles l’API renvoie immédiatement les données.
   

<div id="why-integrate-example-use-cases">
  ##### **Pourquoi intégrer ? Exemples de cas d’usage**
</div>

* Comprendre la portée totale de mon contenu pour voir combien de personnes le consultent. Voir combien de personnes regardent des vidéos, cliquent sur des liens, cliquent sur des hashtags ou installent mes applications.
* Générer à la fois des métriques d’engagement totales et des séries temporelles.
* Comprendre les métriques d’engagement de base (ajouts aux favoris, Retweets, Quote Tweets, réponses) pour n’importe quelle Publication publique.
* Utiliser ces métriques pour déterminer quels types de Publications fonctionnent, afin que je puisse les publier plus souvent et obtenir davantage d’impressions et d’engagement sur mon contenu.
* Automatiser des actions marketing (comme retweeter du contenu depuis un autre compte que je possède) chaque fois qu’une de mes Publications atteint 100 Likes, ou un autre seuil.
* Évaluer et comparer mes campagnes entre elles comme outil de test A/B.
* Analyser quels types de contenus fonctionnent pour mon service client afin de déterminer comment et quand répondre.
* Afficher des statistiques pour le contenu publié depuis ma plateforme.
   

[L’Engagement API a été lancée en 2016](https://blog.x.com/official/en_us/a/2016/gnip-s-engagement-api-is-now-generally-available.html) et a été la première X API à fournir ces métriques d’engagement détaillées à grande échelle. L’Engagement API est simple à utiliser et permet aux clients d’automatiser ces processus. Voici une étude de cas décrivant un exemple d’intégration :

* [Mesurer le succès d’une campagne avec la Croix-Rouge](https://blog.x.com/developer/en_us/topics/spotlight/2016/measuring-campaign-success-with-the-red-cross.html)[](https://simplymeasured.com/blog/true-twitter-impressions-and-url-clicks-new-from-simply-measured/#sm.0007werel134td8zqf02m2mduumr6)

Maintenant que nous avons exploré les raisons d’utiliser l’Engagement API, commençons à entrer dans les détails techniques.

<div id="integrating-the-engagement-api">
  #### Intégration de l’API Engagement
</div>

<div id="introduction-to-api">
  ##### **Introduction à l’API**
</div>

L’Engagement API est une API RESTful simple qui reçoit des requêtes encodées en JSON et renvoie des métriques d’engagement encodées en JSON. Les requêtes se composent de trois parties principales (reportez-vous aux liens pour plus de documentation) :

* Tableau d’***ID de Publications***.
* Tableau spécifiant les [types de métriques](https://developer.x.com/en/docs/x-api/v1/metrics/get-tweet-engagement/overview#EngagementTypes) qui vous intéressent. Les types incluent des éléments tels que « impressions », « retweets », « hashtag&#95;clicks » et « user&#95;follows ».
* [Engagement groupings](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings), qui est une structure JSON indiquant la façon dont vous souhaitez que les données d’engagement soient organisées dans la réponse de l’API.

Dans de nombreux cas, les Engagement Types et Groupings restent relativement constants d’une requête à l’autre, seuls les ID de Publications étant mis à jour.

L’Engagement API propose [trois endpoints](https://developer.x.com/en/docs/x-api/v1/metrics/get-tweet-engagement/overview#RequestEndpoints) :

* **Totals** - Fournit des totaux globaux des engagements pour les Publications. Certaines métriques sont disponibles pour toutes les Publications, tandis que d’autres ne sont disponibles que pour les 90 derniers jours.
* **28 hour** - Fournit des métriques d’engagement sous forme de séries temporelles pour les 28 dernières heures.
* **Historical** - Fournit des métriques d’engagement sous forme de séries temporelles pour une période pouvant aller jusqu’à quatre semaines consécutives pour les Publications postées depuis le 1ᵉʳ septembre 2014.

L’endpoint **/totals** prend en charge les requêtes de métriques pour jusqu’à **250 Publications par requête**. Les endpoints **/28hour** et **/historical** prennent en charge **25 Publications par requête**.

Après avoir abordé la façon d’obtenir l’accès à l’Engagement API, nous passerons en revue la création d’une requête d’API, fournirons une vue d’ensemble d’OAuth et fournirons des liens vers d’autres ressources techniques.

<div id="getting-api-access">
  ##### **Accès à l’API**
</div>

Si vous lisez ce document, vous avez très probablement déjà obtenu l’accès à l’Engagement API. Sinon, veuillez contacter votre responsable de compte Enterprise ou demander un accès Enterprise [ici](/fr/x-api/enterprise-gnip-2.0/enterprise-gnip).

La première étape consiste à créer une [application X](/fr/resources/fundamentals/developer-apps) à l’aide d’un compte développeur approuvé via la [Console de Développement](/fr/resources/fundamentals/developer-portal). Votre responsable de compte aura besoin de l’App ID numérique associé à cette application pour vous accorder l’accès. Si vous devez faire une demande de compte développeur, vous pouvez le faire [ici](/fr/resources/fundamentals/developer-apps).

<div id="making-a-request">
  ##### **Effectuer une requête**
</div>

La bonne nouvelle est qu’effectuer des requêtes vers l’Engagement API est simple. Pour notre requête, nous allons lui demander le nombre total de Retweets, de Quote Tweets, de favoris et de réponses pour les deux Publications [@XDevelopers](https://x.com/XDevelopers) suivantes :

> 1/ Today we’re sharing our vision for the future of the X API platform![https://t.co/XweGngmxlP](https://t.co/XweGngmxlP)
>
> — Twitter Dev (@TwitterDev) [April 6, 2017](https://x.com/TwitterDev/status/850006245121695744)

> Don’t miss the Posts about your Post.
>
> Now on iOS, you can see Retweets with comments all in one place. [pic.x.com/oanjZfzC6y](https://t.co/oanjZfzC6y)
>
> — X (@X) [May 12, 2020](https://x.com/status/1260294888811347969?ref_src=twsrc%5Etfw)

La première étape consiste à construire la requête d’API au format JSON, qui comprend ces deux identifiants de Publication placés dans un tableau, un tableau des types d’engagement qui nous intéressent, et un objet JSON « groupings » personnalisé qui indique comment nous voulons que les métriques soient organisées dans la réponse. Voici à quoi ressemble notre requête :

```json
{
  "tweet_ids": [
    1260294888811347969, 850006245121695744
  ],
  "engagement_types": [
    "retweets", "quote_tweets", "favorites", "replies"
  ],
  "groupings": {
    "engagement-types-by-id": {
      "group_by": [
        "Tweet.id", "engagement.type"
      ]
    }
  }
}
```

Pour récupérer ces métriques totales, nous effectuons une requête POST avec ce JSON vers l’endpoint https://data-api.x.com/insights/engagement/totals.

Nous incluons les en-têtes suivants pour indiquer que notre requête est encodée en JSON et qu’elle est compressée avec Gzip (les corps de requêtes peuvent devenir volumineux) :

* Content-Type: application/json
* Accept-Encoding: gzip
   

Lors de l’envoi de requêtes, nous nous authentifions à l’aide d’OAuth, ce que nous aborderons plus en détail dans la section suivante.

L’API renvoie la réponse suivante :

```json
{
  "grouping name": {
    "1260294888811347969": {
      "favorites": "17111",
      "quote_tweets": "3254",
      "replies": "1828",
      "retweets": "5218"
    },
    "850006245121695744": {
      "favorites": "492",
      "quote_tweets": "66",
      "replies": "42",
      "retweets": "324"
    }
  }
}
```

Notez que la réponse contient les métriques demandées dans la structure décrite par les définitions de « groupings », avec les métriques organisées d’abord par id de publication, puis par type d’engagement au niveau suivant.

C’était assez simple. Si vous débutez avec l’authentification OAuth, consultez la section suivante.

<div id="authenticating-with-oauth">
  #### Authentification avec OAuth
</div>

OAuth est une norme d’authentification très courante dans l’industrie technologique. Si vous utilisez déjà OAuth (peut-être avec d’autres X API), vous utilisez probablement une bibliothèque OAuth spécifique à votre langage qui masque tous les détails compliqués. Si vous découvrez OAuth, consultez notre page [OAuth avec X API](/fr/resources/fundamentals/authentication) ou rendez-vous directement sur [https://oauth.net](https://oauth.net/) pour en savoir plus. Nous vous recommandons ensuite de choisir une bibliothèque OAuth adaptée au langage que vous utilisez pour votre intégration et de commencer par là. Avec ces bibliothèques, le processus d’authentification consiste généralement à configurer vos clés et jetons, à créer une sorte d’objet HTTP, puis à effectuer des requêtes avec cet objet.

Par exemple, dans l’écosystème Ruby, le pseudo-code suivant illustre une recette pour créer une application compatible OAuth en utilisant la gem Ruby « oauth » et en effectuant une requête POST :

```js
require 'oauth'

#Assemble JSON request (as above).
request = make_json_request()

#Build an app consumer object with my app consumer key and secret.
consumer = OAuth::Consumer.new(keys['consumer_key'], keys['consumer_secret'], {:site => ‘https://data-api.x.com’})
#Construire un token utilisateur avec les tokens fournis par le compte accordant la permission. Si vous effectuez une #requête application uniquement (vérification de Tweets ne nécessitant pas de permission avec le point de terminaison /totals), cette étape peut être #ignorée.
token = {:oauth_token => keys['access_token'], :oauth_token_secret => keys['access_token_secret']}

#Create oauth-enabled app object.
app = OAuth::AccessToken.from_hash(consumer, token)
#Make POST request.
result = app.post(“/insights/engagement/totals", request, {"content-type" => "application/json", "Accept-Encoding" => "gzip"})
```

L’API Engagement prend en charge à la fois l’authentification en mode application uniquement et l’authentification avec contexte utilisateur. Si vous collectez des métriques d’engagement pour des Publications publiques qui ne vous appartiennent pas avec l’endpoint /totals, aucune autorisation d’utilisateur n’est alors requise et vous pouvez utiliser l’authentification en mode application uniquement. Dans ce cas, vous utiliserez uniquement la clé et le secret de votre application pour vous authentifier.

OAuth permet également à une application d’effectuer une requête API « au nom d’un autre utilisateur », en utilisant des jetons liés à cet utilisateur. Si vous générez des métriques d’engagement pour des Publications qui vous appartiennent, c’est‑à‑dire des Publications publiées par un utilisateur pour lequel vous disposez de jetons utilisateur, vous effectuerez des requêtes avec un contexte utilisateur, ce qui signifie une authentification à la fois avec les clés de votre application et avec des jetons d’accès spécifiques à l’utilisateur. Ces jetons d’accès utilisateur sont généralement fournis par le processus &#39;[Sign‑in with X](/fr/resources/fundamentals/authentication#log-in-with-x)&#39; ou acquis directement auprès de l’utilisateur (veuillez noter que vous devez utiliser [twurl](https://github.com/xdevplatform/xurl) si vous acquérez les jetons directement auprès de l’utilisateur). Une fois que l’utilisateur vous a fourni ses jetons, ils n’expirent pas et peuvent être utilisés avec l’API Engagement pour effectuer des requêtes en son nom, tant que l’utilisateur ne réinitialise pas ses jetons ou ne change pas son mot de passe, auquel cas il devra vous fournir les nouveaux jetons.

Vous pouvez vérifier quelles métriques nécessitent quel type d’authentification via [ce tableau](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings).

<div id="selecting-an-engagement-api-endpoint">
  ### Sélection d’un endpoint de l’Engagement API
</div>

L’Engagement API fournit trois endpoints distincts :

* **[Totals](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement)** - fournit des totaux globaux pour certains indicateurs à partir de Publications « owned » ou « unowned ». Certains indicateurs sont disponibles pour toutes les Publications, tandis que d’autres ne sont disponibles que pour les Publications publiées au cours des 90 derniers jours. Gère jusqu’à 250 Publications par requête.
* **[28 hour](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement)** - fournit des indicateurs d’engagement sous forme de séries temporelles pour les Publications « owned » des 28 dernières heures. Gère jusqu’à 25 Publications par requête.
* **[Historical](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-historical)** - fournit des indicateurs d’engagement sous forme de séries temporelles pour une période allant jusqu’à quatre semaines consécutives pour les Publications « owned » publiées depuis le 1ᵉʳ septembre 2014. Gère jusqu’à 25 Publications par requête.
   

Chaque endpoint possède ses propres caractéristiques. Que vous prévoyiez d’utiliser les trois, ou que vous essayiez de déterminer lequel correspond le mieux à votre cas d’utilisation, il est important de comprendre les différences entre eux.

Ci-dessous, nous présentons quelques concepts clés, examinons plus en détail les trois endpoints, puis proposons des exemples de cas d’utilisation qui correspondent de manière générale à un endpoint spécifique. Nous espérons que ces informations vous aideront à intégrer plus efficacement les trois, ou à décider quel endpoint unique correspond le mieux à votre objectif.
 

<div id="key-concepts">
  #### Concepts clés
</div>

Plusieurs concepts clés permettent de comprendre les différentes fonctionnalités des trois endpoints de l’Engagement API et les données qu’ils fournissent.
 

<div id="impressions-and-engagement-metrics">
  ##### Métriques d&#39;impressions et d&#39;engagement
</div>

Les impressions représentent le nombre de fois qu&#39;une Publication donnée a été vue sur la plateforme X dans un contexte organique. Les impressions générées à partir de Publications vues dans un contexte sponsorisé ou payant ne sont pas incluses. Avant l&#39;API Engagement, les impressions de Publication ne représentaient qu&#39;une mesure de vues potentielles. Elles étaient basées sur le comptage des abonnés du compte de l&#39;auteur et de ceux de tout compte ayant retweeté le contenu. Elles ne prenaient pas en compte la situation courante où un utilisateur donné ne voit pas réellement la Publication.

Les métriques d&#39;impression générées par l&#39;API Engagement constituent une mesure réelle du nombre de fois qu&#39;une Publication a été affichée. Si un abonné de votre compte ne voit pas votre Publication, cela ne compte pas comme une impression.

L&#39;API Engagement fournit des métriques sur 14 [types de métriques](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#available-metrics) d&#39;engagement uniques, chacun représentant une action distincte qu&#39;un utilisateur peut effectuer lorsqu&#39;une Publication lui est présentée. Celles-ci incluent le retweet, le like, la réponse, le clic sur des entités telles que les #hashtags, les liens et les médias, le suivi de l&#39;auteur et la consultation du profil de l&#39;auteur. Toutes ces actions individuelles sont regroupées dans une seule métrique Engagements.

<div id="owned-and-unowned-x-content">
  ##### Contenus X détenus et non détenus
</div>

L’API Engagement établit une distinction claire entre les Publications détenues et non détenues. Les Publications détenues sont des Publications publiées depuis votre compte ou des Publications pour lesquelles vous avez obtenu l’autorisation de demander des données d’engagement. Comme avec les autres X API, vous obtenez cette autorisation lorsque d’autres utilisateurs ou comptes X partagent des jetons d’accès qui vous permettent d’effectuer des requêtes API en leur nom. Une façon courante d’obtenir ces jetons consiste à utiliser le [processus « Sign in with X »](/fr/resources/fundamentals/authentication#log-in-with-x).

L’endpoint `/totals` fournit des données d’engagement pour les Publications détenues et non détenues. Pour les Publications non détenues, vous pouvez demander des métriques d’engagement qui sont publiquement disponibles dans l’affichage d’une Publication : Favorite, Retweet et Reply. Pour ces métriques, ce que l’API Engagement apporte, c’est la possibilité de récupérer ces métriques à grande échelle de manière automatisée. Pour les Publications détenues, l’endpoint `/totals` fournit également les métriques d’Impression et d’Engagement (total).

Les endpoints `/28hr` et `/historical` fournissent des métriques uniquement pour les Publications détenues, ce qui signifie que vous devez transmettre le contexte utilisateur lorsque vous effectuez une requête vers ces endpoints.

<div id="total-and-time-series-engagement-data">
  ##### Données d’engagement totales et en séries temporelles
</div>

L’endpoint /totals fournit, comme son nom l’indique, uniquement des totaux globaux pour ses types d’engagement. Ses chiffres représentent les totaux à jour depuis la mise en ligne de la Publication. Si une Publication vient juste d’être publiée et que vous demandez à plusieurs reprises ses métriques, ces totaux évolueront généralement à chaque requête.

Les endpoints /28hr et /historical peuvent fournir à la fois des totaux globaux et des données en séries temporelles. Lorsque vous demandez des données en séries temporelles, les métriques d’engagement peuvent être agrégées en données quotidiennes ou horaires.   

Consultez notre documentation sur les [regroupements d’engagement](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings) pour savoir comment demander des données en séries temporelles avec les endpoints /28hr et /historical.

<div id="endpoints-and-example-use-cases">
  #### Points de terminaison et exemples de cas d&#39;utilisation
</div>

Compte tenu des caractéristiques et des différences décrites ci-dessus, chaque point de terminaison correspond généralement à différents types de cas d&#39;utilisation. Pour vous aider à déterminer quel point de terminaison répond le mieux à votre cas d&#39;utilisation spécifique, vous trouverez ci-dessous quelques exemples de besoins exprimés par des utilisateurs et le point de terminaison qui les satisfait le mieux.

<div id="totals">
  ##### **/totals**
</div>

* J’ai seulement besoin d’accéder à certains types de métriques (Impressions, Engagements, Favoris, Retweets, Tweets cités, Réponses et Vues vidéo).
* J’ai besoin d’accéder aux données d’engagement de base pour n’importe quelle Publication, pas seulement pour celles que je possède.
* Je veux comparer les performances avec un concurrent.
* Je veux suivre les statistiques d’engagement de base pour un hashtag ou une campagne qui inclut des Publications qui ne m’appartiennent pas.
* Je n’ai pas besoin de données ventilées par jour ou par heure, j’ai seulement besoin du total actuel au moment où j’effectue une requête.
* J’ai besoin d’une seule métrique à afficher dans un rapport ou un tableau de bord et je ne veux stocker aucune donnée.
* Je veux afficher les données lors du chargement de la page et j’ai seulement besoin d’effectuer une requête et d’obtenir une réponse.
* J’ai besoin d’accéder aux données pour des centaines de milliers ou des millions de Publications par jour.
   

<div id="28hr">
  ##### **/28hr**
</div>

* J&#39;ai besoin d&#39;accéder aux 17 types de métriques.
* Je veux afficher des données pour des Publications très récentes, publiées au cours des 28 dernières heures.
* J&#39;ai une tâche qui s&#39;exécute une fois par jour pour récupérer les données qui m&#39;intéressent et je n&#39;ai besoin d&#39;obtenir des données que pour le dernier jour.
* J&#39;ai besoin que les métriques soient ventilées par jour ou par heure.
* Je veux afficher, dans un tableau de bord, des séries temporelles de l&#39;activité heure par heure.
* J&#39;ai besoin d&#39;un niveau d&#39;accès élevé pour des centaines de milliers de Publications par jour.
* J&#39;ai des capacités de stockage et je peux actualiser les données une fois par jour et conserver un total cumulé.
   

<div id="historical">
  ##### **/historical**
</div>

* J’ai besoin d’accéder aux 17 types de métriques.
* J’ai besoin d’obtenir des données historiques pour des Publications créées depuis septembre 2014.
* Je souhaite afficher une analyse historique détaillée comparant les campagnes.
* J’ai besoin que les métriques soient ventilées par jour ou par heure.
* Je n’ai pas besoin d’un niveau d’accès élevé à l’Engagement API et j’ai seulement besoin d’obtenir des données pour quelques centaines ou milliers de Publications par jour.

<div id="engagement-api-key-characteristics">
  ### Principales caractéristiques de l’API Engagement
</div>

* **API RESTful** renvoyant des données JSON, prenant en charge les requêtes POST avec des corps de requête au format JSON.
* **Types de requêtes :** les applications clientes peuvent effectuer les types de requêtes suivants :
  * **Total des interactions** -- requête HTTP POST vers le endpoint /totals
  * **Interactions sur les 28 dernières heures** -- requête HTTP POST vers le endpoint /28hr
  * **Interactions historiques** -- requête HTTP POST vers le endpoint /historical
* **Authentification OAuth :**
  * [OAuth 1.0a User Context](/fr/resources/fundamentals/authentication) : toutes les métriques disponibles sont accessibles pour les Publications appartenant à un utilisateur qui a autorisé votre application à l’aide de [3-legged OAuth](https://developer.x.com/resources/fundamentals/authentication/obtaining-user-access-tokens). Vous devez utiliser les Access Tokens de cet utilisateur lorsque vous effectuez votre requête.[](/fr/resources/fundamentals/authentication)
  * [OAuth 2.0 Bearer Token](/fr/resources/fundamentals/authentication#oauth-2-0) : certaines métriques (Retweets, Quote Tweets, Replies, Favorites et Video Views) sont disponibles pour toute Publication publique. 
* **Métadonnées et structure de la requête :** les données de la requête sont représentées par un objet JSON composé d’un tableau d’ID de Publication, d’un tableau de types d’interactions et d’une structure de regroupement d’interactions.
* **Publications par requête :**
  * Endpoint /totals : 250 ID de Publication
  * Endpoint /28hr : 25 ID de Publication
  * Endpoint /historical : 25 ID de Publication
* **Disponibilité des métriques d’interaction :**
  * **/totals** -- Totaux des métriques depuis la date à laquelle la Publication a été publiée. Impressions et Engagements sont disponibles pour les Publications publiées au cours des 90 derniers jours, tandis que Retweets, Quote Tweets, Replies, Favorites et Video Views sont disponibles pour toutes les Publications.
  * **/28hr** -- 28 dernières heures à partir du moment de la requête.
  * **/historical** -- Toute période de 28 jours à partir du 1er septembre 2014.
* **Types de métriques :** chaque requête inclut un tableau de [Metric Types](http://support.gnip.com/apis/engagement_api/overview.html#EngagementTypes). Leur disponibilité dépend du endpoint et, pour les requêtes vers le endpoint /totals, du fait que les Publications soient ou non autorisées par l’utilisateur propriétaire.
  * Endpoint /totals :
    * Toutes les Publications : Favorites, Retweets, Quote Tweets, Replies et Video Views
    * Nécessite OAuth 1.0a User Context : Impressions, Engagements, Favorites, Replies et Retweets
  * Endpoints /28hr et /historical (nécessitent OAuth 1.0a User Context avec l’Access Token du propriétaire de la Publication) : Impressions, Engagements, Favorites, Replies, Retweets, URL Clicks, Hashtag Clicks, Detail Click, Permalink Clicks, Media Clicks, App Install Attempts, App Opens, Post Emails, Video Views et Media Views
* **Regroupements d’engagement :** chaque requête inclut un tableau de [Engagement Groupings](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings). Grâce à ces regroupements, vous pouvez personnaliser la façon dont les métriques renvoyées sont organisées. Jusqu’à trois regroupements peuvent être inclus dans chaque requête. Les métriques peuvent être organisées selon les valeurs suivantes :
  * Tous les endpoints : ID de Publication, type d’interaction
  * Endpoints /28hr et /historical : ces endpoints fournissent des séries temporelles si ces regroupements supplémentaires sont spécifiés : Engagement Day, Engagement Hour
* **Attentes en matière d’intégration :** votre équipe sera responsable de ce qui suit.
  * Créer et maintenir une application cliente capable d’envoyer des requêtes HTTP à l’API Engagement qui renvoient des métriques d’interaction pour l’ID de Publication inclus dans la requête.
* **Limitations**
* Les Video Views ne sont disponibles que pour les Publications âgées de 1 800 jours ou moins.

<div id="authenticating-with-the-engagement-api">
  ### Authentification avec l’Engagement API
</div>

> **Veuillez noter** : 
>
> X doit activer l’accès à l’Engagement API pour votre App développeur avant que vous puissiez commencer à utiliser l’API. À cette fin, veillez à communiquer l’ID d’App que vous comptez utiliser à des fins d’authentification à votre responsable de compte ou à votre équipe de support technique.

Deux méthodes d’authentification sont disponibles avec l’Engagement API : [OAuth 1.0a](/fr/resources/fundamentals/authentication#oauth-1-0a-2) et [OAuth 2.0 Bearer Token](/fr/resources/fundamentals/authentication#bearer-token-also-known-as-app-only). 

**OAuth 2.0 Bearer Token** (également appelée « application-only ») vous permet d’accéder aux indicateurs d’engagement publics. Cette méthode d’authentification peut être utilisée pour obtenir les totaux de Favoris (également appelés Likes), Retweets, Quote Tweets, Réponses et vues vidéo pour toute Publication publique lorsque vous envoyez des requêtes vers le point de terminaison [/totals](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-totals). 

**OAuth 1.0a** (également appelée « user context ») vous permet d’envoyer des requêtes au nom d’un utilisateur et d’accéder aux indicateurs d’engagement privés appartenant à l’utilisateur en question. 

Cette méthode d’authentification est obligatoire pour :

* Toutes les requêtes envoyées vers le point de terminaison [/28hr](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-28hr) et le point de terminaison [/historical](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-historical)
* L’accès à l’une quelconque des métriques privées suivantes : Impressions, Engagements, Vues média, Engagements média, Clics sur URL, Clics sur hashtag, Développements de détails, Clics sur permalien, Tentatives d’installation d’App, Ouvertures d’App, Envoi de Publication par e‑mail, Abonnements utilisateur et Clics sur le profil utilisateur

Lorsque vous envoyez une requête avec OAuth 1.0a, vous devez inclure les Access Tokens (Access Token et Secret) de l’utilisateur qui possède la Publication ou la ressource protégée qui vous intéresse. Si vous ne fournissez pas les Access Tokens utilisateur corrects lorsque vous demandez des données utilisateur protégées, l’Engagement API renverra une erreur `403 Forbidden`.

L’Engagement API ne vous permettra pas de récupérer des données d’engagement pour des [Publications protégées](https://help.x.com/en/safety-and-security/public-and-protected-tweets), même si vous vous authentifiez au nom de l’utilisateur propriétaire de ces Publications. Toute tentative en ce sens renverra une erreur `400 Bad Request`, avec le message `"Tweet ID(s) are unavailable"`.

Si vous envoyez une requête au nom de votre propre compte X (en d’autres termes, le compte qui possède l’App développeur), vous pouvez générer les Access Tokens requis directement depuis la [Console de Développement](https://developer.x.com/en/portal/projects-and-apps), sous l’onglet « Keys and tokens » de l’App développeur.

Si vous envoyez une requête au nom de tout autre utilisateur, vous devrez utiliser le flux OAuth à 3 volets (3-legged OAuth) pour obtenir les Access Tokens requis. La documentation suivante contient plus d’informations sur la façon de procéder : [OAuth 1.0a: how to obtain a user’s access tokens](/fr/resources/fundamentals/authentication#oauth-1-0a-2).

Pour des exemples supplémentaires, y compris la façon de vous authentifier avec OAuth 1.0a, consultez le [code Python d’exemple XDevelopers pour l’Engagement API](https://github.com/xdevplatform/enterprise-scripts-python/tree/master/Engagement-API).

<div id="interpreting-the-metrics">
  ### Interpréter les métriques
</div>

**Remarque :** Vous pouvez constater des différences entre les données indiquées sur certains tableaux de bord web X et les données renvoyées par l’API Engagement. Ces différences surviennent parce que les tableaux de bord web n’affichent généralement que les engagements et/ou impressions qui se sont produits dans l’intervalle de temps sélectionné. Par exemple, un tableau de bord web peut afficher l’engagement relatif à des Publications sur la durée d’un mois calendaire, tandis que l’API Engagement peut afficher des engagements qui dépassent cette période, mais restent dans l’intervalle de temps demandé. Dans ce type de situation, l’API Engagement doit être considérée comme la source de référence.
 

<div id="impressions-and-engagement-data">
  #### Données d’impressions et d’engagement
</div>

L’API Engagement fournit des impressions **organiques** et des données d’engagement.

Les impressions représentent le nombre de fois qu’une Publication donnée a été vue sur la plateforme X dans un contexte organique. Les impressions générées par des Publications vues dans un contexte sponsorisé ou payant ne sont **pas** incluses.

Les engagements représentent le nombre de fois qu’une Publication donnée a fait l’objet d’une interaction de la part d’un utilisateur, dans un contexte à la fois **organique** et **sponsorisé**. Les engagements incluent, sans s’y limiter, les Retweets, les favoris, les réponses, les clics sur une URL, les clics sur un hashtag, les clics sur une mention et les vues de média. Pour la liste complète des actions d’engagement incluses, consultez la section Engagement Data. 

Pour calculer un taux d’engagement de référence, utilisez le nombre total d’engagements divisé par le nombre total d’impressions pour une Publication donnée sur la période que vous analysez.

Les données d’impressions et d’engagement ne peuvent être récupérées que pour des Publications provenant de @handles vous appartenant, ou de @handles qui ont autorisé votre application à afficher des informations détaillées sur leurs Publications. En interne, l’API Engagement suit le nombre de @handles uniques qui ont été demandés par rapport à la limite de @handles prévue au contrat. Il est également recommandé de suivre l’utilisation des requêtes de @handles côté client tout au long du mois.  

<div id="video-metrics">
  #### Statistiques vidéo
</div>

Il existe plusieurs indicateurs différents qui représentent les impressions de médias sur X. Le premier est notre indicateur de vues vidéo, qui repose sur le standard MRC de 50 % de la vidéo visible pendant au moins deux secondes. Le second est la métrique Media Views, qui inclut toutes les vues (lecture automatique et clic) de vos médias, comptabilisées pour les vidéos, vines, GIF et images.

L’indicateur de vues vidéo est disponible pour les Publications dont vous êtes le propriétaire via les endpoints /28hour et /historical, ainsi que pour toutes les Publications dont vous n’êtes pas le propriétaire via l’endpoint /totals. 

Bien que l’indicateur de vues vidéo au sein de l’interface utilisateur de X utilise le même standard MRC, veuillez noter que vous pouvez constater un écart entre l’indicateur de vues vidéo affiché sur les plateformes détenues et exploitées par X (application mobile et site web) et le nombre que vous recevez via les différents endpoints de l’Engagement API.

* Les vues vidéo fournies par l’endpoint /totals et l’interface utilisateur de X affichent le nombre de vues vidéo agrégé sur l’ensemble des Publications dans lesquelles la vidéo donnée a été publiée. Cela signifie que la métrique fournie via /totals et affichée dans l’interface de X inclut les vues combinées de toute instance où la vidéo a été Retweetée ou republiée dans des Publications distinctes.
* Les vues vidéo fournies par les endpoints /28hour et /historical de l’Engagement API incluent uniquement les vues générées par la Publication spécifique pour laquelle vous récupérez des métriques.

<div id="engagement-api-groupings">
  ### Regroupements de l’API Engagement
</div>

Les regroupements permettent d’organiser de manière personnalisée les métriques d’engagement renvoyées. Vous pouvez inclure au maximum 3 regroupements par requête. Vous pouvez choisir de regrouper les métriques selon une ou plusieurs des valeurs suivantes :

*Les trois endpoints prennent tous en charge :*

* tweet.id
* engagement.type
   

*Les endpoints `/28hr` et `/historical` peuvent fournir des métriques sous forme de séries chronologiques et prennent donc en charge :*

* engagement.day
* engagement.hour

Les regroupements sont appliqués de manière séquentielle, ce qui vous permet de modifier le format de résultat souhaité en changeant l’ordre de vos valeurs `group_by`. Les regroupements qui contiennent quatre valeurs `group_by` ne seront pris en charge que dans l’un des deux formats suivants :

```bash
"group_by": [
    "tweet.id",
    "engagement.type",
    "engagement.day",
    "engagement.hour"
  ]
```

OU

```bash
"group_by": [
    "engagement.type",
    "tweet.id",
    "engagement.day",
    "engagement.hour"
]
```

Par exemple, si vous souhaitez générer des totaux globaux par type de métrique, incluez la spécification de « groupings » suivante dans votre requête (et consultez la page [Référence de l’API](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement) pour plus d’informations sur la façon de construire vos requêtes) :

```json
{
  "engagement_types": [
    "favorites",
    "replies",
    "retweets"
  ],
  "groupings": {
    "Grand Totals": {
      "group_by": [
        "engagement.type"
      ]
    }
  }
}
```

Avec ce regroupement, la réponse JSON de l’Engagement API inclura un attribut de niveau racine `"Grand Totals"` qui contient les totaux globaux par type de métrique :

```json
{
  "Grand Totals": {
    "favorites": "12",
    "replies": "2",
    "retweets": "2"
  }
}
```

Pour générer une série chronologique de métriques sur 4 heures pour une seule Publication, regroupée par ID de publication, la spécification Grouping suivante ferait partie de la requête :

```json
{
  "start": "2016-02-10T17:00:00Z",
  "end": "2016-02-10T21:00:00Z",
  "tweet_ids": [
    "697506383516729344"
  ],
  "engagement_types": [
    "impressions",
    "engagements"
  ],
  "groupings": {
    "Tweets_MetricType_TimeSeries": {
      "group_by": [
        "tweet.id",
        "engagement.type",
        "engagement.hour"
      ]
    }
  }
}
```

Avec ce regroupement, la réponse JSON de l’API Engagement inclura un attribut racine `"Tweets_MetricType_TimeSeries"` contenant les métriques ventilées par ID de Publication, puis par type de métrique, ainsi que la série temporelle horaire correspondante :


    **Le champ de métadonnées `engagements` renvoyé dans la charge utile n’est pas égal à la somme de tous les différents totaux de métriques d’engagement. Pourquoi est-ce le cas ?**

    Ce comportement est normal. Le champ de métadonnées `engagements` peut ne pas toujours correspondre à la somme de toutes les métriques d’engagement individuelles renvoyées par l’API. Cela s’explique par le fait que le champ de métadonnées `engagements` peut inclure des engagements supplémentaires qui n’ont pas de métriques spécifiques détaillées dans la charge utile. En d’autres termes, additionner tous les différents totaux de métriques d’engagement peut ne pas être égal à la valeur que vous voyez dans le champ de métrique `engagements` qui vous est renvoyé dans la charge utile.

    Vous pouvez considérer le champ de métadonnées `engagements` comme tout clic ou interaction effectué sur la Publication.
     

    **Le champ `url_clicks` dans la charge utile de la réponse renvoie un nombre, alors qu’en réalité la Publication ne contient pas d’URL. Comment est-ce possible ?**

    Cela peut être dû au fait qu’une Publication contenant quelque chose comme un hashtag (qui crée un lien vers une autre page) sera comptabilisée comme un clic d’URL si un utilisateur clique dessus.
     
  </Accordion>

  <Accordion title="Pourquoi ne puis-je pas recevoir de données d’engagement pour une Publication spécifique ?">
    Il existe plusieurs raisons pour lesquelles vous pourriez ne pas être en mesure de récupérer des données d’engagement pour une Publication spécifique, notamment :

    * L’ID de la Publication ou les ID de Publication que vous avez demandés ne sont pas disponibles en fonction du jeton d’authentification que vous utilisez pour récupérer des données pour le compte d’un tiers.
    * L’ID de la Publication ou les ID de Publication que vous avez demandés, spécifiquement pour le point de terminaison /totals, ne datent pas de 90 jours ou moins et ne sont donc pas disponibles pour renvoyer les impressions ou les métriques d’engagement.
    * L’ID de la Publication ou les ID de Publication que vous avez demandés ne sont plus disponibles, ce qui indique généralement qu’elles ont été supprimées ou qu’elles ne sont plus publiques pour une autre raison.

    Veuillez consulter les différents [messages d’erreur](/fr/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#error-messages) que vous êtes susceptible de recevoir dans l’un des cas ci-dessus.
  </Accordion>

  <Accordion title="Comment puis-je gérer la limitation de débit avec l’Engagement API ?">
    Vous pouvez utiliser les informations `x-per-minute-limit` et `x-per-minute-remaining` renvoyées par l’en-tête de la réponse lorsque vous faites une requête à l’Engagement API pour surveiller votre consommation.

    `x-per-minute-limit` vous indique quel est votre quota et `x-per-minute-remaining` vous indique combien d’appels il vous reste.

<div id="authentication">
  #### **Authentification**
</div>

L’Engagement API nécessite l’utilisation de HTTPS et prend en charge à la fois User Context et Application-Only OAuth. La plupart des requêtes vers l’Engagement API nécessitent l’utilisation de 3-Legged OAuth (une version spécifique de User Context), ce qui signifie que vous utilisez la consumer key et la consumer secret de l’application qui a été enregistrée et approuvée pour l’accès à l’Engagement API par votre responsable de compte Twitter, ainsi que le jeton d’accès et le secret du jeton d’accès du propriétaire du Tweet pour appeler l’endpoint. Les requêtes suivantes nécessitent ce type d’OAuth :

* Toute requête vers /totals pour obtenir les métriques Impressions et Engagements, qui sont limitées aux Tweets appartenant au compte
* Toute requête vers /28hr
* Toute requête vers /historical

Certaines requêtes à l’Engagement API peuvent être effectuées en utilisant Application-Only OAuth, ce qui signifie que vous devez simplement fournir votre consumer key et votre consumer secret, ou un Bearer Token. La requête suivante peut être effectuée avec ce type d’OAuth :

* Toute requête vers /totals pour obtenir les métriques Favorites, Replies, Retweets ou Video Views, qui peuvent être récupérées pour n’importe quel Tweet

Pour toute requête, vous devrez configurer une application Twitter et une clé d’API correspondante à l’aide de la console de gestion d’applications disponible sur [developer.x.com](https://developer.x.com/en/portal/dashboard).

Remarque : vous pouvez afficher et modifier vos [applications Twitter](/fr/resources/fundamentals/developer-apps) existantes via le [Twitter app dashboard](https://developer.x.com/en/apps) si vous êtes connecté à votre compte Twitter sur developer.x.com.

Une fois que vous avez configuré votre application, l’ID de l’application devra être approuvé par votre représentant de compte afin que votre application puisse envoyer des requêtes à l’Engagement API. Les jetons d’accès doivent être utilisés pour représenter l’« utilisateur actuel » et les requêtes effectuées pour le compte d’un autre utilisateur doivent être signées avec un jeton valide. Assurez-vous d’[encoder correctement les caractères réservés](https://tools.ietf.org/html/rfc3986) dans les URL et les corps de requête POST avant de préparer les chaînes de base de signature OAuth.

Pour plus d’informations sur la façon de démarrer avec OAuth, consultez les liens suivants :

* [Vue d’ensemble d’OAuth](/fr/resources/fundamentals/authentication)
* [Utiliser 3 Legged OAuth, également appelé User Context](/fr/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow)
* [Utiliser Application-Only OAuth](/fr/resources/fundamentals/authentication#bearer-token-also-known-as-app-only)

<div id="error-messages">
  #### **Messages d’erreur**
</div>

Dans différents scénarios, l’API Engagement renverra des messages d’erreur spécifiques au contexte que votre application doit être en mesure de gérer. Le tableau ci-dessous présente des exemples courants de ces messages d’erreur et la manière de les interpréter. Veuillez noter que, dans de nombreux cas, l’API Engagement renverra des résultats partiels pour les données disponibles, ainsi que des messages d’erreur spécifiques, dans le cadre d’une Réponse 200 OK fournissant plus d’informations.

| Message d’erreur | Description |
| :--- | :--- |
| `"errors":["Your account could not be authenticated. Reason: Access token not found"]` | Une erreur dans le composant d’authentification de la requête. Le « Reason » doit fournir des informations utiles pour diagnostiquer l’erreur. Si vous ne parvenez pas à la résoudre, veuillez envoyer l’erreur complète, y compris le « Reason », à notre équipe d’assistance. |
| `"errors":["1 Tweet ID(s) are unavailable"],"unavailable_tweet_ids": ["TWEET_IDS"]` | L’ID de Tweet ou les ID de Tweet que vous avez demandés ne sont plus disponibles, ce qui indique généralement qu’ils ont été supprimés ou ne sont plus accessibles publiquement pour une autre raison. |
| `"errors":["Impressions & engagements for tweets older than 90 days (*TIME_PERIOD*) are not supported"],"unsupported_for_impressions_engagements_tweet_ids":[*TWEET_IDS*]` | L’ID de Tweet ou les ID de Tweet que vous avez demandés, spécifiquement pour l’endpoint /totals, ne datent pas de 90 jours ou moins et ne peuvent donc pas être utilisés pour renvoyer les métriques d’impressions ou d’engagements. |
| `"errors":["Forbidden to access tweets: *TWEET_IDS*"]` | L’ID de Tweet ou les ID de Tweet que vous avez demandés ne sont pas accessibles en fonction du jeton d’authentification que vous utilisez pour récupérer des données pour le compte d’un tiers. |

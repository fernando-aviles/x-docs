<div id="overview">
  ## Aperçu
</div>

`Enterprise`

*Les API Enterprise sont disponibles uniquement dans le cadre de nos niveaux d’accès gérés. Pour utiliser ces API, vous devez d’abord configurer un compte avec notre équipe commerciale Enterprise. Pour en savoir plus, consultez [ICI](https://developer.x.com/en/products/x-api/enterprise).*

*Vous pouvez consulter toutes les offres de recherche de Publications de X API [ICI](/fr/x-api/enterprise-gnip-2.0/fundamentals/search-api).*

Il existe deux API Enterprise de recherche :

1. 30-Day Search API fournit des données des 30 derniers jours.
2. Full-Archive Search API fournit un accès complet et instantané à l’intégralité du corpus de données de X, remontant jusqu’à la première Publication en mars 2006.

Ces API RESTful prennent en charge une requête unique pouvant contenir jusqu’à 2 048 caractères par requête. Les requêtes sont rédigées avec la syntaxe de règles PowerTrack – voir [Rules and filtering](/fr/x-api/enterprise-gnip-2.0/fundamentals/rules-filtering#getting-started-with-enterprise-rules-and-queries) pour plus de détails. Les utilisateurs peuvent spécifier n’importe quelle période, avec une granularité à la minute. Cependant, les réponses seront limitées au plus petit des deux entre votre `maxResults` spécifié OU 31 jours, et incluront un jeton `next` pour paginer vers le prochain ensemble de résultats. Si les paramètres temporels ne sont pas spécifiés, l’API renverra les données correspondantes pour les 30 derniers jours.

Les API Enterprise de recherche fournissent un accès à faible latence, avec fidélité complète et basé sur des requêtes, à l’archive des Publications avec une granularité à la minute. Les données de Publication sont renvoyées dans l’ordre chronologique inverse, en commençant par la Publication la plus récente qui correspond à votre requête. Les Publications sont disponibles à partir de l’API de recherche environ 30 secondes après leur publication.

Ces endpoints de recherche fournissent les métadonnées de Publication modifiée. Tous les objets pour les Publications créées depuis le 29 septembre 2022 incluent des métadonnées d’édition de Publication, même si la Publication n’a jamais été modifiée. Chaque fois qu’une Publication est modifiée, un nouvel ID de Publication est créé. L’historique des modifications d’une Publication est documenté par un tableau d’ID de Publication, en commençant par l’ID d’origine.

Ces endpoints renverront toujours la modification la plus récente, ainsi que tout l’historique des modifications. Toute Publication collectée après sa fenêtre d’édition de 30 minutes représentera sa version finale. Pour en savoir plus sur les métadonnées d’édition de Publication, consultez la page [Principes de base des Publications modifiées](/fr/x-api/fundamentals/edit-posts).

Les requêtes incluent un paramètre `maxResults` qui spécifie le nombre maximal de Publications à renvoyer par réponse d’API. Si davantage de Publications sont associées à la requête que ce nombre maximal de résultats par réponse, un jeton `next` est inclus dans la réponse. Ces jetons `next` sont utilisés dans les requêtes suivantes pour parcourir l’ensemble complet des Publications associées à la requête.

Ces API Enterprise de recherche fournissent un endpoint *counts* qui permet aux utilisateurs de demander le volume de données associé à leur requête. 

<div id="request-types">
  ### Types de requêtes
</div>

Les API de recherche Enterprise prennent en charge deux types de requêtes :

<div id="search-requests-data">
  #### Search requests (données)
</div>

Les requêtes de recherche auprès des API de recherche Enterprise vous permettent de récupérer jusqu’à 500 résultats par réponse pour une période donnée, avec la possibilité de paginer pour obtenir des données supplémentaires. En utilisant le paramètre `maxResults`, vous pouvez spécifier des tailles de page plus petites pour les cas d’usage d’affichage (permettant à votre utilisateur de demander plus de résultats si nécessaire) ou des tailles de page plus grandes (jusqu’à 500) pour des extractions de données plus volumineuses. Les données sont renvoyées dans un ordre antichronologique et sont conformes au moment de leur livraison.

<div id="counts-requests-post-count">
  #### Counts requests (Post count)
</div>

Les requêtes de comptage permettent de récupérer des décomptes d’activité historiques, qui reflètent le nombre d’activités correspondant à une requête donnée pendant la période demandée. La réponse vous fournira essentiellement un histogramme de comptages, regroupés par jour, par heure ou par minute (le regroupement par défaut est l’*heure*). Il est important de noter que les résultats de comptage ne reflètent pas toujours les événements de conformité (par exemple, les suppressions de Publications) qui se produisent bien après (7+ jours) la publication d’une Publication ; il est donc normal que la métrique de comptage ne corresponde pas toujours à celle d’une requête de données portant sur les mêmes critères.

**Note concernant la facturation :** chaque requête – *y compris les requêtes de pagination* – effectuée sur les endpoints `data` et `counts` est comptabilisée comme une requête facturée. Par conséquent, s’il y a plusieurs pages de résultats pour une seule requête, parcourir les X pages de résultats équivaut à X requêtes facturées.

<div id="data-updates-and-mutability">
  ### Mises à jour des données et mutabilité
</div>

Avec les API de recherche Enterprise, certaines des données d’une Publication sont mutables, c’est‑à‑dire qu’elles peuvent être mises à jour ou modifiées après l’archivage initial.

Ces données mutables se répartissent en deux catégories :

* Métadonnées de l’objet utilisateur :
  * @handle de l’utilisateur (l’id numérique ne change jamais)
  * Description de la biographie
  * Compteurs : statuts, abonnés, abonnements, favoris, listes
  * Localisation du profil
  * Autres détails comme le fuseau horaire et la langue
* Statistiques de la Publication – c’est‑à‑dire tout ce qui peut être modifié sur la plateforme par des actions d’utilisateurs (exemples ci‑dessous) :
  * Nombre de favoris
  * Nombre de Retweets

Dans la plupart de ces cas, les API de recherche renverront les données telles qu’elles existent sur la plateforme au *moment de la requête*, plutôt qu’au moment de la génération de la Publication. Cependant, dans le cas des requêtes utilisant des opérateurs de sélection (par exemple from, to, @, is:verified), cela peut ne pas être le cas. Les données sont mises à jour régulièrement dans notre index, avec une fréquence accrue pour les périodes les plus récentes. En conséquence, dans certains cas, les données renvoyées peuvent ne pas correspondre exactement aux données actuelles telles qu’elles sont affichées sur X.com, mais correspondent aux données au moment où elles ont été indexées pour la dernière fois.

Remarque : ce problème d’incohérence ne s’applique qu’aux requêtes où l’opérateur s’applique à des données mutables. Par exemple, pour le filtrage par noms d’utilisateur, la meilleure solution consiste à utiliser les identifiants numériques des utilisateurs plutôt que les @handles pour ces requêtes.

<div id="single-vs-multi-threaded-requests">
  ### Requêtes monothread vs multithread
</div>

Chaque client dispose d’une limite de débit définie pour son endpoint de recherche. La limite de débit par minute par défaut pour la recherche Full-Archive est de 120 requêtes par minute, soit une moyenne de 2 requêtes par seconde (QPS). Cette moyenne de QPS signifie que, en théorie, 2 requêtes peuvent être adressées à l’API chaque seconde. Étant donné la pagination du produit, si une requête portant sur un an a un million de Publications qui lui sont associées, réparties uniformément sur l’année, plus de 2 000 requêtes seraient nécessaires (en supposant un « maxResults » de 500) pour recevoir toutes les données. En supposant qu’il faille deux secondes par Réponse, cela représente 4 000 secondes (un peu plus d’une heure) pour récupérer toutes ces données de façon séquentielle via un seul thread (1 requête par seconde en utilisant le jeton « next » de la Réponse précédente). Pas mal !

Considérez maintenant la situation où douze threads parallèles sont utilisés pour recevoir les données. En supposant une répartition uniforme du million de Publications sur la période d’un an, vous pourriez répartir les requêtes sur douze threads parallèles (multithread) et utiliser davantage de la limite de débit par seconde pour un seul « job ». En d’autres termes, vous pourriez exécuter un thread par mois qui vous intéresse et, ce faisant, les données pourraient être récupérées 12 fois plus rapidement (soit environ 6 minutes).

Cet exemple multithread s’applique tout aussi bien à l’endpoint de comptage. Par exemple, si vous souhaitez recevoir les nombres de Publications pour une période de deux ans, vous pouvez effectuer une requête monothread et revenir en arrière sur les nombres par tranches de 31 jours. En supposant qu’il faille 2 secondes par Réponse, il faudrait environ 48 secondes pour effectuer les 24 requêtes API et récupérer l’ensemble des nombres. Cependant, vous avez également la possibilité d’effectuer plusieurs requêtes d’un mois à la fois. En effectuant 12 requêtes par seconde, l’ensemble des nombres pourrait être récupéré en environ 2 secondes.

<div id="retry-logic">
  ### Logique de réessai
</div>

Si vous rencontrez une erreur 503 avec les API de recherche Enterprise, il s’agit probablement d’une erreur transitoire qui peut être résolue en réessayant la requête un peu plus tard.

Si la requête échoue 4 fois de suite et que vous avez attendu au moins 10 minutes entre chaque échec, suivez les étapes de dépannage suivantes :

* Réessayez la requête après avoir réduit l’intervalle de temps qu’elle couvre. Répétez cette opération, si nécessaire, jusqu’à une fenêtre de 6 heures.
* Si vous combinez un grand nombre de termes avec l’opérateur OR, scindez-les en règles distinctes et réessayez chacune individuellement.
* Si vous utilisez un grand nombre d’exclusions dans votre règle, réduisez le nombre de termes exclus par négation dans la règle et réessayez.

<div id="getting-started-with-enterprise-search-posts-30-day-api">
  ### Premiers pas avec l’enterprise Search Posts : 30-Day API
</div>

L’enterprise Search Posts : 30-Day API vous fournit les Publications publiées au cours des 30 derniers jours. Les Publications sont trouvées et renvoyées en fonction de la requête que vous spécifiez dans votre demande. Une requête est une règle qui définit ce que la Publication que vous obtenez doit contenir. Dans ce tutoriel, nous allons rechercher des Publications provenant du compte X @XDevelopers en anglais.

Les Publications que vous recevez dans votre payload peuvent être dans un format data, qui vous fournit le payload complet de la Publication, ou dans un format de comptage, qui vous donne des données numériques sur le nombre de Publications correspondantes. Nous utiliserons cURL pour effectuer des requêtes vers les endpoints data et counts.

Vous aurez besoin des éléments suivants :

* [Un compte enterprise]https://developer.x.com/en/products/x-api/enterprise
* Votre nom d’utilisateur, votre mot de passe et le nom de votre compte
* Le libellé associé à votre endpoint de recherche, tel qu’affiché sur console.gnip.com

#### Accéder au endpoint data

Le endpoint data nous fournira la charge utile complète des Publications correspondantes. Nous utiliserons les opérateurs `from:` et `lang:` pour trouver les Publications provenant de @XDevelopers rédigées en anglais. *Pour plus d’opérateurs [cliquez ici](/fr/x-api/enterprise-gnip-2.0/fundamentals/search-api#enterprise-operators).*

<Tabs>

    * **Nom d’utilisateur** `<USERNAME>` par ex. `email@domain.com`

| mot-clé                            | Fait correspondre un mot-clé tokenisé présent dans le corps ou les URL d’une Publication. Il s’agit d’une correspondance tokenisée, ce qui signifie que votre chaîne de caractères de mot-clé sera comparée au texte tokenisé du corps de la Publication – la tokenisation est basée sur la ponctuation, les symboles et les caractères séparateurs du plan multilingue de base Unicode. Ces jetons seraient ensuite comparés à la chaîne de caractères de mot-clé utilisée dans votre règle. Pour faire correspondre des chaînes contenant des signes de ponctuation (par exemple, coca-cola), des symboles ou des caractères séparateurs, vous devez utiliser une correspondance exacte entre guillemets, comme décrit ci-dessous.<br /><br />**Remarque :** Avec l’API de recherche, les caractères accentués et spéciaux sont normalisés en caractères latins standards, ce qui peut changer le sens dans les langues étrangères ou produire des résultats inattendus :<br />Par exemple, &quot;músic&quot; correspondra à « music » et inversement.<br />Par exemple, les expressions courantes comme &quot;Feliz Año Nuevo!&quot; en espagnol seront indexées comme &quot;Feliz Ano Nuevo&quot;, ce qui change le sens de l’expression.<br /><br />**Remarque :** Cet opérateur fera correspondre à la fois les URL et les URL développées dans une Publication. |

<div id="product-overview">
  ### Présentation du produit
</div>

La fonctionnalité de recherche sur l’archive complète pour l’offre entreprise a été lancée en août 2015, et la version pour l’offre premium a été lancée en février 2018. Ces produits de recherche permettent aux clients d’accéder immédiatement à toute Publication disponible publiquement. Avec la recherche sur l’archive complète, vous soumettez une seule requête et recevez une réponse selon le mode RESTful classique. La recherche sur l’archive complète met en œuvre une pagination allant jusqu’à 500 Publications par réponse, et prend en charge une limite de débit pouvant atteindre 60 requêtes par minute (rpm) pour l’offre premium et 120 rpm pour l’offre entreprise. Étant donné ces caractéristiques, la recherche sur l’archive complète peut être utilisée pour récupérer rapidement des Publications, et à grande échelle en utilisant des requêtes concurrentes.

Contrairement à Historical PowerTrack, dont l’archive est basée sur un ensemble de fichiers plats de Publications stockés sur disque, l’archive de Publications de la recherche sur l’archive complète ressemble davantage à une base de données en ligne. Comme pour toute base de données, elle prend en charge l’exécution de requêtes sur son contenu. Elle utilise également un *index* pour permettre une récupération des données hautes performances. Avec les endpoints de recherche sur l’archive complète, le langage de requête est composé d’opérateurs PowerTrack, et chacun de ces opérateurs correspond à un attribut JSON de Publication indexé.

De même que pour Historical PowerTrack, certains attributs de Publication sont actualisés à la date à laquelle la requête est effectuée. Par exemple, si vous utilisez la Search API aujourd’hui pour accéder à une Publication publiée en 2010, la description du profil de l’utilisateur, l’emplacement « home » du compte, le nom d’affichage et les métriques de la Publication pour les favoris et les comptes de Retweet seront mis à jour avec les valeurs d’aujourd’hui, et non celles de 2010. 

<div id="metadata-timelines">
  ### Chronologie des métadonnées
</div>

Ci-dessous se trouve une chronologie indiquant à partir de quand les opérateurs de l’endpoint Full-archive search commencent à faire des correspondances. Dans certains cas, la prise en compte par les opérateurs a commencé bien *après* qu’une « convention de communication » soit devenue courante sur X. Par exemple, les @Replies sont apparues comme une convention d’utilisation en 2006, mais ne sont devenues un *objet de première classe* ou un *événement* doté de JSON « d’accompagnement » qu’au début de 2007. En conséquence, faire correspondre les @Replies en 2006 nécessite d’examiner le corps de la Publication, plutôt que de s’appuyer sur les opérateurs PowerTrack `to:` et `in_reply_to_status_id:`.

Les détails fournis ici ont été générés à l’aide de Full-Archive Search (le résultat de centaines de recherches). Cette chronologie n’est pas exhaustive ni parfaitement précise. Si vous identifiez une autre « date de naissance » de filtrage/métadonnées fondamentale pour votre cas d’usage, veuillez nous en informer.

Notez que l’index Search sous-jacent peut être reconstruit. En conséquence, ces détails chronologiques sont susceptibles d’être modifiés.

<div id="2006">
  #### 2006
</div>

* 26 mars - `lang:`. Un exemple de métadonnées de Publication renseignées a posteriori lors de la génération de l’index de recherche.
* 13 juillet - `has:mentions` commence à être pris en compte.
* 6 octobre - `has:symbols`. Les $cashtags (ou symboles) pour discuter des symboles boursiers ne deviennent courants qu’au début de 2009. Jusqu’alors, la plupart des utilisations étaient probablement de l’argot (par exemple, $slang).
* 26 octobre - `has:links` commence à être pris en compte.
* 23 novembre - `has:hashtags` commence à être pris en compte.

<div id="2007">
  #### 2007
</div>

* 30 janvier - Première @reply officielle (in&#95;reply&#95;to&#95;user&#95;id), `reply_to_status_id:` commence à faire le lien.
* 23 août - Les hashtags émergent comme convention courante pour organiser les sujets et les conversations. Première utilisation effective une semaine plus tard.

<div id="2009">
  #### 2009
</div>

* 15 mai - `is:retweet`. Notez que cet opérateur commence à faire correspondre la version « bêta » des Retweets officiels et son motif « Via @ ». Pendant cette période bêta, le verbe de Publication est « post » et la Publication d’origine n’est pas incluse dans le payload.

<div id="filtering-tips">
  ### Conseils de filtrage
</div>

Compte tenu de toutes les informations de chronologie ci-dessus, il est clair qu&#39;il y a beaucoup de détails à prendre en compte lors de la rédaction de filtres pour les API de recherche. Il y a deux éléments clés à considérer :

* Certaines métadonnées ont des dates de « naissance » (« born-on »), de sorte que les filtres peuvent produire des *faux négatifs*. De telles recherches incluent des opérateurs reposant sur des métadonnées qui n&#39;existaient pas pendant tout ou partie de la période de recherche. Par exemple, si vous recherchez des Publications avec l&#39;opérateur `has:images`, vous n&#39;obtiendrez aucun résultat pour les périodes antérieures à juillet 2011. C&#39;est parce que cet opérateur correspond aux photos *natives* (jointes à une Publication à l&#39;aide de l&#39;interface utilisateur de X). Pour obtenir un ensemble de données plus complet de Publications contenant des photos partagées, les filtres pour les périodes avant juillet 2011 devraient contenir des clauses de règle qui correspondent aux URL courantes d&#39;hébergement de photos.
* Certaines métadonnées ont été complétées rétroactivement avec des métadonnées provenant d&#39;une période *postérieure* à celle où la Publication a été publiée sur X.

Plusieurs types d&#39;attributs sont fréquemment ciblés lors de la création de requêtes PowerTrack :

* Profils X
* Publications originales ou partagées
* Classification de la langue des Publications
* Publications géoréférencées
* Médias des liens partagés

Certains de ces éléments ont un comportement spécifique au produit tandis que d&#39;autres ont un comportement identique. Voir ci-dessous pour plus de détails.

<div id="x-profiles">
  #### Profils X
</div>

Les API de recherche renvoient des Publications historiques avec les données du profil utilisateur telles qu’elles sont au *moment de la récupération*. Si vous demandez une Publication datant de 2014, les métadonnées du profil de l’utilisateur refléteront l’état du profil au moment de la requête.

<div id="original-posts-and-retweets">
  #### Publications originales et Retweets
</div>

L’opérateur PowerTrack `_is:retweet_` permet aux utilisateurs d’inclure ou d’exclure les Retweets. Les utilisateurs de cet opérateur doivent disposer de deux stratégies pour la mise en correspondance (ou la non‑correspondance) des Retweets pour les données antérieures à août 2009. Avant août 2009, le contenu même de la Publication doit être vérifié, à l’aide d’une correspondance de phrase exacte, pour détecter les occurrences du motif « @RT » (en réalité, si vous filtrez les Retweets entre mai et août 2009, le motif « Via @ » doit être inclus). Pour les périodes postérieures à août 2009, l’opérateur *is:retweet* est disponible.

<div id="post-language-classifications">
  #### Classification linguistique des Publications
</div>

Pour filtrer les Publications selon leur classification linguistique, les produits historiques de X se comportent de manière assez différente. Lors de la création de l’archive de recherche, toutes les Publications ont été enrichies avec la classification linguistique de X. Par conséquent, l’opérateur lang : est disponible pour l’ensemble de l’archive de Publications.

<div id="geo-referencing-posts">
  #### Référencement géographique des Publications
</div>

Il existe trois façons principales de géoréférencer des Publications :

* **Références géographiques dans le contenu de la Publication.** Le rapprochement basé sur des références géographiques présentes dans le contenu de la Publication, bien que ce soit souvent la méthode la plus difficile puisqu’elle dépend de connaissances locales, est possible sur l’intégralité de l’archive de Publications. [Voici](https://x.com/biz/statuses/28311) un exemple de correspondance géoréférencée de 2006 pour la région de San Francisco, basée sur un filtre « golden gate ».

* **Publications géotaguées par l’utilisateur.** Avec les API de recherche, la possibilité de commencer à faire correspondre des Publications à l’aide de certains opérateurs géographiques (Geo Operators) a débuté en mars 2010, puis avec d’autres en février 2015 :

  * 6 mars 2010 : `has:geo`, `bounding_box:` et `point_radius:`
  * 17 février 2015 : `place_country:` et `place:`

* **Emplacement « domicile » du profil de compte défini par l’utilisateur.** Les opérateurs géographiques de profil (Profile Geo Operators) sont disponibles à la fois dans Historical PowerTrack et dans les API de recherche. Avec les API de recherche, ces métadonnées de géolocalisation de profil sont disponibles à partir de février 2015. Pour les Publications postées avant que les métadonnées de Profile Geo ne soient disponibles, l’opérateur `bio_location:` est disponible et peut être utilisé pour faire correspondre des saisies utilisateur non normalisées.

<div id="shared-links-and-media">
  #### Liens partagés et médias
</div>

En mars 2012, l’enrichissement des URL développées a été introduit. Avant cette date, les payloads des Publications incluaient uniquement l’URL telle que fournie par l’utilisateur. Ainsi, si l’utilisateur incluait une URL raccourcie, il peut être difficile de faire correspondre les URL (développées) d’intérêt. Avec les API de recherche, ces métadonnées sont disponibles à partir de mars 2012.

En juillet 2016, l’enrichissement d’URL amélioré a été introduit. Cette version améliorée fournit le titre HTML et la description d’un site web dans le payload de la Publication, ainsi que des opérateurs pour faire des correspondances sur ces éléments. Ces métadonnées commencent à apparaître en décembre 2014.

En septembre 2016, X a introduit les « pièces jointes natives », où un lien partagé en fin de Publication n’est pas comptabilisé dans la limite de 140 caractères d’une Publication. Les deux enrichissements d’URL s’appliquent toujours à ces liens partagés.

Voici à partir de quand les opérateurs de recherche associés commencent à produire des correspondances :

* 26 octobre 2006 - `has:links`
* 20 juillet 2011 - `has:images` et `has:media`
* Août 2011 - `url:` avec l’[enrichissement Expanded URLs](/fr/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments) Dès septembre 2006, `(url:"spotify.com" OR url:gnip OR url:microsoft OR url:google OR url:youtube)` correspond à http://x.com/Adam/statuses/16602, même s’il n’y a pas de métadonnées urls[] dans twitter&#95;entities et les objets gnip. « youtube.com » est un exemple de contenu de message qui, sans aucune métadonnée urls[], correspond à url:youtube.
* 10 février 2015 - `has:videos` pour les vidéos natives. Entre le 28/08/2010 et le 10/02/2015, cet opérateur correspond aux Publications contenant des liens vers certains sites d’hébergement vidéo comme youtube.com, vimeo.com et vivo.com.
* 1er mai 2016 - `url_title:` et `url_description:`, basés sur l’[enrichissement Enhanced URLs](/fr/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments), généralement disponible. Les premières métadonnées Enhanced URL ont commencé à apparaître en décembre 2014.

<div id="enterprise-search-apis">
  ### API de recherche Enterprise
</div>

Il existe deux API de recherche Enterprise :

* 30-Day Search API - fournit les Tweets publiés au cours des 30 derniers jours.
* Full-Archive Search API - fournit des Tweets dès 2006, en commençant par le premier Tweet publié en mars 2006.

Ces API de recherche partagent une conception commune et la documentation ci-dessous s’applique aux deux. Notez que pour les Tweets créés à partir du 29 septembre 2022, les objets Tweet incluent des métadonnées d’édition de Tweet qui décrivent leur historique de modifications. Consultez la page de notions de base [&quot;Modifier des Tweets&quot;](/fr/x-api/enterprise-gnip-2.0/fundamentals/edit-tweets) pour plus de détails.

Vous trouverez ci-dessous des informations importantes nécessaires lors de l’intégration avec les API de recherche Enterprise :

* Méthodes pour demander des données de Tweets et des décomptes
* Authentification
* Pagination
* Paramètres de requête API et exemples de requêtes
* Charges utiles JSON des réponses d’API et exemples de réponses
* Codes de réponse HTTP

Les API Enterprise offrent un accès à faible latence et haute fidélité, basé sur des requêtes, à l’archive de Tweets. La seule différence entre les deux API est la plage temporelle dans laquelle vous pouvez effectuer une recherche, soit les 30 derniers jours, soit dès 2006. Les plages temporelles peuvent être définies avec une granularité à la minute. Les données de Tweets sont renvoyées dans l’ordre chronologique inverse, en commençant par le Tweet le plus récent qui correspond à votre requête. Les Tweets sont disponibles à partir de l’API de recherche environ 30 secondes après leur publication.

<div id="methods">
  #### Methods
</div>

L’URI de base pour la recherche Enterprise est `https://gnip-api.x.com/search/`.

| Méthode | Description |
| :--- | :--- |
| [POST /search/:product/accounts/:account&#95;name/:label](#SearchRequests) | Récupérer les Tweets des 30 derniers jours qui correspondent à la règle PowerTrack spécifiée. |
| [POST /search/:product/accounts/:account&#95;name/:label/counts](#CountRequests) | Récupérer le nombre de Tweets des 30 derniers jours qui correspondent à la règle PowerTrack spécifiée. |

Où :

* `:product` indique le point de terminaison de recherche auquel vous envoyez vos requêtes, soit `30day` soit `fullarchive`.
* `:account_name` est le nom (sensible à la casse) associé à votre compte, tel qu’il apparaît sur console.gnip.com.
* `:label` est le libellé (sensible à la casse) associé à votre point de terminaison de recherche, tel qu’il apparaît sur console.gnip.com.

Par exemple, si le compte TwitterDev dispose du produit de recherche sur 30 jours avec le libellé « prod » (abréviation de production), les points de terminaison de recherche seraient :

* Point de terminaison de données : [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json)
* Point de terminaison de comptage : [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json)

Votre point de terminaison complet de l’API de recherche Enterprise est affiché sur [https://console.gnip.com](https://console.gnip.com).

Vous trouverez ci-dessous plusieurs exemples de requêtes utilisant un simple outil HTTP en ligne de commande nommé curl. Ces exemples utilisent des URL contenant `:product`, `:account_name` et `:label`. Pour utiliser ces exemples, veillez à mettre à jour les URL avec vos informations.

<div id="authentication">
  #### Authentification
</div>

Toutes les requêtes adressées aux API de recherche Enterprise doivent utiliser l’*authentification HTTP Basic*, construite à partir d’une combinaison valide d’adresse e‑mail et de mot de passe utilisée pour vous connecter à votre compte sur [https://console.gnip.com](https://console.gnip.com). Les identifiants doivent être fournis dans l’en-tête HTTP *Authorization* pour chaque requête.

<div id="requestresponse-behavior">
  #### Comportement des requêtes/réponses
</div>

En utilisant les paramètres `fromDate` et `toDate`, vous pouvez demander n&#39;importe quelle période que l&#39;API prend en charge. L&#39;API de recherche 30-Day fournit des Tweets des 31 derniers jours (même si elle est appelée API « 30-Day », elle met 31 jours à disposition afin de permettre aux utilisateurs d&#39;effectuer des requêtes sur un mois complet). L&#39;API de recherche Full-Archive fournit des Tweets remontant jusqu&#39;au tout premier Tweet (21 mars 2006). Cependant, une seule réponse sera limitée à la plus petite des deux valeurs : votre paramètre « maxResults » ou 31 jours. Si les données correspondantes ou votre plage temporelle dépassent la valeur spécifiée de maxResults ou 31 jours, vous recevrez un jeton « next » que vous devrez utiliser pour paginer le reste de la plage temporelle que vous avez spécifiée.

Par exemple, supposons que vous utilisiez la recherche Full-Archive et que vous souhaitiez tous les Tweets correspondant à votre requête du 1ᵉʳ janvier 2017 au 30 juin 2017. Vous indiquerez cette période complète de six mois dans votre requête en utilisant les paramètres `fromDate` et `toDate`. L&#39;API de recherche répondra avec la première « page » de Tweets, avec un nombre de Tweets correspondant à votre paramètre `maxResults` (qui est de 100 par défaut). En supposant qu&#39;il y ait davantage de Tweets (ce qui sera très probablement le cas), l&#39;API fournira également un jeton « next » qui vous permettra d&#39;effectuer une requête pour la « page » suivante de données. Ce processus est répété jusqu&#39;à ce que l&#39;API ne renvoie plus de jeton « next ». Consultez la section suivante pour plus de détails.

<div id="pagination">
  #### Pagination
</div>

Lorsque vous effectuez à la fois des requêtes de données et de comptage, il est probable qu’il y ait plus de données que ce qui peut être renvoyé dans une seule réponse. Dans ce cas, la réponse inclura un jeton « next ». Le jeton « next » est fourni sous forme d’attribut JSON de niveau racine. Chaque fois qu’un jeton « next » est fourni, il reste des données supplémentaires à récupérer, vous devrez donc continuer à envoyer des requêtes à l’API.

**Remarque :** Le comportement du jeton « next » diffère légèrement pour les requêtes de données et de comptage, et les deux sont décrits ci‑dessous avec des exemples de réponses fournis dans la section Référence de l’API.

<div id="data-pagination">
  ##### Pagination des données
</div>

Les requêtes de données sont susceptibles de générer plus de données qu&#39;il n&#39;est possible d&#39;en renvoyer dans une seule réponse. Chaque requête de données inclut un paramètre qui définit le nombre maximal de Tweets à renvoyer par requête. Ce paramètre `maxResults` est par défaut défini à 100 et peut être configuré dans une plage de 10 à 500. Si votre requête correspond à plus de Tweets que la valeur du paramètre &#39;maxResults&#39; utilisée dans la requête, la réponse inclura un jeton &#39;next&#39; (en tant qu&#39;attribut JSON de niveau racine). Ce jeton &#39;next&#39; est utilisé dans la requête suivante pour récupérer la portion suivante des Tweets correspondants pour cette requête (c&#39;est‑à‑dire la &#39;page&#39; suivante). Des jetons &#39;next&#39; continueront d&#39;être fournis jusqu&#39;à ce que vous ayez atteint la dernière &#39;page&#39; de résultats pour cette requête, et qu&#39;aucun jeton &#39;next&#39; ne soit plus fourni.

Pour demander la &#39;page&#39; suivante de données, vous devez effectuer exactement la même requête que l&#39;originale, y compris les paramètres `query`, `toDate` et `fromDate`, le cas échéant, et inclure également un paramètre de requête &#39;next&#39; défini sur la valeur de la réponse précédente. Cela peut être utilisé avec une requête GET ou POST. Cependant, le paramètre &#39;next&#39; doit être encodé au format URL dans le cas d&#39;une requête GET.

Vous pouvez continuer à transmettre l&#39;élément &#39;next&#39; de votre requête précédente jusqu&#39;à ce que vous ayez reçu tous les Tweets pour la période couverte par votre requête. Lorsque vous recevez une réponse qui n&#39;inclut pas d&#39;élément &#39;next&#39;, cela signifie que vous avez atteint la dernière page et qu&#39;aucune donnée supplémentaire n&#39;est disponible pour la requête et la plage temporelle spécifiées.

<div id="counts-pagination">
  ##### Pagination des counts
</div>

Le point de terminaison `counts` fournit les volumes de Tweet associés à une requête sur une base quotidienne, horaire ou à la minute. Le point de terminaison d’API `counts` renverra un tableau horodaté de décomptes pour une période maximale de 31 jours. Si vous demandez plus de 31 jours de décomptes, un jeton `next` vous sera fourni. Comme pour les jetons `next` de `data`, vous devez effectuer exactement la même requête que l’originale et inclure également un paramètre de requête `next` défini sur la valeur de la réponse précédente.

Au-delà des demandes portant sur plus de 31 jours de décomptes, il existe un autre scénario dans lequel un jeton `next` est fourni. Pour les requêtes à volume plus élevé, il est possible que la génération des décomptes prenne suffisamment de temps pour déclencher un dépassement de délai de la réponse. Lorsque cela se produit, vous recevrez moins de 31 jours de décomptes, mais un jeton `next` vous sera fourni afin de continuer à effectuer des requêtes pour l’ensemble des décomptes. ***Important :*** les dépassements de délai ne renverront que des « buckets » complets – ainsi, 2,5 jours donneraient 2 « buckets » de journée complets.

<div id="additional-notes">
  ##### Notes supplémentaires
</div>

* Lorsque vous utilisez un fromDate ou un toDate dans une requête de recherche, vous n&#39;obtenez des résultats que dans votre plage temporelle. Lorsque vous atteignez le dernier groupe de résultats dans votre plage temporelle, vous ne recevez plus de jeton &#39;next&#39;.
* L&#39;élément &#39;next&#39; peut être utilisé avec n&#39;importe quelle valeur maxResults entre 10 et 500 (avec une valeur par défaut de 100). maxResults détermine combien de Posts sont renvoyés dans chaque réponse, mais ne vous empêche pas, à terme, d&#39;obtenir l&#39;ensemble des résultats.
* L&#39;élément &#39;next&#39; n&#39;expire pas. Plusieurs requêtes utilisant le même paramètre &#39;next&#39; recevront les mêmes résultats, quel que soit le moment où la requête est effectuée.
* Lors de la pagination des résultats à l&#39;aide du paramètre &#39;next&#39;, vous pouvez rencontrer des doublons aux limites de la requête. Votre application doit savoir les gérer.

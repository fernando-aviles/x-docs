<div id="overview">
  ## Overview
</div>

`Enterprise`

*Les API Enterprise sont disponibles uniquement dans le cadre de nos niveaux d’accès gérés. Pour utiliser ces API, vous devez d’abord créer un compte avec notre équipe commerciale Enterprise. Pour en savoir plus, consultez [ici](https://developer.x.com/en/products/x-api/enterprise).*

*Vous pouvez consulter toutes les offres de recherche de Publications de X API [ici](/fr/x-api/enterprise-gnip-2.0/fundamentals/search-api).*

Il existe deux API Enterprise de recherche :

1. L’API 30-Day Search fournit des données des 30 derniers jours.
2. L’API Full-Archive Search fournit un accès complet et instantané à l’intégralité du corpus de données X, depuis la toute première Publication en mars 2006.

Ces API RESTful prennent en charge une seule requête de jusqu’à 2 048 caractères par appel. Les requêtes sont écrites avec la syntaxe de règles PowerTrack – consultez [Rules and filtering](/fr/x-api/enterprise-gnip-2.0/fundamentals/rules-filtering#getting-started-with-enterprise-rules-and-queries) pour plus de détails. Les utilisateurs peuvent spécifier n’importe quelle période, avec une granularité à la minute. Cependant, les réponses seront limitées au plus petit de votre `maxResults` spécifié OU 31 jours et incluront un jeton `next` pour paginer vers l’ensemble de résultats suivant. Si les paramètres de temps ne sont pas spécifiés, l’API renverra les données correspondantes des 30 derniers jours.

Les API Enterprise de recherche offrent un accès à faible latence, avec une fidélité complète et basé sur des requêtes à l’archive des Publications, avec une granularité à la minute. Les données de Publication sont renvoyées dans l’ordre antéchronologique, en commençant par la Publication la plus récente qui correspond à votre requête. Les Publications sont disponibles via l’API de recherche environ 30 secondes après leur publication.

Ces endpoints de recherche fournissent des métadonnées relatives aux Publications éditées. Tous les objets pour les Publications créées depuis le 29 septembre 2022 incluent des métadonnées d’édition de Publication, même si la Publication n’a jamais été modifiée. Chaque fois qu’une Publication est modifiée, un nouvel ID de Publication est créé. L’historique des modifications d’une Publication est documenté par un tableau d’ID de Publication, en commençant par l’id d’origine.

Ces endpoints renverront toujours la modification la plus récente, ainsi que tout historique d’édition. Toute Publication collectée après sa fenêtre de modification de 30 minutes représentera sa version finale. Pour en savoir plus sur les métadonnées d’édition de Publication, consultez la page [Edit Posts fundamentals](/fr/x-api/fundamentals/edit-posts).

Les requêtes incluent un paramètre `maxResults` qui spécifie le nombre maximal de Publications à renvoyer par réponse d’API. Si plus de Publications sont associées à la requête que ce nombre maximal de résultats par réponse, un jeton `next` est inclus dans la réponse. Ces jetons `next` sont utilisés dans les requêtes suivantes pour parcourir l’ensemble complet des Publications associées à la requête.

Ces API Enterprise de recherche fournissent un endpoint *counts* qui permet aux utilisateurs de demander le volume de données associé à leur requête. 

<div id="request-types">
  ### Types de requêtes
</div>

Les API de recherche Enterprise prennent en charge deux types de requêtes :

<div id="search-requests-data">
  #### Search requests (data)
</div>

Les requêtes de recherche vers les API de recherche Enterprise vous permettent de récupérer jusqu&#39;à 500 résultats par réponse pour une période donnée, avec la possibilité d&#39;effectuer une pagination pour obtenir des données supplémentaires. À l&#39;aide du paramètre maxResults, vous pouvez spécifier des tailles de page plus petites pour les cas d&#39;usage d&#39;affichage (permettant à votre utilisateur de demander davantage de résultats si nécessaire) ou des tailles de page plus grandes (jusqu&#39;à 500) pour des extractions de données plus volumineuses. Les données sont renvoyées dans l&#39;ordre chronologique inverse et sont conformes au moment où elles sont renvoyées.

<div id="counts-requests-post-count">
  #### Requêtes de comptage (nombre de Publications)
</div>

Les requêtes de comptage permettent de récupérer des volumes d’activité historiques, qui reflètent le nombre d’activités correspondant à une requête donnée pendant la période demandée. La réponse vous fournit essentiellement un histogramme de ces comptes, regroupés par jour, heure ou minute (le regroupement par défaut est *hour*). Il est important de noter que les résultats de comptage ne reflètent pas toujours les événements de conformité (par exemple, les suppressions de Publications) qui se produisent bien après (7 jours ou plus) la publication d’une Publication ; par conséquent, il est normal que la métrique de comptage ne corresponde pas toujours à celle d’une requête de données pour la même requête.

**Note de facturation :** chaque requête – *y compris les requêtes de pagination* – effectuée sur les points de terminaison de données et de comptage est comptabilisée comme une requête facturée. Ainsi, s’il existe plusieurs pages de résultats pour une seule requête, parcourir les X pages de résultats équivaut à X requêtes pour la facturation.

<div id="data-updates-and-mutability">
  ### Mises à jour des données et mutabilité
</div>

Avec les API de recherche Enterprise, certaines des données au sein d’une Publication sont mutables, c’est-à-dire qu’elles peuvent être mises à jour ou modifiées après l’archivage initial.

Ces données mutables se répartissent en deux catégories :

* Métadonnées de l’objet User :
  * @handle de l’utilisateur (l’ID numérique ne change jamais)
  * Description de la bio
  * Compteurs : statuts, followers, amis, favoris, listes
  * Localisation du profil
  * Autres détails tels que le fuseau horaire et la langue
* Statistiques de la Publication – c’est-à-dire tout ce qui peut être modifié sur la plateforme par les actions des utilisateurs (exemples ci-dessous) :
  * Nombre de favoris
  * Nombre de Retweets

Dans la plupart de ces cas, les API de recherche renverront les données telles qu’elles existent sur la plateforme au *moment de la requête*, plutôt qu’au moment de la génération de la Publication. Cependant, dans le cas de requêtes utilisant des opérateurs de sélection (par exemple from, to, @, is:verified), cela peut ne pas être le cas. Les données sont mises à jour régulièrement dans notre index, avec une fréquence accrue pour les périodes les plus récentes. Par conséquent, dans certains cas, les données renvoyées peuvent ne pas correspondre exactement aux données actuelles telles qu’elles s’affichent sur X.com, mais correspondent aux données au moment où elles ont été indexées pour la dernière fois.

Notez que ce problème d’incohérence s’applique uniquement aux requêtes où l’opérateur porte sur des données mutables. Un exemple est le filtrage par noms d’utilisateur, et la meilleure solution de contournement consiste à utiliser les ID numériques des utilisateurs plutôt que les @handles pour ces requêtes.

<div id="single-vs-multi-threaded-requests">
  ### Requêtes mono‑thread vs multi‑thread
</div>

Chaque client dispose d’une limite de débit définie pour son endpoint de recherche. La limite de débit par minute par défaut pour la recherche Full‑Archive est de 120 requêtes par minute, soit une moyenne de 2 requêtes par seconde (QPS). Cette moyenne de QPS signifie qu’en théorie, 2 requêtes peuvent être envoyées à l’API chaque seconde. Étant donné la fonctionnalité de pagination du produit, si une requête sur un an a un million de Publications qui lui sont associées, réparties uniformément sur l’année, plus de 2 000 requêtes seraient nécessaires (en supposant un `maxResults` de 500) pour recevoir toutes les données. En supposant qu’il faille deux secondes par Réponse, cela représente 4 000 secondes (ou un peu plus d’une heure) pour récupérer toutes ces données en série, de manière séquentielle, via un seul thread (1 requête par seconde en utilisant le jeton « next » de la Réponse précédente). Pas mal !

Considérons maintenant la situation où douze threads parallèles sont utilisés pour recevoir les données. En supposant une répartition uniforme du million de Publications sur la période d’un an, vous pouvez répartir les requêtes sur douze threads parallèles (multi‑thread) et utiliser davantage la limite de débit par seconde pour un seul « job ». En d’autres termes, vous pourriez exécuter un thread par mois qui vous intéresse et, ce faisant, les données pourraient être récupérées 12 fois plus rapidement (soit environ 6 minutes).

Cet exemple multi‑thread s’applique tout aussi bien à l’endpoint counts. Par exemple, si vous souhaitez recevoir les décomptes de Publications pour une période de deux ans, vous pouvez effectuer une requête mono‑thread et revenir en arrière dans les décomptes par tranches de 31 jours. En supposant qu’il faille 2 secondes par Réponse, il faudrait environ 48 secondes pour effectuer les 24 requêtes API et récupérer l’ensemble des décomptes. Cependant, vous avez également la possibilité d’effectuer plusieurs requêtes d’un mois en parallèle. En effectuant 12 requêtes par seconde, l’ensemble des décomptes pourrait être récupéré en environ 2 secondes.

<div id="retry-logic">
  ### Logique de réessai
</div>

Si vous rencontrez une erreur 503 avec les API de recherche Enterprise, il est probable qu’il s’agisse d’une erreur transitoire qui peut être résolue en réessayant la requête après un court laps de temps.

Si la requête échoue 4 fois de suite et que vous avez attendu au moins 10 minutes entre chaque échec, procédez comme suit pour le dépannage :

* Renvoyez la requête après avoir réduit l’intervalle de temps couvert. Répétez cette opération jusqu’à atteindre une fenêtre de 6 heures si nécessaire.
* Si vous combinez un grand nombre de termes avec l’opérateur OR, divisez-les en règles distinctes et réessayez chaque règle individuellement.
* Si vous utilisez un grand nombre d’exclusions dans votre règle, réduisez le nombre de termes exclus dans la règle et réessayez.

<div id="getting-started-with-enterprise-search-posts-30-day-api">
  ### Premiers pas avec l’API entreprise Search Posts : 30-Day
</div>

L’API entreprise Search Posts : 30-Day vous fournit les Publications créées au cours des 30 derniers jours. Les Publications sont identifiées et renvoyées en fonction de la requête que vous spécifiez dans votre demande. Une requête est une règle qui définit ce que la Publication que vous récupérez doit contenir. Dans ce tutoriel, nous allons rechercher des Publications provenant du compte X @XDevelopers et rédigées en anglais.

Les Publications que vous recevez dans votre payload peuvent être au format data, qui vous fournit le payload complet de la Publication, ou au format counts, qui vous donne des données de comptage numériques sur les Publications correspondantes. Nous utiliserons cURL pour effectuer des requêtes vers les endpoints data et counts.

Vous aurez besoin des éléments suivants :

* [An enterprise account]https://developer.x.com/en/products/x-api/enterprise
* Votre nom d’utilisateur, votre mot de passe et le nom de votre compte
* Le label associé à votre endpoint de recherche, tel qu’il apparaît sur console.gnip.com

<div id="accessing-the-data-endpoint">
  #### Accéder au point de terminaison de données
</div>

Le point de terminaison de données nous fournira la charge utile (payload) complète des Publications correspondantes. Nous utiliserons les opérateurs `from:` et `lang:` pour trouver les Publications provenant de @XDevelopers en anglais. *Pour plus d’opérateurs, [cliquez ici](/fr/x-api/enterprise-gnip-2.0/fundamentals/search-api#enterprise-operators).*

<div id="product-overview">
  ### Présentation du produit
</div>

L’offre Full-archive Search de niveau entreprise a été lancée en août 2015, et la version de niveau premium en février 2018. Ces produits de recherche permettent aux clients d’accéder immédiatement à n’importe quelle Publication disponible publiquement. Avec Full-archive Search, vous soumettez une seule requête et recevez une réponse selon le modèle REST classique. Full-archive Search met en œuvre une pagination de (jusqu’à) 500 Publications par réponse et prend en charge jusqu’à 60 requêtes par minute (rpm) comme limite de débit pour le niveau premium, et 120 rpm pour le niveau entreprise. Compte tenu de ces caractéristiques, Full-archive Search peut être utilisé pour récupérer rapidement des Publications, et à grande échelle à l’aide de requêtes concurrentes.

Contrairement à Historical PowerTrack, dont l’archive est basée sur un ensemble de fichiers plats de Publications sur disque, l’archive de Publications de Full-archive Search ressemble davantage à une base de données en ligne. Comme pour toutes les bases de données, elle prend en charge l’exécution de requêtes sur son contenu. Elle utilise également un *index* pour permettre une récupération performante des données. Avec les points de terminaison Full-archive Search, le langage de requête est composé de PowerTrack Operators, et chacun de ces Operators correspond à un attribut JSON de Publication qui est indexé.

De même que pour Historical PowerTrack, certains attributs de Publication sont actualisés au moment où une requête est effectuée. Par exemple, si vous utilisez Search API aujourd’hui pour accéder à une Publication publiée en 2010, la description du profil de l’utilisateur, l’emplacement « domicile » du compte, le nom d’affichage, ainsi que les métriques de la Publication pour les nombres de favoris et de Retweets seront mis à jour avec les valeurs actuelles et non celles de 2010. 

<div id="metadata-timelines">
  ### Chronologie des métadonnées
</div>

Vous trouverez ci-dessous une chronologie indiquant à partir de quand les opérateurs de l’endpoint de recherche dans l’archive complète commencent à faire correspondre les éléments. Dans certains cas, la correspondance par opérateur n’a commencé que bien *après* qu’une « convention de communication » soit devenue courante sur X. Par exemple, les @Replies sont apparues comme convention d’usage en 2006, mais ne sont devenues un *objet de première classe* ou un *événement* avec un JSON « associé » qu’au début de l’année 2007. En conséquence, pour faire correspondre les @Replies en 2006, il faut examiner le corps de la Publication, plutôt que de s’appuyer sur les opérateurs PowerTrack `to:` et `in_reply_to_status_id:`.

Les détails fournis ici ont été générés à l’aide de la recherche dans l’archive complète (résultat de centaines de recherches). Cette chronologie n’est pas complète ni parfaitement précise à 100 %. Si vous identifiez une autre « date de naissance » de filtrage ou de métadonnées fondamentale pour votre cas d’usage, merci de nous en informer.

Notez que l’index de recherche sous-jacent peut être reconstruit. En conséquence, ces détails chronologiques sont susceptibles d’être modifiés.

<div id="filtering-tips">
  ### Conseils de filtrage
</div>

Compte tenu de toutes les informations ci-dessus sur la chronologie, il est clair qu’il y a de nombreux détails à prendre en compte lors de la conception de filtres pour les API de recherche. Deux éléments clés sont à considérer :

* Certaines métadonnées ont des dates de « naissance », de sorte que les filtres peuvent entraîner des *faux négatifs*. Ces recherches incluent des opérateurs qui dépendent de métadonnées qui n’existaient pas pour tout ou partie de la période de recherche. Par exemple, si vous recherchez des Publications avec l’opérateur `has:images`, vous n’aurez aucune correspondance pour les périodes antérieures à juillet 2011. Cela vient du fait que cet opérateur correspond aux photos *natives* (jointes à une Publication via l’interface utilisateur de X). Pour obtenir un ensemble de données de Publications de partage de photos plus exhaustif, les filtres pour la période antérieure à juillet 2011 devraient contenir des clauses de règle qui correspondent aux URL courantes d’hébergement de photos.
* Certaines métadonnées ont été enrichies a posteriori par des métadonnées provenant d’une période *postérieure* à la Publication sur X.

Plusieurs types d’attributs sont fréquemment utilisés lors de la création de requêtes PowerTrack :

* Profils X
* Publications originales ou partagées
* Classification de la langue des Publications
* Publications géoréférencées
* Médias des liens partagés

Certains de ces éléments présentent un comportement spécifique à un produit, tandis que d’autres ont un comportement identique. Reportez-vous aux sections ci-dessous pour plus de détails.

<div id="x-profiles">
  #### Profils X
</div>

Les API de recherche renvoient des Publications historiques avec l’ensemble des données de profil utilisateur telles qu’elles sont au *moment de leur récupération*. Si vous demandez une Publication de 2014, les métadonnées du profil de l’utilisateur correspondront à son état au moment de la requête.

<div id="original-posts-and-retweets">
  #### Publications originales et Retweets
</div>

L’opérateur PowerTrack `_is:retweet_` permet aux utilisateurs d’inclure ou d’exclure les Retweets. Les utilisateurs de cet opérateur doivent adopter deux stratégies de correspondance (ou de non-correspondance) des Retweets pour les données antérieures à août 2009. Avant août 2009, le contenu de la publication elle-même doit être vérifié, à l’aide d’une correspondance de phrase exacte, afin de repérer les occurrences du motif « @RT » (en fait, si vous filtrez des Retweets entre mai et août 2009, le motif « Via @ » doit être inclus). Pour les périodes postérieures à août 2009, l’opérateur *is:retweet* est disponible.

<div id="post-language-classifications">
  #### Classifications linguistiques des Publications
</div>

Pour filtrer selon la classification linguistique d&#39;une Publication, les produits historiques de X fonctionnent de manière assez différente. Lorsque l&#39;archive de recherche a été créée, toutes les Publications ont été complétées rétroactivement avec la classification linguistique de X. Par conséquent, l&#39;opérateur lang : est disponible pour l&#39;intégralité de l&#39;archive de Publications.

<div id="geo-referencing-posts">
  #### Géoréférencement des Publications
</div>

Il existe trois principales façons de géoréférencer des Publications :

* **Références géographiques dans le message de la Publication.** Faire correspondre des références géographiques présentes dans le message de la Publication, bien que ce soit souvent la méthode la plus difficile puisqu’elle dépend de connaissances locales, est une option pour l’ensemble de l’archive des Publications. [Voici](https://x.com/biz/statuses/28311) un exemple de correspondance géoréférencée datant de 2006 pour la région de San Francisco, basé sur un filtre « golden gate ».

* **Publications géo‑taguées par l’utilisateur.** Avec les API de recherche, la possibilité de commencer à faire correspondre des Publications à l’aide de certains opérateurs Geo a débuté en mars 2010, et avec d’autres en février 2015 :

  * 6 mars 2010 : `has:geo`, `bounding_box:` et `point_radius:`
  * 17 février 2015 : `place_country:` et `place:`

* **Lieu « domicile » du profil de compte défini par l’utilisateur.** Les opérateurs Geo de profil sont disponibles à la fois dans Historical PowerTrack et dans les API de recherche. Avec les API de recherche, ces métadonnées géo de profil sont disponibles à partir de février 2015. Pour les Publications publiées avant que les métadonnées géo de profil ne soient disponibles, l’opérateur `bio_location:` est disponible et peut être utilisé pour faire correspondre une saisie utilisateur non normalisée.

<div id="shared-links-and-media">
  #### Liens partagés et médias
</div>

En mars 2012, l’enrichissement d’URL développée a été introduit. Avant cette date, les payloads de Publication ne contenaient que l’URL telle que fournie par l’utilisateur. Ainsi, si l’utilisateur incluait une URL raccourcie, il pouvait être difficile de faire correspondre les URL (développées) d’intérêt. Avec les Search APIs, ces métadonnées sont disponibles à partir de mars 2012.

En juillet 2016, l’enrichissement d’URL amélioré a été introduit. Cette version améliorée fournit le titre HTML et la description d’un site web dans le payload de la Publication, ainsi que des opérateurs permettant d’effectuer des correspondances dessus. Ces métadonnées commencent à apparaître en décembre 2014.

En septembre 2016, X a introduit les « native attachments » où un lien partagé terminal n’est pas comptabilisé dans la limite de 140 caractères d’une Publication. Les deux enrichissements d’URL s’appliquent toujours à ces liens partagés.

Voici à partir de quand les Search Operators associés commencent à faire des correspondances :

* 26 octobre 2006 - `has:links`
* 20 juillet 2011 - `has:images` et `has:media`
* Août 2011 - `url:` avec l’[enrichissement Expanded URLs](/fr/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments) Dès septembre 2006, `(url:"spotify.com" OR url:gnip OR url:microsoft OR url:google OR url:youtube)` correspond à http://x.com/Adam/statuses/16602, même s’il n’y a aucune métadonnée urls[] dans twitter&#95;entities et les objets gnip. « youtube.com » est un exemple de contenu de message qui, sans aucune métadonnée urls[], correspond à url:youtube.
* 10 février 2015 - `has:videos` pour les vidéos natives. Entre le 28/08/2010 et le 10/02/2015, cet opérateur correspond aux Publications contenant des liens vers certains sites d’hébergement vidéo tels que youtube.com, vimeo.com et vivo.com.
* 1er mai 2016 - `url_title:` et `url_description:`, basés sur l’[enrichissement Enhanced URLs](/fr/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments), généralement disponible. Les premières métadonnées Enhanced URL ont commencé à apparaître en décembre 2014.

<div id="enterprise-search-apis">
  ### API de recherche Enterprise
</div>

Il existe deux API de recherche Enterprise :

* 30-Day Search API - fournit les Tweets publiés au cours des 30 derniers jours.
* Full-Archive Search API - fournit les Tweets depuis 2006, en commençant par le premier Tweet publié en mars 2006.

Ces API de recherche partagent une conception commune et la documentation ci-dessous s’applique aux deux. Notez que, pour les Tweets créés à partir du 29 septembre 2022, les objets Tweet incluront des métadonnées d’édition de Tweet qui décrivent leur historique de modifications. Consultez la page de notions fondamentales [&quot;Edit Tweets&quot;](/fr/x-api/enterprise-gnip-2.0/fundamentals/edit-tweets) pour plus de détails.

Vous trouverez ci-dessous des détails importants nécessaires lors de l’intégration avec les API de recherche Enterprise :

* Méthodes pour récupérer les données de Tweet et les comptages de Tweets
* Authentification
* Pagination
* Paramètres des requêtes API et exemples de requêtes
* Corps JSON des réponses d’API et exemples de réponses
* Codes de réponse HTTP

Les API Enterprise offrent un accès à faible latence, avec fidélité complète et basé sur des requêtes à l’archive des Tweets. La seule différence entre les deux API est la période sur laquelle vous pouvez effectuer une recherche, soit les 30 derniers jours, soit depuis 2006. Les fenêtres temporelles peuvent être spécifiées avec une granularité à la minute. Les données de Tweet sont renvoyées dans l’ordre chronologique inverse, en commençant par le Tweet le plus récent qui correspond à votre requête. Les Tweets sont disponibles via l’API de recherche environ 30 secondes après leur publication.

<div id="methods">
  #### Méthodes
</div>

L’URI de base pour la recherche Enterprise est `https://gnip-api.x.com/search/`.

| Méthode | Description |
| :--- | :--- |
| [POST /search/:product/accounts/:account&#95;name/:label](#SearchRequests) | Récupère les Tweets des 30 derniers jours qui correspondent à la règle PowerTrack spécifiée. |
| [POST /search/:product/accounts/:account&#95;name/:label/counts](#CountRequests) | Récupère le nombre de Tweets des 30 derniers jours qui correspondent à la règle PowerTrack spécifiée. |

Où :

* `:product` indique l’endpoint de recherche auquel vous adressez vos requêtes, soit `30day` soit `fullarchive`.
* `:account_name` est le nom (sensible à la casse) associé à votre compte, tel qu’affiché sur console.gnip.com.
* `:label` est l’étiquette (sensible à la casse) associée à votre endpoint de recherche, telle qu’affichée sur console.gnip.com.

Par exemple, si le compte TwitterDev dispose du produit de recherche 30 jours avec l’étiquette « prod » (abréviation de « production »), les endpoints de recherche seraient :

* Endpoint de données : [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json)
* Endpoint de comptage : [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json)

Votre endpoint complet de l’API de recherche Enterprise est indiqué sur [https://console.gnip.com](https://console.gnip.com).

Vous trouverez ci-dessous plusieurs exemples de requêtes utilisant un utilitaire HTTP simple appelé curl. Ces exemples utilisent des URL avec `:product`, `:account_name` et `:label`. Pour utiliser ces exemples, veillez à mettre à jour les URL avec vos propres informations.

<div id="authentication">
  #### Authentification
</div>

Toutes les requêtes adressées aux API de recherche Enterprise doivent utiliser l’*authentification HTTP Basic*, reposant sur une combinaison valide d’adresse e-mail et de mot de passe utilisée pour vous connecter à votre compte sur [https://console.gnip.com](https://console.gnip.com). Les identifiants doivent être transmis dans l’en-tête HTTP *Authorization* pour chaque requête.

<div id="requestresponse-behavior">
  #### Comportement des requêtes/réponses
</div>

En utilisant les paramètres `fromDate` et `toDate`, vous pouvez demander n’importe quelle période prise en charge par l’API. L’API de recherche sur 30 jours fournit des Tweets issus des 31 derniers jours (même si elle est appelée « API sur 30 jours », elle met 31 jours à disposition afin de permettre aux utilisateurs d’effectuer des requêtes sur des mois complets). L’API de recherche Full-Archive fournit des Tweets remontant jusqu’au tout premier Tweet (21 mars 2006). Cependant, une seule réponse sera limitée à la valeur la plus faible entre votre paramètre « maxResults » et 31 jours. Si les données correspondantes ou votre plage temporelle dépassent votre valeur « maxResults » ou 31 jours, vous recevrez un jeton « next » que vous devrez utiliser pour paginer le reste de la plage temporelle spécifiée.

Par exemple, supposons que vous utilisiez la recherche Full-Archive et que vous souhaitiez tous les Tweets correspondant à votre requête du 1er janvier 2017 au 30 juin 2017. Vous indiquerez cette période complète de six mois dans votre requête en utilisant les paramètres `fromDate` et `toDate`. L’API de recherche répondra avec la première « page » de Tweets, avec un nombre de Tweets correspondant à votre paramètre `maxResults` (dont la valeur par défaut est 100). En supposant qu’il y ait davantage de Tweets (et il est très probable qu’il y en ait), l’API fournira également un jeton « next » qui vous permettra d’envoyer une requête pour la « page » suivante de données. Ce processus est répété jusqu’à ce que l’API ne renvoie plus de jeton « next ». Consultez la section suivante pour plus de détails.

<div id="pagination">
  #### Pagination
</div>

Lors de l’envoi de requêtes portant à la fois sur les données et sur les comptages, il est probable qu’il y ait plus de données que ce qui peut être renvoyé dans une seule réponse. Dans ce cas, la réponse inclura un jeton « next ». Le jeton « next » est fourni en tant qu’attribut JSON au niveau racine. Chaque fois qu’un jeton « next » est fourni, cela signifie qu’il y a des données supplémentaires à récupérer et vous devrez donc continuer à effectuer des requêtes vers l’API.

**Remarque :** Le comportement du jeton « next » diffère légèrement entre les requêtes de données et les requêtes de comptage, et les deux sont décrits ci-dessous avec des exemples de réponses fournis dans la section Référence de l’API.

<div id="data-pagination">
  ##### Pagination des données
</div>

Les requêtes de données génèrent probablement plus de données qu&#39;il n&#39;est possible d&#39;en renvoyer dans une seule réponse. Chaque requête de données inclut un paramètre qui définit le nombre maximal de Tweets à renvoyer par requête. Ce paramètre `maxResults` est défini par défaut sur 100 et peut être fixé dans une plage de 10 à 500. Si votre requête correspond à plus de Tweets que la valeur du paramètre `maxResults` utilisée dans la requête, la réponse inclura un jeton `next` (en tant qu&#39;attribut JSON de niveau racine). Ce jeton `next` est utilisé dans la requête suivante pour récupérer la portion suivante des Tweets correspondants pour cette requête (c.-à-d. la « page » suivante). Des jetons `next` continueront d&#39;être fournis jusqu&#39;à ce que vous ayez atteint la dernière « page » de résultats pour cette requête, c&#39;est-à-dire lorsqu&#39;aucun jeton `next` n&#39;est fourni.

Pour demander la « page » suivante de données, vous devez effectuer exactement la même requête que l&#39;originale, y compris les paramètres `query`, `toDate` et `fromDate`, s&#39;ils sont utilisés, et inclure également un paramètre de requête `next` défini sur la valeur de la réponse précédente. Cela peut être utilisé avec une requête GET ou POST. Cependant, le paramètre `next` doit être encodé dans l&#39;URL dans le cas d&#39;une requête GET.

Vous pouvez continuer à transmettre l&#39;élément `next` de votre requête précédente jusqu&#39;à ce que vous ayez reçu tous les Tweets de la période couverte par votre requête. Lorsque vous recevez une réponse qui n&#39;inclut pas d&#39;élément `next`, cela signifie que vous avez atteint la dernière page et qu&#39;aucune donnée supplémentaire n&#39;est disponible pour la requête et la plage temporelle spécifiées.

<div id="counts-pagination">
  ##### Pagination des décomptes
</div>

Le point de terminaison `counts` fournit les volumes de Tweets associés à une requête, sur une base quotidienne, horaire ou par minute. Le point de terminaison d’API `counts` renverra un tableau horodaté de décomptes correspondant à un maximum de 31 jours de résultats. Si vous demandez plus de 31 jours de décomptes, un jeton `next` vous sera fourni. Comme pour les jetons `next` de data, vous devez effectuer exactement la même requête que l’originale et inclure également un paramètre de requête `next` défini sur la valeur de la réponse précédente.

Au-delà des requêtes portant sur plus de 31 jours de décomptes, il existe un autre scénario dans lequel un jeton `next` est fourni. Pour les requêtes à volume plus élevé, il est possible que la génération des décomptes prenne suffisamment de temps pour déclencher un délai d’expiration de la réponse. Lorsque cela se produit, vous recevrez moins de 31 jours de décomptes, mais un jeton `next` vous sera fourni afin de continuer à effectuer des requêtes pour l’ensemble de la charge utile de décomptes. ***Important :*** les délais d’expiration ne renvoient que des « segments » complets : ainsi, 2,5 jours se traduiront par 2 segments de journée complets.

<div id="additional-notes">
  ##### Notes supplémentaires
</div>

* Lorsque vous utilisez un `fromDate` ou un `toDate` dans une requête de recherche, vous n&#39;obtenez que des résultats compris dans votre plage temporelle. Lorsque vous atteignez le dernier groupe de résultats dans votre plage temporelle, vous ne recevez pas de jeton `next`.
* L&#39;élément `next` peut être utilisé avec n&#39;importe quelle valeur `maxResults` comprise entre 10 et 500 (avec une valeur par défaut de 100). Le paramètre `maxResults` détermine combien de Tweets sont renvoyés dans chaque réponse, mais ne vous empêche pas d&#39;obtenir au final l&#39;ensemble des résultats.
* L&#39;élément `next` n&#39;expire pas. Plusieurs requêtes utilisant le même paramètre `next` recevront les mêmes résultats, indépendamment du moment où la requête est effectuée.
* Lorsque vous parcourez des résultats en utilisant le paramètre `next`, vous pouvez rencontrer des doublons aux limites de la requête. Votre application doit être tolérante à ces doublons.

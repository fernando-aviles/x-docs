Présentation

`Enterprise`

L’API Account Activity vous permet de vous abonner en temps réel aux activités liées à un compte utilisateur via des webhooks. Cela signifie que vous pouvez recevoir en temps réel des Publications, des Direct Messages et d’autres événements de compte provenant d’un ou de plusieurs comptes que vous possédez ou auxquels vous êtes abonné, via une seule connexion.

Vous recevrez toutes les activités suivantes pour chaque abonnement utilisateur associé à votre inscription de webhook :

| Activity types |     |
| :--- | :--- |
| * Publications (par l’utilisateur)  <br />    <br />* Suppressions de Publications (par l’utilisateur)<br />* @mentions (de l’utilisateur)<br />* Réponses (vers ou depuis l’utilisateur)<br />* Retweets (par l’utilisateur ou concernant l’utilisateur)<br />* Quote Tweets (par l’utilisateur ou concernant l’utilisateur)<br />* Retweets de Quote Tweets (par l’utilisateur ou concernant l’utilisateur)<br />* J’aime (par l’utilisateur ou concernant l’utilisateur)<br />* Abonnements (par l’utilisateur ou à l’utilisateur)  <br />    <br />* Désabonnements (par l’utilisateur) | * Blocages (par l’utilisateur)<br />* Déblocages (par l’utilisateur)<br />* Mises en sourdine (par l’utilisateur)<br />* Annulations de mise en sourdine (par l’utilisateur)<br />* Direct Messages envoyés (par l’utilisateur)<br />* Direct Messages reçus (par l’utilisateur)<br />* Indicateurs de frappe (vers l’utilisateur)<br />* Accusés de lecture (vers l’utilisateur)<br />* Révocations d’abonnement (par l’utilisateur) |

**Veuillez noter** - Nous ne fournissons pas les données du fil d’actualité de la page d’accueil via l’API Account Activity. Veuillez utiliser [GET statuses/home&#95;timeline](https://developer.x.com/en/docs/x-api/v1/tweets/timelines/overview) pour récupérer ces données.

<div id="manage-webhooks-and-subscribed-users">
  ## Gérer les webhooks et les utilisateurs abonnés
</div>

**⏱ Lecture de 10 min**

L&#39;API Enterprise Account Activity fournit des messages JSON via webhook chaque fois que des événements sont associés à des comptes X abonnés à votre service. X envoie ces activités à votre webhook enregistré. Dans les étapes suivantes, vous apprendrez à gérer les webhooks et les utilisateurs abonnés.

Vous apprendrez à enregistrer, afficher et supprimer à la fois des webhooks et des utilisateurs abonnés. Nous utiliserons de simples commandes cURL pour effectuer des requêtes vers les différents endpoints de l&#39;API. cURL est un outil en ligne de commande permettant d&#39;envoyer ou de récupérer des données en utilisant la syntaxe d&#39;URL.

Vous aurez besoin de :

* D&#39;une application X enregistrée - *[inscrivez-vous ici](https://developer.x.com/content/developer-twitter/en/apps)*
* D&#39;un Bearer Token - *[en savoir plus](/fr/resources/fundamentals/authentication#using-and-generating-an-app-only-bearer-token)*
* D&#39;un webhook qui réussit un Challenge-Response Check (CRC) - *[en savoir plus](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks)*
* D&#39;un compte Enterprise - *[postulez ici]https://developer.x.com/en/products/x-api/enterprise*

*Avant de commencer, nous vous recommandons de consulter notre [dépôt GitHub ici](https://github.com/xdevplatform/account-activity-dashboard), qui fournit une application web d&#39;exemple et des scripts d&#39;aide pour commencer avec l&#39;API Enterprise Account Activity de X*

<div id="managing-a-webhook">
  #### Gestion d’un webhook :
</div>

L’utilisation d’un webhook vous permet de vous abonner aux activités en temps réel liées à un compte utilisateur via une seule connexion. 

<Tabs>
  <Tab title="Ajout d’un webhook">
    Commençons par enregistrer une nouvelle URL de webhook pour le contexte d’application donné.

    L’URL sera validée via une requête CRC avant d’être enregistrée. Une fois que vous avez enregistré un webhook, veillez à documenter l’ID du webhook, car vous en aurez besoin plus tard.

    Copiez la requête cURL suivante dans votre ligne de commande après avoir modifié les éléments suivants :

    * **URL** `<URL>` par ex. `https://yourdomain.com/webhooks/twitter/`

    * **Consumer key** `<CONSUMER_KEY>` par ex. `xvz1evFS4wEEPTGEFPHBog`

    * **Access token** `<ACCESS_TOKEN>` par ex.  `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request POST --url 'https://api.x.com/1.1/account_activity/webhooks.json?url=<URL>' --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>

  <Tab title="Affichage d’un webhook">
    Nous allons exécuter la commande suivante pour renvoyer toutes les URL de webhooks enregistrés et leur état pour l’application donnée.

    Copiez la requête cURL suivante dans votre ligne de commande après avoir modifié les éléments suivants :

    * **Bearer Token** `<BEARER_TOKEN>` par ex. `AAAAAAAAAAAA0%2EUifi76ZC9Ub0wn...`

      ```curl --request GET --url https://api.x.com/1.1/account_activity/webhooks.json --header 'authorization: Bearer <BEARER_TOKEN>'
      ```
  </Tab>

  <Tab title="Suppression d’un webhook">
    Pour supprimer un webhook de la configuration de l’application fournie, copiez la requête cURL suivante dans votre ligne de commande après avoir modifié les éléments suivants :

    * **Webhook ID** `<:WEBHOOK_ID>` par ex. `1234567890`

    * **Consumer key** `<CONSUMER_KEY>` par ex. `xvz1evFS4wEEPTGEFPHBog`

    * **Access token** `<ACCESS_TOKEN>` par ex.  `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```curl --request DELETE --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>.json --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>
</Tabs>

<div id="managing-subscribed-users">
  #### Gestion des utilisateurs abonnés :
</div>

Une fois que vous avez enregistré un webhook, vous pouvez ajouter un utilisateur abonné à l’Account Activity API pour commencer à recevoir les activités de son compte.

<Tabs>
  <Tab title="Ajout d’un abonnement">
    Nous allons commencer par abonner un utilisateur afin que vous receviez tous les types d’événements.

    Copiez la requête cURL suivante dans votre ligne de commande après avoir apporté les modifications suivantes :

    * **Webhook ID** `<:WEBHOOK_ID>` par exemple `1234567890`

    * **Nom de la consumer key** `<CONSUMER_KEY>` par exemple `xvz1evFS4wEEPTGEFPHBog`

    * **Access token de l’utilisateur abonné** `<SUBSCRIBING_USER'S_ACCESS_TOKEN>` par exemple `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request POST --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>/subscriptions/all.json --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<SUBSCRIBING_USER'S_ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>

  <Tab title="Affichage des abonnements">
    Pour afficher la liste de tous les abonnements aux types d’activité pour un webhook donné, copiez la requête cURL suivante dans votre ligne de commande après avoir apporté les modifications suivantes :

    * **Webhook ID** `<:WEBHOOK_ID>` par exemple `1234567890`

    * **Bearer token** `<BEARER_TOKEN>` par exemple `AAAAAAAAAAAA0%2EUifi76ZC9Ub0wn...`

      ```
      curl --request GET --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>/subscriptions/all/list.json --header 'authorization: Bearer <BEARER_TOKEN>'
      ```
  </Tab>

  <Tab title="Suppression d’un abonnement">
    Après la désactivation, tous les événements pour l’utilisateur à l’origine de la requête ne seront plus envoyés à l’URL du webhook.

    Pour désactiver un abonnement pour le contexte utilisateur et l’application fournis, copiez la requête cURL suivante dans votre ligne de commande après avoir apporté les modifications suivantes :

    * **Webhook ID** `<:WEBHOOK_ID>` par exemple `1234567890`

    * **Consumer key** `<CONSUMER_KEY>` par exemple `xvz1evFS4wEEPTGEFPHBog`

    * **Access token de l’utilisateur abonné** `<SUBSCRIBING_USER'S_ACCESS_TOKEN>` par exemple `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request DELETE --url https://api.x.com/1.1/account_activity/webhooks/:WEBHOOK_ID/subscriptions/all.json --header 'authorization: OAuth oauth_consumer_key="CONSUMER_KEY", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="SUBSCRIBED_USER'S_ACCESS_TOKEN", oauth_version="1.0"'
      ```
  </Tab>
</Tabs>

Excellent travail ! Vous devriez maintenant pouvoir gérer vos webhooks et vos utilisateurs abonnés.

<div id="getting-started-with-webhooks">
  ## Premiers pas avec les webhooks
</div>

L’Account Activity API est une API basée sur des webhooks qui envoie des événements de compte à une application web que vous développez, déployez et hébergez. 

Plusieurs détails techniques doivent être pris en compte avant que vous puissiez commencer à recevoir des événements de webhook dans votre application de consommation d’événements. Comme décrit ci-dessous, vous devrez créer une app X, obtenir l’accès à l’API Account Activity et développer une application web qui consomme les événements de webhook. 

<div id="1-create-a-x-app">
  ### 1. Créer une application X.
</div>

* Créez une [application X](/fr/resources/fundamentals/developer-apps) avec un compte développeur approuvé à partir de la [Developer Console](/fr/resources/fundamentals/developer-portal). Si vous créez l&#39;application pour le compte de votre entreprise, il est recommandé de la créer avec un compte X d’entreprise. Pour demander un compte développeur, [cliquez ici](/fr/resources/fundamentals/developer-apps).
* Activez « Read, Write and Access direct messages » dans l’onglet [permissions](/fr/resources/fundamentals/developer-apps#oauth-1-0a-app-permissions) de la page de votre application.
* Dans l’onglet « Keys and Access Tokens », relevez la Consumer Key (API Key) et le Consumer Token (API Secret) de votre application.
* Dans ce même onglet, générez les [Access Token and Access Token Secret](/fr/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow) de votre application. Vous aurez besoin de ces Access Tokens pour enregistrer l’URL de votre webhook, à laquelle X enverra les événements de compte.
* Si vous ne connaissez pas bien [X Sign-in](/fr/resources/fundamentals/authentication#log-in-with-x) ni la façon dont les contextes utilisateur fonctionnent avec X API, consultez [Obtaining Access Tokens](https://dev.x.com/webhooks/access-tokens). Lorsque vous ajoutez des comptes pour lesquels recevoir des événements, vous les abonnerez en utilisant les access tokens de ces comptes.
* Notez l’ID numérique de votre application, tel qu’il apparaît sur la page [« Apps »](/fr/resources/fundamentals/developer-apps) de la [Developer Console](/fr/resources/fundamentals/developer-portal). Lorsque vous demanderez l’accès à l’Account Activity API, vous aurez besoin de cet ID d’application.
   

<div id="2-get-account-activity-api-access">
  ### 2. Obtenir l’accès à l’API Account Activity
</div>

Après avoir créé une application X, l’étape suivante consiste à demander l’accès à l’API Account Activity. 

L’API Account Activity n’est disponible que dans l’offre Enterprise ; vous devrez donc soumettre une demande à l’aide du lien ci-dessous.

<Button href="https://developer.x.com/en/enterprise-application.html">
  Demander un accès Enterprise
</Button>

<div id="3-develop-webhook-consumer-app">
  ### 3. Développer une application consommatrice de webhooks
</div>

Une fois que vous avez obtenu l’accès à l’Account Activity API, vous devez développer, déployer et héberger une application web qui recevra les événements de webhook X. 

* Créez une application web avec une URL à utiliser comme webhook pour recevoir les événements. Il s’agit du endpoint déployé sur votre serveur pour écouter les événements de webhook X entrants. 
  * Le chemin URI *path* est entièrement à votre discrétion. Cet exemple serait valide : https://mydomain.com&#95;/service/listen&#95;

  * Si vous écoutez des webhooks provenant de différentes sources, un modèle courant est : https://mydomain.com/webhook/twitter

  * Notez que l’URL spécifiée ne peut pas inclure de spécification de port (https://mydomain.com:5000/NoWorkie).

* Comme décrit dans notre guide [Securing Webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks), une première étape consiste à écrire du code qui reçoit une requête GET X Challenge Response Check (CRC) et y répond avec une réponse JSON correctement formatée. 

* Enregistrez votre URL de webhook. Vous effectuerez une requête POST vers un endpoint /webhooks.json?url=. Lorsque vous faites cette requête, X enverra une requête CRC à votre application web. Lorsqu’un webhook est enregistré avec succès, la réponse inclura un id de webhook. Cet id de webhook sera nécessaire plus tard pour certaines requêtes vers l’Account Activity API. 

* X enverra les événements de webhook de compte à l’URL que vous avez enregistrée. Assurez-vous que votre application web prend en charge les requêtes POST pour les événements entrants. Ces événements seront encodés en JSON. Consultez [ICI](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-data-object-structure) pour des exemples de charges utiles JSON de webhook.

* Une fois que votre application web est prête, l’étape suivante consiste à ajouter des comptes pour lesquels recevoir des activités. Lorsque vous ajoutez (ou supprimez) des comptes, vous effectuerez des requêtes POST en faisant référence à l’id du compte. Consultez notre [guide sur l’ajout d’abonnements](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#managing-webhooks-and-subscriptions) pour plus d’informations.

<div id="4-validate-setup">
  ### 4. Valider la configuration
</div>

* Pour vérifier que votre application et votre webhook sont correctement configurés, ajoutez une Publication aux favoris parmi celles publiées par l’un des comptes X auxquels votre application est abonnée. Vous devez recevoir un `favorite_events` via une requête POST vers l’URL de votre webhook pour chaque favori reçu par vos abonnés.
* Notez que la remise des événements peut prendre jusqu’à 10 secondes après l’ajout d’un abonnement.

**Notes importantes**

* Lors de l’enregistrement de l’URL de votre webhook, votre application web doit s’authentifier avec son consumer token et secret *et le jeton d’accès utilisateur et le secret du propriétaire de l’application*. 

* Tous les Messages privés entrants seront livrés via des webhooks. Tous les Messages privés envoyés via [POST direct&#95;messages/events/new (message&#95;create)](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/new-event) seront également livrés via des webhooks. Cela permet à votre application web d’être informée des Messages privés envoyés via un autre client.

* Notez que chaque événement de webhook inclut un identifiant utilisateur for&#95;user&#95;id qui indique pour quel abonnement l’événement a été livré.

* Si deux utilisateurs utilisent votre application web pour les Messages privés dans une même conversation, votre webhook recevra deux événements en double (un pour chaque utilisateur). Votre application web doit en tenir compte. 

* Si vous avez plus d’une application web partageant la même URL de webhook et le même utilisateur associé à chaque application, le même événement sera envoyé plusieurs fois à votre webhook (une fois par application web).

* Dans certains cas, votre webhook peut recevoir des événements en double. Votre application de webhook doit être tolérante à cela et supprimer les doublons en fonction de l’identifiant d’événement.

* Ne vous attendez pas à ce qu’une réponse Quick Reply fasse directement suite à une requête. Un utilisateur peut ignorer une demande Quick Reply et répondre via un Message privé traditionnel. L’utilisateur peut également envoyer une réponse Quick Reply à une requête à laquelle il n’a pas répondu plus tôt dans le fil de messages.

<div id="securing-webhooks">
  ## Sécurisation des webhooks
</div>

Les API de X reposant sur les webhooks fournissent deux méthodes pour confirmer la sécurité de votre serveur de webhooks :

1. Les vérifications de type challenge-réponse permettent à X de confirmer la propriété de l’application web qui reçoit les événements webhook. 
2. L’en-tête de signature dans chaque requête POST vous permet de confirmer que X est la source des webhooks entrants.
    

<div id="challenge-response-checks">
  ### Vérifications challenge-réponse
</div>

Afin de vérifier que vous êtes à la fois le propriétaire de l&#39;application et de l&#39;URL du webhook, X effectuera une vérification challenge-réponse (CRC), à ne pas confondre avec un contrôle de redondance cyclique. Lorsqu&#39;un CRC est envoyé, X effectuera une requête GET vers votre application web avec un paramètre ;*`crc_token`*. Lorsque cette requête est reçue, votre application web doit générer un `response_token` chiffré à partir du paramètre *`crc_token`* et du Consumer Secret de votre application (détails ci-dessous). Le `response_token` doit être encodé en JSON (voir l&#39;exemple ci-dessous) et renvoyé dans un délai de trois secondes. En cas de succès, un `id` de webhook sera renvoyé. 

Un CRC sera envoyé lorsque vous enregistrez votre URL de webhook, de sorte que l&#39;implémentation de votre code de réponse CRC constitue une première étape fondamentale. Une fois votre webhook établi, X déclenchera un CRC approximativement toutes les 24 heures à partir du moment où nous avons reçu une réponse réussie. Votre application peut également déclencher un CRC au besoin en effectuant une requête PUT avec l&#39;`id` de votre webhook. Déclencher un CRC est utile lorsque vous développez votre application webhook, après le déploiement de nouveau code et le redémarrage de votre service. 

Le *`crc_token`* doit être considéré comme susceptible de changer pour chaque requête CRC entrante et doit être utilisé comme message dans le calcul, où votre Consumer Secret est la clé.

Dans le cas où la réponse n&#39;est pas envoyée en moins de 3 secondes ou devient invalide, les événements cesseront d&#39;être envoyés au webhook enregistré.

<div id="the-crc-request-will-occur">
  #### La requête CRC aura lieu :
</div>

* Lorsqu’une URL de webhook est enregistrée.
* Environ *une fois par heure* pour valider votre URL de webhook.
* Vous pouvez déclencher manuellement un CRC en effectuant une requête PUT. Lorsque vous développez votre client webhook, vous devez prévoir de déclencher manuellement le CRC au fur et à mesure que vous développez votre réponse CRC. 
   

<div id="response-requirements">
  #### Exigences de réponse :
</div>

* Un hachage HMAC SHA-256 encodé en base64 généré à partir du `crc_token` et du Consumer Secret de votre application
* Un `response_token` valide et un format JSON valide.
* Une latence inférieure à 3 secondes.
* Un code de réponse HTTP 200.
   

<div id="language-specific-hmac-libraries">
  #### Bibliothèques HMAC par langage :
</div>

* [Java/Scala](https://docs.oracle.com/javase/8/docs/api/index.html?javax/crypto/Mac.html)
* [Ruby](http://ruby-doc.org/stdlib-2.1.0/libdoc/openssl/rdoc/OpenSSL/HMAC.html)
* [Node.js](https://nodejs.org/api/crypto.html#crypto_class_hmac)
* [Python](https://docs.python.org/2/library/hmac.html)

<div id="example-response-token-generation-in-python">
  #### Exemple de génération de jeton de réponse en Python :
</div>

Ce qui suit définit une route dans une application web Flask en Python 2.7 qui répondra correctement à la vérification challenge-réponse.

```
import base64
import hashlib
import hmac
import json


\# Defines a route for the GET request
@app.route('/webhooks/twitter', methods=\['GET'\])
def webhook_challenge():

  # crée un hachage HMAC SHA-256 à partir du jeton entrant et de votre clé secrète consommateur
  sha256\_hash\_digest = hmac.new(TWITTER\_CONSUMER\_SECRET, msg=request.args.get('crc_token'), digestmod=hashlib.sha256).digest()

  # construit les données de réponse avec le hachage encodé en base64
  response = {
    'response\_token': 'sha256=' + base64.b64encode(sha256\_hash_digest)
  }

  # retourne la réponse JSON correctement formatée
  return json.dumps(response)
```

  #### Exemple de réponse JSON :
</div>

Avec la route définie comme ci-dessus, votre application Web doit renvoyer une réponse similaire à celle ci-dessous lorsque vous vous rendez sur https://your-app-domain/webhooks/twitter?crc&#95;token=foo dans votre navigateur Web.

```
{
  "response_token": "sha256=x0mYd8hz2goCTfcNAaMqENy2BFgJJfJOb4PdvTffpwg="
}
```

<div id="optional-signature-header-validation">
  ### Validation facultative de l’en-tête de signature
</div>

Lors de la réception d’une requête POST provenant de X, de l’envoi d’une requête GET pour créer un webhook ou de l’envoi d’une requête GET pour effectuer un CRC manuel, une signature de hachage est transmise dans les en-têtes sous la forme x-twitter-webhooks-signature. Cette signature peut être utilisée pour vérifier que la source des données est X. La signature de hachage POST commence par sha256=, ce qui indique l’utilisation de HMAC SHA-256 pour signer le Consumer Secret de votre application X et la charge utile. Le hachage GET est calculé à partir de la chaîne de paramètres de requête crc&#95;token=$token&amp;nonce=$nonce. 

**Étapes pour valider une requête**

1. Créez un hachage en utilisant votre Consumer Secret et le corps de la charge utile entrante.
2. Comparez le hachage obtenu avec la valeur x-twitter-webhooks-signature encodée en base64. Utilisez une méthode comme [compare&#95;digest](https://docs.python.org/2/library/hmac.html) pour réduire la vulnérabilité aux attaques par temporisation.

<div id="why-cant-i-just-update-the-webhook-url">
  #### Pourquoi ne puis-je pas simplement mettre à jour l’URL du webhook ?
</div>

Pourquoi les configurations de webhook ne peuvent-elles pas être modifiées ? X prend la sécurité très au sérieux. Si l’URL de votre webhook est modifiée, il est possible que la clé consommateur et le secret consommateur de votre application aient été compromis. En vous obligeant à créer une nouvelle configuration de webhook, vous êtes également tenu de vous réabonner aux événements de vos utilisateurs. Cela nécessite l’utilisation de jetons d’accès qu’une partie malveillante est moins susceptible de posséder. Par conséquent, la probabilité qu’une autre partie reçoive les informations privées de vos utilisateurs est réduite.

  X doit activer l’accès à l’Account Activity API pour votre App développeur avant que vous puissiez commencer à utiliser l’API. À cette fin, assurez-vous de partager l’App ID que vous avez l’intention d’utiliser pour les besoins d’authentification avec votre responsable de compte ou votre équipe de support technique.
</Note>

L’[Account Activity API](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity) se compose d’un ensemble d’endpoints qui vous permettent de créer et de gérer des abonnements utilisateur afin de recevoir en temps réel les activités de compte pour tous vos comptes abonnés via une seule connexion. 

Deux méthodes d’authentification sont disponibles avec l’Account Activity API ([OAuth 1.0a](/fr/resources/fundamentals/authentication#oauth-1-0a-2) et [OAuth 2.0 Bearer Token](/fr/resources/fundamentals/authentication#oauth-2-0)). *&#95; L’authentification nécessite les jetons d’accès de l’utilisateur abonné. &#95;

Pour les endpoints qui nécessitent une authentification OAuth 1.0a en contexte utilisateur, vous devez fournir les informations d’identification suivantes pour authentifier la requête : 

* Consumer Keys (API Key et Secret)
* Access Tokens (Access Token et Secret)

Dans le cas des trois endpoints suivants, vous effectuez des actions d’écriture dans le contexte de votre application (aucun utilisateur X n’est impliqué). Par conséquent, les Access Tokens que vous devez fournir sont ceux qui appartiennent à votre App développeur. Ils peuvent être générés directement depuis la [Developer Console](https://developer.x.com/en/portal/projects-and-apps), dans l’onglet « Keys and tokens » de votre App.  

* [POST account&#95;activity/webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#post-account-activity-webhooks) : Enregistrer une nouvelle URL de webhook pour le contexte d’application donné

<div id="retries">
  ## Réessais
</div>

`Enterprise`

L’un des avantages de l’offre Enterprise de l’Account Activity API est la prise en charge d’un mécanisme de réessai pour les événements de webhook. Si aucun code de réponse HTTP 200 « success » n’est reçu, le serveur X déclenche un mécanisme de réessai et renvoie l’événement de webhook jusqu’à trois fois sur une période de cinq minutes. Ce service de réessai d’événements de webhook améliore la fiabilité et la reprise des événements lorsque des problèmes de réseau surviennent, ainsi que lors des interruptions de service et des déploiements côté client.
 

<div id="what-are-retries">
  ### Que sont les tentatives de réessai ?
</div>

L&#39;Account Activity API fournit une fonctionnalité de nouvelle tentative lorsque l&#39;application web du client ne renvoie pas de réponse 200 « success » pour un événement de webhook d&#39;activité de compte. Lorsque le côté client ne confirme pas la bonne réception d&#39;un événement, X suppose que l&#39;événement n&#39;a pas été reçu. Si une réponse non-200 est reçue, si aucune réponse n&#39;est reçue dans les trois secondes, ou si nous ne recevons aucune réponse, nous réessayons la requête et la laissons ouverte pendant trois secondes. Cela signifie que vous disposez d&#39;environ cinq secondes, réparties sur deux tentatives, pour répondre afin de recevoir l&#39;activité que nous essayons d&#39;envoyer à votre URL de webhook. Dans le cas où votre serveur ne répond pas ou renvoie une erreur transitoire, nous effectuerons de nouvelles tentatives pendant cinq minutes. Il y aura au total trois tentatives de réessai pour confirmer la validation. Cela apporte de la redondance et garantit que vous recevez tous les événements de webhook. Notez que les abonnements avec nouvelles tentatives recevront des événements rejoués pour toutes les activités de tous les utilisateurs abonnés sur leur webhook.

Si vous ne confirmez pas la validation au cours de ces huit tentatives, l&#39;activité ne sera plus disponible via l&#39;Account Activity API. 

<div id="retry-timeline">
  ### Chronologie des nouvelles tentatives
</div>

L’Account Activity API effectuera jusqu’à trois nouvelles tentatives sur une période de cinq minutes, jusqu’à réception d’une Réponse 200. Reportez-vous au tableau ci-dessous pour plus de détails. Passé environ cinq minutes, l’activité ne peut plus être renvoyée via l’Account Activity API. Vous devrez utiliser d’autres endpoints de X pour récupérer les données manquées. Par exemple, les [API de recherche](/fr/x-api/enterprise-gnip-2.0/fundamentals/search-api) peuvent être utilisées pour récupérer les Publications, les Retweets, les Tweets cités, les mentions et les réponses pertinents. Les Messages privés manqués peuvent être récupérés avec [cet endpoint](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events).

<div id="retries-timeline">
  #### Chronologie des tentatives de réessai
</div>

|     |
| :--- |
| Activité créée : requête POST vers l’URL du webhook depuis Account Activity API, avec expiration au bout de trois secondes. |
| Attendre trois secondes après la fin de l’expiration précédente, puis effectuer une requête POST vers l’URL du webhook depuis Account Activity API, qui expire au bout de trois secondes. |
| Attendre 27 secondes après la fin de l’expiration précédente, puis effectuer une requête POST vers l’URL du webhook depuis Account Activity API, qui expire au bout de trois secondes. |
| Attendre 242 secondes après la fin de l’expiration précédente, puis effectuer une requête POST vers l’URL du webhook depuis Account Activity API, qui expire au bout de trois secondes. |
| Après cela, Account Activity API cesse de tenter d’effectuer des requêtes POST. Le client doit utiliser d’autres endpoints X pour récupérer les données. |

<div id="account-activity-replay-api">
  ## API de relecture de l’activité de compte
</div>

`Enterprise`

L’API de relecture de l’activité de compte est un outil de récupération de données qui vous permet de récupérer des événements jusqu’à cinq jours en arrière. Elle doit être utilisée pour récupérer des données dans les cas où votre serveur de [webhook](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#enterprise-account-activity-api) manque des événements, que ce soit en raison de déconnexions plus longues que la [fenêtre de réessai](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries), ou dans les scénarios de reprise après sinistre où vous avez besoin de quelques jours pour rétablir votre système à la normale.

L’API de relecture de l’activité de compte a été conçue pour tout scénario dans lequel vous ne parvenez pas à ingérer des [activités](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity) pendant une certaine période. Elle envoie les activités au même webhook que celui utilisé pour la diffusion en temps réel d’origine de ces activités. Ce produit est un outil de récupération et non un outil de reconstitution historique (backfill), ce qui signifie que les événements ne seront rejoués que si une tentative de livraison précédente a déjà eu lieu. L’API de relecture de l’activité de compte ne peut pas livrer d’événements pour une période antérieure à l’heure de création d’un abonnement.

<div id="using-account-activity-replay-api">
  ### Utilisation de l’API Account Activity Replay
</div>

Si votre compte est configuré avec la fonctionnalité Replay, vous pouvez envoyer des requêtes de manière similaire aux requêtes adressées à l’API Account Activity. Il est important de noter que votre requête doit spécifier un paramètre webhook id afin d’indiquer pour quel webhook vous souhaitez rejouer les activités. En d’autres termes, une requête Replay demande à l’API Account Activity Replay de récupérer des événements d’une date et heure de début à une date et heure de fin, sur la base du webhook id et de l’application id.

Veuillez noter que l’heure doit être fournie en UTC. Ces activités sont envoyées via le webhook enregistré associé à l’id, à un débit pouvant atteindre 2 500 événements par seconde. Gardez également à l’esprit qu’un seul job Replay par webhook peut être en cours d’exécution à la fois, même si tous les abonnements qui étaient actifs pendant la plage de dates/heures spécifiée sur ce webhook seront rejoués.

Les événements sont envoyés en commençant par la première minute (la plus ancienne) de la période spécifiée, puis en continuant de manière chronologique (autant que possible) jusqu’à ce que la dernière minute soit envoyée. À ce moment-là, Replay enverra un [événement de fin de job](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#job-completed-successfully-message) au webhook. Comme nous procédons de manière chronologique pour la livraison des activités, s’il y a peu ou pas de résultats correspondants près de l’heure de début, il y aura probablement un délai avant que les premiers résultats ne soient envoyés.

<div id="limitations">
  ### Limitations
</div>

Replay est conçu comme un outil permettant de récupérer facilement des activités jusqu’à cinq jours en arrière, mais il ne fournit pas d’événements antérieurs au moment de la création d’un abonnement. Par exemple, si vous avez ajouté un nouvel abonnement il y a trois jours et exécuté une tâche Replay avec une fenêtre couvrant les cinq jours précédant aujourd’hui, vous ne recevrez des données que pour les trois jours pendant lesquels ce nouvel abonnement était actif.

<div id="data-availability-and-types">
  ### Disponibilité et types de données
</div>

Les activités de l’API Account Activity Replay sont disponibles pendant cinq jours à partir de l’envoi de la requête, avec de nouvelles données devenant disponibles environ 10 minutes après la création d’une activité donnée. Vous pourrez effectuer des requêtes en spécifiant un intervalle de temps à l’intérieur de cette fenêtre de cinq jours en utilisant les paramètres from&#95;date et to&#95;date dans la requête. Les événements qui ont été initialement livrés avant d’avoir accès à Replay ne peuvent pas être rejoués. Par exemple, si votre compte a été activé pour l’accès à l’API Account Activity Replay le 1er juin 2019 à 15 h 30 UTC, vous ne pourrez pas utiliser Replay pour récupérer des événements antérieurs à cette date et heure.

Consultez la [Référence de l’API Account Activity Replay](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#delete-account-activity-webhooks-webhook-id-subscriptions-all-deprecated)

<div id="differences-migration-considerations">
  ### Différences et considérations de migration
</div>

**Format de l’API :** La nouvelle Account Activity API fonctionne différemment de User Streams et Site Streams. Vous devrez modifier votre application web pour recevoir des données via des webhooks. Vous pouvez trouver davantage d’informations sur les webhooks [ici](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks).

**Données disponibles :** Une autre différence clé que vous remarquerez concerne les données livrées. X n’enverra plus d’événements provenant des personnes que vous suivez sur X (c’est-à-dire votre fil d’accueil). Il s’agit d’un changement intentionnel et nous ne prévoyons pas de le modifier à l’avenir.

**Fiabilité :** Contrairement au streaming, les webhooks permettent la confirmation de la remise et offrent des options pour réessayer les activités envoyées en POST qui n’atteignent pas l’URL du webhook. Cela offre une meilleure garantie que l’application reçoit toutes les activités applicables, même en cas de brèves déconnexions ou de périodes d’indisponibilité.

<div id="new-features">
  ### Nouvelles fonctionnalités
</div>

L’Account Activity API propose de nombreuses nouvelles fonctionnalités, notamment le fait que les données sont désormais fournies via des webhooks plutôt que par streaming. Les webhooks offrent de nombreux avantages par rapport au streaming, les plus importants étant la rapidité et la fiabilité. L’API vous enverra des données sous forme d’événements JSON au fur et à mesure qu’ils seront disponibles et vous n’aurez plus besoin de maintenir une connexion active ni d’interroger le point de terminaison. Cela réduit le besoin de fonctionnalités de redondance et améliore globalement l’efficacité. Vous trouverez davantage d’informations sur les webhooks dans la [documentation technique](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks).

<div id="managing-user-subscriptions">
  ### Gestion des abonnements utilisateur
</div>

L’Account Activity API permet de configurer plusieurs abonnements pour un seul webhook enregistré. Cela permet d’acheminer l’activité de plusieurs abonnements utilisateur vers le même point de livraison, de manière similaire à l’architecture Site Streams, mais en utilisant des webhooks. Vous pouvez ainsi suivre les abonnements, notamment par rapport à vos limites d’abonnement, indépendamment de la connexion du webhook. Elle permet également de passer à l’échelle, d’un ou de quelques abonnements à des milliers d’abonnements pour un seul webhook.

  ### **Procédure de migration**
</div>

<div id="follow-the-steps-below-to-easily-migrate-from-the-site-streams-api-to-the-account-activity-api">
  ### **Suivez les étapes ci-dessous pour migrer facilement de l’API Site Streams vers l’API Account Activity**
</div>

**Étape 1 : Choisir une offre**

Selon la façon dont vous utilisez actuellement User Streams ou Site Streams, vous devriez envisager de passer à la version Enterprise ou Premium de l’API Account Activity. Tenez compte du nombre d’applications ou d’utilisateurs autorisés que vous prenez actuellement en charge et adaptez‑vous au volume et au niveau de fiabilité requis. Lors du choix de l’offre la mieux adaptée à vos besoins, quelques éléments sont à prendre en considération :

* Nombre de webhooks nécessaires
* Nombre actuel/prévisionnel d’abonnements/utilisateurs autorisés gérés sur votre application
* Nombre actuel d’applications clientes X
* Le niveau de support que vous préférez de la part de X (support via forum ou support Enterprise géré, en 1:1)
* Prix de chaque offre

**Étape 2 :** **Vérifier la configuration de votre application X dans la Developer Console**

L’[application X](/fr/resources/fundamentals/developer-apps) actuellement utilisée pour User Streams ou Site Streams sera répertoriée pour l’utilisateur propriétaire dans la [Developer Console](/fr/resources/fundamentals/developer-portal). Cette application X peut également être utilisée pour l’API Account Activity afin de conserver les utilisateurs autorisés pour cette application. Une nouvelle application peut aussi être créée, et les utilisateurs peuvent être à nouveau autorisés pour cette nouvelle application si nécessaire. Si vous créez une nouvelle application pour le compte d’une entreprise, il est recommandé de créer l’application avec un compte X @handle d’entreprise.

* Activez « Read, Write and Access direct messages » dans l’onglet [permissions](/fr/resources/fundamentals/developer-apps#app-permissions) de la page de votre application X. 
  *Notez que la modification de ces paramètres n’est pas rétroactive ; tous les utilisateurs déjà autorisés conserveront les paramètres d’autorisation en vigueur au moment où ils ont été autorisés. Si un utilisateur ne vous a pas encore accordé l’accès en lecture, écriture et messages privés, vous devrez lui demander de réautoriser votre application.
* Si vous ne connaissez pas encore [X Sign-in](/fr/resources/fundamentals/authentication#log-in-with-x) et la façon dont les contextes utilisateur fonctionnent avec X API, consultez la section [Obtaining Access Tokens](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks).
* Générez des jetons d’accès pour le propriétaire de l’application X en bas de l’onglet « Keys and Tokens ». Sur ce même onglet, notez votre Consumer Key, Consumer Secret, Access Token et Access Token Secret. Vous en aurez besoin pour utiliser l’API.
* Générez un Bearer Token à l’aide de votre Consumer Key et de votre Consumer Secret pour les méthodes d’API [application-only](/fr/resources/fundamentals/authentication#bearer-token-also-known-as-app-only).

**Étape 3 : Configurer vos webhooks**

* Créez une application web avec un endpoint à utiliser comme webhook pour recevoir les événements (par exemple : https://your&#95;domain.com/webhook/twitter ou https://webhooks.your&#95;domain.com).

* Utilisez votre Consumer Key, Consumer Secret, Access Token et Access Token Secret lors de la création de votre webhook. Notez que votre endpoint doit renvoyer une réponse JSON contenant un response&#95;token qui est un hachage HMAC SHA-256 encodé en base64, créé à partir du crc&#95;token et du Consumer Secret de votre application.

* Consultez la documentation [Securing Webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks), en accordant une attention particulière aux exigences du Challenge Response Check (CRC).

* Assurez‑vous que votre webhook prend en charge les requêtes POST pour les événements entrants et les requêtes GET pour le CRC.

* Assurez‑vous que votre webhook présente une faible latence (&lt;3 secondes pour répondre aux requêtes POST).

**Étape 4 : Valider la configuration de votre webhook**

* Les API Webhook sécuriseront vos webhooks de deux manières :

               - Exiger des Challenge Response Checks pour valider que le propriétaire du webhook est bien le propriétaire de l’application web.

               - Ajouter un en‑tête de signature dans chaque requête POST, permettant à votre application web de valider la source.

* Afin de vérifier que vous êtes à la fois le propriétaire de l’application web et de l’URL du webhook, X effectuera un Challenge Response Check (CRC), à ne pas confondre avec un contrôle de redondance cyclique (cyclic redundancy check).
* Une requête GET avec un paramètre nommé crc&#95;token sera envoyée à l’URL de votre webhook. Votre endpoint doit renvoyer une réponse JSON avec un response&#95;token qui est un hachage HMAC SHA-256 encodé en base64, créé à partir du crc&#95;token et du Consumer Secret de votre application.
* Il faut s’attendre à ce que le crc&#95;token change pour chaque requête CRC entrante. Le crc&#95;token doit être utilisé comme message dans le calcul, où votre Consumer Secret est la clé.
* Si la réponse est invalide, les événements cesseront d’être envoyés au webhook enregistré.

**Étape 5 : Créer des abonnements pour chaque utilisateur autorisé de User Streams ou Site Streams**

Passage de User Streams à l’API Account Activity :

* Générez une liste de vos abonnements utilisateur actuels sur User Streams.
* Configurez vos nouveaux abonnements à l’Account Activity API à l’aide de la requête *POST account&#95;activity/all/:env&#95;name/subscriptions*.
* Confirmez vos abonnements à l’Account Activity API à l’aide de la requête *GET account&#95;activity/all/:env&#95;name/subscriptions/list*.
   &#95;

Migration vers l’Account Activity API à partir de Site Streams : (à l’aide de flux de contrôle) :

* Générez une liste de vos abonnements actuels sur Site Streams à l’aide de la requête *GET /1.1/site/c/:stream&#95;id/info.json*.
* Configurez vos nouveaux abonnements à l’Account Activity API à l’aide de la requête *POST account&#95;activity/all/:env&#95;name/subscriptions*.
* Confirmez vos abonnements à l’Account Activity API à l’aide de la requête *GET account&#95;activity/all/:env&#95;name/subscriptions/list*.
   &#95;

Enregistrement d’un webhook et création d’abonnements (sans migration à partir de Site Streams ou User Streams)

* Enregistrez l’URL de votre webhook auprès de votre application à l’aide de [POST webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#enterprise-account-activity-api) et recevez un webhook&#95;id.
* Utilisez le webhook&#95;id renvoyé pour ajouter des abonnements utilisateur avec [POST webhooks/:webhook&#95;id/subscriptions/all](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#post-account-activity-webhooks-webhook-id-subscriptions-all).

<div id="sending-direct-messages">
  ### Envoi de messages privés
</div>

[POST direct&#95;messages/events/new](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/new-event) remplace directement l’envoi de messages privés. La différence la plus significative avec ce point de terminaison est que toutes les informations sont désormais envoyées en JSON dans le corps de la requête POST, plutôt que sous forme de paramètres POST individuels.

**Exemple de requête Twurl**

```bash
twurl -A 'Content-type: application/json' -X POST /1.1/direct\_messages/events/new.json -d '{"event": {"type": "message\_create", "message\_create": {"target": {"recipient\_id": "4534871"}, "message_data": {"text": "Hello World!"}}}}'
```

Notez, dans la requête ci-dessus, que l’en-tête Content-Type est défini sur application/json plutôt que sur application/x-www-form-urlencoded. De plus, si vous générez la signature OAuth 1.0a, notez que le corps JSON n’est pas inclus dans la génération de la signature. La plupart des bibliothèques OAuth prennent déjà cela en compte. Si vous utilisez [twurl](https://github.com/twitter/twurl), assurez-vous d’utiliser au minimum la version 0.9.3.

<div id="summary">
  #### Résumé
</div>

* Le message est défini dans le corps JSON de la requête POST
* L’en-tête Content-Type doit être renseigné avec la valeur application/json
* Le corps JSON n’est pas inclus dans le calcul de la signature OAuth.
   

<div id="retrieving-direct-messages">
  ### Récupération des Messages Privés
</div>

La récupération des anciens messages privés s’effectue désormais via un seul endpoint d’API : [GET direct&#95;messages/events/list](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events). La différence majeure avec ce nouvel endpoint est qu’il retourne désormais à la fois les messages envoyés et reçus, dans l’ordre chronologique inverse. Cela peut faciliter la reconstitution d’une conversation. Toutefois, si vous ne recherchez que les messages envoyés ou que les messages reçus, vous devrez post-traiter la réponse en vous référant à la propriété `sender_id`.

La pagination est désormais basée sur une valeur de curseur plutôt que sur l’identifiant d’un message privé. Une propriété `cursor` est renvoyée avec chaque réponse. [GET direct&#95;messages/events/list](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events) renvoie jusqu’à 30 jours de messages passés, quel que soit le nombre de messages existant au cours de ces 30 derniers jours. Lorsqu’aucun curseur n’est renvoyé, cela signifie qu’il n’y a plus de messages à retourner. La méthode d’accès à un message privé individuel avec [GET direct&#95;messages/events/show](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/get-event) reste la même, bien que l’objet message privé renvoyé ait une structure différente, comme décrit précédemment.

Enfin, l’accès en temps réel aux messages privés se fait désormais via un webhook avec l’[Account Activity API](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity). Pour obtenir des conseils sur la migration depuis User Streams ou Site Streams, consultez le guide de migration vers l’Account Activity API pour plus d’informations.

<div id="summary">
  #### Résumé
</div>

* Les messages envoyés et reçus sont désormais renvoyés par le même endpoint.
* Jusqu’à 30 jours d’historique de messages.
* Pagination par curseur.
* Accès en temps réel aux messages privés via webhook.

<div id="deleting-direct-messages">
  ### Suppression des messages privés
</div>

Les messages privés peuvent désormais être supprimés avec DELETE direct&#95;messages/events/destroy. L’interface reste en grande partie la même et nécessite l’ID du message à supprimer. La principale différence est que le point de terminaison nécessite désormais une requête DELETE au lieu d’une requête POST.

La façon dont les messages privés supprimés apparaissent dans les clients X officiels reste la même. Les messages privés sont uniquement retirés de l’interface de l’utilisateur du contexte fourni. Les autres participants à la conversation peuvent toujours accéder au message privé.

<div id="summary">
  #### Résumé
</div>

* La suppression d’un message privé nécessite l’id.
* Le nouvel endpoint nécessite une requête DELETE.
* La manière dont les messages privés supprimés apparaissent dans les clients X officiels reste inchangée.

  ## FAQ

<div id="general">
  ### Général
</div>

**Quels sont les avantages d’utiliser l’Account Activity API ?**

L’Account Activity API utilise des webhooks, ce qui signifie que, contrairement aux API de streaming, nous n’avons pas besoin que vous mainteniez une connexion ouverte pour que nous puissions vous envoyer des informations. Les webhooks sont également différents des API REST, car vous n’avez pas à nous interroger des centaines de fois toutes les 15 minutes pour obtenir les données qui vous intéressent. Cela améliore l’efficacité entre un utilisateur et votre application, car les données sont livrées au moment où l’activité se produit.

L’Account Activity API présente plusieurs avantages :

1. **Vitesse** : nous livrons les données à la vitesse de X.
2. **Simplicité** : nous livrons tous les événements d’un compte via une seule connexion webhook. Les activités livrées dans l’API incluent les Publications, les @mentions, les réponses, les Retweets, les Quote Tweets, les Retweets de Quote Tweets, les favoris, les Messages privés envoyés, les Messages privés reçus, les abonnements, les blocages, les mises en sourdine. 
3. **Évolutivité** : vous recevez l’ensemble des activités pour un compte que vous gérez, sans être limité par des limites de débit ni des plafonds d’événements.

L’Account Activity API est disponible en sandbox Premium, Premium payant et offre Enterprise, ce qui vous permet de monter en charge à mesure que vous avez besoin de plus de comptes pour des fonctionnalités de conformité ou des fonctionnalités supplémentaires.

Pour commencer, téléchargez des extraits de code d’exemple depuis [GitHub](https://github.com/xdevplatform/account-activity-dashboard).
 

**Comment déterminer quel niveau de produit est le mieux adapté à mes besoins ?**

Veuillez consulter notre page [Account Activity API Overview](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity) pour en savoir plus sur les différences entre les options Premium et l’option Enterprise. 
 

**Quelle est la différence entre un environnement Premium et un webhook Enterprise ?**

Il n’y en a aucune. Chaque environnement Premium aura son propre `webhook_id`.
 

**J’ai besoin d’environnements de développement, de préproduction et de production pour l’Account Activity API, est‑ce possible ?**

Oui ! Avec les niveaux payants de l’Account Activity API (Premium payant et Enterprise), il est possible d’enregistrer plusieurs URL de webhook et de gérer séparément les abonnements pour chacune via les méthodes de l’API. De plus, plusieurs applications clientes peuvent être ajoutées à une allowlist pour conserver l’autorisation de vos utilisateurs actuellement autorisés.
 

**Avez-vous des guides pas à pas pour configurer l’Account Activity API ?**

En effet, nous en avons !

* Si vous débutez, nous vous recommandons de consulter notre guide [Getting started with webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)

* Suivez nos scripts pris en charge par X Dev : 
  * [Account Activity API dashboard](https://github.com/xdevplatform/account-activity-dashboard), une application web Node.js qui affiche les événements de webhook.
  * Le [chatbot SnowBot](https://github.com/xdevplatform/SnowBotDev), une application web Ruby construite sur les Account Activity et Direct Message APIs. Cette base de code inclut un [script](https://github.com/xdevplatform/SnowBotDev/wiki/Account-Activity-API-setup-script) pour aider à configurer les webhooks de l’Account Activity API.
     

**Existe‑t‑il un moyen de récupérer les données si notre système est indisponible pendant une période donnée ?**

Avec les niveaux payants de l’Account Activity API (Premium payant et Enterprise), notre système va [réessayer](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries) de vous envoyer les activités plusieurs fois sur une période de quatre heures. Si votre système ne répond pas dans ce délai de quatre heures, l’activité sera perdue et vous devrez utiliser d’autres endpoints REST pour récupérer les données dans un délai de 7 jours.

Nous vous suggérons d’utiliser vos différents webhooks, ou environnements, comme outil de redondance, par exemple l’[Account Activity Replay API](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-replay-api), pour vous assurer de ne manquer aucune activité si l’un de vos systèmes tombe en panne.
 

**Quelle authentification dois‑je utiliser avec l’Account Activity API ?**

Les méthodes d’autorisation requises pour l’Account Activity API sont décrites pour chaque méthode dans les pages de [Référence de l’API](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-api-reference-index). Si vous débutez avec l’authentification X, nous vous recommandons de lire [cette section](/fr/resources/fundamentals/authentication).

**Qu’est‑ce qu’un challenge-response check (CRC) ?**

La vérification de la « challenge response » de l’Account Activity API est une fonctionnalité de sécurité mise en place pour garantir que les activités de l’Account Activity API sont envoyées au bon développeur. Elle peut aussi être utilisée par les développeurs pour s’assurer que les données qu’ils reçoivent proviennent de X. X enverra automatiquement un CRC à votre URL de webhook une fois toutes les 24 heures, à partir du moment où l’URL du webhook a été validée pour la dernière fois. Votre système doit répondre avec une réponse valide en moins de 3 secondes pour rester validé. 

Veuillez consulter notre page [Securing webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks) pour plus de détails.
 

**Y a‑t‑il quelque chose qui invaliderait immédiatement mon URL de webhook ?**

Si l’un des éléments suivants se produit, nous marquerons immédiatement votre webhook comme invalide :

* Le serveur répond à un CRC avec un jeton incorrect. Dans ce cas, notre système ne [réessaiera](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries) pas de vous envoyer l’activité.
* L’URL du webhook a un certificat mal configuré. Dans ce cas, notre système ne [réessaiera](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries) pas de vous envoyer l’activité.
* Votre serveur renvoie un code de réponse non‑2XX, non‑4XXX, non‑5XXX.
* Vous indiquez utiliser gzip sans réellement l’envoyer.
* Vous n’indiquez pas utiliser gzip, mais vous l’envoyez effectivement dans la réponse.
   

**Vais‑je recevoir des activités en double si je suis abonné à des utilisateurs qui interagissent entre eux ?**

Oui. Si votre application web a des abonnements actifs pour l’Utilisateur A et l’Utilisateur B, et que l’Utilisateur A mentionne l’Utilisateur B dans une Publication, deux activités POST seront envoyées au webhook enregistré. Chaque activité aura un indicateur « for&#95;user&#95;id » pour indiquer à quel abonnement l’activité appartient.
 

**Quand je crée un abonnement vers mon webhook, puis‑je remplacer la partie `/all/` de l’endpoint suivant par d’autres objets de données d’Account Activity pour limiter les activités que l’API délivre ? **`POST https://api.x.com/1.1/account_activity/all/:env_name/subscriptions.json`

Non, ce n’est pas possible. À l’heure actuelle, nous n’avons que le produit `/all/` disponible.
 

**Existe‑t‑il un moyen d’utiliser l’Account Activity API sans demander aux utilisateurs les autorisations pour les Messages privés ? **

À ce stade, les autorisations pour les Messages privés sont obligatoires, car il n’existe aucun moyen de « filtrer » les activités de Messages privés pour cette API. 
 

**Existe‑t‑il une version sandbox de l’Account Activity API ?**

Oui, nous proposons une option sandbox pour les tests. Notre option sandbox est limitée à un seul webhook, avec un maximum de 15 abonnements. Vous pouvez en savoir plus sur l’option sandbox dans [notre documentation](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity). 

**Est‑il possible d’utiliser l’Account Activity API pour obtenir les Retweets de Publications qui mentionnent des utilisateurs abonnés ? **

Malheureusement, cela ne fait pas partie des activités délivrées avec cette API. Pour cela, nous suggérons d’utiliser plutôt la Streaming API. 
 

**Quels sont les types d’activité possibles qui sont représentés par un tweet&#95;create&#95;event ?**

Un payload tweet&#95;create&#95;event sera envoyé :

Si l’utilisateur abonné effectue l’une des actions suivantes :

* Crée une Publication
* Retweete
* Répond à une Publication

Si un autre utilisateur :

* @mentionne* l’utilisateur abonné
* Cite un Tweet créé par l’utilisateur abonné 

*Remarque : l’Account Activity API ne délivre des événements que lorsque l’utilisateur abonné recevrait une notification de X et pourrait voir l’événement publiquement. Cela signifie que, si le compte mentionné (@userA) suit le compte protégé (@userB), alors UserA recevra une notification indiquant que UserB l’a mentionné. Si UserA ne suit pas UserB (et n’a pas été approuvé par UserB), UserA ne recevra pas de notification et, par conséquent, un tweet&#95;create&#95;event ne serait pas envoyé via AAA si @userA avait un abonnement.*

**Si un utilisateur bloqué mentionne mon utilisateur abonné, comment puis‑je l’identifier ?**

Vous verrez un champ booléen `user&#95;has&#95;blocked` au niveau supérieur de la réponse JSON, défini sur « true » ou « false ». Ce champ ne sera exposé que sur les mentions de Publication.

**Comment puis‑je ajouter mon application à une allowlist ou vérifier si mon application est déjà sur l’allowlist ?**

Pour gérer les [X apps](/fr/resources/fundamentals/developer-apps) que vous avez ajoutées à une allowlist pour un accès via les Enterprise APIs, veuillez contacter votre chargé de compte en lui communiquant l’ID de votre application. Vous pouvez trouver l’ID de votre application en accédant à la page [&quot;Apps&quot;](/fr/resources/fundamentals/developer-apps) dans la [Developer Console](/fr/resources/fundamentals/developer-portal).
 

**Si j’ai accès à trois webhooks, puis-je utiliser trois webhooks pour chacune des apps que j’ai enregistrées pour une utilisation entreprise ?**

La limite de webhooks est définie au niveau du compte, et non au niveau de l’app. Si vous avez accès à trois webhooks et à deux apps enregistrées pour une utilisation entreprise, vous pouvez utiliser deux webhooks sur une app et le troisième sur l’autre app, mais pas trois sur chaque app. 

**Puis-je spécifier quels types d’événements seront renvoyés à l’aide de l’Account Activity Replay API ?**

Les types d’événements à rejouer ne peuvent pas être spécifiés. Tous les événements livrés pendant l’intervalle de dates et d’heures indiqué seront rejoués. 

**Y aura-t-il de nouvelles tentatives si mon application ne parvient pas à ingérer un événement Account Activity Replay API ?**

Non, il n’y aura pas de nouvelles tentatives. Si une application ne parvient pas à ingérer un événement envoyé par l’Account Activity Replay API, un autre Replay job peut être soumis pour la même période afin de tenter une nouvelle livraison des événements Replay manqués. 

**Que dois-je faire lorsque je reçois un événement de fin avec succès partiel ?**

Nous vous suggérons de noter les horodatages des événements qui ont été reçus et de demander un autre Replay job pour les événements qui ont été manqués. 

**Combien de jobs Account Activity Replay API puis-je avoir en cours d’exécution simultanément ?**

Un seul job Account Activity Replay API par webhook peut être en cours d’exécution à la fois. 

**Comment puis-je différencier les événements Account Activity Replay API des événements de production en temps réel lorsqu’ils sont livrés à mon webhook ?**

Comme l’Account Activity Replay API livrera toujours des événements passés, les événements peuvent être différenciés des événements de production en temps réel en se basant sur l’horodatage de l’événement. 

**Combien de temps après puis-je commencer à utiliser l’Account Activity Replay API pour renvoyer une activité que mon application a perdue ou manquée ?**

Une activité devient disponible pour une nouvelle livraison environ 10 minutes après sa création. 

<div id="error-troubleshooting-guide">
  ### Guide de résolution des erreurs
</div>

<div id="code-32">
  #### Code 32
</div>

Cette erreur signifie généralement que quelque chose est mal formé dans la requête, les en-têtes, l’autorisation ou l’URL que vous indiquez. Ce n’est pas une erreur de l’Account Activity API, c’est une erreur d’autorisation et X ne reçoit pas la configuration OAuth ou l’URL correcte.

* **Enterprise** - Assurez-vous que les consumer keys et access tokens que vous utilisez appartiennent à une [application X](/fr/resources/fundamentals/developer-apps) qui a été enregistrée pour l’utilisation des produits Enterprise. Si vous ne disposez pas de vos consumer keys et access tokens, ou si vous devez ajouter votre application X à la allowlist (liste d’autorisation), veuillez contacter votre gestionnaire de compte. 

* Si vous vous authentifiez avec un contexte utilisateur, assurez-vous d’avoir correctement [autorisé votre requête](/fr/resources/fundamentals/authentication#authorizing-a-request) avec les `oauth nonce`, `oauth_signature` et `oauth_timestamp` appropriés.

* Assurez-vous que vos access tokens ont le niveau d’autorisation approprié.
  * Dans l’onglet &#39;Keys and tokens&#39; du [tableau de bord de l’application](/fr/resources/fundamentals/developer-apps), veuillez vérifier que vos access tokens ont le niveau d’autorisation &#39;Read, write, and direct messages&#39; [permission level](/fr/resources/fundamentals/developer-apps#app-permissions). 
  * Si le niveau d’autorisation des tokens est défini sur une valeur inférieure, allez dans l’onglet &#39;Permissions&#39;, ajustez l’autorisation d’accès à &#39;Read, write, and direct messages&#39;, puis régénérez vos access tokens et leur secret depuis l’onglet &#39;Keys and tokens&#39;.

* Assurez-vous que votre URL est correctement formée.
  * Veuillez garder à l’esprit que `:env_name` est sensible à la casse.
     

<div id="code-200-forbidden">
  #### Code 200 - Interdit
</div>

* **Premium** - Assurez-vous que vous disposez d’un [compte développeur](/fr/resources/fundamentals/developer-portal) approuvé avant de tenter d’envoyer une requête à l’API. Vous devez également utiliser le :env&#95;name approprié dans la requête, que vous pouvez configurer sur la page des [environnements de développement](/fr/resources/fundamentals/developer-portal).

* **Enterprise** - Assurez-vous que votre gestionnaire de compte s’est assuré que vous disposez de l’accès à l’Account Activity API.

* Assurez-vous d’avoir correctement configuré votre URI. Cette erreur peut se produire si vous avez saisi une URI incorrecte dans votre requête.
   

<div id="code-214-webhook-url-does-not-meet-the-requirements">
  #### Code 214 - L’URL du webhook ne répond pas aux exigences.
</div>

* Assurez-vous d’utiliser HTTPS.
* L’URL de votre webhook peut être mal formée.
* Pour en savoir plus sur la configuration de votre URL de webhook, consultez la section [Develop webhook consumer app](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#3-develop-webhook-consumer-app) de la page [Getting started with webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks).
   

<div id="code-214-high-latency-on-crc-get-request-your-webhook-should-respond-in-less-than-3-seconds">
  #### Code 214 - Latence élevée sur la requête GET de CRC. Votre webhook doit répondre en moins de 3 secondes.
</div>

* Cela signifie que votre serveur est lent. Assurez-vous de répondre au CRC en moins de 3 secondes.
   

<div id="code-214-non-200-response-code-during-crc-get-request-ie-404-500-etc">
  #### Code 214 - Code de réponse non-200 lors d&#39;une requête CRC GET (c.-à-d. 404, 500, etc).
</div>

* Votre serveur est hors service. Assurez-vous qu&#39;il fonctionne correctement.
   

<div id="code-214-too-many-resources-already-created">
  #### Code 214 - Trop de ressources déjà créées.
</div>

* **Enterprise** - Vous avez déjà utilisé tous vos webhooks. Utilisez le point de terminaison [GET webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#get-account-activity-webhooks) avec chacune de vos applications enregistrées pour identifier la répartition de vos webhooks. 

<div id="code-261-application-cannot-perform-write-actions">
  #### Code 261 - L’application ne peut pas effectuer d’actions d’écriture.
</div>

* L’application que vous utilisez avec l’API n’a pas le bon [niveau d’autorisation](/fr/resources/fundamentals/developer-apps#app-permissions) défini pour son access token et son access token secret. Accédez à l’onglet « Keys and tokens » sur le tableau de bord [X apps](/fr/resources/fundamentals/developer-apps) et vérifiez les niveaux d’autorisation attribués à votre access token et à votre access token secret. Si le niveau est défini sur autre chose que « Read, write and Direct Messages », vous devrez ajuster les paramètres dans l’onglet « Permission » et régénérer votre access token et votre access token secret pour appliquer les nouveaux paramètres.
* Autrement, vous essayez d’enregistrer un webhook en utilisant l’authentification « app-only », qui n’est pas prise en charge. Authentifiez-vous plutôt avec un contexte utilisateur, comme indiqué dans les sections de la Référence de l’API consacrées à l’enregistrement d’un webhook pour [Enterprise Account Activity API](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#post-account-activity-webhooks).

<div id="replay-api">
  ### API de relecture
</div>

**POST /1.1/account&#95;activity/replay/webhooks/:webhook&#95;id/subscriptions/all.json [¶](#post-1-1-account-activity-replay-webhooks-webhook-id-subscriptions-all-json- "Permalink to this headline")**

Envoie une requête pour récupérer les activités des cinq derniers jours au maximum, pour tous les abonnements présents pendant les fenêtres de date et d’heure spécifiées dans la requête. Si votre webhook a des abonnements utilisateur actifs, vous recevrez également ces événements en parallèle. Remarque : nous effectuons un CRC avant de livrer les événements de relecture.

|     |     |
| :--- | :--- |
| **Request Method** | HTTP POST |
| **URL** | /1.1/account&#95;activity/replay/webhooks/:webhook&#95;id/subscriptions/all.json?from&#95;date=yyyymmddhhmm&amp;to&#95;date=yyyymmddhhmm |
| **Response Format** | JSON |
| **Requires Authentication** | Oui (application uniquement - Bearer Token) |
| **Rate Limit** | 5 requêtes par tranche de 15 minutes. Il n’y a actuellement aucune limite maximale quant au nombre de tâches de relecture pouvant être demandées. |
| **from&#95;date** | L’horodatage UTC le plus ancien (de début) à partir duquel les événements seront fournis, doit être au format &#39;yyyymmddhhmm&#39;. L’horodatage a une granularité à la minute et est inclusif (c’est-à-dire que 12:00 inclut la minute 00). Les heures valides doivent se situer dans les 5 derniers jours, en heure UTC, et pas plus récentes que 31 minutes avant le moment actuel. Il est recommandé que `from_date` et `to_date` soient distants d’environ 2 heures au maximum. |
| **to&#95;date** | L’horodatage UTC le plus récent (de fin) jusqu’auquel l’événement sera fourni, doit être au format &#39;yyyymmddhhmm&#39;. L’horodatage a une granularité à la minute et est exclusif (c’est-à-dire que 12:30 n’inclut pas la 30e minute de l’heure). Les heures valides doivent se situer dans les 5 derniers jours, en heure UTC, et pas plus récentes que 10 minutes avant le moment actuel. |

<div id="job-completed-successfully-message">
  #### &quot;Job completed successfully” message
</div>

Une fois que votre job est terminé avec succès, l’API Account Activity Replay enverra l’événement de fin de job suivant. Une fois que vous recevez cet événement, le job a fini de s’exécuter et vous pouvez en soumettre un autre.

```json
{
  "replay\_job\_status": {
    "webhook_id": "1234577122340233217",
    "job_state": "Complete",
    "job\_state\_description": "Job completed successfully"
    "job_id": "1095098195724558337"
  }
}
```

<div id="job-failed-to-complete-message">
  #### &quot;Job failed to complete&quot; message
</div>

Si votre tâche ne se termine pas correctement, nous renverrons le message suivant pour vous encourager à relancer votre tâche Replay. Une fois que vous avez reçu cet événement, la tâche a terminé son exécution et une autre peut être soumise.

```json
{
  "replay\_job\_status": {
    "webhook_id": "123451374207332352",
    "job_state": "Incomplete",
    "job\_state\_description": "Job failed to deliver all events, please retry your replay job",
    "job_id": "1093226942650736640"
  }
}
```

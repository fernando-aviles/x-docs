Présentation

`Enterprise`

L’Account Activity API vous permet de vous abonner aux activités en temps réel liées à un compte utilisateur via des webhooks. Cela signifie que vous pouvez recevoir en temps réel des Publications, des Direct Messages et d’autres événements de compte à partir d’un ou de plusieurs comptes que vous possédez ou auxquels vous êtes abonné, via une seule connexion.

Vous recevrez toutes les activités suivantes pour chaque abonnement utilisateur dans le cadre de votre enregistrement de webhook :

| Types d’activité |     |
| :--- | :--- |
| * Publications (par l’utilisateur)  <br />    <br />* Suppressions de Publication (par l’utilisateur)<br />* @mentions (de l’utilisateur)<br />* Réponses (vers ou depuis l’utilisateur)<br />* Retweets (par l’utilisateur ou de l’utilisateur)<br />* Publications citées (par l’utilisateur ou de l’utilisateur)<br />* Retweets de Publications citées (par l’utilisateur ou de l’utilisateur)<br />* J’aime (par l’utilisateur ou de l’utilisateur)<br />* Abonnements (par l’utilisateur ou à l’utilisateur)  <br />    <br />* Désabonnements (par l’utilisateur) | * Blocages (par l’utilisateur)<br />* Déblocages (par l’utilisateur)<br />* Mises en sourdine (par l’utilisateur)<br />* Annulations de mise en sourdine (par l’utilisateur)<br />* Direct Messages envoyés (par l’utilisateur)<br />* Direct Messages reçus (par l’utilisateur)<br />* Indicateurs de saisie (à destination de l’utilisateur)<br />* Accusés de lecture (à destination de l’utilisateur)<br />* Révocations d’abonnement (par l’utilisateur) |

**Veuillez noter** - Nous ne fournissons pas les données du fil d’accueil via l’Account Activity API. Veuillez utiliser [GET statuses/home&#95;timeline](https://developer.x.com/en/docs/x-api/v1/tweets/timelines/overview) pour récupérer ces données.

<div id="manage-webhooks-and-subscribed-users">
  ## Gérer les webhooks et les utilisateurs abonnés
</div>

**⏱ 10 min de lecture**

L’API Enterprise Account Activity fournit des messages JSON basés sur des webhooks chaque fois que des événements sont associés à des comptes X abonnés à votre service. X envoie ces activités à votre webhook enregistré. Dans les étapes suivantes, vous apprendrez à gérer les webhooks et les utilisateurs abonnés.

Vous apprendrez à enregistrer, afficher et supprimer les webhooks ainsi que les utilisateurs abonnés. Nous utiliserons de simples commandes cURL pour effectuer des requêtes vers les différents endpoints de l’API. cURL est un outil en ligne de commande permettant d’envoyer ou de récupérer des requêtes en utilisant la syntaxe d’URL.

Vous aurez besoin de :

* D’une application X enregistrée - *[inscrivez-vous ici](https://developer.x.com/content/developer-twitter/en/apps)*
* D’un Bearer Token - *[en savoir plus](/fr/resources/fundamentals/authentication#using-and-generating-an-app-only-bearer-token)*
* D’un webhook qui passe un Challenge-Response Check (CRC) - *[en savoir plus](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks)*
* D’un compte Enterprise - *[postuler ici]https://developer.x.com/en/products/x-api/enterprise*

*Avant de commencer, nous vous recommandons de consulter notre [repo GitHub ici](https://github.com/xdevplatform/account-activity-dashboard), qui fournit une application web d’exemple et des scripts d’assistance pour commencer à utiliser l’API Account Activity de X*

<div id="managing-a-webhook">
  #### Gestion d’un webhook :
</div>

L’utilisation d’un webhook vous permet de vous abonner, via une seule connexion, aux activités en temps réel liées à un compte utilisateur. 

<Tabs>
  <Tab title="Ajouter un webhook">
    Commençons par enregistrer une nouvelle URL de webhook pour le contexte d’application donné.

    L’URL sera validée via une requête CRC avant l’enregistrement. Une fois que vous avez enregistré un webhook, veillez à consigner l’ID du webhook, car vous en aurez besoin plus tard.

    Copiez la requête cURL suivante dans votre ligne de commande après avoir modifié les éléments suivants :

    * **URL** `<URL>` par exemple : `https://yourdomain.com/webhooks/twitter/`

    * **Consumer key** `<CONSUMER_KEY>` par exemple : `xvz1evFS4wEEPTGEFPHBog`

    * **Access token** `<ACCESS_TOKEN>` par exemple : `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request POST --url 'https://api.x.com/1.1/account_activity/webhooks.json?url=<URL>' --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>

  <Tab title="Afficher un webhook">
    Nous allons exécuter la commande suivante pour récupérer toutes les URL de webhook enregistrées ainsi que leurs états pour l’application donnée.

    Copiez la requête cURL suivante dans votre ligne de commande après avoir modifié les éléments suivants :

    * **Bearer token** `<BEARER_TOKEN>` par exemple : `AAAAAAAAAAAA0%2EUifi76ZC9Ub0wn...`

      ```curl --request GET --url https://api.x.com/1.1/account_activity/webhooks.json --header 'authorization: Bearer <BEARER_TOKEN>'
      ```
  </Tab>

  <Tab title="Supprimer un webhook">
    Pour supprimer un webhook de la configuration de l’application concernée, copiez la requête cURL suivante dans votre ligne de commande après avoir modifié les éléments suivants :

    * **Webhook ID** `<:WEBHOOK_ID>` par exemple : `1234567890`

    * **Consumer key** `<CONSUMER_KEY>` par exemple : `xvz1evFS4wEEPTGEFPHBog`

    * **Access token** `<ACCESS_TOKEN>` par exemple : `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```curl --request DELETE --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>.json --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>
</Tabs>

<div id="managing-subscribed-users">
  #### Gestion des utilisateurs abonnés :
</div>

Une fois que vous avez enregistré un webhook, vous pouvez ajouter un utilisateur abonné à l’API Account Activity pour commencer à recevoir l’activité de son compte.

<Tabs>
  <Tab title="Ajouter un abonnement">
    Nous allons commencer par abonner un utilisateur afin que vous receviez tous les types d’événements.

    Copiez la requête cURL suivante dans votre ligne de commande après avoir modifié les éléments suivants :

    * **Webhook ID** `<:WEBHOOK_ID>` par exemple `1234567890`

    * **Nom de la consumer key** `<CONSUMER_KEY>` par exemple `xvz1evFS4wEEPTGEFPHBog`

    * **Access token de l’utilisateur abonné** `<SUBSCRIBING_USER'S_ACCESS_TOKEN>` par exemple `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request POST --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>/subscriptions/all.json --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<SUBSCRIBING_USER'S_ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>

  <Tab title="Afficher les abonnements">
    Pour afficher la liste de tous les abonnements aux types d’activité pour un webhook donné, copiez la requête cURL suivante dans votre ligne de commande après avoir modifié les éléments suivants :

    * **Webhook ID** `<:WEBHOOK_ID>` par exemple `1234567890`

    * **Bearer token** `<BEARER_TOKEN>` par exemple `AAAAAAAAAAAA0%2EUifi76ZC9Ub0wn...`

      ```
      curl --request GET --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>/subscriptions/all/list.json --header 'authorization: Bearer <BEARER_TOKEN>'
      ```
  </Tab>

  <Tab title="Supprimer un abonnement">
    Après la désactivation, tous les événements concernant l’utilisateur à l’origine de la requête ne seront plus envoyés à l’URL du webhook.

    Pour désactiver un abonnement dans le contexte de l’utilisateur et de l’application fournis, copiez la requête cURL suivante dans votre ligne de commande après avoir modifié les éléments suivants :

    * **Webhook ID** `<:WEBHOOK_ID>` par exemple `1234567890`

    * **Consumer key** `<CONSUMER_KEY>` par exemple `xvz1evFS4wEEPTGEFPHBog`

    * **Access token de l’utilisateur abonné** `<SUBSCRIBING_USER'S_ACCESS_TOKEN>` par exemple `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request DELETE --url https://api.x.com/1.1/account_activity/webhooks/:WEBHOOK_ID/subscriptions/all.json --header 'authorization: OAuth oauth_consumer_key="CONSUMER_KEY", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="SUBSCRIBED_USER'S_ACCESS_TOKEN", oauth_version="1.0"'
      ```
  </Tab>
</Tabs>

Excellent travail ! Vous êtes maintenant en mesure de gérer vos webhooks et vos utilisateurs abonnés.

<div id="getting-started-with-webhooks">
  ## Premiers pas avec les webhooks
</div>

L’API Account Activity est une API basée sur des webhooks qui envoie des événements de compte à une application web que vous développez, déployez et hébergez. 

Plusieurs détails « d’infrastructure » nécessitent votre attention avant de pouvoir commencer à recevoir des événements de webhook dans votre application de consommation d’événements. Comme décrit ci‑dessous, vous devrez créer une application X, obtenir l’accès à l’API Account Activity et développer une application web qui consomme les événements de webhook. 

<div id="1-create-a-x-app">
  ### 1. Créez une application X.
</div>

* Créez une [application X](/fr/resources/fundamentals/developer-apps) avec un compte développeur approuvé à partir de la [Console de Développement](/fr/resources/fundamentals/developer-portal). Si vous créez l’application au nom de votre entreprise, il est recommandé de la créer avec un compte X d’entreprise. Pour demander un compte développeur, [cliquez ici](/fr/resources/fundamentals/developer-apps).
* Activez « Read, Write and Access direct messages » dans l’onglet [permissions](/fr/resources/fundamentals/developer-apps#oauth-1-0a-app-permissions) de la page de votre application.
* Dans l’onglet « Keys and Access Tokens », notez la Consumer Key (API Key) et le Consumer Token (API Secret) de votre application.
* Dans le même onglet, générez l’[Access Token et Access Token Secret](/fr/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow) de votre application. Vous aurez besoin de ces Access Tokens pour enregistrer l’URL de votre webhook, c’est là que X enverra les événements de compte.
* Si vous ne connaissez pas encore [X Sign-in](/fr/resources/fundamentals/authentication#log-in-with-x) ni la façon dont les contextes utilisateur fonctionnent avec l’X API, consultez [Obtaining Access Tokens](https://dev.x.com/webhooks/access-tokens). Lorsque vous ajoutez des comptes pour lesquels recevoir des événements, vous vous y abonnerez en utilisant les Access Tokens de ce compte.
* Notez l’ID numérique de votre application, tel qu’il apparaît sur la page [Apps](/fr/resources/fundamentals/developer-apps) de la [Console de Développement](/fr/resources/fundamentals/developer-portal). Lorsque vous demanderez l’accès à l’Account Activity API, vous aurez besoin de cet id d’application.

<div id="3-develop-webhook-consumer-app">
  ### 3. Développer l&#39;application consommatrice de webhooks
</div>

Une fois que vous avez obtenu l&#39;accès à l&#39;Account Activity API, vous devez développer, déployer et héberger une application web qui recevra les événements de webhook X. 

* Créez une application web avec une URL à utiliser comme webhook pour recevoir les événements. Il s&#39;agit du endpoint déployé sur votre serveur pour écouter les événements de webhook X entrants. 
  * Le chemin d’URI *path* est entièrement à votre discrétion. Cet exemple serait valide : https://mydomain.com&#95;/service/listen&#95;

  * Si vous écoutez des webhooks provenant de différentes sources, un modèle courant est : https://mydomain.com/webhook/twitter

  * Notez que l’URL spécifiée ne peut pas comporter de spécification de port (https://mydomain.com:5000/NoWorkie).

* Comme décrit dans notre guide [Securing Webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks), une première étape consiste à écrire du code qui reçoit une requête GET X Challenge Response Check (CRC) et qui répond avec une réponse JSON correctement formatée. 

* Enregistrez votre URL de webhook. Vous effectuerez une requête POST vers un endpoint /webhooks.json?url=. Lorsque vous ferez cette requête, X enverra une requête CRC à votre application web. Lorsqu’un webhook est enregistré avec succès, la réponse contiendra un webhook id. Ce webhook id est nécessaire plus tard lors de certaines requêtes vers l’Account Activity API. 

* X enverra les événements de webhook de compte à l’URL que vous avez enregistrée. Assurez-vous que votre application web prend en charge les requêtes POST pour les événements entrants. Ces événements seront encodés en JSON. Consultez [ICI](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-data-object-structure) pour des exemples de charges utiles JSON de webhook.

* Une fois que votre application web est prête, l’étape suivante consiste à ajouter des comptes pour lesquels recevoir des activités. Lors de l’ajout (ou de la suppression) de comptes, vous effectuerez des requêtes POST en faisant référence à l’account id. Consultez notre [guide sur l’ajout d’abonnements](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#managing-webhooks-and-subscriptions) pour plus d’informations.

<div id="4-validate-setup">
  ### 4. Valider la configuration
</div>

* Pour valider que votre application et votre webhook sont correctement configurés, ajoutez aux favoris une Publication postée par l’un des comptes X auxquels votre application est abonnée. Vous devriez recevoir un `favorite_events` via une requête POST vers l’URL de votre webhook pour chaque favori que vos abonnés reçoivent.
* Notez qu’il peut s’écouler jusqu’à 10 secondes avant que les événements ne commencent à être envoyés après l’ajout d’un abonnement.

**Remarques importantes**

* Lors de l’enregistrement de l’URL de votre webhook, votre application web doit s’authentifier avec son jeton consommateur et son secret *et le jeton d’accès utilisateur et le secret du propriétaire de l’application*. 

* Tous les Messages privés entrants seront envoyés via des webhooks. Tous les Messages privés envoyés via [POST direct&#95;messages/events/new (message&#95;create)](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/new-event) seront également envoyés via des webhooks. Cela permet à votre application web d’être informée des Messages privés envoyés via un autre client.

* Notez que chaque événement webhook inclut un id d’utilisateur `for_user_id` qui indique pour quel abonnement l’événement a été envoyé.

* Si deux utilisateurs utilisent votre application web pour des Messages privés dans la même conversation, votre webhook recevra deux événements en double (un pour chaque utilisateur). Votre application web doit en tenir compte. 

* Si vous avez plusieurs applications web partageant la même URL de webhook et le même utilisateur mappé à chaque application, le même événement sera envoyé à votre webhook plusieurs fois (une fois par application web).

* Dans certains cas, votre webhook peut recevoir des événements en double. Votre application de webhook doit être tolérante à cela et supprimer les doublons par id d’événement.

* Ne vous attendez pas à ce qu’une réponse Quick Reply suive directement une requête. Un utilisateur peut ignorer une requête Quick Reply et répondre via un Message privé classique. L’utilisateur peut également fournir une réponse Quick Reply à une requête à laquelle il n’a pas répondu plus tôt dans le fil de messages.

<div id="securing-webhooks">
  ## Sécurisation des webhooks
</div>

Les API de X basées sur des webhooks fournissent deux méthodes pour vérifier la sécurité de votre serveur de webhook :

1. Les vérifications de type challenge-response permettent à X de confirmer la propriété de l’application web qui reçoit les événements de webhook. 
2. L’en-tête de signature dans chaque requête POST vous permet de confirmer que X est bien à l’origine des webhooks entrants.
    

<div id="challenge-response-checks">
  ### Vérifications de type Challenge-Response
</div>

Afin de vérifier que vous êtes à la fois le propriétaire de l’app et de l’URL de webhook, X effectuera une vérification de type Challenge-Response (CRC), à ne pas confondre avec un contrôle de redondance cyclique (cyclic redundancy check). Lorsqu’un CRC est envoyé, X effectuera une requête GET vers votre application web avec un paramètre *`crc_token`*. Lorsque cette requête est reçue, votre application web doit construire un `response_token` chiffré à partir du paramètre *`crc_token`* et du Consumer Secret de votre app (détails ci-dessous). Le `response_token` doit être encodé en JSON (voir l’exemple ci-dessous) et renvoyé en moins de trois secondes. En cas de succès, un `id` de webhook sera renvoyé. 

Un CRC sera envoyé lorsque vous enregistrez votre URL de webhook, donc implémenter votre code de réponse CRC est une première étape fondamentale. Une fois votre webhook établi, X déclenchera un CRC environ toutes les 24 heures à partir du dernier moment où nous avons reçu une réponse réussie. Votre app peut également déclencher un CRC si nécessaire en effectuant une requête PUT avec votre `id` de webhook. Déclencher un CRC est utile lorsque vous développez votre application de webhook, après le déploiement de nouveau code et le redémarrage de votre service. 

Le *`crc_token`* doit être considéré comme susceptible de changer pour chaque requête CRC entrante et doit être utilisé comme message dans le calcul, où votre Consumer Secret est la clé.

Dans le cas où la réponse n’est pas renvoyée en moins de 3 secondes ou devient invalide, les événements cesseront d’être envoyés au webhook enregistré.

<div id="the-crc-request-will-occur">
  #### La requête CRC aura lieu :
</div>

* Lorsqu’une URL de webhook est enregistrée.
* Environ *une fois par heure* pour valider votre URL de webhook.
* Vous pouvez déclencher manuellement un CRC en effectuant une requête PUT. Lorsque vous développez votre client de webhook, prévoyez de déclencher manuellement le CRC au fur et à mesure que vous développez votre réponse CRC. 
   

<div id="response-requirements">
  #### Exigences de la réponse :
</div>

* Un hachage HMAC SHA-256 encodé en Base64 créé à partir du `crc_token` et du Consumer Secret de votre application
* Un response&#95;token valide et au format JSON.
* Une latence inférieure à 3 secondes.
* Un code de réponse HTTP 200.
   

<div id="language-specific-hmac-libraries">
  #### Bibliothèques HMAC par langage :
</div>

* [Java/Scala](https://docs.oracle.com/javase/8/docs/api/index.html?javax/crypto/Mac.html)
* [Ruby](http://ruby-doc.org/stdlib-2.1.0/libdoc/openssl/rdoc/OpenSSL/HMAC.html)
* [Node.js](https://nodejs.org/api/crypto.html#crypto_class_hmac)
* [Python](https://docs.python.org/2/library/hmac.html)

<div id="example-response-token-generation-in-python">
  #### Exemple de génération de jeton de réponse en Python :
</div>

L’exemple suivant définit une route dans une application web Flask en Python 2.7 qui répondra correctement à la vérification Challenge-Response.

```
import base64
import hashlib
import hmac
import json


\# Defines a route for the GET request
@app.route('/webhooks/twitter', methods=\['GET'\])
def webhook_challenge():

  # crée un hachage HMAC SHA-256 à partir du jeton entrant et de votre consumer secret
  sha256\_hash\_digest = hmac.new(TWITTER\_CONSUMER\_SECRET, msg=request.args.get('crc_token'), digestmod=hashlib.sha256).digest()

  # construit les données de réponse avec le hachage encodé en base64
  response = {
    'response\_token': 'sha256=' + base64.b64encode(sha256\_hash_digest)
  }

  # retourne la réponse JSON correctement formatée
  return json.dumps(response)
```

<div id="example-json-response">
  #### Exemple de réponse JSON :
</div>

Avec la route définie comme ci-dessus, votre application web doit renvoyer une réponse similaire à celle ci-dessous lorsque vous accédez à l’URL https://your-app-domain/webhooks/twitter?crc&#95;token=foo dans votre navigateur web.

```
{
  "response_token": "sha256=x0mYd8hz2goCTfcNAaMqENy2BFgJJfJOb4PdvTffpwg="
}
```

<div id="optional-signature-header-validation">
  ### Validation facultative de l’en-tête de signature
</div>

Lors de la réception d’une requête POST provenant de X, de l’envoi d’une requête GET pour créer un webhook ou de l’envoi d’une requête GET pour effectuer un CRC manuel, une signature de hachage est transmise dans les en-têtes sous la clé x-twitter-webhooks-signature. Cette signature peut être utilisée pour vérifier que la source des données est X. La signature de hachage POST commence par sha256=, indiquant l’utilisation de HMAC SHA-256 pour signer votre X App Consumer Secret et la charge utile. Le hachage GET est calculé à partir de la chaîne de paramètres de requête crc&#95;token=$token&amp;nonce=$nonce. 

**Étapes pour valider une requête**

1. Créez un hachage en utilisant votre consumer secret et le corps de la charge utile reçue.
2. Comparez le hachage créé avec la valeur x-twitter-webhooks-signature encodée en base64. Utilisez une méthode comme [compare&#95;digest](https://docs.python.org/2/library/hmac.html) pour réduire la vulnérabilité aux attaques par temporisation.

<div id="why-cant-i-just-update-the-webhook-url">
  #### Pourquoi ne puis-je pas simplement mettre à jour l’URL du webhook ?
</div>

Pourquoi les configurations de webhook ne peuvent-elles pas être modifiées ? X prend la sécurité très au sérieux. Si l’URL de votre webhook est modifiée, il est possible que la consumer key et le consumer secret de votre application aient été compromis. En vous obligeant à créer une nouvelle configuration de webhook, vous devez également vous réabonner aux événements de votre utilisateur. Cela nécessite l’utilisation de jetons d’accès qu’un tiers malveillant est moins susceptible de posséder. Par conséquent, la probabilité qu’un tiers reçoive les informations privées de votre utilisateur est réduite.

<div id="retries">
  ## Réessais
</div>

`Enterprise`

L’un des avantages du niveau Enterprise de l’Account Activity API est un mécanisme de réessai pour les événements de webhook. Si aucun code de réponse HTTP 200 « success » n’est reçu, le serveur X déclenchera un mécanisme de réessai, en renvoyant l’événement de webhook jusqu’à trois fois sur une période de cinq minutes. Ce service de réessai d’événements de webhook contribue à assurer la fiabilité et la récupération des événements lorsque des problèmes de réseau surviennent ou pendant les interruptions de service et les déploiements côté client.
 

<div id="what-are-retries">
  ### Quelles sont les nouvelles tentatives ?
</div>

L’Account Activity API propose une fonctionnalité de nouvelle tentative lorsque l’application web du client ne renvoie pas une réponse 200 `success` pour un événement de webhook d’activité de compte. Lorsque la partie cliente ne confirme pas la bonne réception d’un événement, X suppose que l’événement n’a pas été reçu. Si une réponse non 200 est reçue, si aucune réponse n’est reçue dans les trois secondes, ou si nous ne recevons pas de réponse du tout, nous réessayons la requête et laissons celle-ci ouverte pendant trois secondes. Cela signifie que vous disposez d’environ cinq secondes, réparties sur deux tentatives, pour répondre et recevoir l’activité que nous essayons d’envoyer à votre URL de webhook. Dans le cas où votre serveur ne répond pas ou renvoie une erreur transitoire, nous réessaierons pendant cinq minutes. Il y aura au total trois tentatives de nouvelle exécution pour confirmer la validation. Cela permet une redondance et une garantie que vous recevez tous les événements de webhook. Notez que les abonnements avec nouvelles tentatives recevront des événements renvoyés pour n’importe quelle activité / toutes les activités, pour tous les utilisateurs abonnés via leur webhook.

Si vous ne confirmez pas la validation au cours de ces huit tentatives, l’activité ne sera plus disponible via l’Account Activity API. 

<div id="retry-timeline">
  ### Chronologie des tentatives de renvoi
</div>

L&#39;Account Activity API effectuera jusqu&#39;à trois tentatives de renvoi sur une période de cinq minutes, jusqu&#39;à ce qu&#39;une réponse 200 soit reçue. Reportez-vous au tableau ci-dessous pour plus de détails. Après environ cinq minutes, l&#39;activité ne peut plus être renvoyée via l&#39;Account Activity API. Vous devrez utiliser d&#39;autres endpoints X pour collecter les données manquantes. Par exemple, les [API de recherche](/fr/x-api/enterprise-gnip-2.0/fundamentals/search-api) peuvent être utilisées pour récupérer les Publications, Retweets, Tweets cités, Mentions et réponses pertinentes. Les Messages privés manqués peuvent être récupérés avec [cet endpoint](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events).

<div id="account-activity-replay-api">
  ## API de relecture de l’activité de compte
</div>

`Enterprise`

L’API de relecture de l’activité de compte est un outil de récupération de données qui vous permet de retrouver des événements jusqu’à cinq jours en arrière. Elle doit être utilisée pour restaurer des données dans les scénarios où votre serveur de [webhook](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#enterprise-account-activity-api) ne reçoit pas certains événements — que ce soit en raison de déconnexions plus longues que la [fenêtre de nouvelle tentative](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries), ou dans des scénarios de reprise après sinistre où vous avez besoin de quelques jours pour remettre votre système à l’état normal.

L’API de relecture de l’activité de compte a été développée pour tout scénario dans lequel vous ne parvenez pas à ingérer des [activités](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity) pendant une certaine période. Elle envoie les activités au même webhook que celui utilisé pour la diffusion en temps réel initiale des activités. Ce produit est un outil de récupération et non un outil de rattrapage (backfill), ce qui signifie que les événements ne seront rejoués que si une tentative de diffusion précédente a déjà eu lieu. L’API de relecture de l’activité de compte ne peut pas délivrer d’événements pour une période antérieure à l’heure de création de l’abonnement.

<div id="using-account-activity-replay-api">
  ### Utilisation de l’Account Activity Replay API
</div>

Si votre compte est configuré avec la fonctionnalité Replay, vous pouvez effectuer des requêtes de manière similaire aux requêtes vers l’Account Activity API. Il est important de noter que votre requête doit spécifier un paramètre webhook id pour indiquer pour quel webhook vous souhaitez rejouer les activités. En d’autres termes, une requête Replay demande à l’Account Activity Replay API de récupérer des événements d’une date et heure de début à une date et heure de fin, sur la base du webhook id et de l’application id.

Veuillez noter que les heures doivent être exprimées en UTC. Ces activités sont envoyées via le webhook enregistré associé à l’id, à un débit pouvant atteindre 2 500 événements par seconde. Gardez également à l’esprit qu’un seul job Replay par webhook peut être en cours d’exécution à la fois, même si tous les abonnements qui étaient actifs pendant la date/heure spécifiée pour ce webhook seront rejoués.

Les événements sont envoyés en commençant par la première minute (la plus ancienne) de la plage horaire spécifiée, puis en continuant de manière chronologique (autant que possible) jusqu’à ce que la dernière minute soit envoyée. À ce stade, Replay enverra un [événement de fin de job](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#job-completed-successfully-message) au webhook. Comme la livraison des activités se fait de manière chronologique, s’il y a peu ou pas de résultats correspondants près de l’heure de début, il y aura probablement un délai avant que les premiers résultats ne soient envoyés.

<div id="limitations">
  ### Limitations
</div>

Replay est conçu comme un outil permettant de récupérer facilement des activités jusqu’à cinq jours en arrière, mais il ne renverra pas d’événements antérieurs au moment de la création d’un abonnement. Par exemple, si vous avez ajouté un nouvel abonnement il y a trois jours et exécuté une tâche Replay avec une fenêtre couvrant les cinq jours précédant aujourd’hui, vous ne recevrez des données que pour les trois jours pendant lesquels ce nouvel abonnement était actif.

<div id="data-availability-and-types">
  ### Disponibilité et types de données
</div>

Les activités de l’API Account Activity Replay sont disponibles pendant cinq jours à partir de l’envoi de la requête, de nouvelles données devenant disponibles environ 10 minutes après la création d’une activité donnée. Vous pourrez effectuer des requêtes en spécifiant une période dans cette fenêtre de cinq jours à l’aide des paramètres from&#95;date et to&#95;date dans la requête. Les événements qui ont été initialement envoyés avant que vous n’ayez accès à Replay ne peuvent pas être rejoués. Par exemple, si votre compte a été activé pour l’accès à l’API Account Activity Replay le 1er juin 2019 à 15 h 30 UTC, vous ne pourrez pas utiliser Replay pour récupérer des événements antérieurs à cette date et heure.

Consultez la [Référence de l’API Account Activity Replay](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#delete-account-activity-webhooks-webhook-id-subscriptions-all-deprecated)

<div id="differences-migration-considerations">
  ### Différences et considérations de migration
</div>

**Format de l’API :** La nouvelle API Account Activity fonctionne différemment de User Streams et Site Streams. Vous devrez modifier votre application web pour recevoir des données via des webhooks. Vous trouverez plus d’informations sur les webhooks [ici](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks).

**Données disponibles :** Une autre différence majeure que vous remarquerez concerne les données livrées. X n’enverra plus d’événements générés par les personnes que vous suivez sur X (c’est-à-dire votre fil d’accueil). Il s’agit d’un changement intentionnel et nous ne prévoyons pas de le modifier à l’avenir.

**Fiabilité :** Contrairement au streaming, les webhooks permettent de confirmer la remise et offrent des options pour réessayer l’envoi des activités POSTées qui n’atteignent pas l’URL du webhook. Cela offre davantage de garanties que l’application reçoit toutes les activités pertinentes, même en cas de brèves déconnexions ou de périodes d’indisponibilité.

<div id="new-features">
  ### Nouvelles fonctionnalités
</div>

L’Account Activity API offre de nombreuses nouvelles fonctionnalités, notamment le fait que les données sont désormais transmises via des webhooks plutôt que par diffusion en continu (streaming). Les webhooks présentent de nombreux avantages par rapport au streaming, les plus importants étant la rapidité et la fiabilité. L’API vous envoie les données sous forme d’événements JSON dès qu’elles sont disponibles, et vous n’avez plus besoin de maintenir une connexion active ni d’interroger le point de terminaison. Cela réduit le besoin de fonctionnalités de redondance et améliore l’efficacité globale. Vous trouverez plus d’informations sur les webhooks dans la [documentation technique](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks).

<div id="managing-user-subscriptions">
  ### Gestion des abonnements utilisateur
</div>

L’API Account Activity permet de configurer plusieurs abonnements pour un seul webhook enregistré. Cela permet d’acheminer les activités de plusieurs abonnements utilisateur vers la même destination, de manière similaire à l’architecture Site Streams, mais avec des webhooks. Vous pouvez ainsi suivre vos abonnements, notamment par rapport à vos limites d’abonnement, indépendamment de la connexion du webhook. Cela permet également de passer à l’échelle, d’un seul ou de quelques abonnements à des milliers d’abonnements pour un seul webhook.

  ### **Procédure de migration**
</div>

<div id="follow-the-steps-below-to-easily-migrate-from-the-site-streams-api-to-the-account-activity-api">
  ### **Suivez les étapes ci-dessous pour migrer facilement de l’API Site Streams vers l’API Account Activity**
</div>

**Étape 1 : Choisir une offre**

Selon la manière dont vous utilisez actuellement User Streams ou Site Streams, vous devriez envisager de passer soit à la version entreprise, soit à la version premium de l’API Account Activity.  Tenez compte du nombre d’applications ou d’utilisateurs autorisés que vous prenez actuellement en charge et adaptez-vous au volume et au niveau de fiabilité requis.  Lors du choix de l’offre qui répond le mieux à vos besoins, certains éléments à prendre en compte sont :

* Nombre de webhooks nécessaires
* Nombre actuel/prévisionnel d’abonnements/utilisateurs autorisés gérés sur votre application
* Nombre actuel d’applications client X
* Niveau de support souhaité de la part de X (support via forum ou support entreprise géré en 1:1)
* Prix de chaque offre

**Étape 2 :** **Vérifier la configuration de votre application X dans la Console de Développement**

L’[application X](/fr/resources/fundamentals/developer-apps) actuellement utilisée pour User Streams ou Site Streams sera répertoriée pour l’utilisateur propriétaire dans la [Console de Développement](/fr/resources/fundamentals/developer-portal). Cette application X peut également être utilisée pour l’API Account Activity afin de conserver les utilisateurs autorisés pour cette application.  Une nouvelle application peut aussi être créée, et les utilisateurs peuvent être à nouveau autorisés pour cette nouvelle application si vous le souhaitez.  Si vous créez une nouvelle application pour le compte d’une entreprise, il est recommandé de créer l’application avec un compte X @handle d’entreprise.

* Activez « Read, Write and Access direct messages » dans l’onglet [permissions](/fr/resources/fundamentals/developer-apps#app-permissions) de la page de votre application X. 
  *Notez que la modification de ces paramètres n’est pas rétroactive : tout utilisateur déjà autorisé conservera les paramètres d’autorisation en vigueur au moment où il a été autorisé. Si un utilisateur ne vous a pas encore donné l’accès lecture, écriture et aux messages privés, vous devrez lui demander de réautoriser votre application.
* Si vous ne connaissez pas [X Sign-in](/fr/resources/fundamentals/authentication#log-in-with-x) et la façon dont les contextes utilisateurs fonctionnent avec l’X API, consultez la section [Obtaining Access Tokens](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks).
* Générez des jetons d’accès pour le propriétaire de l’application X en bas de l’onglet « Keys and Tokens ». Sur ce même onglet, notez votre Consumer Key, Consumer Secret, Access Token et Access Token Secret. Vous en aurez besoin pour utiliser l’API.
* Générez un Bearer Token à l’aide de votre Consumer Key et de votre Consumer Secret pour les méthodes d’API [application-only](/fr/resources/fundamentals/authentication#bearer-token-also-known-as-app-only).

**Étape 3 : Configurer votre webhook**

* Créez une application web avec un endpoint (point de terminaison) à utiliser comme webhook pour recevoir les événements (par exemple : https://your&#95;domain.com/webhook/twitter ou https://webhooks.your&#95;domain.com).

* Utilisez votre Consumer Key, Consumer Secret, Access Token et Access Token Secret lors de la création de votre webhook. Notez que votre endpoint doit renvoyer une réponse JSON contenant un response&#95;token qui est un hachage HMAC SHA-256 encodé en base64, créé à partir du crc&#95;token et du Consumer Secret de votre application.

* Consultez la documentation [Securing Webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks) en accordant une attention particulière aux exigences du Challenge Response Check (CRC).

* Assurez-vous que votre webhook prend en charge les requêtes POST pour les événements entrants et les requêtes GET pour le CRC.

* Assurez-vous que votre webhook a une faible latence (&lt;3 secondes pour répondre aux requêtes POST)

**Étape 4 : Valider la configuration de votre webhook**

* Les API de webhook sécurisent vos webhooks de deux manières :

               - Exiger des Challenge Response Checks pour valider que le propriétaire du webhook est le propriétaire de l’application web.

               - Fournir un en-tête de signature dans chaque requête POST afin que votre application web puisse valider la source.

* Pour vérifier que vous êtes bien à la fois le propriétaire de l’application web et de l’URL du webhook, X effectuera un Challenge Response Check (CRC), à ne pas confondre avec un contrôle de redondance cyclique (cyclic redundancy check).
* Une requête GET avec un paramètre nommé crc&#95;token sera envoyée à l’URL de votre webhook. Votre endpoint doit renvoyer une réponse JSON avec un response&#95;token qui est un hachage HMAC SHA-256 encodé en base64, créé à partir du crc&#95;token et du Consumer Secret de votre application.
* Le crc&#95;token doit être considéré comme susceptible de changer pour chaque requête CRC entrante. Le crc&#95;token doit être utilisé comme message dans le calcul, où votre Consumer Secret est la clé.
* Si la réponse est invalide, les événements cesseront d’être envoyés au webhook enregistré.

**Étape 5 : Créer des abonnements pour chaque utilisateur autorisé User Streams ou Site Streams**

Conversion vers l’API Account Activity à partir de User Streams :

* Générez une liste de vos abonnements utilisateur actuels sur User Streams
* Configurez vos nouveaux abonnements à l’Account Activity API à l’aide de la requête  *POST account&#95;activity/all/:env&#95;name/subscriptions*
* Confirmez vos abonnements à l’Account Activity API à l’aide de la requête  &#95;GET account&#95;activity/all/:env&#95;name/subscriptions/list
   &#95;

Conversion vers l’Account Activity API à partir de Site Streams : (à l’aide de flux de contrôle) :

* Générez une liste de vos abonnements actuels sur Site Streams à l’aide de la requête  *GET /1.1/site/c/:stream&#95;id/info.json*
* Configurez vos nouveaux abonnements à l’Account Activity API à l’aide de la requête  *POST account&#95;activity/all/:env&#95;name/subscriptions*
* Confirmez vos abonnements à l’Account Activity API à l’aide de la requête  &#95;GET account&#95;activity/all/:env&#95;name/subscriptions/list
   &#95;

Enregistrement d’un webhook et création d’abonnements (sans migration depuis Site Streams ou User Streams)

* Enregistrez l’URL de votre webhook auprès de votre application à l’aide de [POST webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#enterprise-account-activity-api) et recevez un webhook&#95;id.
* Utilisez le webhook&#95;id renvoyé pour ajouter des abonnements utilisateur avec [POST webhooks/:webhook&#95;id/subscriptions/all](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#post-account-activity-webhooks-webhook-id-subscriptions-all).

Les nouveaux endpoints d’API se comportent très différemment de leurs versions précédentes. Se contenter de mettre à jour les URL des endpoints entraînera des erreurs dans votre application. Tenez compte des points suivants lors de la mise à jour de votre application pour cette migration.

<div id="sending-direct-messages">
  ### Envoi de messages privés
</div>

[POST direct&#95;messages/events/new](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/new-event) est l’équivalent direct pour l’envoi de messages privés. La différence la plus importante avec cet endpoint est que toutes les informations sont désormais envoyées au format JSON dans le corps de la requête POST, plutôt que sous forme de paramètres POST individuels.

**Exemple de requête Twurl**

```bash
twurl -A 'Content-type: application/json' -X POST /1.1/direct\_messages/events/new.json -d '{"event": {"type": "message\_create", "message\_create": {"target": {"recipient\_id": "4534871"}, "message_data": {"text": "Hello World!"}}}}'
```

Notez que, dans la requête ci-dessus, l’en-tête Content-Type est défini sur application/json plutôt que sur application/x-www-form-urlencoded. De plus, si vous générez la signature OAuth 1.0a, notez que le corps JSON n’est pas inclus dans la génération de la signature. La plupart des bibliothèques OAuth en tiennent déjà compte. Si vous utilisez [twurl](https://github.com/twitter/twurl), assurez-vous d’utiliser au minimum la version 0.9.3.

<div id="summary">
  #### Résumé
</div>

* Le message est défini dans le corps JSON de la requête POST
* L’en-tête Content-Type doit être défini sur application/json
* Le corps JSON n’est pas inclus dans la génération de la signature OAuth.
   

<div id="retrieving-direct-messages">
  ### Récupérer des Messages privés
</div>

La récupération d’anciens Messages privés s’effectue désormais via un unique endpoint d’API : [GET direct&#95;messages/events/list](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events). La différence majeure avec ce nouvel endpoint est qu’il renvoie maintenant à la fois les messages envoyés et reçus, dans l’ordre chronologique inverse. Cela peut faciliter la reconstitution d’une conversation. Cependant, si vous recherchez uniquement les messages envoyés ou reçus, vous devrez post‑traiter la réponse en vous référant à la propriété `sender_id`.

La pagination est maintenant basée sur une valeur de curseur plutôt que sur l’id d’un Message privé. Une propriété de curseur est renvoyée avec chaque réponse. [GET direct&#95;messages/events/list](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events) renverra jusqu’à 30 jours de messages passés, quel que soit le nombre de messages existant sur ces 30 derniers jours. Lorsqu’aucun curseur n’est renvoyé, il n’y a plus de messages à récupérer. La méthode d’accès aux Messages privés individuels avec [GET direct&#95;messages/events/show](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/get-event) reste la même, bien que l’objet Message privé renvoyé ait une structure différente, comme décrit précédemment.

Enfin, l’accès en temps réel aux Messages privés s’effectuera désormais via un webhook avec l’[Account Activity API](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity). Pour obtenir des conseils sur la migration à partir de User Streams ou Site Streams, consultez le guide de migration vers l’Account Activity API pour plus d’informations.

<div id="summary">
  #### Résumé
</div>

* Les messages envoyés et reçus sont désormais fournis par le même endpoint.
* Jusqu’à 30 jours de messages peuvent être récupérés.
* Pagination basée sur un curseur.
* Accès en temps réel aux Messages privés via un webhook.

<div id="deleting-direct-messages">
  ### Suppression de messages privés
</div>

Les messages privés peuvent désormais être supprimés à l’aide de DELETE direct&#95;messages/events/destroy. L’interface reste globalement la même et nécessite l’id du message à supprimer. La principale différence est que ce point de terminaison requiert désormais une requête DELETE au lieu d’une requête POST.

La façon dont les messages privés supprimés apparaissent dans les clients X officiels reste la même. Les messages privés ne sont retirés que de l’interface de l’utilisateur pour le contexte fourni. Les autres participants à la conversation peuvent toujours accéder au message privé.

<div id="summary">
  #### Résumé
</div>

* La suppression d’un message privé nécessite l’identifiant.
* Le nouveau point de terminaison nécessite une requête DELETE.
* La manière dont les messages privés supprimés sont affichés dans les clients officiels X reste inchangée.

  ## FAQ

<div id="general">
  ### Général
</div>

**Quels sont les avantages de l’utilisation de l’Account Activity API ?**

L’Account Activity API utilise des webhooks, ce qui signifie que, contrairement aux API de streaming, nous n’avons pas besoin que vous mainteniez une connexion ouverte pour que nous puissions vous envoyer des informations. Les webhooks sont également différents des API REST, car vous n’avez pas à nous interroger des centaines de fois toutes les 15 minutes pour obtenir les données qui vous intéressent. Cela améliore l’efficacité entre un utilisateur et votre application, car les données sont livrées au moment où l’activité se produit.

L’Account Activity API présente plusieurs avantages :

1. **Vitesse** : nous livrons les données à la vitesse de X.
2. **Simplicité** : nous livrons tous les événements d’un compte via une seule connexion webhook. Les activités livrées dans l’API incluent les Publications, les @mentions, les réponses, les Retweets, les Quote Tweets, les Retweets de Quote Tweets, les favoris, les Direct Messages envoyés, les Direct Messages reçus, les follows, les blocks, les mutes. 
3. **Montée en charge** : vous recevez toutes les activités pour un compte que vous gérez sans être limité par des limites de débit ou des plafonds d’événements.

L’Account Activity API est disponible en sandbox Premium, offre Premium payante et offre Enterprise, de sorte que vous pouvez monter en charge à mesure que vous avez besoin de plus de comptes pour des fonctionnalités de conformité ou des fonctionnalités supplémentaires.

Pour commencer, téléchargez des exemples d’extraits de code depuis [GitHub](https://github.com/xdevplatform/account-activity-dashboard).
 

**Comment identifier le niveau de produit le mieux adapté à mes besoins ?**

Veuillez consulter notre page [Account Activity API Overview](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity) pour en savoir plus sur les différences entre les options Premium et l’option Enterprise. 
 

**Quelle est la différence entre un environnement Premium et un webhook Enterprise ?**

Il n’y en a pas. Chaque environnement Premium aura son propre `webhook_id`.
 

**J’ai besoin d’environnements de développement, de staging et de production pour l’Account Activity API, est-ce possible ?**

Oui ! Avec les niveaux payants de l’Account Activity API (Premium payant et Enterprise), il est possible d’enregistrer plusieurs URL de webhook et de gérer séparément les abonnements pour chacune via les méthodes de l’API. En outre, plusieurs applications clientes peuvent être ajoutées à une liste d’autorisation (allowlist) pour conserver l’autorisation de vos utilisateurs actuellement autorisés.
 

**Disposez-vous de guides étape par étape pour la mise en place de l’Account Activity API ?**

En effet, c’est le cas !

* Si vous débutez, nous vous recommandons de consulter notre guide [Getting started with webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)

* Suivez nos scripts fournis par X Dev : 
  * [Account Activity API dashboard](https://github.com/xdevplatform/account-activity-dashboard), une application web Node.js qui affiche les événements webhook.
  * Le [SnowBot chatbot](https://github.com/xdevplatform/SnowBotDev), une application web Ruby construite sur les API Account Activity et Direct Message. Cette base de code inclut un [script](https://github.com/xdevplatform/SnowBotDev/wiki/Account-Activity-API-setup-script) pour aider à configurer les webhooks de l’Account Activity API.
     

**Existe-t-il un moyen de récupérer les données si notre système est indisponible pendant un certain temps ?**

Avec les niveaux payants de l’Account Activity API (Premium payant et Enterprise), notre système va [réessayer](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries) de vous envoyer les activités plusieurs fois sur une période de quatre heures. Si votre système ne répond pas pendant cette période de quatre heures, l’activité sera perdue et vous devrez utiliser d’autres endpoints REST pour récupérer les données dans un délai de 7 jours.

Nous vous suggérons d’utiliser vos différents webhooks, ou environnements, comme outil de redondance, par exemple l’[Account Activity Replay API](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-replay-api), afin de vous assurer que vous ne manquez aucune activité si l’un de vos systèmes tombe en panne.
 

**Quelle authentification dois-je utiliser avec l’Account Activity API ?**

Les méthodes d’autorisation requises pour l’Account Activity API sont décrites, méthode par méthode, dans les [pages de Référence de l’API](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-api-reference-index). Si vous débutez avec l’authentification X, nous vous recommandons de lire [cette section](/fr/resources/fundamentals/authentication).

**Qu’est-ce qu’un challenge-response check (CRC) ?**

La vérification du challenge response de l’Account Activity API est une fonctionnalité de sécurité mise en place pour garantir que les activités de l’Account Activity API sont envoyées au bon développeur. Elle peut aussi être utilisée par les développeurs pour s’assurer que les données qu’ils reçoivent proviennent de X. X enverra automatiquement un CRC à votre URL de webhook toutes les 24 heures, à partir de la dernière fois où l’URL du webhook a été validée. Votre système doit répondre avec une réponse valide en moins de 3 secondes pour rester validé. 

Veuillez consulter notre page [Securing webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks) pour plus de détails.
 

**Y a-t-il quelque chose qui invaliderait immédiatement mon URL de webhook ?**

Si l’un des éléments suivants se produit, nous marquerons immédiatement votre webhook comme invalide :

* Le serveur répond à un CRC avec un jeton incorrect. Dans ce cas, notre système ne [réessaiera pas](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries) de vous envoyer l’activité.
* L’URL du webhook a un certificat incorrect configuré. Dans ce cas, notre système ne [réessaiera pas](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries) de vous envoyer l’activité.
* Votre serveur renvoie un code de réponse qui n’est ni 2XX, ni 4XXX, ni 5XXX.
* Vous indiquez l’utilisation de gzip sans réellement l’envoyer.
* Vous n’indiquez pas l’utilisation de gzip, mais vous l’envoyez en réalité dans la réponse.
   

**Vais-je recevoir des activités en double si je suis abonné à des utilisateurs qui interagissent entre eux ?**

Oui. Si votre application web a des abonnements actifs pour l’utilisateur A et l’utilisateur B, et que l’utilisateur A mentionne l’utilisateur B dans une Publication, deux activités POST seront envoyées au webhook enregistré. Chaque activité aura un indicateur &quot;for&#95;user&#95;id&quot; pour indiquer à quel abonnement l’activité appartient.
 

**Lorsque je crée un abonnement vers mon webhook, puis-je remplacer la partie `/all/` de l’endpoint suivant par d’autres objets de données d’account activity pour limiter les activités délivrées par l’API ?** `POST https://api.x.com/1.1/account_activity/all/:env_name/subscriptions.json`

Non, ce n’est pas possible. À l’heure actuelle, nous ne proposons que le produit `/all/`.
 

**Existe-t-il un moyen d’utiliser l’Account Activity API sans demander aux utilisateurs les autorisations pour les Messages privés ?**

À ce stade, les autorisations pour les Messages privés sont obligatoires, car il n’existe aucun moyen de « filtrer » les activités de Messages privés pour cette API. 
 

**Existe-t-il une version sandbox de l’Account Activity API ?**

Oui, nous proposons une option sandbox pour les tests. Notre option sandbox est limitée à un seul webhook avec une limite de 15 abonnements maximum. Vous pouvez en savoir plus sur l’option sandbox dans [notre documentation](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity). 

**Est-il possible d’utiliser l’Account Activity API pour obtenir les Retweets de Publications qui mentionnent des utilisateurs abonnés ?**

Malheureusement, cela ne fait pas partie des activités délivrées par cette API. Pour cela, nous vous suggérons d’utiliser à la place la Streaming API. 
 

**Quels sont les types d’activités possibles représentés par un tweet&#95;create&#95;event ?**

Un payload tweet&#95;create&#95;event sera envoyé :

Si l’utilisateur abonné effectue l’une des actions suivantes :

* Crée une Publication
* Retweete
* Répond à une Publication

Si un autre utilisateur :

* *@mentionne* l’utilisateur abonné
* Cite un Tweet créé par l’utilisateur abonné 

*Remarque : l’Account Activity API ne livre des événements que lorsque l’utilisateur abonné recevrait une notification de X et pourrait voir l’événement publiquement. Cela signifie que, si le compte mentionné (@userA) suit le compte protégé (@userB), alors UserA recevra une notification indiquant que UserB l’a mentionné. Si UserA ne suit pas UserB (et n’a pas été approuvé par UserB), UserA ne recevra pas de notification, et par conséquent, aucun tweet&#95;create&#95;event ne sera envoyé via AAA si @userA avait un abonnement.*

**Si un utilisateur bloqué mentionne mon utilisateur abonné, comment puis-je l’identifier ?**

Vous verrez un champ booléen `user&#95;has&#95;blocked` au niveau supérieur de la réponse JSON, défini sur « true » ou « false ». Ce champ ne sera exposé que sur les mentions de Publication.

Vous pouvez trouver l’ID de votre application en vous rendant sur la page [&quot;Apps&quot;](/fr/resources/fundamentals/developer-apps) dans la [Console de Développement](/fr/resources/fundamentals/developer-portal).
 

**Si j’ai accès à trois webhooks, puis-je utiliser trois webhooks pour chacune des applications que j’ai enregistrées pour une utilisation Enterprise ?**

La limite de webhooks est définie au niveau du compte, et non au niveau de l’application. Si vous avez accès à trois webhooks et à deux applications enregistrées pour une utilisation Enterprise, vous pouvez utiliser deux webhooks sur une application et le troisième sur l’autre application, mais pas trois sur chaque application. 

**Puis-je spécifier quels types d’événements seront renvoyés à l’aide de l’API Account Activity Replay ?**

Les types d’événements à rejouer ne peuvent pas être spécifiés. Tous les événements envoyés pendant l’intervalle de dates et d’heures indiqué seront rejoués. 

**Y aura-t-il de nouvelles tentatives si mon application ne parvient pas à ingérer un événement de l’API Account Activity Replay ?**

Non, il n’y aura pas de nouvelles tentatives de remise. Si une application ne parvient pas à ingérer un événement envoyé par l’API Account Activity Replay, un autre job de Replay peut être soumis pour la même période afin de tenter de renvoyer les événements de Replay manqués. 

**Que dois-je faire lorsque je reçois un événement de fin de traitement indiquant un succès partiel ?**

Nous vous recommandons de noter les horodatages des événements qui ont été reçus et de demander un autre job de Replay pour les événements qui ont été manqués. 

**Combien de jobs de l’API Account Activity Replay puis-je exécuter en parallèle ?**

Un seul job de l’API Account Activity Replay par webhook peut être exécuté à la fois. 

**Comment puis-je différencier les événements de l’API Account Activity Replay des événements de production en temps réel lorsqu’ils sont livrés à mon webhook ?**

Comme l’API Account Activity Replay livrera toujours des événements passés, les événements peuvent être différenciés des événements de production en temps réel en se basant sur l’horodatage de l’événement. 

**À partir de quand puis-je commencer à utiliser l’API Account Activity Replay pour renvoyer une activité que mon application a ratée ?**

Une activité devient disponible pour un renvoi environ 10 minutes après sa création. 

<div id="error-troubleshooting-guide">
  ### Guide de résolution des erreurs
</div>

<div id="code-32">
  #### Code 32
</div>

Cette erreur signifie généralement qu’un élément est mal formé dans la requête, les en-têtes, l’autorisation ou l’URL que vous indiquez. Il ne s’agit pas d’une erreur de l’Account Activity API, mais d’une erreur d’autorisation, et X ne reçoit pas la configuration OAuth ou l’URL appropriée.

* **Enterprise** - Assurez-vous que les consumer keys et access tokens que vous utilisez appartiennent à une [application X](/fr/resources/fundamentals/developer-apps) qui a été enregistrée pour l’utilisation des produits Enterprise. Si vous ne disposez pas de vos consumer keys et access tokens, ou si vous devez ajouter votre application X à l’allowlist, veuillez contacter votre gestionnaire de compte. 

* Si vous vous authentifiez dans un contexte utilisateur, assurez-vous d’avoir correctement [autorisé votre requête](/fr/resources/fundamentals/authentication#authorizing-a-request) avec les `oauth nonce`, `oauth_signature` et `oauth_timestamp` appropriés.

* Assurez-vous que vos access tokens disposent du niveau d’autorisation approprié.
  * Dans l’onglet « Keys and tokens » du [app dashboard](/fr/resources/fundamentals/developer-apps), veuillez vérifier que vos access tokens ont le niveau d’autorisation « Read, write, and direct messages » [permission level](/fr/resources/fundamentals/developer-apps#app-permissions). 
  * Si le niveau d’autorisation des tokens est défini sur une valeur inférieure, accédez à l’onglet « Permissions », définissez l’autorisation d’accès sur « Read, write, and direct messages », puis régénérez vos access tokens et leur secret depuis l’onglet « Keys and tokens ».

* Assurez-vous que votre URL est correctement formée.
  * Veuillez garder à l’esprit que `:env_name` est sensible à la casse.
     

<div id="code-200-forbidden">
  #### Code 200 - Interdit
</div>

* **Premium** - Assurez-vous de disposer d’un [compte développeur](/fr/resources/fundamentals/developer-portal) approuvé avant de tenter d’effectuer une requête vers l’API. Vous devez également utiliser le :env&#95;name approprié dans la requête, que vous pouvez configurer sur la page [dev environments](/fr/resources/fundamentals/developer-portal).

* **Enterprise** - Assurez-vous que votre gestionnaire de compte vous a bien donné accès à l’Account Activity API.

* Assurez-vous d’avoir correctement configuré votre URI. Cette erreur peut se produire si vous avez saisi une URI incorrecte dans votre requête.
   

<div id="code-214-webhook-url-does-not-meet-the-requirements">
  #### Code 214 - L’URL du webhook ne respecte pas les exigences.
</div>

* Assurez-vous d’utiliser le protocole HTTPS.
* L’URL de votre webhook est peut-être mal formée.
* Pour en savoir plus sur la configuration de votre URL de webhook, consultez la section [Develop webhook consumer app](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#3-develop-webhook-consumer-app) sur la page [Getting started with webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks).
   

<div id="code-214-high-latency-on-crc-get-request-your-webhook-should-respond-in-less-than-3-seconds">
  #### Code 214 - Latence élevée lors de la requête GET CRC. Votre webhook doit répondre en moins de 3 secondes.
</div>

* Cela signifie que votre serveur est lent. Assurez-vous de répondre à la requête CRC en moins de 3 secondes.
   

<div id="code-214-non-200-response-code-during-crc-get-request-ie-404-500-etc">
  #### Code 214 - Code de réponse différent de 200 lors d&#39;une requête GET CRC (par ex. 404, 500, etc).
</div>

* Votre serveur est en panne. Assurez-vous que votre serveur fonctionne correctement.
   

<div id="code-214-too-many-resources-already-created">
  #### Code 214 - Trop de ressources déjà créées.
</div>

* **Enterprise** - Vous avez déjà utilisé tous vos webhooks. Utilisez l’endpoint [GET webhooks](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#get-account-activity-webhooks) avec chacune de vos applications enregistrées afin d’identifier la répartition de vos webhooks. 

<div id="code-261-application-cannot-perform-write-actions">
  #### Code 261 - L&#39;application ne peut pas effectuer d&#39;actions d&#39;écriture.
</div>

* L’application que vous utilisez avec l’API n’a pas le [niveau d’autorisation](/fr/resources/fundamentals/developer-apps#app-permissions) approprié configuré pour son access token et son access token secret. Accédez à l’onglet &#39;Keys and tokens&#39; sur le tableau de bord [X apps](/fr/resources/fundamentals/developer-apps) et vérifiez les niveaux d’autorisation attribués à votre access token et à votre access token secret. S’il est défini sur autre chose que &#39;Read, write and Direct Messages,&#39; vous devrez ajuster les paramètres dans l’onglet &#39;Permission&#39; et régénérer votre access token et votre access token secret pour appliquer les nouveaux paramètres.
* Sinon, vous essayez d’enregistrer un webhook avec l’authentification app-only, ce qui n’est pas pris en charge. Authentifiez-vous plutôt avec un contexte utilisateur, comme indiqué dans les sections de la Référence de l’API consacrées à l’enregistrement d’un webhook pour l’[Enterprise Account Activity API](/fr/x-api/enterprise-gnip-2.0/fundamentals/account-activity#post-account-activity-webhooks).

<div id="replay-api">
  ### API de relecture
</div>

**POST /1.1/account&#95;activity/replay/webhooks/:webhook&#95;id/subscriptions/all.json [¶](#post-1-1-account-activity-replay-webhooks-webhook-id-subscriptions-all-json- "Permalien vers ce titre")**

Envoie une requête pour récupérer les activités des cinq derniers jours au maximum, à partir de tous les abonnements présents pendant les fenêtres de date et d’heure spécifiées dans la requête. Si votre webhook a des abonnements d’utilisateurs actifs, vous recevrez également ces événements simultanément. Remarque : nous effectuons un CRC avant de livrer les événements de relecture.

|     |     |
| :--- | :--- |
| **Méthode de la requête** | HTTP POST |
| **URL** | /1.1/account&#95;activity/replay/webhooks/:webhook&#95;id/subscriptions/all.json?from&#95;date=yyyymmddhhmm&amp;to&#95;date=yyyymmddhhmm |
| **Format de réponse** | JSON |
| **Nécessite une authentification** | Oui (application uniquement - Bearer Token) |
| **Limite de débit** | 5 requêtes par tranche de 15 minutes. Il n’y a actuellement aucune limite maximale au nombre de tâches de relecture pouvant être demandées. |
| **from&#95;date** | L’horodatage UTC le plus ancien (de début) à partir duquel les événements seront fournis, doit être au format &#39;yyyymmddhhmm&#39;. L’horodatage est à la granularité de la minute et est inclusif (c’est-à-dire que 12:00 inclut la minute 00). Les heures valides doivent se situer dans les 5 derniers jours, en heure UTC, et ne pas être plus récentes que 31 minutes avant le moment actuel. Il est recommandé que les valeurs de from&#95;date et to&#95;date soient espacées d’environ 2 heures au maximum. |
| **to&#95;date** | L’horodatage UTC le plus récent (de fin) jusqu’auquel les événements seront fournis, doit être au format &#39;yyyymmddhhmm&#39;. L’horodatage est à la granularité de la minute et est exclusif (c’est-à-dire que 12:30 n’inclut pas la 30e minute de l’heure). Les heures valides doivent se situer dans les 5 derniers jours, en heure UTC, et ne pas être plus récentes que 10 minutes avant le moment actuel. |

  "replay\_job\_status": {

    "job_state": "Complete",

  }
}
```

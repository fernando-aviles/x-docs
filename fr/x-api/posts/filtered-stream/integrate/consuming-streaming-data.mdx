<div id="building-a-client-to-consume-streaming-data">
  ### Créer un client pour consommer des données en streaming
</div>

Lorsque vous utilisez un endpoint de streaming, appliquez quelques bonnes pratiques générales pour en optimiser l’utilisation.  
 

<div id="client-design">
  #### Conception du client
</div>

Lors de la création d&#39;une solution avec l&#39;endpoint de flux filtré, vous aurez besoin d&#39;un client capable d&#39;effectuer les opérations suivantes :

1. Établir une connexion de streaming HTTPS vers l&#39;endpoint de flux filtré.
2. Envoyer de manière asynchrone des requêtes POST à l&#39;endpoint des règles de flux filtré pour ajouter et supprimer des règles du flux.
3. Gérer de faibles volumes de données – maintenir la connexion de streaming, détecter les objets Publication et les signaux de maintien de connexion (keep-alive).
4. Gérer de forts volumes de données – découpler l&#39;ingestion du flux du traitement supplémentaire à l&#39;aide de processus asynchrones, et s&#39;assurer que les tampons côté client sont vidés régulièrement.
5. Assurer le suivi de la consommation de volume côté client.
6. Détecter les déconnexions du flux, les évaluer et se reconnecter automatiquement au flux.
    

<div id="connecting-to-a-streaming-endpoint">
  #### Connexion à un endpoint de streaming
</div>

Établir une connexion à des endpoints de streaming de X API v2 implique d’effectuer une requête HTTP de très longue durée de vie et de traiter la réponse de manière incrémentielle. Conceptuellement, vous pouvez l’envisager comme le téléchargement d’un fichier infiniment long via HTTP. Une fois la connexion établie, le serveur X enverra des événements de publication par cette connexion tant qu’elle restera ouverte.
 

<div id="consuming-data">
  #### Consommation des données
</div>

Notez que les différents champs des objets JSON ne sont pas ordonnés et que tous les champs ne seront pas présents dans toutes les circonstances. De même, les activités distinctes ne sont pas livrées dans un ordre particulier et vous pouvez recevoir des messages en double. Gardez à l&#39;esprit qu&#39;au fil du temps, de nouveaux types de messages peuvent être ajoutés et envoyés via le flux.

Ainsi, votre client doit tolérer :

* Des champs apparaissant dans n&#39;importe quel ordre
* Des champs inattendus ou manquants
* Des Publications non triées
* Des messages en double
* De nouveaux types de messages arbitraires pouvant apparaître sur le flux à tout moment

En plus des données pertinentes de Publication et des paramètres de champs que vous avez demandés, les types de messages suivants peuvent être renvoyés sur une connexion de flux. Notez que cette liste peut ne pas être exhaustive — des objets supplémentaires peuvent être introduits dans les flux. Veillez à ce que votre analyseur puisse gérer des formats de messages inattendus.
 

<div id="buffering">
  #### Mise en mémoire tampon
</div>

Les points de terminaison de streaming vous enverront des données dès qu’elles sont disponibles, ce qui peut dans de nombreux cas entraîner des volumes élevés. Si le serveur X ne peut pas écrire immédiatement de nouvelles données dans le flux (par exemple si votre client ne lit pas assez rapidement, voir [gestion des déconnexions](/fr/x-api/posts/filtered-stream#what-is-a-disconnection) pour plus d’informations), il mettra le contenu en mémoire tampon de son côté afin de permettre à votre client de rattraper son retard. Cependant, lorsque cette mémoire tampon est pleine, une déconnexion forcée sera effectuée et la connexion sera interrompue, et les Publications mises en mémoire tampon seront supprimées et ne seront pas renvoyées. Voir ci-dessous pour plus de détails.

Une façon d’identifier les moments où votre application prend du retard consiste à comparer l’horodatage des Publications reçues avec l’heure actuelle et à suivre cet écart dans le temps.

Même si les engorgements du flux ne peuvent jamais être complètement éliminés en raison de la latence potentielle et des à-coups sur l’Internet public, ils peuvent être largement réduits grâce à une configuration adéquate de votre application. Pour minimiser la survenue de ces engorgements :

* Assurez-vous que votre client lit le flux suffisamment rapidement. En règle générale, vous ne devez effectuer aucun véritable travail de traitement pendant la lecture du flux. Lisez le flux et confiez l’activité à un autre thread/processus/stockage de données pour effectuer votre traitement de manière asynchrone.
* Assurez-vous que votre data center dispose d’une bande passante entrante suffisante pour prendre en charge des volumes de données importants et soutenus, ainsi que des pics nettement plus élevés (par exemple 5 à 10 fois le volume normal). Pour le flux filtré, le volume et la bande passante correspondante requis de votre côté dépendent entièrement des Publications correspondant à vos règles.
   

<div id="usage-tracking-and-rule-management">
  #### Suivi d’utilisation et gestion des règles
</div>

Comme les attentes des développeurs concernant ce que devrait être un volume de données « normal » pour leurs flux varient, nous n’avons pas de recommandation générale pour un pourcentage spécifique de baisse/hausse ni pour une période donnée. 

Nous vous recommandons de surveiller les volumes de données de votre flux pour détecter toute variation inattendue. Une baisse du volume de données peut être symptomatique d’un problème différent d’une déconnexion du flux. Dans une telle situation, un flux continuerait à recevoir le signal keep-alive et probablement quelques nouvelles données d’activité. Cependant, une diminution significative du nombre de Publications doit vous amener à vérifier s’il existe un facteur qui provoque la baisse du volume de données entrantes vers votre application ou votre réseau, et à consulter la [page de statut](https://api.twitterstat.us/) pour voir si des avis y sont liés.

Pour mettre en place un tel mécanisme de surveillance, vous pouvez suivre le nombre de nouvelles Publications que vous vous attendez à voir dans une durée donnée. Si le volume de données d’un flux descend suffisamment en dessous du seuil spécifié et ne se rétablit pas dans une période définie, alors des alertes et notifications doivent être déclenchées. Vous pouvez également souhaiter surveiller une forte augmentation du volume de données, en particulier si vous êtes en train de modifier des règles dans un flux filtré, ou si un événement se produit et génère un pic d’activité de Publications.

Il est important de noter que les Publications livrées via un flux filtré comptent dans le volume mensuel total de Publications, et que vous devez suivre et ajuster la consommation afin de l’optimiser. Si le volume est élevé, envisagez d’ajouter un opérateur sample: à chacune de vos règles pour réduire la correspondance de 100 % à sample:50 ou sample:25 lorsque cela est nécessaire.

De plus, nous vous encourageons à mettre en place dans votre application des mécanismes qui alerteront votre équipe si le volume dépasse un seuil prédéfini, et éventuellement à introduire d’autres mesures, telles que la suppression automatique de règles qui génèrent trop de données, ou la déconnexion complète du flux dans des cas extrêmes.
 

<div id="responding-to-system-messages">
  #### Répondre aux messages système
</div>

Signaux de maintien en vie
Au moins toutes les 20 secondes, le flux enverra un signal de maintien en vie (ou battement de cœur) sous la forme d’un retour chariot \r\n via la connexion ouverte afin d’empêcher votre client d’expirer. Votre application cliente doit être tolérante aux caractères \r\n présents dans le flux.

Si votre client implémente correctement un délai d’expiration de lecture (read timeout) au niveau de votre bibliothèque HTTP, votre application pourra s’appuyer sur le protocole HTTP et sur votre bibliothèque HTTP pour déclencher un événement si aucune donnée n’est lue pendant cette période, et vous n’aurez pas besoin de surveiller explicitement l’apparition du caractère \r\n.

Cet événement sera généralement une exception levée ou un autre type d’événement selon la bibliothèque HTTP utilisée. Il est fortement recommandé d’entourer vos méthodes HTTP de gestionnaires d’erreurs/d’événements pour détecter ces délais d’expiration. En cas de délai d’expiration, votre application doit tenter de se reconnecter.

Messages d’erreur
Les endpoints de streaming v2 peuvent également envoyer des messages d’erreur dans le flux. Le format de base de ces messages est fourni ci-dessous, accompagné de quelques exemples. Notez que les messages envoyés peuvent changer, avec de nouveaux messages introduits. Les applications clientes doivent être tolérantes aux évolutions des charges utiles des messages système.

Notez que les messages d’erreur contiendront un lien vers la documentation décrivant comment résoudre le problème.

Format du message :

```{
	"errors": [{
		"title": "operational-disconnect",
		"disconnect_type": "UpstreamOperationalDisconnect",
		"detail": "This stream has been disconnected upstream for operational reasons.",
		"type": "https://api.x.com/2/problems/operational-disconnect"
	}]
}
```

Notez que les messages d’erreur indiquant une déconnexion forcée en raison d’un tampon plein peuvent ne jamais parvenir à votre Client, si l’engorgement qui a provoqué la déconnexion forcée les empêche de passer. Par conséquent, votre application ne doit pas compter sur ces messages pour déclencher une reconnexion.

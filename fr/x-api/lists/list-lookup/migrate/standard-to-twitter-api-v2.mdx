<div id="list-lookup-standard-v11-compared-to-x-api-v2">
  ### Recherche de listes : standard v1.1 comparé à X API v2
</div>

Si vous utilisez les endpoints standard v1.1 [GET lists/show](https://developer.x.com/en/docs/twitter-api/v1/accounts-and-users/create-manage-lists/api-reference/get-lists-show) et [GET lists/ownerships](https://developer.x.com/en/docs/twitter-api/v1/accounts-and-users/create-manage-lists/api-reference/get-lists-ownerships), l’objectif de ce guide est de vous aider à comprendre les similitudes et les différences entre les endpoints de recherche de listes du standard v1.1 et de X API v2.

* **Similitudes**
  * Méthodes d’authentification
  * Limites de débit
* **Différences**
  * URL des endpoints
  * Exigences relatives aux applications et au Project
  * Limites du nombre d’objets de données par requête
  * Formats de données de réponse
  * Paramètres de requête

<div id="similarities">
  #### Similarités
</div>

**Authentification**

Les deux versions d’endpoint prennent en charge à la fois [OAuth 1.0a User Context](/fr/resources/fundamentals/authentication#oauth-1-0a-2) et [App only](/fr/resources/fundamentals/authentication#app-only-authentication-and-oauth-2-0-bearer-token). Par conséquent, si vous utilisiez auparavant l’un des endpoints de recherche de listes standard v1.1, vous pouvez continuer à utiliser la même méthode d’authentification si vous migrez vers la version X API v2.

En fonction de la bibliothèque ou du package d’authentification de votre choix, l’authentification App only est probablement la façon la plus simple de commencer et peut être configurée avec un simple en-tête de requête. Pour savoir comment générer un App only Access Token, consultez [ce guide App only](/fr/resources/fundamentals/authentication#using-and-generating-an-app-only-bearer-token).

**Limites de fréquence**

|     |     |
| :--- | :--- |
| **Standard v1.1** | **X API v2** |
| /1.1/lists/show.json<br /><br />75 requêtes par fenêtre de 15 minutes avec OAuth 1.0a User Context<br /><br />75 requêtes par fenêtre de 15 minutes avec App only | /2/lists/:id<br /><br />75 requêtes par fenêtre de 15 minutes avec OAuth 1.0a User Context<br /><br />75 requêtes par fenêtre de 15 minutes avec OAuth 2.0 Authorization Code with PKCE |
| /1.1/lists/ownerships.json<br /><br />15 requêtes par fenêtre de 15 minutes avec OAuth 1.0a User Context<br /><br />15 requêtes par fenêtre de 15 minutes avec App only | /2/users/:id/owned&#95;lists<br /><br />15 requêtes par fenêtre de 15 minutes avec OAuth 1.0a User Context<br /><br />15 requêtes par fenêtre de 15 minutes avec OAuth 2.0 Authorization Code with PKCE<br /><br />15 requêtes par fenêtre de 15 minutes avec App only |

<div id="differences">
  #### Différences
</div>

**URL des endpoints**

* Endpoints standard v1.1 :
  * GET https://api.x.com/1.1/lists/show.json
    (Recherche d&#39;une Liste donnée)
  * GET https://api.x.com/1.1/lists/ownerships.json
    (Recherche des Listes appartenant à un utilisateur donné)
* Endpoint X API v2 :
  * GET https://api.x.com/2/lists/:id
    (Recherche d&#39;une Liste donnée)

  * GET https://api.x.com/2/users/:id/owned&#95;lists
    (Recherche des Listes appartenant à un utilisateur donné)

**Exigences liées à l&#39;App et au Projet**

Les endpoints X API v2 exigent que vous utilisiez des identifiants provenant d&#39;une [App développeur](/fr/resources/fundamentals/developer-apps) associée à un [Projet](/fr/resources/fundamentals/developer-apps) lors de l&#39;authentification de vos requêtes. Tous les endpoints X API v1.1 peuvent utiliser des identifiants provenant d&#39;Apps ou d&#39;Apps associées à un Projet.

**Limites sur le nombre d&#39;objets de données par requête**

L&#39;endpoint standard v1.1 /lists/ownerships vous permet de renvoyer jusqu&#39;à 1000 Listes par requête. Les nouveaux endpoints v2 vous permettent de renvoyer jusqu&#39;à 100 Listes par requête. Par défaut, 100 objets utilisateur seront renvoyés ; pour modifier le nombre de résultats, vous devez transmettre un paramètre de requête max&#95;results= avec un nombre compris entre 1 et 100 ; vous pouvez ensuite transmettre le next&#95;token renvoyé dans la charge utile de la Réponse au paramètre de requête pagination&#95;token dans votre requête suivante.

**Format des données de la Réponse**

L&#39;une des plus grandes différences entre les versions des endpoints standard v1.1 et X API v2 est la manière dont vous sélectionnez les champs renvoyés dans votre charge utile.

Pour les endpoints standard, vous recevez de nombreux champs de Réponse par défaut, puis vous avez la possibilité d&#39;utiliser des paramètres pour identifier quels champs supplémentaires ou ensembles de champs doivent être renvoyés dans la charge utile.

La version X API v2 ne délivre par défaut que les champs id et name de la Liste. Pour demander des champs ou objets supplémentaires, vous devez utiliser les paramètres [fields](/fr/x-api/fundamentals/fields) et [expansions](/fr/x-api/fundamentals/expansions). Tous les champs de Liste que vous demandez depuis cet endpoint seront renvoyés dans l&#39;objet principal Liste. Tout objet et champ de Publication ou d&#39;utilisateur étendu sera renvoyé dans un objet includes au sein de votre Réponse. Vous pourrez ensuite faire correspondre les objets étendus à l&#39;objet Liste en faisant correspondre les IDs situés à la fois dans l&#39;objet user et dans l&#39;objet Publication étendu. 

Voici des exemples de champs de Liste et d&#39;expansions possibles :

* created&#95;at

* follower&#95;count

* member&#95;count

* owner&#95;id

* description

* private

|     |     |
| :--- | :--- |
| **Endpoint** | **Expansion** |
| /2/lists/:id | owner&#95;id |
| /2/users/:id/owned&#95;lists | owner&#95;id |

Nous vous encourageons à en savoir plus sur ces nouveaux paramètres dans leurs guides respectifs, ou en lisant notre guide sur [comment utiliser fields et expansions](/fr/x-api/fundamentals/data-dictionary#how-to-use-fields-and-expansions). 

Nous avons également élaboré un [guide de migration de format de données](/fr/x-api/migrate/data-format-migration) qui peut vous aider à faire correspondre les champs standard v1.1 aux champs plus récents v2. Ce guide vous fournira également le paramètre d&#39;expansion et de champ spécifique que vous devrez transmettre avec votre requête v2 pour renvoyer des champs spécifiques. 

En plus des changements dans la manière de demander certains champs, X API v2 introduit également de nouveaux modèles JSON pour les objets renvoyés par les APIs, y compris les objets [Post](/fr/x-api/fundamentals/data-dictionary#tweet) et [user](/fr/x-api/fundamentals/data-dictionary#user).

* Au niveau racine du JSON, les endpoints standard renvoient des objets Post dans un tableau statuses, tandis que X API v2 renvoie un tableau data. 

* Au lieu de faire référence à des &quot;statuses&quot; Retweeted et Quoted, le JSON de X API v2 fait référence à des Tweets Retweeted et Quoted. De nombreux champs hérités et obsolètes, tels que contributors et user.translator&#95;type, sont supprimés. 

* Au lieu d&#39;utiliser à la fois favorites (dans l&#39;objet Post) et favourites (dans l&#39;objet user), X API v2 utilise le terme like. 

* X adopte la convention selon laquelle les valeurs JSON sans valeur (par exemple null) ne sont pas écrites dans la charge utile. Les attributs de Publication et d&#39;utilisateur ne sont inclus que s&#39;ils ont des valeurs non nulles.

**Paramètres de requête**

Les paramètres de requête standard v1.1 suivants ont des équivalents dans X API v2 :

**Recherche de Liste par ID**

|     |     |
| :--- | :--- |
| **Standard v1.1** | **X API v2** |
| list&#95;id | id  |
| slug | Aucun équivalent |
| owner&#95;screen&#95;name | Aucun équivalent |
| owner&#95;id | Demandé via le paramètre expansions/fields |

**Recherche de Liste appartenant à un utilisateur**

|     |     |
| :--- | :--- |
| **Standard v1.1** | **X API v2** |
| user&#95;id | id  |
| screen&#95;name | Aucun équivalent |
| count | max&#95;results |
| cursor | pagination&#95;token |

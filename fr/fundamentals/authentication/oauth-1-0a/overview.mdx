<div id="oauth-10a">
  ## OAuth 1.0a
</div>

De nombreux endpoints sur la plateforme développeur X utilisent la méthode OAuth 1.0a pour agir, ou effectuer des requêtes API, au nom d’un compte X. Par exemple, si vous avez une App développeur X, vous pouvez effectuer des requêtes API au nom de n’importe quel compte X, tant que cet utilisateur a autorisé votre App.

Veuillez noter : si vous n’êtes pas à l’aise avec des concepts tels que HMAC-SHA1 et l’encodage en pourcentage, nous vous recommandons de consulter la section « useful tools » ci-dessous, qui répertorie certains clients API qui simplifient grandement le processus d’authentification.

<div id="key-concepts">
  ### Concepts clés
</div>

<div id="signing-a-request-with-keys-and-tokens">
  #### Signer une requête avec des clés et des jetons
</div>

Vous devez signer chaque requête API en incluant plusieurs clés et jetons générés dans un en-tête d&#39;autorisation. Pour commencer, vous pouvez générer plusieurs clés et jetons sur la page de détails de votre [App développeur X](/fr/resources/fundamentals/developer-apps), notamment les éléments suivants :

|     |     |
| :--- | :--- |
| Clé d’API et secret :<br /><br />`oauth_consumer_key`<br /><br />`oauth_consumer_secret` | Considérez-les comme le nom d&#39;utilisateur et le mot de passe qui représentent votre App développeur X lors de l&#39;envoi de requêtes API. |
| Jeton d’accès et secret :<br /><br />`oauth_token`<br /><br />`oauth_token_secret` | Un jeton d&#39;accès et un secret de jeton d&#39;accès sont des identifiants spécifiques à un utilisateur, utilisés pour authentifier les requêtes d&#39;API OAuth 1.0a. Ils indiquent le compte X au nom duquel la requête est effectuée.<br /><br />Vous pouvez générer votre propre jeton d&#39;accès et son secret si vous souhaitez que votre App envoie des requêtes au nom du même compte X associé à votre compte développeur sur la page de détails de l&#39;[App développeur X]/resources/fundamentals/developer-apps).<br /><br />Si vous souhaitez générer des jetons d&#39;accès pour un autre utilisateur, consultez « Making requests on behalf of users » ci-dessous. |

<div id="making-requests-on-behalf-of-users">
  #### Envoyer des requêtes pour le compte d’utilisateurs
</div>

Lors de la création d’une signature, vous avez besoin d’un ensemble de jetons d’accès qui représentent l’utilisateur pour le compte duquel vous allez envoyer une requête.

Vous pouvez générer un ensemble de jetons d’accès qui représente le compte X propriétaire de l’App développeur X à partir de la [page de détails de l’app](https://developer.x.com/content/developer-twitter/en/apps), mais si vous souhaitez envoyer une requête pour le compte d’un autre compte X, le propriétaire de ce compte doit vous accorder l’accès en se connectant à son compte dans le cadre du [flux OAuth à 3 volets (3-legged OAuth)](/fr/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow). Le résultat de ce processus est un ensemble de jetons d’accès (oauth&#95;token et oauth&#95;token&#95;secret) qui peuvent être utilisés pour envoyer une requête OAuth 1.0a.

Une fois que vous disposez de ces clés et jetons, vous pouvez [créer une signature](/fr/resources/fundamentals/authentication#creating-a-signature) à partir de zéro. Nous ne le recommandons pas, sauf si vous savez ce que vous faites ou si vous utilisez l’un des outils mentionnés ci-dessous pour envoyer une requête à un point de terminaison qui nécessite OAuth 1.0a.

Pour référence, voici un exemple de requête cURL signée avec tous les jetons générés transmis dans un en-tête d’autorisation :

```bash
curl --request POST \
  --url 'https://api.x.com/1.1/statuses/update.json?status=Hello%20world' \
  --header 'authorization: OAuth oauth_consumer_key="CONSUMER_API_KEY", oauth_nonce="OAUTH_NONCE", oauth_signature="OAUTH_SIGNATURE", oauth_signature_method="HMAC-SHA1", oauth_timestamp="OAUTH_TIMESTAMP", oauth_token="ACCESS_TOKEN", oauth_version="1.0"' \
```

<Note>
  **Remarque :** Les jetons d’accès utilisateur sont sensibles et doivent être protégés avec le plus grand soin. Lorsque des jetons d’accès sont générés, l’utilisateur qu’ils représentent fait confiance à votre application pour les conserver en toute sécurité. Si la sécurité des clés d’API ainsi que des jetons d’accès utilisateur est compromise, votre application pourrait potentiellement exposer l’accès à des informations privées et à des fonctionnalités de compte. Nous vous encourageons à en apprendre davantage sur [la sécurisation des clés et des jetons d’accès](/fr/resources/fundamentals/developer-apps).
</Note>

<div id="useful-tools">
  ### Outils utiles
</div>

Le processus de [signature d’une requête](/fr/resources/fundamentals/authentication#creating-a-signature) est complexe. Nous vous recommandons d’utiliser une bibliothèque cliente d’API qui prend automatiquement en charge une grande partie de la gestion du jeton d’authentification :

|     |     |
| :--- | :--- |
| [Postman](https://www.getpostman.com/) | Un client d’API qui vous permet de créer et d’envoyer des requêtes d’API REST. Lisez notre tutoriel « [Bien démarrer avec Postman](/fr/tutorials/postman-getting-started) » pour en savoir plus sur cet outil. |
| [Insomnia](https://insomnia.rest/) | Insomnia est un client d’API REST avec gestion des cookies, variables d’environnement, génération de code et authentification pour Mac, Windows et Linux. |

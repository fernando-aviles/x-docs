Vos clés et jetons API doivent être protégés avec le plus grand soin. 

Ces identifiants sont directement liés à votre [App développeur](/fr/resources/fundamentals/developer-apps) et aux comptes X qui vous ont autorisé à effectuer des requêtes en leur nom. Si vos clés sont compromises, des personnes malveillantes pourraient les utiliser pour effectuer des requêtes vers les endpoints X au nom de votre App développeur ou de ses utilisateurs autorisés, ce qui pourrait vous faire atteindre des limites de débit inattendues, épuiser votre quota d’accès payant, voire entraîner la suspension de votre App développeur.

Les sections suivantes présentent des bonnes pratiques à prendre en compte lors de la gestion de vos clés et jetons API.

<div id="regenerate-api-keys-and-tokens">
  ## Régénérer des clés et des tokens d’API
</div>

Si vous pensez que vos clés d’API ont été compromises, vous devez les régénérer en suivant ces étapes :

1. Accédez à la [page &quot;Apps&quot; de la Developer Console](https://developer.x.com/en/portal/projects-and-apps.html).
2. Cliquez sur l’icône &quot;Keys and tokens&quot; (🗝 ) à côté de l’App concernée.
3. Cliquez sur le bouton &quot;Regenerate&quot; à côté de l’ensemble de clés et de tokens que vous souhaitez régénérer. 

Si vous préférez régénérer vos Access Tokens ou Bearer Tokens de manière programmatique, vous pouvez le faire en utilisant nos endpoints d’authentification.

* Si vous souhaitez régénérer vos Access Tokens, vous devez d’abord invalider vos tokens à l’aide de l’endpoint [POST oauth/invalidate&#95;token](/fr/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token), puis régénérer vos tokens à l’aide du [flux OAuth à 3 volets](/fr/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens).
* Si vous souhaitez régénérer votre Bearer Token, vous devez d’abord invalider votre token à l’aide de l’endpoint [POST oauth2/invalidate&#95;token](/fr/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token), puis régénérer votre token à l’aide de l’endpoint [POST oauth2/token](/fr/resources/fundamentals/authentication/api-reference#post-oauth2-token).

<div id="having-a-central-file-for-your-secrets">
  ## Avoir un fichier central pour vos secrets
</div>

Disposer d’un fichier tel qu’un fichier .env ou de tout autre type de fichier .yaml pour stocker vos secrets peut être utile, mais assurez-vous d’avoir un fichier .gitignore robuste qui empêche de les valider par inadvertance dans un dépôt Git. 

<div id="environment-variables">
  ## Variables d&#39;environnement
</div>

Écrire du code qui utilise des variables d&#39;environnement peut être utile. 

En voici un exemple en Python :

```python
import os

consumer_key = os.environ.get("CONSUMER_KEY")

consumer_secret = os.environ.get("CONSUMER_SECRET")
```

Dans votre terminal, saisissez une commande similaire à celle-ci :

```bash
export CONSUMER_KEY='xxxxxxxxxxxxxxxxxxx'
export CONSUMER_SECRET='xxxxxxxxxxxxxxxxxxxxxxx'
```

<div id="source-code-and-version-control">
  ## Code source et contrôle de version
</div>

Les erreurs de sécurité les plus courantes commises par les développeurs consistent à avoir des clés d’API et des jetons enregistrés dans le code source, dans des systèmes de contrôle de version accessibles comme GitHub et BitBucket. Beaucoup de ces dépôts de code sont accessibles publiquement. Cette erreur est si fréquente dans les dépôts publics qu’il existe des bots très rentables qui explorent ces dépôts à la recherche de clés d’API.

* Utilisez des variables d’environnement côté serveur. En stockant vos clés d’API dans des variables d’environnement, vous les gardez hors de votre code et de votre contrôle de version. Cela vous permet également d’utiliser facilement des clés différentes pour des environnements différents.
* Utilisez un fichier de configuration exclu du contrôle de version. Ajoutez le nom de fichier à votre fichier [.gitignore](https://git-scm.com/docs/gitignore) pour exclure ce fichier du suivi par le contrôle de version.
* Si vous supprimez les clés d’API de votre code après avoir utilisé le contrôle de version, il est probable que les clés d’API restent accessibles en consultant les versions précédentes de votre code. Régénérez vos clés d’API, comme décrit dans la section suivante.

<div id="databases">
  ## Bases de données
</div>

Si vous devez stocker vos jetons d&#39;accès dans une base de données, gardez à l&#39;esprit les points suivants :

* Limitez l&#39;accès à la base de données de façon à ce que les jetons d&#39;accès ne soient lisibles que par le propriétaire du jeton.
* Restreignez les privilèges de modification/écriture sur la table de base de données contenant les jetons d&#39;accès ; cela doit être automatisé avec le système de gestion des clés.
* Chiffrez les jetons d&#39;accès avant de les stocker dans tout système de stockage de données.

<div id="password-management-tools">
  ## Outils de gestion de mots de passe
</div>

Les outils de gestion de mots de passe tels que 1Password ou LastPass peuvent être utiles pour conserver vos clés et jetons en lieu sûr. Il peut être préférable d’éviter de les partager dans un gestionnaire de mots de passe d’équipe partagé.

<div id="web-storage-cookies">
  ## Stockage web &amp; cookies
</div>

Il existe deux types de stockage web : `LocalStorage` et `SessionStorage`. Ceux-ci ont été créés comme une amélioration par rapport à l’utilisation de cookies, car la capacité de stockage pour le stockage web est bien plus élevée que pour les cookies. Cependant, chaque option de stockage présente des avantages et des inconvénients différents.
 

**Web Storage : LocalStorage**

Tout ce qui est stocké dans le stockage web local est persistant. Cela signifie que les données persisteront jusqu’à ce qu’elles soient explicitement supprimées. Selon les besoins de votre projet, vous pouvez considérer cela comme un avantage. Toutefois, vous devez être attentif lorsque vous utilisez `LocalStorage`, car toute modification ou tout ajout de données sera disponible lors de toutes les visites futures de la page web concernée. Nous ne recommandons généralement pas l’utilisation de `LocalStorage`, même s’il peut exister quelques exceptions. Si vous décidez d’utiliser `LocalStorage`, il est utile de savoir qu’il respecte la politique de même origine (same-origin policy), de sorte que toutes les données stockées ici ne seront accessibles qu’à partir de la même origine. Un avantage de performance supplémentaire de l’utilisation de `LocalStorage` est la diminution du trafic client-serveur, puisque les données n’ont pas à être renvoyées au serveur pour chaque requête HTTP.
 

**Web Storage : SessionStorage**

`SessionStorage` est similaire à `LocalStorage`, mais la différence clé est que `SessionStorage` n’est pas persistant. Une fois la fenêtre (ou l’onglet, selon le navigateur que vous utilisez) qui a été utilisée pour écrire dans `SessionStorage` fermée, les données sont perdues. Cela est utile pour limiter l’accès en lecture à votre jeton pendant une session utilisateur. L’utilisation de `SessionStorage` est généralement préférable à `LocalStorage` si l’on raisonne en termes de sécurité. Comme pour `LocalStorage`, les avantages de la prise en charge de la politique de même origine et de la diminution du trafic client-serveur s’appliquent également à `SessionStorage`.
 

**Cookies**

Les cookies sont la méthode plus traditionnelle pour stocker des données de session. Vous pouvez définir une date d’expiration pour chaque cookie, ce qui facilite la révocation et la restriction de l’accès. Cependant, le trafic client-serveur augmentera nettement lorsque vous utilisez des cookies, puisque les données sont renvoyées au serveur à chaque requête HTTP. Si vous décidez d’utiliser des cookies, vous devez vous protéger contre le détournement de session (session hijacking). Par défaut, les cookies sont envoyés en clair sur HTTP, ce qui rend leur contenu vulnérable à l’interception de paquets et/ou aux attaques de type homme du milieu, au cours desquelles des attaquants peuvent modifier votre trafic. Vous devez toujours imposer HTTPS pour protéger vos données en transit. Cela fournira la confidentialité, l’intégrité (des données) et l’authentification. Cependant, si votre application ou site web est accessible à la fois via HTTP et HTTPS, vous devrez également utiliser l’attribut `Secure` sur le cookie. Cela empêchera les attaquants d’envoyer à un utilisateur des liens vers la version HTTP de votre site et d’espionner la requête HTTP qui en résulte.

Une autre mesure de défense secondaire contre le détournement de session lors de l’utilisation de cookies consiste à valider de nouveau l’identité de l’utilisateur avant d’exécuter toute action à fort impact. Un autre attribut à envisager pour améliorer la sécurité de vos cookies est l’attribut `HttpOnly`. Cet attribut indique au navigateur que le cookie en question ne doit être accessible qu’à partir du serveur spécifié. Toute tentative effectuée par des scripts côté client sera interdite par cet attribut, ce qui contribue à se protéger contre la plupart des attaques de type cross-site scripting (XSS).

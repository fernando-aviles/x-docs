<div id="app-only-authentication-and-oauth-20-bearer-token">
  ### Authentification applicative seule et OAuth 2.0 Bearer Token
</div>

X offre aux applications la possibilité d’émettre des requêtes authentifiées pour le compte de l’application elle-même, plutôt que pour le compte d’un utilisateur spécifique. L’implémentation de X est basée sur le flux [Client Credentials Grant](http://tools.ietf.org/html/rfc6749#section-4.4) de la [spécification OAuth 2](http://tools.ietf.org/html/rfc6749).

L’authentification applicative seule n’inclut aucun contexte utilisateur et est une forme d’authentification dans laquelle une application effectue des requêtes API en son propre nom. Cette méthode est destinée aux développeurs qui ont uniquement besoin d’un accès en lecture aux informations publiques. 

Vous pouvez effectuer une authentification applicative seule en utilisant les clés API consommateur de vos applications, ou en utilisant un App only Access Token (Bearer Token). Cela signifie que les seules requêtes que vous pouvez effectuer vers l’X API ne doivent pas nécessiter d’utilisateur authentifié.

Avec l’authentification applicative seule, vous pouvez effectuer des actions telles que :

* Récupérer les timelines des utilisateurs
* Accéder aux abonnements et abonnés de n’importe quel compte
* Accéder aux ressources de listes
* Rechercher des Tweets

Veuillez noter que seuls [OAuth 1.0a](/fr/resources/fundamentals/authentication/oauth-1-0a/api-key-and-secret) ou [OAuth 2.0 Authorization Code Flow](/fr/resources/fundamentals/authentication/oauth-2-0/authorization-code) avec PKCE sont requis pour émettre des requêtes au nom des utilisateurs. La page [Référence de l’API](/fr/resources/fundamentals/authentication/api-reference) décrit la méthode d’authentification requise pour utiliser une API. Vous aurez besoin d’une authentification utilisateur, avec contexte utilisateur, et d’un [access token](/fr/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens) pour effectuer les actions suivantes :

* Publier des Tweets ou d’autres ressources
* Rechercher des utilisateurs
* Utiliser n’importe quel endpoint géographique
* Accéder aux messages privés ou aux informations d’identification du compte
* Récupérer les adresses e‑mail des utilisateurs

<div id="auth-flow">
  #### Flux d’authentification
</div>

Pour utiliser cette méthode, vous devez utiliser un [App only Access Token](/fr/resources/fundamentals/authentication/oauth-2-0/application-only) (également appelé [Bearer Token](/fr/resources/fundamentals/authentication/oauth-2-0/bearer-tokens)). Vous pouvez générer un App only Access Token (Bearer Token) en transmettant votre consumer key et votre consumer secret à l’endpoint [POST oauth2/token](/fr/resources/fundamentals/authentication/api-reference#post-oauth2-token).

Le flux d’authentification application-only suit les étapes suivantes :

* Une application encode sa consumer key et son consumer secret dans un ensemble d’identifiants spécifiquement encodés.
* Une application envoie une requête à l’endpoint [POST oauth2/token](/fr/resources/fundamentals/authentication/api-reference#post-oauth2-token) pour échanger ces identifiants contre un [App only Access Token](/fr/resources/fundamentals/authentication/oauth-2-0/application-only).
* Lorsqu’elle accède à l’API REST, l’application utilise l’App only Access Token pour s’authentifier.

Comme il n’est pas nécessaire de signer une requête, cette approche est beaucoup plus simple que le modèle OAuth 1.0a standard.

<div id="about-application-only-auth">
  #### À propos de l’authentification uniquement par application
</div>

**Les jetons sont des mots de passe**

Gardez à l’esprit que la consumer key, le consumer secret et l’App only Access Token (Bearer Token) lui‑même permettent d’effectuer des requêtes au nom d’une application. Ces valeurs doivent être considérées comme aussi sensibles que des mots de passe et ne doivent pas être partagées ni distribuées à des tiers non fiables.

**SSL obligatoire**

Toutes les requêtes (tant pour obtenir que pour utiliser les jetons) *doivent* utiliser des endpoints HTTPS. Suivez les bonnes pratiques décrites dans [Connecting to X API using TLS](/fr/resources/fundamentals/authentication/guides/tls) — les pairs doivent **toujours** être vérifiés.

**Aucun contexte utilisateur**

Lorsque vous émettez des requêtes en utilisant l’authentification uniquement par application, il n’y a pas de notion d’« utilisateur actuel ». Par conséquent, des endpoints comme [POST statuses/update](/fr/x-api/posts/creation-of-a-post) ne fonctionneront pas avec l’authentification uniquement par application. Consultez [using OAuth](/fr/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens) pour plus d’informations sur l’émission de requêtes au nom d’un utilisateur.

**Limitation de débit**

Les applications disposent de deux types de pools de limitation de débit.

Les requêtes effectuées au nom des utilisateurs avec des jetons d’accès, également appelées contexte utilisateur, utilisent un contexte de limitation de débit différent de celui utilisé dans l’authentification uniquement par application. En d’autres termes, les requêtes effectuées au nom des utilisateurs n’entameront pas les limites de débit disponibles via l’authentification uniquement par application, et les requêtes effectuées via l’authentification uniquement par application n’entameront pas les limites de débit utilisées dans l’authentification basée sur l’utilisateur.

Pour en savoir plus, consultez [API Rate Limiting](/fr/x-api/fundamentals/rate-limits) et [consultez les limites](https://developer.x.com/en/portal/products).

<div id="issuing-application-only-requests">
  #### Émission de requêtes en mode application seule
</div>

**Étape 1 : Encoder la consumer key et le consumer secret**

Les étapes pour encoder la consumer key et le consumer secret d’une application dans un ensemble d’identifiants afin d’obtenir un Bearer Token sont :

1. Appliquer un encodage URL à la consumer key et au consumer secret conformément à la [RFC 1738](http://www.ietf.org/rfc/rfc1738.txt). Notez qu’au moment de la rédaction, cela ne modifie en réalité ni la consumer key ni le consumer secret, mais cette étape doit tout de même être effectuée au cas où le format de ces valeurs changerait à l’avenir.
2. Concaténer la consumer key encodée, un caractère deux-points &quot;:&quot;, et le consumer secret encodé en une seule chaîne de caractères.
3. [Encoder en Base64](http://en.wikipedia.org/wiki/Base64) la chaîne de caractères obtenue à l’étape précédente.

Vous trouverez ci-dessous des valeurs d’exemple montrant le résultat de cet algorithme. Notez que le consumer secret utilisé sur cette page est destiné à des fins de test et ne fonctionnera pas pour des requêtes réelles.

|                                                                |                                                                                             |
| :------------------------------------------------------------- | :------------------------------------------------------------------------------------------ |
| Consumer key                                                   | xvz1evFS4wEEPTGEFPHBog                                                                      |
| Consumer secret                                                | L8qq9PZyRg6ieKGEKhZolGC0vJWLw8iEJ88DRdyOg                                                   |
| Consumer<br /><br />key encodée selon la RFC 1738 (inchangée)  | xvz1evFS4wEEPTGEFPHBog                                                                      |
| Consumer<br /><br />secret encodé selon la RFC 1738 (inchangé) | L8qq9PZyRg6ieKGEKhZolGC0vJWLw8iEJ88DRdyOg                                                   |
| Identifiants pour le Bearer Token                              | xvz1evFS4wEEPTGEFPHBog:L8qq9PZyRg6ieKGEKhZolGC0vJWLw8iEJ88DRdyOg                            |
| Identifiants pour le Bearer Token encodés en Base64            | :: eHZ6MWV2RlM0d0VFUFRHRUZQSEJvZzpMOHFxOVBaeVJnNmllS0dFS2hab2xHQzB2SldMdzhpRUo4OERSZHlPZw== |

**Étape 2 : Obtenir un jeton d’accès App only (Bearer Token)**

La valeur calculée à l’étape 1 doit être échangée contre un jeton d’accès App only en envoyant une requête vers [POST oauth2/token](/fr/resources/fundamentals/authentication/api-reference#post-oauth2-token) :

* La requête doit être une requête HTTP POST.
* La requête doit inclure un en-tête `Authorization` avec la valeur `Basic <base64 encoded value from step 1>.`
* La requête doit inclure un en-tête `Content-Type` avec la valeur `application/x-www-form-urlencoded;charset=UTF-8.`
* Le corps de la requête doit être `grant_type=client_credentials`.

**Exemple de requête (l’en-tête Authorization a été replié sur plusieurs lignes) :**

```json
POST /oauth2/token HTTP/1.1
Host: api.x.com
User-Agent: My X App v1.0.23
Authorization: Basic eHZ6MWV2RlM0d0VFUFRHRUZQSEJvZzpMOHFxOVBaeVJn
                     NmllS0dFS2hab2xHQzB2SldMdzhpRUo4OERSZHlPZw==
Content-Type: application/x-www-form-urlencoded;charset=UTF-8
Content-Length: 29
Accept-Encoding: gzip

grant\_type=client\_credentials
```

Si la requête est correctement formatée, le serveur renvoie un corps de réponse encodé en JSON :

**Exemple de réponse :**

```json
HTTP/1.1 200 OK
Status: 200 OK
Content-Type: application/json; charset=utf-8
...
Content-Encoding: gzip
Content-Length: 140

{"token\_type":"bearer","access\_token":"AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA%2FAAAAAAAAAAAAAAAAAAAA%3DAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"}
```

Les applications doivent vérifier que la valeur associée à la clé `token_type` de l’objet renvoyé est `bearer`. La valeur associée à la clé `access_token` est le jeton d’accès App only (Bearer Token).

Notez qu’un jeton d’accès App only est valide pour une application à la fois. Si vous émettez une nouvelle requête avec les mêmes identifiants vers `/oauth2/token`, la même valeur de jeton sera renvoyée tant qu’il n’est pas invalidé.

**Étape 3 : Authentifier les requêtes d’API avec le jeton d’accès App only (Bearer Token)**

Le jeton d’accès App only (Bearer Token) peut être utilisé pour émettre des requêtes vers les endpoints d’API qui prennent en charge l’authentification App only. Pour utiliser le jeton d’accès d’application, construisez une requête HTTPS normale et incluez un en-tête `Authorization` avec la valeur `Bearer <base64 bearer token value from step 2>. Signing is not required.`

**Exemple de requête (l’en-tête Authorization a été affiché sur plusieurs lignes) :**

```
GET /1.1/statuses/user\_timeline.json?count=100&screen\_name=twitterapi HTTP/1.1
Host: api.x.com
User-Agent: My X App v1.0.23
Authorization: Bearer AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA%2FAAAAAAAAAAAA
                      AAAAAAAA%3DAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
Accept-Encoding: gzip
```

**Invalidation d’un jeton d’accès App-only (Bearer Token)**

Si un jeton d’accès App-only est compromis ou doit être invalidé pour quelque raison que ce soit, envoyez une requête à [POST oauth2/invalidate&#95;token](/fr/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token).

**Exemple de requête (l’en-tête Authorization a été renvoyé à la ligne) :**

```bash
POST /oauth2/invalidate_token HTTP/1.1
Authorization: Basic eHZ6MWV2RlM0d0VFUFRHRUZQSEJvZzpMOHFxOVBaeVJn
                     NmllS0dFS2hab2xHQzB2SldMdzhpRUo4OERSZHlPZw==
User-Agent: My X App v1.0.23
Host: api.x.com
Accept: */*
Content-Length: 119
Content-Type: application/x-www-form-urlencoded

access_token=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA%2FAAAAAAAAAAAAAAAAAAAA%3DAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
```

**Exemple de réponse :**

```json
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 127
...

{"access_token":"AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA%2FAAAAAAAAAAAAAAAAAAAA%3DAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"}
```

<div id="common-error-cases">
  #### Cas d’erreurs courants
</div>

Cette section décrit certaines erreurs fréquentes liées à la négociation et à l’utilisation des Bearer Tokens. Notez que toutes les réponses d’erreur possibles ne sont pas couvertes ici ; soyez attentif aux codes d’erreur et réponses non gérés.

**Requêtes non valides pour obtenir ou révoquer un App only Access Token**

Tentatives visant à :

* Obtenir un App only Access Token (Bearer Token) avec une requête non valide (par exemple, en omettant `grant_type=client_credentials`).
* Obtenir ou révoquer un App only Access Token (Bearer Token) avec des identifiants d’application incorrects ou expirés.
* Invalider un App only Access Token (Bearer Token) incorrect ou déjà révoqué.
* Obtenir un App only Access Token (Bearer Token) trop fréquemment sur une courte période.

Entraîneront :

```json
HTTP/1.1 403 Forbidden
Content-Length: 105
Content-Type: application/json; charset=utf-8
...

{"errors":\[{"code":99,"label":"authenticity\_token\_error","message":"Impossible de vérifier vos informations d'identification"}\]}
```

<div id="api-request-contains-invalid-app-only-access-token-bearer-token">
  #### La requête API contient un jeton d’accès applicatif (Bearer Token) invalide
</div>

L’utilisation d’un jeton d’accès incorrect ou révoqué pour effectuer des requêtes vers l’API entraînera :

```json
HTTP/1.1 401 Unauthorized
Content-Type: application/json; charset=utf-8
Content-Length: 61
...

{"errors":\[{"message":"Invalid or expired token","code":89}\]}
```

<div id="app-only-access-token-bearer-token-used-on-endpoint-which-doesnt-support-application-only-auth">
  #### Jeton d’accès applicatif seul (Bearer Token) utilisé sur un endpoint qui ne prend pas en charge l’authentification applicative seule
</div>

L’appel à un endpoint qui requiert un contexte utilisateur (comme `statuses/home_timeline`) avec un jeton d’accès applicatif seul (Bearer Token) produira :

```json
HTTP/1.1 403 Forbidden
Content-Type: application/json; charset=utf-8
Content-Length: 91
...

{"errors":\[{"message":"Your credentials do not allow access to this resource","code":220}\]}
```

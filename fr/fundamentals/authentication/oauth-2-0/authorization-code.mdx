<div id="oauth-20-authorization-code-flow-with-pkce">
  ### Flux de code d’autorisation OAuth 2.0 avec PKCE
</div>

<div id="introduction">
  #### Introduction
</div>

OAuth 2.0 est un protocole d’autorisation standard du secteur qui offre un contrôle plus fin sur les scopes d’une application et sur les flux d’autorisation sur plusieurs appareils. OAuth 2.0 vous permet de choisir des scopes précis et granulaires qui vous confèrent des autorisations spécifiques pour le compte d’un utilisateur. 

Pour activer OAuth 2.0 dans votre App, vous devez l’activer dans les paramètres d’authentification de votre App, situés dans la section des paramètres de l’App de la Console de Développement.

<div id="how-long-will-my-credentials-stay-valid">
  #### Combien de temps mes identifiants resteront-ils valides ?
</div>

Par défaut, le jeton d’accès que vous créez via le flux Authorization Code Flow with PKCE ne restera valide que deux heures, sauf si vous avez utilisé le scope `offline.access`.

<div id="refresh-tokens">
  #### Jetons d’actualisation
</div>

Les jetons d’actualisation permettent à une application d’obtenir un nouveau jeton d’accès sans solliciter l’utilisateur, via le flux d’actualisation de jeton.

Si le scope `offline.access` est appliqué, un jeton d’actualisation OAuth 2.0 est émis. Avec ce jeton d’actualisation, vous pouvez obtenir un jeton d’accès. Si ce scope n’est pas transmis, nous ne générons pas de jeton d’actualisation.

Voici un exemple de requête que vous pouvez effectuer pour utiliser un jeton d’actualisation afin d’obtenir un nouveau jeton d’accès :

```bash
POST 'https://api.x.com/2/oauth2/token' \
--header 'Content-Type: application/x-www-form-urlencoded' \
--data-urlencode 'refresh_token=bWRWa3gzdnk3WHRGU1o0bmRRcTJ5VUxWX1lZTDdJSUtmaWcxbTVxdEFXcW5tOjE2MjIxNDc3NDM5MTQ6MToxOnJ0OjE' \
--data-urlencode 'grant_type=refresh_token' \
--data-urlencode 'client_id=rG9n6402A3dbUJKzXTNX4oWHJ
```

<div id="app-settings">
  #### Paramètres de l’App
</div>

Vous pouvez configurer les paramètres d’authentification de votre App sur OAuth 1.0a ou OAuth 2.0. Vous pouvez également autoriser une App à utiliser à la fois OAuth 1.0a et OAuth 2.0.

OAuth 2.0 peut uniquement être utilisé avec X API v2. Si vous avez sélectionné OAuth 2.0, vous verrez un Client ID dans la section Keys and Tokens de votre App. 

<div id="confidential-clients">
  #### Clients confidentiels
</div>

[Les clients confidentiels](https://datatracker.ietf.org/doc/html/rfc6749#section-2.1) peuvent conserver des identifiants de manière sécurisée sans les exposer à des parties non autorisées et s’authentifier de façon sécurisée auprès du serveur d’autorisation. Ils permettent ainsi de garder votre secret client en sécurité. Les clients publics, eux, s’exécutent généralement dans un navigateur ou sur un appareil mobile et ne peuvent pas utiliser vos secrets client. Si vous sélectionnez un type d’App qui est un client confidentiel, un secret client vous sera fourni. 

Si, dans la Console de Développement, vous avez sélectionné un type de client qui est un client confidentiel, vous pourrez également voir un secret client. Vos options sont Native App, Single page App, Web App, Automated App ou bot. Les Native App et Single page Apps sont des clients publics, et les Web App et Automated App ou bots sont des clients confidentiels.

Vous n’avez pas besoin d’`id` de client pour les clients confidentiels avec un en-tête d’autorisation (`Authorization Header`) valide. Vous devez en revanche toujours inclure l’`id` de client dans le corps de la requête pour les demandes effectuées avec un client public.

<div id="rate-limits">
  #### Limites de débit
</div>

Dans l&#39;ensemble, les limites de débit sont les mêmes que lors de l’authentification avec OAuth 1.0a, à l’exception de Tweet lookup et Users lookup. Nous faisons passer la limite par application de 300 à 900 requêtes par tranche de 15 minutes lors de l’utilisation d’OAuth 2.0 pour Tweet lookup et user lookup. Pour en savoir plus, consultez notre [documentation sur les limites de débit](/fr/resources/fundamentals/rate-limits).

<div id="grant-types">
  #### Types de grant
</div>

Nous proposons uniquement le [code d’autorisation](https://oauth.net/2/grant-types/authorization-code/) avec [PKCE](https://oauth.net/2/pkce/) et le [refresh token](https://oauth.net/2/grant-types/refresh-token/) comme [grant types](https://oauth.net/2/grant-types/) pris en charge pour ce lancement initial. Nous pourrions proposer d’autres grant types à l’avenir.

<div id="oauth-20-flow">
  #### Flux OAuth 2.0
</div>

OAuth 2.0 utilise un flux similaire à celui que nous employons actuellement pour OAuth 1.0a. Vous trouverez un schéma et une explication détaillée dans notre [documentation sur ce sujet](/fr/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens). 

<div id="glossary">
  #### Glossary
</div>

|     |     |
| :--- | :--- |
| **Term** | **Description** |
| Grant types | Le framework OAuth spécifie plusieurs types de grant pour différents cas d’usage, ainsi qu’un mécanisme pour créer de nouveaux types de grant. Par exemple : authorization code, client credentials, device code et refresh token. |
| Confidential client | Les clients confidentiels sont des applications qui peuvent s’authentifier de manière sécurisée auprès du serveur d’autorisation, par exemple en conservant leur secret client enregistré en sécurité. |
| Public client | Les clients publics ne peuvent pas utiliser de secrets client enregistrés, comme les applications s’exécutant dans un navigateur ou sur un appareil mobile. |
| Authorization code flow | Utilisé à la fois par les clients confidentiels et publics pour échanger un code d’autorisation contre un jeton d’accès. |
| PKCE | Une extension du flux de code d’autorisation pour empêcher plusieurs types d’attaques et permettre d’effectuer l’échange OAuth de manière sécurisée depuis des clients publics. |
| Client ID | Se trouve dans la section clés et jetons de la Console de Développement sous l’en-tête « Client ID ». Si vous ne le voyez pas, veuillez contacter directement notre équipe. Le Client ID sera nécessaire pour générer l’URL d’autorisation. |
| Redirect URI | Votre URL de redirection (callback). Vous devrez respecter la [validation de correspondance exacte](https://datatracker.ietf.org/doc/html/rfc6749#section-10.6). |
| Authorization code | Cela permet à une application d’appeler des API pour le compte des utilisateurs. Appelé auth&#95;code. L’auth&#95;code a une durée de validité de 30 secondes à compter du moment où le propriétaire de l’App reçoit de l’utilisateur un auth&#95;code approuvé. Vous devrez l’échanger contre un jeton d’accès dans les 30 secondes, sinon l’auth&#95;code expirera. |
| Access token | Les jetons d’accès sont les jetons que les applications utilisent pour effectuer des requêtes API au nom d’un utilisateur. |
| Refresh token | Permet à une application d’obtenir un nouveau jeton d’accès sans solliciter l’utilisateur, via le flux de refresh token. |
| Client Secret | Si vous avez sélectionné un type d’App qui est un client confidentiel, un « Client Secret » vous sera fourni sous « Client ID » dans la section clés et jetons de votre App. |

<div id="parameters">
  #### Paramètres
</div>

Pour construire une URL d’autorisation OAuth 2.0, vous devez vous assurer que les paramètres suivants sont présents dans l’URL d’autorisation. 

|     |     |
| :--- | :--- |
| **Paramètre** | **Description** |
| response&#95;type | Vous devez spécifier qu’il s’agit d’un code avec le mot « code ». |
| client&#95;id | Peut être trouvé dans la Console de Développement sous l’en-tête « Client ID ». |
| redirect&#95;uri | Votre URL de rappel (callback). Cette valeur doit correspondre à l’une des URL de rappel définies dans les paramètres de votre App. Pour OAuth 2.0, vous devez utiliser la [validation de correspondance exacte](https://datatracker.ietf.org/doc/html/rfc6749#section-10.6) pour votre URL de rappel. |
| state | Une chaîne de caractères aléatoire que vous fournissez pour vous protéger contre les [attaques CSRF](https://auth0.com/docs/protocols/state-parameters).  La longueur de cette chaîne peut aller jusqu’à 500 caractères. |
| code&#95;challenge | Un paramètre [PKCE](https://www.oauth.com/oauth2-servers/pkce/authorization-request/), un secret aléatoire pour chaque requête que vous envoyez. |
| code&#95;challenge&#95;method | Précise la méthode que vous utilisez pour effectuer une requête (S256 OU plain). |

<div id="authorize-url">
  #### URL d’autorisation
</div>

Avec OAuth 2.0, vous créez une URL d’autorisation que vous pouvez utiliser pour permettre à un utilisateur de s’authentifier via un flux d’authentification, similaire à « Se connecter avec X ». 

Voici un exemple de l’URL que vous allez créer :

```
https://x.com/i/oauth2/authorize?response_type=code&client_id=M1M5R3BMVy13QmpScXkzTUt5OE46MTpjaQ&redirect_uri=https://www.example.com&scope=tweet.read%20users.read%20account.follows.read%20account.follows.write&state=state&code_challenge=challenge&code_challenge_method=plain
```

Vous devrez utiliser le bon encodage pour que cette URL fonctionne. Consultez notre documentation sur le [percent-encoding](/fr/resources/fundamentals/authentication/oauth-1-0a/percent-encoding-parameters).

<div id="oauth-20-authorization-code-flow-with-pkce">
  ### Flux OAuth 2.0 avec code d’autorisation et PKCE
</div>

<div id="introduction">
  #### Introduction
</div>

OAuth 2.0 est un protocole d’autorisation standard de l’industrie qui permet un contrôle plus précis sur le périmètre d’une application et sur les flux d’autorisation sur plusieurs appareils. OAuth 2.0 vous permet de choisir des scopes fins qui vous accordent des autorisations précises pour le compte d’un utilisateur. 

Pour activer OAuth 2.0 dans votre App, vous devez l’activer dans les paramètres d’authentification de votre App, situés dans la section Paramètres de l’App de la Developer Console.

<div id="how-long-will-my-credentials-stay-valid">
  #### Pendant combien de temps mes identifiants resteront-ils valides ?
</div>

Par défaut, le jeton d’accès que vous créez au moyen de l’Authorization Code Flow with PKCE ne reste valide que pendant deux heures, sauf si vous avez utilisé le scope `offline.access`.

<div id="refresh-tokens">
  #### Refresh tokens
</div>

Les refresh tokens permettent à une application d’obtenir un nouveau jeton d’accès sans redemander l’autorisation à l’utilisateur, via le flux de refresh token.

Si le scope `offline.access` est appliqué, un refresh token OAuth 2.0 sera émis. À l’aide de ce refresh token, vous pouvez obtenir un jeton d’accès. Si ce scope n’est pas transmis, nous ne générerons pas de refresh token.

Voici un exemple de requête permettant d’utiliser un refresh token pour obtenir un nouveau jeton d’accès :

```bash
POST 'https://api.x.com/2/oauth2/token' \
--header 'Content-Type: application/x-www-form-urlencoded' \
--data-urlencode 'refresh_token=bWRWa3gzdnk3WHRGU1o0bmRRcTJ5VUxWX1lZTDdJSUtmaWcxbTVxdEFXcW5tOjE2MjIxNDc3NDM5MTQ6MToxOnJ0OjE' \
--data-urlencode 'grant_type=refresh_token' \
--data-urlencode 'client_id=rG9n6402A3dbUJKzXTNX4oWHJ
```

<div id="app-settings">
  #### Paramètres de l’App
</div>

Vous pouvez configurer les paramètres d’authentification de votre App sur OAuth 1.0a ou OAuth 2.0. Vous pouvez également autoriser une App à utiliser à la fois OAuth 1.0a et OAuth 2.0.

OAuth 2.0 peut uniquement être utilisé avec X API v2. Si vous avez sélectionné OAuth 2.0, vous pourrez voir un Client ID dans la section Keys and Tokens de votre App. 

<div id="confidential-clients">
  #### Clients confidentiels
</div>

[Clients confidentiels](https://datatracker.ietf.org/doc/html/rfc6749#section-2.1) peuvent conserver des informations d’identification de manière sécurisée sans les exposer à des tiers non autorisés et s’authentifier en toute sécurité auprès du serveur d’autorisation, ce qui permet de garder votre secret client à l’abri. Les clients publics, qui s’exécutent généralement dans un navigateur ou sur un appareil mobile, ne peuvent pas utiliser vos secrets client. Si vous sélectionnez un type d’App qui est un client confidentiel, un secret client vous sera fourni. 

Si vous avez sélectionné un type de client qui est un client confidentiel dans le Developer Console, vous pourrez également voir un secret client. Vos options sont les suivantes : Native App, Single Page App, Web App, Automated App ou bot. Native App et Single Page Apps sont des clients publics, et Web App, Automated App et les bots sont des clients confidentiels.

Vous n’avez pas besoin d’ID client pour les clients confidentiels avec un en-tête Authorization valide. Vous devez néanmoins inclure l’ID client dans le corps des requêtes effectuées avec un client public. 

<div id="scopes">
  #### Scopes
</div>

Les scopes vous permettent de définir un contrôle d’accès granulaire pour votre application afin qu’elle ne dispose que des autorisations dont elle a besoin. Pour en savoir plus sur les correspondances entre les scopes et les endpoints, consultez notre [guide de correspondance d’authentification](/fr/resources/fundamentals/authentication/guides/v2-authentication-mapping).

<div id="rate-limits">
  #### Limites de débit
</div>

Dans l’ensemble, les limites de débit sont les mêmes que lorsque vous vous authentifiez avec OAuth 1.0a, à l’exception de la recherche de Tweets et de la recherche d’utilisateurs. Nous faisons passer la limite par application de 300 à 900 requêtes toutes les 15 minutes lorsque vous utilisez OAuth 2.0 pour la recherche de Tweets et d’utilisateurs. Pour en savoir plus, consultez notre [documentation sur les limites de débit](/fr/resources/fundamentals/rate-limits).

<div id="grant-types">
  #### Types de grant
</div>

Nous ne proposons, pour ce lancement initial, que le [code d’autorisation](https://oauth.net/2/grant-types/authorization-code/) avec [PKCE](https://oauth.net/2/pkce/) et le [jeton d’actualisation](https://oauth.net/2/grant-types/refresh-token/) comme [types de grant](https://oauth.net/2/grant-types/) pris en charge. D’autres types de grant pourront être proposés à l’avenir.

<div id="oauth-20-flow">
  #### Flux OAuth 2.0
</div>

OAuth 2.0 suit un flux similaire à celui que nous utilisons actuellement pour OAuth 1.0a. Vous pouvez consulter un schéma et une explication détaillée dans notre [documentation à ce sujet](/fr/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens). 

<div id="glossary">
  #### Glossary
</div>

|     |     |
| :--- | :--- |
| **Term** | **Description** |
| Grant types | Le framework OAuth spécifie plusieurs types de grant pour différents cas d’utilisation ainsi qu’un cadre pour créer de nouveaux types de grant. Exemples : authorization code, client credentials, device code et refresh token. |
| Confidential client | Les clients confidentiels sont des applications qui peuvent s’authentifier de manière sécurisée auprès du serveur d’autorisation, par exemple en conservant leur client secret enregistré en sécurité. |
| Public client | Les clients publics sont des applications qui ne peuvent pas utiliser de client secrets enregistrés, comme les applications s’exécutant dans un navigateur ou sur un appareil mobile. |
| Authorization code flow | Utilisé par les clients confidentiels et publics pour échanger un authorization code contre un access token. |
| PKCE | Une extension de l’authorization code flow visant à empêcher plusieurs types d’attaques et à permettre d’effectuer l’échange OAuth de manière sécurisée depuis des clients publics. |
| Client ID | Peut être trouvé dans la section Keys and tokens de la Developer Console sous l’en-tête « Client ID ». Si vous ne voyez pas cet élément, veuillez contacter directement notre équipe. Le Client ID sera nécessaire pour générer l’URL d’autorisation (authorize URL). |
| Redirect URI | Votre URL de callback. Vous devrez disposer de la [validation de correspondance exacte](https://datatracker.ietf.org/doc/html/rfc6749#section-10.6). |
| Authorization code | Cela permet à une application d’appeler des API pour le compte des utilisateurs. Appelé auth&#95;code. L’auth&#95;code a une limite de temps de 30 secondes une fois que le propriétaire de l’application reçoit un auth&#95;code approuvé de la part de l’utilisateur. Vous devrez l’échanger contre un access token dans un délai de 30 secondes, faute de quoi l’auth&#95;code expirera. |
| Access token | Les access tokens sont les jetons qu’une application utilise pour effectuer des requêtes API au nom d’un utilisateur. |
| Refresh token | Permet à une application d’obtenir un nouvel access token sans solliciter l’utilisateur via le refresh token flow. |
| Client Secret | Si vous avez sélectionné un type d’application qui est un confidential client, un « Client Secret » vous sera fourni sous « Client ID » dans la section Keys and tokens de votre application. |

<div id="parameters">
  #### Paramètres
</div>

Pour construire une URL d’autorisation OAuth 2.0, vous devez vous assurer d’inclure les paramètres suivants dans l’URL d’autorisation. 

|     |     |
| :--- | :--- |
| **Paramètre** | **Description** |
| response&#95;type | Vous devez indiquer qu’il s’agit d’un code en utilisant le mot « code ». |
| client&#95;id | Se trouve dans la Developer Console sous l’en-tête « Client ID ». |
| redirect&#95;uri | Votre URL de rappel (callback URL). Cette valeur doit correspondre à l’une des Callback URLs définies dans les paramètres de votre App. Pour OAuth 2.0, vous devez utiliser une [validation par correspondance exacte](https://datatracker.ietf.org/doc/html/rfc6749#section-10.6) pour votre URL de rappel. |
| state | Une chaîne aléatoire que vous fournissez pour vous prémunir contre les [attaques CSRF](https://auth0.com/docs/protocols/state-parameters). La longueur de cette chaîne peut aller jusqu’à 500 caractères. |
| code&#95;challenge | Un paramètre [PKCE](https://www.oauth.com/oauth2-servers/pkce/authorization-request/), un secret aléatoire pour chaque requête que vous effectuez. |
| code&#95;challenge&#95;method | Spécifie la méthode que vous utilisez pour envoyer une requête (S256 OU plain). |

<div id="authorize-url">
  #### URL d’autorisation
</div>

Avec OAuth 2.0, vous créez une URL d’autorisation que vous pouvez utiliser pour permettre à un utilisateur de s’authentifier via un flux d’authentification, similaire à « Se connecter » avec X. 

Un exemple de l’URL que vous créez est le suivant :

```
https://x.com/i/oauth2/authorize?response_type=code&client_id=M1M5R3BMVy13QmpScXkzTUt5OE46MTpjaQ&redirect_uri=https://www.example.com&scope=tweet.read%20users.read%20account.follows.read%20account.follows.write&state=state&code_challenge=challenge&code_challenge_method=plain
```

Vous devez utiliser le bon encodage pour que cette URL fonctionne. Veillez à consulter notre documentation sur l’[encodage en pourcentage](/fr/resources/fundamentals/authentication/oauth-1-0a/percent-encoding-parameters).

Les applications sont des conteneurs pour vos identifiants API. Chaque application dispose de ses propres clés, jetons et paramètres.

---

<div id="app-credentials">
  ## Identifiants d’app
</div>

Lorsque vous créez une app, vous pouvez générer ces identifiants :

| Identifiant | Cas d’usage |
|:-----------|:------------|
| **API Key & Secret** | Authentification avec OAuth 1.0a. Utilisés pour signer les requêtes ou générer des jetons utilisateur. |
| **Access Token & Secret** | Effectuer des requêtes en votre nom (OAuth 1.0a). |
| **Client ID & Secret** | Authentification avec OAuth 2.0. Utilisés pour le flux de code d’autorisation. |
| **Bearer Token** | Authentification App-only pour les endpoints de données publiques. |

<Tip>
Choisissez **OAuth 2.0** pour les nouveaux projets. Il offre des scopes plus précis et est obligatoire pour les endpoints X API v2 avec contexte utilisateur.
</Tip>

<div id="creating-an-app">
  ## Création d'une application
</div>

<Steps>
  <Step title="Ouvrir le Developer Console">
    Rendez-vous sur [console.x.com](https://console.x.com) et connectez-vous.
  </Step>
  <Step title="Cliquer sur Create App">
    Saisissez un nom, une description et un cas d'utilisation pour votre application.
  </Step>
  <Step title="Générer les identifiants">
    Après la création, générez les clés et les jetons dont vous avez besoin.
  </Step>
  <Step title="Stocker en lieu sûr">
    Enregistrez immédiatement les identifiants — ils ne s'affichent qu'une seule fois.
  </Step>
</Steps>

<div id="app-permissions-oauth-10a">
  ## Autorisations d'application (OAuth 1.0a)
</div>

Les applications OAuth 1.0a disposent de trois niveaux d'autorisation :

<Tabs>
  <Tab title="Lecture seule">
    - Afficher les publications, les utilisateurs et les données publiques
    - Impossible de publier, d'aimer ou de modifier quoi que ce soit
    - Impossible d'accéder aux Messages privés
  </Tab>
  <Tab title="Lecture et écriture">
    - Toutes les autorisations de lecture
    - Publier et supprimer des publications
    - Suivre/ne plus suivre des utilisateurs
    - Aimer et republier
    - Impossible d'accéder aux Messages privés
  </Tab>
  <Tab title="Lecture, écriture et Messages privés">
    - Toutes les autorisations de lecture et d'écriture
    - Envoyer et lire des Messages privés
  </Tab>
</Tabs>

<Note>
Modifier les autorisations nécessite que les utilisateurs réautorisent votre application afin d'obtenir de nouveaux jetons avec la portée mise à jour.
</Note>

<div id="oauth-20-app-types">
  ## Types d'applications OAuth 2.0
</div>

Lors de la configuration d'OAuth 2.0, sélectionnez le type de votre application :

| Type | Client | Cas d'utilisation |
|:-----|:-------|:------------------|
| **Application web** | Confidentiel | Applications côté serveur pouvant stocker des secrets de manière sécurisée |
| **Application automatisée / Bot** | Confidentiel | Bots et services automatisés exécutés sur des serveurs |
| **Application native** | Public | Applications mobiles ou de bureau qui ne peuvent pas protéger les secrets |
| **Application monopage** | Public | Applications JavaScript exécutées dans le navigateur |

Les **clients confidentiels** reçoivent un secret client. Les **clients publics** utilisent uniquement PKCE.

<div id="callback-urls">
  ## URL de rappel
</div>

Les URL de rappel (URI de redirection) sont Obligatoire pour les flux OAuth. Après qu’un utilisateur a autorisé votre application, il est redirigé vers l’URL de rappel de votre application avec un code d’autorisation.

<div id="requirements">
  ### Exigences
</div>

- Ajoutez les URL de rappel à la liste d’autorisation de votre application dans la Developer Console
- Les URL doivent correspondre exactement (y compris la barre oblique finale)
- Maximum **10 URL de rappel** par application
- Utilisez `https://` en production
- Pour le développement local, utilisez `http://127.0.0.1` (et non `localhost`)

<div id="disallowed-protocols">
  ### Protocoles non autorisés
</div>

Ces protocoles ne peuvent pas être utilisés : `javascript`, `data`, `file`, `ftp`, `mailto`, `telnet` et d'autres schémas non standard.

<Accordion title="Liste complète des protocoles non autorisés">
`vbscript`, `javascript`, `vbs`, `data`, `mocha`, `keyword`, `livescript`, `ftp`, `file`, `gopher`, `acrobat`, `callto`, `daap`, `itpc`, `itms`, `firefoxurl`, `hcp`, `ldap`, `mailto`, `mmst`, `mmsu`, `msbd`, `rtsp`, `mso-offdap`, `snews`, `news`, `nntp`, `outlook`, `stssync`, `rlogin`, `telnet`, `tn3270`, `shell`, `sip`
</Accordion>

<div id="automated-account-labels">
  ## Libellés de comptes automatisés
</div>

Si votre application utilise un compte bot, vous pouvez l’indiquer comme automatisé :

1. Accédez aux **Paramètres** du compte de votre bot
2. Sélectionnez **Votre compte** → **Automatisation**
3. Associez le compte qui le gère

Cela renforce la confiance des utilisateurs et distingue votre bot du spam.

<div id="troubleshooting">
  ## Dépannage
</div>

<Accordion title="Erreur : URL de rappel non approuvée">
Assurez-vous que votre URL de rappel est exactement la même que celle enregistrée dans la Developer Console, y compris le protocole et toute barre oblique finale. Encodez l’URL (encodage URL/HTTP) lorsque vous la transmettez en tant que paramètre de requête.

```json
{
  "errors": [{
    "code": 415,
    "message": "Callback URL not approved for this client application."
  }]
}
```
</Accordion>

<Accordion title="Application suspendue">
Si votre application apparaît comme suspendue, vérifiez vos e-mails pour un message de l’équipe de la plateforme X. Utilisez le [formulaire d’aide de la plateforme](https://help.x.com/forms/platform) pour faire appel.
</Accordion>

Les apps sont des conteneurs pour vos identifiants d'API. Chaque app dispose de ses propres clés, jetons et paramètres.

---

<div id="app-credentials">
  ## Identifiants de l’application
</div>

Lorsque vous créez une application, vous pouvez générer les identifiants suivants :

| Identifiant | Cas d’utilisation |
|:-----------|:------------------|
| **API Key & Secret** | S’authentifier avec OAuth 1.0a. Utilisés pour signer les requêtes ou générer des jetons utilisateur. |
| **Access Token & Secret** | Effectuer des requêtes au nom de votre propre compte (OAuth 1.0a). |
| **Client ID & Secret** | S’authentifier avec OAuth 2.0. Utilisés pour le flux de code d’autorisation. |
| **Bearer Token** | Authentification applicative uniquement pour les endpoints de données publiques. |

<Tip>
Choisissez **OAuth 2.0** pour les nouveaux projets. Il offre des scopes très précis et est obligatoire pour les endpoints X API v2 en contexte utilisateur.
</Tip>

<div id="creating-an-app">
  ## Création d'une application
</div>

<Steps>
  <Step title="Ouvrir la Console de Développement">
    Accédez à [console.x.com](https://console.x.com) et connectez-vous.
  </Step>
  <Step title="Cliquer sur « Create App »">
    Saisissez un nom, une description et un cas d'utilisation pour votre application.
  </Step>
  <Step title="Générer les identifiants">
    Après la création, générez les clés et les jetons dont vous avez besoin.
  </Step>
  <Step title="Stocker en lieu sûr">
    Enregistrez immédiatement les identifiants — ils ne s'affichent qu'une seule fois.
  </Step>
</Steps>

<div id="app-permissions-oauth-10a">
  ## Autorisations d'application (OAuth 1.0a)
</div>

Les applications OAuth 1.0a ont trois niveaux d'autorisation :

<Tabs>
  <Tab title="Lecture seule">
    - Afficher les publications, les utilisateurs et les données publiques
    - Impossible de publier, d'aimer ou de modifier quoi que ce soit
    - Impossible d'accéder aux messages privés
  </Tab>
  <Tab title="Lecture et écriture">
    - Toutes les autorisations de lecture
    - Publier et supprimer des publications
    - Suivre/ne plus suivre des utilisateurs
    - Aimer et reposter
    - Impossible d'accéder aux messages privés
  </Tab>
  <Tab title="Lecture, écriture et MP">
    - Toutes les autorisations de lecture et d'écriture
    - Envoyer et lire des messages privés
  </Tab>
</Tabs>

<Note>
La modification des autorisations nécessite que les utilisateurs réautorisent votre application pour obtenir de nouveaux jetons avec la portée mise à jour.
</Note>

<div id="oauth-20-app-types">
  ## Types d’applications OAuth 2.0
</div>

Lors de la configuration d’OAuth 2.0, sélectionnez le type de votre application :

| Type | Client | Cas d’utilisation |
|:-----|:-------|:------------------|
| **Web App** | Confidential | Applications côté serveur pouvant stocker des secrets en toute sécurité |
| **Automated App / Bot** | Confidential | Bots et services automatisés exécutés sur des serveurs |
| **Native App** | Public | Applications mobiles ou de bureau qui ne peuvent pas stocker de secrets en toute sécurité |
| **Single Page App** | Public | Applications JavaScript exécutées dans le navigateur |

Les **clients confidentiels** reçoivent un Client Secret. Les **clients publics** n’utilisent que PKCE.

<div id="callback-urls">
  ## URL de rappel
</div>

Les URL de rappel (URI de redirection) sont obligatoires pour les flux OAuth. Après qu’un utilisateur a autorisé votre application, il est redirigé vers votre URL de rappel avec un code d’autorisation.

<div id="requirements">
  ### Prérequis
</div>

- Ajoutez des URL de callback à la liste d’autorisation de votre application dans la Console de Développement
- Les URL doivent correspondre exactement (y compris les barres obliques finales)
- Maximum de **10 URL de callback** par application
- Utilisez `https://` en production
- Pour le développement local, utilisez `http://127.0.0.1` (et non `localhost`)

<div id="disallowed-protocols">
  ### Protocoles non autorisés
</div>

Les protocoles suivants ne peuvent pas être utilisés : `javascript`, `data`, `file`, `ftp`, `mailto`, `telnet` et d'autres schémas d’URI non standard.

<Accordion title="Liste complète des protocoles non autorisés">
`vbscript`, `javascript`, `vbs`, `data`, `mocha`, `keyword`, `livescript`, `ftp`, `file`, `gopher`, `acrobat`, `callto`, `daap`, `itpc`, `itms`, `firefoxurl`, `hcp`, `ldap`, `mailto`, `mmst`, `mmsu`, `msbd`, `rtsp`, `mso-offdap`, `snews`, `news`, `nntp`, `outlook`, `stssync`, `rlogin`, `telnet`, `tn3270`, `shell`, `sip`
</Accordion>

<div id="automated-account-labels">
  ## Libellés de comptes automatisés
</div>

Si votre application gère un compte bot, vous pouvez l’indiquer comme automatisé :

1. Accédez aux **Settings** de votre compte bot
2. Sélectionnez **Your account** → **Automation**
3. Associez votre compte gestionnaire

Cela renforce la confiance des utilisateurs et permet de distinguer votre bot du spam.

<div id="troubleshooting">
  ## Dépannage
</div>

<Accordion title="Erreur d’approbation de l’URL de rappel">
Assurez-vous que votre URL de rappel correspond exactement à celle enregistrée dans la Console de Développement, y compris le protocole et tout slash de fin. Encodez l’URL (encodage URL) lorsque vous la transmettez en tant que paramètre de requête.

```json
{
  "errors": [{
    "code": 415,
    "message": "Callback URL not approved for this client application."
  }]
}
```
</Accordion>

<Accordion title="Application suspendue">
Si votre application est indiquée comme suspendue, vérifiez vos e-mails pour une notification de l’équipe de la plateforme X. Utilisez le [formulaire d’assistance de la plateforme](https://help.x.com/forms/platform) pour contester cette décision.
</Accordion>

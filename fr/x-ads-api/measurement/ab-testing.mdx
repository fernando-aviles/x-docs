<div id="introduction">
  ### Introduction
</div>

Les tests A/B permettent aux annonceurs de segmenter les utilisateurs qu&#39;ils touchent sur X afin de déterminer la meilleure façon d&#39;optimiser les performances de leurs campagnes et de recueillir des enseignements pour éclairer leurs stratégies marketing.

Ces segments — appelés groupes d&#39;utilisateurs — sont aléatoires et mutuellement exclusifs. Grâce à la randomisation, les facteurs qui influencent les résultats sont répartis de manière égale. En d&#39;autres termes, il n&#39;y a pas de différences intrinsèques entre les groupes ni entre leurs comportements attendus. De ce fait, lorsqu&#39;une seule variante est appliquée à un groupe d&#39;utilisateurs et pas aux autres, la différence de performance de la campagne peut être attribuée à cette variante.

Bien qu&#39;il soit possible de tester de nombreuses variantes en parallèle, nous recommandons vivement de tester une seule variante à la fois. Cela permet d&#39;isoler le facteur causal de la différence observée dans les performances de la campagne.

Les variantes sont définies au niveau de la campagne. Par exemple, si l&#39;annonceur souhaite tester l&#39;efficacité d&#39;une nouvelle création publicitaire, il doit créer deux campagnes identiques dont la seule différence est cette création. À l&#39;avenir, nous prévoyons de prendre en charge les variantes au niveau de l&#39;élément de campagne (line item).

<div id="use-cases">
  ### Cas d’utilisation
</div>

Les tests A/B sont le plus souvent utilisés pour (1) des cas d’utilisation d’optimisation pour les clients orientés performance qui souhaitent comprendre ce qui fonctionne le mieux sur X afin d’optimiser leur investissement et (2) des cas d’utilisation d’apprentissage pour les annonceurs de marque qui veulent tirer parti de ces enseignements pour éclairer leur stratégie marketing. 

L’API prendra en charge les tests A/B pour n’importe quelle variable de campagne, y compris :

* Création publicitaire 

* Ciblage 

* Type d’enchère

* Unité d’enchère

<div id="ab-testing">
  ## Tests A/B
</div>

Les tests A/B permettent aux annonceurs de segmenter les utilisateurs qu’ils touchent sur X afin de comprendre comment optimiser au mieux les performances de leurs campagnes et d’en tirer des enseignements pour orienter leurs stratégies marketing.

Ces segments — appelés répartitions de groupes d’utilisateurs — sont constitués de manière aléatoire et sont mutuellement exclusifs. Grâce à cette répartition aléatoire, les facteurs qui influencent les résultats sont distribués de façon égale. En d’autres termes, il n’existe aucune différence intrinsèque entre les groupes ou leurs comportements attendus. De ce fait, lorsqu’une seule variation est appliquée à un groupe d’utilisateurs et non aux autres, la différence de performance de la campagne peut être attribuée à cette variation.

Bien qu’il soit possible de tester plusieurs variations simultanément, nous recommandons fortement de tester une seule variation à la fois. Cela permet d’isoler le facteur causal à l’origine de la différence observée dans les performances de la campagne.

Les variations sont définies soit au niveau de la campagne, soit au niveau du groupe d’annonces. Le groupe d’annonces est défini via le [line item](https://developer.x.com/en/docs/twitter-ads-api/campaign-management/api-reference/line-items) dans l’Ads API. Par exemple, pour une variation au niveau du groupe d’annonces, si l’annonceur souhaite tester l’efficacité d’une nouvelle création publicitaire, il doit créer une campagne avec deux groupes d’annonces identiques dont la seule différence est cette création.

<div id="use-cases">
  ### Cas d’utilisation
</div>

Les tests A/B sont le plus souvent utilisés pour (1) des cas d’usage d’optimisation, pour les clients axés sur la performance qui souhaitent comprendre ce qui fonctionne le mieux sur X afin d’optimiser leur investissement, et (2) des cas d’usage d’apprentissage, pour les annonceurs orientés image de marque qui souhaitent utiliser ces enseignements pour définir leur stratégie marketing. 

L’API permettra de réaliser des tests A/B sur n’importe quelle variable de campagne, notamment :

* Création publicitaire

* Ciblage

* Type d’enchère

* Unité d’enchère

<div id="attributes">
  ### Attributs
</div>

Les tests A/B sont représentés sous forme de structures imbriquées. Il existe des champs de niveau supérieur pour le test A/B lui‑même et un tableau d’objets de groupes d’utilisateurs, chacun avec un ensemble de champs qui le décrivent.

De manière générale, chaque test A/B doit inclure les informations suivantes.

* La durée du test, représentée par les champs start&#95;time et end&#95;time

* Le niveau auquel la répartition aura lieu, représenté par le champ entity&#95;type

* Au moins deux (et au maximum 30) groupes d’utilisateurs, chacun étant représenté sous forme d’objet dans le tableau user&#95;groups

Chaque groupe d’utilisateurs *doit* inclure les informations suivantes.

* Le pourcentage d’utilisateurs qui doivent être affectés au groupe d’utilisateurs donné, représenté par le champ size

* Les ID de campagne/ID de line item qui doivent constituer le pool d’utilisateurs pour le groupe d’utilisateurs donné, représentés par le tableau entity&#95;ids

Il est également possible de définir des valeurs de nom et de description pour les tests A/B et pour les groupes d’utilisateurs. Des informations sur les règles de validation et autres contraintes sont disponibles ci‑dessous.

D’autres métadonnées, telles que l’ID ou la date de création, sont également incluses, mais sont automatiquement définies par X.

<div id="usage">
  ### Utilisation
</div>

Les sous-sections suivantes expliquent comment créer et mettre à jour des tests A/B. Les opérations de lecture et de suppression fonctionnent comme pour tous les autres endpoints de l’API Ads.

<div id="creating">
  #### Création
</div>

Créez un test A/B à l&#39;aide de l&#39;endpoint [POST accounts/:account&#95;id/ab&#95;tests](https://developer.x.com/en/docs/x-ads-api/measurement/api-reference/ab-tests). Cet endpoint n&#39;accepte que des corps de requête POST au format JSON. L’en-tête `Content-Type` doit être défini sur `application/json`.

Après que l’annonceur a configuré au moins deux campagnes, un test A/B peut être créé. Comme indiqué ci-dessus, les tests A/B *doivent* inclure : la durée du test, le niveau de répartition et au moins deux groupes d’utilisateurs. Chaque groupe d’utilisateurs doit déclarer le pourcentage d’utilisateurs qui doit lui être alloué, ainsi que les id de campagne qui constitueront son pool d’utilisateurs. Chacun de ces éléments est décrit plus en détail ci-dessous.

Durée du test :

* Les valeurs `start_time` et `end_time` doivent

  * être dans le futur (par rapport au moment où le test A/B est créé) ;

  * chevaucher les dates de diffusion des campagnes/line items.

* Le test doit durer au moins un jour pour les campagnes qui ne sont pas basées sur une application et au moins cinq jours pour les campagnes basées sur une application.

Niveau de répartition :

* Le `entity_type` peut être défini sur `CAMPAIGN` ou `LINE_ITEM`.

Groupes d’utilisateurs :

* Chaque groupe d’utilisateurs est représenté par un objet dans le tableau `user_groups`

  * Un minimum de deux groupes d’utilisateurs est requis

  * Un maximum de 30 groupes d’utilisateurs est autorisé

* La taille de chaque groupe d’utilisateurs est définie à l’aide d’une représentation sous forme de chaîne de caractères d’une valeur numérique comprise entre 1,00 et 99,00

  * **Remarque** : Les valeurs de taille, *tous objets confondus*, **doivent** totaliser 100,00

* Les id de campagne doivent être spécifiés dans le tableau `entity_ids` de chaque groupe d’utilisateurs.

Vous pouvez éventuellement définir le nom et la description du test A/B ou d’un ou plusieurs groupes d’utilisateurs.

**Pour les tests A/B au niveau de l’élément de campagne**

La principale différence entre les tests A/B au niveau de la campagne et au niveau de l’élément de campagne est la valeur de entity&#95;type. Pour les tests A/B au niveau de l’élément de campagne, nous devons définir ‘entity&#95;type’ = ‘LINE&#95;ITEM’. Cela s’applique à toutes les actions ci‑dessous sur un test A/B déjà créé. 

Exigences :

1. Tous les éléments de campagne de la campagne de test A/B doivent être inclus dans le split test.
2. Seule une répartition égale est autorisée au niveau de l’élément de campagne.
3. Le nombre d’éléments de campagne (groupes d’utilisateurs) autorisés dans un split test doit être inférieur ou égal à 5. 
4. Un seul élément de campagne par groupe d’utilisateurs.

<div id="updating">
  ### Mise à jour
</div>

Mettez à jour un test A/B à l’aide du endpoint [PUT accounts/:account&#95;id/ab&#95;tests/:ab&#95;test&#95;id](https://developer.x.com/en/docs/x-ads-api/measurement/api-reference/ab-tests). Cet endpoint nécessite l’envoi d’un bloc JSON dans la requête. L’en-tête Content-Type doit être défini sur application/json.

Comme pour les autres endpoints de mise à jour, le endpoint [PUT accounts/:account&#95;id/ab&#95;tests/:ab&#95;test&#95;id](/fr/x-ads-api/measurement/ab-testing#get-accounts-account-id-ab-tests) exige que l’ID du test A/B soit référencé dans l’URL. En général, les tests A/B ne peuvent être mis à jour que lorsque leur statut est SCHEDULED. Il existe une exception : il est possible de mettre à jour la valeur end&#95;time du test A/B lorsqu’il est LIVE.

Cet endpoint prend en charge le JSON partiel avec des ID d’objets. Les principes suivants s’appliquent :

* Pour ajouter ou supprimer des objets ou des éléments, transmettez l’intégralité du tableau (et ses sous-structures) ; il s’agit d’une opération de **remplacement**

* Sinon, modifiez (changez, ajoutez, supprimez) les *champs* existants en vous référant aux noms de clés ou aux ID

  * Pour supprimer un champ, définissez sa valeur sur null

  * Les champs qui ne sont pas transmis ne sont pas modifiés

Par exemple, pour ajouter un troisième groupe d’utilisateurs au test A/B précédemment créé, nous devrions envoyer le tableau user&#95;groups avec les deux objets de groupes d’utilisateurs existants ainsi qu’avec le nouveau que nous souhaitons ajouter. Considérez cela comme une *recréation* du tableau user&#95;groups ; transmettez les données comme si vous le créiez de cette manière dès le départ (ne transmettez pas les ID des objets de groupes d’utilisateurs). Le tableau user&#95;groups dans la requête de mise à jour pourrait être représenté comme suit.

```json
[
  {
    "entity_ids": [
      "f2qcw",
      "f2tht"
    ],
    "size": "30.0",
    "name": "first group"
  },
  {
    "entity_ids": [
      "f2rqi",
      "f2tws"
    ],
    "size": "30.0",
    "name": "second group",
    "description": "second AB test group"
  },
  {
    "entity_ids": [
      "i1vwr",
      "i1xre"
    ],
    "size": "40.0"
  }
]
```

Remarquez que les valeurs de taille de l’ensemble des objets totalisent toujours 100,00. Si nous ne les avions pas mises à jour pour les deux premiers objets — qui étaient auparavant définis à 50,00 chacun — la requête aurait échoué.

Si, en revanche, nous souhaitions simplement ajouter une description au premier groupe d’utilisateurs, le tableau user&#95;groups dans la requête de mise à jour serait le suivant.

```json
[
  {
    "id": "p1bcx",
    "description": "updated using a PUT request"
  }
]
```

Nous faisons référence à l&#39;objet de groupe d&#39;utilisateurs via son id et n&#39;incluons que le champ que nous souhaitons modifier.

Ce point de terminaison prend en charge du JSON partiel avec des IDs d&#39;objet. Les principes suivants s&#39;appliquent :

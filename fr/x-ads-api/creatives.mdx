<div id="overview">
  ## Vue d’ensemble
</div>

Les éléments créatifs sont toutes les entités qui peuvent être promues dans une campagne. Les publications peuvent inclure du texte, des images, des GIF, des vidéos ou des cartes. Les cartes peuvent inclure des images ou des vidéos.

Les éléments créatifs image, GIF ou vidéo sont téléversés à l’aide soit de l’endpoint [POST media/upload](/fr/x-api/media/upload-media#post-media-upload) — un endpoint de téléversement simple qui ne prend en charge que les images — soit des endpoints POST media/upload (chunked). Ils peuvent être ajoutés aux

cartes :

* POST accounts/:account&#95;id/cards
  Tweets :
* POST accounts/:account&#95;id/tweets - Pour ajouter des cartes aux Tweets, utilisez le paramètre card&#95;uri.
  Tweets programmés :
* POST accounts/:account&#95;id/scheduled&#95;tweets

Pour plus de détails sur les cartes, veuillez consulter la page Cartes. La page Vidéo sponsorisée fournit des détails sur l’association de vidéos avec des cartes ou des Tweets.

### Cards

L’API Ads prend en charge plusieurs types de cartes qui peuvent être utilisées dans des Tweets, puis promues dans des campagnes. **Remarque** : une fois le Tweet publié, les détails de la carte sont visibles publiquement. Cela peut inclure des informations sur l’utilisateur titulaire de la carte.

<div id="image">
  #### Image
</div>

Les spécifications d’image suivantes s’appliquent aux ressources utilisées dans les [Cards](/fr/x-ads-api/creatives#cards-2). Les images doivent avoir un poids maximal de 3 Mo et une largeur d’au moins 800 px. De plus, nous prenons en charge les rapports largeur : hauteur suivants.

* Site web : 1:1 et 1,91:1
* Image App Download : 1:1 et 1,91:1
* Poll : 1,91:1
* Image Conversation : 1,91:1
* Image Direct Message : 1,91:1

Nous prenons en charge les formats d’image suivants : .bmp, .jpeg et .png.

<div id="video">
  #### Vidéo
</div>

Les spécifications vidéo suivantes s’appliquent aux éléments utilisés dans les [Cards](/fr/x-ads-api/creatives#cards-2). Nous prenons en charge les rapports largeur/hauteur suivants.

* Vidéo pour site web : 16:9 et 1:1
* Vidéo pour téléchargement d’app : 16:9 et 1:1
* Sondage : 16:9
* Conversation vidéo : 16:9
* Message privé vidéo : 16:9

<div id="promoted-video">
  ### Vidéo sponsorisée
</div>

Ce document fournit une brève vue d’ensemble du processus de téléversement et de promotion de vidéo via l’Ads API.

L’Ads API prend en charge la vidéo sponsorisée dans les [Tweets](/fr/x-ads-api/creatives#tweets-2) et dans les cartes suivantes :

* [Vidéo vers site web](https://devcommunity.x.com/t/ads-api-version-11/168814)
* [Vidéo de téléchargement d’application](https://devcommunity.x.com/t/ads-api-version-11/168814)
* [Vidéo de conversation](/fr/x-ads-api/creatives#video-conversation-cards)

Commencez par téléverser la vidéo à l’aide de l’endpoint [POST media/upload (chunked)](https://developer.x.com/en/docs/media/upload-media/api-reference/post-media-upload-init.html). En utilisant le `media_id`, associez la vidéo à un compte publicitaire à l’aide de l’endpoint POST accounts/:account&#95;id/videos. L’`id` de la vidéo, parfois appelé `media_key`, sera utilisé dans les requêtes suivantes. Il s’agit d’une chaîne de caractères qui commence par un entier (int), est suivie d’un caractère de soulignement (&#95;) et se termine par une valeur de type long. Par exemple : `13_875943225764098048`.

<div id="promoted-video-in-tweets">
  #### Vidéo sponsorisée dans les Publications
</div>

Pour créer une Publication, utilisez l’endpoint [POST accounts/:account&#95;id/tweet](/fr/x-ads-api/creatives#get-accounts-account-id-tweets) avec l’`id` de la vidéo. À ce stade, vous pouvez également fournir un titre pour la vidéo, une description et un appel à l’action (CTA). Ces valeurs sont visibles par les utilisateurs.

<div id="promoted-video-in-cards">
  #### Vidéo sponsorisée dans les cartes
</div>

Les cartes Video App Download et Video Conversation permettent d&#39;ajouter des images de couverture (posters). Chargez une image à utiliser dans ces cartes à l&#39;aide de l&#39;endpoint [POST media/upload](https://developer.x.com/en/docs/media/upload-media/api-reference/post-media-upload.html).

Créez la carte en utilisant l&#39;un des endpoints suivants :

* [POST accounts/:account&#95;id/cards/video&#95;website](https://devcommunity.x.com/t/ads-api-version-11/168814)
* [POST accounts/:account&#95;id/cards/video&#95;app&#95;download](https://devcommunity.x.com/t/ads-api-version-11/168814)
* [POST accounts/:account&#95;id/cards/video&#95;conversation](https://devcommunity.x.com/t/ads-api-version-11/168814)

en utilisant l&#39;`id` de la vidéo et, de façon facultative, le `media_id` de l&#39;image (pour l&#39;image de couverture).

Enfin, créez le Tweet à l&#39;aide de l&#39;endpoint POST accounts/:account&#95;id/tweet. Les cartes sont associées aux Tweets à l&#39;aide du paramètre `card_uri`.

<div id="general-information">
  #### Informations générales
</div>

Pour des conseils détaillés sur le téléversement de vidéos via l’API, consultez le [guide de téléversement de vidéos](https://developer.x.com/en/docs/media/upload-media/uploading-media.html).

Les vidéos peuvent également être promues en tant qu’éléments pré-roll. Consultez le [guide sur l’objectif de vues vidéo pré-roll](/fr/x-ads-api/campaign-management#video-views-preroll-objective) pour une explication détaillée.

* (Depuis le 22 octobre 2015) Lors du téléversement de vidéos destinées à être utilisées dans du contenu promu, le paramètre `media_category` doit être défini avec la valeur `amplify_video` pour toutes les requêtes `INIT` vers l’endpoint [POST media/upload (chunked)](https://developer.x.com/en/docs/media/upload-media/api-reference/post-media-upload-init.html). L’utilisation de ce paramètre garantit que la vidéo est prétraitée de manière asynchrone et préparée pour être utilisée dans du contenu promu. La commande `STATUS` peut être utilisée pour vérifier l’achèvement du traitement asynchrone après le téléversement de la vidéo.
* La durée maximale actuellement autorisée pour une vidéo promue est de 10 minutes, avec une taille de fichier de 500 Mo ou moins.
* La vidéo téléversée doit être au format MP4 ou MOV.
* Une vidéo téléversée est généralement traitée rapidement, mais les temps de traitement peuvent varier en fonction de la durée de la vidéo et de la taille du fichier.
* Les images d’aperçu téléversées doivent être au format PNG ou JPG. Il n’y a pas de contrainte concernant le rapport largeur/hauteur ou la taille, mais l’image d’aperçu sera ajustée pour s’adapter au lecteur vidéo.

### Tweets planifiés

<div id="introduction">
  #### Introduction
</div>

La fonctionnalité Scheduled Tweets permet à un annonceur ou à un utilisateur de créer un Post pouvant être programmé pour être publié à une date ultérieure. Outre la création et la gestion de ces Posts, l’API permet d’associer ces Posts à un line item, afin de les promouvoir une fois le Post publié. Cela permet aux annonceurs de préparer des Posts natifs et de planifier à l’avance les éléments créatifs de leurs campagnes pour toute initiative clé. Par exemple, préparer un Post créatif pour qu’il soit publié immédiatement lors de l’annonce d’un nouveau produit.

L’ensemble des fonctionnalités fournies par les endpoints de l’API Scheduled Tweets est répertorié ci‑dessous :

* Créer, modifier et consulter de nouveaux Posts programmés
* Associer un Post programmé à un line item
* Interroger et gérer les Posts programmés existants
* Une fois qu’un Post programmé est publié, récupérer l’`id` du Post en ligne

</div>

* [GET accounts/:account&#95;id/scheduled&#95;tweets/preview/:scheduled&#95;tweet&#95;id](/fr/x-ads-api/creatives#scheduled-tweets-2) (afficher un Scheduled Tweet existant)

Du fait que les Scheduled Tweets sont des entités distinctes des Tweets « en direct », deux séries distinctes de validations sont effectuées lors de toute création ou modification de ces Tweets. La première série de règles de validation est appliquée lors de l’étape de création du Scheduled Tweet, plus précisément :

<div id="scheduled-tweet-create">
  #### Création de Tweet programmé :
</div>

* Vérifiez que l’utilisateur authentifié a accès à la création de Tweets organiques pour un @handle donné. Les privilèges de création de Tweet Promoted-Only exigent que l’utilisateur authentifié soit un utilisateur du compte disposant des [autorisations du compositeur de Tweet](https://developer.x.com/content/developer-twitter/en/docs/ads/campaign-management/api-reference/authenticated-user-access#get-accounts-account-id-authenticated-user-access).
* Vérifiez qu’il n’y a pas plus de 30 Tweets programmés pour être créés dans une fenêtre de 15 minutes autour de l’heure scheduled&#95;at. Un message d’erreur SCHEDULED&#95;TWEET&#95;LIMIT&#95;EXCEEDED indique qu’un trop grand nombre de Tweets programmés ont été planifiés dans le même intervalle de 15 minutes à venir. Les annonceurs devront supprimer un Tweet programmé existant ou déplacer l’heure scheduled&#95;at plus tôt ou plus tard.

<div id="scheduled-tweet-goes-live">
  #### Publication du Tweet programmé :
</div>

* Ces règles de validation sont exécutées à l’heure indiquée dans scheduled&#95;at et sont identiques à celles appliquées lors de la création d’un Tweet classique via l’API. Par exemple, un Tweet programmé ne sera pas publié et le scheduled&#95;status sera défini sur FAILED si le Tweet programmé contient à la fois une image et un GIF.

**Créer un nouveau Tweet programmé**

Un nouveau Tweet programmé peut être créé à l’aide du point de terminaison [POST accounts/:account&#95;id/scheduled&#95;tweets](https://developer.x.com/content/developer-twitter/en/docs/ads/creatives/api-reference/scheduled-tweets#post-accounts-account-id-scheduled-tweets). Ce point de terminaison comporte les paramètres obligatoires suivants : l’horodatage `scheduled_at`, ainsi que le `text` du Tweet si aucune entité média n’est incluse dans le Tweet. En outre, ce point de terminaison fournit quelques options supplémentaires qui vous permettent de créer un Tweet programmé au nom d’un autre @handle via le paramètre `as_user_id`, ainsi que la possibilité d’ajouter une carte (`card_uri`) et des médias (`media_ids`). À noter : un Tweet ne peut contenir que des entités d’un seul type, c’est‑à‑dire soit Vidéo, soit Gif, soit Image. Le paramètre `nullcast` détermine si le Tweet est un Tweet « Promoted-Only » ou non. Tous les nouveaux Tweets programmés créés sont « Promoted-Only » (`nullcast=true`) par défaut. Si `nullcast=false`, alors un Tweet programmé organique est créé.

Une fois qu’un Tweet programmé est créé avec succès, la réponse contient un champ `id`, qui correspond à l’identifiant unique du Tweet programmé lui-même. En plus de ce champ, un autre champ appelé `tweet_id` est également renvoyé. Ce champ est initialement défini sur `null`, mais une fois que le Tweet est publié, ce champ est renseigné avec l’id du Tweet « en direct ».

```
twurl -H 'ads-api.x.com' -X POST "/6/accounts/:account_id/scheduled_tweets" -d 'scheduled_at=2017-12-24T23:59:00Z&text=Happy Holidays!'
```

Cela va créer le Tweet programmé suivant :

```json
{
  "request": {
    "params": {
      "text": "Joyeuses fêtes !",
      "scheduled_at": "2017-12-24T23:59:00Z"
    }
  },
  "data": {
    "completed_at": null,
    "id_str": "917507899668099072",
    "text": "Joyeuses fêtes !",
    "user_id": "3271358660",
    "scheduled_status": "SCHEDULED",

```

Une fois que ce Tweet programmé sera mis en ligne, le champ `tweet_id` sera renseigné avec l’identifiant du Tweet « en direct ».

**Associer un Tweet programmé à un line item**

Bien que les Tweets programmés puissent être utilisés pour créer des Tweets organiques, nous permettons également aux partenaires de créer un Tweet « Promoted-Only » (`nullcast=true`), dont chacun peut être associé à un line item. Pour ce faire, nous mettons également à disposition un endpoint [POST accounts/:account&#95;id/scheduled&#95;promoted&#95;tweets](https://developer.x.com/content/developer-twitter/en/docs/ads/campaign-management/api-reference/scheduled-promoted-tweets#post-accounts-account-id-scheduled-promoted-tweets). Cet endpoint permet uniquement d’associer un seul Tweet promu programmé à un line item au cours d’un seul appel d’API. Pour associer plusieurs Tweets programmés au même line item, plusieurs appels d’API sont nécessaires.

Veuillez noter qu’il n’est pas possible de modifier un Tweet promu programmé existant.

```
twurl -H 'ads-api.x.com' -X POST "/6/accounts/:account_id/scheduled_promoted_tweets" -d 'line_item_id=a44qc&scheduled_tweet_id=917507899668099072'
```

```json
{
  "data": {
    "line_item_id": "a44qc",
    "id": "26576",
    "created_at": "2017-10-09T22:24:16Z",
    "updated_at": "2017-10-09T22:24:16Z",
    "scheduled_tweet_id": "917507899668099072",
    "tweet_id": null,
    "deleted": false
  },
  "request": {
    "params": {
      "line_item_id": "a44qc",
      "scheduled_tweet_id": 917507899668099100,
      "account_id": "aaaaa"
    }
  }
}
```

Cet endpoint crée uniquement une association entre un Scheduled Tweet donné et un line item. Une fois que les dates de diffusion de la campagne/du line item sont actuelles, le line item commencera automatiquement à diffuser le Tweet « en ligne » correspondant. Bien que nous validions à cette étape que le Scheduled Tweet est dans l’état `SCHEDULED` et que le Scheduled Tweet donné est valide pour l’objectif donné, aucune autre validation n’est effectuée. Les règles de validation restantes qui s’appliquent au line item et au Scheduled Tweet sont exécutées lorsque le Tweet passe « en ligne ».

Afin de garantir qu’il n’y ait aucun problème de diffusion de la campagne, il est recommandé que le champ `scheduled_at` du Scheduled Tweet soit défini à un moment antérieur aux dates de diffusion de la campagne/du line item.

Par exemple, imaginons que le Scheduled Tweet soit configuré pour passer en ligne après la date de début de la campagne (et qu’il n’y ait qu’un seul Tweet associé à un seul line item), alors la campagne sera `ACTIVE`. Cependant, étant donné que le Scheduled Tweet n’est pas encore en ligne, il n’y aura aucune création publicitaire disponible pour la diffusion.

**Gestion des Scheduled Tweets**

Les endpoints restants permettent aux utilisateurs de l’API de gérer tous leurs Scheduled Tweets et Scheduled Promoted Tweets. Ces API peuvent être utilisées soit pour renvoyer une liste de tous les Scheduled Tweets, éventuellement filtrés par un état donné, soit pour rechercher un Scheduled Tweet donné par son `id`.

<div id="what-happens-when-a-scheduled-tweet-goes-live">
  #### Que se passe-t-il lorsqu’un Tweet programmé est mis en ligne ?
</div>

Lorsqu’un Tweet programmé est sur le point d’être mis en ligne, ou en d’autres termes à l’heure `scheduled_at`, les mises à jour suivantes sont effectuées :

* Le Tweet « en ligne » est créé, mais cela peut avoir une latence pouvant aller jusqu’à 1 seconde
* Le `tweet_id` est ajouté aux entités suivantes :
* Tweet programmé
* Tweet programmé sponsorisé
* Une nouvelle entité de Tweet sponsorisé est créée

<div id="best-practices">
  #### Bonnes pratiques
</div>

Les bonnes pratiques suivantes sont recommandées lors de la création ou de la promotion de Tweets programmés :

* Assurez-vous que le Tweet est valide lors de la création du Tweet programmé (par exemple, un Tweet peut uniquement contenir une image, une vidéo ou un GIF, et non une combinaison des trois)
* Assurez-vous que les dates de diffusion de la campagne (c’est-à-dire `start_time` et `end_time`) correspondent à l’heure `scheduled_at` du Tweet programmé
* Les Tweets programmés ne doivent pas être programmés à plus d’un an dans le futur (365 jours)
* L’aperçu du Tweet n’est actuellement pas disponible pour les Tweets programmés (il s’agit de la possibilité de prévisualiser les Tweets programmés avant leur création)

<div id="media-library">
  ### Bibliothèque de médias
</div>

<div id="introduction">
  #### Introduction
</div>

Les points de terminaison de la Media Library permettent de gérer les images, les GIFs et les vidéos pour les comptes X Ads. Les ressources média de la bibliothèque peuvent être utilisées dans des Posts et pour créer des cartes. Elles peuvent également être réutilisées dans plusieurs [créatifs](https://developer.x.com/content/developer-twitter/en/docs/ads/creatives/overview), ce qui évite d’avoir à importer plusieurs fois la même ressource.

<div id="api-endpoints">
  #### Points de terminaison de l’API
</div>

* [POST media/upload](https://developer.x.com/content/developer-twitter/en/docs/media/upload-media/api-reference/post-media-upload#post-media-upload) ou [POST media/upload (chunked)](https://developer.x.com/content/developer-twitter/en/docs/media/upload-media/api-reference/post-media-upload-init#post-media-upload-init) (téléverser un média)
* [POST accounts/:account&#95;id/media&#95;library](https://developer.x.com/x-ads-api/creatives#get-accounts-account-id-media-library#post-accounts-account-id-media-library) (ajouter des médias à la Media Library)

<div id="adding-to-the-library">
  #### Ajout à la bibliothèque
</div>

L’ajout de médias à la bibliothèque est un processus en deux étapes. Commencez par téléverser la ressource en utilisant soit l’endpoint [POST media/upload](https://developer.x.com/content/developer-twitter/en/docs/media/upload-media/api-reference/post-media-upload#post-media-upload), soit la série d’endpoints [POST media/upload (chunked)](https://developer.x.com/content/developer-twitter/en/docs/media/upload-media/api-reference/post-media-upload-init#post-media-upload-init). (Consultez le guide [Chunked media upload](https://developer.x.com/content/developer-twitter/en/docs/media/upload-media/uploading-media/chunked-media-upload) pour plus de détails sur notre processus de téléversement en plusieurs parties.)

twurl -X POST -H upload.x.com "/1.1/media/upload.json?additional_owners=756201191646691328" --file latte.jpeg --file-field "media"

<div id="request-parameters">
  #### Paramètres de requête
</div>

Toutes les requêtes POST de Media Library nécessitent un identifiant de média. Cette valeur est renvoyée lors de l’étape de téléchargement. Lors de l’utilisation de `media_id`, comme dans l’exemple ci-dessus, une `media_category` doit également être spécifiée. Il existe quatre valeurs de catégorie possibles : `AMPLIFY_VIDEO`, `TWEET_GIF`, `TWEET_IMAGE` et `TWEET_VIDEO`.

En option, les valeurs `name` et `file_name` peuvent être définies pour les objets de la Media Library. Ces attributs aident les utilisateurs à distinguer les variantes de média dans la bibliothèque.

Pour les vidéos, il est également possible de définir un titre et une description. Ces valeurs sont destinées à être transmises en tant que paramètres de requête `video_title` et `video_description` avec l’endpoint [POST accounts/:account&#95;id/tweet](https://developer.x.com/content/developer-twitter/en/docs/ads/creatives/api-reference/tweets#post-accounts-account-id-tweet). Dans la Publication, ce texte apparaît sous la vidéo.

<div id="attributes">
  #### Attributs
</div>

La Media Library introduit formellement le concept de media&#95;key. Il s&#39;agit de l&#39;identifiant unique des objets de la bibliothèque. Les media keys sont des valeurs de type chaîne de caractères au format suivant : 13&#95;875943225764098048. Elles sont entièrement prises en charge dans tous nos endpoints de cartes.

En outre, la réponse Media Library inclut le media&#95;id, représenté sous forme de chaîne de caractères. Celui-ci est inclus pour les ressources qui n&#39;acceptent pas encore de media key : [Tweets](https://developer.x.com/content/developer-twitter/en/docs/ads/creatives/api-reference/tweets#post-accounts-account-id-tweet)*, [Tweet preview](https://developer.x.com/content/developer-twitter/en/docs/ads/creatives/api-reference/tweets#get-accounts-account-id-tweet-preview)* et [Scheduled Tweets](https://developer.x.com/content/developer-twitter/en/docs/ads/creatives/api-reference/scheduled-tweets#post-accounts-account-id-scheduled-tweets). Nous travaillons à la prise en charge des media keys partout.

L&#39;attribut aspect&#95;ratio est renvoyé pour les GIFs et les vidéos. Il peut être utilisé pour filtrer les médias à utiliser dans les cartes qui n&#39;acceptent que certains rapports largeur/hauteur.

*Ces endpoints prennent en charge le paramètre video&#95;id, qui est une media key.

<div id="identifying-cards">
  ### Identifier les Cards
</div>

<div id="introduction">
  #### Introduction
</div>

Les Cards sont des formats publicitaires personnalisables qui utilisent des médias et qui peuvent être associés à un site web, une application ou à des appels à l’action pour générer certains types d’engagements de la part des utilisateurs, comme le démarrage d’un message privé. Elles peuvent être ajoutées à des Posts, des Posts programmés ou des brouillons de Post.

Les Cards peuvent être référencées dans les objets Tweet de deux manières : par le `card_uri` de la Card ou par son `preview_url`. Des exemples de valeurs pour chacun sont présentés ci-dessous.

| card&#95;uri | preview&#95;url |
| :--- | :--- |
| card://1043282691834048513 | https://cards.x.com/cards/18ce54d4x5t/68w3s |

**Remarque** : à partir de la version 3 de l’Ads API, seul le `card_uri` est généré et renvoyé dans la réponse `cards` pour les Cards nouvellement créées.

**Remarque** : à partir de la version 5 de l’Ads API, le `preview_url` dans la réponse `cards` n’est plus renvoyé.

Le type de référence dans la réponse de l’objet Tweet dépendra de la manière dont le Tweet a été créé. En d’autres termes, si le Tweet a été créé en utilisant le paramètre de requête `card_uri`, la valeur de l’URI de la Card apparaîtra dans la réponse. Si, en revanche, le `preview_url` a été inclus dans le texte du Tweet, l’URL d’aperçu apparaîtra dans la réponse.

<div id="identifying-media">
  ### Identification des médias
</div>

<div id="introduction">
  #### Introduction
</div>

Les médias — images, GIF et vidéos — peuvent être ajoutés aux Tweets et aux cartes. En outre, les vidéos peuvent être utilisées comme ressources de pré-roll et les images peuvent être promues sur la [X Audience Platform](https://developer.x.com/en/docs/ads/measurement/overview/twitter-audience-platform). Cette section décrit comment trouver les références média au sein de ces entités.

Il existe deux types d’identifiants de média : des ID et des clés. Des exemples de valeurs pour chacun sont présentés ci-dessous.

| **ID de média** | **Clé de média** |
| :--- | :--- |
| 1029825579531807971 | 13&#95;1029825579531807971 |

La clé de média correspond à l’ID précédé d’un préfixe numérique et d’un caractère de soulignement.

<div id="images">
  #### Images
</div>

Le tableau suivant présente les types d’identifiants actuellement disponibles dans la réponse de chaque ressource liée aux images, ainsi que le ou les noms d’attributs correspondants.

| **Resource** | **Identifier** | **Attribute(s)** |
| :--- | :--- | :--- |
| Image cards | None |  |
| Tweet | Both | `entities["media"]["id_str"]`  `entities["media"]["media_key"]` |
| Scheduled Tweet | Both | `media_ids` and `media_keys` |
| Draft Tweet | Both | `media_ids` and `media_keys` |
| Account Media | None |  |
| Media Library | Both | `media_id` and `media_key` |

Les Image cards et les ressources Account Media ne comportent aucune référence à un identifiant de média. Les Tweets ne comportent que des identifiants de média. Les Scheduled et Draft Tweets incluent à la fois l’identifiant de média et la clé de média. La Media Library renvoie également les deux.

Pour les Tweets, les champs id et id&#95;str de l’objet au sein du tableau entities[&quot;media&quot;] correspondent à l’identifiant de média. Lorsqu’un Tweet contient plusieurs images, les références à chaque entité média ne sont disponibles que dans extended&#95;entities[&quot;media&quot;].

En plus des références aux identifiants, il est souvent important d’avoir accès à l’URL de l’image.

| **Resource** | **Attribute(s)** | **Format** |
| :--- | :--- | :--- |
| Image cards | `image` | .jpg |
| Tweet* | `entities["media"][0]["media_url"]` ou `extended_entities["media"][i]["media_url"]` | .jpg |
| Scheduled Tweet | None |  |
| Draft Tweet | None |  |
| Account Media | `media_url` | .jpg |
| Media Library | `media_url` | .jpg |

* L’emplacement de cette URL dépend du fait que le Tweet contienne une seule image ou plusieurs images.

Toutes les Image cards incluent un attribut de réponse image qui contient l’URL de l’image X. (Pour les image app download cards, le nom est wide&#95;app&#95;image.)

Pour les Tweets, l’emplacement de l’URL de média dépend à la fois du type de média et de l’endpoint utilisé. Pour les Tweets avec une seule image, l’URL se trouve dans entities[&quot;media&quot;][0][&quot;media&#95;url&quot;]. Cela vaut aussi bien pour l’Ads API que pour la Standard API. En revanche, lorsque les Tweets contiennent plusieurs images, les URL ne se trouvent que dans extended&#95;entities[&quot;media&quot;][i][&quot;media&#95;url&quot;]. Ceci n’est disponible que dans la Standard API.

<div id="videos">
  #### Vidéos
</div>

Le tableau suivant indique les types d&#39;identifiants actuellement disponibles dans la réponse de chaque ressource liée à la vidéo, ainsi que le ou les noms d&#39;attributs correspondants.

| **Ressource** | **Identifiant** | **Attribut(s)** |
| :--- | :--- | :--- |
| Cartes vidéo | Peut être l&#39;un ou l&#39;autre | `video_content_id` |
| Cartes de sondage vidéo | Aucun |  |
| Tweet | Les deux | `entities["media"]["id_str"]`  `entities["media"]["media_key"]` |
| Tweet programmé | Les deux | `media_ids` et `media_keys` |
| Tweet brouillon | Les deux | `media_ids` et `media_keys` |
| Médias du compte | Clé de média | `video_id` |
| Médiathèque | Les deux | `media_id` et `media_key` |

Bien que les cartes vidéo (à l&#39;exception des cartes de sondage avec vidéo) incluent un attribut de réponse video&#95;content&#95;id, le type de valeur renvoyée n&#39;est pas cohérent. Dans certains cas, il s&#39;agit d&#39;un ID de média ; dans d&#39;autres, d&#39;une clé de média.

Les informations expliquant comment accéder à l&#39;URL de la vidéo sont présentées ci-dessous.

| **Ressource** | **Attribut(s)** | **Format** |
| :--- | :--- | :--- |
| Cartes vidéo | `video_url` et `video_hls_url` | .vmap  .m3u8 |
| Tweet avec vidéo | `extended_entities["media"][i]["video_info"]["variants"][j]["url"]` | .mp4 |
| Tweet programmé | Aucun |  |
| Tweet brouillon | Aucun |  |
| Médias du compte | Aucun |  |
| Médiathèque | `media_url` | .mp4 |

Les cartes vidéo incluent les attributs de réponse video&#95;url et video&#95;hls&#95;url avec, respectivement, des URL .vmap et .m3u8.

#### Media Library

Il est parfois nécessaire de récupérer des informations supplémentaires sur une ressource média. Un cas d’utilisation, pour les cartes vidéo, consiste à récupérer l’URL mp4 au lieu de l’URL vmap. Ces informations sont disponibles dans la Media Library. Pour plus de détails sur les informations disponibles, consultez notre [Media Library Guide](https://developer.x.com/content/developer-twitter/en/docs/ads/creatives/guides/media-library). La plupart des ressources appartenant à l’utilisateur FULL promouvable du compte publicitaire se trouvent dans la bibliothèque. Il existe toutefois quelques exceptions.

**Fetching media**

Comme indiqué ci-dessus, les cartes image ne contiennent aucune référence ni aux media IDs ni aux media keys. Par conséquent, il n’est pas possible de récupérer leurs ressources via la Media Library. Cela est également vrai pour les images [Account Media](https://developer.x.com/content/developer-twitter/en/docs/ads/creatives/api-reference/account-media#account-media).

Les cartes vidéo exigent que la ressource vidéo fasse partie de la Media Library (ou de la ressource Videos avant son introduction) avant leur création. En conséquence, ces ressources seront toujours récupérables dans la Media Library. Cela est également vrai pour les ressources Account Media PREROLL.

Enfin, les médias des Tweets sont toujours garantis comme étant présents dans la Media Library.

Le tableau suivant récapitule quelles ressources sont récupérables dans la Media Library, en tenant compte du fait que la réponse de la ressource contient ou non un identifiant à utiliser pour la recherche.

| **Resource** | **In the Media Library** |
| :--- | :--- |
| Image cards | No |
| Video cards | Yes* |
| Tweets (any media)** | Yes |
| Scheduled Tweets | Yes |
| Draft Tweets | Yes |
| Account media images | No |
| Account media videos (`PREROLL`) | Yes |

* Pour les cartes où le `video_content_id` est une media key. Lorsque la valeur est un media ID, la ressource existe toujours dans la Media Library, mais sa récupération implique d’y ajouter un préfixe numérique et un caractère de soulignement (*).
** Les Tweets ne renvoient que des media IDs. Bien que la ressource soit garantie comme étant présente dans la Media Library, sa récupération implique d’y ajouter un préfixe numérique et un caractère de soulignement (*).

**Interactions with Account Media**

Il existe deux cas où les ressources média ajoutées à la bibliothèque sont automatiquement ajoutées à la ressource Account Media.

* Lorsqu’une ressource AMPLIFY&#95;VIDEO est ajoutée à la Media Library, elle est automatiquement ajoutée comme ressource Account Media avec un creative type PREROLL.
* Lorsque des images ayant des dimensions spécifiques (voir « Creative Types » sur notre [page des énumérations](https://developer.x.com/content/developer-twitter/en/docs/ads/general/overview/enums)) sont ajoutées à la Media Library, elles sont automatiquement ajoutées comme ressources Account Media. Le creative type (par exemple, INTERSTITIAL) dépend des dimensions de l’image.

<div id="tweets">
  ### Tweets
</div>

<div id="introduction">
  #### Introduction
</div>

L&#39;API X Ads prend en charge trois types de Tweets : publiés, programmés et brouillons.

<div id="nullcasted-tweets">
  #### Tweets nullcastés
</div>

Les Tweets peuvent être nullcastés (également appelés « Promoted-only ») ou organiques. Les Tweets nullcastés, une fois publiés, n&#39;apparaissent pas dans la timeline publique de l&#39;utilisateur, même s&#39;ils sont publics. Les Tweets organiques, en revanche, sont diffusés aux abonnés de l&#39;utilisateur et apparaissent dans la timeline publique de l&#39;utilisateur.

**Création de Tweets**

Chacun des trois endpoints de création de Tweet prend en charge un paramètre booléen nullcast qui donne à l&#39;utilisateur de l&#39;API la possibilité de créer des Tweets nullcastés ou organiques. Les Tweets nullcastés peuvent être créés par l&#39;utilisateur ou par toute personne disposant de l&#39;autorisation de créer des Tweets au nom de l&#39;utilisateur. Les Tweets organiques ne peuvent être créés que par le [full promotable user](https://developer.x.com/content/developer-twitter/en/docs/tutorials/ads-api-hierarchy-terminology#promotable-users).

**Mise à jour de Tweets**

Il est possible de modifier la propriété nullcast pour les Tweets programmés et les Tweets en brouillon. Pour les Tweets programmés, les modifications peuvent être effectuées jusqu&#39;à l&#39;heure scheduled&#95;at du Tweet. Les Tweets en brouillon peuvent être modifiés indéfiniment. Une fois publiés, cependant, il n&#39;est plus possible de changer un Tweet de nullcasté à organique ou inversement.

<div id="promoting-tweets">
  #### Promotion de Tweets
</div>

Seuls les Tweets publiés et programmés peuvent être promus. Ceux-ci peuvent être soit nullcastés, soit organiques, sans aucune restriction. Un annonceur peut promouvoir ses propres Tweets ou ceux d’un autre utilisateur, à condition d’avoir obtenu l’autorisation de le faire. (Voir : [Promoting another user&#39;s Tweets](https://developer.x.com/content/developer-twitter/en/docs/tutorials/promoting-another-users-content) pour plus d’informations.)

Plusieurs Tweets peuvent être promus dans une seule campagne. De même, un même Tweet peut être promu dans une ou plusieurs campagnes.

Pour promouvoir des Tweets publiés, utilisez l’endpoint [POST accounts/:account&#95;id/promoted&#95;tweets](https://developer.x.com/content/developer-twitter/en/docs/ads/campaign-management/api-reference/promoted-tweets#post-accounts-account-id-promoted-tweets). Cet endpoint associe des Tweets publiés à un élément de campagne (line item). Pour promouvoir des Tweets programmés, utilisez l’endpoint [POST accounts/:account&#95;id/scheduled&#95;promoted&#95;tweets](https://developer.x.com/content/developer-twitter/en/docs/ads/campaign-management/api-reference/scheduled-promoted-tweets#post-accounts-account-id-scheduled-promoted-tweets).

<div id="tweet-ids">
  #### ID de Tweet
</div>

Les ID de Tweet publiés, programmés et en brouillon sont [numériques](https://developer.x.com/content/developer-twitter/en/docs/basics/twitter-ids) : ce sont des entiers non signés sur 64 bits. Par exemple, l’ID du Tweet publié suivant est 1166476031668015104.

<div id="carousels">
  ### Carrousels
</div>

<div id="introduction">
  #### Introduction
</div>

L&#39;API X Ads permet de créer et de récupérer des carrousels vidéo et des carrousels d&#39;images. Le carrousel est un type de carte qui peut contenir entre 2 et 6 éléments multimédias. La carte carrousel peut diriger un utilisateur vers un site web ou l&#39;inciter à installer une application mobile. Pour plus d&#39;informations sur les carrousels, leurs avantages, les bonnes pratiques et les FAQ, consultez notre page [Carousel Ads on X](https://business.x.com/en/advertising/carousels.html).

Un carrousel, comme tout autre type de carte, peut être utilisé dans des Tweets, et ces Tweets peuvent ensuite être sponsorisés. Le processus est le même que celui auquel vous êtes déjà habitué :

1. Téléverser les médias
2. Créer la carte
3. Créer le Tweet
4. Promouvoir le Tweet

La seule différence concerne la façon dont la carte est créée. Alors que les autres requêtes de création de carte acceptent des paramètres de requête, les requêtes de création de carte carrousel n&#39;acceptent qu&#39;un corps de requête POST au format JSON.

<div id="endpoints">
  #### Points de terminaison
</div>

L’API Ads permet de créer et de récupérer des carrousels.

Pour créer un carrousel — quel qu’en soit le type — utilisez le point de terminaison [POST accounts/:account&#95;id/cards](https://developer.x.com/en/docs/twitter-ads-api/creatives/api-reference/cards#post-accounts-account-id-cards). Pour récupérer des carrousels, utilisez le point de terminaison [GET accounts/:account&#95;id/cards](https://developer.x.com/en/docs/twitter-ads-api/creatives/api-reference/cards#get-accounts-account-id-cards).

<div id="json-post-body">
  #### Corps de la requête POST JSON
</div>

Les carrousels sont créés à l’aide de deux composants. Le premier spécifie les éléments multimédias qui seront utilisés. Le second spécifie les informations concernant soit le site web, soit l’application.

Plus précisément, une carte de carrousel est créée en utilisant les composants suivants, dans cet ordre :

* Un composant `SWIPEABLE_MEDIA`, qui accepte un tableau de clés de média
* *Un* des éléments suivants :
* Un composant `DETAILS` pour spécifier les informations du site web
* Un composant `BUTTON` pour spécifier les informations de l’application

Le composant `SWIPEABLE_MEDIA` doit inclure un tableau `media_keys` dans lequel vous pouvez spécifier entre 2 et 6 images ou vidéos. L’ordre dans lequel les clés de média sont passées détermine l’ordre dans lequel elles seront rendues.

```
{
  "type": "SWIPEABLE_MEDIA",
  "media_keys": [
    "13_1089771253848666112",
    "13_1191948012077092867"
  ]
}
```

Pour rappel, vous pouvez obtenir des clés média en effectuant une requête vers l’endpoint [GET accounts/:account&#95;id/media&#95;library](https://developer.x.com/en/docs/twitter-ads-api/creatives/api-reference/media-library#get-accounts-account-id-media-library).

La composition du deuxième objet de composant dépend de si vous souhaitez rediriger un utilisateur vers un site web ou l’encourager à installer une application. Le tableau ci-dessous résume les deux options. (**Remarque** : toutes les clés répertoriées sont Obligatoires.)

|                            | **Site web**                                                       | **Application**                                   |
| :------------------------- | :----------------------------------------------------------------- | :------------------------------------------------ |
| Specify the component type | `"type": "DETAILS"`                                                | `"type": "BUTTON"`                                |
| Title/Label                | `"title": "X"`                                                     | `"label": { "type": "ENUM", "value": "INSTALL" }` |
| Destination                | `"destination": { "type": "WEBSITE", "url": "https://www.x.com" }` | `"destination": { "type": "APP", ... }`           |

En combinant ces éléments, un exemple de corps de requête POST JSON pour un carrousel de site web est présenté ci-dessous.

```
{
  "name": "website carousel",
  "components": [
    {
      "type": "SWIPEABLE_MEDIA",
      "media_keys": [
        "13_1089771253848666112",
        "13_1191948012077092867"
      ]
    },
    {
      "type": "DETAILS",
      "title": "X",
      "destination": {
        "type": "WEBSITE",
        "url": "https://www.x.com"
      }
    }
  ]
}
```

Les objets de destination d&#39;application dans les composants `BUTTON` nécessitent un code pays et au moins un identifiant d&#39;application. Ils peuvent également accepter des liens profonds (deep links). Pour une description de ces champs, consultez la [documentation de référence](https://developer.x.com/en/docs/twitter-ads-api/creatives/api-reference/cards#app-destination).

En combinant ces éléments, un exemple de corps de requête POST JSON pour un carrousel d&#39;applications est présenté ci-dessous.

```
{
  "name": "app carousel",
  "components": [
    {
      "type": "SWIPEABLE_MEDIA",
      "media_keys": [
        "13_1089771253848666112",
        "13_1191948012077092867"
      ]
    },
    {
      "type": "BUTTON",
      "label": {
        "type": "ENUM",
        "value": "INSTALL"
      },
      "destination": {
        "type": "APP",
        "country_code": "US",
        "googleplay_app_id": "com.twitter.android",
        "iphone_app_id": "333903271"
      }
    }
  ]
}
```

<div id="creative-metadata-tagging">
  ### balisage des métadonnées des créations
</div>

<div id="introduction">
  #### Introduction
</div>

Ce guide s’adresse aux partenaires créatifs, aux agences et aux développeurs créatifs souhaitant baliser les ressources utilisées dans les campagnes X afin de mieux comprendre la valeur et les performances de chaque ressource.

**Remarque :** Les ressources média ne doivent être balisées que par le partenaire ou le développeur qui crée la ressource média. Si l’utilisateur de la ressource média n’a pas créé cette ressource, n’implémentez pas le marquage de métadonnées.

Le marquage des métadonnées créatives permet d’attribuer les images et les vidéos créées par les partenaires créatifs, quel que soit l’endroit où la ressource est mise en ligne sur X ou l’entité qui la met en ligne. Pour établir le lien entre la ressource créative et le partenaire créatif, la norme [XMP](https://exiftool.org/TagNames/XMP.html) est utilisée.

<div id="tagging-creative-assets">
  #### Attribution de balises aux ressources créatives
</div>

Le tableau suivant présente les types d&#39;identifiants actuellement disponibles dans la réponse de chaque ressource liée aux images, ainsi que le ou les noms d&#39;attributs correspondants. Un outil de marquage est nécessaire pour ajouter des balises aux ressources créatives. [ExifTool](https://exiftool.org/), une bibliothèque Perl multiplateforme associée à une [application en ligne de commande](https://exiftool.org/exiftool_pod.html) permettant de lire, d&#39;écrire et de modifier les métadonnées, est recommandé. Consultez tous les [types de fichiers](https://exiftool.org/#supported) pris en charge.

Suivez les [instructions d&#39;installation d&#39;ExifTool](https://exiftool.org/install.html). Il existe également des paquets logiciels proposés par [Homebrew](https://formulae.brew.sh/) pour simplifier davantage l&#39;installation en fournissant la [commande d&#39;installation d&#39;exiftool](https://formulae.brew.sh/formula/exiftool) pour macOS et Linux. Vérifiez que votre outil est correctement installé en entrant exiftool -ver dans la ligne de commande afin d&#39;afficher le numéro de version de l&#39;outil. Pour en savoir plus sur les paramètres de commande ExifTool, consultez la [documentation ExifTool](https://exiftool.org/).

Les partenaires créatifs peuvent attribuer des balises de métadonnées à de nouvelles ressources créatives ou à des ressources existantes en renseignant leur X app&#95;id dans la balise XMP contributor, ainsi qu&#39;une balise date. Les ressources créatives respecteront les limites de taille existantes lors du [téléversement de médias](https://developer.x.com/en/docs/twitter-api/v1/media/upload-media/overview). 

**Remarque :** l&#39;utilisation par X de la balise XMP contributor garantit que les métadonnées capturent des valeurs exclusivement pour les campagnes sur X.

`exiftool -contributor="<YOUR APP ID>" -creative_file.jpg`

`exiftool -date="<date>" -creative_file.jpg`

L&#39;app&#95;id peut être consulté dans la [Developer Console](https://developer.x.com/en/portal/dashboard) sous Projects &amp; Apps. Exemple : 16489123

L&#39;exemple suivant ajoute app&#95;id comme balise contributor et date comme balise date pour une image :

```

```

```

```

```

```

```

```

<div id="parameters">

</div>

Le corps de la requête POST au format JSON doit inclure un champ de carte `name` et un tableau `components`. Les composants sont représentés sous forme d’objets et décrivent les attributs de la carte visibles par l’annonceur.

L’exemple suivant montre la structure générale de la charge utile (mais inclut des informations non valides).

```
{
  "name": "some name",
  "components": [

      "type": "TYPE_ENUM",
      "key": "value"
    }
  ]
}
```

| Nom                                | Description                                                                                                                                                                                                                                                                                                                                                                                                               |
| :--------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| account&#95;id   *Obligatoire*     | L’identifiant du compte utilisé. Apparaît dans le chemin de la ressource et est généralement un paramètre obligatoire pour toutes les requêtes de l’API Advertiser, à l’exception de [GET accounts](https://developer.x.com/en/docs/ads/campaign-management/api-reference/accounts#get-accounts). Ne peut pas être spécifié avec `slides`.  **Remarque** : l’ordre des composants est important.  Type : tableau d’objets                                                                                                                                                                                                   |
| slides   *Parfois obligatoire*     | Utilisez ce tableau de tableaux pour créer des carrousels multi-destinations.  Décrit chaque carte comme un regroupement de composants. <div id="components">
  #### Composants
</div>

Chaque composant doit inclure un champ `type` qui détermine le schéma de l&#39;objet. L&#39;Ads API prend en charge les types de composants suivants, regroupés en composants basés sur les médias et sur la description.

* Médias :
* `MEDIA` : une seule vidéo ou image
* `SWIPEABLE_MEDIA` : entre 2 et 6 vidéos ou images
* Description :
* `DETAILS`
* `BUTTON`

Chaque composant possède un ensemble de champs obligatoires (en plus de la clé `type`). Ceux-ci sont répertoriés dans le tableau suivant.

| Component `type`  | Champ                   | Type de valeur                   |
| :---------------- | :---------------------- | :------------------------------- |
| `MEDIA`           | `media_key`             | chaîne de caractères             |
| `SWIPEABLE_MEDIA` | `media_keys`            | tableau de chaînes de caractères |
| `DETAILS`         | `title`   `destination` | chaîne de caractères   objet     |
| `BUTTON`          | `label`   `destination` | objet   objet                    |

Voici un exemple de composant `BUTTON` dans le contexte du tableau `components` (en omettant intentionnellement la clé `name`). (Les points de suspension indiquent les endroits où davantage d&#39;informations doivent être précisées.)

```
{
  "components": [
    {
      "type": "BUTTON",
      "label": {
        ...
      },
      "destination": {
        ...
      }
    }
  ]
}
```

L’ordre dans lequel les objets composants sont spécifiés définit l’ordre d’affichage de haut en bas. Les Cards doivent être créées à l’aide d’un composant basé sur un média et d’un composant `DETAILS` ou `BUTTON`. Les composants basés sur une description sont rendus sous le média et ont des destinations associées, soit des URL, soit des applications mobiles.

**Label**

Les labels définissent le texte affiché sur les boutons et, par conséquent, ne s’appliquent qu’au composant `BUTTON`. Les objets label comportent deux clés obligatoires : `type` et `value`. Le `type` doit être défini sur `ENUM` et la `value` peut être l’une des valeurs suivantes : `BOOK`, `CONNECT`, `INSTALL`, `OPEN`, `ORDER`, `PLAY` ou `SHOP`.

En s’appuyant sur l’exemple précédent, l’exemple suivant illustre l’objet `label` au sein du composant `BUTTON`.

```
{
  "components": [
    {
      "type": "BUTTON",
      "label": {
        "type": "ENUM",
        "value": "INSTALL"
      },
      "destination": {
        ...
      }
    }
  ]
}
```

**Destination**

Les destinations sont les emplacements vers lesquels les annonceurs souhaitent diriger les utilisateurs. Elles sont toujours obligatoires dans les composants `DETAILS` ou `BUTTON`. Il existe deux types de destination : `WEBSITE` ou `APP`.

**Remarque** : les destinations de type site web ne peuvent être utilisées qu’avec les composants `DETAILS`, et les destinations de type application ne peuvent être utilisées qu’avec les composants `BUTTON`.

**Destination de type site web**

| Nom                  | Description                                                                                                                                   |
| :------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------- |
| type   *Obligatoire* | Le type de destination, qui détermine son schéma.  Type : enum  Valeurs possibles : `WEBSITE`                                                 |
| url   *Obligatoire*  | L’URL du site web vers lequel rediriger un utilisateur.  Type : chaîne de caractères  Exemple : `https://devcommunity.x.com/c/advertiser-api` |

**Destination de type application**

| Nom                                                          | Description                                                                                                                                                                                                                            |
| :----------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

<div id="post-accountsaccount_idtweet">
  #### POST accounts/:account_id/tweet
</div>

Créez un Tweet pour l&#39;utilisateur promouvable principal (`full promotable user`) du compte (par défaut) ou pour l&#39;utilisateur spécifié dans le paramètre `as_user_id`. La création de Tweets nullcastés (par défaut) et de Tweets organiques est prise en charge. Les Tweets nullcastés n&#39;apparaissent pas dans la timeline publique et ne sont pas diffusés aux abonnés. Les deux types peuvent être utilisés dans des campagnes.

Si l&#39;utilisateur authentifié n&#39;est pas l&#39;utilisateur promouvable `FULL` de ce compte, déterminez s&#39;il a l&#39;autorisation de publier des Tweets en son nom en envoyant une requête au point de terminaison [GET accounts/:account&#95;id/authenticated&#95;user&#95;access](https://developer.x.com/en/docs/ads/campaign-management/api-reference/authenticated-user-access#get-accounts-account-id-authenticated-user-access). Une permission `TWEET_COMPOSER` indique que l&#39;utilisateur peut utiliser ce point de terminaison pour créer des Tweets nullcastés au nom de l&#39;[utilisateur promouvable](https://developer.x.com/en/docs/ads/campaign-management/api-reference/promotable-users#get-accounts-account-id-promotable-users) `FULL`.

Lorsque vous utilisez le point de terminaison [upload.x.com](https://developer.x.com/rest/reference/post/media/upload) pour les médias, transmettez la même valeur `user_id` pour le paramètre `additional_owners` que la valeur `as_user_id` que vous transmettez à ce point de terminaison.

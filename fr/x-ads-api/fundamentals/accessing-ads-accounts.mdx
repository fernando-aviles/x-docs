<div id="user-accounts-vs-ad-accounts">
  # Comptes d’utilisateur vs comptes publicitaires
</div>

Deux types de comptes différents interviennent dans l’utilisation de l’API Ads : les comptes publicitaires et les comptes d’utilisateur X. Dans l’ensemble de la documentation de l’API Ads, le terme « compte » fait généralement référence au compte publicitaire.

* Les comptes publicitaires sont enregistrés sur **business.x.com** et identifiés dans l’API par `account_id`. Les comptes publicitaires sont directement liés aux sources de financement et exploitent le contenu d’un ou de plusieurs comptes d’utilisateur X en tant que « promotable users ». Chaque compte publicitaire peut accorder une autorisation à un ou plusieurs comptes d’utilisateur X. Le compte publicitaire, ou « compte actuel », est représenté dans presque toutes les URL exécutées sous la forme d’un paramètre en ligne `:account_id`.
* Les comptes d’utilisateur X (tels que @AdsAPI) sont identifiés par `user_id` dans l’API Ads. Un ou plusieurs de ces comptes peuvent être associés à un compte publicitaire. Le compte d’utilisateur X authentifié qui effectue les requêtes sur l’API est appelé « utilisateur actuel ». Une liste des comptes publicitaires auxquels l’utilisateur actuel a accès est disponible via [GET accounts](/fr/x-ads-api/campaign-management#accounts). Les « promotable users » sont des handles X (noms d’utilisateur X) qui peuvent être promus par un compte publicitaire spécifique. Pour plus de détails à ce sujet, voir [Obtaining Ads Account Access](/fr/x-ads-api/introduction).

<div id="methods-for-ad-account-access">
  ## Méthodes d’accès au compte publicitaire
</div>

Vous pouvez utiliser deux méthodes pour effectuer des requêtes Ads API pour le compte d’un annonceur :

1. Effectuer des requêtes au nom d’un annonceur (**recommandé**)
2. Effectuer des requêtes en utilisant votre compte qui a reçu l’accès au compte d’un annonceur, par exemple une [agence](https://business.x.com/en/blog/agencies-manage-multiple-Twitter-Ads-accounts.html) gérant plusieurs comptes.

Ce document propose un bref aperçu des différences entre ces options et doit être utilisé conjointement avec nos autres ressources, telles que la [FAQ sur la connexion multi-utilisateurs](https://business.x.com/en/help/troubleshooting/multi-user-login-faq.html). 

Comme décrit dans [Autoriser une requête](/fr/resources/fundamentals/authentication#authorizing-a-request#authorizing-a-request), toutes les requêtes vers l’Ads API nécessitent des en-têtes Authorization utilisant [OAuth 1.0a](/fr/resources/fundamentals/authentication) avec un jeton d’accès obtenu via le flux [3-legged](/fr/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow) [OAuth](/fr/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow). Votre application devra implémenter un flux OAuth basé sur le Web pour [obtenir des jetons d’accès](/fr/resources/fundamentals/authentication#oauth-1-0a-2). Les développeurs Ads API ne doivent jamais demander à nos annonceurs X de partager leurs identifiants de connexion.

Par défaut, chaque [App développeur X](/fr/resources/fundamentals/developer-apps) contient un **jeton d’accès** statique qui peut être utilisé pour effectuer des requêtes Ads API pour le compte propriétaire de l’application. Ces identifiants sont idéaux pour les cas d’usage à compte unique, sans qu’il soit nécessaire d’utiliser un flux OAuth 3-legged ou [basé sur un code PIN](/fr/resources/fundamentals/authentication#pin-based-authorization). Si vous n’accédez pas à un autre compte publicitaire X, utilisez ces identifiants [utilisateur unique](/fr/resources/fundamentals/authentication#oauth-1-0a-2) au lieu des étapes suivantes.

<div id="levels-of-access">
  ## Niveaux d&#39;accès
</div>

<div id="app-level-permissions">
  ### Autorisations au niveau de l’application
</div>

Chaque utilisateur disposera d’un niveau d’accès défini lors de la [demande d’accès à l’Ads API](/fr/x-ads-api/getting-started/step-by-step-guide) :

* **Conversion uniquement** : l’utilisateur a accès aux endpoints [Mobile](/fr/x-ads-api/measurement/mobile-conversions) et [Web Conversion](/fr/x-ads-api/measurement/web-conversions) avec un accès en [lecture et écriture](/fr/resources/fundamentals/developer-apps).
* **Accès standard** : l’utilisateur a accès aux endpoints [Analytics](/fr/x-ads-api/analytics), [Campaign Management](https://developer.x.com/en/docs/twitter-ads-api/campaign-management/overview), [Creatives](https://developer.x.com/en/docs/twitter-ads-api/creatives/overview), [Custom Audiences](https://developer.x.com/en/docs/twitter-ads-api/audiences/overview) et [Conversion](/fr/x-ads-api/measurement/web-conversions), avec un accès en [lecture et écriture](/fr/resources/fundamentals/developer-apps).

**Remarque :** les développeurs Ads API qui ont demandé l’accès avant juillet 2023 peuvent disposer de niveaux d’accès et d’autorisations différents, et peuvent être limités à cinq jetons OAuth. Consultez notre guide sur [l’augmentation des niveaux d’accès](/fr/x-ads-api/getting-started/increasing-access) pour obtenir l’accès à des endpoints supplémentaires ou lever les limites de jetons pour les applications existantes.

<div id="ad-account-level-permissions">
  ### Autorisations au niveau du compte publicitaire
</div>

Chaque utilisateur ayant accès à un compte publicitaire dispose d’une autorisation spécifique au niveau du compte : **Account administrator**, **Ad manager**, **Campaign analyst**, **Organic analyst** et **Creative Manager** ; consultez **business.x.com** pour la documentation la plus récente concernant les autorisations au niveau du compte. Les applications doivent récupérer les autorisations de l’utilisateur actuellement authentifié via le point de terminaison d’API [Authenticated User Access](/fr/x-ads-api/campaign-management#authenticated-user-access) afin de déterminer à quels points de terminaison d’API et à quelles fonctionnalités publicitaires elles peuvent accéder.

**Remarque :** Tous les jetons utilisateur utilisés avec la [Conversion API](/fr/x-ads-api/measurement/web-conversions) doivent appartenir à des utilisateurs disposant des autorisations au niveau du compte **Account administrator** ou **Ad manager**.                                                                                                                                              

<div id="methods-of-obtaining-access-tokens">
  ## Méthodes pour obtenir des jetons d’accès
</div>

<div id="1-obtain-an-advertisers-user-access-token">
  ### 1. Obtenir le jeton d’accès (Utilisateur) d’un annonceur
</div>

Il existe deux méthodes pour obtenir le **jeton d’accès** d’un annonceur. La méthode la plus courante consiste à utiliser un [flux OAuth en 3 étapes](/fr/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow) directement à partir de votre interface Web. Les applications qui n’ont pas d’interface utilisateur publiquement accessible pour les annonceurs peuvent implémenter un processus OAuth [basé sur un code PIN](/fr/resources/fundamentals/authentication#pin-based-authorization). Une fois que l’utilisateur a terminé le flux en 3 étapes, votre application disposera des identifiants nécessaires pour envoyer des requêtes à son compte Ads via l’API.

Obtenir les identifiants utilisateur via un flux OAuth est la méthode que nous **recommandons vivement** à la majorité des développeurs de l’API Ads pour obtenir l’accès à un compte d’annonceur. Cela vous permet d’appeler l’API au nom d’un utilisateur et d’effectuer des actions en tant que cet utilisateur. Ces jetons n’expirent pas, mais peuvent être révoqués par l’utilisateur à tout moment.

<div id="2-obtain-your-developer-access-token">
  ### 2. Obtenir votre jeton d’accès (Developer)
</div>

Cette option nécessite que l’annonceur [accorde à votre @username](https://business.x.com/en/help/troubleshooting/multi-user-login-faq.html) (ou à vos @usernames) l’accès à son compte X Ads via l’interface X sur business.x.com. Les **jetons d’accès** obtenus via le flux OAuth à 3 étapes (3-legged OAuth) pour votre compte pourront accéder au compte X Ads de l’annonceur.

Cela vous permet d’appeler l’API en utilisant les jetons OAuth de votre propre @username plutôt que ceux de l’annonceur. La principale différence avec cette option est que vous ne pouvez créer des Publications « Promoted-Only » que si l’autorisation de délégation/de composition de Publication a été accordée à votre @username.

Pour obtenir l’accès nécessaire afin de créer des Publications « Promoted-Only » pour l’utilisateur promouvable de type `FULL` sur le compte, il doit également vous être accordé l’accès à la création de Publications dans ce flux. Cela activera l’accès via la permission `TWEET_COMPOSER` sur le point de terminaison [GET accounts/:account&#95;id/authenticated&#95;user&#95;access](/fr/x-ads-api/campaign-management#accounts).

<div id="differences-between-these-methods">
  ## Différences entre ces méthodes
</div>

|     |     |     |
| :--- | :--- | :--- |
|     | Jeton OAuth annonceur (utilisateur) | Jeton OAuth (développeur)  <br /> (@username ajouté pour distinguer le compte) |
| Accéder au compte publicitaire | ✔   | ✔   |
| Créer des Publications pour le compte de l’utilisateur | ✔   | ✔*  |
| Gérer les campagnes | ✔   | ✔   |
| Accéder aux statistiques | ✔   | ✔   |
| Créer des Cards pour le compte de l’utilisateur | ✔   | ✔   |
| Possibilité pour le développeur d’accéder  <br />depuis l’interface X Ads |     | ✔   |
| [Limites de débit](/fr/x-api/enterprise-gnip-2.0/fundamentals/rate-limits) | Distinctes pour chaque annonceur | Distinctes pour chaque compte annonceur |

## Introduction

Les indicateurs analytiques aident les partenaires et les annonceurs à comprendre les performances du contenu qu’ils diffusent sur X. Cela inclut des informations telles que les impressions, les clics, les vues vidéo et les dépenses. De plus, les partenaires et les annonceurs peuvent obtenir des indicateurs détaillés pour différents segments des audiences qu’ils atteignent.

L’Ads API prend en charge deux méthodes pour récupérer des indicateurs détaillés de performance de campagne : de manière synchrone et de manière asynchrone. Avec les appels analytiques synchrones, les indicateurs demandés sont renvoyés dans la réponse. Avec les endpoints analytiques asynchrones, les indicateurs demandés sont disponibles dans un fichier de résultats téléchargeable une fois que la « tâche » associée a terminé son traitement. L’endpoint synchrone prend en charge de courtes plages temporelles et est idéal pour les optimisations de campagnes en temps réel. Les endpoints asynchrones prennent en charge des plages temporelles beaucoup plus longues et sont donc conçus pour récupérer un volume de données bien plus important, ce qui est idéal pour générer des rapports ou reconstituer des historiques (backfills).

<div id="synchronous-vs-asynchronous">
  ### Synchrones vs asynchrones
</div>

Les différences entre les endpoints d’analytics synchrones et asynchrones sont résumées dans le tableau suivant. Ces informations sont destinées à aider les développeurs à choisir quels endpoints utiliser.

| Feature | Synchronous | Asynchronous |
|:---------|:------------|:--------------|
| Rate limiting | Niveau utilisateur : 250 requêtes / 15 minutes | Niveau compte : 100 tâches* simultanées |
| Time range | 7 jours | 90 jours (non segmenté)<br />45 jours (segmenté) |
| Segmentation | Non | Oui |
| Response returns | Données de métriques | État de traitement de la tâche** |
| Recommended use case | Optimisation en temps réel<br />Requêtes de l’interface utilisateur | Synchronisation planifiée récurrente<br />Compléter les données historiques |

<Note>
  * Ceci fait référence au nombre maximal de tâches pouvant être en cours de traitement à un moment donné.

  ** Une fois que la tâche a terminé son traitement avec succès, une URL est renvoyée. C’est à cette adresse que le fichier de résultats compressé (gzip) peut être téléchargé.

  En dehors de cela, les endpoints offrent les mêmes fonctionnalités.
</Note>

<div id="use-cases">
  ### Cas d’utilisation
</div>

Il existe trois principaux cas d’utilisation pour l’analytique.

1. Optimisation en temps réel : utiliser les métriques de performance pour mettre à jour des campagnes actives
2. Synchronisation : synchronisations régulières planifiées en arrière-plan
3. Intégration de nouveaux comptes : rétro-remplissage des données historiques

L’endpoint analytique synchrone peut être utilisé pour l’optimisation en temps réel afin de mettre à jour des campagnes en fonction des changements de métriques survenus au cours des 5 à 15 dernières minutes. L’un ou l’autre endpoint peut être utilisé pour la synchronisation analytique. Gardez à l’esprit que l’intervalle de temps souhaité et le fait de savoir si une segmentation est requise détermineront quel endpoint utiliser. L’intégration de nouveaux comptes doit uniquement être effectuée à l’aide des endpoints analytiques asynchrones. (L’endpoint analytique synchrone ne doit jamais être utilisé pour récupérer de grandes quantités de données.)

Les endpoints analytiques asynchrones peuvent alimenter des tableaux de bord et d’autres éléments d’interface utilisateur si les métriques sont synchronisées via un processus back-end. Votre implémentation doit éviter d’appeler les endpoints analytiques asynchrones pour répondre aux requêtes de l’interface utilisateur.

<div id="request-options">
  ### Options de requête
</div>

Les requêtes d’analyses sont limitées aux comptes publicitaires et nécessitent donc l’identifiant du compte dans le chemin de la ressource. Les options de requête, listées ci-dessous, sont spécifiées sous forme de paramètres de requête. Les types de valeurs suivants sont obligatoires.

* Entités : le type d’entité ainsi que jusqu’à 20 identifiants d’entité pour lesquels vous souhaitez demander des analyses
* Plage temporelle : les heures de début et de fin, exprimées au format ISO 8601
  * **Remarque :** doivent être exprimées en heures pleines
* Groupes de métriques : un ou plusieurs ensembles de métriques liées (voir Metrics and Segmentation pour une liste des métriques dans chaque groupe de métriques)
* Granularité : spécifie le niveau d’agrégation auquel les métriques doivent être renvoyées
* Emplacement : détermine si les métriques sont extraites pour les annonces diffusées sur X ou en dehors de X
  * **Remarque :** une seule valeur d’emplacement peut être spécifiée par requête

Utilisez les paramètres de requête `start_time` et `end_time` pour spécifier une plage temporelle. Ces valeurs doivent être alignées avec la granularité spécifiée de la manière suivante.

1. `TOTAL` : spécifiez n’importe quelle plage temporelle (dans les limites du point de terminaison)
2. `DAY` : les valeurs d’heure de début et de fin doivent toutes deux être alignées sur minuit dans le fuseau horaire du compte
3. `HOUR` : spécifiez n’importe quelle plage temporelle (dans les limites du point de terminaison)

L’heure de fin est exclusive. Par exemple, une requête avec `start_time=2019-01-01T00:00:00Z` et `end_time=2019-01-02T00:00:00Z` renverra une seule journée de métriques d’analyses (et non deux), car cette plage temporelle ne couvre qu’une période de 24 heures.

**Segmentation**

Disponible uniquement via nos points de terminaison d’analyses asynchrones, la segmentation permet aux partenaires et aux annonceurs de récupérer des métriques ventilées par certaines valeurs de ciblage spécifiques. Pour demander des métriques segmentées, utilisez le paramètre de requête `segmentation_type`. Pour plus de détails sur les options de segmentation, consultez [Metrics and Segmentation](/fr/x-ads-api/analytics#metrics-and-segmentation).

<div id="faqs">
  ## FAQs
</div>

Pourquoi les chiffres de l&#39;Ads API ne correspondent-ils pas à ceux affichés dans l&#39;interface X Ads ?

* Assurez-vous d&#39;avoir demandé des données pour les deux emplacements : `ALL_ON_TWITTER` et `PUBLISHER_NETWORK`, `SPOTLIGHT` et `TREND`.
* N&#39;oubliez pas que les heures de fin dans l&#39;Ads API sont exclusives ; elles sont inclusives dans l&#39;interface Ads.

Pourquoi les chiffres changent-ils selon le moment où je demande les données ?

* Dès que les métriques de reporting sont disponibles, vous pouvez les récupérer. Elles sont disponibles en quasi temps réel. Cependant, ces premiers résultats sont des estimations et sont donc susceptibles de changer. Les métriques sont finalisées après 24 heures, à l&#39;exception des données de dépenses.
* Les métriques de dépenses sont généralement définitives dans les 3 jours suivant l&#39;événement. Cependant, nous traitons les données de facturation jusqu&#39;à 14 jours après la date de l&#39;événement (pour le filtrage du spam, par exemple).

Comment puis-je déterminer quels id d&#39;entités demander pour une période spécifique ?

* Utilisez l&#39;[endpoint Active Entities](/fr/x-ads-api/analytics#active-entities-2)

Pourquoi toutes les valeurs de la réponse analytics sont-elles `null` ?

* Il est probable que la campagne n&#39;ait pas diffusé pendant la période demandée.
* Utilisez l&#39;[endpoint Active Entities](/fr/x-ads-api/analytics#active-entities-2) pour déterminer pour quelles entités et pour quelle période récupérer les analytics.

Pourquoi l&#39;API affiche-t-elle des valeurs `null` alors que l&#39;interface affiche des 0 ?

* L&#39;interface choisit d&#39;afficher ces valeurs sous forme de 0, mais les valeurs sont équivalentes.

Comment puis-je demander des métriques associées à un emplacement granulaire, comme la timeline X ?

* Nous prenons en charge les valeurs d&#39;emplacement suivantes dans les analytics : `ALL_ON_TWITTER` et `PUBLISHER_NETWORK`, `SPOTLIGHT` et `TREND` (c&#39;est-à-dire la [X Audience Platform](/fr/x-ads-api/audiences)).

Est-il possible de récupérer des métriques pour des entités supprimées ou en pause ?

* Oui. Le statut de l&#39;entité n&#39;affecte pas la disponibilité des métriques analytics.

Pourquoi les valeurs segmentées ne correspondent-elles pas aux valeurs non segmentées ?

* Il n&#39;est *pas* attendu que les données segmentées représentent 100 % des données non segmentées, en raison de la façon dont ces informations sont dérivées.

Est-il possible de demander des données segmentées selon plusieurs dimensions ?

* Nous ne prenons pas en charge la segmentation multiple.

<div id="best-practices">
  ## Bonnes pratiques
</div>

Quelques bonnes pratiques pour collecter des données d&#39;[analytics](/fr/x-ads-api/analytics) via l&#39;Ads API.

<div id="rate-limiting-and-retries">
  ### Limitation de débit et nouvelles tentatives
</div>

* Pour les requêtes soumises à une limitation de débit (celles qui renvoient un code d’état `HTTP 429`), vous devez inspecter l’en-tête `x-rate-limit-reset` et ne réessayer qu’au moment indiqué ou après.
* Pour les requêtes qui renvoient un code d’état HTTP 503 Service Unavailable, vous devez inspecter l’en-tête `retry-after` et ne réessayer qu’après le moment indiqué.
* Les applications qui ne respectent pas les délais de nouvelle tentative indiqués peuvent voir leur accès à l’Ads API révoqué ou limité sans préavis.

<div id="analytics-metrics-in-a-nutshell">
  ### Les métriques Analytics en bref
</div>

* Toutes les métriques Analytics sont figées et ne changent plus après 24 heures, à l’exception de `billed_charge_local_micro`.
* La métrique `billed_charge_local_micro` est une estimation pendant une durée maximale de 3 jours après le renvoi des données.
* Après 24 heures, cette métrique peut diminuer en raison de crédits pour dépassement de budget (publicités diffusées après le `end_time` indiqué) et pour des événements facturables ultérieurement considérés comme non valides. Cette métrique évolue très peu après 24 heures.
* Veuillez consulter la page [Analytics](/fr/x-ads-api/analytics) pour plus d’informations.

<div id="fetching-real-time-non-segmented-data">
  ### Récupération de données en temps réel non segmentées
</div>

* Indiquez toujours à la fois un `start_time` et un `end_time`.
* Ne récupérez pas de données pour des entités antérieures à plus de 7 jours.
* Demandez (idéalement) les données avec la granularité `HOUR`, car vous pouvez toujours agréger et regrouper les métriques pour obtenir une granularité `DAY` et `TOTAL`.
* Demandez (idéalement) les données au niveau `line_items` et `promoted_tweets`, car vous pouvez toujours agréger et regrouper ces métriques pour obtenir des totaux sur l’ensemble de la hiérarchie des entités publicitaires (c.-à-d. aux niveaux de la campagne, de l’instrument de financement ou du compte).
* Enregistrez et conservez localement les valeurs des métriques d’analytics de votre côté.
* Ne redemandez pas à plusieurs reprises des données âgées de plus de 30 jours. Ces données ne changeront pas et doivent être stockées localement.
* Toutes les données non segmentées sont en temps réel et doivent être disponibles quelques secondes après la survenue d’un événement.
* Regroupez les métriques de conversion et les métriques non liées aux conversions dans des requêtes distinctes.

<div id="fetching-segmented-data">
  ### Récupération de données segmentées
</div>

* Consultez les recommandations fournies ci-dessus pour « Récupération de données en temps réel non segmentées ». Des conseils supplémentaires sont fournis ci-dessous.
* Pour la plupart des types de données segmentées, il est possible que les données restent incomplètes pendant une durée allant jusqu’à 1 heure. Les données segmentées par `INTERESTS` peuvent être retardées jusqu’à 12 heures.
* Les données segmentées ne devraient pas totaliser exactement 100 % des données non segmentées, en raison de la manière dont ces informations sont dérivées.

<div id="fetching-historical-data">
  ### Récupération de données historiques
</div>

* Lors du backfill de données (par exemple lors de l’ajout d’un nouveau compte annonceur), vous devrez peut-être effectuer plusieurs requêtes en tranches de temps plus petites définies par `start_time` et `end_time`.
* Limitez vos extractions à des fenêtres temporelles de 30 jours.
* Régulez ces requêtes et étalez-les dans le temps afin de ne pas épuiser vos limites de débit pour ces extractions.

<div id="active-entities">
  ### Entités actives
</div>

<div id="introduction">
  #### Introduction
</div>

L’[endpoint Active Entities](/fr/x-ads-api/analytics#get-stats-accounts-account-id-active-entities) est conçu pour être utilisé conjointement avec nos endpoints d’analyse [synchrones](/fr/x-ads-api/analytics#get-stats-accounts-account-id) et [asynchrones](/fr/x-ads-api/analytics#asynchronous-analytics), car il fournit des informations sur les campagnes pour lesquelles vous devez demander des analyses. Pour ce faire, il renvoie des détails sur les entités publicitaires et sur le moment où leurs métriques ont changé. L’utilisation de cet endpoint simplifiera considérablement votre code et votre logique de récupération des données d’analyse.

Ce guide inclut des informations et du contexte sur l’endpoint et sa source de données. Il fournit également des [directives d’utilisation](#usage) et une série d’[exemples de requêtes](#example), qui montrent comment utiliser Active Entities conjointement avec nos endpoints d’analyse. La [section Résumé](#summary) fournit une description de haut niveau de l’approche recommandée.

<div id="data">
  #### Données
</div>

Chaque fois qu&#39;une métrique d&#39;entité publicitaire change, nous enregistrons des informations sur ce changement. Ces événements de modification sont stockés dans des tranches horaires et incluent des détails sur l&#39;entité ainsi que sur le moment auquel la modification s&#39;applique. Ce dernier point est important, car les événements de modification ne correspondent pas toujours au moment où ils ont été enregistrés. Les ajustements de facturation en sont une raison fréquente, parmi d&#39;autres.

<div id="endpoint">
  #### Endpoint
</div>

<div id="request">
  ### Requête
</div>

Les requêtes Active Entities sont limitées aux comptes publicitaires et comportent trois paramètres de requête obligatoires : `entity`, `start_time` et `end_time`.

`twurl -H ads-api.x.com "/11/stats/accounts/18ce54d4x5t/active_entities?entity=PROMOTED_TWEET&start_time=2019-03-05T00:00:00Z&end_time=2019-03-06T00:00:00Z"`

Les valeurs `entity` suivantes sont prises en charge : `CAMPAIGN`, `FUNDING_INSTRUMENT`, `LINE_ITEM`, `MEDIA_CREATIVE`, `PROMOTED_ACCOUNT` et `PROMOTED_TWEET`. Cela reflète les types d’entités pris en charge par nos endpoints d’analytics.

Les valeurs `start_time` et `end_time` doivent être exprimées au format [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) et spécifier quels créneaux horaires d’une heure interroger. Elles doivent obligatoirement être exprimées en heures pleines.

Cet endpoint prend également en charge trois paramètres optionnels qui peuvent être utilisés pour filtrer les résultats : `funding_instrument_ids`, `campaign_ids` et `line_item_ids`. Ceux-ci fonctionnent à tous les niveaux de la hiérarchie des publicités et avec n’importe quel type d’`entity` spécifié.

<div id="response">
  ### Réponse
</div>

Voici la réponse Active Entities pour la requête ci-dessus.

```json
    {
      "request": {
        "params": {
          "account_id": "18ce54d4x5t",
          "entity": "PROMOTED_TWEET",
          "start_time": "2019-03-05T00:00:00Z",
          "end_time": "2019-03-06T00:00:00Z"
        }
      },
      "data": [
        {
          "entity_id": "2r0wxw",
          "activity_start_time": "2019-03-04T20:55:20Z",
          "activity_end_time": "2019-03-05T03:43:56Z",
          "placements": [
            "ALL_ON_TWITTER"
          ]
        },
        {
          "entity_id": "2r30fn",
          "activity_start_time": "2019-03-05T08:11:08Z",
          "activity_end_time": "2019-03-05T14:40:59Z",
          "placements": [
            "ALL_ON_TWITTER",
            "PUBLISHER_NETWORK"
          ]
        }
      ]
    }
```

Le tableau `data` contient un objet pour chaque entité devant être incluse dans une requête d’analytics ultérieure. Vous ne devez pas demander d’analytics pour des id en dehors de cet ensemble.

Chaque objet comprend quatre champs : `entity_id`, `activity_start_time`, `activity_end_time` et `placements`. Les heures de début et de fin d’activité représentent l’intervalle de temps auquel s’appliquent les événements de modification de l’entité associée et déterminent donc les dates qui doivent être spécifiées dans les requêtes d’analytics ultérieures. Le tableau `placements` peut inclure les valeurs suivantes : `ALL_ON_TWITTER`, `PUBLISHER_NETWORK`, `SPOTLIGHT` et `TREND`. Il indique quels emplacements doivent être demandés pour l’id d’entité donné.

<div id="usage">
  #### Utilisation
</div>

L’endpoint Active Entities doit déterminer la manière dont les requêtes d’analytics sont effectuées. Les directives d’utilisation suivantes sont rédigées pour prendre en charge la synchronisation des analytics, afin de permettre aux partenaires de garder leurs magasins de données synchronisés avec Twitter. En d’autres termes, elles décrivent comment effectuer des synchronisations planifiées en arrière-plan.

Un développeur doit prendre deux décisions.

1. À quelle fréquence demander les informations sur les entités actives et, par conséquent, à quelle fréquence extraire les analytics.
2. Comment utiliser les heures de début et de fin d’activité pour déterminer les valeurs `start_time` et `end_time` de la requête d’analytics.

Ces points sont abordés plus en détail dans chacune des deux sous-sections ci-dessous, après le résumé.

<div id="summary">
  ### Résumé
</div>

Utilisez l&#39;endpoint Active Entities de la manière suivante pour déterminer comment les requêtes d&#39;analyse sont effectuées. Suivez cette procédure après avoir décidé de la fréquence à laquelle vous demandez les informations sur les entités actives et, par conséquent, de la fréquence à laquelle vous récupérez les données d&#39;analyse.

1. Effectuez la requête Active Entities.
2. Divisez la réponse par emplacement. Un groupe pour `ALL_ON_TWITTER`, un pour `PUBLISHER_NETWORK`, un pour `SPOTLIGHT`, et un pour `TREND`.
3. Pour chaque groupe d&#39;emplacement, procédez comme suit.
   1. Extrayez les id d&#39;entité.
   2. Déterminez les valeurs `start_time` et `end_time` pour l&#39;analyse.
      * Trouvez la valeur minimale de `activity_start_time`. Arrondissez cette valeur à la valeur inférieure la plus proche.
      * Trouvez la valeur maximale de `activity_end_time`. Arrondissez cette valeur à la valeur supérieure la plus proche.
   3. Effectuez la ou les requêtes d&#39;analyse.
      * Regroupez les id d&#39;entité par lots de 20.
      * Utilisez les valeurs `start_time` et `end_time` de l&#39;étape 3b.
      * Indiquez la valeur de `placement` appropriée.
   4. Écrivez dans votre système de stockage de données.

Veuillez consulter [active&#95;entities.py](https://github.com/xdevplatform/twitter-python-ads-sdk/blob/master/examples/active_entities.py) pour un exemple utilisant le SDK Python.

<div id="frequency">
  ### Fréquence
</div>

La réponse à la première question détermine l’intervalle de temps qui doit être utilisé dans les requêtes Active Entities. Par exemple, si vous demandez les informations d’entités actives toutes les heures, l’intervalle de temps doit être d’une heure. Si vous demandez les informations d’entités actives une fois par jour, l’intervalle de temps doit être d’une journée. En d’autres termes, les intervalles de temps doivent être choisis de sorte que le `start_time` de la requête en cours soit égal au `end_time` de la requête précédente.

<Note>
  **Remarque** : Une fenêtre temporelle ne doit être demandée qu’une seule fois. Demander une fenêtre temporelle plus d’une fois entraînera des requêtes d’analyses inutiles. (Exception ci‑dessous.)
</Note>

Pour les partenaires souhaitant demander des données analytiques plusieurs fois par heure pour l’heure *en cours*, le même principe s’applique : la fréquence détermine l’intervalle de temps. Le tableau ci‑dessous présente des exemples d’horodatages de début et de fin Active Entities pour ce scénario.

|     |     |     |
| :--- | :--- | :--- |
| **Heure de la requête** | **Horodatage `start_time`** | **Horodatage `end_time`** |
| 00:15:00 | 00:00:00 | 00:15:00 |
| 00:30:00 | 00:15:00 | 00:30:00 |
| 00:45:00 | 00:30:00 | 00:45:00 |
| 01:00:00 | 00:45:00 | 01:00:00 |

Étant donné la manière dont les événements de modification sont stockés, les quatre requêtes Active Entities ci‑dessus interrogent toutes le même segment horaire, ce qui est nécessaire pour ce cas d’utilisation. Cependant, après l’heure en cours, ce segment horaire ne doit plus être interrogé.

<div id="activity-times">
  ### Heures d&#39;activité
</div>

Nous recommandons l&#39;approche suivante pour travailler avec les heures de début et de fin d&#39;activité. Dans tous les objets de la réponse Active Entities, trouvez le minimum de `activity_start_time` et le maximum de `activity_end_time`. Modifiez ces valeurs en arrondissant l&#39;heure de début d&#39;activité minimale à la baisse et l&#39;heure de fin d&#39;activité maximale à la hausse. Plus précisément, définissez les horodatages en mettant les heures, minutes et secondes à zéro pour les deux, puis ajoutez un jour à l&#39;heure de fin, comme illustré dans le tableau suivant. Ce sont les heures de début et de fin qui doivent être spécifiées dans les requêtes d’analytics ultérieures.

|     |     |
| :--- | :--- |
| **Heures d&#39;activité min, max** | **Heures dérivées** |
| 2019-03-04T20:55:20Z  <br />  <br />2019-03-05T14:40:59Z | 2019-03-04T00:00:00Z  <br />  <br />2019-03-06T00:00:00Z |

**Remarque** : Il est important d&#39;inclure les horodatages avec les heures, minutes et secondes définies à zéro. Sinon, si seule la date est transmise, nous supposerons que vous demandez des analytics commençant et se terminant à minuit dans le fuseau horaire du compte publicitaire, ce qui peut ne pas être souhaitable. Par exemple, si l&#39;heure minimale de début d&#39;activité est 2019-02-28T01:30:07Z et que l&#39;horodatage est omis pour un compte publicitaire avec un décalage de -08:00:00, la requête d’analytics ne prendra pas en compte les changements survenus entre 01:30 et 08:00.

Vous pouvez également choisir de demander des analytics uniquement pour la fenêtre temporelle d&#39;activité retournée, sans l&#39;étendre à des jours complets. En utilisant cette approche, les heures de début et de fin dérivées seraient respectivement 2019-03-04T20:00:00Z et 2019-03-05T15:00:00Z. (Notez que ce type d’intervalle n&#39;est pas accepté si vous spécifiez une granularité `DAY` dans la requête d’analytics.)

<div id="asynchronous-analytics">
  ### Analyse asynchrone
</div>

<div id="introduction">
  #### Introduction
</div>

Les endpoints d’analytics asynchrones permettent aux partenaires et aux annonceurs de demander des métriques en envoyant des requêtes de création que le serveur traite de manière asynchrone (nous appelons cela des « jobs » d’analytics asynchrones). Avec cette approche, la connexion du client n’a pas besoin de rester ouverte jusqu’à ce que la requête soit traitée.

Ces endpoints, comme leurs équivalents synchrones, permettent aux partenaires et aux annonceurs de demander des statistiques détaillées sur les performances des campagnes. Ils prennent en charge les demandes de données pour les comptes, les instruments de financement, les campagnes, les line items, les Tweets promus et les créatifs média. La différence entre ceux-ci et l’endpoint synchrone est que les endpoints d’analytics asynchrones prennent en charge des plages de dates plus longues, jusqu’à 90 jours, ainsi que la segmentation. Des informations supplémentaires sur les différences entre les deux sont disponibles sur notre page [Vue d’ensemble des analytics](/fr/x-ads-api/analytics).

Contrairement à nos endpoints synchrones, la limitation de débit est basée sur le nombre de jobs concurrents pour un compte donné. En d’autres termes, elle est basée sur le nombre de jobs pouvant être en cours de traitement à un moment donné. Nous comptabilisons cela au niveau du compte publicitaire.

<div id="usage">
  #### Utilisation
</div>

La récupération des mesures de campagne à l’aide des points de terminaison d’analyses asynchrones est un processus en plusieurs étapes. Elle implique la création d’un job, la vérification de la fin de son traitement et, enfin, le téléchargement des données. Le fichier de données doit être décompressé. Les quatre étapes suivantes sont décrites ci-dessous.

1. Créez le job à l’aide du point de terminaison [POST stats/jobs/accounts/:account&#95;id](/fr/x-ads-api/analytics#asynchronous-analytics).
2. Effectuez des requêtes à intervalles réguliers vers le point de terminaison [GET stats/jobs/accounts/:account&#95;id](/fr/x-ads-api/analytics#asynchronous-analytics) pour déterminer si le job a terminé son traitement.
3. Une fois le traitement du job terminé, téléchargez le fichier de données.
4. Décompressez le fichier de données.

L’objet de réponse renvoyé dans le fichier de données a le même schéma JSON que la réponse du point de terminaison d’analyses synchrones.

Les mesures de campagne segmentées ne sont disponibles qu’au moyen des points de terminaison d’analyses asynchrones. Les mesures de campagne peuvent être ventilées par lieu, genre, centre d’intérêt, mot-clé, et plus encore. Pour obtenir la liste complète des options, consultez la page [Metrics and Segmentation](/fr/x-ads-api/analytics#metrics-and-segmentation). Pour demander des mesures segmentées, utilisez le paramètre de requête `segmentation_type` lors de la création du job.

  #### GET stats/accounts/:account_id/active_entities[](#get-stats-accounts-account-id-active-entities "Permalink to this headline")
</div>

Récupère des informations détaillées sur les entités dont les métriques d’analytics ont changé sur une période donnée.

Cet endpoint doit être utilisé conjointement avec nos endpoints d’analytics. Les résultats de cet endpoint indiquent pour quelles entités publicitaires il faut demander des données d’analytics. Consultez notre [guide Active Entities](/fr/x-ads-api/analytics#active-entities) pour les recommandations d’utilisation.

Les événements de modification sont disponibles dans des tranches horaires.

* Les valeurs `start_time` et `end_time` indiquent quelles tranches horaires interroger.
* Le tableau `data` retourné inclura un objet pour chaque entité devant être incluse dans les requêtes d’analytics ultérieures.
* **IMPORTANT** : Les dates à spécifier dans les requêtes d’analytics ultérieures doivent être déterminées à partir des valeurs `activity_start_time` et `activity_end_time`.
  * Ces valeurs représentent les plages temporelles auxquelles les événements de modification enregistrés *s’appliquent*. Elles sont renvoyées par entité.

**Remarque** : Un intervalle de temps maximal (`end_time` - `start_time`) de 90 jours est autorisé.

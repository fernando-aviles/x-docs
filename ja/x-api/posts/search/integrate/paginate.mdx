<div id="recent-search-pagination">
  ### Recent search のページネーション
</div>

<div id="introduction">
  #### 概要
</div>

検索クエリは通常、1 回の API レスポンスで返せる数より多くの投稿にマッチします。その場合、data は一連の「ページ」に分割されて返されます。ページネーションとは、データセット全体を取得するために、すべてのページを順番にリクエストする方法を指します。

以下は、recent search のページネーションに関する基本的な事項です。

* recent search エンドポイントは、クエリに対して最低 1 ページのレスポンスを返し、追加のページがある場合は JSON レスポンス内に next&#95;token を含めます。一致する投稿を受け取るには、このプロセスを、レスポンスにトークンが含まれなくなるまで繰り返します。

* next&#95;token には有効期限がありません。同じ next&#95;token の値を使って複数回リクエストしても、リクエストしたタイミングに関わらず、同じ結果が返されます。

* 投稿は UTC タイムゾーンで、新しいものから古いものへの逆時系列順で配信されます。これは各ページ内だけでなく、複数ページにまたがる場合にも当てはまります。 
  * 最初のレスポンス内の最初の投稿が、クエリにマッチした中で最も新しい投稿になります。
  * 最後のレスポンス内の最後の投稿が、クエリにマッチした中で最も古い投稿になります。

* max&#95;results リクエストパラメータを使うと、1 回のレスポンスで返される投稿数を設定できます。デフォルトは 10 投稿で、最大は 100 です。 

* すべてのページネーション実装では、レスポンスペイロードから next&#95;token をパースし、それを「次のページ」の検索リクエストに含める必要があります。これらの「次のページ」リクエストの構築方法については、以下を参照してください。
   

recent search エンドポイントは、次の 2 つの基本的な利用パターンをサポートするように設計されています。

* **Get historical（過去データの取得）** - 関心のある期間に投稿された、一致する投稿をリクエストするパターンです。通常は、履歴調査を目的とした一度きりのリクエストになります。検索リクエストでは、start&#95;time と end&#95;time のリクエストパラメータを指定できます。recent search エンドポイントは、クエリにマッチした投稿を、最も新しい投稿から始まる逆時系列順で返します。 

* **Polling（ポーリング）** - 最後に受信した投稿以降に投稿された、一致する投稿をリクエストするパターンです。これらのユースケースは、ほぼリアルタイムの処理を目的とし、関心のある新規投稿を「待ち受ける」頻繁なリクエストが特徴です。recent search エンドポイントは、この「ポーリング」パターンをサポートするために since&#95;id リクエストパラメータを提供しています。投稿 ID を使って範囲を指定しやすくするため、until&#95;id リクエストパラメータも利用できます。
   

次に、履歴モードについて説明します。これは recent search エンドポイントのデフォルトモードであり、ページネーションの基本を示すものです。その後、ポーリングユースケースの例について説明します。ポーリングでページネーションが発生する場合、検索リクエストを管理するための追加ステップが必要になります。
 

<div id="retrieving-historical-data">
  #### 履歴データの取得
</div>

このセクションでは、start&#95;time と end&#95;time リクエストパラメータを使用して、関心のある期間（現在は直近 7 日間に限定）から投稿を取得する方法の概要を説明します。過去データに対するリクエストは、一般的に調査や分析を目的とした一度きりのリクエストになります。 

期間を指定してデータを取得するリクエストは、recent search エンドポイントのデフォルト動作です。search リクエストで start&#95;time、end&#95;time、または since&#95;id リクエストパラメータが指定されていない場合、end&#95;time はデフォルトで「現在」（実際にはクエリ実行時刻の 30 秒前）となり、start&#95;time はデフォルトで 7 日前になります。

エンドポイントは、最も新しい投稿から始まる逆時系列順で、最初の「ページ」の投稿を返します。JSON レスポンスのペイロードには、追加のデータページが存在する場合、next&#95;token も含まれます。ページ数に関わらず、一致する投稿の全セットを収集するには、next&#95;token が返されなくなるまでリクエストを繰り返します。 

例えば、過去 1 週間におけるキーワード snow を含む投稿に対する初回リクエストは次のようになります。

https://api.x.com/2/tweets/search/recent?query=snow

レスポンスには、直近の 10 件の投稿とともに、JSON レスポンス内の次のメタデータ（&quot;meta&quot; 属性）が含まれます。

```
"meta": {
        "newest_id": "1204860593741553664",
        "oldest_id": "1204860580630278147",
        "next_token": "b26v89c19zqg8o3fobd8v73egzbdt3qao235oql",
        "result_count": 10
    }
```

次の 10 件の投稿を取得するには、この next&#95;token を元のリクエストに追加します。リクエストは次のとおりです。

https://api.x.com/2/tweets/search/recent?query=snow&amp;next&#95;token=b26v89c19zqg8o3fobd8v73egzbdt3qao235oql

next&#95;token を探して次回以降のリクエストに含める処理は、すべて（または任意の数の）投稿が収集されるまで、あるいは指定されたリクエスト回数に達するまで繰り返すことができます。ユースケースにおいてデータの完全性（クエリに一致するものをすべて収集すること）が重要であれば、「request.next&#95;token が null になるまで繰り返す」という単純な設計で十分です。

<div id="polling-and-listening-use-cases">
  #### ポーリングおよびリスニングのユースケース
</div>

このセクションでは、`since_id` リクエストパラメータを指定して recent search エンドポイントをポーリングし、直近の投稿を取得する方法を説明します。 

ポーリングのユースケースでは、「新しい関心のある投稿はあるか？」という問い合わせを、継続的かつ高頻度で行います。リクエストを時間に基づいて行う履歴系ユースケースとは異なり、ポーリングのユースケースでは、通常リクエストを投稿 ID に基づいて行います。

ポーリング利用パターンの中核となるのは、すべての新しい投稿には [一意の ID](/ja/resources/fundamentals/x-ids) が割り当てられ、その ID は X プラットフォーム上で一般的に昇順になるように「発行」されるという点です。ある投稿の ID が別の投稿より小さい場合、その投稿の方が先に投稿されたことを意味します。

recent search エンドポイントでは、投稿 ID に基づいて投稿アーカイブをたどることができます。エンドポイントからのレスポンスには、`oldest_id` と `newest_id` の投稿 ID が含まれます。ポーリングモードでは、これまでに受け取った中で最大／最新の ID を `since_id` に設定してリクエストを行います。 

例えば、雪に関する新しい投稿を 5 分ごとに検索しており、最後に受け取った投稿の投稿 ID が 10000 だったとします。ポーリングするタイミングになったとき、リクエストは次のようになります。

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=10000

次に、前回のリクエスト以降に 7 件の投稿が新たに投稿されたとします。これらはすべて 1 つの data 「ページ」に収まるため、`next_token` は存在しません。レスポンスには、最新（最も新しい）の投稿の投稿 ID が含まれます。

```
"meta": {
        "newest_id": "12000",
        "oldest_id": "10005",
        "result_count": 7
    }
```

次のポーリングクエリを行うには、この newest&#95;id の値を使って、次の since&#95;id パラメータを設定します。

`https://api.x.com/2/tweets/search/recent?query=snow&since_id=12000`

利用可能な追加の data があり、next トークンが返される場合は、結果の最初のページに含まれる newest&#95;id の値だけを使用すれば十分です。各ページの data には newest&#95;id と oldest&#95;id の値が含まれますが、次の定期的なポーリングリクエストに必要なのは、最初のページで提供される値だけです。したがって、ポーリング方式を実装している場合や、ID 範囲で投稿を検索している場合、ページネーションロジックはやや複雑になります。 

ここで、新たに一致する投稿が 18 件あるとします。エンドポイントは、この 5 分間の期間から次のページの data をリクエストするための next&#95;token を含む、1 ページ分の完全な data を最初のレスポンスとして返します。また、次のポーリング間隔（5 分後）に必要となる最新の投稿 ID も含まれます。

```
"meta": {
        "newest_id": "13800",
        "oldest_id": "12500",
        "next_token": "fnsih9chihsnkjbvkjbsc",
        "result_count": 10
    }
```

この5分間の期間に条件に一致するすべてのデータを収集するには、前回のリクエストと同じ since&#95;id の値を指定した上で、次回のリクエストで next&#95;token を渡します。

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=12000&amp;next&#95;token=fnsih9chihsnkjbvkjbsc

```
"meta": {
        "newest_id": "12300",
        "oldest_id": "12010",
        "result_count": 8
    }
```

この2回目のレスポンスには残りの8件の投稿が含まれ、next&#95;token は返されません。なお、newest&#95;id の値 (12300) は更新せず、次の since&#95;id リクエストも最初のレスポンスの newest&#95;id の値に基づいて送信します。

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=13800

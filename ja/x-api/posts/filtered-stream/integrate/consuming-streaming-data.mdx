<div id="building-a-client-to-consume-streaming-data">
  ### ストリーミングデータを取り込むクライアントの構築
</div>

ストリーミングエンドポイントを利用する際は、利用効率を最適化するために押さえておくべき一般的なベストプラクティスがいくつかあります。  
 

<div id="client-design">
  #### クライアント設計
</div>

filter stream エンドポイントを使ってソリューションを構築する場合、次のことが可能なクライアントが必要です。

1. filter stream エンドポイントへの HTTPS ストリーミング接続を確立する。
2. filter stream rules エンドポイントへ非同期に POST リクエストを送信し、ストリームのルールを追加および削除する。
3. データボリュームが少ない場合の処理 – ストリーミング接続を維持し、投稿オブジェクトおよびキープアライブ信号を検出する。
4. データボリュームが多い場合の処理 – ストリームの取り込みを、非同期処理による追加処理から分離し、クライアント側のバッファが定期的にフラッシュされるようにする。
5. クライアント側でのボリューム消費のトラッキングを管理する。
6. ストリーム切断を検出し、状況を評価して自動的にストリームへ再接続する。
    

<div id="connecting-to-a-streaming-endpoint">
  #### ストリーミングエンドポイントへの接続
</div>

X API v2 のストリーミングエンドポイントへの接続を確立するということは、非常に長時間にわたって維持される HTTP リクエストを発行し、レスポンスを逐次的に解析することを意味します。概念的には、HTTP 経由で無限に長いファイルをダウンロードしていると捉えることができます。接続が一度確立されると、その接続が開いている限り、X のサーバーは投稿イベントをその接続経由で配信し続けます。
 

<div id="consuming-data">
  #### data の消費
</div>

JSON オブジェクトの各フィールドには順序は保証されず、あらゆる状況で常にすべてのフィールドが存在するとは限らない点に注意してください。同様に、個々のアクティビティはソート済みの順序で配信されるわけではなく、重複したメッセージが届く場合もあります。時間の経過とともに、新しいメッセージタイプが追加され、ストリーム経由で送信される可能性があることも念頭に置いてください。

したがって、クライアントは次の点を許容する必要があります:

* 任意の順序で現れるフィールド
* 予期しないフィールドや欠落しているフィールド
* ソートされていない投稿
* 重複したメッセージ
* いつでもストリームに流れてくる、新しい任意のメッセージタイプ

関連する投稿の data や、要求したフィールドパラメータに加えて、ストリーム接続では次の種類のメッセージが配信される場合があります。この一覧は網羅的ではなく、今後ストリームに新しいオブジェクトが追加される可能性があります。パーサーが予期しないメッセージ形式にも耐性を持つようにしてください。
 

<div id="buffering">
  #### バッファリング
</div>

ストリーミングエンドポイントは、データが利用可能になり次第、可能な限り速く送信するため、多くの場合は非常に大きなボリュームになる可能性があります。X のサーバーがすぐに新しいデータをストリームに書き込めない場合（たとえば、クライアントの読み取りが十分に速くない場合。詳しくは [handling disconnections](/ja/x-api/posts/filtered-stream#what-is-a-disconnection) を参照してください）、クライアントが追いつけるよう、サーバー側でコンテンツをバッファリングします。しかし、このバッファがいっぱいになると、接続を切断するための強制切断が行われ、バッファリングされていた投稿は破棄され、再送されません。詳細については以下を参照してください。

アプリが処理に遅れ始めているタイミングを特定する 1 つの方法は、受信している投稿のタイムスタンプを現在時刻と比較し、その差を時間経過とともに追跡することです。

ストリームの滞留は、パブリックインターネット上で発生し得るレイテンシーや一時的な障害のため完全に排除することはできませんが、アプリを適切に構成することで大部分を防ぐことができます。滞留の発生を最小限に抑えるには、次の点を確認してください。

* クライアントがストリームを十分な速度で読み取っていることを確認します。通常、ストリームを読み取っている最中に本格的な処理を行うべきではありません。ストリームは読み取りに専念し、処理は別のスレッド／プロセス／データストアに渡して非同期に実行してください。
* データセンターの受信帯域幅が、大量の継続的なデータ量だけでなく、はるかに大きなスパイク（例: 通常の 5～10 倍のボリューム）にも対応できる十分な容量を持っていることを確認します。filtered stream の場合、発生するボリュームと、それに応じて必要となる帯域幅は、ルールがどの投稿にマッチするかに完全に依存します。
   

<div id="usage-tracking-and-rule-management">
  #### 使用状況の追跡とルール管理
</div>

ストリームの「通常」のデータ量がどの程度であるべきかについては、開発者ごとに期待値が異なるため、特定の増減率や期間について一般的な推奨値は提供していません。 

ストリームのデータ量を監視し、想定外の変動がないか確認することを検討してください。データ量の減少は、ストリーム切断とは異なる問題の兆候である場合があります。このような状況でも、ストリームは keep-alive シグナルや新しいアクティビティの一部を受信し続けているはずです。しかし、投稿数が大幅に減少した場合には、アプリケーションまたはネットワークへの着信データ量を減少させている要因がないかを調査し、関連する告知がないか [ステータスページ](https://api.twitterstat.us/) を確認してください。

こうした監視を行うには、一定時間内に想定される新規投稿数を追跡するとよいでしょう。ストリームのデータ量が設定したしきい値を大きく下回り、かつ一定時間内に回復しない場合には、アラートや通知が発報されるようにしてください。また、特にフィルタリングされたストリームでルールを変更している場合や、投稿アクティビティがスパイクするイベントが発生した場合には、データ量が大幅に増加していないかも監視した方がよいでしょう。

フィルタリングされたストリーム経由で配信される投稿も、月間の総投稿量にカウントされる点に注意してください。最適化のために、消費量を追跡し、必要に応じて調整する必要があります。ボリュームが多い場合は、各ルールに sample: 演算子を追加し、必要に応じて 100% のマッチングから sample:50 や sample:25 に減らすことを検討してください。 

さらに、アプリ内に、ボリュームがあらかじめ設定したしきい値を超えた際にチームへアラートを送る仕組みを実装することを推奨します。加えて、過剰なデータを取り込んでいるルールを自動的に削除する、あるいは極端な場合にはストリームから完全に切断するなど、他の対策も導入することを検討してください。
 

<div id="responding-to-system-messages">
  #### システムメッセージへの応答
</div>

キープアライブ信号
少なくとも 20 秒ごとに、ストリームはキープアライブ信号（ハートビート）として、開いた接続を通じて \r\n のキャリッジリターンを送信し、クライアントがタイムアウトすることを防ぎます。クライアントアプリケーションは、ストリーム内の \r\n 文字を許容するように実装する必要があります。

クライアントが HTTP ライブラリで適切に読み取りタイムアウトを実装している場合、この期間内にデータが読み取られないときには HTTP プロトコルおよび HTTP ライブラリがイベントを発生させてくれるため、\r\n 文字を明示的に監視する必要はありません。

このイベントは通常、例外がスローされる、または使用している HTTP ライブラリに応じて何らかのイベントが発生する形になります。これらのタイムアウトを検出するために、HTTP メソッドをエラー／イベントハンドラーでラップすることを強く推奨します。タイムアウトが発生した場合、アプリケーションは再接続を試みる必要があります。

エラーメッセージ
v2 ストリーミングエンドポイントは、ストリーム内でエラーメッセージを配信する場合があります。以下に、これらのメッセージの基本的な形式といくつかの例を示します。配信されるメッセージは変更される可能性があり、新しいメッセージが追加される場合があることに注意してください。クライアントアプリケーションは、変更されうるシステムメッセージのペイロードに対しても問題なく動作する必要があります。

エラーメッセージには、問題の解決方法を説明するドキュメントへのリンクが含まれることに注意してください。

メッセージ形式:

```{
	"errors": [{
		"title": "operational-disconnect",
		"disconnect_type": "UpstreamOperationalDisconnect",
		"detail": "This stream has been disconnected upstream for operational reasons.",
		"type": "https://api.x.com/2/problems/operational-disconnect"
	}]
}
```

バッファがいっぱいになったことによる強制切断を示すエラーメッセージは、その原因となったバッファの滞留によって送信自体が妨げられ、クライアントに届かない場合があります。したがって、アプリは再接続を開始するトリガーとしてこれらのメッセージに依存しないでください。

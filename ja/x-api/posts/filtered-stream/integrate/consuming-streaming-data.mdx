<div id="building-a-client-to-consume-streaming-data">
  ### ストリーミングデータを取得するクライアントの構築
</div>

ストリーミングエンドポイントを使用する場合、効率的に利用するために考慮すべき一般的なベストプラクティスがいくつかあります。  
 

<div id="client-design">
  #### クライアント設計
</div>

filter stream エンドポイントを使用してソリューションを構築する場合、次のことが可能なクライアントが必要です。

1. filter stream エンドポイントへの HTTPS ストリーミング接続を確立する。
2. filter stream rules エンドポイントに POST リクエストを非同期で送信し、ストリームからルールを追加および削除する。
3. 少量のデータを処理する – ストリーミング接続を維持し、投稿オブジェクトとキープアライブ信号を検出する。
4. 大量のデータを処理する – 非同期プロセスを使用して、ストリームの取り込み処理を追加処理から分離し、クライアント側バッファーが定期的にフラッシュされるようにする。
5. クライアント側でデータ量の消費状況を管理・追跡する。
6. ストリーム切断を検出し、状況を評価してストリームに自動的に再接続する。
    

<div id="connecting-to-a-streaming-endpoint">
  #### ストリーミングエンドポイントへの接続
</div>

X API v2 のストリーミングエンドポイントへの接続を確立するということは、非常に長時間にわたって維持される HTTP リクエストを送信し、そのレスポンスを逐次的に解析することを意味します。イメージとしては、HTTP 経由で終わりのないファイルをダウンロードしているようなものだと考えることができます。一度接続が確立されると、接続が開いているかぎり、X のサーバーはその接続を通じて投稿イベントを配信し続けます。
 

<div id="consuming-data">
  #### data の取り込み
</div>

JSON オブジェクトの個々のフィールドには順序がなく、また、あらゆる状況で必ずしもすべてのフィールドが存在するわけではない点に注意してください。同様に、個々のアクティビティは順序付きで配信されるとは限らず、重複したメッセージに遭遇する可能性もあります。時間の経過とともに、新しいメッセージタイプが追加され、ストリームを通じて送信される可能性があることも念頭に置いてください。

したがって、クライアントは次の点に対応できる必要があります。

* 任意の順序で出現しうるフィールド
* 予期しない、あるいは欠落しているフィールド
* 順不同の投稿
* 重複したメッセージ
* いつでもストリームに流れてくる新しい任意のメッセージタイプ

関連する投稿データおよびリクエストしたフィールドパラメータに加えて、ストリーム接続では次の種類のメッセージが配信される場合があります。この一覧は網羅的ではなく、ストリームに追加のオブジェクトが導入される可能性がある点に注意してください。パーサーが予期しないメッセージ形式にも対応できるようにしてください。
 

<div id="buffering">
  #### バッファリング
</div>

ストリーミングエンドポイントは、データが利用可能になり次第すぐに送信するため、多くの場合、非常に大量のデータが流れる可能性があります。X のサーバーがすぐに新しいデータをストリームへ書き込めない場合（たとえば、クライアントの読み取り速度が十分でない場合。詳しくは [handling disconnections](/ja/x-api/posts/filtered-stream#what-is-a-disconnection) を参照）、クライアントが追いつけるよう、サーバー側でコンテンツをバッファリングします。ただし、このバッファがいっぱいになると、接続を切断するための強制切断が行われ、それまでにバッファリングされていた投稿は破棄され、再送されません。詳細は以下を参照してください。

アプリケーションが処理に遅れ始めているタイミングを特定する 1 つの方法は、受信している投稿のタイムスタンプと現在時刻を比較し、その差分を継続的に追跡することです。

パブリックインターネット上で発生しうるレイテンシーや一時的な不具合のため、ストリームのバックアップ（滞留）を完全に排除することはできませんが、アプリを適切に構成することで大部分を防ぐことができます。バックアップの発生を最小限に抑えるには、次の点に注意してください。

* クライアントがストリームを十分な速度で読み取っていることを確認してください。通常、ストリームを読み取る処理の中で実際の処理作業を行うべきではありません。ストリームを読み取り、そのアクティビティは別のスレッド／プロセス／データストアに渡して非同期に実行してください。
* データセンターが、大きな連続データ量だけでなく、さらに大きなスパイク（たとえば通常の 5～10 倍のボリューム）にも対応できる十分な受信帯域幅を備えていることを確認してください。Filtered stream の場合、発生するボリュームと、それに対応して必要となる帯域幅は、ルールによってマッチしている投稿に完全に依存します。
   

<div id="usage-tracking-and-rule-management">
  #### 利用状況の追跡とルール管理
</div>

開発者が自分のストリームにとって「通常」のデータ量がどの程度かを把握していることを前提としているため、特定の割合の増減や期間についての一般的な推奨値は設けていません。 

ストリームのデータ量について、予期しない変動がないか監視することを検討してください。データ量の減少は、ストリーム切断とは別の問題の兆候である可能性があります。このような状況では、ストリームは引き続きキープアライブ信号を受信し、おそらく新しいアクティビティデータも受信し続けます。しかし、投稿数が大きく減少した場合は、アプリケーションやネットワークへの入力データ量を減少させている原因がないかを調査し、関連する通知がないか[ステータスページ](https://api.twitterstat.us/)も確認する必要があります。

このような監視を行うには、一定時間内に発生すると想定している新規投稿数を追跡する方法があります。ストリームのデータ量が指定したしきい値を大きく下回り、かつ一定時間内に回復しない場合は、アラートや通知を発するようにすべきです。また、特にフィルタードストリームのルールを変更している最中や、投稿アクティビティが急増するイベントが発生した場合には、データ量の大きな増加も監視したい場合があるでしょう。

フィルタードストリームを通じて配信される投稿は、月間の総投稿量にカウントされる点にも注意が必要です。最適化のために、消費量を追跡し、調整してください。ボリュームが多い場合は、必要に応じて各ルールに sample: 演算子を追加し、100% のマッチングから sample:50 や sample:25 に削減することを検討してください。

さらに、アプリ内で、データ量があらかじめ設定したしきい値を超えた場合にチームへ通知する仕組みを実装することをお勧めします。また、過剰な量のデータを取り込んでいるルールを自動で削除する、あるいは極端な状況ではストリームから完全に切断するなどの対策を導入することも検討してください。
 

<div id="responding-to-system-messages">
  #### システムメッセージへの応答
</div>

キープアライブシグナル
少なくとも 20 秒ごとに、ストリームはオープンな接続を通じて、\r\n のキャリッジリターンという形式でキープアライブシグナル（ハートビート）を送信し、クライアントのタイムアウトを防ぎます。クライアントアプリケーションは、ストリーム内に含まれる \r\n 文字を許容できるようにしておく必要があります。

クライアントが HTTP ライブラリで読み取りタイムアウトを適切に実装していれば、アプリは HTTP プロトコルと HTTP ライブラリに依存して、この期間内にデータが読み取れなかった場合にイベントを発生させることができ、\r\n 文字を明示的に監視する必要はありません。

このイベントは、通常は例外がスローされるか、使用している HTTP ライブラリに応じてその他のイベントとして発生します。これらのタイムアウトを検出するために、HTTP メソッドをエラー／イベントハンドラーでラップすることを強く推奨します。タイムアウトが発生した場合、アプリケーションは再接続を試みる必要があります。

エラーメッセージ
v2 のストリーミングエンドポイントは、ストリーム内でエラーメッセージを配信する場合があります。以下に、これらのメッセージの基本形式といくつかの例を示します。配信されるメッセージは変更される可能性があり、新しいメッセージが追加される場合がある点に注意してください。クライアントアプリケーションは、変化するシステムメッセージのペイロードを許容できるようにしておく必要があります。

エラーメッセージには、問題の解決方法を説明するドキュメントへのリンクが含まれます。

メッセージ形式:

```{
	"errors": [{
		"title": "operational-disconnect",
		"disconnect_type": "UpstreamOperationalDisconnect",
		"detail": "This stream has been disconnected upstream for operational reasons.",
		"type": "https://api.x.com/2/problems/operational-disconnect"
	}]
}
```

バッファーがいっぱいになったことによる強制切断を示すエラーメッセージは、その強制切断を引き起こした滞留によってメッセージ自体が途中で届かなくなる可能性があるため、クライアントに届かない場合があります。したがって、アプリでは再接続を開始するためにこれらのメッセージに依存しないようにする必要があります。

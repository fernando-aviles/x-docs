<div id="introduction">
  #### はじめに
</div>

ストリーミングデータを利用する際には、接続時間を最大化し、マッチしたすべてのデータを受信することが基本的な目標となります。そのためには、冗長接続を活用し、自動的に切断を検知して迅速に再接続し、失われたデータを復旧するための計画を用意しておくことが重要です。

このインテグレーションガイドでは、さまざまな復旧および冗長化機能について説明します。具体的には、冗長接続、バックフィル、リカバリについて取り上げます。
 

**冗長接続**

冗長接続を利用すると、filtered stream への同時接続を 1 つではなく複数確立できます。これにより、同じストリームに 2 つの別々のコンシューマーから接続し、両方の接続を通じて同じデータを受信することで、冗長性が確保されます。その結果、1 つのストリームが切断された場合や、アプリケーションのプライマリサーバーが障害を起こした場合など、さまざまな状況に対してアプリにホットフェイルオーバーが用意されている状態になります。

現在、Filtered stream では Enterprise アクセスを持つ Project のみが、最大 2 つまでの冗長接続を確立できます。冗長ストリームを使用するには、プライマリ接続で使用しているものと同じ URL に接続するだけです。ストリームのデータは両方の接続に送信されます。

<div id="recovering-missed-data-after-a-disconnection-backfill">
  #### 切断後の欠損データの復旧: バックフィル
</div>

切断を検知したら、システムはストリームに再接続できるように実装しておく必要があります。可能であれば、どのくらいの時間切断されていたかを記録しておき、その情報に基づいて適切な復旧機能を使い、データをバックフィルできるようにします。 

Enterprise アクセス権のある Project を利用していて、切断時間が 5 分以内であると判断できる場合、バックフィル用パラメータ `backfill_minutes` を使用できます。このパラメータを [GET /tweets/search/stream](/ja/x-api/posts/filtered-stream#get-2-tweets-search-stream) リクエストに指定すると、直近 1～5 分以内で、ルールに一致する投稿を受け取ることができます。通常、これらの古い投稿は、新しくマッチした投稿よりも先に配信されます。また、投稿の重複排除は行いません。つまり、例えば 90 秒間切断されていたにもかかわらず、2 分分のバックフィルデータを要求した場合、30 秒分の重複した投稿を受け取ることになり、システム側でそれを許容できる必要があります。以下は、バックフィルパラメータを指定したリクエスト例です:

`curl 'https://api.x.com/2/tweets/search/stream?backfill_minutes=5' -H "Authorization: Bearer $ACCESS_TOKEN"`

Enterprise アクセス権がない場合、または切断時間が 5 分を超えていると判断した場合は、 [recent search endpoint](/ja/x-api/posts/search/introduction)（最近の検索エンドポイント）またはリカバリ機能を利用して、欠損データをリクエストできます。ただし、検索用の投稿エンドポイントでは `sample:`, `bio:`, `bio_name:`, `bio_location:` オペレーターは利用できないこと、また keyword および `#hashtag` オペレーターでアクセントやダイアクリティカルマークを使用する際のマッチング動作にいくつか違いがあることに注意してください。これらの違いにより、filtered stream エンドポイント経由で本来受信できたはずの投稿を、完全には復旧できない可能性があります。 

**切断後の欠損データの復旧: リカバリ**

Enterprise アクセス権のある Project を利用している場合、5 分間のバックフィルウィンドウ内に再接続できなかったときでも、直近 24 時間以内の欠損データを復旧するために Recovery 機能を利用できます。

ストリーミングのリカバリ機能を使うと、バックフィルウィンドウを 24 時間まで拡張できます。Recovery を使用すると、欠損データが発生した期間を「再生」できます。リカバリストリームは、`start_time` および `end_time` リクエストパラメータを指定して接続リクエストを行った時点で開始されます。接続が確立されると、Recovery は指定された時間範囲のデータを再ストリーミングし、その後切断します。  

同時に 2 件まで Recovery への並行リクエスト、つまり「2 つのリカバリジョブ」を実行できます。Recovery は、開始時刻と終了時刻が定義される点を除き、技術的にはバックフィルと同じように動作します。1 回のリカバリ期間は、単一の時間範囲に対して行われます。

|     |     |     |
| :--- | :--- | :--- |
| **Name** | **Type** | **Description** |
| start&#95;time | date (ISO 8601) | YYYY-MM-DDTHH:mm:ssZ (ISO 8601/RFC 3339)。<br /><br />復旧を開始する UTC の日時。 |
| end&#95;time | date (ISO 8601) | YYYY-MM-DDTHH:mm:ssZ (ISO 8601/RFC 3339)。<br /><br />復旧を終了する UTC の日時。 |

リクエスト URL の例: [https://api.x.com/2/tweets/search/stream?start&#95;time=2022-07-12T15:10:00Z&amp;end&#95;time=2022-07-12T15:20:00Z](https://api.x.com/2/tweets/search/stream?start_time=1985-04-12T23:20:50.52Z\&end_time=1985-04-13T00:20:50.52Z)

<div id="overview">
  ## 概要
</div>

`Enterprise`

X の中核的な価値の 1 つは、ユーザーの声を守り、尊重することです。これには、ユーザーが X 上で共有するコンテンツを削除、変更、または編集したときに、その期待や意図を尊重することも含まれます。これは、世界最大級の公共のリアルタイム情報プラットフォームの長期的な健全性にとって、極めて重要だと私たちは考えています。X はコントロールをユーザーの手に委ね、個々人が自分自身の X 体験をコントロールできるようにしています。X のデータを受け取るビジネス利用者には、エンドユーザーの期待と意図を尊重する責任があると私たちは考えています。

X プラットフォームで発生しうるコンプライアンスイベントの種類についての詳細は、記事 [X におけるユーザーの意図の尊重](/ja/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter) を参照してください。

API を通じて X データを利用するあらゆる開発者や企業には、ユーザーコンテンツへの変更を尊重するために、合理的なあらゆる手段を講じる義務があります。この義務は、削除、変更、共有オプションの変更（例: コンテンツがプロテクトされたり、保留・差し止め状態になったりする場合）といったユーザーイベントにも及びます。これには、ユーザーが自分の投稿を編集した場合も含まれます。この義務があなたの X データの利用にどのように影響するかを理解するために、[Developer Policy](https://developer.x.com/en/developer-terms/policy) および／またはあなたの X Data Agreement に記載されている具体的な文言を参照してください。

X は、これらのユーザーコンプライアンスイベントに関する情報と、特定の投稿またはユーザーが公開状態かどうかを提供する、次のソリューションを提供しています。ソリューションの概要と一般的な統合パターンについては、以下で簡単に説明します。

<div id="get-statuseslookup-and-get-userslookup">
  #### GET statuses/lookup と GET users/lookup
</div>

* 形式: REST API。詳細は [GET statuses/lookup](https://developer.x.com/en/docs/x-api/v1/tweets/post-and-engage/api-reference/get-statuses-lookup) および [GET users/lookup](https://developer.x.com/en/docs/x-api/v1/accounts-and-users/follow-search-get-users/api-reference/get-users-lookup) を参照してください。

* これらのエンドポイントは、常にあらゆる投稿の編集に関する最新バージョンを返します。編集機能が導入された後に作成された投稿を表すすべての Post オブジェクトには、投稿編集メタデータが含まれます。これは、実際には編集されていない投稿にも当てはまります。 

* すべての投稿について、作成から 30 分を過ぎて行われたリクエストでは、その投稿の最終状態が返されます。 

* API リクエストの一部として呼び出し元によって指定された特定の投稿またはユーザーについて、その可用性情報を返します。

* 特定の投稿 / ユーザーの現在の可用性状態を、随時スポットチェックする用途に使用できます。

* 特定の投稿またはユーザーの、ある時点における状態を確認する必要があるお客様に最適です。

* これらの API は、コンテンツの可用性を確認する必要があるお客様にとって有用な手段を提供します。たとえば、次のような場合です:
  1. 投稿を表示する場合
  2. 投稿やユーザーと 1 対 1 でやり取りする場合
  3. 許可されたファイルダウンロードを通じて X コンテンツを第三者に配信する場合
  4. 投稿を長期間保存する場合

<div id="compliance-firehose-enterprise-only">
  #### Compliance Firehose (エンタープライズのみ)
</div>

* 形式: Streaming API。詳細は [Compliance Firehose](/ja/x-api/enterprise-gnip-2.0/fundamentals/firehouse#api-reference) を参照してください。
* X 上で発生する[コンプライアンスアクティビティ](/ja/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects)のリアルタイムストリームを配信します。これらのアクティビティには、投稿が編集されたタイミングなどが含まれます。
* プラットフォーム上で新しいコンプライアンスイベントが発生した際に、一連の保存済みデータ全体にわたってコンプライアンス状態を維持するために使用できます。
* X のデータを長期間にわたって大量に取得・保存するお客様に最適です。

<div id="recommendations-best-practices">
  #### **推奨事項とベストプラクティス**
</div>

* **数値の投稿IDとユーザーIDを保存するデータ保存スキーマを構築する**: ユーザーのメッセージに対しては、そのユーザーのすべての投稿に対してアクションを実行する必要があります。そのため、すべてのコンプライアンスメッセージは数値IDでのみ配信されることから、投稿とユーザーの関係を数値IDに基づいて保持するような保存スキーマを設計することが重要です。データ利用者は、投稿IDおよびユーザーIDの両方でコンプライアンスイベントを監視し、ローカルデータストアを適切に更新できる必要があります。

* **すべてのコンプライアンスステータスに対応するスキーマを構築する**: さまざまなアプリケーションでコンプライアンス関連の処理をどのように行うかによっては、データストアに他のメタデータを追加する必要がある場合があります。たとえば、データ利用者は、`status_withheld` メッセージの影響を受ける国でコンテンツの表示を制限しやすくするために、既存のデータベースにメタデータを追加することを選択するかもしれません。

* **リツイート削除の処理**: リツイートは特別な種類の投稿であり、元のメッセージがリツイート内のオブジェクトとしてネストされています。この場合、リツイートには 2 つの投稿IDが参照されます。1 つはリツイートのID、もう 1 つは（ネストされたオブジェクト内に含まれる）元のメッセージのIDです。元のメッセージが削除されると、元のIDに対する投稿削除メッセージが発行されます。投稿の削除イベントは通常、すべてのリツイートに対する削除イベントをトリガーしますが、場合によってはすべてが送信されないことがあり、クライアントシステムは不完全なリツイート削除に対しても許容できるようにしておく必要があります。元のIDの削除が行われれば、その後に行われたすべてのリツイートを削除するのに十分です。リツイートを保存する際には元の投稿IDを参照しておき、投稿削除イベントを受信したときに、参照されているすべてのリツイートを削除することがベストプラクティスです。

<div id="compliance-firehose-api">
  #### **Compliance Firehose API**
</div>

発生しうるコンプライアンスイベントの種類には、投稿（または「ステータス」）イベントとユーザーイベントが含まれます。これらには、以下で説明する複数のタイプがあります。  

注意事項:

* ユーザーのステータスについての詳細は[こちら](https://support.x.com/articles/14016)、削除された投稿に関する開発者ポリシーは[こちら](https://dev.x.com/overview/terms/policy#3.Update_Respect_Users_Control_and_Privacy)をご覧ください。
* Compliance Firehose は &#39;tweet&#95;edit&#39; イベントを提供するように更新されています。 
* いくつかのユーザー削除、保護および凍結イベントは、必ずしも恒久的ではなく、状態が無限にトグルされる可能性があります。これには、user&#95;delete、user&#95;undelete、user&#95;protect、user&#95;unprotect、user&#95;suspend、user&#95;unsuspend が含まれます。
* user&#95;delete は、そのユーザーがアカウントの user&#95;undelete を選択しなかった場合に限り、30 日後に status&#95;deletes が続きます。ユーザーが user&#95;delete を取り消し、その後 30 日後にそのユーザーのすべての投稿に対する削除が発生しない可能性もあります。
* user&#95;suspend は、ユーザーが user&#95;unsuspend イベントの対象とならない限り、有効なままとなるアクションです。これらは 30 日間の期間中のいかなる変更の対象にもなりません。

各イベントタイプの処理方法を理解し、エンドユーザーのプライバシーと意図を尊重するには、「Recommended Action」列を参照してください。

| Original Message Type | Object | Permanent (Yes/No) | Recommended Action |
| :--- | :--- | :--- | :--- |
| delete | Status | Yes | 関連する投稿を削除します。 |
| status&#95;withheld | Status | Yes | status&#95;withheld メッセージに記載されている特定の国で、関連する投稿を非表示にします。 |
| drop | Status | No  | 投稿を一般公開の表示から削除します。 |
| undrop | Status | No  | ステータスは再び表示され、公開コンテンツとして扱われる場合があります。 |
| tweet&#95;edit | Status | Yes | 新しい編集内容を反映し、該当する場合には表示します。 |
| user&#95;delete | User | No  | 関連ユーザーによるすべての投稿を非表示にするか削除します。 |
| user&#95;undelete | User | No  | 関連ユーザーによるすべての投稿は、再び表示され、公開コンテンツとして扱われる場合があります。 |
| user&#95;protect | User | No  | 関連ユーザーによるすべての投稿を非表示にするか削除します。 |
| user&#95;unprotect | User | No  | 関連ユーザーによるすべての投稿は、再び表示され、公開コンテンツとして扱われる場合があります。 |
| user&#95;suspend | User | No  | 関連ユーザーによるすべての投稿を非表示にするか削除します。 |
| user&#95;unsuspend | User | No  | 関連ユーザーによるすべての投稿は、再び表示され、公開コンテンツとして扱われる場合があります。 |
| scrub&#95;geo | User | Yes | scrub&#95;geo メッセージ内で指定された投稿より前の、そのユーザーによるすべての投稿について、X によって提供されたすべてのジオデータを削除します。なお、その後の投稿には利用可能なジオデータが含まれる場合があります。 |
| user&#95;withheld | User | Yes | user&#95;withheld メッセージに記載されている特定の国で、関連ユーザーによる投稿を非表示にします。 |
| delete | Favorite | Yes | 関連する「いいね／お気に入り」を削除します。 |

<div id="integrating-compliance-firehose">
  ### Compliance Firehose との統合
</div>

Compliance Firehose は、X プラットフォーム上で発生するコンプライアンスイベントを配信するリアルタイム ストリーミング API です。コンプライアンスイベントと、それらが X 上でどのように生成されるかについて理解を深めるには、[Honoring User Intent on X](/ja/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter) を参照してください。

投稿イベントおよびユーザーイベントはそれぞれ独立して配信され、それぞれを独立して処理する必要がある点に注意してください（つまり、ある投稿の削除がユーザーイベントを意味するわけではなく、その逆も同様です）。いくつかのユーザーイベントは必ずしも永続的ではなく、状態間を無制限に切り替わる可能性があります。これには、user&#95;delete、user&#95;undelete、user&#95;protect、user&#95;unprotect、user&#95;suspend、user&#95;unsuspend が含まれます。

User&#95;delete が発生した場合、ユーザーがアカウントの user&#95;undelete を選択していない場合に限り、30 日後に status&#95;delete が行われます。ユーザーが user&#95;delete を元に戻す可能性があり、その場合には 30 日後にそのユーザーのすべての投稿に対する削除は発生しません。

User&#95;suspend は、ユーザーに対して user&#95;unsuspend イベントが発生しない限り有効なままとなるアクションです。これらは 30 日という期間によるいかなる変更にも左右されません。

コンプライアンスイベントを、自社ソフトウェアの利用者に対して直接表示したり、それ以外の方法でプロダクトやユーザー向けエクスペリエンスに組み込んだりすることは決して適切ではありません。これらは、コンプライアンスを維持し、X ユーザーの行動を尊重する目的のみに使用されるべきものです。

<div id="integrating-with-the-compliance-firehose">
  #### **Compliance Firehose との統合**
</div>

Compliance Firehose をシステムに統合するには、次のことが可能な連携機能を構築する必要があります。

1. Compliance Firehose の各ストリーミング API パーティションへのストリーミング接続を確立する
2. 非同期プロセスを使用してストリームの取り込みと追加処理を分離し、大量のデータに対応する
3. 何らかの理由で切断された場合に、ストリームパーティションへ自動的に再接続する
4. 上記のガイダンスに従い、保持している投稿およびユーザーデータに関連するコンプライアンスイベントを処理する

<div id="honoring-user-intent-on-twitter">
  ### X におけるユーザーの意図を尊重すること
</div>

私たちは、X ユーザーのプライバシーおよび意図を尊重することが、世界最大級の公共かつリアルタイムな情報プラットフォームの長期的な健全性を保つうえで極めて重要であると考えています。X はプライバシー管理をユーザー自身の手に委ねており、個々人が自らの X での体験をコントロールできるようにしています。X data を利用するビジネスユーザーとして、このような信頼と敬意の環境を維持するために、エンドユーザーのプライバシーと行動を尊重することは、私たち全員の責任です。

プラットフォーム上での表示方法に影響を与える、投稿やユーザーアカウントに対するさまざまな変化や操作が存在します。プライバシーおよび意図に影響するアクションは、Status（投稿）レベルと User レベルの両方で定義されます。これらのアクションには、次のようなものが含まれます。

<div id="user">
  #### ユーザー
</div>

| Action | Description |
| :--- | :--- |
| Protect Account | X ユーザーは、いつでも自分のアカウントを非公開にしたり、再び公開したりできます。非公開アカウントでは、自分のアカウントの投稿を閲覧できる相手をユーザーが手動で承認する必要があります。   <br />詳細は [公開投稿と非公開投稿について](https://support.x.com/articles/14016-about-public-and-protected-tweets)をご覧ください。 |
| Delete Account | X ユーザーは、いつでも自分のアカウントと、それに関連付けられているすべてのステータスメッセージを削除することができます。ユーザーが削除を取り消してアカウントを再有効化できるようにするため、X はアカウント情報を削除後 30 日間保持します。 |
| Scrub Geo | X ユーザーは、いつでも過去の投稿からすべての位置情報データを削除できます。この操作は「scrub geo」と呼ばれます。 |
| Suspend Account | X は、X ルールに違反しているアカウント、またはハッキングや不正アクセスの疑いがあるアカウントを凍結する権利を有します。アカウントの凍結解除（unsuspend）は X のみが行えます。 |
| Withhold Account | X は、特定の国において、状況に応じて特定のコンテンツへのアクセスを制限する権利を有します。保留（withhold）されたアカウントの保留解除（unwithhold）は X のみが行えます。   <br />詳細は [国別に制限されたコンテンツについて](https://support.x.com/articles/20169222-country-withheld-content)をご覧ください。 |

<div id="keeping-track-of-user-and-status-changes">
  #### ユーザーおよびステータスの変更の追跡
</div>

上記のいずれかのアクションにより、User または Status の状態はいつでも変化する可能性があり、これにより X data の利用者に求められる、関連するすべてのコンテンツの可用性およびプライバシーの取り扱いが影響を受けます。これらのアクションが発生すると、Status または User の状態が変更されたことを示す、対応するコンプライアンスメッセージが送信されます。

</div>

Compliance firehose データストリームへの永続的な接続を確立し、そのストリームを通じてコンプライアンスイベントが配信されます。

**Example Curl Request**

次のサンプルリクエストは、コマンドラインで cURL を使用して実行されます。

```bash
curl --compressed -v -uexample@customer.com "https://gnip-stream.x.com/stream/compliance/accounts/:account_name/publishers/twitter/:stream_label.json?partition=1"
```

*注:* 上記のリクエストでは、Compliance firehose の `partition=1` にのみ接続しています。このストリーム全体を取得するには、8 個すべてのパーティションに接続する必要があります。

| Status | Text | Definition |

<div id="other-recommendations-best-practices">
  #### その他の推奨事項およびベストプラクティス
</div>

* **数値のツイートIDとユーザーIDを保存するデータストレージスキーマを構築する**: ユーザーメッセージでは、そのユーザーのすべてのツイートに対してアクションを実行する必要があります。そのため、すべてのコンプライアンスメッセージは数値IDでのみ配信されることから、ツイートとユーザーの関係を数値IDに基づいて保持できるようにストレージスキーマを設計することが重要です。データ利用者は、ツイートIDとユーザーIDの両方でコンプライアンスイベントを監視し、ローカルのデータストアを適切に更新できる必要があります。

* **すべてのコンプライアンスステータスに対応するスキーマを構築する**: さまざまなアプリケーションでコンプライアンス関連の処理をどのように行うかに応じて、データストアに他のメタデータを追加する必要が生じる場合があります。たとえば、データ利用者は、`status_withheld` メッセージの対象となる国でコンテンツの表示を制限しやすくするために、既存のデータベースにメタデータを追加することを選択するかもしれません。

* **リツイートの削除処理**: リツイートは特別な種類のツイートであり、元のメッセージがリツイート内のオブジェクトにネストされた形で含まれています。この場合、リツイートには2つのツイートIDが参照されます — リツイート自体のIDと、（ネストされたオブジェクト内に含まれる）元のメッセージのIDです。元のメッセージが削除されると、元のIDに対してツイート削除メッセージが発行されます。その後、すべてのリツイートに対して削除メッセージが発行されることはありません。元のIDの削除だけで、その後のすべてのリツイートも削除されたものとして扱えます。

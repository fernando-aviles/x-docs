<div id="overview">
  ## 概要
</div>

`Enterprise`

X の中核的な価値のひとつは、ユーザーの声を守り、尊重することです。これには、ユーザーが X 上で共有することを選んだコンテンツを削除・変更・編集する際の、ユーザー自身の期待や意図を尊重することも含まれます。これは、世界最大級の公共かつリアルタイムな情報プラットフォームの長期的な健全性にとって、極めて重要であると考えています。X はコントロールをユーザーの手に委ね、各個人が自分自身の X での体験をコントロールできるようにしています。X のデータを受け取るビジネス利用者には、エンドユーザーの期待と意図を尊重する責任があると、私たちは考えています。

X プラットフォームで発生しうるコンプライアンスイベントのタイプについて詳しくは、記事 [Honoring User Intent on X](/ja/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter) を参照してください。

API を介して X のデータを利用するあらゆる開発者や企業には、ユーザーコンテンツへの変更を尊重するために、合理的な範囲で可能なあらゆる手段を講じる義務があります。この義務は、削除や変更、共有オプションの変更（例: コンテンツが保護された、または提供が保留・制限された状態になる場合）といったユーザーイベントにも及びます。これは、ユーザーが自分の投稿を編集した場合も含みます。この義務があなたによる X データの利用にどのような影響を与えるかを理解するには、[Developer Policy](https://developer.x.com/en/developer-terms/policy) および／または X Data Agreement の該当文言を参照してください。

X では、これらのユーザーコンプライアンスイベントに関する情報と、特定の投稿またはユーザーが公開状態かどうかを提供するために、次のソリューションを用意しています。これらのソリューションの概要と一般的な統合パターンを、以下に簡潔に示します。

<div id="get-statuseslookup-and-get-userslookup">
  #### GET statuses/lookup および GET users/lookup
</div>

* 形式: REST API。詳細は [GET statuses/lookup](https://developer.x.com/en/docs/x-api/v1/tweets/post-and-engage/api-reference/get-statuses-lookup) および [GET users/lookup](https://developer.x.com/en/docs/x-api/v1/accounts-and-users/follow-search-get-users/api-reference/get-users-lookup) を参照してください。

* これらのエンドポイントは、常に投稿編集の最新バージョンを返します。編集機能が導入された後に作成された投稿を表すすべての Post オブジェクトには、投稿編集に関するメタデータが含まれます。これは、投稿が編集されていない場合でも同様です。 

* すべての投稿について、作成から 30 分以上経過した後に行われた投稿のリクエストは、対象となる投稿の最終状態を表します。 

* API リクエストの一部として呼び出し元によって定義された特定の投稿またはユーザーの利用可能性情報を返します。

* 特定の投稿 / ユーザーの現在の利用可能性状態を、アドホックにスポットチェックする用途で使用できます。

* 特定の時点における特定の投稿またはユーザーの現在の状態を確認する必要があるお客様に最適です。

* これらの API は、お客様がコンテンツの利用可否を確認する必要がある場合に使用できる有用な仕組みを提供します。たとえば次のような場合です:
  1. 投稿を表示する場合
  2. 投稿やユーザーと 1:1 でやり取りする場合
  3. 許可されたファイルダウンロードを通じて X コンテンツを第三者に配信する場合
  4. 投稿を長期間保存する場合

<div id="compliance-firehose-enterprise-only">
  #### Compliance Firehose（エンタープライズのみ）
</div>

* 形式: ストリーミング API。詳細: [Compliance Firehose](/ja/x-api/enterprise-gnip-2.0/fundamentals/firehouse#api-reference)。
* X 上の[コンプライアンスアクティビティ](/ja/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects)をリアルタイムストリームで配信します。これらのアクティビティには、投稿が編集されたタイミングなどが含まれます。
* プラットフォーム上で新しいコンプライアンスイベントが発生した際に、一連の保存済みデータ全体のコンプライアンス状態を維持する目的で利用できます。
* X データを長期間にわたって大量に取得・保存するお客様に最適です。

<div id="recommendations-best-practices">
  #### **推奨事項とベストプラクティス**
</div>

* **数値の投稿IDとユーザーIDを保存するデータ保存スキーマを構築する**: ユーザー単位のメッセージでは、そのユーザーによるすべての投稿に対してアクションを実行する必要があります。そのため、すべてのコンプライアンスメッセージは数値IDでのみ配信されることから、投稿とユーザーの関係を数値IDに基づいて保持するようにストレージスキーマを設計することが重要です。データ利用者は、投稿IDとユーザーIDの両方でコンプライアンスイベントを監視し、ローカルのデータストアを適切に更新できる必要があります。

* **すべてのコンプライアンスステータスに対応するスキーマを構築する**: さまざまなアプリケーションでコンプライアンスアクティビティにどのように対応するかによっては、データストアに他のメタデータを追加する必要が生じる場合があります。たとえば、データ利用者は、`status_withheld` メッセージの影響を受ける国でコンテンツの表示制限を容易にするために、既存のデータベースにメタデータを追加することを検討する場合があります。

* **リツイートの削除処理**: リツイートは特殊な種類の投稿であり、元のメッセージがリツイート内のオブジェクトとしてネストされています。この場合、リツイートには 2 つの投稿IDが参照されます ― リツイート自体のIDと、（ネストされたオブジェクト内に含まれる）元のメッセージのIDです。元のメッセージが削除されると、元のIDに対して投稿削除メッセージが発行されます。投稿の削除イベントは通常、すべてのリツイートに対する削除イベントをトリガーします。ただし、場合によってはすべてが送信されないこともあり、クライアントシステムは不完全なリツイート削除を許容できるようにしておく必要があります。元のIDの削除だけで、その後に行われたすべてのリツイートを削除するには十分であるはずです。リツイートを保存する際には、元の投稿IDを参照として保持し、投稿削除イベントを受信したときに、参照されているすべてのリツイートを削除することがベストプラクティスです。

<div id="compliance-firehose-api">
  #### **Compliance Firehose API**
</div>

想定されるコンプライアンスイベントの種類には、投稿（または「ステータス」）イベントとユーザーイベントが含まれます。それぞれについての複数の種類を、以下で説明します。  

次の点に注意してください:

* ユーザーステータスについては[こちら](https://support.x.com/articles/14016)、削除された投稿に関する開発者向けポリシーについては[こちら](https://dev.x.com/overview/terms/policy#3.Update_Respect_Users_Control_and_Privacy)を参照してください。
* Compliance Firehose は、`tweet_edit` イベントを提供するように更新されています。 
* いくつかのユーザー削除、保護、および凍結イベントは必ずしも恒久的なものではなく、状態が無限にトグルされる可能性があります。これには、user&#95;delete、user&#95;undelete、user&#95;protect、user&#95;unprotect、user&#95;suspend、user&#95;unsuspend が含まれます。
* user&#95;delete の後には、ユーザーがアカウントの user&#95;undelete を選択していない場合に限り、30 日後に status&#95;delete が発生します。ユーザーによって user&#95;delete が取り消され、その後 30 日後にそのユーザーのすべての投稿が削除されない可能性があります。
* user&#95;suspend は、ユーザーが user&#95;unsuspend イベントの対象とならない限り、有効な状態のまま維持されるアクションです。これらについては、30 日間の期間によるいかなる変更も適用されません。

エンドユーザーのプライバシーと意図を尊重するために、各タイプのイベントをどのように処理すべきかを理解するには、「Recommended Action」列を参照してください。

| Original Message Type | Object | Permanent (Yes/No) | Recommended Action |
| :--- | :--- | :--- | :--- |
| delete | Status | Yes | 関連する投稿を削除します。 |
| status&#95;withheld | Status | Yes | status&#95;withheld メッセージに記載されている特定の国で、関連する投稿を非表示にします。 |
| drop | Status | No  | 投稿を一般公開から非表示にします。 |
| undrop | Status | No  | ステータスは再び表示され、公開として扱うことができます。 |
| tweet&#95;edit | Status | Yes | 新しい編集内容を尊重し、該当する場合はその内容を表示します。 |
| user&#95;delete | User | No  | 関連ユーザーによるすべての投稿を非表示または削除します。 |
| user&#95;undelete | User | No  | 関連ユーザーによるすべての投稿は再び表示され、公開として扱うことができます。 |
| user&#95;protect | User | No  | 関連ユーザーによるすべての投稿を非表示または削除します。 |
| user&#95;unprotect | User | No  | 関連ユーザーによるすべての投稿は再び表示され、公開として扱うことができます。 |
| user&#95;suspend | User | No  | 関連ユーザーによるすべての投稿を非表示または削除します。 |
| user&#95;unsuspend | User | No  | 関連ユーザーによるすべての投稿は再び表示され、公開として扱うことができます。 |
| scrub&#95;geo | User | Yes | scrub&#95;geo メッセージ内で指定された投稿より前に、そのユーザーが行ったすべての投稿について、X によって提供されたすべての位置情報データを削除します。なお、その後の投稿には、利用可能な位置情報データが含まれる場合があります。 |
| user&#95;withheld | User | Yes | user&#95;withheld メッセージに記載されている特定の国で、関連ユーザーによる投稿を非表示にします。 |
| delete | Favorite | Yes | 関連する「いいね」/「お気に入り」を削除します。 |

<div id="integrating-compliance-firehose">
  ### Compliance Firehose の統合
</div>

Compliance Firehose は、X プラットフォーム上で発生するコンプライアンスイベントをリアルタイムで配信するストリーミング API です。コンプライアンスイベントの概要と、それらが X 上でどのように生成されるかについては、記事「[Honoring User Intent on X](/ja/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter)」を参照してください。

投稿イベントとユーザーイベントは独立して配信され、それぞれを個別に処理する必要がある点に注意してください（つまり、ある投稿の削除がユーザーイベントを意味するわけではなく、その逆も同様です）。いくつかのユーザーイベントは必ずしも恒久的なものではなく、状態が何度でも切り替わる可能性があります。これには次のものが含まれます: user&#95;delete、user&#95;undelete、user&#95;protect、user&#95;unprotect、user&#95;suspend、user&#95;unsuspend。

User&#95;delete イベントの後には、そのユーザーがアカウントの user&#95;undelete を選択していない場合に限り、30 日後に status&#95;delete が発生します。ユーザーが user&#95;delete を取り消し、その結果、そのユーザーのすべての投稿について 30 日後に削除が発生しない可能性もあります。

User&#95;suspend は、ユーザーが user&#95;unsuspend イベントの対象とならない限り真のままで維持されるアクションです。これらは 30 日間の期間におけるいかなる変更の対象にもなりません。

コンプライアンスイベントをあなたのソフトウェアのユーザーに直接表示したり、製品やカスタマーエクスペリエンスに組み込んだりすることは、決して適切ではありません。これらは、コンプライアンス順守を維持し、X ユーザーの行動を尊重する目的のみに利用されるべきものです。

<div id="integrating-with-the-compliance-firehose">
  #### **Compliance Firehose の統合**
</div>

Compliance Firehose をお使いのシステムに統合するには、次のことが可能な連携機能を構築する必要があります。

1. Compliance Firehose の各ストリーミング API パーティションへのストリーミング接続を確立する
2. 非同期プロセスを用いてストリームの取り込みと追加処理を分離し、大量のデータを処理する
3. 何らかの理由で切断された場合に、ストリーミング API パーティションへ自動的に再接続する
4. 上記のガイダンスに従って保存している投稿およびユーザーデータに関連するコンプライアンスイベントを処理する

<div id="honoring-user-intent-on-twitter">
  ### Twitter におけるユーザーの意図の尊重
</div>

私たちは、X ユーザーのプライバシーと意図を尊重することが、世界最大級の公共のリアルタイム情報プラットフォームである X の長期的な健全性にとって極めて重要であると考えています。X はプライバシー管理をユーザー自身の手に委ねており、個々人が自分の X での体験を自ら管理できるようにしています。X のデータを利用するビジネスユーザーとして、私たちには、エンドユーザーのプライバシーと行動を尊重し、この信頼と敬意に基づく環境を維持するという共同の責任があります。

プラットフォーム上での表示方法に影響を与える、投稿やユーザーアカウントに対するさまざまな変化やアクションが存在します。プライバシーと意図に影響を与えるアクションは、Status（投稿）レベルと User レベルの両方で定義されています。これらのアクションには次のようなものが含まれます。

<div id="user">
  #### ユーザー
</div>

| Action | Description |
| :--- | :--- |
| Protect Account | X ユーザーは、いつでも自分のアカウントを非公開にしたり、非公開を解除したりできます。非公開アカウントでは、自分のアカウントの投稿を閲覧できる相手ごとに、手動で承認する必要があります。   <br />詳細については、[公開投稿と非公開投稿について](https://support.x.com/articles/14016-about-public-and-protected-tweets)を参照してください。 |
| Delete Account | X ユーザーは、いつでも自分のアカウントおよびそれに関連付けられたすべての投稿を削除することができます。X は、ユーザーが削除を取り消してアカウントを再有効化できるよう、削除後 30 日間はアカウント情報を保持します。 |
| Scrub Geo | X ユーザーは、いつでも過去の投稿からすべての位置情報を削除できます。これは「scrub geo」と呼ばれています。 |
| Suspend Account | X は、X ルールに違反しているアカウント、またはハッキングや不正アクセスが疑われるアカウントを凍結する権利を有します。アカウントの凍結解除（unsuspend）は X のみが行うことができます。 |
| Withhold Account | X は、特定の国において、特定のコンテンツへのアクセスを状況に応じて制限（withhold）する権利を有します。制限されたアカウントの制限解除（unwithhold）は X のみが行うことができます。   <br />詳細については、[国別に表示制限されたコンテンツ](https://support.x.com/articles/20169222-country-withheld-content)を参照してください。 |

<div id="status">
  #### ステータス
</div>

| アクション | 説明 |
| :--- | :--- |
| ステータスを削除 | X ユーザーは、任意のタイミングでステータスを削除できます。削除されたステータスは元に戻すことはできず、永久に削除されます。 |
| ステータスを保留 | X は、特定の国において特定のコンテンツへのアクセスを、必要に応じて制限（保留）する権利を有します。保留されたステータスは、X によってのみ保留解除することができます。   <br />詳細については、[Country Withheld Content](https://support.x.com/articles/20169222-country-withheld-content) を参照してください。 |

<div id="keeping-track-of-user-and-status-changes">
  #### ユーザーおよびステータスの変更の追跡
</div>

User または Status の状態は、上記のいずれかのアクションによりいつでも変化する可能性があり、その結果、X のデータを利用する利用者は、関連するすべてのコンテンツの可用性とプライバシーをどのように取り扱うべきかに影響を受けます。これらのアクションが発生すると、Status または User の状態が変更されたことを示す、対応するコンプライアンスメッセージが送信されます。

<div id="get-compliancestream">

</div>

Compliance Firehose データストリームへの永続的な接続を確立し、このストリーム経由でコンプライアンスイベントが配信されます。

| :-------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| **Connection Type**         | Keep-Alive                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **URL**                     | ダッシュボードのストリームの API ヘルプページに記載されており、次のような構造になります。  <br />  <br /><br />[https://gnip-stream.x.com/stream/compliance/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json?partition=1](https://gnip-stream.x.com/stream/compliance/accounts/:account_name/publishers/twitter/:stream_label.json?partition=1)<br /><br />**注:** &quot;partition&quot; パラメータは必須です。合計ボリュームのそれぞれ 12.5% を含む 8 つすべてのパーティションに接続して、完全なストリームを取得する必要があります。 |

**Example Curl Request**

次のサンプルリクエストは、コマンドラインで cURL を使用して実行します。

```bash
curl --compressed -v -uexample@customer.com "https://gnip-stream.x.com/stream/compliance/accounts/:account_name/publishers/twitter/:stream_label.json?partition=1"
```

*注:* 上記のリクエストは、Compliance firehose の `partition=1` にのみ接続しています。このストリームの全データを取得するには、8 つあるすべてのパーティションに接続する必要があります。

<div id="response-codes">

</div>

これらのリクエストに対して、API からは次のレスポンスが返される可能性があります。ほとんどのエラーコードは、ボディ内に追加情報を含む文字列とともに返されます。200 以外のレスポンスについては、クライアントは再接続を試みる必要があります。

| Status | Text | Definition |
| :--- | :--- | :--- |
| 200 | Success | 接続が正常に確立され、新しいアクティビティは到着し次第送信されます。 |
| 401 | Unauthorized | 無効な認証情報により HTTP 認証に失敗しました。console.gnip.com に認証情報でログインし、リクエストでそれらを正しく使用していることを確認してください。 |
| 406 | Not Acceptable | 一般的には、クライアントがストリームからの gzip エンコードを受け入れるためのヘッダーを正しく含めていない場合に発生しますが、他の状況でも発生する可能性があります。「この接続では圧縮が必要です。圧縮を有効にするには、リクエストに `Accept-Encoding: gzip` ヘッダーを付与し、クライアント側でストリームを読み取る際に伸張できるようにしておいてください。」といった内容の JSON メッセージが含まれます。 |
| 429 | Rate Limited | アプリが接続リクエストの上限を超えました。 |
| 503 | Service Unavailable | X サーバー側の問題です。指数バックオフ方式で再接続してください。この問題に関する通知が [X API Status Page](https://api.twitterstat.us/) に掲載されていない場合は、サポートに連絡してください。 |

<div id="other-recommendations-best-practices">
  #### その他の推奨事項とベストプラクティス
</div>

* **数値の Tweet ID および User ID を保存するデータストレージスキーマを構築する**: ユーザーに対するメッセージでは、そのユーザーのすべてのツイートに対してアクションを行う必要があります。したがって、すべてのコンプライアンスメッセージは数値の ID のみで配信されるため、数値 ID に基づいて Tweet と User の関係を保持できるようにストレージスキーマを設計することが重要です。データ利用者は、Tweet ID と User ID の両方でコンプライアンスイベントを監視し、ローカルのデータストアを適切に更新できるようにする必要があります。

* **すべてのコンプライアンスステータスに対応するスキーマを構築する**: さまざまなアプリケーションでコンプライアンス処理をどのように行うかによっては、データストアに他のメタデータを追加する必要がある場合があります。たとえば、データ利用者は、status&#95;withheld メッセージの影響を受ける国でコンテンツの表示を制限しやすくするために、既存のデータベースにメタデータを追加することを決定する場合があります。

* **Retweet の削除処理**: Retweet は、元のメッセージが Retweet 内のオブジェクトとしてネストされた、特殊な種類のツイートです。この場合、Retweet には 2 つの Tweet ID が参照されます — Retweet 自体の ID と、（ネストされたオブジェクトに含まれる）元のメッセージの ID です。元のメッセージが削除されると、元の ID に対して Tweet の削除メッセージが発行されます。以降、すべての Retweet に対して削除メッセージが再度発行されることはありません。元の ID の削除を処理するだけで、以降のすべての Retweet を削除したものとして扱うことができます。

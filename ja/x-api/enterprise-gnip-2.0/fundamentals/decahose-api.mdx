<div id="decahose-stream">
  ### Decahose ストリーム
</div>

[Enterprise](https://developer.x.com/en/products/x-api/enterprise)

*これは、当社のマネージドアクセスレベル内でのみ利用可能なエンタープライズ向け API です。この API を利用するには、まず当社のエンタープライズセールスチームとの間でアカウントを開設する必要があります。 [詳細はこちら](https://developer.x.com/en/products/x-api/enterprise)*

Decahose は、ストリーミング接続を通じて、リアルタイムの X Firehose のデータから 10% のランダムサンプルを配信します。これは、データをランダムに選択しつつ、X の Firehose から送信されるデータを期待される低レイテンシで配信できるようにするリアルタイムサンプリングアルゴリズムによって実現されています。

以下は、Decahose で利用できる主な機能です。

* **拡張・強化された URL:** - 短縮 URL を完全に展開し、追加のメタデータ（ページタイトルと説明）を提供
* **ストリームのパーティション分割** - 2 つのパーティションで構成され、それぞれが Decahose ストリーム全体の 50% のボリュームを保持
* **信頼性の向上** - バックエンドシステムの地理的な多様性

注: このデータは一括で配信され、キーワードなどによる追加フィルタリングには対応していません。

<div id="streaming-likes">
  ### いいねのストリーミング
</div>

*これはマネージドアクセスレベルでのみ利用可能なエンタープライズ API です。この API を利用するには、まずエンタープライズセールスチームとのアカウント設定が必要です。 [詳細はこちら](https://developer.x.com/en/products/x-api/enterprise)*

いいねは、誰が投稿にいいねしているかを把握するための手段となり、正確ないいね数を得ることができます。Gnip の Firehose と Decahose は、Gnip 経由で配信される投稿に関連する公開いいねを配信できます。これにより、投稿に紐づくリアルタイムの公開エンゲージメントおよびオーディエンス指標が得られます。
 

**いいねの利用を開始する**

いいねに関するデータを取得するにあたって、次の点を理解しておく必要があります。

* いいねは、独立した別個のストリームで配信されます
* いいねは、これまで歴史的には「Favorites」と呼ばれてきました。ネイティブ拡張形式のペイロードでは、この呼称が維持されています
* ストリームには公開いいねのみが含まれます
  * 公開とは、いいねをしたユーザー、投稿作成者、および投稿がすべてプラットフォーム上で公開であることを意味します
* いいねはリツイートと非常によく似ており、公開されたエンゲージメントシグナルを表します
* ペイロード要素には以下が含まれます:
  * 元の投稿オブジェクト
  * 元の投稿を作成した Actor オブジェクト
  * いいねアクションを実行した Actor オブジェクト
* オリジナルのコンテンツのみがいいね可能です
  * リツイートにはいいねできません。リツイートへのいいねは元の投稿に対して適用されます
  * 引用ツイートには、いいねを *行うことができます*
* いいねアクティビティには、該当する場合は購入済み/適用済みの Gnip Enrichments が含まれます
* 対応製品 / 機能
  * いいねストリームは Backfill をサポートします（購入/適用済みの場合）
  * いいねストリームには Replay のサポートはありません
  * いいねには Search または Historical のサポートはありません
  * PowerTrack にいいねのサポートを追加する予定は、当面ありません

**Decahose**

* Decahose で配信される 10% サンプル投稿に対して、ストリームには該当する公開いいねが 100% 含まれています
* **パーティション数:** 2
* **URL 構造**
  * https://gnip-stream.x.com/stream/sample10-likes/accounts/&lt;accountName&gt;/publishers/twitter/&lt;streamLabel&gt;.json?partition=1

<div id="recovery-and-redundency">
  ### Recovery and Redundency
</div>

**概要**

大量のリアルタイム投稿をストリーミングする場合、データの信頼性と完全性の両方を高めるための一連のベストプラクティスがあります。リアルタイムデータを取得する際には、接続時間を最大化することが基本的な目標となります。切断が発生した場合は、それを自動的に検知して再接続することが重要です。再接続後は、バックフィルすべき期間が存在しないかを確認する必要があります。こうした詳細を管理し、リアルタイム投稿を取得するコンポーネントは、ネットワーク、データストア、サーバー、ストレージといった考慮事項を持つシステム全体の一部にすぎません。これらのシステムの複雑さを踏まえると、別々のストリーミング環境、少なくとも開発／テスト用と本番用で分離したストリームを用意することも、もう一つのベストプラクティスです。

Decahose には、これらの取り組みを支援するための一連の機能が用意されています。

1. 複数の環境をサポートするために、アカウントに対して [Additional Streams](#AdditionalStreams) をデプロイできます。これらのストリームは互いに独立しており、それらを区別するための異なる stream&#95;label が設定されています。
2. 接続維持を支援するために、各 Decahose ストリームは [Redundant Connections](/ja/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#additional-streams) をサポートします。最も一般的なアーキテクチャは、1 つのストリームに 2 つの接続を持たせ、クライアント側には 2 つの独立したコンシューマーを配置するものです（理想的には異なるネットワーク上）。この設計により、クライアント側のネットワーク、サーバー、データストア経路にまたがる冗長性を持たせることができます。各接続ごとにデータの完全なコピーが配信されるため、クライアント側は重複したデータを許容し、管理できる必要がある点に注意してください。
3. 10 秒ごとに「**heartbeat**」が送信されます。ただし、Decahose ストリームではデータのボリュームが十分に大きいため、短い時間（数秒など）であっても投稿がまったく流れない場合は接続の問題を示している可能性があります。したがって、「&#39;data silence&#39;」と heartbeat の欠如の両方を、切断を検知する手段として利用できます。

切断は避けられないため、Decahose ストリームには、切断やその他の運用上の問題により取り逃がしたデータを復旧するのに役立つ、専用の [Recovery](/ja/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#overview) 機能と [Backfill](/ja/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#backfill) 機能が用意されています。

<div id="additional-streams">
  #### 追加ストリーム
</div>

追加の Decahose ストリームを用意することは、ソリューションに信頼性を組み込むもう 1 つの方法です。追加ストリームはすべて完全に独立しており、それぞれ固有のエンドポイントを持ちます。各ストリームにはそれぞれ専用の `stream_label` が割り当てられ、このラベルとアカウント名がそのストリームの URL の一部になります。以下の例を参照してください。

https://gnip-stream.x.com/stream/sample10/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json

最も一般的な慣例は、本番システム専用のリアルタイムストリームを 1 つ持ち、加えて開発およびテスト用のストリームを 1 つ用意することです。テスト/開発ストリームを持つことで、Decahose を利用するお客様はクライアント（コンシューマー）の更新をテストするためのストリームを確保できます。ストリームには任意の（ユニークな）ラベルを割り当てることができますが、1 つの慣例として、本番ストリームには「prod」、追加の開発ストリームには「dev」または「sandbox」を使用します。

ストリームの数とそれぞれの固有ラベルは、アカウント担当者によって設定可能です。

**冗長接続**

冗長接続を使用すると、データストリームに対して同時に複数の接続を確立できるようになります。これにより、同じストリームに 2 つの別々のコンシューマーから接続し、両方の接続で同じデータを受信することで冗長性が確保されます。したがって、たとえば一方のストリームが切断された場合や、アプリのプライマリサーバーが障害を起こした場合などに、アプリはホットフェイルオーバーを行うことができます。

任意のストリームに許可される接続数は、アカウント担当者によって設定可能です。冗長接続を利用するには、プライマリ接続と同じ URL に単に接続するだけです。ストリームのデータは両方の接続を通じて送信され、両方のストリーム接続はストリームダッシュボード上に表示されます。

課金の観点からは、複数の接続を通じて受信したアクティビティ数について重複排除を行い、各ユニークなアクティビティごとに 1 回だけ請求されるようにしている点に注意してください。Decahose には 2 つのパーティションがあるため、以下に接続数がどのようにカウントされるかの例を示します。

Connect to decahose partition=1
Connect to decahose partition=1
Connect to decahose partition=2

上記の状況では、partition=1 への接続が 2 つ、partition=2 への接続が 1 つの合計 3 接続になります。通常は、各パーティションに対して同じ数の接続を持つことが望ましいため、この例は partition=2 への冗長接続が切断されており、さらに調査が必要な状況を示しています。

**復旧**

<div id="overview">
  #### 概要
</div>

Recovery は、最新の X の履歴データに対して、直近 5 日間のローリングウィンドウへのストリーミングアクセスを提供するデータ復旧ツールです（プライマリなデータ収集用途には使用しないでください）。このツールは、短時間の切断などによりリアルタイムストリームでデータを取り逃がした場合や、その他いかなる理由であっても一定期間リアルタイムデータの取り込みに失敗したシナリオにおいて、データを復旧するために利用してください。

<div id="using-recovery">
  #### Recovery の使用
</div>

Recovery ストリームを使うことで、アプリはリアルタイムストリームへのリクエストと同じ要領で、このストリームにリクエストを送信できます。ただし、アプリはリクエストしている時間範囲を示すパラメータを URL に指定する必要があります。言い換えると、Recovery リクエストは API に対して「時刻 A から時刻 B までの投稿」を要求します。これらの投稿は、その後、リアルタイムストリームを模倣する形でストリーミング接続経由で配信されますが、リアルタイムよりわずかに遅いペースで配信されます。以下に例を示します。

&quot;https://stream-data-api.x.com/stream/powertrack/accounts/someAccountName/publishers/twitter/powertrack.json?startTime=2023-07-05T17:09:12.070Z&quot;

投稿は、指定した期間の最初（最も古い）1 分から配信が開始され、最後の 1 分が配信されるまで時系列順に続きます。その時点で、Recovery Request Completed メッセージが接続経由で送信され、その後サーバーによって接続がクローズされます。リクエストの開始時刻が、マッチする結果がほとんど、またはまったく存在しない時間帯である場合、最初の結果が配信されるまでに一定の時間が発生する可能性があります。Recovery がその時点で処理しているアーカイブの部分でマッチを検出した時点で、データが配信されます。配信可能な結果がない場合でも、ストリームはタイムアウトを防ぐために、キャリッジリターン、つまり「heartbeats」を接続を通じて送り続けます。

Recovery は、短時間の切断によって取り逃したデータを簡単に回復するためのツールとして設計されており、1 日全体のような非常に長い期間を対象としたものではありません。長期間のデータ復旧が必要になった場合は、インターネットの不安定さなどの理由によりリクエスト処理中に切断される可能性を減らし、長時間のリクエストの進行状況を把握しやすくするために、長いリクエストを（例: 2 時間などの）より短い時間ウィンドウに分割することを推奨します。

<div id="data-availability">
  #### データ可用性
</div>

5 分間のバックフィルの猶予時間内に再接続できない場合でも、Recovery 機能を使用して直近 24 時間以内に取りこぼしたデータを復旧できます。

ストリーミング向け Recovery 機能を利用すると、バックフィルの猶予時間を 24 時間まで延長できます。Recovery を使用すると、取りこぼしたデータの期間を「リカバリ」できます。&#39;start&#95;time&#39; と &#39;end&#95;time&#39; リクエストパラメータを使用して接続リクエストを行うと、リカバリストリームが開始されます。接続が確立されると、Recovery は指定された期間のデータを再ストリーミングし、その後切断されます。  

Recovery には同時に 2 つまでリクエストでき、つまり「2 つのリカバリジョブ」を実行できます。Recovery は、開始時刻と終了時刻が定義される点を除き、技術的にはバックフィルと同じように動作します。1 回のリカバリ期間で扱えるのは 1 つの時間範囲のみです。

<div id="backfill">
  #### バックフィル
</div>

バックフィルをリクエストするには、接続リクエストに backfillMinutes=N パラメーターを追加する必要があります。ここで N は、接続が確立されたときにバックフィルする分数（1〜5、整数のみ）です。たとえば、90 秒間切断された場合は、接続リクエストに backfillMinutes=2 を追加する必要があります。このリクエストでは、切断前の 30 秒間を含めて 2 分間のバックフィルが提供されるため、*コンシューマーアプリは重複したデータを許容できる設計にしておく必要があります*。

5 分間のバックフィルをパーティション 1 に対してリクエストする Decahose 接続リクエスト URL の例は次のとおりです。

https://gnip-stream.x.com/stream/sample10/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json?partition=1&amp;backfillMinutes=5

**注意:**

* 接続するたびに常に「backfillMinutes=5」を使用し、提供される重複データをアプリ側で処理するという選択肢もあります。

* 5 分を超えて切断された場合は、Recovery を使用してデータを復元できます。

**切断からの復旧**

再起動および切断からの復旧には、いくつかの手順が含まれます。

* 切断時間の長さを判定する。
  * 5 分以内か？
    * ストリームで Backfill が有効になっている場合は、適切な「backfillMinutes」パラメーターを指定して接続リクエストを準備します。
  * 5 分を超えるか？
    * Recovery ストリームがある場合は、切断されていた時間帯に対して Recovery リクエストを行います（可能であれば、必要に応じて Rules API を使用し、現在のリアルタイムルールセットを用いて行うのが理想的です）。
* 新しい接続をリクエストします。

切断やダウンタイムが発生した場合、このような状況を軽減し、復旧するための戦略は次のとおりです。

1. **バックフィルを実装する**\
   バックフィルを使用すると、ストリーム接続から切断される前の時点から再接続することができ、最大 5 分間の切断をカバーできます。これは接続リクエストにパラメーターを含めることで実装します。

2. **別の場所から冗長ストリームを消費する**\
   冗長ストリームを同じ本番環境にストリーミングし、データの重複排除ができる場合、通常のストリームと冗長ストリームの両方で同時にダウンタイムや切断が発生しない限り、Recovery の必要性をなくすことができます。冗長ストリームを本番環境にライブでストリーミングできない場合は、別の「緊急用」データストアに書き込むことができます。その後、プライマリストリーム接続で切断やダウンタイムが発生した場合に、データが欠落している期間について、プライマリデータベースを補完するためのデータをシステム側で保持していることになります。

3. **Recovery を実装する**\
   切断やダウンタイムがプライマリストリームと冗長ストリームの両方に影響する場合は、Decahose Recovery を使用して欠落したデータを復旧します。API はアーカイブの 5 日間分をカバーするローリングウィンドウを提供しており、そのウィンドウのうち 1 時間以内の範囲をリクエストし、ストリーミングする形で利用するのが最適です。これはリアルタイムストリームと並行して実行します。Recovery が提供する 5 日間のウィンドウを超えた Decahose データを復旧する手段はないため、自社側で大きなダウンタイムが発生した場合にも完全なコピーを保持できるよう、冗長ストリームを利用することが重要です。

保存データ量に異常を検知したとき –\
切断やダウンタイムが発生していないにもかかわらずデータが欠落していることを検知するための、いくつかの方法は次のとおりです。

1. 受信した投稿数をカウントする\
   システムは取り込みアプリの最初の段階で受信した生の投稿数をカウントし、その数値を最終的なデータストアに到達した投稿数と比較できるようにするべきです。差分を監視し、それによって受信後にデータがドロップする原因となっている問題をチームに通知できるようにします。

2. 異常な保存ボリュームを分析する\
   最終的なデータベース内の保存データ量を分析し、異常な減少がないか確認することも検討してください。これも問題の兆候を示す場合がありますが、ボリュームの減少が正常である状況（例: X プラットフォームが利用不可であり、一定期間ユーザーが投稿を作成できない場合）も発生し得ます。

<div id="authentication">
  #### 認証[](#authentication- "Permalink to this headline")
</div>

Volume Stream API へのすべてのリクエストは、console.gnip.com のアカウントにログインする際に使用する有効なメールアドレスとパスワードの組み合わせから構成される HTTP Basic 認証を使用する必要があります。認証情報は、各リクエストで Authorization ヘッダーとして渡さなければなりません。そのため、すべての API リクエストに対して、クライアントが（HTTPS 上でエンコードされた認証情報を含む）&quot;Authorization: Basic&quot; HTTP ヘッダーを追加していることを確認してください。

#### GET {stream-type}:stream

Firehose ストリームへの常時接続を確立し、この接続を通じてリアルタイムデータが配信されます。

<div id="responses">
  #### レスポンス
</div>

これらのリクエストに対して、API からは次のレスポンスが返される可能性があります。ほとんどのエラーコードは、本文内に追加の詳細を含む文字列として返されます。200 以外のレスポンスの場合、クライアント側で再接続を試みてください。

| Status | Text | Description |
| :--- | :--- | :--- |
| 200 | Success | 接続が正常に確立され、新しいアクティビティが到着し次第送信されます。 |
| 401 | Unauthorized | 不正な認証情報により HTTP 認証に失敗しました。console.gnip.com にご利用の認証情報でログインし、リクエストで正しく使用できているか確認してください。 |
| 406 | Not Acceptable | 一般的には、ストリームからの gzip エンコードを受け付けるためのヘッダーをクライアントが正しく含めていない場合に発生しますが、その他の状況でも発生する可能性があります。  <br />  <br />「This connection requires compression. To enable compression, send an &#39;Accept-Encoding: gzip&#39; header in your request and be ready to uncompress the stream as it is read on the client end.」のような JSON メッセージが含まれます。 |
| 429 | Rate Limited | アプリが接続リクエストの上限を超えています。 |
| 503 | Service Unavailable | Twitter 側のサーバーの問題です。指数バックオフパターンで再接続してください。この問題に関する通知が [X API Status Page](https://api.twitterstat.us/) に掲載されておらず、10 分経過しても接続できない場合は、サポートまたは緊急連絡先にお問い合わせください。 |

<div id="replay-api">
  #### Replay API
</div>

Replay API は、リアルタイムの Volume ストリームを補完するうえで重要な機能です。Replay は、直近の X の履歴データを一定期間分含むローリングウィンドウへのストリーミングアクセスを提供するデータ復旧ツールです。

<div id="overview">
  ## 概要
</div>

`Enterprise`

*Enterprise API は、弊社が管理するアクセスレベルでのみ利用可能です。これらの API を利用するには、まず Enterprise 営業チームと連携してアカウントを開設する必要があります。詳細については [こちら](https://developer.x.com/en/products/x-api/enterprise) を参照してください。*

*X API におけるすべての検索用投稿オファリングは [こちら](/ja/x-api/enterprise-gnip-2.0/fundamentals/search-api) から確認できます。*

Enterprise 検索 API には 2 種類あります。

1. 30-Day Search API は、過去 30 日間のデータを提供します。
2. Full-Archive Search API は、2006 年 3 月の最初の投稿までさかのぼる、X の全データコーパスへの完全かつ即時のアクセスを提供します。

これらの RESTful API は、1 リクエストあたり最大 2,048 文字の単一クエリをサポートします。クエリは PowerTrack ルール構文で記述します。詳細は [Rules and filtering](/ja/x-api/enterprise-gnip-2.0/fundamentals/rules-filtering#getting-started-with-enterprise-rules-and-queries) を参照してください。ユーザーは 1 分単位の粒度で任意の期間を指定できます。ただし、レスポンスは、指定した maxResults または 31 日間のうち小さい方に制限され、次の結果セットをページングするための next トークンが含まれます。時間パラメータが指定されていない場合、API は直近 30 日間の一致するデータを返します。

Enterprise 検索 API は、低レイテンシかつ完全な忠実度で、1 分単位の粒度によるクエリベースの投稿アーカイブアクセスを提供します。投稿データは、クエリに一致する最新の投稿から始まり、逆時系列で提供されます。投稿は、公開後おおよそ 30 秒で検索 API から利用可能になります。

これらの検索エンドポイントは、編集された投稿のメタデータを提供します。2022 年 9 月 29 日以降に作成された投稿のすべてのオブジェクトには、その投稿が一度も編集されていない場合でも、投稿編集メタデータが含まれます。投稿が編集されるたびに、新しい投稿 ID が作成されます。投稿の編集履歴は、元の ID から始まる投稿 ID の配列によって記録されます。

これらのエンドポイントは常に、最新の編集内容と、存在する場合は編集履歴を返します。投稿が 30 分間の編集可能時間を過ぎて収集された場合、その投稿は最終版を表すことになります。編集された投稿のメタデータについて詳しくは、[Edit Posts fundamentals](/ja/x-api/fundamentals/edit-posts) ページを参照してください。

リクエストには、API レスポンスごとに返す投稿の最大数を指定する maxResults パラメータが含まれます。クエリに紐づく投稿数が、レスポンスごとのこの最大件数を超える場合、レスポンスには next トークンが含まれます。これらの next トークンは、後続のリクエストで使用し、そのクエリに関連付けられた投稿の全セットをページングして取得します。

これらの Enterprise 検索 API には、クエリに関連するデータボリュームをリクエストできる *counts* エンドポイントが用意されています。 

<div id="request-types">
  ### リクエストのタイプ
</div>

Enterprise Search API では、2つのタイプのリクエストをサポートしています。

<div id="search-requests-data">
  #### Search requests (data)
</div>

enterprise search API への Search リクエストでは、指定した期間について、1 回のレスポンスあたり最大 500 件の結果を取得でき、ページネーションによって追加の data を取得することもできます。`maxResults` パラメータを使用すると、表示用途のケース向けに小さいページサイズを指定したり（必要に応じてユーザーがさらに結果を要求できるようにする）、より大量の data を取得する用途で大きいページサイズ（最大 500 まで）を指定したりできます。data は新しいものから順に配信され、配信時点でコンプライアンス要件を満たしています。

<div id="counts-requests-post-count">
  #### カウントリクエスト（投稿数のカウント）
</div>

カウントリクエストを使用すると、過去のアクティビティ数（履歴データ）を取得できます。これは、指定した期間内に、指定したクエリにマッチしたアクティビティが発生した回数を表します。レスポンスでは、日単位、時間単位、または分単位（デフォルトのバケットは *hour*）で区切られたカウントのヒストグラムが返されます。なお、カウント結果は、投稿が公開されてからかなり後（7日以上）に発生するコンプライアンスイベント（例：投稿の削除）を常に反映するわけではありません。そのため、同じクエリに対する data リクエストの結果と、カウント指標の値が常に一致するとは限りません。

**課金に関する注意:** data エンドポイントおよび counts エンドポイントに対して行われる各リクエストは、*ページネーション用のリクエストを含めて*、課金対象のリクエストとしてカウントされます。したがって、1 つのクエリに対して複数ページの結果が存在する場合、結果の X ページを順に取得すると、課金上は X 回のリクエストに相当します。

* 最初のジオタグ付き投稿: 11/19/2009
* フィルタリング用に URL が初めてインデックスされた日: 8/27/2011
* 強化された URL 展開メタデータ（ウェブサイトのタイトルと説明）: 12/1/2014
* プロフィール位置情報の拡張メタデータおよびフィルタリング: 2/17/2015

<div id="data-updates-and-mutability">
  ### データの更新と可変性
</div>

Enterprise 検索 API では、投稿内の一部のデータは可変、つまり初回アーカイブ後に更新または変更される可能性があります。

この可変なデータは次の 2 つのカテゴリに分類されます。

* User オブジェクトのメタデータ:
  * ユーザーの @handle（数値 id は決して変わりません）
  * 自己紹介（Bio）説明文
  * 各種カウント: 投稿数、フォロワー数、フォロー数、いいね数、リスト数
  * プロフィールの所在地
  * タイムゾーンや言語などのその他の詳細
* 投稿の統計情報 — つまり、ユーザーの操作によってプラットフォーム上で変更され得るもの（以下は例）:
  * いいね数
  * リツイート数

これらの多くの場合、検索 API は、投稿生成時点ではなく、*クエリ実行時* にプラットフォーム上に存在するデータを返します。ただし、特定の演算子（例: from、to、@、is:verified）を使用するクエリの場合は、これが当てはまらないことがあります。インデックス上のデータは定期的に更新されており、最新の期間に対しては更新頻度が高くなっています。その結果、返されるデータが、X.com 上に現在表示されているデータと完全には一致しない場合がありますが、最後にインデックスが更新された時点のデータとは一致します。

この不一致の問題は、演算子が可変データに適用されるクエリにのみ発生する点に注意してください。一例としてユーザー名でのフィルタリングが挙げられ、この場合の最善の回避策は、@handle ではなくユーザーの数値 id を使用してクエリを行うことです。

<div id="single-vs-multi-threaded-requests">
  ### 単一スレッド vs. マルチスレッドのリクエスト
</div>

各お客様には、検索エンドポイントに対して定義されたレート制限があります。Full-Archive search のデフォルトの 1 分あたりのレート制限は 1 分あたり 120 リクエストで、平均すると 1 秒あたり 2 クエリ (QPS) となります。この平均 QPS は、理論上は毎秒 2 件のリクエストを API に対して行えることを意味します。本プロダクトのページネーション機能を考えると、1 年分のクエリに関連付けられた投稿が 100 万件あり、それが 1 年を通して均等に分布している場合、すべてのデータを受け取るには 2,000 件以上のリクエストが必要になります（`maxResults` を 500 と仮定）。1 レスポンスあたり 2 秒かかると仮定すると、合計で 4,000 秒（約 1 時間強）かけて、単一スレッドで逐次・直列に（直前のレスポンスの `next` トークンを使い、1 秒あたり 1 リクエストで）すべてのデータを取得することになります。悪くありません。

次に、12 本の並列スレッドを使用してデータを受信する状況を考えます。100 万件の投稿が 1 年間に均等に分布していると仮定すると、リクエストを 12 本の並列スレッド（マルチスレッド）に分割し、単一の「ジョブ」に対して 1 秒あたりのレート制限をより多く活用できます。言い換えれば、対象とする各月ごとに 1 本のスレッドを実行することで、データを 12 倍の速度（約 6 分）で取得することができます。

このマルチスレッドの例は、counts エンドポイントにも同様に当てはまります。たとえば、2 年間の期間について投稿数を取得したい場合、単一スレッドのリクエストを行い、31 日単位で counts をさかのぼってページングすることができます。1 レスポンスあたり 2 秒かかると仮定すると、24 件の API リクエストを行い、counts 全体を取得するのに約 48 秒かかります。しかし、同時に複数の 1 か月単位のリクエストを行うことも可能です。1 秒あたり 12 件のリクエストを行う場合、counts 全体を約 2 秒で取得できます。

<div id="retry-logic">
  ### リトライロジック
</div>

エンタープライズ検索 API で 503 エラーが発生した場合、多くは一時的なエラーであり、短時間待ってからリクエストを再試行することで解決できます。

リクエストが連続して 4 回失敗し、かつ各失敗の間に少なくとも 10 分待っている場合は、次の手順でトラブルシューティングを行ってください。

* 対象としている時間範囲を短くしてから、リクエストを再試行します。うまくいかない場合は、最短で 6 時間の時間ウィンドウになるまで繰り返します。
* 多数の検索語を OR 条件で結合している場合は、それらを個別のルールに分割し、それぞれを個別に再試行します。
* ルール内で多数の除外条件を使用している場合は、ルール内の否定条件の数を減らしてから再試行します。

<div id="getting-started-with-enterprise-search-posts-30-day-api">
  ### enterprise Search Posts: 30-Day API の利用を開始する
</div>

enterprise Search Posts: 30-Day API は、直近 30 日以内に作成された投稿を取得できる API です。投稿は、リクエストで指定したクエリに基づいてマッチングされて返されます。クエリとは、取得する投稿にどのような内容が含まれているべきかを定義するルールです。このチュートリアルでは、X アカウント @XDevelopers から英語で投稿された投稿を検索します。

レスポンスとして返される投稿は、投稿の完全なペイロードを提供する data 形式か、マッチした投稿の数値カウントデータを返す counts 形式のいずれかになります。ここでは、cURL を使用して data エンドポイントと counts エンドポイントにリクエストを送信します。

次のものが必要です:

* [エンタープライズアカウント]https://developer.x.com/en/products/x-api/enterprise
* ユーザー名、パスワード、およびアカウント名
* console.gnip.com に表示される、検索エンドポイントに関連付けられたラベル

<div id="accessing-the-data-endpoint">
  #### data エンドポイントへのアクセス
</div>

data エンドポイントは、一致した投稿 (Post) の完全なペイロードを提供します。ここでは、`from:` と `lang:` 演算子を使用して、@XDevelopers からの英語の投稿を検索します。 *利用できる演算子の詳細については [こちら](/ja/x-api/enterprise-gnip-2.0/fundamentals/search-api#enterprise-operators) を参照してください。*

<Tabs>
  <Tab title="cURL">
    *cURL は、URL 構文を使ってファイルを取得または送信するためのコマンドラインツールです。*

    次の項目を変更したうえで、以下の cURL リクエストをコマンドラインにコピーして実行します。

    * **Username** `<USERNAME>` 例: `email@domain.com`

    * **Account name** `<ACCOUNT-NAME>` 例: `john-doe`

    * **Label** `<LABEL>` 例: `prod`

    * **fromDate and toDate** 例: `"fromDate":"201811010000", "toDate":"201811122359"`

    *リクエストを送信すると、パスワードの入力を求められます。*

    ```bash
    curl -X POST -u<USERNAME> "https://gnip-api.x.com/search/30day/accounts/<ACCOUNT-NAME>/<LABEL>.json" -d '{"query":"from:TwitterDev lang:en","maxResults":"500","fromDate":"<yyyymmddhhmm>","toDate":"<yyyymmddhhmm>"}'
    ```
  </Tab>

<div id="getting-started-with-enterprise-search-posts-full-archive-api">
  ### enterprise Search Posts: Full-Archive API を使い始める
</div>

enterprise Search Posts: Full-Archive API は、2006 年に最初の投稿が行われて以降のすべての投稿にアクセスできるようにします。投稿は、リクエストで指定したクエリに基づいて照合され、その結果が返されます。クエリとは、取得する投稿に何が含まれているべきかを定義するルールのことです。このチュートリアルでは、X アカウント @XDevelopers から英語で投稿された投稿を検索します。

レスポンスペイロードで受け取る投稿は、完全な投稿ペイロードを取得できる data 形式か、マッチした投稿の件数を数値で返す counts 形式のいずれかになります。ここでは、cURL を使用して data エンドポイントと counts エンドポイントにリクエストを送信します。

次のものが必要です:

* [An enterprise account]https://developer.x.com/en/products/x-api/enterprise
* ユーザー名、パスワード、およびアカウント名
* console.gnip.com に表示される、検索エンドポイントに関連付けられたラベル

<div id="product-overview">
  ### プロダクト概要
</div>

エンタープライズ向けの Full-archive Search は 2015 年 8 月に、プレミアム向けバージョンは 2018 年 2 月にリリースされました。これらの検索プロダクトにより、顧客は公開されている任意の投稿へ即時にアクセスできます。Full-archive Search では、1 つのクエリを送信し、クラシックな RESTful スタイルでレスポンスを受け取ります。Full-archive Search は、1 レスポンスあたり最大 500 件の投稿を返すページネーションを実装しており、プレミアムでは 1 分あたり最大 60 リクエスト（rpm）、エンタープライズでは 120 rpm のレート制限をサポートします。これらの仕様から、Full-archive Search を使用すると、同時リクエストを用いて、大規模かつ高速に投稿を取得できます。

ディスク上の投稿フラットファイル群に基づくアーカイブを持つ Historical PowerTrack とは異なり、Full-archive Search の投稿アーカイブはオンラインデータベースに非常によく似ています。他のあらゆるデータベースと同様に、その内容に対するクエリをサポートします。また、高性能なデータ取得を可能にするために *index* を利用しています。Full-archive Search エンドポイントでは、クエリ言語は PowerTrack Operators で構成されており、各 Operator はインデックスされた投稿の JSON 属性に対応しています。

また、Historical PowerTrack と同様に、クエリを実行した時点の最新状態を表す投稿属性も存在します。たとえば、Search API を使用して、今、2010 年に投稿された投稿へアクセスする場合、そのユーザーのプロフィール説明、アカウントの「ホーム」ロケーション、表示名、およびお気に入り数とリツイート数に関する投稿メトリクスは、2010 年当時の値ではなく、現在時点の値に更新されたものになります。 

<div id="metadata-timelines">

</div>

以下は、Full-archive search エンドポイントの Operator がマッチングを開始した時期のタイムラインです。いくつかのケースでは、Operator のマッチング開始は、X 上で「コミュニケーション上の慣習」が一般的になってからかなり *後* になります。たとえば、@Replies は 2006 年にユーザーによる慣習として登場しましたが、「サポートする」JSON を伴った *第一級オブジェクト* や *イベント* になったのは 2007 年初頭でした。そのため、2006 年の @Replies にマッチさせるには、`to:` や `in_reply_to_status_id:` といった PowerTrack Operator に頼るのではなく、投稿本文を精査する必要があります。

ここで提示している詳細は、数百回におよぶ Full-Archive Search の実行結果から生成されたものです。このタイムラインは 100% 完全かつ正確というわけではありません。もし、あなたのユースケースにとって重要な、別のフィルタリング／メタデータの「誕生日」を見つけた場合は、お知らせください。

<div id="filtering-tips">
  ### フィルタリングのヒント
</div>

ここまで説明してきたタイムライン情報から、Search API フィルターを作成する際に考慮すべき細かな点が多いことが分かります。特に重要なポイントは次の 2 つです。

* 一部のメタデータには「生成開始日（born-on 日付）」があるため、フィルター結果に *偽陰性* が含まれる可能性があります。このような検索には、検索対象期間の一部または全部では存在していなかったメタデータに依存するオペレーターが含まれます。たとえば、`has:images` オペレーターを使用して投稿を検索する場合、2011 年 7 月以前の期間には一致するものがありません。これは、そのオペレーターが *ネイティブ* 写真（X のユーザーインターフェースを使って投稿に添付された写真）に対してマッチするためです。写真共有投稿の、より完全なデータセットを取得するには、2011 年 7 月以前を対象にするフィルターには、写真ホスティングサービスで一般的な URL にマッチするルール句を含める必要があります。
* 一部のメタデータは、その投稿が X に投稿された時点よりも *後* の時点に作成されたメタデータでバックフィルされています。

PowerTrack クエリを作成する際によく注目される属性タイプがいくつかあります。

* X Profiles
* オリジナル投稿か共有投稿か
* 投稿の言語分類
* 位置情報付き投稿
* 共有リンクに含まれるメディア

これらの中にはプロダクト固有の挙動を持つものもあれば、共通の挙動をするものもあります。詳細は以下を参照してください。

<div id="x-profiles">
  #### X プロフィール
</div>

Search API は、ユーザーのプロフィールのデータセットを *取得時点* の状態のまま、過去の投稿とともに返します。たとえば 2014 年の投稿をリクエストした場合でも、ユーザーのプロフィールメタデータはクエリ時点での状態を反映します。

<div id="original-posts-and-retweets">
  #### オリジナル投稿とリツイート
</div>

PowerTrack `_is:retweet_` オペレーターを使用すると、リツイートを含めるか除外するかを指定できます。このオペレーターを利用する場合、2009 年 8 月以前のデータについては、リツイートをマッチさせる場合とマッチさせない場合の両方に対応する 2 つの戦略が必要です。2009 年 8 月以前では、投稿メッセージ自体に対して「@RT 」パターンとの完全一致検索を行ってチェックする必要があります（実際には、2009 年 5〜8 月のリツイートをフィルタリングする場合、「Via @」パターンも含める必要があります）。2009 年 8 月以降の期間については、*is:retweet* オペレーターを利用できます。

<div id="post-language-classifications">
  #### 投稿の言語分類
</div>

投稿の言語分類でフィルタリングする場合、X の従来プロダクト間で仕様が大きく異なります。Search アーカイブが構築された際には、すべての投稿に対して X の言語分類がバックフィルされました。そのため、`lang:` オペレーターは投稿アーカイブ全体で利用できます。

<div id="geo-referencing-posts">
  #### 投稿の位置情報参照（ジオリファレンス）
</div>

投稿の位置情報を参照する主な方法は 3 つあります。

* **投稿本文中の地理的な言及。** 投稿本文中に含まれる地名などの地理的な言及にマッチさせる方法です。ローカルな知識に依存するため最も難易度が高い方法になることが多い一方で、すべての投稿アーカイブに対して利用できるオプションです。[こちら](https://x.com/biz/statuses/28311) は 2006 年のサンフランシスコ地域の例で、「golden gate」フィルターに基づく位置情報参照マッチです。

* **ユーザーによって位置情報タグ（ジオタグ）が付けられた投稿。** 検索 API では、2010 年 3 月から一部の Geo Operator を使って位置情報付きの投稿にマッチできるようになり、その後 2015 年 2 月に他の Operator が追加されました。

  * 2010 年 3 月 6 日: `has:geo`、`bounding_box:`、`point_radius:`
  * 2015 年 2 月 17 日: `place_country:`、`place:`

* **ユーザーによって設定されたアカウントプロフィールの「ホーム」位置情報。** Profile Geo Operator は Historical PowerTrack と Search API の両方で利用可能です。Search API では、これらの Profile Geo メタデータは 2015 年 2 月から利用できます。Profile Geo メタデータが利用可能になる前に投稿された投稿に対しては、正規化されていないユーザー入力にマッチさせるために使用できる `bio_location:` Operator が利用可能です。

<div id="shared-links-and-media">
  #### 共有リンクとメディア
</div>

2012年3月に、展開済み URL エンリッチメントが導入されました。この時点より前は、投稿ペイロードにはユーザーが指定した URL のみが含まれていました。そのため、ユーザーが短縮 URL を含めていた場合、関心のある（展開済みの）URL と照合するのが難しい場合があります。Search API では、これらのメタデータは 2012年3月以降に利用可能です。

2016年7月に、強化された URL エンリッチメントが導入されました。この強化版では、投稿ペイロードにウェブサイトの HTML の title と説明が含まれ、それらに対して照合するためのオペレーターも提供されます。これらのメタデータは、2014年12月から付与され始めます。

2016年9月、X は「ネイティブ添付ファイル」を導入し、末尾にある共有リンクが 140 文字の投稿文字数制限にカウントされないようになりました。これらの共有リンクに対しても、両方の URL エンリッチメントが引き続き適用されます。

関連する Search オペレーターが照合を開始するタイミングは次のとおりです。

* 2006年10月26日 - `has:links`
* 2011年7月20日 - `has:images` および `has:media`
* 2011年8月 - `url:` と [Expanded URLs enrichment](/ja/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments)。早ければ 2006年9月から `(url:"spotify.com" OR url:gnip OR url:microsoft OR url:google OR url:youtube)` は http://x.com/Adam/statuses/16602 に一致します。これは、twitter&#95;entities と gnip オブジェクトに urls[] メタデータが存在しない場合でも同様です。&quot;youtube.com&quot; は、urls[] メタデータが一切なくても url:youtube に一致するメッセージコンテンツの一例です。
* 2015年2月10日 - ネイティブ動画向け `has:videos`。2010/08/28 から 2015/02/10 の間、このオペレーターは youtube.com、vimeo.com、vivo.com などの一部の動画ホスティングサイトへのリンクを含む投稿に一致します。
* 2016年5月1日 - [Enhanced URLs enrichment](/ja/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments) に基づく `url_title:` および `url_description:` が一般提供開始。最初の強化 URL メタデータは 2014年12月から出現し始めました。

  <Accordion title="data エンドポイントで取得できる投稿数が、counts エンドポイントで得られる投稿数と一致しません。なぜこのようなことが起きるのですか？">
    counts エンドポイントと data エンドポイントが返す結果には、既知の違いがあります。counts エンドポイントはコンプライアンス適用前（削除された投稿や位置情報の削除などを考慮しない状態）のデータを返す一方で、data エンドポイントは配信時点でコンプライアンスが適用され、すべてのコンプライアイベントを反映しているため、結果に不一致が生じる場合があります。
  </Accordion>

  <Accordion title="クエリに一致するはずの投稿が返ってきません。なぜですか？">
    これが発生した理由として、いくつかの可能性が考えられます。

    1. 期待していた投稿が、非公開アカウントからの投稿である
    2. data エンドポイントがすべてのコンプライアンスイベントを考慮しているため（つまり、削除された投稿や位置情報の削除などはレスポンスに含まれません）。

<div id="enterprise-search-apis">
  ### エンタープライズ検索 API
</div>

エンタープライズ検索 API には 2 種類あります。

* 30-Day Search API - 直近 30 日間に投稿されたツイートを提供します。
* Full-Archive Search API - 2006 年 3 月に最初のツイートが投稿された時点までさかのぼり、2006 年以降のツイートを提供します。

これらの検索 API は共通の設計に基づいており、以下のドキュメントは両方に適用されます。なお、2022 年 9 月 29 日以降に作成されたツイートについては、その編集履歴を記述する編集メタデータが Tweet オブジェクトに含まれます。詳細については、[&quot;Edit Tweets&quot;](/ja/x-api/enterprise-gnip-2.0/fundamentals/edit-tweets) の基礎編ページを参照してください。

以下に、エンタープライズ検索 API と統合する際に必要となる重要なポイントを示します。

* ツイートデータおよび件数をリクエストするメソッド
* 認証
* ページネーション
* API リクエストパラメータとリクエスト例
* API レスポンス JSON ペイロードとレスポンス例
* HTTP レスポンスコード

エンタープライズ API は、ツイートアーカイブへの低レイテンシで完全忠実な、クエリベースのアクセスを提供します。2 つの API の唯一の違いは検索できる期間であり、直近 30 日間か、2006 年までさかのぼるかの違いです。期間は分単位の粒度で指定できます。ツイートデータは、クエリにマッチする最新のツイートから始まり、新しいものから順に逆時系列で返されます。ツイートは、公開後おおよそ 30 秒で検索 API から利用可能になります。

<div id="methods">
  #### メソッド
</div>

エンタープライズ検索のベース URI は `https://gnip-api.x.com/search/` です。

| メソッド | 説明 |
| :--- | :--- |
| [POST /search/:product/accounts/:account&#95;name/:label](#SearchRequests) | 指定された PowerTrack ルールに一致する、過去 30 日間のツイートを取得します。 |
| [POST /search/:product/accounts/:account&#95;name/:label/counts](#CountRequests) | 指定された PowerTrack ルールに一致する、過去 30 日間のツイート数を取得します。 |

ここで:

* `:product` は、リクエスト先の検索エンドポイントを示し、`30day` または `fullarchive` のいずれかです。
* `:account_name` は、console.gnip.com に表示される、アカウントに紐づく（大文字と小文字が区別される）名前です。
* `:label` は、console.gnip.com に表示される、検索エンドポイントに紐づく（大文字と小文字が区別される）ラベルです。

たとえば、TwitterDev アカウントがラベル &#39;prod&#39;（production の略）付きの 30 日間検索プロダクトを利用している場合、検索エンドポイントは次のようになります。

* データエンドポイント: [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json)
* カウントエンドポイント: [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json)

エンタープライズ検索 API の完全なエンドポイントは [https://console.gnip.com](https://console.gnip.com) に表示されます。

以下に、curl というシンプルな HTTP ユーティリティを使った、いくつかのリクエスト例を示します。これらの例では、URL 内に `:product`、`:account_name`、および `:label` を使用しています。これらの例を使用するには、URL を自身の情報に合わせて更新してください。

<div id="authentication">
  #### 認証
</div>

Enterprise search API へのすべてのリクエストは、[https://console.gnip.com](https://console.gnip.com) のアカウントにログインする際に使用する有効なメールアドレスとパスワードの組み合わせから構成される、HTTP の *Basic Authentication* を使用する必要があります。認証情報は、各リクエストの *Authorization* ヘッダーに指定しなければなりません。

<div id="requestresponse-behavior">
  #### リクエスト／レスポンスの動作
</div>

`fromDate` と `toDate` パラメータを使うことで、API がサポートする任意の期間をリクエストできます。30-Day search API は直近 31 日分のツイートを提供します（「30-Day」API と呼ばれていますが、ユーザーが 1 か月分を完全な形でリクエストできるように 31 日分を利用可能にしています）。Full-Archive search API は、最初のツイート（2006 年 3 月 21 日）までさかのぼったツイートを提供します。ただし、1 回のレスポンスで返されるツイートは、指定した `maxResults` または 31 日分のうち小さい方に制限されます。条件に一致するデータ量や指定した期間が、指定した `maxResults` もしくは 31 日分を超える場合、指定した期間の残りをページネーションで取得するために使用すべき &#39;next&#39; トークンが返されます。

たとえば、Full-Archive search を使用して、2017 年 1 月 1 日から 2017 年 6 月 30 日までの間で、クエリに一致するすべてのツイートを取得したいとします。リクエストでは、`fromDate` と `toDate` パラメータを使用して、その 6 か月間全体を指定します。search API は、`maxResults` パラメータ（デフォルトは 100）で指定された件数分のツイートを含む最初の「ページ」を返します。さらにツイートが存在する（可能性は高い）場合、API は次の「ページ」のデータをリクエストできるようにする &#39;next&#39; トークンも返します。この処理は、API が &#39;next&#39; トークンを返さなくなるまで繰り返されます。詳細については次のセクションを参照してください。

<div id="pagination">
  #### ページネーション
</div>

data リクエストと count リクエストの両方を行う場合、1 回のレスポンスですべてを返せないほど多くのデータが存在する可能性があります。その場合、レスポンスには「next」トークンが含まれます。「next」トークンはトップレベルの JSON 属性として提供されます。「next」トークンが提供されている場合は、取得すべき追加データがあることを意味するため、API リクエストを継続して送信する必要があります。

**注:** 「next」トークンの動作は、data リクエストと count リクエストでわずかに異なります。両方の動作については、以下の APIリファレンス セクションで、例となるレスポンスとともに説明します。

<div id="data-pagination">
  ##### データのページネーション
</div>

データをリクエストすると、1 回のレスポンスで返せる量を超えるデータが生成される可能性があります。各データリクエストには、1 回のリクエストで返される最大ツイート数を設定するパラメータが含まれています。この `maxResults` パラメータのデフォルト値は 100 で、10～500 の範囲で設定できます。リクエストで使用した `maxResults` パラメータよりも多くのツイートがクエリに一致した場合、レスポンスには（ルートレベルの JSON 属性として）`next` トークンが含まれます。この `next` トークンは後続のリクエストで使用し、そのクエリに一致するツイートの次の部分（つまり次の「ページ」）を取得するために使われます。`next` トークンは、そのクエリの結果の最後の「ページ」に到達し、`next` トークンが提供されなくなるまで返され続けます。

次のデータ「ページ」をリクエストするには、元のクエリとまったく同じ内容のリクエストを行う必要があります。`query`、`toDate`、`fromDate` パラメータを使用している場合はそれらも含め、さらに前回のレスポンスで返された値を設定した `next` リクエストパラメータも含める必要があります。これは GET リクエストまたは POST リクエストのいずれでも利用できます。ただし、GET リクエストの場合、`next` パラメータは URL エンコードされている必要があります。

クエリで対象としている期間に含まれるすべてのツイートを取得するまで、前回のクエリから返された `next` パラメータを渡し続けることができます。`next` パラメータを含まないレスポンスを受け取った場合、それは最後のページに到達しており、指定したクエリと期間に対して利用可能な追加のデータがないことを意味します。

<div id="counts-pagination">
  ##### カウントのページネーション
</div>

`counts` エンドポイントは、クエリに紐づくツイート数を日次、時間単位、または分単位のいずれかで提供します。`counts` API エンドポイントは、最大 31 日分のカウントをペイロードとして、タイムスタンプ付きのカウント配列を返します。31 日を超える期間のカウントをリクエストした場合、`next` トークンが返されます。`data` の `next` トークンと同様に、元のクエリとまったく同じ内容のクエリを実行し、前回のレスポンスで返された値を設定した `next` リクエストパラメータも含める必要があります。

31 日を超えるカウントをリクエストする場合とは別に、`next` トークンが返されるもう 1 つのシナリオがあります。ボリュームの多いクエリでは、カウントの生成に時間がかかりすぎてレスポンスのタイムアウトが発生する可能性があります。この場合、31 日分より少ないカウントしか受け取れませんが、全カウント・ペイロードを取得し続けられるように `next` トークンが返されます。***重要:*** タイムアウト時には常に、完全な「バケット」単位でのみ返されます。そのため、2.5 日分の期間であれば、2 日分の完全な「バケット」が返されます。

<div id="additional-notes">
  ##### 追加の注意事項
</div>

* 検索リクエストで fromDate または toDate を使用する場合、指定した時間範囲内に含まれる結果のみが取得されます。時間範囲内の最後の結果グループに到達すると、&#39;next&#39; トークンは返されません。
* &#39;next&#39; 要素は、10〜500 の任意の maxResults 値（デフォルト値は 100）とともに使用できます。maxResults は各レスポンスで返されるツイート数を決定しますが、最終的にすべての結果を取得することを妨げるものではありません。
* &#39;next&#39; 要素には有効期限がありません。同じ &#39;next&#39; クエリを使用した複数のリクエストは、リクエストしたタイミングに関係なく同じ結果を受け取ります。
* &#39;next&#39; パラメータを使用して結果をページングする際、クエリの境界付近で重複が発生する場合があります。アプリケーションはこれらの重複を許容できるように実装する必要があります。

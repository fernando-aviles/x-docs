<div id="overview">
  ## Overview
</div>

`Enterprise`

*エンタープライズ API は、当社の管理対象アクセスレベルでのみ利用できます。これらの API を利用するには、まずエンタープライズ営業チームとアカウントを開設する必要があります。詳しくは [こちら](https://developer.x.com/en/products/x-api/enterprise) をご覧ください。*

*X API の投稿検索プロダクトの一覧は [こちら](/ja/x-api/enterprise-gnip-2.0/fundamentals/search-api) から確認できます。*

エンタープライズ検索 API には 2 種類あります。

1. 30-Day Search API は、直近 30 日分のデータを提供します。
2. Full-Archive Search API は、2006 年 3 月の最初の投稿までさかのぼる、X の全データコーパスへの完全かつ即時のアクセスを提供します。

これらの RESTful API では、1 回のリクエストにつき最大 2,048 文字の単一クエリをサポートします。クエリは PowerTrack ルール構文で記述します。詳細は [Rules and filtering](/ja/x-api/enterprise-gnip-2.0/fundamentals/rules-filtering#getting-started-with-enterprise-rules-and-queries) を参照してください。ユーザーは、最小で 1 分単位の任意の期間を指定できます。ただし、レスポンスは、指定した maxResults と 31 日のうち小さい方に制限され、次の結果セットをページングするための next トークンが含まれます。時間パラメータを指定しない場合、API は直近 30 日分の一致するデータを返します。

エンタープライズ検索 API は、分単位の粒度で投稿アーカイブへの低レイテンシかつ完全忠実なクエリベースアクセスを提供します。投稿データは、クエリに一致する最新の投稿から始まり、逆時系列順で提供されます。投稿は、公開されてから約 30 秒後に検索 API から利用可能になります。

これらの検索エンドポイントは、投稿の編集メタデータを提供します。2022 年 9 月 29 日以降に作成された投稿のすべてのオブジェクトには、投稿が一度も編集されていない場合でも、投稿の編集メタデータが含まれます。投稿が編集されるたびに、新しい投稿 ID が作成されます。投稿の編集履歴は、元の ID から始まる投稿 ID の配列として記録されます。

これらのエンドポイントは常に、最新の編集と、存在する場合は編集履歴を返します。30 分の編集ウィンドウ経過後に収集された投稿は、その最終版を表します。投稿の編集メタデータについて詳しくは、[Edit Posts fundamentals](/ja/x-api/fundamentals/edit-posts) ページを参照してください。

リクエストには、API レスポンスごとに返す投稿の最大数を指定する maxResults パラメータが含まれます。クエリに関連する投稿が、1 レスポンスあたりのこの最大結果数を超える場合、レスポンスには next トークンが含まれます。これらの next トークンは、後続のリクエストで使用し、クエリに関連する投稿の全セットをページングするために利用します。

これらのエンタープライズ検索 API には、クエリに関連するデータ量をリクエストできる *counts* エンドポイントが用意されています。 

<div id="request-types">
  ### リクエストのタイプ
</div>

エンタープライズ検索 API では、2 つのタイプのリクエストがサポートされています。

<div id="search-requests-data">
  #### Search requests (data)
</div>

Enterprise search API への検索リクエストでは、指定した時間範囲に対して 1 回のレスポンスあたり最大 500 件の結果を取得でき、ページネーションによって追加の data を取得することもできます。`maxResults` パラメータを使用すると、表示用途ではより小さいページサイズを指定して（必要に応じてユーザーがさらに結果を要求できるようにし）、大規模なデータ取得ではより大きいページサイズ（最大 500）を指定できます。data は新しいものから古いものへの逆時系列で配信され、配信時点でコンプライアンス要件を満たしています。

<div id="counts-requests-post-count">
  #### カウントリクエスト（投稿数カウント）
</div>

カウントリクエストを使用すると、指定した期間内に特定のクエリに一致したアクティビティの件数（履歴アクティビティ数）を取得できます。レスポンスには、日・時間・分のいずれかの単位で区切られたカウントのヒストグラムが返されます（デフォルトのバケットは *hour*）。カウント結果は、投稿が公開されてからかなり後（7 日以上）に発生するコンプライアンスイベント（例: 投稿の削除）を常に反映しているとは限らない点に注意してください。そのため、同じクエリに対する data リクエストの結果と、カウントの値が常に一致するとは限りません。

**課金に関する注意:** data エンドポイントおよび counts エンドポイントに対して行われる各リクエスト（*ページネーション用のリクエストも含む*）は、課金対象のリクエストとしてカウントされます。したがって、1 つのクエリに対して複数ページの結果がある場合、結果の X ページをページングして取得すると、課金上は X 件のリクエストとなります。

<div id="data-updates-and-mutability">
  ### データの更新と可変性
</div>

エンタープライズ検索 API では、投稿内の一部のデータは可変（mutable）であり、初回アーカイブ後に更新または変更される可能性があります。

この可変データは、次の 2 つのカテゴリに分類されます。

* User オブジェクトのメタデータ:
  * ユーザーの @handle（数値 ID は決して変わりません）
  * 自己紹介（Bio）の説明文
  * カウント: ステータス、フォロワー、フォロー、いいね、お気に入り、リスト
  * プロフィールの場所
  * タイムゾーンや言語などのその他の詳細情報
* 投稿の統計情報 - つまり、ユーザーの操作によってプラットフォーム上で変更され得るもの（以下は例）:
  * いいね数（お気に入り数）
  * リツイート数

これらの多くの場合、検索 API は、投稿が生成された時点ではなく、*クエリ実行時* にプラットフォーム上に存在するデータを返します。ただし、select オペレーター（例: from, to, @, is:verified）を使用したクエリでは、この限りではない場合があります。データはインデックス内で定期的に更新されており、直近の期間については更新頻度が高くなっています。その結果として、返されるデータが X.com 上に現在表示されているデータと完全には一致せず、最後にインデックスされた時点のデータと一致している場合があります。

なお、この不一致の問題は、オペレーターが可変データに適用されるクエリにのみ当てはまります。たとえばユーザー名でのフィルタリングが該当し、この場合の最善の回避策は、@handle ではなくユーザーの数値 ID を使用してクエリを実行することです。

<div id="single-vs-multi-threaded-requests">
  ### シングルスレッドリクエストとマルチスレッドリクエスト
</div>

各顧客には、検索エンドポイントに対してレート制限が定義されています。Full-Archive Search の 1 分あたりのデフォルトレート制限は 1 分あたり 120 リクエストで、平均すると 1 秒あたり 2 クエリ（QPS）になります。この平均 QPS（Queries Per Second）は、理論上、毎秒 2 件のリクエストを API に送信できることを意味します。このプロダクトのページネーション機能を踏まえると、1 年分のクエリに関連づけられた投稿が 100 万件あり、それが 1 年間に均等に分布している場合、すべてのデータを取得するには 2,000 件超のリクエストが必要になります（`maxResults` を 500 と仮定）。1 レスポンスあたり 2 秒かかると仮定すると、単一スレッド（直前のレスポンスの &quot;next&quot; トークンを使って 1 秒あたり 1 リクエスト）でそれらすべてのデータを逐次的／直列に取得するには 4,000 秒（約 1 時間強）かかる計算になります。悪くはありません。

次に、12 本の並列スレッドを使ってデータを取得する状況を考えてみます。100 万件の投稿が 1 年間に均等に分布していると仮定すると、リクエストを 12 本の並列スレッド（マルチスレッド）に分割し、単一の「ジョブ」に対する 1 秒あたりのレート制限をさらに活用できます。言い換えると、関心のある各月ごとに 1 本のスレッドを実行することで、データを 12 倍の速度（約 6 分）で取得できるようになります。

このマルチスレッドの例は、counts エンドポイントにも同様に当てはまります。たとえば、2 年間の期間について投稿数を取得したい場合、シングルスレッドリクエストを行い、31 日ずつさかのぼりながらカウントを取得することができます。1 レスポンスあたり 2 秒かかると仮定すると、24 件の API リクエストを行ってカウントの全セットを取得するのに、およそ 48 秒かかります。しかし、同時に複数の 1 か月単位のリクエストを行うこともできます。1 秒あたり 12 件のリクエストを行う場合、カウントの全セットは約 2 秒で取得できます。

<div id="retry-logic">
  ### リトライロジック
</div>

enterprise search API で 503 エラーが発生した場合、多くは一時的なエラーであり、短時間待ってからリクエストを再試行することで解決できます。

リクエストが連続して 4 回失敗し、その間に少なくとも 10 分以上待機している場合は、次の手順でトラブルシューティングを行ってください。

* 対象とする時間範囲を短くしてから、リクエストを再試行します。解消しない場合は、最小で 6 時間の時間ウィンドウになるまでこの手順を繰り返します。
* 多数の語句を OR で連結している場合は、それらを複数のルールに分割し、それぞれ個別に再試行します。
* ルール内で多数の除外条件を使用している場合は、ルール内の否定語句の数を減らし、再試行します。

<div id="getting-started-with-enterprise-search-posts-30-day-api">
  ### enterprise Search Posts: 30-Day API の利用を開始する
</div>

enterprise Search Posts: 30-Day API を使用すると、直近 30 日以内に行われた投稿を取得できます。投稿は、リクエストで指定したクエリに基づいて照合され、返されます。クエリとは、返される投稿にどのような内容が含まれているべきかを定義するルールです。このチュートリアルでは、X アカウント @XDevelopers から英語で行われた投稿を検索します。

レスポンスで返される投稿は、投稿全体のペイロードを取得できる data 形式か、マッチした投稿数の数値データを返す counts 形式のいずれかになります。ここでは、data エンドポイントおよび counts エンドポイントへのリクエストを行うために cURL を使用します。

次のものが必要です:

* [エンタープライズアカウント]https://developer.x.com/en/products/x-api/enterprise
* ユーザー名、パスワード、およびアカウント名
* console.gnip.com に表示される、検索エンドポイントに関連付けられたラベル

<div id="accessing-the-data-endpoint">
  #### data エンドポイントへのアクセス
</div>

data エンドポイントは、一致した投稿の完全な Post ペイロードを返します。`from:` と `lang:` オペレーターを使用して、@XDevelopers による英語の投稿を検索します。 *他のオペレーターについては [こちら](/ja/x-api/enterprise-gnip-2.0/fundamentals/search-api#enterprise-operators) を参照してください。*

<Tabs>
  <Tab title="cURL">
    *cURL は、URL 構文を使用してファイルを取得または送信するためのコマンドラインツールです。*

    次の cURL リクエストを、以下を変更したうえでコマンドラインにコピーしてください。

    * **Username** `<USERNAME>` 例: `email@domain.com`

    * **Account name** `<ACCOUNT-NAME>` 例: `john-doe`

    * **Label** `<LABEL>` 例: `prod`

    * **fromDate と toDate** 例: `"fromDate":"201811010000", "toDate":"201811122359"`

    *リクエスト送信後、パスワードの入力を求められます。*

    ```bash
    curl -X POST -u<USERNAME> "https://gnip-api.x.com/search/30day/accounts/<ACCOUNT-NAME>/<LABEL>.json" -d '{"query":"from:TwitterDev lang:en","maxResults":"500","fromDate":"<yyyymmddhhmm>","toDate":"<yyyymmddhhmm>"}'
    ```
  </Tab>

<div id="accessing-the-counts-endpoint">
  #### counts エンドポイントへのアクセス
</div>

counts エンドポイントを使用すると、@XDevelopers アカウントから英語で投稿された投稿数を、`day` 単位でグルーピングして取得できます。

<Tabs>
  <Tab title="cURL">
    *cURL は、URL 構文を使ってファイルを取得したり送信したりするコマンドラインツールです。*

    以下の cURL リクエストを、次の項目を変更したうえでコマンドラインにコピーしてください。

    * **Username** `<USERNAME>` 例: `email@domain.com`

    * **Account name** `<ACCOUNT-NAME>` 例: `john-doe`

    * **Label** `<LABEL>` 例: `prod`

    * **fromDate と toDate** 例: `"fromDate":"201811010000", "toDate":"201811122359"`

    *リクエストを送信すると、パスワードの入力を求められます。*

    ```bash
    curl -X POST -u<USERNAME> "https://gnip-api.x.com/search/30day/accounts/<ACCOUNT-NAME>/<LABEL>/counts.json" -d '{"query":"from:TwitterDev lang:en","fromDate":"<yyyymmddhhmm>","toDate":"<yyyymmddhhmm>","bucket":"day"}'
    ```
  </Tab>

  <Tab title="cURL の例">

<div id="getting-started-with-enterprise-search-posts-full-archive-api">
  ### enterprise Search Posts: Full-Archive API を使い始める
</div>

enterprise Search Posts: Full-Archive API を使用すると、2006 年に最初に投稿されたものから現在までの投稿にアクセスできます。投稿は、リクエストで指定したクエリに基づいて一致したものが返されます。クエリとは、返される投稿にどのような内容が含まれるべきかを定義するルールです。このチュートリアルでは、X アカウント @XDevelopers から英語で行われた投稿を検索します。

レスポンスのペイロード内で取得する投稿は、投稿全体のペイロードが提供される `data` フォーマット、またはマッチした投稿の数値カウントデータが提供される `counts` フォーマットのいずれかになります。ここでは、`data` エンドポイントと `counts` エンドポイントへのリクエストに cURL を使用します。

次のものを用意してください。

* [An enterprise account]https://developer.x.com/en/products/x-api/enterprise
* ユーザー名、パスワード、アカウント名
* console.gnip.com に表示される、検索エンドポイントに関連付けられたラベル

#### データエンドポイントへのアクセス

データエンドポイントは、一致した投稿の完全なペイロードを提供します。`from:` と `lang:` オペレーターを使用して、@XDevelopers からの英語の投稿を検索します。*他のオペレーターについては [こちら](/ja/x-api/enterprise-gnip-2.0/fundamentals/search-api#enterprise-operators)を参照してください。*

<div id="product-overview">
  ### 製品概要
</div>

エンタープライズ向けの Full-archive Search は 2015 年 8 月に、プレミアム向けバージョンは 2018 年 2 月にリリースされました。これらの検索プロダクトによって、顧客は公開されている任意の投稿に即座にアクセスできます。Full-archive Search では、単一のクエリを送信し、従来の RESTful 方式でレスポンスを受け取ります。Full-archive Search は 1 レスポンスあたり最大 500 件の投稿となるページネーションを実装しており、レート制限はプレミアム向けが 1 分あたり最大 60 リクエスト (rpm)、エンタープライズ向けが 120 rpm です。これらの条件から、Full-archive Search は、投稿を迅速かつ同時実行リクエストを用いた大規模な取得に適しています。

ディスク上の投稿フラットファイル群をアーカイブの基盤とする Historical PowerTrack とは異なり、Full-archive Search の投稿アーカイブはオンライン・データベースのようなものです。すべてのデータベースと同様に、その内容に対してクエリを実行できます。また、高速なデータ取得を可能にするために *index*（インデックス）も利用しています。Full-archive Search エンドポイントでは、クエリ言語は PowerTrack Operators で構成されており、各 Operator はインデックス対象となっている投稿の JSON 属性に対応します。

また、Historical PowerTrack と同様に、クエリ実行時点の「現在の値」を持つ投稿属性も存在します。たとえば、本日 Search API を使って 2010 年に投稿された投稿にアクセスする場合、ユーザーのプロフィール説明、アカウントの「home」ロケーション、表示名、およびお気に入り数やリツイート数などの投稿メトリクスは、2010 年当時ではなく、本日時点の値に更新された状態で返されます。 

<div id="metadata-timelines">
  ### メタデータのタイムライン
</div>

以下は、Full-archive search エンドポイントの Operator がマッチングを開始した時期のタイムラインです。ケースによっては、Operator のマッチングが、X 上で「コミュニケーション上の慣習」が一般的になった *かなり後* に始まっています。たとえば、@Replies は 2006 年にはユーザーによる慣習として登場しましたが、「サポートする」JSON を伴う *ファーストクラスのオブジェクト* や *イベント* になったのは 2007 年初頭でした。そのため、2006 年の @Replies に対してマッチングするには、`to:` や `in_reply_to_status_id:` という PowerTrack Operator に依存するのではなく、投稿本文を調査する必要があります。

ここで提供している詳細は、Full-Archive Search（数百件に及ぶ検索を元にしたもの）を使用して生成されたものです。このタイムラインは 100% 完全でも厳密でもありません。ユースケースにとって本質的な、別のフィルタリング / メタデータの「誕生日」を特定した場合は、ぜひお知らせください。

なお、基盤となる Search インデックスは再構築される場合があります。そのため、このタイムラインの詳細は変更される可能性があります。

<div id="filtering-tips">
  ### フィルタリングのヒント
</div>

これまで説明してきたタイムライン情報からわかるように、Search API のフィルターを作成する際には多くの詳細を考慮する必要があります。特に重要な点が 2 つあります。

* いくつかのメタデータには「開始日」があり、そのためフィルターによって *偽陰性* が発生する可能性があります。こうした検索には、検索対象期間の全体または一部においてまだ存在していなかったメタデータに依存するオペレーターが含まれます。たとえば、`has:images` オペレーターを使って画像付きの投稿を検索する場合、2011 年 7 月以前の期間については一致する結果がありません。これは、そのオペレーターが *ネイティブ* 写真（X のユーザーインターフェースを使って投稿に添付された写真）にマッチするためです。写真共有投稿のより完全なデータセットを取得するには、2011 年 7 月以前を対象とするフィルターに、写真ホスティングサービスで一般的な URL にマッチするルール句を含める必要があります。
* 一部のメタデータは、その投稿が行われた *後* の時点の情報を使って後から補完（バックフィル）されています。

PowerTrack クエリを作成する際に、一般的に注目される属性タイプはいくつかあります。

* X プロフィール
* オリジナル投稿または共有投稿
* 投稿の言語分類
* 位置情報付きの投稿
* 共有リンク内のメディア

これらの中には製品固有の挙動を持つものもあれば、同じ挙動を持つものもあります。詳細は以下を参照してください。

<div id="x-profiles">
  #### X プロフィール
</div>

Search API は、*取得時点* のユーザープロフィール情報を含む過去の投稿を返します。2014年の投稿をリクエストした場合でも、ユーザーのプロフィールメタデータはクエリ時点の状態を反映します。

<div id="original-posts-and-retweets">
  #### 元の投稿とリツイート
</div>

PowerTrack `_is:retweet_` 演算子を使用すると、リツイートを含めるか除外するかを制御できます。この演算子を利用する場合、2009 年 8 月以前のデータに対するリツイートのマッチング（または非マッチング）について、2 つの方法を用意する必要があります。2009 年 8 月以前では、投稿メッセージ自体を厳密なフレーズ一致で確認し、「@RT 」というパターンにマッチするかどうかをチェックする必要があります（なお、2009 年 5 月〜 8 月のリツイートをフィルタリングする場合は、「Via @」というパターンも含める必要があります）。2009 年 8 月以降の期間については、*is:retweet* 演算子が利用可能です。

<div id="post-language-classifications">
  #### 投稿の言語分類
</div>

投稿の言語分類でフィルタリングを行う場合、X の履歴系プロダクトはかなり性質が異なります。Search アーカイブが構築された際、すべての投稿に対し、過去分も含めて X の言語分類が付与されました。そのため、`lang:` 演算子は投稿アーカイブ全体に対して利用できます。

<div id="geo-referencing-posts">
  #### 投稿の地理参照
</div>

投稿を地理情報と関連付ける主な方法は 3 つあります。

* **投稿メッセージ内の地理的な記述。** 投稿本文に含まれる地名などの地理的な記述に基づいてマッチングを行う方法です。ローカルな知識に依存するため、しばしば最も難易度の高い方法ではありますが、投稿アーカイブ全体に対して利用できるオプションです。[こちら](https://x.com/biz/statuses/28311)は、2006 年にサンフランシスコ地域向けに「golden gate」フィルターに基づいて地理参照でマッチした例です。

* **ユーザーによってジオタグされた投稿。** 検索 API では、一部の Geo オペレーターについては 2010 年 3 月から、他の Geo オペレーターについては 2015 年 2 月から、位置情報を含む投稿に対してマッチングを開始できるようになりました。

  * 2010 年 3 月 6 日: `has:geo`, `bounding_box:` および `point_radius:`
  * 2015 年 2 月 17 日: `place_country:` および `place:`

* **ユーザーが設定したアカウントプロフィールの「ホーム」位置情報。** Profile Geo オペレーターは、Historical PowerTrack と Search APIs の両方で利用できます。Search APIs では、これらの Profile Geo メタデータは 2015 年 2 月から利用可能です。Profile Geo メタデータが利用可能になる前に投稿された投稿については、正規化されていないユーザー入力に対してもマッチングできる `bio_location:` オペレーターが利用できます。

<div id="shared-links-and-media">
  #### 共有リンクとメディア
</div>

2012年3月に、展開された URL エンリッチメントが導入されました。これ以前は、Post ペイロードにはユーザーが指定した URL のみが含まれていました。そのため、ユーザーが短縮 URL を含めている場合、関心のある（展開済みの）URL と照合するのが困難になることがあります。Search API では、これらのメタデータは 2012年3月以降利用可能です。

2016年7月に、強化された URL エンリッチメントが導入されました。この強化版では、Post ペイロードに Web サイトの HTML タイトルと説明が含まれるようになり、それらに対して照合するためのオペレーターも提供されます。これらのメタデータは、2014年12月から含まれ始めます。

2016年9月、X は「ネイティブアタッチメント」を導入しました。これにより、末尾の共有リンクは投稿の 140 文字制限にカウントされなくなりました。これらの共有リンクには、両方の URL エンリッチメントが引き続き適用されます。

関連する Search オペレーターがマッチし始めるタイミングは次のとおりです:

* 2006年10月26日 - `has:links`
* 2011年7月20日 - `has:images` および `has:media`
* 2011年8月 - `url:` と [Expanded URLs enrichment](/ja/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments)。早いものでは 2006年9月には、`(url:"spotify.com" OR url:gnip OR url:microsoft OR url:google OR url:youtube)` が http://x.com/Adam/statuses/16602 にマッチします。これは、twitter&#95;entities や gnip オブジェクトに urls[] メタデータが存在しない場合でも同様です。&quot;youtube.com&quot; は、urls[] メタデータが一切なくても `url:youtube` にマッチするメッセージコンテンツの一例です。
* 2015年2月10日 - ネイティブ動画向けの `has:videos`。2010/08/28 から 2015/02/10 の間、このオペレーターは youtube.com、vimeo.com、vivo.com などの一部の動画ホスティングサイトへのリンクを含む投稿にマッチします。
* 2016年5月1日 - [Enhanced URLs enrichment](/ja/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments) に基づく `url_title:` および `url_description:` が一般提供開始。最初の Enhanced URL メタデータは 2014年12月に出現し始めました。

<div id="general-search-post-api-questions">
  ### Search Post API に関する一般的な質問
</div>

<AccordionGroup>
  <Accordion title="data エンドポイントで取得した投稿数が、counts エンドポイントで返される投稿数と一致しません。これはなぜですか？">
    `counts` エンドポイントと `data` エンドポイントが返す結果には既知の違いがあります。`counts` エンドポイントはコンプライアンス適用前の状態（削除された投稿や位置情報の削除などを反映しない状態）で集計されるのに対し、`data` エンドポイントは配信時点でコンプライアンスに準拠しており、すべてのコンプライアンスイベントを反映しているため、結果に不整合が生じる場合があります。
  </Accordion>

  <Accordion title="クエリに一致するはずの投稿が返ってきません。なぜですか？">
    これが起きた理由としてはいくつか考えられます。たとえば、次のようなものがあります。

    1. 期待していた投稿が、保護された（非公開の）アカウントからの投稿である
    2. data エンドポイントではすべてのコンプライアイベントが考慮されるため（削除された投稿やジオ情報の削除などは、レスポンスに含まれません）。

<div id="enterprise-search-apis">
  ### エンタープライズ検索 API
</div>

エンタープライズ検索 API には 2 種類あります。

* 30-Day Search API - 直近 30 日以内に投稿されたツイートを提供します。
* Full-Archive Search API - 2006 年 3 月に投稿された最初のツイートを含め、2006 年までさかのぼるツイートを提供します。

これらの検索 API は共通の設計となっており、以下のドキュメントは両方の API に適用されます。なお、2022 年 9 月 29 日以降に作成されたツイートについては、その編集履歴を示すツイート編集メタデータが Tweet オブジェクトに含まれます。詳しくは、「[&quot;Edit Tweets&quot;](/ja/x-api/enterprise-gnip-2.0/fundamentals/edit-tweets)」の基礎情報ページを参照してください。

以下では、エンタープライズ検索 API と連携する際に必要となる重要な情報を説明します。

* ツイートデータおよび件数をリクエストするためのメソッド
* 認証
* ページネーション
* API リクエストパラメータとリクエスト例
* API レスポンスの JSON ペイロードとレスポンス例
* HTTP レスポンスコード

エンタープライズ API は、ツイートアーカイブへの低レイテンシーかつ高い忠実度のクエリベースアクセスを提供します。2 つの API の違いは、検索可能な期間のみであり、直近 30 日間か、2006 年までさかのぼるかのいずれかです。期間は分単位の粒度で指定できます。ツイートデータは、クエリにマッチする最新のツイートから時系列を遡る形で返却されます。ツイートは公開からおおよそ 30 秒後には、検索 API から利用可能になります。

<div id="methods">
  #### Methods
</div>

エンタープライズ検索のベース URI は `https://gnip-api.x.com/search/` です。

| Method | Description |
| :--- | :--- |
| [POST /search/:product/accounts/:account&#95;name/:label](#SearchRequests) | 指定された PowerTrack ルールに一致する、過去 30 日間のツイートを取得します。 |
| [POST /search/:product/accounts/:account&#95;name/:label/counts](#CountRequests) | 指定された PowerTrack ルールに一致する、過去 30 日間のツイート数を取得します。 |

ここでは、次のようになります。

* `:product` は、リクエストを送信する検索エンドポイントを表し、`30day` または `fullarchive` のいずれかです。
* `:account_name` は、console.gnip.com に表示される、アカウントに関連付けられた（大文字と小文字を区別する）名前です。
* `:label` は、console.gnip.com に表示される、検索エンドポイントに関連付けられた（大文字と小文字を区別する）ラベルです。

たとえば、TwitterDev アカウントが、ラベルが「prod」（production の略）の 30 日間検索プロダクトを持っている場合、検索エンドポイントは次のようになります。

* データエンドポイント: [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json)
* カウントエンドポイント: [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json)

お使いのエンタープライズ検索 API の完全なエンドポイントは [https://console.gnip.com](https://console.gnip.com) に表示されます。

以下では、curl と呼ばれるシンプルな HTTP ユーティリティを使用したリクエスト例をいくつか示します。これらの例では、URL に `:product`、`:account_name`、および `:label` を使用しています。これらの例を使用するには、必ず URL をご自身の情報に合わせて更新してください。

<div id="authentication">
  #### 認証
</div>

Enterprise search APIs へのすべてのリクエストでは、[https://console.gnip.com](https://console.gnip.com) のアカウントにログインするときに使用する有効なメールアドレスとパスワードの組み合わせで構成される HTTP の *Basic Authentication* を使用する必要があります。認証情報は、各リクエストで *Authorization* ヘッダーとして送信する必要があります。

<div id="requestresponse-behavior">
  #### リクエストとレスポンスの動作
</div>

`fromDate` と `toDate` パラメータを使用すると、API がサポートする任意の期間をリクエストできます。30-Day search API は、直近 31 日分のツイートを提供します（「30-Day」API と呼ばれていますが、ユーザーが 1 か月分を完全に取得できるように 31 日分が利用可能です）。Full-Archive search API は、最初のツイート（2006 年 3 月 21 日）まで遡ったツイートを提供します。ただし、単一のレスポンスに含まれるのは、指定した `maxResults` または 31 日分のうち小さい方に相当する結果だけです。条件に合致するデータまたは指定した時間範囲が、指定した `maxResults` もしくは 31 日分を超える場合、指定した時間範囲の残りをページング取得するために使用できる `next` トークンが返されます。

たとえば、Full-Archive search を使用して、2017 年 1 月 1 日から 2017 年 6 月 30 日までの間で、クエリにマッチするすべてのツイートを取得したいとします。この場合、リクエストでは `fromDate` と `toDate` パラメータを使って、その 6 か月全体の期間を指定します。search API は、まずツイートの最初の「ページ」を返し、そのツイート数は `maxResults` パラメータ（デフォルトは 100）で指定した数になります。さらにツイートが存在すると仮定すると（そしてほとんどの場合は存在します）、API は次の「ページ」のデータを取得するためのリクエストを行えるように、`next` トークンも返します。この処理は、API が `next` トークンを返さなくなるまで繰り返されます。詳細は次のセクションを参照してください。

<div id="pagination">
  #### ページネーション
</div>

data リクエストと count リクエストの両方を行う場合、1 回のレスポンスで返せる量を超えるデータが存在する可能性があります。その場合、レスポンスには「next」トークンが含まれます。「next」トークンは、ルートレベルの JSON 属性として提供されます。「next」トークンが含まれている場合は、さらに取得すべきデータが存在することを意味するため、API リクエストを継続して行う必要があります。

**注:** 「next」トークンの挙動は、data リクエストと count リクエストとでわずかに異なります。両者の挙動および例となるレスポンスは、APIリファレンス セクションで説明しています。

<div id="data-pagination">
  ##### データのページネーション
</div>

データをリクエストすると、1 回のレスポンスで返せる量を超えるデータが返される可能性があります。各データリクエストには、1 回のリクエストで返すツイートの最大件数を設定するパラメータが含まれます。この `maxResults` パラメータのデフォルトは 100 で、10〜500 の範囲で設定できます。リクエストで指定した `maxResults` パラメータよりも多くのツイートがクエリにマッチした場合、レスポンスには（ルートレベルの JSON 属性として）`next` トークンが含まれます。この `next` トークンは後続のリクエストで使用され、そのクエリにマッチするツイートの次の分（つまり次の「ページ」）を取得します。クエリ結果の最後の「ページ」に到達し、`next` トークンが返されなくなるまで、`next` トークンは引き続き提供されます。

次の「ページ」のデータをリクエストするには、元のクエリとまったく同じクエリを実行する必要があります。使用している場合は `query`、`toDate`、`fromDate` パラメータを含め、さらに前のレスポンスで返された値を設定した `next` リクエストパラメータも含めます。これは GET リクエストと POST リクエストのどちらでも利用できます。ただし、GET リクエストの場合は `next` パラメータを URL エンコードする必要があります。

前回のレスポンスで受け取った `next` トークンを渡し続けることで、そのクエリで対象としている期間内のすべてのツイートを取得し終えるまでリクエストを続行できます。`next` トークンが含まれないレスポンスを受信した場合、それは最後のページに到達しており、指定したクエリと時間範囲に対して利用可能な追加データがないことを意味します。

<div id="counts-pagination">
  ##### counts ページネーション
</div>

`counts` エンドポイントは、クエリに関連付けられたツイート数を、日次・時間単位・分単位のいずれかで提供します。`counts` API エンドポイントは、最大 31 日分のカウントからなるタイムスタンプ付き配列を返します。31 日を超える期間のカウントをリクエストした場合は、`next` トークンが返されます。`data` の `next` トークンの場合と同様に、元のリクエストとまったく同じクエリを使用し、前回のレスポンスで返された値を設定した `next` リクエストパラメータを必ず含める必要があります。

31 日を超えるカウントをリクエストした場合以外にも、`next` トークンが提供されるケースがあります。ボリュームの多いクエリでは、カウントの生成に時間がかかりすぎてレスポンスがタイムアウトする可能性があります。この場合は、31 日分未満のカウントしか受け取れませんが、カウントのペイロード全体を取得し続けるための `next` トークンが提供されます。***重要:*** タイムアウト時には、常に完全な「バケット」のみが返されます。そのため、2.5 日分のデータがある場合は、2 日分の完全な「バケット」が返されます。

<div id="additional-notes">
  ##### 追加の注意事項
</div>

* 検索リクエストで `fromDate` または `toDate` を使用する場合、結果として返されるのは指定した時間範囲内のデータのみです。指定した時間範囲内の最後の結果グループに到達すると、`next` トークンは返されません。
* `next` 要素は、`maxResults` の値が 10〜500 の任意の値（デフォルト値は 100）で使用できます。`maxResults` は各レスポンスで返されるツイート数を決定しますが、最終的にすべての結果を取得することを妨げるものではありません。
* `next` 要素には有効期限がありません。同じ `next` クエリを使用した複数のリクエストは、リクエストがいつ行われたかに関係なく同じ結果を受け取ります。
* `next` パラメータを使用して結果をページングする場合、クエリの境界部分で重複が発生することがあります。アプリケーション側でこれらの重複を許容できるように実装してください。

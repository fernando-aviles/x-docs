<div id="what-is-a-disconnection">
  ## 切断とは何ですか？
</div>

ストリーミング API への接続を確立するとは、非常に長時間にわたって持続する HTTPS リクエストを発行し、そのレスポンスを逐次的に処理することを意味します。`powerstream` エンドポイントに接続する場合は、HTTPS リクエストを送信し、可能な限り長く結果のストリームを読み取り続ける必要があります。サーバー側のエラー、クライアント側での過度な遅延、ネットワーク障害、定期的なサーバーメンテナンス、もしくは重複ログインがない限り、当社のサーバーは接続を無期限に維持します。ストリーミングエンドポイントへの接続では、切断が発生する可能性が高く、また発生するものと想定しておくべきであり、再接続ロジックを実装しておく必要があります。

<div id="why-a-streaming-connection-might-be-disconnected">
  ## ストリーミング接続が切断される理由
</div>

ストリームは、さまざまな理由で切断される可能性があります。ストリームから返されるエラーメッセージを確認して、障害の原因を把握してください。切断の主な理由には、次のようなものがあります。

* 誤ったトークンや誤った認証方式の使用などによる認証エラー。
* X 側のストリーミングサーバーの再起動。これは通常コードのデプロイに関連しており、あらかじめ想定し、それに対応した設計を行う必要があります。
* クライアントがストリームから配信される投稿の量についていけない、またはデータを読む速度が遅すぎる場合。すべてのストリーミング接続には、クライアントに送信されるメッセージのキューが用意されています。このキューが時間の経過とともに大きくなりすぎると、接続は終了されます。
* アカウントが 1 日あたり／1 か月あたりの投稿数の上限（クォータ）を超過した。
* アクティブな冗長接続が多すぎる。
* クライアントが突然データの読み取りを停止した場合。ストリームから読み取られる投稿のレートが急激に低下すると、接続は終了されます。
* サーバーとクライアント間のネットワーク問題の可能性。
* 一時的なサーバー側の問題、計画メンテナンスや更新。（[ステータスページ](/ja/status)を確認してください）

<div id="anticipating-disconnects-and-reconnecting">
  ## 切断を見越した対応と再接続
</div>

投稿をストリーミングする際は、切断が発生しうることを認識しつつ、できるだけ長く接続を維持することが目標です。エンドポイントは 20 秒ごとにキープアライブ用のハートビート（改行文字として現れます）を送信します。このシグナルを使って、切断されつつあるかどうかを検出してください。

1. 新しいコンテンツとハートビートの受信が止まったことを、コードで検出できるようにします。
2. その場合、コードで再接続ロジックを起動する必要があります。一部のクライアントや言語では読み取りタイムアウトを指定できるため、これを 20 秒に設定できます。
3. サービスは、これらの切断を検出し、可能なかぎり速やかに再接続する必要があります。

一度確立された接続が切れたら、ただちに再接続を試みてください。再接続に失敗した場合は、発生したエラーのタイプに応じて再接続試行の頻度を下げてください。

* TCP/IP レベルのネットワークエラーに対しては、線形にバックオフします。これらの問題は一般的に一時的で、すぐに解消される傾向があります。再接続までの待機時間を試行ごとに 250ms ずつ増やし、最大 16 秒までとします。
* 再接続が適切な HTTP エラーについては、指数的にバックオフします。まず 5 秒待機し、試行ごとに待機時間を倍にして、最大 320 秒までとします。
* HTTP 429 エラー（レート制限超過）の場合も、指数的にバックオフします。最初は 1 分待機し、試行ごとに待機時間を倍にします。HTTP 429 を受信するたびに、アカウントに対するレート制限が解除されるまで待機しなければならない時間が増加することに注意してください。
   

<div id="recovering-lost-data">
  ## 失われたデータの復旧
</div>

切断が発生した場合に、取り逃した可能性のあるすべてのデータを確実に受信するために利用できる、いくつかの方法があります。取り逃したデータを復旧するために実行できる主な手順については、[データの復旧](/ja/x-api/powerstream/recovery-and-redundancy) に関するインテグレーションガイドで解説しています。 
 

<div id="rate-limits-and-usage">
  ## レート制限と使用状況
</div>

接続制限を確認するには、レスポンスに含まれる 3 つのヘッダーを参照します。これは、ルールエンドポイントを何回使用できるか、またストリーミングエンドポイントで再接続試行が何回許可されているかを把握するのに役立ちます。

* `x-rate-limit-limit` は、15 分間のウィンドウ内でクライアントが行うことを許可されているリクエスト数を示します。

* `x-rate-limit-remaining` は、15 分間のウィンドウ内でこれまでに実行されたリクエスト数を示します。

* `x-rate-limit-reset` は、15 分間のウィンドウがいつ再開し、その際に `x-rate-limit-remaining` が 0 にリセットされるかを示す UNIX タイムスタンプです。

filter stream エンドポイントは、現在使用状況データを報告しません。配信された投稿数を確認するには、必要に応じて消費量を計測し一時停止できるように、メータリングロジックをコード内に実装してください。 

ストリームのクライアント側を実装するコードは、受信した投稿を先入れ先出し (FIFO) キュー、または同様のメモリ構造に単純に挿入します。別のプロセス／スレッドが、そのキューから投稿を取り出して解析し、保存用に準備する必要があります。この設計により、受信する投稿の量が大きく変動した場合でも効率的にスケールできるサービスを実装できます。概念的には、HTTP 経由で無限に長いファイルをダウンロードしているようなものだと考えることができます。

<div id="reconnection-best-practices">
  ## 再接続のベストプラクティス
</div>

<div id="test-backoff-strategies">
  ### バックオフ戦略をテストする
</div>

バックオフ実装をテストする有効な方法は、無効な認可クレデンシャルを使用して再接続試行の挙動を確認することです。適切に実装されていれば、429 レスポンスを一切受け取りません。

<div id="issue-alerts-for-multiple-reconnects">
  ### 複数回の再接続発生時の問題アラート
</div>

クライアントが再接続間隔の上限しきい値に達した場合は、接続に影響している問題を切り分けて対処できるよう、通知を送信するようにする必要があります。

<div id="handle-dns-changes">
  ### DNS 変更への対応
</div>

クライアントプロセスが DNS の TTL（Time To Live）に正しく従っているかテストしてください。スタックによっては、解決済みアドレスをプロセスの実行中ずっとキャッシュしてしまい、定められた TTL 内の DNS 変更を反映しない場合があります。このような過度なキャッシュは、X が IP アドレス間で負荷分散を行う際に、クライアント側でのサービス中断を引き起こします。

<div id="user-agent">
  ### User Agent
</div>

`user-agent` HTTP ヘッダーにクライアントのバージョンを必ず含めてください。これは X 側での問題診断において重要です。環境によって `user-agent` フィールドを設定できない場合は、代わりに `x-user-agent` ヘッダーを設定してください。

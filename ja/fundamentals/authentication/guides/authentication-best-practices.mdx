API key とトークンは、細心の注意を払って保護する必要があります。 

これらの認証情報は、あなたの[開発者用 App](/ja/resources/fundamentals/developer-apps)および、あなたによるリクエスト送信を承認した X アカウントに直接紐づいています。もしキーが漏えいした場合、悪意のある第三者がそれらを使用して、あなたの開発者用 App やその承認ユーザーの代理として X のエンドポイントにリクエストを送信できてしまいます。その結果、想定外のレート制限に達してしまったり、有料アクセス枠を使い切ってしまったり、さらにはあなたの開発者用 App が停止されてしまう可能性もあります。

以下のセクションでは、API key とトークンを管理する際に考慮すべきベストプラクティスを紹介します。

<div id="regenerate-api-keys-and-tokens">
  ## API key とトークンを再生成する
</div>

API key が漏えいした可能性がある場合は、次の手順に従って API key を再生成してください。

1. [開発者コンソールの「Apps」ページ](https://developer.x.com/en/portal/projects-and-apps.html)に移動します。
2. 該当する App の横にある「Keys and tokens」アイコン (🗝 ) をクリックします。
3. 再生成したいキーおよびトークンのセットの横にある「Regenerate」ボタンをクリックします。 

Access Token や Bearer Token をプログラムから再生成したい場合は、認証エンドポイントを使用して実行できます。

* Access Token を再生成したい場合は、まず [POST oauth/invalidate&#95;token](/ja/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token) エンドポイントを使用してトークンを失効させてから、[3-legged OAuth flow](/ja/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens) を使用してトークンを再生成する必要があります。
* Bearer Token を再生成したい場合は、まず [POST oauth2/invalidate&#95;token](/ja/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token) エンドポイントを使用してトークンを失効させてから、[POST oauth2/token](/ja/resources/fundamentals/authentication/api-reference#post-oauth2-token) エンドポイントを使用してトークンを再生成する必要があります。

<div id="having-a-central-file-for-your-secrets">
  ## シークレット情報を一元管理するファイルを用意する
</div>

`.ENV` ファイルや、その他の `.yaml` ファイルなどにシークレット情報をまとめて格納する方法は便利ですが、それらを誤って git リポジトリにコミットしてしまわないよう、必ず `.gitignore` ファイルを適切に設定しておいてください。 

<div id="environment-variables">
  ## 環境変数
</div>

環境変数を利用するコードを書くと便利な場合があります。 

その一例を、Python では次のように記述できます。

```python
import os

consumer_key = os.environ.get("CONSUMER_KEY")

consumer_secret = os.environ.get("CONSUMER_SECRET")
```

ターミナルで次のように入力します。

```bash
export CONSUMER_KEY='xxxxxxxxxxxxxxxxxxx'
export CONSUMER_SECRET='xxxxxxxxxxxxxxxxxxxxxxx'
```

<div id="source-code-and-version-control">
  ## ソースコードとバージョン管理
</div>

開発者が犯しがちな最も一般的なセキュリティ上のミスは、GitHub や BitBucket のような、誰でもアクセス可能なバージョン管理システム上のソースコードに API キーやトークンをコミットしてしまうことです。これらのコードリポジトリの多くは一般に公開されています。公開コードリポジトリでこのミスが非常に頻繁に発生するため、API キーをスクレイピングすることで収益を上げているボットが存在します。

* サーバーの環境変数を使用してください。API キーを環境変数に保存することで、コードやバージョン管理システムの外に出すことができます。これにより、環境ごとに異なるキーを容易に使い分けることもできます。
* バージョン管理から除外された設定ファイルを使用してください。ファイルをバージョン管理の追跡対象から除外するために、ファイル名を [.gitignore](https://git-scm.com/docs/gitignore) に追加します。
* バージョン管理を使用した後にコードから API キーを削除しても、コードベースの以前のバージョンにアクセスすることで API キーが依然として取得可能な場合があります。次のセクションで説明する手順に従って、API キーを再生成してください。

<div id="databases">
  ## データベース
</div>

アクセストークンをデータベースに保存する必要がある場合は、次の点に注意してください。

* アクセストークンがその所有者だけに読み取り可能となるように、データベースへのアクセスを制限します。
* アクセストークン用のデータベーステーブルに対する編集・書き込み権限を制限します。これはキー管理システムで自動化されている必要があります。
* いかなるデータストアに保存する場合でも、事前にアクセストークンを暗号化します。

<div id="password-management-tools">
  ## パスワード管理ツール
</div>

1Password や LastPass などのパスワード管理ツールは、キーやトークンを安全に保管するのに役立ちます。共有のチーム用パスワード管理ツール上で、これらを共有することは避けたほうがよい場合があります。

<div id="web-storage-cookies">
  ## Web storage と Cookie
</div>

Web storage には LocalStorage と SessionStorage の 2 種類があります。これらは Cookie よりも高い保存容量を持つ、Cookie 利用の改善版として作られました。ただし、それぞれのストレージオプションには異なる長所と短所があります。
 

**Web Storage: LocalStorage**

ローカルの web storage に保存されたものは永続的です。つまり、データを明示的に削除しない限り、データは保持され続けます。これは、プロジェクトの要件によっては好ましい特性と見なせる場合があります。ただし LocalStorage を利用する際には注意が必要です。なぜなら、データに対する変更や追加は、対象のウェブページへの将来のすべての訪問時に利用可能になるためです。通常は LocalStorage の使用は推奨されませんが、いくつかの例外があり得ます。LocalStorage を使用することにした場合、同一オリジンポリシーをサポートしている点を知っておくとよいでしょう。そのため、ここに保存されたすべてのデータは同じオリジンからのみ利用可能です。LocalStorage を使用することによる追加のパフォーマンス上の利点として、すべての HTTP リクエストでデータをサーバーに送り返す必要がないため、クライアントとサーバー間のトラフィックを減らせることが挙げられます。
 

**Web Storage: SessionStorage**

SessionStorage は LocalStorage と似ていますが、主な違いは SessionStorage が永続的ではないという点です。SessionStorage に書き込みを行ったウィンドウ（または、使用しているブラウザによってはタブ）を閉じると、データは失われます。これは、ユーザーセッション内でトークンの読み取りを制限するのに有用です。セキュリティの観点から考えると、通常は LocalStorage よりも SessionStorage の利用が好まれます。LocalStorage と同様に、同一オリジンポリシーのサポートやクライアントとサーバー間トラフィックの減少といった利点は、SessionStorage にも当てはまります。
 

**Cookies**

Cookies はセッションデータを保存する、より従来型の方法です。各 cookie に有効期限を設定できるため、取り消しやアクセス制限を容易に行うことができます。ただし、cookie を使用すると、すべての HTTP リクエストでデータがサーバーに送り返されるため、クライアントとサーバー間のトラフィックは確実に増加します。cookie を使用する場合は、セッションハイジャックに対する防御が必要です。デフォルトでは、cookie は HTTP 上で平文のまま送信されるため、その内容はパケットスニッフィングや、攻撃者がトラフィックを改ざんし得る中間者攻撃に対して脆弱です。転送中のデータを保護するために、常に HTTPS を強制する必要があります。これにより、機密性、（データの）完全性、および認証が提供されます。ただし、Web アプリケーションやサイトが HTTP と HTTPS の両方で利用できる場合は、cookie に &quot;Secure&quot; フラグを使用することも必要です。これにより、攻撃者がユーザーに対してサイトの HTTP 版へのリンクを送信し、その結果生成される HTTP リクエストを盗聴することを防げます。

cookie 利用時のセッションハイジャックに対する二次的な防御策としては、重大な影響を持つ操作を実行する前に、ユーザーの本人確認を再度行うことが挙げられます。cookie のセキュリティを向上させるために検討すべき、もう 1 つのフラグは &quot;HttpOnly&quot; フラグです。このフラグは、該当する cookie は指定されたサーバーからのみアクセス可能であることをブラウザに伝えます。クライアントサイドスクリプトによるあらゆるアクセス試行は、このフラグによって禁止されるため、ほとんどのクロスサイトスクリプティング（XSS）攻撃に対する防御の一助となります。

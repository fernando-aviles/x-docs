<div id="oauth-20-authorization-code-flow-with-pkce">
  ### PKCE を用いた OAuth 2.0 認可コードフロー
</div>

<div id="introduction">
  #### はじめに
</div>

OAuth 2.0 は業界標準の認可プロトコルであり、アプリケーションのスコープや複数デバイス間の認可フローをより細かく制御できるようにします。OAuth 2.0 を使用すると、ユーザーに代わって特定の権限を付与するための、きめ細かなスコープを選択できます。 

App で OAuth 2.0 を有効にするには、Developer Console の App settings セクションにある認証設定で有効化する必要があります。

<div id="how-long-will-my-credentials-stay-valid">
  #### 資格情報はどのくらいの期間有効ですか?
</div>

デフォルトでは、PKCE を利用した Authorization Code Flow で作成したアクセストークンは、`offline.access` スコープを使用していない限り、2 時間だけ有効です。

<div id="refresh-tokens">
  #### リフレッシュトークン
</div>

リフレッシュトークンを使用すると、リフレッシュトークンフロー経由でユーザーに再度認可を求めることなく、アプリケーションが新しいアクセストークンを取得できます。

`offline.access` スコープが付与されている場合、OAuth 2.0 のリフレッシュトークンが発行されます。このリフレッシュトークンを使用してアクセストークンを取得できます。このスコープが指定されていない場合、リフレッシュトークンは生成されません。

新しいアクセストークンを取得するためにリフレッシュトークンを使用して行うリクエストの例は次のとおりです。

```bash
POST 'https://api.x.com/2/oauth2/token' \
--header 'Content-Type: application/x-www-form-urlencoded' \
--data-urlencode 'refresh_token=bWRWa3gzdnk3WHRGU1o0bmRRcTJ5VUxWX1lZTDdJSUtmaWcxbTVxdEFXcW5tOjE2MjIxNDc3NDM5MTQ6MToxOnJ0OjE' \
--data-urlencode 'grant_type=refresh_token' \
--data-urlencode 'client_id=rG9n6402A3dbUJKzXTNX4oWHJ
```

<div id="app-settings">
  #### アプリ設定
</div>

アプリの認証方式として、OAuth 1.0a または OAuth 2.0 のいずれかを選択できます。アプリで OAuth 1.0a と OAuth 2.0 の両方を利用できるように設定することも可能です。

OAuth 2.0 は X API v2 でのみ使用できます。OAuth 2.0 を選択している場合、アプリの「Keys and Tokens」セクションに Client ID が表示されます。 

<div id="confidential-clients">
  #### 機密クライアント
</div>

[Confidential clients](https://datatracker.ietf.org/doc/html/rfc6749#section-2.1) は、認証情報を不正な第三者に公開せずに安全に保持し、認可サーバーと安全に認証できるクライアントであり、client secret を安全に保管できます。パブリッククライアントは通常ブラウザー上またはモバイルデバイス上で動作するため、client secret を安全に利用することができません。機密クライアントである App のタイプを選択した場合、client secret が提供されます。 

Developer Console で機密クライアントであるクライアントタイプを選択した場合、Client Secret も確認できます。選択できるオプションは、Native App、Single page App、Web App、Automated App、bot です。Native App と Single page App はパブリッククライアントであり、Web App と Automated App または bot は機密クライアントです。

有効な Authorization Header を送信している機密クライアントの場合、client id は不要です。パブリッククライアントによるリクエストでは、リクエストボディに Client Id を含めることが依然として必須です。 

<div id="scopes">
  #### スコープ
</div>

スコープを使用すると、アプリに対して細かなアクセス権を設定でき、アプリが必要とする権限だけを付与できます。各スコープがどのエンドポイントに対応しているかの詳細は、[認証マッピングガイド](/ja/resources/fundamentals/authentication/guides/v2-authentication-mapping)を参照してください。

|     |     |
| :--- | :--- |
| **Scope** | **説明** |
| tweet.read | 閲覧可能なすべてのツイート（保護されたアカウントのツイートを含む）を取得する権限。 |
| tweet.write | アプリがあなたに代わってツイートおよびリツイートを行う権限。 |
| tweet.moderate.write | あなたのツイートへの返信を非表示／再表示する権限。 |
| users.email | 認証済みユーザーのメールアドレスにアクセスする権限。 |
| users.read | 閲覧可能なすべてのアカウント（保護されたアカウントを含む）を取得する権限。 |
| follows.read | あなたをフォローしているアカウントと、あなたがフォローしているアカウントを取得する権限。 |
| follows.write | アプリがあなたに代わってアカウントのフォロー／フォロー解除を行う権限。 |
| offline.access | あなたがアクセス権を取り消すまで、アプリがあなたのアカウントへの接続を維持する権限。 |
| space.read | 閲覧可能なすべてのスペースを取得する権限。 |
| mute.read | あなたがミュートしているアカウントを取得する権限。 |
| mute.write | アプリがあなたに代わってアカウントのミュート／ミュート解除を行う権限。 |
| like.read | あなたが「いいね」したツイートおよび閲覧可能な「いいね」を取得する権限。 |
| like.write | アプリがあなたに代わってツイートに「いいね」／「いいね」取り消しを行う権限。 |
| list.read | あなたが作成した、またはメンバーになっているリストのリスト本体、リストメンバー、リストフォロワー（非公開リストを含む）を取得する権限。 |
| list.write | アプリがあなたに代わってリストを作成および管理する権限。 |
| block.read | あなたがブロックしているアカウントを取得する権限。 |
| block.write | アプリがあなたに代わってアカウントのブロック／ブロック解除を行う権限。 |
| bookmark.read | 認証済みユーザーのブックマーク済みツイートを取得する権限。 |
| bookmark.write | ツイートをブックマークし、ブックマークを削除する権限。 |
| media.write | メディアをアップロードする権限。 |

<div id="rate-limits">
  #### レート制限
</div>

ほとんどの場合、OAuth 1.0a を使用して認証する場合と同じレート制限が適用されますが、Tweets lookup と Users lookup は例外です。OAuth 2.0 を使用した Tweets lookup と Users lookup では、15 分あたりのアプリごとの上限を 300 回から 900 回に引き上げています。詳しくは、[レート制限に関するドキュメント](/ja/resources/fundamentals/rate-limits)をご覧ください。

<div id="grant-types">
  #### グラントタイプ
</div>

この初期リリースでは、サポートされる[グラントタイプ](https://oauth.net/2/grant-types/)として、[PKCE](https://oauth.net/2/pkce/) を用いた[認可コード](https://oauth.net/2/grant-types/authorization-code/)と[リフレッシュトークン](https://oauth.net/2/grant-types/refresh-token/)のみをサポートしています。今後、対応するグラントタイプを追加する可能性があります。

<div id="oauth-20-flow">
  #### OAuth 2.0 フロー
</div>

OAuth 2.0 は、現在 OAuth 1.0a で使用しているものと同様のフローに従います。このトピックに関する図と詳細な解説は、[こちらのドキュメント](/ja/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens)で確認できます。 

<div id="glossary">
  #### 用語集
</div>

|     |     |
| :--- | :--- |
| **用語** | **説明** |
| Grant types | OAuth フレームワークでは、さまざまなユースケース向けに複数のグラントタイプと、新しいグラントタイプを作成するための仕組みが規定されています。例として、authorization code、client credentials、device code、refresh token などがあります。 |
| Confidential client | Confidential client とは、登録済みの client secret を安全に保持するなど、認可サーバーに対して安全に認証できるアプリケーションです。 |
| Public client | Public client とは、ブラウザやモバイルデバイス上で動作するアプリケーションなど、登録済みの client secret を使用できないクライアントです。 |
| Authorization code flow | Confidential client と Public client の両方が、authorization code を access token に交換するために使用するフローです。 |
| PKCE | Authorization code flow を拡張し、複数の攻撃を防ぎ、Public client からも安全に OAuth のやり取りを実行できるようにする仕組みです。 |
| Client ID | Developer Console の Keys and tokens セクション内の「Client ID」という見出しの下にあります。表示されない場合は、弊社まで直接お問い合わせください。Client ID は authorize URL を生成する際に必要になります。 |
| Redirect URI | コールバック URL です。[完全一致検証](https://datatracker.ietf.org/doc/html/rfc6749#section-10.6) を通過する必要があります。 |
| Authorization code | アプリケーションがユーザーに代わって API を呼び出せるようにするコードです。auth&#95;code とも呼ばれます。auth&#95;code の有効期限は、アプリの所有者がユーザーから承認済みの auth&#95;code を受け取ってから 30 秒です。30 秒以内に access token と交換する必要があり、そうしない場合は auth&#95;code は失効します。 |
| Access token | Access token は、アプリケーションがユーザーに代わって API リクエストを行うために使用するトークンです。 |
| Refresh token | Refresh token flow を通じて、ユーザーに再度認可を求めることなく、新しい access token を取得できるようにするトークンです。 |
| Client Secret | Confidential client の App タイプを選択している場合、アプリの Keys and tokens セクション内の「Client ID」の下に「Client Secret」が表示されます。 |

<div id="parameters">
  #### パラメーター
</div>

OAuth 2.0 の authorize URL を構成するには、認可 URL に次のパラメーターが含まれていることを確認する必要があります。

|     |     |
| :--- | :--- |
| **Parameter** | **Description** |
| response&#95;type | この値がコードであることを示すため、`code` という値を指定する必要があります。 |
| client&#95;id | Developer Console の「Client ID」ヘッダーの下で確認できます。 |
| redirect&#95;uri | コールバック URL です。この値は、App の設定で定義されている Callback URLs のいずれかと一致している必要があります。OAuth 2.0 では、コールバック URL に対して[完全一致検証](https://datatracker.ietf.org/doc/html/rfc6749#section-10.6)を行う必要があります。 |
| state | ランダムな文字列で、[CSRF 攻撃](https://auth0.com/docs/protocols/state-parameters)に対する検証に使用します。この文字列の長さは最大 500 文字まで指定できます。 |
| code&#95;challenge | 各リクエストごとに生成するランダムなシークレットである [PKCE](https://www.oauth.com/oauth2-servers/pkce/authorization-request/) のパラメーターです。 |
| code&#95;challenge&#95;method | リクエストを行う際に使用するメソッドを指定します (S256 または plain)。 |

<div id="authorize-url">
  #### 認可 URL
</div>

OAuth 2.0 では、ユーザーが「X でログイン」と同様の認証フローを通じて認証できるようにするための認可 URL を作成します。 

作成する URL の例は次のとおりです。

```
https://x.com/i/oauth2/authorize?response_type=code&client_id=M1M5R3BMVy13QmpScXkzTUt5OE46MTpjaQ&redirect_uri=https://www.example.com&scope=tweet.read%20users.read%20account.follows.read%20account.follows.write&state=state&code_challenge=challenge&code_challenge_method=plain
```

この URL が正しく機能するようにするには、適切なエンコードが必要です。[パーセントエンコーディング](/ja/resources/fundamentals/authentication/oauth-1-0a/percent-encoding-parameters)に関するドキュメントを必ず参照してください。

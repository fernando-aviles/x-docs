<div id="what-is-a-disconnection">
  ### 什么是断开连接？
</div>

与流式 API 建立连接意味着发起一个生命周期很长的 HTTPS 请求，并对其响应进行增量解析。连接到过滤流端点时，你应当发起一个 HTTPS 请求，并在尽可能长的时间内持续消费返回的流。除非发生服务端错误、客户端延迟过大、网络问题、例行服务器维护或重复连接，我们的服务器会一直保持该连接处于打开状态。对于与流式端点的连接，出现断开是很常见且应当预期的情况，因此你需要实现相应的重连逻辑。
 

<div id="why-a-streaming-connection-might-be-disconnected">
  #### 为什么流式连接可能会断开
</div>

你的流式连接可能会因为多种原因而断开。检查流返回的错误消息来了解失败的原因。可能的断开原因包括：

* 认证错误（例如使用了错误的 token 或错误的认证方法）。
* X 端的流式服务器被重启。这通常与代码部署有关，属于应预期的情况，需要在系统设计中加以考虑。
* 你的客户端跟不上流中传递的帖子数量，或者读取 data 的速度过慢。每个流式连接背后都有一个要发送给客户端的消息队列。如果这个队列随着时间推移变得过大，连接将被关闭。
* 你的账户超过了每日或每月的帖子配额。
* 你有过多处于活动状态的冗余连接。
* 客户端突然停止读取 data。如果从流中读取帖子的速率突然下降，连接将被关闭。
* 服务器和客户端之间可能存在网络问题。
* 临时的服务器端问题、计划维护或更新。（请查看[状态页](https://api.twitterstat.us/)）

<div id="anticipating-disconnects-and-reconnecting">
  #### 预期断开与重新连接
</div>

在流式获取帖子时，目标是尽可能长时间保持连接，同时要认识到连接中断是可能发生的。该 endpoint 会提供一个 20 秒的保活心跳（表现为一个换行符）。使用这一信号来检测你是否正在被断开连接。

1. 你的代码应检测到新内容和心跳何时停止到达。
2. 如果发生这种情况，你的代码应触发重连逻辑。某些客户端和语言允许你指定读取超时时间，你可以将其设为 20 秒。
3. 你的服务应检测到这些断开连接，并尽快重新连接。

一旦已建立的连接被中断，应立即尝试重连。如果重连失败，根据遇到的错误类型放缓重连尝试的频率：

* 对于 TCP/IP 级别的网络错误，使用线性退避。这类问题通常是暂时的，往往会很快恢复。每次重连尝试将重连延迟增加 250ms，最高增加到 16 秒。
* 对于适合重连的 HTTP 错误，使用指数退避。先等待 5 秒，然后每次尝试将等待时间加倍，最高加到 320 秒。
* 对于 HTTP 429 错误（超出速率限制），使用指数退避。先等待 1 分钟，然后每次尝试将等待时间加倍。请注意，每收到一次 HTTP 429，都会增加你必须等待的时间，直到你账号上的速率限制不再生效为止。

<div id="rate-limits-and-usage">
  #### 速率限制与使用情况
</div>

要检查连接限制，响应会返回三个头部字段。这有助于了解你可以使用规则端点的次数，以及流式端点允许的重连尝试次数。

* `x-rate-limit-limit` 表示在 15 分钟时间窗口内，你的客户端被允许发出的请求配额数量。

* `x-rate-limit-remaining` 表示在当前 15 分钟时间窗口内，已经发出的请求数量。

* `x-rate-limit-reset` 是一个 UNIX 时间戳，表示 15 分钟时间窗口何时会重新开始，并将 `x-rate-limit-remaining` 重置为 0。

过滤流端点目前不会报告使用情况数据。要检查已投递了多少帖子，你的代码可以实现计量逻辑，以便在需要时对消费进行统计和暂停。 

托管流客户端一侧的代码只需将接收到的帖子插入到先进先出 (FIFO) 队列或类似的内存结构中；一个单独的进程/线程应从该队列中消费帖子，对内容进行解析并为存储做准备。采用这种设计，当传入帖子量剧烈变化时，你可以实现一个能够高效扩展的服务。从概念上，你可以将它理解为通过 HTTP 下载一个无限长的文件。

<div id="reconnection-best-practices">
  #### 重新连接最佳实践
</div>

**测试退避策略**

测试退避机制实现的一个好方法是使用无效的授权凭证，并检查重新连接的尝试情况。良好的实现不应收到任何 429 状态码响应。

**为多次重新连接发出告警**

如果客户端在两次重新连接之间的时间达到其设定的上限阈值，应向你发送通知，以便你排查影响连接的问题。

**处理 DNS 变更**

测试你的客户端进程是否遵守 DNS 的生存时间（TTL）。某些技术栈会在进程整个生命周期内缓存解析得到的地址，且不会在规定的 TTL 内采用 DNS 变更。这种激进的缓存行为会在 X 在 IP 地址之间进行负载切换时导致你的客户端出现服务中断。

**User Agent**

确保你的 user-agent HTTP 头部中包含客户端的版本信息。这对诊断 X 端的问题至关重要。如果你的环境不允许设置 user-agent 字段，则设置一个 x-user-agent 头部。

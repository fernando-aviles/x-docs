<div id="what-is-a-disconnection">
  ### 什么是断开连接？
</div>

与流式 API 建立连接，意味着发起一个长时间保持打开状态的 HTTPS 请求，并以增量方式解析响应。连接到 filtered stream 端点时，你应当构造一个 HTTPS 请求，并在实际可行的情况下尽可能长时间持续消费返回的流。除非出现服务器端错误、过度的客户端延迟、网络问题、例行的服务器维护，或重复登录，否则我们的服务器会无限期保持该连接。对于与流式端点的连接，应当预见到连接很可能会被断开，因此需要实现相应的重连逻辑。
 

<div id="why-a-streaming-connection-might-be-disconnected">
  #### 为什么流式连接可能会断开
</div>

你的流式连接可能会因为多种原因而断开。检查流返回的错误信息，以了解失败的原因。可能的断开原因包括：

* 认证错误（例如使用了错误的令牌或错误的认证方法）。
* X 端的流式服务器被重启。这通常与代码部署有关，一般应视为预期行为并在设计时加以考虑。
* 你的客户端无法跟上流中传递的帖子量，或者读取数据的速度过慢。每个流式连接后面都有一个要发送给客户端的消息队列。如果这个队列随着时间推移变得过大，连接将被关闭。
* 你的账号超出了每日 / 每月的帖子配额。
* 你有过多处于活动状态的冗余连接。
* 某个客户端突然停止读取数据。如果从流中读取帖子速率突然下降，连接将被关闭。
* 服务器与客户端之间可能存在网络问题。
* 临时的服务器端问题、计划内维护或更新。（请查看[状态页面](https://api.twitterstat.us/)）

<div id="anticipating-disconnects-and-reconnecting">
  #### 预期断连并重新连接
</div>

在流式传输帖子时，在意识到可能会发生断连的情况下，目标是尽可能长时间保持连接。该端点会每 20 秒发送一次保活心跳（形式为一个换行符）。使用该信号来检测你是否已被断开连接。

1. 你的代码应检测新内容和心跳何时不再到达。
2. 如果发生这种情况，你的代码应触发重连逻辑。某些客户端和编程语言允许你指定读取超时时间，你可以将其设置为 20 秒。
3. 你的服务应检测到这些断连并尽快重新连接。

一旦已建立的连接中断，应立即尝试重新连接。如果重连失败，应根据遇到的错误类型放慢重连尝试节奏：

* 对 TCP/IP 层面的网络错误采用线性退避。这类问题通常是暂时的，并且往往会很快恢复。每次重连尝试将重连延迟增加 250ms，最多增加到 16 秒。
* 对适合重连的 HTTP 错误采用指数退避。起始等待时间为 5 秒，每次尝试加倍，最多加倍到 320 秒。
* 对 HTTP 429 错误（超出速率限制）采用指数退避。起始等待时间为 1 分钟，并在每次尝试时加倍。请注意，每收到一次 HTTP 429，都会增加你的帐户在速率限制不再生效前必须等待的时间。

<div id="rate-limits-and-usage">
  #### 速率限制和使用情况
</div>

要检查连接的速率限制情况，响应中会返回三个响应头。这有助于了解你可以调用规则端点的次数，以及流式端点允许的重连尝试次数。

* x-rate-limit-limit 表示在 15 分钟时间窗口内，你的客户端被允许发起的请求配额。

* x-rate-limit-remaining 表示在当前 15 分钟时间窗口内，到目前为止已发起的请求数量。

* x-rate-limit-reset 是一个 UNIX 时间戳，表示当前 15 分钟时间窗口何时重置，并将 x-rate-limit-remaining 重新设为 0。

过滤流端点当前不会返回用量数据。要检查已经传递了多少条帖子，你的代码可以实现计量逻辑，以便在需要时衡量并暂停消费。

在客户端一侧用于承载流的代码只需将接收到的帖子插入到一个先进先出 (FIFO) 队列或类似的内存结构中；然后由单独的进程/线程从该队列中取出帖子，进行解析并为存储做准备。通过这种设计，当传入帖子量发生剧烈变化时，你可以实现一个能够高效扩展的服务。从概念上讲，你可以把它看作通过 HTTP 下载一个无限长的文件。

<div id="reconnection-best-practices">
  #### 重新连接最佳实践
</div>

**测试退避策略**

测试退避实现的一个好方法是使用无效的授权凭证，并检查重连尝试的情况。良好的实现方式不应收到任何 429 响应。

**为多次重新连接发出告警**

如果客户端的重连间隔时间达到了设定的上限阈值，它应向你发送通知，以便你对影响连接的问题进行排查和处理。

**处理 DNS 变更**

测试你的客户端进程是否遵循 DNS 的生存时间（Time To Live，TTL）。某些技术栈会在进程存续期间缓存已解析的地址，而不会在规定的 TTL 内采纳 DNS 变更。这种激进的缓存策略会在 X 在不同 IP 地址之间迁移负载时导致你的客户端服务中断。

**User Agent**

确保你的 `user-agent` HTTP 头中包含客户端的版本信息。这对于诊断 X 端的问题至关重要。如果你的环境无法设置 `user-agent` 字段，则改为设置 `x-user-agent` 头。

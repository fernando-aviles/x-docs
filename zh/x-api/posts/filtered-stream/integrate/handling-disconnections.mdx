<div id="what-is-a-disconnection">
  ### 什么是断开连接？
</div>

与流式 API 建立连接意味着发起一个持续时间很长的 HTTPS 请求，并以增量方式解析响应。在连接到过滤流端点时，你应当构造一个 HTTPS 请求，并在实际可行的前提下尽可能长时间地读取该流。除非发生服务器端错误、客户端过度延迟、网络问题、例行服务器维护或重复登录等情况，我们的服务器会无限期保持此连接处于打开状态。对于与流式端点建立的连接，连接中断是常见且应当预期的情况，因此需要构建相应的重连逻辑。
 

<div id="why-a-streaming-connection-might-be-disconnected">
  #### 流式连接可能被断开的原因
</div>

你的流式连接可能由于多种原因被断开。检查流返回的错误信息，以了解失败的原因。可能的断开原因包括：

* 身份验证错误（例如使用了错误的令牌或错误的身份验证方式）。
* X 侧的流式服务器被重启。这通常与代码部署相关，应视为预期情况，并在设计时加以考虑。
* 你的客户端无法跟上流中传递的帖子数量，或读取 data 的速度过慢。每个流式连接背后都有一个待发送到客户端的消息队列。如果该队列随着时间推移变得过大，连接将被关闭。
* 你的账户超过了每日或每月的帖子配额上限。
* 你有过多处于活动状态的冗余连接。
* 你的客户端突然停止读取 data。如果从流中读取帖子的速率突然下降，连接将被关闭。
* 服务器与客户端之间可能存在网络问题。
* 临时的服务器端问题、计划内维护和更新。（查看[状态页](https://api.twitterstat.us/)）

<div id="anticipating-disconnects-and-reconnecting">
  #### 预期断连并重新连接
</div>

在流式传输帖子时，目标是尽可能长时间保持连接，同时要认识到断连在所难免。该端点会提供一个 20 秒的保活心跳（它看起来像一个换行符）。使用此信号来检测你是否正在被断开连接。

1. 你的代码应检测新内容和心跳何时不再到达。
2. 如果发生这种情况，你的代码应触发重连逻辑。某些客户端和语言允许你指定读取超时时间，你可以将其设置为 20 秒。
3. 你的服务应检测到这些断连并尽快重新连接。

一旦已建立的连接中断，应立即尝试重连。如果重连失败，请根据遇到的错误类型放慢重连尝试节奏：

* 对于 TCP/IP 级别的网络错误，采用线性退避。这类问题通常是暂时的，往往会很快恢复。每次重连尝试将重连延迟增加 250ms，最多增加到 16 秒。
* 对于适合重连的 HTTP 错误，采用指数退避。从等待 5 秒开始，每次尝试将等待时间加倍，最多到 320 秒。
* 对于 HTTP 429 错误（超过速率限制），采用指数退避。从等待 1 分钟开始，每次尝试将等待时间加倍。请注意，每收到一次 HTTP 429，都会增加你必须等待的时间，直到你的账户不再受到速率限制的影响。

<div id="rate-limits-and-usage">
  #### 速率限制和使用情况
</div>

要检查连接限制，响应会返回三个响应头。这有助于了解你可以使用规则端点的次数，以及流式端点允许的重连尝试次数。

* `x-rate-limit-limit` 表示在 15 分钟时间窗内，你的客户端被分配到的请求总数上限。

* `x-rate-limit-remaining` 表示在 15 分钟时间窗内，到目前为止已经发出的请求数。

* `x-rate-limit-reset` 是一个 UNIX 时间戳，表示 15 分钟时间窗何时重启，并将 `x-rate-limit-remaining` 重置为 0。

过滤流端点目前不会报告使用情况数据。要检查已传递了多少帖子，你的代码可以实现计量逻辑，以便在需要时对消费量进行度量和暂停。 

在客户端一侧承载流的代码，只需将接收到的帖子插入先进先出 (FIFO) 队列或类似的内存结构；一个单独的进程/线程应从该队列中消费帖子，以解析并准备内容进行存储。通过这种设计，当传入帖子量剧烈变化时，你可以实现一个能够高效扩展的服务。从概念上讲，你可以将其视为通过 HTTP 下载一个无限长的文件。

<div id="reconnection-best-practices">
  #### 重新连接最佳实践
</div>

**测试退避策略**

测试退避机制的一个好方法是使用无效的授权凭证，并检查重新连接的尝试情况。良好的实现不应收到任何 429 响应。

**为多次重新连接发出告警**

如果客户端达到了重新连接间隔时间的上限阈值，它应向你发送通知，以便你排查影响连接的问题。

**处理 DNS 变更**

测试你的客户端进程是否遵守 DNS 的生存时间（TTL，Time To Live）。某些协议栈会在整个进程生命周期内缓存已解析的地址，并不会在指定的 TTL 内感知 DNS 变更。这种过于激进的缓存会在 X 在不同 IP 地址之间进行负载切换时导致你的客户端服务中断。

**User Agent**

确保你的 user-agent HTTP 头中包含客户端的版本信息。这对诊断 X 端的问题至关重要。如果你的环境无法设置 user-agent 字段，则设置一个 x-user-agent 头。

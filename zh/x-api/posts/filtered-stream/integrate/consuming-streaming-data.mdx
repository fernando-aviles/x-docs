<div id="building-a-client-to-consume-streaming-data">
  ### 构建用于处理流式数据的客户端
</div>

在使用流式端点时，有一些通用的最佳实践可以帮助优化使用效果。  
 

<div id="client-design">
  #### 客户端设计
</div>

在使用 filter stream 端点构建解决方案时，你需要一个能够执行以下操作的客户端：

1. 与 filter stream 端点建立 HTTPS 流式连接。
2. 以异步方式向 filter stream rules 端点发送 POST 请求，在流中添加和删除规则。
3. 处理低数据量场景——维持流式连接，检测帖子对象和保活信号。
4. 处理高数据量场景——使用异步处理流程将流数据摄取与后续处理解耦，并确保客户端缓冲区定期刷新。
5. 在客户端侧管理和跟踪数据量消耗。
6. 检测流断开，进行评估并自动重新连接到流。
    

<div id="connecting-to-a-streaming-endpoint">
  #### 连接到流式端点
</div>

与 X API v2 流式端点建立连接意味着发起一个长时间保持活动的 HTTP 请求，并以增量方式解析响应。从概念上讲，你可以将其视为通过 HTTP 下载一个无限长的文件。一旦连接建立，只要连接保持打开，X 服务器就会通过该连接持续发送帖子事件。
 

<div id="consuming-data">
  #### 消费数据
</div>

请注意，JSON 对象中的各个字段没有固定顺序，且在任何情况下都不一定包含所有字段。同样，各个活动不会按顺序投递，并且可能会遇到重复消息。请记住，随着时间推移，新的消息类型可能会被添加并通过流发送。

因此，你的客户端必须能够容忍：

* 字段以任意顺序出现
* 意料之外或缺失的字段
* 未排序的帖子
* 重复消息
* 在任意时间通过流传来的新的任意消息类型

除了相关的帖子数据和请求的字段参数之外，下列类型的消息也可能通过流连接传递。请注意，此列表可能并不完整——后续可能会向流中引入更多对象。请确保你的解析器能够容忍意外的消息格式。
 

<div id="buffering">
  #### 缓冲
</div>

流式端点会在数据可用时尽快将其发送给你，这在很多情况下会产生大量数据。如果 X 服务器无法立即将新数据写入流（例如你的客户端读取速度不够快，更多信息请参见[处理断开连接](/zh/x-api/posts/filtered-stream#what-is-a-disconnection)），它会在服务端对内容进行缓冲，以便让你的客户端有机会追上进度。但是，当该缓冲区被填满时，将触发一次强制断开以关闭连接，已缓冲的帖子会被丢弃且不会重发。详情见下文。

识别你的应用何时出现处理滞后的一个方法，是将接收到的帖子的时间戳与当前时间进行比较，并持续跟踪这种差异。

尽管由于公共互联网上的潜在延迟和短暂故障，流数据积压无法被完全消除，但通过对应用进行合理配置，可以在很大程度上避免这种情况。要尽量减少积压的发生：

* 确保你的客户端读取流的速度足够快。通常，在读取流时不应执行任何实质性的处理工作。先读取流，然后将这项工作交给其他线程 / 进程 / 数据存储，以异步方式进行处理。
* 确保你的数据中心拥有足够的入站带宽，以应对大规模的持续数据量以及明显更大的峰值（例如正常流量的 5–10 倍）。对于 filtered stream，你端所需的数据量和相应带宽完全取决于你的规则匹配到了哪些帖子。
   

<div id="usage-tracking-and-rule-management">
  #### 使用情况跟踪与规则管理
</div>

由于开发者对其流中“正常”数据量的预期各不相同，我们无法就具体的百分比增减或时间周期给出通用建议。 

请考虑监控你的流数据量，以发现异常偏差。数据量下降可能反映出的问题与流断开并不相同。在这种情况下，流仍会收到 keep-alive 信号，并且很可能仍有一些新的活动数据。然而，帖子数量显著下降应促使你调查是否存在导致流入你应用或网络的数据量减少的原因，并检查[状态页](https://api.twitterstat.us/)上是否有任何相关通知。

要实现此类监控，你可以跟踪在一定时间内预期看到的新帖子数量。如果某个流的数据量远低于指定阈值，并且在设定的时间段内没有恢复，则应触发告警和通知。你也可能希望监控数据量的大幅上升，尤其是在你正在修改过滤流中的规则，或发生导致帖子活动激增的事件时。

需要注意的是，通过过滤流传递的帖子会计入每月帖子总量，你应跟踪并调整使用量以实现优化。如果数据量较高，可以考虑在每条规则中添加一个 `sample:` 运算符，以在必要时将 100% 匹配降低为 `sample:50` 或 `sample:25`。

此外，我们鼓励你在应用中实现相关机制，当数据量超过预设阈值时向你的团队发出告警，并在必要时引入其他措施，例如自动删除带来过多数据的规则，或在极端情况下彻底断开与流的连接。
 

<div id="responding-to-system-messages">
  #### 响应系统消息
</div>

Keep-alive 信号
流会通过已打开的连接至少每 20 秒发送一次 keep-alive 信号（心跳），以 `\r\n` 回车符的形式，防止你的客户端超时。你的客户端应用应当能够容忍流中的 `\r\n` 字符。

如果你的客户端在 HTTP 库中正确实现了读取超时，你的应用就可以依赖 HTTP 协议和 HTTP 库，在在此时间段内未读取到任何 data 时触发事件，而不需要显式监控 `\r\n` 字符。

该事件通常表现为抛出异常，或根据所使用的 HTTP 库触发其他事件。强烈建议为你的 HTTP 方法添加错误/事件处理程序，以检测这些超时情况。发生超时时，你的应用应尝试重新连接。

错误消息
v2 流式端点也可能在流中返回错误消息。下面给出了这些消息的基本格式以及一些示例。请注意，返回的消息可能会发生变化，并引入新的消息。客户端应用需要能够适应系统消息负载的变化。

请注意，错误消息会提供指向文档的链接，文档说明了如何解决该 Problem。

消息格式：

```{
	"errors": [{
		"title": "operational-disconnect",
		"disconnect_type": "UpstreamOperationalDisconnect",
		"detail": "此流因运营原因已在上游断开连接。",
		"type": "https://api.x.com/2/problems/operational-disconnect"
	}]
}
```

请注意，如果导致强制断开的数据积压本身阻止了错误消息成功发送到你的客户端，那么指示因缓冲区已满而进行强制断开的错误消息可能永远无法到达你的客户端。因此，你的应用不应依赖这些消息来发起重新连接。

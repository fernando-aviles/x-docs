<div id="building-a-client-to-consume-streaming-data">
  ### 构建用于处理流式数据的客户端
</div>

在使用流式端点时，有一些通用的最佳实践可以帮助你优化使用效果。  
 

<div id="client-design">
  #### 客户端设计
</div>

在使用过滤流（filter stream）端点构建解决方案时，你需要一个能够执行以下操作的客户端：

1. 建立到过滤流端点的 HTTPS 流式连接。
2. 以异步方式向过滤流规则端点发送 POST 请求，在流中添加和删除规则。
3. 处理低数据量场景——维护流式连接，识别帖子对象和保活（keep-alive）信号。
4. 处理高数据量场景——使用异步处理将流数据摄取与后续处理解耦，并确保客户端缓冲区被定期刷新。
5. 在客户端管理流量消耗跟踪。
6. 检测流断开，评估情况并自动重新连接到流。
    

<div id="connecting-to-a-streaming-endpoint">
  #### 连接到流式端点
</div>

与 X API v2 流式端点建立连接意味着发起一个存活时间非常长的 HTTP 请求，并按数据到达顺序增量解析响应。从概念上讲，你可以将其理解为通过 HTTP 下载一个无限长的文件。一旦连接建立，只要连接保持打开，X 服务器就会持续通过该连接传递帖子事件。
 

<div id="consuming-data">
  #### 消费数据
</div>

请注意，JSON 对象中的各个字段没有固定顺序，且在不同情况下并不一定都会出现所有字段。同样，各个事件的投递顺序不作排序保证，并且可能会遇到重复消息。请记住，随着时间推移，新的消息类型可能会被添加并通过流发送。

因此，你的客户端必须能够容忍：

* 字段以任意顺序出现
* 意外出现或缺失的字段
* 未排序的帖子
* 重复消息
* 任意时间在流中出现新的任意消息类型

除了相关的帖子数据和请求的字段参数外，流连接还可能会传递以下类型的消息。请注意，此列表可能并不完整——流中可能会引入其他对象。请确保你的解析器能够容忍意外的消息格式。
 

<div id="buffering">
  #### 缓冲
</div>

流式端点会在数据一旦可用时就尽快发送给你，在许多情况下这会导致高数据量。如果 X 服务器无法立即将新数据写入流（例如，如果你的客户端读取速度不够快，更多信息请参见[处理断开连接](/zh/x-api/posts/filtered-stream#what-is-a-disconnection)），它会在自身一侧对内容进行缓冲，以便让你的客户端有时间赶上。不过，当该缓冲区被填满时，将会强制断开连接，缓冲的帖子会被丢弃且不会重发。更多详情见下文。

识别你的应用何时开始落后的一个方法，是将接收到的帖子的时间戳与当前时间进行比较，并在一段时间内持续跟踪这一差异。

尽管由于公共互联网中的潜在延迟和短暂故障，不可能完全消除流的积压，但通过对应用进行适当配置，可以在很大程度上避免这种情况。要尽量减少积压的发生：

* 确保你的客户端读取流的速度足够快。通常在读取流时不应进行任何实质性的处理工作。应先读取流，并将处理任务交由其他线程/进程/数据存储异步完成。
* 确保你的数据中心具有足够的入站带宽，既能支持大规模的持续数据量，也能处理显著更大的突发流量（例如正常流量的 5–10 倍）。对于过滤流，其数据量以及你这边所需的相应带宽完全取决于你的规则匹配到了哪些帖子。
   

<div id="usage-tracking-and-rule-management">
  #### 使用情况跟踪和规则管理
</div>

由于开发者对其流的“正常”数据量应当是多少的预期各不相同，我们无法对具体的百分比增减或时间周期给出通用建议。 

请考虑监控你的流数据量，以发现异常波动。数据量减少可能反映的是与流断开不同的问题。在这种情况下，流仍会接收到保活信号，并且很可能还能收到一些新的活动数据。但是，帖子数量的明显下降应促使你调查，是否存在导致进入你应用或网络的入站数据量下降的原因，并检查 [状态页面](https://api.twitterstat.us/) 上是否有任何相关通知。

要创建此类监控，你可以跟踪在固定时间内预期看到的新帖子数量。如果某个流的数据量下降到远低于指定阈值，且在设定时间内未恢复，则应触发警报和通知。你也可能需要监控数据量的大幅增加，特别是在你正在修改过滤流中的规则，或发生导致帖子活动激增的事件时。

需要特别注意的是，通过过滤流投递的帖子会计入每月帖子总量，你应当跟踪并调整使用量以进行优化。如果数据量较高，可考虑在每条规则中添加 `sample:` 操作符，在必要时将 100% 匹配降低为 `sample:50` 或 `sample:25`。

此外，我们鼓励你在应用内实现相关机制，当数据量超过预设阈值时提醒你的团队，并视情况引入其他措施，例如自动删除带来过多数据的规则，或在极端情况下完全断开与流的连接。
 

<div id="responding-to-system-messages">
  #### 响应系统消息
</div>

保活信号
流至少每 20 秒会发送一个保活信号（keep-alive），也称为心跳（heartbeat），以 \r\n 回车符的形式通过已打开的连接发送，以防止你的客户端超时。你的客户端应用应当能够容忍流中的 \r\n 字符。

如果你的客户端在 HTTP 库中正确实现了读取超时（read timeout），你的应用就可以依赖 HTTP 协议和 HTTP 库，在此时间段内未读取到任何数据时抛出事件，而无需显式监控 \r\n 字符。

该事件通常表现为抛出异常，或根据所使用的 HTTP 库触发其他事件。强烈建议为你的 HTTP 方法添加错误/事件处理程序，以检测这些超时情况。发生超时时，你的应用应尝试重新连接。

错误消息
v2 流式端点也可能在流中返回错误消息。下面给出了这些消息的基本格式以及一些示例。请注意，返回的消息可能会发生变化，并可能引入新的消息。客户端应用需要能够容忍不断变化的系统消息负载。

请注意，错误消息会链接到说明如何解决该 Problem 的文档。

消息格式：

```{
	"errors": [{
		"title": "operational-disconnect",
		"disconnect_type": "UpstreamOperationalDisconnect",
		"detail": "此流因运营原因已在上游断开连接。",
		"type": "https://api.x.com/2/problems/operational-disconnect"
	}]
}
```

请注意，由于缓冲区已满而被强制断开连接的错误消息，可能永远不会到达你的客户端，因为触发这次强制断开的积压本身就可能阻止该消息发送成功。因此，你的应用不应依赖这些消息来发起重连。

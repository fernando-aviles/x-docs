<div id="building-a-client-to-consume-streaming-data">
  ### 构建用于处理流式数据的 Client
</div>

在使用流式端点时，有一些通用的最佳实践可以帮助你更高效地使用它。  
 

<div id="client-design">
  #### Client 设计
</div>

在使用 filter stream endpoint 构建解决方案时，你需要一个能够执行以下操作的 Client：

1. 建立到 filter stream endpoint 的 HTTPS 流式连接。
2. 以异步方式向 filter stream rules endpoint 发送 POST 请求，在流中添加和删除规则。
3. 处理低数据量场景——保持流式连接，检测帖子对象和 keep-alive 保活信号。
4. 处理高数据量场景——使用异步进程将流数据接入与后续处理解耦，并确保客户端缓冲区定期刷新。
5. 在客户端跟踪并管理数据量消耗。
6. 检测流中断，进行评估并自动重新连接到流。
    

<div id="connecting-to-a-streaming-endpoint">
  #### 连接到流式端点
</div>

与 X API v2 流式端点建立连接，意味着发起一个生命周期很长的 HTTP 请求，并以增量方式解析响应。从概念上讲，可以把它理解为通过 HTTP 下载一个无限长的文件。一旦连接建立，只要连接保持打开状态，X 服务器就会持续通过该连接发送帖子事件。
 

<div id="consuming-data">
  #### 消费数据
</div>

请注意，JSON 对象中的各个字段没有顺序保证，并且在任何情况下都不一定会包含所有字段。同样，各个活动不会按排序顺序投递，并且可能会遇到重复消息。还要牢记，随着时间推移，新的消息类型可能会被添加并通过流发送。

因此，你的客户端必须能够容忍：

* 字段以任意顺序出现
* 非预期字段或缺失字段
* 未排序的帖子
* 重复消息
* 任何时候可能从流中传来的新的任意类型的消息

除了相关的帖子数据和请求的字段参数外，通过流连接还可能投递以下类型的消息。请注意，此列表可能并不完整——流中可能会引入额外的对象。请确保你的解析器能够容忍非预期的消息格式。
 

<div id="buffering">
  #### 缓冲
</div>

流式端点会在数据一旦可用时就尽快发送给你，在很多情况下这会带来很高的数据量。如果 X 服务器无法立即向流中写入新数据（例如你的 client 读取速度不够快，更多信息参见[处理断开连接](/zh/x-api/posts/filtered-stream#what-is-a-disconnection)），它会在自身一侧对内容进行缓冲，以便让你的 client 有时间追上进度。不过，当该缓冲区被填满时，将触发一次强制断开连接来关闭连接，已缓冲的帖子将被丢弃且不会重发。更多细节见下文。

识别你的 app 何时开始落后的一个方法，是比较接收到的帖子时间戳与当前时间，并在一段时间内持续跟踪这一差异。

尽管由于公共互联网的潜在延迟和抖动，流数据积压无法被完全消除，但通过正确配置你的 app，可以在很大程度上避免这种情况。要尽量减少积压的发生：

* 确保你的 client 以足够快的速度读取流。通常在读取流的同时不应进行任何实际的处理工作。应先读取流，然后将活动交给其他线程/进程/数据存储，异步地执行处理。
* 确保你的数据中心具备足够的入站带宽，以容纳大规模的持续数据量以及明显更大的峰值（例如正常流量的 5–10 倍）。对于过滤流，数据量以及你这端所需的对应带宽完全取决于你的规则匹配到了哪些帖子。
   

<div id="usage-tracking-and-rule-management">
  #### 使用情况跟踪与规则管理
</div>

由于开发者对其流中“正常”数据量的预期各不相同，我们无法就具体的百分比增减或时间周期给出通用建议。 

请考虑监控流数据量是否出现异常偏差。数据量减少可能反映的是与流断开不同的问题。在这种情况下，流仍会接收保活信号，并且很可能仍有一些新的活动数据。然而，如果帖子数量显著减少，应调查是否存在导致应用或网络入站数据量下降的原因，并检查 [状态页面](https://api.twitterstat.us/) 上是否有任何相关通知。

要实现此类监控，您可以跟踪在一定时间内预期看到的新帖子数量。如果某个流的数据量大幅低于指定阈值，并且在设定时间内未恢复，则应触发告警和通知。您也可能需要监控数据量的大幅增加，尤其是在您正在修改过滤流中的规则，或者出现导致帖子活动激增的事件时。

需要注意的是，通过过滤流传送的帖子会计入每月帖子总量，您应跟踪并调整使用量以进行优化。如果数据量较高，请考虑在每条规则中添加 `sample:` 运算符，将 100% 匹配根据需要降低为 `sample:50` 或 `sample:25`。

此外，我们建议您在 App 中实现一些机制：当数据量超过预设阈值时向团队发出告警，并在必要时引入其他措施，例如自动删除带来过多数据的规则，或在极端情况下完全断开与流的连接。
 

<div id="responding-to-system-messages">
  #### 响应系统消息
</div>

Keep-alive 信号
流会至少每 20 秒通过已打开的连接发送一个 keep-alive（心跳）信号，其形式为一个 \r\n 回车符，以防止客户端超时。你的客户端应用应能够正确处理流中的这些 \r\n 字符。

如果你的客户端在 HTTP 库中正确实现了读取超时机制，你的应用就可以依赖 HTTP 协议和 HTTP 库，在该时间段内没有读取到任何数据时触发事件，而无需显式监控 \r\n 字符。

该事件通常表现为抛出一个异常，或者是其他形式的事件，这取决于所使用的 HTTP 库。强烈建议使用错误/事件处理程序包装你的 HTTP 方法，用于检测这些超时情况。发生超时时，你的应用应尝试重新连接。

错误消息
v2 流式端点也可能在流中推送错误消息。下面给出了这些消息的基本格式以及一些示例。请注意，返回的消息可能会发生变化，并且可能会引入新的消息。客户端应用程序需要对系统消息载荷的变化保持兼容。

请注意，错误消息会包含指向相关文档的链接，该文档会说明如何解决该 Problem。

消息格式：

```{
	"errors": [{
		"title": "operational-disconnect",
		"disconnect_type": "UpstreamOperationalDisconnect",
		"detail": "此流因运营原因已在上游断开连接。",
		"type": "https://api.x.com/2/problems/operational-disconnect"
	}]
}
```

请注意，如果导致强制断开的积压阻止错误消息发送成功，那么指示缓冲区已满并触发强制断开的错误消息可能永远无法到达你的客户端。因此，你的 App 不应依赖接收到这些消息来发起重连。

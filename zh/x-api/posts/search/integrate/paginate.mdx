<div id="recent-search-pagination">
  ### 最近搜索的分页
</div>

<div id="introduction">
  #### 引言
</div>

搜索查询通常会匹配到比单个 API 响应中可返回数量更多的帖子。发生这种情况时，数据会以一系列“页面”的形式返回。分页是指按顺序请求所有页面，以便获取整个数据集的方法。

以下是最近搜索分页的基本细节：

* 最近搜索端点会针对一次查询返回至少一页结果，如果还有更多页面可用，则会在 JSON 响应中提供一个 next&#95;token。为了接收所有匹配的帖子，可以重复这一过程，直到响应中不再包含该 token。

* next&#95;token 不会过期。多次使用相同的 next&#95;token 值发起请求，无论请求何时发出，都将收到相同的结果。

* 帖子按时间逆序（从新到旧）返回，并使用 UTC 时区。对于单个页面以及跨多个页面都是如此： 
  * 第一页响应中的第一条帖子是与你的查询匹配的最新帖子。
  * 最后一页响应中的最后一条帖子是与你的查询匹配的最早帖子。

* max&#95;results 请求参数使你可以配置每个响应中返回的帖子数量。默认值是 10 条帖子，最大值为 100 条。 

* 每种分页实现都需要从响应负载中解析 next&#95;token，并在“下一页”的搜索请求中包含它。有关如何构造这些“下一页”请求的更多细节，请参见下文。
   

最近搜索端点旨在支持两种基本使用模式：

* **获取历史数据（Get historical）** - 从感兴趣的时间范围中请求匹配的帖子。这通常是为支持历史研究而发起的一次性请求。搜索请求可以基于 start&#95;time 和 end&#95;time 请求参数。最近搜索端点会以时间逆序返回帖子，从与你的查询匹配的最新帖子开始。 

* **轮询（Polling）** - 请求自上一次接收的帖子以来新发布的匹配帖子。这类用例通常侧重于近实时，并且以频繁请求、“监听”感兴趣的新帖子为特征。最近搜索端点提供 since&#95;id 请求参数，以支持“轮询”模式。为了便于基于帖子 ID 进行定位，还提供了 until&#95;id 请求参数。
   

接下来我们将讨论历史模式。这是最近搜索端点的默认模式，并用于说明分页的基本原理。然后我们将讨论轮询用例的示例。当轮询触发分页时，管理搜索请求还需要一个额外步骤。
 

<div id="retrieving-historical-data">
  #### 检索历史数据
</div>

本节介绍如何使用 start&#95;time 和 end&#95;time 请求参数，从指定时间范围（目前仅限最近 7 天）中检索帖子。历史请求通常是一次性请求，用于支持研究和分析。 

按时间范围发起请求是 recent search 端点的默认行为。如果搜索请求未指定 start&#95;time、end&#95;time 或 since&#95;id 请求参数，则 end&#95;time 默认为“现在”（实际上是查询时间前 30 秒），start&#95;time 默认为 7 天前。

该端点将以时间倒序返回第一页帖子，从最新的帖子开始。如果还有更多页数据，响应 JSON 负载中还会包含一个 next&#95;token。为了收集所有符合条件的帖子，而不管有多少页数据，都需要持续发起请求，直到不再返回 next&#95;token。 

例如，下面是一个检索上周内包含关键字 snow 的帖子的初始请求：

https://api.x.com/2/tweets/search/recent?query=snow

响应会包含最近的 10 条帖子，以及 JSON 响应中的这些 `meta`（元数据）属性：

```
"meta": {
        "newest_id": "1204860593741553664",
        "oldest_id": "1204860580630278147",
        "next_token": "b26v89c19zqg8o3fobd8v73egzbdt3qao235oql",
        "result_count": 10
    }
```

要获取接下来的 10 条帖子，需要在原始请求中加入这个 next&#95;token。请求如下：

https://api.x.com/2/tweets/search/recent?query=snow&amp;next&#95;token=b26v89c19zqg8o3fobd8v73egzbdt3qao235oql

查找 next&#95;token 并将其包含在后续请求中的过程可以重复执行，直到收集到所有（或指定数量的）帖子，或直到已发出指定数量的请求。如果在你的用例中数据保真度（收集查询的所有匹配结果）至关重要，那么采用一种简单的“重复直到 request.next&#95;token 为 null”设计就足够了。

<div id="polling-and-listening-use-cases">
  #### 轮询与监听用例
</div>

本节说明如何通过在最近搜索端点中使用 since&#95;id 请求参数来获取最近的帖子。 

在轮询用例中，会以持续且高频的方式发起“是否有新的感兴趣帖子？”这类查询。与基于时间发起请求的历史用例不同，轮询用例通常是基于帖子 ID 发起请求。

轮询使用模式的核心在于，每一条新的帖子都有一个[唯一 ID](/zh/resources/fundamentals/x-ids)，该 ID 由 X 平台按总体递增的顺序“生成并发出”。如果一条帖子的 ID 小于另一条的 ID，意味着它发布得更早。

最近搜索端点支持按帖子 ID 浏览帖子存档。来自该端点的响应包含 oldest&#95;id 和 newest&#95;id 帖子 ID。在轮询模式下，请求会将 since&#95;id 设置为目前为止收到的最大/最新 ID。 

例如，假设每五分钟请求一次关于 “snow” 的新帖子，并且我们上一次接收到的最后一条帖子的帖子 ID 为 10000。到达轮询时间时，请求如下所示：

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=10000

接下来，假设自上一次请求以来又发布了七条帖子。由于这些帖子全部被包含在同一个 data “页面”中，因此不会有 next&#95;token。响应会提供最新（最近发布）帖子的帖子 ID：

```
"meta": {
        "newest_id": "12000",
        "oldest_id": "10005",
        "result_count": 7
    }
```

要发起下一次轮询查询，需要使用这个 newest&#95;id 值来设置下一个 since&#95;id 参数：

`https://api.x.com/2/tweets/search/recent?query=snow&since_id=12000`

当有更多数据可用并且返回了 next token 时，只需要结果第一页中的 newest&#95;id 值。每一页数据都会包含 newest&#95;id 和 oldest&#95;id 值，但在下一次按计划进行的轮询请求中，只需要使用第一页返回的那个值即可。因此，如果你实现的是轮询方案，或者按 ID 范围搜索帖子，分页逻辑会稍微复杂一些。 

现在假设又新增了 18 条匹配的帖子。该 endpoint 会首先返回一个初始响应，其中包含一整页数据以及一个 next&#95;token，用于在这 5 分钟时间段内请求下一页数据。同时，它还会包含下一次 5 分钟轮询间隔所需的最新帖子 ID。

```
"meta": {
        "newest_id": "13800",
        "oldest_id": "12500",
        "next_token": "fnsih9chihsnkjbvkjbsc",
        "result_count": 10
    }
```

要在这五分钟时间段内收集所有匹配的数据，请在下一次请求中传递 `next_token`，并使用与上一次请求相同的 `since_id` 值。

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=12000&amp;next&#95;token=fnsih9chihsnkjbvkjbsc

```
"meta": {
        "newest_id": "12300",
        "oldest_id": "12010",
        "result_count": 8
    }
```

第二个响应返回剩余的 8 条帖子，并且不包含 next&#95;token。请注意，我们不会更新 newest&#95;id 值（12300），而是仍然基于第一个响应中的 newest&#95;id 值来构建下一次 since&#95;id 请求：

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=13800

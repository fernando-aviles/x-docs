<div id="recent-search-pagination">
  ### 最近搜索分页
</div>

<div id="introduction">
  #### 介绍
</div>

搜索查询通常会匹配到多于单个 API 响应所能返回的帖子。出现这种情况时，data 会以一系列“页面”的形式返回。“分页”指的是为了获取整个数据集而按顺序请求所有页面的方法。

以下是近期搜索分页的基本信息：

* 近期搜索端点对查询至少会返回一页 data，如果还有更多页面可用，则会在其 JSON 响应中提供一个 next&#95;token。为了接收所有匹配的帖子，可以重复此过程，直到响应中不再包含 token。

* next&#95;token 不会过期。使用相同 next&#95;token 值发起的多个请求，无论在何时发出，都会收到相同的结果。

* 帖子按时间逆序（最新在前）并使用 UTC 时区返回。这一规则在单个页面内以及跨多个页面时都成立： 
  * 第一个响应中的第一条帖子将是与你的查询匹配的最新帖子。
  * 最后一个响应中的最后一条帖子将是与你的查询匹配的最早帖子。

* max&#95;results 请求参数允许你配置每个响应中返回的帖子数量。默认值为 10 条帖子，最大值为 100 条。 

* 任何分页实现都需要从响应负载中解析 next&#95;token，并将其包含在“下一页”的搜索请求中。有关如何构建这些“下一页”请求的更多详细信息，请参阅下文。
   

近期搜索端点旨在支持两种基本使用模式：

* **获取历史数据（Get historical）** - 从感兴趣的时间段中请求匹配的帖子。这类请求通常为支持历史研究的一次性请求。搜索请求可以基于 start&#95;time 和 end&#95;time 请求参数。近期搜索端点会按时间逆序返回帖子，从最新的匹配帖子开始。 

* **轮询（Polling）** - 请求自上次接收帖子以来新发布的匹配帖子。这类用例通常接近实时，并以频繁请求为特征，用于“监听”新的目标帖子。近期搜索端点提供 since&#95;id 请求参数以支持这种“轮询”模式。为便于通过帖子 ID 进行定位，还提供了 until&#95;id 请求参数。
   

接下来，我们将讨论历史模式。这是近期搜索端点的默认模式，并用于说明分页的基本原理。然后我们会讨论轮询用例的示例。当轮询触发分页时，管理搜索请求还需要一个额外步骤。
 

<div id="retrieving-historical-data">
  #### 检索历史数据
</div>

本节说明如何使用 `start_time` 和 `end_time` 请求参数，从你关注的时间段（当前限制为最近 7 天）中检索帖子。历史数据请求通常是为研究和分析而进行的一次性请求。 

按时间范围发起请求是 recent search 端点的默认模式。如果搜索请求未指定 `start_time`、`end_time` 或 `since_id` 请求参数，则 `end_time` 将默认为“现在”（实际为查询时间前 30 秒），而 `start_time` 将默认为 7 天前。

该端点会以时间倒序返回第一“页”帖子，从最新的帖子开始。如果存在更多数据页，JSON 响应负载中还会包含一个 `next_token`。为了收集所有匹配的帖子，而不论页数多少，需要重复发送请求，直到不再返回 `next_token`。 

例如，以下是一个获取最近一周内包含关键词 snow 的帖子的初始请求：

https://api.x.com/2/tweets/search/recent?query=snow

响应中包含最近的 10 条帖子，以及 JSON 响应中的以下名为 `meta` 的元数据属性：

```
"meta": {
        "newest_id": "1204860593741553664",
        "oldest_id": "1204860580630278147",
        "next_token": "b26v89c19zqg8o3fobd8v73egzbdt3qao235oql",
        "result_count": 10
    }
```

要检索接下来的 10 条帖子，需要在原始请求中添加该 next&#95;token。请求如下：

https://api.x.com/2/tweets/search/recent?query=snow&amp;next&#95;token=b26v89c19zqg8o3fobd8v73egzbdt3qao235oql

查找 next&#95;token 并在后续请求中将其加入的过程可以重复进行，直到收集到所有（或指定数量的）帖子，或直到达到预设的请求次数。如果你的用例非常重视数据完备性（收集到与你的查询匹配的所有结果），一个简单的 &quot;repeat until request.next&#95;token is null&quot; 设计即可满足需求。

<div id="polling-and-listening-use-cases">
  #### 轮询和监听用例
</div>

本节介绍如何通过使用 `since_id` 请求参数轮询 recent search 端点来获取最新的帖子。 

在轮询用例中，会以持续且高频的方式发出“有新的感兴趣的帖子吗？”这类查询。不同于基于时间发起请求的历史用例，轮询用例通常是基于帖子 ID 发起请求。

轮询模式的核心在于：每条新的帖子都有一个从 X 平台“发出”的[唯一 ID](/zh/resources/fundamentals/x-ids)，通常按升序排列。如果一条帖子的 ID 比另一条小，就意味着它发布得更早。

recent search 端点支持按帖子 ID 在帖子存档中进行遍历。该端点的响应中会包含 `oldest_id` 和 `newest_id` 这两个帖子 ID。在轮询模式中，请求会使用 `since_id`，并将其设置为目前为止收到的最大/最新 ID。 

例如，假设每五分钟查询一次关于“snow”的新帖子，而我们最后收到的那条帖子的帖子 ID 是 10000。当需要进行轮询时，请求如下：

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=10000

接下来，假设自上次请求以来又发布了七条帖子。由于这些帖子都位于同一个 data “页”中，因此不会返回 `next_token`。该响应会提供最新一条帖子的帖子 ID：

```
"meta": {
        "newest_id": "12000",
        "oldest_id": "10005",
        "result_count": 7
    }
```

要发起下一次轮询查询，需要使用这个 newest&#95;id 值来设置下一次的 since&#95;id 参数：

`https://api.x.com/2/tweets/search/recent?query=snow&since_id=12000`

当有更多可用数据并且提供了 next token 时，只需要第一页结果中的 newest&#95;id 值即可。每一页 data 都会包含 newest&#95;id 和 oldest&#95;id 值，但只有第一页中提供的值是在下一次按预定时间进行的轮询请求中所需的。因此，如果你在实现轮询方案，或者按 ID 区间搜索帖子，分页逻辑会稍微复杂一些。 

现在假设又有 18 条新的匹配帖子。该端点会返回一个初始响应，其中包含完整的一页 data，以及一个用于在这 5 分钟时间段内请求下一页 data 的 next&#95;token。它还会包含在 5 分钟后下一次轮询间隔中所需的最新帖子 ID。

```
"meta": {
        "newest_id": "13800",
        "oldest_id": "12500",
        "next_token": "fnsih9chihsnkjbvkjbsc",
        "result_count": 10
    }
```

要在这五分钟时间段内收集所有匹配的 data，请在下一个请求中传递 `next_token`，并使用与上一个请求相同的 `since_id` 值。

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=12000&amp;next&#95;token=fnsih9chihsnkjbvkjbsc

```
"meta": {
        "newest_id": "12300",
        "oldest_id": "12010",
        "result_count": 8
    }
```

第二个响应返回剩余的八条帖子，并且不包含 next&#95;token。请注意，我们不会更新 newest&#95;id 值（12300），而是基于第一个响应中的 newest&#95;id 值来发起下一个 since&#95;id 请求：

https://api.x.com/2/tweets/search/recent?query=snow&amp;since&#95;id=13800

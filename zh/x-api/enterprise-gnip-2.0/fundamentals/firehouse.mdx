<div id="overview">
  ## 概览
</div>

`Enterprise`

X 的核心价值之一是捍卫和尊重用户的声音。这包括在用户在 X 上删除、修改或编辑他们选择分享的内容时，尊重他们的期望和意图。我们认为，这对于维护全球最大公共、实时信息平台之一的长期健康至关重要。X 将控制权交到用户手中，使个人能够掌控自己的 X 使用体验。我们认为，获取 X 数据的商业用户有责任尊重终端用户的期望和意图。

关于 X 平台上可能出现的各类合规相关事件的更多信息，请参考我们的文章：[在 X 上尊重用户意图](/zh/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter)。

任何通过 API 使用 X 数据的开发者或公司都有义务尽一切合理努力来尊重并跟进用户对其内容所做的变更。该义务扩展到用户事件，例如删除、修改以及分享选项的更改（例如内容变为受保护或被屏蔽）。这也包括用户编辑其帖子时的情况。请参考[开发者政策](https://developer.x.com/en/developer-terms/policy)和/或您的 X 数据协议中的具体条款，以了解该义务将如何影响您对 X 数据的使用。

X 提供以下解决方案，用于提供关于这些用户合规事件的信息，以及某条特定帖子或用户当前是否公开可用。以下是这些解决方案及其通用集成模式的简要概述：

<div id="get-statuseslookup-and-get-userslookup">
  #### GET statuses/lookup 和 GET users/lookup
</div>

* 格式：REST API。参见：[GET statuses/lookup](https://developer.x.com/en/docs/x-api/v1/tweets/post-and-engage/api-reference/get-statuses-lookup) 和 [GET users/lookup](https://developer.x.com/en/docs/x-api/v1/accounts-and-users/follow-search-get-users/api-reference/get-users-lookup)。

* 这些端点始终返回任意帖子编辑后的最新版本。所有在编辑功能推出之后创建的帖子对象都会包含帖子编辑元数据，即便是那些从未被编辑过的帖子也会如此。

* 对于所有帖子，在帖子创建 30 分钟之后发起的请求，将会反映所有帖子的最终状态。

* 根据调用方在 API 请求中的定义，提供特定帖子或用户的可用状态信息。

* 可用于对特定一组帖子 / 用户当前可用状态进行临时抽查。

* 适用于需要在某一特定时刻检查特定帖子或用户当前状态的客户。

* 这些 API 为需要检查某条内容可用性的客户提供了一种有用机制，例如在以下场景中：
  1. 展示帖子
  2. 以 1:1 的方式与帖子或用户进行互动
  3. 通过允许的文件下载向第三方分发 X 内容
  4. 长期存储帖子

<div id="compliance-firehose-enterprise-only">
  #### Compliance Firehose（仅限企业版）
</div>

* 格式：流式 API。参见：[Compliance Firehose](/zh/x-api/enterprise-gnip-2.0/fundamentals/firehouse#api-reference)。
* 提供 X 上[合规活动](/zh/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects)的实时流。这些活动包括帖子被编辑时发生的事件。 
* 可用于在平台上出现新的合规事件时，维护一组已存储数据的合规状态。
* 非常适合需要获取并长期存储大量 X 数据的客户。

  ### **合规性最佳实践**
</div>

<div id="recommendations-best-practices">
  #### **建议与最佳实践**
</div>

* **构建存储数值型 Post ID 和 User ID 的数据存储模式（schema）**：用户级合规消息要求针对该用户的所有帖子采取相应操作。因此，由于所有合规消息仅通过数值型 ID 传递，设计数据存储模式时务必要基于数值型 ID 维护帖子与用户之间的关联关系。数据使用方需要同时按 Post ID 和 User ID 监控合规事件，并能够相应更新本地数据存储。

* **构建设计涵盖所有合规状态的模式（schema）**：根据在不同应用中处理合规活动的方式，可能需要向数据存储中添加其他元数据。例如，数据使用方可以决定在现有数据库中添加元数据，以便在收到 status&#95;withheld 消息时，更方便地限制在受影响国家/地区展示内容。

* **处理转推删除**：转推是一种特殊类型的帖子，其中原始消息作为一个对象嵌套在转推中。在这种情况下，一个转推中会引用两个 Post ID：一个是转推自身的 ID，另一个是原始消息的 ID（包含在嵌套对象中）。当原始消息被删除时，会针对原始 ID 发送一条帖子删除消息。帖子删除事件通常会触发所有相关转推的删除事件。但在某些情况下，并非所有删除事件都会被发送，客户端系统应能容忍转推删除不完整的情况。删除原始 ID 通常就足以删除所有后续转推。最佳实践是在存储转推时引用原始 Post ID，并在收到帖子删除事件时删除所有被引用的转推。

<div id="compliance-firehose-api">
  #### **Compliance Firehose API**
</div>

可能发生的合规事件类型包括帖子（或“status”）事件和用户事件，具体类型如下所述。  

请注意：

* 在[此处](https://support.x.com/articles/14016)了解更多用户状态相关信息，我们面向开发者的、关于已删除帖子的政策请见[此处](https://dev.x.com/overview/terms/policy#3.Update_Respect_Users_Control_and_Privacy)。
* Compliance Firehose 已更新以提供 `tweet_edit` 事件。 
* 若干用户删除、保护和封禁事件不一定是永久性的，可以在不同状态之间无限次切换。这些包括：user&#95;delete、user&#95;undelete、user&#95;protect、user&#95;unprotect 以及 user&#95;suspend、user&#95;unsuspend。
* 仅当用户没有选择 user&#95;undelete 其账号时，user&#95;delete 事件之后才会在 30 天后触发 status&#95;delete 事件。用户有可能撤销 user&#95;delete，而在 30 天后其所有帖子的删除则不会发生。
* user&#95;suspend 是一个始终保持为 true 的操作，除非该用户发生 user&#95;unsuspend 事件。这些事件不受 30 天时间段内任何变化的影响。

请参考 “Recommended Action”（建议操作）一列，以了解如何处理每种事件类型，从而尊重终端用户的隐私和意图。

| Original Message Type | Object | Permanent (Yes/No) | Recommended Action |
| :--- | :--- | :--- | :--- |
| delete | Status | Yes | 删除关联的帖子。 |
| status&#95;withheld | Status | Yes | 在 status&#95;withheld 消息列出的特定国家/地区屏蔽关联帖子。 |
| drop | Status | No  | 将帖子从公共视图中移除。 |
| undrop | Status | No  | 状态可以再次显示并视为公开。 |
| tweet&#95;edit | Status | Yes | 尊重并在适用时展示新的编辑内容。 |
| user&#95;delete | User | No  | 屏蔽或删除关联用户的所有帖子。 |
| user&#95;undelete | User | No  | 关联用户的所有帖子可以再次显示并视为公开。 |
| user&#95;protect | User | No  | 屏蔽或删除关联用户的所有帖子。 |
| user&#95;unprotect | User | No  | 关联用户的所有帖子可以再次显示并视为公开。 |
| user&#95;suspend | User | No  | 屏蔽或删除关联用户的所有帖子。 |
| user&#95;unsuspend | User | No  | 关联用户的所有帖子可以再次显示并视为公开。 |
| scrub&#95;geo | User | Yes | 删除 X 为该用户在 scrub&#95;geo 消息中指定的帖子之前的所有帖子所提供的地理数据。请注意，该用户后续的帖子可能包含可使用的地理数据。 |
| user&#95;withheld | User | Yes | 在 user&#95;withheld 消息列出的特定国家/地区屏蔽关联用户的帖子。 |
| delete | Favorite | Yes | 删除关联的点赞/收藏。 |

<div id="integrating-compliance-firehose">
  ### 集成 Compliance Firehose
</div>

Compliance Firehose 是一个实时流式 API，用于传递在 X 平台上发生的合规事件。若要了解合规事件以及它们在 X 上是如何生成的，请参考我们的文章，[在 X 上尊重用户意图](/zh/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter)。

需要特别注意的是，帖子事件和用户事件是分别投递的，并且每类事件都应分别处理（即，一个帖子删除并不意味着会有用户事件，反之亦然）。某些用户事件不一定是永久性的，可以在不同状态之间无限次切换。这些事件包括：user&#95;delete、user&#95;undelete、user&#95;protect、user&#95;unprotect 以及 user&#95;suspend、user&#95;unsuspend。

只有在用户没有选择 user&#95;undelete 其账户的情况下，user&#95;delete 事件之后才会在 30 天后跟随 status&#95;deletes。用户有可能撤销一次 user&#95;delete 操作，从而在 30 天后不会对其所有帖子执行删除。

user&#95;suspend 是一个一旦发生即持续生效的操作，除非该用户随后发生 user&#95;unsuspend 事件。这些操作不受任何 30 天时间周期相关更改的影响。

绝不应将合规事件直接展示给你软件的终端用户，或以其他方式将其融入你的产品或客户体验中。它们仅用于维护合规性并尊重 X 用户的操作意图。

<div id="integrating-with-the-compliance-firehose">
  #### **与 Compliance Firehose 集成**
</div>

要将 Compliance Firehose 集成到你的系统中，你需要构建一个集成组件，使其能够执行以下操作：

1. 为 Compliance Firehose 的每个流式 API 分区建立流式连接
2. 处理大规模数据量 —— 使用异步处理流程，将流数据摄取与后续处理解耦
3. 在因任何原因断开连接时自动重新连接到流分区
4. 按照上文所述指南，处理与你存储的帖子和用户数据相关的合规事件

<div id="honoring-user-intent-on-twitter">
  ### 在 Twitter 上尊重用户意图
</div>

我们相信，尊重 X 用户的隐私和意图，对这个世界上最大规模的公共实时信息平台之一的长期健康发展至关重要。X 将隐私控制权交到用户自己手中，使个人能够掌控自己的 X 使用体验。作为 X 数据的企业级使用方，我们肩负着共同的责任，需要尊重终端用户的隐私和行为，从而维护这种信任与尊重的环境。

帖子和用户账户可能会发生多种变化，从而影响它们在平台上的展示方式。影响隐私和意图的操作在状态（帖子）层级和用户层级上都有定义。这些操作包括：

<div id="user">
  #### 用户
</div>

| 操作 | 描述 |
| :--- | :--- |
| 保护账号 | X 用户可以随时将其账号设置为受保护或取消保护。受保护账号要求用户手动批准每一位被允许查看其账号帖子的用户。  <br />有关更多信息，请参阅 [关于公开和受保护的帖子](https://support.x.com/articles/14016-about-public-and-protected-tweets)。 |
| 删除账号 | X 用户可以随时决定删除其账号以及所有关联的状态消息。X 会在删除后的 30 天内保留账号信息，以防用户决定撤销删除并重新激活其账号。 |
| 清除地理位置 | X 用户可以随时从过去的帖子中删除所有位置信息。这被称为“scrub geo”（清除地理位置）。 |
| 暂停账号 | 如果账号违反了 X 规则，或被怀疑遭到入侵或被攻破，X 保留暂停该账号的权利。账号暂停只能由 X 撤销（解除暂停）。 |
| 限制账号 | X 保留在特定国家/地区按需限制访问某些内容的权利。被限制的账号只能由 X 解除限制。  <br />有关更多信息，请参阅 [按国家/地区限制的内容](https://support.x.com/articles/20169222-country-withheld-content)。 |

<div id="status">
  #### 状态
</div>

| 操作 | 描述 |
| :--- | :--- |
| 删除状态 | X 用户可以在任何时间删除状态。已删除的状态无法恢复，并会被永久删除。 |
| 限制状态 | X 保留在特定国家/地区不时限制访问某些内容的权利。受限制的状态只能由 X 取消限制。   <br />如需更多信息，请参阅 [因国家/地区限制的内容](https://support.x.com/articles/20169222-country-withheld-content)。 |

<div id="keeping-track-of-user-and-status-changes">
  #### 跟踪 User 和 Status 的变更
</div>

User 或 Status 的状态可能在任何时候由于上述操作之一而发生变化，这会影响 X 数据使用方应如何处理所有关联内容的可用性和隐私。当这些操作发生时，会发送相应的合规消息，表明某个 Status 或 User 的状态已发生更改。

**Example Curl Request**

下面的示例请求是在命令行中使用 cURL 发起的：

```bash
curl --compressed -v -uexample@customer.com "https://gnip-stream.x.com/stream/compliance/accounts/:account_name/publishers/twitter/:stream_label.json?partition=1"
```

*注意：* 上述请求只连接到了合规 Firehose 的 `partition=1` —— 你需要连接全部 8 个分区才能消费完整的数据流。

</div>

以下响应可能由 API 在这些请求中返回。大多数错误代码会在响应正文中包含一个字符串形式的详细说明。对于非 200 响应，客户端应尝试重新连接。

| Status | Text | Definition |
| :--- | :--- | :--- |
| 200 | Success | 连接已成功打开，新活动到达时会通过该连接发送。 |
| 401 | Unauthorized | 由于凭证无效导致 HTTP 身份验证失败。请使用你的凭证登录 console.gnip.com，确保在请求中正确使用这些凭证。 |
| 406 | Not Acceptable | 通常在你的客户端未能在请求头中正确声明接受来自流的 gzip 编码时发生，但在其他情况下也可能出现。响应中会包含类似如下的 JSON 消息：“该连接要求启用压缩。要启用压缩，请在请求中发送 `Accept-Encoding: gzip` 请求头，并确保客户端在读取流时能够对其进行解压。” |
| 429 | Rate Limited | 你的 App 已超出连接请求的限制。 |
| 503 | Service Unavailable | Twitter 服务器出现问题。请使用指数退避模式重新连接。如果在 [X API Status Page](https://api.twitterstat.us/) 上未看到关于该问题的公告，请联系支持。 |

<div id="other-recommendations-best-practices">
  #### 其他建议和最佳实践
</div>

* **构建存储数值型 Tweet ID 和 User ID 的数据存储模式（schema）**：User 类型消息要求对该 User 的所有推文采取相应操作。因此，由于所有合规消息仅通过数值型 ID 进行传递，设计数据存储模式时，务必要基于数值型 ID 维护 Tweet 与 User 之间的关联关系。数据使用方需要同时基于 Tweet ID 和 User ID 监控合规事件，并能够相应地更新本地数据存储。

* **构建可处理所有合规状态的模式（schema）**：根据各个应用处理合规活动的方式，可能需要在数据存储中添加其他元数据。例如，数据使用方可以选择在现有数据库中添加元数据，以便在收到 `status_withheld` 消息时，更方便地限制受影响国家/地区的内容展示。

* **处理 Retweet 删除**：Retweet 是一种特殊类型的推文，其中原始消息作为一个对象嵌套在 Retweet 中。在这种情况下，一个 Retweet 中会引用两个 Tweet ID——一个是 Retweet 自身的 ID，另一个是原始消息的 ID（包含在嵌套对象中）。当原始消息被删除时，会针对该原始 ID 发送一条推文删除消息。之后不会针对所有 Retweet 再分别发送删除消息。删除原始 ID 即可视为删除了所有后续的 Retweet。

<div id="overview">
  ## 概览
</div>

`Enterprise`

X 的核心价值之一是维护和尊重用户的声音。这包括在用户删除、修改或编辑他们选择在 X 上分享的内容时，尊重他们的期望和意图。我们认为，这对于作为全球最大公共、实时信息平台之一的长期健康发展至关重要。X 将控制权交到用户手中，使个人能够掌控自己的 X 使用体验。我们相信，获取 X data 的企业用户有责任遵守终端用户的期望和意图。

有关在 X 平台上可能发生的各类合规事件的更多信息，请参考我们的文章：[在 X 上尊重用户意图](/zh/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter)。

任何通过 API 使用 X data 的开发者或公司都有义务尽其合理努力来遵守用户内容的变更。这一义务涵盖用户事件，例如删除、修改以及分享选项的更改（例如内容变为受保护或被屏蔽）。这也包括用户编辑其帖子时的情况。请参考 [Developer Policy](https://developer.x.com/en/developer-terms/policy) 和/或你的 X Data Agreement 中的具体条款，以了解这一义务如何影响你对 X data 的使用。

X 提供以下解决方案，用于提供这些用户合规事件相关的信息，以及特定帖子或用户当前是否公开可见。下面对这些解决方案及其通用集成模式作简要概述：

<div id="get-statuseslookup-and-get-userslookup">
  #### GET statuses/lookup 和 GET users/lookup
</div>

* 格式：REST API。参见：[GET statuses/lookup](https://developer.x.com/en/docs/x-api/v1/tweets/post-and-engage/api-reference/get-statuses-lookup) 和 [GET users/lookup](https://developer.x.com/en/docs/x-api/v1/accounts-and-users/follow-search-get-users/api-reference/get-users-lookup)。

* 这些端点始终返回任意帖子的最新编辑版本。所有描述在编辑功能推出之后创建的帖子的 Post 对象都会包含帖子编辑元数据，即使该帖子从未被编辑过。

* 对于所有帖子，在其创建后超过 30 分钟发起的请求都会反映该帖子的最终状态。

* 按调用方在 API 请求中定义的内容，提供特定帖子或用户的可用性信息。

* 可用于对一组特定帖子 / 用户当前可用性状态进行临时抽查。

* 非常适合需要在某一特定时间点检查某个特定帖子或用户当前状态的客户。

* 这些 API 为需要检查某条内容可用性的客户提供了一种有用的机制，例如在以下场景中：
  1. 展示帖子
  2. 以一对一方式与帖子或用户互动
  3. 通过许可的文件下载方式将 X 内容分发给第三方
  4. 长期存储帖子

<div id="compliance-firehose-enterprise-only">
  #### Compliance Firehose（仅限企业版）
</div>

* 格式：流式 API。参见：[Compliance Firehose](/zh/x-api/enterprise-gnip-2.0/fundamentals/firehouse#api-reference)。
* 提供 X 上[合规活动](/zh/x-api/enterprise-gnip-2.0/fundamentals/firehouse#compliance-data-objects)的实时流。这些活动包括帖子被编辑时的事件。
* 可用于在平台上发生新的合规事件时，维护一组已存储数据的合规状态。
* 非常适合需要长期消费和存储大量 X 数据的客户使用。

<div id="recommendations-best-practices">
  #### **建议与最佳实践**
</div>

* **构建可存储数值型帖子 ID 和用户 ID 的数据存储架构**：针对某个用户的所有帖子，都可能需要对其执行合规操作。因此，由于所有合规消息都仅通过数值型 ID 传递，设计存储架构时，务必要基于数值型 ID 维护帖子与用户之间的关联关系。数据使用方需要同时按帖子 ID 和用户 ID 监控合规事件，并能够对本地数据存储进行相应更新。

* **构建涵盖所有合规状态的架构**：根据在各类应用中处理合规活动的方式，可能需要在数据存储中添加其他元数据。例如，数据使用方可以选择向现有数据库添加元数据，以便在收到 status&#95;withheld 消息时，便于限制在受影响国家/地区显示相关内容。

* **处理转推删除**：转推是一种特殊类型的帖子，其中原始消息作为一个对象嵌套在转推内。在这种情况下，一个转推中会引用两个帖子 ID——一个是该转推本身的 ID，另一个是原始消息的 ID（包含在嵌套对象中）。当原始消息被删除时，会针对原始 ID 发送帖子删除消息。帖子删除事件通常会触发所有相关转推的删除事件。但在某些情况下，可能不会发送全部事件，因此客户端系统应能容忍不完整的转推删除。删除原始 ID 一般应足以删除所有后续的转推。最佳实践是在存储转推时引用原始帖子 ID，并在收到帖子删除事件时删除所有被引用的转推。

<div id="compliance-firehose-api">
  #### **Compliance Firehose API**
</div>

可能的合规事件类型包括帖子（或“status”）事件和用户事件，下面将介绍多种不同的类型。  

请注意：

* 在[此处](https://support.x.com/articles/14016)了解更多有关用户状态的信息，以及在[此处](https://dev.x.com/overview/terms/policy#3.Update_Respect_Users_Control_and_Privacy)了解我们针对已删除帖子制定的开发者政策。
* Compliance Firehose 已更新以提供 `tweet_edit` 事件。 
* 若干用户删除、保护和暂停事件不一定是永久性的，并且可以在不同状态之间反复切换。这些事件包括：user&#95;delete、user&#95;undelete、user&#95;protect、user&#95;unprotect 以及 user&#95;suspend、user&#95;unsuspend。
* 仅当用户未选择执行 user&#95;undelete（撤销删除）其账号时，user&#95;delete 事件发生 30 天后才会触发 status&#95;delete。用户可能会撤销 user&#95;delete，因此在 30 天后不会对其所有帖子执行删除操作。
* user&#95;suspend 是一种操作，一经触发即持续生效，除非发生 user&#95;unsuspend 事件将其解除。这些事件不受任何 30 天时间周期规则的影响。

请参阅 “Recommended Action”（推荐操作）列，以了解如何处理每种事件类型，从而尊重最终用户的隐私和意图。

| Original Message Type | Object | Permanent (Yes/No) | Recommended Action |
| :--- | :--- | :--- | :--- |
| delete | Status | Yes | 删除关联的帖子。 |
| status&#95;withheld | Status | Yes | 在 status&#95;withheld 消息中列出的特定国家/地区隐藏关联帖子。 |
| drop | Status | No  | 将该帖子从公开视图中移除。 |
| undrop | Status | No  | 该状态可以再次显示并视为公开内容。 |
| tweet&#95;edit | Status | Yes | 应用并（在相关情况下）展示新的编辑内容。 |
| user&#95;delete | User | No  | 隐藏或删除关联用户的所有帖子。 |
| user&#95;undelete | User | No  | 关联用户的所有帖子可以再次显示并视为公开内容。 |
| user&#95;protect | User | No  | 隐藏或删除关联用户的所有帖子。 |
| user&#95;unprotect | User | No  | 关联用户的所有帖子可以再次显示并视为公开内容。 |
| user&#95;suspend | User | No  | 隐藏或删除关联用户的所有帖子。 |
| user&#95;unsuspend | User | No  | 关联用户的所有帖子可以再次显示并视为公开内容。 |
| scrub&#95;geo | User | Yes | 删除 X 为该用户在 scrub&#95;geomessage 中指定帖子之前的所有帖子所提供的地理数据。请注意，该用户后续的帖子可能包含可继续使用的地理数据。 |
| user&#95;withheld | User | Yes | 在 user&#95;withheld 消息中列出的特定国家/地区隐藏关联用户的帖子。 |
| delete | Favorite | Yes | 删除关联的点赞/收藏。 |

<div id="integrating-compliance-firehose">
  ### 集成 Compliance Firehose
</div>

Compliance Firehose 是一个实时流式 API，用于传输在 X 平台上发生的合规事件。若要了解合规事件以及它们在 X 上是如何生成的，请参阅我们的文章 [在 X 上尊重用户意图](/zh/x-api/enterprise-gnip-2.0/fundamentals/firehouse#honoring-user-intent-on-twitter)。

需要注意的是，帖子和用户事件是独立传递的，并且每种事件都应独立处理（即，帖子删除并不意味着会发生用户事件，反之亦然）。有些用户事件不一定是永久性的，可以在不同状态之间无限切换。这些包括：user&#95;delete、user&#95;undelete、user&#95;protect、user&#95;unprotect 和 user&#95;suspend、user&#95;unsuspend。

只有在用户未选择对其账号执行 user&#95;undelete 操作的情况下，user&#95;deletes 才会在 30 天后跟随 status&#95;deletes。用户执行的 user&#95;delete 操作有可能被撤销，此时 30 天后将不会对其所有帖子执行删除。

user&#95;suspend 是一种状态操作，一旦为真将保持不变，除非该用户发生 user&#95;unsuspend 事件。该状态不受 30 天时间周期内任何变更的影响。

绝不应直接将合规事件展示给你软件的终端用户，或以其他方式将其纳入你的产品或客户体验中。合规事件仅用于维持合规性并尊重 X 用户的操作。

<div id="integrating-with-the-compliance-firehose">
  #### **集成 Compliance Firehose**
</div>

要将 Compliance Firehose 集成到您的系统中，您需要构建一个能够执行以下操作的集成方案：

1. 为 Compliance Firehose 的每个流式 API 分区建立流式连接
2. 处理高数据量——使用异步处理流程，将流数据摄取与后续处理解耦
3. 在因任何原因断开连接时，自动重新连接到流式分区
4. 按照上述指导，处理与您已存储的帖子和用户数据相关的合规事件

<div id="honoring-user-intent-on-twitter">
  ### 尊重在 Twitter 上的用户意图
</div>

我们认为，尊重 X 用户的隐私和意图对于这一全球最大公共实时信息平台之一的长期良性发展至关重要。X 将隐私控制权交到用户手中，使个人能够掌控自己的 X 使用体验。作为 X 数据的商业使用方，我们共同承担责任，必须尊重终端用户的隐私和行为，从而维护这一基于信任与尊重的环境。

帖子和用户账户可能发生多种变动，会影响它们在平台上的展示方式。影响隐私和意图的操作可以在 Status（帖子）层面和用户层面进行定义。这些操作包括：

<div id="user">
  #### 用户
</div>

| 操作 | 描述 |
| :--- | :--- |
| 保护账号 | X 用户可以随时将其账号设置为受保护或取消保护。受保护账号要求用户对每一位被允许查看其账号帖子的人进行手动批准。   <br />如需了解更多信息，请参阅 [关于公开和受保护的帖子](https://support.x.com/articles/14016-about-public-and-protected-tweets)。 |
| 删除账号 | X 用户可以随时决定删除其账号以及所有关联的状态消息。账号被删除后，X 会保留账号信息 30 天，以防用户决定撤销删除并重新激活其账号。 |
| 清除地理位置 | X 用户可以随时从以往的帖子中删除所有位置信息。这被称为“scrub geo（清除地理位置）”。 |
| 暂停账号 | 如果账号违反了 X 规则，或被怀疑遭到黑客攻击或被入侵，X 保留暂停该账号的权利。账号暂停只能由 X 撤销（解除暂停）。 |
| 限制账号 | X 保留不时在特定国家/地区限制访问某些内容的权利。被限制的账号只能由 X 解除限制。   <br />如需了解更多信息，请参阅 [按国家/地区限制的内容](https://support.x.com/articles/20169222-country-withheld-content)。 |

<div id="status">
  #### 状态
</div>

| 操作 | 描述 |
| :--- | :--- |
| Delete Status | X 用户可以在任何时间点删除一条状态。已删除的状态无法恢复，并会被永久删除。 |
| Withhold Status | X 保留在特定国家/地区根据需要限制访问某些内容的权利。被限制的状态只能由 X 取消限制。   <br />如需更多信息，请参阅 [Country Withheld Content](https://support.x.com/articles/20169222-country-withheld-content)。 |

<div id="keeping-track-of-user-and-status-changes">
  #### 跟踪用户和状态变更
</div>

由于上述任一操作，User 或 Status 的状态可能随时发生变化，这会影响 X 数据的使用方应如何处理所有相关内容的可用性和隐私。当这些操作发生时，系统会发送相应的合规消息，用于指示某个 Status 或 User 的状态已发生更改。

**cURL 请求示例**

以下示例请求演示了如何在命令行中使用 cURL 发起请求：

```bash

```

*注意：* 上述请求仅连接到 Compliance firehose 的 `partition=1`——你需要连接到全部 8 个分区才能消费完整的流数据。

对于这些请求，API 可能返回以下响应。大多数错误代码会在响应正文中包含一个带有更多详细信息的字符串。对于非 200 响应，客户端应尝试重新建立连接。

| Status | Text | Definition |
| :--- | :--- | :--- |

| 406 | Not Acceptable | 通常发生在客户端未能在请求头中正确声明可以从流中接收 gzip 编码时，但也可能在其他情况下出现。响应将包含类似如下的 JSON 消息：“此连接需要压缩。若要启用压缩，请在请求中发送 `Accept-Encoding: gzip` 头，并在客户端读取流时准备好对其进行解压。” |

<div id="other-recommendations-best-practices">
  #### 其他建议与最佳实践
</div>

* **构建可存储数值型推文 ID 和用户 ID 的数据存储架构**：针对用户的合规消息需要对该用户的所有推文采取操作。因此，由于所有合规消息仅通过数值型 ID 传递，设计能够基于数值型 ID 维护推文与用户关系的数据存储架构非常重要。数据使用方需要同时按推文 ID 和用户 ID 监控合规事件，并能够相应地更新本地数据存储。

* **构建涵盖所有合规状态的架构**：根据在各类应用中处理合规活动的方式，可能需要向数据存储中添加其他元数据。例如，数据使用方可能会决定在现有数据库中添加元数据，以便在收到 status&#95;withheld 消息时，更便捷地限制受影响国家/地区的内容展示。

* **处理转推删除**：转推是一种特殊类型的推文，其中原始消息嵌套在转推内部的一个对象中。在这种情况下，转推中会引用两个推文 ID——一个是转推本身的 ID，另一个是原始消息的 ID（包含在嵌套对象中）。当原始消息被删除时，会针对原始 ID 发送一条推文删除消息。不会为所有转推分别发送后续删除消息。删除原始 ID 即可删除所有后续的转推。

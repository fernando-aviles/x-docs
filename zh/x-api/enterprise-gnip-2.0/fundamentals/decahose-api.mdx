<div id="decahose-stream">
  ### Decahose 流
</div>

[Enterprise](https://developer.x.com/en/products/x-api/enterprise)

*这是仅在我们受管访问级别中提供的企业级 API。要使用此 API，你必须先通过我们的企业销售团队开通账户。[了解更多](https://developer.x.com/en/products/x-api/enterprise)*

Decahose 通过流式连接提供 X Firehose 实时数据中 10% 的随机样本。这是通过实时采样算法实现的，该算法随机选择数据，同时仍然可以在 X 通过 Firehose 发送数据时，按预期以低延迟传输数据。

以下是 Decahose 提供的一些功能：

* **展开并增强的 URL：** - 完整展开缩短的 URL，并提供额外的元数据（页面标题和描述）
* **流分区** - 2 个分区，每个分区各包含 Decahose 流量的 50%
* **增强的可靠性** - 通过后端系统的地理多样化部署提升可靠性

注意：此数据为批量交付，不支持额外过滤（例如按关键词过滤）。

  ### 点赞流式数据
</div>

*这是仅在我们的托管访问级别中提供的企业级 API。若要使用此 API，必须先通过我们的企业销售团队开通企业账户。[了解更多](https://developer.x.com/en/products/x-api/enterprise)*

点赞可以帮助洞察是谁给帖子点赞，并提供精确的点赞计数。Gnip 的 Firehose 和 Decahose 可以传递与通过 Gnip 交付的帖子相关的公开点赞。这可以生成与某条帖子相关的实时公开互动和受众指标。
 

**开始使用 Likes**

在准备使用点赞数据时，你需要了解：

* 点赞通过独立的、单独的流进行传递
* 点赞此前通常被称为 “Favorites”。增强型原生格式载荷保留了这一命名
* 流仅包含公开点赞
  * “公开”意味着点赞用户、帖子创建者以及帖子本身在平台上均为公开
* 点赞与转推非常相似，代表一种公开的互动信号
* 载荷元素包括：
  * 原始帖子对象
  * 创建原始帖子的参与者（Actor）对象
  * 执行点赞操作的参与者（Actor）对象
* 只有原始内容可以被点赞
  * 转推不能被点赞。对转推的点赞会应用到原始帖子上
  * 引用推文 *可以* 被点赞
* 点赞活动包含适用的 Gnip Enrichments（如已购买/应用）
* 支持的产品 / 功能
  * 点赞流支持 Backfill（如已购买/应用）
  * 点赞流不支持 Replay
  * 点赞不支持 Search 或 Historical
  * 目前暂无在 PowerTrack 中添加点赞支持的计划

**Decahose**

* 对于 Decahose 中提供的 10% 抽样帖子，流包含 100% 适用的公开点赞
* **分区（Partitions）：** 2
* **URL 结构**
  * https://gnip-stream.x.com/stream/sample10-likes/accounts/&lt;accountName&gt;/publishers/twitter/&lt;streamLabel&gt;.json?partition=1

<div id="recovery-and-redundency">
  ### 恢复与冗余
</div>

**简介** 

在高容量的实时帖子流式传输场景下，有一系列最佳实践可以同时提升数据可靠性以及数据的完整性和保真度。在消费实时数据时，尽可能延长连接持续时间是一个基本目标。当出现断线时，自动检测并重新连接非常重要。重新连接后，需要评估是否存在需要回填数据的时间段。负责管理这些细节并消费实时帖子的组件，只是一个同时涉及网络、数据存储、服务器和存储等问题的系统中的一部分。鉴于这些系统的复杂性，另一个最佳实践是使用不同的流式环境，至少为开发/测试和生产分别提供独立的流。

Decahose 提供了一组有助于实现这些目标的功能。

1. 为了支持多个环境，我们可以为您的账户部署 [Additional Streams](#AdditionalStreams)。这些流彼此独立，并带有不同的 `stream_label` 以便区分。
2. 为了帮助维持连接，每个 Decahose 流都支持 [冗余连接](/zh/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#additional-streams)。最常见的架构是一个流有两个连接，在客户端侧有两个相互独立的消费者——理想情况下位于不同的网络上。通过这种设计，可以在客户端侧的网络、服务器和数据存储路径上实现冗余。请注意，每个连接都会提供一份完整副本的数据，客户端必须能够容忍并处理重复数据。
3. 每 10 秒会发送一次“**heartbeat**”；然而，在 Decahose 流中，数据量足够大，以至于即便是一个很短的时间段（例如几秒钟）没有帖子，都可能表示连接问题。因此，既可以通过“数据静默”，也可以通过缺少 heartbeat 来检测断线。

由于断线在所难免，Decahose 流提供了专门的 [恢复](/zh/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#overview) 和 [回填](/zh/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#backfill) 功能，用于帮助恢复因断线和其他运维问题而错过的数据。

<div id="additional-streams">
  #### 额外流
</div>

增加额外的 Decahose 流是将可靠性构建到解决方案中的另一种方式。任何额外的流都是完全独立的，并拥有自己唯一的端点。每个流都会分配一个专属的 stream&#95;label，该标签会与您的账户名称一起，作为该流 URL 的一部分。参见下面的示例：

https://gnip-stream.x.com/stream/sample10/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json

最常见的约定是：为生产系统保留一个专用的实时流，并再为开发和测试提供一个额外的流。拥有一个测试/开发流可以让 Decahose 客户使用该流来测试客户端消费者的更新。虽然可以为一个流分配任意（唯一的）label，但一种常见做法是：生产流使用 “prod”，而额外的开发流使用 “dev” 或 “sandbox”。

流的数量及其唯一 label 由您的账户代表进行配置。

**冗余连接**

冗余连接是指允许您对数据流建立多个同时连接。这通过允许您使用两个独立的消费者连接到同一个流，并通过两个连接接收相同数据，从而提供冗余能力。因此，应对各种情况时（例如某个流断开连接，或应用的主服务器发生故障），您的应用都具备热备切换能力。

对于任意给定的流，允许的连接数量可以由您的账户代表进行配置。要使用冗余连接，只需连接与主连接相同的 URL 即可。您的流数据将通过这两个连接发送，且这两个流连接都会在流仪表板上显示。

请注意，就计费而言，我们会对您通过多个连接收到的 activity 计数进行去重，因此每个唯一的 activity 您只会被计费一次。鉴于 Decahose 拥有两个分区，下面是一个关于连接计数如何工作的示例：

Connect to decahose partition=1\
Connect to decahose partition=1\
Connect to decahose partition=2

上述情况总共产生三个连接——两个连接到 partition=1，一个连接到 partition=2。通常情况下，您会希望每个分区拥有相同数量的连接，因此该示例突出了这样一种情形：到 partition=2 的冗余连接已断开，您需要进一步进行排查。

**恢复**

<div id="overview">
  #### 概览
</div>

Recovery 是一个数据恢复工具（不应作为主要数据采集手段），它提供对 X 最近 5 天历史数据滚动窗口的流式访问。它应在你的消费端应用错过实时流中的数据时使用，无论是因为短时间断开连接，还是出于任何其他导致你在一段时间内无法摄取实时数据的情况，用于补回这些缺失数据。

<div id="using-recovery">
  #### 使用 Recovery
</div>

借助 Recovery 流，你的应用可以以与对实时流请求相同的方式向其发起请求。不过，你的应用必须在 URL 中指定参数，以表明你所请求的时间窗口。换句话说，一个 Recovery 请求会向 API 请求“从时间 A 到时间 B 的帖子”。这些帖子随后会通过你的流式连接交付，交付方式仿照实时流，但速率会略慢于实时。示例如下：

&quot;https://stream-data-api.x.com/stream/powertrack/accounts/someAccountName/publishers/twitter/powertrack.json?startTime=2023-07-05T17:09:12.070Z&quot;

帖子会从指定时间段内最早（最旧）的那一分钟开始交付，按时间顺序持续传输，直到最后一分钟的内容被交付。到那时，连接中会收到一条 Recovery Request Completed 消息，然后服务器会关闭该连接。如果你的请求起始时间处于某个几乎没有或完全没有匹配结果的时段，那么在传输第一条结果之前，很可能会有一段时间没有数据被交付——当 Recovery 在当时正在处理的归档部分中遇到匹配项时，才会开始交付数据。当没有可交付的结果时，流会继续通过连接发送回车符（carriage-return），即“心跳（heartbeats）”，以防止你的连接超时。

Recovery 旨在作为一个工具，用于轻松恢复因短暂断连而错过的数据，而不是用于恢复很长时间段的数据，比如整整一天。如果需要在较长时间范围内恢复数据，建议将较长请求拆分为较短的时间窗口（例如两小时），以降低由于网络波动或其他原因在请求过程中断连的可能性，并帮助你更好地了解长时间请求的执行进度。

<div id="data-availability">
  #### 数据可用性
</div>

如果你无法在 5 分钟的回填窗口内重新建立连接，可以使用 Recovery 功能恢复过去 24 小时内遗漏的数据。

流式恢复功能可以将回填窗口扩展到 24 小时。Recovery 使你能够“补回”遗漏数据对应的这段时间区间。当你在连接请求中使用 `start_time` 和 `end_time` 请求参数时，就会启动一个恢复流。一旦建立连接，Recovery 会重新推送指定时间段内的数据，然后断开连接。  

你最多可以同时发起 2 个恢复请求，即“两个恢复作业”。Recovery 在技术上与回填的工作方式相同，只是需要额外定义开始时间和结束时间。每次恢复只针对一个连续的时间范围。

<div id="backfill">
  #### 回填（Backfill）
</div>

要请求回填，你需要在连接请求中添加一个 `backfillMinutes=N` 参数，其中 N 是在建立连接时需要回填的分钟数（1–5 的整数）。例如，如果你断开了 90 秒，你应该在连接请求中添加 `backfillMinutes=2`。由于该请求会提供 2 分钟的回填数据，其中包括你断开连接前的那 30 秒，因此你的 *消费端应用必须能够容忍重复数据*。

一个 Decahose 连接请求 URL 示例，请求对分区 1 进行 5 分钟回填，如下所示：

https://gnip-stream.x.com/stream/sample10/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json?partition=1&amp;backfillMinutes=5

**注意：**

* 你可以选择在每次连接时都使用 `backfillMinutes=5`，然后在你的端处理可能提供的任何重复数据。

* 如果你断开连接超过 5 分钟，可以使用 Recovery 来恢复数据。

**从断连中恢复**

重新启动并从断连中恢复涉及几个步骤：

* 确定断连时间长度。
  * 5 分钟或更少？
    * 如果你的流启用了 Backfill，为连接请求准备合适的 `backfillMinutes` 参数。
  * 超过 5 分钟？
    * 如果你有 Recovery 流，为断连时间段发起 Recovery 请求（理想情况下使用你当前的实时规则集，如有需要可通过 Rules API 更新）。
* 发起新的连接请求。

当你遇到断连或停机时，可以采用以下策略来缓解并在这种情况下实现恢复：

1. **实现回填（Backfill）**\
   Backfill 允许你从断开流连接之前的某个时间点重新连接，可覆盖最长 5 分钟的断连。通过在连接请求中包含一个参数来实现。

2. **从其他位置消费冗余流**\
   如果可以将冗余流实时导入同一个生产环境并对数据去重，除非正常流和冗余流同时出现停机或断连，否则你就不需要进行恢复。如果冗余流不能实时导入生产环境，可以将其写入一个单独的“应急”数据存储。然后，当主流连接发生断连或停机时，你的系统就可以利用这些数据来填补主数据库在该时间段内缺失的数据。

3. **实现 Recovery**\
   当断连或停机同时影响到主流和冗余流时，使用 Decahose Recovery 来恢复遗漏的数据。该 API 提供覆盖过去 5 天存档的滚动时间窗口，最佳做法是一次请求不超过该窗口中的 1 小时时间段并将其流式导入。这是在与实时流并行的通道中完成的。请注意，我们无法恢复 Recovery 提供的 5 天窗口之外的 Decahose 数据，因此你需要使用冗余流，以确保在你端发生重大停机时，你这边仍然有完整的数据副本。

当你检测到存储数据量异常时——\
在没有发生断连或停机的情况下，检测缺失数据的一些潜在方法包括：

1. 统计入站帖子（Posts）\
   你的系统应在采集 App 的最开始统计你接收到的原始帖子数量，并提供一种方式将这些数字与最终数据存储中到达的帖子数量进行对比。任何差异都可以被监控，并用来提醒你的团队注意导致数据在接收后被丢弃的问题。

2. 分析异常的存储量\
   你也可以分析最终数据库中存储数据的体量，以发现异常下降。这同样可能表明存在问题，尽管在某些情况下，数据量下降是正常的（例如，当 X 平台不可用、用户在一段时间内无法创建帖子时）。

对 Volume Stream API 的所有请求都必须使用 HTTP 基本身份验证（HTTP Basic Authentication），其凭据由用于登录 console.gnip.com 帐户的有效电子邮件地址和密码组合组成。凭据必须作为每个请求的 Authorization 头部传递。因此，请确认你的客户端为所有 API 请求添加了 `"Authentication: Basic"` HTTP 头部（通过 HTTPS 发送的编码凭据）。

#### GET {stream-type}:stream

建立与 Firehose 流的持久连接，实时数据将通过此连接传送。

<div id="request-specifications">
  #### 请求规范
</div>

|     |     |
| :--- | :--- |
| **请求方法** | HTTP GET |
| **连接类型** | Keep-Alive  <br />  <br />这应当在请求的 header 中进行指定。 |
| **URL** | 可在你的仪表板中该流的 API Help 页面找到，使用如下结构：  <br />  <br />Decahose:<br /><br />[https://gnip-stream.x.com/stream/sample10/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json?partition=1](https://gnip-stream.x.com/stream/sample10/accounts/:account_name/publishers/twitter/:stream_label.json?partition=1) |
| **分区（必填）** | `partition=\{#}` - 现在必须使用分区才能消费完整的数据流。你需要在连接到流时指定 partition 参数。下面是每个流的分区数量：<br /><br />* Decahose：2 个分区 |
| **压缩** | Gzip。要使用 Gzip 压缩连接到流，只需在连接请求中发送 Accept-Encoding header。该 header 如下所示：  <br />  <br />Accept-Encoding: gzip |
| **字符编码** | UTF-8 |
| **响应格式** | JSON。你的请求 header 应指定响应使用 JSON 格式。 |
| **速率限制** | 每 60 秒 10 个请求。 |
| **Backfill 参数** | 如果你购买了启用 Backfill 的流，你需要在 GET 请求中添加 &quot;backfillMinutes&quot; 参数以启用它。 |
| **读取超时** | 在你的 Client 上设置读取超时时间，并确保其值大于 30 秒。 |
| **对推文编辑的支持** | 所有推文对象都会包含描述该推文编辑历史的推文编辑元数据。更多详情请参阅[&quot;编辑推文&quot;基础知识页面](/zh/x-api/enterprise-gnip-2.0/fundamentals/edit-tweets)。 |

<div id="responses">
  #### 响应
</div>

对于这些请求，API 可能返回以下响应。大多数错误代码会在响应体中附带一个字符串形式的详细说明。对于非 200 响应，客户端应尝试重新连接。

| Status | Text | Description |
| :--- | :--- | :--- |
| 200 | Success | 连接已成功打开，新的活动会在到达时通过该连接发送。 |
| 401 | Unauthorized | 由于凭证无效导致 HTTP 身份验证失败。请使用你的凭证登录 console.gnip.com，以确保你在请求中正确使用了这些凭证。 |
| 406 | Not Acceptable | 通常发生在客户端未能正确包含用于接受来自流的 gzip 编码的请求头时，但在其他情况下也可能发生。  <br />  <br />会包含一条类似于“此连接需要压缩。要启用压缩，请在请求中发送 ‘Accept-Encoding: gzip’ 头，并在客户端读取流时准备好对其进行解压缩。”的 JSON 消息。 |
| 429 | Rate Limited | 你的 App 已超出连接请求的限制。 |
| 503 | Service Unavailable | Twitter 服务器故障。请使用指数退避策略重新连接。如果在 [X API Status Page](https://api.twitterstat.us/) 上未发布有关此问题的公告，并且在 10 分钟后仍无法连接，请联系支持或紧急支持。 |

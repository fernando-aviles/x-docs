<div id="decahose-stream">
  ### Decahose 流
</div>

[Enterprise](https://developer.x.com/en/products/x-api/enterprise)

*这是仅在我们的托管访问层级中提供的 Enterprise API。要使用此 API，您必须先通过我们的 Enterprise 销售团队开通账户。[了解更多](https://developer.x.com/en/products/x-api/enterprise)*

Decahose 通过流式连接提供来自 X 实时 Firehose 的 10% 随机样本。其实现方式是使用实时采样算法随机选择数据，同时在 X 通过 Firehose 发送数据时，仍然能够保持预期的低延迟数据传递。

以下是 Decahose 提供的一些功能：

* **扩展和增强的 URL：** - 完整展开缩短的 URL，并提供额外的元数据（页面标题和描述）
* **流分区** - 2 个分区，每个分区包含 Decahose 流量的 50%
* **更高的可靠性** - 后端系统具备地理多样性部署

注意：这些数据以批量形式交付，不支持额外过滤（例如按关键字过滤）。

</div>

*这是仅在我们的托管访问级别下提供的企业级 API。要使用此 API，必须先与我们的企业销售团队开通账户。[了解更多](https://developer.x.com/en/products/x-api/enterprise)*

点赞可帮助你了解谁给帖子点赞，并提供精确的点赞计数。Gnip 的 Firehose 和 Decahose 可以传输与通过 Gnip 传输的帖子相关的公开点赞。这能够提供与某条帖子相关的实时公开互动和受众指标。
 

**开始使用点赞功能**

在准备接收点赞 data 时，你需要了解以下内容：

* 点赞通过独立的、单独的流传输
* 点赞在历史上被称为 “Favorites”。富化的原生格式载荷保留了这一命名方式
* 流仅包含公开点赞
  * “公开” 意味着点赞用户、帖子创建者以及帖子本身在平台上都是公开的
* 点赞与转发非常相似，代表一种公开的互动信号
* 载荷元素包括：
  * 原始 Post 对象
  * 创建原始帖子的 Actor 对象
  * 执行点赞操作的 Actor 对象
* 只有原始内容可以被点赞
  * 转发不能被点赞。对转发的点赞会应用到原始帖子上
  * 引用推文&#95;可以&#95;被点赞
* 点赞活动包含适用的 Gnip Enrichments（在购买/应用时）
* 支持的产品 / 功能
  * 点赞流支持 Backfill（在购买/应用时）
  * 点赞流不支持 Replay
  * 点赞不支持 Search 或 Historical
  * 目前没有将点赞支持添加到 PowerTrack 的计划

* 对于在 Decahose 中传输的 10% 抽样帖子，该流会包含 100% 的适用公开点赞
* **分区数：**2
* **URL 结构**

<div id="recovery-and-redundency">
  ### 恢复与冗余
</div>

**简介** 

在以流方式处理大规模实时帖子时，有一套有助于提升数据可靠性以及数据完整性和保真度的最佳实践。在使用实时数据时，最大化连接在线时长是一个基本目标。当发生断连时，重要的是能够自动检测并重新连接。重新连接后，还需要评估是否存在需要回补数据的时间段。负责管理这些细节并消费实时帖子的组件，只是一个同时涉及网络、数据存储系统、服务器和存储等问题的整体系统的一部分。鉴于这些系统的复杂性，另一项最佳实践是设置不同的流式处理环境，至少要为开发/测试和生产分别提供独立的流。

Decahose 提供了一组有助于实现这些目标的功能。

1. 为支持多个环境，我们可以为你的账号部署[附加流](#AdditionalStreams)。这些流彼此独立，并具有不同的 `stream_label` 以帮助区分它们。
2. 为帮助维持连接，每个 Decahose 流都支持[冗余连接](/zh/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#additional-streams)。最常见的架构是一个流有两个连接，在客户端有两个相互独立的消费者——理想情况下位于不同的网络上。通过这种设计，可以在客户端网络、服务器和数据存储路径上实现冗余。请注意，每个连接上都会提供一份完整拷贝的数据，客户端必须能够容忍并管理重复数据。
3. 每 10 秒会提供一次“**心跳**”；然而，对于 Decahose 流而言，数据量足够大，以至于即便是一个较短的时间段（例如几秒钟）没有帖子出现，也可能表明连接存在问题。因此，“数据静默”和缺少心跳信号都可用于检测断连。

由于断连在所难免，Decahose 流提供了专门的[恢复](/zh/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#overview)和[回补](/zh/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#backfill)功能，用于帮助恢复因断连和其他运维问题而错过的数据。

<div id="additional-streams">
  #### 其他流
</div>

配置额外的 Decahose 流是为你的解决方案构建可靠性的另一种方式。任何额外的流都是完全独立的，并拥有其唯一的 endpoint。每个流都会被分配其自己的 stream&#95;label，该标签连同你的账户名称一起构成该流的 URL。示例如下：

https://gnip-stream.x.com/stream/sample10/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json

最常见的约定是：为生产系统专门配置一个实时流，并额外配置一个用于开发和测试的流。拥有测试/开发流可以让 Decahose 客户使用该流来测试客户端消费端的更新。虽然可以为一个流分配任何（唯一的）标签，但一种常见约定是：生产流使用 “prod”，额外的开发流使用 “dev” 或 “sandbox”。

流的数量及其唯一标签可由你的客户代表进行配置。

**冗余连接**

冗余连接允许你针对同一个数据流建立多个同时存在的连接。这样可以通过让你使用两个独立的消费者连接到同一个流，并通过两条连接接收相同的数据来提供冗余。因此，你的应用在多种情况下都具备热故障切换能力，例如某个流断开连接，或应用的主服务器发生故障。

针对任何给定流允许的连接数量可由你的客户代表进行配置。要使用冗余流，只需连接到与你的主连接相同的 URL。你的流数据将通过这两条连接发送，并且这两条流连接都会在流仪表板中显示。

请注意，就计费目的而言，我们会对你通过多条连接接收到的活动计数进行去重，这样你只会为每个唯一活动支付一次费用。鉴于 Decahose 有两个分区，下面是一个关于连接计数如何工作的示例：

Connect to decahose partition=1\
Connect to decahose partition=1\
Connect to decahose partition=2

上述情况总共产生三个连接——两个连接到 partition=1，一个连接到 partition=2。通常，你会希望每个分区拥有相同数量的连接，因此该示例表明连接到 partition=2 的冗余连接已中断，你需要进一步排查。

**恢复**

<div id="overview">
  #### 概览
</div>

Recovery 是一款数据恢复工具（不应用于主要数据采集），它通过滚动的 5 天时间窗口，为最近的 X 历史数据提供流式访问能力。 当你的消费端应用在实时流中遗漏了数据时——无论是由于短时间断开连接，还是出于任何其他原因在一段时间内未能接收实时数据——都应使用它来恢复这些数据。

<div id="using-recovery">
  #### 使用 Recovery
</div>

借助 Recovery 流，你的应用可以向其发起请求，其行为方式与向实时流发起请求相同。不过，你的应用必须在 URL 中指定参数，用来表明你请求的时间窗口。换句话说，一个 Recovery 请求会向 API 请求“从时间 A 到时间 B 的帖子”。这些帖子随后会通过你的流式连接传输，方式与实时流类似，但速率会略慢于实时。示例如下：

&quot;https://stream-data-api.x.com/stream/powertrack/accounts/someAccountName/publishers/twitter/powertrack.json?startTime=2023-07-05T17:09:12.070Z&quot;

帖子会从所指定时间段内的第 1 分钟（最早的那一分钟）开始传输，按时间顺序持续传输，直到最后一分钟发送完毕。此时，系统会通过连接发送一条 Recovery Request Completed 消息，然后服务器会关闭该连接。如果你的请求起始时间落在匹配结果很少或没有匹配结果的时段，在传递第一个结果之前很可能会有一段空档——只有当 Recovery 在当前处理的归档片段中遇到匹配结果时，才会开始传递数据。当没有可传递的结果时，流会持续通过连接发送回车符（carriage-return），即“心跳（heartbeats）”，以防止你的连接超时。

Recovery 旨在作为一种工具，用于轻松恢复因短暂断连而遗漏的数据，而不是用于覆盖整天这类的超长时间段。如果需要在较长时间范围内恢复数据，我们建议将较长请求拆分为更短的时间窗口（例如两小时），以降低由于网络波动或其他原因导致在请求中途断连的可能性，并为长时间请求的进度提供更好的可见性。

<div id="data-availability">
  #### 数据可用性
</div>

如果你无法在 5 分钟的回填窗口内重新连接，可以使用 Recovery 功能来恢复最近 24 小时内错过的 数据。

流式 Recovery 功能允许你将回填窗口扩展到 24 小时。Recovery 使你能够“恢复”错过的这段数据时间区间。当你在连接请求中使用 `start_time` 和 `end_time` 请求参数时，就会启动一个恢复流。一旦连接建立，Recovery 会重新推送该时间段内的数据，然后断开连接。  

你可以同时向 Recovery 发起 2 个并发请求，即“两个恢复作业”。Recovery 在技术上与回填的工作方式相同，只是额外定义了开始时间和结束时间。每个恢复周期仅对应一个单独的时间范围。

<div id="backfill">
  #### 回填（Backfill）
</div>

要请求回填，你需要在连接请求中添加一个 `backfillMinutes=N` 参数，其中 N 是在建立连接时要回填的分钟数（1–5 的整数）。例如，如果你断开了 90 秒，则应在连接请求中添加 `backfillMinutes=2`。由于该请求会提供 2 分钟的回填，包括你断开前的 30 秒时间段，*你的消费者应用必须能够容忍重复 data*。

一个 Decahose 连接请求 URL 示例，请求对分区 1 进行 5 分钟回填，如下所示：

https://gnip-stream.x.com/stream/sample10/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json?partition=1&amp;backfillMinutes=5

**注意：**

* 你可以选择在每次连接时始终使用 `backfillMinutes=5`，然后在你的系统中处理提供的任何重复 data。

* 如果你断开连接超过五分钟，可以使用 Recovery 来恢复 data。

**从断连中恢复**

重新启动并从断连中恢复涉及几个步骤：

* 确定断连时间长度。
  * 是否为 5 分钟或更少？
    * 如果你的流启用了 Backfill，准备一个包含合适 `backfillMinutes` 参数的连接请求。
  * 是否超过 5 分钟？
    * 如果你有 Recovery 流，为断连时间段发起 Recovery 请求（理想情况下使用你当前的实时规则集，如有必要可使用 Rules API）。

* 请求一个新的连接。

当你遇到断连或停机时，可以采用以下策略来减轻影响并进行恢复：

1. **实施回填（Backfill）**\
   Backfill 允许你从断开流连接之前的某个时间点重新连接，可覆盖最长 5 分钟的断连。它是通过在连接请求中包含一个参数来实现的。

2. **从其他位置消费冗余流**\
   如果冗余流可以被流式传入同一个实时环境，并对 data 进行去重，那么除非正常流和冗余流同时发生停机或断连，否则你将不需要进行恢复。如果冗余流无法实时流入生产环境，则可以将其写入单独的“应急” data 存储。然后，当主流连接发生断连或停机时，你的系统将手头拥有用于填补主数据库中缺失时间段的 data。

3. **实施 Recovery**\
   当断连或停机同时影响主流和冗余流时，使用 Decahose Recovery 来恢复任何遗漏的 data。该 API 提供一个覆盖 5 天归档内容的滚动窗口，最佳用法是每次请求不超过一小时的窗口，并将其流式导入。这与实时流并行完成。请注意，我们没有方案从 Recovery 提供的 5 天窗口之外恢复 Decahose data，因此你务必要利用冗余流，确保在你这边发生重大停机时，你这边拥有完整的 data 副本。

当你检测到异常存储 data 量时——\
在没有发生断连或停机的情况下，你可以通过以下潜在方式检测缺失 data……

1. 统计入站帖子数\
   你的系统应在摄取应用的最开始阶段统计你接收到的原始帖子数量，然后提供一种方式，将这些数字与最终 data 存储中到达的帖子数量进行比较。可以对任何差异进行监控，并提醒你的团队注意导致 data 在接收后被丢弃的问题。

2. 分析异常存储量\
   你可能还希望分析最终数据库中存储的 data 量，以查找异常下降情况。这同样可以指示问题，尽管在某些情况下，数据量的下降是正常的（例如，当 X 平台不可用、用户在一段时间内无法创建帖子时）。

对 Volume Stream API 的所有请求都必须使用 HTTP 基本身份验证（HTTP Basic Authentication），该身份验证由用于登录你在 console.gnip.com 上账户的有效电子邮件地址和密码组合构成。凭证必须作为每个请求的 Authorization 头传递。因此，请确认你的客户端在所有 API 请求中都添加了 `"Authentication: Basic"` HTTP 头（携带经过编码的凭证，并通过 HTTPS 发送）。

#### GET {stream-type}:stream

建立到 Firehose 流的持久连接，通过该连接传输实时数据。

<div id="request-specifications">
  #### 请求规范
</div>

|     |     |
| :--- | :--- |
| **Request Method** | HTTP GET |
| **Connection Type** | Keep-Alive  <br />  <br />应在请求头中指定此项。 |
| **URL** | 可在仪表板中该流的 API 帮助页面上找到，使用以下结构：  <br />  <br />Decahose:<br /><br />[https://gnip-stream.x.com/stream/sample10/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json?partition=1](https://gnip-stream.x.com/stream/sample10/accounts/:account_name/publishers/twitter/:stream_label.json?partition=1) |
| **Partition (required)** | `partition=\{#}` - 现在必须使用分区，才能消费完整的流数据。你需要在连接到流时指定 partition 参数。以下是每个流的分区数量：<br /><br />* Decahose：2 个分区 |
| **Compression** | Gzip。要使用 Gzip 压缩连接到流，只需在连接请求中发送 Accept-Encoding 请求头。该请求头应如下所示：  <br />  <br />Accept-Encoding: gzip |
| **Character Encoding** | UTF-8 |
| **Response Format** | JSON。你的请求头中应指定响应格式为 JSON。 |
| **Rate Limit** | 每 60 秒 10 个请求。 |
| **Backfill Parameter** | 如果你购买了启用回填（Backfill）的流，则需要在 GET 请求中添加 &quot;backfillMinutes&quot; 参数以启用它。 |
| **Read Timeout** | 在客户端中设置读取超时时间，并确保其值大于 30 秒。 |
| **Support for Tweet edits** | 所有推文对象都会包含推文编辑元数据，用于描述该推文的编辑历史。更多详情请参阅 [&quot;Edit Tweets&quot; 基础知识页面](/zh/x-api/enterprise-gnip-2.0/fundamentals/edit-tweets)。 |

<div id="responses">
  #### 响应
</div>

API 针对这些请求可能返回以下响应。大多数错误代码会在响应体中包含一个带有更多详细信息的字符串。对于非 200 响应，客户端应尝试重新连接。

| Status | Text | Description |
| :--- | :--- | :--- |
| 200 | Success | 连接已成功打开，新的活动将在到达时通过连接发送。 |
| 401 | Unauthorized | 由于凭证无效导致 HTTP 身份验证失败。请使用你的凭证登录 console.gnip.com，以确保在请求中正确使用这些凭证。 |
| 406 | Not Acceptable | 通常发生在你的客户端未能正确包含用于接收来自流的 gzip 编码所需的请求头时，但在其他情况下也可能发生。  <br />  <br />将包含类似于 &quot;This connection requires compression. To enable compression, send an &#39;Accept-Encoding: gzip&#39; header in your request and be ready to uncompress the stream as it is read on the client end.&quot; 的 JSON 消息。 |
| 429 | Rate Limited | 你的应用已超出连接请求的上限。 |
| 503 | Service Unavailable | Twitter 服务器出现问题。请使用指数退避模式重新连接。如果在 [X API Status Page](https://api.twitterstat.us/) 上没有关于此问题的公告，并且在 10 分钟后仍无法连接，请联系支持或紧急支持渠道。 |

重放 API 是对实时 Volume 流的重要补充。重放是一种数据恢复工具，可通过流式方式访问 X 近期历史数据的滚动时间窗口。

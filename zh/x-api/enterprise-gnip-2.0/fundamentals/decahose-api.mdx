  ### Decahose 流
</div>

[Enterprise](https://developer.x.com/en/products/x-api/enterprise)

*这是仅在我们的托管访问级别中提供的企业级 API。要使用此 API，您必须先与我们的企业销售团队开通企业账户。[了解更多](https://developer.x.com/en/products/x-api/enterprise)*

Decahose 通过流式连接提供 X 实时 Firehose 的 10% 随机采样。这是通过实时抽样算法实现的，该算法随机选择数据，同时仍然能够在 X 将数据发送到 Firehose 时，以预期的低延迟交付这些数据。

以下是 Decahose 提供的一些功能：

* **扩展和增强的 URL：** - 完整展开缩短的 URL，并提供附加元数据（页面标题和描述）
* **流分区** - 2 个分区，每个分区包含 Decahose 流量的 50%
* **增强的可靠性** - 后端系统具备地理多样性

注意：这些数据以批量方式交付，不支持额外的过滤（例如按关键字过滤）。

  ### 流式传输点赞
</div>

*这是仅在我们的托管访问级别中提供的企业级 API。要使用此 API，您必须先通过我们的企业销售团队开通账户。[了解更多](https://developer.x.com/en/products/x-api/enterprise)*

点赞可帮助了解谁点赞了帖子，并提供准确的点赞计数。Gnip 的 Firehose 和 Decahose 可以传递与通过 Gnip 传递的帖子相关的公开点赞。这为与某条帖子相关的实时公开互动及受众指标提供了数据。
 

**开始使用点赞**

在准备使用点赞相关数据时，您需要了解：

* 点赞通过独立的、单独的流进行传递
* 点赞在历史上被称为 “Favorites（收藏）”。增强型原生格式的有效负载保留了这一命名
* 流仅包含公开的点赞
  * “公开”意味着点赞用户、帖子创建者以及帖子本身在平台上都是公开的
* 点赞与转发非常相似，代表了一种公开的互动信号
* 有效负载元素包括：
  * 原始帖子对象
  * 创建原始帖子的 Actor 对象
  * 执行点赞操作的 Actor 对象
* 只有原始内容可以被点赞
  * 转发不能被点赞。对转发的点赞会作用到原始帖子上
  * 引用推文 *可以* 被点赞
* 点赞活动包含适用的 Gnip Enrichments（如已购买/应用）
* 支持的产品 / 功能
  * 点赞流支持 Backfill（如已购买/应用）
  * 点赞流不支持 Replay
  * 点赞不支持 Search 或 Historical
  * 目前没有将点赞支持添加到 PowerTrack 的计划

**Decahose**

* 对于在 Decahose 中传递的 10% 抽样帖子，流将包含 100% 的适用公开点赞
* **分区：**2
* **URL 结构**
  * https://gnip-stream.x.com/stream/sample10-likes/accounts/&lt;accountName&gt;/publishers/twitter/&lt;streamLabel&gt;.json?partition=1

<div id="recovery-and-redundency">
  ### 恢复和冗余
</div>

**简介** 

在高吞吐量的实时帖子流式传输场景中，有一系列最佳实践有助于同时提升数据的可靠性和数据的完整保真性。在消费实时数据时，最大化连接时长是一个基本目标。当发生断连时，自动检测并重新连接非常重要。重新连接后，还需要评估是否存在需要回补数据的时间段。负责管理这些细节并消费实时帖子的组件，只是整个系统中涉及网络、数据存储、服务器和存储等方面的一部分。鉴于这些系统的复杂性，另一项最佳实践是使用不同的流式环境，至少要为开发/测试和生产环境分别使用独立的流。

Decahose 提供了一组功能，用于支持这些工作。

1. 为了支持多环境，我们可以为你的账户部署 [附加流](#AdditionalStreams)。这些流彼此独立，并使用不同的 `stream_label` 来帮助区分。
2. 为了帮助维持连接，每个 Decahose 流都支持 [冗余连接](/zh/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#additional-streams)。最常见的架构是一个流有两个连接，而在客户端有两个相互独立的消费端——理想情况下位于不同的网络上。通过这种设计，可以在客户端侧的网络、服务器和数据存储路径之间实现冗余。请注意，每个连接都会提供一份完整拷贝的数据，客户端必须能够容忍并处理重复数据。
3. 每 10 秒会提供一次“**心跳**”；然而，在 Decahose 流中，数据量足够大，以至于即使是一个很短的时间段（例如几秒钟）没有帖子也可能表明存在连接问题。因此，“数据静默”和缺少心跳都可以用于检测断连。

由于断连在所难免，Decahose 流提供了专门的 [恢复](/zh/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#overview) 和 [回补](/zh/x-api/enterprise-gnip-2.0/fundamentals/decahose-api#backfill) 功能，用于帮助恢复因断连和其他运维问题而遗漏的数据。

<div id="additional-streams">
  #### 额外流（Additional Streams）
</div>

拥有额外的 Decahose 流是提升你的解决方案可靠性的另一种方式。任何额外流都是完全独立的，并拥有各自唯一的 endpoint。每个流都会分配自己的 `stream_label`，该标签会与你的账户名称一起构成该流的 URL。请参见下面的示例：

https://gnip-stream.x.com/stream/sample10/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json

最常见的做法是：为生产系统专门配置一个实时流，并另外提供一个用于开发和测试的流。拥有一个测试/开发流可以让 Decahose 客户在更新客户端消费程序时，有一个可用于测试的流。虽然可以为流分配任意（唯一的）标签，但常见约定是对生产流使用 `prod`，对用于开发的额外流使用 `dev` 或 `sandbox`。

流的数量及其唯一标签可以由你的客户经理进行配置。

**冗余连接**

冗余连接可以让你为同一个数据流建立多个并发连接。这样，你可以通过两个独立的消费者连接到同一个流，并通过两个连接接收相同的数据，从而提供冗余。因此，在各种情况下（例如某个流断开，或应用的主服务器发生故障），你的应用都可以实现热故障转移（hot failover）。

对任一给定流允许的连接数量可以由你的客户经理进行配置。要使用冗余连接，只需连接到与你主连接相同的 URL。你的流数据会通过两个连接发送，并且这两个流连接都会显示在流仪表板上。

请注意，在计费方面，我们会对你通过多个连接接收到的活动数据进行去重，因此你只会针对每个唯一的活动计费一次。鉴于 Decahose 有两个分区，下面是一个连接计数工作方式的示例：

Connect to decahose partition=1\
Connect to decahose partition=1\
Connect to decahose partition=2

上述情况总共产生三个连接——两个连接到 partition=1，一个连接到 partition=2。通常，你会希望每个分区具有相同数量的连接，因此这个示例突出了一个场景：连接到 partition=2 的冗余连接已掉线，而你需要进一步调查这一情况。

**恢复（Recovery）**

<div id="overview">
  #### 概览
</div>

Recovery 是一款数据恢复工具（不用于主数据采集），提供对最近 5 天 X 历史数据滚动窗口的流式访问。它应在以下场景中用于恢复数据：当你的消费端应用程序在实时流中错过了数据时——无论是因为短时间断开连接，还是任何其他导致你在一段时间内未能摄取实时数据的情况。

<div id="using-recovery">
  #### Using Recovery
</div>

使用 Recovery 流时，你的应用可以以与实时流相同的方式向其发起请求。但你的应用必须在 URL 中指定参数，以表明你要请求的时间窗口。换句话说，Recovery 请求是向 API 询问“从时间 A 到时间 B 的帖子”。这些帖子会通过你的流式连接传送，其行为模仿实时流，但速率会略慢于实时。示例如下：

&quot;https://stream-data-api.x.com/stream/powertrack/accounts/someAccountName/publishers/twitter/powertrack.json?startTime=2023-07-05T17:09:12.070Z&quot;

帖子会从所指定时间区间中最早的一分钟开始按时间顺序传送，一直到最后一分钟被传送完成。此时，会通过连接发送一条 Recovery Request Completed 消息，然后服务器会关闭该连接。如果你的请求从一个匹配结果很少甚至没有的时间点开始，那么在第一次结果被传送之前，可能会有一段等待时间——当 Recovery 在当时正在处理的归档部分中遇到匹配结果时，才会传送数据。当没有可传送的结果时，流会继续通过连接发送回车符（carriage return）或“心跳”（heartbeats），以防止你的连接超时。

Recovery 旨在作为一种便捷工具，用于恢复因短暂断连而错过的数据，而不是用于恢复诸如整天这类非常长时间段的数据。如果需要在较长时间范围内恢复数据，我们建议将较长请求拆分为较短的时间窗口（例如两个小时），以降低由于网络波动或其他原因在请求中途断开的可能性，并提升对长时间请求处理进度的可见性。

<div id="data-availability">
  #### 数据可用性
</div>

如果你无法在 5 分钟的回填窗口内重新建立连接，可以使用 Recovery 功能恢复过去 24 小时内错过的数据。

流式恢复功能允许你将回填窗口扩展到 24 小时。Recovery 使你能够“恢复”错过数据对应的这段时间区间。当你在连接请求中使用 `start_time` 和 `end_time` 请求参数时，就会启动一个恢复流。连接建立后，Recovery 会重新流式传输指定时间段的数据，然后断开连接。  

你可以同时向 Recovery 发起两个并发请求，即“两项恢复任务”。从技术实现上看，Recovery 的工作方式与回填相同，只是定义了开始时间和结束时间。一次恢复仅对应单一的时间范围。

<div id="backfill">
  #### 回填（Backfill）
</div>

要请求回填，你需要在连接请求中添加 `backfillMinutes=N` 参数，其中 N 是在建立连接时要回填的分钟数（1–5，只能是整数）。例如，如果你断开了 90 秒，那么你应在连接请求中添加 `backfillMinutes=2`。由于此请求会提供 2 分钟的回填，包括你断开前的那 30 秒时间段，你的 *consumer app 必须能够容忍重复数据*。

一个 Decahose 连接请求 URL 示例，请求对分区 1 进行 5 分钟回填，如下所示：

https://gnip-stream.x.com/stream/sample10/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json?partition=1&amp;backfillMinutes=5

**注意：**

* 你可以选择在连接时始终使用 `backfillMinutes=5`，然后处理提供的任何重复数据。

* 如果你断开连接超过五分钟，可以使用 Recovery 来恢复数据。

**从断连中恢复**

重新启动并从断连中恢复涉及多个步骤：

* 确定断连时间长度。
  * 5 分钟或以下？
    * 如果你为流启用了 Backfill，请准备带有适当 `backfillMinutes` 参数的连接请求。
  * 超过 5 分钟？
    * 如果你有 Recovery 流，请针对断连时间段发起 Recovery 请求（理想情况下使用你当前的实时规则集，如有必要可使用 Rules API）。

* 请求一个新的连接。

当你遇到断连或停机时，可使用以下策略来缓解影响并进行恢复：

1. **实施回填（Backfill）**\
   回填允许你从断开流连接之前的某个时间点重新连接，并覆盖最长 5 分钟的断连。它通过在连接请求中包含一个参数来实现。

2. **从其他位置消费冗余流**\
   如果冗余流可以被流式传输到同一个实时环境，并对数据进行去重，那么除非正常流和冗余流同时出现停机或断连，否则你将不再需要Recovery 操作。如果冗余流无法实时流式导入生产环境，可以将其写入单独的“应急”数据存储。然后，一旦主流连接发生断连或停机，你的系统就可以利用手头的数据来填补主数据库在数据缺失时间段内的空白。

3. **实施 Recovery**\
   当断连或停机同时影响到主流和冗余流时，请使用 Decahose Recovery 来恢复任何遗漏的数据。该 API 提供覆盖 5 天归档数据的滚动时间窗口，最好的用法是每次请求不超过一小时的时间段，并以流式方式拉取。这与实时流并行完成。请注意，我们无法提供超过 Recovery 所提供的 5 天窗口之外的 Decahose 数据恢复方案，因此在你这边发生严重停机的情况下，务必要使用冗余流，以确保你在本端拥有完整的数据副本。

当你检测到异常的已存储数据量时——\
在未发生断连或停机的情况下，检测数据缺失的潜在方式包括……

1. 统计入站帖子数量\
   你的系统应该在采集应用程序最开始的地方统计接收到的原始帖子数量，并提供一种方式，将这些数字与最终数据存储中实际存入的帖子数量进行比较。任何差异都可以被监控，并在数据在接收后被丢弃时向你的团队发出警报。

2. 分析异常的存储量\
   你还可以分析最终数据库中存储数据的量，以查找异常下降。这同样可以表明存在问题，尽管在某些情况下，数据量下降是正常的（例如，如果 X 平台不可用，人们在一段时间内无法创建帖子）。

对 Volume Stream API 的所有请求都必须使用 HTTP 基本身份验证（HTTP Basic Authentication），该验证由用于登录你在 console.gnip.com 上账户的有效电子邮箱地址和密码组合组成。每个请求都必须通过 Authorization 头部字段传递凭据。因此，请确认你的客户端为所有 API 请求都添加了 `Authorization: Basic` HTTP 头（通过 HTTPS 发送编码后的凭据）。

#### GET {stream-type}:stream

建立到 Firehose 流的持久连接，实时数据将通过该连接传送。

<div id="request-specifications">
  #### 请求规范
</div>

|     |     |
| :--- | :--- |
| **请求方法** | HTTP GET |
| **连接类型** | Keep-Alive  <br />  <br />应在请求头中指定该值。 |
| **URL** | 可在你的仪表板中该流的 API 帮助页面找到，使用以下结构：  <br />  <br />Decahose：<br /><br />[https://gnip-stream.x.com/stream/sample10/accounts/:account&#95;name/publishers/twitter/:stream&#95;label.json?partition=1](https://gnip-stream.x.com/stream/sample10/accounts/:account_name/publishers/twitter/:stream_label.json?partition=1) |
| **Partition (required)** | `partition=\{#}` - 现在必须使用分区才能消费完整的流。你需要在连接到流时指定 partition 参数。下面是每个流的分区数量：<br /><br />* Decahose：2 个分区 |
| **压缩** | Gzip。要使用 Gzip 压缩连接到流，只需在连接请求中发送 Accept-Encoding 请求头。该请求头应如下所示：  <br />  <br />Accept-Encoding: gzip |
| **字符编码** | UTF-8 |
| **响应格式** | JSON。你的请求头应指定响应使用 JSON 格式。 |
| **速率限制** | 60 秒内最多 10 次请求。 |
| **Backfill 参数** | 如果你购买了启用 Backfill 的流，你需要在 GET 请求中添加 &quot;backfillMinutes&quot; 参数以启用该功能。 |
| **读取超时** | 在你的客户端上设置读取超时，并确保其值大于 30 秒。 |
| **支持推文编辑** | 所有推文对象都将包含描述推文编辑历史的推文编辑元数据。有关更多详细信息，请参阅 [&quot;Edit Tweets&quot; 基础知识页面](/zh/x-api/enterprise-gnip-2.0/fundamentals/edit-tweets)。 |

<div id="responses">
  #### 响应
</div>

API 对这些请求可能返回以下响应。大多数错误代码会在响应正文中返回一个包含更多详细信息的字符串。对于非 200 状态码的响应，客户端应尝试重新连接。

| Status | Text | Description |
| :--- | :--- | :--- |
| 200 | Success | 连接已成功打开，新的活动将在产生时通过该连接发送。 |
| 401 | Unauthorized | 由于凭据无效，HTTP 身份验证失败。请使用你的凭据登录 console.gnip.com，以确保在请求中正确使用这些凭据。 |
| 406 | Not Acceptable | 一般来说，当你的客户端未能在请求头中正确声明接受来自流的 gzip 编码时会发生此情况，但在其他情况下也可能发生。  <br />  <br />将包含类似于 “此连接需要压缩。要启用压缩，请在请求中发送 `Accept-Encoding: gzip` 请求头，并在客户端读取流时准备好解压该流。” 的 JSON 消息。 |
| 429 | Rate Limited | 你的应用已超出连接请求的限制。 |
| 503 | Service Unavailable | Twitter 服务器出现问题。请使用指数退避模式重新连接。如果在 [X API Status Page](https://api.twitterstat.us/) 上没有关于此问题的公告，并且在 10 分钟后仍无法连接，请联系支持或紧急支持渠道。 |

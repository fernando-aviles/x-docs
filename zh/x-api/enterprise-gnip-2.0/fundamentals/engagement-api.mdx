<div id="overview">
  ## 概览
</div>

[`Enterprise`](https://developer.x.com/en/products/x-api/enterprise)

*这是仅在我们的受管访问级别中提供的企业级 API。要使用此 API，你必须先通过我们的企业销售团队开通账号。 [了解更多](/zh/x-api/enterprise-gnip-2.0/enterprise-gnip)*

Engagement API 可用于获取帖子展示量和互动指标。虽然大多数指标和端点都要求你使用 [OAuth 1.0a 用户上下文](/zh/resources/fundamentals/authentication) 进行认证，但你可以使用 [OAuth 2.0 Bearer Token](/zh/resources/fundamentals/authentication#oauth-2-0) 和 /totals 端点访问公开的“收藏”“转发”“回复”和“视频观看次数”等指标。

**注意：** 你可能会发现某些 X 网页仪表盘中报告的数据与 Engagement API 报告的数据之间存在差异。这是因为网页仪表盘通常只显示在所选时间范围内发生的互动和/或展示。例如，某个网页仪表盘可能只显示某个日历月内帖子获得的互动，而 Engagement API 可能会显示超出该月份范围但仍在所请求时间范围内发生的互动。在这些情况下，应将 Engagement API 视为权威的数据来源。
 

<div id="request-endpoints">
  ### 请求端点
</div>

Engagement API 有三个端点：

<div id="current-totals-totals">
  #### 当前总计：[/totals]
</div>

* 请求会返回目标帖子展示次数总计指标和互动总计指标
* 仅限以下指标：Impressions（展示次数）、Engagements（互动）、Favorites（点赞）、Replies（回复）、Retweets（转发）、Quote Tweets（引用推文）以及 Video Views（视频播放量）
* 支持使用 OAuth 1.0a 用户上下文，获取**在最近 90 天内创建的**帖子对应的 **Impressions** 和 **Engagements** 指标
* 支持使用 OAuth 2.0 Bearer Token，获取**任意帖子**的 **Favorites、Retweets、Quote Tweets、Replies** 和 **Video Views** 指标
* 结果基于发起请求时刻的当前展示次数和互动总计
* 适用于为仪表板报告提供数据，以及计算多个 @handle 的互动率
* 支持在单个请求中最多为 250 条帖子请求指标
   

<div id="last-28-hours-28hr">
  #### 最近 28 小时：[/28hr]
</div>

* 请求可以返回展示次数的总指标、互动次数的总指标，以及最近 28 小时内发生的各项互动指标的明细
* 数据可以按帖子 ID 分组，也可以按时间序列进行聚合，按天或按小时分组
* 非常适合跟踪最近创建内容的表现
* 支持所有可用的指标
* 支持在每个请求中为最多 25 条帖子请求指标
   

<div id="historical-historical">
  #### 历史：[/historical]
</div>

* 请求可以根据互动时间（而非帖子创建时间）返回最近一年的展示次数、互动量以及各类互动指标的细分。
* 请求支持开始日期和结束日期参数，可灵活缩小到最长为 4 周的特定时间范围。
* 帖子互动数据仅限追溯至过去 365 天。
* 数据可以按帖子 ID 分组，或以时间序列形式汇总，按天或按小时聚合。
* 非常适合将近期表现与历史基准进行比较，或构建某个 @handle 历史表现的整体概览。
* 支持所有可用指标。
* 每个请求最多可为 25 条帖子获取指标。

分组功能可以帮助你自定义整理返回的互动指标。每个请求最多可包含 3 个分组。你可以按下列一个或多个值对指标进行分组：

本文档旨在向开发者介绍如何与 Engagement API 集成。我们将先讨论为什么要进行集成，然后再深入讲解具体的技术实现细节。

<div id="what-does-the-engagement-api-provide">
  ##### **Engagement API 提供了什么功能？**
</div>

* Engagement API 为任意 X 账号在过去 90 天内发布的自有帖子提供展示量和互动数据，前提是该账号已通过 [3-legged OAuth](/zh/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow) 授权你的 App 代表其请求相关指标。这一功能强大且易于实现的解决方案，可立即获取展示量，以及 URL 点击、#话题标签点击等多种深度互动行为。
* Engagement API 为任意帖子提供点赞（favorites）、转发（Retweets）、引用转发（Quote Tweets）、回复以及视频播放量等汇总指标。这可以作为获取任意单条或一组帖子基础互动数据的有力方式。
* Engagement API 通过允许客户使用 15+ 个表现指标有效衡量内容表现，为社交聆听、营销和发布平台带来了新的价值，从而帮助客户衡量在 X 上的投资回报率（ROI）。
* Engagement API 是一种请求/响应类型的 API，允许应用开发者发送包含帖子 ID、所需指标和时间范围的请求，API 会即时返回相应的 data。
   

<div id="why-integrate-example-use-cases">
  ##### **为什么要集成？示例用例**
</div>

* 了解你的内容的总体触达范围，查看有多少人看到这些内容。了解有多少人观看视频、点击链接、点击话题标签，或者安装你的应用。
* 生成总量和时间序列两类互动指标。
* 了解任意公开帖子的一些基础互动指标（收藏、转发、引用帖子、回复）。
* 使用这些指标来判断哪些类型的帖子效果更好，从而可以更频繁地发布此类内容，为你的内容获取更多展示量和更多互动。
* 将营销行为自动化（例如，当你的某条帖子获得 100 个赞，或达到其他阈值时，自动从另一个自有账号转发该内容）。
* 将各个活动相互对标比较，把它们作为进行 A/B 测试的工具。
* 分析哪些类型的内容最适合客服团队，从而确定如何以及何时进行回复。
* 展示从你的平台发布的内容的分析数据。

<div id="integrating-the-engagement-api">
  #### 集成 Engagement API
</div>

<div id="introduction-to-api">
  ##### **API 简介**
</div>

Engagement API 是一个简单的 RESTful API，它接收使用 JSON 编码的请求，并返回使用 JSON 编码的互动指标。请求由三个主要部分组成（点击链接查看更多文档）：

* ***帖子 ID*** 的数组。
* 指定所需[指标类型](https://developer.x.com/en/docs/x-api/v1/metrics/get-tweet-engagement/overview#EngagementTypes)的数组。类型包括 “impressions”、“retweets”、“hashtag&#95;clicks” 和 “user&#95;follows” 等。
* [互动分组](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings)，这是一个 JSON 结构，用于指示希望在 API 响应中如何组织互动数据。

在许多情况下，互动类型和分组在各次请求之间会保持相对固定，只有帖子 ID 会被更新。

Engagement API 提供[三个端点](https://developer.x.com/en/docs/x-api/v1/metrics/get-tweet-engagement/overview#RequestEndpoints)：

* **Totals** - 为帖子提供整体互动总数。某些指标适用于所有帖子，而另一些仅提供过去 90 天内的数据。
* **28 hour** - 提供最近 28 小时的时间序列互动指标。
* **Historical** - 为自 2014 年 9 月 1 日以来发布的帖子提供最长连续四周的时间序列互动指标。

**/totals** 端点支持在一次请求中为最多 **250 条帖子** 请求指标。**/28hour** 和 **/historical** 端点支持 **每次请求最多 25 条**。

在讨论如何获取 Engagement API 的访问权限之后，我们将演示如何发起 API 请求，提供 OAuth 概览，并给出其他技术资源的链接。

<div id="getting-api-access">
  ##### **获取 API 访问权限**
</div>

如果你正在阅读本文档，你很可能已经获得了 Engagement API 的访问权限。否则，请联系你的 Enterprise 客户经理，或在[此处](/zh/x-api/enterprise-gnip-2.0/enterprise-gnip)申请 Enterprise 访问权限。

第一步是使用已获批准的开发者账号，通过[开发者控制台](/zh/resources/fundamentals/developer-portal)创建一个 [X app](/zh/resources/fundamentals/developer-apps)。你的客户经理需要与你的这个应用关联的数值型 App ID，才能为你开通访问权限。如果你需要申请开发者账号，可以在[此处](/zh/resources/fundamentals/developer-apps)进行申请。

<div id="making-a-request">
  ##### **发起请求**
</div>

好消息是，向 Engagement API 发起请求非常简单。在本例中，我们将请求以下两条 [@XDevelopers](https://x.com/XDevelopers) 帖子的转推、引用推文、点赞和回复的总数：

> 1/ Today we’re sharing our vision for the future of the X API platform![https://t.co/XweGngmxlP](https://t.co/XweGngmxlP)
>
> — Twitter Dev (@TwitterDev) [April 6, 2017](https://x.com/TwitterDev/status/850006245121695744)

> Don’t miss the Posts about your Post.
>
> Now on iOS, you can see Retweets with comments all in one place. [pic.x.com/oanjZfzC6y](https://t.co/oanjZfzC6y)
>
> — X (@X) [May 12, 2020](https://x.com/status/1260294888811347969?ref_src=twsrc%5Etfw)

第一步是构造一个 JSON 格式的 API 请求，其中包括：由这两个帖子 id 组成的数组、一个包含我们感兴趣的互动类型的数组，以及一个自定义命名的 “groupings” JSON 对象，用来指示我们希望在响应中如何组织这些指标。我们的请求如下所示：

```json
{
  "tweet_ids": [
    1260294888811347969, 850006245121695744
  ],
  "engagement_types": [
    "retweets", "quote_tweets", "favorites", "replies"
  ],
  "groupings": {
    "engagement-types-by-id": {
      "group_by": [
        "Tweet.id", "engagement.type"
      ]
    }
  }
}
```

要获取这些汇总指标，我们向 https://data-api.x.com/insights/engagement/totals 这个 endpoint 发送一个 JSON `POST` 请求。

我们会在请求中包含以下 headers，用来表明请求体采用 JSON 编码，并且经过 Gzip 压缩（因为请求体可能会很大）：

* Content-Type: application/json
* Accept-Encoding: gzip
   

发起请求时，我们使用 OAuth 进行认证，我们会在下一节中进一步介绍。

API 会返回如下 payload（载荷）：

```json
{
  "grouping name": {
    "1260294888811347969": {
      "favorites": "17111",
      "quote_tweets": "3254",
      "replies": "1828",
      "retweets": "5218"
    },
    "850006245121695744": {
      "favorites": "492",
      "quote_tweets": "66",
      "replies": "42",
      "retweets": "324"
    }
  }
}
```

请注意，响应中的指标是按照 “groupings” 定义的结构返回的，首先按帖子ID 列出指标，然后在下一层级按互动类型区分。

这很简单。如果你刚开始进行 OAuth 认证，请继续阅读下一节。

<div id="authenticating-with-oauth">
  #### 使用 OAuth 进行身份验证
</div>

OAuth 是技术行业中非常常见的一种身份验证标准。 如果你已经在使用 OAuth（比如在其他 X API 中），那么你很可能已经在使用某种特定语言的 OAuth 包，它会帮你屏蔽掉所有繁琐的细节。 如果你是第一次接触 OAuth，请访问我们的 [Oauth with the X API](/zh/resources/fundamentals/authentication) 页面，或直接前往 [https://oauth.net](https://oauth.net/) 了解更多。 然后，我们建议你为自己选择的集成语言找到一个合适的 OAuth 包，并从那里开始。 使用这些包时，完成身份验证的典型步骤通常包括：配置你的密钥和令牌、创建某种 HTTP 对象，然后使用该对象发起请求。

例如，在 Ruby 生态中，下面的伪代码展示了一个使用 Ruby gem ‘oauth’ 构建支持 OAuth 的应用并发起 POST 请求的“配方”示例：

```js
require 'oauth'

#Assemble JSON request (as above).
request = make_json_request()

#Build an app consumer object with my app consumer key and secret.
consumer = OAuth::Consumer.new(keys['consumer_key'], keys['consumer_secret'], {:site => ‘https://data-api.x.com’})
#使用提供权限的账户所提供的令牌构建用户令牌。如果进行仅限应用的请求(使用 /totals 端点检查不需要权限的推文),则可以跳过此步骤。
token = {:oauth_token => keys['access_token'], :oauth_token_secret => keys['access_token_secret']}

#Create oauth-enabled app object.
app = OAuth::AccessToken.from_hash(consumer, token)
#Make POST request.
result = app.post(“/insights/engagement/totals", request, {"content-type" => "application/json", "Accept-Encoding" => "gzip"})
```

Engagement API 同时支持仅应用（application-only）和用户上下文（user-context）身份验证。如果你使用 `/totals` 端点为非自有的公开帖子收集互动指标，则不需要任何用户授权，可以使用仅应用身份验证。在这种情况下，你只需使用应用的 key 和 secret 进行身份验证。

OAuth 还允许应用使用与用户相关的令牌，以“代表其他用户”的方式发起 API 请求。如果你要为自有帖子生成 Engagement 指标，即由你已拥有其用户令牌的用户发布的帖子，那么你将以用户上下文发起请求，也就是说，需要同时使用应用密钥和特定用户的访问令牌进行身份验证。这些用户访问令牌通常通过 &#39;[Sign-in with X](/zh/resources/fundamentals/authentication#log-in-with-x)&#39; 流程获得，或直接从用户处获取（请注意，如果你是直接从用户获取令牌，则必须使用 [twurl](https://github.com/xdevplatform/xurl)）。一旦用户向你提供了他们的令牌，这些令牌不会过期，并且只要用户不重置令牌或更改密码，你就可以使用 Engagement API 代表他们发起请求；如果发生这些情况，用户将需要向你提供新的令牌。

你可以通过 [此表格](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings) 查看各个指标所需的身份验证类型。

<div id="selecting-an-engagement-api-endpoint">
  ### 选择 Engagement API 端点
</div>

Engagement API 提供三个不同的端点：

* **[Totals](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement)** - 提供“自有”或“非自有”帖子中所选指标的总计汇总。一些指标适用于所有帖子，而另一些仅适用于最近 90 天内发布的帖子。每个请求最多支持 250 条帖子。
* **[28 hour](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement)** - 提供最近 28 小时内“自有”帖子的 Engagement 时间序列指标。每个请求最多支持 25 条帖子。
* **[Historical](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-historical)** - 提供自 2014 年 9 月 1 日以来发布的“自有”帖子、最长连续四周的 Engagement 时间序列指标。每个请求最多支持 25 条帖子。
   

每个端点都有其独特特性。无论你计划同时使用这三个端点，还是想决定哪一个最符合你的用例，都需要理解它们之间的差异。

下面我们将介绍一些关键概念，进一步说明这三个端点，并给出示例用例，这些用例大致对应到特定端点。我们希望这些信息可以帮助你更高效地集成这三个端点，或帮助你决定哪个单一端点最适合你的目标。
 

<div id="key-concepts">
  #### 关键概念
</div>

有几个关键概念，有助于阐明 Engagement API 的三个端点各自的功能特点以及它们提供的数据。
 

<div id="impressions-and-engagement-metrics">
  ##### 展现与互动指标
</div>

展现（impressions）表示某条帖子在 X 平台自然场景下被查看的次数。来自推广或付费场景中展示的帖子所产生的展现不会计入。在 Engagement API 出现之前，帖子展现只代表潜在的查看次数，其计算方式基于作者账号以及所有转发该内容账号的关注者数量，并未考虑某位用户实际上并没有看到该帖子的常见情况。

由 Engagement API 生成的展现指标衡量的是帖子被实际渲染用于展示的次数。如果你账号的一位关注者没有看到你的帖子，则不会计为一次展现。

Engagement API 提供 14 种唯一的互动[指标类型](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#available-metrics)，每一种都代表用户在看到帖子时可以采取的一种特定操作。这些操作包括转发、点赞、回复、点击 #话题标签、链接和媒体、关注作者，以及查看作者的个人资料。上述所有单独操作最终都会汇总为一个 Engagements（总互动次数）指标。

<div id="owned-and-unowned-x-content">
  ##### 自有与非自有 X 内容
</div>

Engagement 明确区分自有和非自有帖子。自有帖子是指从你的账号发布的帖子，或你已经获得权限可以请求其 Engagement data 的帖子。与其他 X API 一样，你通过让其他 X 用户/账号共享访问令牌来获得权限，这些访问令牌使你能够代表他们发出 API 请求。获取这些令牌的一种常见方式是使用 [“使用 X 登录”流程](/zh/resources/fundamentals/authentication#log-in-with-x)。

/totals endpoint 为自有和非自有帖子都提供互动数据。对于非自有帖子，你可以请求帖子展示中公开可见的互动指标：Favorite、Retweet 和 Reply。对于这些指标，Engagement API 的价值在于能够以自动化的方式，在大规模场景下获取这些指标。对于自有帖子，/totals endpoint 还会提供 Impression 和（总）Engagement 指标。

/28hr 和 /historical endpoints 只提供自有帖子的指标，这意味着在向这些 endpoints 发出请求时，你必须传递用户上下文信息。

<div id="total-and-time-series-engagement-data">
  ##### 总量和时间序列互动数据
</div>

顾名思义，`/totals` 端点仅提供各类互动的总体汇总数据。其数值表示自帖子发布以来截至当前的累计总数。如果某个帖子刚刚发布，而你反复请求其指标，这些总数通常会在每次请求时发生变化。

`/28hr` 和 `/historical` 端点既可以提供总体汇总数据，也可以提供时间序列数据。在请求时间序列数据时，可以将互动指标聚合为按天或按小时的时间序列数据。  

关于如何使用 `/28hr` 和 `/historical` 端点请求时间序列数据，请参阅我们关于[互动分组](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings)的文档。

<div id="endpoints-and-example-use-cases">
  #### 端点和示例用例
</div>

鉴于上文讨论的特性和差异，各个端点通常对应不同类型的用例。为帮助你判断哪个端点最适合你的特定用例，下面列出了一些用户示例表述以及最能满足这些表述的端点。

<div id="totals">
  ##### **/totals**
</div>

* 我只需要访问部分指标类型（Impressions、Engagements、Favorites、Retweets、Quote Tweets、Replies 和 Video Views）。
* 我需要访问任何帖子的基础互动数据，而不仅仅是我拥有的帖子。
* 我想将表现与竞争对手进行对比。
* 我想跟踪某个话题标签或活动的基础互动统计，其中包含我不拥有的帖子。
* 我不需要按天或按小时拆分的数据，只需要在发起请求时得到当前总数。
* 我需要一个可以在报告或仪表板中展示的单一指标，并且不想存储任何数据。
* 我想在页面加载时展示数据，只需发起一次请求并获得响应。
* 我需要每天获取数十万甚至数百万条帖子的相关数据。
   

<div id="28hr">
  ##### **/28hr**
</div>

* 我需要访问全部 17 种指标类型。
* 我想展示最近 28 小时内发布的帖子的数据。
* 我有一个每天运行一次的任务来获取我关心的数据，只需要获取过去一天的数据。
* 我需要将指标按天或按小时拆分。
* 我想在仪表盘中按小时展示活动的时间序列拆分。
* 我每天需要对数十万条帖子拥有较高的访问级别。
* 我具备存储能力，可以每天刷新一次数据并维护一份持续累积的统计数据。
   

<div id="historical">
  ##### **/historical**
</div>

* 我需要访问全部 17 种指标类型。
* 我需要获取最早可追溯到 2014 年 9 月创建的帖子历史数据。
* 我想展示对不同广告活动的详细历史对比分析。
* 我需要按天或按小时细分指标。
* 我不需要对 Engagement API 的高访问级别，每天只需要为几百或几千条帖子获取数据。

<div id="engagement-api-key-characteristics">
  ### Engagement API 关键特性
</div>

* **RESTful API**，以 JSON 格式提供数据，支持带有 JSON 请求体的 POST 请求。
* **请求类型：** 客户端应用可以发起以下类型的请求：
  * **总互动量（Total engagements）** -- 向 /totals 端点发起 HTTP POST 请求
  * **最近 28 小时互动量（Last 28-hour engagements）** -- 向 /28hr 端点发起 HTTP POST 请求
  * **历史互动量（Historical engagements）** -- 向 /historical 端点发起 HTTP POST 请求
* **OAuth 认证：**
  * [OAuth 1.0a 用户上下文](/zh/resources/fundamentals/authentication)：所有可用指标适用于由已通过 [3-legged OAuth](https://developer.x.com/resources/fundamentals/authentication/obtaining-user-access-tokens) 授权你的应用的用户所拥有的帖子。进行请求时，你必须使用该用户的 Access Token。[](/zh/resources/fundamentals/authentication)
  * [OAuth 2.0 Bearer Token](/zh/resources/fundamentals/authentication#oauth-2-0)：部分指标（转发、引用推文、回复、点赞和视频观看次数）适用于任何公开帖子。 
* **请求元数据和结构：** 请求 data 是一个 JSON 对象，由帖子 ID 数组、互动类型数组以及互动分组结构组成。
* **每个请求可包含的帖子数量：**
  * /totals 端点：250 个帖子 ID
  * /28hr 端点：25 个帖子 ID
  * /historical 端点：25 个帖子 ID
* **互动指标可用性：**
  * **/totals** -- 自帖子发布以来的指标总数。展示次数（Impressions）和互动量（Engagements）适用于过去 90 天内发布的帖子，而转发、引用推文、回复、点赞和视频观看次数适用于所有帖子。
  * **/28hr** -- 自请求时间起最近 28 小时。
  * **/historical** -- 自 2014 年 9 月 1 日起的任意 28 天时间段。
* **指标类型：** 每个请求都包含一个 [Metric Types](http://support.gnip.com/apis/engagement_api/overview.html#EngagementTypes) 数组。这些指标的可用性取决于端点，并且如果是从 /totals 端点请求，还取决于帖子是否为基于用户授权的（user-permissioned）。
  * /totals 端点：
    * 所有帖子：点赞、转发、引用推文、回复和视频观看次数
    * 需要 OAuth 1.0a 用户上下文：展示次数、互动量、点赞、回复和转发
  * /28hr 和 /historical 端点（需要带有帖子所有者 Access Token 的 OAuth 1.0a 用户上下文）：展示次数、互动量、点赞、回复、转发、URL 点击、话题标签点击、详情点击、固定链接点击、多媒体点击、App 安装尝试、App 打开、帖子邮件、视频观看次数和媒体观看次数
* **互动分组：** 每个请求都包含一个 [Engagement Groupings](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#engagement-api-groupings) 数组。通过这些分组，你可以自定义返回指标的组织方式。每个请求最多可包含三个分组。指标可以按以下值进行组织：
  * 所有端点：帖子 ID、互动类型
  * /28hr 和 /historical 端点：如果指定以下额外分组，这些端点会提供时间序列：互动日期、互动小时
* **集成预期：** 你的团队将负责以下事项。
  * 创建并维护一个客户端应用，用于向 Engagement API 发送 HTTP 请求，返回请求中包含的帖子 ID 的互动指标。
* **限制**
* 视频观看次数仅适用于发布时间不超过 1800 天的帖子。

<div id="authenticating-with-the-engagement-api">
  ### 使用 Engagement API 进行认证
</div>

> **请注意**： 
>
> 在你开始使用 Engagement API 之前，X 需要为你的开发者 App 启用对 Engagement API 的访问权限。为此，请务必将你打算用于认证的 App ID 提供给你的客户经理或技术支持团队。

Engagement API 提供两种可用的认证方法：[OAuth 1.0a](/zh/resources/fundamentals/authentication#oauth-1-0a-2) 和 [OAuth 2.0 Bearer Token](/zh/resources/fundamentals/authentication#bearer-token-also-known-as-app-only)。 

**OAuth 2.0 Bearer Token**（也称为“仅应用”（application-only））允许你访问公开可用的互动指标。使用这种认证方法，在向 [/totals 端点](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-totals) 发送请求时，你可以获取任何公开可见帖子对应的收藏（也称为点赞）、转发、引用帖子、回复和视频观看次数的总数。 

**OAuth 1.0a**（也称为“用户上下文”）允许你代表某个用户发起请求，并访问该用户的私有互动指标。 

在以下情况下必须使用这种认证方法：

* 所有发送到 [/28hr 端点](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-28hr) 和 [/historical 端点](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement-historical) 的请求
* 访问下列任一私有指标：展示次数（Impressions）、互动次数（Engagements）、媒体观看次数（Media Views）、媒体互动次数（Media Engagements）、URL 点击次数（URL Clicks）、话题标签点击次数（Hashtag Clicks）、详情展开次数（Detail Expands）、永久链接点击次数（Permalink Clicks）、应用安装尝试次数（App Install Attempts）、应用打开次数（App Opens）、通过电子邮件分享帖子（Email Post）、用户关注次数（User Follows）以及用户个人资料点击次数（User Profile Clicks）

使用 OAuth 1.0a 发送请求时，你需要包含拥有目标帖子或受保护资源的用户的访问令牌（Access Token 和 Secret）。如果在请求受保护的用户数据时未提供正确的用户访问令牌，Engagement API 将返回 `403 Forbidden` 错误。

即使你代表拥有这些帖子对应账户的用户进行认证，Engagement API 也不允许你获取[受保护帖子](https://help.x.com/en/safety-and-security/public-and-protected-tweets)的互动数据。尝试这样做将返回 `400 Bad Request` 错误，错误消息为 `"Tweet ID(s) are unavailable"`。

如果你代表自己的 X 账号发送请求（也就是说，该账号拥有该开发者 App），可以直接在 [Developer Console](https://developer.x.com/en/portal/projects-and-apps) 中该开发者 App 的 “Keys and tokens” 选项卡下生成所需的访问令牌。

如果你代表其他任何用户发起请求，则需要使用三方（3-legged）OAuth 流程来获取所需的访问令牌。以下文档包含有关如何执行此操作的更多信息：[OAuth 1.0a: how to obtain a user’s access tokens](/zh/resources/fundamentals/authentication#oauth-1-0a-2)。

如需更多示例（包括如何使用 OAuth 1.0a 进行认证），请查看 [XDevelopers 针对 Engagement API 的 Python 示例代码](https://github.com/xdevplatform/enterprise-scripts-python/tree/master/Engagement-API)。

<div id="recent-changes-to-the-engagement-api">
  ### Engagement API 的最新更改
</div>

Engagement API 提供了极有价值的曝光和互动指标，帮助你监控自己在 X 上活动的表现。为了持续支持基于我们数据的营销决策，我们很高兴分享 Engagement API 的最新更改，这些更改提升了整个 X 平台各项指标的一致性。 

我们最近对 Engagement API 进行了更新，使其使用与 X 分析仪表板（analytics.x.com）相同的指标聚合方法。在推出这些新指标时，我们尽量减少向后不兼容的 API 变更，并于 2017 年 10 月 9 日部署了第一批更改。这些更改提升了你或你的客户在所有监控 X 表现的渠道之间的一致性。以下是这些更改的详细说明：

|     |     |
| :--- | :--- |
| **Metric（指标）** | **Change（变更）** |
| engagements | 我们更新了汇总为整体 engagements 的各项指标，使其与帖子分析仪表板保持一致。Engagements 衡量“人们与此帖子互动的次数”。<br /><br />对于包含视频或 GIF 等媒体的帖子，engagements 指标将不再包含媒体观看次数。媒体观看次数现在可以通过一个新的指标 *media&#95;views* 获取。 |
| media&#95;clicks* | 此指标已被名为“*media&#95;engagements*”的新指标替代。 |
| video&#95;views | 自 2018 年 7 月 6 日起，此指标通过 [/totals](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement) 端点对“非自有”帖子开放。这意味着你可以使用仅应用认证（app-only authentication）访问**所有**帖子的 视频观看次数。 <br /><br />你只能请求 1800 天内的 视频观看次数。如果你尝试请求某条超过 1800 天的帖子的 视频观看次数，你将收到如下返回：<br /><br />&quot;unsupported&#95;for&#95;video&#95;views&#95;tweet&#95;ids&quot;: [&quot;TWEET&#95;ID&quot;]<br /><br />**请注意**，它与 media&#95;views 不同，因为 video&#95;views 依赖 MRC 标准：至少有两秒钟视频有 50% 处于可视范围内。  <br /><br />**另外，**请注意，你可能会看到 X 自有平台（移动应用和网站）中显示的 视频观看次数指标，与通过 /28hr 和 /historical 端点获取的数值之间存在差异。<br /><br />* X 用户界面中显示、并通过 /totals 端点提供的 视频观看次数，将是该视频在所有帖子中被发布时的总观看次数。这意味着 UI 中显示的指标包含该视频在任何被转发或在其他单独帖子中再次发布时产生的合并观看次数。<br />* 通过 /28hr 和 /historical 端点提供的 视频观看次数，则只包含你为其获取指标的特定帖子所产生的观看次数。 |
| media&#95;views | 这包括你媒体在视频、vines、GIF 和图片中的所有观看（自动播放和点击）。<br /><br />**请注意**，带图片的帖子在分析仪表板中不会显示 media&#95;views 指标，但在 Engagement API 中会返回该指标。 |
| media&#95;engagements* | 这包括你媒体在视频、vines、GIF 和图片上的点击次数。此指标替代了 *media&#95;clicks*。 |
| quote&#95;tweets | 自 2020 年 7 月 7 日起，此指标通过 /totals 端点对“非自有”帖子开放。这意味着你可以使用仅应用认证访问所有帖子的引用帖子数量。 |

<div id="interpreting-the-metrics">
  ### 解读指标
</div>

**注意：**你可能会发现某些 X 网页仪表板上报告的数据与 Engagement API 中报告的数据之间存在差异。出现这些差异的原因是，网页仪表板通常只展示在所选时间范围内发生的互动和/或展示次数。例如，一个网页仪表板可能只显示某个日历月内帖子上的互动情况，而 Engagement API 则可能会显示超出该月份范围、但仍在你请求的时间区间内发生的互动。在这些情况下，应以 Engagement API 的数据为准。
 

<div id="impressions-and-engagement-data">
  #### 展示次数和互动数据
</div>

Engagement API 提供**自然**展示次数和互动数据。

展示次数表示某条给定帖子在 X 平台上以自然场景被查看的总次数。在推广（Promoted）或付费（Paid）场景下产生的展示次数**不**包含在内。

互动表示某条给定帖子在**自然**和**推广**两种场景下，被查看者产生互动的总次数。互动包括但不限于转推、收藏、回复、URL 点击、话题标签点击、提及点击以及媒体播放。有关包含在内的全部互动行为列表，请参见 Engagement Data 部分。 

要计算基础互动率，请在你分析的时间范围内，用该帖子总互动次数除以总展示次数。

展示次数和互动数据只能针对自有 @账号 的帖子，或已授权你的应用查看其帖子详细信息的 @账号 的帖子进行获取。在内部实现上，Engagement API 会跟踪已被请求的唯一 @账号 数量，并与合同约定的 @账号 上限进行比较。建议你在整个月内也在客户端侧跟踪 @账号 请求使用情况。  

<div id="video-metrics">
  #### 视频指标
</div>

在 X 中，有几种不同的指标用来表示媒体的展现量。第一种是我们的视频观看量指标，它依赖 MRC 标准：至少有 50% 的视频画面在视窗中可见，且持续至少两秒。第二种是 Media Views，它包含你的媒体在视频、vines、gifs 和图片中的所有观看次数（自动播放和点击播放）。

视频观看量指标可通过 /28hour 和 /historical 端点获取自有帖子（owned Posts）的数据，也可通过 /totals 端点获取所有非自有帖子（unowned Posts）的数据。 

虽然 X 用户界面中的视频观看量指标使用的是相同的 MRC 标准，但请注意，你可能会看到 X 自有及运营平台（移动应用和网站）上显示的视频观看量指标，与通过不同 Engagement API 端点获取的数值之间存在差异。

* /totals 端点和 X 用户界面提供的视频观看量，会展示该视频在所有发布过它的帖子中的聚合观看次数。这意味着，通过 /totals 提供并在 X UI 中显示的指标，包含了该视频在被转发（Retweeted）或在其他单独帖子中再次发布时产生的所有观看次数总和。
* /28hour 和 /historical Engagement API 端点提供的视频观看量，仅包含由你为其拉取指标的那条特定帖子所产生的观看次数。 
   

请注意，我们不会为超过 1800 天的帖子提供视频观看量指标。相反，我们会返回一个对象，其中列出那些超过 1800 天的帖子。对于你请求的帖子，其他所有指标仍会在一个单独的对象中返回。以下是一个示例响应：

<div id="engagement-api-groupings">
  ### Engagement API 分组
</div>

分组用于对返回的互动指标进行自定义组织。每个请求最多可以包含 3 个分组。你可以按以下一个或多个值对指标进行分组：

*以下三个 endpoint 均支持：*

* tweet.id
* engagement.type
   

*`/28hr` 和 `/historical` 可以提供时间序列指标，因此支持：*

* engagement.day
* engagement.hour

分组会按顺序依次生效，因此你可以通过更改 `group_by` 值的顺序来改变期望的结果格式。包含四个 `group_by` 值的分组仅支持以下两种格式之一：

```bash
"group_by": [
    "tweet.id",
    "engagement.type",
    "engagement.day",
    "engagement.hour"
  ]
```

或

```bash
"group_by": [
    "engagement.type",
    "tweet.id",
    "engagement.day",
    "engagement.hour"
]
```

例如，如果你想生成各类指标类型的总计，请在请求中包含如下所示的 “groupings” 规范（有关如何构造请求的更多信息，请参阅 [API 参考](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#post-insights-engagement) 页面）：

```json
{
  "engagement_types": [
    "favorites",
    "replies",
    "retweets"
  ],
  "groupings": {
    "Grand Totals": {
      "group_by": [
        "engagement.type"
      ]
    }
  }
}
```

通过这种分组方式，Engagement API 的 JSON 响应会在顶层包含一个名为 `"Grand Totals"` 的属性，该属性按指标类型给出总体汇总值：

```json
{
  "Grand Totals": {
    "favorites": "12",
    "replies": "2",
    "retweets": "2"
  }
}
```

要为单个帖子按帖子 ID 分组生成 4 小时时间序列指标，请求中将包含以下分组规范：

```json
{
  "start": "2016-02-10T17:00:00Z",
  "end": "2016-02-10T21:00:00Z",
  "tweet_ids": [
    "697506383516729344"
  ],
  "engagement_types": [
    "impressions",
    "engagements"
  ],
  "groupings": {
    "Tweets_MetricType_TimeSeries": {
      "group_by": [
        "tweet.id",
        "engagement.type",
        "engagement.hour"
      ]
    }
  }
}
```

通过这种分组方式，Engagement API 的 JSON 响应将包含一个根级 `"Tweets_MetricType_TimeSeries"` 属性，其中的指标先按帖子 ID 划分，再按指标类型细分，并提供相应的按小时粒度时间序列：

```json
{
  "Tweets_MetricType_TimeSeries": {
    "697506383516729344": {
      "impressions": {
        "2016-02-10": {
          "17": "551",
          "18": "412",
          "19": "371",
          "20": "280"
        }
      },
      "engagements": {
        "2016-02-10": {
          "17": "8",
          "18": "6",
          "19": "3",
          "20": "0"
        }
      }
    }
  }
}
```

    如果你的合同中包含可与 Engagement API 一起使用的唯一 handle 数量上限，X 内部系统会跟踪使用 Engagement API 查询的、拥有相关帖子（Posts）的已通过认证的用户数量。客户也应在客户端自行跟踪这一唯一数量。目前，没有用于检查 Engagement API 的 @handle 用量的用量 API 或 UI。如果请求的 @handle 数量多于合同约定的数量，系统不会阻止超额使用。在结算月末，系统会将查询到的唯一 @handle 数量与合同约定的数量进行比较，并根据合同条款对超额部分收费。
  </Accordion>

    目前，没有用于检查 Engagement API 的 @handle 用量的用量 API 或 UI。如果请求的 @handle 数量多于合同约定的数量，系统不会阻止超额使用。在结算月末，系统会将查询到的唯一 @handle 数量与合同约定的数量进行比较，并根据合同条款对超额部分收费。

    **响应负载中返回的 `engagements` 元数据字段不等于各类互动指标总数之和。这是为什么？**

    这是预期行为。`engagements` 元数据字段可能并不总是与 API 返回的所有单项互动指标之和完全对应。这是因为 `engagements` 元数据字段中可能包含了一些在响应负载中没有以独立指标形式拆分出来的额外互动。换句话说，把各种互动指标的总数相加，可能不会等于响应负载中返回给你的 `engagements` 指标字段的数值。

    你可以将 `engagements` 元数据字段理解为在该帖子上发生的任何点击或交互。
     

    **响应负载中的 `url_clicks` 字段返回了一个数值，但实际上该帖子并没有 URL。这怎么可能？**

    这可能是因为帖子中包含了类似话题标签（会创建到其他页面的链接）之类的内容，用户点击该内容时会被计为一次 URL 点击。
     
  </Accordion>

  <Accordion title="为什么我无法获取某条特定帖子的互动数据？">
    你可能无法获取某条特定帖子的互动数据，原因包括但不限于：

    * 你请求的帖子 ID 在你用于代表第三方获取数据的认证令牌权限范围内不可用。
    * 你在 /totals 端点中请求的帖子 ID 超过 90 天，因此无法返回曝光或互动指标。
    * 你请求的帖子 ID 已不再可用，通常意味着这些帖子已被删除，或者因其他原因不再公开可见。

    请查看在上述任一情况下你可能会收到的不同[错误消息](/zh/x-api/enterprise-gnip-2.0/fundamentals/engagement-api#error-messages)。
  </Accordion>

  <Accordion title="如何在使用 Engagement API 时处理速率限制？">
    当你向 Engagement API 发起请求时，可以使用响应头中返回的 `x-per-minute-limit` 和 `x-per-minute-remaining` 信息来监控你的使用量。

    `x-per-minute-limit` 告诉你你的配额上限，而 `x-per-minute-remaining` 告诉你还剩余多少次调用。
  </Accordion>
</AccordionGroup>

<div id="authentication">
  #### **Authentication**
</div>

Engagement API 要求使用 HTTPS，并同时支持 User Context 和 Application-Only OAuth。对 Engagement API 的大多数请求都需要使用 3-Legged OAuth（User Context 的一种特定形式），这意味着你需要使用由你的 Twitter 客户经理为 Engagement API 访问注册并批准的应用的 consumer key 和 secret，以及推文所有者的 access token 和 access token secret 来调用该 endpoint。以下请求需要这种类型的 OAuth：

* 任何对 /totals 的请求，如果要获取 Impressions 和 Engagements 指标类型（这些指标仅限于你拥有的推文）
* 任何对 /28hr 的请求
* 任何对 /historical 的请求

对 Engagement API 的某些请求可以使用 Application-Only OAuth 来执行，也就是说你只需要提供 consumer key 和 secret，或一个 Bearer Token。以下请求可以使用这种类型的 OAuth：

* 任何对 /totals 的请求，如果要获取 Favorites、Replies、Retweets 或 Video Views 指标类型（这些指标可以针对任何推文进行获取）

对于任何请求，你都需要通过 [developer.x.com](https://developer.x.com/en/portal/dashboard) 上提供的应用管理控制台来设置一个 Twitter 应用及其对应的 API key。

请注意：如果你已在 developer.x.com 登录了你的 Twitter 账号，可以通过 [Twitter app dashboard](https://developer.x.com/en/apps) 查看和编辑你现有的 [Twitter apps](/zh/resources/fundamentals/developer-apps)。

设置好应用后，你的 app ID 需要获得你的客户代表的批准，应用才能向 Engagement API 发起请求。Access token 必须用于表示“当前用户”，并且代表其他用户发起的请求必须使用有效 token 进行签名。请确保在构造 OAuth 签名基础字符串之前，已在 URL 和 POST 请求体中对[保留字符进行编码](https://tools.ietf.org/html/rfc3986)。

有关如何开始使用 OAuth 的更多信息，请访问以下链接：

* [OAuth 概览](/zh/resources/fundamentals/authentication)
* [使用 3-Legged OAuth，也称为 User Context](/zh/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow)
* [使用 Application-Only OAuth](/zh/resources/fundamentals/authentication#bearer-token-also-known-as-app-only)

| Status | Text | Description |
| :--- | :--- | :--- |
| 200 | OK  | 请求已成功。 |
| 400 | Bad Request | 通常由于请求中包含无效的 JSON，或请求未发送任何 JSON 负载而返回此响应。 |

<div id="error-messages">
  #### **错误消息**
</div>

在不同场景下，Engagement API 会返回特定场景的错误消息，你的应用程序需要能够妥善处理这些错误。下表列出了这些错误消息的常见示例以及你应如何理解它们。请注意，在许多情况下，Engagement API 会在返回 `200 OK` 响应时，在可用的 `data` 中返回部分结果，并同时包含带有更多信息的特定错误消息。

| Error Message | Description |
| :--- | :--- |
| `"errors":["Your account could not be authenticated. Reason: Access token not found"]` | 请求中的身份验证部分出现错误。“Reason” 字段应提供有助于排查错误的信息。如果你无法自行解决，请将完整错误（包括 “Reason” 字段）发送给我们的支持团队。 |
| `"errors":["1 Tweet ID(s) are unavailable"],"unavailable_tweet_ids": ["TWEET_IDS"]` | 你请求的一个或多个 Tweet ID 已不再可用，通常表示这些推文已被删除，或因其他原因不再公开可见。 |
| `"errors":["Impressions & engagements for tweets older than 90 days (*TIME_PERIOD*) are not supported"],"unsupported_for_impressions_engagements_tweet_ids":[*TWEET_IDS*]` | 你在 `/totals` 端点中请求的一个或多个 Tweet ID 创建时间早于 90 天，因此无法返回其展示量（impressions）或互动量（engagements）指标。 |
| `"errors":["Forbidden to access tweets: *TWEET_IDS*"]` | 由于你用于代表第三方检索 data 的访问令牌权限所限，你请求的一个或多个 Tweet ID 无法访问。 |

概览

`Enterprise`

Account Activity API 使你能够通过 webhooks 订阅与用户账户相关的实时活动。也就是说，你可以通过单一连接，从一个或多个你拥有或已订阅的账户中接收实时帖子、私信以及其他账户事件。

对于在你的 webhook 注册下的每个用户订阅，你将收到以下所有相关活动：

| 活动类型 |     |
| :--- | :--- |
| * 帖子（由用户发布）  <br />    <br />* 帖子删除（由用户执行）<br />* @ 提及（提及该用户）<br />* 回复（发给用户或来自用户）<br />* 转推（由用户转推或转推用户的推文）<br />* 引用推文（由用户发布或引用用户的推文）<br />* 对被引用推文的转推（由用户转推或转推用户的被引用推文）<br />* 喜欢（由用户点赞或点赞用户的推文）<br />* 关注（由用户关注或关注用户）  <br />    <br />* 取消关注（由用户执行） | * 拉黑（由用户执行）<br />* 取消拉黑（由用户执行）<br />* 静音（由用户执行）<br />* 取消静音（由用户执行）<br />* 发送的私信（由用户发送）<br />* 接收的私信（由用户接收）<br />* 正在输入状态指示（发送给用户）<br />* 已读回执（发送给用户）<br />* 订阅撤销（由用户执行） |

**请注意** - 我们不会通过 Account Activity API 提供首页时间线数据。请使用 [GET statuses/home&#95;timeline](https://developer.x.com/en/docs/x-api/v1/tweets/timelines/overview) 来拉取这些数据。

<div id="manage-webhooks-and-subscribed-users">
  ## 管理 webhooks 和已订阅用户
</div>

**⏱ 阅读时间约 10 分钟**

企业版 Account Activity API 会在订阅了你服务的 X 账号发生相关事件时，通过 webhook 向你提供基于 JSON 的消息。X 会将这些活动推送到你注册的 webhook。通过以下步骤，你将学习如何管理 webhooks 和已订阅用户。

你将学习如何注册、查看和删除 webhooks 以及已订阅用户。我们将使用简单的 cURL 命令向各个 API 端点发起请求。cURL 是一个使用 URL 语法来发送或获取请求的命令行工具。

你需要：

* 一个已注册的 X 应用 - *[在此注册](https://developer.x.com/content/developer-twitter/en/apps)*
* 一个 Bearer Token - *[了解更多](/zh/resources/fundamentals/authentication#using-and-generating-an-app-only-bearer-token)*
* 一个通过 Challenge-Response Check (CRC) 的 webhook - *[了解更多](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks)*
* 一个企业账号 - *[在此申请](https://developer.x.com/en/products/x-api/enterprise)*

*在开始之前，我们建议你查看我们的 [GitHub 仓库](https://github.com/xdevplatform/account-activity-dashboard)，其中提供了一个示例 Web 应用程序和辅助脚本，帮助你快速开始使用 X 的 Account Activity API*

<div id="managing-a-webhook">
  #### 管理 webhook：
</div>

使用 webhook 可以通过单一连接订阅某个用户账号相关的实时活动。

<Tabs>
  <Tab title="添加 webhook">
    我们先为给定的应用上下文注册一个新的 webhook URL。

    在保存之前，系统会通过 CRC 请求验证该 URL。注册 webhook 之后，请务必记录下 webhook ID，后续会用到。

    在进行如下修改后，将下面的 cURL 请求复制到命令行中执行：

    * **URL** `<URL>`，例如：`https://yourdomain.com/webhooks/twitter/`

    * **Consumer key（消费者密钥）** `<CONSUMER_KEY>`，例如：`xvz1evFS4wEEPTGEFPHBog`

    * **Access token（访问令牌）** `<ACCESS_TOKEN>`，例如：`370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request POST --url 'https://api.x.com/1.1/account_activity/webhooks.json?url=<URL>' --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>

  <Tab title="查看 webhook">
    我们将运行以下命令，来获取给定应用下所有已注册的 webhook URL 及其状态。

    在进行如下修改后，将下面的 cURL 请求复制到命令行中执行：

    * **Bearer token** `<BEARER_TOKEN>`，例如：`AAAAAAAAAAAA0%2EUifi76ZC9Ub0wn...`

      ```curl --request GET --url https://api.x.com/1.1/account_activity/webhooks.json --header 'authorization: Bearer <BEARER_TOKEN>'
      ```
  </Tab>

  <Tab title="移除 webhook">
    要从指定应用的配置中移除某个 webhook，请在进行如下修改后，将下面的 cURL 请求复制到命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>`，例如：`1234567890`

    * **Consumer key（消费者密钥）** `<CONSUMER_KEY>`，例如：`xvz1evFS4wEEPTGEFPHBog`

    * **Access token（访问令牌）** `<ACCESS_TOKEN>`，例如：`370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```curl --request DELETE --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>.json --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>
</Tabs>

<div id="managing-subscribed-users">
  #### 管理已订阅用户：
</div>

注册 Webhook 之后，你可以将订阅用户添加到 Account Activity API，以开始接收其账号活动。

<Tabs>
  <Tab title="添加订阅">
    首先为用户创建订阅，这样你就可以接收所有事件类型。

    在对以下内容进行相应修改后，将下面的 cURL 请求复制到命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>`，例如 `1234567890`

    * **Consumer key 名称** `<CONSUMER_KEY>`，例如 `xvz1evFS4wEEPTGEFPHBog`

    * **订阅用户的 access token** `<SUBSCRIBING_USER'S_ACCESS_TOKEN>`，例如 `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request POST --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>/subscriptions/all.json --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<SUBSCRIBING_USER'S_ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>

  <Tab title="查看订阅">
    要查看指定 Webhook 的所有活动类型订阅列表，在对以下内容进行相应修改后，将下面的 cURL 请求复制到命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>`，例如 `1234567890`

    * **Bearer token** `<BEARER_TOKEN>`，例如 `AAAAAAAAAAAA0%2EUifi76ZC9Ub0wn...`

      ```
      curl --request GET --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>/subscriptions/all/list.json --header 'authorization: Bearer <BEARER_TOKEN>'
      ```
  </Tab>

  <Tab title="移除订阅">
    停用后，请求用户的所有事件将不再发送到该 Webhook URL。

    要在给定的用户上下文和应用中停用某个订阅，在对以下内容进行相应修改后，将下面的 cURL 请求复制到命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>`，例如 `1234567890`

    * **Consumer key** `<CONSUMER_KEY>`，例如 `xvz1evFS4wEEPTGEFPHBog`

    * **订阅用户的 access token** `<SUBSCRIBING_USER'S_ACCESS_TOKEN>`，例如 `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request DELETE --url https://api.x.com/1.1/account_activity/webhooks/:WEBHOOK_ID/subscriptions/all.json --header 'authorization: OAuth oauth_consumer_key="CONSUMER_KEY", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="SUBSCRIBED_USER'S_ACCESS_TOKEN", oauth_version="1.0"'
      ```
  </Tab>
</Tabs>

做得很好！现在你应该能够管理你的 Webhook 和已订阅用户了。

<div id="getting-started-with-webhooks">
  ## 开始使用 webhooks
</div>

Account Activity API 是一个基于 webhook 的 API，它会将账号事件发送到由你自行开发、部署和托管的 Web 应用。

在你的事件消费应用开始接收 webhook 事件之前，有若干基础配置细节需要先处理。如下所述，你需要创建一个 X 应用、获取 Account Activity API 的访问权限，并开发一个用于消费 webhook 事件的 Web 应用。 

<div id="1-create-a-x-app">
  ### 1. 创建一个 X 应用。
</div>

* 使用已获批准的开发者账号，在 [Developer Console](/zh/resources/fundamentals/developer-portal) 中创建一个 [X app](/zh/resources/fundamentals/developer-apps)。如果你是代表公司创建应用，建议使用公司的 X 账号来创建该应用。要申请开发者账号，请[点击此处](/zh/resources/fundamentals/developer-apps)。
* 在应用页面的 [permissions](/zh/resources/fundamentals/developer-apps#oauth-1-0a-app-permissions) 选项卡中启用 “Read, Write and Access direct messages” 权限。
* 在 &quot;Keys and Access Tokens&quot; 选项卡中，记下你的应用的 Consumer Key（API Key）和 Consumer Token（API Secret）。
* 在同一选项卡中，生成你的应用的 [Access Token and Access Token Secret](/zh/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow)。你需要使用这些 Access Token 来注册你的 webhook URL，X 将把账号事件发送到该 URL。
* 如果你不熟悉 [X Sign-in](/zh/resources/fundamentals/authentication#log-in-with-x) 以及在 X API 中用户上下文是如何工作的，请查看 [Obtaining Access Tokens](https://dev.x.com/webhooks/access-tokens)。当你添加要接收事件的账号时，你需要使用该账号的 access token 为其订阅事件。
* 记下你的应用的数字 ID，可在 [Developer Console](/zh/resources/fundamentals/developer-portal) 的 [&quot;Apps&quot;](/zh/resources/fundamentals/developer-apps) 页面中看到。当你申请 Account Activity API 访问权限时，需要提供这个应用 ID。
   

<div id="2-get-account-activity-api-access">
  ### 2. 获取 Account Activity API 访问权限
</div>

创建 X 应用后，下一步是申请 Account Activity API 访问权限。 

Account Activity API 仅面向企业级（Enterprise）提供，因此你需要通过以下链接提交申请。

<Button href="https://developer.x.com/en/enterprise-application.html">
  申请企业级（Enterprise）访问权限
</Button>

<div id="3-develop-webhook-consumer-app">
  ### 3. 开发 webhook 消费者应用
</div>

在你获得 Account Activity API 访问权限后，你需要开发、部署并托管一个用于接收 X webhook 事件的 Web 应用。 

* 创建一个带有 URL 的 Web 应用，将其作为 webhook 来接收事件。这个 URL 是部署在你服务器上的端点，用于监听传入的 X webhook 事件。 
  * URI *path* 完全由你决定。下面是一个有效示例：https://mydomain.com&#95;/service/listen&#95;

  * 如果你需要从多个来源监听 webhooks，一个常见的模式是：https://mydomain.com/webhook/twitter

  * 注意，指定的 URL 不能包含端口号（https://mydomain.com:5000/NoWorkie）。

* 如我们的 [Securing Webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks) 指南所述，第一步是编写代码来接收 X Challenge Response Check（CRC）GET 请求，并返回格式正确的 JSON 响应。 

* 注册你的 webhook URL。你需要向 `/webhooks.json?url=` 端点发送 POST 请求。当你发出该请求时，X 会向你的 Web 应用发送 CRC 请求。webhook 成功注册后，响应中会包含一个 webhook id。稍后在向 Account Activity API 发出某些请求时需要使用该 webhook id。 

* X 会将账户 webhook 事件发送到你注册的 URL。确保你的 Web 应用支持处理传入事件的 POST 请求。这些事件将以 JSON 编码。有关 webhook JSON 负载示例，请参见[此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-data-object-structure)。

* 当你的 Web 应用准备就绪后，下一步是添加要接收账户活动的账户。在添加（或删除）账户时，你将发出引用账户 id 的 POST 请求。更多信息请参见我们的[订阅添加指南](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#managing-webhooks-and-subscriptions)。

<div id="4-validate-setup">
  ### 4. 验证设置
</div>

* 要验证你的应用和 webhook 是否配置正确，请为你的应用已订阅的某个 X 账号发布的帖子点一次赞。对于这些你已订阅的 X 账号收到的每一次点赞，你都应通过发送到你的 webhook URL 的 POST 请求收到一个 `favorite_events`。
* 请注意，在添加订阅之后，事件开始投递可能最多需要 10 秒钟。

**重要说明**

* 在注册你的 webhook URL 时，你的 web 应用必须使用其 consumer token 和 secret *以及应用所有者的用户访问 token 和 secret* 进行身份验证。 

* 所有传入的 Direct Messages 都将通过 webhooks 投递。所有通过 [POST direct&#95;messages/events/new (message&#95;create)](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/new-event) 发送的 Direct Messages 也将通过 webhooks 投递。这样可以让你的 web 应用获知通过其他客户端发送的 Direct Messages。

* 请注意，每个 webhook 事件都包含一个 for&#95;user&#95;id 用户 ID，用于指明该事件是为哪个订阅投递的。

* 如果有两个用户在同一会话中使用你的 web 应用处理 Direct Messages，你的 webhook 将会收到两个重复事件（每个用户各一个）。你的 web 应用应对此进行处理。 

* 如果有多个 web 应用共享同一个 webhook URL，且同一个用户映射到每个应用，则同一事件会多次发送到你的 webhook（每个 web 应用一次）。

* 不要指望 Quick Reply 响应会紧接在请求之后到达。用户可以选择忽略 Quick Reply 请求，并通过传统 Direct Message 进行回复。用户也可能对其在消息线程中先前尚未回复的某个请求提供 Quick Reply 响应。

<div id="securing-webhooks">
  ## 保护 Webhook 安全
</div>

X 的 webhook API 提供两种方法，用于验证你的 webhook 服务器的安全性：

1. 质询-响应检查使 X 能够验证接收 webhook 事件的 Web 应用的所有权。 
2. 每个 POST 请求中的签名请求头使你能够验证传入的 webhook 确实来自 X。
    

<div id="challenge-response-checks">
  ### 挑战-响应检查
</div>

为了验证您既是应用的所有者又是 webhook URL 的所有者，X 会执行一次 Challenge-Response Check（CRC，挑战-响应检查），这不应与循环冗余校验（cyclic redundancy check）混淆。当发送 CRC 时，X 会向您的 Web 应用发起一个带有 *`crc_token`* 参数的 GET 请求。收到该请求后，您的 Web 应用需要基于 *`crc_token`* 参数和应用的 Consumer Secret（如下所述）构建一个加密的 `response_token`。`response_token` 必须使用 JSON 编码（见下例），并在三秒内返回。成功后，会返回一个 webhook `id`。 

在您注册 webhook URL 时会发送 CRC，因此实现 CRC 响应代码是首要的基础步骤。一旦 webhook 建立，X 将从上次收到成功响应的时间起，大约每 24 小时触发一次 CRC。您的应用也可以在需要时通过使用 webhook `id` 发起 PUT 请求来触发 CRC。在开发 webhook 应用、部署新代码并重启服务之后，触发 CRC 会非常有用。 

应当预期每个传入的 CRC 请求中，*`crc_token`* 都会改变，并且在计算时应将其作为消息、将您的 Consumer Secret 作为密钥来使用。

如果在 3 秒内未返回有效响应，或者响应变得无效，将停止向该注册 webhook 发送事件。

<div id="the-crc-request-will-occur">
  #### CRC 请求将在以下情况下发生：
</div>

* 当注册 webhook URL 时。
* 大约每隔 *一小时* 验证一次你的 webhook URL。
* 你可以通过发送 PUT 请求手动触发 CRC。在开发 webhook 客户端时，你应当在开发 CRC 响应的同时规划手动触发 CRC 的方式。 
   

<div id="response-requirements">
  #### 响应要求：
</div>

* 使用 `crc_token` 和你的应用 Consumer Secret 生成的、经 base64 编码的 HMAC SHA-256 哈希值
* 有效的 response&#95;token，且为 JSON 格式。
* 延迟小于 3 秒。
* HTTP 200 状态码。
   

<div id="language-specific-hmac-libraries">
  #### 各语言的 HMAC 库：
</div>

* [Java/Scala](https://docs.oracle.com/javase/8/docs/api/index.html?javax/crypto/Mac.html)
* [Ruby](http://ruby-doc.org/stdlib-2.1.0/libdoc/openssl/rdoc/OpenSSL/HMAC.html)
* [Node.js](https://nodejs.org/api/crypto.html#crypto_class_hmac)
* [Python](https://docs.python.org/2/library/hmac.html)

<div id="example-response-token-generation-in-python">
  #### 在 Python 中生成示例响应令牌：
</div>

下面定义了一个 Python 2.7 Flask Web 应用中的路由，用于对质询-响应校验作出正确响应。

```
import base64
import hashlib
import hmac
import json


\# Defines a route for the GET request
@app.route('/webhooks/twitter', methods=\['GET'\])
def webhook_challenge():

  # 使用传入的令牌和您的 consumer secret 创建 HMAC SHA-256 哈希
  sha256\_hash\_digest = hmac.new(TWITTER\_CONSUMER\_SECRET, msg=request.args.get('crc_token'), digestmod=hashlib.sha256).digest()

  # 使用 base64 编码的哈希构造响应数据
  response = {
    'response\_token': 'sha256=' + base64.b64encode(sha256\_hash_digest)
  }

  # 返回格式正确的 JSON 响应
  return json.dumps(response)
```

  #### 示例 JSON 响应：
</div>

在按上述方式定义路由后，当你在浏览器中访问 https://your-app-domain/webhooks/twitter?crc&#95;token=foo 时，你的 Web 应用程序应返回与下方类似的响应。

```
{
  "response_token": "sha256=x0mYd8hz2goCTfcNAaMqENy2BFgJJfJOb4PdvTffpwg="
}
```

<div id="optional-signature-header-validation">
  ### 可选的签名请求头验证
</div>

当接收来自 X 的 POST 请求、发送 GET 请求创建 webhook，或发送 GET 请求执行手动 CRC 时，会在请求头中通过 `x-twitter-webhooks-signature` 传递哈希签名。此签名可用于验证数据来源是否为 X。POST 哈希签名以 `sha256=` 开头，表示使用 HMAC SHA-256，基于你的 X 应用 Consumer Secret 和负载计算签名。GET 请求的哈希签名是从查询参数字符串 `crc_token=$token&nonce=$nonce` 计算得到的。

**验证请求的步骤**

1. 使用你的 consumer secret 和传入的请求体负载生成一个哈希值。
2. 将生成的哈希值与经 base64 编码的 `x-twitter-webhooks-signature` 值进行比较。使用类似 [`compare_digest`](https://docs.python.org/2/library/hmac.html) 的方法，以降低遭受计时攻击的风险。

<div id="retries">
  ## 重试
</div>

`Enterprise`

Account Activity API 企业级版本的优势之一是为 webhook 事件提供重试机制。如果未收到表示“成功”的 200 HTTP 响应状态码，X 服务器会启动重试机制，在五分钟内最多重新发送该 webhook 事件三次。此 webhook 事件重试服务有助于在发生网络问题，以及在客户端服务中断或部署期间，提升可靠性并实现事件恢复。
 

<div id="what-are-retries">
  ### 什么是重试？
</div>

当客户端的 Web 应用未对某个账户活动 webhook 事件返回“成功”的 200 响应时，Account Activity API 会启用重试功能。当客户端未确认成功接收到某个事件时，X 会认为该事件未被接收。如果收到非 200 响应、在三秒内未收到响应，或者完全没有收到响应，我们会重试该请求，并在接下来的三秒内保持该请求处于打开状态。这意味着在两次尝试中，你大约有五秒时间来进行响应，以接收我们试图发送到你的 webhook URL 的活动。如果你的服务器没有响应或返回了临时性错误，我们会在五分钟内进行重试。总共会有三次重试尝试来完成验证。这提供了冗余机制和保障，确保你接收到所有 webhook 事件。请注意，启用了重试的订阅会针对其 webhook 上所有已订阅用户的任何活动接收被重试的事件。

如果你在这八次尝试内未完成验证，该活动将不再通过 Account Activity API 提供。 

<div id="retry-timeline">
  ### 重试时间线
</div>

Account Activity API 会在五分钟内最多重试三次，直到收到 200 响应为止。有关更多详细信息，请参阅下表。大约五分钟后，该活动将无法通过 Account Activity API 重新发送。你需要使用 X 的其他端点来收集遗漏的数据。例如，可以使用 [search APIs](/zh/x-api/enterprise-gnip-2.0/fundamentals/search-api) 来检索相关的帖子、转发、引用推文、提及和回复。遗漏的私信可以通过[此端点](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events)来检索。

<div id="retries-timeline">
  #### 重试时间线
</div>

|     |
| :--- |
| 创建活动后，Account Activity API 向 webhook URL 发起 POST 请求，并在三秒内超时。 |
| 在上一次超时结束后三秒，Account Activity API 再次向 webhook URL 发起 POST 请求，并在三秒内超时。 |
| 在上一次超时结束后 27 秒，Account Activity API 再次向 webhook URL 发起 POST 请求，并在三秒内超时。 |
| 在上一次超时结束后 242 秒，Account Activity API 再次向 webhook URL 发起 POST 请求，并在三秒内超时。 |
| 此后，Account Activity API 将停止尝试发送 POST。客户端必须使用其他 X 端点来恢复数据。 |

<div id="account-activity-replay-api">
  ## Account Activity Replay API
</div>

`Enterprise`

Account Activity Replay API 是一种数据恢复工具，可让你检索最长可追溯至五天前的事件。它应在你的 [webhook](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#enterprise-account-activity-api) 服务器错过事件时用于恢复数据——无论是因为断线时间超过了[重试时间窗口](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)，还是在灾难恢复场景中，你需要几天时间才能将系统恢复到正常状态。

Account Activity Replay API 是为任何在一段时间内未能摄取[活动](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity)的场景而开发的。它会将活动投递到与原始实时活动投递所使用的同一个 webhook。此产品是恢复工具，而不是补数工具，这意味着只有在曾尝试过投递这些事件的情况下，它们才会被重放。Account Activity Replay API 无法为订阅创建时间之前的时间段投递事件。

<div id="using-account-activity-replay-api">
  ### 使用 Account Activity Replay API
</div>

如果你的账号已配置 Replay 功能，你可以以类似于调用 Account Activity API 的方式发起请求。需要特别注意的是，你的请求必须指定一个 webhook id 参数，用于指明你希望回放哪个 webhook 的活动。换句话说，一个 Replay 请求会要求 Account Activity Replay API 基于 webhook id 和 application id，从某个开始日期时间到结束日期时间之间检索事件。

请注意，时间需要使用 UTC。系统会通过与该 id 关联的已注册 webhook 投递这些活动，速率最高为每秒 2,500 个事件。同时请记住，同一时间每个 webhook 仅能运行一个 Replay 作业，尽管该 webhook 在指定日期/时间范围内处于活动状态的所有订阅都会被回放。

事件会从指定时间段内的第一个（最早的）整分钟开始投递，并按时间顺序（尽可能严格）持续投递，直到最后一分钟的事件投递完成。此时，Replay 会向该 webhook 投递一个[作业完成事件](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#job-completed-successfully-message)。由于我们按照时间顺序投递活动，如果在起始时间附近几乎没有匹配结果，那么在第一个结果被投递之前很可能会有一段延迟。

<div id="limitations">
  ### 限制
</div>

Replay 旨在作为一种工具，方便地恢复最久可追溯到五天前的活动，但它无法提供早于订阅创建时间的事件。比如说，如果您在三天前添加了一个新的订阅，并运行了一个 Replay 任务，将时间窗口设置为从今天起往前五天，那么您只会收到这三天内该新订阅处于激活状态期间的数据显示。

<div id="data-availability-and-types">
  ### 数据可用性和类型
</div>

Account Activity Replay API 提供的活动在请求发起后的五天内可用，新产生的活动大约会在创建后 10 分钟左右变得可用。你可以在请求中使用 from&#95;date 和 to&#95;date 参数，指定这五天时间窗口内的时间范围进行请求。在开通 Replay 访问权限之前已经投递的事件无法被回放。例如，如果你的账户在 2019 年 6 月 1 日 15:30（UTC）被启用访问 Account Activity Replay API，则你将无法使用 Replay 检索该时间点之前的任何事件。

继续查看 [Account Activity Replay API 参考](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#delete-account-activity-webhooks-webhook-id-subscriptions-all-deprecated)

<div id="differences-migration-considerations">
  ### 差异与迁移注意事项
</div>

**API 格式：** 新的 Account Activity API 与 User Streams 和 Site Streams 的工作方式不同。你需要修改你的 Web 应用，以通过 webhooks 接收数据。你可以在[此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)找到有关 webhooks 的更多信息。

**可用数据：** 你会注意到的另一个关键差异与传递的数据有关。X 不再发送你在 X 上关注的用户（即你的 home timeline）产生的事件。这是一个有意为之的改动，我们目前没有计划在未来改变这一行为。

**可靠性：** 与流式传输不同，webhooks 支持确认交付，并可对未成功到达 webhook URL 的已 POST 活动进行重试。这样可以更好地确保应用接收到所有适用的活动，即使存在短暂的连接中断或停机时间。

### 新功能

Account Activity API 提供了许多新功能，其中最显著的一点是现在通过 webhooks 而不是流式传输来传递数据。与流式传输相比，webhooks 具有很多优势，其中最突出的就是速度和可靠性。API 会在 JSON 事件可用时，以事件的形式将数据发送给你，你不再需要维持一个活动连接或轮询该 endpoint。这样可以减少对冗余机制的需求，并整体提升效率。关于 webhooks 的更多信息，请参阅[技术文档](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)。

<div id="managing-user-subscriptions">
  ### 管理用户订阅
</div>

Account Activity API 允许在单个已注册的 webhook 上创建多个订阅。这样可以通过 webhooks 将多个订阅的用户活动发送到同一位置，其架构与 Site Streams 类似。这意味着，你可以在与订阅配额相关的维度上，将订阅管理与 webhook 连接解耦并分别跟踪。这也使得单个 webhook 能够从只有一个或少量订阅，平滑扩展到成千上万的订阅。

  ### **如何迁移**
</div>

<div id="follow-the-steps-below-to-easily-migrate-from-the-site-streams-api-to-the-account-activity-api">
  ### **请按照以下步骤，将 Site Streams API 轻松迁移到 Account Activity API**
</div>

**步骤 1：选择套餐**

根据你当前使用 User Streams 或 Site Streams 的方式，你应考虑迁移到 Account Activity API 的 enterprise 或 premium 版本。请根据你目前支持的应用程序或已授权用户的数量，按需扩展到所需的规模和可靠性。在决定最适合你需求的套餐时，值得考虑的因素包括：

* 所需的 webhook 数量
* 你的应用当前/预期管理的订阅数/已授权用户数
* 当前的 X 客户端应用程序数量
* 你期望从 X 获得的支持级别（论坛支持或托管的 enterprise 级一对一支持）
* 各套餐的价格

**步骤 2：** **在 Developer Console 中检查你的 X 应用设置**

当前用于 User Streams 或 Site Streams 的 [X app](/zh/resources/fundamentals/developer-apps) 会在 [Developer Console](/zh/resources/fundamentals/developer-portal) 中列在所属用户名下。该 X 应用也可以继续用于 Account Activity API，以保留该应用的已授权用户。你也可以创建一个新的应用，并在需要时让用户重新授权这个新应用。如果你是代表某个企业创建新应用，建议使用企业的 X @handle 账号来创建应用。

* 在你的 X 应用页面的 [permissions](/zh/resources/fundamentals/developer-apps#app-permissions) 选项卡中启用 “Read, Write and Access direct messages”。
  *请注意，更改这些设置不会追溯生效，任何已授权用户都会保留他们在授权时所赋予的权限。如果某个用户尚未授予你读取、写入和私信访问权限，你需要让该用户重新授权你的应用。
* 如果你不熟悉 [X Sign-in](/zh/resources/fundamentals/authentication#log-in-with-x) 以及用户上下文如何与 X API 配合使用，请查看 [Obtaining Access Tokens](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)。
* 在 “Keys and Tokens” 选项卡的底部，为 X 应用所有者生成访问令牌（access tokens）。在同一选项卡中记下你的 Consumer Key、Consumer Secret、Access Token 和 Access Token Secret。你需要使用这些信息来调用 API。
* 使用你的 Consumer Key 和 Consumer Secret 为 [application-only](/zh/resources/fundamentals/authentication#bearer-token-also-known-as-app-only) API 方法生成 Bearer Token。

**步骤 3：设置并配置你的 Webhook**

* 创建一个 Web 应用，并提供一个用于接收事件的 webhook 端点（例如：https://your&#95;domain.com/webhook/twitter 或 https://webhooks.your&#95;domain.com）。

* 在创建 webhook 时，使用你的 Consumer Key、Consumer Secret、Access Token 和 Access Token Secret。注意，你的端点必须返回一个 JSON 响应，其中包含一个 response&#95;token，该值是使用 crc&#95;token 和你的应用 Consumer Secret 生成的、经 base64 编码的 HMAC SHA-256 哈希值。

* 查看 [Securing Webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks) 文档，特别注意 Challenge Response Check (CRC) 的要求。

* 确保你的 webhook 支持用于接收事件的 POST 请求，以及用于 CRC 的 GET 请求。

* 确保你的 webhook 具有较低的延迟（对 POST 请求的响应时间小于 3 秒）

**步骤 4：验证你的 Webhook 设置**

* Webhook API 将通过两种方式保护你的 webhook：

               - 要求进行挑战响应检查，以验证 webhook 所有者即为 Web 应用所有者。

               - 在每个发往你 Web 应用的 POST 请求中添加签名头，供你验证请求来源。

* 为了验证你同时是 Web 应用和 webhook URL 的所有者，X 将执行一次 Challenge Response Check (CRC)，这不要与循环冗余校验（cyclic redundancy check）混淆。
* 一条带有名为 crc&#95;token 参数的 GET 请求会发送到你的 webhook URL。你的端点必须返回一个 JSON 响应，其中包含一个 response&#95;token，该值是使用 crc&#95;token 和你的应用 Consumer Secret 生成的、经 base64 编码的 HMAC SHA-256 哈希值。
* 应预期每个传入的 CRC 请求都会使用不同的 crc&#95;token。crc&#95;token 应作为计算中的消息部分，而你的 Consumer Secret 作为密钥。
* 如果响应无效，将停止向已注册的 webhook 发送事件。

**步骤 5：为每个 User Stream 或 Site Streams 已授权用户创建订阅**

从 User Streams 迁移到 Account Activity API：

* 在 User Streams 上获取当前用户订阅列表
* 使用请求：  *POST account&#95;activity/all/:env&#95;name/subscriptions* 来设置新的 Account Activity API 订阅
* 使用请求：  &#95;GET account&#95;activity/all/:env&#95;name/subscriptions/list
   &#95; 来确认你的 Account Activity API 订阅

从 Site Streams 迁移到 Account Activity API：（使用 control streams）：

* 使用请求：  *GET /1.1/site/c/:stream&#95;id/info.json* 在 Site Streams 上获取当前订阅列表
* 使用请求：  *POST account&#95;activity/all/:env&#95;name/subscriptions* 来设置新的 Account Activity API 订阅
* 使用请求：  &#95;GET account&#95;activity/all/:env&#95;name/subscriptions/list
   &#95; 来确认你的 Account Activity API 订阅

注册 Webhook 并创建订阅（不从 Site Streams 或 User Streams 迁移的场景）

* 使用 [POST webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#enterprise-account-activity-api) 在应用中注册你的 webhook URL，并获取一个 webhook&#95;id。
* 使用返回的 webhook&#95;id，通过 [POST webhooks/:webhook&#95;id/subscriptions/all](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#post-account-activity-webhooks-webhook-id-subscriptions-all) 为用户添加订阅。

<div id="sending-direct-messages">
  ### 发送私信
</div>

[POST direct&#95;messages/events/new](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/new-event) 是发送私信的直接替代端点。此端点最大的不同之处在于，现在所有信息都作为 JSON 放在 POST 请求正文中发送，而不是作为单独的 POST 参数。

**Twurl 请求示例**

```bash
twurl -A 'Content-type: application/json' -X POST /1.1/direct\_messages/events/new.json -d '{"event": {"type": "message\_create", "message\_create": {"target": {"recipient\_id": "4534871"}, "message_data": {"text": "Hello World!"}}}}'
```

请注意，在上述请求中，`Content-Type` 被设置为 `application/json`，而不是 `application/x-www-form-urlencoded`。另外，如果你正在自行构建 OAuth 1.0a 签名，请注意 JSON 请求体不会被包含在签名生成过程中。大多数 OAuth 库已经考虑到了这一点。如果你在使用 [twurl](https://github.com/twitter/twurl)，请确保使用的版本至少为 0.9.3。

<div id="summary">
  #### 摘要
</div>

* 消息定义在 JSON POST 请求体中
* Content-Type 首部必须设置为 application/json
* 在生成 OAuth 签名时，JSON 请求体不会被包含在内。
   

<div id="retrieving-direct-messages">
  ### 检索私信
</div>

现在可以通过一个单个 API 端点来检索历史私信：[`GET direct_messages/events/list`](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events)。这个新端点的一个重要区别在于，它现在会按时间倒序返回已发送和已接收的消息，这有助于你更容易重建一段会话。不过，如果你只想获取已发送或已接收的消息，则需要通过引用 `sender_id` 属性对响应进行后处理。

分页现在基于一个游标值（cursor），而不是某条私信的 ID。每个响应都会返回一个 `cursor` 属性。[`GET direct_messages/events/list`](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events) 将返回最多 30 天内的历史消息，而不受这 30 天内实际消息数量的影响。当不再返回游标时，表示没有更多消息可返回。使用 [`GET direct_messages/events/show`](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/get-event) 访问单条私信的方法保持不变，不过如前所述，返回的私信对象具有不同的结构。

最后，对私信的实时访问现在将通过 webhook 和 [Account Activity API](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity) 来实现。关于从 User Streams 或 Site Streams 迁移的指导，请参阅 Account Activity API 迁移指南以获取更多信息。

<div id="summary">
  #### 摘要
</div>

* 发送和接收的消息现在由同一端点返回。
* 最多可返回最近 30 天内的消息。
* 基于游标的分页。
* 可通过 webhook 实时获取私信。

<div id="deleting-direct-messages">
  ### 删除私信
</div>

现在可以通过 DELETE direct&#95;messages/events/destroy 删除私信。端点基本保持不变，仍然需要提供要删除消息的 ID。关键区别在于，该端点现在需要使用 DELETE 请求，而不是 POST 请求。

已删除私信在官方 X 客户端中的呈现方式保持不变。私信只会从所提供的用户上下文对应的界面中移除，会话中的其他成员仍然可以访问该私信。

<div id="summary">
  #### 摘要
</div>

* 删除私信需要提供 id。
* 新的端点需要使用 DELETE 请求。
* 已删除的私信在官方 X 客户端中的显示方式保持不变。

<div id="general">
  ### 常规
</div>

**使用 Account Activity API 有哪些优势？**

Account Activity API 使用 webhook，这意味着与流式 API 不同，我们不要求你保持一个开放连接来接收我们发送的信息。webhook 也不同于 REST API，因为你不需要每 15 分钟轮询数百次才能获取你关心的数据信息。这样可以提高用户与应用之间的效率，因为它会在事件发生时立即投递数据。

Account Activity API 具有以下优点：

1. **速度**：我们以 X 的速度向你投递数据。
2. **简洁**：我们通过单一的 webhook 连接，投递某个账号的所有事件。API 中投递的活动包括：帖子、@ 提及、回复、转推、引用推文、对引用推文的转推、点赞、发送的私信、接收的私信、关注、拉黑、静音。
3. **可扩展性**：你可以接收所管理账号的全部活动，而不会受到任何事件上限或速率限制的约束。

Account Activity API 提供高级沙盒、高级付费和企业版多种产品形态，因此当你需要为责任相关功能或附加功能扩展更多账号时，可以按需扩容。

要开始使用，请从 [GitHub](https://github.com/xdevplatform/account-activity-dashboard) 下载示例代码片段。
 

**如何判断哪个产品层级最适合我？**

请阅读我们的 [Account Activity API 概览](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity) 页面，了解高级版选项与企业版选项之间的差异。 
 

**高级环境与企业版 webhook 有什么区别？**

没有区别。每个高级环境都会拥有自己的 webhook&#95;id。
 

**我需要为 Account Activity API 准备开发、预发布和生产环境，这可以实现吗？**

可以！在 Account Activity API 的付费层级（付费高级版和企业版）中，你可以注册多个 webhook URL，并通过 API 方法分别管理每个 URL 的订阅。此外，可以将多个客户端应用添加到允许列表（allowlist）中，以保持对你当前已授权用户的授权状态。
 

**你们是否有关于如何设置 Account Activity API 的逐步指南？**

实际上，我们确实有！

* 如果你刚刚开始使用，我们建议你先阅读[使用 webhook 入门](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks) 指南

* 按照我们由 X Dev 提供支持的脚本进行操作： 
  * [Account Activity API dashboard](https://github.com/xdevplatform/account-activity-dashboard)，一个用于展示 webhook 事件的 Node.js Web 应用程序。
  * [SnowBot chatbot](https://github.com/xdevplatform/SnowBotDev)，一个基于 Account Activity 和 Direct Message API 构建的 Ruby Web 应用程序。该代码库包含一个用于帮助你设置 Account Activity API webhook 的[脚本](https://github.com/xdevplatform/SnowBotDev/wiki/Account-Activity-API-setup-script)。
     

**如果我们的系统在一段时间内宕机，有办法恢复数据吗？**

在 Account Activity API 的付费层级（付费高级版和企业版）中，我们的系统会在四小时内[重试](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)多次向你发送活动。如果你的系统在这四小时内始终没有响应，那么该活动将会丢失，你需要在 7 天内使用其他 REST 端点来恢复相应的数据。

我们建议你将不同的 webhook 或环境用作冗余工具，例如使用 [Account Activity Replay API](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-replay-api)，以确保当你的某个系统宕机时，不会错过任何活动。
 

**使用 Account Activity API 时，我需要采用哪种身份验证方式？**

Account Activity API 所需的授权方法会在对应的方法说明中列出，详见 [API 参考页面](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-api-reference-index)。如果你刚刚开始接触 X 的身份验证，我们建议你阅读[本部分](/zh/resources/fundamentals/authentication)。

**什么是 challenge-response check (CRC)？**

Account Activity API 的挑战响应检查是一项安全功能，用于确保 Account Activity API 的活动被发送给正确的开发者。开发者也可以利用它来确保自己接收到的 data 确实来自 X。自上次验证 webhook URL 起，X 会每 24 小时自动向你的 webhook URL 发送一次 CRC。你的系统必须在 3 秒内返回一个有效的响应，才能保持验证状态。 

如需更多详情，请访问我们的页面 [Securing webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks)。
 

**有没有什么情况会立即使我的 webhook URL 失效？**

如果发生以下任一情况，我们会立即将你的 webhook 标记为无效：

* 服务器对 CRC 返回了错误的 token。在这种情况下，我们的系统不会[重试](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)向你发送该活动。
* webhook URL 配置了错误的证书。在这种情况下，我们的系统不会[重试](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)向你发送该活动。
* 你的服务器返回了非 2XX、非 4XXX、非 5XXX 的响应代码。
* 你声明使用 gzip，但实际并未使用。
* 你没有声明使用 gzip，但在响应中实际发送了 gzip。
   

**如果我为彼此有互动的用户订阅了活动，会不会收到重复的活动？**

会。如果你的 Web 应用对用户 A 和用户 B 都有有效订阅，而用户 A 在帖子中提及了用户 B，则会向已注册的 webhook 发送两个 POST 活动。每个活动中都会包含一个名为 &quot;for&#95;user&#95;id&quot; 的标记，用于指示该活动属于哪个订阅。
 

**当我向我的 webhook 发起订阅时，能否将以下端点中的 `/all/` 部分替换为其他 account activity 数据对象，从而限制 API 投递的活动？** `POST https://api.x.com/1.1/account_activity/all/:env_name/subscriptions.json`

不能，目前这是不可能的。就目前而言，我们只提供 `/all/` 产品。
 

**有没有办法在不向用户请求 Direct Messages 权限的情况下使用 Account Activity API？**

目前必须请求 Direct Messages 权限，因为此 API 没有办法“过滤掉” Direct Messages 活动。 
 

**Account Activity API 是否有沙箱版本？**

有，我们提供用于测试的沙箱选项。沙箱选项仅限一个 webhook，最多 15 个订阅。你可以在[我们的文档](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity)中了解更多关于沙箱选项的信息。 

**是否可以使用 Account Activity API 获取提及已订阅用户的帖子所产生的转推？**

很遗憾，这不在此 API 投递的活动范围内。对此，我们建议改用 Streaming API。 
 

**tweet&#95;create&#95;event 表示的可能活动类型有哪些？**

在以下情况下会发送 tweet&#95;create&#95;event 载荷：

如果订阅用户执行了以下任一操作：

* 创建帖子
* 转推
* 回复帖子

如果是其他用户：

* *@提及*订阅用户
* 引用由订阅用户创建的 Tweet 

*注意：Account Activity API 只会在订阅用户会从 X 收到通知并且可以公开看到该事件时投递事件。这意味着，如果被提及的账号（@userA）关注了受保护账号（@userB），那么 UserA 将会收到 UserB 提及他们的通知。如果 UserA 没有关注 UserB（且未被 UserB 批准），UserA 就不会收到通知，因此即使 @userA 具有订阅，也不会通过 AAA 发送 tweet&#95;create&#95;event。*

**如果被屏蔽的用户提及了我订阅的用户，我该如何识别这种情况？**

你会在 JSON 响应的顶层看到一个布尔字段 `user_has_blocked`，其值为 “true” 或 “false”。该字段只会在帖子提及事件中暴露。

**如何将我的应用添加到允许列表中，或检查我的应用是否已在允许列表中？**

要管理你已添加到允许列表、可通过 Enterprise APIs 访问的 [X apps](/zh/resources/fundamentals/developer-apps)，请联系你的客户经理并提供你的 app ID。你可以通过前往 [Developer Console](/zh/resources/fundamentals/developer-portal) 中的 [&quot;Apps&quot;](/zh/resources/fundamentals/developer-apps) 页面来找到你的 app ID。
 

**如果我有 3 个 webhook 的访问权限，是否可以为我注册为企业使用的每个应用分别使用 3 个 webhook？**

webhook 限制是设置在账号级别，而不是应用级别。如果你有 3 个 webhook 的访问权限，并且有 2 个注册为企业使用的应用，你可以在一个应用上使用 2 个 webhook，在另一个应用上使用第 3 个 webhook，但不能在每个应用上都使用 3 个 webhook。 

**我可以指定要通过 Account Activity Replay API 重新投递的事件类型吗？**

无法指定要重放的事件类型。在指定的日期和时间窗口内投递的所有事件都会被重放。 

**如果我的应用未能摄取某个 Account Activity Replay API 事件，会有重试吗？**

不会，不会进行任何重试。如果应用未能摄取由 Account Activity Replay API 发送的事件，你可以针对同一时间段再次提交 Replay 作业，以尝试重新投递任何错过的 Replay 事件。 

**当我收到部分成功的完成事件时应该怎么做？**

我们建议记录已接收事件的时间戳，然后为漏掉的事件再次请求一个 Replay 作业。 

**我一次可以运行多少个 Account Activity Replay API 作业？**

每个 webhook 同一时间只能运行一个 Account Activity Replay API 作业。 

**在 Account Activity Replay API 将事件投递到我的 webhook 时，我如何区分 Replay 事件和实时生产事件？**

由于 Account Activity Replay API 始终会投递过去的事件，因此可以根据事件的时间戳将其与实时生产事件区分开来。 

**在我的应用丢弃或错过某个活动后，我最早多久可以使用 Account Activity Replay API 重新投递该活动？**

活动在创建约 10 分钟后即可用于重新投递。

<div id="code-32">
  #### 代码 32
</div>

此错误通常意味着你在指定的请求、headers、authorization 或 URL 中有某些内容格式不正确。这不是 Account Activity API 错误，而是授权错误，X 未获得正确的 OAuth 配置或 URL。

* **Enterprise** - 确保你正在使用的 consumer key 和 access token 属于已注册用于 Enterprise 产品的 [X app](/zh/resources/fundamentals/developer-apps)。如果你没有 consumer key 和 access token，或需要将你的 X app 添加到 allowlist，请联系你的客户经理。 

* 如果在用户上下文下进行身份验证，请确保你已使用正确的 `oauth nonce`、`oauth_signature` 和 `oauth_timestamp` [正确授权了请求](/zh/resources/fundamentals/authentication#authorizing-a-request)。

* 确保你的 access token 具有适当的权限级别。
  * 在 [app dashboard](/zh/resources/fundamentals/developer-apps) 的“Keys and tokens”标签页中，请确认你的 access token 具有“Read, write, and direct messages”[权限级别](/zh/resources/fundamentals/developer-apps#app-permissions)。 
  * 如果 token 的权限级别低于此，请进入“Permissions”标签页，将访问权限调整为“Read, write, and direct messages”，然后在“Keys and tokens”标签页重新生成你的 access token 和 secret。

* 确保你的 URL 格式正确。
  * 请注意，`:env_name` 区分大小写。
     

<div id="code-200-forbidden">
  #### Code 200 - 禁止访问
</div>

* **Premium** - 在尝试向 API 发送请求之前，请确保你已经拥有一个通过审核的[开发者账号](/zh/resources/fundamentals/developer-portal)。你还必须在请求中使用正确的 :env&#95;name，你可以在 [dev environments](/zh/resources/fundamentals/developer-portal) 页面进行配置。

* **Enterprise** - 请确保你的客户经理已为你开通 Account Activity API 的访问权限。

* 请确保你已正确配置 URI。如果你在请求中输入了不正确的 URI，也会触发此错误。
   

<div id="code-214-webhook-url-does-not-meet-the-requirements">
  #### 代码 214 - Webhook URL 不符合要求。
</div>

* 请确保你使用的是 HTTPS。
* 你的 webhook URL 可能格式不正确。
* 请参见 [Getting started with webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks) 页面中的 [Develop webhook consumer app](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#3-develop-webhook-consumer-app) 部分，了解如何设置 webhook URL 的更多信息。
   

<div id="code-214-high-latency-on-crc-get-request-your-webhook-should-respond-in-less-than-3-seconds">
  #### Code 214 - CRC GET 请求延迟过高。你的 webhook 必须在 3 秒内作出响应。
</div>

* 这意味着你的服务器响应过慢。请确保在 3 秒内对 CRC 请求作出响应。
   

<div id="code-214-non-200-response-code-during-crc-get-request-ie-404-500-etc">
  #### Code 214 - 在 CRC GET 请求期间返回非 200 响应状态码（例如 404、500 等）。
</div>

* 您的服务器已宕机。请确保服务器正在正常运行。
   

<div id="code-214-too-many-resources-already-created">
  #### Code 214 - 已创建的资源过多。
</div>

* **Enterprise** - 你已用尽所有的 webhooks。对每个已注册的应用使用 [GET webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#get-account-activity-webhooks) 端点，以确定你的 webhooks 的分布情况。 

<div id="code-261-application-cannot-perform-write-actions">
  #### Code 261 - 应用程序无法执行写入操作。
</div>

* 你在 API 中使用的 app 没有为其 access token 和 access token secret 设置正确的[权限级别](/zh/resources/fundamentals/developer-apps#app-permissions)。请前往 [X apps](/zh/resources/fundamentals/developer-apps) 仪表板中的“Keys and tokens”选项卡，检查分配给你的 access token 和 access token secret 的权限级别。如果权限级别不是 “Read, write and Direct Messages”，则需要在 “Permission” 选项卡下调整设置，并重新生成你的 access token 和 access token secret 以应用新设置。
* 或者，你正在尝试使用仅应用程序身份验证（app-only authentication）来注册 webhook，但这是不支持的。请改为使用用户上下文进行认证，如在为 [Enterprise Account Activity API](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#post-account-activity-webhooks) 注册 webhook 的 API 参考部分中所述。

<div id="replay-api">
  ### Replay API
</div>

**POST /1.1/account&#95;activity/replay/webhooks/:webhook&#95;id/subscriptions/all.json [¶](#post-1-1-account-activity-replay-webhooks-webhook-id-subscriptions-all-json- "Permalink to this headline")**

提交请求，根据请求中指定的日期和时间窗口，从过去最多五天内的所有订阅中检索活动。如果你的 webhook 具有活跃的用户订阅，你也会同时接收到这些事件。注意：在投递回放事件之前，我们会执行 CRC。

|     |     |
| :--- | :--- |
| **Request Method** | HTTP POST |
| **URL** | /1.1/account&#95;activity/replay/webhooks/:webhook&#95;id/subscriptions/all.json?from&#95;date=yyyymmddhhmm&amp;to&#95;date=yyyymmddhhmm |
| **Response Format** | JSON |
| **Requires Authentication** | 是（仅应用 - Bearer Token） |
| **Rate Limit** | 每 15 分钟 5 个请求。目前对可请求的回放任务数量没有上限。 |
| **from&#95;date** | 将提供事件的最早（起始）UTC 时间戳，必须为 `yyyymmddhhmm` 格式。时间戳以分钟为粒度且为包含关系（例如 12:00 包含第 00 分钟）。有效时间必须在最近 5 天内（UTC 时间），且不得晚于当前时间点前 31 分钟。建议 from&#95;date 和 to&#95;date 之间的时间范围应在约 2 小时以内。 |
| **to&#95;date** | 将提供事件的最晚（结束）UTC 时间戳，必须为 `yyyymmddhhmm` 格式。时间戳以分钟为粒度且为排他（不包含）关系（例如 12:30 不包含该小时的第 30 分钟）。有效时间必须在最近 5 天内（UTC 时间），且不得晚于当前时间点前 10 分钟。 |

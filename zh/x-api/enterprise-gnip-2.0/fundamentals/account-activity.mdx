Overview

`Enterprise`

Account Activity API 使你能够通过 webhooks 订阅与用户账户相关的实时活动。也就是说，你可以通过单一连接，从一个或多个你拥有或已订阅的账户接收实时帖子、私信以及其他账户事件。

对于在你的 webhook 注册中的每个用户订阅，你将收到以下所有相关活动：

| Activity types |     |
| :--- | :--- |
| * 帖子（由用户发布）  <br />    <br />* 删除帖子（由用户执行）<br />* @ 提及（提及该用户）<br />* 回复（发给用户或来自用户）<br />* 转推（由用户转推或转推用户的推文）<br />* 引用推文（由用户引用或引用用户的推文）<br />* 被引用推文的转推（由用户执行或针对用户）<br />* 点赞（由用户点赞或点赞用户的推文）<br />* 关注（由用户关注或关注用户）  <br />    <br />* 取消关注（由用户执行） | * 拉黑（由用户执行）<br />* 取消拉黑（由用户执行）<br />* 静音（由用户执行）<br />* 取消静音（由用户执行）<br />* 发送的私信（由用户发送）<br />* 接收的私信（由用户接收）<br />* 正在输入指示（发送给用户）<br />* 已读回执（发送给用户）<br />* 撤销订阅（由用户执行） |

**请注意** - 我们不会通过 Account Activity API 提供主页时间线数据。请使用 [GET statuses/home&#95;timeline](https://developer.x.com/en/docs/x-api/v1/tweets/timelines/overview) 来获取这些数据。

<div id="manage-webhooks-and-subscribed-users">
  ## 管理 webhooks 和已订阅用户
</div>

**⏱ 阅读时间约 10 分钟**

企业版 Account Activity API 会在与订阅了你服务的 X 账户相关的事件发生时，通过 webhook 向你提供 JSON 消息。X 会将这些活动发送到你注册的 webhook。通过以下步骤，你将学习如何管理 webhooks 和已订阅用户。

你将学习如何注册、查看和删除 webhooks 以及已订阅用户。我们将使用简单的 cURL 命令向各个 API 端点发起请求。cURL 是一个使用 URL 语法来发送或获取请求的命令行工具。

你需要：

* 一个已注册的 X 应用 - *[在此注册](https://developer.x.com/content/developer-twitter/en/apps)*
* 一个 Bearer Token - *[了解更多](/zh/resources/fundamentals/authentication#using-and-generating-an-app-only-bearer-token)*
* 一个能通过挑战-响应检查（Challenge-Response Check，CRC）的 webhook - *[了解更多](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks)*
* 一个企业账号 - *[在此申请](https://developer.x.com/en/products/x-api/enterprise)*

*在开始之前，我们建议你查看我们的 [GitHub 仓库](https://github.com/xdevplatform/account-activity-dashboard)，其中提供了一个示例 Web 应用程序和辅助脚本，帮助你开始使用 X 的 Account Activity API。*

<div id="managing-a-webhook">
  #### 管理 webhook：
</div>

使用 webhook，可以通过单一连接订阅与某个用户帐户相关的实时活动。 

<Tabs>
  <Tab title="添加 webhook">
    先为给定的应用上下文注册一个新的 webhook URL。

    在保存之前，该 URL 会通过 CRC 请求进行验证。注册 webhook 后，请务必记录 webhook ID，因为后续还会用到。

    在将下面的占位符替换为你的实际值之后，将以下 cURL 请求复制到命令行中执行：

    * **URL** `<URL>` 例如：`https://yourdomain.com/webhooks/twitter/`

    * **Consumer key** `<CONSUMER_KEY>` 例如：`xvz1evFS4wEEPTGEFPHBog`

    * **Access token** `<ACCESS_TOKEN>` 例如：  `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request POST --url 'https://api.x.com/1.1/account_activity/webhooks.json?url=<URL>' --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>

  <Tab title="查看 webhook">
    运行以下命令，以获取给定应用下所有已注册的 webhook URL 及其状态。

    在将下面的占位符替换为你的实际值之后，将以下 cURL 请求复制到命令行中执行：

    * **Bearer Token** `<BEARER_TOKEN>` 例如：`AAAAAAAAAAAA0%2EUifi76ZC9Ub0wn...`

      ```curl --request GET --url https://api.x.com/1.1/account_activity/webhooks.json --header 'authorization: Bearer <BEARER_TOKEN>'
      ```
  </Tab>

  <Tab title="移除 webhook">
    若要从指定应用的配置中移除某个 webhook，在将下面的占位符替换为你的实际值之后，将以下 cURL 请求复制到命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>` 例如：`1234567890`

    * **Consumer key** `<CONSUMER_KEY>` 例如：`xvz1evFS4wEEPTGEFPHBog`

    * **Access token** `<ACCESS_TOKEN>` 例如：  `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```curl --request DELETE --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>.json --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>
</Tabs>

<div id="managing-subscribed-users">
  #### 管理已订阅用户：
</div>

注册 Webhook 之后，你可以在 Account Activity API 中添加一个已订阅用户，以开始接收其账号活动。

<Tabs>
  <Tab title="添加订阅">
    我们先从为用户添加订阅开始，这样你就能接收所有类型的事件。

    在进行以下更改后，将下面的 cURL 请求复制到命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>` 如 `1234567890`

    * **Consumer key 名称** `<CONSUMER_KEY>` 如 `xvz1evFS4wEEPTGEFPHBog`

    * **订阅用户的 access token** `<SUBSCRIBING_USER'S_ACCESS_TOKEN>` 如 `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request POST --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>/subscriptions/all.json --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<SUBSCRIBING_USER'S_ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>

  <Tab title="查看订阅">
    若要查看指定 Webhook 的所有活动类型订阅列表，在进行以下更改后，将下面的 cURL 请求复制到命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>` 如 `1234567890`

    * **Bearer Token** `<BEARER_TOKEN>` 如 `AAAAAAAAAAAA0%2EUifi76ZC9Ub0wn...`

      ```
      curl --request GET --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>/subscriptions/all/list.json --header 'authorization: Bearer <BEARER_TOKEN>'
      ```
  </Tab>

  <Tab title="移除订阅">
    停用后，请求用户的所有事件将不再发送到该 Webhook URL。

    要在给定的用户上下文和应用下停用订阅，在进行以下更改后，将下面的 cURL 请求复制到命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>` 如 `1234567890`

    * **Consumer key** `<CONSUMER_KEY>` 如 `xvz1evFS4wEEPTGEFPHBog`

    * **订阅用户的 access token** `<SUBSCRIBING_USER'S_ACCESS_TOKEN>` 如 `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request DELETE --url https://api.x.com/1.1/account_activity/webhooks/:WEBHOOK_ID/subscriptions/all.json --header 'authorization: OAuth oauth_consumer_key="CONSUMER_KEY", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="SUBSCRIBED_USER'S_ACCESS_TOKEN", oauth_version="1.0"'
      ```
  </Tab>
</Tabs>

做得很好！你现在应该已经能够管理你的 Webhook 和已订阅用户了。

<div id="getting-started-with-webhooks">
  ## Webhook 入门
</div>

Account Activity API 是一个基于 webhook 的 API，会将账户事件发送到你自行开发、部署和托管的 web 应用。 

在你的事件消费应用开始接收 webhook 事件之前，需要先处理若干基础的“管线”细节。如下所述，你需要创建一个 X 应用、获取 Account Activity API 的访问权限，并开发一个用于消费 webhook 事件的 web 应用。 

<div id="1-create-a-x-app">
  ### 1. 创建一个 X 应用。
</div>

* 使用已获批准的开发者账号，通过[开发者控制台](/zh/resources/fundamentals/developer-portal)创建一个 [X 应用](/zh/resources/fundamentals/developer-apps)。如果你是代表公司创建应用，建议使用公司的 X 账号来创建该应用。要申请开发者账号，请[点击这里](/zh/resources/fundamentals/developer-apps)。
* 在应用页面的 [permissions](/zh/resources/fundamentals/developer-apps#oauth-1-0a-app-permissions) 选项卡中启用“Read, Write and Access direct messages”（读、写和访问私信）权限。
* 在“Keys and Access Tokens”选项卡中，记下你应用的 Consumer Key（API Key）和 Consumer Token（API Secret）。
* 在同一选项卡中，生成你应用的 [Access Token 和 Access Token Secret](/zh/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow)。你需要这些 Access Tokens 来注册你的 webhook URL，X 会将账号事件发送到该地址。
* 如果你还不熟悉 [X Sign-in](/zh/resources/fundamentals/authentication#log-in-with-x) 以及用户上下文在 X API 中的工作方式，请查看 [Obtaining Access Tokens](https://dev.x.com/webhooks/access-tokens)。当你添加要接收事件的账号时，你将使用该账号的 access tokens 为其订阅事件。
* 记下你应用的数字 ID，可在[开发者控制台](/zh/resources/fundamentals/developer-portal)的 [&quot;Apps&quot;](/zh/resources/fundamentals/developer-apps) 页面中查看。当你申请 Account Activity API 访问权限时，需要提供这个应用 ID。
   

<div id="2-get-account-activity-api-access">
  ### 2. 获取 Account Activity API 访问权限
</div>

创建 X 应用后，下一步是申请 Account Activity API 的访问权限。 

Account Activity API 仅在 Enterprise 级别提供，因此你需要通过下面的链接提交申请。

<Button href="https://developer.x.com/en/enterprise-application.html">
  申请 Enterprise 访问权限
</Button>

<div id="3-develop-webhook-consumer-app">
  ### 3. 开发 webhook 消费端应用
</div>

在你获得 Account Activity API 访问权限后，需要开发、部署并托管一个用于接收 X webhook 事件的 web 应用。 

* 创建一个带有 URL 的 web 应用，将其作为你的 webhook 来接收事件。这个 URL 是部署在你服务器上的端点，用于监听来自 X 的入站 webhook 事件。 
  * URI 的 *path* 完全由你决定。如下示例是有效的：https://mydomain.com&#95;/service/listen&#95;

  * 如果你要同时监听来自多种来源的 webhooks，一个常见模式是：https://mydomain.com/webhook/twitter

  * 请注意，指定的 URL 不能包含端口号（https://mydomain.com:5000/NoWorkie）。

* 如我们的 [Securing Webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks) 指南所述，第一步是编写代码来接收 X Challenge Response Check (CRC) 的 GET 请求，并返回格式正确的 JSON 响应。 

* 注册你的 webhook URL。你将向 /webhooks.json?url= 这个端点发送一个 POST 请求。当你发起该请求时，X 会向你的 web 应用发出 CRC 请求。当 webhook 成功注册后，响应中会包含一个 webhook id。稍后在向 Account Activity API 发起某些请求时会需要这个 webhook id。 

* X 会将账号的 webhook 事件发送到你注册的 URL。确保你的 web 应用支持针对入站事件的 POST 请求。这些事件将以 JSON 编码。参见[此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-data-object-structure)查看 webhook JSON 负载示例。

* 当你的 web 应用准备就绪后，下一步就是添加账号以接收其活动。在添加（或删除）账号时，你将发起引用账号 id 的 POST 请求。更多信息请参阅我们的[添加订阅指南](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#managing-webhooks-and-subscriptions)。

<div id="4-validate-setup">
  ### 4. 验证设置
</div>

* 为验证你的应用和 webhook 是否已正确配置，可以为你的应用已订阅的某个 X 账号发布的帖子点“喜欢”。对于订阅者收到的每次“喜欢”，你都应该通过发送到你的 webhook URL 的 POST 请求收到一个 `favorite_events` 事件。
* 请注意，在添加订阅后，开始投递事件可能最多需要 10 秒时间。

**重要说明**

* 在注册你的 webhook URL 时，你的 Web 应用必须使用其消费者 token 和 secret *以及应用所有者的用户访问 token 和 secret* 进行认证。 

* 所有接收的私信（Direct Messages）都会通过 webhooks 投递。所有通过 [POST direct&#95;messages/events/new (message&#95;create)](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/new-event) 发送的私信也会通过 webhooks 投递。这样可以让你的 Web 应用获知通过其他客户端发送的私信。

* 请注意，每个 webhook 事件都包含一个 for&#95;user&#95;id 用户 ID，用于指示该事件是为哪个订阅投递的。

* 如果有两个用户在同一会话中使用你的 Web 应用收发私信，你的 webhook 将会收到两条重复事件（每个用户各一条）。你的 Web 应用应当考虑这一点。 

* 如果你有多个 Web 应用共享同一个 webhook URL，且同一个用户被映射到每个应用，那么同一事件会多次发送到你的 webhook（每个 Web 应用各一次）。

* 在某些情况下，你的 webhook 可能会收到重复事件。你的 webhook 应用应当能够容忍这一点，并按事件 ID 去重。

* 不要期望 Quick Reply 响应会紧接在请求之后到达。用户可以选择忽略 Quick Reply 请求，并通过传统私信进行回复。用户也可能会对先前在消息线程中尚未回复的请求发送 Quick Reply 响应。

<div id="securing-webhooks">
  ## 保障 webhook 安全
</div>

X 基于 webhook 的 API 提供两种方法来确认你的 webhook 服务器的安全性：

1. 质询-响应检查用于让 X 验证接收 webhook 事件的 Web 应用的所有权。 
2. 每个 POST 请求中的签名请求头用于让你验证传入的 webhook 是否确实来自 X。
    

<div id="challenge-response-checks">
  ### 挑战–响应检查
</div>

为了验证你既是应用的所有者，也是 webhook URL 的所有者，X 会执行一次挑战–响应检查（CRC），不要将其与循环冗余校验（cyclic redundancy check）混淆。当发送 CRC 时，X 会向你的 Web 应用发起一个带有 *`crc_token`* 参数的 GET 请求。收到该请求后，你的 Web 应用需要基于 *`crc_token`* 参数和应用的 Consumer Secret（详见下文）构建一个加密的 `response_token`。`response_token` 必须使用 JSON 编码（参见下方示例），并在三秒内返回。成功时，会返回一个 webhook `id`。 

在你注册 webhook URL 时会发送一次 CRC，因此实现 CRC 响应代码是至关重要的第一步。一旦 webhook 建立，X 将从上次收到成功响应的时间起，大约每 24 小时触发一次 CRC。你的应用也可以在需要时通过使用 webhook `id` 发起 PUT 请求来触发 CRC。在开发 webhook 应用、部署新代码以及重启服务之后，触发 CRC 会非常有用。 

应当预期每个传入的 CRC 请求都会携带变化的 *`crc_token`*，并且在计算中应将其作为消息、将 Consumer Secret 作为密钥来使用。

如果在 3 秒内未返回响应，或者响应被判定为无效，将不再向已注册的 webhook 发送事件。

<div id="the-crc-request-will-occur">
  #### CRC 请求会在以下情况下触发：
</div>

* 在注册 webhook URL 时。
* 大约每隔 *一小时* 对你的 webhook URL 进行一次验证。
* 你可以通过发出 PUT 请求手动触发 CRC。当你开发 webhook 客户端时，应计划在实现 CRC 响应的同时手动触发 CRC。 
   

<div id="response-requirements">
  #### 响应要求：
</div>

* 使用 `crc_token` 和你的应用 Consumer Secret 生成的、经 Base64 编码的 HMAC SHA-256 哈希值
* 有效的 response&#95;token，并采用 JSON 格式。
* 延迟低于 3 秒。
* HTTP 状态码 200。
   

<div id="language-specific-hmac-libraries">
  #### 按语言划分的 HMAC 库：
</div>

* [Java/Scala](https://docs.oracle.com/javase/8/docs/api/index.html?javax/crypto/Mac.html)
* [Ruby](http://ruby-doc.org/stdlib-2.1.0/libdoc/openssl/rdoc/OpenSSL/HMAC.html)
* [Node.js](https://nodejs.org/api/crypto.html#crypto_class_hmac)
* [Python](https://docs.python.org/2/library/hmac.html)

<div id="example-response-token-generation-in-python">
  #### 使用 Python 生成响应令牌的示例：
</div>

下面的示例在一个 Python 2.7 Flask Web 应用程序中定义了一个路由，用于正确处理 challenge-response 检查。

```
import base64
import hashlib
import hmac
import json


\# Defines a route for the GET request
@app.route('/webhooks/twitter', methods=\['GET'\])
def webhook_challenge():

  # 根据传入的令牌和您的 consumer secret 创建 HMAC SHA-256 哈希
  sha256\_hash\_digest = hmac.new(TWITTER\_CONSUMER\_SECRET, msg=request.args.get('crc_token'), digestmod=hashlib.sha256).digest()

  # 使用 base64 编码的哈希构建响应数据
  response = {
    'response\_token': 'sha256=' + base64.b64encode(sha256\_hash_digest)
  }

  # 返回格式正确的 JSON 响应
  return json.dumps(response)
```

<div id="example-json-response">
  #### 示例 JSON 响应：
</div>

按上述方式定义路由后，当你在浏览器中访问 https://your-app-domain/webhooks/twitter?crc&#95;token=foo 时，你的 Web 应用程序应该返回与下方类似的响应。

```
{
  "response_token": "sha256=x0mYd8hz2goCTfcNAaMqENy2BFgJJfJOb4PdvTffpwg="
}
```

<div id="optional-signature-header-validation">
  ### 可选的签名请求头验证
</div>

当从 X 接收一个 POST 请求、发送一个用于创建 webhook 的 GET 请求，或发送一个用于执行手动 CRC 的 GET 请求时，会在请求头中通过 `x-twitter-webhooks-signature` 传递哈希签名。该签名可用于验证数据来源是否为 X。POST 哈希签名以 `sha256=` 开头，表示使用 HMAC SHA-256 对你的 X App Consumer Secret 和请求负载进行加密生成。GET 哈希是基于查询参数字符串 `crc_token=$token&nonce=$nonce` 计算得到的。 

**验证请求的步骤**

1. 使用你的 consumer secret 和传入的请求正文（payload body）创建一个哈希值。
2. 将生成的哈希值与经过 base64 编码的 `x-twitter-webhooks-signature` 值进行比较。使用类似 [compare&#95;digest](https://docs.python.org/2/library/hmac.html) 的方法，以降低遭受计时攻击的风险。

<div id="retries">
  ## 重试
</div>

`Enterprise`

Account Activity API 企业版的优势之一，是为 webhook 事件提供重试机制。如果未收到表示成功的 200 HTTP 响应状态码，X 服务器会启动重试机制，在五分钟内最多重新发送该 webhook 事件三次。此 webhook 事件重试服务有助于在发生网络问题以及客户端服务中断或进行部署期间，提升可靠性并实现事件恢复。
 

<div id="what-are-retries">
  ### 什么是重试？
</div>

当客户端的 Web 应用在账户活动 webhook 事件中未返回“成功”的 200 响应时，Account Activity API 会提供重试机制。如果客户端未确认成功接收事件，X 会认为该事件未被接收。如果收到的是非 200 响应、在三秒内未收到响应，或者完全未收到任何响应，我们会重试该请求，并将该请求的连接保持开放三秒钟。这意味着，在两次尝试中，你总共有大约五秒的时间来返回响应，从而接收我们尝试发送到你的 webhook URL 的活动。如果你的服务器未响应或返回了临时错误，我们会在五分钟内进行重试。总共会有三次重试尝试来完成验证确认。这样可以提供冗余和保障，确保你接收到所有 webhook 事件。请注意，启用重试的订阅会在其 webhook 上，为所有已订阅用户的任何/所有活动接收到重试后的事件。

如果你在这八次尝试内仍未确认验证，该活动将不再通过 Account Activity API 提供。 

<div id="retry-timeline">
  ### 重试时间线
</div>

Account Activity API 会在五分钟内最多重试三次，直到收到 200 响应为止。有关更多详细信息，请参阅下表。约五分钟后，无法再通过 Account Activity API 重新发送该活动。你需要使用其他 X 端点来收集遗漏的数据。例如，可以使用 [search APIs](/zh/x-api/enterprise-gnip-2.0/fundamentals/search-api) 来检索相关的帖子、转推、引用推文、提及和回复。遗漏的私信可以通过 [此端点](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events) 进行检索。

<div id="retries-timeline">
  #### 重试时间线
</div>

|     |
| :--- |
| 活动创建后，Account Activity API 向 webhook URL 发起 POST 请求，并在三秒内超时。 |
| 在上一次超时结束后等待三秒，然后 Account Activity API 再次向 webhook URL 发起 POST 请求，并在三秒内超时。 |
| 在上一次超时结束后等待 27 秒，然后 Account Activity API 再次向 webhook URL 发起 POST 请求，并在三秒内超时。 |
| 在上一次超时结束后等待 242 秒，然后 Account Activity API 再次向 webhook URL 发起 POST 请求，并在三秒内超时。 |
| 之后，Account Activity API 将停止尝试发送 POST。客户端必须使用其他 X 端点来恢复数据。 |

<div id="account-activity-replay-api">
  ## Account Activity Replay API
</div>

`Enterprise`

Account Activity Replay API 是一款数据恢复工具，可让你检索最久可追溯到 5 天前的事件。它应在你的 [webhook](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#enterprise-account-activity-api) 服务器遗漏事件的场景下用于恢复数据——无论是由于断连时间超过了[重试窗口](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)，还是在灾难恢复的场景中，你需要几天时间将系统恢复到正常状态。

Account Activity Replay API 适用于在一段时间内未能摄取[活动](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity)的任何场景。它会将活动投递到与原始实时活动投递相同的 webhook。该产品是恢复工具，而不是回填工具，这意味着只有在之前尝试过投递的事件才会被重放。Account Activity Replay API 无法投递早于订阅创建时间的时间段内的事件。

<div id="using-account-activity-replay-api">
  ### 使用 Account Activity Replay API
</div>

如果你的账户已配置 Replay 功能，你可以以与调用 Account Activity API 类似的方式发起请求。需要注意的是，请求必须指定一个 webhook id 参数，以表明你希望重放哪个 webhook 的活动。换句话说，一个 Replay 请求是要求 Account Activity Replay API 根据 webhook id 和 application id，在指定的开始日期时间与结束日期时间之间检索事件。

请注意，需要使用 UTC 时间。这些活动会通过与该 id 关联的已注册 webhook 进行投递，速率最高可达每秒 2,500 个事件。还要记住，同一时间每个 webhook 仅能运行一个 Replay 作业，但在该 webhook 上在所指定日期/时间范围内处于活动状态的所有订阅都会被重放。

事件的投递会从所指定时间范围内的第一分钟（最早的一分钟）开始，按时间顺序持续进行（在尽可能范围内），直到最后一分钟的事件被投递完毕。届时，Replay 将向该 webhook 发送一个[作业完成事件](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#job-completed-successfully-message)。由于我们按时间顺序投递活动，如果在开始时间附近几乎没有匹配结果，那么在首次结果被投递之前，很可能会有一段等待时间。

<div id="limitations">
  ### 限制
</div>

Replay 旨在作为一种工具，帮助你轻松回放最久可追溯到 5 天前的活动，但它不会提供订阅创建时间之前的事件。举例来说，如果你在 3 天前新增了一个订阅，并运行了一个时间范围为从今天起向前追溯 5 天的 Replay 任务，你只能收到该新订阅这 3 天内处于活动状态时的数据。

<div id="data-availability-and-types">
  ### 数据可用性和类型
</div>

Account Activity Replay API 中的活动在你发起请求之后的五天内可用，新的数据通常会在某个活动创建后大约 10 分钟变为可用。你可以在这五天的时间窗口内，在请求中通过 `from_date` 和 `to_date` 参数指定一个时间范围来发起请求。在开通 Replay 访问权限之前已经投递的事件无法被重新回放。举例来说，如果你的账户在 2019 年 6 月 1 日 UTC 时间下午 3:30 被启用访问 Account Activity Replay API，那么你将无法通过 Replay 来检索该日期和时间之前的任何事件。

继续查看 [Account Activity Replay API 参考](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#delete-account-activity-webhooks-webhook-id-subscriptions-all-deprecated)

<div id="differences-migration-considerations">
  ### 差异与迁移注意事项
</div>

**API 格式：** 新的 Account Activity API 与 User Streams 和 Site Streams 的运行方式不同。你需要修改你的 Web 应用，以通过 webhooks 接收数据。你可以在[此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)找到有关 webhooks 的更多信息。

**可用数据：** 你会注意到的另一项关键差异与所传输的数据有关。X 将不再发送来自你在 X 上关注的用户（即你的主页时间线）的事件。这是有意的变更，我们也没有计划在未来对此进行调整。

**可靠性：** 与流式传输不同，webhooks 可以确认投递结果，并提供在通过 POST 发送的活动未到达 webhook URL 时进行重试的选项。即便存在短暂的断线或停机时间，这也能进一步确保应用接收到所有相关活动。

<div id="new-features">
  ### 新功能
</div>

Account Activity API 提供了许多新功能，其中最重要的一点是，现在通过 webhooks 而不是流式传输来投递 data。与流式传输相比，webhooks 有许多优势，其中最突出的就是速度和可靠性。API 会在 JSON 事件可用时将 data 发送给你，你不再需要维护持久连接或轮询该 endpoint。这样可以减少对冗余功能的需求，并整体提升效率。关于 webhooks 的更多信息，请参阅[技术文档](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)。

<div id="managing-user-subscriptions">
  ### 管理用户订阅
</div>

Account Activity API 允许在单个已注册 webhook 上创建多个订阅。这样可以将多个用户的订阅活动通过 webhook 传递到同一个位置，其架构类似于 Site Streams。这意味着你可以在订阅配额层面，将订阅与 webhook 连接解耦，分别进行跟踪。这也使得你可以从只有一个或少量订阅，平滑扩展到在单个 webhook 上承载成千上万个订阅。

<div id="how-to-migrate">
  ### **如何迁移**
</div>

<div id="follow-the-steps-below-to-easily-migrate-from-the-site-streams-api-to-the-account-activity-api">
  ### **按照以下步骤，从 Site Streams API 轻松迁移到 Account Activity API**
</div>

**步骤 1：选择套餐**

根据你当前使用 User Streams 或 Site Streams 的方式，你应当考虑迁移到 Account Activity API 的 enterprise 或 premium 版本之一。请根据你当前所支持的应用或授权用户数量进行评估，并按需扩展以满足所需的请求量和可靠性。在决定最适合你需求的套餐时，值得考虑的因素包括：

* 所需的 webhook 数量
* 你的应用当前/预估管理的订阅数/授权用户数量
* 当前的 X 客户端应用数量
* 你期望从 X 获得的支持级别（论坛支持或托管的 enterprise 级别一对一支持）
* 各套餐的价格

**步骤 2：** **检查你在开发者控制台中的 X 应用设置**

当前用于 User Streams 或 Site Streams 的 [X app](/zh/resources/fundamentals/developer-apps) 会在 [开发者控制台](/zh/resources/fundamentals/developer-portal) 中列在拥有者用户名下。该 X app 也可以用于 Account Activity API，以保留该应用的已授权用户。你也可以创建一个新应用，并在需要时让用户重新授权这个新应用。如果你是代表某个企业创建新应用，建议使用企业的 X @handle 账号来创建该应用。

* 在 X 应用页面的 [permissions](/zh/resources/fundamentals/developer-apps#app-permissions) 选项卡中启用 “Read, Write and Access direct messages” 权限。\
  *请注意，更改这些设置不会追溯生效，任何已授权用户将保留其在授权时的设置。如果某个用户尚未授予你读取、写入和私信访问权限，你需要让该用户重新授权你的应用。*
* 如果你不熟悉 [X Sign-in](/zh/resources/fundamentals/authentication#log-in-with-x) 以及用户上下文在 X API 中的工作方式，请查看 [Obtaining Access Tokens](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)。
* 在 “Keys and Tokens” 选项卡底部为 X 应用拥有者生成访问令牌。在同一选项卡中记录你的 Consumer Key、Consumer Secret、Access Token 和 Access Token Secret。你需要这些信息来使用 API。
* 使用你的 Consumer Key 和 Consumer Secret 为 [application-only](/zh/resources/fundamentals/authentication#bearer-token-also-known-as-app-only) API 方法生成一个 Bearer Token。

**步骤 3：设置并配置你的 Webhook**

* 创建一个带有端点的 Web 应用，将其作为 webhook 用于接收事件（例如：https://your&#95;domain.com/webhook/twitter 或 https://webhooks.your&#95;domain.com）。

* 在创建 webhook 时使用你的 Consumer Key、Consumer Secret、Access Token 和 Access Token Secret。请注意，你的端点必须返回一个包含 response&#95;token 的 JSON 响应。该 response&#95;token 必须是从 crc&#95;token 和你的应用 Consumer Secret 生成的 base64 编码 HMAC SHA-256 哈希。

* 查阅 [Securing Webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks) 文档，特别关注 Challenge Response Check (CRC) 相关要求。

* 确保你的 webhook 支持用于接收事件的 POST 请求和用于 CRC 的 GET 请求。

* 确保你的 webhook 具有较低延迟（对 POST 请求的响应时间小于 3 秒）。

**步骤 4：验证你的 Webhook 设置**

* Webhook API 将通过两种方式保护你的 webhook：

               - 要求进行 Challenge Response Check，以验证 webhook 拥有者即为该 Web 应用的拥有者。

               - 在发往你 Web 应用的每个 POST 请求中包含一个签名头部，供你验证请求来源。

* 为了验证你同时是 Web 应用的拥有者和 webhook URL 的拥有者，X 将执行一次 Challenge Response Check (CRC)，这与循环冗余校验（cyclic redundancy check）并不相同。
* 一条带有名为 crc&#95;token 参数的 GET 请求将会发送到你的 webhook URL。你的端点必须返回一个包含 response&#95;token 的 JSON 响应，该 response&#95;token 必须是从 crc&#95;token 和你的应用 Consumer Secret 生成的 base64 编码 HMAC SHA-256 哈希。
* 你应预期每次收到 CRC 请求时 crc&#95;token 都会发生变化。在计算时，应将 crc&#95;token 作为消息内容，将 Consumer Secret 作为密钥。
* 如果响应无效，将停止向已注册的 webhook 发送事件。

**步骤 5：为每个 User Stream 或 Site Streams 授权用户创建订阅**

从 User Streams 迁移到 Account Activity API：

* 在 User Streams 上生成当前用户订阅列表
* 使用以下请求设置新的 Account Activity API 订阅：  *POST account&#95;activity/all/:env&#95;name/subscriptions*
* 使用以下请求确认你的 Account Activity API 订阅：  &#95;GET account&#95;activity/all/:env&#95;name/subscriptions/list
   &#95;

从 Site Streams 转换为 Account Activity API：（使用控制流 control streams）：

* 使用以下请求在 Site Streams 上生成当前订阅列表：  *GET /1.1/site/c/:stream&#95;id/info.json*
* 使用以下请求设置新的 Account Activity API 订阅：  *POST account&#95;activity/all/:env&#95;name/subscriptions*
* 使用以下请求确认你的 Account Activity API 订阅：  &#95;GET account&#95;activity/all/:env&#95;name/subscriptions/list
   &#95;

注册 Webhook 并创建订阅（非从 Site Streams 或 User Streams 迁移的场景）

* 使用 [POST webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#enterprise-account-activity-api) 在应用中注册你的 webhook URL，并获取一个 webhook&#95;id。
* 使用返回的 webhook&#95;id，通过 [POST webhooks/:webhook&#95;id/subscriptions/all](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#post-account-activity-webhooks-webhook-id-subscriptions-all) 添加用户订阅。

<div id="sending-direct-messages">
  ### 发送私信
</div>

[POST direct&#95;messages/events/new](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/new-event) 是用于发送私信的直接替代端点。此端点最大的变化在于，现在所有信息都作为 JSON 放在 POST 请求正文中发送，而不再通过单独的 POST 参数传递。

**Twurl 请求示例**

```bash
twurl -A 'Content-type: application/json' -X POST /1.1/direct\_messages/events/new.json -d '{"event": {"type": "message\_create", "message\_create": {"target": {"recipient\_id": "4534871"}, "message_data": {"text": "Hello World!"}}}}'
```

请注意，在上述请求中，`content-type` 被设置为 `application/json`，而不是 `application/x-www-form-urlencoded`。另外，如果你正在生成 OAuth 1.0a 签名，请注意 JSON 请求体不会参与签名的生成。大多数 OAuth 库已经考虑到了这一点。如果你在使用 [twurl](https://github.com/twitter/twurl)，请确保你使用的版本至少为 0.9.3。

<div id="summary">
  #### 摘要
</div>

* 消息在 JSON POST 请求体中定义
* 必须将 Content-Type 头部设置为 application/json
* 在生成 OAuth 签名时不会包含 JSON 请求体。
   

<div id="retrieving-direct-messages">
  ### 检索私信
</div>

现在可以通过单个 API 端点来检索历史私信：[GET direct&#95;messages/events/list](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events)。这个新端点的一个显著区别在于，它现在会按时间倒序返回已发送和已接收的消息。这有助于你更容易重建一段会话。不过，如果你只想获取已发送或已接收的消息，就需要通过查看 `sender_id` 属性，对响应进行后处理。

分页现在基于游标值，而不是某条私信的 ID。每个响应都会返回一个游标（cursor）属性。[GET direct&#95;messages/events/list](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events) 最多会返回过去 30 天的消息，而不管这 30 天内存在多少条消息。当不再返回游标时，表示没有更多消息可返回。使用 [GET direct&#95;messages/events/show](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/get-event) 访问单条私信的方法保持不变，不过，如前所述，其返回的私信对象结构有所不同。

最后，实时访问私信现在将通过 webhook 搭配 [Account Activity API](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity) 来实现。关于从 User Streams 或 Site Streams 迁移的指导，请参阅迁移到 Account Activity API 的指南以获取更多信息。

<div id="summary">
  #### 摘要
</div>

* 已发送和已接收的消息现在通过同一个 endpoint 返回。
* 最多可返回最近 30 天内的消息。
* 基于游标的分页。
* 通过 webhook 实时访问私信。

<div id="deleting-direct-messages">
  ### 删除私信
</div>

现在可以使用 DELETE direct&#95;messages/events/destroy 删除私信。该接口在很大程度上保持不变，仍然需要提供要删除消息的 ID。主要区别在于，现在该端点需要使用 DELETE 请求，而不是 POST 请求。

已删除私信在官方 X 客户端中的呈现方式保持不变。私信只会从所提供用户上下文对应的界面中移除，会话中的其他成员仍然可以访问该私信。

<div id="summary">
  #### 摘要
</div>

* 删除一条私信需要提供其 id。
* 新的端点需要使用 DELETE 请求。
* 已删除私信在官方 X 客户端中的显示方式保持不变。

<div id="frequently-asked-questions">
  ## 常见问题解答
</div>

<div id="general">
  ### 常见问题
</div>

**使用 Account Activity API 有哪些优势？**

Account Activity API 使用 webhooks，这意味着与流式 API 不同，我们无需你保持一个打开的连接，就可以向你发送信息。Webhooks 也不同于 REST API，因为你不必每 15 分钟轮询上百次来获取你关心的数据。这样可以提高用户与你的应用之间的效率，因为它会在事件发生时立即传递数据。

Account Activity API 具有以下多项优点：

1. **速度**：我们以 X 的速度向你传递数据。
2. **简洁**：我们通过单一的 webhook 连接，传递某个账号的全部事件。API 中传递的活动包括帖子、@ 提及、回复、转推、引用推文、对引用推文的转推、点赞、发送的私信、接收的私信、关注、拉黑、静音。
3. **可扩展性**：对于你所管理的账号，你将收到该账号的全部活动，而不会受到任何事件上限或速率限制的约束。

Account Activity API 以高级沙盒、高级付费和企业版形式提供，因此在你因合规功能或额外功能而需要更多账号时，可以按需进行扩展。

要开始使用，请从 [GitHub](https://github.com/xdevplatform/account-activity-dashboard) 下载示例代码片段。
 

**我该如何确定哪个产品层级最适合我？**

请阅读我们的 [Account Activity API 概览](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity) 页面，了解高级版选项与企业版选项之间的差异。 
 

**高级版环境和企业版 webhook 有什么区别？**

没有区别。每个高级版环境都会有其自己的 webhook&#95;id。
 

**我需要为 Account Activity API 准备开发、预发布和生产环境，这可以实现吗？**

可以！在 Account Activity API 的付费层级（付费高级版和企业版）中，你可以注册多个 webhook URL，并通过 API 方法为每个 URL 分别管理订阅。此外，可以将多个客户端应用添加到允许列表中，以便保持对当前已授权用户的授权状态。
 

**你们有没有关于如何配置 Account Activity API 的分步指南？**

当然有！

* 如果你刚刚开始使用，我们建议你查看[使用 webhooks 入门](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks) 指南

* 按照我们由 X Dev 支持的脚本进行操作： 
  * [Account Activity API dashboard](https://github.com/xdevplatform/account-activity-dashboard)，一个用于显示 webhook 事件的 Node Web 应用程序。
  * [SnowBot chatbot](https://github.com/xdevplatform/SnowBotDev)，一个基于 Account Activity 和 Direct Message APIs 构建的 Ruby Web 应用程序。该代码库包含一个用于帮助设置 Account Activity API webhooks 的[脚本](https://github.com/xdevplatform/SnowBotDev/wiki/Account-Activity-API-setup-script)。
     

**如果我们的系统在一段时间内宕机，有办法恢复数据吗？**

在 Account Activity API 的付费层级（付费高级版和企业版）中，我们的系统会在四小时内[重试](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)数次向你发送活动。如果你的系统在这四小时内仍未响应，则该活动将丢失，你需要使用其他 REST 端点在 7 天内恢复数据。

我们建议你将不同的 webhooks 或环境用作冗余工具，例如 [Account Activity Replay API](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-replay-api)，以确保当某个系统宕机时，你不会错过任何活动。
 

**使用 Account Activity API 时，我需要使用哪种认证方式？**

Account Activity API 所需的身份验证方法，会在每个方法的 [API 参考页面](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-api-reference-index)中进行说明。如果你刚开始接触 X 身份验证，我们建议你阅读[本章节](/zh/resources/fundamentals/authentication)。

**什么是挑战-响应检查（CRC，challenge-response check）？**

Account Activity API 的质询响应（challenge response）检查是一项安全功能，用于确保 Account Activity API 产生的活动被发送给正确的开发者。开发者也可以借此确保他们接收到的 data 确实来自 X。X 会从上次验证 webhook URL 的时间开始，每 24 小时自动向你的 webhook URL 发送一次 CRC。你的系统必须在 3 秒内返回一个有效响应，才会保持为已验证状态。 

请访问我们的页面 [Securing webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks) 了解更多详情。
 

**有哪些情况会立即使我的 webhook URL 失效？**

如果发生以下任一情况，我们会立即将你的 webhook 标记为无效：

* 服务器对 CRC 的响应中包含错误的令牌（token）。在这种情况下，我们的系统不会[重试](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)向你发送活动。
* webhook URL 配置了错误的证书。在这种情况下，我们的系统不会[重试](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)向你发送活动。
* 你的服务器返回的响应状态码不是 2XX、4XXX 或 5XXX。
* 你声明使用 gzip，但实际并未按 gzip 格式发送。
* 你未声明使用 gzip，但实际在响应中按 gzip 格式发送。
   

**如果我订阅了彼此有互动的用户，我会收到重复的活动吗？**

会的。如果你的 Web 应用对用户 A 和用户 B 都有有效订阅，并且用户 A 在帖子中提及用户 B，那么会向已注册的 webhook 发送两个 POST 活动。每个活动都会包含一个 &quot;for&#95;user&#95;id&quot; 指示器，用于表明该活动属于哪个订阅。
 

**当我向我的 webhook 发起订阅时，是否可以将以下端点中的 `/all/` 部分替换为其他账号活动数据对象，以限制 API 投递的活动？**`POST https://api.x.com/1.1/account_activity/all/:env_name/subscriptions.json`

不可以，目前我们只提供 `/all/` 这一种产品。
 

**有没有办法在不向用户请求私信（Direct Messages）权限的情况下使用 Account Activity API？**

目前，私信权限是必需的，因为在该 API 中没有办法“过滤掉”与私信相关的活动。 
 

**Account Activity API 是否有沙箱版本？**

有，我们提供用于测试的沙箱选项。我们的沙箱仅支持一个 webhook，且最多允许 15 个订阅。你可以在[我们的文档](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity)中了解有关沙箱选项的更多信息。 

**能否使用 Account Activity API 获取提及已订阅用户的帖子被转发（Retweet）的活动？**

不能，目前这不在该 API 投递的活动范围内。针对这类需求，我们建议改用 Streaming API。 
 

**tweet&#95;create&#95;event 可以表示哪些活动类型？**

在以下情况下会发送 tweet&#95;create&#95;event 负载：

如果订阅用户执行了以下任一操作：

* 创建帖子
* 转发（Retweet）
* 回复帖子

如果其他用户：

* @提及*订阅用户
* 引用由订阅用户创建的推文 

*注意：仅当订阅用户会从 X 收到通知且可以公开看到该事件时，Account Activity API 才会投递事件。这意味着，如果被提及账号（@userA）关注了受保护账号（@userB），那么 UserA 将收到 UserB 提及他们的通知。如果 UserA 没有关注 UserB（且未被 UserB 批准），UserA 将不会收到通知，因此即便 @userA 有订阅，也不会通过 AAA 发送 tweet&#95;create&#95;event。*

**如果被我屏蔽的用户提及了我的订阅用户，我该如何识别？**

你会在 JSON 响应的顶层看到一个布尔字段 `user_has_blocked`，其值为 “true” 或 “false”。该字段只会在帖子提及事件中暴露。 

企业版

**我如何将我的应用添加到允许列表，或检查我的应用是否已在允许列表中？**

要管理你已添加到企业 API 访问允许列表中的 [X apps](/zh/resources/fundamentals/developer-apps)，请联系你的客户经理并提供你的 app ID。你可以通过前往 [开发者控制台](/zh/resources/fundamentals/developer-portal)中的 [&quot;Apps&quot;](/zh/resources/fundamentals/developer-apps) 页面来找到你的 app ID。
 

**如果我有三个 webhook 的访问权限，是否可以为我注册用于企业用途的每个应用分别使用三个 webhook？**

webhook 限额是按账号设置的，而不是按应用设置的。如果你有三个 webhook 的访问权限，并且有两个应用注册为企业用途，你可以在一个应用上使用两个 webhook，在另一个应用上使用第三个 webhook，但不能在每个应用上都使用三个 webhook。 

**我可以指定要使用 Account Activity Replay API 重新投递哪些类型的事件吗？**

要重放的事件类型无法指定。在你设置的日期和时间窗口内投递的所有事件都会被重放。 

**如果我的应用未能摄取某个 Account Activity Replay API 事件，是否会进行重试？**

不会，不会进行任何重试。如果应用未能摄取由 Account Activity Replay API 发送的事件，你可以针对同一时间段再次提交 Replay 任务，以尝试重新投递任何遗漏的 Replay 事件。 

**当我收到部分成功的完成事件时应该怎么办？**

我们建议记录已接收事件的时间戳，并为遗漏的事件再次请求一个 Replay 任务。 

**我一次可以运行多少个 Account Activity Replay API 任务？**

每个 webhook 在同一时间只能运行一个 Account Activity Replay API 任务。 

**在 Account Activity Replay API 将事件投递到我的 webhook 时，我如何区分这些事件与实时生产事件？**

由于 Account Activity Replay API 始终投递过去发生的事件，因此可以根据事件的时间戳将其与实时生产事件区分开来。 

**在我的应用丢弃或错过某个活动后，我多久可以开始使用 Account Activity Replay API 重新投递该活动？**

活动在创建后大约 10 分钟即可用于重新投递。

<div id="code-32">
  #### Code 32
</div>

此错误通常表示你在请求、请求头、授权信息或所指定的 URL 中有内容格式不正确。该错误不是 Account Activity API 错误，而是授权错误，说明 X 没有获得正确的 OAuth 配置或 URL。

* **Enterprise** - 请确保你所使用的 consumer key 和 access token 属于已注册用于 Enterprise 产品的 [X app](/zh/resources/fundamentals/developer-apps)。如果你没有 consumer key 和 access token，或需要将你的 X app 添加到 allowlist，请联系你的客户经理。 

* 如果在用户上下文下进行认证，请确保你已使用正确的 `oauth nonce`、`oauth_signature` 和 `oauth_timestamp` [对请求进行了授权](/zh/resources/fundamentals/authentication#authorizing-a-request)。

* 确保你的 access token 具有适当的权限级别。
  * 在 [app dashboard](/zh/resources/fundamentals/developer-apps) 的“Keys and tokens”选项卡中，请确认你的 access token 具有“Read, write, and direct messages”[权限级别](/zh/resources/fundamentals/developer-apps#app-permissions)。 
  * 如果 token 的权限级别低于此，请转到“Permissions”选项卡，将访问权限调整为“Read, write, and direct messages”，然后在“Keys and tokens”选项卡中重新生成你的 access token 和 secret。

* 确保你的 URL 格式正确。
  * 请注意，`:env_name` 区分大小写。
     

<div id="code-200-forbidden">
  #### Code 200 - 禁止访问
</div>

* **Premium** - 在尝试向 API 发起请求之前，请确保你拥有已获批准的[开发者账号](/zh/resources/fundamentals/developer-portal)。你还必须在请求中使用正确的 :env&#95;name，可以在 [dev environments](/zh/resources/fundamentals/developer-portal) 页面中进行配置。

* **Enterprise** - 请确保你的客户经理已为你开通 Account Activity API 的访问权限。

* 请确保你已正确配置 URI。如果你在请求中输入了错误的 URI，就会触发此错误。
   

<div id="code-214-webhook-url-does-not-meet-the-requirements">
  #### 代码 214 - Webhook URL 不符合要求。
</div>

* 请确保你使用的是 HTTPS。
* 你的 webhook URL 可能格式不正确。
* 请在[开始使用 webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)页面的[开发 webhook consumer 应用](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#3-develop-webhook-consumer-app)部分，了解如何设置你的 webhook URL。
   

<div id="code-214-high-latency-on-crc-get-request-your-webhook-should-respond-in-less-than-3-seconds">
  #### 代码 214 - CRC GET 请求延迟过高。你的 webhook 应在 3 秒内响应。
</div>

* 这表明你的服务器较慢。请确保在 3 秒内对 CRC 请求作出响应。
   

<div id="code-214-non-200-response-code-during-crc-get-request-ie-404-500-etc">
  #### Code 214 - 在 CRC GET 请求期间返回非 200 响应状态码（例如 404、500 等）。
</div>

* 您的服务器可能已宕机。请确保服务器正在正常运行。
   

<div id="code-214-too-many-resources-already-created">
  #### 代码 214 - 已创建的资源过多。
</div>

* **Enterprise** - 您已经用完了所有的 webhook。对每一个已注册的应用使用 [GET webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#get-account-activity-webhooks) 端点，以确定 webhook 的分布位置。 

<div id="code-261-application-cannot-perform-write-actions">
  #### Code 261 - Application cannot perform write actions.
</div>

* 您与 API 搭配使用的应用没有为其 access token 和 access token secret 设置正确的[权限级别](/zh/resources/fundamentals/developer-apps#app-permissions)。请前往 [X apps](/zh/resources/fundamentals/developer-apps) 控制面板中的 “Keys and tokens” 选项卡，检查分配给您的 access token 和 access token secret 的权限级别。如果权限级别不是 “Read, write and Direct Messages”，则需要在 “Permission” 选项卡中调整设置，并重新生成 access token 和 access token secret 以应用新的设置。
* 另一种情况是，您正在尝试使用仅应用身份验证（app-only authentication）方式注册 webhook，这是不受支持的。请按照 [Enterprise Account Activity API](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#post-account-activity-webhooks) 中关于注册 webhook 的 API 参考部分所述，改为使用用户上下文进行身份验证。

<div id="replay-api">
  ### 回放 API
</div>

**POST /1.1/account&#95;activity/replay/webhooks/:webhook&#95;id/subscriptions/all.json [¶](#post-1-1-account-activity-replay-webhooks-webhook-id-subscriptions-all-json- "此标题的固定链接")**

提交请求，从请求中指定的日期和时间窗口内存在的所有订阅中，检索过去最多五天内的活动。如果你的 webhook 存在活跃的用户订阅，你也会同时接收到这些事件。注意：在投递回放事件之前，我们会执行一次 CRC 校验。

|     |     |
| :--- | :--- |
| **Request Method** | HTTP POST |
| **URL** | /1.1/account&#95;activity/replay/webhooks/:webhook&#95;id/subscriptions/all.json?from&#95;date=yyyymmddhhmm&amp;to&#95;date=yyyymmddhhmm |
| **Response Format** | JSON |
| **Requires Authentication** | 是（仅应用程序 - Bearer Token） |
| **Rate Limit** | 每 15 分钟 5 个请求。目前对可请求的回放作业数量没有上限。 |
| **from&#95;date** | 提供事件的最早（起始）UTC 时间戳，必须为“yyyymmddhhmm”格式。时间戳的精度为分钟且为包含关系（即 12:00 包含第 0 分钟）。有效时间必须在最近 5 天内（UTC 时间），且至少早于当前时间点 31 分钟。建议 from&#95;date 和 to&#95;date 之间的间隔应在约 2 小时以内。 |
| **to&#95;date** | 提供事件的最晚（结束）UTC 时间戳，必须为“yyyymmddhhmm”格式。时间戳的精度为分钟且为不包含关系（即 12:30 不包含该小时的第 30 分钟）。有效时间必须在最近 5 天内（UTC 时间），且至少早于当前时间点 10 分钟。 |

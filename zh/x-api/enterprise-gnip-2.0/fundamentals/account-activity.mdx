概览

`Enterprise`

Account Activity API 允许你通过 webhooks 订阅与用户账号相关的实时活动。也就是说，你可以通过单一连接，从一个或多个你拥有或订阅的账号接收实时帖子、Direct Messages，以及其他账号事件。

针对你在 webhook 注册中订阅的每个用户，你将接收到下述所有相关活动：

| 活动类型 |     |
| :--- | :--- |
| * 帖子（由用户发布）  <br />    <br />* 帖子删除（由用户发起）<br />* @ 提及（提及该用户）<br />* 回复（发给用户或由用户发出）<br />* 转发（由用户转发或转发用户的帖子）<br />* 引用推文（由用户发出或引用用户的推文）<br />* 对引用推文的转发（由用户发出或转发用户的引用推文）<br />* 点赞（由用户发起或对用户帖子发起）<br />* 关注（由用户发起或关注用户）  <br />    <br />* 取消关注（由用户发起） | * 拉黑（由用户发起）<br />* 取消拉黑（由用户发起）<br />* 静音（由用户发起）<br />* 取消静音（由用户发起）<br />* 发送的 Direct Messages（由用户发送）<br />* 接收的 Direct Messages（由用户接收）<br />* 正在输入指示器（发给用户）<br />* 已读回执（发给用户）<br />* 订阅撤销（由用户发起） |

**请注意** - 我们不会通过 Account Activity API 提供主页时间线数据。请使用 [GET statuses/home&#95;timeline](https://developer.x.com/en/docs/x-api/v1/tweets/timelines/overview) 来拉取这些数据。

<div id="manage-webhooks-and-subscribed-users">
  ## 管理 webhooks 和已订阅用户
</div>

**⏱ 约 10 分钟阅读**

企业版 Account Activity API 会在与你的服务已订阅的 X 账号发生相关事件时，通过 webhook 向你发送 JSON 格式的消息。X 会将这些活动推送到你注册的 webhook。通过以下步骤，你将学习如何管理 webhooks 和已订阅用户。

你将学习如何注册、查看和移除 webhook 以及已订阅用户。我们将使用简单的 cURL 命令向各个 API 端点发起请求。cURL 是一个使用 URL 语法来获取或发送请求的命令行工具。

你需要具备：

* 一个已注册的 X App - *[在此注册](https://developer.x.com/content/developer-twitter/en/apps)*
* 一个 Bearer 令牌 - *[了解更多](/zh/resources/fundamentals/authentication#using-and-generating-an-app-only-bearer-token)*
* 一个通过 Challenge-Response Check (CRC) 的 webhook - *[了解更多](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks)*
* 一个企业账号 - *[在此申请](https://developer.x.com/en/products/x-api/enterprise)*

*在开始之前，我们建议你先查看我们的 [GitHub 仓库](https://github.com/xdevplatform/account-activity-dashboard)，其中提供了一个示例 Web 应用和辅助脚本，帮助你快速上手使用 X 的 Account Activity API。*

<div id="managing-a-webhook">
  #### 管理 webhook：
</div>

使用 webhook 可以让你通过单一连接订阅与某个用户账号相关的实时活动。 

<Tabs>
  <Tab title="添加 webhook">
    我们先从为指定的应用上下文注册一个新的 webhook URL 开始。

    在保存之前，会通过 CRC 请求对该 URL 进行验证。注册 webhook 之后，请务必记录 webhook ID，后续还会用到。

    完成下面几项替换后，将以下 cURL 请求复制到命令行中执行：

    * **URL** `<URL>`，例如：`https://yourdomain.com/webhooks/twitter/`

    * **Consumer key（消费者密钥）** `<CONSUMER_KEY>`，例如：`xvz1evFS4wEEPTGEFPHBog`

    * **Access token（访问令牌）** `<ACCESS_TOKEN>`，例如：  `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request POST --url 'https://api.x.com/1.1/account_activity/webhooks.json?url=<URL>' --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>

  <Tab title="查看 webhook">
    运行以下命令，将返回指定应用下所有已注册的 webhook URL 及其状态。

    完成下面几项替换后，将以下 cURL 请求复制到命令行中执行：

    * **Bearer 令牌** `<BEARER_TOKEN>`，例如：`AAAAAAAAAAAA0%2EUifi76ZC9Ub0wn...`

      ```curl --request GET --url https://api.x.com/1.1/account_activity/webhooks.json --header 'authorization: Bearer <BEARER_TOKEN>'
      ```
  </Tab>

  <Tab title="移除 webhook">
    要从指定应用的配置中移除某个 webhook，完成下面几项替换后，将以下 cURL 请求复制到命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>`，例如：`1234567890`

    * **Consumer key（消费者密钥）** `<CONSUMER_KEY>`，例如：`xvz1evFS4wEEPTGEFPHBog`

    * **Access token（访问令牌）** `<ACCESS_TOKEN>`，例如：  `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```curl --request DELETE --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>.json --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>
</Tabs>

<div id="managing-subscribed-users">
  #### 管理已订阅用户：
</div>

注册 Webhook 之后，你可以为 Account Activity API 添加订阅用户，以开始接收其账号活动。

<Tabs>
  <Tab title="添加订阅">
    我们先从为用户创建订阅开始，这样你就可以接收所有事件类型的事件。

    在对以下内容进行相应修改后，将下面的 cURL 请求复制到你的命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>`，例如 `1234567890`

    * **消费者密钥名称 (consumer key name)** `<CONSUMER_KEY>`，例如 `xvz1evFS4wEEPTGEFPHBog`

    * **订阅用户的访问令牌** `<SUBSCRIBING_USER'S_ACCESS_TOKEN>`，例如 `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request POST --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>/subscriptions/all.json --header 'authorization: OAuth oauth_consumer_key="<CONSUMER_KEY>", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="<SUBSCRIBING_USER'S_ACCESS_TOKEN>", oauth_version="1.0"'
      ```
  </Tab>

  <Tab title="查看订阅">
    要查看指定 Webhook 的所有活动类型订阅列表，在对以下内容进行相应修改后，将下面的 cURL 请求复制到你的命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>`，例如 `1234567890`

    * **Bearer 令牌** `<BEARER_TOKEN>`，例如 `AAAAAAAAAAAA0%2EUifi76ZC9Ub0wn...`

      ```
      curl --request GET --url https://api.x.com/1.1/account_activity/webhooks/<:WEBHOOK_ID>/subscriptions/all/list.json --header 'authorization: Bearer <BEARER_TOKEN>'
      ```
  </Tab>

  <Tab title="移除订阅">
    停用后，请求用户的所有事件将不再发送到该 Webhook URL。

    要在指定的用户上下文和应用下停用某个订阅，在对以下内容进行相应修改后，将下面的 cURL 请求复制到你的命令行中执行：

    * **Webhook ID** `<:WEBHOOK_ID>`，例如 `1234567890`

    * **消费者密钥 (consumer key)** `<CONSUMER_KEY>`，例如 `xvz1evFS4wEEPTGEFPHBog`

    * **订阅用户的访问令牌** `<SUBSCRIBING_USER'S_ACCESS_TOKEN>`，例如 `370773112-GmHxMAgYyLbNEtIKZeRNFsMKPR9EyMZeS9weJAEb`

      ```
      curl --request DELETE --url https://api.x.com/1.1/account_activity/webhooks/:WEBHOOK_ID/subscriptions/all.json --header 'authorization: OAuth oauth_consumer_key="CONSUMER_KEY", oauth_nonce="GENERATED", oauth_signature="GENERATED", oauth_signature_method="HMAC-SHA1", oauth_timestamp="GENERATED", oauth_token="SUBSCRIBED_USER'S_ACCESS_TOKEN", oauth_version="1.0"'
      ```
  </Tab>
</Tabs>

做得很好！现在你应该已经可以管理你的 Webhook 和已订阅用户了。

<div id="getting-started-with-webhooks">
  ## 开始使用 Webhook
</div>

Account Activity API 是一个基于 Webhook 的 API，它会将账户事件发送到你自行开发、部署并托管的 Web 应用程序。

在你的事件消费应用程序能够开始接收 Webhook 事件之前，需要先处理若干“管道”层面的细节。如下所述，你需要创建一个 X App，获取 Account Activity API 的访问权限，并开发一个用于消费 Webhook 事件的 Web 应用程序。 

<div id="1-create-a-x-app">
  ### 1. 创建一个 X App。
</div>

* 使用在[开发者控制台](/zh/resources/fundamentals/developer-portal)中获批的开发者账号创建一个 [X app](/zh/resources/fundamentals/developer-apps)。如果你是代表公司创建 App，建议使用公司的 X 账号来创建该 App。要申请开发者账号，[点击这里](/zh/resources/fundamentals/developer-apps)。
* 在 App 页面中的 [permissions](/zh/resources/fundamentals/developer-apps#oauth-1-0a-app-permissions) 选项卡里启用“Read, Write and Access direct messages”权限。
* 在“Keys and Access Tokens”选项卡中，记录下你的 App 的 Consumer Key（API Key）和 Consumer Token（API Secret）。
* 在同一选项卡中，生成你的 App 的 [Access Token 和 Access Token Secret](/zh/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow)。你需要使用这些 Access Token 来注册你的 webhook URL，X 会将账号事件发送到该 URL。
* 如果你不熟悉 [X Sign-in](/zh/resources/fundamentals/authentication#log-in-with-x) 以及用户上下文在 X API 中是如何工作的，请查阅 [Obtaining Access Tokens](https://dev.x.com/webhooks/access-tokens)。当你添加要接收事件的账号时，会使用该账号的 access tokens 为其订阅事件。
* 记录下你的 App 的数字 ID，可在[开发者控制台](/zh/resources/fundamentals/developer-portal)的 [&quot;Apps&quot;](/zh/resources/fundamentals/developer-apps) 页面中看到。当你申请 Account Activity API 访问权限时，需要提供这个 App ID。
   

<div id="2-get-account-activity-api-access">
  ### 2. 获取 Account Activity API 访问权限
</div>

在创建 X App 之后，下一步是申请 Account Activity API 的访问权限。 

Account Activity API 仅在 Enterprise 级别中提供，因此你需要通过下面的链接提交申请。

<Button href="https://developer.x.com/en/enterprise-application.html">
  申请 Enterprise 访问权限

<div id="3-develop-webhook-consumer-app">
  ### 3. 开发 webhook 消费端 App
</div>

在你获得 Account Activity API 访问权限后，你需要开发、部署并托管一个用于接收 X webhook 事件的 Web 应用程序。 

* 创建一个带有 URL 的 Web 应用程序，用作接收事件的 webhook。这个 URL 是部署在你服务器上的端点，用于监听传入的 X webhook 事件。 
  * URI *路径* 完全由你决定。下面这个示例是有效的：https://mydomain.com&#95;/service/listen&#95;

  * 如果你要从多个来源接收 webhooks，一个常见的模式是：https://mydomain.com/webhook/twitter

  * 注意，指定的 URL 不能包含端口号（https://mydomain.com:5000/NoWorkie）。

* 如我们的 [Securing Webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks) 指南中所述，第一步是编写代码来接收 X 的 Challenge Response Check (CRC) GET 请求，并返回格式正确的 JSON 响应。 

* 注册你的 webhook URL。你需要向 /webhooks.json?url= 端点发送一个 POST 请求。当你发送该请求时，X 会向你的 Web 应用程序发出 CRC 请求。webhook 成功注册后，响应中会包含一个 webhook id。在之后向 Account Activity API 发出某些请求时需要使用这个 webhook id。 

* X 会将账号的 webhook 事件发送到你注册的 URL。确保你的 Web 应用程序支持针对传入事件的 POST 请求。这些事件将以 JSON 编码。示例 webhook JSON 载荷见 [此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-data-object-structure)。

* 当你的 Web 应用程序准备就绪后，下一步是添加要接收活动的账号。在添加（或删除）账号时，你需要发送引用该账号 id 的 POST 请求。更多信息请参阅我们的[添加订阅指南](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#managing-webhooks-and-subscriptions)。

<div id="4-validate-setup">
  ### 4. 验证设置
</div>

* 要验证你的 App 和 webhook 是否配置正确，可以给你的 App 订阅的某个 X 账号发布的帖子点“喜欢”。对于你的订阅者收到的每一次“喜欢”，你都应该通过发往你的 webhook URL 的 POST 请求收到一个 `favorite_events`。
* 请注意，在添加订阅之后，事件开始投递可能会有最长 10 秒的延迟。

**重要说明**

* 在注册你的 webhook URL 时，你的 Web App 必须使用其 consumer token 和 secret **以及 App 所有者的用户访问 token 和 secret** 进行认证。 

* 所有收到的私信（Direct Messages）都会通过 webhooks 投递。所有通过 [POST direct&#95;messages/events/new (message&#95;create)](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/new-event) 发送的私信也会通过 webhooks 投递。这样可以让你的 Web App 感知通过其他客户端发送的私信。

* 请注意，每个 webhook 事件都会包含一个 `for_user_id` 用户 ID，用来指明该事件是为哪个订阅投递的。

* 如果有两个用户在同一会话中使用你的 Web App 处理私信，你的 webhook 将会收到两条重复事件（每个用户各一条）。你的 Web App 需要考虑到这一点。 

* 如果你有多个 Web App 共享同一个 webhook URL，并且同一个用户被映射到每个 App，那么同一个事件会被多次发送到你的 webhook（每个 Web App 一次）。

* 在某些情况下，你的 webhook 可能会收到重复事件。你的 webhook App 应当具有容错能力，并基于事件 ID 进行去重。

* 不要期望 Quick Reply（快速回复）的响应会紧接在请求之后到达。用户可以选择忽略 Quick Reply 请求，而改用传统私信进行回复。用户也可以对其在消息线程中先前尚未回复的请求给出 Quick Reply 响应。

  * [Enterprise Account Activity API dashboard](https://github.com/xdevplatform/account-activity-dashboard-enterprise)，一个使用 Account Activity API 企业级别的 Node Web App，用于展示 webhook 事件，并包含 [Replay](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-replay-api) 功能。

  * [SnowBot chatbot](https://github.com/xdevplatform/SnowBotDev)，一个基于 Account Activity 和 Direct Message API 构建的 Ruby Web App。该代码库包含一个用于帮助设置 Account Activity API webhooks 的[脚本](https://github.com/xdevplatform/SnowBotDev/wiki/Account-Activity-API-setup-script)。

<div id="securing-webhooks">
  ## 保障 webhooks 的安全
</div>

X 的基于 webhook 的 API 提供两种方法，帮助你验证 webhook 服务器的安全性：

1. 挑战‑响应检查使 X 能够确认接收 webhook 事件的 Web 应用的所有权。 
2. 每个 POST 请求中的签名请求头使你能够确认 X 是传入 webhook 的来源。
    

<div id="challenge-response-checks">
  ### 质询-响应检查（Challenge-Response Checks）
</div>

为了验证你既是 App 的所有者又是 webhook URL 的所有者，X 会执行一次 Challenge-Response Check（CRC），不要将其与循环冗余校验（cyclic redundancy check）混淆。发送 CRC 时，X 会向你的 Web App 发送一个带有 *`crc_token`* 参数的 GET 请求。收到该请求后，你的 Web App 需要基于 *`crc_token`* 参数和你的 App 的 Consumer Secret（详情见下文）构建一个加密的 `response_token`。`response_token` 必须使用 JSON 编码（参见下面的示例），并在三秒内返回。成功后，将返回一个 webhook `id`。 

当你注册 webhook URL 时会发送一次 CRC，因此实现 CRC 响应代码是首要且关键的一步。一旦你的 webhook 建立，X 会在上次收到成功响应后，大约每 24 小时触发一次 CRC。你的 App 也可以在需要时，通过使用你的 webhook `id` 发起一个 PUT 请求来触发 CRC。在开发 webhook 应用、部署新代码并重启服务之后，触发 CRC 会非常有用。 

应预期 *`crc_token`* 会在每个传入的 CRC 请求中发生变化，并应在计算中作为消息使用，而你的 Consumer Secret 作为密钥。

如果响应未在 3 秒内发送，或变得无效，将停止向已注册的 webhook 发送事件。

<div id="the-crc-request-will-occur">
  #### CRC 请求将在以下情况下发起：
</div>

* 当注册 webhook URL 时。
* 大约每隔&#95;一小时&#95;验证一次你的 webhook URL。
* 你可以通过发送 PUT 请求手动触发 CRC。在开发 webhook 客户端和 CRC 响应时，应提前规划如何手动触发 CRC。 
   

<div id="response-requirements">
  #### 响应要求：
</div>

* 使用 `crc_token` 和你的 App Consumer Secret 生成的、经 base64 编码的 HMAC SHA-256 哈希
* 有效的 `response_token`，且为 JSON 格式。
* 响应时间小于 3 秒。
* HTTP 200 响应状态码。
   

<div id="language-specific-hmac-libraries">
  #### 各种语言的 HMAC 库：
</div>

* [Java/Scala](https://docs.oracle.com/javase/8/docs/api/index.html?javax/crypto/Mac.html)
* [Ruby](http://ruby-doc.org/stdlib-2.1.0/libdoc/openssl/rdoc/OpenSSL/HMAC.html)
* [Node.js](https://nodejs.org/api/crypto.html#crypto_class_hmac)
* [Python](https://docs.python.org/2/library/hmac.html)

<div id="example-response-token-generation-in-python">
  #### 使用 Python 生成响应令牌的示例：
</div>

下面的示例在一个 Python 2.7 Flask Web 应用中定义了一个路由，用于正确通过挑战响应检查。

```
import base64
import hashlib
import hmac
import json


\# Defines a route for the GET request
@app.route('/webhooks/twitter', methods=\['GET'\])
def webhook_challenge():

  # 使用传入的令牌和您的 consumer secret 创建 HMAC SHA-256 哈希
  sha256\_hash\_digest = hmac.new(TWITTER\_CONSUMER\_SECRET, msg=request.args.get('crc_token'), digestmod=hashlib.sha256).digest()

  # 使用 base64 编码的哈希构造响应数据
  response = {
    'response\_token': 'sha256=' + base64.b64encode(sha256\_hash_digest)
  }

  # 返回格式正确的 JSON 响应
  return json.dumps(response)
```

<div id="example-json-response">
  #### 示例 JSON 响应：
</div>

按上述方式定义路由后，当你在浏览器中访问 https://your-app-domain/webhooks/twitter?crc&#95;token=foo 时，你的 Web 应用应返回类似如下的响应。

```
{
  "response_token": "sha256=x0mYd8hz2goCTfcNAaMqENy2BFgJJfJOb4PdvTffpwg="
}
```

<div id="optional-signature-header-validation">
  ### 可选的签名请求头验证
</div>

当接收来自 X 的 POST 请求、发送 GET 请求以创建 webhook，或发送 GET 请求以执行手动 CRC 时，会在请求头中通过 `x-twitter-webhooks-signature` 传递一个哈希签名。此签名可用于验证数据来源是否为 X。POST 的哈希签名以 `sha256=` 开头，表示使用 HMAC SHA-256 基于你的 X App Consumer Secret 和有效负载生成签名。GET 的哈希是从查询参数字符串 `crc_token=$token&nonce=$nonce` 计算得到的。 

**验证请求的步骤**

1. 使用你的 consumer secret 和接收到的请求有效负载主体创建一个哈希。
2. 将生成的哈希与经 base64 编码的 `x-twitter-webhooks-signature` 值进行比较。使用类似 [compare&#95;digest](https://docs.python.org/2/library/hmac.html) 的方法，以降低遭受计时攻击的风险。

<div id="retries">
  ## 重试
</div>

`Enterprise`

Account Activity API 的 `Enterprise` 级别的优势之一，是为 webhook 事件提供重试机制。如果没有收到表示“成功”的 200 HTTP 响应代码，X 服务器会启动重试机制，在五分钟内最多重新发送该 webhook 事件三次。这个 webhook 事件重试服务有助于在发生网络问题，以及客户端服务中断或服务发布与部署期间，提升可靠性并实现事件恢复。
 

<div id="what-are-retries">
  ### 什么是重试？
</div>

当客户端的 Web 应用未对某个账号活动 webhook 事件返回“成功”的 200 响应时，Account Activity API 会启用重试机制。当客户端未确认已成功接收某个事件时，X 会认为该事件未被接收。如果收到的是非 200 响应、在三秒内未收到响应，或者根本没有收到响应，我们会重试该请求，并在接下来的三秒内保持该请求处于等待状态。这意味着，在两次尝试中，你大约有五秒时间来返回响应，以接收我们尝试发送到你 webhook URL 的活动。如果你的服务器没有响应或返回了临时性错误，我们将在五分钟内持续重试。总共会有三次重试尝试来完成验证确认。这样可以提供冗余和保障机制，确保你接收到所有 webhook 事件。请注意，启用了重试的订阅，其 webhook 将会针对其所有已订阅用户的任意／所有活动接收被重试的事件。

如果你在这八次尝试内没有完成验证确认，该活动将无法再通过 Account Activity API 获取。 

<div id="retry-timeline">
  ### 重试时间线
</div>

Account Activity API 会在五分钟内最多重试三次，直到收到 200 响应为止。有关更多详细信息，请参阅下表。大约五分钟后，该活动将无法通过 Account Activity API 重新发送。你需要使用其他 X API 端点来收集遗漏的数据。例如，可以使用 [search APIs](/zh/x-api/enterprise-gnip-2.0/fundamentals/search-api) 来检索相关帖子、转帖、引用推文、提及和回复。遗漏的私信可以通过 [此端点](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events) 检索。

<div id="retries-timeline">
  #### 重试时间线
</div>

|     |
| :--- |
| 活动已创建，Account Activity API 向 webhook URL 发送 POST 请求，并在 3 秒内超时。 |
| 在上一次超时结束后等待 3 秒，然后 Account Activity API 向 webhook URL 再次发送 POST 请求，并在 3 秒内超时。 |
| 在上一次超时结束后等待 27 秒，然后 Account Activity API 向 webhook URL 再次发送 POST 请求，并在 3 秒内超时。 |
| 在上一次超时结束后等待 242 秒，然后 Account Activity API 向 webhook URL 再次发送 POST 请求，并在 3 秒内超时。 |
| 之后，Account Activity API 将停止尝试发送 POST 请求。Client 必须使用其他 X 端点来恢复数据。 |

<div id="account-activity-replay-api">
  ## Account Activity Replay API
</div>

`Enterprise`

Account Activity Replay API 是一款数据恢复工具，可让你检索最多可追溯至过去五天的事件。它适用于在你的 [webhook](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#enterprise-account-activity-api) 服务器错过事件时进行数据恢复的场景——无论是由于断开连接时间超过了[重试窗口](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)，还是在灾难恢复场景下，你需要几天时间才能将系统恢复到正常状态。

Account Activity Replay API 是为任何在一段时间内未能摄取[活动](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity)的场景而开发的。它会将活动投递到用于原始实时活动投递的同一 webhook。该产品是一个恢复工具，而不是数据回填工具，这意味着只有在曾经尝试过投递的事件才会被重放。Account Activity Replay API 无法投递订阅创建时间之前时间段内的事件。

<div id="using-account-activity-replay-api">
  ### 使用 Account Activity Replay API
</div>

如果你的账号已配置 Replay 功能，你可以以类似调用 Account Activity API 的方式发起请求。需要特别注意的是，你的请求必须指定一个 webhook id 参数，以指明你希望回放哪个 webhook 的活动。换句话说，一个 Replay 请求会要求 Account Activity Replay API 基于 webhook id 和 application id，在指定的开始日期和时间与结束日期和时间之间检索事件。

请注意，这里要求使用 UTC 时间。这些活动会通过与该 id 关联的已注册 webhook 进行发送，速率最高可达每秒 2,500 个事件。同样需要记住的是，每个 webhook 在任一时刻只能运行一个 Replay 作业，尽管在该 webhook 上、在所指定日期/时间范围内处于活动状态的所有订阅都会被回放。

事件的传递从指定时间范围内的第一个（最早的）分钟开始，按时间顺序（尽可能准确地）持续到最后一分钟被传递完毕。届时，Replay 会向该 webhook 发送一个[作业完成事件](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#job-completed-successfully-message)。由于我们按时间顺序传递活动，如果在起始时间附近几乎没有或完全没有匹配结果，那么在第一次结果被传递之前，很可能会有一段时间的延迟。

<div id="limitations">
  ### 限制
</div>

Replay 旨在作为一种工具，用于便捷地恢复最久可追溯到五天前的活动数据，但它不会返回订阅创建时间之前的事件。举例来说，如果你在三天前添加了一个新的订阅，并运行了一个 Replay 作业，将时间窗口设为从今天往前推五天，你只能接收到这三天内该新订阅处于生效状态时的数据。

<div id="data-availability-and-types">
  ### 数据可用性和类型
</div>

Account Activity Replay API 返回的活动数据自发起请求之时起可用，为期五天，新数据通常会在某个活动创建大约 10 分钟后变得可用。你可以在请求中使用 from&#95;date 和 to&#95;date 参数，指定这 5 天窗口期内的时间范围来发起请求。在获得 Replay 访问权限之前已投递的事件无法被重新回放。举例来说，如果你的账户在 2019 年 6 月 1 日 UTC 时间下午 3:30 获得了 Account Activity Replay API 的访问权限，你将无法使用 Replay 检索该日期和时间之前的任何事件。

继续阅读 [Account Activity Replay API 参考](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#delete-account-activity-webhooks-webhook-id-subscriptions-all-deprecated)

  ## 迁移指南：从 User Streams/Site Streams 迁移到 Account Activity API

**自 2018 年 8 月 23 日起，我们已停用 Site Streams 和 User Streams。请务必迁移到 Account Activity API。**

本指南旨在帮助你从旧版 User Streams 和 Site Streams API 迁移到其替代方案 Account Activity API。下面你将看到变更摘要、新功能列表，以及关键差异和注意事项，以帮助顺利完成迁移。如需从基础 DM 端点迁移的指导，请参考 [Direct Message 迁移指南](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/guides/direct-message-migration)。

<div id="differences-migration-considerations">
  ### 差异与迁移注意事项
</div>

**API 格式：** 新的 Account Activity API 的运行方式与 User Streams 和 Site Streams 不同。你需要修改你的 Web 应用，以通过 webhooks 接收数据。你可以在[此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)找到关于 webhooks 的更多信息。

**可用数据：** 你会注意到的另一个关键差异与所推送的数据有关。X 将不再发送来自你在 X 上关注的用户（也就是你的首页时间线）的事件。这是刻意做出的变更，我们目前没有在未来进行调整的计划。

**可靠性：** 与流式传输不同，webhooks 支持对投递进行确认，并提供对未成功发送到 webhook URL 的 POST 活动进行重试的选项。这样可以更能确保 App 接收到所有适用的活动，即使存在短暂的断连或停机时间段。

<div id="new-features">
  ### 新功能
</div>

Account Activity API 提供了许多新功能，其中最显著的变化在于：数据现在通过 webhooks 发送，而不再通过流式传输。与流式传输相比，webhooks 具有许多优势，其中最重要的是速度和可靠性。API 会在数据可用时以 JSON 事件的形式将其发送给你，你不再需要维护活动连接或轮询端点。这样可以减少对冗余机制的需求，并整体提升效率。关于 webhooks 的更多信息，请参阅[技术文档](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)。

<div id="managing-user-subscriptions">
  ### 管理用户订阅
</div>

Account Activity API 允许为单个已注册的 webhook 创建多个订阅。这样可以将多个用户订阅产生的活动通过 webhook 发送到同一个位置，其架构类似于 Site Streams。这意味着，你可以在不依赖 webhook 连接的情况下，单独跟踪订阅本身及其与订阅上限之间的关系。这也便于扩展，可以从只有一个或少数几个订阅，扩展到针对单个 webhook 的成千上万个订阅。

<div id="how-to-migrate">
  ### **迁移方法**
</div>

<div id="follow-the-steps-below-to-easily-migrate-from-the-site-streams-api-to-the-account-activity-api">
  ### **按照以下步骤，从 Site Streams API 轻松迁移到 Account Activity API**
</div>

**步骤 1：选择套餐**

根据你当前使用 User Streams 或 Site Streams 的方式，你应当考虑迁移到 Account Activity API 的 enterprise 或 premium 版本。请根据你当前支持的应用或已授权用户的数量进行评估，并按所需的流量规模和可靠性进行适配。在决定最适合你需求的套餐时，值得考虑的因素包括：

* 所需的 webhook 数量
* 你的应用当前/预计管理的订阅数/已授权用户数
* 当前的 X 客户端应用程序数量
* 你希望从 X 获得的支持级别（论坛支持或托管的 enterprise 级企业级 1:1 支持）
* 各套餐的价格

**步骤 2：** **检查你在开发者控制台中的 X App 设置**

当前用于 User Streams 或 Site Streams 的 [X app](/zh/resources/fundamentals/developer-apps)，会在 [开发者控制台](/zh/resources/fundamentals/developer-portal) 中列在所属用户名下。该 X app 也可以用于 Account Activity API，从而保留该应用已授权的用户。如果需要，也可以创建一个新的 app，并让用户对这个新 app 重新授权。如果你是代表企业创建新 app，建议使用企业的 X @handle 账号来创建该 app。

* 在你的 X app 页面上的 [permissions](/zh/resources/fundamentals/developer-apps#app-permissions) 选项卡中启用 “Read, Write and Access direct messages”。
  *请注意，更改这些设置并不会追溯生效，任何已授权用户将继续保留其在授权时所赋予的权限设置。如果某个用户尚未授予你读取、写入以及访问私信的权限，你需要让该用户重新授权你的应用。
* 如果你不熟悉 [X Sign-in](/zh/resources/fundamentals/authentication#log-in-with-x) 以及用户上下文在 X API 中的工作方式，请查看 [Obtaining Access Tokens](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)。
* 在 “Keys and Tokens” 选项卡底部为 X app 所有者生成访问令牌。在该选项卡中同时记下你的 Consumer Key、Consumer Secret、Access Token 和 Access Token Secret。你在使用 API 时会需要这些信息。
* 使用你的 Consumer Key 和 Consumer Secret 生成用于 [application-only](/zh/resources/fundamentals/authentication#bearer-token-also-known-as-app-only) API 方法的 Bearer 令牌。

**步骤 3：设置并配置你的 Webhook**

* 创建一个带有端点的 web 应用，将其用作 webhook 以接收事件（例如：https://your&#95;domain.com/webhook/twitter 或 https://webhooks.your&#95;domain.com）。

* 在创建 webhook 时，使用你的 Consumer Key、Consumer Secret、Access Token 和 Access Token Secret。请注意，你的端点必须返回一个 JSON 响应，其中包含一个 response&#95;token，该值是使用 crc&#95;token 和你的 app Consumer Secret 创建的、经 base64 编码的 HMAC SHA-256 哈希。

* 查阅 [Securing Webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks) 文档，特别留意 Challenge Response Check (CRC) 的要求。

* 确保你的 webhook 支持用于接收传入事件的 POST 请求，以及用于 CRC 的 GET 请求。

* 确保你的 webhook 具备低延迟（对 POST 请求的响应时间小于 3 秒）

**步骤 4：验证你的 Webhook 设置**

* Webhook API 将通过两种方式保护你的 webhook：

               - 要求进行挑战-响应检查，以验证 webhook 拥有者是该 web 应用的拥有者。

               - 在每个发送到你的 web 应用的 POST 请求中包含一个签名头，供你验证请求来源。

* 为了验证你既是 web 应用的所有者，也是 webhook URL 的所有者，X 会执行 Challenge Response Check (CRC)，这与循环冗余校验不同，不要混淆。
* 一条带有名为 crc&#95;token 参数的 GET 请求将被发送到你的 webhook URL。你的端点必须返回一个 JSON 响应，其中包含一个 response&#95;token，该值是使用 crc&#95;token 和你的 app Consumer Secret 创建的、经 base64 编码的 HMAC SHA-256 哈希。
* 你应该预期每个传入的 CRC 请求都会携带不同的 crc&#95;token。crc&#95;token 应作为计算中的消息内容，而你的 Consumer Secret 是密钥。
* 如果响应无效，将停止向已注册的 webhook 发送事件。

**步骤 5：为每个 User Stream 或 Site Streams 授权用户创建订阅**

从 User Streams 迁移到 Account Activity API：

* 生成当前在 User Streams 上的用户订阅列表
* 使用以下请求设置新的 Account Activity API 订阅：  *POST account&#95;activity/all/:env&#95;name/subscriptions*
* 使用以下请求确认你的 Account Activity API 订阅：  &#95;GET account&#95;activity/all/:env&#95;name/subscriptions/list
   &#95;

从 Site Streams 迁移到 Account Activity API（使用控制流）：

* 使用以下请求生成当前在 Site Streams 上的订阅列表：  *GET /1.1/site/c/:stream&#95;id/info.json*
* 使用以下请求设置新的 Account Activity API 订阅：  *POST account&#95;activity/all/:env&#95;name/subscriptions*
* 使用以下请求确认你的 Account Activity API 订阅：  &#95;GET account&#95;activity/all/:env&#95;name/subscriptions/list
   &#95;

注册 Webhook 并创建订阅（不是从 Site Streams 或 User Streams 迁移）

* 使用 [POST webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#enterprise-account-activity-api) 在你的 App 中注册 webhook URL，并获取一个 webhook&#95;id。
* 使用返回的 webhook&#95;id 通过 [POST webhooks/:webhook&#95;id/subscriptions/all](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#post-account-activity-webhooks-webhook-id-subscriptions-all) 添加用户订阅。

<div id="sending-direct-messages">
  ### 发送私信（Direct Messages）
</div>

[POST direct&#95;messages/events/new](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/new-event) 是用于发送私信（Direct Messages）的直接替代接口。这个端点最大的区别在于，现在所有信息都作为 JSON 放在 POST 请求体中发送，而不再是作为单独的 POST 参数发送。

**Twurl 请求示例**

```bash
twurl -A 'Content-type: application/json' -X POST /1.1/direct\_messages/events/new.json -d '{"event": {"type": "message\_create", "message\_create": {"target": {"recipient\_id": "4534871"}, "message_data": {"text": "Hello World!"}}}}'
```

请注意，在上述请求中，`Content-Type` 被设置为 `application/json`，而不是 `application/x-www-form-urlencoded`。另外，如果你在构造 `OAuth 1.0a` 签名，要注意 JSON 请求体不会参与签名计算。大多数 OAuth 库已经考虑到了这一点。如果你在使用 [twurl](https://github.com/twitter/twurl)，请确保使用的版本至少为 0.9.3。

<div id="summary">
  #### 摘要
</div>

* 私信定义在 JSON POST 请求体中
* 必须将 Content-Type 请求头设置为 application/json
* JSON 请求体不参与 OAuth 签名的生成
   

<div id="retrieving-direct-messages">
  ### 检索私信
</div>

现在可以通过单个 API 端点来检索历史私信：[GET direct&#95;messages/events/list](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events)。这个新端点的一个重要变化是，它现在会按时间倒序返回已发送和已接收的消息，这有助于你更方便地重建一段会话。不过，如果你只想获取已发送或已接收的消息，则需要在响应中根据 `sender_id` 属性进行后处理。

分页现在基于游标值，而不是某条私信的 ID。每个响应中都会返回一个游标属性。[GET direct&#95;messages/events/list](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/list-events) 最多会返回过去 30 天的历史消息，而不管这 30 天内存在多少条消息。如果未返回游标，则表示没有更多消息可返回。通过 [GET direct&#95;messages/events/show](https://developer.x.com/en/docs/x-api/v1/direct-messages/sending-and-receiving/api-reference/get-event) 访问单条私信的方法保持不变，不过返回的私信对象结构已如前文所述发生变化。

最后，实时访问私信现在将通过使用 webhook 的 [Account Activity API](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity) 来实现。有关从 User Streams 或 Site Streams 迁移的指导，请参阅 Account Activity API 的迁移指南以获取更多信息。

#### 概述

* 发送和接收的消息现在通过同一个端点返回。
* 最多可返回最近 30 天内的消息。
* 基于游标的分页。
* 通过 webhook 实时访问私信。

<div id="deleting-direct-messages">
  ### 删除私信
</div>

现在可以使用 DELETE direct&#95;messages/events/destroy 删除私信。接口在很大程度上保持不变，仍然需要要删除消息的 ID。主要区别在于该端点现在需要使用 DELETE 请求，而不是 POST 请求。

已删除私信在官方 X 客户端中的呈现方式保持不变。私信只会在所提供用户上下文对应的界面中被移除，会话中的其他成员仍然可以访问该私信。

<div id="summary">
  #### 摘要
</div>

* 删除一条私信需要提供 ID。
* 新的端点需要使用 DELETE 请求。
* 已删除私信在官方 X 客户端中的呈现方式保持不变。

  ## 常见问题解答

<div id="general">
  ### 常规
</div>

**使用 Account Activity API 有哪些优势？**

Account Activity API 使用 webhooks，这意味着与流式 API 不同，我们不需要你保持一个打开的连接来向你发送信息。Webhooks 也不同于 REST API，因为你不必每 15 分钟轮询我们的服务器数百次来获取你关心的数据。它可以在事件发生时推送数据，从而提升用户与你的 App 之间的数据传输效率。

Account Activity API 具有以下优势：

1. **速度**：我们以 X 的速度向你传递数据。
2. **简洁**：我们通过单一 webhook 连接向你传递某个账号的所有事件。API 中投递的活动包括帖子、@ 提及、回复、转发（Retweets）、引用推文（Quote Tweets）、对引用推文的转发、收藏、发送的私信、接收的私信、关注、拉黑、静音。
3. **可扩展性**：你可以接收所管理账号的全部活动，而不会受到任何速率限制或事件上限的约束。

Account Activity API 以高级沙盒、高级付费和企业产品形式提供，因此当你需要为更多账号启用合规性功能或额外功能时，可以按需扩展。

开始使用时，可以从 [GitHub](https://github.com/xdevplatform/account-activity-dashboard) 下载示例代码片段。
 

**如何确定哪个产品层级最适合我？**

请阅读我们的 [Account Activity API Overview](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity) 页面，了解高级（Premium）选项与企业（Enterprise）选项之间的差异。 
 

**高级环境和企业 webhook 有什么区别？**

没有区别。每个高级环境都会有自己专属的 webhook&#95;id。
 

**我需要为 Account Activity API 准备开发、预发布和生产环境，这可以实现吗？**

可以！在 Account Activity API 的付费层级（付费高级和企业）中，可以注册多个 webhook URL，并通过 API 方法分别管理每个环境的订阅。此外，可以将多个客户端 App 加入允许列表（allowlist），以便为当前已授权用户维持授权状态。
 

**是否有关于如何配置 Account Activity API 的分步指南？**

确实有！

* 如果你刚刚开始使用，我们建议访问 [Getting started with webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks) 指南

* 还可以配合使用我们由 X Dev 提供支持的脚本： 
  * [Account Activity API dashboard](https://github.com/xdevplatform/account-activity-dashboard)，一个用于展示 webhook 事件的 Node Web App。
  * [SnowBot chatbot](https://github.com/xdevplatform/SnowBotDev)，一个基于 Account Activity 和 Direct Message API 构建的 Ruby Web App。该代码库包含一个用于帮助配置 Account Activity API webhooks 的[脚本](https://github.com/xdevplatform/SnowBotDev/wiki/Account-Activity-API-setup-script)。
     

**如果我们的系统在一段时间内宕机，有办法恢复数据吗？**

在 Account Activity API 的付费层级（付费高级和企业）中，我们的系统会在 4 小时内[重试](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)多次向你发送这些活动。如果你的系统在这 4 小时内始终没有响应，那么该活动将会丢失，你需要在 7 天内通过其他 REST 端点来恢复数据。

我们建议你将不同的 webhooks 或环境作为冗余工具来使用，例如 [Account Activity Replay API](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-replay-api)，以确保在某个系统宕机时你不会错过任何活动。 

**使用 Account Activity API 需要哪种身份验证方式？**

Account Activity API 所需的授权方式在各个方法的 [API 参考页面](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#account-activity-api-reference-index) 中分别进行了说明。如果你刚开始使用 X 身份验证，我们建议你阅读[此部分](/zh/resources/fundamentals/authentication)。

**什么是 challenge-response check（CRC）？**

Account Activity API 质询响应校验是一项安全功能，用于确保 Account Activity API 的活动数据被发送给正确的开发者。开发者也可以用它来确保自己接收到的数据确实来自 X。自上次验证 webhook URL 起，X 会每 24 小时自动向你的 webhook URL 发送一次 CRC。你的系统必须在 3 秒内返回一个有效响应，才能保持验证状态。 

有关更多详情，请访问我们的页面 [保护 webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#securing-webhooks)。
 

**有没有什么情况会立刻使我的 webhook URL 失效？**

如果发生以下任一情况，我们会立即将你的 webhook 标记为无效：

* 服务器对 CRC 的响应令牌不正确。在这种情况下，我们的系统不会[重试](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)向你发送活动。
* webhook URL 配置了不正确的证书。在这种情况下，我们的系统不会[重试](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#retries)向你发送活动。
* 你的服务器返回的响应状态码不是 2XX、4XXX 或 5XXX。
* 你声明使用 gzip，但实际上并未使用 gzip 发送。
* 你没有声明使用 gzip，但实际上在响应中使用了 gzip 发送。
   

**如果我订阅的用户之间互相互动，我会收到重复的活动吗？**

会的。如果你的 Web 应用为用户 A 和用户 B 都建立了有效订阅，当用户 A 在帖子中提及用户 B 时，会向已注册的 webhook 发送两个 POST 活动。每个活动都会包含一个 &quot;for&#95;user&#95;id&quot; 指示器，用于表明该活动属于哪个订阅。
 

**当我为我的 webhook 创建订阅时，能否将以下端点中的 `/all/` 部分替换为其他账号活动数据对象，从而限制 API 投递的活动？**`POST https://api.x.com/1.1/account_activity/all/:env_name/subscriptions.json`

不能，目前这是不可能的。就目前而言，我们只提供 `/all/` 产品。
 

**有没有办法在不向用户请求私信（Direct Messages）权限的情况下使用 Account Activity API？**

目前必须请求私信权限，因为在此 API 中没有办法“过滤掉”与私信相关的活动。 
 

**Account Activity API 是否有沙箱版本？**

有的，我们提供用于测试的沙箱选项。沙箱选项限制为单个 webhook，且最多只能有 15 个订阅。你可以在[我们的文档](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity)中阅读有关沙箱选项的更多信息。 

**能否使用 Account Activity API 获取提及已订阅用户的帖子的转发（Retweet）？**

很遗憾，这不属于此 API 投递的活动范围。为此，我们建议改用 Streaming API。 
 

**tweet&#95;create&#95;event 可以代表哪些可能的活动类型？**

在以下情况下会发送 tweet&#95;create&#95;event 负载（payload）：

如果订阅用户执行了以下任一操作：

* 创建帖子
* 转发（Retweet）
* 回复帖子

如果其他用户：

* @提及*订阅用户
* 引用由订阅用户创建的推文（Quote Tweet） 

*注意：Account Activity API 只会在订阅用户会从 X 收到通知且能公开看到事件时投递事件。这意味着，如果被提及账号（@userA）关注了受保护账号（@userB），那么 UserA 会收到 UserB 提及他们的通知。如果 UserA 没有关注 UserB（且未被 UserB 批准），UserA 将不会收到通知，因此如果 @userA 有订阅，就不会通过 AAA 发送 tweet&#95;create&#95;event。*

**如果被我订阅的用户拉黑的某个用户提及了我订阅的用户，我该如何识别这一情况？**

你会在 JSON 响应的顶层看到一个布尔字段 `user_has_blocked`，其值为 “true” 或 “false”。该字段只会在帖子提及时暴露。 

企业版

**我如何将我的 App 添加到 allowlist（允许列表）中，或检查我的 App 是否已经在 allowlist 中？**

要管理你已添加到允许列表以通过 Enterprise API 访问的 [X apps](/zh/resources/fundamentals/developer-apps)，请联系你的客户经理并提供你的应用 ID。你可以通过前往 [开发者控制台](/zh/resources/fundamentals/developer-portal)中的 [&quot;Apps&quot;](/zh/resources/fundamentals/developer-apps) 页面找到你的应用 ID。
 

**如果我有 3 个 webhook 配额，我是否可以为每个已注册为企业级使用的 App 使用 3 个 webhook？**

webhook 限制是设置在账号级别，而不是 App 级别。如果你有 3 个 webhook 的额度，并且有 2 个 App 注册为企业级使用，你可以在一个 App 上使用 2 个 webhook，在另一个 App 上使用第 3 个 webhook，但不能为每个 App 都使用 3 个 webhook。 

**我可以指定哪些类型的事件会通过 Account Activity Replay API 重新投递吗？**

不能指定要重放的事件类型。在所指定的日期和时间窗口内投递的所有事件都会被重放。 

**如果我的应用未能接收某个 Account Activity Replay API 事件，会进行重试吗？**

不会，不会进行任何重试。如果应用未能接收由 Account Activity Replay API 发送的事件，你可以针对同一时间段再次提交 Replay 任务，尝试重新投递任何遗漏的 Replay 事件。 

**当我收到部分成功的完成事件时，该怎么办？**

我们建议记录已接收到事件的时间戳，并为遗漏的事件再次请求一个 Replay 任务。 

**同一时间最多可以运行多少个 Account Activity Replay API 任务？**

每个 webhook 在任意时间点只能运行一个 Account Activity Replay API 任务。 

**当 Account Activity Replay API 将事件投递到我的 webhook 时，我如何区分这些事件与实时生产事件？**

由于 Account Activity Replay API 始终会投递过去的事件，因此可以根据事件的时间戳将其与实时生产事件区分开来。 

**在我的应用丢弃或错过某个 activity 之后，多快可以开始使用 Account Activity Replay API 重新投递该 activity？**

某个 activity 在创建后大约 10 分钟会变得可用于重新投递。

<div id="code-32">
  #### 代码 32
</div>

此错误通常意味着你在请求、请求头、授权信息或所指定的 URL 中有某些内容格式不正确。这不是 Account Activity API 的错误，而是授权错误，X 没有收到正确配置的 OAuth 或 URL。

* **Enterprise** - 请确保你使用的 consumer key 和 access token 属于已注册用于 Enterprise 产品的 [X App](/zh/resources/fundamentals/developer-apps)。如果你没有 consumer key 和 access token，或者需要将你的 X App 加入 allowlist，请联系你的客户经理。 

* 如果在用户上下文下进行认证，请确保你已使用正确的 `oauth nonce`、`oauth_signature` 和 `oauth_timestamp` [为请求授权](/zh/resources/fundamentals/authentication#authorizing-a-request)。

* 确保你的 access token 具有正确的权限级别。
  * 在 [app dashboard](/zh/resources/fundamentals/developer-apps) 的 “Keys and tokens” 标签页中，请确保你的 access token 拥有 “Read, write, and direct messages” [权限级别](/zh/resources/fundamentals/developer-apps#app-permissions)。 
  * 如果 token 的权限级别被设置为低于该级别，请转到 “Permissions” 标签页，将访问权限调整为 “Read, write, and direct messages”，然后在 “Keys and tokens” 标签页中重新生成你的 access token 和 secret。

* 确保你的 URL 格式正确。
  * 请注意，`:env_name` 区分大小写。
     

<div id="code-200-forbidden">
  #### 代码 200 - 禁止访问
</div>

* **Premium** - 在尝试向 API 发送请求之前，请确保你已经拥有已获批准的[开发者账号](/zh/resources/fundamentals/developer-portal)。你还必须在请求中使用正确的 :env&#95;name，并在 [dev environments](/zh/resources/fundamentals/developer-portal) 页面中进行设置。

* **Enterprise** - 请确保你的客户经理已经为你开通了对 Account Activity API 的访问权限。

* 请确保你已正确设置 URI。如果你在请求中填入了错误的 URI，可能会触发此错误。
   

<div id="code-214-webhook-url-does-not-meet-the-requirements">
  #### 代码 214 - Webhook URL 不符合要求。
</div>

* 请确保你使用的是 HTTPS。
* 你的 webhook URL 可能格式无效。
* 你可以在[开始使用 webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#getting-started-with-webhooks)页面的[开发 webhook consumer App](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#3-develop-webhook-consumer-app)部分了解如何设置你的 webhook URL。
   

<div id="code-214-high-latency-on-crc-get-request-your-webhook-should-respond-in-less-than-3-seconds">
  #### 代码 214 - CRC GET 请求延迟过高。你的 webhook 必须在 3 秒内返回响应。
</div>

* 这意味着你的服务器处理速度较慢。请确保你在 3 秒内对 CRC 做出响应。
   

<div id="code-214-non-200-response-code-during-crc-get-request-ie-404-500-etc">
  #### Code 214 - CRC GET 请求期间收到非 200 响应码（例如 404、500 等）。
</div>

* 你的服务器可能已宕机。请确保你的服务器正在正常运行。
   

<div id="code-214-too-many-resources-already-created">
  #### Code 214 - 已创建的资源数量过多。
</div>

* **Enterprise** - 您已用尽所有 webhook。请针对每个已注册的 App 调用 [GET webhooks](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#get-account-activity-webhooks) 端点，以确定这些 webhook 的分布位置。 

<div id="code-261-application-cannot-perform-write-actions">
  #### Code 261 - Application cannot perform write actions.
</div>

* 您通过 API 使用的 App 未为其 access token 和 access token secret 设置正确的[权限级别](/zh/resources/fundamentals/developer-apps#app-permissions)。请前往 [X apps](/zh/resources/fundamentals/developer-apps) 仪表板中的“Keys and tokens”选项卡，检查分配给您的 access token 和 access token secret 的权限级别。如果其设置为 “Read, write and Direct Messages” 以外的任何值，则需要在“Permission”选项卡下调整设置，并重新生成 access token 和 access token secret 以应用新的设置。
* 或者，您正在尝试使用仅 App 身份验证（app-only authentication）注册 webhook，这是不受支持的。请改为按照 [Enterprise Account Activity API](/zh/x-api/enterprise-gnip-2.0/fundamentals/account-activity#post-account-activity-webhooks) 中注册 webhook 的 API 参考部分所述，使用用户上下文进行身份验证。

<div id="replay-api">
  ### Replay API
</div>

**POST /1.1/account&#95;activity/replay/webhooks/:webhook&#95;id/subscriptions/all.json [¶](#post-1-1-account-activity-replay-webhooks-webhook-id-subscriptions-all-json- "Permalink to this headline")**

提交请求，从请求中指定的日期和时间窗口内存在的所有订阅中，检索过去最长五天内的活动。如果你的 webhook 具有活跃的用户订阅，你也会同时实时收到这些事件。注意：在投递回放事件之前，我们会先执行 CRC 校验。

|     |     |
| :--- | :--- |
| **Request Method** | HTTP POST |
| **URL** | /1.1/account&#95;activity/replay/webhooks/:webhook&#95;id/subscriptions/all.json?from&#95;date=yyyymmddhhmm&amp;to&#95;date=yyyymmddhhmm |
| **Response Format** | JSON |
| **Requires Authentication** | Yes (application only - Bearer 令牌) |
| **Rate Limit** | 每 15 分钟 5 个请求。目前对可请求的回放作业数量没有上限。 |
| **from&#95;date** | 提供事件的最早（起始）UTC 时间戳，必须使用“yyyymmddhhmm”格式。时间戳的粒度为分钟，并且是包含性的（例如 12:00 包含第 0 分钟）。有效时间必须是过去 5 天内的 UTC 时间，且不能晚于当前时间点之前 31 分钟。建议 from&#95;date 和 to&#95;date 之间的间隔控制在约 2 小时内。 |
| **to&#95;date** | 提供事件的最晚（结束）UTC 时间戳，必须使用“yyyymmddhhmm”格式。时间戳的粒度为分钟，并且是排他性的（例如 12:30 不包含该小时的第 30 分钟）。有效时间必须是过去 5 天内的 UTC 时间，且不能晚于当前时间点之前 10 分钟。 |

<div id="overview">
  ## 概览
</div>

`Enterprise`

*企业版 API 仅在我们的受管访问级别内提供。要使用这些 API，您必须先通过我们的企业销售团队开通账户。要了解更多信息，请参见 [此处](https://developer.x.com/en/products/x-api/enterprise)。*

*您可以在[此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/search-api)查看所有 X API 搜索帖子功能。*

有两个企业搜索 API：

1. 30-Day Search API 提供过去 30 天的数据。
2. Full-Archive Search API 提供对完整 X 数据语料库的全面、即时访问，最早可追溯到 2006 年 3 月发布的第一条帖子。

这些 RESTful API 每次请求支持一条最长 2,048 个字符的查询。查询使用 PowerTrack 规则语法编写——更多详情请参见 [规则和过滤](/zh/x-api/enterprise-gnip-2.0/fundamentals/rules-filtering#getting-started-with-enterprise-rules-and-queries)。用户可以指定任意时间范围，精确到分钟级。不过，响应将受限于您指定的 maxResults 或 31 天中较小的一方，并包含一个 next 令牌，用于分页获取下一批结果。如果未指定时间参数，API 将返回最近 30 天内的匹配数据。

企业搜索 API 以分钟粒度提供对帖子存档的低延迟、高保真、基于查询的访问。帖子数据按时间倒序返回，从与您的查询匹配的最新帖子开始。帖子通常在发布约 30 秒后即可通过搜索 API 获取。

这些搜索端点提供已编辑帖子的元数据。自 2022 年 9 月 29 日起创建的所有帖子对象都包含帖子编辑元数据，即使该帖子从未被编辑。每次帖子被编辑时，都会创建一个新的帖子 ID。帖子的编辑历史记录在一个帖子 ID 数组中，从原始 ID 开始。

这些端点始终返回最新的编辑版本以及完整的编辑历史。在帖子 30 分钟的可编辑窗口结束后收集到的任何帖子都将表示其最终版本。要了解有关编辑帖子元数据的更多信息，请查看 [编辑帖子基础知识](/zh/x-api/fundamentals/edit-posts)页面。

请求中包含一个 maxResults 参数，用于指定每个 API 响应要返回的最大帖子数。如果与查询关联的帖子数量超过每个响应允许的最大结果数，响应中会包含一个 next 令牌。这些 next 令牌会在后续请求中使用，以分页获取与该查询关联的全部帖子集合。

这些企业搜索 API 提供一个 *counts* 端点，使用户能够请求与其查询相关的数据量。 

<div id="request-types">
  ### 请求类型
</div>

企业搜索 API 支持以下两种请求类型：

<div id="search-requests-data">
  #### 搜索请求（data）
</div>

针对企业搜索 API 的搜索请求，允许你在指定的时间范围内，每个响应最多检索 500 条结果，并可以通过分页获取更多 data。通过 `maxResults` 参数，你可以为展示类用例指定较小的分页大小（允许用户按需请求更多结果），也可以为大批量 data 拉取指定较大的分页大小（最多 500）。data 按时间倒序返回，并在交付时保持合规。

<div id="counts-requests-post-count">
  #### 计数请求（帖子计数）
</div>

计数请求用于检索历史活动次数统计，这些统计反映在所请求的时间范围内满足给定查询条件的活动发生次数。响应本质上会提供一个按天、小时或分钟划分时间桶的计数直方图（默认时间桶为“小时”——*hour*）。需要特别注意的是，计数结果并不总是会反映在帖子发布很久之后（7 天以上）才发生的合规事件（例如帖子删除）；因此，可以预期计数指标不一定总能与针对相同查询发起的数据请求结果一致。

**计费说明：** 针对 data 和 counts 端点发起的每个请求——*包括分页请求*——都将计为一条计费请求。因此，如果单个查询存在多页结果，翻页浏览 X 页结果在计费上就等同于发起了 X 次请求。

<div id="data-availability-important-date">
  ### 数据可用性 / 重要日期
</div>

在使用 Full-Archive 搜索 API 时，请记住，自 2006 年以来，X 平台一直在不断演进。随着新功能的加入，底层 JSON 对象也不断新增元数据。因此，了解搜索算子所匹配的帖子属性是从何时开始可用的非常重要。下面列出了一些重要元数据分组较为基础的“诞生”日期。要进一步了解帖子属性最初何时引入，请参阅[本指南](/zh/x-api/enterprise-gnip-2.0/fundamentals/search-api#full-archive-search-metadata-timeline)。  

* 第一条帖子：2006 年 3 月 21 日
* 首次原生转发：2009 年 11 月 6 日
* 第一条带地理标签的帖子：2009 年 11 月 19 日
* 首次对 URL 建立索引用于过滤：2011 年 8 月 27 日
* 增强的 URL 展开元数据（网站标题和描述）：2014 年 12 月 1 日
* 个人资料地理信息增强元数据及过滤：2015 年 2 月 17 日

<div id="data-updates-and-mutability">
  ### 数据更新与可变性
</div>

在企业搜索 API 中，帖子中的部分数据是可变的，即在初次归档之后可以被更新或更改。

这些可变数据主要分为两类：

* 用户对象的元数据：
  * 用户的 @handle（数字 id 永不改变）
  * 个人简介
  * 计数：statuses、followers、friends、favorites、lists
  * 个人资料中的位置
  * 其他详情，例如时区和语言
* 帖子统计数据——即任何可以通过用户在平台上的操作而发生改变的内容（如下示例）：
  * Favorites 计数（点赞数）
  * Retweet 计数（转发数）

在上述大多数情况下，搜索 API 会返回在&#95;查询时&#95;平台上存在的最新数据，而不是帖子生成时的数据。然而，对于使用选择类运算符（例如 from、to、@、is:verified）的查询，情况可能并非如此。我们的索引会定期更新，对最近时间范围的更新频率更高。因此，在某些情况下，返回的数据可能与 X.com 上当前展示的数据不完全一致，而是与其上次被索引时的数据一致。

注意，这种不一致性问题只适用于运算符作用于可变数据的查询。例如按用户名进行过滤时，最佳的变通办法是对于这类查询使用用户的数字 id，而不是 @handle。

<div id="single-vs-multi-threaded-requests">
  ### 单线程请求与多线程请求
</div>

每个客户的搜索 endpoint 都有明确的速率上限。Full-Archive 搜索的默认每分钟速率上限为 120 个请求，平均为每秒 2 个查询（QPS）。这个平均 QPS 意味着，理论上每秒可以向 API 发出 2 个请求。鉴于产品的分页功能，如果某个一年期的查询有一百万条与之关联的帖子，并且在这一年中均匀分布，那么要接收所有数据将需要 2,000 多个请求（假设 `maxResults` 为 500）。假设每个响应耗时 2 秒，那就是 4,000 秒（略多于一小时），通过单个线程（使用前一个响应的 “next” token，以每秒 1 个请求的速率）串行/顺序地拉取所有这些数据。还不错！

现在再考虑使用 12 个并行线程来接收数据的情况。假设这一百万条帖子在一年的时间里分布均匀，你可以将这些请求拆分为 12 个并行线程（多线程），从而在单个 “job” 上更多地利用每秒的速率上限。换句话说，你可以针对感兴趣的每一个月运行一个线程，这样数据的检索速度可以提升 12 倍（大约 6 分钟）。

这个多线程示例同样适用于 counts endpoint。比如，如果你想要获取两年时间范围内的帖子计数，你可以发出单线程请求，并一次回溯 31 天的计数。假设每个响应耗时 2 秒，那么发出 24 个 API 请求并检索到整个计数集大约需要 48 秒。不过，你也可以选择同时发出多个单月请求。当每秒发出 12 个请求时，整个计数集大约可以在 2 秒内检索完毕。

<div id="retry-logic">
  ### 重试逻辑
</div>

如果你在使用企业搜索 API 时遇到 503 错误，这很可能是一个临时错误，可以在稍后重新发起请求来解决。

如果请求连续失败 4 次，并且每次失败之间你都至少等待了 10 分钟，请按照以下步骤进行排查：

* 缩短请求所覆盖的时间范围后重试。如果仍然不成功，重复此操作，直到将时间窗口缩小到 6 小时。
* 如果你使用 OR 将大量搜索词连接在一起，将它们拆分为单独的规则，并分别重试每个规则。
* 如果你在规则中使用了大量排除条件，请减少规则中否定搜索词的数量并重试。

<div id="getting-started-with-enterprise-search-posts-30-day-api">
  ### 企业级 Search Posts: 30-Day API 入门
</div>

enterprise Search Posts: 30-Day API 会返回过去 30 天内发布的帖子。系统会根据你在请求中指定的查询来匹配帖子并返回给你。查询是一条规则，你可以在其中定义返回的帖子应当包含的内容。在本教程中，我们将搜索来自 X 账号 @XDevelopers、语言为英文的帖子。

你在响应负载中获取的帖子可以是 `data` 格式，它会提供完整的帖子负载；也可以是 counts 格式，它会提供匹配帖子的数值统计数据。我们将使用 cURL 向 data 和 counts 端点发起请求。

你需要准备以下内容：

* [企业级账户]https://developer.x.com/en/products/x-api/enterprise
* 你的用户名、密码和账户名称
* 与搜索端点关联的标签（Label），可在 console.gnip.com 中查看

<div id="accessing-the-data-endpoint">
  #### 访问 data 端点
</div>

data 端点会向我们提供所有匹配帖子（Post）的完整负载。我们将使用 `from:` 和 `lang:` 运算符来查找来自 @XDevelopers 的英文帖子。*如需查看更多运算符，[请点击此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/search-api#enterprise-operators)。*

<Tabs>

    根据以下内容进行替换后，将下面的 cURL 请求复制到命令行中：

    * **Username** `<USERNAME>` 例如 `email@domain.com`

<div id="product-overview">
  ### 产品概览
</div>

企业级（enterprise）的 Full-archive Search 于 2015 年 8 月推出，高级版（premium）则于 2018 年 2 月推出。这些搜索产品使客户能够即时访问任意公开可用的帖子。使用 Full-archive Search 时，你只需提交一个查询，就会以经典的 RESTful 方式收到一个响应。Full-archive Search 实现了最多每个响应返回 500 条帖子的分页，并支持高级版每分钟最多 60 次请求（rpm）的速率限制，企业版为每分钟 120 次请求。基于这些特性，Full-archive Search 可用于快速检索帖子，并可通过并发请求在大规模场景下使用。

与基于磁盘上一组帖子平面文件（flat-files）构建归档的 Historical PowerTrack 不同，Full-archive Search 的帖子归档更类似于一个在线数据库。与所有数据库一样，它支持对其内容进行查询。它还使用一个 *index* 来实现高性能数据检索。在 Full-archive Search 端点中，查询语言由 PowerTrack Operators 组成，这些 Operators 分别对应一个已建立索引的帖子 JSON 属性。

同样地，与 Historical PowerTrack 一样，也存在以发起查询时为准的帖子属性。例如，如果你今天使用 Search API 访问一条 2010 年发布的帖子，那么用户的个人资料描述、账户“home”位置、显示名称，以及该帖子的收藏（Favorites）和转发（Retweet）计数等指标，都会更新为今天的值，而不是 2010 年时的数值。 

<div id="metadata-timelines">
  ### 元数据时间线
</div>

下面是 Full-Archive Search 端点运算符开始匹配的时间线。在某些情况下，运算符开始匹配的时间远晚于某种“交流约定”在 X 上成为常规用法的时间。例如，@Replies 作为一种用户约定在 2006 年就出现了，但直到 2007 年初才通过带有“支持性” JSON 的形式成为&#95;一等对象&#95;或&#95;事件&#95;。因此，要在 2006 年匹配 @Replies，需要检查帖子正文内容，而不是依赖 `to:` 和 `in_reply_to_status_id:` PowerTrack 运算符。

这里提供的细节是使用 Full-Archive Search 生成的（基于数百次搜索的结果）。该时间线并非 100% 完整或精确。如果你发现了对你的用例至关重要的其他过滤条件/元数据的“诞生日期”，请告知我们。

请注意，底层搜索索引可能会被重建。因此，这些时间线中的细节可能会发生变化。

<div id="filtering-tips">
  ### 过滤技巧
</div>

结合以上所有时间线信息，在编写 Search API 过滤条件时，很明显需要考虑大量细节。需要重点考虑两点：

* 某些元数据有“启用日期”，因此过滤可能会产生&#95;假阴性&#95;（漏检）。这类搜索包括依赖于在整个或部分搜索时间段内并不存在的元数据的 Operators。比如，如果你使用 `has:images` Operator 搜索帖子，在 2011 年 7 月之前的时间段中将不会有任何匹配结果。这是因为该 Operator 匹配的是&#95;原生&#95;照片（通过 X 用户界面附加到帖子的照片）。若要获得更完整的照片分享帖子数据集，对 2011 年 7 月之前的时间段进行过滤时，需要在规则中加入能够匹配常见照片托管 URL 的子句。
* 某些元数据是在帖子在 X 上发布&#95;之后&#95;的某个时间点，通过回填方式补充上的。

在创建 PowerTrack 查询时，通常会重点关注以下几类属性类型：

* X 个人资料
* 原创或被分享的帖子
* 帖子语言分类
* 带地理位置信息的帖子
* 链接中所含媒体

其中一些具有产品特有的行为，另一些则行为相同。详情见下文。

<div id="x-profiles">
  #### X 个人资料
</div>

Search API 返回历史帖子时，会使用&#95;检索时刻&#95;的用户个人资料数据集。如果你请求一条 2014 年发布的帖子，该用户的个人资料元数据将反映其在查询时的状态。

<div id="original-posts-and-retweets">
  #### 原始帖子和转推
</div>

PowerTrack `_is:retweet_` 运算符让用户可以选择包含或排除转推。使用该运算符的用户需要针对 2009 年 8 月之前的数据，制定两种关于转推匹配（或不匹配）的策略。对于 2009 年 8 月之前的时间段，需要在帖子内容本身中，通过精确短语匹配检查是否符合“@RT ”模式（实际上，如果要过滤 2009 年 5 月至 8 月间的转推，还应包含“Via @”模式）。对于 2009 年 8 月之后的时间段，则可以使用 *is:retweet* 运算符。

<div id="post-language-classifications">
  #### 帖子语言分类
</div>

在根据帖子语言分类进行过滤时，X 的历史产品有较大差异。构建搜索存档（Search archive）时，所有帖子都使用 X 的语言分类进行了回填。因此，`lang:` 运算符可用于整个帖子存档。

<div id="geo-referencing-posts">
  #### 帖子的地理关联
</div>

为帖子建立地理关联主要有三种方式：

* **帖子内容中的地理引用。** 在帖子内容中基于地理相关引用进行匹配，尽管通常是最具挑战性的方法，因为它依赖于本地背景知识，但这是适用于整个帖子存档的一种方式。[此处](https://x.com/biz/statuses/28311) 是一条 2006 年关于旧金山地区的地理关联匹配示例，基于 “golden gate” 过滤条件进行匹配。

* **由用户给帖子添加地理标签。** 使用搜索 API，从 2010 年 3 月开始可以通过部分 Geo Operators 对帖子进行匹配，2015 年 2 月又新增了其他运算符：

  * 2010 年 3 月 6 日：`has:geo`、`bounding_box:` 和 `point_radius:`
  * 2015 年 2 月 17 日：`place_country:` 和 `place:`

* **由用户在账号资料中设置的 “home” 位置。** Profile Geo Operators 在 Historical PowerTrack 和 Search APIs 中均可用。对于 Search APIs，这些 Profile Geo 元数据从 2015 年 2 月开始可用。对于在 Profile Geo 元数据可用之前发布的帖子，可以使用 `bio_location:` Operator 来匹配未规范化的用户输入。

<div id="shared-links-and-media">
  #### 分享的链接和媒体
</div>

2012 年 3 月，引入了扩展 URL 富化（expanded URL enrichment）功能。在此之前，帖子载荷中只包含用户提供的 URL。因此，如果用户使用了短链接，要匹配到目标的（展开后的）URL 会比较困难。通过 Search API，这些元数据从 2012 年 3 月开始可用。

2016 年 7 月，引入了增强 URL 富化（enhanced URL enrichment）功能。这个增强版本会在帖子载荷中提供网站的 HTML 标题和描述，并提供用于匹配这些内容的搜索运算符（Operators）。这些元数据从 2014 年 12 月开始出现。

2016 年 9 月，X 引入了“原生附件”，当结尾的分享链接作为原生附件时，不再计入 140 字符的帖子长度限制。这两种 URL 富化仍然适用于这些分享链接。

以下是相关搜索运算符开始匹配的时间：

* 2006 年 10 月 26 日 - `has:links`
* 2011 年 7 月 20 日 - `has:images` 和 `has:media`
* 2011 年 8 月 - `url:` 配合 [Expanded URLs enrichment](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments)。早在 2006 年 9 月，`(url:"spotify.com" OR url:gnip OR url:microsoft OR url:google OR url:youtube)` 就可以匹配到 http://x.com/Adam/statuses/16602，即便在 twitter&#95;entities 和 gnip objects 中没有任何 urls[] 元数据。“youtube.com” 就是一个示例：即使没有任何 urls[] 元数据，它仍然可以匹配 url:youtube。
* 2015 年 2 月 10 日 - 原生视频的 `has:videos`。在 2010/08/28 到 2015/02/10 之间，此运算符会匹配带有指向特定视频托管站点（如 youtube.com、vimeo.com 和 vivo.com）链接的帖子。
* 2016 年 5 月 1 日 - 基于 [Enhanced URLs enrichment](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments) 的 `url_title:` 和 `url_description:` 全面可用。首批增强 URL 元数据在 2014 年 12 月开始出现。

  <Accordion title="通过 data endpoint 返回的帖子数量，与 counts endpoint 统计到的帖子数量不一致。为什么会这样？">
    `counts` 端点与 `data` 端点返回的结果之间存在已知差异。你可能会在结果中看到不一致，这是因为 `counts` 端点是在合规处理之前统计的（也就是说，它不会将已删除的帖子、地理位置清除（scrub geo）等因素计入在内），而 `data` 端点在数据交付时已经过合规处理，并会计入所有合规事件。

    这种情况可能有几种不同的原因，包括：

    1. 你本期待看到的帖子来自受保护的账号
    2. data 端点会对所有合规事件进行处理（也就是说，被删除的帖子、被清除的地理信息等将不会包含在响应中）。
  </Accordion>

<div id="enterprise-search-apis">
  ### 企业搜索 API
</div>

有两个企业搜索 API：

* 30-Day Search API - 提供过去 30 天内发布的推文。
* Full-Archive Search API - 提供最早可追溯至 2006 年的推文，从 2006 年 3 月发布的第一条推文开始。

这些搜索 API 采用相同的设计，下面的文档适用于二者。请注意，对于在 2022 年 9 月 29 日之后创建的推文，Tweet 对象将包含描述其编辑历史的 Tweet 编辑元数据。有关更多详细信息，请参阅 [&quot;Edit Tweets&quot;](/zh/x-api/enterprise-gnip-2.0/fundamentals/edit-tweets) 基础知识页面。

下面是与企业搜索 API 集成时所需的重要细节：

* 请求推文数据及其计数的方法
* 身份验证
* 分页
* API 请求参数和请求示例
* API 响应 JSON 载荷和响应示例
* HTTP 响应代码

企业 API 提供低延迟、完整且高保真的、基于查询的推文归档访问。两个 API 唯一的区别是可搜索的时间范围：要么是过去 30 天，要么是最早从 2006 年开始。时间范围可以精确到分钟。推文数据以时间倒序返回，从与查询匹配的最新推文开始。推文在发布后大约 30 秒即可通过搜索 API 获取。

<div id="methods">
  #### 方法
</div>

企业搜索的基础 URI 为 `https://gnip-api.x.com/search/`。

| Method | Description |
| :--- | :--- |
| [POST /search/:product/accounts/:account&#95;name/:label](#SearchRequests) | 获取过去 30 天内与指定 PowerTrack 规则匹配的推文。 |
| [POST /search/:product/accounts/:account&#95;name/:label/counts](#CountRequests) | 获取过去 30 天内与指定 PowerTrack 规则匹配的推文数量。 |

其中：

* `:product` 表示你正在请求的搜索端点，即 `30day` 或 `fullarchive`。
* `:account_name` 是与你的账户关联的名称（区分大小写），如 console.gnip.com 中所显示。
* `:label` 是与你的搜索端点关联的标签（区分大小写），如 console.gnip.com 中所显示。

例如，如果 TwitterDev 账户已开通 30 天搜索产品，并使用标签 &#39;prod&#39;（production 的缩写），则搜索端点为：

* 数据端点: [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json)
* 计数端点: [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json)

你的完整企业搜索 API 端点会显示在 [https://console.gnip.com](https://console.gnip.com)。

下面是使用一个名为 curl 的简单 HTTP 工具的一些请求示例。这些示例在 URL 中使用 `:product`、`:account_name` 和 `:label`。要使用这些示例，请务必将 URL 更新为你的实际信息。

<div id="authentication">
  #### 身份验证
</div>

所有对企业搜索 API 的请求都必须使用 HTTP *Basic Authentication*，其凭据由用于登录您在 [https://console.gnip.com](https://console.gnip.com) 上账户的有效电子邮件地址和密码组合构成。凭据必须在每个请求中通过 *Authorization* 请求头传递。

<div id="requestresponse-behavior">
  #### 请求与响应行为
</div>

通过使用 `fromDate` 和 `toDate` 参数，你可以请求 API 所支持的任意时间范围。30-Day search API 提供最近 31 天内的推文（尽管被称为 “30-Day” API，它实际上提供 31 天的数据，以便用户可以发起完整自然月的请求）。Full-Archive search API 则提供从第一条推文（2006 年 3 月 21 日）开始的所有推文。不过，单个响应会被限制在你指定的 `maxResults` 或 31 天这两者中较小的那个范围内。如果匹配到的数据量或你的时间范围超过了你指定的 `maxResults` 或 31 天，你将会收到一个 `next` 令牌，你应该使用它在你指定的时间范围内继续分页获取剩余数据。

例如，假设你使用 Full-Archive search，并希望获取 2017 年 1 月 1 日到 2017 年 6 月 30 日期间所有与查询匹配的推文。你需要在请求中通过 `fromDate` 和 `toDate` 参数指定这整整六个月的时间范围。搜索 API 会返回第一“页”推文，其推文数量由你指定的 `maxResults` 参数决定（默认值为 100）。假设还有更多推文（而且很可能会有更多），API 还会返回一个 `next` 令牌，使你能够发起请求以获取下一“页”的数据。这个过程会反复进行，直到 API 不再返回 `next` 令牌为止。有关更多详情，请参见下一节。

<div id="pagination">
  #### 分页
</div>

当发起数据请求和计数请求时，返回的数据很可能多于单个响应所能包含的内容。在这种情况下，响应会包含一个 `next` 令牌。`next` 令牌作为顶层 JSON 属性提供。每当返回 `next` 令牌时，表示还有更多数据可供检索，因此你需要继续发起 API 请求。

**注意：** `next` 令牌在数据请求和计数请求中的行为略有不同，这两种情况都会在下文中说明，并在 API 参考部分提供示例响应。

<div id="data-pagination">
  ##### 数据分页
</div>

对数据的请求通常会返回超过单个响应所能包含的数据量。每个数据请求都包含一个参数，用于设置每次请求返回的最大推文数量。`maxResults` 参数的默认值为 100，可以设置在 10–500 的范围内。如果你的查询匹配的推文数量多于请求中使用的 `maxResults` 参数值，响应会包含一个 `next` 令牌（作为 JSON 根级属性）。这个 `next` 令牌会在后续请求中被使用，以检索该查询下一部分匹配的推文（即下一“页”）。系统会持续返回 `next` 令牌，直到你到达该查询结果的最后一“页”，此时将不会再提供 `next` 令牌。

要请求下一“页”数据，你必须发出与最初查询完全相同的请求，如果使用了 `query`、`toDate` 和 `fromDate` 参数，也必须一并包含，并额外添加一个 `next` 请求参数，其值设置为前一个响应中的 `next` 值。这既可以用于 GET 请求，也可以用于 POST 请求。但是，在 GET 请求的情况下，`next` 参数必须进行 URL 编码。

你可以持续传入前一次查询响应中的 `next` 元素，直到你收到了查询所覆盖时间段内的全部推文。当你收到一个不包含 `next` 元素的响应时，这意味着你已经到达最后一页，指定查询和时间范围内不再有其他可用数据。

<div id="counts-pagination">
  ##### Counts 分页
</div>

`counts` 端点会按天、按小时或按每分钟的粒度，提供与查询相关联的推文量。`counts` API 端点将返回一个带时间戳的计数数组，单次最多返回覆盖 31 天的计数数据。如果你请求超过 31 天的计数，将会返回一个 `next` 令牌。与 data 的 `next` 令牌一样，你必须发出与原始请求完全相同的查询，并在其中包含一个 `next` 请求参数，其值设置为上一个响应中的 `next` 令牌值。

除了请求超过 31 天的计数之外，还有另一种会返回 `next` 令牌的情况。对于数据量较大的查询，生成计数所需的时间可能足够长，从而触发响应超时。当发生这种情况时，你将会收到少于 31 天的计数，但会获得一个 `next` 令牌，以便继续发起请求以获取完整的计数数据。***重要提示：*** 超时只会返回完整的“bucket”（时间分桶）——因此 2.5 天将会返回 2 个完整天数的“bucket”。

<div id="additional-notes">
  ##### 其他说明
</div>

* 在搜索请求中使用 fromDate 或 toDate 时，你只会获得位于该时间范围内的结果。当你到达该时间范围内最后一组结果时，将不会再收到 `next` 令牌。
* `next` 元素可以与 10–500 之间的任意 maxResults 值一起使用（默认值为 100）。maxResults 决定每个响应中返回的推文数量，但不会阻止你最终获取全部结果。
* `next` 元素不会过期。使用相同 `next` 查询多次发出的请求，不论发出请求的时间如何，都会收到相同的结果。
* 在使用 `next` 参数对结果进行分页时，你可能会在查询边界处遇到重复结果。你的应用程序应当能够容忍这些重复。

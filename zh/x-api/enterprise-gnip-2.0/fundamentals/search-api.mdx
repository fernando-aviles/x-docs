<div id="overview">
  ## 概览
</div>

`Enterprise`

*企业版 API 仅在我们的托管访问级别下提供。要使用这些 API，您必须先与我们的企业销售团队创建账户。要了解更多信息，请参阅 [此处](https://developer.x.com/en/products/x-api/enterprise)。*

*您可以在[此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/search-api)查看所有 X API 搜索帖子产品。*

共有两个企业版搜索 API：

1. 30-Day Search API 提供最近 30 天内的数据。
2. Full-Archive Search API 提供对 X 全量数据存档的完整、即时访问，数据可追溯到 2006 年 3 月发布的第一条帖子。

这些 RESTful API 在每个请求中支持长度最多为 2,048 个字符的单个查询。查询使用 PowerTrack 规则语法编写——有关更多详细信息，请参阅 [规则和过滤](/zh/x-api/enterprise-gnip-2.0/fundamentals/rules-filtering#getting-started-with-enterprise-rules-and-queries)。用户可以精确到分钟级别指定任意时间段。不过，响应会被限制为您指定的 `maxResults` 或 31 天（取较小值），并在响应中包含用于获取下一批结果的 next token。如果未指定时间参数，API 将返回最近 30 天内的匹配数据。

企业版搜索 API 以分钟粒度提供对帖子存档的低延迟、全保真、基于查询的访问。帖子数据按时间倒序返回，从与您的查询匹配的最新帖子开始。帖子在发布后大约 30 秒即可通过搜索 API 获取。

这些搜索端点提供编辑帖子元数据。自 2022 年 9 月 29 日创建的所有帖子对象都包含帖子编辑元数据，即使该帖子从未被编辑。每次帖子被编辑时，都会创建一个新的 Post ID。帖子的编辑历史由一个 Post ID 数组记录，从原始 ID 开始。

这些端点将始终返回最新编辑版本以及任何编辑历史。任何在 30 分钟编辑窗口结束后被收集的帖子都将代表其最终版本。要了解有关编辑帖子元数据的更多信息，请查看 [编辑帖子基础知识](/zh/x-api/fundamentals/edit-posts)页面。

请求中包含一个 `maxResults` 参数，用于指定每个 API 响应中要返回的帖子最大数量。如果与查询关联的帖子数量超过每个响应的上述最大结果数，响应中会包含一个下一页令牌。后续请求使用这些 `next` 令牌来分页遍历与该查询关联的整套帖子。

这些企业版搜索 API 提供一个 *counts* 端点，允许用户请求与其查询相关的数据量。 

<div id="request-types">
  ### 请求类型
</div>

企业级搜索 API 支持两种请求类型：

<div id="search-requests-data">
  #### Search requests (data)
</div>

对 Enterprise Search API 的搜索请求允许你在指定时间范围内，每个响应最多检索 500 条结果，并可以通过分页获取更多 data。使用 `maxResults` 参数，你可以为展示类场景指定较小的页面大小（允许用户在需要时请求更多结果），或者为大规模 data 提取指定较大的页面大小（最高 500）。data 按时间倒序返回，并在交付时保证合规。

<div id="counts-requests-post-count">
  #### 计数请求（帖子计数）
</div>

计数请求可用于检索历史活动计数，用于反映在所请求的时间范围内，与给定查询匹配的活动发生的次数。响应本质上会为你提供一个按天、小时或分钟分桶的计数直方图（默认分桶为 *hour*）。需要特别注意的是，计数结果并不总是反映在帖子发布后很久（7 天以上）才发生的合规事件（例如帖子删除）；因此，预期计数量度可能并不总是与针对同一查询的数据请求返回的结果完全一致。

**计费说明：** 针对 data 端点和 counts 端点发起的每一次请求——*包括分页请求*——都将计为一次计费请求。因此，如果单个查询有多页结果，遍历这 X 页结果在计费上将等同于 X 次请求。

<div id="data-updates-and-mutability">
  ### 数据更新与可变性
</div>

在企业级搜索 API 中，Post 中的某些数据是可变的，即在初次归档之后仍然可以被更新或更改。

这些可变数据分为两类：

* User 对象元数据：
  * 用户的 @handle（数字 id 永远不会改变）
  * 个人简介（bio）描述
  * 计数：statuses、followers、friends、favorites、lists
  * 个人资料所在地
  * 其他详细信息，例如时区和语言
* Post 统计数据——即可以通过用户在平台上的操作而改变的任何内容（如下示例）：
  * Favorites 数量
  * Retweet 数量

在大多数情况下，搜索 API 会返回在&#95;查询时&#95;平台上的现有数据，而不是 Post 生成时的数据。不过，对于使用选择型运算符（例如 from、to、@、is:verified）的查询，则可能并非如此。数据会在我们的索引中定期更新，对最近时间段的更新频率更高。因此，在某些情况下，返回的数据可能与当前在 X.com 上显示的数据并不完全一致，而是与其上次被索引时的数据一致。

注意，这种不一致性问题仅适用于运算符作用于可变数据的查询。例如按用户名进行过滤时，最好的变通方法是对这些查询使用用户的数字 id，而不是 @handle。

<div id="single-vs-multi-threaded-requests">
  ### 单线程请求与多线程请求
</div>

每位客户的搜索端点都有定义好的速率限制。Full-Archive search 的默认每分钟速率限制是每分钟 120 次请求，平均每秒 2 次查询（QPS）。这个平均 QPS 意味着理论上每秒可以向 API 发起 2 个请求。考虑到产品的分页功能，如果一个跨度一年的查询关联了一百万条帖子，并且这些帖子在这一年中均匀分布，那么要获取所有数据将需要 2,000 多次请求（假设 `maxResults` 为 500）。假设每个响应耗时 2 秒，那么通过单线程串行/顺序地拉取所有这些数据（使用前一个响应的 “next” token，以每秒 1 个请求）将需要 4,000 秒（或略多于一小时）。还不错！

现在考虑使用 12 个并行线程来接收数据的情况。假设这一百万条帖子在一年的时间段内分布均匀，你可以将请求拆分到 12 个并行线程（多线程）中，从而在这个单个 “job” 上利用更多的每秒速率限制。换句话说，你可以针对感兴趣的每一个月份运行一个线程，这样获取数据的速度可以提升 12 倍（约 6 分钟）。

这个多线程示例同样适用于 counts 端点。比如，如果你想获取两年时间范围内的帖子计数，你可以发起单线程请求，并以每次 31 天的粒度分页回溯这些计数。假设每个响应耗时 2 秒，那么发出 24 次 API 请求并获取完整的计数集大约需要 48 秒。不过，你也可以选择一次发起多个按月的请求。如果以每秒 12 次请求的速率发送请求，则大约 2 秒就能获取完整的计数集。

<div id="retry-logic">
  ### 重试逻辑
</div>

如果你在使用企业搜索 API 时遇到 503 错误，这很可能是暂时性错误，可以在稍后重新发起请求来解决。

如果请求连续失败 4 次，并且每次失败之间你至少间隔了 10 分钟，请按以下步骤进行排查：

* 缩短请求所覆盖的时间范围后再重试。如果仍未成功，继续逐步缩短，直到时间窗口减小到 6 小时。
* 如果你在规则中使用了大量通过 OR 运算符连接的检索词，将它们拆分为多个独立规则，并分别重试每个规则。
* 如果你在规则中使用了大量排除条件，减少规则中被取反的检索词数量，然后重试。

<div id="getting-started-with-enterprise-search-posts-30-day-api">
  ### 入门使用企业版 Search Posts：30 天 API
</div>

企业版 Search Posts：30 天 API 可提供最近 30 天内发布的帖子。系统会根据你在请求中指定的查询条件匹配帖子并返回给你。查询即是一条规则，你可以在其中定义希望返回的帖子应当包含的内容。在本教程中，我们将搜索来自 X 账号 @XDevelopers、语言为英语的帖子。

你在响应负载中得到的帖子可以是 data 格式，它会为你提供完整的帖子负载；也可以是 counts 格式，它会为你提供匹配帖子数量的数值统计数据。我们将使用 cURL 向 data 和 counts 端点发起请求。

你需要准备以下内容：

* [企业版账号]https://developer.x.com/en/products/x-api/enterprise
* 你的用户名、密码和账号名称
* 与搜索端点关联的 label，如 console.gnip.com 中所显示

<div id="accessing-the-data-endpoint">
  #### 访问 data 端点
</div>

data 端点会返回与查询匹配的帖子完整负载。我们将使用 `from:` 和 `lang:` 运算符来查找由 @XDevelopers 发布的英文帖子。*有关更多运算符 [请点击此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/search-api#enterprise-operators)。*

<Tabs>
  <Tab title="cURL">
    *cURL 是一个使用 URL 语法获取或发送文件的命令行工具。*

    在完成以下更改后，将下面的 cURL 请求复制到命令行中：

    * **Username** `<USERNAME>`，例如 `email@domain.com`

    * **Account name** `<ACCOUNT-NAME>`，例如 `john-doe`

    * **Label** `<LABEL>`，例如 `prod`

<div id="product-overview">
  ### 产品概览
</div>

企业级 Full-archive Search 于 2015 年 8 月推出，高级版于 2018 年 2 月推出。这些搜索产品可让客户即时访问任何公开可用的帖子。借助 Full-archive Search，你只需提交一个查询，就可以以经典的 RESTful 方式接收一个响应。Full-archive Search 实现了每个响应最多 500 条帖子的分页，并支持高级版最高 60 次请求/分钟（rpm）、企业版 120 rpm 的速率限制。基于这些特性，Full-archive Search 可通过并发请求快速、大规模地检索帖子。

与其归档基于磁盘上一组帖子平面文件的 Historical PowerTrack 不同，Full-archive Search 的帖子归档更像是一个联机数据库。与所有数据库一样，它支持对其内容进行查询。它还使用 *索引* 来实现高性能的数据检索。对于 Full-archive Search 端点，其查询语言由 PowerTrack Operators 组成，这些 Operators 各自对应一个已建立索引的帖子 JSON 属性。

同样地，与 Historical PowerTrack 一样，存在一些在发起查询时以当前值为准的帖子属性。举例来说，如果你今天使用 Search API 访问一条发布于 2010 年的帖子，该用户的个人资料描述、账号主页位置、显示名称，以及该帖子点赞数和转发数等指标都会更新为今天的数值，而不是 2010 年时的数值。

下面是 Full-archive search 端点中各个 Operator 开始匹配的时间线。在某些情况下，Operator 开始匹配的时间远晚于某种“沟通惯例”在 X 上已被广泛采用的时间。例如，@Replies 作为一种用户惯例在 2006 年就已出现，但直到 2007 年初，才通过“支持性”JSON 成为一等对象（*first-class object*）或事件（*event*）。因此，要在 2006 年匹配 @Replies，需要检查帖子正文，而不能依赖 `to:` 和 `in_reply_to_status_id:` 这些 PowerTrack Operator。

此处提供的细节是使用 Full-Archive Search（基于数百次搜索结果的产品）生成的。该时间线并非 100% 完整或精确。如果你发现了对你的用例至关重要的其他过滤器/元数据的“首次可用日期”，请告知我们。

请注意，底层 Search 索引可能会被重建。因此，这些时间线细节可能会发生变化。

<div id="filtering-tips">
  ### 过滤提示
</div>

综合以上所有时间线信息，在编写 Search APIs 过滤条件时显然需要考虑大量细节。需要重点注意两点：

* 某些元数据具有“生效”日期，因此过滤条件可能会产生&#95;假阴性&#95;。这类搜索是指使用依赖于在整个或部分搜索期间尚不存在的元数据的 Operators。比如，如果你使用 `has:images` Operator 搜索帖子，那么在 2011 年 7 月之前的时间段内将不会有任何匹配结果。这是因为该 Operator 匹配的是&#95;原生&#95;照片（通过 X 用户界面附加到帖子上的照片）。如果要获得更完整的照片分享帖子数据集，那么 2011 年 7 月之前的过滤条件需要包含匹配常见图片托管 URL 的规则子句。
* 某些元数据是在帖子发布到 X 之后的某个时间点被回填的。

在创建 PowerTrack 查询时，通常会重点关注以下几类属性类型：

* X 个人资料
* 原始帖子或转发帖子
* 帖子语言分类
* 地理标注的帖子
* 包含分享链接的媒体

其中一些具有特定产品的行为，而另一些则具有相同的行为。详细信息见下文。

<div id="x-profiles">
  #### X 个人资料
</div>

Search API 会根据&#95;检索时刻&#95;的用户个人资料数据返回历史帖子。比如，如果你请求一条 2014 年的帖子，该用户的个人资料元数据将反映其在查询时刻的状态。

<div id="original-posts-and-retweets">
  #### 原始帖子和转推
</div>

PowerTrack `_is:retweet_` 运算符允许用户选择包含或排除转推。使用该运算符的用户，在匹配（或不匹配）2009 年 8 月之前的转推时需要采用两种策略。对于 2009 年 8 月之前的 data，需要检查帖子文本本身，并使用精确短语匹配来查找符合 “@RT ” 模式的内容（实际上，如果你在筛选 2009 年 5 月至 8 月之间的转推，还应包括 “Via @” 模式）。对于 2009 年 8 月之后的时间段，可以使用 `_is:retweet_` 运算符。

<div id="post-language-classifications">
  #### 帖子语言分类
</div>

在根据帖子语言分类进行过滤时，X 的历史产品有很大差异。在构建搜索存档时，所有帖子都被补充上了 X 的语言分类。因此，`lang:` 运算符可用于整个帖子存档。

<div id="geo-referencing-posts">
  #### 帖子地理定位（Geo-referencing Posts）
</div>

为帖子进行地理定位主要有三种方式：

* **帖子内容中的地理引用。** 基于帖子内容中的地理引用进行匹配，虽然通常是最具挑战性的方法，因为它依赖本地知识，但可以应用于整个帖子存档。[此处](https://x.com/biz/statuses/28311) 是 2006 年针对旧金山地区、基于 “golden gate” 过滤条件的一个地理定位匹配示例。

* **由用户为帖子添加地理标签。** 使用搜索 API 后，从 2010 年 3 月起，可以开始基于部分 Geo 运算符匹配帖子，并在 2015 年 2 月新增了其他运算符：

  * 2010 年 3 月 6 日：`has:geo`、`bounding_box:` 和 `point_radius:`
  * 2015 年 2 月 17 日：`place_country:` 和 `place:`

* **由用户在账号资料中设置的 “home” 位置。** Profile Geo 运算符在 Historical PowerTrack 和搜索 API 中均可用。对于搜索 API，这些 Profile Geo 元数据自 2015 年 2 月起可用。对于在 Profile Geo 元数据可用之前发布的帖子，可以使用 `bio_location:` 运算符来匹配未标准化的用户输入。

<div id="shared-links-and-media">
  #### 分享的链接和媒体
</div>

2012 年 3 月，引入了扩展 URL 富化功能。在此之前，帖子负载中只包含用户提供的 URL。因此，如果用户使用了短链接 URL，就很难根据（展开后的）目标 URL 进行匹配。通过 Search API，这些元数据从 2012 年 3 月开始可用。

2016 年 7 月，引入了增强 URL 富化功能。这个增强版本会在帖子负载中提供网站的 HTML 标题和描述，以及用于匹配这些内容的运算符。这些元数据从 2014 年 12 月开始出现。

2016 年 9 月，X 引入了“原生附件”，此时结尾的分享链接不再计入 140 字符的帖子长度限制内。这两种 URL 富化仍然适用于这些分享链接。

下面是相关搜索运算符开始生效的时间：

* 2006 年 10 月 26 日 - `has:links`
* 2011 年 7 月 20 日 - `has:images` 和 `has:media`
* 2011 年 8 月 - `url:` 配合 [Expanded URLs enrichment](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments) 使用。早在 2006 年 9 月，`(url:"spotify.com" OR url:gnip OR url:microsoft OR url:google OR url:youtube)` 就可以匹配 http://x.com/Adam/statuses/16602，即使在 twitter&#95;entities 和 gnip 对象中没有 urls[] 元数据。“youtube.com” 就是一个示例，说明在没有任何 urls[] 元数据的情况下，消息内容仍然可以匹配 url:youtube。
* 2015 年 2 月 10 日 - 用于原生视频的 `has:videos`。在 2010/08/28 至 2015/02/10 之间，此运算符会匹配带有指向特定视频托管站点（例如 youtube.com、vimeo.com 和 vivo.com）链接的帖子。
* 2016 年 5 月 1 日 - 基于 [Enhanced URLs enrichment](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments) 的 `url_title:` 和 `url_description:` 开始全面可用。首批增强 URL 元数据自 2014 年 12 月开始出现。

  <Accordion title="为什么我通过 data 端点获取到的帖子数量与 counts 端点返回的帖子数量不一致？这是为什么？">
    `counts` 端点返回的结果与 `data` 端点返回的结果之间存在已知差异。你可能会在结果中看到差异，因为 `counts` 端点是在合规处理之前生成结果的（也就是说，它不会考虑已删除帖子、地理信息清除（scrub geo）等情况），而 `data` 端点在交付时已完成合规处理，并且会考虑所有合规事件。
  </Accordion>

    这可能发生有几种不同的原因，包括：

    1. 你预期看到的帖子来自受保护的账号
    2. data endpoint 会涵盖所有合规事件（这意味着已删除的帖子、被清除的地理位置信息（geos）等都不会包含在响应中）。
  </Accordion>

<div id="enterprise-search-apis">
  ### 企业搜索 API
</div>

有两个企业搜索 API：

* 30-Day Search API - 提供最近 30 天内发布的推文。
* Full-Archive Search API - 提供可追溯至 2006 年的推文，从 2006 年 3 月发布的第一条推文开始。

这些搜索 API 采用统一的设计，下面的文档同时适用于两者。请注意，对于自 2022 年 9 月 29 日起创建的推文，Tweet 对象将包含描述其编辑历史的推文编辑元数据。更多详情请参阅 [&quot;Edit Tweets&quot;](/zh/x-api/enterprise-gnip-2.0/fundamentals/edit-tweets) 基础说明页面。

下面是你在集成企业搜索 API 时需要了解的重要细节：

* 请求推文 data 及计数的方法
* 身份验证
* 分页
* API 请求参数和示例请求
* API 响应 JSON 载荷和示例响应
* HTTP 响应状态码

企业 API 提供对推文存档的低延迟、全保真、基于查询的访问。这两个 API 的唯一区别是可搜索的时间范围，要么是过去 30 天，要么是自 2006 年起。时间范围可以精确到分钟级。推文 data 按时间倒序返回，从与你的查询匹配的最新推文开始。推文在发布后大约 30 秒内即可通过搜索 API 获取。

<div id="methods">
  #### 方法
</div>

企业搜索的基本 URI 为 `https://gnip-api.x.com/search/`。

| Method | Description |
| :--- | :--- |
| [POST /search/:product/accounts/:account&#95;name/:label](#SearchRequests) | 检索过去 30 天内与指定 PowerTrack 规则匹配的推文。 |
| [POST /search/:product/accounts/:account&#95;name/:label/counts](#CountRequests) | 检索过去 30 天内与指定 PowerTrack 规则匹配的推文数量。 |

其中：

* `:product` 表示你要请求的搜索端点，可以是 `30day` 或 `fullarchive`。
* `:account_name` 是与你的账号关联的（区分大小写的）名称，如在 console.gnip.com 中所示。
* `:label` 是与你的搜索端点关联的（区分大小写的）标签，如在 console.gnip.com 中所示。

例如，如果 TwitterDev 账号拥有 30 天搜索产品，并且其标签为 “prod”（production 的缩写），则搜索端点为：

* 数据端点：[https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json)
* 计数端点：[https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json)

你的完整企业搜索 API 端点地址会显示在 [https://console.gnip.com](https://console.gnip.com)。

下面是几个使用名为 curl 的简单 HTTP 工具发起请求的示例。这些示例在 URL 中使用了 `:product`、`:account_name` 和 `:label`。要使用这些示例，请务必将其中的 URL 更新为你自己的信息。

<div id="authentication">
  #### 身份验证
</div>

所有对企业搜索 API 的请求都必须使用 HTTP *Basic Authentication*，其凭据由用于登录你在 [https://console.gnip.com](https://console.gnip.com) 上账户的有效电子邮件地址和密码组合构成。凭据必须作为每个请求的 *Authorization* 头部进行传递。

<div id="requestresponse-behavior">
  #### 请求/响应行为
</div>

使用 `fromDate` 和 `toDate` 参数，你可以请求任意一个 API 所支持的时间范围。30-Day search API 提供最近 31 天的推文（尽管称为 “30-Day” API，它实际上提供 31 天的数据，以便用户可以发起完整自然月的请求）。Full-Archive search API 则提供自第一条推文（2006 年 3 月 21 日）起的所有推文数据。不过，单个响应中返回的结果会受限于你指定的 `maxResults` 或 31 天这两者中较小的那个。如果匹配的数据量或你请求的时间范围超过你指定的 `maxResults` 或 31 天，你会收到一个 `next` 令牌，你应使用它在你指定的时间范围内继续进行分页请求。

例如，假设你正在使用 Full-Archive search，并且希望获取 2017 年 1 月 1 日到 2017 年 6 月 30 日之间与你的查询匹配的所有推文。你会在请求中使用 `fromDate` 和 `toDate` 参数指定这一完整的六个月时间段。search API 将返回第一“页”推文，其推文数量与 `maxResults` 参数（默认为 100）相匹配。假设还有更多推文（并且很可能会有更多），API 还会返回一个 `next` 令牌，使你可以请求下一“页”数据。这个过程会重复，直到 API 不再返回 `next` 令牌为止。更多细节请参见下一节。

<div id="pagination">
  #### 分页
</div>

当你同时发起数据请求和计数请求时，数据量很可能超过单个响应可返回的范围。在这种情况下，响应会包含一个 “next” 令牌。该 “next” 令牌作为 JSON 顶层属性提供。只要响应中包含 “next” 令牌，就表示还有更多数据需要获取，因此你需要继续发起 API 请求。

**注意：**“next” 令牌在数据请求和计数请求中的行为略有不同，下面会分别进行说明，并在 API 参考部分提供示例响应。

<div id="data-pagination">
  ##### 数据分页
</div>

数据请求返回的数据通常会多于单个响应所能返回的数量。每个数据请求都包含一个参数，用于设置每次请求要返回的最大推文数。`maxResults` 参数默认为 100，可设置为 10–500 范围内的任意值。如果你的查询匹配到的推文数量多于请求中指定的 `maxResults` 值，响应会包含一个 &#39;next&#39; token（作为 JSON 根级属性）。这个 &#39;next&#39; token 会在后续请求中使用，以检索该查询匹配推文的下一部分（即下一“页”）。在你到达该查询结果的最后一“页”之前，响应都会继续提供 &#39;next&#39; token；当不再提供 &#39;next&#39; token 时，即表示已经到达最后一“页”。

要请求下一“页”数据，你必须发出与原始请求完全相同的查询，包括 `query`、`toDate` 和 `fromDate` 参数（如果使用了它们），并且还要包含一个 &#39;next&#39; 请求参数，其值设置为前一个响应中的值。这既可以用于 GET 请求，也可以用于 POST 请求。但在 GET 请求的情况下，必须对 &#39;next&#39; 参数进行 URL 编码。

你可以持续传入上一次查询返回的 &#39;next&#39; token，直到你已经获取到查询所覆盖时间区间内的所有推文。当你收到的响应不再包含 &#39;next&#39; token 时，这意味着你已经到达最后一页，指定查询和时间范围内不再有其他可用数据。

<div id="counts-pagination">
  ##### 计数分页
</div>

`counts` 端点会基于查询，按天、按小时或按分钟提供相关推文数量。`counts` API 端点将返回一个带时间戳的计数数组，最多可覆盖 31 天的计数数据。如果你请求超过 31 天的计数，将会返回一个 `next` 令牌。与 data 中的 `next` 令牌一样，你必须发起与原始请求完全相同的查询，并在其中加入一个 `next` 请求参数，其值设置为上一个响应中的该字段值。

除了请求超过 31 天的计数以外，还有另一种会返回 `next` 令牌的情况。对于数据量较大的查询，生成计数可能会花费足够长的时间，从而触发响应超时。当发生这种情况时，你会收到少于 31 天的计数结果，但同时会得到一个 `next` 令牌，以便继续发起请求以获取完整的计数数据。***重要：*** 超时情况下只会返回完整的“桶”（bucket）——例如，2.5 天只会返回 2 个完整的天级“桶”。

<div id="additional-notes">
  ##### 补充说明
</div>

* 在搜索请求中使用 `fromDate` 或 `toDate` 时，你只会获得处于该时间范围内的结果。当你到达该时间范围内最后一组结果时，将不会再收到 `next` 令牌。
* `next` 元素可以与 10-500 范围内的任意 `maxResults` 值一起使用（默认值为 100）。`maxResults` 决定每个响应中返回多少条推文，但不会阻止你最终获取所有结果。
* `next` 元素不会过期。使用相同 `next` 查询参数的多次请求将收到相同的结果，而不论请求是在何时发出的。
* 当使用 `next` 参数对结果进行分页时，你可能会在查询的边界处遇到重复结果。你的应用程序应能够容忍这些重复结果。

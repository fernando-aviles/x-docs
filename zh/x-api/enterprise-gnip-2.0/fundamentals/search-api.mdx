<div id="overview">
  ## 概览
</div>

`Enterprise`

*企业级 API 仅在我们的托管访问级别中可用。要使用这些 API，您必须先与我们的企业销售团队开通企业账户。要了解更多信息，请参见 [此处](https://developer.x.com/en/products/x-api/enterprise)。*

*您可以在[此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/search-api)查看所有 X API 搜索帖子产品。*

共有两个企业级搜索 API：

1. 30-Day Search API 提供最近 30 天的数据。
2. Full-Archive Search API 提供对 X 全量数据语料库的完整、即时访问，可一直追溯到 2006 年 3 月的第一条帖子。

这些 RESTful API 每个请求支持一个最长 2,048 个字符的查询。查询使用 PowerTrack 规则语法编写——更多详情请参见 [规则与过滤](/zh/x-api/enterprise-gnip-2.0/fundamentals/rules-filtering#getting-started-with-enterprise-rules-and-queries)。用户可以指定任意时间区间，精确到分钟级。不过，响应会受到您指定的 `maxResults` 或 31 天（取较小者）的限制，并包含一个 `next` 令牌，用于分页获取下一组结果。如果未指定时间参数，API 将返回最近 30 天内与查询匹配的数据。

企业级搜索 API 以分钟粒度提供低延迟、全保真、基于查询的帖子归档访问。帖子数据按时间倒序返回，从与您的查询匹配的最新帖子开始。帖子通常在发布约 30 秒后即可通过搜索 API 获取。

这些搜索端点会提供已编辑帖子的元数据。自 2022 年 9 月 29 日之后创建的所有帖子对象都会包含帖子编辑元数据，即使该帖子从未被编辑过。每次帖子被编辑时，都会创建一个新的帖子 ID。帖子的编辑历史通过一个帖子 ID 数组进行记录，以原始 ID 开头。

这些端点将始终返回最新的编辑版本以及完整的编辑历史。任何在 30 分钟编辑窗口之后被采集的帖子都将代表其最终版本。要了解有关编辑帖子元数据的更多信息，请参阅 [编辑帖子基础知识](/zh/x-api/fundamentals/edit-posts)页面。

请求中包含一个 `maxResults` 参数，用于指定每个 API 响应要返回的帖子最大数量。如果与查询关联的帖子数量超过每个响应允许的最大结果数，响应中将包含一个 `next` 令牌。后续请求使用这些 `next` 令牌分页获取与查询关联的整套帖子。

这些企业级搜索 API 提供一个 *counts* 端点，使用户可以请求与其查询相关的数据量信息。 

<div id="request-types">
  ### 请求类型
</div>

企业搜索 API 支持两种请求类型：

<div id="search-requests-data">
  #### 搜索请求（数据）
</div>

对企业搜索 API 的搜索请求允许你在指定时间范围内，每个响应最多检索 500 条结果，并且可以通过分页获取更多数据。使用 `maxResults` 参数，你可以为展示类用例指定较小的每页结果数（允许你的用户在需要时请求更多结果），或者为大规模数据提取指定较大的每页结果数（最多 500）。数据按时间倒序返回，并在交付时保证合规性。

<div id="counts-requests-post-count">
  #### 计数请求（帖子计数）
</div>

计数请求用于获取历史活动计数，反映在指定时间范围内，与给定查询匹配的活动发生次数。响应本质上会提供一个按天、小时或分钟分桶的计数直方图（默认分桶为 *hour*）。需要特别注意的是，计数结果并不总是反映在帖子发布很久之后（7 天以上）发生的合规事件（例如帖子删除）；因此，预期计数指标不一定总能与针对相同查询的数据请求结果完全一致。

**计费说明：** 对数据和计数端点发起的每次请求（*包括分页请求*）都计为一次计费请求。因此，如果单个查询有多页结果，遍历这 X 页结果在计费上相当于 X 次请求。

<div id="data-updates-and-mutability">
  ### 数据更新与可变性
</div>

在 enterprise 搜索 API 中，帖子中的部分数据是可变的，即在初次归档之后仍然可以被更新或更改。

这些可变数据主要分为两类：

* 用户对象元数据：
  * 用户的 @handle（数值型 id 永不改变）
  * 个人简介（Bio）描述
  * 计数：帖子数、关注者数、关注数、收藏数、列表数
  * 个人资料中的位置信息
  * 其他详情，例如时区和语言
* 帖子统计数据——即任何可以通过用户在平台上的操作而改变的内容（如下示例）：
  * 收藏数
  * 转推数

在大多数情况下，search API 会返回在平台上于&#95;查询时&#95;存在的数据，而不是帖子生成时的数据。然而，对于使用 select 运算符（例如 from、to、@、is:verified）的查询，情况可能并非如此。数据会定期在我们的索引中更新，且最近时间段的数据更新频率更高。因此，在某些情况下，返回的数据可能不会与 X.com 上当前显示的数据完全一致，而是与其上次被索引时的数据一致。

请注意，这种不一致问题只适用于运算符作用于可变数据的查询。例如按用户名进行过滤时，最好的变通方法是对这类查询使用用户的数值型 id，而不是 @handle。

<div id="single-vs-multi-threaded-requests">
  ### 单线程请求与多线程请求
</div>

每位客户的搜索端点都有预设的速率限制。完整归档（Full-Archive）搜索的默认每分钟速率限制为 120 个请求，平均为每秒 2 个查询（QPS）。这个平均 QPS 意味着理论上每秒可以向 API 发出 2 个请求。鉴于产品的分页特性，如果一个为期一年的查询关联了一百万条帖子，并且这些帖子在一年内均匀分布，那么需要发出 2,000 多个请求（假设 `maxResults` 为 500）才能接收所有数据。假设每个响应需要 2 秒钟，这就是 4,000 秒（或略多于一小时），通过单个线程以串行/顺序方式拉取所有这些数据（使用前一个响应的 &quot;next&quot; token，以每秒 1 个请求的速率）。还不错！

现在再考虑使用十二个并行线程接收数据的情况。假设这一百万条帖子在一年的时间内分布均匀，你可以将请求拆分为十二个并行线程（多线程），以便在同一个“任务”上利用更多的每秒速率限制。换句话说，你可以针对每一个你感兴趣的月份运行一个线程，这样一来，获取数据的速度可以提升 12 倍（约 6 分钟）。

这个多线程示例同样适用于 counts 端点。比如，如果你希望获取两年时间范围内的帖子计数，你可以发出单线程请求，并一次回溯分页 31 天的计数。假设每个响应需要 2 秒，那么大约需要 48 秒来完成 24 次 API 请求并检索整套计数。不过，你也可以选择一次性发出多个按月的请求。当以每秒 12 个请求的速率发出时，可以在大约 2 秒内检索整套计数。

<div id="retry-logic">
  ### 重试逻辑
</div>

如果你在使用 enterprise search API 时遇到 503 错误，这很可能是暂时性错误，可以通过在稍后重新尝试该请求来解决。

如果请求连续失败 4 次，并且每次失败之间你至少等待了 10 分钟，请按以下步骤进行排查：

* 先缩短请求所覆盖的时间范围后再重试。如果仍然失败，继续逐步缩短时间范围，直到缩小到 6 小时的时间窗口。
* 如果你在使用 OR 组合大量检索词，请将它们拆分为多条独立规则，并分别重试每条规则。
* 如果你在规则中使用了大量排除条件，请减少规则中取反（否定）检索词的数量，然后重试。

<div id="getting-started-with-enterprise-search-posts-30-day-api">
  ### 开始使用 enterprise Search Posts: 30-Day API
</div>

enterprise Search Posts: 30-Day API 为你提供最近 30 天内发布的帖子。系统会根据你在请求中指定的查询条件匹配帖子并返回给你。查询是一条规则，用来定义你希望返回的帖子应当包含的内容。在本教程中，我们将搜索来自 X 账号 @XDevelopers 的英文帖子。

你在响应载荷中得到的帖子可以采用 data 格式，该格式会为你提供完整的帖子载荷；或者采用 counts 格式，该格式会为你提供匹配帖子的数量统计数据。我们将使用 cURL 向 data 和 counts 端点发起请求。

你需要准备以下内容：

* [企业账户]https://developer.x.com/en/products/x-api/enterprise
* 你的用户名、密码和账户名称
* 与搜索端点关联的标签（label），如在 console.gnip.com 中所示

<div id="accessing-the-data-endpoint">
  #### 访问数据端点
</div>

数据端点会向我们返回匹配帖子的完整 Post 负载。我们将使用 `from:` 和 `lang:` 运算符来查找由 @XDevelopers 账户以英语发布的帖子。 *有关更多运算符 [请点击此处](/zh/x-api/enterprise-gnip-2.0/fundamentals/search-api#enterprise-operators)。*

<Tabs>

    在按如下所示替换参数后，将以下 cURL 请求复制到你的命令行中：

    * **Username** `<USERNAME>`，例如 `email@domain.com`

    * **Account name** `<ACCOUNT-NAME>`，例如 `john-doe`

<div id="product-overview">
  ### 产品概览
</div>

企业级 Full-archive Search 于 2015 年 8 月上线，高级版（premium）于 2018 年 2 月上线。这些搜索产品使客户可以立即访问任何公开可用的帖子。使用 Full-archive Search 时，你提交一个查询，并以经典的 RESTful 方式接收响应。Full-archive Search 实现了每个响应最多返回 500 条帖子（500-Posts-per-response）的分页机制，并支持高级版每分钟最多 60 次请求（rpm）、企业版每分钟最多 120 次请求。基于这些特性，Full-archive Search 可用于快速、大规模检索帖子，并可通过并发请求实现大规模访问。

与基于磁盘上一组帖子平面文件（flat-files）的 Historical PowerTrack 不同，Full-archive Search 的帖子归档更像是一个联机数据库。与所有数据库一样，它支持对其内容进行查询。它还使用 *索引* 来实现高性能数据检索。在 Full-archive search 端点中，查询语言由 PowerTrack Operators 组成，每个 Operator 都对应一个被索引的帖子 JSON 属性。

同样地，与 Historical PowerTrack 一样，有一些帖子属性会以发起查询时的时间点为准。例如，如果你今天使用 Search API 访问一条发布于 2010 年的帖子，那么该用户的个人简介、账户“home”位置、显示名称，以及帖子在收藏（Favorites）和转发（Retweet）上的计数指标，都会更新为今天的值，而不是 2010 年时的值。 

<div id="metadata-timelines">
  ### 元数据时间线
</div>

下面是 Full-archive search 端点中各类 Operator 开始匹配的时间线。在某些情况下，Operator 开始匹配的时间远晚于某种在 X 上已经普遍使用的「交流约定」。例如，@Replies 作为一种用户约定在 2006 年出现，但直到 2007 年初才通过配套的 JSON 支持，成为一种&#95;一等公民对象&#95;或&#95;事件&#95;。因此，要在 2006 年匹配 @Replies，需要检查帖子正文，而不是依赖 `to:` 和 `in_reply_to_status_id:` 这两个 PowerTrack Operator。

此处提供的细节是通过 Full-archive search（基于数百次搜索的结果）生成的。该时间线并非 100% 完整或精确。如果你发现了对你的用例至关重要、但未包含在此处的其他过滤/元数据「诞生日期」，请告知我们。

请注意，底层的 Search 索引可能会被重建。因此，这些时间线细节可能会发生变化。

<div id="filtering-tips">
  ### 过滤技巧
</div>

综合上述所有时间线信息，在编写 Search APIs 的过滤条件时，显然需要考虑很多细节。这里有两个关键点需要注意：

* 某些元数据有“生效”日期，因此过滤可能会导致&#95;假阴性&#95;。此类搜索包括依赖于在搜索时间段的全部或部分期间内尚不存在的元数据的 Operators。比如，如果你使用 `has:images` Operator 搜索帖子，那么在 2011 年 7 月之前的时间段内，你不会得到任何匹配结果。这是因为该 Operator 匹配的是&#95;原生&#95;照片（通过 X 用户界面附加到帖子上的照片）。如果想获得更完整的照片分享帖子数据集，那么在对 2011 年 7 月之前的时间段进行过滤时，需要在规则中加入匹配常见图片托管 URL 的条件。
* 某些元数据是基于帖子在 X 上发布&#95;之后&#95;的时间回填得到的。

在创建 PowerTrack 查询时，通常会着重关注以下几类属性：

* X 个人资料
* 原创或分享的帖子
* 帖子语言分类
* 带地理标注的帖子
* 共享链接中的媒体

其中一些具有特定于产品的行为，而另一些则具有相同的行为。详情见下文。

<div id="x-profiles">
  #### X 个人资料
</div>

Search API 会在 *检索时* 返回历史帖子，并附带当时的用户个人资料数据集。如果你请求一条 2014 年发布的帖子，该用户的个人资料元数据将以查询时刻的状态为准。

<div id="original-posts-and-retweets">
  #### 原始帖子和转推
</div>

PowerTrack `_is:retweet_` 运算符可以让用户选择包含或排除转推。该运算符的用户在处理 2009 年 8 月之前的数据时，需要为是否匹配转推准备两套策略。对于 2009 年 8 月之前的情况，需要检查帖子消息文本本身，通过精确短语匹配来查找符合 “@RT ” 模式的内容（实际上，如果你在过滤 2009 年 5 月至 8 月期间的转推，还应当同时包含 “Via @” 模式）。对于 2009 年 8 月之后的时间段，则可以使用 `_is:retweet_` 运算符。

<div id="post-language-classifications">
  #### 帖子语言分类
</div>

在按帖子语言分类进行过滤时，X 的各历史产品之间存在较大差异。构建 Search 存档时，所有帖子都被补充上了 X 的语言分类。因此，`lang:` 运算符可用于整个帖子存档。

<div id="geo-referencing-posts">
  #### 帖子地理定位
</div>

给帖子进行地理定位主要有三种方式：

* **帖子内容中的地理引用。** 基于帖子内容中的地理引用进行匹配，虽然通常是最具挑战性的方法（因为依赖本地知识），但可用于整个帖子归档。[此处](https://x.com/biz/statuses/28311) 是一个 2006 年的地理定位匹配示例，基于 “golden gate” 过滤器，定位到旧金山地区。

* **由用户为帖子添加地理标签。** 使用搜索 API 后，从 2010 年 3 月开始可以通过部分 Geo Operators 对帖子进行匹配，2015 年 2 月又加入了其他 Geo Operators：

  * 2010 年 3 月 6 日：`has:geo`、`bounding_box:` 和 `point_radius:`
  * 2015 年 2 月 17 日：`place_country:` 和 `place:`

* **由用户在账号资料中设置 “home” 位置。** Profile Geo Operators 在 Historical PowerTrack 和 Search API 中均可用。对于 Search API，这些 Profile Geo 元数据从 2015 年 2 月开始可用。对于 Profile Geo 元数据尚不可用之前发布的帖子，可以使用 `bio_location:` Operator，它可以用来匹配非规范化的用户输入。

<div id="shared-links-and-media">
  #### 共享链接和媒体
</div>

在 2012 年 3 月，引入了扩展 URL 丰富功能（expanded URL enrichment）。在此之前，帖子负载中只包含用户提供的 URL。因此，如果用户使用的是短链接，那么要匹配到目标（展开后的）URL 会比较困难。使用 Search APIs 时，这些元数据从 2012 年 3 月开始可用。

在 2016 年 7 月，引入了增强型 URL 丰富功能（enhanced URL enrichment）。这个增强版本会在帖子负载中提供网站的 HTML 标题和描述，并提供用于匹配这些内容的 Operator。这些元数据从 2014 年 12 月开始出现。

在 2016 年 9 月，X 引入了“原生附件”，尾部的共享链接不再计入 140 字符的帖子长度限制。这两种 URL 丰富功能仍适用于这些共享链接。

下面是相关 Search Operator 开始匹配的时间点：

* 2006 年 10 月 26 日 - `has:links`
* 2011 年 7 月 20 日 - `has:images` 和 `has:media`
* 2011 年 8 月 - `url:` 搭配 [Expanded URLs enrichment](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments)。早在 2006 年 9 月，`(url:"spotify.com" OR url:gnip OR url:microsoft OR url:google OR url:youtube)` 就能匹配 http://x.com/Adam/statuses/16602，即便在 twitter&#95;entities 和 gnip 对象中没有 urls[] 元数据。“youtube.com” 是一个示例：即使消息内容中只有这个字符串，在没有任何 urls[] 元数据的情况下，依然能匹配 url:youtube。
* 2015 年 2 月 10 日 - 原生视频的 `has:videos`。在 2010/08/28 到 2015/02/10 之间，此 Operator 会匹配包含指向 youtube.com、vimeo.com 和 vivo.com 等特定视频托管站点链接的帖子。
* 2016 年 5 月 1 日 - 基于 [Enhanced URLs enrichment](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-enrichments) 的 `url_title:` 和 `url_description:` 一般可用。首批增强型 URL 元数据从 2014 年 12 月开始出现。

<AccordionGroup>
  <Accordion title="为什么通过 data 端点接收到的帖子数量与 counts 端点统计的帖子数量不一致？">
    `counts` 端点和 `data` 端点返回的结果之间存在已知差异。你可能会在结果中看到差异，这是因为 `counts` 端点在返回前尚未进行合规处理（也就是说，它不会考虑已删除的帖子、位置数据清除等），而 `data` 端点在交付时已经完成合规处理，并且会计入所有合规事件。

    出现这种情况可能有几种不同的原因，包括：

    1. 你原本期望看到的帖子来自受保护账号
    2. 数据端点会纳入所有合规事件（也就是说，已删除的帖子、被清除的地理信息等将不会出现在响应中）。
  </Accordion>

<div id="enterprise-search-apis">
  ### 企业搜索 API
</div>

有两个企业搜索 API：

* 30-Day Search API - 提供最近 30 天内发布的推文（Tweets）。
* Full-Archive Search API - 提供自 2006 年起的推文，从 2006 年 3 月发布的第一条推文开始。

这些搜索 API 采用统一的设计，下面的文档同样适用于二者。请注意，对于自 2022 年 9 月 29 日起创建的推文，Tweet 对象将包含描述其编辑历史的推文编辑元数据。有关更多详细信息，请参阅 [&quot;Edit Tweets&quot;](/zh/x-api/enterprise-gnip-2.0/fundamentals/edit-tweets) 基础说明页面。

下面是你在集成企业搜索 API 时需要了解的重要细节：

* 请求推文数据和数量统计的方法
* 身份验证
* 分页
* API 请求参数和示例请求
* API 响应 JSON 载荷和示例响应
* HTTP 响应代码

企业 API 提供对推文存档的低延迟、全保真、基于查询的访问。这两个 API 的唯一差异在于可搜索的时间范围：要么是最近 30 天，要么是早至 2006 年。时间范围可以精确到分钟级别。推文数据按时间逆序返回，从与你的查询匹配的最新推文开始。推文在发布后大约 30 秒即可通过搜索 API 获取。

<div id="methods">
  #### 方法
</div>

enterprise search 的基础 URI 为 `https://gnip-api.x.com/search/`。

| Method | Description |
| :--- | :--- |
| [POST /search/:product/accounts/:account&#95;name/:label](#SearchRequests) | 检索过去 30 天内与指定 PowerTrack 规则匹配的推文。 |
| [POST /search/:product/accounts/:account&#95;name/:label/counts](#CountRequests) | 检索过去 30 天内与指定 PowerTrack 规则匹配的推文数量。 |

其中：

* `:product` 表示你要调用的搜索端点，可以是 `30day` 或 `fullarchive`。
* `:account_name` 是与你账户关联的名称（区分大小写），与 console.gnip.com 上显示的一致。
* `:label` 是与你搜索端点关联的标签（区分大小写），与 console.gnip.com 上显示的一致。

例如，如果 TwitterDev 账户拥有标签为“prod”（production 的缩写）的 30 天搜索产品，则对应的搜索端点为：

* 数据端点： [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod.json)
* 计数端点： [https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json](https://gnip-api.x.com/search/30day/accounts/TwitterDev/prod/counts.json)

你的完整 enterprise search API 端点会显示在 [https://console.gnip.com](https://console.gnip.com)。

下面是若干使用名为 curl 的简单 HTTP 工具发起请求的示例。这些示例在 URL 中使用了 `:product`、`:account_name` 和 `:label`。如需使用这些示例，请务必将 URL 更新为你的实际信息。

<div id="authentication">
  #### 身份验证
</div>

所有对 Enterprise search API 的请求都必须使用 HTTP *Basic Authentication*，该认证由用于登录你在 [https://console.gnip.com](https://console.gnip.com) 上账户的有效电子邮件地址和密码组合构成。凭据必须作为每个请求的 *Authorization* 请求头传递。

<div id="requestresponse-behavior">
  #### 请求/响应行为
</div>

通过使用 `fromDate` 和 `toDate` 参数，你可以请求该 API 所支持的任意时间范围。30-Day search API 提供最近 31 天内的推文（尽管被称为“30-Day” API，但它实际提供 31 天的数据，以便用户可以发起完整自然月的请求）。Full-Archive search API 提供从第一条推文（2006 年 3 月 21 日）开始的全部历史推文。不过，单次响应中返回的数据会被限制为你指定的 `maxResults` 或 31 天中较小的那个。如果匹配的数据量或你的时间范围超过了你指定的 `maxResults` 或 31 天，你将会收到一个 `next` 令牌，你应当使用该令牌对剩余的指定时间范围进行分页请求。

例如，假设你正在使用 Full-Archive search，并且希望获取从 2017 年 1 月 1 日到 2017 年 6 月 30 日之间符合查询条件的所有推文。你会在请求中通过 `fromDate` 和 `toDate` 参数指定这整整六个月的时间范围。search API 将返回第一“页”推文，其数量与 `maxResults` 参数（默认为 100）所指定的条数相匹配。假设还有更多推文（而且极有可能会有更多），API 还会提供一个 `next` 令牌，使你能够请求下一“页”数据。这个过程会反复进行，直到 API 不再返回 `next` 令牌为止。有关更多详细信息，请参见下一小节。

<div id="pagination">
  #### 分页
</div>

当你同时发起数据请求和计数请求时，返回的数据很可能多于单个响应所能包含的内容。在这种情况下，响应中会包含一个 `next` 令牌。`next` 令牌作为 JSON 顶层属性提供。每当返回 `next` 令牌时，就表示还有更多数据可获取，因此你需要继续发起 API 请求。

**注意：** `next` 令牌在数据请求和计数请求中的行为略有不同，下文会分别进行说明，并在 API 参考部分提供示例响应。

<div id="data-pagination">
  ##### 数据分页
</div>

数据请求通常会返回超过单个响应可包含的数据量。每个数据请求都包含一个参数，用于设置每次请求返回的最大推文数量。`maxResults` 参数默认值为 100，可以设置为 10 到 500 之间的任意值。如果你的查询匹配到的推文数量超过请求中使用的 `maxResults` 参数值，响应中会包含一个 `next` 令牌（作为 JSON 根级属性）。该 `next` 令牌会在后续请求中使用，用于检索该查询下一部分匹配的推文（即下一“页”）。系统会持续提供 `next` 令牌，直到你到达该查询结果的最后一“页”，这时将不再提供 `next` 令牌。

要请求下一“页”数据，你必须发送与原始请求完全相同的查询，包括（如有使用）`query`、`toDate` 和 `fromDate` 参数，并且还要包含一个名为 `next` 的请求参数，其值设置为前一个响应中返回的 `next` 令牌值。这既可以用于 GET 请求，也可以用于 POST 请求。但是，在使用 GET 请求时，`next` 参数必须进行 URL 编码。

你可以持续传入前一次查询返回的 `next` 令牌，直到获取到查询所覆盖时间范围内的所有推文。当你收到的响应中不再包含 `next` 令牌时，这意味着你已经到达最后一页，在指定的查询和时间范围内不再有可用的其他数据。

<div id="counts-pagination">
  ##### 计数分页
</div>

`counts` 端点会按天、按小时或按分钟的粒度，返回与查询关联的推文数。`counts` API 端点会返回一个带时间戳的计数数组，单次最多包含 31 天的计数数据。如果你请求的计数范围超过 31 天，将会返回一个 `next` token。与数据的 `next` token 一样，你必须发起与原始请求完全相同的查询，并额外包含一个 `next` 请求参数，其值设置为上一个响应中返回的值。

除了请求超过 31 天的计数之外，还有另一种会返回 `next` token 的情况。对于较高数据量的查询，生成计数可能需要较长时间，从而触发响应超时。当发生这种情况时，你会收到少于 31 天的计数结果，但会得到一个 `next` token，以便继续发出请求以获取完整的计数数据。***重要提示：*** 发生超时时只会返回完整的“桶（bucket）”——因此 2.5 天的时间范围将只会返回 2 个完整天的“桶”。

<div id="additional-notes">
  ##### 补充说明
</div>

* 在搜索请求中使用 fromDate 或 toDate 时，你只会获得处于该时间范围内的结果。当你获取到该时间范围内最后一组结果时，将不会再收到 “next” 令牌。
* “next” 元素可以与 10 到 500（含）之间的任意 maxResults 值一起使用（默认值为 100）。maxResults 决定每个响应中返回多少条推文，但不会阻止你最终获取全部结果。
* “next” 元素不会过期。如果在多次请求中使用相同的 “next” 查询参数，无论何时发出请求，都会收到相同的结果。
* 使用 “next” 参数在结果中进行分页时，你可能会在查询结果的边界处遇到重复结果。你的应用应当能够处理这些重复结果。

## 介绍

`Enterprise`

Enterprise 富化是附加的元数据，会包含在某些数据 API 的响应载荷中。它们仅在付费订阅方案中提供。

下表对每种富化类型做了简要说明：

| 富化类型： | 描述： |
| :--- | :--- |
| 展开和增强的 URL | 自动展开包含在帖子正文中的短链接 URL（例如 bitly），并从目标页面提供 HTML 标题和描述等元数据。 |
| 匹配规则对象 | 指示接收到的帖子匹配了哪些规则。该对象在响应中返回规则标签和规则 ID。 |
| 投票元数据 | 标记帖子中是否包含投票，包含投票选项列表，以及投票持续时间和到期时间。 |
| 个人资料地理信息 | 基于用户个人资料中的位置推导出的地理位置数据，包括（在可能的情况下）[经度, 纬度] 坐标以及相关地点元数据。 |

<div id="expanded-and-enhanced-urls">
  ### 展开和增强的 URL
</div>

Expanded and Enhanced URL 富化功能会自动展开包含在帖子正文中的短链接，并将最终解析得到的 URL 作为元数据包含在载荷中。此外，该富化还会提供目标页面 `title` 和 `description` 中的 HTML 页面元数据。

**重要细节：**

* 为了解析短链接，我们的系统会向提供的 URL 发送 HTTP HEAD 请求，并跟随所有重定向，直到到达最终 URL。然后会将该最终 URL（而不是页面本身的内容）包含在响应载荷中。

* URL 富化会为实时流增加大约 5–10 秒的延迟。

* 对于对 Full Archive Search API 发起的请求，展开后的 URL 富化数据仅适用于发布时间在 13 个月以内的帖子。

* URL 富化不适用于帖子链接（包括引用推文）、Moments 链接以及包含在帖子中的个人主页链接。 
   

#### 帖子载荷

扩展和增强 URL 富化位于帖子载荷中的 `entities` 对象内——具体来说是在 `entitites.urls.unwound` 对象中。它提供以下元数据字段：

* 扩展后的 URL - `unwound.url`
* 扩展后的 HTTP 状态 - `unwound.status`
* 扩展后 URL 的 HTML 标题（最多 300 个字符）- `unwound.title`
* 扩展后 URL 的 HTML 描述（最多 1000 个字符）- `unwound.description`

**这是一个带有 URL 富化的 [entities 对象](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-dictionary#x-entities) 示例：**

```
"entities": {
    "hashtags": [

    ],
    "urls": [
      {
        "url": "https:\/\/t.co\/HkTkwFq8UT",
        "expanded_url": "http:\/\/bit.ly\/2wYTb9y",
        "display_url": "bit.ly\/2wYTb9y",
        "unwound": {
          "url": "https:\/\/www.forbes.com\/sites\/laurencebradford\/2016\/12\/08\/11-websites-to-learn-to-code-for-free-in-2017\/",
          "status": 200,
          "title": "11 Websites To Learn To Code For Free In 2017",
          "description": "It\u2019s totally possible to learn to code for free...but what are the best resources to achieve that? Here are 11 websites where you can get started."
        },
        "indices": [
          10,
          33
        ]
      }
    ],
    "user_mentions": [

    ],
    "symbols": [

    ]
  },
```

**这是一个 `entities` 对象示例，其中包含一个未富化的帖子链接：
**

```
"entities": {
  "urls": [{
    "url": "https://t.co/SywNbZdDmb",
    "expanded_url": "https://x.com/XDevelopers/status/1050118621198921728",
    "display_url": "x.com/XDevelopers/s…",
     "indices": [
        142,

     ]
   }
  ]
}
```

<div id="filtering-operators">
  #### 过滤运算符
</div>

下面的运算符会在与 URL 元数据相关的字段上进行过滤，并执行基于分词的匹配：

**url:**

* 示例：“url:tennis”
* 对任意包含单词 tennis 的展开 URL 执行基于分词的匹配
* 也可以用作过滤器，通过类似 “url:npr.org” 的方式包含或排除来自特定网站的链接

**url&#95;title:**

* 示例：“url&#95;title:tennis”
* 对任意 HTML 标题中包含单词 tennis 的展开 URL 执行基于分词的匹配
* 在响应负载中包含的 HTML 标题数据上进行匹配，该数据最多 300 个字符。

**url&#95;description:**

* 示例：“url&#95;description:tennis”
* 对任意 HTML 描述中包含单词 tennis 的展开 URL 执行基于分词的匹配
* 在响应负载中包含的 HTML 描述上进行匹配，该数据最多 1000 个字符。
   

<div id="http-status-codes">
  #### HTTP 状态码
</div>

URL 展开富化还会提供我们尝试展开的最终 URL 的 HTTP 状态码。正常情况下，这将是 200。其他 400 系列的值表示解析该 URL 时出现问题。

在尝试展开一个 URL 时，可能会返回多种状态码。在展开 URL 的过程中，如果遇到重定向，我们会一直跟随，直到：

* 收到 200 系列状态码（成功）
* 收到非重定向系列状态码（失败）
* 因为最终 URL 无法在合理时间内解析而超时（返回 408（Timeout））
* 遇到某种异常
   

如果遇到异常，我们使用以下原因与返回状态码之间的映射：

| 原因 | 返回的状态码 |
| :--- | :--- |
| SSL 异常 | 403 (Forbidden) |
| 不允许对该 URL 进行展开 | 405 |
| 套接字超时 | 408 (Timeout) |
| 未知主机异常 | 404 (Not Found) |
| 不支持的操作 | 404 (Not Found) |
| 连接异常 | 404 (Not Found) |
| 非法参数 | 400 (Bad Request) |
| 其他所有情况 | 400 (Bad Request) |

<div id="matching-rules">
  ### 匹配规则
</div>

matching rules 富化数据是一个元数据对象，用于指示接收到的帖子匹配了哪些规则。这最常与 PowerTrack 流一起使用。

匹配是通过对规则中包含的词项进行精确匹配来完成的，会在带标点和不带标点两种情况下扫描活动内容。匹配不区分大小写。当发现内容包含规则中定义的所有词项时，会在根级别包含一个 matching&#95;rules 对象，用于指示导致匹配的规则。

**PowerTrack**

通过 PowerTrack（realtime、Replay 和 Historical）传送的帖子会包含如下所示的 matching&#95;rules 对象：

```
"matching_rules": [{
        "tag": null,
        "id": 907728589029646336,
        "id_str": "907728589029646336"
    }]
```

在 PowerTrack 中，`matching_rules` 对象表示与给定结果匹配的*所有*规则。换句话说，如果多个规则匹配同一个帖子，该帖子只会被投递一次，但 `matching_rules` 元素会包含所有与之匹配的规则。

<div id="poll-metadata">
  ### 投票元数据
</div>

投票元数据是一种免费富化数据，可在所有产品（实时和历史 API）的原生富化格式负载中使用。该元数据会指示帖子中是否包含投票，列出投票选项列表，并包含投票时长和到期时间。此类富化数据便于识别帖子中是否包含投票，并支持正确渲染用于展示的投票帖子。

<div id="important-details">
  ##### 重要细节：
</div>

* 适用于所有企业级 API（PowerTrack、Replay、Search、Historical PowerTrack）
  * *注意：* 对于 Replay 和 Historical PowerTrack，此元数据首次提供于 2017 年 2 月 22 日（02/22/17）。
* 不包含投票信息或投票结果
* 目前不支持 filter/operator
* 仅提供 **增强的原生格式（enriched native format）**
  * 增强的原生格式是一个由用户控制的设置，可随时通过 Console 控制台进行更改：*Select a Product (PowerTrack, Replay, Search) &gt; Settings tab &gt; Output Format (Leave data in its original format)*

<div id="post-payload">
  #### 帖子有效负载
</div>

投票帖子会在有效负载中的 “entities.polls” 对象里包含以下元数据：

* 一个 “options” 数组，最多包含四个选项，其中包括位置（1-4）和选项文本
* 投票结束日期
* 投票持续时长

请参阅下面的示例有效负载作为参考。

#### 示例负载

下面是一个扩展后的原生格式负载片段，用于展示新增的投票元数据：

```json
"entities":{
          "hashtags":[],
          "urls":[],
          "user_mentions":[],
          "symbols":[],
          "polls":[
             {

<div id="profile-geo">
  ### 个人资料地理位置
</div>

<div id="introduction">
  #### 介绍
</div>

许多 X 用户的个人资料包含由用户提供的公共位置信息。该数据以普通字符串形式返回在 user.location 字段中（参见 [User 对象数据字典](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-dictionary#native-enriched-user-object)）。Profile Geo Enrichment 通过在可能的情况下对位置字符串进行地理编码和规范化，为 user.location 的值添加相关的结构化地理数据。只有当这些数据在 enterprise API 产品中作为 Post 负载的一部分出现时，纬度/经度坐标以及相关地点元数据才会被添加到 user.derived.locations 中。使用 [增强的原生格式](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-dictionary) 时可以获取这些数据，并且可以结合使用 [PowerTrack 规则](/zh/x-api/enterprise-gnip-2.0/fundamentals/rules-filtering#enterprise-operators) 进行过滤。

<Note>
  **注意：** 用于创建 Profile Geo Enrichment 的部分辅助地理数据来自 GeoNames.org，X 依据 [Creative Commons Attribution 3.0 License](https://creativecommons.org/licenses/by/3.0/us/legalcode) 许可协议使用这些数据。
</Note>

Profile Geo 数据将会包含在 X 的 PowerTrack、Replay、Volume Stream、Search 和 Historical PowerTrack API 中。

<div id="profile-geo-data">
  #### 个人资料地理数据
</div>

| 增强后的原生字段名称 | 示例值 | 说明 |
| :--- | :--- | :--- |
| user.derived.locations.country | United States | 创建该帖子的用户所在的国家/地区。 |
| user.derived.locations.country&#95;code | US  | 与创建该帖子的用户所在国家/地区相对应的两个字母 ISO-3166 国家代码。 |
| user.derived.locations.locality | Birmingham | 创建该帖子的用户所在的地区（通常为城市）。 |
| user.derived.locations.region | Alabama | 创建该帖子的用户所在的区域（通常为州/省）。 |
| user.derived.locations.sub&#95;region | Jefferson County | 创建该帖子的用户所在的次级区域（通常为县）。 |
| user.derived.locations.full&#95;name | Birmingham, Alabama, United States | 创建该帖子的用户所在位置的完整名称（不含次级区域）。 |
| User.derived.locations.geo | See Below | 一个数组，其中包含与创建该帖子的用户所在位置的最细粒度位置相对应的经纬度坐标值。 |

Historical PowerTrack、Search 和 PowerTrack API 支持基于个人资料地理数据进行过滤。有关可用于对个人资料地理数据进行过滤的运算符的更多详细信息，请参阅相应的产品文档。

</div>

                {

```

<div id="limitations">
  #### 限制
</div>

* Profile Geo 丰富化会尝试为用户资料位置字符串中描述的地理位置确定最佳匹配结果。由于可能存在多个名称相似的地点或地名本身存在歧义等因素，结果在所有情况下可能都不够准确。
* 如果用户的资料位置字段（actor.location）中未提供值，我们将不会尝试进行分类。
* 精度级别：如果 Profile Geo Enrichment 只能在国家或地区级别上有把握地确定结果，则诸如 subRegion 和 locality 等更低级别的地理信息将不会包含在负载中。
* Profile Geo 丰富化会提供与其结果精度级别相对应的纬度/经度坐标（单个点）。这些坐标代表丰富化结果位置的地理中心。例如，如果精度级别是国家级别，则这些坐标将设置为该国家的地理中心。
* 为地址属性（locality/region/country/country code）提供的 PowerTrack 运算符在设计上具有较高的粒度，以支持多种规则组合。当尝试定位与其他地点同名的特定位置时，请考虑组合使用地址规则。例如，以下规则可以避免匹配到“San Francisco, Philippines”：profile&#95;locality:&quot;San Francisco&quot; profile&#95;region:California。在构建针对单个 Profile Geo 字段的规则时，请注意，每提升一级粒度，您看到的结果范围都会进一步收窄。在某些情况下，当尝试查看来自某个城市的数据时，您可能只希望依赖 region 规则，而该 region 与该城市具有较大重叠。例如，通过 profile&#95;region:&quot;Zurich&quot; 可以有效地定位瑞士苏黎世市及其周边区域。
* 与原生地理信息帖子配合使用：Profile Geo 丰富化为帖子提供了一种不同于负载中原生 geo 值的替代地理信息类型。这两种地理信息类型可以组合使用，以捕获与给定区域相关的所有可能帖子（基于可用地理数据），尽管在概念上它们并不等价。

## 介绍

`Enterprise`

Enterprise 富化数据是添加到某些数据 API 的响应负载中的附加元数据。它们仅适用于付费订阅方案。

下表对每种富化数据进行了简要说明：

| Enrichment: | Description: |
| :--- | :--- |
| Expanded and Enhanced URLs | 自动展开帖子正文中包含的短链接（如 bitly），并从目标页面提取 HTML 标题和描述等元数据。 |
| Matching rules object | 指明接收到的帖子匹配了哪些规则。该对象会在响应对象中返回规则标签和规则 ID。 |
| Poll metadata | 标记帖子中是否存在投票，包含投票选项列表，并包括投票持续时间和到期时间。 |
| Profile geo | 基于用户个人资料中的位置推导出的位置信息数据，包括（在可能的情况下）[经度、纬度] 坐标以及相关地点元数据。 |

<div id="expanded-and-enhanced-urls">
  ### 扩展和增强的 URL
</div>

扩展和增强 URL 富化功能会自动展开包含在帖子正文中的短链接 URL，并将解析得到的最终 URL 作为元数据包含在负载中。此外，此富化还会从目标页面的 `title` 和 `description` 中提取 HTML 页面元数据。

**重要细节：**

* 为了解析短链接，我们的系统会向提供的 URL 发送 HTTP HEAD 请求，并跟随所有重定向，直到到达最终的 URL。该最终 URL（而非页面本身的内容）会被包含在响应负载中。

* URL 富化会为实时流增加大约 5-10 秒的延迟。

* 对于发往 Full Archive Search API 的请求，扩展 URL 富化数据仅适用于发布时间在过去 13 个月以内的帖子。

* URL 富化不适用于帖子链接（包括引用推文）、Moments 链接以及包含在帖子中的个人资料链接。 
   

<div id="post-payload">
  #### Post 负载
</div>

Expanded 和 Enhanced URL 富化位于帖子负载中的 `entities` 对象内——具体是在 `entitites.urls.unwound` 对象中。它提供以下元数据字段：

* 展开后的 URL - `unwound.url`
* 展开后的 HTTP 状态码 - `unwound.status`
* 展开后的 URL HTML 标题 - 最多 300 个字符 - `unwound.title`
* 展开后的 URL HTML 描述 - 最多 1000 个字符 - `unwound.description`

**下面是一个带有 URL 富化的 [entities 对象](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-dictionary#x-entities) 示例：**

```
"entities": {
    "hashtags": [

    ],
    "urls": [
      {
        "url": "https:\/\/t.co\/HkTkwFq8UT",
        "expanded_url": "http:\/\/bit.ly\/2wYTb9y",
        "display_url": "bit.ly\/2wYTb9y",
        "unwound": {
          "url": "https:\/\/www.forbes.com\/sites\/laurencebradford\/2016\/12\/08\/11-websites-to-learn-to-code-for-free-in-2017\/",
          "status": 200,
          "title": "11 Websites To Learn To Code For Free In 2017",
          "description": "It\u2019s totally possible to learn to code for free...but what are the best resources to achieve that? Here are 11 websites where you can get started."
        },
        "indices": [
          10,
          33
        ]
      }
    ],
    "user_mentions": [

    ],
    "symbols": [

    ]
  },
```

<div id="filtering-operators">
  #### 过滤运算符
</div>

以下运算符会在 URL 元数据的相关字段上进行过滤，并执行分词匹配：

**url:**

* 示例：“url:tennis”
* 在任何包含单词 tennis 的 Expanded URL 上进行分词匹配
* 也可用作过滤器，通过类似 “url:npr.org” 这样的语法来包含或排除来自特定网站的链接

**url&#95;title:**

* 示例：“url&#95;title:tennis”
* 在任何包含单词 tennis 的 Expanded URL 的 HTML 标题上进行分词匹配
* 匹配负载（payload）中包含的 HTML 标题数据，该内容限制为 300 个字符。

**url&#95;description:**

* 示例：“url&#95;description:tennis”
* 在任何包含单词 tennis 的 Expanded URL 的 HTML 描述上进行分词匹配
* 匹配负载（payload）中包含的 HTML 描述，该内容限制为 1000 个字符。
   

<div id="http-status-codes">
  #### HTTP 状态码
</div>

展开 URL 的富化功能还会提供我们尝试展开得到的最终 URL 的 HTTP 状态码。在正常情况下，这将是 200 状态码。其他 400 系列的状态码表示解析 URL 时出现问题。

在尝试展开一个 URL 时，可能会返回不同的状态码。在展开 URL 的过程中，如果遇到重定向，我们会一直跟随重定向，直到出现以下情况之一：

* 命中 200 系列状态码（成功）
* 命中非重定向系列状态码（失败）
* 因为在合理时间内无法解析最终 URL 而超时（返回 408（超时））
* 遇到某种异常
   

如果遇到异常，我们会在原因与返回状态码之间使用以下映射关系：

| 原因 | 返回的状态码 |
| :--- | :--- |
| SSL Exceptions | 403 (Forbidden) |
| Unwinding not allowed by URL | 405 |
| Socket Timeout | 408 (Timeout) |
| Unknown Host Exception | 404 (Not Found) |
| Unsupported Operation | 404 (Not Found) |
| Connect Exception | 404 (Not Found) |
| Illegal Argument | 400 (Bad Request) |
| Everything else | 400 (Bad Request) |

<div id="matching-rules">
  ### 匹配规则
</div>

匹配规则富化信息是一个元数据对象，用于指示接收到的帖子匹配了哪些规则。它最常用于 PowerTrack 流。

匹配将通过对规则中包含的关键词进行精确匹配来完成，会在带标点和不带标点的情况下扫描活动内容。匹配不区分大小写。当发现内容包含规则中定义的所有关键词时，将在根级出现一个 matching&#95;rules 对象，指示导致匹配的规则。

**PowerTrack**

通过 PowerTrack（实时、回放和历史）传送的帖子将包含如下所示的 matching&#95;rules 对象：

```
"matching_rules": [{
        "tag": null,
        "id": 907728589029646336,
        "id_str": "907728589029646336"
    }]
```

在 PowerTrack 中，`matching_rules` 对象表示与给定结果匹配的*所有*规则。换句话说，如果有多条规则匹配某条帖子，该帖子只会被投递一次，但 `matching_rules` 元素会包含所有与之匹配的规则。

<div id="poll-metadata">
  ### 投票元数据
</div>

投票元数据是一种免费富化信息，可在所有产品（实时和历史 API）的富化原生格式负载中使用。该元数据会指示帖子中是否存在投票，包含投票选项列表，以及投票时长和到期时间。此类富化信息便于识别帖子中是否包含投票，并支持对含投票的帖子进行正确渲染以用于展示。

<div id="important-details">
  ##### 重要说明：
</div>

* 适用于所有企业级 API（PowerTrack、Replay、Search、Historical PowerTrack）
  * *注意：* 对于 Replay 和 Historical PowerTrack，此元数据最早于 2017 年 2 月 22 日提供。
* 不包含投票信息或投票结果
* 目前不支持过滤器/运算符
* 仅以**增强原生格式（enriched native format）**提供
  * 增强原生格式是一项由用户控制的设置，可随时通过 Console 修改：*Select a Product (PowerTrack, Replay, Search) &gt; Settings tab &gt; Output Format (Leave data in its original format)*

#### 帖子负载

投票帖子会在负载中的 “entities.polls” 对象里包含以下元数据：

* 一个 “options” 数组，最多包含四个选项，每个选项包括序号（1–4）和选项文本
* 投票到期日期
* 投票持续时间

有关详细信息，请参阅下方的示例负载。

<div id="profile-geo">
  ### 个人资料地理位置
</div>

<div id="introduction">
  #### 简介
</div>

许多 X 用户个人资料都包含用户提供的公开位置信息。此数据以普通字符串形式返回在 `user.location` 中（参见 [User object data dictionary](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-dictionary#native-enriched-user-object)）。Profile Geo Enrichment 会在可能的情况下对位置字符串进行地理编码和规范化，从而为 `user.location` 的值添加相关的结构化地理数据。Profile Geo 的纬度/经度坐标及相关地点元数据，只有在作为企业级 API 产品中帖子载荷的一部分时，才会添加到 `user.derived.locations` 中。使用 [增强的原生格式](/zh/x-api/enterprise-gnip-2.0/fundamentals/data-dictionary) 时，这些数据可用，并且可以结合使用 [PowerTrack rules](/zh/x-api/enterprise-gnip-2.0/fundamentals/rules-filtering#enterprise-operators) 进行过滤。

<Note>
  **注意：** 用于创建 Profile Geo 增强功能的一部分支撑性地理数据来自 GeoNames.org，X 依据 [Creative Commons Attribution 3.0 License](https://creativecommons.org/licenses/by/3.0/us/legalcode) 使用这些数据。
</Note>

Profile Geo 数据将包含在 X 的 PowerTrack、Replay、Volume Stream、Search 和 Historical PowerTrack API 中。

<div id="profile-geo-data">
  #### Profile Geo 数据
</div>

| 扩展的原生字段名称 | 示例值 | 描述 |
| :--- | :--- | :--- |
| user.derived.locations.country | United States | 发布该帖子的用户所在的国家。 |
| user.derived.locations.country&#95;code | US  | 对应发布该帖子的用户所在国家的两个字母 ISO-3166 国家代码。 |
| user.derived.locations.locality | Birmingham | 发布该帖子的用户所在的地方信息（通常为城市）。 |
| user.derived.locations.region | Alabama | 发布该帖子的用户所在的区域信息（通常为州/省）。 |
| user.derived.locations.sub&#95;region | Jefferson County | 发布该帖子的用户所在的次级区域信息（通常为县）。 |
| user.derived.locations.full&#95;name | Birmingham, Alabama, United States | 发布该帖子的用户所在位置的全称（不包括次级区域）。 |
| User.derived.locations.geo | See Below | 一个数组，其中包含与发布该帖子的用户所在的最细粒度位置相对应的经纬度坐标值。 |

Historical PowerTrack、Search 和 PowerTrack API 支持基于 Profile Geo 数据进行过滤。有关可用于对 Profile Geo 数据进行过滤的运算符的详细信息，请参阅相应的产品文档。

#### 示例载荷

```
{
    "user": {
        "derived": {
            "locations": \[
                {
                    "country": "United States",
                    "country_code": "US",
                    "locality": "Birmingham",
                    "region": "Alabama",
                    "sub_region": "Jefferson County",
                    "full_name": "伯明翰, 阿拉巴马州, 美国",
                    "geo": {
                        "coordinates": \[
                            -86.80249,
                            33.52066
                        \],
                        "type": "point"
                    }
                }
            \]
        }
    }
}
```

<div id="limitations">
  #### 限制
</div>

* Profile Geo 增强功能会尝试在用户资料中 location 字符串所描述的地理地点中，选取最合适的地点。由于可能存在多个名称相似的地点或名称本身含义不明确等因素，结果在所有情况下可能并不准确。
* 如果用户资料中的 location 字段（actor.location）没有提供值，我们将不会尝试进行分类。
* 精度级别：如果 Profile Geo 增强只能在国家或地区级别上有足够信心做出判断，则诸如 subRegion 和 locality 等更低级别的地理信息将从返回的 payload 中省略。
* Profile Geo 增强会提供与其结果精度级别相对应的经纬度坐标（单个点）。这些坐标代表增强结果位置的地理中心。例如，如果精度级别是国家级，那么这些坐标将被设置为该国家的地理中心。
* 为地址属性（locality/region/country/country code）提供的 PowerTrack 运算符在设计上比较细粒度，以支持多种规则组合。当尝试定位名称与其他地点相同的特定位置时，可以考虑组合使用多个地址规则。例如，下面的组合可以避免匹配到 “San Francisco, Philippines”：profile&#95;locality:&quot;San Francisco&quot; profile&#95;region:California。构建针对单个 Profile Geo 字段的规则时，请记住，每增加一级粒度都会减少你看到的结果。在某些场景下，当你尝试查看某个城市的数据时，如果该地区与该城市高度重叠，你可能只依赖 region 规则会更合适，例如，瑞士苏黎世市及其周边区域可以通过 profile&#95;region:&quot;Zurich&quot; 得到有效覆盖。
* 与原生地理信息帖子配合使用：Profile Geo 增强为帖子提供了一种替代类型的地理信息，与 payload 中的原生 geo 值不同。这两种地理信息类型可以组合使用，以捕获与给定区域相关的所有可能帖子（基于可用的地理数据），尽管它们在概念上并不等同。

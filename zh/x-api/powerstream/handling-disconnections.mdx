<div id="what-is-a-disconnection">
  ## 什么是断开连接？
</div>

与流式 API 建立连接意味着发起一个生命周期非常长的 HTTPS 请求，并按增量方式解析其响应。当连接到 powerstream 端点时，你应该构造一个 HTTPS 请求，并在实际可行的情况下尽可能长时间地持续消费返回的流。我们的服务器会在没有服务器端错误、客户端严重延迟、网络问题、例行服务器维护或重复登录等情况的前提下无限期保持该连接处于打开状态。对于与流式端点的连接，连接被断开是很有可能、也应当预期的情况，因此需要实现相应的重连逻辑。

<div id="why-a-streaming-connection-might-be-disconnected">
  ## 流式连接可能断开的原因
</div>

你的流式连接可能因多种原因断开。请检查流返回的错误信息，以确定失败原因。可能的断开原因包括：

* 身份验证错误（例如使用了错误的令牌或错误的身份验证方式）。
* X 端的流式服务器被重启。这通常与代码部署相关，应被视为预期情况，并在设计中加以考虑。
* 你的客户端无法跟上流中传送的帖子量，或者读取 data 的速度过于缓慢。每个流式连接背后都有一个要发送给客户端的消息队列。如果该队列随着时间推移增长过大，连接将被关闭。
* 你的账号超出了每日或每月的帖子配额。
* 你的冗余活动连接过多。
* 客户端突然停止读取 data。如果从流中读取帖子的速率突然下降，连接将被关闭。
* 服务器与客户端之间可能出现网络问题。
* 暂时性的服务器端问题、计划内维护或更新。（请查看[状态页面](/zh/status)）

<div id="anticipating-disconnects-and-reconnecting">
  ## 预判断连并进行重连
</div>

在流式获取帖子时，目标是尽可能长时间保持连接，同时要意识到可能会发生断连。该端点会提供一个 20 秒的保活心跳（表现为一个换行符）。使用这一信号来检测自己是否正在被断开连接。

1. 你的代码应检测心跳和新内容是否停止到达。
2. 如果发生这种情况，你的代码应触发重连逻辑。某些客户端和编程语言允许你指定读取超时时间，你可以将其设置为 20 秒。
3. 你的服务应检测到这些断连并尽快重新连接。

一旦已建立的连接中断，应立即尝试重连。如果重连失败，应根据遇到的错误类型放慢重连尝试的频率：

* 对于 TCP/IP 层面的网络错误，采用线性退避。这类问题通常是暂时的，并且往往很快就会恢复。每次重连尝试将延迟时间增加 250ms，最长增加到 16 秒。
* 对于适合重连的 HTTP 错误，采用指数退避。从等待 5 秒开始，每次尝试将等待时间加倍，最长到 320 秒。
* 对于 HTTP 429 错误（超出速率限制），采用指数退避。从等待 1 分钟开始，每次尝试将等待时间加倍。请注意，每收到一次 HTTP 429，都会增加你必须等待的时间，直到你的账号不再受到速率限制影响。
   

<div id="recovering-lost-data">
  ## 恢复丢失的数据
</div>

如果你确实遇到了断连，可以采用几种不同的策略，来确保你能获取到可能错过的所有数据。我们在集成指南的[数据恢复](/zh/x-api/powerstream/recovery-and-redundancy)部分记录了一些关键步骤，你可以按照这些步骤来恢复遗漏的数据。 
 

<div id="rate-limits-and-usage">
  ## 速率限制和使用情况
</div>

要检查速率限制，响应会返回三个响应头。这样可以帮助你了解在 15 分钟窗口内可以使用多少次规则端点，以及流式端点允许多少次重连尝试。

* x-rate-limit-limit 表示在 15 分钟窗口内，分配给你的客户端可以发起的请求次数。

* x-rate-limit-remaining 表示在 15 分钟窗口内，当前窗口中剩余可用的请求次数。

* x-rate-limit-reset 是一个 UNIX 时间戳，表示 15 分钟窗口何时重新开始，并将 x-rate-limit-remaining 重置为 0。

过滤流端点当前不会报告使用数据。要检查已传递了多少条帖子，你的代码可以实现计量逻辑，以便在需要时对消费进行度量和暂停。 

在流的客户端一侧，你的代码只需将接收到的帖子插入到先进先出 (FIFO) 队列或类似的内存结构中；应由单独的进程或线程从该队列中消费帖子，以便解析并准备内容进行存储。通过这种设计，当传入帖子数量发生剧烈变化时，你可以实现一个能够高效扩展的服务。从概念上讲，你可以将其看作通过 HTTP 下载一个无限长的文件。

<div id="reconnection-best-practices">
  ## 重连最佳实践
</div>

<div id="test-backoff-strategies">
  ### 测试退避策略
</div>

测试退避机制的一个有效方法是使用无效的授权凭证，并观察重连尝试。设计良好的实现不应收到任何 429 响应。

<div id="issue-alerts-for-multiple-reconnects">
  ### 为多次重连发出告警
</div>

当客户端的重连间隔时间达到配置的上限阈值时，它应向你发送通知，以便你排查影响连接的问题。

<div id="handle-dns-changes">
  ### 处理 DNS 变更
</div>

测试你的客户端进程是否遵守 DNS 的生存时间（TTL，Time To Live）。某些协议栈会在整个进程生命周期内缓存解析出的地址，而不会在规定的 TTL 内应用 DNS 变更。这样的激进缓存会在 X 在不同 IP 地址之间进行负载切换时，导致你的客户端出现服务中断。

<div id="user-agent">
  ### User Agent
</div>

请确保你的 user-agent HTTP 头部中包含客户端的版本信息。这对于我们在 X 端诊断问题至关重要。如果你的运行环境无法设置 user-agent 头部，则请改为设置一个 x-user-agent 头部。

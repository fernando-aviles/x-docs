<div id="typical-response-structure">
  ## 典型响应结构
</div>

成功的响应会以 200 系列的 HTTP 状态码表示，并带有 JSON 格式的负载，其中包含被请求、创建、修改或删除的对象，以及服务器对你请求的理解结果。

如果你发送的请求成功，你会在响应中收到一个 `request` 节点，用于回显你的请求。

*示例：* [GET accounts/abcdefg/campaigns?with&#95;deleted=true](/zh/x-ads-api/campaign-management#campaigns)

```json
{
  /* 您的响应的 data... */,
  "request": {
    "params": {
      "account_id": "abcdefg",
      "with_deleted": "true"
    }
  }
}
```

JSON 响应中的 `data` 字段将包含与所使用的资源关联的具体对象。当响应可能包含一个或多个结果时，`data` 节点的格式为 JSON 数组；当响应中只可能有一个结果时，则会返回为 JSON 哈希对象。在某些罕见情况下，本应返回一个集合的响应可能会改为返回一个哈希表（hashmap）。在这种情况下，应将该单一哈希表视为一个与 `type` 字段中指定类型相同的对象。

<div id="error-response-structure">
  ## 错误响应结构
</div>

错误响应会返回非 200 系列的 HTTP 状态码。通常会附带一个 JSON 响应，但某些错误会返回不同类型的响应体。在这些无法解析出标准响应结构的情况下，应优先依据 HTTP 状态码本身的含义。例如，你可能偶尔会看到一个 HTTP 404 搭配一个 HTML 响应。在这种情况下，可以安全地认为请求的内容不存在（HTTP 404 表示“Not Found”）。

典型的错误响应在结构上与成功的响应类似。错误的性质会通过响应中的 `errors` 节点进行传达。`errors/code` 节点会提供一个 CAPS&#95;CASE 常量错误代码，你可以在程序中使用它来做出错误处理决策。`errors/message` 节点会提供一个（通常是）面向人的英文错误描述。还可能附加其他字段，以提供关于该错误更细粒度的详细信息。

```json
{
  "errors": [
    {
      "parameter": "start_time",
      "details": "无效的日期",
      "code": "INVALID_PARAMETER",
      "value": "",
      "message": "start_time 应为时间值,实际为 \"\""
    }
  ],
  "request": {
    "params": {
      "account_id": "hkk5"
    }
  }
}
```

在上述示例中，我们向分析端点发起了一个请求，其中 `start_time` 参数的值无效。对于包含无效参数的请求，其 `errors/code` 字段为 `INVALID_PARAMETER`。

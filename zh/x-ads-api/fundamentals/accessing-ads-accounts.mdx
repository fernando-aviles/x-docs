<div id="user-accounts-vs-ad-accounts">
  # 用户账号与广告账号
</div>

在使用 Ads API 时会涉及两种不同类型的账号：广告账号和 X 用户账号。在 Ads API 文档中，“account” 一词通常指广告账号。

* 广告账号在 **business.x.com** 上注册，并在 API 中通过 `account_id` 标识。广告账号直接关联资金来源，并使用一个或多个 X 用户账号的内容，这些账号被视为“可推广用户”。每个广告账号可以授予一个或多个 X 用户账号访问权限。广告账号（或称为“当前账号”）在几乎每个执行的 URL 中都以内联参数 `:account_id` 的形式出现。
* X 用户账号（例如 @AdsAPI）在 Ads API 中通过 `user_id` 标识。可以将一个或多个此类账号与某个广告账号关联。通过 API 发起请求的已认证 X 用户账号被称为“当前用户”。当前用户可访问的广告账号列表可以通过 [GET accounts](/zh/x-ads-api/campaign-management#accounts) 获取。“Promotable users”（可推广用户）是指某个特定广告账号可以推广的 X 账号（X 句柄）。有关这方面的更多详情，请参阅 [Obtaining Ads Account Access](/zh/x-ads-api/introduction)。

<div id="methods-for-ad-account-access">
  ## 获取广告账户访问权限的方法
</div>

你可以通过两种方式为广告主的账户发起 Ads API 请求：

1. 代表某个广告主发起请求（**推荐**）
2. 使用你自己的账户（该账户已被授予访问某个广告主账户的权限）发起请求，例如为多个账户提供支持的[代理商](https://business.x.com/en/blog/agencies-manage-multiple-Twitter-Ads-accounts.html)。

本文档简要概述了这两种方式之间的差异，应与我们的其他资源（例如[多用户登录常见问题解答](https://business.x.com/en/help/troubleshooting/multi-user-login-faq.html)）结合使用。 

如[授权请求](/zh/resources/fundamentals/authentication#authorizing-a-request#authorizing-a-request)中所述，对 Ads API 的所有请求都需要在 Authorization 头部中使用 [OAuth 1.0a](/zh/resources/fundamentals/authentication)，其访问令牌需通过[三方](/zh/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow)[OAuth](/zh/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow) 流程获取。你的应用需要实现基于 Web 的 OAuth 授权流程来[获取访问令牌](/zh/resources/fundamentals/authentication#oauth-1-0a-2)。Ads API 开发者绝不应要求我们的 X 广告主共享其登录凭据。

默认情况下，每个 [X 开发者 App](/zh/resources/fundamentals/developer-apps)都包含一个固定的 **access token**，可用于为拥有该 App 的账户发起 Ads API 请求。对于无需三方或[基于 PIN 的 OAuth](/zh/resources/fundamentals/authentication#pin-based-authorization)流程的单账户用例，这些凭据是理想选择。如果你不需要访问其他 X Ads 账户，请使用这些[单用户](/zh/resources/fundamentals/authentication#oauth-1-0a-2)凭据，而不是使用下文所述的步骤。

<div id="levels-of-access">
  ## 权限级别
</div>

<div id="app-level-permissions">
  ### 应用级权限
</div>

每位用户都会在[申请 Ads API 访问权限](/zh/x-ads-api/getting-started/step-by-step-guide)时获得相应的访问级别：

* **仅转化（Conversion Only）**：用户可以以[读写](/zh/resources/fundamentals/developer-apps)访问权限访问 [Mobile](/zh/x-ads-api/measurement/mobile-conversions) 和 [Web Conversion](/zh/x-ads-api/measurement/web-conversions) 端点。
* **标准访问（Standard Access）**：用户可以以[读写](/zh/resources/fundamentals/developer-apps)访问权限访问 [Analytics](/zh/x-ads-api/analytics)、[Campaign Management](https://developer.x.com/en/docs/twitter-ads-api/campaign-management/overview)、[Creatives](https://developer.x.com/en/docs/twitter-ads-api/creatives/overview)、[Custom Audiences](https://developer.x.com/en/docs/twitter-ads-api/audiences/overview) 和 [Conversion](/zh/x-ads-api/measurement/web-conversions) 端点。

**注意：** 在 2023 年 7 月之前申请访问权限的 Ads API 开发者，其访问级别和权限可能不同，并且可能被限制为最多五个 OAuth 令牌。请参阅我们的[提升访问权限](/zh/x-ads-api/getting-started/increasing-access)指南，以获取更多端点访问权限，或为现有应用解除令牌数量限制。

<div id="ad-account-level-permissions">
  ### 广告账户级别权限
</div>

每个有权访问某个广告账户的用户都会被授予一个特定的账户级别权限：**Account administrator**、**Ad manager**、**Campaign analyst**、**Organic analyst** 和 **Creative Manager**。请参阅 **business.x.com** 了解最新的账户级别权限文档。应用程序应通过 [Authenticated User Access](/zh/x-ads-api/campaign-management#authenticated-user-access) API 端点获取当前已授权用户的权限，以确定该用户可以访问哪些 API 端点和 Ads 功能。

**注意：** 与 [Conversion API](/zh/x-ads-api/measurement/web-conversions) 一起使用的任何用户令牌必须对应具有 **Account administrator** 或 **Ad manager** 账户级别权限的用户。                                                                                                                                              

<div id="methods-of-obtaining-access-tokens">
  ## 获取访问令牌的方式
</div>

<div id="1-obtain-an-advertisers-user-access-token">
  ### 1. 获取广告主（用户）访问令牌
</div>

获取广告主 **access token** 有两种方法。最常见的方法是通过你 Web UI 中的[三方 OAuth 授权流程](/zh/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow)直接获取。对于没有向广告主公开可访问 UI 的应用程序，可以采用[基于 PIN 的](/zh/resources/fundamentals/authentication#pin-based-authorization) OAuth 授权流程。用户完成三方流程后，你的应用程序就会拥有代表其 Ads 账户通过 API 发起请求所需的凭据。

通过 OAuth 流程获取用户凭据是我们对大多数 Ads API 开发者 **强烈建议** 用于获取广告主账户访问权限的方法。它允许你代表用户调用 API，并以该用户身份执行操作。这些令牌本身不会过期，但用户可以在任何时间撤销它们。

<div id="2-obtain-your-developer-access-token">
  ### 2. 获取你的（开发者）访问令牌
</div>

此选项要求广告主通过 business.x.com 上的 X 用户界面（UI）[授予你的 @username](https://business.x.com/en/help/troubleshooting/multi-user-login-faq.html)（或多个 @username）对其 X Ads 账户的访问权限。通过你的账户使用三方（3-legged）OAuth 授权流程获取的**访问令牌**将能够访问该广告主的 X Ads 账户。

这样你可以使用自己 @username 的 OAuth 令牌来调用 API，而不是使用广告主的 OAuth 令牌。此选项的关键区别在于：只有当已为你的 @username 授予 Post delegation/composer 权限时，你才能创建仅推广帖子（Promoted-Only Posts）。

若要代表账户中的 `FULL` promotable user 创建仅推广帖子，你还必须在此流程中被授予创建帖子（Posts）的权限。这样就可以通过 [GET accounts/:account&#95;id/authenticated&#95;user&#95;access](/zh/x-ads-api/campaign-management#accounts) 端点上的 `TWEET_COMPOSER` 权限获得访问权限。

<div id="differences-between-these-methods">
  ## 这些方法之间的差异
</div>

|     |     |     |
| :--- | :--- | :--- |
|     | 广告主（用户）OAuth Token | （开发者）OAuth Token  <br /> （添加 @username 以区分账户） |
| 访问 Ads 账户 | ✔   | ✔   |
| 代表用户创建帖子 | ✔   | ✔*  |
| 管理广告活动 | ✔   | ✔   |
| 访问分析数据 | ✔   | ✔   |
| 代表用户创建卡片 | ✔   | ✔   |
| 开发者通过  <br />X Ads UI 进行访问的权限 |     | ✔   |
| [速率限制](/zh/x-api/enterprise-gnip-2.0/fundamentals/rate-limits) | 针对每个广告主单独计算 | 针对每个广告主账户单独计算 |

<Note>
  **注意：** 详情请参阅上文的 **[获取（开发者）access token](/zh/x-ads-api/fundamentals/accessing-ads-accounts#2-obtain-your-developer-access-token)** 部分。
</Note>

<div id="advertisers-access-token-via-oauth-3-legged-web-flow">
  ### 通过 OAuth 3-legged Web 流程获取广告主访问令牌
</div>

标准流程是基于 Web 的，并使用 [3-legged 授权](/zh/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow) 的 OAuth 流程。这里展示的截图来自一个示例应用，你可以在此查看其源代码：[https://github.com/xdevplatform/twauth-web](https://github.com/xdevplatform/twauth-web)。

在应用程序的某个阶段，你需要重定向到 X，以便为你的应用程序授权。

  <img src="https://cdn.cms-twdigitalassets.com/content/dam/developer-twitter/images/twauth-web-2.png" alt="image0" />
</Frame>

当你携带请求令牌重定向到 X 时，系统会提示用户为你的应用程序授权。

<Frame>
  <img src="https://cdn.cms-twdigitalassets.com/content/dam/developer-twitter/images/twauth-web-3.png" alt="image1" />
</Frame>

在用户为你的应用程序授权之后，将被重定向到你在生成请求令牌时提供的回调 URL。你将使用该回调 URL 获取该用户的永久访问令牌，并将其存储在本地！

## 自定义受众

<div id="overview">
  ### 概述
</div>

合作伙伴有多种方式可以创建[自定义受众](https://business.x.com/en/targeting/tailored-audiences.html)。

* [受众 API（CRM）](#crm)
* [网页](#web)
* [移动端](#mobile)
* [灵活受众](#flexible)

请注意，无法在定向时排除相似（lookalike）自定义受众。此外，也不能在同一个广告明细项（广告组）中同时定向自定义受众和其相似自定义受众。

**受众管理**

受众可以通过受众合作伙伴和 Ads API 合作伙伴进行管理。我们在 API 中提供了一系列端点来访问和维护自定义受众。

对于自定义受众信息，我们提供 2 个端点：

* [GET accounts/:account&#95;id/custom&#95;audiences](/zh/x-ads-api/audiences)
* [GET accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id](/zh/x-ads-api/audiences)

有关如何上传和管理受众的更多详细信息，请参阅[受众 API 指南](/zh/x-ads-api/audiences)。

**处理时间**

一般来说，受众更改会以批处理方式进行处理，每 6–8 小时运行一次。在受众更改处理期间，正在更新的现有受众不会受到影响。我们不建议在这一时间范围内对同一受众进行超过一次的添加操作更新和一次的移除操作更新。

**定向**

只有当某个受众在过去 90 天内于 X 自有及运营的客户端上匹配到至少 100 名活跃用户时，才可以对其进行定向。[GET accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id](/zh/x-ads-api/audiences) 会指示某个受众是否因匹配用户过少而无法被定向。

<div id="audiences-faq">
  ### Audiences FAQ[](#real-time-tailored-audiences "此标题的永久链接")

**问：我们推送了大量数据，为什么受众规模显示为 TOO&#95;SMALL？**

答：当前系统正在实时将数据添加到受众中，但用于处理数据并计算受众规模的任务只会在一段时间后运行。正确的受众规模应在数小时后显示在 UI 中。

**问：我们已经完成发送受众数据，并等待了 24 小时或更久，但仍然无法投放到该受众——下一步应该怎么做？**

答：请确认以下事项：

* 传递的用户 id 正确且格式未出错。
* 传递的受众名称正确，并且与之前的成员更新相匹配。
* 请确认来自 POST 命令的响应。
* 请确认 ID Sync 像素已正确部署，并且如 ID Sync 流程所述，有足够的用户访问了相关站点以完成用户映射。在成员更新中无法映射的用户将不会被转换为可被定向的用户。

如果以上各项都已确认正确且工作正常，请联系 X 产品联系人，并尽可能详细地提供信息（可参考 [Guide to Partner Inbounds](/zh/x-ads-api/introduction) 中推荐的信息示例）。

**问：我们可以调用该端点多少次，应使用什么算法？**

答：我们强烈建议你只向我们的系统发送增量变化数据，切勿重复发送完整的受众成员列表。系统已经过测试，吞吐量足以处理全球最大网站之一的增量数据更新。受众的初始上传应谨慎限流，且预期首次上传将需要相当长的时间才能完成。

**问：受众用于投放时的最小规模是多少？**

* 受众用于投放时的最小规模为 100 名用户（匹配后人数）。如果受众匹配到的用户少于 500 名，则不会在 X Ads UI 中显示为可投放对象。

**问：处理受众文件需要多长时间？受众文件在 X 用户界面中准备就绪需要多长时间？**

* 通常处理受众文件需要 4–6 小时，但这取决于文件大小。文件处理完成后，这些受众会在 X Ads UI 中可用。

**问：匹配率是如何计算的？**

* 匹配率 = 过去 90 天内活跃的 X 用户数 / 提供的用户数量

**问：如何测试一个受众文件是否正常工作？**

* 你可以提供一个测试受众文件，并使用 “keltonlynn” 作为广告主账号名（handle）。然后我们可以验证该文件是否能够被正确导入并加载到 X UI 中。

**问：什么是合作伙伴用户标识符（`p_user_id`）？**

* 这是你的公司用来唯一标识每位客户的标识符。

**问：什么是标准 ID？**

* 这可以是电子邮件地址、设备 ID、X @handle 或 ID。

**问：如何获取 HMAC Key？**

* 我们会通过加密电子邮件提供该密钥。请将你的公有 PGP key 发送至 [mpp-inquiry@x.com](mailto:mpp-inquiry%x.com)，我们会先向你发送一封测试邮件以验证一切工作正常。验证通过后，我们会向你发送 HMAC Key。

**问：如何使用给定的 HMAC Key 验证哈希过程是否成功？**

* X 会提供一个测试文件（包含示例电子邮件地址、设备 ID 等）以及一个对应的哈希结果文件，你可以将自己的结果与之比对验证。

**问：完整数据匹配文件是否有大小限制？**

* 没有，完整数据匹配文件没有大小限制。

**问：完整数据匹配文件的处理需要多长时间？**

* 一旦 X 收到该文件，处理大约需要 1 天时间。

**摘要**

Company 将代表客户向 X 提供一份经过哈希处理的常见用户标识符列表（例如电子邮件地址）或合作伙伴用户 ID，用于执行盲匹配并生成一份用于定向投放的 X 用户 ID 列表。用于定向投放的受众分段（segments）将根据在 ads.x.com 广告系列设置中由文件名指定的、对应广告主的特定 @handle 提供给该广告主使用。

来自 Company 的所有文件都将通过 IronBox（www.golockbox.com）上的安全数据包传输至 X，使用的是 X 为 Company 提供的特定账户。X 将为 Company 开通对 IronBox 的访问权限。有关 IronBox API 的文档可在 [https://secure.goironcloud.com/Docs/Help/](https://secure.goironcloud.com/Docs/Help/) 查阅。

<div id="partner-id-matching-requirements">
  #### 合作方 ID 匹配要求
</div>

如果公司使用其自身的标准 ID 系统来跟踪用户（即不是使用电子邮件地址、设备 id、X 用户 ID 等这类通用用户标识符），则建议使用以下流程。

**1. 全量数据匹配**

在初始阶段，公司需向 X 提供一份完整的用户记录列表，其中每条记录都包含一个与 X 共有的唯一通用用户标识符，将其放在单个文件中，用于执行一次全量数据匹配，并由 X 生成一份映射，将合作方 ID（`p_user_id`）映射到 X 的 ID（`tw_id`），并由 X 保存。此操作将以 2–3 个月为周期定期进行，以确保数据保持最新。匹配完成后，X 将通过电子邮件向公司反馈该文件的基线匹配率。

该文件的格式应为：

Name Convention: FullDataMatch.[CompanyName].txt

Hashing Algorithm: HMAC&#95;SHA-256

Format:

Column 1: 通用用户标识符的 HMAC 哈希值

Column 2: 合作方用户 ID（对每个用户唯一，在文件中可重复出现）

Column Delimiter (CSV): 使用逗号将已哈希的通用用户标识符与合作方 ID 分隔

Line separated values

* 例如：如果用户记录 A 的合作方用户 ID 为 1，且具有通用用户标识符 1、2 和 3：

|     |     |
| :--- | :--- |
| 通用用户标识符 1 | p&#95;user&#95;1 |
| 通用用户标识符 2 | p&#95;user&#95;1 |
| 通用用户标识符 3 | p&#95;user&#95;1 |

*有关通用用户标识符，请参阅下方“Hashing Directions”部分

**2. 自定义分群列表**

公司将以 `p_user_id` 列表的形式提供用户，用于在 X 上为客户创建用于定向的自定义受众。

* Line separated values
* `p_user_id`
* * (Same as provided in 1. Full Data Match section above. If the value provided in full data match is hashed then Company will provide same hashed value in audience file. If value provided is not hashed then Company will provide unhashed value.)

<div id="standard-matching-requirements">
  #### 标准匹配要求
</div>

如果公司未使用统一的标准 ID 来映射所有客户的用户标识符，建议遵循以下流程。

**自定义细分列表**

公司将代表客户直接向 X 提供常用用户标识符（如电子邮件地址）的哈希列表，用于创建自定义受众。

该文件的格式应为：

* 每行一个值
* 常用用户标识符的哈希值（例如电子邮件地址）
* 遵循下面列出的文件命名约定
* 遵循下文“哈希处理指引”中针对电子邮件地址的哈希要求

<div id="custom-segment-list-file-naming-operations">
  #### 自定义 Segment 列表文件命名与操作
</div>

文件应执行的操作由其文件名决定，可用操作及通用文件命名约定如下：audiencename&#95;partnername.handle.operation.filetype

* audiencename：Custom Audience 的名称。此字段的值是在 ads.x.com 广告系列设置界面中选择受众时显示的名称，例如 brand&#95;loyalty&#95;card&#95;holders。
* partnername：代表广告主提供 data 的公司名称，例如 company&#95;name。
* handle：将有权访问 Custom Audiences 的 X 账号（@handle），例如 @pepsi、@dietpepsi。
* operation：new、add、remove、removeall、replace（详见下文）。
* ：标准 Unix epoch 时间（以秒为单位），用于确保上传的每个受众文件都是唯一的。
* filetype：文件必须为 *.txt 格式。

<div id="creating-and-updating-audiences">
  #### 创建和更新受众
</div>

使用单个文件创建一个新受众，例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.new.txt

Add - 将列表中的匹配项添加到现有受众，例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.add..txt

Remove - 从现有受众中移除列表中的匹配项，例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.remove..txt

Remove All - 从该客户的所有受众中移除由定期更新的累积列表产生的匹配项（即客户的退订名单）。例如：partnername.pepsi.removeall.txt

* 可用于维护一个包含所有已从该广告主退订用户的完整列表。
* X 只会采用此文件中提供的最新列表，并会将其应用到在提供并处理此文件时已匹配到的所有现有和未来受众中的 X 用户。

Replace - 删除现有受众并用新的受众列表替换。例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.replace..txt

Overall Company Opt-Out - 公司将提供一个累积的退订文件，用于移除根据公司退订政策已退订的用户。

X 只会采用此公司退订文件中提供的最新列表，并会将其应用到在提供并处理此文件时已匹配到的 X 用户所属的所有现有和未来受众中。公司退订文件的格式如下：例如：partnername.removeall.txt

Delete - 从当前受众列表中移除现有受众，例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.delete.txt

<div id="hashing-directions">
  #### 哈希指引
</div>

X 将通过 PGP 安全地共享一个使用 base64 编码的生产密钥，用于对常见用户标识符（如电子邮件地址）进行哈希处理。Company 将对该密钥进行 base64 解码，以生成一个 32 字节的密钥，用于执行哈希运算。

base64 编码密钥示例：

BrQvOg+dACBUmKjRiNxZgJLh6zydjS0ZOv80FelTNzM=

base64 解码密钥示例：

/:� TшY

规范化：Company 在进行哈希之前，将对常见用户标识符执行基本规范化处理（设备 ID 除外，参见 Device ID Normalization 部分）。

<div id="e-mail-normalization">
  #### 电子邮件规范化
</div>

即去除首尾空格，并将电子邮件地址整体转换为小写。

示例：原始电子邮件地址：testemail&#95;Organisational&#95;baseball+884`@`It92I6Ev2B`.`Com

规范化后：testemail&#95;organisational&#95;baseball+884`@`it92i6ev2b`.`com

哈希值：74d9584eded0ad1e5572a1c1849f3716751d371d6117a6155dad5363f4b4fbec

注意：编码后的 HMAC 值和密钥的字符数会根据输入和编码方式而变化，因此字符数量并不固定。

<div id="device-id-normalization">
  #### Device ID 规范化
</div>

对于使用 SHA-256 哈希算法以及我们提供给数据合作伙伴的通用盐值对 Device ID 进行哈希处理，适用相同的要求。我们会像处理电子邮件地址一样去除空格，但不会对 IDFA/Android ID 进行小写规范化，必须使用 IDFA/Android ID 的精确原始格式。

以下是 iOS 和 Android 在哈希前的 Device ID 原始格式示例：

iOS IDFA: DD99CFF7-6186-4602-9DF2-ED3FD0B2D431

Android ID: b5bf2122961b3595

哈希后的 iOS IDFA: 134fb8cd95c7fd42e2793f469a447198ca5f990968db2dbadad70e723ed9750b

哈希后的 Android ID: 130dddff1939f229476f50bc8adab8fcb7e3525b0e9604fe8effc15e68cee4a4

<div id="x-user-id-normalization">
  #### X 用户 ID 规范化
</div>

X ID 仍然会进行哈希处理，因为对 data 的分组（例如基于 @handles 的 Customer List）对广告主来说是私有的，即使这些信息本身不是个人可识别信息（PII）。我们对使用 SHA-256 哈希算法以及我们提供给数据合作伙伴的统一 salt 对 X ID 进行哈希有相同的要求。应当从 X ID/`@`username 中移除所有空格，但 User ID 本身不需要规范化。用于规范化时，@username 应转换为小写形式，并且 @ 符号不应作为 username 的一部分包含在内。

原始 ID 格式为：

* User ID: 27674040
* @username: testusername

Hashed User ID: bf6b57d4e861e83bea8bbed2b800b251a64c95468ee6e8cb07c3368c9ed45e85

Hashed @username: 12201ae78ad1afa907c7112d17f498154ffb0bf9ea523f5390e072a06d7d9812

<div id="custom-audiences-user-data">
  ### 自定义受众用户数据
</div>

本文档概述了 [Custom Audience]/x-ads-api/audiences 用户数据的格式。

**数据标准化处理**

**设备 ID**：

* IDFA：使用带连字符的小写形式；例如：`4b61639e-47cc-4056-a16a-c8217e029462`
* AdID：必须为设备上的原始格式，为带连字符的小写形式，不要全部大写；例如：`2f5f5391-3e45-4d02-b645-4575a08f86e`
* Android id：必须为设备上的原始格式，不要全部大写，且不带连字符或空格；例如：`af3802a465767e36`

**电子邮件地址**：

* 全部转换为小写，去除首尾空格；例如：`support@x.com`

**X 用户名**：

* 不含 @，全部小写，并去除首尾空格；例如：`jack`

**X 用户 ID**：

* 标准整数；例如：`143567`

**数据哈希处理**

每一行数据必须使用 `SHA256` 进行哈希，且不使用盐（salt）。此外，最终输出的哈希值必须为小写。例如：49e0be2aeccfb51a8dee4c945c8a70a9ac500cf6f5cb08112575f74db9b1470d，**而不是**49E0BE2AECCFB51A8DEE4C945C8A70A9AC500CF6F5CB08112575F74DB9B1470D

```
# hasing user @AdsAPI using python
import hashlib
hashlib.sha256("adsapi".encode()).hexdigest()

#output
49e0be2aeccfb51a8dee4c945c8a70a9ac500cf6f5cb08112575f74db9b1470d
```

更多关于哈希的代码示例可以在 [github.com/xdevplatform/ads-platform-tools](https://github.com/xdevplatform/ads-platform-tools) 上找到。

  ### 自定义受众：Web
</div>

<Frame>
  <img src="https://cdn.cms-twdigitalassets.com/content/dam/developer-twitter/images/info.png" alt="info.png" />

**说明**

合作伙伴会代表广告主发送一个 ID 列表（`p_user_ids`）用于定向投放。通过 ID 同步（ID Sync）流程，在 `p_user_ids` 与 X 用户 ID 之间建立映射关系来实现这一点。随后使用该映射生成可用于定向投放的 X 用户 ID 列表。这些自定义受众将根据在 ads.x.com 自定义受众 Web 广告系列设置中由标签指定的、广告主专用的 @handle 提供给该广告主使用。

X 将提供一个安全像素（secure pixel），可部署在合作伙伴的标签和站点上，用于将 ID（`p_user_ids`）与 X 用户 ID 进行匹配。ID 同步流程完成后，合作伙伴会创建定向文件，并通过一个 HTTPS 端点提供给 X。X 会定期导入这些定向文件，并在 X 的 UI 中提供使用。

**X 安全像素**

X 安全像素格式如下：

https://analytics.x.com/i/adsct?p&#95;user&#95;id=xyz&amp;p&#95;id=123

**`p_user_id`** - xyz 表示由合作伙伴提供的合作伙伴用户 ID

**`p_id`** - 123 表示合作伙伴的唯一 ID（由 X 提供）

**合作伙伴 HTTPS 端点与定向用户文件**

合作伙伴需要向 X 提供一个 HTTPS 端点以及凭据（用户名/密码），以便定期导入定向文件。示例 HTTPS 端点如下所示：

```
https://<partnerdomain>/twitter/partner_targeting_%Y-%M-%D.tsv.gz
```

%Y - 年的格式代码 (YYYY)

%M - 月的格式代码 (MM)

%D - 日的格式代码 (DD)

传输的数据将包含以下文件：

1. Partner 目标用户文件
2. 目标转化文件

所有文件都将采用 TSV 格式，其中每一行内的各个字段由制表符分隔。有效的字段值本身绝不会包含制表符。

**允许的 X IP 段：**

下面是可被允许访问 Partner Endpoint 的 IP 段。

* 199.16.156.0/22
* 199.59.148.0/22

**Partner 目标用户文件：**

| **列号** | **列名称**           | **列类型** | **说明**                                                                                                                                                                    |
| :----- | :---------------- | :------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1      | partner id        | string  | “partner id” 是 X 提供给 Partner、用于唯一标识每个 Partner 的 id。                                                                                                                       |
| 2      | advertiser id     | string  | “advertiser id” 是广告主的 @handle。                                                                                                                                            |
| 3      | p&#95;user&#95;id | string  | “p&#95;user&#95;id” 是 Partner 用来标识用户的唯一 id。                                                                                                                               |
| 3      | confidence score  | integer | “confidence score”（置信度评分）是可选字段。我们对 confidence score 的建议范围是 0–100。如果用例是再营销（retargeting），那么 confidence score 为 “100” 表示被直接再营销的用户。0–99 之间的任何分数都对应于对相似受众（look-alike）置信度的不同等级。 |
| 4      | segment label     | string  | “segment label”（分段标签）是可选字段。Partner 可以使用 “segment label” 来指定产品类别等。我们建议使用此 “segment label”，因为它是在 ads.x.com UI 中展示的 Custom Audiences 的可读名称。                                  |

**注意：**

每当我们收到新的 Partner Targeting File 时，除非另有约定，我们都期望它是 Partner 建议我们投放的完整用户列表，而不是增量列表。我们会与每个 Partner 协商此 Partner Targeting File 的投递频率。如果在预期时间没有收到 Partner Targeting File，我们将继续使用上一版本，并应用预先定义的过期时间。

<div id="audience-api-integration">
  ## 受众 API 集成
</div>

### 概览

Audience API 是作为 Ads API [v4](/zh/x-ads-api/introduction) 的一部分推出的，同时对旧版 Audiences 端点进行了多项改进。这个新端点由全新的 Audience 处理后端提供支持，在稳定性、健壮性和可靠性方面带来了多重提升。本指南旨在重点说明 Audience API 与旧版 Audience 上传和管理流程之间的差异。 

相关参考文档可在 [Audience API](/zh/x-ads-api/audiences) 参考文档页面查阅。 

**注意**：所有 Audience 用户数据在上传前必须先进行 SHA-256 哈希处理。有关更多详情，以及可接受的用户标识符类型和数据规范化方式，请参见 [user data](/zh/x-ads-api/audiences) 页面。

**Audience 功能变更**

自 v4 起，引入了以下针对 Custom Audiences 的更改，一旦 Ads API 的 v3 下线，任何已弃用的端点将不再可用：

* **已弃用** TON Upload：
  * GET accounts/:account&#95;id/custom&#95;audience&#95;changes
  * GET accounts/:account&#95;id/custom&#95;audience&#95;changes/:custom&#95;audience&#95;change&#95;id
  * POST accounts/:account&#95;id/custom&#95;audience&#95;changes
  * PUT accounts/:account&#95;id/custom&#95;audiences/global&#95;opt&#95;out
* **已弃用** Real Time Audiences：
  * POST custom&#95;audience&#95;memberships
* Custom Audience：
  * `list_type` 参数将从所有 [Custom Audience](/zh/x-ads-api/audiences) 端点的请求和响应中移除。此前该参数用于标识 Audience 中用户标识符的类型（例如 email、X User ID 等），但由于现在同一个 Audience 可以接收多种用户标识符，因此该值不再具有意义。
* 通用变更：
  * Audience 的回溯窗口已更新为匹配过去 90 天内活跃的用户（此前为 30 天）
  * 受众可被定向投放所需的匹配用户最小数量已从 500 降至 100

<Note>
  **先决条件**

  * Ads API 访问权限
  * 若要访问 Audience 端点，你需要被加入允许列表（allowlist）。如果你最初接受协议的日期早于 2018-08-01，请填写此表单，并接受新的 [X Ads Products and Services Agreement](/zh/x-ads-api/introduction)
</Note>

**Audience 上传流程**

下表列出了旧版与新版 Audience 创建流程之间的主要差异，后文将提供更多详细说明：

| 流程步骤 | Audience API | （已弃用）TON Upload |
| :--- | :--- | :--- |
| 创建空壳 Audience | 可通过 [POST custom&#95;audience endpoint]/x-ads-api/audiences 创建 | 可通过 [POST custom&#95;audience endpoint]/x-ads-api/audiences 创建 |
| 添加新用户 | 在 [Audience endpoint](/zh/x-ads-api/audiences) 中使用 `operation_type` `Update` | 在 [POST custom&#95;audience&#95;changes](/zh/x-ads-api/audiences) 端点中使用 `operation` `ADD` |
| 移除用户 | 在 [Audience endpoint](/zh/x-ads-api/audiences) 中使用 `operation_type` `Delete` | 在 [POST custom&#95;audience&#95;changes](/zh/x-ads-api/audiences) 端点中使用 `operation` `REMOVE` |
| 将用户退订（Opt-out） | 在 [Audience endpoint](/zh/x-ads-api/audiences) 中使用 `operation_type` `Delete`，并提供该用户所属的对应 `custom_audience_id` | 使用 [Global opt-out endpoint](/zh/x-ads-api/audiences) |

**注意** 任何通过 TON Upload 路径进行更新或退订（opt-out）的 Audience，必须先通过 [TON Upload](/zh/x-ads-api/audiences) 端点上传对应列表，并使用 [custom&#95;audience&#95;changes](/zh/x-ads-api/audiences) 端点将其关联到 Audience。

**速率限制**

Audience API 端点的速率限制为每个账号每分钟 1500 次。对单个 payload 中可发送的用户数量没有限制。对 payload 的唯一约束为：

1. 操作总数：2500 个操作

2. 最大 payload 大小：5,000,000 字节

**Audience 用户管理**

要创建一个新的 Audience，需要完成以下步骤。

            {
              "email": [
                "abc@x.com"
              ],

                "x",
                "adsapi"
              ]
            },

        }

<div id="remove-users-from-an-audience">
  #### 从受众中移除用户
</div>

与添加用户的流程类似，可以使用如下方式将用户从受众中移除：

POST https://ads-api.x.com/11/accounts/18ce54d4x5t/custom&#95;audiences/1nmth/users

```
    # 所有值都必须经过哈希处理,此示例中使用的未哈希值仅用于说明目的
    [
      {
        "operation_type": "Delete",
        "params": {
          "effective_at": "2018-05-15T00:00:00Z",
          "expires_at": "2019-01-01T07:00:00Z",
          "users": [
            {
              "email": [
                "abc@x.com"
              ],
              "twitter_id": [
                "783214",
                "1225933934"
              ]
            },
            {
              "email": [
                "edf@x.com"
              ],
              "twitter_id": [
                "121291606",
                "17874544"
              ]
            }
          ]
        }
      }
    ]
```

`operation_type` 必须设置为 `Delete`，并且系统会根据当初将用户添加到受众时所使用的任意键来匹配用户。比如，如果某个用户是通过 `email` 和 `twitter_id` 被添加到某个受众中的，那么之后可以使用这两个键中的任意一个将该用户移除，即只用 `email`、只用 `twitter_id`，或者同时使用这两个键。

此外，可以在同一个请求中同时向某个 Audience 添加和移除用户。该 endpoint 支持在单个请求中使用多个 `operation_type`。

<div id="opt-out-users">
  #### 选择退出的用户
</div>

随着全局选择退出（opt-out）端点的弃用，合作伙伴必须 `Delete` 任何已从任意 Audiences 中选择退出的用户。可以通过以下几种方式实现：

1. 记录哪些用户属于哪些 Audiences，并从每个 Audience 中分别移除这些用户。
2. 将该用户从与某个 Ads 账户关联的**所有** Audiences 中移除。

**通用最佳实践**

* 我们强烈建议以接近实时的批处理方式调用此端点，以避免出现处理时间更长的峰值队列，并总体上减少对我们系统的不必要负载。这也能确保用户更快可用于广告活动定向。
* 成功的 API 调用将返回一个 `success_count` 和一个 `total_count`，分别对应请求中接收到的 `user` 对象数量。
* 此端点具有原子性特征，即要么整个请求全部成功，要么在出现任何错误时整个请求都会失败。出现错误响应时，建议 API 使用方修复错误后，使用完整负载重新重试该请求。 
* 发生失败时，建议合作伙伴在重试时使用[指数退避](https://en.wikipedia.org/wiki/Exponential_backoff)策略。例如，首次失败后立即重试，第二次失败后在 1 分钟后重试，第三次连续失败后在 5 分钟后重试，依此类推。

  #### POST accounts/:account_id/custom_audiences/:custom_audience_id/users[](#post-accounts-account-id-custom-audiences-custom-audience-id-users "Permalink to this headline")
</div>

此端点允许合作伙伴向指定的 `custom_audience_id` 添加、更新和移除用户。该端点也支持为每个用户提供多种用户标识符类型。

在请求的 `users` 字段中提供的所有数据（**`partner_user_id` 除外**）都必须使用 `SHA256` 进行哈希，并进行[规范化](/zh/x-ads-api/audiences#twitter-user-id-normalization)。

**批量请求**

* 当前**此端点**的最大批量大小为 `2500`。批量大小由每个请求中的操作数（`Update`/`Delete`）决定。例如，在一个数组中包含超过 2500 个操作对象（`{"operation_type": "Update/Delete", [..] }`）会导致错误。
* 此端点可接受的 POST 请求正文最大大小为 `5,000,000` 字节。
* 此端点的速率限制为每 1 分钟窗口 1500 次请求。
* 所有参数都通过请求正文发送，并且必须使用 `Content-Type` 为 `application/json`。
* 批量请求作为一个整体一起失败或成功，并且无论是错误还是成功的所有 API 响应都会保留初始请求中各项的顺序。

**批量响应**

Ads API 返回的响应包含两个字段：`success_count` 和 `total_count`。这两个值必须始终相等，它们表示后端已处理的请求记录数。当请求正文中发送的记录数**不**等于 `success_count` 和 `total_count` 时，应视为错误情况，需要重试。

**批量错误**

* 请求级错误（例如，超过最大批量大小）会在响应中的 `errors` 对象下显示。
* 条目级错误（例如，缺少必需参数）会在响应中的 `operation_errors` 对象下显示。
* `operation_errors` 中错误的索引对应于输入项中的索引，并附带相应的错误消息。

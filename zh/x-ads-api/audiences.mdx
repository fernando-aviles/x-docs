## 自定义受众

<div id="overview">
  ### 概览
</div>

合作伙伴可以通过多种方式创建[自定义受众](https://business.x.com/en/targeting/tailored-audiences.html)。

* [Audience API（CRM）](#crm)
* [Web](#web)
* [Mobile](#mobile)
* [Flexible](#flexible)

请注意，无法在定向中排除相似自定义受众（lookalike custom audiences）。此外，不能在同一个广告项目（广告组）中同时定向一个自定义受众和一个自定义受众的相似受众。

**受众管理**

受众可以通过受众合作伙伴和 Ads API 合作伙伴进行管理。我们在 API 中提供了一系列端点，用于访问和维护自定义受众。

对于自定义受众信息，我们提供 2 个端点：

* [GET accounts/:account&#95;id/custom&#95;audiences](/zh/x-ads-api/audiences)
* [GET accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id](/zh/x-ads-api/audiences)

有关如何上传和管理受众的更多详细信息，请参阅 [Audience API 指南](/zh/x-ads-api/audiences)。

**处理时间**

总体而言，受众更改会通过每 6–8 小时运行一次的批处理任务进行处理。在受众更改正在处理中时，待更新的现有受众不会受到影响。我们不建议在该时间范围内，对同一受众进行超过一次的新增更新以及超过一次的移除更新。

**定向**

仅当某个受众在过去 90 天内，至少匹配到 100 位在 X 自有及运营的客户端上活跃的用户时，该受众才能被用于定向。[GET accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id](/zh/x-ads-api/audiences) 会指示某个受众是否由于匹配用户过少而无法用于定向。

<div id="audiences-faq">
  ### 受众常见问答[](#real-time-tailored-audiences "Permalink to this headline")
</div>

**问：我们推送了大量数据，为什么受众规模却显示为 TOO&#95;SMALL？**

答：目前数据会实时被加入受众，但用于处理数据并计算受众规模的任务只会在一段时间后运行。正确的受众规模会在数小时后显示在 UI 中。

**问：我们已经完成发送受众数据，并等待了 24 小时或更久，但仍然无法定向到该受众——下一步应该怎么做？**

答：请确认以下事项：

* 传入的用户 ID 是正确的，且格式正确、未损坏。
* 传入的受众名称是正确的，并且与之前的成员更新相匹配。
* 请确认 `POST` 命令的响应。
* 请确认 ID Sync 像素已正确实现，并且如 ID Sync 流程所述，有足够多的用户访问了相关站点来完成用户映射。未被映射的用户即使出现在成员更新中，也不会转化为可定向用户。

如果以上都已确认无误且工作正常，请联系 X 产品对接人，并尽可能提供详细信息（参考 [Guide to Partner Inbounds](/zh/x-ads-api/introduction) 中关于首选信息的示例）。

**问：我们可以调用该 endpoint 多少次，应使用什么算法？**

答：我们强烈建议你使用增量变更数据调用我们的系统，切勿重复发送完整的受众成员列表。系统已在吞吐量方面经过测试，足以处理全球一些最大网站的增量数据更新。受众的首次上传应进行谨慎限流，且预计首次上传完成将需要相当长的时间。

**问：受众用于投放定向时的最小规模是多少？**

* 受众的最小规模为 100 名用户（匹配完成后）。如果匹配到的受众少于 500 名用户，则该受众不会在 X Ads UI 中用于定向。

**问：处理受众文件需要多长时间？受众文件在 X 用户界面中可用又需要多久？**

* 通常处理受众文件需要 4–6 小时，但这取决于文件大小。文件处理完成后，相应受众会在 X Ads UI 中可用。

**问：匹配率是如何计算的？**

* 匹配率 = 90 天内活跃的 X 用户数 / 提供的用户数

**问：我们如何测试受众文件是否正常工作？**

* 你可以提供一个测试受众文件，并使用 “keltonlynn” 作为广告主 handle。我们可以据此验证该文件是否能够被正确导入并加载到 X UI 中。

**问：什么是合作伙伴用户标识符（`p_user_id`）？**

* 这是你的公司用来唯一标识每一位客户的标识符。

**问：什么是标准 ID？**

* 可以是电子邮件地址、设备 ID、X 的 @handle 或 ID。

**问：如何获取 HMAC Key？**

* 我们会通过加密电子邮件提供该密钥。请将你的 PGP 公钥发送至 [mpp-inquiry@x.com](mailto:mpp-inquiry%x.com)，我们会先向你发送一封测试邮件以验证一切工作正常。验证完成后，我们会向你发送 HMAC Key。

**问：如何使用给定的 HMAC Key 验证哈希过程是否成功？**

* X 会提供一个测试文件（包含示例电子邮件地址、设备 ID 等）以及一个对应的哈希结果文件，你可以将自己的结果与之进行比对验证。

**问：完整数据匹配文件是否有大小限制？**

* 不，完整数据匹配文件没有大小限制。

**问：处理完整数据匹配文件需要多长时间？**

* 一旦 X 收到该文件，处理大约需要 1 天时间。

**摘要**

公司将代表客户向 X 提供一份经过哈希处理的常见用户标识符（例如电子邮件地址）或合作伙伴用户 ID 列表，以便 X 执行盲匹配，并生成一份用于定向投放的 X 用户 ID 列表。用于定向的受众分段将根据文件名中指定的、广告主对应的特定 @handle，在 ads.x.com 的广告系列设置中提供给该广告主使用。

公司发送给 X 的所有文件都将通过 IronBox（www.golockbox.com）上的安全包，使用 X 授予公司的专用账户进行传输。X 将提供对 IronBox 的访问权限。有关 IronBox API 的文档可在 [https://secure.goironcloud.com/Docs/Help/](https://secure.goironcloud.com/Docs/Help/) 查阅。

<div id="partner-id-matching-requirements">
  #### 合作伙伴 ID 匹配要求
</div>

如果公司使用自己的标准 ID 系统来跟踪用户(即不使用常见的用户标识符,如电子邮件地址、设备 ID、X 用户 ID 等),则建议采用以下流程。

**1. 完整数据匹配**

首先,公司需要提供一个包含所有用户记录的完整列表,其中包括与 X 共有的唯一通用用户标识符,并将其放在单个文件中以执行完整数据匹配,生成由 X 存储的合作伙伴 ID(`p_user_id`)到 X ID(`tw_id`)的映射关系。此操作将定期每 2-3 个月执行一次,以确保数据的准确性。匹配完成后,X 将通过电子邮件向公司提供此文件的基准匹配率。

此文件的格式应为:

命名规范: FullDataMatch.[CompanyName].txt

哈希算法: HMAC&#95;SHA-256

格式:

第 1 列: 通用标识符的 HMAC 哈希值

第 2 列: 合作伙伴用户 ID(每个用户唯一,文件中可重复)

列分隔符 (CSV): 使用逗号分隔哈希后的通用用户标识符和合作伙伴 ID

按行分隔的值

* 示例: 如果用户记录 A 具有合作伙伴用户 ID 1 和通用标识符 1、2 和 3:

|     |     |
| :--- | :--- |
| 通用用户标识符 1 | p&#95;user&#95;1 |
| 通用用户标识符 2 | p&#95;user&#95;1 |
| 通用用户标识符 3 | p&#95;user&#95;1 |

*请参阅下方的通用用户标识符哈希说明部分

**2. 自定义细分列表**

公司需要以 `p_user_id` 的形式提供用户列表,用于为客户创建自定义受众,以便在 X 上进行定向投放。

* 按行分隔的值
* `p_user_id`
* * (与上述 1. 完整数据匹配部分中提供的相同。如果完整数据匹配中提供的值已进行哈希处理,则公司需在受众文件中提供相同的哈希值。如果提供的值未进行哈希处理,则公司需提供未哈希的值。)

<div id="standard-matching-requirements">
  #### 标准匹配要求
</div>

如果公司未使用标准 ID 来映射所有客户的用户标识符，建议遵循以下流程。

**自定义分群列表**

公司将代表客户向 X 提供经过哈希处理的常见用户标识符列表，以创建自定义受众。

该文件的格式应为：

* 逐行分隔的值
* 经过哈希处理的常见用户标识符（例如电子邮件地址）
* 遵循下文概述的文件命名约定
* 遵循下文“哈希说明”部分中对电子邮件地址的哈希处理指引

<div id="custom-segment-list-file-naming-operations">
  #### 自定义分段列表文件命名与操作
</div>

文件的操作由文件名决定，可用的操作以及通用文件命名规则为：audiencename&#95;partnername.handle.operation.filetype

* audiencename: 自定义受众的名称。此字段是在 ads.x.com 广告系列设置 UI 中选择受众时显示的名称，例如 brand&#95;loyalty&#95;card&#95;holders。
* partnername: 代表广告主提供数据的公司名称，例如 company&#95;name。
* handle: 拥有自定义受众访问权限的 X 账号（@handle），例如 @pepsi、@dietpepsi
* operation: new、add、remove、removeall、replace（详见下文）
* : 标准 Unix 纪元时间（单位为秒），用于确保每个上传的受众文件都是唯一的
* filetype: 文件必须为 *.txt 格式

<div id="creating-and-updating-audiences">
  #### 创建和更新受众
</div>

使用单个文件创建一个新受众，例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.new.txt

Add - 将列表中的匹配项添加到一个已有受众，例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.add..txt

Remove - 将列表中的匹配项从一个已有受众中移除，例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.remove..txt

Remove All - 将由定期更新的累计列表产生的匹配项，从该 Client 的所有受众中移除（即该 Client 的 Opt Out 退出列表）。例如：partnername.pepsi.removeall.txt

* 可用于维护一个已从该广告主选择退出的用户的完整列表。
* X 只会遵循此文件中最新提供的列表，并会在所有现有和未来受众中，对在提供并处理此文件时匹配到的 X 用户生效。

Replace - 移除一个现有受众并用一个新的受众列表替换。例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.replace..txt

整体公司级退出（Overall Company Opt-Out）- 公司将提供一个累计的退出（Opt-Out）文件，用于根据公司的退出策略移除已选择退出的用户。

X 只会遵循此公司退出（Company Opt-Out）文件中最新提供的列表，并会在所有现有和未来受众中，对在提供并处理此文件时匹配到的 X 用户生效。公司退出文件的格式如下：例如：partnername.removeall.txt

Delete - 从当前受众列表中移除一个现有受众，例如：Ex: loyalty&#95;card&#95;holders&#95;partnername.pepsi.delete.txt

<div id="hashing-directions">
  #### 哈希指引
</div>

X 将通过 PGP 安全地共享一个经过 base64 编码的生产密钥，用于对常见用户标识符（例如电子邮件地址）进行哈希处理。公司将对该密钥执行 base64 解码，以生成一个 32 字节的密钥，用于执行哈希操作。

示例 base64 编码密钥：

BrQvOg+dACBUmKjRiNxZgJLh6zydjS0ZOv80FelTNzM=

示例 Base64 解码密钥：

/:� TшY

规范化：在执行哈希之前，公司将对常见用户标识符进行基本规范化处理（Device ID 除外，详见 Device ID 规范化部分）。

<div id="e-mail-normalization">
  #### 电子邮件规范化
</div>

也就是说，去除前后空格，并将电子邮件地址全部转换为小写。

例如：原始电子邮件地址：testemail&#95;Organisational&#95;baseball+884`@`It92I6Ev2B`.`Com

规范化后：testemail&#95;organisational&#95;baseball+884`@`it92i6ev2b`.`com

哈希值：74d9584eded0ad1e5572a1c1849f3716751d371d6117a6155dad5363f4b4fbec

注意：编码后的 HMAC 和密钥的字符数会根据输入和编码方式而变化，因此字符数并不是固定的。

<div id="device-id-normalization">
  #### 设备 ID 规范化
</div>

我们对设备 ID 的哈希有相同的要求：使用 SHA-256 哈希算法和我们提供给数据合作伙伴的统一盐值。我们会像处理电子邮件地址那样去除空格，但不会对 IDFA/Android ID 进行小写转换规范化，必须使用 IDFA/Android ID 的精确格式。

下面是 iOS 和 Android 设备 ID 在哈希前的原始格式示例：

iOS IDFA: DD99CFF7-6186-4602-9DF2-ED3FD0B2D431

Android ID: b5bf2122961b3595

哈希后的 iOS IDFA: 134fb8cd95c7fd42e2793f469a447198ca5f990968db2dbadad70e723ed9750b

哈希后的 Android ID: 130dddff1939f229476f50bc8adab8fcb7e3525b0e9604fe8effc15e68cee4a4

<div id="x-user-id-normalization">
  #### X 用户 ID 规范化
</div>

X 的 ID 仍会进行哈希处理，因为数据分组（例如由 @handle 组成的客户列表）对于广告主来说是私有的，即便这些数据并非个人可识别信息（PII）。对于 X ID 的哈希，我们仍有相同要求：使用 SHA-256 哈希算法，以及我们提供给数据合作伙伴的通用盐值（salt）。应当从 X ID 和 `@`username 中移除所有空格，但 User ID 本身不需要做规范化处理。为实现规范化，@username 应转换为小写。同时，@ 符号不应算作 username 的一部分。

原始 ID 格式如下：

* User ID: 27674040
* @username: testusername

User ID 的哈希值：bf6b57d4e861e83bea8bbed2b800b251a64c95468ee6e8cb07c3368c9ed45e85

@username 的哈希值：12201ae78ad1afa907c7112d17f498154ffb0bf9ea523f5390e072a06d7d9812

**数据规范化**

**设备 ID**：

* IDFA - 使用带连字符的小写形式；例如：`4b61639e-47cc-4056-a16a-c8217e029462`
* AdID - 必须使用设备上的原始格式，不要大写，保留连字符；例如：`2f5f5391-3e45-4d02-b645-4575a08f86e`
* Android id - 必须使用设备上的原始格式，不要大写，不带连字符和空格；例如：`af3802a465767e36`

**电子邮件地址**：

* 转为小写，移除首尾空格；例如：`support@x.com`

**X 用户名**：

* 不包含 @，转为小写并移除首尾空格；例如：`jack`

**X 用户 ID**：

* 标准整数；例如：`143567`

**数据哈希**

每一行的数据必须使用 `SHA256` 进行哈希运算，且不使用 `salt`。此外，最终输出的哈希值必须为小写。例如：49e0be2aeccfb51a8dee4c945c8a70a9ac500cf6f5cb08112575f74db9b1470d，**而不是**49E0BE2AECCFB51A8DEE4C945C8A70A9AC500CF6F5CB08112575F74DB9B1470D

```
# hasing user @AdsAPI using python
import hashlib
hashlib.sha256("adsapi".encode()).hexdigest()

#output
49e0be2aeccfb51a8dee4c945c8a70a9ac500cf6f5cb08112575f74db9b1470d
```

更多关于哈希的代码示例可在 [github.com/xdevplatform/ads-platform-tools](https://github.com/xdevplatform/ads-platform-tools) 中找到。

  ### 自定义受众：Web
</div>

<Frame>

**信息**

合作伙伴会代表广告主发送一个用于定向的 ID 列表（`p_user_ids`）。这是通过 ID 同步流程完成的，该流程在 `p_user_ids` 与 X 用户 ID 之间建立映射关系。然后使用此映射生成可用于定向的 X 用户 ID 列表。这些自定义受众将在广告主特定的 @handle（账号）下可用，该 @handle 由 ads.x.com 上自定义受众 Web 广告系列设置中的标签指定。

X 将提供一个安全像素，可嵌入到合作伙伴的标签和站点上，用于将这些 ID（`p_user_ids`）与 X 用户 ID 进行匹配。ID 同步流程完成后，合作伙伴将创建定向文件，并通过一个 HTTPS 端点提供给 X。X 会定期获取并导入这些定向文件，然后在 X 的 UI 中提供使用。

**X 安全像素**

X 安全像素如下所示：

https://analytics.x.com/i/adsct?p&#95;user&#95;id=xyz&amp;p&#95;id=123

**`p_user_id`** - xyz 表示由合作伙伴提供的合作伙伴用户 ID

**`p_id`** - 123 表示合作伙伴的唯一 ID（由 X 提供）

**合作伙伴 HTTPS 端点与定向用户文件**

合作伙伴需要向 X 提供一个 HTTPS 端点和凭证（用户名/密码），以便定期用于获取并导入定向文件。示例 HTTPS 端点如下所示：

```
https://<partnerdomain>/twitter/partner_targeting_%Y-%M-%D.tsv.gz
```

%Y - 年格式代码 (YYYY)

%M - 月格式代码 (MM)

%D - 日格式代码 (DD)

传输的数据将包含以下文件：

1. Partner Targeting User File（合作方定向用户文件）
2. Targeting Conversion File（定向转化文件）

所有文件都将采用 TSV 格式，其中每一行中的各个字段之间由制表符分隔。合法的字段值本身绝不会包含制表符字符。

**允许的 X IP 段：**

以下是可以为访问 Partner Endpoint 开放的 IP 段。

* 199.16.156.0/22
* 199.59.148.0/22

**Partner Targeting User File：**

| **Column Number** | **Column Name**   | **Column Type** | **Description**                                                                                                                                                            |
| :---------------- | :---------------- | :-------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1                 | partner id        | string          | “partner id” 是 X 提供给合作方、用于唯一标识每个合作方的 ID。                                                                                                                                   |
| 2                 | advertiser id     | string          | “advertiser id” 是广告主的 @handle。                                                                                                                                             |
| 3                 | p&#95;user&#95;id | string          | “p&#95;user&#95;id” 是合作方用于标识用户的唯一 ID。                                                                                                                                      |
| 3                 | confidence score  | integer         | “confidence score”（置信度评分）为可选项。我们建议 confidence score 的取值范围为 0-100。如果用例是用于再营销（retargeting），那么 confidence score 为 “100” 表示该用户是被直接再营销的用户。0-99 的任何分数都对应于相似人群（look-alike）的置信度水平。 |
| 4                 | segment label     | string          | “segment label” 为可选项。合作方可以使用 “segment label” 指定例如产品类别等信息。我们建议使用此 “segment label”，因为这是 ads.x.com UI 中自定义受众（Custom Audiences）的人类可读名称。                                        |

**Notes:**

每次我们收到新的 Partner Targeting File 时，除非另有约定，我们期望其中包含的是合作方推荐我们进行定向的完整用户列表，而不是增量列表。我们会与每个合作方就该 Partner Targeting File 的投递频率达成一致。如果我们未按预期收到 Partner Targeting File，我们将继续使用先前版本，并设置一个预先定义的过期时间。

<div id="audience-api-integration">
  ## Audience API 集成
</div>

### 概述

Audience API 作为 Ads API [v4](/zh/x-ads-api/introduction) 的一部分推出，相比旧版 Audiences 端点带来了多项改进。这个新端点由全新的 Audience 处理后端提供支持，在稳定性、健壮性和可靠性方面都有显著提升。本指南旨在突出 Audience API 与旧版 Audience 上传和管理流程之间的差异。 

参考文档可在 [Audience API](/zh/x-ads-api/audiences) 参考文档页面找到。 

**注意**：所有 Audience 用户数据在上传前都必须进行 SHA-256 哈希处理。关于更多详细信息、支持的用户标识符类型以及数据规范化说明，请参见 [user data](/zh/x-ads-api/audiences) 页面。

**Audience 功能变更**

自 v4 起，引入了以下对自定义受众（Custom Audiences）的更改，一旦 Ads API 的 v3 退役，所有已弃用端点将不再可用：

* **已弃用** TON Upload：
  * GET accounts/:account&#95;id/custom&#95;audience&#95;changes
  * GET accounts/:account&#95;id/custom&#95;audience&#95;changes/:custom&#95;audience&#95;change&#95;id
  * POST accounts/:account&#95;id/custom&#95;audience&#95;changes
  * PUT accounts/:account&#95;id/custom&#95;audiences/global&#95;opt&#95;out
* **已弃用** Real Time Audiences：
  * POST custom&#95;audience&#95;memberships
* Custom Audience：
  * `list_type` 参数将从所有 [Custom Audience](/zh/x-ads-api/audiences) 端点的请求和响应中移除。该参数之前用于标识 Audience 的用户标识符类型（例如 email、X 用户 ID 等），但现在 Audience 支持为同一个 Audience 接收多个用户标识符，因此该值已不再有意义。
* 通用：
  * Audience 回溯时间窗口已更新为匹配过去 90 天内活跃的用户（此前为 30 天）
  * 受众可被定向投放所需的最小匹配用户数已降低至 100（此前为 500）

<Note>
  **前提条件**

  * Ads API 访问权限
  * 如需访问 Audience 端点，你需要被加入允许列表。请填写此表单，并在最初接受日期早于 2018-08-01 的情况下，接受新的 [X Ads Products and Services Agreement](/zh/x-ads-api/introduction)
</Note>

**Audience 上传流程**

下表列出了旧版和新版 Audience 创建流程的主要差异，更多细节将在下文展开说明：

| 流程步骤 | Audience API | （已弃用）TON Upload |
| :--- | :--- | :--- |
| 创建一个空壳 Audience | 可以通过 [POST custom&#95;audience endpoint]/x-ads-api/audiences 创建 | 可以通过 [POST custom&#95;audience endpoint]/x-ads-api/audiences 创建 |
| 添加新用户 | 在 [Audience endpoint](/zh/x-ads-api/audiences) 中使用 `operation_type` 为 `Update` | 在 [POST custom&#95;audience&#95;changes](/zh/x-ads-api/audiences) 端点中使用 `operation` 为 `ADD` |
| 移除用户 | 在 [Audience endpoint](/zh/x-ads-api/audiences) 中使用 `operation_type` 为 `Delete` | 在 [POST custom&#95;audience&#95;changes](/zh/x-ads-api/audiences) 端点中使用 `operation` 为 `REMOVE` |
| 用户选择退出（Opting-Out Users） | 在 [Audience endpoint](/zh/x-ads-api/audiences) 中使用 `operation_type` 为 `Delete`，并传入该用户所属的对应 `custom_audience_id` | 使用 [Global opt-out endpoint](/zh/x-ads-api/audiences) |

**注意** 任何通过 TON Upload 路径进行更新或选择退出的 audiences，都必须先通过 [TON Upload](/zh/x-ads-api/audiences) 端点上传相应的列表，并使用 [custom&#95;audience&#95;changes](/zh/x-ads-api/audiences) 端点将其关联到某个 Audience。

**速率限制**

Audience API 端点的速率限制为每个账号每 1 分钟 1500 次请求。对于单个请求负载中可发送的用户数量没有限制。对该负载唯一的约束如下：

1. 操作总数上限：2500 个操作

2. 最大负载大小：5,000,000 字节

**Audience 用户管理**

要创建一个新的 Audience，需要执行以下步骤：

                "adsapi"

              ]
            }
          ]
        }

<div id="remove-users-from-an-audience">
  #### 从受众中移除用户
</div>

与上文添加用户的流程类似，可以通过如下请求将用户从受众中移除：

POST https://ads-api.x.com/11/accounts/18ce54d4x5t/custom&#95;audiences/1nmth/users

```
    # 所有值都必须经过哈希处理,此示例中使用的未哈希值仅用于说明目的
    [
      {
        "operation_type": "Delete",
        "params": {
          "effective_at": "2018-05-15T00:00:00Z",
          "expires_at": "2019-01-01T07:00:00Z",
          "users": [
            {
              "email": [
                "abc@x.com"
              ],
              "twitter_id": [
                "783214",
                "1225933934"
              ]
            },
            {
              "email": [
                "edf@x.com"
              ],
              "twitter_id": [
                "121291606",
                "17874544"
              ]
            }
          ]
        }
      }
    ]
```

`operation_type` 必须设置为 `Delete`，系统会根据在将用户添加到受众时所使用的任意键来匹配用户。举例来说，如果某个用户是通过 `email` 和 `twitter_id` 被添加到某个受众中的，那么在移除该用户时，可以使用这些键中的任意一个来完成匹配，即只使用 `email`、只使用 `twitter_id`，或同时使用二者。

此外，可以在同一个请求中同时向某个 Audience 添加和移除用户。该 endpoint 支持在一次请求中使用多个 `operation_type`。

<div id="opt-out-users">
  #### 选择退出的用户
</div>

随着全局选择退出（opt-out）endpoint 被弃用，合作伙伴必须对已从任意 Audience 中选择退出的用户执行 `Delete` 操作。可以通过以下几种方式实现：

1. 记录每个用户分别属于哪些 Audience，并从每个 Audience 中逐一移除这些用户。
2. 将该用户从与某个 Ads 账号关联的 **所有** Audience 中移除。

**通用最佳实践**

* 我们强烈建议以接近实时的批处理方式调用此 endpoint，以避免队列出现需要更长时间处理的突发峰值，并整体上减少对我们系统的不必要负载。这样也能确保用户更早可用于广告投放定向。
* 一次成功的 API 调用会返回 `success_count` 和 `total_count`，它们对应于请求中已接收的 `user` 对象数量。
* 此 endpoint 具有原子性，即要么整个请求全部成功，要么在出现任何错误时整个请求都会失败。对于错误响应，建议 API 使用方修复错误后，使用完整的 payload 重新发起请求。 
* 如果调用失败，建议合作伙伴在重试时采用[指数退避（exponential backoff）](https://en.wikipedia.org/wiki/Exponential_backoff)策略。例如，第一次失败后立即重试；第二次失败后在 1 分钟后重试；第三次连续失败后在 5 分钟后重试，依此类推。

  #### POST accounts/:account_id/custom_audiences/:custom_audience_id/users[](#post-accounts-account-id-custom-audiences-custom-audience-id-users "此标题的永久链接")

此 endpoint 允许合作伙伴向指定的 `custom_audience_id` 中添加、更新和移除用户。该 endpoint 也支持为每个用户提供多种用户标识符类型。

除 `partner_user_id` 之外，请求中 `users` 字段所提供的所有数据都必须使用 `SHA256` 进行哈希处理，并且需要先[规范化](/zh/x-ads-api/audiences#twitter-user-id-normalization)。

**批量请求（Batch Requests）**

* 当前最大批量大小为 `2500`，**仅适用于此 endpoint**。批量大小由每个请求中的操作（`Update`/`Delete`）数量决定。例如，在一个数组中包含超过 2500 个操作对象（`{"operation_type": "Update/Delete", [..] }`）将会导致错误。
* 此 endpoint 可接受的最大请求 POST body 大小为 `5,000,000` 字节。
* 此 endpoint 的速率限制为每 1 分钟窗口内 1500 次。
* 所有参数都通过请求 body 发送，并且必须将 `Content-Type` 设为 `application/json`。
* 批量请求作为一个整体一起成功或失败，并且无论成功还是失败，所有 API 响应都会保留与初始请求中条目相同的顺序。

**批量响应（Batch Responses）**

Ads API 返回的响应包含两个字段：`success_count` 和 `total_count`。这两个值必须始终相等，它们表示已由后端处理的请求记录数量。如果请求 body 中发送的记录数**不**等于 `success_count` 和 `total_count`，则应视为错误情况，需要重试。

**批量错误（Batch Errors）**

* 请求级错误（例如超出最大批量大小）会在响应中的 `errors` 对象下显示。
* 条目级错误（例如缺少必需参数）会在响应中的 `operation_errors` 对象下显示。
* `operation_errors` 中错误的索引对应于输入条目中的索引，并带有相应的错误消息。

**注意：** 此批量端点目前处于**封闭测试（closed beta）**阶段，仅向特定广告主开放。在此测试期间，只能创建基于移动端自定义受众的灵活受众（Flexible Audiences）。

**批量请求（Batch Requests）**

* 当前最大批量大小为 10。
* 所有参数都通过请求正文发送，并且请求头中的 `Content-Type` 必须为 `application/json`。

**批量响应（Batch Responses）**

批量 API 响应返回的是一个有序的项目集合。除此之外，其结构与对应的单项目端点相同。

**批量错误（Batch Errors）**

* 请求级别错误（例如，超过最大批量大小）会在响应中的 `errors` 对象下显示。
* 项目级别错误（例如，缺少必需参数）会在响应中的 `operation_errors` 对象下显示。

* Do Not Reach List API 不接受 `effective_at` 时间戳，并默认使用当前时间戳
* Do Not Reach List 不会将用户从该账号中的任何或所有自定义受众中移除，而是作为该账号所有投放广告系列的排除定向条件

* 当前此 endpoint 的最大批量大小为 `2500`。批量大小由每个请求中的操作数（`Update`/`Delete`）决定。例如，一个数组中包含超过 2500 个操作对象（`{"operation_type": "Update/Delete", [..] }`）将导致错误。
* 此 endpoint 可接受的最大 POST 请求正文（body）大小为 `5,000,000` 字节。
* 此 endpoint 的速率限制为在 1 分钟时间窗口内 1500 次请求。
* 所有参数都在请求 body 中发送，并且必须提供 `Content-Type` 为 `application/json`。
* 批量请求作为一个整体一起失败或成功，对于错误和成功两种情况，所有 API 响应都会保留与初始请求相同的条目顺序。

**批量响应**

Ads API 返回的响应包含两个字段：`success_count` 和 `total_count`。这两个值必须始终相等，它们表示后端已处理的请求记录数量。如果请求 body 中发送的记录数**不**等于 `success_count` 和 `total_count`，应将其视为错误情况，需要重试。

**批量错误**

* 请求级错误（例如超过最大批量大小）会在响应中的 `errors` 对象下返回。
* 条目级错误（例如缺少必填参数）会在响应中的 `operation_errors` 对象下返回。

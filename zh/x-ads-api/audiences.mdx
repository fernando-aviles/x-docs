## 自定义受众

<div id="overview">
  ### 概览
</div>

合作伙伴有多种方式创建[自定义受众](https://business.x.com/en/targeting/tailored-audiences.html)。

* [Audience API（CRM）](#crm)
* [Web](#web)
* [移动端](#mobile)
* [灵活受众](#flexible)

请注意，您无法在定向时排除相似自定义受众。此外，您不能在同一个广告行项目（广告组）中同时定向一个自定义受众和一个自定义受众相似受众。

**受众管理**

受众可以通过受众合作伙伴和 Ads API 合作伙伴进行管理。我们在 API 中提供了一系列端点，用于访问和维护自定义受众。

对于自定义受众信息，我们提供 2 个端点：

* [GET accounts/:account&#95;id/custom&#95;audiences](/zh/x-ads-api/audiences)
* [GET accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id](/zh/x-ads-api/audiences)

有关如何上传和管理受众的更多详情，请参阅 [Audience API 指南](/zh/x-ads-api/audiences)。

**处理时间**

一般来说，受众更改会以批处理方式执行，每 6–8 小时运行一次。在受众更改处于处理过程中时，正在更新的现有受众不会受到影响。我们不建议在此时间范围内对同一受众执行多于一次的添加更新和一次的移除更新。

**定向**

只有当某个受众至少匹配了过去 90 天内在 X 自有及运营客户端上活跃的 100 名用户时，该受众才可以被定向。[GET accounts/:account&#95;id/custom&#95;audiences/:custom&#95;audience&#95;id](/zh/x-ads-api/audiences) 将指明某个受众是否因为匹配的用户过少而无法被定向。

<div id="audiences-faq">
  ### 受众常见问题[](#real-time-tailored-audiences "Permalink to this headline")
</div>

**问：我们推送了大量数据，为什么受众规模仍然显示为 TOO&#95;SMALL？**

答：当前数据正在实时添加到受众中，但用于处理数据并计算受众规模的作业只会在一段时间后运行。正确的受众规模会在数小时后显示在 UI 中。

**问：我们已经完成发送受众数据，并等待了 24 小时或更久，但仍然无法定向到该受众——下一步应该怎么做？**

答：请确认以下事项：

* 传递的用户 ID 是否正确且没有格式错误。
* 传递的受众名称是否正确，并且与之前的成员更新相匹配。
* 请确认来自 POST 命令的响应。
* 请确认 ID Sync 像素是否已正确部署，并且按照 ID Sync 流程的说明，有足够多的用户访问了相关站点以完成用户映射。未被映射的用户在成员更新中将不会被转换为可定向用户。

如果以上各项都已确认无误且正常工作，请联系 X 产品联系人，并尽可能提供详尽的信息（参见 [Guide to Partner Inbounds](/zh/x-ads-api/introduction) 了解推荐的信息示例）。

**问：我们可以调用该 endpoint 多少次，以及应该使用什么算法？**

答：我们强烈建议你以增量变更（incremental deltas）的方式调用我们的系统，而不要重新发送完整的受众成员列表。系统在吞吐量方面已通过测试，足以处理全球一些最大网站的增量数据更新。初始受众上传应进行严格的节流控制，预计首次上传将需要相当长的时间才能完成。

**问：受众用于定向时的最小规模是多少？**

* 受众的最小规模为 100 个用户（匹配完成后）。如果匹配到的受众少于 500 个用户，则不会在 X Ads UI 中可用于定向。

**问：处理受众文件需要多长时间？受众文件在 X 用户界面中可用又需要多久？**

* 处理受众文件通常需要 4–6 小时，但这取决于文件大小。文件一旦处理完成，相应受众就会在 X Ads UI 中可用。

**问：匹配率是如何计算的？**

* 匹配率 = 90 天内活跃的 X 用户数 / 提供的用户数

**问：我们如何测试受众文件是否正常工作？**

* 你可以提供一个测试受众文件，并使用 “keltonlynn” 作为广告主 handle。然后我们可以验证该文件是否能够被正确导入并加载到 X UI 中。

**问：什么是合作伙伴用户标识符（`p_user_id`）？**

* 这是你公司用来唯一标识每个客户的标识符。

**问：什么是标准 ID？**

* 它可以是电子邮件地址、设备 ID、X 的 @handle 或 ID。

**问：如何获取 HMAC Key？**

* 我们会通过加密电子邮件提供该密钥。请将你的公共 PGP 密钥发送至 [mpp-inquiry@x.com](mailto:mpp-inquiry%x.com)，我们会先发送一封测试邮件来验证一切是否正常。验证通过后，我们会发送 HMAC Key。

**问：如何使用给定的 HMAC Key 验证哈希过程是否成功？**

* X 会提供一个测试文件（包含示例电子邮件地址、设备 ID 等）以及一个结果哈希文件，你可以将自己的结果与之进行比对验证。

**问：完整 data 匹配文件有没有大小限制？**

* 没有，完整 data 匹配文件没有大小限制。

**问：完整 data 匹配文件需要多长时间才能处理完成？**

* 一旦 X 收到该文件，处理大约需要 1 天时间。

本文档描述了面向自定义受众（Custom Audiences）CRM 合作伙伴的集成细节，包括文件格式和数据交换流程。

**摘要**

Company 将代表广告主向 X 提供一份经过哈希处理的通用用户标识符列表（例如电子邮件地址）或合作伙伴用户 ID 列表，以便 X 执行盲匹配并生成一份用于定向投放的 X 用户 ID 列表。用于定向的受众分段（segments）将按照在 ads.x.com 广告系列设置中由文件名所指定的、属于该广告主的特定 @handle 提供给该广告主使用。

Company 提供给 X 的所有文件都将通过 IronBox（www.golockbox.com）上的安全数据包传输，使用 X 为 Company 授权的特定账户。X 将提供对 IronBox 的访问权限。有关 IronBox API 的文档可在 [https://secure.goironcloud.com/Docs/Help/](https://secure.goironcloud.com/Docs/Help/) 查阅。

<div id="partner-id-matching-requirements">
  #### 合作伙伴 ID 匹配要求
</div>

如果公司使用自己的标准 ID 系统来跟踪用户(即不使用常见的用户标识符,如电子邮件地址、设备 ID、X 用户 ID 等),则建议采用以下流程。

**1. 完整数据匹配**

首先,公司需要提供一个包含所有用户记录的完整列表,其中包括与 X 共有的唯一通用用户标识符,以单个文件形式提交以执行完整数据匹配,并生成由 X 存储的合作伙伴 ID(`p_user_id`)到 X ID(`tw_id`)的映射关系。此操作将定期每 2-3 个月执行一次,以确保数据的准确性。匹配完成后,X 将通过电子邮件向公司提供此文件的基准匹配率。

文件格式要求如下:

命名规范: FullDataMatch.[CompanyName].txt

哈希算法: HMAC&#95;SHA-256

格式:

第 1 列: 通用标识符的 HMAC 哈希值

第 2 列: 合作伙伴用户 ID(每个用户唯一,文件中可重复)

列分隔符 (CSV): 使用逗号分隔哈希后的通用用户标识符与合作伙伴 ID

行分隔值

* 示例: 如果用户记录 A 的合作伙伴用户 ID 为 1,通用标识符为 1、2 和 3:

|     |     |
| :--- | :--- |
| 通用用户标识符 1 | p&#95;user&#95;1 |
| 通用用户标识符 2 | p&#95;user&#95;1 |
| 通用用户标识符 3 | p&#95;user&#95;1 |

*请参阅下方的通用用户标识符哈希说明部分

**2. 自定义细分列表**

公司需要以 `p_user_id` 的形式提供用户列表,以便为客户创建自定义受众,用于在 X 上进行定向投放。

* 行分隔值
* `p_user_id`
* * (与上述 1. 完整数据匹配部分中提供的值相同。如果完整数据匹配中提供的值已进行哈希处理,则公司需在受众文件中提供相同的哈希值。如果提供的值未进行哈希处理,则公司需提供未哈希的值。)

<div id="standard-matching-requirements">
  #### 标准匹配要求
</div>

如果公司未使用统一的标准 ID 来映射所有客户的用户标识符，建议采用以下流程。

**自定义分组列表**

公司将代表客户直接向 X 提供经过哈希处理的常见用户标识符列表，用于创建自定义受众。

此文件的格式应为：

* 每行一个值
* 经过哈希处理的常见用户标识符（例如电子邮件地址）
* 遵循下文所列的文件命名约定
* 遵循下文“哈希说明”部分中对电子邮件地址的哈希处理指引

<div id="custom-segment-list-file-naming-operations">
  #### 自定义细分列表文件命名与操作
</div>

文件的操作将由文件名决定，可用的操作以及通用的文件命名约定如下：audiencename&#95;partnername.handle.operation.filetype

* audiencename：Custom Audience 的名称。此字段是在 ads.x.com 广告活动设置界面中选择受众时显示的名称，例如 brand&#95;loyalty&#95;card&#95;holders。
* partnername：代表广告主提供 data 的公司的名称，例如 company&#95;name。
* handle：将拥有 Custom Audiences 访问权限的 X 账号（@handle），例如 @pepsi、@dietpepsi
* operation：new、add、remove、removeall、replace（详见下文）
* ：标准 Unix epoch 时间戳（单位为秒），用于确保每个上传的受众文件都是唯一的
* filetype：文件应为 *.txt 格式

<div id="creating-and-updating-audiences">
  #### 创建和更新受众
</div>

使用单个文件创建一个新受众，例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.new.txt

Add - 将列表中的匹配用户添加到现有受众中，例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.add..txt

Remove - 从现有受众中移除列表中的匹配用户，例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.remove..txt

Remove All - 从该客户端的所有受众中移除由定期更新的累积列表所产生的所有匹配用户（即客户端的退订名单 Opt Out List）。例如：partnername.pepsi.removeall.txt

* 可用于维护一个已从该广告主退订的用户的完整列表。
* X 只会遵从此文件中提供的最新列表，并会在所有现有和未来的受众中，对在提供并处理此文件时匹配到的 X 用户生效。

Replace - 删除一个现有受众并用新的受众列表替换。例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.replace..txt

整体公司退订（Overall Company Opt-Out）- 公司将提供一个累积退订（Opt-Out）文件，用于移除根据公司退订政策已选择退订的用户。

X 只会遵从此公司退订文件中提供的最新列表，并会在所有现有和未来的受众中，对在提供并处理此文件时匹配到的 X 用户生效。公司退订文件的格式如下：例如：partnername.removeall.txt

Delete - 从当前受众列表中移除一个现有受众，例如：loyalty&#95;card&#95;holders&#95;partnername.pepsi.delete.txt

<div id="hashing-directions">
  #### 哈希说明
</div>

X 将通过 PGP 安全地共享一个用于对常见用户标识符（即电子邮件地址）进行哈希的 base64 编码生产环境密钥。Company 将对该密钥进行 base64 解码，以生成一个用于执行哈希的 32 字节密钥。

示例 base64 编码密钥：

BrQvOg+dACBUmKjRiNxZgJLh6zydjS0ZOv80FelTNzM=

示例 Base64 解码密钥：

/:� TшY

标准化处理：在哈希之前，Company 将对常见用户标识符执行基本标准化处理（设备 ID 除外，参见 Device ID Normalization 部分）。

<div id="e-mail-normalization">
  #### E-mail 规范化
</div>

即去除首尾空格，并将电子邮件地址转换为小写。

例如：原始电子邮件地址：testemail&#95;Organisational&#95;baseball+884`@`It92I6Ev2B`.`Com

规范化后：testemail&#95;organisational&#95;baseball+884`@`it92i6ev2b`.`com

哈希值：74d9584eded0ad1e5572a1c1849f3716751d371d6117a6155dad5363f4b4fbec

注意：编码后的 HMAC 和密钥的字符数可能会根据输入和编码方式而变化，因此字符数并不是固定的。

<div id="device-id-normalization">
  #### Device ID 规范化
</div>

设备 ID 的哈希需要满足相同的要求：使用 SHA-256 哈希算法，以及我们提供给数据合作伙伴的通用盐值。我们会像处理电子邮件地址一样去除空格，但不会对 IDFA/Android ID 进行小写转换，必须使用 IDFA/Android ID 的原始精确格式。

下面是在哈希前适用于 iOS 和 Android 的设备 ID 原始格式示例：

iOS IDFA: DD99CFF7-6186-4602-9DF2-ED3FD0B2D431

Android ID: b5bf2122961b3595

Hashed iOS IDFA: 134fb8cd95c7fd42e2793f469a447198ca5f990968db2dbadad70e723ed9750b

Hashed Android ID: 130dddff1939f229476f50bc8adab8fcb7e3525b0e9604fe8effc15e68cee4a4

<div id="x-user-id-normalization">
  #### X 用户 ID 规范化
</div>

X 的 ID 仍然会被哈希处理，因为数据分组（例如由 @handle 组成的 Customer List）虽然不是 PII，但对广告主而言是私有的。我们对 X ID 的哈希处理有相同的要求：使用 SHA-256 哈希算法以及我们提供给数据合作伙伴的通用 salt。X ID 和 `@`username 中的空格都应去除，但 User ID 不需要进行规范化。为进行规范化，@username 应转换为小写，并且 @ 符号不应作为 username 的一部分包含在内。

原始 ID 格式如下：

* User ID: 27674040
* @username: testusername

哈希后的 User ID: bf6b57d4e861e83bea8bbed2b800b251a64c95468ee6e8cb07c3368c9ed45e85

哈希后的 @username: 12201ae78ad1afa907c7112d17f498154ffb0bf9ea523f5390e072a06d7d9812

**数据规范化**

**设备 ID**：

* IDFA - 使用带短横线的小写格式；例如：`4b61639e-47cc-4056-a16a-c8217e029462`
* AdID - 必须采用设备上的原始格式，不要改为大写，保留短横线；例如：`2f5f5391-3e45-4d02-b645-4575a08f86e`
* Android id - 必须采用设备上的原始格式，不要改为大写，且不包含短横线或空格；例如：`af3802a465767e36`

**电子邮件地址**：

* 使用小写，移除首尾空格；例如：`support@x.com`

**X 用户名**：

* 不包含 @，使用小写，并移除首尾空格；例如：`jack`

**X 用户 ID**：

* 标准整数；例如：`143567`

**数据哈希**

每一行的数据必须使用 `SHA256` 进行哈希，且不添加盐值（salt）。此外，最终输出的哈希值必须为小写。例如：49e0be2aeccfb51a8dee4c945c8a70a9ac500cf6f5cb08112575f74db9b1470d，**而不是**49E0BE2AECCFB51A8DEE4C945C8A70A9AC500CF6F5CB08112575F74DB9B1470D

```
# hasing user @AdsAPI using python
import hashlib
hashlib.sha256("adsapi".encode()).hexdigest()

#output
49e0be2aeccfb51a8dee4c945c8a70a9ac500cf6f5cb08112575f74db9b1470d
```

更多有关哈希的代码示例可以在 [github.com/xdevplatform/ads-platform-tools](https://github.com/xdevplatform/ads-platform-tools) 中找到。

  ### 自定义受众：Web
</div>

<Frame>
  <img src="https://cdn.cms-twdigitalassets.com/content/dam/developer-twitter/images/info.png" alt="info.png" />
</Frame>

**说明**

为了代表广告主进行定向投放，合作伙伴会向 X 发送一份 ID 列表（`p_user_ids`）。通过 ID 同步（ID Sync）流程，在 `p_user_ids` 与 X 用户 ID 之间建立映射关系。随后利用该映射关系生成可用于定向的 X 用户 ID 列表。这些自定义受众会关联到广告主在 ads.x.com 上的特定 @handle，该 @handle 由 Custom Audiences Web 广告系列设置中的标签指定。

X 会提供安全像素（secure pixel），可嵌入到合作伙伴的标签和站点上，用于将这些 ID（`p_user_ids`）与 X 用户 ID 进行匹配。ID 同步流程完成后，合作伙伴将创建定向文件，并通过一个 HTTPS 端点供 X 获取。X 会定期拉取并导入这些定向文件，随后在 X 的 UI 中提供使用。

**X 安全像素**

X 安全像素的形式如下：

https://analytics.x.com/i/adsct?p&#95;user&#95;id=xyz&amp;p&#95;id=123

**`p_user_id`** - xyz 表示由合作伙伴提供的合作伙伴用户 ID

**`p_id`** - 123 表示合作伙伴的唯一 ID（由 X 提供）

**合作伙伴 HTTPS 端点与定向用户文件**

合作伙伴需要向 X 提供一个 HTTPS 端点以及可用于定期拉取并导入定向文件的凭据（用户名/密码）。示例 HTTPS 端点如下所示：

```
https://<partnerdomain>/twitter/partner_targeting_%Y-%M-%D.tsv.gz
```

%Y - 年的格式代码 (YYYY)

%M - 月的格式代码 (MM)

%D - 日的格式代码 (DD)

传输的数据将包含以下文件：

1. Partner Targeting User File
2. Targeting Conversion File

所有文件都将采用 TSV 格式，其中每一行中的各个字段之间使用制表符分隔。字段的有效取值本身绝不会包含制表符。

**允许的 X IP 地址范围：**

下面是可以允许访问 Partner Endpoint 的 IP 地址范围。

* 199.16.156.0/22
* 199.59.148.0/22

**Partner Targeting User File：**

| **Column Number** | **Column Name**   | **Column Type** | **Description**                                                                                                               |
| :---------------- | :---------------- | :-------------- | :---------------------------------------------------------------------------------------------------------------------------- |
| 1                 | partner id        | string          | “partner id” 是 X 提供给合作方、用于唯一标识每个合作方的 ID。                                                                                      |
| 2                 | advertiser id     | string          | “advertiser id” 是该广告主的 @handle。                                                                                               |
| 3                 | p&#95;user&#95;id | string          | “p&#95;user&#95;id” 是合作方用于标识用户的唯一 ID。                                                                                         |
| 3                 | confidence score  | integer         | “confidence score”（置信度分数）是可选字段。我们建议将置信度分数设置在 0–100 之间。如果用例是重定向，则置信度分数为 “100” 表示该用户被直接重定向。0–99 之间的任意分数对应于该相似受众的置信度等级。          |
| 4                 | segment label     | string          | “segment label” 是可选字段。合作方可以使用 “segment label” 来指定例如产品类别等信息。我们建议使用此 “segment label”，因为这是 ads.x.com 界面中 Custom Audiences 的可读名称。 |

**Notes：**

每次我们收到新的 Partner Targeting File 时，除非另有约定，我们都期望它是合作方推荐我们投放的用户的完整列表，而不是增量列表。我们会与每个合作方协商该 Partner Targeting File 的投递频率。如果在预期时间内未收到 Partner Targeting File，我们将继续使用上一版本（在预定义的过期时间内有效）。

<div id="audience-api-integration">
  ## Audience API 集成
</div>

### 概述

Audience API 作为 Ads API [v4](/zh/x-ads-api/introduction) 的一部分发布，相比旧版 Audiences 端点带来了多项改进。这个新端点由全新的 Audience 处理后端提供支持，在稳定性、健壮性和可靠性方面都有明显提升。本指南旨在突出 Audience API 与旧版受众上传与管理流程之间的差异。 

相关参考文档可在 [Audience API](/zh/x-ads-api/audiences) 参考文档页面中找到。 

**注意**：所有 Audience 用户数据在上传前都必须进行 SHA-256 哈希处理。更多详情，以及可接受的用户标识符类型和数据规范化说明，请参见 [user data](/zh/x-ads-api/audiences) 页面。

**Audience 功能变更**

以下对自定义受众（Custom Audiences）的变更自 v4 起生效，一旦 Ads API 的 v3 版本下线，所有已弃用端点将不再可用：

* **已弃用** TON 上传：
  * GET accounts/:account&#95;id/custom&#95;audience&#95;changes
  * GET accounts/:account&#95;id/custom&#95;audience&#95;changes/:custom&#95;audience&#95;change&#95;id
  * POST accounts/:account&#95;id/custom&#95;audience&#95;changes
  * PUT accounts/:account&#95;id/custom&#95;audiences/global&#95;opt&#95;out
* **已弃用** Real Time Audiences：
  * POST custom&#95;audience&#95;memberships
* 自定义受众（Custom Audience）：
  * `list_type` 参数将从所有 [Custom Audience](/zh/x-ads-api/audiences) 端点的请求和响应中移除。该参数此前用于标识 Audience 的用户标识符类型（例如 email、X User ID 等），但现在单个 Audience 已支持接收多种用户标识符，因此该值已不再具有意义。
* 通用变更：
  * Audience 回溯时间窗口已更新为匹配过去 90 天内活跃的用户（原为 30 天）
  * 使受众可被定向投放所需的匹配用户最小数量已从 500 个用户降低至 100 个用户

<Note>
  **先决条件**

  * Ads API 访问权限
  * 若需访问 Audience 端点，您需要被加入 allowlist。请填写此表单，并在最初接受日期早于 2018-08-01 的情况下，接受新的 [X Ads Products and Services Agreement](/zh/x-ads-api/introduction)
</Note>

**Audience 上传流程**

下表列出了旧版与新版 Audience 创建流程之间的主要差异，更多详情见下文：

| 流程步骤 | Audience API | （已弃用）TON 上传 |
| :--- | :--- | :--- |
| 创建占位 Audience | 可通过 [POST custom&#95;audience 端点]/x-ads-api/audiences 创建 | 可通过 [POST custom&#95;audience 端点]/x-ads-api/audiences 创建 |
| 添加新用户 | 在 [Audience 端点](/zh/x-ads-api/audiences) 中使用 `operation_type` 为 `Update` | 在 [POST custom&#95;audience&#95;changes](/zh/x-ads-api/audiences) 端点中使用 `operation` 为 `ADD` |
| 移除用户 | 在 [Audience 端点](/zh/x-ads-api/audiences) 中使用 `operation_type` 为 `Delete` | 在 [POST custom&#95;audience&#95;changes](/zh/x-ads-api/audiences) 端点中使用 `operation` 为 `REMOVE` |
| 将用户选择退出 | 在 [Audience 端点](/zh/x-ads-api/audiences) 中使用 `operation_type` 为 `Delete`，并提供该用户所属的相应 `custom_audience_id` | 使用 [Global opt-out 端点](/zh/x-ads-api/audiences) |

**注意**：通过 TON 上传路径进行更新或选择退出操作的任何受众，必须先通过 [TON Upload](/zh/x-ads-api/audiences) 端点上传相应列表，并使用 [custom&#95;audience&#95;changes](/zh/x-ads-api/audiences) 端点将其关联到某个 Audience。

**速率限制（Rate Limiting）**

Audience API 端点对每个账户的速率限制为 1500/1 分钟。单个负载中可发送的用户数量没有限制。对负载的唯一约束为：

1. 操作总数：最多 2500 个操作

2. 最大负载大小：5,000,000 字节

**Audience 用户管理**

<div id="remove-users-from-an-audience">
  #### 从受众中移除用户
</div>

与上文添加用户的流程类似，可以通过以下方式将用户从受众中移除：

POST https://ads-api.x.com/11/accounts/18ce54d4x5t/custom&#95;audiences/1nmth/users

```
    # 所有值都必须经过哈希处理,此示例中使用的未哈希值仅用于说明目的
    [
      {
        "operation_type": "Delete",
        "params": {
          "effective_at": "2018-05-15T00:00:00Z",
          "expires_at": "2019-01-01T07:00:00Z",
          "users": [
            {
              "email": [
                "abc@x.com"
              ],
              "twitter_id": [
                "783214",
                "1225933934"
              ]
            },
            {
              "email": [
                "edf@x.com"
              ],
              "twitter_id": [
                "121291606",
                "17874544"
              ]
            }
          ]
        }
      }
    ]
```

`operation_type` 必须设置为 `Delete`，并且会根据当初将用户添加到受众时所提供的任意键来匹配用户。比如，如果某个用户是通过 `email` 和 `twitter_id` 被添加到某个受众中的，那么之后可以使用这些键中的任意一个将同一用户移除，即使用 `email` 或 `twitter_id` 中的任意一个，或者同时使用二者。

此外，在同一个请求中可以同时向某个受众添加和移除用户。该 endpoint 在单个请求中支持多个 `operation_type`。

<div id="opt-out-users">
  #### 选择退出的用户
</div>

随着全局 opt-out endpoint 的弃用，合作伙伴必须对任何已从任一 Audience 中选择退出的用户执行 `Delete` 操作。可以通过以下几种方式实现：

1. 记录哪些用户属于哪些 Audience，并从每个 Audience 中单独移除这些用户。
2. 将用户从与某个 Ads 账号关联的**所有** Audience 中移除。

**通用最佳实践**

* 我们强烈建议以接近实时的批处理方式调用此 endpoint，以避免出现处理时间较长的突发队列，并总体上减少对我们系统的不必要负载。这也可以确保用户更快可用于广告活动（campaign）定向。
* 成功的 API 调用将返回 `success_count` 和 `total_count`，它们与请求中接收到的 `user` 对象数量相对应。
* 此 endpoint 具有原子性，也就是说，要么整个请求成功，要么在出现任何错误时整个请求失败。出现错误响应时，建议 API 使用方修复错误，并使用完整的 payload 重试该请求。
* 如果请求失败，建议合作伙伴在重试时采用[指数退避](https://en.wikipedia.org/wiki/Exponential_backoff)策略。例如，第一次失败后立即重试，第二次失败后在 1 分钟后重试，第三次连续失败后在 5 分钟后重试，依此类推。

  #### POST accounts/:account_id/custom_audiences/:custom_audience_id/users[](#post-accounts-account-id-custom-audiences-custom-audience-id-users "Permalink to this headline")
</div>

此 endpoint 允许合作伙伴在给定的 `custom_audience_id` 中添加、更新和移除用户。该 endpoint 也支持为每个用户接收多种用户标识符类型。

请求中 `users` 字段中提供的所有数据 **除** `partner_user_id` 外，都必须使用 `SHA256` 进行哈希，并且需要先进行[规范化](/zh/x-ads-api/audiences#twitter-user-id-normalization)。

**批量请求（Batch Requests）**

* 当前 **此 endpoint** 的最大批量大小为 `2500`。批量大小由每个请求中的操作数（`Update`/`Delete`）决定。例如，在一个数组中包含超过 2500 个操作对象（`{"operation_type": "Update/Delete", [..] }`）将导致错误。
* 此 endpoint 可接受的请求 POST 请求体的最大大小为 `5,000,000` 字节。
* 此 endpoint 的速率限制为每 1 分钟窗口 1500 次。
* 所有参数都通过请求体发送，并且必须将 `Content-Type` 设置为 `application/json`。
* 批量请求会作为一个整体一起失败或一起成功，对于错误和成功情况的所有 API 响应都会保留初始请求中各项的顺序。

**批量响应（Batch Responses）**

Ads API 返回的响应包含两个字段：`success_count` 和 `total_count`。这两个值必须始终相等，它们表示后端已经处理的请求记录数量。当请求体中发送的记录数量与 `success_count` 和 `total_count` **不**相等时，应视为错误情况，需要进行重试。

**批量错误（Batch Errors）**

* 请求级错误（例如超出最大批量大小）会在响应中的 `errors` 对象下返回。
* 项级错误（例如缺少必需参数）会在响应中的 `operation_errors` 对象下返回。
* `operation_errors` 中错误的索引指向输入项中的对应索引，并附带相应的错误消息。

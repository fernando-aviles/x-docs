## 介绍

分析指标帮助合作伙伴和广告主了解他们在 X 上推广内容的表现。其中包括展示次数、点击量、视频观看次数以及花费金额等信息。此外，合作伙伴和广告主还能获取其所触达受众中不同细分群体的详细指标。

Ads API 支持两种获取广告活动详细绩效指标的方式：同步和异步。使用同步分析调用时，请求的指标会在响应中直接返回。使用异步分析端点时，请求的指标会在关联的“job”完成处理后，通过可下载的结果文件提供。同步端点支持较短的时间范围，非常适合实时优化广告活动。异步端点支持更长的时间范围，因此适用于获取更多数据，非常适合用于生成报表或进行历史数据回填。

<div id="synchronous-vs-asynchronous">
  ### 同步与异步
</div>

下表总结了同步与异步分析端点之间的差异。这些信息旨在帮助开发者选择应使用哪一组端点。

| 功能 | 同步 | 异步 |
|:---------|:------------|:--------------|
| 速率限制 | 用户级：250 个请求 / 15 分钟 | 账户级：100 个*并发作业 |
| 时间范围 | 7 天 | 90 天（未分段）<br />45 天（已分段） |
| 分段 | 否 | 是 |
| 响应返回内容 | 指标数据 | 作业**的处理状态 |
| 推荐用例 | 实时优化<br />用户界面请求 | 定期同步<br />回填历史数据 |

<Note>
  * 这是指在任意时间点可以处于处理状态的最大作业数量。

  ** 作业成功完成处理后，会返回一个 URL。可以从该 URL 下载压缩（gzip）结果文件。

  除此之外，这些端点在功能上是相同的。
</Note>

<div id="use-cases">
  ### 使用场景
</div>

主要有三种分析类使用场景。

1. 实时优化：使用效果指标更新正在投放的推广活动
2. 同步：定期运行的后台同步
3. 新账号接入：回填历史数据

同步分析端点可用于实时优化，根据最近 5 到 15 分钟内的指标变化更新推广活动。任一端点都可用于分析数据同步。请注意，所需的时间范围以及是否需要进行细分分析将决定应使用哪个端点。新账号接入只能通过异步分析端点完成。（同步分析端点绝不应用于检索大量数据。）

如果通过后端进程同步指标，异步分析端点可以为仪表板和其他 UI 元素提供支持。你的实现应避免为了响应用户界面请求而调用异步分析端点。

<div id="request-options">
  ### 请求选项
</div>

Analytics 请求以广告账号为范围，因此需要在资源路径中包含账号 ID。下面列出的请求选项通过查询参数进行指定。以下几类值为必需：

* Entities：实体类型，以及最多 20 个希望获取分析数据的实体 id
* 时间范围：开始和结束时间，采用 ISO 8601 格式表示
  * **注意：** 必须精确到整点小时
* 指标组：一个或多个相关指标集合（各指标组所包含的指标列表参见 Metrics and Segmentation）
* 粒度：指定返回指标的聚合级别
* 投放位置：决定是否为在 X 内或 X 外投放的广告提取指标
  * **注意：** 每个请求只能指定一个投放位置值

使用 `start_time` 和 `end_time` 请求参数来指定时间范围。这些值必须根据指定的粒度按以下方式对齐：

1. `TOTAL`：可指定任意时间范围（在该端点的限制内）
2. `DAY`：开始时间和结束时间都必须与账号所在时区的午夜对齐
3. `HOUR`：可指定任意时间范围（在该端点的限制内）

结束时间为不包含在内的上界。例如，一个 `start_time=2019-01-01T00:00:00Z` 且 `end_time=2019-01-02T00:00:00Z` 的请求只会返回一天的分析指标（而不是两天），因为该时间范围仅覆盖 24 小时。

**分段（Segmentation）**

分段仅可通过我们的异步分析端点使用，它允许合作伙伴和广告主按特定定向值拆分并获取指标。要请求分段指标，请使用 `segmentation_type` 请求参数。有关分段选项的更多详情，请参见 [Metrics and Segmentation](/zh/x-ads-api/analytics#metrics-and-segmentation)。

<div id="faqs">
  ## 常见问题解答
</div>

为什么 Ads API 中的数值与 X Ads UI 中显示的不一致？

* 确保你为两类投放位置都请求了数据：`ALL_ON_TWITTER` 以及 `PUBLISHER_NETWORK`、`SPOTLIGHT` 和 `TREND`。
* 请记住，Ads API 中的结束时间是排他的；而在 Ads UI 中则是包含在内的。

为什么我请求数据的时间不同，得到的数值会发生变化？

* 一旦报表指标可用，你就可以获取它们。它们是近乎实时可用的。不过这些早期结果是估算值，因此预期会发生变化。除花费数据外，其他指标会在 24 小时后最终确定。
* 花费类指标通常会在事件发生后的 3 天内最终确定。但是，我们会在事件发生后的最长 14 天内处理计费数据（例如用于垃圾信息过滤）。

如何确定在特定时间段应该请求哪些实体 ID？

* 使用 [Active Entities endpoint](/zh/x-ads-api/analytics#active-entities-2)

为什么分析响应中的所有数值都是 `null`？

* 这很可能是因为在所请求的时间段内该广告系列没有投放
* 使用 [Active Entities endpoint](/zh/x-ads-api/analytics#active-entities-2) 来确定应为哪些实体以及在什么时间段获取分析数据

为什么 API 显示 `null` 值，而 UI 显示的是 0？

* UI 选择将这些值显示为 0，但它们在语义上是等价的。

如何请求与更细粒度投放位置（例如 X 时间线）相关联的指标？

* 我们在分析中支持以下投放位置的取值：`ALL_ON_TWITTER` 以及 `PUBLISHER_NETWORK`、`SPOTLIGHT` 和 `TREND`（即 [X Audience Platform](/zh/x-ads-api/audiences)）

是否可以检索已删除或已暂停实体的指标？

* 可以。实体的状态不会影响分析指标的可用性。

为什么分段后的数值与未分段的数值对不上？

* 由于数据生成方式的原因，分段数据&#95;不&#95;预期会 100% 汇总到未分段数据。

是否可以请求按多个维度分段的数据？

* 我们不支持多维度分段。

<div id="best-practices">
  ## 最佳实践
</div>

在通过 Ads API 收集[分析](/zh/x-ads-api/analytics)数据时的一些最佳实践。

<div id="rate-limiting-and-retries">
  ### 速率限制与重试
</div>

* 对于受到速率限制的请求（返回 `HTTP 429` 状态码的请求），你必须检查 `x-rate-limit-reset` 响应头，并且只能在该响应头指示的时间点或之后重试。
* 对于返回 HTTP 503 Service Unavailable 状态码的请求，你必须检查 `retry-after` 响应头，并且只能在该响应头指示的时间之后重试。
* 不遵守指定重试时间的应用，可能会在不另行通知的情况下被暂停或限制其对 Ads API 的访问权限。

<div id="analytics-metrics-in-a-nutshell">
  ### 分析指标概览
</div>

* 除 `billed_charge_local_micro` 外，所有分析指标在 24 小时后将被锁定且不再变化。
* `billed_charge_local_micro` 指标在返回 data 起最长 3 天内为预估值。
* 在 24 小时之后，该指标可能会因超支抵扣（在指定 `end_time` 之后投放的广告）以及被判定为垃圾的可计费事件而减少。该指标在 24 小时后变动幅度极小。
* 更多信息请参阅 [Analytics](/zh/x-ads-api/analytics)。

<div id="fetching-real-time-non-segmented-data">
  ### 获取实时、未分段数据
</div>

* 始终同时提供 `start_time` 和 `end_time`。
* 不要拉取早于 7 天的实体数据。
* 建议以 `HOUR` 粒度请求数据，因为你始终可以通过聚合和汇总指标来获得 `DAY` 和 `TOTAL` 粒度。
* 建议在 `line_items` 和 `promoted_tweets` 层级请求数据，因为你始终可以聚合和汇总这些指标，以获得整个广告实体层级（即 campaign、funding instrument 或 account 层级）的总计。
* 在你这边（本地）保存并存储分析指标的值。
* 不要重复查询早于 30 天的数据。这些数据不会发生变化，应存储在本地。
* 所有未分段数据都是实时的，数据应在事件发生后的数秒内可用。
* 将转化类指标和非转化类指标拆分为单独的请求。

<div id="fetching-segmented-data">
  ### 获取分段数据
</div>

* 请参考上文“获取实时、非分段数据”的相关指南。下面提供了补充建议。
* 对于大多数分段数据类型，在某些情况下，数据在长达 1 小时内可能不完整。按 `INTERESTS` 维度分段的数据可能会延迟最长 12 小时。
* 由于此类信息的生成方式不同，分段数据汇总后与非分段数据总量不一定能 100% 对齐。

<div id="fetching-historical-data">
  ### 获取历史数据
</div>

* 在回填数据（例如添加新的广告主账号）时，可能需要将 `start_time` 和 `end_time` 拆分为更小的时间段，多次发起请求。
* 将每次获取限制在最长 30 天的时间窗口内。
* 对这些请求进行限流，并在一段时间内分散发送，以避免耗尽这类请求的速率限制。

<div id="active-entities">
  ### 活跃实体
</div>

<div id="introduction">
  #### 简介
</div>

[Active Entities 端点](/zh/x-ads-api/analytics#get-stats-accounts-account-id-active-entities) 旨在与我们的[同步](/zh/x-ads-api/analytics#get-stats-accounts-account-id)和[异步](/zh/x-ads-api/analytics#asynchronous-analytics)分析端点配合使用，因为它可以告知你应为哪些广告系列请求分析数据。它通过返回广告实体的详细信息以及其指标发生变动的时间来实现这一点。使用此端点将大大简化你的代码和获取分析数据的逻辑。

本指南包含有关该端点及其数据源的信息和上下文说明。它还提供了[使用指南](#usage)以及一系列[请求示例](#example)，演示如何将 Active Entities 与我们的分析端点结合使用。[摘要部分](#summary)提供了推荐方法的高层次说明。

<div id="data">
  #### 数据
</div>

每当广告实体的指标发生变化时，我们都会记录有关该变化的信息。这些变更事件会按小时分段存储，并包含关于实体本身的详细信息，以及该变化所适用的时间。后者之所以必要，是因为变更事件并不总是与其被记录的时间相对应。账单调整就是造成这种情况的常见原因之一，但也可能还有其他原因。

<div id="endpoint">
  #### 端点
</div>

<div id="request">
  ### 请求
</div>

Active Entities 请求以广告账户为作用域，并且有三个必需的查询参数：`entity`、`start_time` 和 `end_time`。

`twurl -H ads-api.x.com "/11/stats/accounts/18ce54d4x5t/active_entities?entity=PROMOTED_TWEET&start_time=2019-03-05T00:00:00Z&end_time=2019-03-06T00:00:00Z"`

支持以下 `entity` 值：`CAMPAIGN`、`FUNDING_INSTRUMENT`、`LINE_ITEM`、`MEDIA_CREATIVE`、`PROMOTED_ACCOUNT` 和 `PROMOTED_TWEET`。这反映了我们的分析端点所支持的实体类型。

`start_time` 和 `end_time` 的值必须使用 [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) 格式，并指定要查询的按小时划分的时间段。这些时间必须以整点小时来表示。

此端点还支持三个可选参数，可用于过滤结果：`funding_instrument_ids`、`campaign_ids` 和 `line_item_ids`。它们适用于广告层级中的所有级别，并可与任意指定的 `entity` 类型一起使用。

<div id="response">
  ### 响应
</div>

上述请求的 Active Entities 响应如下所示。

```json
    {
      "request": {
        "params": {
          "account_id": "18ce54d4x5t",
          "entity": "PROMOTED_TWEET",
          "start_time": "2019-03-05T00:00:00Z",
          "end_time": "2019-03-06T00:00:00Z"
        }
      },
      "data": [
        {
          "entity_id": "2r0wxw",
          "activity_start_time": "2019-03-04T20:55:20Z",
          "activity_end_time": "2019-03-05T03:43:56Z",
          "placements": [
            "ALL_ON_TWITTER"
          ]
        },
        {
          "entity_id": "2r30fn",
          "activity_start_time": "2019-03-05T08:11:08Z",
          "activity_end_time": "2019-03-05T14:40:59Z",
          "placements": [
            "ALL_ON_TWITTER",
            "PUBLISHER_NETWORK"
          ]
        }
      ]
    }
```

`data` 数组中为每个应在后续分析请求中包含的实体都包含一个对象。你不应为不在此集合中的 ID 请求分析。

每个对象包含四个字段：`entity_id`、`activity_start_time`、`activity_end_time` 和 `placements`。活动开始时间和结束时间表示相关实体变更事件适用的时间范围，因此决定了在后续分析请求中应指定的日期。`placements` 数组可以包含以下值：`ALL_ON_TWITTER`、`PUBLISHER_NETWORK`、`SPOTLIGHT` 和 `TREND`。它表示针对给定实体 ID 应请求哪些投放位置。

#### 用法

Active Entities 端点应当作为发出分析请求的依据。以下使用指南旨在支持分析同步，使合作伙伴能够保持其数据存储与 Twitter 同步。换句话说，它说明了如何执行定期计划的后台同步任务。

开发者需要做出两个决定：

1. 多长时间请求一次 Active Entities 信息，从而决定多长时间拉取一次分析数据。
2. 如何使用活动开始和结束时间来确定分析请求的 `start_time` 和 `end_time` 值。

在下面的两个小节中，将在摘要之后对这些内容进行更详细的讨论。

<div id="summary">
  ### 摘要
</div>

按照以下方式使用 Active Entities 端点，以决定如何发起分析请求。在你确定了多长时间请求一次活动实体信息、以及多长时间拉取一次分析数据之后，再遵循下面的步骤。

1. 发起 Active Entities 请求。
2. 按照 `placement` 拆分响应：一个分组用于 `ALL_ON_TWITTER`，一个用于 `PUBLISHER_NETWORK`，一个用于 `SPOTLIGHT`，一个用于 `TREND`。
3. 对于每个 `placement` 分组，执行以下操作。
   1. 提取实体 ID。
   2. 确定分析请求的 `start_time` 和 `end_time` 值。
      * 找到最小的 `activity_start_time`，并将该值向下取整。
      * 找到最大的 `activity_end_time`，并将该值向上取整。
   3. 发起分析请求。
      * 将实体 ID 分成每批 20 个。
      * 使用步骤 3b 中的 `start_time` 和 `end_time` 值。
      * 指定相应的 `placement` 值。
   4. 写入你的数据存储。

请参阅 [active&#95;entities.py](https://github.com/xdevplatform/twitter-python-ads-sdk/blob/master/examples/active_entities.py)，该示例演示了如何使用 Python SDK。

<div id="frequency">
  ### 频率
</div>

对第一个问题的回答决定在 Active Entities 请求中应使用的时间范围。例如，如果每小时请求一次 Active Entities 信息，则时间范围应为一小时。如果每天请求一次 Active Entities 信息，则时间范围应为一天。换言之，应选择这样的时间范围：当前请求的 `start_time` 等于上一次请求的 `end_time`。

<Note>
  **Note**: 同一个时间窗口应只被请求一次。对同一个时间窗口发起多次请求会导致不必要的分析数据请求。（下面有例外情况。）
</Note>

对于希望在当前这一小时内每小时多次请求分析数据的合作伙伴，同样适用这一模式——请求频率决定时间范围。下表展示了在这种场景下 Active Entities 的示例开始和结束时间戳。

|     |     |     |
| :--- | :--- | :--- |
| **Request time** | **`start_time` timestamp** | **`end_time` timestamp** |
| 00:15:00 | 00:00:00 | 00:15:00 |
| 00:30:00 | 00:15:00 | 00:30:00 |
| 00:45:00 | 00:30:00 | 00:45:00 |
| 01:00:00 | 00:45:00 | 01:00:00 |

鉴于变更事件的存储方式，上述四个 Active Entities 请求都会查询同一个按小时划分的桶（hourly bucket），这对该用例而言是必要的。但是，在当前这一小时结束之后，就不应再查询这个按小时划分的桶。

<div id="activity-times">
  ### 活动时间
</div>

我们建议按以下方式处理活动开始时间和结束时间。在 Active Entities 响应中的所有对象里，找到最小的 `activity_start_time` 和最大的 `activity_end_time`。对这些值进行调整：将最小活动开始时间向下取整，将最大活动结束时间向上取整。具体来说，把这两个时间戳的时、分、秒都设为零，并在结束时间上额外加一天，如下表所示。这些就是你在后续分析请求中应当指定的开始和结束时间。

|     |     |
| :--- | :--- |
| **最小、最大活动时间** | **推导出的时间** |
| 2019-03-04T20:55:20Z  <br />  <br />2019-03-05T14:40:59Z | 2019-03-04T00:00:00Z  <br />  <br />2019-03-06T00:00:00Z |

**注意**：务必包含将时、分、秒设为零的时间戳。否则，如果只传入日期，我们会假定你请求的分析数据区间为广告账户所在时区从午夜开始到午夜结束，这可能不是你想要的。比如，如果最小活动开始时间是 2019-02-28T01:30:07Z，而对一个偏移量为 -08:00:00 的广告账户省略了时间戳，那么该分析请求将遗漏发生在 01:30 到 08:00 之间的变更。

或者，如果你更希望只针对返回的活动时间窗口本身请求分析数据，而不扩展到整天，也可以这样做。采用这种方式时，推导出的开始和结束时间分别为 2019-03-04T20:00:00Z 和 2019-03-05T15:00:00Z。（请注意，如果在分析请求中指定了 `DAY` 粒度，则不接受此类时间范围。）

<div id="asynchronous-analytics">
  ### 异步分析
</div>

#### 介绍

异步分析端点允许合作伙伴和广告主通过提交创建请求来获取指标，这些请求由服务器以异步方式处理。（我们将其称为异步分析“任务”。）采用这种方式时，客户端的连接无需一直保持打开，直到请求完成。

这些端点与其同步对应端点类似，允许合作伙伴和广告主请求关于广告系列表现的详细统计数据。它们支持为账户、资金工具、广告系列、广告单元、推广推文以及媒体创意请求数据。不同于同步端点的是，异步分析端点支持更长的日期范围（最长 90 天），并支持细分。关于这两者差异的更多详情，请参阅我们的 [分析概览](/zh/x-ads-api/analytics) 页面。

与我们的同步端点不同，速率限制是基于给定账户的并发任务数量。换句话说，它基于在任一时刻可以处于处理状态的任务数量。我们在广告账户层级进行统计。

<div id="usage">
  #### 使用方法
</div>

使用异步分析端点检索广告活动指标是一个包含多个步骤的过程。该过程包括创建作业、检查作业是否已完成处理，以及最后下载 data。data 文件必须先解压缩。下面概述了四个具体步骤。

1. 使用 [POST stats/jobs/accounts/:account&#95;id](/zh/x-ads-api/analytics#asynchronous-analytics) 端点创建作业。
2. 以固定时间间隔向 [GET stats/jobs/accounts/:account&#95;id](/zh/x-ads-api/analytics#asynchronous-analytics) 端点发起请求，以确定作业是否已完成处理。
3. 作业完成处理后，下载 data 文件。
4. 解压 data 文件。

data 文件中返回的响应对象与同步分析端点的响应具有相同的 JSON 架构。

分段广告活动指标只能通过异步分析端点获取。广告活动指标可以按地理位置、性别、兴趣、关键词等进行细分。完整选项列表请参阅 [Metrics and Segmentation](/zh/x-ads-api/analytics#metrics-and-segmentation) 页面。若要请求分段指标，请在创建作业时使用 `segmentation_type` 请求参数。

获取在给定时间段内分析指标发生变化的实体详细信息。

此 endpoint 应与我们的分析类 endpoint 一起使用。该 endpoint 的结果指示应为哪些广告实体请求分析数据。有关使用指南，请参阅我们的 [Active Entities 指南](/zh/x-ads-api/analytics#active-entities)。

变更事件以按小时分桶的形式提供。

* `start_time` 和 `end_time` 值指定要查询的小时粒度时间桶。
* 返回的 `data` 数组将为每个应包含在后续分析请求中的实体提供一个对象。
* **重要**：后续分析请求中应指定的日期应基于 `activity_start_time` 和 `activity_end_time` 值来确定。
  * 这些值表示存储的变更事件所**适用**的时间范围。该信息会按实体返回。

## 简介

分析指标帮助合作伙伴和广告主了解他们在 X 上推广内容的效果。这包括展示次数、点击量、视频观看次数以及花费等信息。此外，合作伙伴和广告主还可以获取其触达受众中各个细分群体的详细指标。

Ads API 支持两种方式来获取详细的广告系列效果指标：同步和异步。使用同步分析调用时，请求的指标会在响应中返回。使用异步分析端点时，请求的指标会在关联的“作业”完成处理后，在可下载的结果文件中提供。同步端点支持较短的时间范围，非常适合用于实时广告系列优化。异步端点支持更长的时间范围，因此适用于获取更多数据，非常适合用于生成报表或进行历史数据回填。

<div id="synchronous-vs-asynchronous">
  ### 同步与异步
</div>

同步与异步分析端点之间的差异总结如下表。这些信息旨在帮助开发者选择使用哪一组端点。

| 功能 | 同步 | 异步 |
|:---------|:------------|:--------------|
| 速率限制 | 用户级：每 15 分钟 250 个请求 | 账户级：100 个并发*作业 |
| 时间范围 | 7 天 | 90 天（未分段）<br />45 天（已分段） |
| 分段 | 否 | 是 |
| 响应返回内容 | 指标数据 | 作业的处理状态** |
| 推荐使用场景 | 实时优化<br />用户界面请求 | 定期同步<br />回填历史数据 |

<Note>
  * 指在任意时间点，处于处理状态的作业数量上限。

  ** 作业成功完成处理后，会返回一个 URL。可以从该 URL 下载压缩（gzip）格式的结果文件。

  除此之外，这些端点提供的功能相同。
</Note>

<div id="use-cases">
  ### 使用场景
</div>

有三大主要分析使用场景。

1. 实时优化：使用效果指标更新正在投放的广告系列
2. 同步：按计划定期运行的后台同步
3. 新账户接入：回填历史数据

同步分析端点可用于实时优化，根据最近 5 到 15 分钟内指标的变化来更新广告系列。任一端点都可用于分析同步。请注意，所需的时间范围以及是否需要分段分析将决定应使用哪个端点。新账户接入只能使用异步分析端点完成。（同步分析端点绝不应用于检索大批量数据。）

如果通过后端进程同步指标，异步分析端点可以为仪表板和其他 UI 元素提供支持。你的实现应避免调用异步分析端点来直接响应用户界面请求。

<div id="request-options">
  ### 请求选项
</div>

Analytics 请求以广告账户为作用域，因此需要在资源路径中包含账户 ID。下面列出的请求选项通过查询参数指定。以下类型的值是必需的：

* 实体：实体类型，以及最多 20 个希望获取分析数据的实体 ID
* 时间范围：开始和结束时间，以 ISO 8601 表示
  * **注意：** 必须以整点小时表示
* 指标组：一个或多个相关指标集合（每个指标组内的指标列表参见 Metrics and Segmentation）
* 粒度：指定返回指标时的聚合级别
* 投放位置：决定是否为在 X 平台内或平台外投放的广告提取指标
  * **注意：** 每个请求中只能指定单一的投放位置值

使用 `start_time` 和 `end_time` 请求参数来指定时间范围。这些值必须按如下方式与指定的粒度对齐：

1. `TOTAL`：可指定任意时间范围（在该端点的限制内）
2. `DAY`：开始时间和结束时间都必须与账户时区的午夜对齐
3. `HOUR`：可指定任意时间范围（在该端点的限制内）

结束时间为排他边界。例如，一个带有 `start_time=2019-01-01T00:00:00Z` 和 `end_time=2019-01-02T00:00:00Z` 的请求只会返回一天的分析指标数据（而不是两天），因为该时间范围仅覆盖 24 小时。

**分段**

仅可通过我们的异步 Analytics 端点使用，分段允许合作伙伴和广告主按特定定向条件拆分获取指标。要请求分段指标，请使用 `segmentation_type` 请求参数。有关分段选项的更多详细信息，请参见 [Metrics and Segmentation](/zh/x-ads-api/analytics#metrics-and-segmentation)。

<div id="faqs">
  ## 常见问题
</div>

为什么 Ads API 中的数值与 X Ads 界面中显示的不一致？

* 请确保你请求了以下所有投放位置的数据：`ALL_ON_TWITTER`、`PUBLISHER_NETWORK`、`SPOTLIGHT` 和 `TREND`。
* 请记住，Ads API 中的结束时间是排他的；而在 Ads 界面中则是包含性的。

为什么我在不同时间请求数据时，数值会发生变化？

* 一旦报告指标可用，你就可以获取到它们，这些指标几乎是实时可用的。但这些早期结果是预估值，因此预期会发生变化。除花费数据外，其余指标会在 24 小时后最终确定。
* 花费类指标通常会在事件发生后 3 天内最终确定。不过，我们会在事件发生之日起最多 14 天内处理计费数据（例如用于垃圾信息过滤）。

如何确定在某个特定时间段内应请求哪些实体 ID？

* 使用 [Active Entities endpoint](/zh/x-ads-api/analytics#active-entities-2)

为什么 analytics 响应中的所有值都是 `null`？

* 很可能是在请求的时间段内，该推广活动没有投放。
* 使用 [Active Entities endpoint](/zh/x-ads-api/analytics#active-entities-2) 来确定要为哪些实体、在什么时间段获取 analytics。

为什么 API 显示的是 `null` 值，而界面显示的是 0？

* 界面选择将这些值显示为 0，但两者在含义上是等价的。

如何请求与更细粒度投放位置（例如 X 时间线）相关联的指标？

* 我们在 analytics 中支持以下投放位置取值：`ALL_ON_TWITTER`、`PUBLISHER_NETWORK`、`SPOTLIGHT` 和 `TREND`（即 [X Audience Platform](/zh/x-ads-api/audiences)）。

是否可以获取已删除或已暂停实体的指标？

* 可以。实体的状态不会影响 analytics 指标的可用性。

为什么分段后的数值与未分段的数值对不上？

* 由于数据生成方式的原因，分段数据&#95;不&#95;预期会 100% 汇总到未分段数据。

是否可以按多个维度对数据进行分段请求？

* 我们不支持多重分段（multi-segmentation）。

<div id="best-practices">
  ## 最佳实践
</div>

在通过 Ads API 收集[分析](/zh/x-ads-api/analytics) data 时的一些最佳实践。

<div id="rate-limiting-and-retries">
  ### 速率限制与重试
</div>

* 对于触发速率限制的查询（即返回 `HTTP 429` 状态码的请求），你必须检查 `x-rate-limit-reset` 请求头，并且只能在该头指示的时间点或之后重试。
* 对于返回 HTTP 503 Service Unavailable 状态码的查询，你必须检查 `retry-after` 请求头，并且只能在该头指示的时间之后重试。
* 不遵守上述重试时间要求的应用，可能会在未事先通知的情况下被撤销或限制对 Ads API 的访问权限。

<div id="analytics-metrics-in-a-nutshell">
  ### 分析指标概览
</div>

* 所有分析指标在 24 小时后即被锁定且不再变化，`billed_charge_local_micro` 指标除外。
* `billed_charge_local_micro` 指标在返回 data 之后的最长 3 天内为预估值。
* 在 24 小时之后，由于超支抵扣（在指定 `end_time` 之后投放的广告）以及对被认定为垃圾的可计费事件进行抵扣，该指标可能会下降。该指标在 24 小时后仅会有极小幅度的变动。
* 更多信息请参阅 [Analytics](/zh/x-ads-api/analytics)。

<div id="fetching-real-time-non-segmented-data">
  ### 获取实时、未分段数据
</div>

* 始终同时提供 `start_time` 和 `end_time`。
* 不要为早于 7 天的任何实体拉取数据。
* （理想情况下）按 `HOUR` 粒度请求数据，因为你始终可以通过聚合和汇总指标，将其汇总到 `DAY` 和 `TOTAL` 粒度。
* （理想情况下）在 `line_items` 和 `promoted_tweets` 级别请求数据，因为你始终可以通过聚合和汇总这些指标，获得整个广告实体层级（即 campaign、funding instrument 或 account 层级）的总计。
* 在你自己的系统（本地）保存和存储分析指标的数值。
* 不要重复查询早于 30 天的数据。这些数据不会发生变化，应在本地存储。
* 所有未分段数据都是实时的，数据应在事件发生后的数秒内可用。
* 将转化指标和非转化指标拆分为单独的请求分别获取。

<div id="fetching-segmented-data">
  ### 获取分段数据
</div>

* 请参考上文“获取实时、非分段数据”的指南。以下是补充建议。
* 对于大多数分段数据类型，数据在最长 1 小时内可能不完整。按 `INTERESTS` 分段的数据可能会延迟最长 12 小时。
* 由于此类信息的生成方式，分段数据在汇总时不应期望能与非分段数据 100% 完全对齐。

<div id="fetching-historical-data">
  ### 获取历史数据
</div>

* 在进行历史数据回填（例如添加新的广告主账号）时，可能需要将请求拆分为多个较小的 `start_time` 和 `end_time` 时间区间来发送。
* 将每次拉取的时间范围限制在 30 天之内。
* 对这些请求进行限速，并在一段时间内分散发送，以避免在这类拉取操作上耗尽你的速率限制。

<div id="active-entities">
  ### 活动实体
</div>

<div id="introduction">
  #### 介绍
</div>

[Active Entities endpoint](/zh/x-ads-api/analytics#get-stats-accounts-account-id-active-entities) 旨在与我们的[同步](/zh/x-ads-api/analytics#get-stats-accounts-account-id)和[异步](/zh/x-ads-api/analytics#asynchronous-analytics)分析端点配合使用，因为它可以告知你应当为哪些广告系列请求分析数据。它通过返回广告实体的详细信息以及这些实体的指标何时发生变化来实现这一点。使用此端点将大大简化你的代码和分析数据获取逻辑。

本指南介绍了该端点及其数据源的相关信息和背景。它还提供了[使用指南](#usage)以及一系列[请求示例](#example)，展示如何将 Active Entities 与我们的分析端点结合使用。[摘要部分](#summary)对推荐方法进行了总体性概述。

<div id="data">
  #### 数据
</div>

每当广告实体的某项指标发生变化时，我们都会记录与该变化相关的信息。这些变更事件按小时划分的时间桶进行存储，既包含该实体的详细信息，也包含该变更生效的时间。后者是必要的，因为变更事件并不总是发生在我们记录它们的时间点。计费调整是导致这种情况的常见原因之一，但也可能还有其他原因。

<div id="endpoint">
  #### 端点
</div>

<div id="request">
  ### Request
</div>

Active Entities 请求以广告账号为范围，并包含三个必需的查询参数：`entity`、`start_time` 和 `end_time`。

`twurl -H ads-api.x.com "/11/stats/accounts/18ce54d4x5t/active_entities?entity=PROMOTED_TWEET&start_time=2019-03-05T00:00:00Z&end_time=2019-03-06T00:00:00Z"`

支持以下 `entity` 值：`CAMPAIGN`、`FUNDING_INSTRUMENT`、`LINE_ITEM`、`MEDIA_CREATIVE`、`PROMOTED_ACCOUNT` 和 `PROMOTED_TWEET`。这对应了我们的分析端点所支持的实体类型。

`start_time` 和 `end_time` 值必须使用 [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) 格式表示，并指定要查询的按小时划分的时间段。这些时间必须是整点小时。

此端点还支持三个可选参数，可用于过滤结果：`funding_instrument_ids`、`campaign_ids` 和 `line_item_ids`。这些参数适用于广告层级中的所有级别，并可与任意指定的 `entity` 类型配合使用。

<div id="response">
  ### 响应
</div>

上述请求的 Active Entities 响应如下所示。

```json
    {
      "request": {
        "params": {
          "account_id": "18ce54d4x5t",
          "entity": "PROMOTED_TWEET",
          "start_time": "2019-03-05T00:00:00Z",
          "end_time": "2019-03-06T00:00:00Z"
        }
      },
      "data": [
        {
          "entity_id": "2r0wxw",
          "activity_start_time": "2019-03-04T20:55:20Z",
          "activity_end_time": "2019-03-05T03:43:56Z",
          "placements": [
            "ALL_ON_TWITTER"
          ]
        },
        {
          "entity_id": "2r30fn",
          "activity_start_time": "2019-03-05T08:11:08Z",
          "activity_end_time": "2019-03-05T14:40:59Z",
          "placements": [
            "ALL_ON_TWITTER",
            "PUBLISHER_NETWORK"
          ]
        }
      ]
    }
```

`data` 数组中会包含一个对象，表示每个需要在后续分析请求中纳入的实体。你不应为不在此集合中的 ID 请求分析数据。

每个对象包含四个字段：`entity_id`、`activity_start_time`、`activity_end_time` 和 `placements`。活动的开始时间和结束时间表示关联实体的变更事件所适用的时间范围，并据此决定在后续分析请求中应指定的日期。`placements` 数组可以包含以下取值：`ALL_ON_TWITTER`、`PUBLISHER_NETWORK`、`SPOTLIGHT` 和 `TREND`。它表示对于给定实体 ID 应请求哪些投放位置。

<div id="usage">
  #### 使用方法
</div>

Active Entities 端点应当作为发起分析请求的依据。以下使用指南旨在支持分析同步，使合作伙伴能够让其数据存储与 Twitter 保持同步。换句话说，它描述了如何执行定期的后台同步任务。

开发者必须做出两个决定。

1. 多久请求一次活跃实体信息，从而决定多久拉取一次分析数据。
2. 如何使用活动开始和结束时间来确定分析请求的 `start_time` 和 `end_time` 值。

摘要之后的两个小节将对这两点分别进行更为详细的说明。

<div id="summary">
  ### 摘要
</div>

按如下方式使用 Active Entities 端点，以控制如何发起分析请求。在你已经决定多长时间请求一次活跃实体信息、以及相应多长时间拉取一次分析数据之后，再按照以下步骤操作。

1. 发起 Active Entities 请求。
2. 按 `placement` 拆分响应。将 `ALL_ON_TWITTER` 为一组，`PUBLISHER_NETWORK` 为一组，`SPOTLIGHT` 为一组，`TREND` 为一组。
3. 对每个 placement 分组，执行以下操作。
   1. 提取实体 id。
   2. 确定用于分析的 `start_time` 和 `end_time` 值。
      * 找到最小的 `activity_start_time`，将此值向下取整。
      * 找到最大的 `activity_end_time`，将此值向上取整。
   3. 发起分析请求。
      * 将实体 id 分成每批 20 个。
      * 使用步骤 3b 中得到的 `start_time` 和 `end_time` 值。
      * 指定合适的 `placement` 值。
   4. 写入你的数据存储。

请参阅 [active&#95;entities.py](https://github.com/xdevplatform/twitter-python-ads-sdk/blob/master/examples/active_entities.py)，该文件是一个使用 Python SDK 的示例。

<div id="frequency">
  ### 频率
</div>

第一个问题的答案决定了在 Active Entities 请求中应该使用的时间范围。例如，如果每小时请求一次 Active Entities 信息，则时间范围应该为一小时；如果每天请求一次 Active Entities 信息，则时间范围应该为一天。换句话说，应选择这样的时间范围：当前请求的 `start_time` 等于上一个请求的 `end_time`。

<Note>
  **Note**: 每个时间窗口只应被请求一次。对同一时间窗口发起多次请求会导致不必要的分析请求。（下面是例外情况。）
</Note>

对于希望在&#95;当前&#95;小时内每小时请求多次分析数据的合作方，同样适用这一模式——请求频率决定时间范围。下表展示了在该场景下 Active Entities 的示例开始与结束时间戳。

|     |     |     |
| :--- | :--- | :--- |
| **请求时间** | **`start_time` 时间戳** | **`end_time` 时间戳** |
| 00:15:00 | 00:00:00 | 00:15:00 |
| 00:30:00 | 00:15:00 | 00:30:00 |
| 00:45:00 | 00:30:00 | 00:45:00 |
| 01:00:00 | 00:45:00 | 01:00:00 |

由于变更事件的存储方式，上述四个 Active Entities 请求实际上都查询了同一个按小时划分的时间桶，这对该用例来说是必要的。然而，在当前小时结束之后，就不应再查询这个按小时划分的时间桶。

<div id="activity-times">
  ### 活动时间
</div>

我们建议按以下方法处理活动的开始和结束时间。在 Active Entities 响应中的所有对象里，找到最小的 `activity_start_time` 和最大的 `activity_end_time`。然后对这些值进行调整：将最小活动开始时间向下取整，将最大活动结束时间向上取整。具体来说，将这两个时间戳的时、分、秒都设为零，并在结束时间上加一天，如下表所示。后续的分析请求中应使用这些推算出的开始和结束时间。

|     |     |
| :--- | :--- |
| **最小、最大活动时间** | **推算时间** |
| 2019-03-04T20:55:20Z  <br />  <br />2019-03-05T14:40:59Z | 2019-03-04T00:00:00Z  <br />  <br />2019-03-06T00:00:00Z |

**注意**：务必要包含时、分、秒都设为零的时间戳。否则，如果只传入日期，我们会假定你要请求从广告账户所在时区的午夜开始到午夜结束的分析数据，这可能并非你所期望的结果。例如，如果最小活动开始时间是 2019-02-28T01:30:07Z，而对于时区偏移为 -08:00:00 的广告账户省略了时间戳，那么分析请求将遗漏 01:30 到 08:00 之间发生的更改。

或者，如果你更希望只针对返回的活动时间窗口请求分析数据，而不扩展到整天，也可以这样做。使用这种方法，推算出的开始和结束时间分别为 2019-03-04T20:00:00Z 和 2019-03-05T15:00:00Z。（请注意，如果在分析请求中指定了 `DAY` 粒度，则不接受类似这样的时间范围。）

<div id="asynchronous-analytics">
  ### 异步分析
</div>

#### 简介

异步分析端点允许合作伙伴和广告主通过提交创建请求来获取指标，这些请求由服务器以异步方式处理（我们将这些称为异步分析“作业”）。采用这种方式，客户端的连接无需在请求完成前始终保持打开状态。

这些端点与其同步对应端点类似，允许合作伙伴和广告主请求有关广告系列表现的详细统计数据。它们支持为账户、资金工具、广告系列、投放单、推广推文以及媒体创意请求数据。与同步端点的区别在于，异步分析端点支持更长的时间范围（最长可达 90 天），并支持分段分析。关于二者差异的更多详细信息，请参阅我们的[分析概览](/zh/x-ads-api/analytics)页面。

与我们的同步端点不同，速率限制基于某个账户的并发作业数量。换句话说，它基于在任意时间点处于处理中状态的作业数量。我们在广告账户级别进行统计。

#### 用法

使用异步分析端点来检索广告活动指标是一个多步流程。它包括创建作业、检查作业是否已完成处理，最后下载数据。数据文件必须先解压。以下列出了四个具体步骤。

1. 使用 [POST stats/jobs/accounts/:account&#95;id](/zh/x-ads-api/analytics#asynchronous-analytics) 端点创建作业。
2. 按固定时间间隔向 [GET stats/jobs/accounts/:account&#95;id](/zh/x-ads-api/analytics#asynchronous-analytics) 端点发出请求，以确定作业是否已完成处理。
3. 一旦作业完成处理，下载数据文件。
4. 解压数据文件。

数据文件中返回的响应对象与同步分析端点的响应具有相同的 JSON 架构。

细分的广告活动指标只能通过异步分析端点获取。广告活动指标可以按地域、性别、兴趣、关键词等进行细分。有关可用选项的完整列表，请参阅 [Metrics and Segmentation](/zh/x-ads-api/analytics#metrics-and-segmentation) 页面。要请求细分指标，请在创建作业时使用 `segmentation_type` 请求参数。

获取在给定时间段内其分析指标发生变化的实体详情。

此 endpoint 应与我们的分析相关 endpoint 配合使用。该 endpoint 的结果用于指示应为哪些广告实体请求分析数据。使用规范请参见我们的 [Active Entities 指南](/zh/x-ads-api/analytics#active-entities)。

变更事件以按小时划分的时间桶提供。

* `start_time` 和 `end_time` 的取值指定要查询哪些按小时划分的时间桶。
* 返回的 `data` 数组会为每个应包含在后续分析请求中的实体提供一个对象。
* **重要**：后续分析请求中应指定的日期应基于 `activity_start_time` 和 `activity_end_time` 的值来确定。
  * 这些值表示存储的变更事件 *适用的* 时间范围。该信息会按实体返回。

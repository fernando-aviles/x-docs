## 简介

分析指标帮助合作伙伴和广告主了解他们在 X 上推广内容的投放效果。这包括展示次数、点击量、视频观看次数以及花费等信息。此外，合作伙伴和广告主还能获取他们所触达受众不同细分人群的详细指标。

Ads API 支持通过同步和异步两种方式获取广告活动的详细表现指标。使用同步分析调用时，请求的指标会直接在响应中返回。使用异步分析端点时，请求的指标会在关联的作业（“job”）处理完成后，通过可下载的结果文件提供。同步端点支持较短的时间范围，非常适合用于实时优化广告活动。异步端点支持更长的时间范围，因此适合获取大规模数据，理想用例包括生成报表或进行历史数据回填。

<div id="synchronous-vs-asynchronous">
  ### 同步与异步
</div>

同步和异步分析端点之间的差异总结如下表。此信息旨在帮助开发者选择要使用的端点组。

| 功能 | 同步 | 异步 |
|:---------|:------------|:--------------|
| Rate limiting | 用户级：250 次请求 / 15 分钟 | 账户级：最多并发 *100 个作业 |
| Time range | 7 天 | 90 天（未分段）<br />45 天（分段） |
| Segmentation | 否 | 是 |
| Response returns | 指标数据 | 作业的处理状态** |
| Recommended use case | 实时优化<br />用户界面请求 | 定期同步<br />回填历史数据 |

<Note>
  * 这是指在任何给定时间处于处理状态的作业数量上限。

  ** 作业成功完成处理后，会返回一个 URL。可从该 URL 下载压缩（gzip）结果文件。

  除此之外，这些端点提供相同的功能。
</Note>

<div id="use-cases">
  ### 使用场景
</div>

分析主要有三种使用场景。

1. 实时优化：使用表现指标更新正在投放的广告系列
2. 同步：按固定计划进行的后台同步
3. 新账户上手：回填历史数据

同步分析端点可用于实时优化，根据最近 5 到 15 分钟内指标的变化来更新广告系列。任一端点都可用于分析同步。请注意，所需的时间范围以及是否需要分段（segmentation）将决定应使用哪个端点。新账户上手只能通过异步分析端点完成。（切勿使用同步分析端点来检索大量数据。）

如果通过后端进程同步指标，异步分析端点可以为仪表盘和其他 UI 元素提供数据支持。你的实现应避免调用异步分析端点来直接响应用户界面请求。

<div id="request-options">
  ### 请求选项
</div>

Analytics 请求是以广告账户为作用范围的，因此需要在资源路径中提供账户 ID。下面列出的请求选项需要通过查询参数指定。需要以下类型的取值：

* 实体：实体类型，以及最多 20 个你希望获取分析数据的实体 ID
* 时间范围：开始时间和结束时间，以 ISO 8601 格式表示
  * **注意：** 必须以整点小时表示
* 指标组：一个或多个相关指标集合（各指标组所包含的指标列表参见「Metrics and Segmentation」）
* 粒度：指定返回指标时的聚合级别
* 投放位置：决定是否为在 X 站内或站外投放的广告拉取指标
  * **注意：** 每个请求只能指定一个投放位置值

使用 `start_time` 和 `end_time` 请求参数来指定时间范围。这些值必须按以下方式与指定的粒度对齐。

1. `TOTAL`：可以指定任意时间范围（在该 endpoint 的限制内）
2. `DAY`：开始时间和结束时间都必须对齐到账户所在时区的午夜
3. `HOUR`：可以指定任意时间范围（在该 endpoint 的限制内）

结束时间为不包含端点。例如，一个 `start_time=2019-01-01T00:00:00Z` 且 `end_time=2019-01-02T00:00:00Z` 的请求只会返回一天的分析指标（而不是两天），因为该时间范围仅覆盖 24 小时。

**分段（Segmentation）**

仅可通过异步 analytics endpoint 使用，分段功能允许合作伙伴和广告主按特定定向值拆分获取指标。要请求分段指标，请使用 `segmentation_type` 请求参数。有关分段选项的更多详情，请参见 [Metrics and Segmentation](/zh/x-ads-api/analytics#metrics-and-segmentation)。

<div id="faqs">
  ## 常见问题解答
</div>

为什么 Ads API 中的数值与 X Ads UI 中显示的不一致？

* 请确保你已同时请求以下投放位置的数据：`ALL_ON_TWITTER` 和 `PUBLISHER_NETWORK`、`SPOTLIGHT`、`TREND`。
* 请记住，Ads API 中的结束时间是排他的；而在 Ads UI 中则是包含在内的。

为什么我在不同时间请求数据时，数值会发生变化？

* 一旦报告指标可用，你就可以获取到它们，且几乎是实时可用的。但这些早期结果是预估值，因此预期会发生变化。除花费数据外，各项指标会在 24 小时后最终确定。
* 花费指标通常会在事件发生后 3 天内最终确定。不过，我们会在事件发生之日起最长 14 天内处理账单数据（例如用于垃圾信息过滤）。

如何确定在特定时间段内应该请求哪些实体 id？

* 使用 [Active Entities endpoint](/zh/x-ads-api/analytics#active-entities-2)。

为什么分析响应中的所有值都是 `null`？

* 很可能是该广告活动在请求的时间段内未投放。
* 使用 [Active Entities endpoint](/zh/x-ads-api/analytics#active-entities-2) 来确定应为哪些实体、在什么时间段获取分析数据。

为什么 API 显示的是 `null`，而 UI 显示的是 0？

* UI 选择将这些值显示为 0，但这两种表示是等价的。

如何请求与更细粒度投放位置（例如 X 时间线）关联的指标？

* 我们在分析中支持以下投放位置值：`ALL_ON_TWITTER` 和 `PUBLISHER_NETWORK`、`SPOTLIGHT`、`TREND`（即 [X Audience Platform](/zh/x-ads-api/audiences)）。

是否可以获取已删除或已暂停实体的指标？

* 可以。实体状态不会影响分析指标的可用性。

为什么分段数据与未分段数据对不上？

* 由于分段数据的生成方式不同，分段数据&#95;不&#95;应被期望能够 100% 汇总到未分段数据中。

是否可以按多个维度对数据进行分段请求？

* 我们不支持多维分段。

<div id="best-practices">
  ## 最佳实践
</div>

在通过 Ads API 收集[分析](/zh/x-ads-api/analytics)数据时应遵循的一些最佳实践。

<div id="rate-limiting-and-retries">
  ### 速率限制与重试
</div>

* 对于受到速率限制的请求（那些返回 `HTTP 429` 状态码的请求），你必须检查 `x-rate-limit-reset` 响应头，并且只能在该响应头指示的时间点或之后重试。
* 对于返回 HTTP 503 Service Unavailable 状态码的请求，你必须检查 `retry-after` 响应头，并且只能在该响应头指示的时间之后重试。
* 如果应用未遵守上述重试时间要求，我们可能在不另行通知的情况下撤销或限制其对 Ads API 的访问。

<div id="analytics-metrics-in-a-nutshell">
  ### 分析指标一览
</div>

* 所有分析指标在 24 小时后即会锁定且不再变动，`billed_charge_local_micro` 指标除外。
* `billed_charge_local_micro` 指标在数据返回后的最长 3 天内为预估值。
* 在 24 小时之后，该指标可能因超支抵扣（在指定 `end_time` 之后投放的广告）以及被认定为无效的可计费事件而减少。该指标在 24 小时后仅会发生轻微变化。
* 如需更多信息，请参阅 [Analytics](/zh/x-ads-api/analytics)。

<div id="fetching-real-time-non-segmented-data">
  ### 获取实时、未分段数据
</div>

* 始终同时提供 `start_time` 和 `end_time`。
* 不要获取早于 7 天的实体数据。
* （理想情况下）以 `HOUR` 粒度请求数据，因为你始终可以通过聚合将指标汇总为 `DAY` 和 `TOTAL` 粒度。
* （理想情况下）在 `line_items` 和 `promoted_tweets` 层级请求数据，因为你始终可以将这些指标聚合汇总，得到整个广告实体层级（即 campaign、funding instrument 或 account 层级）的总计。
* 在本地保存和存储分析指标的数值。
* 不要反复查询早于 30 天的数据。此类数据不会变化，应当本地存储。
* 所有未分段数据都是实时的，并且数据应在事件发生后的数秒内可用。
* 将转化指标和非转化指标分成不同的请求进行获取。

<div id="fetching-segmented-data">
  ### 获取分段数据
</div>

* 请参考上文“获取实时、非分段数据”的指南。以下是一些补充建议。
* 对于大多数分段数据类型，在某些情况下，数据在长达 1 小时内可能不完整。按 `INTERESTS` 分段的数据可能会延迟最长 12 小时。
* 由于这类信息的生成方式，分段数据在汇总后通常不会与非分段数据 100% 一致。

<div id="fetching-historical-data">
  ### 获取历史数据
</div>

* 在回填数据时（例如添加新的广告主账户），你可能需要将 `start_time` 和 `end_time` 拆分为较小的时间区间，多次发出请求。
* 将每次获取的数据限制在 30 天的时间窗口内。
* 对这些请求进行节流处理，并在一段时间内分散发送，以免耗尽这些获取操作的速率限制。

<div id="active-entities">
  ### 活跃实体
</div>

<div id="introduction">
  #### 简介
</div>

[Active Entities 端点](/zh/x-ads-api/analytics#get-stats-accounts-account-id-active-entities) 旨在与我们的[同步](/zh/x-ads-api/analytics#get-stats-accounts-account-id)和[异步](/zh/x-ads-api/analytics#asynchronous-analytics)分析端点配合使用，因为它提供了应为哪些广告系列请求分析数据的信息。它通过返回广告实体的详细信息以及其指标发生变化的时间来实现这一点。使用此端点将大大简化你的代码和分析数据获取逻辑。

本指南包含有关该端点及其数据源的说明和背景信息。它还提供了[使用指南](#usage)和一系列[请求示例](#example)，演示如何将 Active Entities 与我们的分析端点结合使用。[总结部分](#summary)对推荐方法进行了高层次概述。

<div id="data">
  #### 数据
</div>

每当广告实体的指标发生变化时，我们都会记录该变化的相关信息。这些变更事件会存储在按小时划分的时间桶中，既包含关于该实体的详细信息，也包含该变更所适用（生效）的时间。之所以需要后者，是因为变更事件的时间并不总是与其被记录的时间一致。账单调整是其中一个常见原因，但也可能还有其他原因。

<div id="endpoint">
  #### 端点
</div>

<div id="request">
  ### 请求
</div>

Active Entities 请求以广告账户为作用域，并且有三个必需的查询参数：`entity`、`start_time` 和 `end_time`。

`twurl -H ads-api.x.com "/11/stats/accounts/18ce54d4x5t/active_entities?entity=PROMOTED_TWEET&start_time=2019-03-05T00:00:00Z&end_time=2019-03-06T00:00:00Z"`

支持以下 `entity` 取值：`CAMPAIGN`、`FUNDING_INSTRUMENT`、`LINE_ITEM`、`MEDIA_CREATIVE`、`PROMOTED_ACCOUNT` 和 `PROMOTED_TWEET`。这反映了我们的分析端点所支持的实体类型。

`start_time` 和 `end_time` 的值必须使用 [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) 格式，并指定要查询的按小时划分的时间段。这些时间必须为整点。

此端点还支持三个可选参数，可用于过滤结果：`funding_instrument_ids`、`campaign_ids` 和 `line_item_ids`。这些参数可在广告层级的所有级别使用，并适用于任何指定的 `entity` 类型。

<div id="response">
  ### 响应
</div>

上述请求的 Active Entities 响应如下所示。

```json
    {
      "request": {
        "params": {
          "account_id": "18ce54d4x5t",
          "entity": "PROMOTED_TWEET",
          "start_time": "2019-03-05T00:00:00Z",
          "end_time": "2019-03-06T00:00:00Z"
        }
      },
      "data": [
        {
          "entity_id": "2r0wxw",
          "activity_start_time": "2019-03-04T20:55:20Z",
          "activity_end_time": "2019-03-05T03:43:56Z",
          "placements": [
            "ALL_ON_TWITTER"
          ]
        },
        {
          "entity_id": "2r30fn",
          "activity_start_time": "2019-03-05T08:11:08Z",
          "activity_end_time": "2019-03-05T14:40:59Z",
          "placements": [
            "ALL_ON_TWITTER",
            "PUBLISHER_NETWORK"
          ]
        }
      ]
    }
```

`data` 数组包含一个对象，表示在后续分析请求中应包含的每个实体。不应为此集合之外的 ID 请求分析数据。

每个对象包含四个字段：`entity_id`、`activity_start_time`、`activity_end_time` 和 `placements`。活动开始时间和结束时间表示相关实体变更事件适用的时间范围，因此决定了在后续分析请求中应指定的日期。`placements` 数组可以包含以下值：`ALL_ON_TWITTER`、`PUBLISHER_NETWORK`、`SPOTLIGHT` 和 `TREND`，用于指示对于给定实体 ID 应该请求哪些展示位置。

#### 用法

Active Entities 端点应当作为确定如何发起分析请求的依据。下面的使用指南旨在支持分析数据同步，使合作伙伴能够让其数据存储与 Twitter 保持同步。换句话说，它描述了如何执行定期安排的后台同步任务。

开发者必须做出两个决策。

1. 多久请求一次 active entities 信息，从而多久拉取一次分析数据。
2. 如何使用活动开始和结束时间来确定分析请求的 `start_time` 和 `end_time` 值。

这两点会在下面的两个小节中分别进行更为详细的讨论。

<div id="summary">
  ### 摘要
</div>

按如下方式使用 Active Entities 端点，以决定如何发出分析请求。在你已经决定多长时间请求一次 active entities 信息、从而多长时间拉取一次分析数据之后，再遵循下面的步骤。

1. 发出 Active Entities 请求。
2. 按 `placement` 拆分响应：为 `ALL_ON_TWITTER` 建立一组，为 `PUBLISHER_NETWORK` 建立一组，为 `SPOTLIGHT` 建立一组，为 `TREND` 建立一组。
3. 对于每个 placement 分组，执行以下操作。
   1. 提取实体 ID。
   2. 确定分析请求的 `start_time` 和 `end_time` 值。
      * 找到最小的 `activity_start_time`，将该值向下取整。
      * 找到最大的 `activity_end_time`，将该值向上取整。
   3. 发出分析请求。
      * 将实体 ID 分组为每批 20 个。
      * 使用第 3b 步中的 `start_time` 和 `end_time` 值。
      * 指定相应的 `placement` 值。
   4. 写入你的数据存储中。

有关使用 Python SDK 的示例，请参见 [active&#95;entities.py](https://github.com/xdevplatform/twitter-python-ads-sdk/blob/master/examples/active_entities.py)。

<div id="frequency">
  ### 频率
</div>

第一个问题的答案决定了在 Active Entities 请求中应使用的时间范围。例如，如果每小时请求一次 active entities 信息，则时间范围应为一小时。如果每天请求一次 active entities 信息，则时间范围应为一天。换句话说，应选择这样的时间范围：当前请求的 `start_time` 等于上一个请求的 `end_time`。

<Note>
  **Note**: 每个时间窗口只能请求一次。对同一时间窗口进行多次请求会导致不必要的分析请求。（下面有例外情况。）
</Note>

对于希望在一个小时内多次为&#95;当前&#95;小时请求分析数据的合作伙伴，同样适用这一模式——请求频率决定时间范围。下表展示了此场景下 Active Entities 请求的示例开始和结束时间戳。

|     |     |     |
| :--- | :--- | :--- |
| **Request time** | **`start_time` timestamp** | **`end_time` timestamp** |
| 00:15:00 | 00:00:00 | 00:15:00 |
| 00:30:00 | 00:15:00 | 00:30:00 |
| 00:45:00 | 00:30:00 | 00:45:00 |
| 01:00:00 | 00:45:00 | 01:00:00 |

鉴于变更事件的存储方式，上述四个 Active Entities 请求都会查询同一个按小时划分的桶，这对该用例来说是必要的。然而，在当前小时结束之后，就不应再查询这个小时桶。

<div id="activity-times">
  ### 活动时间
</div>

我们建议按以下方式处理活动开始时间和结束时间。在 Active Entities 响应中的所有对象中，找到最小的 `activity_start_time` 和最大的 `activity_end_time`。通过向下取整最小活动开始时间、向上取整最大活动结束时间来调整这些值。具体来说，将这两个时间戳的时、分、秒都设置为 0，并在结束时间上加一天，如下表所示。这些就是你在后续分析请求中应当指定的开始和结束时间。

|     |     |
| :--- | :--- |
| **最小、最大活动时间** | **推导时间** |
| 2019-03-04T20:55:20Z  <br />  <br />2019-03-05T14:40:59Z | 2019-03-04T00:00:00Z  <br />  <br />2019-03-06T00:00:00Z |

**注意**：务必包含将时、分、秒都设置为 0 的时间戳。否则，如果只传入日期，我们会假定你要请求从广告账户所属时区的午夜开始到午夜结束的分析数据，这可能不是你想要的。例如，如果最小活动开始时间为 2019-02-28T01:30:07Z，而对于时区偏移为 -08:00:00 的广告账户省略了时间戳，那么分析请求将遗漏 01:30 到 08:00 之间发生的更改。

或者，如果你更愿意只针对返回的活动时间窗口请求分析数据，而不扩展到完整的整天区间，也可以这样做。采用这种方法，推导出的开始和结束时间分别为 2019-03-04T20:00:00Z 和 2019-03-05T15:00:00Z。（请注意，如果你在分析请求中指定了 `DAY` 粒度，则不接受此类时间范围。）

<div id="asynchronous-analytics">
  ### 异步分析
</div>

<div id="introduction">
  #### 简介
</div>

异步分析端点允许合作伙伴和广告主通过提交创建请求来获取指标，这些请求由服务器以异步方式处理。（我们将这些请求称为异步分析“作业”。）采用这种方式，客户端连接无需在请求被完成之前一直保持打开。

这些端点与其同步对应端点一样，允许合作伙伴和广告主请求广告系列效果的详细统计数据。它们支持为账户、资金工具、广告系列、广告单元、推广推文以及媒体创意请求数据。与同步端点的区别在于，异步分析端点支持更长的日期范围（最长 90 天），并支持分段统计。关于两者差异的更多信息，请参见我们的 [Analytics 概览](/zh/x-ads-api/analytics) 页面。

与同步端点不同，速率限制是基于给定账户的并发作业数量。换句话说，它基于在某一时刻可以处于处理中状态的作业数量。我们在广告账户级别统计这一数量。

<div id="usage">
  #### 使用方法
</div>

使用异步分析端点获取广告系列指标是一个包含多个步骤的流程。它包括创建作业、检查作业是否已完成处理，以及最后下载数据。数据文件必须先解压缩。以下列出了四个具体步骤。

1. 使用 [POST stats/jobs/accounts/:account&#95;id](/zh/x-ads-api/analytics#asynchronous-analytics) 端点创建作业。
2. 以固定的时间间隔向 [GET stats/jobs/accounts/:account&#95;id](/zh/x-ads-api/analytics#asynchronous-analytics) 端点发起请求，以确定作业是否已完成处理。
3. 一旦作业完成处理，下载数据文件。
4. 解压数据文件。

数据文件中返回的响应对象，其 JSON 架构与同步分析端点的响应相同。

细分的广告系列指标只能通过异步分析端点获取。广告系列指标可以按位置、性别、兴趣、关键词等进行细分。有关完整选项列表，请参阅 [Metrics and Segmentation](/zh/x-ads-api/analytics#metrics-and-segmentation) 页面。要请求细分指标，请在创建作业时使用 `segmentation_type` 请求参数。

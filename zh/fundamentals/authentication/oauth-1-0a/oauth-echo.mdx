<div id="oauth-echo">
  ### OAuth Echo
</div>

OAuth Echo 是一种在与 API 交互时，将 OAuth 授权安全地委托给第三方的机制。

此交互中涉及四方：

* **用户（User）**，即通过某个已授权的 X 应用使用 X 的人
* **消费者（Consumer）**，即尝试与第三方媒体提供方（例如照片分享网站）交互的 X 应用
* **委托方（Delegator）**，即第三方媒体提供方
* **服务提供方（Service Provider）**，也就是 X 本身
     

本质上，是代表某个应用和用户，准备一个由委托方向 X API 发送的请求。将原本应作为已签名 OAuth 请求发送的内容放入 HTTP 头部中，并让委托方在完成中间处理操作之后，将该请求发送给 X。

例如：用户想要上传一张照片。消费者会通过 POST 调用委托方的 upload 接口。POST 中应包含图片，同时还应在 HTTP 头部中包含以下两个额外字段：

* `x-auth-service-provider` — 实际上，这是身份委托应被发送到的领域（realm）——在 X 的场景下，将其设置为 https://api.x.com/1.1/account/verify_credentials.json。基于 iOS5 的 X 集成会在该 URL 上添加一个额外的 `application_id` 参数，该参数也会用于计算 `x-verify-credentials-authorization` 中使用的 `oauth_signature`。
* `x-verify-credentials-authorization` — 消费者应创建所有必要的 OAuth 参数，以便它可以在 HTTP 头部中使用 OAuth 调用 https://api.x.com/1.1/account/verify_credentials.json（例如，它应类似于：`OAuth oauth_consumer_key=”...”, oauth_token=”...”, oauth_signature_method=”...”, oauth_signature=”...”, oauth_timestamp=”...”, oauth_nonce=”...”, oauth_version=”...”`）。
     

请记住，整个交互过程必须在 `oauth_timestamp` 仍然有效的时间范围内完成。

或者，也可以不在头部发送这两个参数，而是在 POST 中以 `x_auth_service_provider` 和 `x_verify_credentials_authorization` 的形式发送——在这种情况下，请记得在 OAuth 签名基字符串中对这些参数进行转义并包含进去——与在任意请求中对参数进行编码的方式类似。为了尽可能将各个操作解耦，最好使用 HTTP 头部。

此时，委托方（Delegator）的目标是在保存媒体之前，验证用户确实是其声称的身份。一旦委托方通过其上传方法接收到上述所有数据，应临时存储该图片，然后构造一次调用，访问 `x-auth-service-provider` 头中指定的端点——在本例中为 https://api.x.com/1.1/account/verify_credentials.json，并使用消费者在 `x-verify-credentials-authorization` 头中提供的相同 OAuth 身份验证头部。
 

<div id="oauth-echo-best-practices">
  #### OAuth Echo 最佳实践
</div>

使用 `x-auth-service-provider` 提供的 URL 来执行查找，_不要_ 使用硬编码的值。例如，Apple iOS 会在所有 OAuth 请求中添加一个额外的 application_id 参数，并且在 OAuth Echo 的各个阶段都应保留该参数的存在。

在 OAuth 授权部分，从 x-verify-credentials-authorization 中获取头部中的值，并将其作为单独的 Authorization 头，用于发往服务提供方的调用。为稳妥起见，确认 `x-auth-service-provider` 中的值是否为预期值。

* 如果服务提供方返回 HTTP 200，则一切正常。Delegator 应永久存储该图像，生成一个 URL，并将其返回。
* 如果服务提供方未返回 HTTP 200，则丢弃该图像，然后向 Consumer 返回一个错误。

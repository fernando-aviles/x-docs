<div id="oauth-echo">
  ### OAuth Echo
</div>

OAuth Echo 是一种在与 API 交互时，将 OAuth 授权安全地委托给第三方的机制。

在这一交互中涉及四方：

* **User（用户）** 使用某个已授权的 X 应用访问 X
* **Consumer（消费者）**，即试图与第三方媒体提供方（例如照片分享网站）交互的 X 应用
* **Delegator（委托方）**，即第三方媒体提供方
* **Service Provider（服务提供方）**，也就是 X 本身
     

本质上，你需要为 Delegator 准备一个请求，由它代表某个应用和用户发送到 X API。将原本应该作为已签名 OAuth 请求发送的内容放入一个 HTTP 头中，并在完成中间操作后，要求 Delegator 将该请求发送给 X。

例如：User 想要上传一张照片。Consumer 将使用 POST 向 Delegator 调用上传接口。POST 请求应包含图片，但它还应在 HTTP 头中包含两个额外字段：

* `x-auth-service-provider` —— 实际上，这表示应将身份委托发送到的领域（realm）——在 X 的场景下，将其设置为 https://api.x.com/1.1/account/verify_credentials.json。基于 iOS5 的 X 集成会在该 URL 中添加一个额外的 `application_id` 参数，该参数也会用于计算 `x-verify-credentials-authorization` 中使用的 `oauth_signature`。
* `x-verify-credentials-authorization` —— Consumer 应创建调用 https://api.x.com/1.1/account/verify_credentials.json 所需的全部 OAuth 参数，并将其放入 HTTP 头中（例如，其形式应类似于：OAuth oauth\_consumer\_key=”...”, oauth\_token=”...”, oauth\_signature\_method=”...”, oauth\_signature=”...”, oauth\_timestamp=”...”, oauth\_nonce=”...”, oauth_version=”...”）。
     

请记住，整个交互过程需要在 `oauth_timestamp` 仍然有效的时间范围内完成。

或者，可以不在头部发送这两个参数，而是在 POST 中以 `x_auth_service_provider` 和 `x_verify_credentials_authorization` 的形式发送——在这种情况下，请记得在 OAuth 签名基字符串中对这些参数进行转义并包含进去——这与在任何请求中对参数进行编码类似。为了尽可能将各个操作解耦，最好使用 HTTP 头。

此时，Delegator 的目标是在保存媒体之前，验证 User 是否确为其所声称的身份。一旦 Delegator 通过其上传方法接收到上述所有 data，它应临时存储图像，然后构造一次调用，请求 `x-auth-service-provider` 头中指定的 endpoint——在本例中是 https://api.x.com/1.1/account/verify_credentials.json，并使用 Consumer 在 `x-verify-credentials-authorization` 头中提供的同一 OAuth 认证头。
 

<div id="oauth-echo-best-practices">
  #### OAuth Echo 最佳实践
</div>

使用 `x-auth-service-provider` 提供的 URL 来进行查询，_而不是_ 使用硬编码的值。比如，在 Apple iOS 中，所有 OAuth 请求都会增加一个额外的 `application_id` 参数，并且在 OAuth Echo 的每个阶段都应该保留该参数。

在 OAuth 授权部分，从 `x-verify-credentials-authorization` 中获取头部的值，并在向服务提供方发起调用时，将其放入单独的 Authorization 头部中。为保险起见，请确认 `x-auth-service-provider` 中的值符合预期。

* 如果服务提供方返回 HTTP 200，则说明一切正常。Delegator 应永久存储该图像、生成一个 URL，并将其返回。
* 如果服务提供方未返回 HTTP 200，则丢弃该图像，然后向 Consumer 返回一个错误。

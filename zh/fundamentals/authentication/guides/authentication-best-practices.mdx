你的 API 密钥和 token 需要被格外严密地保护。 

这些凭证直接关联到你的 [developer App](/zh/resources/fundamentals/developer-apps) 以及那些已授权你可代表其发起请求的 X 账号。如果你的密钥被泄露，恶意第三方可能会利用它们代表你的开发者 App 或其授权用户向 X 的各个端点发起请求，这可能会导致你意外触发速率限制、耗尽你付费获得的访问配额，甚至导致你的开发者 App 被暂停。

以下各节介绍了在管理 API 密钥和 token 时应当考虑的最佳实践。

<div id="regenerate-api-keys-and-tokens">
  ## 重新生成 API 密钥和令牌
</div>

如果你认为自己的 API 密钥已经暴露，应按照以下步骤重新生成 API 密钥：

1. 访问 [Developer Console 的 &quot;Apps&quot; 页面](https://developer.x.com/en/portal/projects-and-apps.html)。
2. 点击相关 App 旁边的 &quot;Keys and tokens&quot; 图标 (🗝 )。
3. 点击你希望重新生成的那组密钥和令牌旁边的 &quot;Regenerate&quot; 按钮。 

如果你更希望以编程方式重新生成 Access Tokens 或 Bearer Tokens，则可以使用我们的认证端点来完成。

* 如果你希望重新生成 Access Tokens，必须先使用 [POST oauth/invalidate&#95;token](/zh/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token) 端点使你的令牌失效，然后使用 [3-legged OAuth flow](/zh/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens) 重新生成你的令牌。
* 如果你希望重新生成 Bearer Token，必须先使用 [POST oauth2/invalidate&#95;token](/zh/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token) 端点使你的令牌失效，然后使用 [POST oauth2/token](/zh/resources/fundamentals/authentication/api-reference#post-oauth2-token) 端点重新生成你的令牌。

<div id="having-a-central-file-for-your-secrets">
  ## 为机密信息准备一个集中管理的文件
</div>

使用一个文件（例如 .env 文件或其他类型的 .yaml 文件）来集中存放你的机密配置是一种可能有用的做法，但务必确保配置了严格的 .gitignore 文件，以防不小心将这些内容提交到 Git 仓库中。 

<div id="environment-variables">
  ## 环境变量
</div>

在代码中使用环境变量会很有帮助。 

下面是一个用 Python 编写的示例：

```python
import os

consumer_key = os.environ.get("CONSUMER_KEY")

consumer_secret = os.environ.get("CONSUMER_SECRET")
```

在终端中，你可以输入类似下面这样的命令：

```bash
export CONSUMER_KEY='xxxxxxxxxxxxxxxxxxx'
export CONSUMER_SECRET='xxxxxxxxxxxxxxxxxxxxxxx'
```

<div id="source-code-and-version-control">
  ## 源代码和版本控制
</div>

开发者最常见的安全错误之一，是将 API 密钥和令牌提交到源代码中，并推送到 GitHub、Bitbucket 等可访问的版本控制系统。许多此类代码仓库是公开可访问的。这个错误在公共代码仓库中发生得如此频繁，以至于出现了专门抓取 API 密钥的高收益机器人。

* 使用服务器环境变量。通过将 API 密钥存储在环境变量中，可以将它们从代码和版本控制中隔离开来。这样也便于你在不同环境中轻松使用不同的密钥。
* 使用从源代码管理中排除的配置文件。将文件名添加到你的 [.gitignore](https://git-scm.com/docs/gitignore) 文件中，以防止该文件被版本控制跟踪。
* 如果你在已经使用版本控制之后才从代码中移除 API 密钥，那么通过访问代码库的先前版本，这些 API 密钥很可能仍然可以被获取。请重新生成你的 API 密钥，如下一节所述。

<div id="databases">
  ## 数据库
</div>

如果需要在数据库中存储访问令牌，请注意以下几点：

* 限制对数据库的访问，使访问令牌只能被令牌所有者读取。
* 限制对存放访问令牌的数据库表的编辑/写入权限——这应通过密钥管理系统自动化实现。
* 在将访问令牌存入任何数据存储之前先对其进行加密。

<div id="password-management-tools">
  ## 密码管理工具
</div>

像 1Password 或 LastPass 这样的密码管理工具有助于将你的密钥和访问令牌保存在安全的位置。你可能会希望不要在团队共享的密码管理工具中共享这些内容。

<div id="web-storage-cookies">
  ## Web storage &amp; cookies
</div>

有两种 Web 存储机制：LocalStorage 和 SessionStorage。它们是作为对 Cookies 的改进而提出的，因为 Web 存储的容量远高于 Cookie 存储。不过，这几种存储选项各有不同的优缺点。
 

**Web Storage: LocalStorage**

存储在本地 Web 存储中的任何内容都是持久的。这意味着这些数据会一直保留，直到被显式删除。根据你的项目需求，你可能会认为这是一个优点。不过，在使用 LocalStorage 时需要谨慎，因为对数据所做的任何更改或新增，在今后所有访问该网页时都将可用。我们通常不建议使用 LocalStorage，尽管可能会有少数例外情况。如果你决定使用 LocalStorage，需要注意它遵循同源策略，因此此处存储的所有数据只能通过同一来源访问。使用 LocalStorage 的一个额外性能优势是可以减少客户端与服务器之间的流量，因为在每个 HTTP 请求中不必将这些数据发送回服务器。
 

**Web Storage: SessionStorage**

SessionStorage 与 LocalStorage 类似，但关键区别在于 SessionStorage 不是持久存储。一旦用于向 SessionStorage 写入数据的窗口（或标签页，取决于你使用的浏览器）被关闭，这些数据就会丢失。这有助于在用户会话期间限制对令牌的读取访问。从安全角度考虑时，相比 LocalStorage，通常更推荐使用 SessionStorage。与 LocalStorage 一样，SessionStorage 同样受益于对同源策略的支持以及客户端与服务器之间流量的减少。
 

**Cookies**

Cookies 是存储会话数据的更传统方式。你可以为每个 cookie 设置过期时间，从而更容易撤销及限制访问。然而，使用 cookies 时，客户端与服务器之间的流量肯定会增加，因为在每个 HTTP 请求中都会将数据发送回服务器。如果你决定使用 cookies，就需要防范会话劫持。默认情况下，cookies 会通过 HTTP 明文发送，这会使其内容容易受到数据包嗅探和/或中间人攻击（攻击者可能会修改你的流量）。你应始终强制使用 HTTPS 来保护传输中的数据。这将为你提供机密性、完整性（数据完整性）以及认证。然而，如果你的 Web 应用或站点既可通过 HTTP 访问，也可通过 HTTPS 访问，那么你还需要在 cookie 上使用“Secure”标志。这将防止攻击者向用户发送你站点的 HTTP 版本链接，并监听由此产生的 HTTP 请求。

在使用 cookies 时，对抗会话劫持的另一种次要防御措施，是在执行任何高风险操作之前再次验证用户身份。另一个可以考虑用来提升 cookie 安全性的标志是“HttpOnly”标志。该标志告诉浏览器，相关 cookie 只能被服务器访问，而不能被客户端脚本访问。任何由客户端脚本发起的访问尝试都会被该标志禁止，从而有助于防御大多数跨站脚本（XSS）攻击。

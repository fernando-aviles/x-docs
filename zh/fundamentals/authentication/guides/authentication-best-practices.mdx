你的 API key 和 token 应当被非常谨慎地保护。 

这些凭证直接关联到你的 [developer App](/zh/resources/fundamentals/developer-apps)，以及那些已授权你代表其发起请求的 X 账号。如果你的 key 被泄露，恶意行为者可能会利用它们，代表你的 developer App 或其授权用户向 X 的各个 endpoint 发起请求，这可能会导致你意外触发速率限制、耗尽你的付费访问配额，甚至导致你的 developer App 被封禁。

以下各节介绍在管理你的 API key 和 token 时应当考虑的最佳实践。

<div id="regenerate-api-keys-and-tokens">
  ## 重新生成 API 密钥和令牌
</div>

如果你认为 API 密钥已泄露，应按照以下步骤重新生成 API 密钥：

1. 前往 [开发者控制台的 “Apps” 页面](https://developer.x.com/en/portal/projects-and-apps.html)。
2. 点击相关 App 旁边的 “Keys and tokens” 图标 (🗝 )。
3. 点击你希望重新生成的那一组密钥和令牌旁边的 “Regenerate” 按钮。 

如果你更希望通过程序方式重新生成 Access Tokens 或 Bearer Tokens，可以通过我们的身份验证端点来完成。

* 如果你想重新生成 Access Tokens，必须先使用 [POST oauth/invalidate&#95;token](/zh/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token) 端点使令牌失效，然后通过 [3-legged OAuth flow](/zh/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens) 重新生成令牌。
* 如果你想重新生成 Bearer Token，必须先使用 [POST oauth2/invalidate&#95;token](/zh/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token) 端点使令牌失效，然后通过 [POST oauth2/token](/zh/resources/fundamentals/authentication/api-reference#post-oauth2-token) 端点重新生成令牌。

<div id="having-a-central-file-for-your-secrets">
  ## 用于集中管理机密信息的文件
</div>

使用一个文件（例如 `.ENV` 文件或其他类型的 `.yaml` 文件）来存放你的机密信息是一个可能有帮助的做法，但一定要配置好健壮的 `.gitignore` 文件，以防止你不小心将这些内容提交到 git 仓库中。 

<div id="environment-variables">
  ## 环境变量
</div>

编写利用环境变量的代码可能会很有用。 

下面是一个使用 Python 编写的示例：

```python
import os

consumer_key = os.environ.get("CONSUMER_KEY")

consumer_secret = os.environ.get("CONSUMER_SECRET")
```

在终端中，你可以输入类似下面的命令：

```bash
export CONSUMER_KEY='xxxxxxxxxxxxxxxxxxx'
export CONSUMER_SECRET='xxxxxxxxxxxxxxxxxxxxxxx'
```

<div id="source-code-and-version-control">
  ## 源代码和版本控制
</div>

开发者最常见的安全错误之一，是将 API key 和 token 提交到 GitHub、BitBucket 等可访问的版本控制系统中的源代码里。许多这类代码仓库都是公开可访问的。这种错误在公共代码仓库中出现得如此频繁，以至于已经出现了专门抓取 API key 以牟利的机器人。

* 使用服务端环境变量。通过将 API key 存储在环境变量中，可以将它们与代码和版本控制隔离开来。这也使你可以更轻松地为不同环境使用不同的 key。
* 使用一个排除在源码管理之外的配置文件。将该文件名添加到你的 [.gitignore](https://git-scm.com/docs/gitignore) 文件中，以防止该文件被版本控制追踪。
* 如果你在启用版本控制之后才从代码中移除 API key，那么通过访问代码库的历史版本，这些 API key 很可能仍然可以被获取。请重新生成你的 API key，如下一节所述。

<div id="databases">
  ## 数据库
</div>

如果需要在数据库中存储访问令牌，请注意以下几点：

* 限制对数据库的访问权限，确保访问令牌只能被令牌所有者读取。
* 限制对存放访问令牌的数据库表的编辑/写入权限——应通过密钥管理系统自动完成。
* 在将访问令牌写入任何数据存储之前，先对其进行加密。

<div id="password-management-tools">
  ## 密码管理工具
</div>

1Password 或 LastPass 等密码管理工具有助于将你的密钥和令牌保存在安全的位置。你可能会希望避免在团队共用的密码管理工具中存放或共享这些密钥和令牌。

<div id="web-storage-cookies">
  ## Web storage &amp; cookies
</div>

有两种类型的 Web 存储：LocalStorage 和 SessionStorage。它们是对 Cookie 使用方式的改进，因为 Web 存储的容量远高于 Cookie 存储。不过，这几种存储方式各自都有不同的优点和缺点。
 

**Web Storage：LocalStorage**

存储在本地 Web 存储中的任何内容都是持久的。这意味着这些数据会一直保留，直到被显式删除。根据项目需求的不同，你可能会认为这是一个优点。不过，在使用 LocalStorage 时需要格外谨慎，因为对数据所做的任何更改或新增，在后续访问同一网页时都会继续起作用。我们通常不建议使用 LocalStorage，尽管在某些情况下会有少数例外。如果你决定使用 LocalStorage，值得注意的是它遵循同源策略，因此此处存储的所有数据只能通过相同的源（origin）访问。使用 LocalStorage 的一个额外性能优势是可以减少客户端与服务器之间的流量，因为数据不需要随每次 HTTP 请求发送回服务器。
 

**Web Storage：SessionStorage**

SessionStorage 与 LocalStorage 类似，但关键区别在于 SessionStorage 不是持久的。一旦用于向 SessionStorage 写入数据的窗口（或标签页，取决于所使用的浏览器）被关闭，数据就会丢失。这对于将令牌的读取权限限制在某个用户会话内非常有用。从安全角度考虑时，通常 SessionStorage 比 LocalStorage 更可取。与 LocalStorage 一样，SessionStorage 同样受益于同源策略的支持以及减少客户端与服务器之间流量的优势。
 

**Cookies**

Cookies 是一种更传统的会话数据存储方式。你可以为每个 cookie 设置过期时间，从而便于撤销以及限制访问。然而，在使用 cookies 时，客户端与服务器之间的流量肯定会增加，因为数据会在每次 HTTP 请求时被发送回服务器。如果你决定使用 cookies，就需要防范会话劫持。默认情况下，cookies 会以明文形式通过 HTTP 发送，这会使其内容容易受到数据包嗅探和/或中间人攻击的威胁，攻击者可能会修改你的流量。你应始终强制使用 HTTPS 来保护传输中的数据。这将为数据提供机密性、完整性以及身份验证。然而，如果你的 Web 应用或站点可以同时通过 HTTP 和 HTTPS 访问，你还应在 cookie 上使用 `Secure` 标志。这将防止攻击者向用户发送站点的 HTTP 版本链接并窃听由此产生的 HTTP 请求。

在使用 cookies 时，对抗会话劫持的另一种次级防御措施是，在执行任何高影响操作之前再次验证用户身份。为了进一步提升 cookies 的安全性，还可以考虑使用 `HttpOnly` 标志。此标志会告诉浏览器，相关的 cookie 只能由指定的服务器访问。任何由客户端脚本发起的访问尝试都会被该标志禁止，从而有助于防御大多数跨站脚本（XSS）攻击。

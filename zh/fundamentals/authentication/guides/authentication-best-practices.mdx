你的 API 密钥和令牌必须严加保护。 

这些凭证直接关联到你的 [开发者 App](/zh/resources/fundamentals/developer-apps) 以及那些授权你代表其发起请求的 X 账号。如果你的密钥遭到泄露，恶意方可能使用它们代表你的开发者 App 或其已授权用户向 X 的端点发起请求，这可能会导致你意外触发速率限制、耗尽你的付费访问配额，甚至导致你的开发者 App 被暂停。

以下各节介绍在管理 API 密钥和令牌时应当遵循的最佳实践。

<div id="regenerate-api-keys-and-tokens">
  ## 重新生成 API 密钥和令牌
</div>

如果你认为自己的 API 密钥已泄露，应按照以下步骤重新生成 API 密钥：

1. 访问 [开发者控制台的 “Apps” 页面](https://developer.x.com/en/portal/projects-and-apps.html)。
2. 点击相关 App 旁边的 “Keys and tokens” 图标 (🗝)。
3. 点击想要重新生成的那组 keys 和 tokens 旁边的 “Regenerate” 按钮。 

如果你更倾向于以编程方式重新生成 Access Tokens 或 Bearer Tokens，可以使用我们的认证端点来实现。

* 如果你想重新生成 Access Tokens，必须先使用 [POST oauth/invalidate&#95;token](/zh/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token) 端点使现有 tokens 失效，然后通过 [3-legged OAuth flow](/zh/resources/fundamentals/authentication/oauth-1-0a/obtaining-user-access-tokens) 重新生成 tokens。
* 如果你想重新生成 Bearer Token，必须先使用 [POST oauth2/invalidate&#95;token](/zh/resources/fundamentals/authentication/api-reference#post-oauth2-invalidate-token) 端点使现有 token 失效，然后通过 [POST oauth2/token](/zh/resources/fundamentals/authentication/api-reference#post-oauth2-token) 端点重新生成 token。

<div id="having-a-central-file-for-your-secrets">
  ## 为机密信息准备一个统一存放的文件
</div>

使用一个文件（例如 .env 文件或任意类型的 .yaml 文件）来存放你的机密信息，是一种可能有帮助的做法，但务必确保配置一个严格的 .gitignore 文件，以防不小心将这些内容提交到 git 仓库中。 

<div id="environment-variables">
  ## 环境变量
</div>

编写利用环境变量的代码可能会很有帮助。 

下面是一个用 Python 编写的示例：

```python
import os

consumer_key = os.environ.get("CONSUMER_KEY")

consumer_secret = os.environ.get("CONSUMER_SECRET")
```

在终端里，你可以输入类似下面这样的命令：

```bash
export CONSUMER_KEY='xxxxxxxxxxxxxxxxxxx'
export CONSUMER_SECRET='xxxxxxxxxxxxxxxxxxxxxxx'
```

<div id="source-code-and-version-control">
  ## 源代码与版本控制
</div>

开发者最常见的安全错误，是在 GitHub 和 BitBucket 等版本控制系统中的源代码里提交了 API key 和 token。许多这类代码仓库是公开可访问的。这种错误在公共代码仓库中出现得如此频繁，以至于出现了专门用来抓取 API key 的牟利型 bot。

* 使用服务器环境变量。通过将 API key 存储在环境变量中，可以将它们与代码和版本控制隔离开来。这也便于在不同环境中使用不同的 key。
* 使用从源代码管理中排除的配置文件。将文件名添加到你的 [.gitignore](https://git-scm.com/docs/gitignore) 文件中，以避免该文件被版本控制系统跟踪。
* 如果你在已经使用版本控制之后才从代码中移除了 API key，那么仍然可以通过访问代码库的先前版本来获取这些 API key。请重新生成你的 API key，具体方式见下一节。

<div id="databases">
  ## 数据库
</div>

如果你需要在数据库中存储访问令牌，请注意以下事项：

* 限制对数据库的访问权限，确保只有令牌的所有者才能读取相应的访问令牌。
* 限制对存放访问令牌的数据库表的编辑/写入权限——应通过密钥管理系统自动完成。
* 在将访问令牌存储到任何数据存储系统之前先对其进行加密。

<div id="password-management-tools">
  ## 密码管理工具
</div>

诸如 1Password 或 LastPass 等密码管理工具有助于将你的密钥和 token 安全地保存在一个安全的位置。你可能会希望避免将这些内容存放在团队共用的密码管理工具中。

<div id="web-storage-cookies">
  ## Web 存储与 Cookie
</div>

Web 存储有两种类型：`LocalStorage` 和 `SessionStorage`。它们是为改进 Cookie 的使用而引入的，因为 Web 存储的容量远大于 Cookie 存储。不过，这几种存储选项各自都有不同的优缺点。
 

**Web Storage：LocalStorage**

存储在本地 Web 存储中的任何内容都是持久的。这意味着这些数据会一直存在，直到被显式删除为止。根据你的 Project 需求，你可能会认为这是一个优点。不过，在使用 `LocalStorage` 时需要谨慎，因为对数据所做的任何更改或新增，在今后所有访问该网页时都会生效。我们通常并不推荐使用 `LocalStorage`，尽管也可能会有少数例外情况。如果你决定使用 `LocalStorage`，需要了解它支持同源策略，因此存储在这里的所有数据只能通过相同的源来访问。使用 `LocalStorage` 的一个额外性能优势是可以减少客户端与服务器之间的流量，因为每次 HTTP 请求时不必再把这些数据发送回服务器。
 

**Web Storage：SessionStorage**

`SessionStorage` 与 `LocalStorage` 类似，但关键区别在于 `SessionStorage` 不是持久的。一旦用于写入 `SessionStorage` 的窗口（或标签页，取决于你使用的浏览器）被关闭，其中的数据就会丢失。这有助于在单个用户会话中限制对令牌的读取访问。从安全角度考虑，`SessionStorage` 通常比 `LocalStorage` 更可取。与 `LocalStorage` 一样，同源策略支持以及减少客户端与服务器之间流量的优势，同样适用于 `SessionStorage`。
 

**Cookies**

Cookies 是存储会话数据的更传统方式。你可以为每个 cookie 设置过期时间，从而更容易撤销和限制访问。不过，使用 cookies 时客户端与服务器之间的流量肯定会增加，因为这些数据会在每个 HTTP 请求中被发送回服务器。如果你决定使用 cookies，就需要防范会话劫持。默认情况下，cookies 会通过 HTTP 以明文方式发送，这使得其内容容易受到数据包嗅探和/或中间人攻击的威胁，攻击者可以在其中篡改你的流量。你应始终强制使用 HTTPS 来保护传输中的数据。这将为你提供数据的机密性、完整性以及认证。然而，如果你的 Web 应用或网站同时可以通过 HTTP 和 HTTPS 访问，你还需要在 cookie 上使用 `Secure` 标志。这样可以防止攻击者向用户发送你站点的 HTTP 版本链接，并窃听由此产生的 HTTP 请求。

在使用 cookies 时，防御会话劫持的另一种辅助措施，是在执行任何高影响操作之前再次验证用户身份。另一个可以用来提升 cookie 安全性的标志是 `HttpOnly` 标志。该标志会告知浏览器，相关 cookie 只能从指定的服务器访问。任何由客户端脚本发起的访问尝试都会被此标志禁止，从而有助于防范大多数跨站脚本（XSS）攻击。
